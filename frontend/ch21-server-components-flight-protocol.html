Server Components & React Flight Protocol

"What are React Server Components? How does the React Flight protocol stream component payloads?"
Key Takeaway: Server Components run exclusively on the server, ship zero JavaScript to the client for their own code, and can access server-only resources (databases, filesystems, secrets) directly. They don't render to HTML strings the way traditional SSR does — they serialize to a custom streaming wire format (the Flight protocol) describing a tree of element descriptors, which the client reconstructs into real React elements, interleaving Client Component "holes" that hydrate normally. The entire model is a composition problem: Server Components can render Client Components, but Client Components cannot import Server Components — they can only receive them as opaque children.

Interviewer's Intent

What the interviewer is really testing
This question tests three capabilities simultaneously:
  • Precision about what RSC actually is: can you distinguish "runs on the server" from "renders to an HTML string" — the single most common conceptual error candidates make about Server Components?
  • Composition model fluency: do you know why a Server Component can render a Client Component but not vice versa, and how to correctly pass server-fetched data into client interactivity despite that constraint?
  • Production trade-off awareness: can you explain when RSC helps (large dependency trees moved off the client bundle, direct backend access, reduced client-server waterfalls) versus when it adds complexity (two rendering environments, cache invalidation, mental model overhead) without a clear win?
Red flags for interviewers: saying "Server Components are just SSR" (conflates a static, one-time render output with an interactive streaming component model); not knowing that Server Components re-render on the server on every navigation/refetch, not once at build time; claiming Server Components can use useState or useEffect (they cannot — they have no client lifecycle at all).

60-Second Answer

Structured response for time-pressured interviews

React Server Components (RSC) are components that execute exclusively on the server (or at build time), never ship their own code to the browser, and can directly access server-only resources — a database client, the filesystem, environment secrets — without an API layer in between. They render into a serialized description of the resulting UI tree, not an HTML string; this format (the React Flight protocol) is streamed to the client in chunks as data becomes available, letting parts of the page appear progressively rather than waiting for everything to resolve.

The composition rule that defines the whole model: Server Components can import and render Client Components (marked with "use client") directly. Client Components cannot import Server Components — because a client bundle can't contain server-only code — but a Server Component can be passed into a Client Component as children/props, since by that point it's already been rendered into serializable output, not live server code.

Why this matters in practice: heavy dependencies (a markdown parser, a date library, a charting library used only for server-side data transformation) never reach the client bundle if they're only used inside Server Components — reducing bundle size without manual code-splitting. Combined with Suspense, each Server Component can stream in independently, avoiding the "wait for the slowest fetch" problem of traditional SSR.

Every component is a Server Component by default in a framework that supports RSC (e.g. Next.js App Router) — you opt into the client runtime explicitly with a directive, not the other way around. This default is deliberate: it pushes you toward shipping less JavaScript unless a component specifically needs interactivity.

"use client" / "use server" Directives

Boundary markers, not runtime toggles 
// This file, and everything it imports, is bundled for the CLIENT.
// It becomes the boundary: everything above this component in the tree
// can be a Server Component; this component and everything it renders
// beneath it runs in the client's React runtime (with hydration).
'use client';

import { useState } from 'react';

export function LikeButton({ initialCount }) {
  const [count, setCount] = useState(initialCount);
  return <button onClick={() => setCount((c) => c + 1)}>{count} likes</button>;
}
// Marks a function as callable FROM the client, but executed ON the server —
// this is what powers Server Actions (form submissions, mutations)
'use server';

export async function likePost(postId) {
  await db.posts.update(postId, { $inc: { likes: 1 } });
}
"use client" marks a boundary, not the component itself as "client-only forever." A component marked "use client" is still rendered once on the server as part of the initial HTML/Flight payload (for fast first paint), then hydrated in the browser — it isn't skipped server-side, it's just bundled and re-executed on the client after hydration, unlike a pure Server Component which never ships its code to the client at all.

Zero-Bundle-Size Server Components

What "zero bundle size" actually means, mechanically

When a bundler (webpack, Turbopack, Rollup via a framework's RSC integration) builds the client bundle, it treats "use client" files as bundle entry points and everything else (the default, Server Component graph) as excluded from the client build entirely — not tree-shaken after the fact, but never included in the client compilation graph in the first place.

// This heavy markdown parser (and its dependencies) is only ever imported
// by a Server Component — it NEVER appears in the client JS bundle,
// regardless of its size, because this file is never part of the client build.
import { marked } from 'marked'; // ~40KB, zero client cost here

export async function ArticleBody({ slug }) {
  const raw = await db.articles.getContent(slug);
  const html = marked.parse(raw);
  return <div dangerouslySetInnerHTML={{ __html: html }} />;
}
Contrast with traditional code-splitting: React.lazy/dynamic import() still ship the code to the client eventually (just deferred until needed) — it's still part of the client bundle graph. A Server Component's dependencies are excluded from that graph entirely; there's no client-side loading state to manage for them because they never load client-side at all.

React Flight Protocol — Wire Format

Not HTML, not JSON — a streamable element-description format

When Server Components render, the result isn't serialized to an HTML string (that's a separate, additional step for the initial page load). It's serialized to the Flight format: a stream of newline-delimited, indexed rows, each describing either a React element, a reference to a Client Component module (to be resolved and hydrated on the client), or a chunk of resolved data.

0:["$","div",null,{"className":"article","children":["$","h1",null,{"children":"Hello"}]}]
1:{"module":"./LikeButton.client.js","name":"LikeButton"}
2:["$","@1",null,{"initialCount":42}]

Row 0 describes a plain host element tree (server-rendered content, inlined directly). Row 1 is a Client Reference — a pointer to a client module the browser must separately fetch and execute; it is not the component's code, just a reference to where to find it. Row 2 instantiates that client reference (@1) with props, exactly where the LikeButton was rendered inside the server tree.

Why streaming, row-by-row, matters: the client doesn't need the entire payload before it can start reconstructing the UI — rows arrive incrementally as each Server Component (and any await inside it) resolves, and React can begin rendering the parts that are already available while later rows are still in flight over the network, exactly analogous to how Suspense streams HTML in traditional streaming SSR (Chapter 17), but for this richer, component-aware format instead of raw markup.

Format is internal and evolving: The exact row encoding (prefixes like $, @, $L, type indicators J:, M:, S:, I:) has changed between React versions. Don't memorize specific syntax for interviews — focus on understanding what it encodes (element tree + client module references + streaming chunks) and why this format exists (enables progressive rendering without full payload).

// ❌ Passing a plain function from a Server Component to a Client Component
// throws at build/runtime — functions aren't serializable across the boundary
function ServerParent() {
  const handleClick = () => console.log('server-side closure');
  return <ClientButton onClick={handleClick} />; // Error: functions cannot be passed
}

// ✅ Pass a Server Action instead — React serializes it as an invocable reference
async function like(id) {
  'use server';
  await db.posts.like(id);
}

function ServerParent({ postId }) {
  return <ClientButton onLike={like.bind(null, postId)} />; // Works — Server Actions are the exception
}

Composition Patterns (Server Wrapping Client)

The "children as a slot" pattern for mixing Server and Client trees

The rule "Client Components cannot import Server Components" has an important, frequently-tested exception: a Client Component can render whatever React elements it receives as children or other props, even if those elements were produced by a Server Component — because by the time they're passed down, they're already-rendered element descriptors, not live server-only code the client bundle would need to include.

// Client Component — interactive shell (tabs, modal, layout with local state)
'use client';
export function InteractiveShell({ children }) {
  const [tab, setTab] = useState('overview');
  return (
    <div>
      <nav>
        <button onClick={() => setTab('overview')}>Overview</button>
      </nav>
      {/* `children` is opaque to InteractiveShell — it doesn't need to know
          or care that it was produced by a Server Component */}
      <main>{children}</main>
    </div>
  );
}

// Server Component — composes the two together
export default async function Page() {
  const data = await db.dashboard.getStats(); // server-only data fetch
  return (
    <InteractiveShell>
      <DashboardStats data={data} /> {/* still a Server Component, rendered server-side */}
    </InteractiveShell>
  );
}
Interview framing: "Server and Client Components aren't a strict layered hierarchy — the client tree can have server-rendered 'holes' passed in as children, which is exactly how frameworks let you keep interactive chrome (nav, modals, tabs) client-side while keeping the actual data-heavy content server-rendered and zero-bundle."

Client Waterfalls — Causes & Fixes

How RSC eliminates a whole class of request waterfalls — and where new ones sneak in 
// ❌ Client-fetched waterfall: the browser must first receive and parse
// the component's JS, THEN fire this fetch — the component's own code and
// the data fetch cannot happen concurrently, they're sequential
'use client';
function Profile({ userId }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch(`/api/users/${userId}`).then((r) => r.json()).then(setUser);
  }, [userId]);
  // ...
}
// ✅ Server Component fetch: the data fetch happens ON THE SERVER, concurrently
// with the rest of the page's rendering — no client round-trip needed just
// to KICK OFF the fetch, and no client JS is needed for this component at all
async function Profile({ userId }) {
  const user = await db.users.findById(userId); // direct server-side access
  return <div>{user.name}</div>;
}
Where a new waterfall sneaks back in: sequentially await-ing independent data fetches inside one Server Component still serializes them. 
// ❌ Sequential awaits create a server-side waterfall even without any client involved
async function Page({ id }) {
  const user = await getUser(id);      // waits...
  const posts = await getPosts(id);    // ...then waits again, even though independent
  return <Dashboard user={user} posts={posts} />;
}

// ✅ Fire independent fetches concurrently, await together
async function Page({ id }) {
  const [user, posts] = await Promise.all([getUser(id), getPosts(id)]);
  return <Dashboard user={user} posts={posts} />;
}

Data Fetching in Server Components

async/await as the primary data-fetching primitive

A Server Component can simply be an async function — await-ing a database query or fetch call directly in the component body, with no useEffect, no loading state management, and no client-side request at all. Suspense boundaries placed around slower Server Components let independent parts of the page stream in as their data resolves, rather than blocking the entire page on the slowest one.

// Each of these Server Components fetches and streams independently
export default function Page() {
  return (
    <>
      <Suspense fallback={<HeaderSkeleton />}>
        <Header />             {/* fast — streams in first */}
      </Suspense>
      <Suspense fallback={<FeedSkeleton />}>
        <Feed />               {/* slow DB query — streams in when ready, doesn't block Header */}
      </Suspense>
    </>
  );
}

async function Feed() {
  const posts = await db.posts.findRecent(); // Suspense-compatible: the await itself suspends
  return <ul>{posts.map((p) => <li key={p.id}>{p.title}</li>)}</ul>;
}

Caching & Revalidation Strategies

Where framework-level caching sits relative to RSC itself

RSC as a React feature is agnostic about caching — caching semantics (like Next.js's fetch memoization, full-route cache, and revalidatePath/revalidateTag) are framework-layer decisions built on top of the Flight protocol, not part of React's own spec. Interviewers sometimes conflate the two — a precise answer separates "what React's RSC model provides" from "what a specific meta-framework adds."

React's cache() function: React 19 provides cache() as a React-level deduplication primitive for Server Components. It memoizes function results per request — so if two Server Components in the same render call cache(getUser)(userId), only one actual computation runs. This is distinct from framework-level fetch caching — cache() is React's own API for request-scoped deduplication of any async function, not just fetches.

Next.js caching changed significantly between versions. Next.js 14 cached fetch responses by default; Next.js 15 reversed this (no caching by default, opt-in via cache: 'force-cache'). In interviews, focus on the conceptual layer separation rather than citing specific Next.js defaults, which may not match the interviewer's version.

Partial Prerendering (PPR)

Static shell, dynamic holes, one response

Partial Prerendering (an experimental Next.js technique built on Suspense + RSC) precomputes the static portions of a route at build time into a shell, and leaves Suspense-boundary "holes" for anything dynamic (personalized data, request-specific content) to stream in at request time — combining the instant-TTFB feel of static generation with per-request freshness, in a single HTTP response instead of a separate static-then-hydrate-then-fetch sequence.

Server Actions (React 19)

Callable server functions wired directly to client forms 
// actions.js
'use server';
export async function createComment(formData) {
  const text = formData.get('text');
  await db.comments.create({ text });
  revalidatePath('/posts/123');
}

// Client Component — no manual fetch/onSubmit wiring, no client-side JSON serialization code
'use client';
import { createComment } from './actions';

export function CommentForm() {
  return (
    <form action={createComment}>
      <input name="text" />
      <button type="submit">Post</button>
    </form>
  );
}

React serializes the reference to createComment (not its source code) into the Flight payload; submitting the form triggers an RPC-style POST that invokes the actual function on the server, with automatic progressive enhancement — the form works even before client JS has hydrated, since it's a real HTML <form> submission under the hood.

useActionState and useFormStatus (React 19) pair with Server Actions to expose pending/error/result state back in the Client Component without hand-rolling a fetch + loading-state dance.

Key distinction: Islands architecture treats interactivity as isolated, independent widgets dropped into otherwise-static HTML with no shared component tree or state between them. RSC keeps one unified React tree — Server and Client Components compose within the same tree, share the same props/children model, and can be reasoned about with ordinary React composition rules, just split across two execution environments.

Production Architecture

Case study: migrating a dashboard's data-heavy widgets to RSC
Starting point: a client-rendered analytics dashboard shipped ~380KB of JS (gzipped) including a charting library, a large date-manipulation library, and a markdown-based report renderer — all bundled client-side even though most of that logic only ever transformed server-fetched data before display.

Migration

  • Converted data-transformation-only widgets (chart data prep, report rendering) to Server Components — their heavy dependencies dropped out of the client bundle entirely.
  • Kept genuinely interactive pieces (the chart's hover tooltips, zoom/pan controls, filter dropdowns) as Client Components, composed as children/props from the Server Component parents.
  • Replaced several useEffect-driven client fetches with direct async/await in Server Components, wrapped in per-widget <Suspense> boundaries so slow widgets no longer blocked the whole dashboard's first paint.

Results

  • Client JS bundle dropped from ~380KB to ~140KB gzipped — the charting/date/markdown libraries no longer shipped to the browser at all.
  • Time-to-interactive improved because less JS needed parsing/executing/hydrating on the client.
  • Perceived load time improved further because independent widgets streamed in as their own data resolved, instead of the dashboard waiting on the single slowest client-side fetch.

Lessons Learned

  • The biggest wins came from moving data-transformation-heavy, non-interactive code server-side — chasing 100% RSC adoption for genuinely interactive widgets would have added complexity (prop-serialization constraints) without a proportional benefit.
  • Suspense boundary granularity mattered as much as the Server/Client split itself — one giant Suspense boundary around the whole dashboard would have reintroduced the "wait for the slowest thing" problem RSC was meant to solve.

Code Examples

A complete Server + Client composition, end to end 
// app/posts/[id]/page.js — Server Component (default, no directive needed)
import { Suspense } from 'react';
import { LikeButton } from './LikeButton.client';
import { CommentForm } from './actions';

export default async function PostPage({ params }) {
  const post = await db.posts.findById(params.id); // direct server-side data access

  return (
    <article>
      <h1>{post.title}</h1>
      <p>{post.body}</p>

      {/* Client Component composed directly — hydrates for interactivity */}
      <LikeButton postId={post.id} initialCount={post.likes} />

      <Suspense fallback={<p>Loading comments…</p>}>
        <Comments postId={post.id} />   {/* independent Server Component, streams separately */}
      </Suspense>

      <CommentForm postId={post.id} />  {/* Client Component wired to a Server Action */}
    </article>
  );
}

async function Comments({ postId }) {
  const comments = await db.comments.findByPost(postId); // slow query, isolated by Suspense
  return <ul>{comments.map((c) => <li key={c.id}>{c.text}</li>)}</ul>;
}

Common Mistakes

Mistakes even experienced React engineers make with RSC
  • Marking a component "use client" just because it's slow or complex — the directive is about needing browser APIs/interactivity/hooks, not about performance; slow Server Components should get a Suspense boundary, not be pushed to the client.
  • Sequential awaits inside one Server Component re-creating the exact request waterfall RSC is supposed to eliminate — always check whether independent fetches can be Promise.all'd.
  • Trying to pass functions/class instances/non-serializable values as props from Server to Client Components and being surprised by a build or runtime error — only JSON-serializable values (plus React elements and Server Actions) can cross the boundary.
  • Assuming Server Components are equivalent to "runs once at build time" (SSG) — by default they re-execute on the server per request/navigation unless a framework's caching layer explicitly opts them into static/ISR-style caching.
  • Wrapping the entire page in one giant Suspense boundary, reintroducing an all-or-nothing wait instead of the granular, independent streaming RSC + Suspense are meant to enable.

Trade-offs

Decisions worth stating out loud
  • RSC vs pure client-rendered SPA: RSC reduces client bundle size and enables direct backend access, at the cost of introducing two execution environments to reason about, stricter serialization rules at the boundary, and dependency on framework-level plumbing (most production usage today is via Next.js) rather than a standalone library choice.
  • RSC vs Islands architecture: RSC's unified tree gives you ordinary React composition across the server/client boundary; Islands keep server and client concerns fully separate and simpler to reason about individually, at the cost of no shared component tree or state between islands.
  • Granular Suspense boundaries vs one big one: granular boundaries maximize independent streaming and perceived performance but require more deliberate placement and fallback design; one big boundary is simpler to add but reverts to blocking on the slowest piece.
  • Server Actions vs a traditional REST/API-route mutation: Server Actions remove boilerplate (no separate endpoint, no manual fetch/serialization code, progressive enhancement for free) but couple the mutation's invocation mechanism tightly to the framework's RSC implementation, making it less portable than a plain HTTP API a non-React client could also call.

Follow-up Interview Questions

Q1: Can a Server Component have internal state that persists across re-renders?

Strong answer: no — Server Components have no client-side lifecycle at all; there's no useState, no component instance that persists in memory across requests. Each render is a fresh function execution against fresh data. Anything that needs to persist across interactions (a counter, a toggle, an open/closed panel) must live in a Client Component, or as actual server-side/database state re-fetched on each render if it needs to survive navigations.

Q2: If a Client Component needs data that requires a server-only API key, how do you get that data to it without exposing the key?

Strong answer: fetch the data in a Server Component (which has access to the secret via server-only environment variables) and pass only the resulting serializable data down as props to the Client Component — the key itself never crosses the Flight boundary because it's never referenced by any code the client needs to execute. This is a direct security benefit of the Server/Client split: secrets naturally stay server-side as long as they're only touched inside Server Component code, not accidentally imported into a "use client" file.

Q3: How does React know which parts of a Flight payload correspond to already-hydrated Client Components on a subsequent navigation, versus which need fresh module downloads?

Strong answer: Client References in the Flight payload are keyed by a stable module identifier; the client-side React runtime keeps a registry of already-loaded client modules from previous navigations/hydration. When a new Flight payload arrives referencing a module the client has already fetched and instantiated, React reuses the existing module rather than re-fetching it — only genuinely new Client Component modules (not yet loaded in this session) trigger a fresh network request.

Q4: What happens if a Server Component throws an error partway through streaming — does the whole response fail?

Strong answer: no, not if error boundaries are placed appropriately — an error inside a Suspense-boundary-wrapped Server Component is caught by the nearest enclosing error boundary (which, per React's rules, must itself be a Client Component since error boundaries rely on lifecycle methods), and only that boundary's fallback UI is affected. Parts of the page that already streamed successfully (or belong to sibling Suspense boundaries) are unaffected — this granular failure isolation is one of the practical benefits of splitting a page into multiple independently-streamed Suspense boundaries rather than one monolithic render.

Q5: Why can't "use server" functions just be normal exported functions called directly from the client bundle?

Strong answer: because their implementation may reference server-only modules (database drivers, filesystem access, secrets) that cannot exist in a browser bundle at all — attempting to include them client-side would either fail to bundle or leak server-only code/credentials into client JS. Marking them "use server" tells the build tooling to replace the client-side reference with a serializable RPC stub (an ID plus argument-serialization logic) while keeping the real implementation server-only, invoked over the network when called.

Summary

Key mental models for the interview:

  • RSC ≠ SSR. SSR renders to an HTML string once, on demand, then hands off to full client hydration. RSC is a persistent, streamable, component-aware serialization format that composes with Client Components in a single tree.
  • The composition rule is one-directional. Server Components can render Client Components; Client Components can only receive already-rendered Server Component output as opaque children/props.
  • Only serializable values cross the boundary — functions are disallowed except for the special-cased Server Actions, which are serialized as invocable references, not source code.
  • Zero-bundle-size means excluded from the client build graph entirely, not lazily loaded — a meaningfully stronger guarantee than code-splitting.
  • Granular Suspense boundaries are what make streaming actually pay off. Wrapping too much in one boundary reintroduces the waterfall RSC is meant to solve.

What NOT to say in an interview:

  • ❌ "Server Components are just SSR with extra steps" — conflates a one-shot render-to-string with a streaming, composable component model.
  • ❌ "You can use useState in a Server Component, it just doesn't update the UI" — Server Components cannot use useState at all; this is a hard constraint, not a limitation with a workaround.
  • ❌ "RSC eliminates all client-server waterfalls" — it eliminates the client-fetch-triggering-another-fetch pattern, but sequential awaits inside a single Server Component can still create one.
  • ❌ "Islands and RSC are the same idea with different names" — Islands have no shared component tree across islands; RSC's Server and Client Components compose within one unified tree.

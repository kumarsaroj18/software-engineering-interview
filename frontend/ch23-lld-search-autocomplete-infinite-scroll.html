LLD — Search with Debouncing, Autocomplete & Infinite Scroll

"Build a production-quality Search with Debouncing, Autocomplete, and an Infinite Scroll list."
Key Takeaway: These three components are really one underlying skill wearing three outfits: managing an asynchronous, race-prone data fetch against user-driven input, without leaking requests, memory, or stale state. Debouncing controls when you fetch, cancellation controls which response you trust, and virtualization controls how much you render. Interviewers use these to see whether you reach for those three levers deliberately or accidentally get lucky.

Interviewer's Intent

What Interviewers Evaluate in LLD Rounds

Low-Level Design (component design) rounds differ from algorithm rounds: there's rarely one "correct" answer, and the interviewer is scoring your process as much as your final code. Across every FAANG-style frontend LLD round, the evaluation clusters into four buckets:

DimensionWhat's being assessed
Requirements gatheringDid you clarify scale, edge cases, and constraints before writing code?
API & state designIs the component's public interface (props, hooks) clean? Is internal state minimal and non-redundant?
Correctness under real conditionsRace conditions, cleanup, empty/error/loading states — not just the happy path
Performance & accessibility awarenessRe-render cost, network efficiency, keyboard/screen-reader support — raised without prompting
Red flag pattern interviewers watch for: candidates who start typing code within the first 60 seconds. A senior candidate spends 3-5 minutes clarifying scope first — for a search box, that means asking about expected result volume, whether results come from a REST endpoint or a client-side dataset, and whether debounce delay is a product requirement or your own choice.

LLD Round Strategy: Clarify → Design → Implement → Optimize
  1. Clarify (3-5 min): data source, expected scale, network conditions, target devices, accessibility requirements, whether this is a standalone component or part of a larger page.
  2. Design (5 min): sketch the component's props/state on a whiteboard or in comments before writing implementation code — name the hooks you'll extract (useDebounce, useInfiniteScroll) and what each owns.
  3. Implement (20-25 min): build the un-optimized-but-correct version first — loading/error/empty states, cancellation, cleanup — then layer in the trickier mechanics (debounce, virtualization) once the base case works.
  4. Optimize (5-10 min): the interviewer almost always adds a constraint here ("what if there are 100k results?", "what if the network is 3G?") — this is deliberate, not a trick; treat it as the real second half of the round.

Component 1: Search with Debouncing

Requirements & Constraints

Clarifying questions: Is search server-side (network round-trip per query) or client-side (filter an in-memory array)? What's an acceptable perceived latency — is 300ms debounce too slow for this use case (e.g., command palettes usually want ~150ms or less)? Should the previous request be cancelled or just ignored when a new one starts?

Requirements: don't fire a network request per keystroke; always render the result set matching the latest query, never a stale one; show distinct loading/error/empty states; keep the input itself responsive regardless of network state; be screen-reader accessible via aria-live announcements of result counts.

Custom useDebounce Hook

Debouncing delays invoking a function until a pause in calls of at least delay ms has occurred — it collapses a burst of keystrokes into one trailing call. This is distinct from throttling, which guarantees invocation at a maximum rate regardless of pauses.

function useDebouncedValue(value, delay) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // Cancel the pending update if `value` changes again
  }, [value, delay]);

  return debounced;
}

// Callback-style variant, useful when you need to debounce a function
// (not just a value) e.g. an imperative API call triggered by more than typing
function useDebouncedCallback(callback, delay) {
  const callbackRef = useRef(callback);
  callbackRef.current = callback; // Always call the latest version — avoids stale closures

  const timeoutRef = useRef(null);

  const debounced = useCallback(
    (...args) => {
      clearTimeout(timeoutRef.current);
      timeoutRef.current = setTimeout(() => callbackRef.current(...args), delay);
    },
    [delay]
  );

  useEffect(() => () => clearTimeout(timeoutRef.current), []); // Cleanup on unmount

  return debounced;
}

Edge case: If delay changes while a timer is pending, the old timeout still fires with the old delay (only the unmount cleanup clears it). For dynamic delays, add clearTimeout(timeoutRef.current) inside the useCallback when creating a new debounced function, or add delay to the useEffect cleanup deps. In practice, delay is usually static so this rarely matters.

Why debounce the value, not the input's onChange handler: keeping the raw keystroke state (query) updating instantly means the input never feels laggy, while a separate debounced derivative (debouncedQuery) is what actually triggers the fetch. This separation is the single most important design decision in this component.
AbortController for Request Cancellation & Race Condition Prevention

Even with debouncing, two requests can still race: request A (for "reac") is slow, request B (for "react") returns first. Without cancellation, A's response can overwrite B's more recent, more correct one when it finally arrives.

function useSearch(query) {
  const [state, setState] = useState({ status: 'idle', results: [], error: null });

  useEffect(() => {
    if (!query) {
      setState({ status: 'idle', results: [], error: null });
      return;
    }

    const controller = new AbortController();
    setState((s) => ({ ...s, status: 'loading' }));

    fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal: controller.signal })
      .then((res) => {
        if (!res.ok) throw new Error(`Search failed: ${res.status}`);
        return res.json();
      })
      .then((results) => setState({ status: 'success', results, error: null }))
      .catch((err) => {
        if (err.name === 'AbortError') return; // Expected — a newer query superseded this one
        setState({ status: 'error', results: [], error: err.message });
      });

    return () => controller.abort(); // Cancel on query change or unmount
  }, [query]);

  return state;
}
AbortController vs a request-ID ref: when the underlying call is a real fetch, AbortController is strictly better — it actually cancels the network request, saving bandwidth and server load, not just ignoring the response client-side. Use a monotonic request-ID pattern only when the API you're calling doesn't support cancellation (e.g., some SDKs, WebSocket-based RPC).
Loading, Error, Empty States & Accessibility 
function SearchResults({ status, results, error, query }) {
  if (status === 'idle') return null;
  if (status === 'loading') return <p aria-live="polite">Searching…</p>;
  if (status === 'error') return <p role="alert">Something went wrong: {error}</p>;
  if (results.length === 0) return <p aria-live="polite">No results for "{query}"</p>;

  return (
    <ul aria-live="polite" aria-label={`${results.length} results`}>
      {results.map((r) => (
        <li key={r.id}>{r.title}</li>
      ))}
    </ul>
  );
}

aria-live="polite" announces the region's new content to screen readers without interrupting whatever the user is currently doing (e.g., still typing) — role="alert" is reserved for the error state because errors warrant more assertive announcement.

Complete Implementation 
function SearchBox() {
  const [query, setQuery] = useState('');
  const debouncedQuery = useDebouncedValue(query, 300);
  const { status, results, error } = useSearch(debouncedQuery);

  return (
    <div>
      <input
        type="search"
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Search…"
        aria-label="Search"
        aria-controls="search-results"
      />
      <div id="search-results">
        <SearchResults status={status} results={results} error={error} query={debouncedQuery} />
      </div>
    </div>
  );
}
Edge Cases
  • Clearing the input mid-flight: the effect's cleanup must abort the in-flight request even when the new "query" is empty, or a slow response for the last non-empty query can populate results after the user already cleared the box.
  • Query with only whitespace: trim before deciding whether to fetch — otherwise every keystroke of leading spaces triggers a wasted request.
  • Very fast typists exceeding the debounce window repeatedly: confirm the debounce timer resets (not accumulates) on each keystroke — a common off-by-one bug is scheduling additional timers instead of clearing the previous one.
  • Backend returns results out of order relative to request order even without network racing (e.g., server-side load balancing): the AbortController approach sidesteps this because only the most recently-issued, non-aborted request can resolve into state.

Component 2: Autocomplete / Typeahead

Requirements & Constraints

Requirements: full keyboard navigation (no mouse required), announce the active option to screen readers, highlight the matched substring, remember recent searches, and remain performant with a debounced network call underneath — this component builds directly on Component 1's useDebouncedValue and useSearch.

The correct accessibility pattern for this UI shape is the ARIA combobox pattern — not a plain text input paired with a floating <ul> that has no semantic relationship to it.

Combobox ARIA Pattern & Keyboard Navigation 
function useComboboxKeyboard(itemCount, onSelect, isOpen, setIsOpen) {
  const [activeIndex, setActiveIndex] = useState(-1);

  const onKeyDown = (e) => {
    if (!isOpen) {
      if (e.key === 'ArrowDown') setIsOpen(true);
      return;
    }
    switch (e.key) {
      case 'ArrowDown':
        e.preventDefault();
        setActiveIndex((i) => (i + 1) % itemCount);
        break;
      case 'ArrowUp':
        e.preventDefault();
        setActiveIndex((i) => (i - 1 + itemCount) % itemCount);
        break;
      case 'Enter':
        if (activeIndex >= 0) {
          e.preventDefault();
          onSelect(activeIndex);
        }
        break;
      case 'Escape':
        setIsOpen(false);
        setActiveIndex(-1);
        break;
      default:
        break;
    }
  };

  useEffect(() => setActiveIndex(-1), [itemCount]); // Reset when the result set changes

  return { activeIndex, onKeyDown };
}
<div> {/* wrapper — no role (ARIA 1.2: combobox goes on input, not wrapper) */}
  <input
    role="combobox"
    aria-expanded={isOpen}
    aria-controls="ac-listbox"
    aria-autocomplete="list"
    aria-activedescendant={activeIndex >= 0 ? `ac-option-${activeIndex}` : undefined}
    onKeyDown={onKeyDown}
  />
  <ul id="ac-listbox" role="listbox">
    {results.map((r, i) => (
      <li
        key={r.id}
        id={`ac-option-${i}`}
        role="option"
        aria-selected={i === activeIndex}
      >
        {r.label}
      </li>
    ))}
  </ul>
</div>
Why focus never moves to the <li> elements: in the combobox pattern, DOM focus stays on the <input> the entire time. "Active" option highlighting is communicated purely via aria-activedescendant pointing at the visually-highlighted option's id — moving real focus into the list would close the ability to keep typing.
Highlighting Matched Text & Recent Searches 
function HighlightMatch({ text, query }) {
  if (!query) return <>{text}</>;
  const idx = text.toLowerCase().indexOf(query.toLowerCase());
  if (idx === -1) return <>{text}</>;
  return (
    <>
      {text.slice(0, idx)}
      <mark>{text.slice(idx, idx + query.length)}</mark>
      {text.slice(idx + query.length)}
    </>
  );
}

function useRecentSearches(key = 'recent-searches', limit = 5) {
  const [recent, setRecent] = useState(() => {
    try {
      return JSON.parse(localStorage.getItem(key)) ?? [];
    } catch {
      return [];
    }
  });

  const record = (term) => {
    setRecent((prev) => {
      const next = [term, ...prev.filter((t) => t !== term)].slice(0, limit);
      try {
        localStorage.setItem(key, JSON.stringify(next));
      } catch {
        // Storage unavailable — recent searches just won't persist this session
      }
      return next;
    });
  };

  return { recent, record };
}
Focus Management, Mobile Considerations & Complete Implementation 
function Autocomplete() {
  const [query, setQuery] = useState('');
  const [isOpen, setIsOpen] = useState(false);
  const debouncedQuery = useDebouncedValue(query, 250);
  const { status, results } = useSearch(debouncedQuery);
  const { recent, record } = useRecentSearches();
  const listRef = useRef(null);

  const items = query ? results : recent.map((term, i) => ({ id: `recent-${i}`, label: term }));

  const handleSelect = (index) => {
    const item = items[index];
    setQuery(item.label);
    record(item.label);
    setIsOpen(false);
  };

  const { activeIndex, onKeyDown } = useComboboxKeyboard(items.length, handleSelect, isOpen, setIsOpen);

  // Scroll the active option into view as it changes via keyboard
  useEffect(() => {
    if (activeIndex < 0 || !listRef.current) return;
    listRef.current.children[activeIndex]?.scrollIntoView({ block: 'nearest' });
  }, [activeIndex]);

  return (
    <div>
      <input
        role="combobox"
        aria-expanded={isOpen}
        aria-controls="ac-listbox"
        aria-autocomplete="list"
        aria-activedescendant={activeIndex >= 0 ? `ac-option-${activeIndex}` : undefined}
        value={query}
        onChange={(e) => {
          setQuery(e.target.value);
          setIsOpen(true);
        }}
        onFocus={() => setIsOpen(true)}
        onBlur={() => setTimeout(() => setIsOpen(false), 100)} // Delay so option click registers first
        onKeyDown={onKeyDown}
        // inputMode + autoCapitalize help mobile keyboards behave for search
        inputMode="search"
        autoCapitalize="none"
        autoCorrect="off"
      />
      {isOpen && (
        <ul id="ac-listbox" role="listbox" ref={listRef}>
          {status === 'loading' && <li aria-disabled="true">Loading…</li>}
          {items.map((item, i) => (
            <li
              key={item.id}
              id={`ac-option-${i}`}
              role="option"
              aria-selected={i === activeIndex}
              onMouseDown={() => handleSelect(i)} // mousedown fires before input's blur
            >
              <HighlightMatch text={item.label} query={query} />
            </li>
          ))}
        </ul>
      )}
    </div>
  );
}

Mobile considerations: use onMouseDown (not onClick) for option selection because onClick fires after onBlur, which would already have closed the list; set inputMode="search" to surface a "search"-labeled key on virtual keyboards; avoid onBlur-triggered closing being too aggressive on touch devices where a tap can register as blur+focus in quick succession.

Edge Cases
  • Empty query showing recent searches vs a query with zero results: these are different empty states and must render distinct messaging (don't show "no results" when the box is simply empty and hasn't searched yet).
  • Selecting an option programmatically re-triggers the search effect because setQuery changes: guard against re-opening the dropdown immediately after a selection (the setIsOpen(false) in handleSelect handles this, but it's an easy thing to regress when refactoring).
  • Duplicate recent searches after re-searching the same term: dedupe by filtering the existing entry out before prepending, as shown in useRecentSearches.
  • Screen magnifier / low-vision users relying on aria-activedescendant: verify the highlighted option actually scrolls into view (handled above via scrollIntoView) — without it, keyboard navigation can move focus semantically past the visible viewport.

Component 3: Infinite Scroll

Requirements & Constraints

Clarifying questions: cursor-based or offset/page-based pagination on the backend? Expected total item count (hundreds vs hundreds of thousands)? Should scroll position be restored when navigating back to this list? Is this a fixed-height list (virtualization-friendly) or variable-height content?

Requirements: load the next page before the user hits the literal bottom (pre-fetch buffer); never fire duplicate requests for the same page; show a loading sentinel without layout shift; handle errors with retry; and — at scale — avoid keeping every fetched item mounted in the DOM simultaneously.

IntersectionObserver Approach (vs Scroll Event Listeners)

IntersectionObserver is preferred over listening to scroll events because it runs off the main thread's synchronous scroll-handling path, doesn't require manual throttling, and directly answers the question you actually have ("is this sentinel element visible?") instead of requiring you to compute scroll position, viewport height, and element offsets by hand on every scroll tick.

function useInfiniteScroll({ hasMore, isLoading, onLoadMore, rootMargin = '400px' }) {
  const sentinelRef = useRef(null);

  useEffect(() => {
    const node = sentinelRef.current;
    if (!node || !hasMore) return;

    const observer = new IntersectionObserver(
      (entries) => {
        if (entries[0].isIntersecting && !isLoading) {
          onLoadMore();
        }
      },
      { rootMargin } // Trigger before the sentinel is literally on-screen
    );

    observer.observe(node);
    return () => observer.disconnect();
  }, [hasMore, isLoading, onLoadMore, rootMargin]);

  return sentinelRef;
}
rootMargin: '400px' is the pre-fetch buffer: it expands the observer's trigger boundary so the next page starts loading 400px before the sentinel actually enters the viewport, hiding network latency behind the remaining scroll distance instead of showing a loading spinner the user has to wait on.
Pagination Model, Loading Sentinel & Error Handling with Retry 
function usePaginatedList(fetchPage) {
  const [items, setItems] = useState([]);
  const [cursor, setCursor] = useState(null);
  const [status, setStatus] = useState('idle'); // idle | loading | error | done
  const inFlight = useRef(false);
  const abortRef = useRef(null);

  const loadMore = useCallback(async () => {
    if (inFlight.current || status === 'done') return;
    inFlight.current = true;
    setStatus('loading');

    // Cancel any previous in-flight request
    abortRef.current?.abort();
    const controller = new AbortController();
    abortRef.current = controller;

    try {
      const page = await fetchPage(cursor, { signal: controller.signal });
      setItems((prev) => [...prev, ...page.items]);
      setCursor(page.nextCursor);
      setStatus(page.nextCursor ? 'idle' : 'done');
    } catch (e) {
      if (e.name === 'AbortError') return; // Unmounted or superseded — ignore
      setStatus('error');
    } finally {
      inFlight.current = false;
    }
  }, [cursor, fetchPage, status]);

  useEffect(() => {
    loadMore(); // Load the first page on mount
    return () => abortRef.current?.abort(); // Cancel on unmount
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, []);

  return { items, status, loadMore, retry: loadMore };
}
Why inFlight is a ref, not state: the IntersectionObserver callback can fire multiple times in quick succession (e.g., a fast scroll or a resize) before a state update from the first call has re-rendered the component. A ref is read/written synchronously within the same tick, closing the race that a state-based flag would leave open. 
function ListSentinel({ status, retry }) {
  if (status === 'loading') return <li aria-live="polite">Loading more…</li>;
  if (status === 'error')
    return (
      <li role="alert">
        Couldn't load more. <button onClick={retry}>Retry</button>
      </li>
    );
  return null; // 'done' or 'idle' render nothing
}
Virtualization (react-window) & Scroll Position Restoration

Infinite scroll and virtualization solve different problems and are commonly conflated: infinite scroll controls when you fetch more data; virtualization controls how much of the fetched data is actually mounted in the DOM. At small scale (hundreds of items) you need only the former. Past a few thousand rows, mounting every item degrades scroll performance and memory regardless of how efficient the fetching is — that's when virtualization becomes necessary.

import { FixedSizeList } from 'react-window';

function VirtualizedFeed({ items, status, loadMore, hasMore }) {
  const itemCount = hasMore ? items.length + 1 : items.length; // +1 for the sentinel/loading row

  const isItemLoaded = (index) => index < items.length;

  const Row = ({ index, style }) => {
    if (!isItemLoaded(index)) {
      return <div style={style}>Loading…</div>;
    }
    return <div style={style}>{items[index].title}</div>;
  };

  return (
    <FixedSizeList
      height={600}
      width="100%"
      itemCount={itemCount}
      itemSize={72}
      onItemsRendered={({ visibleStopIndex }) => {
        if (visibleStopIndex >= items.length - 5 && hasMore && status !== 'loading') {
          loadMore(); // Pre-fetch when nearing the end of currently-rendered rows
        }
      }}
    >
      {Row}
    </FixedSizeList>
  );
}

Scroll position restoration (returning to a list after navigating into a detail view): store the scroll offset (or the last-visible item's id/index) in a ref or a router-level cache keyed by the list's identity, and on remount, either call scrollTo imperatively (fixed-height virtualization) or scroll the last-visible item's id into view with scrollIntoView (non-virtualized DOM).

Complete Implementation (Non-Virtualized Baseline) 
function InfiniteFeed({ fetchPage }) {
  const { items, status, retry, loadMore } = usePaginatedList(fetchPage);
  const sentinelRef = useInfiniteScroll({
    hasMore: status !== 'done',
    isLoading: status === 'loading',
    onLoadMore: loadMore,
  });

  return (
    <ul>
      {items.map((item) => (
        <li key={item.id}>{item.title}</li>
      ))}
      <li ref={sentinelRef} style={{ height: 1 }} aria-hidden="true" />
      <ListSentinel status={status} retry={retry} />
    </ul>
  );
}

Start with this version in an interview — it's correct, handles the required states, and takes a fraction of the time virtualization would. Only reach for react-window/react-virtual once the interviewer specifies scale that requires it, and say so explicitly.

Memory Management for Large Lists & Edge Cases
  • Unbounded growth of the items array itself: even with virtualization limiting DOM nodes, the JS array of fetched items still grows unboundedly across a very long session. For a true "infinite" feed (social media style), periodically evict off-screen pages from the array, not just from the DOM, keeping a windowed slice around the current scroll position.
  • Sentinel never intersects on a fast/large monitor where the initial page doesn't fill the viewport: trigger an initial loadMore check after the first page loads, in case the sentinel is already visible with no scrolling required.
  • Duplicate items across pages if the underlying dataset mutates between page fetches (offset-based pagination shifting while new items are inserted): prefer cursor-based pagination, which is stable under concurrent inserts, and de-duplicate by id defensively when appending pages regardless.
  • Component unmounts mid-fetch (user navigates away while a page is loading): guard the state-setting calls after the awaited fetch with a mounted-ref check, or use an AbortController tied to the component's cleanup, matching the pattern from Component 1.

Common LLD Mistakes

Mistakes that cost points across all three components
  • Debouncing the wrong thing: debouncing the input's visual value (making typing itself feel laggy) instead of debouncing only the derived value that triggers the network call.
  • No cancellation strategy: relying purely on debounce delay to prevent races, which fails whenever a fast response overtakes an even-faster-fired one under variable network latency.
  • Using scroll event listeners instead of IntersectionObserver, then manually throttling — more code, worse performance, harder to get right.
  • Conflating infinite scroll with virtualization, reaching for react-window immediately when the interviewer hasn't specified a scale that needs it.
  • Ignoring the combobox ARIA pattern for autocomplete and building a plain input plus floating list with no semantic relationship — screen reader users get no indication a list even exists.
  • Not handling duplicate/racing loadMore triggers from IntersectionObserver firing multiple times before a state update lands — missing the ref-based in-flight guard.

Trade-offs (Debounce Delay, Virtualization Threshold)

Decisions worth stating out loud during the round
  • Debounce delay — 150ms vs 300ms vs 500ms: shorter feels more responsive but sends more requests and risks more races under high latency; longer reduces load but the UI feels sluggish. 250-300ms is a reasonable default for search-as-you-type; command palettes and IDE-style autocomplete often go as low as 100-150ms since users expect near-instant feedback there.
  • Debounce vs throttle: throttling guarantees periodic updates during continuous input (useful for e.g. live-updating a chart as a slider drags); debouncing waits for a pause (better for search, where only the final query matters).
  • Client-side filter vs server-side search: client-side is instant and needs no debounce/cancellation machinery at all, but only works while the full dataset comfortably fits in memory and loads upfront — the two approaches aren't a spectrum, they're a fork based on data size.
  • Virtualization threshold: under roughly a few hundred simultaneously-mounted rows, the DOM cost is negligible and virtualization adds complexity (fixed/variable row height management, harder to inspect in devtools) for no measurable benefit — introduce it only once profiling (or the interviewer's stated scale) justifies it.
  • Cursor-based vs offset-based pagination: cursor-based is stable under concurrent writes to the underlying dataset and is the correct default for infinite scroll; offset-based is simpler to implement but can skip or duplicate items if the dataset changes between page fetches.

Follow-up Interview Questions

Q1: How would you add "search-as-you-type" highlighting when the match is case-insensitive and includes diacritics (e.g., searching "cafe" should match "café")?

Strong answer: normalize both the query and the candidate text using String.prototype.normalize('NFD') combined with a regex that strips combining diacritical marks (/[̀-ͯ]/g) before comparing indices, then map the matched range back onto the original (non-normalized) string for display — highlighting must operate on original character offsets, not the normalized copy, or the highlighted substring will be visually wrong.

Q2: The search endpoint has no cancellation support (a legacy SOAP-style RPC client). How do you prevent stale results without AbortController?

Strong answer: fall back to the monotonic request-ID pattern — increment a ref-held counter before each call, capture the current value in the closure, and only commit the response to state if the captured id still matches the ref's current value when the response resolves. This doesn't cancel the actual in-flight call (wasting network/server work) but does guarantee state correctness.

Q3: How would you unit test the debounce behavior without waiting real milliseconds in your test suite?

Strong answer: use fake timers (vi.useFakeTimers() / jest.useFakeTimers()), type simulated input, then advance time programmatically (vi.advanceTimersByTime(300)) and assert the fetch mock was called exactly once with the final value — asserting it was not called before advancing past the delay, and confirming intermediate keystrokes never triggered a call, are the two assertions that actually prove debouncing works rather than just "eventually calling the API."

Q4: The infinite scroll list needs to support "jump to top" without losing the currently-loaded pages. How do you implement it efficiently?

Strong answer: keep the already-fetched items array intact in state — "jump to top" is purely a scroll-position operation, not a data-refetch. For a non-virtualized list, call window.scrollTo({ top: 0, behavior: 'smooth' }) or scroll the container ref; for a virtualized list (react-window), call the list ref's imperative scrollTo(0) method, since the library doesn't expose scroll position through regular DOM APIs on a windowed container.

Q5: How does automatic batching in React 18 change the behavior of the debounced search hook if the fetch resolves inside a non-React-event context (e.g., a raw setTimeout)?

Strong answer: before React 18, state updates inside a plain setTimeout callback (outside any React event handler) were not batched — each setState call triggered its own synchronous re-render. Since React 18's automatic batching, updates inside setTimeout, promises, and native event handlers are batched by default via createRoot. For the search hook, that means multiple state writes inside the fetch's .then()/.catch() chain (e.g., setting both status and results in two calls) now commit as a single render instead of two, which is strictly better and requires no code change to benefit from.

Summary

Key mental models for the interview:

  • Debounce the derived value, not the input. The text box must always feel instant; only the thing that triggers network/expensive work should lag behind typing.
  • Cancellation is not optional at scale. Any async operation triggered by fast-changing input needs a defined "which response wins" rule — AbortController when available, a request-ID ref otherwise.
  • Combobox, not "input + floating div." Autocomplete has a standard ARIA pattern; using it is the difference between an accessible component and one that merely looks like one.
  • IntersectionObserver answers "is it visible," not "where did the user scroll." It's the right tool because it matches the actual question infinite scroll needs answered.
  • Infinite scroll ≠ virtualization. One controls fetch timing, the other controls DOM mounting — introduce the second only once scale demands it.

What NOT to say in an interview:

  • ❌ "I'll debounce the onChange so the input updates slowly too" — this makes typing feel broken; only the fetch trigger should be debounced.
  • ❌ "Race conditions are rare enough to ignore" — under real network variance they are one of the most common production bugs in search UIs.
  • ❌ "I'll just reach for react-window by default" — without a stated scale requirement, this is solving a problem that may not exist and adds real complexity.
  • ❌ "Accessibility can be a follow-up if they ask" — the combobox pattern, live regions, and keyboard support are graded as part of the base implementation in most senior loops.

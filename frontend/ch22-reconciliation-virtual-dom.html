Reconciliation & Virtual DOM

"How does React's reconciliation algorithm work? When does the Virtual DOM help, and when does it hurt?"
Key Takeaway: React's reconciler doesn't diff the DOM — it diffs two trees of lightweight JS objects (the current Fiber tree vs the new element tree produced by rendering) using an O(n) heuristic that trades diffing accuracy for speed: same position + same type = update in place; different type = unmount + remount; and lists rely entirely on the key prop to identify elements across renders, because without it, position is the only identity React has. The Virtual DOM's real value was never "diffing is fast" — it's that it lets you write declarative UI code while React batches and minimizes the actual imperative DOM mutations, which are the expensive part.

Interviewer's Intent

What the interviewer is really testing
This question tests three capabilities simultaneously:
  • Correct mental model: do you know the Virtual DOM is a diffing input, not a performance feature by itself? Many candidates repeat "Virtual DOM is fast because it's in memory" without understanding that the real cost is DOM mutation, which the VDOM only helps minimize.
  • Practical debugging instinct: can you explain why a specific list re-renders incorrectly, loses input focus, or re-mounts unnecessarily by tracing it back to a missing/incorrect key?
  • Awareness of alternatives: do you know that fine-grained reactive systems (SolidJS, Svelte 5 runes, Vue's reactivity) sidestep the VDOM entirely, and can you articulate the actual trade-off rather than dismissing them?
Red flags for interviewers: "Virtual DOM makes React fast" with no further explanation; not knowing why key={index} is dangerous for reorderable lists; claiming React "diffs the whole DOM" (it never touches the real DOM during diffing — only during commit).

60-Second Answer

Structured response for time-pressured interviews

React renders your component tree into a tree of plain JS objects called React elements (the "Virtual DOM"). On every update, React creates a new element tree and compares it against the previous Fiber tree using a heuristic O(n) diffing algorithm — not the theoretically optimal O(n³) tree-diff algorithm, which would be too slow for UI trees of realistic size. The heuristic relies on two rules: elements of different types produce different trees (unmount old, mount new — no attempt to diff their children), and elements in a list are matched across renders by their key, not their index, so React can tell "moved" apart from "changed" apart from "new."

Where it helps: letting you write declarative, value-based UI (return <div>{count}</div>) while React computes the minimal set of real DOM mutations needed, batches them, and applies them in one commit phase — DOM writes are the actually expensive operation, not the diffing.

Where it hurts: high-frequency updates (60fps animations, drag interactions) where even a cheap diff plus commit per frame adds overhead that a fine-grained reactive system (which updates only the exact DOM node bound to a changed signal, no tree walk at all) avoids entirely. This is why libraries like Framer Motion animate via direct DOM/WAAPI manipulation outside React's render cycle rather than through setState on every frame.

Virtual DOM Representation

What a React element actually is, and how it differs from a Fiber

A React element is a plain, immutable JS object — not a class instance, not a DOM node. <div className="a">{count}</div> compiles (via the JSX transform) to something like:

// What JSX compiles to (React 17+ automatic runtime)
const element = {
  $$typeof: Symbol.for('react.element'),
  type: 'div',
  key: null,
  props: { className: 'a', children: count },
  // NOTE: no reference to any real DOM node, no instance methods
};

This element tree is cheap to create — thousands of these objects can be allocated per frame with negligible cost, which is exactly the property that makes "re-render the whole component" a viable default strategy in React, unlike re-touching the whole real DOM.

Element vs Fiber vs DOM node — three different trees: the element tree is the ephemeral, freshly-created-every-render description of what the UI should look like. The Fiber tree is React's persistent, mutable internal data structure — one Fiber node per component/host instance, carrying state, effect lists, and pointers (child, sibling, return) that survive across renders. The DOM tree is the actual browser structure, updated only during the commit phase. Reconciliation is the process of comparing the new element tree against the existing Fiber tree to decide how to mutate the Fiber tree (and, downstream, the DOM).

Diffing Algorithm (O(n) Heuristic)

Why React doesn't use the "optimal" tree-diff algorithm

The general problem of computing the minimum number of operations to transform one arbitrary tree into another is O(n³) in the number of nodes — for a UI tree with thousands of nodes, that's computationally infeasible to run on every update. React's reconciler instead applies two heuristics that are wrong in rare cases but correct and fast in the overwhelming majority of real UI updates:

  1. Different element types produce different trees. If a <div> is replaced by a <span> (or a class/function component is replaced by a different one) at the same position, React does not attempt to diff their children at all — it tears down the entire old subtree and builds the new one from scratch.
  2. Elements with a stable key across renders are assumed to correspond to the same logical item, even if their position in the list changed. Without a key, React falls back to matching purely by index.
// Same type at the same position → React updates the existing DOM node in place
// (only the changed attribute/text is touched, the <div> itself is reused)
<div className="before">Hello</div>
<div className="after">Hello</div>

// Different type at the same position → full unmount + remount
// (all state in the old subtree is destroyed, DOM nodes are discarded, not reused)
<div><Counter /></div>
<span><Counter /></span>
Complexity in practice: because the algorithm only compares elements at the same tree position (with keys providing an escape hatch for list reordering), the overall cost is O(n) in the number of elements — a single linear pass per level — rather than the combinatorial cost of a fully general tree diff.

Key Prop & Element Identity

Keys are React's only source of truth for "is this the same item?"

React has no way to know that "the todo with id 42" in the old render and "the todo with id 42" in the new render are the same logical entity — unless you tell it, via key. Without an explicit key, React defaults to using each child's index in its parent as an implicit key.

// Implicit key = array index. Fine ONLY if the list never reorders,
// never has items inserted/removed from the middle, and items are stateless.
{items.map((item) => <Row data={item} />)}

// Explicit, stable key = correct identity across reorders/insertions/deletions
{items.map((item) => <Row key={item.id} data={item} />)}

A key only needs to be unique among its siblings — not globally across the whole app. It is never passed down to the component as a prop (attempting to read props.key returns undefined); it exists purely as metadata for the reconciler.

Component vs Element Reconciliation

How reconciliation differs for host elements vs component elements

Reconciling a host element (div, span, ...) means diffing its DOM attributes/text and recursing into its children. Reconciling a component element (function or class component) means: if the type is unchanged, keep the existing Fiber (and its hook state / instance) and call the function again with new props to get a new child element tree, then recurse into that. If the type changed, discard the old Fiber's state entirely.

// Same component type at the same position → hook state (e.g. useState) is PRESERVED
// across this update, even though the component function re-executes
function Parent({ showBadge }) {
  return (
    <div>
      <Profile />              {/* re-renders, but its internal useState survives */}
      {showBadge && <Badge />} {/* mounts/unmounts based on the condition, own state */}
    </div>
  );
}
Common misconception: "re-rendering" a component does not mean React throws away its state and remounts it. Re-render = the function runs again to compute a new element tree; the Fiber (and its useState/useRef state) persists across this as long as the type and position match. State is only destroyed on an actual unmount, which reconciliation triggers specifically on type mismatch or key mismatch, not on every re-render.

Sibling Reconciliation (Keyed Lists)

The single-pass algorithm for diffing a list of children

React's list-diffing algorithm is a single forward pass, not a full LCS (longest common subsequence) computation — another deliberate simplification for speed. Conceptually:

  1. Walk both the old children list and the new children list simultaneously by index.
  2. For each position, if the keys match, treat it as an update-in-place (recurse into that element's diff).
  3. The moment keys stop matching at some index, React builds a Map of the remaining old children keyed by their key, then iterates the remaining new children, looking each one up in that map to detect moves (existing key, different position — reuse and move the DOM node) vs insertions (no matching key — mount fresh) vs deletions (leftover old children never matched — unmount).
Old: [A, B, C, D]  (keys)
New: [A, C, B, D]

Pass 1 (by index):
  index 0: A vs A  → match, update in place
  index 1: B vs C  → MISMATCH, fall into the keyed map algorithm for the rest

Remaining old (indices 1-3): B, C, D → build Map{B, C, D}
Remaining new (indices 1-3): C, B, D
  C → found in map at old index 2  → MOVE (existing DOM node relocated)
  B → found in map at old index 1  → MOVE
  D → found in map at old index 3  → same relative position → update in place

Result: 2 DOM move operations, 0 unmount/remounts — because every item kept its key
Why this matters for performance: moving an existing DOM node (and its subtree, including any focused input, video playback state, or CSS transition state) is far cheaper than destroying and recreating it — this is the entire practical payoff of correct keys beyond "no console warning."

Simplification note: The actual reconcileChildrenArray in React source also handles the case where old children have no keys — falling back to index-based matching for the keyless subset. The description above focuses on the keyed path, which is the interview-relevant algorithm. Additionally, there's special handling for single-child optimization (no list-diff needed) and text content shortcuts.

Type Change → Unmount + Remount

Why swapping element types is always destructive, and how to use this deliberately 
// ❌ Conditional swaps the element TYPE at the same position → full remount every toggle,
// losing focus, scroll position, and any internal state of the input each time
function SearchBox({ isExpanded }) {
  return isExpanded
    ? <input type="text" defaultValue="" />
    : <button>Search</button>;
}

// ✅ If you WANT a component to reset its internal state on some condition,
// type/key change is the correct, idiomatic tool — not a workaround
function Wizard({ stepId }) {
  // Changing `key` forces React to unmount the old FormStep and mount a
  // brand-new one, resetting all of its internal useState — intentional here
  // because each step's form fields must not leak into the next step.
  return <FormStep key={stepId} stepId={stepId} />;
}

This is the same mechanism used to "reset a component" idiomatically in React: changing a key is a deliberate, first-class way to force an unmount/remount cycle, distinct from the accidental version caused by conditionally rendering different element types at the same tree position.

Fragment & Portals in Reconciliation

How non-DOM-producing elements are handled by the reconciler

<>...</> (Fragment) doesn't produce a host DOM node — the reconciler flattens its children directly into the parent's child list during diffing, as if the Fragment wrapper weren't there for DOM purposes, while still being a real Fiber node internally (so a keyed Fragment, <Fragment key={id}>, can still participate correctly in list reconciliation without an extra wrapper <div>).

// Keyed fragments let you group multiple elements per list item
// without an extra DOM wrapper, while keeping correct list identity
{items.map((item) => (
  <Fragment key={item.id}>
    <dt>{item.term}</dt>
    <dd>{item.definition}</dd>
  </Fragment>
))}

createPortal is reconciled entirely within the normal React tree (same parent-child Fiber relationship, same event bubbling, same commit-phase ordering) — only the resulting DOM node's actual placement target differs. From the reconciler's perspective, a portal's children are diffed exactly like any other children; only the host-config's DOM insertion step is redirected to a different container element.

Why Keys Matter for Performance & State

The classic index-as-key bug, illustrated 
// ❌ index-as-key: deleting item 0 shifts every remaining item's key down by one,
// so React thinks item[1]'s content CHANGED at key=0, rather than item[0] being removed
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map((todo, index) => (
        <li key={index}>
          <input defaultValue={todo.text} /> {/* uncontrolled input KEEPS its DOM identity */}
        </li>
      ))}
    </ul>
  );
}
// Symptom: delete the first todo, and the text still showing in each remaining
// input is now off-by-one — the DOM nodes were reused for the WRONG logical items,
// because their key (the index) didn't change even though what they represent did.
// ✅ stable, unique key = each DOM node (and its uncontrolled input's live value)
// travels with its correct logical item regardless of what gets removed around it
{todos.map((todo) => (
  <li key={todo.id}>
    <input defaultValue={todo.text} />
  </li>
))}
This bug is invisible with controlled inputs (value driven by React state) because the displayed value comes from props on every render regardless of DOM node identity — it only manifests with uncontrolled inputs, CSS transitions, focus, or any state that lives directly on the DOM node rather than in React. This is exactly why the bug is so commonly missed in code review: it doesn't show up until QA (or a user) interacts with an uncontrolled field in a reorderable list.

When VDOM Overhead Hurts (High-Frequency Updates)

The cost the Virtual DOM doesn't eliminate

Every React update — no matter how small — pays for: re-running the component function, allocating a new element tree, walking it to diff against the Fiber tree, and (if anything changed) committing DOM mutations. For occasional updates (a button click, a form submission) this cost is imperceptible. For updates driven at animation frame rates (dragging, scrubbing, live cursors, real-time charts updating 60 times/second), that per-frame overhead — even when the diff itself finds "nothing changed" — competes with the browser's actual frame budget (~16.6ms at 60fps).

// ❌ Driving a drag interaction through React state re-renders the whole
// subtree on every pointermove event, competing with layout/paint for frame budget
function DraggableBox() {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return (
    <div
      onPointerMove={(e) => setPos({ x: e.clientX, y: e.clientY })}
      style={{ transform: `translate(${pos.x}px, ${pos.y}px)` }}
    />
  );
}

// ✅ Mutate the DOM node directly via a ref for the high-frequency part,
// bypassing React's render/diff/commit cycle entirely for every intermediate frame
function DraggableBox() {
  const ref = useRef(null);
  const onPointerMove = (e) => {
    ref.current.style.transform = `translate(${e.clientX}px, ${e.clientY}px)`;
  };
  return <div ref={ref} onPointerMove={onPointerMove} />;
}
This is exactly why animation libraries bypass React's state: Framer Motion, React Spring, and GSAP all update DOM/CSS properties imperatively outside the render cycle for the animated frames themselves, and only sync back into React state at the start/end of a gesture (or not at all) — because paying the reconciliation cost per animation frame is the actual performance ceiling, not something the Virtual DOM's efficient diffing can optimize away.

Fine-Grained Reactivity Comparison (Signals, Solid.js)

How signal-based frameworks avoid the diff entirely

React's model: state change → re-run a whole component function → produce a new element (sub)tree → diff it against the previous tree → commit the delta. Signal-based frameworks (SolidJS, Svelte 5 runes, Vue's reactivity system, Preact Signals) invert this: at compile/setup time, they build a direct subscription graph between individual reactive values (signals) and the exact DOM text nodes/attributes that read them. A signal update triggers only those specific DOM writes — there is no component re-execution and no tree diff at all.

React model:
  setState → re-run Component() → new element tree → diff vs old Fiber tree → patch DOM
             (whole subtree re-executes even if only one text node actually changed)

Signal model (SolidJS-style):
  signal.set(value) → direct subscriber list lookup → surgical DOM node.textContent = value
             (component function body only ever runs ONCE, at initial setup)
React (Virtual DOM)Signals (SolidJS/Svelte 5)
Update unitComponent (re-executes function body)Individual DOM binding (surgical)
Diffing needed?Yes, every updateNo — direct subscription, no diff
Mental modelRe-render the world, let React figure out the deltaDeclare exactly what depends on what, upfront
Ecosystem/tooling maturityExtremely matureSmaller but growing fast
Interview-ready framing: "React's diffing exists to reconcile the mismatch between a re-run-the-whole-function programming model and a mutate-only-what-changed DOM reality. Fine-grained reactive systems eliminate that mismatch at the source by tracking dependencies precisely, at the cost of a more constrained, compiler-dependent programming model." That sentence alone answers "have you thought about alternatives to VDOM" convincingly.

React Compiler — Reducing VDOM Overhead

Automatic memoization without eliminating the VDOM model

React Compiler (formerly "React Forget") does not remove the Virtual DOM or reconciliation — it automatically inserts the equivalent of useMemo/useCallback/React.memo around values, callbacks, and JSX subtrees based on static analysis of your component, so unrelated state changes don't re-run computations or re-create element trees for subtrees that couldn't have changed. It attacks the "component re-executes unnecessarily" cost, not the "diffing itself is slow" cost — those are different problems, and the compiler only solves the first one.

// Before React Compiler: `ExpensiveChild` re-renders every time `Parent` re-renders,
// because `data` is a fresh array reference, breaking a manual React.memo comparison
function Parent({ items }) {
  const data = items.filter((i) => i.active); // new array reference every render
  return <ExpensiveChild data={data} />;
}

// The compiler automatically memoizes `data` (and the resulting element) based on
// its detected dependencies, equivalent to hand-written useMemo — without you writing it
Key distinction for the interview: React Compiler reduces how often reconciliation has meaningful work to do by skipping unchanged subtrees more aggressively than manual memoization typically achieves in practice — it does not change the underlying O(n) heuristic diffing algorithm itself, and it does not make React "fine-grained" in the SolidJS sense (components still re-execute; the compiler just makes the skip-if-unchanged check automatic and more precise).

Status (2024): The React Compiler is open-source, shipped in production at Meta (Instagram), and available as babel-plugin-react-compiler (RC). It's not yet recommended for all projects, but it's well past theoretical — cite it as "shipping at Meta, available as an RC Babel plugin" in interviews.

Production Performance Implications

Incident: Draggable Kanban Board Dropping Frames
Ticket: "Dragging a card in the Kanban board feels janky on mid-range Android devices — frame rate visibly drops below 30fps during drag, though it's smooth on desktop."

Environment: React 18 project-management SPA, drag-and-drop implemented with per-card useState tracking cursor-relative offset, updated on every pointermove.

Investigation

// React DevTools Profiler, recording during a drag gesture:
// - ~45 renders/second during drag (matches pointermove firing rate)
// - Each render: Board (200+ card components) re-rendering, not just the dragged card
// - "Why did this render?" showed: Board's own state held the drag offset,
//   causing EVERY card in the list to re-render on each pointermove tick,
//   not just the one being dragged

Root Cause

The dragged card's position was lifted into the parent Board component's state (a common pattern for "the parent needs to know where the drop will land"), so every pointermove-driven setState re-rendered Board and, transitively, its full list of 200+ Card children — each one re-executing its function body and going through reconciliation, even though 199 of them had literally nothing to update.

Resolution

// BEFORE: offset lived in Board's state, re-rendering all cards per pointermove
function Board() {
  const [dragOffset, setDragOffset] = useState(null);
  // ...passed dragOffset down, causing all Card children to re-render
}

// AFTER: the dragged card's visual offset is applied via direct DOM mutation
// (ref + style.transform) during the gesture; React state is only updated
// ONCE at drag-end to commit the final column/position
function Card({ id }) {
  const ref = useRef(null);
  const onPointerMove = (e) => {
    ref.current.style.transform = `translate(${e.movementX}px, ${e.movementY}px)`;
  };
  const onPointerUp = () => {
    // Single, final setState — this is the only point reconciliation runs for the drag
    commitFinalPosition(id, ref.current.getBoundingClientRect());
  };
  return <div ref={ref} onPointerMove={onPointerMove} onPointerUp={onPointerUp} />;
}

Lessons Learned

  • High-frequency pointer events should drive direct DOM mutation, not React state, and only "settle" into React state at the end of the gesture.
  • "Why did this render?" in DevTools Profiler was the single most useful signal — it immediately pointed at the lifted state as the fan-out cause.
  • Added a Playwright-based frame-rate regression test that fails CI if a drag gesture drops below 50fps on a throttled CPU profile.

Code Examples

Testing reconciliation-sensitive behavior 
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('uncontrolled input keeps its value attached to the correct item after deletion', async () => {
  const user = userEvent.setup();
  const { rerender } = render(<TodoList todos={[{ id: 1, text: 'a' }, { id: 2, text: 'b' }]} />);

  const inputs = screen.getAllByRole('textbox');
  await user.clear(inputs[1]);
  await user.type(inputs[1], 'edited-b');

  // Remove the first todo — with a correct key={todo.id}, the remaining
  // input (now the only one) must still show "edited-b", not the original "b"
  rerender(<TodoList todos={[{ id: 2, text: 'b' }]} />);
  expect(screen.getByRole('textbox')).toHaveValue('edited-b');
});

This test fails with key={index} and passes with key={todo.id} — a concrete, runnable demonstration of the identity bug from the "Why Keys Matter" section above, useful to reference verbatim if an interviewer asks "how would you test for this."

Common Mistakes

Mistakes senior engineers still make
  • key={index} on reorderable/filterable lists — works fine visually for static lists, breaks silently for uncontrolled inputs, animations, or any DOM-attached state once items can move.
  • Believing re-render means re-mount — leads to unnecessary defensive code (re-fetching data in every render body "just in case") when the actual concern should be about effect dependencies, not reconciliation.
  • Conditionally rendering different element types at the same position to "hide" content, instead of using CSS display/visibility, when preserving state/DOM identity across the toggle is actually desired.
  • Driving high-frequency interactions (drag, scrub, live cursors) entirely through React state, paying a reconciliation cost every frame instead of mutating the DOM directly and settling into state only at the gesture's end.
  • Using array index as key and calling it "good enough" without checking whether the list is ever reordered, filtered, or has items inserted/removed from the middle — the failure mode is often invisible until much later in the component's life.

Trade-offs

Alternative approaches and their costs
  • Virtual DOM (React) vs fine-grained reactivity (SolidJS/Svelte): React trades some runtime overhead (function re-execution + diffing) for a simpler mental model (just re-render, let the framework figure out the DOM delta) and a vastly larger existing ecosystem; signal-based frameworks trade a more constrained, compiler-dependent authoring model for near-zero-overhead surgical updates.
  • Correct keys vs index keys: stable keys cost a small amount of extra bookkeeping (usually already-available IDs) in exchange for correctness under reordering; index keys are "free" but only safe for lists that are provably static in order and membership.
  • React Compiler's automatic memoization vs manual useMemo/React.memo: automatic memoization removes a whole class of "forgot to memoize" bugs and stale-dependency-array bugs, at the cost of relying on a build-time compiler whose static analysis has documented rule constraints (Rules of React) your code must follow to benefit.
  • Direct DOM mutation for animation vs React-state-driven animation: direct mutation is dramatically cheaper per frame but sacrifices React's declarative guarantees for that code path — it must be manually kept in sync if the component also has React-driven state that affects the same DOM node.

Follow-up Interview Questions

Q1: If two sibling elements swap positions and both keep the same key, does React re-render their contents?

Strong answer: No — if the props are otherwise unchanged, React recognizes the same key at a new index as the same logical element and performs a DOM move operation, not a content update. Its internal state and DOM identity (focus, uncontrolled input value, CSS transition state) travel with it. If props did change in addition to the position, React still reuses the same Fiber/DOM node but applies a prop update on top of the move.

Q2: Why can't you use array index as a key even if you add/remove only from the end of the list?

Strong answer: you actually can, safely, in that specific case — index keys are only unsafe when items can be inserted/removed/reordered anywhere except the very end, because that's the only scenario where an item's index changes across renders while its logical identity doesn't. The rule isn't "never use index as key," it's "don't use index as key when index and identity can diverge," which interviewers use to check whether you understand the mechanism rather than a memorized rule.

Q3: Does React.memo change how reconciliation's diffing algorithm behaves?

Strong answer: no — React.memo is a pre-check that runs before reconciliation would even re-execute a component's function: if the shallow prop comparison says props are unchanged, React skips re-rendering that component (and reuses its previous element output) entirely, so the diffing algorithm never even sees new elements for that subtree. It's an opt-out of doing the render-phase work in the first place, not a change to how diffing itself decides update/move/remount for elements that do get compared.

Q4: How would you explain to a teammate why their list's exit animations broke after they "fixed" the key warning by switching from index to item.id?

Strong answer: most naive "animate list item removal" implementations rely on the removed item's DOM node still existing briefly during an exit transition, which requires the list to still render it (often via a library like Framer Motion's AnimatePresence tracking keys internally). If the surrounding code was accidentally depending on index-based key churn to force remounts that happened to look like a transition, switching to stable keys removes that (accidental, fragile) behavior — the correct fix is to implement exit animations explicitly (keeping "exiting" items in a local state array until their animation completes) rather than relying on key-churn side effects.

Q5: A senior candidate claims "the Virtual DOM is always faster than direct DOM manipulation." How do you push back?

Strong answer: that claim is false in general — hand-written, surgical direct DOM manipulation for a known, narrow update is always at least as fast as going through React's render/diff/commit pipeline, because it skips the function re-execution and diffing steps entirely. The Virtual DOM's actual value proposition is developer ergonomics and correctness at scale: it lets you write simple, declarative "re-render the whole thing" code without hand-tracking every possible state transition's minimal DOM delta yourself, while still being fast enough for the vast majority of UI update patterns. The honest framing is "fast enough, with a vastly better authoring experience for typical UI code" — not "always faster."

Summary

Key mental models for the interview:

  • The Virtual DOM is a diffing input, not the speedup itself. The speedup comes from minimizing real DOM mutations, which are the expensive operation.
  • Same type + same key = update in place. Different type = destroy and rebuild. Those two rules are the entire heuristic; everything else follows from them.
  • Keys are identity, not styling. They tell React which old element a new element corresponds to — critical for correct behavior with any DOM-attached state (uncontrolled inputs, focus, CSS transitions).
  • Re-render ≠ re-mount. A component's Fiber (and hook state) survives across re-renders as long as type and key are stable; only an actual type/key mismatch destroys it.
  • Fine-grained reactivity is a different trade-off, not a strictly better one. Signals eliminate diffing overhead by constraining the programming model; React accepts diffing overhead for a simpler, more flexible one.

What NOT to say in an interview:

  • ❌ "The Virtual DOM makes updates instant" — it makes the common case fast enough; it doesn't make updates free, especially at high frequency.
  • ❌ "React diffs the real DOM" — it diffs two in-memory tree representations; the real DOM is only touched during commit.
  • ❌ "Just always use index as key, React handles it" — true only for provably static-order, non-reorderable, non-filterable lists.
  • ❌ "Signal-based frameworks are strictly better/worse than React" — they represent a different point on the ergonomics-vs-overhead trade-off curve, not a strict improvement.

Promises & Async Internals

"Walk through the internal mechanics of Promises. How does async/await desugar, and what are the scheduling implications?"

Key Takeaway: A Promise is a state machine (pending → fulfilled/rejected) whose .then() callbacks are scheduled as microtasks. async/await desugars to generator-like coroutines that suspend and resume via Promise resolution. Understanding this machinery explains why await doesn't yield to the browser, why error propagation differs from try/catch, and how to build cancellation, retry, and timeout patterns on top of the primitive.

Interviewer's Intent

What the interviewer is really testing

This question separates candidates who use Promises from those who understand how they work at the specification level. The interviewer wants to see:

  • Spec-level understanding: Can you describe [[PromiseState]], [[PromiseResult]], and the reaction queues? Do you know why resolve(thenable) costs an extra microtask tick?
  • Microtask scheduling: Can you predict execution order in complex async scenarios? Do you understand the relationship between the microtask queue and the event loop?
  • async/await desugaring: Can you rewrite an async function as its equivalent generator + Promise machinery? Do you know why consecutive awaits are sequential?
  • Production patterns: Can you implement retry, timeout, cancellation, and concurrency control from primitives? Have you debugged real Promise-related failures?

Senior candidates should be able to explain the why behind design decisions — not just describe behavior, but rationalize it from first principles.

60-Second Answer

Concise answer for time-pressured interviews

A Promise is a state machine with three states: pending, fulfilled, and rejected. Transitions are one-way and irreversible. When you call .then(), callbacks are never invoked synchronously — they're enqueued as microtasks, guaranteeing consistent async behavior regardless of whether the Promise is already settled.

async/await is syntactic sugar over the coroutine pattern. An async function returns a Promise. Each await suspends the function's execution context, wraps the operand in Promise.resolve(), and attaches a continuation as a microtask. This desugars conceptually to a generator that yields Promises, with a runner that calls .next() on each resolution.

Scheduling implication: Microtasks run to exhaustion before the browser can paint or process macrotasks. A long chain of awaits or recursive .then() calls blocks rendering. Error propagation via rejection flows through the chain until caught — unlike synchronous try/catch, an uncaught rejection in a .then() chain doesn't stop execution of the surrounding code.

Production impact: This model enables patterns like Promise.all for concurrency, AbortController for cancellation, and exponential backoff for retry — but demands explicit error handling at every async boundary.

Eager Evaluation

Critical distinction: The executor function runs synchronously during Promise construction. The Promise is eagerly evaluated — side effects happen immediately.

console.log('1: before constructor');

const p = new Promise((resolve, reject) => {
  console.log('2: executor runs SYNCHRONOUSLY');
  resolve('done');
  console.log('3: still runs after resolve');
});

console.log('4: after constructor');

p.then(val => console.log('5: microtask -', val));

console.log('6: before microtask drains');

// Output: 1, 2, 3, 4, 6, 5

The executor runs in the same synchronous turn. Only the .then() callback is deferred as a microtask. This is why you see console.log('3') execute even after resolve() — calling resolve doesn't return or throw.

Promise Resolution Procedure

What happens internally when resolve() is called

Simple Value Resolution

When resolve(value) is called with a non-thenable, non-Promise value:

  1. Set [[PromiseState]] to "fulfilled"
  2. Set [[PromiseResult]] to value
  3. Trigger all reactions in [[PromiseFulfillReactions]] as microtasks
  4. Clear both reaction lists

resolve(thenable) — Recursive Unwrapping

// When resolve() receives a thenable, it unwraps it:
const p = new Promise((resolve) => {
  resolve({ then(onFulfill) { onFulfill(42); } });
});
// p eventually fulfills with 42, NOT the thenable object

// This unwrapping costs an extra microtask tick

resolve(promise) — Adoption

const inner = new Promise(resolve => setTimeout(() => resolve('inner'), 100));
const outer = new Promise(resolve => resolve(inner));

// outer "adopts" inner's eventual state
// outer won't settle until inner settles
// This creates a "PromiseResolveThenableJob" — an extra microtask

The Extra Microtask Tick

Performance implication: resolve(promise) creates one additional microtask compared to resolve(value). This is because the spec requires calling the thenable's .then() method in a new microtask job (PromiseResolveThenableJob) to prevent synchronous recursion and ensure consistent ordering.

Promise.resolve()
  .then(() => console.log('A'))  // microtask 1

new Promise(resolve => resolve(Promise.resolve()))
  .then(() => console.log('B'))  // microtask 3 (extra tick!)

Promise.resolve()
  .then(() => console.log('C'))  // microtask 2

// Output: A, C, B
// B is delayed because resolve(Promise) creates PromiseResolveThenableJob

Thenable Assimilation

Duck typing, cross-realm thenables, and microtask cost

Thenable vs Promise

ConceptDefinitionExample
ThenableAny object with a .then method{ then(cb) { cb(1); } }
PromiseObject created by Promise constructor or Promise.resolvenew Promise(r => r(1))

Duck Typing Check

// Spec algorithm (simplified):
function isThenable(value) {
  if (value === null || (typeof value !== 'object' && typeof value !== 'function')) {
    return false;
  }
  const then = value.then; // Property access — can trigger getters!
  return typeof then === 'function';
}

Security concern: The .then property access can trigger a getter, which means a malicious thenable could run arbitrary code during resolution. The spec isolates this by running it in a separate microtask (PromiseResolveThenableJob).

Cross-Realm Thenables

Promises from different realms (iframes, workers, different V8 contexts) are not the same Promise constructor. The spec uses thenable assimilation (duck typing) rather than instanceof checks to ensure interoperability:

// iframe's Promise !== window's Promise
const iframePromise = iframe.contentWindow.eval('Promise.resolve(42)');

// This works because of thenable assimilation:
Promise.resolve(iframePromise).then(val => console.log(val)); // 42

Microtask Cost

Every thenable assimilation creates one additional PromiseResolveThenableJob microtask. In deeply nested thenable chains, this adds up:

// Each level adds a microtask tick:
const t3 = { then(cb) { cb(1); } };               // +1 tick
const t2 = { then(cb) { cb(t3); } };              // +2 ticks
const t1 = { then(cb) { cb(t2); } };              // +3 ticks
Promise.resolve(t1).then(v => console.log(v));    // 1 (after 3 extra ticks)

Microtask Scheduling of .then() Callbacks

Scheduling guarantees, ordering, and design rationale

Key Invariant: .then() Is Never Synchronous

Even when a Promise is already fulfilled, .then() callbacks are always scheduled as microtasks — never called synchronously. This prevents Zalgo (unpredictable sync/async behavior).

Two Cases

Promise StateWhat .then() Does
Already settledImmediately enqueues callback as a microtask
Still pendingStores callback in [[PromiseFulfillReactions]]; enqueued later when settled

Order Guarantees

const p = Promise.resolve('value');

p.then(() => console.log('A'));
p.then(() => console.log('B'));
p.then(() => console.log('C'));

// Always: A, B, C — order of .then() attachment is preserved

Complete Timing Example

console.log('1: sync start');

setTimeout(() => console.log('2: macrotask'), 0);

Promise.resolve()
  .then(() => {
    console.log('3: microtask 1');
    return Promise.resolve();
  })
  .then(() => console.log('4: microtask 2'));

Promise.resolve().then(() => console.log('5: microtask 1b'));

queueMicrotask(() => console.log('6: raw microtask'));

console.log('7: sync end');

// Output: 1, 7, 3, 5, 6, 4, 2
// Explanation:
// - Sync: 1, 7
// - Microtask queue drains: 3, 5, 6 (all level-1 microtasks)
// - 3's .then returns a Promise, so 4 is queued after current batch
// - 4 runs in next microtask batch
// - Macrotask: 2

Design Rationale

The always-async guarantee exists to prevent "release Zalgo" — a term coined by Isaac Z. Schlueter describing APIs that sometimes call callbacks synchronously and sometimes asynchronously. This unpredictability causes subtle race conditions. By always deferring to microtask, Promise behavior is deterministic regardless of settlement timing.

Desugaring to Generator + Promise

// Original:
async function example() {
  const a = await fetchA();
  const b = await fetchB(a);
  return a + b;
}

// Desugared equivalent:
function example() {
  return new Promise((resolve, reject) => {
    const gen = (function* () {
      try {
        const a = yield fetchA();
        const b = yield fetchB(a);
        return a + b;
      } catch (e) {
        throw e;
      }
    })();

    function step(nextFn) {
      let result;
      try {
        result = nextFn();
      } catch (e) {
        return reject(e);
      }
      if (result.done) {
        return resolve(result.value);
      }
      Promise.resolve(result.value).then(
        value => step(() => gen.next(value)),
        err => step(() => gen.throw(err))
      );
    }

    step(() => gen.next());
  });
}

V8 Optimization: Zero-Cost Async Stack Traces

V8 (since 2019) captures async stack traces at near-zero cost by tracking the Promise chain at await points rather than capturing full stacks. The --async-stack-traces flag is enabled by default. This means Error.stack in async functions shows the full async call path.

Implicit Microtask at Each await

async function three() {
  console.log('A');           // sync
  await Promise.resolve();   // suspend → 1 microtask
  console.log('B');           // resumes in microtask
  await Promise.resolve();   // suspend → 1 microtask
  console.log('C');           // resumes in microtask
}

three();
console.log('D');

// Output: A, D, B, C
// Each await adds at minimum one microtask boundary

Why Consecutive Awaits Are Sequential

// ❌ SEQUENTIAL — each await waits for the previous
async function slow() {
  const a = await fetchA(); // 200ms
  const b = await fetchB(); // 200ms
  return a + b;             // Total: 400ms
}

// ✅ CONCURRENT — start both, await together
async function fast() {
  const [a, b] = await Promise.all([fetchA(), fetchB()]);
  return a + b;             // Total: 200ms
}

Each await suspends execution until the awaited Promise resolves. The next line doesn't execute (and therefore doesn't start the next async operation) until resumption. This is by design — it gives async code the readability of synchronous code.

Error Propagation & Unhandled Rejections

.catch() semantics, unhandled rejections, and AggregateError

.catch() vs try/catch

// Promise chain — .catch() handles rejection
fetchData()
  .then(transform)
  .then(save)
  .catch(err => {
    // Catches rejection from fetchData, transform, OR save
    console.error('Pipeline failed:', err);
  });

// async/await — try/catch handles rejection
async function pipeline() {
  try {
    const data = await fetchData();
    const transformed = await transform(data);
    await save(transformed);
  } catch (err) {
    // Same behavior — catches any rejection in the chain
    console.error('Pipeline failed:', err);
  }
}

Error Propagation Through .then Chains

Promise.resolve(1)
  .then(v => { throw new Error('oops'); })
  .then(v => console.log('skipped'))  // skipped!
  .then(v => console.log('also skipped'))  // skipped!
  .catch(err => {
    console.log('caught:', err.message); // 'oops'
    return 'recovered';
  })
  .then(v => console.log(v)); // 'recovered'

Unhandled Rejection Detection

// Browser:
window.addEventListener('unhandledrejection', event => {
  console.error('Unhandled rejection:', event.reason);
  event.preventDefault(); // Prevents default logging
});

// Node.js:
process.on('unhandledRejection', (reason, promise) => {
  console.error('Unhandled rejection at:', promise, 'reason:', reason);
});

// Detection timing: the engine checks at end of microtask checkpoint
// A Promise is "handled" if .catch() is attached before the check

Why Forgotten .catch() Is Dangerous

An unhandled rejection doesn't throw — it fails silently unless you listen for the event. In Node.js 15+, unhandled rejections terminate the process. In browsers, they log a console error but the app continues in a potentially corrupt state.

Promise.prototype.finally

fetchData()
  .then(process)
  .catch(handleError)
  .finally(() => {
    // Runs regardless of fulfillment or rejection
    // Does NOT receive the value/reason
    // Return value is ignored (passes through previous result)
    // UNLESS it throws or returns a rejected Promise
    hideLoadingSpinner();
  });

AggregateError with Promise.any

const results = await Promise.any([
  fetch('/api/primary'),
  fetch('/api/secondary'),
  fetch('/api/tertiary'),
]).catch(err => {
  // Only rejects if ALL promises reject
  console.log(err instanceof AggregateError); // true
  console.log(err.errors); // Array of all rejection reasons
  console.log(err.errors.length); // 3
});

Promise Combinators

all, allSettled, race, any — semantics and comparison

Comparison Table

CombinatorResolves WhenRejects WhenResult Type
Promise.allAll fulfillFirst rejection (fail-fast)Array of values
Promise.allSettledAll settleNever rejectsArray of {status, value/reason}
Promise.raceFirst to settle (fulfill or reject)First to settle (if rejected)Single value/reason

Promise.all — Fail-Fast

// All must succeed; first failure rejects immediately
const [users, posts, comments] = await Promise.all([
  fetchUsers(),
  fetchPosts(),
  fetchComments()
]);
// If fetchPosts() rejects, the whole thing rejects immediately
// But fetchUsers() and fetchComments() continue running (not cancelled!)

Promise.allSettled — Never Rejects

const results = await Promise.allSettled([
  fetchCritical(),
  fetchOptional(),
  fetchNiceToHave()
]);

const succeeded = results.filter(r => r.status === 'fulfilled');
const failed = results.filter(r => r.status === 'rejected');
// Use when you want all results regardless of individual failures

Promise.race — First Settles Wins

// Classic timeout pattern:
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error(`Timeout after ${ms}ms`)), ms)
  );
  return Promise.race([promise, timeout]);
}

Promise.any — First Fulfills Wins

// Hedged request — try multiple sources, use first success
const data = await Promise.any([
  fetchFromCache(),
  fetchFromCDN(),
  fetchFromOrigin()
]);
// Only rejects if ALL three fail

Custom Combinator: Promise.some(n)

// Resolve when at least n promises fulfill
function promiseSome(promises, n) {
  return new Promise((resolve, reject) => {
    const results = [];
    let rejections = 0;
    const total = promises.length;

    if (n > total) {
      return reject(new RangeError(`Cannot fulfill ${n} from ${total} promises`));
    }

    promises.forEach((p, i) => {
      Promise.resolve(p).then(
        value => {
          results.push(value);
          if (results.length === n) resolve(results);
        },
        () => {
          rejections++;
          if (rejections > total - n) {
            reject(new AggregateError([], `Only ${total - rejections} fulfilled, needed ${n}`));
          }
        }
      );
    });
  });
}

AbortController & Cancellation Patterns

Why Promises aren't cancellable, and how to work around it

Why Promises Aren't Natively Cancellable

A Promise represents an eventual value — it's a read handle. Cancellation is a write operation (stopping computation). The spec intentionally separates these concerns. Multiple consumers can observe the same Promise; cancellation by one would break others.

AbortController + AbortSignal Pattern

const controller = new AbortController();
const { signal } = controller;

// Pass signal to fetch
const response = await fetch('/api/data', { signal });

// Cancel from outside:
controller.abort();
// fetch rejects with AbortError: "The user aborted a request."

Custom Async Operations with AbortSignal

async function pollUntilReady(url, { signal } = {}) {
  while (true) {
    signal?.throwIfAborted(); // Check before each iteration

    const res = await fetch(url, { signal });
    const data = await res.json();

    if (data.status === 'ready') return data;

    await new Promise((resolve, reject) => {
      const timer = setTimeout(resolve, 1000);
      signal?.addEventListener('abort', () => {
        clearTimeout(timer);
        reject(signal.reason);
      }, { once: true });
    });
  }
}

Timeout with AbortSignal.timeout()

// Modern approach (supported in Node 17.3+, modern browsers):
const response = await fetch('/api/slow', {
  signal: AbortSignal.timeout(5000) // Auto-aborts after 5s
});

// Composing signals:
const controller = new AbortController();
const timeoutSignal = AbortSignal.timeout(5000);

// Abort on either user action OR timeout:
const combined = AbortSignal.any([controller.signal, timeoutSignal]);
const response = await fetch('/api/data', { signal: combined });

Production Example: Cancellable Search

class SearchService {
  #controller = null;

  async search(query) {
    // Cancel previous in-flight request
    this.#controller?.abort();
    this.#controller = new AbortController();

    try {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(query)}`,
        { signal: this.#controller.signal }
      );
      return await response.json();
    } catch (err) {
      if (err.name === 'AbortError') {
        return null; // Silently ignore cancelled requests
      }
      throw err; // Re-throw real errors
    }
  }
}

Symbol.asyncIterator, generators, and streaming patterns

Symbol.asyncIterator Protocol

const asyncIterable = {

    let i = 0;
    return {
      async next() {
        if (i >= 3) return { done: true, value: undefined };

for await (const val of asyncIterable) {
  console.log(val); // 0, 1, 2 — each after 100ms
}

AsyncGenerator Functions

async function* paginate(url) {
  let nextPage = url;
  while (nextPage) {
    const response = await fetch(nextPage);
    const data = await response.json();
    yield data.items;
    nextPage = data.nextPageUrl;
  }
}

// Consume:
for await (const page of paginate('/api/items?page=1')) {
  renderItems(page);
}

Streaming Data Consumption

async function* readStream(stream) {
  const reader = stream.getReader();
  try {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      yield value;
    }
  } finally {
    reader.releaseLock();
  }
}

// Process a Response body as chunks:
const response = await fetch('/api/large-file');
for await (const chunk of readStream(response.body)) {
  processChunk(chunk);
}

Backpressure Considerations

Backpressure: for-await-of naturally applies backpressure — it won't call .next() until the current iteration completes. This means slow consumers automatically slow down fast producers. However, if you buffer items (e.g., in an array), you lose this guarantee and risk unbounded memory growth.

Structured Concurrency Patterns

Sequential vs concurrent, semaphores, and task queues

Sequential vs Concurrent

// Sequential: 3 seconds total
async function sequential() {
  const a = await taskA(); // 1s
  const b = await taskB(); // 1s
  const c = await taskC(); // 1s
  return [a, b, c];
}

// Concurrent: 1 second total (all run in parallel)
async function concurrent() {
  return Promise.all([taskA(), taskB(), taskC()]);
}

// Mixed: some dependent, some independent
async function mixed() {
  const [a, b] = await Promise.all([taskA(), taskB()]);
  const c = await taskC(a, b); // depends on a and b
  return c;
}

Semaphore Pattern (Limiting Concurrency)

class Semaphore {
  #queue = [];
  #active = 0;

  constructor(limit) {
    this.limit = limit;
  }

  async acquire() {
    if (this.#active < this.limit) {
      this.#active++;
      return;
    }
    await new Promise(resolve => this.#queue.push(resolve));
  }

  release() {
    this.#active--;
    if (this.#queue.length > 0) {
      this.#active++;
      const next = this.#queue.shift();
      next();
    }
  }

  async run(fn) {
    await this.acquire();
    try {
      return await fn();
    } finally {
      this.release();
    }
  }
}

// Usage: limit to 3 concurrent requests
const sem = new Semaphore(3);
const results = await Promise.all(
  urls.map(url => sem.run(() => fetch(url)))
);

Task Queue with Concurrency Control

async function mapWithConcurrency(items, fn, concurrency) {
  const results = new Array(items.length);
  let index = 0;

  async function worker() {
    while (index < items.length) {
      const i = index++;
      results[i] = await fn(items[i], i);
    }
  }

  const workers = Array.from(
    { length: Math.min(concurrency, items.length) },
    () => worker()
  );

  await Promise.all(workers);
  return results;
}

// Process 100 items with max 5 concurrent operations
const results = await mapWithConcurrency(items, processItem, 5);

Error Handling in Concurrent Operations

// Strategy 1: Fail-fast (Promise.all behavior)
// First error aborts — but other operations keep running!

// Strategy 2: Collect all errors (Promise.allSettled)
const results = await Promise.allSettled(tasks.map(execute));
const errors = results
  .filter(r => r.status === 'rejected')
  .map(r => r.reason);
if (errors.length) throw new AggregateError(errors);

// Strategy 3: Fail-fast with cleanup
async function allWithCleanup(tasks, cleanup) {
  const controller = new AbortController();
  try {
    return await Promise.all(
      tasks.map(t => t(controller.signal))
    );
  } catch (err) {
    controller.abort();
    await cleanup?.();
    throw err;
  }
}

Production Patterns

Retry, timeout, debounce, circuit breaker, and resource pools

Retry with Exponential Backoff

async function retry(fn, {
  maxAttempts = 3,
  baseDelay = 1000,
  maxDelay = 30000,
  backoffFactor = 2,
  retryOn = () => true,
  signal
} = {}) {
  let lastError;

  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    try {
      signal?.throwIfAborted();
      return await fn(attempt);
    } catch (err) {
      lastError = err;

      if (attempt === maxAttempts - 1) break;
      if (!retryOn(err, attempt)) break;

      const delay = Math.min(
        baseDelay * Math.pow(backoffFactor, attempt) + Math.random() * 1000,
        maxDelay
      );

      await new Promise((resolve, reject) => {
        const timer = setTimeout(resolve, delay);
        signal?.addEventListener('abort', () => {
          clearTimeout(timer);
          reject(signal.reason);
        }, { once: true });
      });
    }
  }

  throw lastError;
}

Timeout Wrapper

function withTimeout(fn, ms, message = `Operation timed out after ${ms}ms`) {
  return async (...args) => {
    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), ms);

    try {
      return await fn(...args, { signal: controller.signal });
    } catch (err) {
      if (err.name === 'AbortError') {
        throw new Error(message);
      }
      throw err;
    } finally {
      clearTimeout(timer);
    }
  };
}

Debounced Async (Latest-Wins)

function debouncedAsync(fn, delay) {
  let timer = null;
  let activeController = null;

  return function (...args) {
    // Cancel previous timer
    clearTimeout(timer);
    // Abort previous in-flight request
    activeController?.abort();

    return new Promise((resolve, reject) => {
      timer = setTimeout(async () => {
        activeController = new AbortController();
        try {
          const result = await fn(...args, {
            signal: activeController.signal
          });
          resolve(result);
        } catch (err) {
          if (err.name !== 'AbortError') reject(err);
        }
      }, delay);
    });
  };
}

Circuit Breaker Pattern

class CircuitBreaker {
  #state = 'CLOSED'; // CLOSED, OPEN, HALF_OPEN
  #failures = 0;
  #lastFailure = 0;

  constructor({ threshold = 5, resetTimeout = 30000 } = {}) {
    this.threshold = threshold;
    this.resetTimeout = resetTimeout;
  }

  async execute(fn) {
    if (this.#state === 'OPEN') {
      if (Date.now() - this.#lastFailure > this.resetTimeout) {
        this.#state = 'HALF_OPEN';
      } else {
        throw new Error('Circuit is OPEN — request blocked');
      }
    }

    try {
      const result = await fn();
      this.#onSuccess();
      return result;
    } catch (err) {
      this.#onFailure();
      throw err;
    }
  }

  #onSuccess() {
    this.#failures = 0;
    this.#state = 'CLOSED';
  }

  #onFailure() {
    this.#failures++;
    this.#lastFailure = Date.now();
    if (this.#failures >= this.threshold) {
      this.#state = 'OPEN';
    }
  }

  get state() { return this.#state; }
}

Resource Pool Pattern

class Pool {
  #available = [];
  #waiting = [];

  constructor(factory, size) {
    for (let i = 0; i < size; i++) {
      this.#available.push(factory());
    }
  }

  async acquire() {
    if (this.#available.length > 0) {
      return this.#available.pop();
    }
    return new Promise(resolve => this.#waiting.push(resolve));
  }

  release(resource) {
    if (this.#waiting.length > 0) {
      const next = this.#waiting.shift();
      next(resource);
    } else {
      this.#available.push(resource);
    }
  }

  async use(fn) {
    const resource = await this.acquire();
    try {
      return await fn(resource);
    } finally {
      this.release(resource);
    }
  }
}

Production Incident

Silent payment failures from unhandled Promise rejections

Incident Report: Unhandled Promise Rejections in Payment Flow

Symptoms

  • Customer payments were being charged but order confirmations weren't sent
  • No errors in application logs
  • Monitoring dashboards showed normal error rates
  • Customer complaints started after a deployment 3 days earlier

Root Cause

// The problematic code:
async function processPayment(order) {
  const charge = await paymentGateway.charge(order.amount);

  // This Promise was NOT awaited — fire-and-forget
  notificationService.sendConfirmation(order, charge)
    .then(() => analytics.track('confirmation_sent', order.id));
  // ↑ No .catch() — rejection is silent!

  return charge;
}

// The bug: notificationService.sendConfirmation() started rejecting
// after a config change, but since the Promise wasn't awaited or caught,
// the error was completely invisible.

Why It Was Silent

  • The function returned charge successfully — the payment worked
  • The unhandled rejection happened in a detached Promise chain
  • Node.js was running with --unhandled-rejections=warn (not throw)
  • Warning logs were being filtered by the log aggregator's severity level

Fix

async function processPayment(order) {
  const charge = await paymentGateway.charge(order.amount);

  // Fix 1: await the notification (makes it part of the chain)
  try {
    await notificationService.sendConfirmation(order, charge);
    await analytics.track('confirmation_sent', order.id);
  } catch (err) {
    // Fix 2: explicit error handling for non-critical operations
    logger.error('Notification failed', { orderId: order.id, error: err });
    await deadLetterQueue.push({ type: 'confirmation', order, charge });
  }

  return charge;
}

Prevention

  • ESLint rule: no-floating-promises (from @typescript-eslint)
  • Node.js flag: --unhandled-rejections=throw
  • Global handler: process.on('unhandledRejection', ...) with alerting
  • Code review checklist: every async call must be awaited or explicitly fire-and-forget with .catch()

Implement Promise.all from Scratch

function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    const results = [];
    let settled = 0;
    const iterable = Array.from(promises);

    if (iterable.length === 0) {
      return resolve([]);
    }

    iterable.forEach((promise, index) => {
      Promise.resolve(promise).then(
        value => {
          results[index] = value; // Preserve order
          settled++;
          if (settled === iterable.length) {
            resolve(results);
          }
        },
        reason => {
          reject(reason); // Fail-fast on first rejection
        }
      );
    });
  });
}

// Edge cases handled:
// ✓ Empty array → resolve([])
// ✓ Non-Promise values → wrapped with Promise.resolve()
// ✓ Order preserved (not first-resolved order)
// ✓ Fail-fast on first rejection

Async Retry with Backoff

async function fetchWithRetry(url, options = {}) {
  const { maxRetries = 3, baseDelay = 500, signal } = options;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      const response = await fetch(url, { signal });
      if (!response.ok && response.status >= 500) {
        throw new Error(`Server error: ${response.status}`);
      }
      return response;
    } catch (err) {
      if (err.name === 'AbortError') throw err; // Don't retry aborts
      if (attempt === maxRetries) throw err;

      const jitter = Math.random() * 200;
      const delay = baseDelay * Math.pow(2, attempt) + jitter;
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

Task Queue with Concurrency Limit

class TaskQueue {
  #concurrency;
  #running = 0;
  #queue = [];

  constructor(concurrency = 4) {
    this.#concurrency = concurrency;
  }

  add(task) {
    return new Promise((resolve, reject) => {
      this.#queue.push({ task, resolve, reject });
      this.#drain();
    });
  }

  #drain() {
    while (this.#running < this.#concurrency && this.#queue.length > 0) {
      const { task, resolve, reject } = this.#queue.shift();
      this.#running++;

      task()
        .then(resolve, reject)
        .finally(() => {
          this.#running--;
          this.#drain();
        });
    }
  }

  get pending() { return this.#queue.length; }
  get active() { return this.#running; }
}

// Usage:
const queue = new TaskQueue(3);
const urls = [/* 100 URLs */];
const results = await Promise.all(
  urls.map(url => queue.add(() => fetch(url).then(r => r.json())))
);

Common Mistakes

5 critical errors senior engineers still make

1. Forgetting to Return in .then() Chains

// ❌ BUG: the chain gets undefined instead of the fetch result
fetchUser(id)
  .then(user => {
    fetchPosts(user.id); // Missing return!
  })
  .then(posts => {
    console.log(posts); // undefined!
  });

// ✅ CORRECT: return the Promise
fetchUser(id)
  .then(user => {
    return fetchPosts(user.id);
  })
  .then(posts => {
    console.log(posts); // actual posts
  });

2. await in Sequential Loop (Should Use Promise.all)

// ❌ SLOW: sequential — N * latency
async function fetchAll(ids) {
  const results = [];
  for (const id of ids) {
    results.push(await fetchItem(id)); // Waits for each!
  }
  return results;
}

// ✅ FAST: concurrent — max(latencies)
async function fetchAll(ids) {
  return Promise.all(ids.map(id => fetchItem(id)));
}

// ✅ CONTROLLED: limited concurrency
async function fetchAll(ids) {
  return mapWithConcurrency(ids, fetchItem, 5);
}

3. Swallowing Errors with Empty .catch()

// ❌ DANGEROUS: error disappears completely
fetchData()
  .then(process)
  .catch(() => {}); // "It stopped crashing!" — but it's silently broken

// ✅ CORRECT: at minimum, log the error
fetchData()
  .then(process)
  .catch(err => {
    logger.error('Pipeline failed', { error: err });
    return fallbackValue; // Explicit recovery
  });

4. Promise Constructor Anti-pattern

// ❌ UNNECESSARY: wrapping an existing Promise in new Promise
function fetchUser(id) {
  return new Promise((resolve, reject) => {
    fetch(`/api/users/${id}`)
      .then(res => res.json())
      .then(resolve)
      .catch(reject);
  });
}

// ✅ CORRECT: just return the Promise chain
function fetchUser(id) {
  return fetch(`/api/users/${id}`).then(res => res.json());
}

// The ONLY reason to use new Promise():
// - Wrapping callback-based APIs (setTimeout, events)
// - Creating deferred Promises (see Promise.withResolvers below)

// Use resolve/reject externally (event handlers, callbacks, etc.)

const result = await promise;

5. Not Handling Cleanup on Rejection

// ❌ BUG: resource leak on error
async function processFile(path) {
  const handle = await fs.open(path);
  const data = await handle.read(); // If this throws...
  await handle.close();              // ...this never runs!
  return data;
}

// ✅ CORRECT: use try/finally
async function processFile(path) {
  const handle = await fs.open(path);
  try {
    return await handle.read();
  } finally {
    await handle.close(); // Always runs
  }
}

// ✅ FUTURE: using keyword (TC39 Explicit Resource Management, TS 5.2+)
// Deterministic cleanup without try/finally boilerplate
async function processFile(path) {
  await using handle = await fs.open(path);
  return await handle.read();
  // handle[Symbol.asyncDispose]() called automatically at block exit
}

Follow-up Questions

7 deep follow-ups with strong answers

Q1: Why does resolve(Promise.resolve(x)) take more microtask ticks than resolve(x)?

Strong answer: When resolve() receives a thenable, the spec mandates creating a PromiseResolveThenableJob — a microtask that calls the thenable's .then() method. This indirection exists for two reasons: (1) it prevents synchronous recursion if the thenable's .then() immediately calls back, and (2) it ensures consistent ordering by always deferring thenable unwrapping. The result is one extra microtask tick per level of thenable wrapping. Promise.resolve(x) when x is already a native Promise with the same constructor returns x unchanged (fast path), but new Promise(r => r(otherPromise)) always pays the extra tick.

Q2: How do microtasks interact with rendering in the browser?

Strong answer: The browser event loop processes all microtasks to exhaustion before performing a rendering update. This means a Promise chain of 10,000 .then() callbacks will block painting for the entire duration. The rendering pipeline (style → layout → paint → composite) only runs between macrotasks if the browser determines a visual update is needed (~60fps = every 16.7ms). To yield to the browser mid-computation, you must schedule work as a macrotask (setTimeout), use requestAnimationFrame, or use scheduler.yield() (the upcoming Scheduling API). This is why long await chains can cause jank.

Q3: Can you implement a Promise that is truly cancellable?

Strong answer: You can't cancel a Promise itself, but you can cancel the work it represents. The pattern is to use AbortController: pass an AbortSignal to the async operation, check it at suspension points, and listen for the abort event. For cleanup, you combine this with a wrapper that suppresses the resolved value if the signal is aborted. TC39 considered a Promise.cancel() proposal but withdrew it because cancellation semantics conflict with Promise's role as a shared read handle. The community settled on AbortController as the external cancellation mechanism.

Q4: What's the difference between queueMicrotask() and Promise.resolve().then()?

Strong answer: Both schedule microtasks, but queueMicrotask(fn) is the direct, minimal API — it enqueues fn without creating a Promise object. Promise.resolve().then(fn) creates a resolved Promise, allocates a PromiseReaction record, and then schedules the callback. queueMicrotask is more efficient for fire-and-forget microtask scheduling. However, Promise.resolve().then() is preferable when you need the return value wrapped in a Promise or want to chain further operations. In terms of ordering, they interleave in the same queue — a microtask is a microtask regardless of source.

Q5: How does V8 optimize async/await compared to the spec's desugaring?

Strong answer: V8 (since 2018) optimizes await by reducing the number of microtask ticks. The spec originally required 3 microtask ticks per await (create throwaway Promise, create PromiseResolveThenableJob, schedule reaction). V8 optimizes this: if the awaited value is a native Promise (same realm, unmodified prototype), it shortcuts to 1 tick by directly scheduling the resumption without creating intermediate Promises. This was formalized in the spec as the "await optimization" in ES2020. V8 also tracks async call frames cheaply for DevTools async stack traces by storing metadata on the Promise object rather than capturing full stacks.

Q6: How would you implement a deadline-aware Promise.all that cancels remaining work?

Strong answer: Combine AbortController with Promise.race against a timeout. Create a shared AbortController, pass its signal to all tasks, race the Promise.all against a setTimeout rejection. When the timeout fires, abort the controller to signal all tasks to stop. Each task should check the signal at suspension points and clean up on abort. This gives you structured cancellation — unlike raw Promise.all which leaves orphaned operations running after a failure.

async function allWithDeadline(tasks, ms) {
  const controller = new AbortController();
  const { signal } = controller;

  const timer = setTimeout(() => controller.abort(), ms);

  try {
    return await Promise.all(tasks.map(t => t(signal)));
  } finally {
    clearTimeout(timer);
    controller.abort(); // Clean up any stragglers
  }
}

Q7: What problems does structured concurrency (like TC39 proposal) solve that Promise.all doesn't?

Strong answer: Promise.all has two structural problems: (1) if one task rejects, the others continue running with no way to stop them — you've lost structured ownership. (2) Errors in "background" promises (fire-and-forget) are unobservable. Structured concurrency (modeled after Trio in Python or Kotlin coroutines) ensures: all child tasks complete before the parent scope exits, failure in any child cancels siblings, and no task leaks beyond its scope. The TC39 proposal aims to bring this to JavaScript with constructs that guarantee all async work is "joined" before a scope exits, eliminating orphaned promises entirely.

Summary

Mental models and what NOT to say

Mental Models to Internalize

  • Promise = state machine: pending → fulfilled | rejected. One-way, irreversible. Reactions are queued, never synchronous.
  • Microtask queue = flush-to-empty: All microtasks drain before any rendering or macrotask. Long chains block the browser.
  • await = suspend + schedule resumption as microtask: It's a coroutine yield point, not a sleep.
  • Thenable assimilation = duck typing + extra tick: resolve(thenable) always costs a PromiseResolveThenableJob.
  • Cancellation is external: Promises are read handles. Use AbortController for write (cancel) semantics.

What NOT to Say in an Interview

  • ❌ "Promises are like callbacks but cleaner" — this undersells the semantic difference (state machine vs fire-and-forget)
  • ❌ "await pauses execution" — imprecise. It suspends the async function's execution context and returns control to the caller. The event loop continues.
  • ❌ "async/await is just syntax sugar for .then()" — it desugars to generators/coroutines, which have different error and stack trace semantics
  • ❌ ".then() runs the callback immediately if the Promise is resolved" — no, it always schedules a microtask
  • ❌ "You can cancel a Promise with AbortController" — you cancel the operation, not the Promise. The Promise still settles (rejects with AbortError).

One-Sentence Summary

A Promise is an eagerly-evaluated state machine whose reactions execute as microtasks; async/await builds coroutine suspension on top of this, and mastering the scheduling semantics is what enables building robust production patterns for concurrency, cancellation, and error recovery.

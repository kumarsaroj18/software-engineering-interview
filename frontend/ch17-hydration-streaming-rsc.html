Hard React Hydration Streaming SSR Server Components

Chapter 17: Hydration, Streaming & React Server Components

Key Takeaway: Hydration attaches event handlers and React internals to server-rendered HTML. Traditional full hydration blocks interactivity until the entire tree is hydrated. React 18's streaming SSR (renderToPipeableStream) sends HTML progressively as Suspense boundaries resolve. Selective hydration prioritizes hydrating components the user interacts with first. Together these eliminate the all-or-nothing hydration bottleneck.

Interview Question: “Explain React’s hydration model. How do streaming SSR, progressive hydration, and selective hydration improve performance?”

Interviewer Intent

Why interviewers ask this question

Interviewers want to assess whether you understand:

  • The fundamental cost of hydration and why it exists
  • How React 18 fundamentally changed the SSR story
  • The difference between streaming, progressive, and selective hydration
  • Real-world performance implications (TTFB, TTI, INP)
  • When to choose each strategy and the trade-offs involved
  • How React Server Components fit into the hydration picture

Quick Answer (30-Second Version)

Concise answer for time-pressed interviews

Hydration is the process of attaching event handlers and React state to server-rendered HTML. Traditional SSR with renderToString is all-or-nothing: the server must fetch all data, render the complete HTML, send it, then the client must hydrate the entire tree before anything is interactive.

React 18 solves this with three innovations:

  1. Streaming SSR — renderToPipeableStream sends HTML progressively as Suspense boundaries resolve
  2. Progressive Hydration — Components hydrate in stages, not all at once
  3. Selective Hydration — React prioritizes hydrating whichever component the user interacts with first

React Server Components (RSC) take this further by never sending component code to the client at all — they render on the server and stream a serialized tree via the React Flight protocol.

// Traditional SSR with renderToString (React 17 and earlier)
import { renderToString } from 'react-dom/server';
import App from './App';

app.get('/', async (req, res) => {
  // Problem 1: Must fetch ALL data before rendering anything
  const userData = await fetchUser();
  const posts = await fetchPosts();
  const comments = await fetchComments(); // Slowest query blocks everything

  // Problem 2: Render entire tree to string (synchronous, blocks event loop)
  const html = renderToString(
    <App user={userData} posts={posts} comments={comments} />
  );

  // Problem 3: Nothing sent until everything is ready
  res.send(`
    <!DOCTYPE html>
    <html>
      <body>
        <div id="root">${html}</div>
        <script src="/bundle.js"></script>
      </body>
    </html>
  `);
});

// Client-side: hydrate() must process entire tree
import { hydrate } from 'react-dom';
hydrate(<App {...window.__DATA__} />, document.getElementById('root'));

The Four Bottlenecks of Traditional SSR:

  1. Data fetching — Server waits for ALL data before rendering begins
  2. Rendering — renderToString is synchronous; blocks the Node.js event loop
  3. Transfer — Entire HTML payload sent at once (large TTFB)
  4. Hydration — Client must process entire tree before ANY interactivity

Hydration Mismatch

Causes, debugging, suppressHydrationWarning, consequences 
// Common causes of hydration mismatch

// 1. Timestamps and Date objects
function Header() {
  // Server renders at time T, client hydrates at time T+N
  return <span>{new Date().toLocaleTimeString()}</span>; // ❌ MISMATCH
}

// Fix: useEffect for client-only values
function Header() {
  const [time, setTime] = useState(null);
  useEffect(() => {
    setTime(new Date().toLocaleTimeString());
  }, []);
  return <span>{time ?? 'Loading...'}</span>; // ✅
}

// 2. Random values
function Banner() {
  // Different random value on server vs client
  const variant = Math.random() > 0.5 ? 'A' : 'B'; // ❌ MISMATCH
  return <div className={`banner-${variant}`} />;
}

// Fix: Seed random on server, pass via props or context
function Banner({ variant }) {
  return <div className={`banner-${variant}`} />; // ✅
}

// 3. Browser-only APIs
function WindowSize() {
  // window doesn't exist on server
  const width = window.innerWidth; // ❌ Crashes on server
  return <span>{width}px</span>;
}

// Fix: Check environment or use useEffect
function WindowSize() {
  const [width, setWidth] = useState(0);
  useEffect(() => {
    setWidth(window.innerWidth);
  }, []);
  return <span>{width}px</span>; // ✅
}

// 4. Browser extensions injecting DOM nodes
// Fix: Use suppressHydrationWarning on specific elements
function Body() {
  return <div id="root" suppressHydrationWarning>{children}</div>;
}

// 5. Async data race conditions
function Profile({ userId }) {
  // If server and client fetch different versions of data
  const data = useSWR(`/api/user/${userId}`); // ❌ Potential mismatch
  return <span>{data?.name}</span>;
}

// Fix: Serialize server data and reuse on client
function Profile({ serverData }) {
  const data = useSWR(`/api/user/${serverData.id}`, {
    fallbackData: serverData // ✅ Client starts with same data
  });
  return <span>{data?.name}</span>;
}

Consequences of Hydration Mismatch:

  • React 17: Warns in dev mode; attempts to patch text content differences but provides no guarantees for attribute/structural mismatches (potentially leaving DOM inconsistent)
  • React 18: Logs error, falls back to client-side rendering for that subtree
  • React 19: More nuanced — text content mismatches are silently patched in-place (no full re-render), but structural mismatches (different element types, missing/extra nodes) still trigger client re-render with a console error
  • Performance cost: Mismatch forces React to discard server HTML and re-render from scratch
  • SEO risk: Content visible to crawlers differs from what users eventually see
// Debugging hydration mismatches in React 18+
// React provides detailed error messages:
// "Text content does not match. Server: "Hello" Client: "World""
// "Hydration failed because the initial UI does not match what was rendered on the server"

// Strategy: Use React DevTools "Highlight updates" to spot re-renders
// Or add this to your app temporarily:
if (typeof window !== 'undefined') {
  const originalError = console.error;
  console.error = (...args) => {
    if (args[0]?.includes?.('Hydration')) {
      debugger; // Break on hydration errors
    }
    originalError.apply(console, args);
  };
}

Streaming SSR

renderToPipeableStream, pipe(), onShellReady vs onAllReady, chunked transfer

│               STREAMING SSR TIMELINE                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Server:  [Render Shell] → [Stream chunk 1] → [chunk 2] → ...  │
│                │                                                │
│  Network:      [Shell HTML arrives]                             │
│                     [chunk 1 arrives]                           │
│                          [chunk 2 arrives]                      │
│                                                                 │
│  Client:  [Parse Shell] → [Hydrate Shell] → [Hydrate chunks]   │
│                │                                                │
│  User:    sees layout ── sees content ── full interactivity     │
│           (fast TTFB)     (progressive)    (faster TTI)         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
        
// React 18 Streaming SSR with renderToPipeableStream
import { renderToPipeableStream } from 'react-dom/server';
import App from './App';

app.get('/', (req, res) => {
  // No need to await all data upfront!
  const { pipe, abort } = renderToPipeableStream(
    <App />,
    {
      // bootstrapScripts tells React where the client bundle is
      bootstrapScripts: ['/bundle.js'],

      // onShellReady: fires when content outside all Suspense boundaries is ready
      // Use for crawlers and real users
      onShellReady() {
        res.setHeader('Content-Type', 'text/html');
        res.setHeader('Transfer-Encoding', 'chunked');
        res.statusCode = 200;
        pipe(res); // Start streaming HTML to the client
      },

      // onShellError: fires if the shell itself fails to render
      onShellError(error) {
        res.statusCode = 500;
        res.send('<h1>Server Error</h1>');
      },

      // onAllReady: fires when ALL content (including Suspense) is ready
      // Use for crawlers/bots that need complete HTML
      onAllReady() {
        // For bots: could delay pipe() until here
        console.log('All Suspense boundaries resolved');
      },

      // onError: called for each rendering error
      onError(error) {
        console.error('Streaming error:', error);
      }
    }
  );

  // Timeout: abort streaming after 10 seconds
  setTimeout(() => abort(), 10000);
});

// Bot detection: use onAllReady for crawlers
app.get('/', (req, res) => {
  const isBot = /bot|crawler|spider/i.test(req.headers['user-agent']);

  const { pipe, abort } = renderToPipeableStream(<App />, {
    bootstrapScripts: ['/bundle.js'],
    onShellReady() {
      if (!isBot) {
        res.statusCode = 200;
        res.setHeader('Content-Type', 'text/html');
        pipe(res); // Stream immediately for real users
      }
    },
    onAllReady() {
      if (isBot) {
        res.statusCode = 200;
        res.setHeader('Content-Type', 'text/html');
        pipe(res); // Wait for complete HTML for bots
      }
    }
  });
});

How Chunked Transfer Works:

  • Server sends Transfer-Encoding: chunked header (no Content-Length)
  • Browser starts parsing and rendering HTML as chunks arrive
  • Each resolved Suspense boundary triggers a new chunk
  • React injects <script> tags that swap fallback content with resolved content
  • Connection stays open until all Suspense boundaries resolve or timeout

Progressive Hydration

Priority-based hydration, lazy hydration, reducing main-thread blocking 
// Progressive Hydration: Hydrate components in stages
// Strategy: Defer hydration of below-fold content

// Approach 1: Intersection Observer-based lazy hydration
function LazyHydrate({ children, whenVisible = false, whenIdle = false }) {
  const ref = useRef(null);
  const [hydrated, setHydrated] = useState(false);

  useEffect(() => {
    if (whenVisible) {
      const observer = new IntersectionObserver(
        ([entry]) => {
          if (entry.isIntersecting) {
            setHydrated(true);
            observer.disconnect();
          }
        },
        { rootMargin: '200px' } // Start hydrating 200px before visible
      );
      if (ref.current) observer.observe(ref.current);
      return () => observer.disconnect();
    }

    if (whenIdle) {
      // Use requestIdleCallback for non-critical components
      const id = requestIdleCallback(() => setHydrated(true));
      return () => cancelIdleCallback(id);
    }

    setHydrated(true);
  }, [whenVisible, whenIdle]);

  // Server-rendered HTML preserved until hydration triggers
  if (!hydrated) {
    return (
      <div
        ref={ref}
        suppressHydrationWarning
        dangerouslySetInnerHTML={{ __html: '' }}
      />
    );
  }

  return <div ref={ref}>{children}</div>;
}

// Usage: Only hydrate footer when it scrolls into view
function Page() {
  return (
    <>
      <Header />         {/* Hydrates immediately - interactive */}
      <HeroSection />    {/* Hydrates immediately - above fold */}

      <LazyHydrate whenIdle>
        <ArticleBody />  {/* Hydrates during idle time */}
      </LazyHydrate>

      <LazyHydrate whenVisible>
        <Comments />     {/* Hydrates when scrolled near */}
      </LazyHydrate>

      <LazyHydrate whenVisible>
        <Footer />       {/* Hydrates when scrolled near */}
      </LazyHydrate>
    </>
  );
}

// Approach 2: Priority queue for hydration
const PRIORITY = { CRITICAL: 0, HIGH: 1, MEDIUM: 2, LOW: 3 };

class HydrationScheduler {
  constructor() {
    this.queue = [];
    this.isProcessing = false;
  }

  enqueue(component, priority) {
    this.queue.push({ component, priority });
    this.queue.sort((a, b) => a.priority - b.priority);
    if (!this.isProcessing) this.process();
  }

  async process() {
    this.isProcessing = true;
    while (this.queue.length > 0) {
      const { component } = this.queue.shift();
      await component.hydrate();
      // Yield to main thread between hydrations
      await new Promise(resolve => setTimeout(resolve, 0));
    }
    this.isProcessing = false;
  }
}

Key Benefits of Progressive Hydration:

  • Reduces main-thread blocking — hydration work is split into smaller chunks
  • Faster Time to Interactive (TTI) for critical UI elements
  • Reduces Total Blocking Time (TBT) by yielding between hydration tasks
  • Non-visible components never hydrate if user doesn’t scroll to them

Selective Hydration (React 18)

User-interaction priority, event replay, hydrateRoot, priority inversion 
// Selective Hydration in React 18
// React automatically prioritizes hydrating components the user clicks on

import { hydrateRoot } from 'react-dom/client';

// hydrateRoot enables concurrent features including selective hydration
const root = hydrateRoot(document.getElementById('root'), <App />);

// How selective hydration works internally:
// 1. React starts hydrating from top of tree
// 2. When it hits a Suspense boundary, it can pause hydration
// 3. If user clicks a not-yet-hydrated component, React:
//    a. Intercepts the event in the capture phase
//    b. Synchronously hydrates that component's subtree
//    c. Event proceeds naturally through the now-hydrated DOM
//    d. Resumes normal hydration order for remaining boundaries
//
// Note: If code for the boundary isn't downloaded yet (can't hydrate),
// React calls stopPropagation() and increases the boundary's priority.

// Example: Multiple Suspense boundaries with selective hydration
function App() {
  return (
    <>
      <Header /> {/* Hydrates first (no Suspense boundary) */}

      <Suspense fallback={<Spinner />}>
        <Sidebar /> {/* Can be deferred */}
      </Suspense>

      <Suspense fallback={<Spinner />}>
        <MainContent /> {/* Can be deferred */}
      </Suspense>

      <Suspense fallback={<Spinner />}>
        <Comments /> {/* Can be deferred */}
      </Suspense>
    </>
  );
}

// If user clicks on Comments while Sidebar is still hydrating:
// React pauses Sidebar hydration → hydrates Comments → click fires naturally
// This is "priority inversion" — user intent overrides default order

Event Replay Rules:

  • Discrete events (click, keydown, input): Replayed after hydration
  • Continuous events (scroll, mousemove): NOT replayed (stale by the time hydration completes)
  • Only the Suspense boundary containing the target is prioritized
  • If multiple clicks happen on different boundaries, React processes them in click order

Suspense Boundaries & Streaming

Suspense as streaming unit, fallback replacement, out-of-order completion, inline scripts 
// Suspense boundaries define the streaming units
// Each boundary is an independent chunk that can resolve independently

function ProductPage() {
  return (
    <Layout>
      {/* Shell: renders immediately, sent in first chunk */}
      <Header />
      <ProductInfo productId={123} />

      {/* Streaming boundary 1: Reviews (slow API) */}
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews productId={123} />
      </Suspense>

      {/* Streaming boundary 2: Recommendations (ML service) */}
      <Suspense fallback={<RecommendationsSkeleton />}>
        <Recommendations userId={user.id} />
      </Suspense>

      {/* Streaming boundary 3: Inventory check (third-party) */}
      <Suspense fallback={<InventorySkeleton />}>
        <InventoryStatus productId={123} />
      </Suspense>
    </Layout>
  );
}

The Inline Script Injection Pattern:

  • React sends resolved content in a hidden <div> at the end of the stream
  • An inline <script> calls $RC (completeBoundary) to swap fallback with real content
  • This works without JavaScript loaded — the swap happens via tiny inline scripts
  • Content appears progressively even if the main bundle hasn’t downloaded yet

Out-of-Order HTML Streaming

$RC template swapping, progressive enhancement, shell-first architecture 
// How React's out-of-order streaming works under the hood

// The runtime functions injected at the start of the stream:
// $RC = completeBoundary - swaps fallback with resolved content
// $RA = completeSegment - adds content to existing boundary
// $RX = errorBoundary - replaces fallback with error UI

// Simplified implementation of $RC (completeBoundary):
function $RC(boundaryId, contentId) {
  // Find the boundary marker (template tag)
  const boundary = document.getElementById(boundaryId);
  // Find the hidden content that was streamed later
  const content = document.getElementById(contentId);

  if (boundary && content) {
    // Get all nodes between boundary start and end markers
    const fallbackNodes = [];
    let node = boundary.nextSibling;
    while (node && node.nodeType !== 8 /* Comment: /$  */) {
      fallbackNodes.push(node);
      node = node.nextSibling;
    }

    // Remove fallback content
    fallbackNodes.forEach(n => n.remove());

    // Move resolved content from hidden div to boundary location
    while (content.firstChild) {
      boundary.parentNode.insertBefore(content.firstChild, boundary.nextSibling);
    }

    // Clean up
    content.remove();
    boundary.remove();
  }
}

Progressive Enhancement Properties:

  • Content is visible even if JavaScript fails to load (it’s real HTML)
  • The $RC swap scripts are tiny and inline — no bundle dependency
  • Browsers render content as it arrives (streaming HTML parsing)
  • If streaming aborts, users still see the shell and any resolved content
  • Search engines can crawl the content regardless of JS execution

React Flight Protocol (RSC Wire Format)

RSC wire format, serialized component tree, client/server references 
// React Server Components use the "Flight" protocol
// It's a streaming JSON-like format that describes the component tree

// Server Component (runs ONLY on server, zero bundle cost)
// app/page.tsx
async function ProductPage({ params }) {
  const product = await db.query('SELECT * FROM products WHERE id = ?', [params.id]);

  return (
    <Layout>
      <ProductDetails product={product} />
      {/* Client Component: marked with 'use client' */}
      <AddToCartButton productId={product.id} />
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews productId={product.id} />
      </Suspense>
    </Layout>
  );
}

The conceptual model (streaming rows describing a component tree) is stable, but don't memorize exact syntax for interviews — focus on understanding what it encodes (element tree + module references + chunks) and why (enables streaming without full serialization).

Flight Protocol Key Properties:

  • Streaming — Rows arrive incrementally, client renders as they arrive
  • Resumable — Can pause and resume across network boundaries
  • Typed References — Client components are references, not serialized code
  • No Hydration for Server Components — They never run on client, so no hydration cost
  • Composable — Server and client components interleave freely in the tree

Key Distinction: Islands use partial hydration (only interactive components hydrate, rest is static HTML with no framework awareness). React uses selective hydration (entire tree is React-aware, but hydration is prioritized and deferred). RSC bridges the gap — server components are like static islands within a React tree.

Partial Prerendering (PPR, Next.js 14+/React 19): Blurs the line further — the static shell is prerendered at build time, and dynamic "holes" (Suspense boundaries) are filled via streaming at request time. Result: instant TTFB for the static shell + streaming for dynamic content. This is the latest evolution in the islands-vs-streaming spectrum.

Server Actions ("use server"): The mutation counterpart to RSC's data fetching. Form handlers marked with "use server" execute on the server without shipping handler code to the client — eliminating the need to hydrate form submission logic. This further reduces client-side JS for forms.

Hydration Cost on INP: Each hydration pass is a synchronous React render. For a component tree with 1000 nodes, hydration can block the main thread for 100-300ms. Selective hydration breaks this into per-boundary chunks of 10-50ms, staying under the 200ms INP threshold.

// Example 1: Complete renderToPipeableStream server setup
import express from 'express';
import { renderToPipeableStream } from 'react-dom/server';
import { createReadStream } from 'fs';
import App from './App';

const app = express();

app.get('*', (req, res) => {
  // Determine if request is from a bot
  const isBot = /bot|googlebot|crawler|spider|robot|crawling/i.test(
    req.headers['user-agent'] || ''
  );

  let didError = false;
  let shellReady = false;

  const { pipe, abort } = renderToPipeableStream(
    <App url={req.url} />,
    {
      bootstrapScripts: ['/static/js/bundle.js'],
      bootstrapScriptContent: `window.__INITIAL_URL__ = "${req.url}"`,

      onShellReady() {
        shellReady = true;
        if (!isBot) {
          res.statusCode = didError ? 500 : 200;
          res.setHeader('Content-Type', 'text/html; charset=utf-8');
          res.setHeader('Transfer-Encoding', 'chunked');
          // Enable streaming — don't buffer
          res.setHeader('X-Accel-Buffering', 'no'); // Nginx
          pipe(res);
        }
      },

      onAllReady() {
        if (isBot) {
          res.statusCode = didError ? 500 : 200;
          res.setHeader('Content-Type', 'text/html; charset=utf-8');
          pipe(res); // Bots get complete HTML
        }
      },

      onShellError(error) {
        res.statusCode = 500;
        res.setHeader('Content-Type', 'text/html');
        res.send('<h1>Something went wrong</h1>');
        console.error('Shell error:', error);
      },

      onError(error) {
        didError = true;
        console.error('Streaming error:', error);
      }
    }
  );

  // Abort streaming after timeout
  setTimeout(() => {
    if (!shellReady) {
      abort();
      res.statusCode = 504;
      res.end('<h1>Gateway Timeout</h1>');
    }
  }, 10000);
});

app.listen(3000);

Follow-up Questions

7 likely follow-up questions with detailed answers

1. How does React detect which component to hydrate first when multiple clicks happen?

React uses event delegation at the root. When a click event fires on a not-yet-hydrated Suspense boundary, React captures it in its event system. It then synchronously hydrates the target boundary by calling the hydrateRoot internal path for that subtree. If multiple boundaries receive clicks in rapid succession, React processes them in event order (first click, first hydrated). The discrete event is replayed after hydration completes for that boundary.

2. What happens if streaming aborts mid-way (timeout or error)?

If you call abort() or the connection drops:

  • Content already sent to the client remains visible (HTML is progressive)
  • Unresolved Suspense boundaries keep showing their fallback UI
  • Once client JS loads, React attempts client-side rendering for unresolved boundaries
  • The onError callback fires for the aborted boundaries
  • Users see a degraded but functional page rather than a blank screen

3. Can you mix Server Components and Client Components in the same tree?

Yes — this is the primary design goal of RSC. Rules:

  • Server Components can render Client Components (pass them as children or import them)
  • Client Components CANNOT import Server Components directly (but can accept them as children props)
  • Props passed from Server → Client must be serializable (no functions, classes, or Symbols)
  • The boundary is the "use client" directive at the top of a file

4. How do you handle authentication state with streaming SSR?

Authentication typically lives in the shell (not behind Suspense) because:

  • Nav bar and user avatar should appear immediately
  • Auth state determines what content to show
  • Pattern: Read session cookie on server, pass user to shell components, wrap personalized content in Suspense for streaming
// Auth in streaming SSR
async function Layout({ children }) {
  const session = await getSession(); // Fast: cookie/JWT decode
  return (
    <>
      <NavBar user={session?.user} /> {/* In shell */}
      <Suspense fallback={<Skeleton />}>
        {children} {/* Personalized content streams */}
      </Suspense>
    </>
  );
}

5. What is the “double data problem” with SSR and how does RSC solve it?

With traditional SSR, data is fetched on the server, rendered to HTML, then serialized as JSON in a <script> tag so the client can hydrate with the same data. This means the data is sent TWICE (once as HTML, once as JSON). RSC solves this because server components never re-render on the client — their output is the final HTML. Only client components receive serialized props, and those are typically minimal (IDs, flags) rather than large data sets.

6. How does streaming SSR interact with CDN caching?

Streaming and caching are at tension:

  • Streamed responses use Transfer-Encoding: chunked — most CDNs buffer these
  • Solution 1: Cache the shell separately, stream dynamic content from origin
  • Solution 2: Use edge runtimes (Vercel Edge, Cloudflare Workers) that support streaming
  • Solution 3: Use stale-while-revalidate — serve cached version while generating fresh stream
  • Some CDNs (Cloudflare) support streaming through without buffering

7. What is “resumability” (Qwik) and how does it differ from hydration?

Resumability (Qwik framework) eliminates hydration entirely:

  • Hydration: Re-execute component code on client to rebuild state and attach listeners
  • Resumability: Serialize all state, closures, and listener references into HTML. Client resumes exactly where server left off — zero re-execution
  • Trade-off: Qwik requires a custom compiler and specific coding patterns. React chose selective hydration as a more pragmatic approach within existing JS semantics
  • Resumability = O(1) startup. Hydration = O(n) where n = component count

Summary

Mental models and what NOT to say in interviews

Mental Models to Remember:

  • Hydration = “watering dry HTML” — Server HTML is static; hydration makes it alive
  • Streaming = “don’t wait for the slowest” — Send what’s ready, stream the rest
  • Selective = “hydrate what matters to the user” — Clicked components jump the queue
  • RSC = “components that never ship to client” — Zero JS cost for server-only logic
  • Islands = “interactive oases in a static desert” — Only interactive bits get JavaScript

What NOT to Say in Interviews:

  • ❌ “Hydration just re-renders everything on the client” — It ATTACHES to existing DOM, not re-renders
  • ❌ “Streaming SSR requires React Server Components” — Streaming works without RSC
  • ❌ “Selective hydration means some components never hydrate” — They ALL hydrate, just in priority order
  • ❌ “Islands and RSC are the same thing” — Islands are framework-agnostic MPA; RSC is React-specific SPA
  • ❌ “renderToString is deprecated” — It still works, just not recommended for new apps
  • ❌ “You need Next.js for streaming SSR” — renderToPipeableStream works in any Node.js server

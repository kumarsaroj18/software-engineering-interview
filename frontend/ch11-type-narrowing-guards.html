Chapter 11: Type Narrowing & Guards

"How does TypeScript narrow types, and how would you implement exhaustive checking in a large codebase?"

Key Takeaway: TypeScript's control flow analysis (CFA) narrows types through type guards, discriminated unions, and assertion functions. Exhaustive checking via the never type ensures that all variants of a union are handled — making the compiler catch missing cases when new variants are added. This is the foundation of safe, maintainable domain modeling at scale.

Interviewer's Intent

What the interviewer is really testing…

When an interviewer asks about type narrowing and exhaustive checks, they are probing for:

  • Control Flow Analysis (CFA) understanding — Do you know how TypeScript's compiler tracks types through branches, loops, and assignments?
  • Practical narrowing patterns — Can you choose the right guard (typeof, instanceof, in, custom predicates) for each situation?
  • Exhaustive checking mastery — Can you use the never type to guarantee all union variants are handled at compile time?
  • Assertion functions — Do you understand asserts functions and when they're preferable to type guards?
  • Domain modeling maturity — Can you design discriminated unions that scale across a large codebase with multiple contributors?

Senior signal: A senior developer doesn't just use narrowing — they design types that force narrowing, making illegal states unrepresentable and ensuring the compiler catches regressions when the domain evolves.

60-Second Answer

The concise interview response…

TypeScript uses Control Flow Analysis to narrow types at each point in code. After an if (typeof x === "string") check, the compiler knows x is a string inside that branch. This works with typeof, instanceof, the in operator, and custom type predicates (x is Type).

For complex domain models, I use discriminated unions — unions where each variant has a literal kind or type field. A switch on that discriminant narrows to the specific variant in each case.

For exhaustive checking, I add a default case that assigns the value to never:

function assertNever(x: never): never {
  throw new Error(`Unexpected value: ${x}`);
}

function handleShape(shape: Shape) {
  switch (shape.kind) {
    case "circle":    return Math.PI * shape.radius ** 2;
    case "rectangle": return shape.width * shape.height;
    default:          return assertNever(shape);
    // ^^ compile error if a new Shape variant is added
  }
}

This makes the compiler report an error whenever a new variant is added to the union but not handled — catching bugs at build time, not runtime.

Control Flow Analysis

How TypeScript tracks types through code execution paths…

Control Flow Analysis (CFA) is the mechanism by which TypeScript's compiler narrows types as code executes. At every point in the program, the compiler maintains a type state for each variable.

How CFA Tracks Types

┌─────────────────────────────────────────────────────┐
│  function process(value: string | number | null) {  │
│                                                     │
│    // value: string | number | null                 │
│                                                     │
│    if (value === null) {                            │
│      // value: null                                 │
│      return;                                        │
│    }                                                │
│                                                     │
│    // value: string | number  (null eliminated)     │
│                                                     │
│    if (typeof value === "string") {                 │
│      // value: string                              │
│      value.toUpperCase(); // ✓                      │
│    } else {                                         │
│      // value: number                              │
│      value.toFixed(2);    // ✓                      │
│    }                                                │
│  }                                                  │
└─────────────────────────────────────────────────────┘

Narrowing After if / switch

type Response = { status: "ok"; data: string } | { status: "error"; message: string };

function handle(res: Response) {
  if (res.status === "ok") {
    // res: { status: "ok"; data: string }
    console.log(res.data);
  } else {
    // res: { status: "error"; message: string }
    console.error(res.message);
  }
}

Assignment Narrowing

let value: string | number;

value = "hello";
// value: string — narrowed by assignment
console.log(value.toUpperCase()); // ✓

value = 42;
// value: number — re-narrowed by assignment
console.log(value.toFixed(2)); // ✓

Truthiness Narrowing

function printLength(str: string | undefined) {
  if (str) {
    // str: string (undefined and "" eliminated)
    console.log(str.length);
  }
}

// Beware: truthiness eliminates "", 0, NaN, null, undefined
function processNumber(n: number | undefined) {
  if (n) {
    // n: number — but 0 is also excluded!
    // This is a common bug source
  }
  // Prefer: if (n !== undefined) for numbers
}

Type Widening After Reassignment

function example(x: string | number) {
  if (typeof x === "string") {
    // x: string
    x = 42; // x re-assigned
    // x: number — widened to the assigned type
  }
  // x: string | number — back to original declared type
}

// Closures and narrowing:
function closureProblem(x: string | number) {
  if (typeof x === "string") {
    x = x.toUpperCase(); // x is reassigned after narrowing
    setTimeout(() => {
      // x: string | number — narrowing lost!
      // TS cannot guarantee x wasn't reassigned before callback runs
    }, 0);
  }
}

// TS 5.x improvement: if the variable is NEVER reassigned after the
// narrowing check, narrowing now persists into closures:
function closureFixed(x: string | number) {
  if (typeof x === "string") {
    // x is NOT reassigned anywhere in this scope
    setTimeout(() => {
      // x: string ✅ — narrowing preserved in TS 5.x!
      console.log(x.toUpperCase());
    }, 0);
  }
}

Gotcha: In TS 5.x, narrowing persists into closures for variables that are never reassigned after the narrowing check. If the variable is reassigned, narrowing is still lost. For maximum compatibility, assign to a const or pass as a parameter.

Type Guards (typeof, instanceof, in, is)

The four built-in narrowing mechanisms and custom predicates…

typeof Narrowing

Works for primitive types: "string", "number", "bigint", "boolean", "symbol", "undefined", "object", "function".

function padLeft(value: string | number, padding: string | number): string {
  if (typeof padding === "number") {
    // padding: number
    return " ".repeat(padding) + value;
  }
  // padding: string
  return padding + value;
}

// Limitation: typeof null === "object" — a historical JS bug
function processValue(val: object | null) {
  if (typeof val === "object") {
    // val: object | null — NOT narrowed! null leaks through
  }
  if (val !== null && typeof val === "object") {
    // val: object — correctly narrowed
  }
}

instanceof Narrowing

Works for class instances and built-in constructors:

class ApiError extends Error {
  constructor(public statusCode: number, message: string) {
    super(message);
  }
}

class ValidationError extends Error {
  constructor(public fields: string[], message: string) {
    super(message);
  }
}

function handleError(error: Error) {
  if (error instanceof ApiError) {
    // error: ApiError
    console.log(`API ${error.statusCode}: ${error.message}`);
  } else if (error instanceof ValidationError) {
    // error: ValidationError
    console.log(`Invalid fields: ${error.fields.join(", ")}`);
  } else {
    // error: Error
    console.log(`Unknown: ${error.message}`);
  }
}

'in' Operator Narrowing

Checks for property existence — ideal for interfaces without shared constructors:

interface Fish { swim: () => void; }
interface Bird { fly: () => void; }
interface Dog  { run: () => void; swim: () => void; }

function move(animal: Fish | Bird | Dog) {
  if ("fly" in animal) {
    // animal: Bird
    animal.fly();
  } else if ("run" in animal) {
    // animal: Dog (has swim too, but 'run' is unique)
    animal.run();
  } else {
    // animal: Fish
    animal.swim();
  }
}

Custom Type Predicates (paramName is Type)

interface AdminUser {
  role: "admin";
  permissions: string[];
  auditLog: string[];
}

interface RegularUser {
  role: "user";
  permissions: string[];
}

type User = AdminUser | RegularUser;

// Type predicate function
function isAdmin(user: User): user is AdminUser {
  return user.role === "admin";
}

function renderDashboard(user: User) {
  if (isAdmin(user)) {
    // user: AdminUser
    console.log(user.auditLog); // ✓ accessible
  } else {
    // user: RegularUser
    // user.auditLog — ✗ compile error
  }
}

When to Use Each Guard

Guard Best For Limitations
typeof Primitives (string, number, boolean) Cannot distinguish interfaces/objects; typeof null === "object"
instanceof Class hierarchies, built-in objects Doesn't work across realms (iframes); no interface support
in Structural checks, interface unions Only checks property existence, not type; inherited props match
x is Type Complex validation logic, reusable guards Compiler trusts your implementation — can lie

Discriminated Unions

The most powerful narrowing pattern for domain modeling…

What Makes a Good Discriminant?

A discriminant must be a property present in every variant with a literal type (string literal, number literal, or boolean literal) that is unique per variant:

// ✓ Good discriminant: literal string union
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "rectangle"; width: number; height: number }
  | { kind: "triangle"; base: number; height: number };

// ✗ Bad discriminant: non-literal type
type BadShape =
  | { type: string; radius: number }   // "string" is too wide
  | { type: string; width: number };   // can't distinguish

Switch Exhaustiveness

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      return shape.width * shape.height;
    case "triangle":
      return 0.5 * shape.base * shape.height;
    // If we add a new variant to Shape and forget a case,
    // TypeScript errors IF we enable noImplicitReturns or use assertNever
  }
}

Nested Discriminated Unions

type AsyncState<T> =
  | { status: "idle" }
  | { status: "loading"; progress?: number }
  | { status: "success"; data: T; cachedAt: number }
  | { status: "error"; error: Error; retryCount: number };

type FormField =
  | { type: "text"; value: string; validation: TextValidation }
  | { type: "select"; value: string; options: Option[] }
  | { type: "multi-select"; value: string[]; options: Option[] };

// Nested: Form has fields, each narrowed independently
interface Form {
  fields: Record<string, FormField>;
  submission: AsyncState<{ id: string }>;
}

Real-World Domain Modeling

API Responses

type ApiResponse<T> =
  | { type: "success"; data: T; meta: { requestId: string; duration: number } }
  | { type: "error"; code: number; message: string; details?: unknown }
  | { type: "redirect"; location: string; permanent: boolean };

function handleResponse<T>(res: ApiResponse<T>): T | null {
  switch (res.type) {
    case "success":
      return res.data;
    case "error":
      reportError(res.code, res.message);
      return null;
    case "redirect":
      window.location.href = res.location;
      return null;
  }
}

Redux Actions

type TodoAction =
  | { type: "TODO_ADD"; payload: { id: string; text: string } }
  | { type: "TODO_TOGGLE"; payload: { id: string } }
  | { type: "TODO_DELETE"; payload: { id: string } }
  | { type: "TODO_BULK_UPDATE"; payload: { ids: string[]; done: boolean } };

function todoReducer(state: TodoState, action: TodoAction): TodoState {
  switch (action.type) {
    case "TODO_ADD":
      return { ...state, items: [...state.items, action.payload] };
    case "TODO_TOGGLE":
      return {
        ...state,
        items: state.items.map(t =>
          t.id === action.payload.id ? { ...t, done: !t.done } : t
        ),
      };
    case "TODO_DELETE":
      return {
        ...state,
        items: state.items.filter(t => t.id !== action.payload.id),
      };
    case "TODO_BULK_UPDATE":
      return {
        ...state,
        items: state.items.map(t =>
          action.payload.ids.includes(t.id)
            ? { ...t, done: action.payload.done }
            : t
        ),
      };
  }
}

State Machines

type AuthState =
  | { state: "anonymous" }
  | { state: "authenticating"; provider: string }
  | { state: "authenticated"; user: User; token: string; expiresAt: number }
  | { state: "error"; error: Error; lastAttempt: Date };

type AuthEvent =
  | { type: "LOGIN_START"; provider: string }
  | { type: "LOGIN_SUCCESS"; user: User; token: string }
  | { type: "LOGIN_FAILURE"; error: Error }
  | { type: "LOGOUT" }
  | { type: "TOKEN_REFRESH"; token: string };

function transition(state: AuthState, event: AuthEvent): AuthState {
  switch (state.state) {
    case "anonymous":
      if (event.type === "LOGIN_START") {
        return { state: "authenticating", provider: event.provider };
      }
      return state;
    case "authenticating":
      switch (event.type) {
        case "LOGIN_SUCCESS":
          return {
            state: "authenticated",
            user: event.user,
            token: event.token,
            expiresAt: Date.now() + 3600_000,
          };
        case "LOGIN_FAILURE":
          return { state: "error", error: event.error, lastAttempt: new Date() };
        default:
          return state;
      }
    case "authenticated":
      if (event.type === "LOGOUT") return { state: "anonymous" };
      if (event.type === "TOKEN_REFRESH") return { ...state, token: event.token };
      return state;
    case "error":
      if (event.type === "LOGIN_START") {
        return { state: "authenticating", provider: event.provider };
      }
      return state;
  }
}

Tip: When designing discriminated unions for large codebases, keep discriminant fields consistent (kind, type, or status) across the entire codebase. This makes auto-complete and refactoring predictable.

Exhaustive Checks (never type)

Compile-time guarantees that every variant is handled…

The assertNever Pattern

The never type represents values that should never occur. If a value reaches a point where it should be never but isn't, TypeScript reports a compile error:

function assertNever(value: never, message?: string): never {
  throw new Error(message ?? `Unexpected value: ${JSON.stringify(value)}`);
}

type Direction = "north" | "south" | "east" | "west";

function move(direction: Direction): [number, number] {
  switch (direction) {
    case "north": return [0, 1];
    case "south": return [0, -1];
    case "east":  return [1, 0];
    case "west":  return [-1, 0];
    default:      return assertNever(direction);
  }
}

// Later, someone adds "northeast" to Direction:
// type Direction = "north" | "south" | "east" | "west" | "northeast";
// 
// Compile error in assertNever(direction):
// Argument of type '"northeast"' is not assignable to parameter of type 'never'
// This forces them to handle the new case!

Switch Default with never

// Alternative: inline never check without a helper function
function getLabel(status: AsyncState<unknown>["status"]): string {
  switch (status) {
    case "idle":    return "Ready";
    case "loading": return "Loading…";
    case "success": return "Done";
    case "error":   return "Failed";
    default: {
      const _exhaustive: never = status;
      return _exhaustive; // unreachable, but satisfies return type
    }
  }
}

Why This Catches Missing Cases at Compile Time

┌─────────────────────────────────────────────────────────────┐
│  Union: "A" | "B" | "C"                                    │
│                                                             │
│  case "A": → handled, removes "A" from remaining type      │
│  case "B": → handled, removes "B" from remaining type      │
│  case "C": → handled, removes "C" from remaining type      │
│  default:  → remaining type is never → no error            │
│                                                             │
│  If "D" is added to union:                                  │
│  case "A": → removes "A"                                   │
│  case "B": → removes "B"                                   │
│  case "C": → removes "C"                                   │
│  default:  → remaining type is "D" → ERROR: "D" ≠ never   │
└─────────────────────────────────────────────────────────────┘

Comparison with ESLint switch-exhaustiveness-check

Approach Catches at Runtime safety Works in expressions
assertNever Compile time + Runtime Yes (throws) Yes
ESLint switch-exhaustiveness-check Lint time only No No (statements only)
noImplicitReturns tsconfig Compile time No No

Best practice: Use assertNever AND the ESLint rule together. The ESLint rule gives faster IDE feedback, while assertNever provides runtime safety for unexpected values (e.g., from deserialized JSON).

Assertion Functions (asserts)

Narrow types by asserting conditions or types…

asserts condition Syntax

function assertDefined<T>(
  value: T | null | undefined,
  message?: string
): asserts value is T {
  if (value === null || value === undefined) {
    throw new Error(message ?? "Value is null or undefined");
  }
}

function processUser(user: User | null) {
  assertDefined(user, "User must be loaded");
  // After this line, user: User (narrowed!)
  console.log(user.name);
}

// asserts condition — narrows in the enclosing scope
function assertIsString(value: unknown): asserts value is string {
  if (typeof value !== "string") {
    throw new TypeError(`Expected string, got ${typeof value}`);
  }
}

asserts value is Type Syntax

interface LoadedDocument {
  id: string;
  content: string;
  metadata: DocumentMetadata;
}

interface UnloadedDocument {
  id: string;
  content: null;
  metadata: null;
}

type Document = LoadedDocument | UnloadedDocument;

function assertLoaded(doc: Document): asserts doc is LoadedDocument {
  if (doc.content === null) {
    throw new Error(`Document ${doc.id} has not been loaded`);
  }
}

function renderDocument(doc: Document) {
  assertLoaded(doc);
  // doc: LoadedDocument — safely access content and metadata
  render(doc.content, doc.metadata);
}

When to Use vs Type Guards

Feature Type Guard (is) Assertion Function (asserts)
Return type boolean void (throws on failure)
Control flow Narrows in if/else branches Narrows everything after the call
Use case Conditional logic, filtering Preconditions, invariants, fail-fast
Composability Works with &&, ||, ternaries Must be standalone statement

Relationship to Node's assert Module

import assert from "node:assert";

// Node's assert already narrows in TypeScript!
function process(value: string | undefined) {
  assert(value !== undefined, "value is required");
  // value: string — narrowed by assert
  console.log(value.toUpperCase());
}

// Custom assert with more specific narrowing:
function assertInstanceOf<T>(
  value: unknown,
  constructor: new (...args: any[]) => T,
  message?: string
): asserts value is T {
  if (!(value instanceof constructor)) {
    throw new Error(message ?? `Expected instance of ${constructor.name}`);
  }
}

Limitations

  • Assertion functions cannot be used in expressions — only as standalone statements
  • They cannot be arrow functions assigned to variables (must be function declarations or methods) — Note: TS 5.5 relaxed this restriction; arrow functions can now have assertion signatures
  • The compiler trusts your assertion — an incorrect implementation causes unsound types
  • No narrowing in the "else" branch (unlike type guards)
  • Cannot be used with Promise — async assertion functions don't narrow

Warning: Assertion functions are trusted by the compiler. If your assertion logic is wrong, TypeScript will still narrow the type, leading to runtime errors that look type-safe at compile time.

Narrowing with Custom Predicates

Writing reusable, composable type guard functions…

Writing Type Guard Functions

// Basic type guard
function isNonNull<T>(value: T | null | undefined): value is T {
  return value !== null && value !== undefined;
}

// Compound type guard
interface ApiError {
  code: number;
  message: string;
  details?: Record<string, unknown>;
}

function isApiError(error: unknown): error is ApiError {
  return (
    typeof error === "object" &&
    error !== null &&
    "code" in error &&
    "message" in error &&
    typeof (error as ApiError).code === "number" &&
    typeof (error as ApiError).message === "string"
  );
}

Generic Type Guards

// Guard that narrows array elements
function isArrayOf<T>(
  arr: unknown[],
  guard: (item: unknown) => item is T
): arr is T[] {
  return arr.every(guard);
}

// Usage
function isString(value: unknown): value is string {
  return typeof value === "string";
}

const data: unknown[] = ["a", "b", "c"];
if (isArrayOf(data, isString)) {
  // data: string[]
  data.map(s => s.toUpperCase());
}

// Generic "has property" guard
function hasProperty<K extends string>(
  obj: object,
  key: K
): obj is object & Record<K, unknown> {
  return key in obj;
}

Narrowing Arrays (filter with Type Predicates)

const items: (string | null | undefined)[] = ["a", null, "b", undefined, "c"];

// Without type predicate: result is (string | null | undefined)[]
const filtered1 = items.filter(item => item != null);

// With type predicate: result is string[]
const filtered2 = items.filter((item): item is string => item != null);

// Real-world: filtering resolved results
type Result<T> = { ok: true; value: T } | { ok: false; error: Error };

function isOk<T>(result: Result<T>): result is { ok: true; value: T } {
  return result.ok;
}

async function fetchAll(urls: string[]): Promise<string[]> {
  const results = await Promise.allSettled(urls.map(fetch));
  return results
    .filter((r): r is PromiseFulfilledResult<Response> => r.status === "fulfilled")
    .map(r => r.value.url);
}

Common Pitfalls: Lying Predicates

// ✗ DANGEROUS: This predicate lies!
function isNumber(value: unknown): value is number {
  return typeof value === "string"; // BUG: checking string, claiming number
}

const val: unknown = "hello";
if (isNumber(val)) {
  // val is narrowed to number — but it's actually a string!
  console.log(val.toFixed(2)); // Runtime crash: val.toFixed is not a function
}

// ✗ SUBTLE BUG: Incomplete validation
interface Config {
  host: string;
  port: number;
  ssl: boolean;
}

function isConfig(obj: unknown): obj is Config {
  // Only checks one field — could pass with missing fields!
  return typeof obj === "object" && obj !== null && "host" in obj;
}

// ✓ SAFE: Use a validation library (zod, io-ts) for runtime checks
import { z } from "zod";

const ConfigSchema = z.object({
  host: z.string(),
  port: z.number(),
  ssl: z.boolean(),
});

function isValidConfig(obj: unknown): obj is Config {
  return ConfigSchema.safeParse(obj).success;
}

Rule of thumb: The compiler trusts your type predicate unconditionally. If you lie, you get unsound types. For complex shapes, prefer schema validation (zod, io-ts, valibot) over hand-written predicates.

Non-Null Assertion vs Optional Chaining

Navigating nullable types safely (and unsafely)…

The ! Operator (Dangerous)

// Non-null assertion: tells TS "I know this isn't null"
function getElement(id: string): HTMLElement {
  const el = document.getElementById(id)!;
  // el: HTMLElement (null possibility removed)
  // If element doesn't exist → runtime error!
  return el;
}

// When it's acceptable (rare):
// - After a runtime check that TS can't understand
// - In tests where you control the DOM
// - Immediately after a Map.set() → Map.get()

const map = new Map<string, number>();
map.set("key", 42);
const value = map.get("key")!; // We just set it — safe-ish

Optional Chaining ?. (Safe)

interface Company {
  name: string;
  address?: {
    street: string;
    city: string;
    country?: {
      code: string;
      name: string;
    };
  };
}

function getCountryCode(company: Company): string | undefined {
  // Safe traversal — returns undefined if any link is missing
  return company.address?.country?.code;
}

// Works with method calls and indexed access
const arr: number[] | undefined = getNumbers();
const first = arr?.[0];            // number | undefined
const length = arr?.length;        // number | undefined
const result = arr?.map(x => x * 2); // number[] | undefined

Nullish Coalescing ?? 

// ?? returns right-hand side ONLY for null/undefined (not "" or 0)
const port = config.port ?? 3000;        // default only if null/undefined
const name = config.name ?? "anonymous"; // "" would NOT trigger default

// Compare with ||  which treats "", 0, NaN, false as falsy:
const port2 = config.port || 3000; // 0 would trigger default — likely a bug!

// Combining ?. and ??
function getDisplayName(user: User | null): string {
  return user?.profile?.displayName ?? user?.email ?? "Unknown User";
}

// ??= assignment operator
let cache: Map<string, Data> | undefined;
cache ??= new Map(); // initialize only if null/undefined

When Each Is Appropriate

Operator Use When Risk Level
! (non-null assertion) You have external proof the value exists 🔴 High — runtime crash if wrong
?. (optional chaining) Navigating nullable structures safely 🟢 Safe — returns undefined
?? (nullish coalescing) Providing defaults for null/undefined 🟢 Safe — explicit fallback

ESLint Rules

// .eslintrc.json
{
  "rules": {
    "@typescript-eslint/no-non-null-assertion": "warn",
    "@typescript-eslint/prefer-optional-chain": "error",
    "@typescript-eslint/prefer-nullish-coalescing": "error"
  }
}

Senior stance: Ban ! in production code via ESLint. Allow it only in test files. Every ! is a potential runtime crash hiding behind type safety.

satisfies Operator (TS 4.9+)

Type-check without widening — the best of both worlds

Cross-reference: For satisfies in the context of type checking and validation, see Ch9: satisfies & TS 5.x Features. This section focuses specifically on how satisfies interacts with narrowing preservation.

What It Does vs Type Annotation

type Color = "red" | "green" | "blue";
type Theme = Record<string, Color>;

// With type annotation: loses literal key info
const theme1: Theme = {
  primary: "blue",
  secondary: "green",
};
// theme1.primary — type is Color (widened)
// theme1.oops — no error! (Record<string, Color> allows any key)

// With satisfies: keeps literal types AND validates
const theme2 = {
  primary: "blue",

State Machine with Discriminated Unions

// Complete checkout flow state machine
type CheckoutState =
  | { step: "cart"; items: CartItem[]; coupon?: string }
  | { step: "shipping"; items: CartItem[]; address: Address }
  | { step: "payment"; items: CartItem[]; address: Address; method: PaymentMethod }
  | { step: "confirming"; orderId: string }
  | { step: "complete"; orderId: string; receipt: Receipt }
  | { step: "error"; previousStep: CheckoutState["step"]; error: Error };

type CheckoutEvent =
  | { type: "PROCEED_TO_SHIPPING"; address: Address }
  | { type: "PROCEED_TO_PAYMENT"; method: PaymentMethod }
  | { type: "CONFIRM_ORDER" }
  | { type: "ORDER_CONFIRMED"; orderId: string; receipt: Receipt }
  | { type: "GO_BACK" }
  | { type: "ERROR"; error: Error };

function checkoutTransition(
  state: CheckoutState,
  event: CheckoutEvent
): CheckoutState {
  switch (state.step) {
    case "cart":
      if (event.type === "PROCEED_TO_SHIPPING") {
        return { step: "shipping", items: state.items, address: event.address };
      }
      return state;

    case "shipping":
      if (event.type === "PROCEED_TO_PAYMENT") {
        return { ...state, step: "payment", method: event.method };
      }
      if (event.type === "GO_BACK") {
        return { step: "cart", items: state.items, coupon: undefined };
      }
      return state;

    case "payment":
      if (event.type === "CONFIRM_ORDER") {
        return { step: "confirming", orderId: crypto.randomUUID() };
      }
      return state;

    case "confirming":
      if (event.type === "ORDER_CONFIRMED") {
        return { step: "complete", orderId: state.orderId, receipt: event.receipt };
      }
      if (event.type === "ERROR") {
        return { step: "error", previousStep: "confirming", error: event.error };
      }
      return state;

    case "complete":
      return state; // terminal state

    case "error":
      return state; // requires explicit reset
  }
}

API Response Handling

// Type-safe API layer with exhaustive error handling
type HttpResult<T> =
  | { status: "success"; code: 200 | 201; data: T }
  | { status: "client-error"; code: 400 | 401 | 403 | 404 | 422; message: string }
  | { status: "server-error"; code: 500 | 502 | 503; retryable: boolean }
  | { status: "network-error"; error: TypeError };

async function fetchWithNarrowing<T>(
  url: string,
  schema: { parse: (data: unknown) => T }
): Promise<HttpResult<T>> {
  try {
    const res = await fetch(url);
    if (res.ok) {
      const data = schema.parse(await res.json());
      return { status: "success", code: res.status as 200 | 201, data };
    }
    if (res.status < 500) {
      return {
        status: "client-error",
        code: res.status as 400 | 401 | 403 | 404 | 422,
        message: await res.text(),
      };
    }
    return {
      status: "server-error",
      code: res.status as 500 | 502 | 503,
      retryable: res.status !== 501,
    };
  } catch (err) {
    return { status: "network-error", error: err as TypeError };
  }
}

// Consumer narrows with switch
function handleResult<T>(result: HttpResult<T>): T | null {
  switch (result.status) {
    case "success":
      return result.data;
    case "client-error":
      if (result.code === 401) redirectToLogin();
      toast.error(result.message);
      return null;
    case "server-error":
      if (result.retryable) scheduleRetry();
      return null;
    case "network-error":
      toast.error("Network unavailable");
      return null;
  }
}

Error Handling Hierarchies

type AppError =
  | { kind: "validation"; fields: Record<string, string[]> }
  | { kind: "auth"; reason: "expired" | "invalid" | "forbidden" }
  | { kind: "network"; retryable: boolean; timeout: boolean }
  | { kind: "business"; code: string; userMessage: string }
  | { kind: "unknown"; original: unknown };

function toAppError(err: unknown): AppError {
  if (err instanceof Response) {
    if (err.status === 401 || err.status === 403) {
      return { kind: "auth", reason: err.status === 401 ? "expired" : "forbidden" };
    }
  }
  if (err instanceof TypeError && err.message.includes("fetch")) {
    return { kind: "network", retryable: true, timeout: false };
  }
  return { kind: "unknown", original: err };
}

function showError(error: AppError): string {
  switch (error.kind) {
    case "validation":
      return `Please fix: ${Object.keys(error.fields).join(", ")}`;
    case "auth":
      return error.reason === "expired" ? "Session expired" : "Access denied";
    case "network":
      return error.timeout ? "Request timed out" : "Connection lost";
    case "business":
      return error.userMessage;
    case "unknown":
      return "An unexpected error occurred";
  }
}

Complete State Machine

// Generic finite state machine with type-safe transitions
type StateMachine<
  States extends string,
  Events extends string,
  Context extends Record<string, unknown>
> = {
  initial: States;
  context: Context;
  states: {
    [S in States]: {
      on?: Partial<Record<Events, States>>;
      entry?: (ctx: Context) => Context;
      exit?: (ctx: Context) => Context;
    };
  };
};

type MachineInstance<S extends string, C> = {
  current: S;
  context: C;
  send: (event: string) => void;
};

function createMachine<
  S extends string,
  E extends string,
  C extends Record<string, unknown>
>(definition: StateMachine<S, E, C>): MachineInstance<S, C> {
  let current = definition.initial;
  let context = { ...definition.context };

  return {
    get current() { return current; },
    get context() { return context; },
    send(event: string) {
      const stateConfig = definition.states[current];
      const nextState = stateConfig.on?.[event as E];
      if (nextState) {
        if (stateConfig.exit) context = stateConfig.exit(context);
        current = nextState;
        const nextConfig = definition.states[nextState];
        if (nextConfig.entry) context = nextConfig.entry(context);
      }
    },
  };
}

// Usage
const trafficLight = createMachine({
  initial: "red" as const,
  context: { count: 0 },
  states: {
    red: { on: { TIMER: "green" }, entry: (ctx) => ({ ...ctx, count: ctx.count + 1 }) },
    green: { on: { TIMER: "yellow" } },
    yellow: { on: { TIMER: "red" } },
  },
});

API Response Handler

// Complete type-safe API client with narrowing
type ApiState<T> =
  | { tag: "idle" }
  | { tag: "loading"; abortController: AbortController }
  | { tag: "success"; data: T; fetchedAt: number }
  | { tag: "error"; error: AppError; failedAt: number };

class TypedApiClient {
  private cache = new Map<string, ApiState<unknown>>();

  async fetch<T>(
    url: string,
    parse: (raw: unknown) => T
  ): Promise<ApiState<T>> {
    const controller = new AbortController();
    const loadingState: ApiState<T> = { tag: "loading", abortController: controller };
    this.cache.set(url, loadingState);

    try {
      const res = await fetch(url, { signal: controller.signal });
      if (!res.ok) {
        const errorState: ApiState<T> = {
          tag: "error",
          error: { kind: "network", retryable: res.status >= 500, timeout: false },
          failedAt: Date.now(),
        };
        this.cache.set(url, errorState);
        return errorState;
      }
      const data = parse(await res.json());
      const successState: ApiState<T> = {
        tag: "success",
        data,
        fetchedAt: Date.now(),
      };
      this.cache.set(url, successState);
      return successState;
    } catch (err) {
      const errorState: ApiState<T> = {
        tag: "error",
        error: { kind: "unknown", original: err },
        failedAt: Date.now(),
      };
      this.cache.set(url, errorState);
      return errorState;
    }
  }

  getState<T>(url: string): ApiState<T> {
    return (this.cache.get(url) as ApiState<T>) ?? { tag: "idle" };
  }
}

Generic Type Guard Library

// Composable type guard utilities
const Guards = {
  isString: (v: unknown): v is string => typeof v === "string",
  isNumber: (v: unknown): v is number => typeof v === "number" && !Number.isNaN(v),
  isBoolean: (v: unknown): v is boolean => typeof v === "boolean",
  isNull: (v: unknown): v is null => v === null,
  isUndefined: (v: unknown): v is undefined => v === undefined,
  isNonNull: <T>(v: T | null | undefined): v is T => v != null,

  isObject: (v: unknown): v is Record<string, unknown> =>
    typeof v === "object" && v !== null && !Array.isArray(v),

  isArray: (v: unknown): v is unknown[] => Array.isArray(v),

  isArrayOf: <T>(guard: (v: unknown) => v is T) =>
    (v: unknown): v is T[] => Array.isArray(v) && v.every(guard),

  hasKey: <K extends string>(key: K) =>
    (v: unknown): v is Record<K, unknown> =>
      typeof v === "object" && v !== null && key in v,

  // Compose guards with AND logic
  and: <A, B>(
    guardA: (v: unknown) => v is A,
    guardB: (v: unknown) => v is B
  ) => (v: unknown): v is A & B => guardA(v) && guardB(v),

  // Compose guards with OR logic
  or: <A, B>(
    guardA: (v: unknown) => v is A,
    guardB: (v: unknown) => v is B
  ) => (v: unknown): v is A | B => guardA(v) || guardB(v),
};

// Usage
const isStringArray = Guards.isArrayOf(Guards.isString);
const isConfig = Guards.and(
  Guards.hasKey("host"),
  Guards.hasKey("port")
);

const data: unknown = getExternalData();
if (isStringArray(data)) {
  // data: string[]
  data.forEach(s => console.log(s.toUpperCase()));
}

Exhaustive Redux Reducer

// Type-safe Redux with exhaustive action handling
interface AppState {
  users: User[];
  loading: boolean;
  error: string | null;
  selectedId: string | null;
}

type AppAction =
  | { type: "USERS_FETCH_START" }
  | { type: "USERS_FETCH_SUCCESS"; payload: User[] }
  | { type: "USERS_FETCH_ERROR"; payload: string }
  | { type: "USER_SELECT"; payload: string }
  | { type: "USER_DESELECT" }
  | { type: "USER_UPDATE"; payload: { id: string; changes: Partial<User> } };

function assertNever(action: never): never {
  throw new Error(`Unhandled action: ${JSON.stringify(action)}`);
}

function appReducer(state: AppState, action: AppAction): AppState {
  switch (action.type) {
    case "USERS_FETCH_START":
      return { ...state, loading: true, error: null };

    case "USERS_FETCH_SUCCESS":
      return { ...state, loading: false, users: action.payload };

    case "USERS_FETCH_ERROR":
      return { ...state, loading: false, error: action.payload };

    case "USER_SELECT":
      return { ...state, selectedId: action.payload };

    case "USER_DESELECT":
      return { ...state, selectedId: null };

    case "USER_UPDATE":
      return {
        ...state,
        users: state.users.map(u =>
          u.id === action.payload.id
            ? { ...u, ...action.payload.changes }
            : u
        ),
      };

    default:
      return assertNever(action);
      // If a new action type is added to AppAction without handling here,
      // TypeScript will report: Argument of type '{ type: "NEW_ACTION" }' is not
      // assignable to parameter of type 'never'
  }
}

Common Mistakes

Five pitfalls that trip up even experienced developers…

1. Using Type Assertions Instead of Guards

// ✗ BAD: Asserts bypass type checking entirely
function processEvent(event: unknown) {
  const e = event as MouseEvent; // No runtime check!
  console.log(e.clientX); // May crash if event is KeyboardEvent
}

// ✓ GOOD: Guard provides runtime + compile-time safety
function processEvent(event: unknown) {
  if (event instanceof MouseEvent) {
    console.log(event.clientX); // Narrowed safely
  }
}

Rule: as is a lie you tell the compiler. Type guards are a proof you show it. Prefer proofs.

2. Non-Exhaustive Switch Without never Check

type Status = "active" | "inactive" | "suspended" | "deleted";

// ✗ BAD: Silently returns undefined for new variants
function getLabel(status: Status): string {
  switch (status) {
    case "active": return "Active";
    case "inactive": return "Inactive";
    // "suspended" and "deleted" fall through — returns undefined!
  }
}

// ✓ GOOD: Compile error for missing cases
function getLabel(status: Status): string {
  switch (status) {
    case "active": return "Active";
    case "inactive": return "Inactive";
    case "suspended": return "Suspended";
    case "deleted": return "Deleted";
    default: {
      const _: never = status;
      throw new Error(`Unknown status: ${_}`);
    }
  }
}

3. Lying Type Predicates

// ✗ BAD: Predicate doesn't match the claimed type
interface User { id: string; name: string; email: string }

function isUser(obj: unknown): obj is User {
  // Only checks 'id' — name and email might be missing!
  return typeof obj === "object" && obj !== null && "id" in obj;
}

const data: unknown = { id: "1" }; // Missing name, email
if (isUser(data)) {
  console.log(data.name.toUpperCase()); // Runtime crash!
}

// ✓ GOOD: Validate all required properties
function isUser(obj: unknown): obj is User {
  return (
    typeof obj === "object" &&
    obj !== null &&
    "id" in obj && typeof (obj as any).id === "string" &&
    "name" in obj && typeof (obj as any).name === "string" &&
    "email" in obj && typeof (obj as any).email === "string"
  );
}

4. Narrowing Not Persisting Across Function Boundaries

// ✗ BAD: Narrowing lost in callback
function processItems(items: (string | number)[]) {
  items.forEach(item => {
    if (typeof item === "string") {
      // item: string — narrowed here ✓
      setTimeout(() => {
        // item: string — actually still narrowed in this case ✓
        // (TS is smart enough for const-like loop variables)
      }, 0);
    }
  });
}

// ✗ BAD: Narrowing lost when passed to another function
function isValid(x: string | number): void {
  if (typeof x === "string") {
    doSomething(x); // x: string here ✓
  }
}

function doSomething(x: string) {
  // If doSomething reassigns x to a mutable variable, narrowing is gone
  let y: string | number = x;
  // y: string | number — widened
}

// ✓ GOOD: Use const to preserve narrowing
function example(input: string | number) {
  if (typeof input === "string") {
    const str = input; // const preserves the narrowed type
    setTimeout(() => {
      console.log(str.toUpperCase()); // str: string ✓
    }, 100);
  }
}

5. Forgetting undefined in Optional Properties

// ✗ BAD: Optional property ≠ property with type | undefined
interface Config {
  timeout?: number;   // type is number | undefined
  retries?: number;
}

function init(config: Config) {
  // ✗ This doesn't narrow properly with exactOptionalPropertyTypes
  if (config.timeout) {
    // timeout: number — but 0 is valid and would fail this check!
  }

  // ✓ GOOD: Explicit undefined check
  if (config.timeout !== undefined) {
    // timeout: number (correctly handles 0)
    console.log(`Timeout: ${config.timeout}ms`);
  }

  // ✓ GOOD: Nullish coalescing for defaults
  const timeout = config.timeout ?? 5000;
  const retries = config.retries ?? 3;
}

// Enable exactOptionalPropertyTypes in tsconfig for strictest checking:
// { "compilerOptions": { "exactOptionalPropertyTypes": true } }
// This distinguishes { timeout?: number } from { timeout: number | undefined }
//
// Without this flag:  { timeout?: number } means timeout can be number | undefined
//   → You can write: config.timeout = undefined  ✅ (allowed)
//
// With this flag:     { timeout?: number } means timeout can be number OR absent
//   → config.timeout = undefined  ❌ (Error! undefined !== absent)
//   → delete config.timeout       ✅ (removes the property)
//
// This fundamentally changes narrowing: with the flag enabled, checking
// 'timeout' in config narrows to number (not number | undefined).
// It's a senior-level differentiator — most devs don't know this flag exists.
// Not included in strict: true — must be enabled explicitly.

Trade-offs

Comparing approaches and their engineering costs…

Type Guards vs Assertion Functions

Dimension Type Guards (is) Assertion Functions (asserts)
Control flow Narrows in branches (if/else) Narrows everything after the call
Composability Works in expressions, filter(), ternaries Must be standalone statement
Failure handling Returns false — caller decides Throws — fail-fast, no recovery
Best for Conditional paths, array filtering Preconditions, invariants, validation at boundaries
Testing Easy to test (returns boolean) Requires try/catch in tests

Discriminated Unions vs Class Hierarchy

Dimension Discriminated Unions Class Hierarchy
Extensibility Add variant = add to union (open) Add subclass (open, but scattered)
Exhaustiveness Built-in via never Requires visitor pattern or instanceof chains
Serialization Plain objects — easy JSON roundtrip Requires custom serialization logic
Bundle size Zero runtime cost (erased) Classes remain in bundle
Pattern matching Native via switch on discriminant Requires instanceof or visitor
Encapsulation No private state Private fields and methods
Best for Data modeling, state machines, API types Services, complex behaviors, DI

Strict Null Checks: Cost vs Safety

Dimension strictNullChecks: true strictNullChecks: false
Safety Catches null/undefined bugs at compile time Runtime "cannot read property of undefined" errors
Developer friction More guards/checks required, more verbose Less code, faster initial development
Refactoring Compiler guides all affected code paths Silent breakage — found only at runtime
Onboarding Steeper learning curve for juniors Feels easier initially
Verdict Always enable strictNullChecks. The short-term cost is repaid many times over in prevented production bugs.

Senior perspective: In a large codebase, discriminated unions + exhaustive checks prevent entire categories of bugs from reaching production. The compile-time investment pays for itself on the first missed case that the compiler catches.

Follow-up Questions

Seven questions interviewers ask as follow-ups…

1. "How does narrowing interact with generics?"

TypeScript cannot narrow generic type parameters directly. You need to constrain the generic or use a type guard that returns a specific instantiation:

// ✗ Doesn't work: TS can't narrow T
function process<T extends string | number>(value: T) {
  if (typeof value === "string") {
    // value is still T, not string — TS preserves the generic
    // value.toUpperCase(); // Error!
  }
}

// ✓ Works: assign to a wider variable
function process<T extends string | number>(value: T) {
  const v: string | number = value; // widen from T
  if (typeof v === "string") {
    v.toUpperCase(); // ✓ v is string
  }
}

2. "What happens with narrowing in async code?"

Narrowing persists across await as long as the variable isn't reassigned. But assertion functions don't work with async:

async function example(x: string | null) {
  if (x !== null) {
    await someAsyncOp();
    // x is still string ✓ (not reassigned)
    console.log(x.toUpperCase());
  }
}

// ✗ Async assertion functions don't narrow
async function assertLoaded(doc: Doc): asserts doc is LoadedDoc {
  // This doesn't compile — asserts cannot be async
}

3. "How do you narrow unknown vs any?"

unknown requires narrowing before use — it's the type-safe counterpart to any. any disables all type checking:

function handleUnknown(value: unknown) {
  // value.toString(); // ✗ Error — must narrow first
  if (typeof value === "string") {
    value.toUpperCase(); // ✓ narrowed to string
  }
}

function handleAny(value: any) {
  value.anything.goes.here(); // No error — no safety
}

4. "Can you narrow based on array length?"

// TypeScript doesn't narrow array length natively,
// but you can use tuples and type predicates:
type NonEmptyArray<T> = [T, ...T[]];

function isNonEmpty<T>(arr: T[]): arr is NonEmptyArray<T> {
  return arr.length > 0;
}

function first<T>(arr: T[]): T | undefined {
  if (isNonEmpty(arr)) {
    return arr[0]; // ✓ T, not T | undefined
  }
  return undefined;
}

5. "What's the difference between type narrowing and type casting?"

Narrowing is sound — the compiler verifies the check. Casting (as) is unsound — you override the compiler with no proof:

// Narrowing: compiler verifies
if (typeof x === "string") { /* x: string — proven */ }

// Casting: compiler trusts you blindly
const x = value as string; // May be wrong — no verification

6. "How does narrowing work with branded types?"

type UserId = string & { __brand: "UserId" };
type PostId = string & { __brand: "PostId" };

function isUserId(id: string): id is UserId {
  return id.startsWith("usr_");
}

function isPostId(id: string): id is PostId {
  return id.startsWith("post_");
}

function getUser(id: UserId): User { /* ... */ }

const rawId = "usr_123";
if (isUserId(rawId)) {
  getUser(rawId); // ✓ rawId is narrowed to UserId
}
// getUser(rawId); // ✗ Error: string is not UserId

7. "How do you migrate a codebase to stricter narrowing?"

Progressive strictness strategy:

  1. Enable strictNullChecks in tsconfig (the biggest win)
  2. Fix errors file-by-file using // @ts-expect-error as temporary markers
  3. Replace as assertions with proper type guards one module at a time
  4. Add assertNever to all switch statements on discriminated unions
  5. Enable noUncheckedIndexedAccess last (most disruptive)
  6. Use ESLint @typescript-eslint/no-unnecessary-type-assertion to prevent regression

8. "How does using (TS 5.2) interact with narrowing?"

The using declaration (Explicit Resource Management) guarantees Symbol.dispose is called at block exit — even on throw. This interacts with control flow because the compiler knows the resource is valid for the entire block scope. It doesn't add new narrowing capability, but it eliminates the need for try/finally patterns that break narrowing (since variables declared inside try blocks aren't narrowed across the catch/finally boundary).

Key Principles

  • Narrow, don't assert. Type guards prove; as asserts without proof.
  • Discriminate at the top level. A single literal property enables the entire narrowing chain.
  • Exhaust with never. Every switch on a union should end with assertNever.
  • Validate at boundaries. External data gets schema-validated; internal data uses compile-time checks.
  • satisfies > annotation when you want validation without widening.

What NOT to Say

  • ❌ "I use as any to fix type errors quickly" — signals you bypass the type system
  • ❌ "Type guards are just for primitives" — ignores custom predicates, discriminated unions
  • ❌ "I don't bother with exhaustive checks in switch" — misses the core maintenance benefit
  • ❌ "Non-null assertion is fine if you're careful" — seniors know careful isn't scalable
  • ❌ "I use enums for discriminated unions" — string enums are fine, but const objects + as const are preferred in modern TS

One-Sentence Summary

Design your types so that the compiler narrows them naturally, use never to make exhaustive handling mandatory, and validate at system boundaries — this makes illegal states unrepresentable and the compiler your most reliable reviewer.

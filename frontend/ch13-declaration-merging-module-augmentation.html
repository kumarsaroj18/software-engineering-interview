Chapter 13: Declaration Merging & Module Augmentation

“How do declaration merging and module augmentation work? When would you extend third-party types?”

Key Takeaway: Declaration merging is TypeScript’s mechanism for combining multiple declarations of the same name into a single definition. Interface merging adds properties, namespace merging adds exports, and module augmentation (declare module) extends third-party types without forking. Understanding these mechanisms is essential for extending libraries (Express Request, React’s HTMLAttributes), creating plugin systems, and managing type definitions in large monorepos.

Interviewer’s Intent

What the interviewer is really asking
  • Can you extend third-party library types without modifying node_modules?
  • Do you understand how TypeScript merges multiple declarations of the same name?
  • Can you author and maintain .d.ts files for untyped code or custom augmentations?
  • Do you know the difference between module augmentation and global augmentation?
  • Can you set up type-safe environment configurations in production apps?
  • Do you understand how @types packages, triple-slash directives, and tsconfig interact?
Signal: This question separates developers who use TypeScript from those who can architect TypeScript solutions for teams. It reveals mastery of the type system’s extensibility model.

60-Second Answer

Quick interview response

Declaration merging lets TypeScript combine multiple declarations sharing the same name into one definition. The most common form is interface merging—two interface declarations with the same name automatically combine their members. This is how you extend Window, Express.Request, or any global/library interface.

Module augmentation uses declare module "module-name" to add types to an existing module without modifying its source. The file performing the augmentation must itself be a module (have an import or export). Exception: in .d.ts files without imports/exports (script files), declare module creates an ambient module declaration rather than augmenting — this is how @types packages work. The distinction: augmentation extends an existing module; ambient declaration defines one from scratch.

Global augmentation uses declare global { } inside a module file to add to the global scope.

Key rules: interfaces merge freely, namespaces merge with classes/functions/enums to add static members, and you should prefer module-scoped augmentation over global to minimize collision risk.

// Module augmentation example
import 'express';

declare module 'express' {
  interface Request {
    userId?: string;
    correlationId?: string;
  }
}

// Global augmentation example
export {}; // makes this a module

declare global {
  interface Window {
    analytics: AnalyticsSDK;
  }
}

Declaration Merging Rules

What can merge with what — precedence & conflict resolution

Merging Compatibility Matrix

Declaration A Declaration B Merges? Notes
InterfaceInterface✔Members accumulate
NamespaceNamespace✔Exported members accumulate
ClassNamespace✔Adds static members to class
FunctionNamespace✔Adds properties to function
EnumNamespace✔Adds extra members/methods
ClassClass✘Error: duplicate identifier
VariableVariable✘Error: duplicate identifier
Type AliasType Alias✘Error: duplicate identifier
InterfaceType Alias✘Error: duplicate identifier

Precedence Rules

  Declaration Spaces in TypeScript:
  ┌──────────────────────────────────────────┐
  │  Value Space     │  Type Space    │  Namespace Space  │
  │  - var/let/const │  - interface   │  - namespace      │
  │  - function      │  - type alias  │  - module         │
  │  - class         │  - class       │  - enum           │
  │  - enum          │  - enum        │                   │
  │                  │  - namespace   │                   │
  └──────────────────────────────────────────┘

  A single name can occupy multiple spaces simultaneously.
  Merging occurs within and across spaces.

Conflict Resolution

// Non-function members: MUST be identical types
interface Box {
  size: number;
}
interface Box {
  size: number; // OK - same type
  // size: string; // ERROR - conflicts with previous
}

// Function members: become overloads
interface Serializer {
  serialize(input: string): string;
}
interface Serializer {
  serialize(input: number): string; // OK - adds overload
}
// Later declarations get HIGHER priority in overload resolution

// Single string literal parameter gets even higher priority
interface Document {
  createElement(tagName: string): HTMLElement;
}
interface Document {
  createElement(tagName: "div"): HTMLDivElement;  // Higher priority
  createElement(tagName: "span"): HTMLSpanElement; // Higher priority
}
Warning: Non-function members with the same name but different types cause a compile error. There is no “last wins” for properties—they must be type-compatible.

Interface Merging

Properties accumulate, method overloads, generics, practical use

Basic Property Accumulation

interface User {
  id: string;
  name: string;
}

interface User {
  email: string;
  role: 'admin' | 'user';
}

// Merged result:
// interface User {
//   id: string;
//   name: string;
//   email: string;
//   role: 'admin' | 'user';
// }

Method Overload Merging

interface Logger {
  log(message: string): void;
}

interface Logger {
  log(message: string, level: 'info' | 'warn' | 'error'): void;
  log(message: Error): void;
}

// Merged (later declarations get higher overload priority):
// interface Logger {
//   log(message: string, level: 'info' | 'warn' | 'error'): void;
//   log(message: Error): void;
//   log(message: string): void;
// }

Generics in Merged Interfaces

// Generic parameters must match exactly
interface Container<T> {
  value: T;
}

interface Container<T> {
  clone(): Container<T>;
}
// OK: same number of generic parameters with compatible constraints
// Note: parameter NAMES don't need to match (T vs U is fine),
// but the NUMBER of parameters must be the same

Practical: Extending Window

// globals.d.ts
interface Window {
  __REDUX_DEVTOOLS_EXTENSION__?: () => any;
  dataLayer: Record<string, unknown>[];
  gtag: (...args: any[]) => void;
}

// Usage - no type errors
window.__REDUX_DEVTOOLS_EXTENSION__?.();
window.dataLayer.push({ event: 'page_view' });

Extending lib.dom.d.ts

// Extend HTMLElementTagNameMap for custom elements
interface HTMLElementTagNameMap {
  'my-component': MyComponentElement;
  'app-header': AppHeaderElement;
}

// Now document.createElement knows about custom elements
const el = document.createElement('my-component'); // MyComponentElement
Tip: Interface merging is the primary mechanism behind lib.dom.d.ts extensibility. Libraries like Lit and Stencil use this to register custom element types.

Namespace Merging

Adding static members, companion pattern, enum+namespace

Adding Static Members to Classes

class Validator {
  validate(input: string): boolean {
    return input.length > 0;
  }
}

namespace Validator {
  export const VERSION = '2.0.0';
  export function create(): Validator {
    return new Validator();
  }
}

// Usage
Validator.VERSION; // "2.0.0"
Validator.create().validate('hello'); // true

Adding Properties to Functions

function request(url: string): Promise<Response> {
  return fetch(url);
}

namespace request {
  export function get(url: string) {
    return request(url);
  }
  export function post(url: string, body: unknown) {
    return fetch(url, { method: 'POST', body: JSON.stringify(body) });
  }
  export const defaults = {
    baseURL: '',
    timeout: 5000,
  };
}

// Usage
request('https://api.example.com');
request.get('/users');
request.post('/users', { name: 'Alice' });
request.defaults.timeout; // 5000

Companion Namespace Pattern

// The type and the value share the same name
interface Color {
  r: number;
  g: number;
  b: number;
  a?: number;
}

namespace Color {
  export function fromHex(hex: string): Color {
    const r = parseInt(hex.slice(1, 3), 16);
    const g = parseInt(hex.slice(3, 5), 16);
    const b = parseInt(hex.slice(5, 7), 16);
    return { r, g, b };
  }

  export function toCSS(color: Color): string {
    const { r, g, b, a = 1 } = color;
    return `rgba(${r}, ${g}, ${b}, ${a})`;
  }

  export const RED: Color = { r: 255, g: 0, b: 0 };
  export const GREEN: Color = { r: 0, g: 255, b: 0 };
  export const BLUE: Color = { r: 0, g: 0, b: 255 };
}

// Used as both type and value
const bg: Color = Color.fromHex('#ff8800');
const css = Color.toCSS(bg);

Enum + Namespace Merging

enum Direction {
  Up = 'UP',
  Down = 'DOWN',
  Left = 'LEFT',
  Right = 'RIGHT',
}

namespace Direction {
  export function isHorizontal(dir: Direction): boolean {
    return dir === Direction.Left || dir === Direction.Right;
  }
  export function opposite(dir: Direction): Direction {
    const map: Record<Direction, Direction> = {
      [Direction.Up]: Direction.Down,
      [Direction.Down]: Direction.Up,
      [Direction.Left]: Direction.Right,
      [Direction.Right]: Direction.Left,
    };
    return map[dir];
  }
}

Direction.isHorizontal(Direction.Left); // true
Direction.opposite(Direction.Up); // Direction.Down

Enum Merging

Rarely needed in practice: Modern TypeScript best practice strongly discourages enums in favor of as const objects (better tree-shaking, no runtime artifacts, clearer semantics). Enum merging is even more niche — most style guides ban it entirely. Know it exists for interview purposes, but lead with "I'd use as const instead" if asked about extending enum-like types.

How enums merge, const enum limitations, when to use

Basic Enum Merging

// First declaration must contain initializers for numeric enums
enum Status {
  Active = 0,
  Inactive = 1,
}

enum Status {
  Pending = 2,
  Archived = 3,
}

// Merged: Status.Active, Status.Inactive, Status.Pending, Status.Archived

Const Enum Limitations

// const enums CANNOT be merged across declarations
const enum Color {
  Red,
  Green,
}

// ERROR: In 'const' enum declarations member initializer
// must be constant expression
// const enum Color {
//   Blue = 2,
// }

// Workaround: use regular enum or union types instead
type ExtendedColor = Color | 'Blue' | 'Purple';

When to Use vs. When to Avoid

Use Enum Merging WhenAvoid When
Extending a library’s enum with plugin-specific values You need tree-shaking (use union types)
Adding utility methods via namespace merging You’re using const enum (can’t merge)
Organizing related constants that grow over time Cross-file merging causes confusion
Warning: Enum merging across files can cause maintenance headaches. Prefer union types or a single enum definition with namespace companions for utility methods.

Module Augmentation (declare module)

Syntax, rules, extending third-party modules

Basic Syntax

// file: augmentations.ts
// MUST have a top-level import or export to be a module
import { AxiosRequestConfig } from 'axios';

declare module 'axios' {
  interface AxiosRequestConfig {
    retryCount?: number;
    cacheTTL?: number;
  }
}

// Now all axios configs accept retryCount and cacheTTL
const config: AxiosRequestConfig = {
  url: '/api/users',
  retryCount: 3,
  cacheTTL: 60_000,
};

Critical Rule: Must Be in a Module

// ❌ WRONG - this is a script file (no import/export)
declare module 'express' {
  interface Request {
    userId: string; // This becomes a NEW module, not augmentation!
  }
}

// ✅ CORRECT - file is a module
export {}; // This single line makes it a module

declare module 'express' {
  interface Request {
    userId: string; // Now this augments the existing module
  }
}
Warning: Without import or export at the top level, declare module creates an ambient module declaration instead of augmenting an existing module. This is the #1 mistake developers make.

Adding New Exports

// ⚠️ Note: This only adds the TYPE - you must still

Overriding Existing Types

// Override a specific export's type (use with caution)
import 'some-library';

declare module 'some-library' {
  // Re-declare the interface with corrected types
  export interface Config {
    port: number;        // was incorrectly typed as string
    host: string;
    debug?: boolean;     // add missing optional property
  }
}

Global Augmentation (declare global)

Window, ProcessEnv, globalThis, when appropriate vs dangerous

Adding to Window

// types/global.d.ts
export {};

declare global {
  interface Window {
    // Analytics
    analytics: {
      track(event: string, properties?: Record<string, unknown>): void;
      identify(userId: string, traits?: Record<string, unknown>): void;
      page(name?: string): void;
    };
    // Feature flags
    __FEATURE_FLAGS__: Record<string, boolean>;
    // Runtime config injected by server
    __APP_CONFIG__: {
      apiUrl: string;
      environment: 'development' | 'staging' | 'production';
      version: string;
    };
  }
}

Adding to NodeJS.ProcessEnv

// types/env.d.ts
export {};

declare global {
  namespace NodeJS {
    interface ProcessEnv {
      NODE_ENV: 'development' | 'production' | 'test';
      PORT: string;
      DATABASE_URL: string;
      REDIS_URL: string;
      JWT_SECRET: string;
      AWS_REGION: string;
      AWS_ACCESS_KEY_ID: string;
      AWS_SECRET_ACCESS_KEY: string;
      // Make optional ones explicit
      SENTRY_DSN?: string;
      FEATURE_NEW_UI?: 'true' | 'false';
    }
  }
}

// Now process.env.DATABASE_URL is typed as string (not string | undefined)

Safety caveat: Typing env vars as string (not string | undefined) via augmentation gives a false sense of safety — the variable might not actually be set at runtime. Pair this augmentation with runtime validation at startup (e.g., Zod schema parsing process.env, as shown in Ch14). The augmentation makes usage sites ergonomic; the validation ensures correctness.

Extending globalThis

export {};

declare global {
  // Works in both browser and Node
  var logger: {
    info(msg: string, meta?: object): void;
    error(msg: string, error?: Error): void;
    warn(msg: string): void;
  };

  // Add to all array instances
  interface Array<T> {
    last(): T | undefined;
  }
}

When Appropriate vs. Dangerous

AppropriateDangerous
Typing injected runtime config (__APP_CONFIG__) Adding methods to built-in prototypes
Typing environment variables Overriding existing DOM types
Third-party scripts loaded via <script> tags Making the global scope a dumping ground
Polyfill type definitions Adding mutable shared state types
Warning: Every global augmentation is visible to the entire project. Use module-scoped types wherever possible and reserve declare global for genuinely global APIs.

Ambient Declarations

declare keyword, .d.ts authoring, emit behavior

The declare Keyword Semantics

The declare keyword tells TypeScript: “this exists at runtime, but I’m only describing its shape—don’t emit any code for it.”

// declare var - describe an existing global variable
declare var jQuery: (selector: string) => any;

// declare function - describe a global function
declare function require(module: string): any;

// declare class - describe a class that exists at runtime
declare class Stripe {
  constructor(apiKey: string);
  charges: {
    create(params: ChargeParams): Promise<Charge>;
  };
}

// declare module - describe a module's shape
declare module '*.css' {
  const styles: Record<string, string>;
  export default styles;
}

declare module '*.svg' {
  const content: string;
  export default content;
}

// declare namespace - group related declarations
declare namespace google.maps {
  class Map {
    constructor(el: HTMLElement, opts?: MapOptions);
  }
  interface MapOptions {
    center: LatLng;
    zoom: number;
  }
  class LatLng {
    constructor(lat: number, lng: number);
  }
}

When TypeScript Emits vs. Doesn’t Emit

  ┌──────────────────────────────────────────────────────┐
  │              EMITS JavaScript              │  NO EMIT │
  ├──────────────────────────────────────────────────────┤
  │  class Foo { }                            │  declare class Foo { }
  │  function bar() { }                       │  declare function bar(): void
  │  const x = 5;                             │  declare const x: number
  │  enum Color { Red }                       │  declare enum Color { Red }
  │  namespace N { export const a = 1; }      │  declare namespace N { ... }
  │                                           │  interface I { }
  │                                           │  type T = string
  └──────────────────────────────────────────────────────┘

  Rule: declare = type-only description, no runtime code generated.
  All content in .d.ts files is implicitly "declare".

.d.ts File Authoring

// my-library.d.ts
// Everything here is implicitly ambient (declare not needed)
export interface Config {
  apiKey: string;
  region: string;
  timeout?: number;
}

export function initialize(config: Config): Client;

export class Client {
  get<T>(path: string): Promise<T>;
  post<T>(path: string, body: unknown): Promise<T>;
  close(): void;
}

export type EventName = 'connect' | 'disconnect' | 'error';
export type EventHandler = (data: unknown) => void;
Note: In .d.ts files, all declarations are implicitly ambient. You don’t need the declare keyword inside .d.ts files, though it’s harmless to include it.

Triple-Slash Directives

reference types, path, lib — when needed vs tsconfig includes

Types of Triple-Slash Directives

/// <reference types="node" />
// Includes @types/node declarations — equivalent to
// adding "node" to tsconfig's "types" array

/// <reference path="./legacy-types.d.ts" />
// Includes another file's declarations — creates a
// dependency ordering for compilation

/// <reference lib="es2022" />
// Includes a built-in lib — like adding "es2022" to
// tsconfig's "lib" array

When They’re Needed

// 1. In .d.ts files that need to reference other type packages
/// <reference types="express" />
declare namespace MyMiddleware {
  interface Options {
    req: Express.Request;
  }
}

// 2. When publishing type packages that depend on other types
// my-package/index.d.ts
/// <reference types="node" />
export function readConfig(path: string): Promise<Buffer>;

// 3. In global script files (non-module) that need types
/// <reference types="jest" />
// Now describe, it, expect are available

When tsconfig Is Preferred

// tsconfig.json — preferred for project-wide settings
{
  "compilerOptions": {
    "types": ["node", "jest"],    // replaces /// <reference types>
    "lib": ["ES2022", "DOM"],     // replaces /// <reference lib>
  },
  "include": ["src/**/*", "types/**/*"]  // replaces /// <reference path>
}
Tip: Prefer tsconfig.json settings over triple-slash directives for application code. Reserve triple-slash directives for .d.ts files you publish as packages, where you can’t control the consumer’s tsconfig.

@types Packages & DefinitelyTyped

Resolution, typeRoots, creating type packages, versioning

How @types Resolution Works

  import express from 'express';

  TypeScript resolution order:
  1. Check node_modules/express/package.json → "types" or "typings" field
  2. Check node_modules/express/index.d.ts
  3. Check node_modules/@types/express/index.d.ts  ← DefinitelyTyped
  4. If none found → implicitly "any" (with noImplicitAny: error)

typeRoots and types in tsconfig

// tsconfig.json
{
  "compilerOptions": {
    // typeRoots: WHERE to look for type packages
    // Default: ["./node_modules/@types"]
    "typeRoots": [
      "./node_modules/@types",
      "./types"              // custom local types directory
    ],

    // types: WHICH packages to include (whitelist)
    // Default: all packages in typeRoots
    "types": ["node", "jest", "express"]
    // Only these three @types packages will be included
    // Useful to prevent pollution from unrelated types
  }
}

Creating a Type Package

// packages/types-my-sdk/package.json

Extending Express, React, Window

Practical examples for real-world library extension

Adding Custom Properties to Express Request

// types/express.d.ts
import 'express';

declare module 'express' {
  interface Request {
    userId?: string;
    organizationId?: string;
    correlationId: string;
    permissions: string[];
    startTime: number;
  }
}

// middleware/auth.ts
import { Request, Response, NextFunction } from 'express';

export function authMiddleware(req: Request, res: Response, next: NextFunction) {
  const token = req.headers.authorization?.split(' ')[1];
  if (!token) return res.status(401).json({ error: 'Unauthorized' });

  const decoded = verifyToken(token);
  req.userId = decoded.sub;
  req.organizationId = decoded.org;
  req.permissions = decoded.permissions;
  next();
}

Type-Only Imports/Exports

import type, export type, verbatimModuleSyntax, bundler compatibility

import type Syntax

// Import only the type — erased completely at compile time
import type { User, ApiResponse } from './types';
import type { FC, ReactNode } from 'react';

// Mixed import: some values, some types
import { useState, useEffect } from 'react';
import type { Dispatch, SetStateAction } from 'react';

// Inline type qualifier (TS 4.5+)
import { Component, type ComponentProps, type ReactNode } from 'react';

export type

// Re-export only as a type
export type { User, Role } from './models';

// Export a type-only declaration
export type EventMap = {
  click: MouseEvent;
  keydown: KeyboardEvent;
  scroll: Event;
};

// Inline type qualifier in re-exports
export { UserService, type UserDTO } from './user-service';

verbatimModuleSyntax (TypeScript 5.0+)

// tsconfig.json
{
  "compilerOptions": {
    "verbatimModuleSyntax": true
    // Replaces: importsNotUsedAsValues, preserveValueImports
  }
}

// With verbatimModuleSyntax: true
// ❌ ERROR: This import will be erased but isn't marked as type-only
import { User } from './types'; // if User is only a type

// ✅ CORRECT
import type { User } from './types';

// The rule: if an import is erased in the output,
// it MUST be marked as type-only

Why It Matters for Bundlers

  Without type-only imports:
  ┌─────────────────┐     ┌──────────────────┐
  │ import { User } │ ──→ │ Bundler includes  │ → Dead code, side effects
  │ from './types'  │     │ the module        │   may be triggered
  └─────────────────┘     └──────────────────┘

  With type-only imports:
  ┌──────────────────────┐     ┌──────────────────┐
  │ import type { User } │ ──→ │ Bundler skips    │ → Smaller bundle,
  │ from './types'       │     │ the module       │   no side effects
  └──────────────────────┘     └──────────────────┘

isolatedModules Compatibility

// With isolatedModules: true (required for Babel, esbuild, swc)
// These tools process one file at a time — they can't determine
// if an import is type-only without explicit annotation

// ❌ Ambiguous with isolatedModules
export { MyType } from './types'; // Is MyType a value or type?

// ✅ Explicit
export type { MyType } from './types';
Tip: Enable verbatimModuleSyntax in new projects. It enforces clarity and ensures compatibility with all bundlers and transpilers. For even stricter control, TS 5.8 adds erasableSyntaxOnly — which ensures no TypeScript-specific runtime syntax (enums, namespaces with values, parameter properties) is used, enabling tools like --experimental-strip-types in Node.js to directly run .ts files.

Express Middleware Types

// types/express.d.ts
import 'express';
import { JwtPayload } from 'jsonwebtoken';

declare module 'express' {
  interface Request {
    user?: JwtPayload & {
      id: string;
      email: string;
      roles: string[];
    };
    requestId: string;
    startTime: number;
  }
}

// middleware/request-context.ts
import { Request, Response, NextFunction } from 'express';
import { randomUUID } from 'crypto';

export function requestContext(req: Request, _res: Response, next: NextFunction) {
  req.requestId = req.headers['x-request-id'] as string ?? randomUUID();
  req.startTime = Date.now();
  next();
}

// middleware/auth.ts
import { Request, Response, NextFunction } from 'express';
import jwt from 'jsonwebtoken';

export function authenticate(req: Request, res: Response, next: NextFunction) {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return res.status(401).json({ error: 'Missing token' });

  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET!) as Request['user'];
    next();
  } catch {
    res.status(401).json({ error: 'Invalid token' });
  }
}

// middleware/authorize.ts
export function authorize(...roles: string[]) {
  return (req: Request, res: Response, next: NextFunction) => {
    if (!req.user) return res.status(401).json({ error: 'Not authenticated' });
    const hasRole = req.user.roles.some(r => roles.includes(r));
    if (!hasRole) return res.status(403).json({ error: 'Forbidden' });
    next();
  };
}

Plugin System

// core/plugin-system.ts
interface PluginHooks {
  'app:init': () => Promise<void>;
  'app:destroy': () => Promise<void>;
  'request:before': (req: Request) => void;
  'request:after': (req: Request, res: Response) => void;
}

// Extensible via declaration merging
interface PluginHooks {}

interface PluginDefinition<T = unknown> {
  name: string;
  version: string;
  config?: T;
  hooks?: Partial<{ [K in keyof PluginHooks]: PluginHooks[K] }>;
}

class PluginManager {
  private plugins = new Map<string, PluginDefinition>();

  register<T>(plugin: PluginDefinition<T>): void {
    this.plugins.set(plugin.name, plugin);
  }

  async emit<K extends keyof PluginHooks>(
    hook: K,
    ...args: Parameters<PluginHooks[K]>
  ): Promise<void> {
    for (const plugin of this.plugins.values()) {
      const handler = plugin.hooks?.[hook];
      if (handler) await (handler as Function)(...args);
    }
  }
}

// Plugin augments hooks
declare module '../core/plugin-system' {
  interface PluginHooks {
    'cache:invalidate': (keys: string[]) => void;
    'auth:login': (userId: string) => void;
    'auth:logout': (userId: string) => void;
  }
}

Common Mistakes

5 critical mistakes to avoid

Mistake 1: Augmenting in a Non-Module File

// ❌ WRONG — no import/export makes this a script file
// This creates a NEW ambient module, not an augmentation
declare module 'express' {
  interface Request {
    userId: string;
  }
}

// ✅ FIX — add an import or export
import 'express'; // or: export {};

declare module 'express' {
  interface Request {
    userId: string;
  }
}

Mistake 2: Conflicting Augmentations

// File A: types/express-auth.d.ts
import 'express';
declare module 'express' {
  interface Request {
    user: { id: string; name: string };
  }
}

// File B: types/express-tenant.d.ts
import 'express';
declare module 'express' {
  interface Request {
    user: { id: string; tenantId: string }; // ❌ CONFLICT!
  }
}

// ✅ FIX — combine into one declaration or use compatible types
import 'express';
declare module 'express' {
  interface Request {
    user: {
      id: string;
      name: string;
      tenantId: string;
    };
  }
}

Mistake 3: Forgetting to Include .d.ts in tsconfig

// tsconfig.json
{
  "include": ["src/**/*"]  // ❌ misses types/ directory
}

// ✅ FIX
{
  "include": ["src/**/*", "types/**/*"]
}

// Or use typeRoots for ambient declarations
{
  "compilerOptions": {
    "typeRoots": ["./node_modules/@types", "./types"]
  }
}

Mistake 4: Over-Augmenting Global Scope

// ❌ WRONG — polluting global with app-specific types
declare global {
  interface Window {
    userService: UserService;
    productService: ProductService;
    orderService: OrderService;
    notificationService: NotificationService;
    // ... dozens more
  }
}

// ✅ FIX — use dependency injection or module imports
// Only put genuinely global things on Window
declare global {
  interface Window {
    __APP_CONFIG__: AppConfig;  // injected by server
  }
}

// Use module-scoped DI container for services
import { container } from './di';
const userService = container.get(UserService);

Mistake 5: Not Using import type

// ❌ WRONG — imports the module at runtime (may cause side effects)
import { User } from './models'; // User is only used as a type

function processUser(user: User): void { ... }

// ✅ FIX — use import type for type-only imports
import type { User } from './models';

function processUser(user: User): void { ... }

// Benefits:
// - No runtime import (smaller bundle)
// - No side effects from the module
// - Works with isolatedModules
// - Clear intent for other developers
Interview Red Flag: Not knowing the difference between declare module in a script file vs. a module file is a common indicator of superficial TypeScript knowledge.

Follow-up Questions

6 questions with answers

Q1: How would you type a plugin that adds methods to a third-party class?

A: Use module augmentation to extend the class’s interface. For example, to add a method to Mongoose’s Document:

import 'mongoose';

declare module 'mongoose' {
  interface Document {
    softDelete(): Promise<void>;
    restore(): Promise<void>;
    isDeleted: boolean;
  }
}
// Then implement via Mongoose plugin: schema.plugin(softDeletePlugin);

Q2: What happens if two augmentations define the same property with different types?

A: TypeScript will raise a compile error — “Subsequent property declarations must have the same type.” Non-function members must have identical types across all declarations. The fix is to consolidate into a single augmentation file or use a union/intersection type that satisfies both.

Q3: How do you handle augmentations in a monorepo where packages shouldn’t see each other’s augmentations?

A: Use separate tsconfig.json per package with distinct include paths. Each package only includes its own types/ directory. Use project references to share common types explicitly without leaking package-specific augmentations across boundaries.

// packages/api/tsconfig.json
{
  "include": ["src/**/*", "types/**/*"],  // only API types
  "references": [{ "path": "../shared-types" }]
}

// packages/web/tsconfig.json
{
  "include": ["src/**/*", "types/**/*"],  // only web types
  "references": [{ "path": "../shared-types" }]
}

Q4: When should you use declare module vs. creating a wrapper type?

A: Use declare module when you need the augmentation to be visible everywhere the original module is used (e.g., Express Request across all middleware). Use wrapper types when the extension is app-specific and should be explicitly imported, or when you want to avoid global type pollution.

Q5: How do ambient declarations interact with isolatedModules?

A: With isolatedModules: true, each file is transpiled independently. This means:

  • const enum from other files can’t be inlined (use plain enum)
  • Re-exports of types must use export type
  • Ambient .d.ts files still work normally (they’re never transpiled)
  • declare global in .d.ts files is unaffected

Q6: What’s the difference between typeRoots and types in tsconfig?

A: typeRoots specifies where to look for type packages (directories). types specifies which packages to include from those roots (a whitelist). If types is omitted, all packages in all typeRoots are included. If types is specified, only those listed are included — this prevents unwanted global types from leaking in.

// Only include specific type packages
{
  "compilerOptions": {
    "typeRoots": ["./node_modules/@types", "./types"],
    "types": ["node", "jest"]  // Only these are auto-included
  }
}
// Other @types packages (e.g., @types/mocha) won't pollute
// unless explicitly imported in code

Summary

Mental models & what NOT to say

Mental Models

  Declaration Merging Mental Model:
  ┌─────────────────────────────────────────────────────┐
  │  Same Name = Merge (if compatible declarations)     │
  │                                                     │
  │  Interface + Interface → Properties accumulate      │
  │  Namespace + Class     → Static members added       │
  │  Namespace + Function  → Properties on function     │
  │  Namespace + Enum      → Utility methods added      │
  │                                                     │
  │  Module Augmentation:                               │
  │  declare module 'x' { } in a MODULE file            │
  │  = extends existing module                          │
  │                                                     │
  │  declare module 'x' { } in a SCRIPT file            │
  │  = creates new ambient module (DIFFERENT!)          │
  │                                                     │
  │  Global Augmentation:                               │
  │  declare global { } inside a module file            │
  │  = adds to global scope                             │
  └─────────────────────────────────────────────────────┘

Key Points to Hit in an Interview

  • Interface merging is the primary mechanism — properties accumulate, function members become overloads
  • Module augmentation requires the file to be a module (have import/export)
  • Global augmentation should be minimized — prefer module scope
  • Use import type for type-only imports to help bundlers tree-shake
  • Ambient declarations (declare) produce no runtime code
  • Modern libraries bundle types; @types is for older libraries

What NOT to Say

  • “I just put everything in a global.d.ts file” — shows no understanding of module vs global scope
  • “I copy the library types and modify them” — forking types is unmaintainable
  • “I use any when the types don’t match” — defeats the purpose of TypeScript
  • “I don’t know the difference between declare module in a script vs module” — this is the #1 gotcha
  • “Type aliases can be merged like interfaces” — incorrect, only interfaces merge
  • “I use // @ts-ignore when augmentations don’t work” — hides real errors

One-Liner Summary

Declaration merging combines same-named declarations; module augmentation (declare module in a module file) extends third-party types without forking; global augmentation (declare global) should be reserved for genuinely global APIs like Window and ProcessEnv.

React Fiber & Concurrent Rendering

"Explain React Fiber architecture. How does concurrent rendering differ from the legacy synchronous model?"

Key Takeaway: React Fiber is a complete rewrite of React's core reconciliation algorithm that replaces the recursive, uninterruptible stack reconciler with an incremental, interruptible work loop. Each component becomes a 'fiber' node in a linked tree that can be paused, resumed, or abandoned. This enables concurrent rendering: React can work on multiple versions of the UI simultaneously, prioritize urgent updates (user input) over non-urgent ones (data fetching results), and yield to the browser between work units to prevent frame drops.

Interviewer's Intent

When an interviewer asks about React Fiber and concurrent rendering, they are testing:

  • Deep understanding of React's rendering model — Can you explain what actually happens when setState is called, beyond "it re-renders"?
  • Why Fiber was needed — Do you understand the fundamental limitations of the stack reconciler that motivated a complete rewrite?
  • Practical implications for app architecture — Can you connect internal mechanics to real-world decisions: why side effects in render are dangerous, why keys matter, why external stores need synchronization?
  • Systems thinking — Can you reason about scheduling, prioritization, and resource allocation in a UI context?
  • Awareness of trade-offs — Do you understand what React gains and loses with concurrent rendering (memory overhead, complexity, eventual consistency)?

Signal they're looking for: A candidate who can trace a state update from dispatch through the scheduler, into the work loop, through reconciliation, and into the commit phase — and explain where interruption points exist along that path.

60-Second Answer

Use this when time is short:

React Fiber replaces the old recursive stack reconciler with an incremental work loop. Instead of processing the entire component tree in one synchronous pass, Fiber breaks work into units — one fiber node at a time. Each fiber is a plain object representing a component instance, linked via child/sibling/return pointers into a traversable tree.

The work loop calls performUnitOfWork repeatedly, checking shouldYield() after each unit. If the browser needs the main thread (e.g., for user input), React yields, and resumes later. This is "time slicing."

Concurrent rendering builds on this: React can prepare multiple UI trees simultaneously, assign priorities to updates (user input > network response > offscreen prefetch), and discard stale work without committing it. The render phase is interruptible and side-effect-free; only the commit phase touches the DOM, and it runs synchronously to prevent tearing.

Key consequence: your render function may be called multiple times for a single update, so it must be pure.

Legacy Stack Reconciler — Why It Failed

Before React 16, the reconciler used a recursive algorithm that mirrored the call stack:

// Simplified legacy reconciler (conceptual)
function reconcile(parentDom, instance, element) {
  if (instance == null) {
    // Mount: create DOM, recurse into children
    const newInstance = createInstance(element);
    parentDom.appendChild(newInstance.dom);
    element.props.children.forEach((child, i) => {
      reconcile(newInstance.dom, null, child); // recursive!
    });
    return newInstance;
  } else if (element == null) {
    // Unmount
    parentDom.removeChild(instance.dom);
    return null;
  } else if (instance.element.type === element.type) {
    // Update: patch props, recurse into children
    updateDomProperties(instance.dom, instance.element.props, element.props);
    instance.childInstances = reconcileChildren(instance, element);
    instance.element = element;
    return instance;
  } else {
    // Replace
    const newInstance = createInstance(element);
    parentDom.replaceChild(newInstance.dom, instance.dom);
    return newInstance;
  }
}

// This is called recursively for EVERY child
function reconcileChildren(instance, element) {
  const newChildElements = element.props.children || [];
  const oldChildInstances = instance.childInstances;
  const newChildInstances = [];
  const count = Math.max(newChildElements.length, oldChildInstances.length);
  for (let i = 0; i < count; i++) {
    newChildInstances.push(
      reconcile(instance.dom, oldChildInstances[i], newChildElements[i])
    );
  }
  return newChildInstances;
}

Fatal Flaws

Problem Impact
Recursive tree traversal Uses the JavaScript call stack; cannot be paused mid-tree
Synchronous & uninterruptible Once reconciliation starts, it must finish — blocking the main thread
No prioritization A low-priority background update blocks high-priority user input
Dropped frames Large trees (>10K nodes) cause >16ms renders, dropping below 60fps
No way to abort work If a higher-priority update arrives, old work cannot be discarded
No incremental output Users see nothing until the entire tree is processed

The core insight: Using the JavaScript call stack as your "work stack" means you inherit all its limitations. You can't serialize it, pause it, prioritize it, or resume it from where you left off. Fiber replaces the call stack with a virtual stack stored in heap-allocated objects.

Fiber Node Structure

A fiber is a plain JavaScript object that represents a unit of work. Every React element gets a corresponding fiber. The fiber tree is a linked data structure using three pointer types: child, sibling, and return (parent).

Complete Fiber Node Fields 
// Simplified FiberNode (from react-reconciler/src/ReactFiber.js)
function FiberNode(tag, pendingProps, key, mode) {
  // === Instance Identity ===
  this.tag = tag;             // FunctionComponent, ClassComponent, HostComponent, etc.
  this.key = key;             // Reconciliation key for list diffing
  this.elementType = null;    // The resolved type (function/class/string)
  this.type = null;           // For resolved lazy components
  this.stateNode = null;      // DOM node (HostComponent) or class instance

  // === Fiber Tree Structure (linked list) ===
  this.return = null;         // Parent fiber
  this.child = null;          // First child fiber
  this.sibling = null;        // Next sibling fiber
  this.index = 0;             // Position among siblings

  // === Props & State ===
  this.ref = null;
  this.pendingProps = pendingProps;  // Props for this render
  this.memoizedProps = null;        // Props from last render (for bailout)
  this.memoizedState = null;        // State from last render (hooks linked list)
  this.updateQueue = null;          // Queue of state updates

  // === Effects ===
  this.flags = NoFlags;       // Bitmask: Placement | Update | Deletion | ...
  this.subtreeFlags = NoFlags;// Aggregated flags from children (bubbled up)
  this.deletions = null;      // Child fibers to be deleted

  // === Scheduling / Priority ===
  this.lanes = NoLanes;       // Priority lanes for this fiber's pending work
  this.childLanes = NoLanes;  // Union of lanes in subtree

  // === Double Buffering ===
  this.alternate = null;      // Points to the other version (current ↔ workInProgress)
}

Key Fields Explained

Field Purpose Why It Matters
tag Identifies fiber type (0=FunctionComponent, 5=HostComponent, etc.) Determines which reconciliation path to take in beginWork
stateNode Backing instance (DOM node or class instance) Used during commit to apply mutations to the real DOM
return/child/sibling Linked tree pointers Enable iterative traversal without recursion (no call stack needed)
alternate Points to the fiber's twin in the other tree Enables double buffering: current tree vs work-in-progress tree
memoizedProps/State Output from the last committed render Used for bailout optimization (skip work if nothing changed)
flags Bitmask of side effects (Placement, Update, Deletion) Collected during render, executed during commit
lanes Priority bitmask for pending updates Determines which updates to process in this render pass

Traversal Order (DFS via linked list):
  App → Header → (no child, has sibling? no → return to App)
  App → Main → Article → (no child → sibling) → Sidebar → (return to Main)

Each node has:
  .child    → first child
  .sibling  → next sibling
  .return   → parent

Why a linked list instead of arrays? Arrays require knowing the count upfront and make insertion/deletion O(n). A linked list with child/sibling/return pointers allows O(1) navigation in any direction and makes the iterative work loop trivial: go to child, if no child go to sibling, if no sibling go to return's sibling.

Work Loop

The work loop is the heart of Fiber. It processes one fiber at a time in an iterative loop, checking whether it should yield control back to the browser after each unit of work.

// Simplified from ReactFiberWorkLoop.js
function workLoopConcurrent() {
  // Process fibers until we run out or need to yield
  while (workInProgress !== null && !shouldYield()) {
    performUnitOfWork(workInProgress);
  }
}

// Synchronous version (used for discrete events like clicks)
function workLoopSync() {
  while (workInProgress !== null) {
    performUnitOfWork(workInProgress);
  }
}

function performUnitOfWork(unitOfWork) {
  const current = unitOfWork.alternate; // The committed version

  // Phase 1: "Begin" — process this fiber, return its first child
  const next = beginWork(current, unitOfWork, renderLanes);

  // Props are now finalized
  unitOfWork.memoizedProps = unitOfWork.pendingProps;

  if (next === null) {
    // No children — complete this unit and find next work
    completeUnitOfWork(unitOfWork);
  } else {
    // Descend into the first child
    workInProgress = next;
  }
}

function completeUnitOfWork(unitOfWork) {
  let completedWork = unitOfWork;
  do {
    const current = completedWork.alternate;
    const returnFiber = completedWork.return;

    // Phase 2: "Complete" — create/update DOM nodes, bubble flags
    completeWork(current, completedWork, renderLanes);

    // Bubble subtreeFlags to parent
    if (returnFiber !== null) {
      returnFiber.subtreeFlags |= completedWork.subtreeFlags;
      returnFiber.subtreeFlags |= completedWork.flags;
    }

    // Move to sibling if exists, else ascend to parent
    const siblingFiber = completedWork.sibling;
    if (siblingFiber !== null) {
      workInProgress = siblingFiber;
      return; // Exit — the work loop will call performUnitOfWork on sibling
    }
    completedWork = returnFiber;
    workInProgress = completedWork;
  } while (completedWork !== null);
}

beginWork — Descending

beginWork processes a single fiber and returns its first child (or null). Its job depends on the fiber tag:

  • FunctionComponent: Calls the function, processes hooks, reconciles returned elements into child fibers
  • ClassComponent: Calls render(), processes lifecycle, reconciles children
  • HostComponent: Reconciles children (DOM diffing happens here conceptually)
  • All types: Checks for bailout (props/state unchanged → skip subtree)

completeWork — Ascending

completeWork runs when a fiber has no more children to process. It:

  • Creates actual DOM nodes for HostComponents (but doesn't attach them to the live tree yet)
  • Computes the diff of changed props for existing DOM nodes
  • Bubbles effect flags up to the parent via subtreeFlags
  • Appends newly created DOM to a detached fragment (off-screen)

Mental model: Think of the work loop as a depth-first walk. beginWork is going DOWN (entering a node), completeWork is going UP (leaving a node). The traversal is: down to first child, if no child then complete current and move to sibling, if no sibling then complete parent and move to parent's sibling, repeat.

Interruptible Rendering

The fundamental innovation of Fiber: rendering can be paused mid-tree and resumed later, or abandoned entirely if a higher-priority update arrives.

How React Can Pause Mid-Tree

Because the work loop is iterative (not recursive), all traversal state lives in the workInProgress pointer and the fiber tree itself — not on the call stack. When shouldYield() returns true:

  1. The work loop simply exits (the while condition fails)
  2. The workInProgress pointer remains on the last fiber being processed
  3. The partially-built workInProgress tree remains in memory
  4. React schedules a continuation via MessageChannel
  5. When the browser gives back control, the loop resumes from workInProgress
// What happens when React yields:
function workLoopConcurrent() {
  while (workInProgress !== null && !shouldYield()) {
    performUnitOfWork(workInProgress);
  }
  // Loop exits here when shouldYield() returns true
  // workInProgress still points to the next fiber to process
  // The scheduler will re-enter this function later
}

// What happens when a higher-priority update arrives mid-render:
function ensureRootIsScheduled(root) {
  const nextLanes = getNextLanes(root, root === workInProgressRoot ? workInProgressRootRenderLanes : NoLanes);

  if (nextLanes === NoLanes) return;

  const newCallbackPriority = getHighestPriorityLane(nextLanes);
  const existingCallbackPriority = root.callbackPriority;

  if (newCallbackPriority > existingCallbackPriority) {
    // Cancel in-progress render — it will be restarted
    cancelCallback(root.callbackNode);
    // Discard the partial workInProgress tree
    prepareFreshStack(root, nextLanes);
  }
}

What Happens to Incomplete Work

  • Paused (same priority): Work-in-progress tree stays in memory; resumed from the exact fiber where it stopped
  • Preempted (higher priority arrives): The partial workInProgress tree is discarded (prepareFreshStack), and a new render begins. No DOM changes were made, so nothing needs to be rolled back.
  • Expired (starvation): If a lower-priority update waits too long, its priority is escalated to synchronous to prevent indefinite starvation

Re-entrant Rendering

Because the render phase is pure (no side effects, no DOM mutations), React can safely:

  • Start rendering an update
  • Pause halfway through
  • Process a higher-priority update completely
  • Return to the original update (possibly restarting from scratch if the higher-priority update changed the base state)

Critical implication: Your render functions, function component bodies, and any code called during rendering may execute multiple times for a single update. This is why side effects in render are forbidden — they would execute an unpredictable number of times.

Time Slicing

Time slicing is the mechanism by which React breaks rendering work into small chunks and yields control to the browser between chunks, keeping the main thread responsive for user interactions and animations.

5ms Work Chunks

// From scheduler/src/forks/Scheduler.js
let frameInterval = 5; // ms — the target time slice duration

function shouldYieldToHost() {
  const timeElapsed = getCurrentTime() - startTime;
  if (timeElapsed < frameInterval) {
    // No need to yield yet — we're within our time budget
    return false;
  }
  // We've exceeded our time slice — yield to the browser
  return true;
}

// The frame interval can be adjusted (rarely needed):
function forceFrameRate(fps) {
  if (fps < 0 || fps > 125) return;
  if (fps > 0) {
    frameInterval = Math.floor(1000 / fps);
  } else {
    frameInterval = 5; // Reset to default
  }
}

Why 5ms? The 5ms is a yield threshold, not a frame budget allocation. React checks elapsed time after each fiber unit — if ≥5ms has passed, it yields back to the browser. If work finishes in 3ms, React doesn't wait; it yields immediately. Multiple work slices can occur within a single frame. The 5ms value ensures React doesn't monopolize the main thread for too long, but the browser doesn't necessarily get a full paint opportunity between every slice (yields only guarantee a macrotask boundary via MessageChannel).

MessageChannel for Scheduling

// How React schedules continuations (simplified from SchedulerHostConfig.default.js)
const channel = new MessageChannel();
const port = channel.port2;

channel.port1.onmessage = performWorkUntilDeadline;

function requestHostCallback(callback) {
  scheduledHostCallback = callback;
  if (!isMessageLoopRunning) {
    isMessageLoopRunning = true;
    port.postMessage(null); // Schedule a macrotask
  }
}

function performWorkUntilDeadline() {
  if (scheduledHostCallback !== null) {
    const currentTime = getCurrentTime();
    startTime = currentTime; // Reset the time slice start
    const hasMoreWork = scheduledHostCallback(currentTime);

    if (hasMoreWork) {
      // More work remains — schedule another slice
      port.postMessage(null);
    } else {
      isMessageLoopRunning = false;
      scheduledHostCallback = null;
    }
  }
}

Double Buffering (current vs workInProgress)

React maintains two fiber trees at any time, analogous to double buffering in graphics rendering:

  • current tree: The fiber tree that corresponds to what's currently rendered on screen. The DOM reflects this tree.
  • workInProgress tree: The fiber tree being built during the current render. It represents the next version of the UI.

How Alternate Pointers Work

// Each fiber has an 'alternate' pointing to its counterpart
// in the other tree:
currentFiber.alternate === workInProgressFiber;
workInProgressFiber.alternate === currentFiber;

// Creating a workInProgress fiber (simplified):
function createWorkInProgress(current, pendingProps) {
  let workInProgress = current.alternate;
  if (workInProgress === null) {
    // First time: create a new fiber, link as alternate
    workInProgress = createFiber(current.tag, pendingProps, current.key, current.mode);
    workInProgress.elementType = current.elementType;
    workInProgress.type = current.type;
    workInProgress.stateNode = current.stateNode; // Share the DOM node

    workInProgress.alternate = current;
    current.alternate = workInProgress;
  } else {
    // Reuse existing alternate, just update props
    workInProgress.pendingProps = pendingProps;
    workInProgress.flags = NoFlags;
    workInProgress.subtreeFlags = NoFlags;
    workInProgress.deletions = null;
  }
  // Copy fields from current
  workInProgress.childLanes = current.childLanes;
  workInProgress.lanes = current.lanes;
  workInProgress.child = current.child;
  workInProgress.memoizedProps = current.memoizedProps;
  workInProgress.memoizedState = current.memoizedState;
  workInProgress.updateQueue = current.updateQueue;
  return workInProgress;
}

Commit Swap

When the render phase completes and the commit phase finishes applying mutations to the DOM:

// After commit, swap the root pointer:
root.current = finishedWork; // workInProgress becomes current

// The old current tree becomes the next workInProgress
// (its fibers will be reused via alternate pointers)

Why Double Buffering Prevents Visual Tearing

  • During render, the current tree (what's on screen) remains untouched
  • All mutations are prepared on the workInProgress tree
  • Only during the synchronous commit phase are DOM changes applied
  • If rendering is interrupted and restarted, the current tree still represents a consistent state
  • Users never see a half-built UI — either the old version or the complete new version

Commit Phase vs Render Phase

React's work is divided into two fundamentally different phases with different guarantees:

Property Render Phase Commit Phase
Purity Pure — no side effects Effectful — mutates DOM, runs effects
Interruptibility Can be paused, aborted, restarted Synchronous, cannot be interrupted
Execution count May run multiple times per update Runs exactly once per committed update
DOM access No DOM mutations Applies all DOM mutations
What runs here Component render, beginWork, completeWork DOM mutations, refs, effects
Lifecycle methods render(), getDerivedStateFromProps() componentDidMount/Update, useEffect, useLayoutEffect

Three Sub-Phases of Commit

// Simplified commit phase (ReactFiberCommitWork.js)
function commitRoot(root) {
  const finishedWork = root.finishedWork;

  // === Sub-phase 1: Before Mutation ===
  // Read from DOM before changes (e.g., getSnapshotBeforeUpdate)
  commitBeforeMutationEffects(root, finishedWork);

  // === Sub-phase 2: Mutation ===
  // Apply DOM insertions, updates, deletions
  // Detach refs from removed nodes
  commitMutationEffects(root, finishedWork, renderLanes);

  // Swap the fiber trees BETWEEN mutation and layout
  root.current = finishedWork;

  // === Sub-phase 3: Layout ===
  // Run useLayoutEffect callbacks
  // Attach refs
  // componentDidMount / componentDidUpdate
  commitLayoutEffects(finishedWork, root, renderLanes);

  // After layout effects, schedule passive effects (useEffect)
  // These run asynchronously after paint
  if (rootDoesHavePassiveEffects) {
    scheduleCallback(NormalSchedulerPriority, flushPassiveEffects);
  }
}
Why root.current swaps between mutation and layout

The swap happens after DOM mutations but before layout effects. This means:

  • componentWillUnmount (called during mutation) still sees the old tree as "current" — it can read the previous state
  • componentDidMount / useLayoutEffect (called during layout) sees the new tree as "current" — refs point to new DOM nodes

Effect List & Side Effects

During the render phase, React flags fibers that need DOM operations. These flags are collected via subtreeFlags bubbling, and during commit, React traverses only fibers with flags set — skipping the vast majority of the tree.

Effect Flags (Bitmask)

// From ReactFiberFlags.js (simplified)
const NoFlags        = 0b0000000000000000000000000000;
const Placement      = 0b0000000000000000000000000010; // New node to insert
const Update         = 0b0000000000000000000000000100; // Props/state changed
const Deletion       = 0b0000000000000000000000001000; // Node to remove
const ChildDeletion  = 0b0000000000000000000000010000;
const ContentReset   = 0b0000000000000000000000100000;
const Callback       = 0b0000000000000000000001000000;
const Ref            = 0b0000000000000000001000000000;
const Snapshot       = 0b0000000000000000010000000000;
const Passive        = 0b0000000000000000100000000000; // Has useEffect
const LayoutMask     = Update | Callback | Ref | Snapshot;
const PassiveMask    = Passive | ChildDeletion;

// Flags are combined with bitwise OR:
fiber.flags |= Placement | Update;

// Checked with bitwise AND:
if (fiber.flags & Placement) {
  commitPlacement(fiber);
}
if (fiber.flags & Update) {
  commitWork(fiber);
}

subtreeFlags Bubbling (React 18+ optimization)

// In completeWork, flags bubble up:
function bubbleProperties(completedWork) {
  let subtreeFlags = NoFlags;
  let child = completedWork.child;
  while (child !== null) {
    subtreeFlags |= child.subtreeFlags;
    subtreeFlags |= child.flags;
    child = child.sibling;
  }
  completedWork.subtreeFlags |= subtreeFlags;
}

// During commit, subtreeFlags enable skipping entire subtrees:
function commitMutationEffects_begin(root, lanes) {
  while (nextEffect !== null) {
    const fiber = nextEffect;
    const child = fiber.child;

    if ((fiber.subtreeFlags & MutationMask) !== NoFlags && child !== null) {
      // Subtree has effects — descend
      nextEffect = child;
    } else {
      // No effects in subtree — skip entirely, process this node
      commitMutationEffects_complete(root, lanes);
    }
  }
}

Performance win: In React 16-17, an "effect list" linked list was maintained. React 18 replaced this with subtreeFlags bubbling, which enables skipping entire subtrees that have no effects — O(affected nodes) instead of O(total effects). For large trees with localized updates, this is significantly faster.

Concurrent Mode Enabling

Concurrent rendering is not a "mode" you switch on globally — it's a set of features enabled by the new createRoot API that allows React to use interruptible rendering when appropriate.

createRoot vs Legacy render()

// Legacy (React 17 and earlier) — synchronous rendering only
import { render } from 'react-dom';
render(<App />, document.getElementById('root'));
// All updates are synchronous and uninterruptible

// Concurrent (React 18+) — enables concurrent features
import { createRoot } from 'react-dom/client';
const root = createRoot(document.getElementById('root'));
root.render(<App />);
// Updates CAN be concurrent (React decides based on context)

// Important: createRoot doesn't mean ALL renders are concurrent.
// Discrete events (clicks, keydown) still render synchronously.
// Only "transitions" and deferred updates use concurrent rendering.

What Concurrent Features Enable

  • startTransition: Mark state updates as non-urgent, allowing React to interrupt them for user input
  • useDeferredValue: Show stale UI while fresh data renders in the background
  • Suspense for data fetching: Show fallback UI while async data loads, without blocking other content
  • Streaming SSR with selective hydration: Hydrate components as they load, prioritizing user-interacted ones
  • Automatic batching: All updates (even in setTimeout/promises) are batched automatically

StrictMode Double-Render

// In development + StrictMode, React intentionally double-invokes:
// - Function component bodies
// - State updater functions
// - useMemo/useCallback callbacks

// This helps catch side effects in render:
function MyComponent() {
  // ❌ This would fire twice in StrictMode, revealing the bug:
  fetch('/api/track-view'); // Side effect in render!

  // ✅ Correct: use useEffect for side effects
  useEffect(() => {
    fetch('/api/track-view');
  }, []);

  return <div>Content</div>;
}

StrictMode in React 18: Components mount → unmount → remount in development to test resilience to future features (like offscreen rendering / Activity). If your useEffect cleanup isn't symmetric with its setup, StrictMode will expose that bug.

Cooperative Scheduling

React implements cooperative scheduling: the renderer voluntarily yields the main thread at regular intervals, cooperating with the browser's event loop rather than monopolizing it.

Priority Levels

// From scheduler/src/SchedulerPriorities.js
const ImmediatePriority   = 1;  // Synchronous, highest priority
const UserBlockingPriority = 2;  // User interactions (clicks, input)
const NormalPriority       = 3;  // Default (e.g., network responses)
const LowPriority          = 4;  // Data prefetching
const IdlePriority         = 5;  // Offscreen / background work

// Timeout thresholds (from SchedulerFeatureFlags)
const IMMEDIATE_PRIORITY_TIMEOUT = -1;    // Immediately expired → sync
const USER_BLOCKING_PRIORITY_TIMEOUT = 250; // 250ms
const NORMAL_PRIORITY_TIMEOUT = 5000;       // 5 seconds
const LOW_PRIORITY_TIMEOUT = 10000;         // 10 seconds
const IDLE_PRIORITY_TIMEOUT = 1073741823;   // Max int — never expires naturally

Task Expiration & Starvation Prevention

// When a task is scheduled, it gets an expiration time:
function scheduleCallback(priorityLevel, callback) {
  const currentTime = getCurrentTime();
  const startTime = currentTime; // or + delay for delayed tasks
  
  let timeout;
  switch (priorityLevel) {
    case ImmediatePriority: timeout = -1; break;
    case UserBlockingPriority: timeout = 250; break;
    case NormalPriority: timeout = 5000; break;
    case LowPriority: timeout = 10000; break;
    case IdlePriority: timeout = 1073741823; break;
  }

  const expirationTime = startTime + timeout;
  const newTask = {
    callback,
    priorityLevel,
    startTime,
    expirationTime,
    sortIndex: expirationTime // Used by the priority queue
  };

  push(taskQueue, newTask); // Insert into min-heap
  requestHostCallback(flushWork);
  return newTask;
}

// Starvation prevention:
// If currentTime >= task.expirationTime, the task is "expired"
// Expired tasks run synchronously regardless of shouldYield()
function workLoop(initialTime) {
  let currentTime = initialTime;
  currentTask = peek(taskQueue);

  while (currentTask !== null) {
    if (currentTask.expirationTime > currentTime && shouldYieldToHost()) {
      // Task not expired AND we should yield → break
      break;
    }
    // Task expired OR we have time → execute it
    const callback = currentTask.callback;
    const continuationCallback = callback(currentTask.expirationTime <= currentTime);
    // ...
  }
}

Why Not requestIdleCallback?

  • Granularity: rIC fires at most once per frame, with unpredictable deadlines (20-50ms). React needs sub-5ms scheduling precision.
  • Browser support: Not available in Safari (iOS) at all, making it unusable for production
  • Priority control: rIC has no priority system — all callbacks are treated equally
  • Cancellation: rIC cancellation is coarse-grained and unreliable
  • Background tabs: rIC behavior varies when tabs are backgrounded

React's custom scheduler via MessageChannel gives consistent, predictable, priority-aware scheduling across all environments.

React's Internal Scheduler Package

The scheduler package (packages/scheduler in the React repo) is a standalone priority task scheduler. It's designed to be React-agnostic but is currently only used by React.

Priority Queue (Min-Heap)

// From scheduler/src/SchedulerMinHeap.js
// Tasks are stored in a min-heap sorted by sortIndex (expirationTime)
// This gives O(1) peek, O(log n) push/pop

function push(heap, node) {
  const index = heap.length;
  heap.push(node);
  siftUp(heap, node, index);
}

function peek(heap) {
  return heap.length === 0 ? null : heap[0];
}

function pop(heap) {
  if (heap.length === 0) return null;
  const first = heap[0];
  const last = heap.pop();
  if (last !== first) {
    heap[0] = last;
    siftDown(heap, last, 0);
  }
  return first;
}

function siftUp(heap, node, i) {
  let index = i;
  while (index > 0) {
    const parentIndex = (index - 1) >>> 1;
    const parent = heap[parentIndex];
    if (compare(parent, node) > 0) {
      // Parent is larger — swap
      heap[parentIndex] = node;
      heap[index] = parent;
      index = parentIndex;
    } else {
      return;
    }
  }
}

function compare(a, b) {
  const diff = a.sortIndex - b.sortIndex;
  return diff !== 0 ? diff : a.id - b.id; // FIFO for equal priority
}

Relationship to Lanes

Lanes are React's internal priority model (used by the reconciler). The scheduler has its own priority levels. The mapping between them:

// From ReactFiberLane.js — Lanes are bitmasks
const SyncLane            = 0b0000000000000000000000000000001;
const InputContinuousLane = 0b0000000000000000000000000000100;
const DefaultLane         = 0b0000000000000000000000000010000;
const TransitionLanes     = 0b0000000011111111111111110000000;
const IdleLane            = 0b0100000000000000000000000000000;
const OffscreenLane       = 0b1000000000000000000000000000000;

// Lane → Scheduler Priority mapping:
function lanesToSchedulerPriority(lanes) {
  const lane = getHighestPriorityLane(lanes);
  if (lane === SyncLane) return ImmediatePriority;
  if (lane === InputContinuousLane) return UserBlockingPriority;
  if (lane === DefaultLane) return NormalPriority;
  if (lane === IdleLane) return IdlePriority;
  return NormalPriority;
}

// Why two priority systems?
// Lanes: fine-grained, bitmask-based, supports batching multiple priorities
// Scheduler: coarse-grained, for host-level task ordering
// A single scheduler task may process multiple lanes in one render.

shouldYield Implementation

// The shouldYield exposed to the reconciler
function shouldYield() {
  const currentTime = getCurrentTime();
  advanceTimers(currentTime); // Move expired delayed tasks to taskQueue

  const firstTask = peek(taskQueue);
  return (
    (firstTask !== currentTask &&   // A different task is now highest priority
     currentTask !== null &&
     firstTask !== null &&
     firstTask.expirationTime < currentTask.expirationTime) ||
    shouldYieldToHost()             // Time slice exceeded
  );
}

Host config abstraction: The scheduler uses a "host config" pattern to abstract away platform-specific APIs. In a browser, it uses MessageChannel and performance.now(). In Node.js (for testing), it uses setTimeout and Date.now(). This allows the same scheduler logic to work in any environment.

Production Implications

Concurrent rendering changes the contract between React and your code. Here's what it means in practice:

No Side Effects in Render

// ❌ Broken under concurrent rendering:
function UserProfile({ userId }) {
  // This might fire multiple times if render is interrupted and restarted!
  analytics.trackView(userId);

  const [user, setUser] = useState(null);

  // ❌ Mutating external state in render
  window.currentUser = userId;

  // ❌ Subscribing in render body
  eventBus.on('update', handleUpdate);

  return <div>{user?.name}</div>;
}

// ✅ Correct: side effects in useEffect
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    analytics.trackView(userId);
    const unsub = eventBus.on('update', handleUpdate);
    return () => unsub();
  }, [userId]);

  return <div>{user?.name}</div>;
}

useRef for Mutable Values

// ❌ Module-level mutable state is shared across renders
let renderCount = 0;
function MyComponent() {
  renderCount++; // Incorrect count under concurrent rendering
  return <span>Rendered {renderCount} times</span>;
}

// ✅ useRef persists across renders without triggering re-renders
function MyComponent() {
  const renderCount = useRef(0);
  useEffect(() => {
    renderCount.current++;
  });
  return <span>Committed {renderCount.current} times</span>;
}

External Store Synchronization (useSyncExternalStore)

// Problem: concurrent rendering can read from an external store at
// two different points in time during a single render, causing "tearing"
// (parts of the UI reflecting different store versions)

// ❌ Naive subscription — may tear under concurrent rendering:
function useStore(store) {
  const [state, setState] = useState(store.getState());
  useEffect(() => {
    return store.subscribe(() => setState(store.getState()));
  }, [store]);
  return state;
}

// ✅ useSyncExternalStore — handles tearing prevention:
import { useSyncExternalStore } from 'react';

function useStore(store) {
  return useSyncExternalStore(
    store.subscribe,    // Subscribe function
    store.getState,     // Get current client state
    store.getState      // Get server snapshot (SSR)
  );
}

// How it prevents tearing:
// 1. During render, reads the store snapshot
// 2. After render completes (before commit), checks if the store changed
// 3. If changed during render → forces synchronous re-render
// 4. This guarantees the committed UI is consistent with one store version

Strict Mode Compatibility Checklist

  • ✅ All component bodies are pure functions of props/state
  • ✅ useEffect cleanups properly reverse their setup
  • ✅ No reading from mutable globals during render
  • ✅ External stores use useSyncExternalStore
  • ✅ No assumptions about render-to-commit being 1:1
  • ✅ Refs are only read/written in effects or event handlers, not during render

Simplified Fiber Reconciler

Minimal Fiber Implementation (~80 lines) 
// A simplified fiber reconciler demonstrating the core concepts
// (NOT actual React code — educational abstraction)

let wipRoot = null;       // Work-in-progress root
let currentRoot = null;   // Currently committed root
let nextUnitOfWork = null;
let deletions = [];

function createElement(type, props, ...children) {
  return {
    type,
    props: {
      ...props,
      children: children.map(child =>
        typeof child === 'object' ? child : createTextElement(child)
      )
    }
  };
}

function createFiber(element, parent) {
  return {
    type: element.type,
    props: element.props,
    parent,
    dom: null,
    child: null,
    sibling: null,
    alternate: null,  // Link to previous fiber
    flags: 'PLACEMENT' // PLACEMENT | UPDATE | DELETION
  };
}

function render(element, container) {
  wipRoot = {
    dom: container,
    props: { children: [element] },
    alternate: currentRoot  // Link to previous tree
  };
  deletions = [];
  nextUnitOfWork = wipRoot;
  requestIdleCallback(workLoop); // ⚠️ Educational only — React uses MessageChannel, not rIC (see "Why Not rIC?" above)
}

function workLoop(deadline) {
  let shouldYield = false;
  while (nextUnitOfWork && !shouldYield) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
    shouldYield = deadline.timeRemaining() < 1;
  }

  if (!nextUnitOfWork && wipRoot) {
    commitRoot(); // All work done — commit synchronously
  }

  if (nextUnitOfWork) {
    requestIdleCallback(workLoop); // Educational only — schedule continuation
  }
}

function performUnitOfWork(fiber) {
  // Create DOM node (but don't attach to live tree yet)
  if (!fiber.dom) {
    fiber.dom = createDom(fiber);
  }

  // Reconcile children
  const elements = fiber.props.children || [];
  reconcileChildren(fiber, elements);

  // Return next unit of work (depth-first traversal)
  if (fiber.child) return fiber.child;

  let nextFiber = fiber;
  while (nextFiber) {
    if (nextFiber.sibling) return nextFiber.sibling;
    nextFiber = nextFiber.parent;
  }
  return null;
}

function reconcileChildren(wipFiber, elements) {
  let oldFiber = wipFiber.alternate?.child;
  let prevSibling = null;

  for (let i = 0; i < elements.length || oldFiber; i++) {
    const element = elements[i];
    let newFiber = null;
    const sameType = oldFiber && element && element.type === oldFiber.type;

    if (sameType) {
      // UPDATE: reuse fiber, update props
      newFiber = { ...oldFiber, props: element.props,
                   alternate: oldFiber, parent: wipFiber, flags: 'UPDATE' };
    }
    if (element && !sameType) {
      // PLACEMENT: new fiber
      newFiber = createFiber(element, wipFiber);
    }
    if (oldFiber && !sameType) {
      // DELETION: mark old fiber for removal
      oldFiber.flags = 'DELETION';
      deletions.push(oldFiber);
    }

    if (oldFiber) oldFiber = oldFiber.sibling;
    if (i === 0) wipFiber.child = newFiber;
    else if (prevSibling) prevSibling.sibling = newFiber;
    prevSibling = newFiber;
  }
}

function commitRoot() {
  deletions.forEach(commitWork);
  commitWork(wipRoot.child);
  currentRoot = wipRoot; // Swap: WIP becomes current
  wipRoot = null;
}

function commitWork(fiber) {
  if (!fiber) return;
  const parentDom = fiber.parent.dom;
  if (fiber.flags === 'PLACEMENT' && fiber.dom) {
    parentDom.appendChild(fiber.dom);
  } else if (fiber.flags === 'UPDATE' && fiber.dom) {
    updateDom(fiber.dom, fiber.alternate.props, fiber.props);
  } else if (fiber.flags === 'DELETION') {
    parentDom.removeChild(fiber.dom);
    return;
  }
  commitWork(fiber.child);
  commitWork(fiber.sibling);
}

Common Mistakes

Mistake 1: Side Effects in the Render Phase 
// ❌ WRONG: Side effect during render
function UserList({ users }) {
  // This runs during render — may fire multiple times!
  localStorage.setItem('lastViewed', Date.now());

  // This mutates a ref during render — unsafe
  countRef.current++;

  // This subscribes during render — leaks on every interrupted render
  window.addEventListener('resize', handleResize);

  return users.map(u => <User key={u.id} {...u} />);
}

// ✅ CORRECT: Side effects in effects
function UserList({ users }) {
  useEffect(() => {
    localStorage.setItem('lastViewed', Date.now());
  });

  const commitCountRef = useRef(0);
  useEffect(() => {
    commitCountRef.current++;
  });

  useEffect(() => {
    window.addEventListener('resize', handleResize);
    return () => window.removeEventListener('resize', handleResize);
  }, []);

  return users.map(u => <User key={u.id} {...u} />);
}

Why it matters: Under concurrent rendering, the render phase can be invoked multiple times, paused, and restarted. Side effects will execute unpredictably — potentially multiple times or not at all for an aborted render.

Mistake 2: Relying on Render Count 
// ❌ WRONG: Assuming render count == commit count
let globalRenderCount = 0;
function Analytics() {
  globalRenderCount++; // Fires extra times in StrictMode + concurrent
  // May report 2x, 3x the actual renders

  return <span>Renders: {globalRenderCount}</span>;
}

// ✅ CORRECT: Track commits, not renders
function Analytics() {
  const commitCount = useRef(0);

  useEffect(() => {
    commitCount.current++;
    reportMetric('component_committed', commitCount.current);
  });

  return <span>Commits: {commitCount.current}</span>;
}

Why it matters: React may call your render function speculatively (for pre-rendering, StrictMode validation, or after interruption). Only committed renders (those that reach the commit phase) represent actual UI updates.

Mistake 3: Not Using Key Properly 
// ❌ WRONG: Index as key for dynamic lists
function TodoList({ todos }) {
  return todos.map((todo, index) => (
    <TodoItem key={index} todo={todo} />
    // If items reorder, React matches fibers by index
    // → wrong state associated with wrong items
    // → unnecessary DOM mutations (update all items vs move one)
  ));
}

// ❌ WRONG: Non-stable keys
function TodoList({ todos }) {
  return todos.map(todo => (
    <TodoItem key={Math.random()} todo={todo} />
    // Every render creates new keys → all fibers unmount/remount
    // → destroys component state, triggers mount effects
    // → terrible performance
  ));
}

// ✅ CORRECT: Stable, unique identifier
function TodoList({ todos }) {
  return todos.map(todo => (
    <TodoItem key={todo.id} todo={todo} />
    // React can match old fiber to new element by key
    // → minimal DOM operations (only move/update what changed)
    // → preserves component state correctly
  ));
}

Why it matters for Fiber: Keys are how the reconciler identifies which fiber corresponds to which element across renders. reconcileChildFibers uses keys to determine Placement vs Update vs Deletion flags. Bad keys cause O(n) unnecessary DOM work instead of O(1) moves.

Mistake 4: Ignoring Strict Mode Warnings 
// StrictMode double-invokes these in development:
// - Function component bodies
// - useState initializer functions
// - useMemo callbacks
// - useReducer reducers

// If you see doubled API calls, doubled console logs, or doubled
// subscriptions in development — that's StrictMode catching bugs:

function Chat({ roomId }) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect();
    // ❌ Missing cleanup → StrictMode reveals the leak:
    // Mount → Unmount → Mount = 2 connections, 0 disconnections
  }, [roomId]);

  // ✅ Proper cleanup:
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect();
    return () => connection.disconnect(); // Symmetric cleanup
  }, [roomId]);
}

Why it matters: StrictMode simulates the lifecycle of future concurrent features (offscreen rendering, fast refresh). Warnings today become bugs tomorrow when React leverages these rendering capabilities more aggressively.

Mistake 5: Assuming Synchronous State Updates 
// ❌ WRONG: Reading state immediately after setState
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count); // Still 0! State updates are batched
    setCount(count + 1); // Both use stale count=0 → result is 1, not 2

    // ❌ Assuming DOM is updated synchronously
    setCount(5);
    document.title = `Count: ${count}`; // Still shows old count
  }

  // ✅ CORRECT: Use updater function for sequential updates
  function handleClickCorrect() {
    setCount(c => c + 1); // Uses latest state
    setCount(c => c + 1); // Chains correctly → result is 2

    // For DOM reads after state update, use useEffect or flushSync:
    flushSync(() => {
      setCount(5); // Forces synchronous commit
    });
    // DOM is now updated — safe to read
    console.log(document.title); // Reflects count=5
  }
}

Why it matters: In React 18, ALL state updates are batched by default (even in setTimeout, promises, native event handlers). Under concurrent rendering, updates may also be delayed or reordered based on priority. Never assume immediate state reflection.

Trade-offs

Dimension Synchronous Rendering Concurrent Rendering
Responsiveness Can block main thread for entire tree traversal Yields every 5ms, stays responsive to user input
Predictability Render → commit is a single synchronous operation Renders may be interrupted, restarted, or discarded
Memory Single tree in memory during reconciliation Two full fiber trees (current + workInProgress) always in memory
Complexity Simple mental model: setState → immediate render → DOM update Complex: priorities, lanes, interruption, starvation, tearing
Consistency UI always reflects one state version (never torn) External stores can tear without useSyncExternalStore
CPU cost per update Lower overhead (no scheduling, no yielding checks) Higher overhead per fiber (shouldYield check, alternate management)
Perceived performance Fast for small updates, janky for large ones Consistently smooth — distributes work across frames
Code constraints Side effects in render are buggy but "work" Side effects in render are actively broken (non-deterministic)
Debugging Single call stack, predictable profiling Fragmented execution, harder to trace with DevTools

When synchronous is still used: Even with createRoot, React uses synchronous rendering for discrete events (clicks, key presses) where immediate feedback is expected. Concurrent rendering activates for transitions, deferred values, and Suspense boundaries. It's not all-or-nothing.

Memory vs Responsiveness Trade-off

The double-buffer approach (two fiber trees) roughly doubles memory usage for fiber metadata. For a tree with 10,000 fibers, this might be ~5-10MB of additional object allocations. React mitigates this through:

  • Fiber reuse: Alternates are recycled, not garbage collected and reallocated
  • Lazy creation: workInProgress fibers are only created for nodes that need work
  • Structural sharing: Unchanged subtrees share the same child pointers

Follow-up Questions

1. How does React determine which lane (priority) an update belongs to?

Lane assignment depends on the context in which setState is called:

  • Inside a click/keydown handler: SyncLane (highest priority, processed synchronously)
  • Inside mousemove/scroll handler: InputContinuousLane
  • Inside startTransition: TransitionLane (one of 16 transition lanes, for parallelism)
  • Default (e.g., in a setTimeout): DefaultLane
  • Inside useDeferredValue: TransitionLane (treated as a transition)

React tracks the "current event priority" via a module-level variable (currentUpdatePriority) that's set by the event system before dispatching handlers and reset after.

2. What happens if a higher-priority update arrives while React is mid-render on a lower-priority update?

React performs "preemption":

  1. The scheduler detects a higher-priority task exists (via shouldYield() or task queue comparison)
  2. The current work loop exits
  3. ensureRootIsScheduled sees the new higher-priority lanes
  4. It calls prepareFreshStack which discards the partially-built workInProgress tree
  5. A new render begins at the higher-priority lane, using the committed current tree as the base
  6. After the high-priority render commits, the original lower-priority work is rescheduled (it may need to be restarted from scratch if the base state changed)
3. How does Suspense interact with Fiber and concurrent rendering?

When a component inside a Suspense boundary throws a Promise (the "suspend" signal):

  1. React catches the thrown promise during beginWork
  2. It marks the Suspense boundary fiber with a DidCapture flag
  3. React renders the fallback UI instead of the suspended subtree
  4. The promise is attached to the fiber; when it resolves, React schedules a "retry" at the same lane
  5. With concurrent rendering, React can keep showing the old UI while the new version loads (instead of immediately showing the fallback) — this is the "concurrent Suspense" behavior enabled by transitions
4. Why are there 31 lanes (bits) instead of simple numeric priorities?

Lanes use a 31-bit integer as a bitmask because:

  • Batching: Multiple updates at the same priority can be merged into one render by OR-ing their lanes: renderLanes = lane1 | lane2
  • Subset checking: "Does this fiber have work at this priority?" is a single AND: fiber.lanes & renderLanes !== 0
  • Parallel transitions: 16 transition lanes allow multiple in-flight transitions to be tracked independently
  • Entanglement: Some updates must commit together (e.g., if update B depends on update A's state). Entangled lanes ensure they're processed in the same render.
  • Performance: Bitmask operations are single CPU instructions — O(1) for union, intersection, subset checks
5. How does React handle errors during concurrent rendering?

Error boundaries work across both phases:

  • Render phase error: React catches it, discards the partial workInProgress subtree, walks up to find the nearest error boundary, re-renders that boundary with the fallback UI
  • Commit phase error: More serious — DOM may be partially mutated. React still catches it and unmounts the errored subtree, showing the boundary's fallback
  • Concurrent specifics: If an error occurs during an interruptible render and is caused by a race condition (e.g., reading stale data), React may retry the render synchronously before showing the error boundary. This is the "error retry" mechanism.
6. What is "tearing" and how does useSyncExternalStore prevent it?

Tearing: Different parts of the UI reflecting different versions of the same data source in a single frame. This can't happen with React state (React controls when state is read), but CAN happen with external stores (Redux, Zustand, module-level variables).

How it happens:

  1. React starts rendering Component A, reads store version 1
  2. React yields (time slicing)
  3. External code updates the store to version 2
  4. React resumes, renders Component B, reads store version 2
  5. Result: A shows v1 data, B shows v2 data — torn UI

Prevention: useSyncExternalStore takes a snapshot at render start and checks it before commit. If the store changed during render, React forces a synchronous re-render to get a consistent snapshot.

7. How does the Offscreen (Activity) API relate to Fiber's architecture?

The Offscreen API (renamed to <Activity>) leverages Fiber's ability to:

Status (2024): <Activity> remains experimental/unstable in React 19. It's not available in the stable API surface. Don't present it as shipped in an interview — say "there's an experimental Activity API that React is exploring."

  • Render at lowest priority: Offscreen content uses IdleLane, only processed when nothing else needs the CPU
  • Keep fiber trees alive but hidden: Components are rendered but their DOM effects are suppressed (visibility: hidden or detached)
  • Pre-render future views: A tab you haven't clicked yet can be pre-rendered in the background, its fiber tree ready to be committed instantly when activated
  • Retain state during hide/show: Unlike unmounting, offscreen fibers keep their state and refs — enabling instant tab switching without data refetching

This is fundamentally only possible because Fiber separates the render phase (building the tree) from the commit phase (showing it). You can render without committing, or commit selectively.

8. How does React 19's use() hook integrate with Fiber/Suspense?

use() is a new hook (React 19) that reads the value of a Promise or Context during render. When it encounters an unresolved Promise, it throws it (like Suspense), causing Fiber to suspend that subtree. Key differences from existing patterns:

  • Unlike useEffect + state, use() integrates directly with the render phase and Suspense machinery
  • It can be called conditionally (unlike other hooks), because it doesn't maintain hook slot state — it reads an external value
  • The Promise must be created outside the render function (parent component, cache, or module scope) — otherwise a new Promise is created each render, causing infinite Suspense loops

Summary

Mental Models

  • Fiber = virtual stack frame: Each fiber is a unit of work that would have been a frame on the call stack in the old reconciler. By moving to heap-allocated objects, React can pause/resume/reorder work.
  • Double buffer = back buffer in games: You never see a half-drawn frame because rendering happens off-screen (workInProgress tree), and only the finished result gets "swapped in" (commit).
  • Scheduler = cooperative OS process scheduler: React's scheduler multiplexes multiple "processes" (renders at different priorities) onto a single thread, using time slicing and priority queues — exactly like a cooperative multitasking OS.
  • Lanes = bitmask priority groups: Think of lanes as highway lanes — multiple updates can ride in the same lane (batched), and React processes lanes from fastest (SyncLane) to slowest (IdleLane).
  • Render phase = planning, Commit phase = execution: The render phase figures out what needs to change (pure computation). The commit phase makes it happen (side effects). Only the planning can be interrupted.

What NOT to Say in an Interview

  • ❌ "Fiber uses requestIdleCallback" — It doesn't. React has its own scheduler using MessageChannel.
  • ❌ "Concurrent mode makes everything async" — Discrete events (clicks) are still synchronous. Only transitions and deferred values use concurrent rendering.
  • ❌ "Virtual DOM diffing is what makes React fast" — The virtual DOM is about declarative programming, not speed. Fiber's contribution is scheduling and interruptibility, not diffing speed.
  • ❌ "Fiber is about rendering components in parallel" — Fiber is single-threaded. Concurrency here means interleaving, not parallelism. React can switch between tasks, but only one runs at a time.
  • ❌ "You need to opt into concurrent rendering per component" — Concurrent rendering is enabled at the root level (createRoot). Individual components opt into concurrent features via startTransition, useDeferredValue, etc.
  • ❌ "useEffect runs during render" — Effects are scheduled during render but execute during or after commit. This distinction is fundamental to Fiber's architecture.

Key Takeaways for Senior Engineers

  1. Fiber replaced the call stack with a linked-list tree of work units that can be paused and resumed
  2. The work loop processes one fiber at a time, yielding every ~5ms to keep the main thread responsive
  3. Double buffering (current + workInProgress trees) prevents visual tearing
  4. The render phase is pure and interruptible; the commit phase is synchronous and effectful
  5. Lanes provide fine-grained priority scheduling with bitmask efficiency
  6. Your code's contract with React: render must be pure, side effects belong in effects
  7. External stores must use useSyncExternalStore to prevent tearing under concurrent rendering

Memory Leaks in Browser Applications

"How would you investigate a memory leak that only appears after hours of usage in a single-page application?"
Key Takeaway: Memory leaks in SPAs are objects that remain reachable from GC roots but serve no purpose. The three-snapshot technique, allocation timelines, and retainer chain analysis in Chrome DevTools are your primary investigative tools. The most common causes — detached DOM nodes, forgotten event listeners, closures over stale state, uncleared timers, and growing global collections — all share one root cause: references that outlive their intended lifecycle.

Interviewer's Intent

What the interviewer is really testing
This question tests three capabilities simultaneously:
  • Systematic debugging approach: Can you methodically isolate a leak that takes hours to manifest, rather than guessing? Do you have a reproducible workflow?
  • Understanding of browser memory model: Do you know how V8 manages memory, what constitutes a GC root, and why certain patterns prevent collection?
  • Production experience: Have you actually debugged memory issues in real applications? Can you describe specific tooling, metrics, and war stories?

Senior candidates should demonstrate fluency with Chrome DevTools Memory panel, articulate the difference between shallow and retained size, and explain why SPA architecture inherently creates more leak opportunities than traditional multi-page apps.

Red flags for interviewers: Candidates who jump straight to "use a profiler" without explaining what they'd look for, or who can't differentiate between high memory usage and an actual leak (monotonically growing heap).

60-Second Answer

Structured response for time-pressured interviews
Framework: Detect → Isolate → Identify → Fix → Prevent

Investigation methodology: I'd start by confirming it's a true leak (monotonically increasing heap, not just high watermark) using performance.measureUserAgentSpecificMemory() in production or the Performance Monitor in DevTools. Then I'd use the three-snapshot technique: snapshot baseline, perform the suspected leaking action repeatedly, snapshot again, compare retained objects.

Common causes in SPAs:

  1. Detached DOM trees held by JavaScript references
  2. Event listeners on removed elements (or window/document listeners never removed)
  3. Closures capturing large scopes in long-lived callbacks
  4. Uncleared setInterval/setTimeout chains
  5. Growing collections (Maps, arrays, caches) without eviction

Tools: Chrome DevTools Memory panel (heap snapshots, allocation timeline), Performance Monitor for real-time tracking, memlab from Meta for automated detection in CI.

Fix patterns: Proper cleanup in component unmount/destroy lifecycle, WeakMap/WeakRef for caches, AbortController for fetch + event listeners, bounded LRU caches for data stores.

Process Isolation

Each browser tab (origin) runs in its own renderer process with its own V8 isolate. This means:

  • A leak in one tab cannot directly affect another tab's memory
  • Each tab has independent GC scheduling and heap limits
  • Site Isolation (Chrome 67+) ensures cross-origin iframes get separate processes
  • Service Workers get their own isolate but share the registration's memory budget

Shared Memory

SharedArrayBuffer allows sharing raw byte buffers between workers and the main thread. It lives outside the normal V8 heap in a separately allocated memory region, and is not subject to GC — it's reference-counted across agents.

Cross-origin isolation required: SharedArrayBuffer requires Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp headers since Spectre mitigations (Chrome 92+).

Heap Generations

Young Gen scavenging, Old Gen compaction, and promotion

Young Generation: Scavenger (Semi-Space Copying)

The Young Generation is divided into two equal semi-spaces: From-Space (active) and To-Space (empty). When From-Space fills up:

  1. Live objects are identified by tracing from GC roots
  2. Live objects are copied to To-Space (compacting in the process)
  3. From-Space and To-Space labels are swapped
  4. Dead objects are implicitly freed (the old From-Space is now empty To-Space)
// Objects here are short-lived — most die in Young Gen
function processEvent(event) {
  const temp = { x: event.clientX, y: event.clientY }; // Born, used, dies
  return temp.x + temp.y;
  // temp becomes unreachable, collected in next scavenge
}

Old Generation: Mark-Compact

Objects that survive Young Gen are promoted to Old Gen, where a full Mark-Sweep-Compact cycle runs less frequently:

  • Mark: Traverse from roots, mark all reachable objects
  • Sweep: Iterate heap, free unmarked objects, build free lists
  • Compact: Move surviving objects to eliminate fragmentation

Promotion Criteria

An object is promoted to Old Gen when it has survived two scavenger cycles (configurable but rarely changed). This is the "generational hypothesis" — if an object survived two GCs, it's likely long-lived.

Large Object Space

Objects larger than ~128KB are allocated directly in Large Object Space. They are never moved by the GC (copying them would be too expensive), and are individually collected via mark-sweep.

Why Leaks End Up in Old Gen

A leaked object by definition persists across many GC cycles. After surviving two scavenges (~seconds), it's promoted to Old Gen where it will remain until the retainer chain is broken. This is why leaks cause Old Gen growth — and why Old Gen pressure triggers expensive full GCs that cause visible jank.

Garbage Collection Algorithms in V8

Mark-Sweep-Compact, incremental/concurrent marking, and Orinoco

Incremental Marking

Full marking can take 100ms+ on large heaps. V8 breaks this into small increments (~5ms chunks) interleaved with application execution using a write barrier to track mutations during marking:

// Conceptual write barrier (V8 internal)
function writeBarrier(object, field, value) {
  object[field] = value;
  if (isMarking && isBlack(object) && isWhite(value)) {
    // Object was already marked but now points to unmarked value
    markGray(value); // Re-add to marking worklist
  }
}

Concurrent Marking

Since V8 6.3, marking happens on background threads concurrently with JavaScript execution. The main thread only handles write barriers and finalization. This reduced GC pause times by 60-70%.

Parallel Scavenging

Young Gen scavenging uses multiple threads to copy objects in parallel. Each thread claims a portion of From-Space and copies to To-Space using atomic pointer operations to handle cross-thread references.

Orinoco GC Improvements

  • Concurrent sweeping: Free lists are built on background threads
  • Concurrent compaction: Page evacuation happens off main thread
  • Lazy sweeping: Pages are swept on-demand when allocation fails
  • Black allocation: Objects allocated during marking are born black (marked)

Common SPA Leak Patterns

Detached DOM Nodes

A detached DOM node is an element removed from the document tree but still referenced by JavaScript. The entire subtree under that element is retained.

// ❌ LEAK: Reference prevents GC of entire subtree
let cachedElement = null;

function showModal() {
  const modal = document.createElement('div');
  modal.innerHTML = '<div class="modal"><p>Large content...</p></div>';
  document.body.appendChild(modal);
  cachedElement = modal; // Strong reference retained
}

function hideModal() {
  cachedElement.remove(); // Removed from DOM...
  // But cachedElement still points to it! Detached but not collected.
}
// ✅ FIX: Null the reference after removal
function hideModal() {
  cachedElement.remove();
  cachedElement = null; // Allow GC
}

// ✅ BETTER: Use WeakRef if you need conditional re-access
let cachedRef = null;

function showModal() {
  const modal = document.createElement('div');
  document.body.appendChild(modal);
  cachedRef = new WeakRef(modal);
}

function getCachedModal() {
  return cachedRef?.deref(); // Returns undefined if GC'd
}
Forgotten Event Listeners

Event listeners on window, document, or long-lived elements create closures that capture their enclosing scope. If the component is destroyed but the listener remains, the entire closure scope is retained.

// ❌ LEAK: Listener on window outlives component
class ChatWidget {
  constructor(container) {
    this.container = container;
    this.messages = []; // Grows unbounded
    window.addEventListener('resize', () => {
      this.relayout(); // Closure captures `this` (the whole ChatWidget)
    });
  }

  destroy() {
    this.container.remove();
    // Listener still attached to window! ChatWidget cannot be GC'd
  }
}
// ✅ FIX: Store reference and remove on cleanup
class ChatWidget {
  constructor(container) {
    this.container = container;
    this.messages = [];
    this.handleResize = () => this.relayout();
    window.addEventListener('resize', this.handleResize);
  }

  destroy() {
    window.removeEventListener('resize', this.handleResize);
    this.container.remove();
    this.messages = null;
  }
}

// ✅ MODERN: Use AbortController for bulk cleanup
class ChatWidget {
  constructor(container) {
    this.controller = new AbortController();
    const { signal } = this.controller;

    window.addEventListener('resize', () => this.relayout(), { signal });
    window.addEventListener('online', () => this.reconnect(), { signal });
    document.addEventListener('visibilitychange', () => this.pause(), { signal });
  }

  destroy() {
    this.controller.abort(); // Removes ALL listeners at once
  }
}
Closures Holding References

JavaScript closures capture variables from their lexical scope. If a closure is long-lived (stored in a callback, timer, or cache), it retains everything in scope — even variables you don't use in the closure body.

// ❌ LEAK: Closure retains `hugeData` even though it only uses `id`
function createHandler(hugeData) {
  const id = hugeData.id;
  // V8 may or may not optimize away hugeData —
  // if debugger is attached or eval exists, it won't
  return function handler() {
    console.log('Processing', id);
  };
}

// The returned handler keeps hugeData alive in its closure scope
const handler = createHandler(fetchLargeDataset());
element.addEventListener('click', handler);
// ✅ FIX: Extract only what you need before creating the closure
function createHandler(hugeData) {
  const id = hugeData.id;
  const name = hugeData.name;
  // hugeData goes out of scope here — no closure captures it
  return function handler() {
    console.log('Processing', id, name);
  };
}
V8 Context Specialization: V8's optimizer can sometimes eliminate unused captured variables, but this is not guaranteed — especially with eval, with, debugger breakpoints, or when the closure is passed across module boundaries.
Timers & Intervals Not Cleared 
// ❌ LEAK: Interval holds reference to component forever
function startPolling(component) {
  setInterval(() => {
    const data = fetchUpdates();
    component.updateView(data); // `component` kept alive by closure
  }, 5000);
  // No handle stored — can never be cleared!
}

// Component is "destroyed" but interval keeps running and retaining it
// ✅ FIX: Store handle, clear on cleanup
function startPolling(component) {
  const intervalId = setInterval(() => {
    if (!component.isConnected) {
      clearInterval(intervalId); // Self-cleaning
      return;
    }
    const data = fetchUpdates();
    component.updateView(data);
  }, 5000);

  return () => clearInterval(intervalId); // Return cleanup function
}

// In component lifecycle:
const stopPolling = startPolling(this);
// On destroy:
stopPolling();
Global State Accumulation 
// ❌ LEAK: Cache grows without bound
const responseCache = new Map();

async function fetchWithCache(url) {
  if (responseCache.has(url)) return responseCache.get(url);
  const response = await fetch(url);
  const data = await response.json();
  responseCache.set(url, data); // Never evicted!
  return data;
}
// After navigating 1000 pages, cache holds 1000 entries
// ✅ FIX: Bounded LRU cache
class LRUCache {
  constructor(maxSize = 100) {
    this.cache = new Map();
    this.maxSize = maxSize;
  }

  get(key) {
    if (!this.cache.has(key)) return undefined;
    const value = this.cache.get(key);
    this.cache.delete(key);
    this.cache.set(key, value); // Move to end (most recent)
    return value;
  }

  set(key, value) {
    this.cache.delete(key);
    this.cache.set(key, value);
    if (this.cache.size > this.maxSize) {
      const oldest = this.cache.keys().next().value;
      this.cache.delete(oldest);
    }
  }
}
Observers Not Disconnected 
// ❌ LEAK: Observers hold strong refs to callbacks and targets
function trackVisibility(element, callback) {
  const observer = new IntersectionObserver(callback);
  observer.observe(element);
  // If element is removed, observer still references it
  // Observer itself is rooted by the browser's internal observer list
}

// Same pattern with MutationObserver and ResizeObserver
// ✅ FIX: Disconnect observers on cleanup
function trackVisibility(element, callback) {
  const observer = new IntersectionObserver((entries) => {
    callback(entries);
  });
  observer.observe(element);

  return () => {
    observer.unobserve(element);
    observer.disconnect(); // Full cleanup
  };
}

// Usage with cleanup
const cleanup = trackVisibility(el, handleVisible);
// On destroy:
cleanup();

// ❌ LEAK: Missing effect cleanup
function useSubscription(channel) {

  useEffect(() => {
    const ws = new WebSocket(channel);
    ws.onmessage = (e) => {

// ❌ LEAK: Stale ref holding detached DOM

    playerInstance.current = new HeavyVideoLib(containerRef.current);

// ✅ FIX: Proper effect cleanup
function useSubscription(channel) {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    let cancelled = false;
    const ws = new WebSocket(channel);
    ws.onmessage = (e) => {
      if (!cancelled) setMessages(prev => [...prev, e.data]);
    };
    return () => {
      cancelled = true;
      ws.close();
    };
  }, [channel]);
}

// ✅ FIX: Cleanup refs
function VideoPlayer() {
  const containerRef = useRef(null);
  const playerInstance = useRef(null);

  useEffect(() => {
    playerInstance.current = new HeavyVideoLib(containerRef.current);
    return () => {
      playerInstance.current?.destroy();
      playerInstance.current = null;
    };
  }, []);
}

Heap Snapshot Interpretation

A heap snapshot shows every reachable object on the V8 heap. Key columns:

  • Constructor: The function that created the object (or built-in type)
  • Distance: Shortest path from GC root (lower = closer to root = harder to leak)
  • Shallow Size: Memory directly held by the object itself
  • Retained Size: Memory that would be freed if this object were collected

Shallow Size vs Retained Size

  Object A (shallow: 32B)
    ├── Object B (shallow: 64B)  ← only referenced by A
    │     └── Object C (shallow: 1MB) ← only referenced by B
    └── Object D (shallow: 128B) ← also referenced by Root

  A's retained size = 32 + 64 + 1MB = ~1MB + 96B
  (D is NOT included because it has another retainer)
Investigation tip: Sort by Retained Size descending to find the objects whose collection would free the most memory. These are your primary suspects.

Object Groups and Distances

Objects at distance 1 are directly referenced by GC roots (window, active stack frames, native handles). Most leaked objects will be at distance 3+ — they're kept alive through a chain of intermediaries.

Filtering and Searching

  • Filter by class name: type constructor names in the filter bar
  • Search for "Detached" to find detached DOM trees
  • Right-click → "Reveal in Summary view" to jump between views
  • Use "Containment" view to see the exact reference chain from GC root

Heap Snapshots Comparison

Three-snapshot technique, comparison view, finding leaks

Three-Snapshot Technique (Step by Step)

  1. Snapshot 1 (Baseline): Load app, navigate to the suspect page, force GC (trash icon), take snapshot
  2. Action: Perform the leaking operation (e.g., open/close modal, navigate away and back) 5-10 times
  3. Snapshot 2: Force GC again, take second snapshot
  4. Verify: Repeat the action 5-10 more times
  5. Snapshot 3: Force GC, take third snapshot

DevTools tip: The "force GC" step uses the 🗑️ trash can icon in the top-left of the Memory panel (or Performance Monitor). This triggers a full garbage collection, ensuring objects retained only by weak references or pending finalization are cleaned up before you snapshot. Without forcing GC first, your snapshots will include noise from objects that are technically eligible for collection but haven't been swept yet.

Why three? Snapshot 1 establishes baseline (includes lazy initialization). Snapshot 2 catches leaks from the first batch. Snapshot 3 confirms the pattern is consistent (not just one-time initialization).

Comparison View

Select Snapshot 3, then choose "Comparison" and compare against Snapshot 1. This shows:

  • # New: Objects allocated since Snapshot 1 that are still alive
  • # Deleted: Objects that existed in Snapshot 1 but are now gone
  • # Delta: Net change — positive means growing (potential leak)
  • Size Delta: Net memory change per constructor

Containment View

Shows the reference hierarchy from GC roots. Navigate: GC Root → Window → your object chain. This reveals why an object is alive — the retainer path.

Statistics View

Pie chart showing memory breakdown: Code, Strings, JS Arrays, Typed Arrays, System objects. Useful for identifying if the leak is DOM nodes, string accumulation, or object growth.

Allocation Instrumentation

Timeline tracking, sampling, and identifying allocation hot spots

Allocation Instrumentation on Timeline

Records every allocation with a full stack trace. High overhead but provides the most detail:

  • Start recording, perform the suspect action, stop recording
  • Blue bars: objects still alive at the end of recording
  • Gray bars: objects that were allocated then collected (healthy)
  • Select a time range to see only allocations in that window

Allocation Sampling

Statistical approach — samples allocations at regular intervals (~512KB). Much lower overhead, suitable for longer recording sessions:

  • Records allocation site (call stack) but not every individual object
  • Shows a flame chart of allocation frequency by code path
  • Best for identifying "which function allocates the most"

Blue vs Gray Bars Interpretation

Timeline: ──────────────────────────────────────────▶ time
           █ █ ░ █ ░ ░ █ █ █ █ ░ █ █ █ █ █ █ █ █ █
           ▲               ▲
           │               │
      Healthy:         Suspicious:
      Some blue,       Monotonically increasing
      mostly gray      blue bars = leak
Key insight: If blue bars accumulate over time without corresponding gray bars, you have a leak. Click the blue bars to see the allocation stack trace — this tells you exactly what code created the leaked objects.

performance.measureUserAgentSpecificMemory()

Modern memory measurement, cross-origin isolation, and production RUM

The Modern Memory Measurement API

// Requires cross-origin isolation
async function measureMemory() {
  if (!crossOriginIsolated) {
    console.warn('Cross-origin isolation required');
    return;
  }

  const result = await performance.measureUserAgentSpecificMemory();
  console.log('Total bytes:', result.bytes);
  console.log('Breakdown:', result.breakdown);
  // breakdown: [{ bytes, attribution: [{ url, scope }], types }]
}

Cross-Origin Isolation Requirements

The API requires two response headers on your document:

// Required HTTP headers:
// Cross-Origin-Opener-Policy: same-origin
// Cross-Origin-Embedder-Policy: require-corp

// Verify in code:
if (self.crossOriginIsolated) {
  // Safe to use measureUserAgentSpecificMemory()
}

Breakdown by URL

The API attributes memory to specific URLs (scripts, iframes), enabling you to identify which third-party script is consuming the most memory:

const result = await performance.measureUserAgentSpecificMemory();
for (const entry of result.breakdown) {
  if (entry.bytes > 1_000_000) {
    console.warn('High memory:', entry.attribution[0]?.url, entry.bytes);
  }
}

Using in Production RUM

// Report memory metrics periodically
function startMemoryMonitoring(intervalMs = 60_000) {
  if (!crossOriginIsolated) return;

  setInterval(async () => {
    try {
      const { bytes } = await performance.measureUserAgentSpecificMemory();
      navigator.sendBeacon('/metrics', JSON.stringify({
        type: 'memory',
        bytes,
        timestamp: Date.now(),
        url: location.href,
        sessionDuration: performance.now()
      }));
    } catch (e) {
      // API may throw if GC is busy
    }
  }, intervalMs);
}

WeakMap for DOM Node Metadata

// ✅ Metadata is automatically cleaned when DOM node is GC'd
const nodeMetadata = new WeakMap();

function annotateElement(el, data) {
  nodeMetadata.set(el, {
    createdAt: Date.now(),
    analytics: data
  });
}

// When `el` is removed from DOM and no other refs exist,
// the WeakMap entry is automatically collected

WeakRef for Caches

// ✅ Cache that lets GC reclaim memory under pressure
class WeakCache {
  #cache = new Map(); // key → WeakRef

  get(key) {
    const ref = this.#cache.get(key);
    if (!ref) return undefined;
    const value = ref.deref();
    if (!value) {
      this.#cache.delete(key); // Clean up dead reference
      return undefined;
    }
    return value;
  }

  set(key, value) {
    this.#cache.set(key, new WeakRef(value));
  }
}

FinalizationRegistry for Cleanup

// ✅ Release external resources when JS object is collected
const registry = new FinalizationRegistry((handle) => {
  // Called after the registered object is GC'd
  console.log(`Object collected, releasing handle: ${handle}`);
  externalResource.release(handle);
});

function createManagedResource() {
  const handle = externalResource.acquire();
  const wrapper = { handle, data: new ArrayBuffer(1024) };
  registry.register(wrapper, handle); // Track wrapper, hold handle as value
  return wrapper;
}
// When wrapper is GC'd, registry callback fires with `handle`

Limitations and Caveats

  • Non-deterministic: WeakRef.deref() may return the object even after all strong refs are gone (GC hasn't run yet). Don't rely on timing.
  • FinalizationRegistry is advisory: Callbacks may be delayed or never called (tab closed, process killed).
  • No iteration: WeakMap/WeakSet cannot be iterated — you can't enumerate contents or get size.
  • Keys must be objects or non-registered symbols: Strings, numbers, and registered symbols (Symbol.for()) cannot be WeakMap keys. Non-registered symbols (plain Symbol()) are valid keys since ES2023.
  • Don't use for critical cleanup: Use explicit dispose patterns. The using keyword with Symbol.dispose/Symbol.asyncDispose (TC39 Explicit Resource Management, shipping in TypeScript 5.2+ and Chrome 134+) provides deterministic, non-GC-dependent cleanup — the modern replacement for try/finally boilerplate.

Production Incident: Email Client SPA

Full incident writeup — investigation, root cause, and resolution

Symptoms

Ticket: "Application becomes increasingly sluggish after 4-6 hours of continuous use. Users who keep the tab open all day report unresponsive UI by afternoon. Tab eventually crashes with 'Aw, Snap!' (OOM)."

Environment: React 18 SPA email client, virtualized inbox list (react-window), ~50k messages for power users, used 8+ hours/day by support staff.

Investigation

// Step 1: Confirm the leak with Performance Monitor
// Opened DevTools → Performance Monitor → watched "JS Heap Size"
// Observation: Heap grows ~5MB/hour with no plateau

// Step 2: Reproduce in accelerated fashion
// Automated rapid navigation: Inbox → Message → Back (100 cycles)
// Heap grew from 45MB to 120MB in 100 cycles

// Step 3: Three-snapshot technique
// Snapshot 1: After initial load (45MB)
// Action: Navigate to 20 messages and back
// Snapshot 2: Force GC → 67MB (should be ~45MB)
// Action: Navigate to 20 more messages and back
// Snapshot 3: Force GC → 89MB

// Step 4: Compare Snapshot 3 vs Snapshot 1
// Found: +800 "Detached HTMLDivElement" (Delta view)
// Each detached tree: ~24KB retained size

Root Cause

The virtualized list component used ResizeObserver to measure row heights for variable-size virtualization. When scrolling caused rows to leave the viewport, the component unmounted the row DOM — but the ResizeObserver maintained a strong reference to the row element in its observation list.

// ❌ BEFORE: The leaking VirtualRow component
function VirtualRow({ index, style, data }) {
  const rowRef = useRef(null);
  const { setRowHeight } = data;

  useEffect(() => {
    const observer = new ResizeObserver((entries) => {
      setRowHeight(index, entries[0].contentRect.height);
    });
    observer.observe(rowRef.current);
    // BUG: No cleanup! Observer keeps reference to unmounted DOM
  }, [index, setRowHeight]);

  return (
    <div ref={rowRef} style={style}>
      <EmailPreview messageId={data.messages[index].id} />
    </div>
  );
}

Resolution

// ✅ AFTER: Proper observer cleanup
function VirtualRow({ index, style, data }) {
  const rowRef = useRef(null);
  const { setRowHeight } = data;

  useEffect(() => {
    const el = rowRef.current;
    if (!el) return;

    const observer = new ResizeObserver((entries) => {
      if (entries[0]) {
        setRowHeight(index, entries[0].contentRect.height);
      }
    });
    observer.observe(el);

    return () => {
      observer.unobserve(el);
      observer.disconnect(); // Full cleanup
    };
  }, [index, setRowHeight]);

  return (
    <div ref={rowRef} style={style}>
      <EmailPreview messageId={data.messages[index].id} />
    </div>
  );
}

// ADDITIONAL FIX: Shared observer pattern (one observer for all rows)
const sharedObserver = new ResizeObserver((entries) => {
  for (const entry of entries) {

Lessons Learned

  • Virtualized lists amplify leaks — hundreds of mount/unmount cycles per session
  • Always audit useEffect for missing cleanup returns, especially with Observers
  • Shared observers (one per list) are more efficient than per-row observers
  • Added automated memory regression test to CI (heap delta < 1MB after 50 navigation cycles)
  • Added production RUM memory reporting for early detection

Debugging Workflow

Systematic approach, CI automation, and production monitoring

Step-by-Step Systematic Approach

  1. Confirm the leak: Use Performance Monitor to verify JS Heap grows monotonically (not just fluctuating)
  2. Identify the trigger: Which user action correlates with growth? Navigate, open modal, switch tabs?
  3. Isolate the component: Disable features one by one (feature flags) to narrow the source
  4. Three-snapshot technique: Baseline → Action × N → Snapshot → Action × N → Snapshot
  5. Analyze delta: In comparison view, find constructors with positive delta
  6. Trace retainers: For each leaked object, follow the retainer chain to find the root cause
  7. Fix and verify: Apply fix, repeat step 4 — delta should be near zero

  await performAction(page);

    await undoAction(page);

}

class Component {

    element.addEventListener('click', this.#handleClick, { signal });

  }

    try {
      const res = await fetch('/api/data', { signal });

        this.data = await res.json();

      if (e.name !== 'AbortError') throw e;
    }
  }

  #handleClick = (e) => { /* ... */ };
  #handleResize = () => { /* ... */ };
  #handleKeydown = (e) => { /* ... */ };

  unmount() {
    this.#controller.abort(); // One call cleans everything
  }
}

Self-Cleaning Cache with TTL and Size Limit

class BoundedCache {
  #map = new Map();
  #maxSize;
  #ttlMs;
  #cleanupInterval;

  constructor({ maxSize = 200, ttlMs = 300_000 } = {}) {
    this.#maxSize = maxSize;
    this.#ttlMs = ttlMs;
    this.#cleanupInterval = setInterval(() => this.#evictExpired(), ttlMs);
  }

  get(key) {
    const entry = this.#map.get(key);
    if (!entry) return undefined;
    if (Date.now() - entry.timestamp > this.#ttlMs) {
      this.#map.delete(key);
      return undefined;
    }
    // LRU: move to end
    this.#map.delete(key);
    this.#map.set(key, entry);
    return entry.value;
  }

  set(key, value) {
    this.#map.delete(key); // Remove if exists (for LRU ordering)
    this.#map.set(key, { value, timestamp: Date.now() });
    this.#enforceSize();
  }

  #enforceSize() {
    while (this.#map.size > this.#maxSize) {
      const oldest = this.#map.keys().next().value;
      this.#map.delete(oldest);
    }
  }

  #evictExpired() {
    const now = Date.now();
    for (const [key, entry] of this.#map) {
      if (now - entry.timestamp > this.#ttlMs) {
        this.#map.delete(key);
      }
    }
  }

  dispose() {
    clearInterval(this.#cleanupInterval);
    this.#map.clear();
  }
}

React Hook for Memory Leak Detection in Development

// useLeakDetector.js — development-only hook
import { useEffect, useRef } from 'react';

const registry = new FinalizationRegistry((label) => {
  console.log(`[LeakDetector] ✅ ${label} was collected`);
});

const tracked = new Set();

export function useLeakDetector(label) {
  const markerRef = useRef(null);

  useEffect(() => {
    if (process.env.NODE_ENV !== 'development') return;

    // Create a marker object that should be collected on unmount
    const marker = { label, mountedAt: Date.now() };
    markerRef.current = marker;
    tracked.add(label);

    return () => {
      markerRef.current = null;
      // Give GC a chance, then check
      setTimeout(() => {
        // If FinalizationRegistry hasn't fired after 10s, warn
        setTimeout(() => {
          if (tracked.has(label)) {
            console.warn(`[LeakDetector] ⚠️ ${label} may be leaked`);
          }
        }, 10_000);
      }, 0);
      registry.register(marker, label);
      tracked.delete(label);
    };
  }, [label]);
}

Automated Leak Test Using Puppeteer

// leak-test.mjs — Run with: node --expose-gc leak-test.mjs
import puppeteer from 'puppeteer';

async function detectLeaks(url, action, undo, { cycles = 20, threshold = 1_048_576 } = {}) {
  const browser = await puppeteer.launch({
    args: ['--js-flags=--expose-gc']
  });
  const page = await browser.newPage();
  await page.goto(url, { waitUntil: 'networkidle0' });

  // Warm-up cycle (lazy init, caches)
  await action(page);
  await undo(page);
  await page.evaluate('window.gc()');

  const baseline = (await page.metrics()).JSHeapUsedSize;
  const samples = [];

  for (let i = 0; i < cycles; i++) {
    await action(page);
    await undo(page);
    if (i % 5 === 0) {
      await page.evaluate('window.gc()');
      samples.push((await page.metrics()).JSHeapUsedSize);
    }
  }

  await page.evaluate('window.gc()');
  const final = (await page.metrics()).JSHeapUsedSize;
  const delta = final - baseline;

  // Check for monotonic growth (not just noise)
  const isMonotonic = samples.every((v, i) => i === 0 || v >= samples[i - 1] * 0.95);

  await browser.close();

  return {
    leaked: delta > threshold && isMonotonic,
    baseline,
    final,
    delta,
    samples
  };
}

Common Mistakes

Five mistakes senior developers make in interviews and production

1. Assuming React Handles All Cleanup

React's reconciler removes DOM nodes and unmounts components, but it does NOT automatically clean up: WebSocket connections, setInterval handles, event listeners on window/document, IntersectionObservers, Web Workers, or BroadcastChannels. You must return cleanup functions from useEffect.

2. Not Considering Third-Party Library Leaks

Libraries like chart.js, video players, rich text editors, and map SDKs allocate internal state that requires explicit .destroy() calls. Wrapping them in React without calling their cleanup API leaks their internal DOM trees and canvas contexts.

// ❌ Chart instance leaks its internal canvas and data
useEffect(() => {
  const chart = new Chart(canvasRef.current, config);
}, []);

// ✅ Must call destroy
useEffect(() => {
  const chart = new Chart(canvasRef.current, config);
  return () => chart.destroy();
}, []);

3. Using Map Where WeakMap Would Suffice

If your Map keys are objects whose lifecycle is managed elsewhere (DOM nodes, component instances), use WeakMap. A Map holds strong references to keys and values — the entries persist even after the key object is logically "dead" elsewhere in your app.

4. Storing DOM References in Module Scope

// ❌ Module-level reference survives across route navigations
let formElement = null;

export function initForm() {
  formElement = document.getElementById('signup-form');
}
// When user navigates away, formElement holds a detached DOM tree

Module scope is effectively global — it persists for the lifetime of the page. Store DOM references in component-scoped variables that are cleaned up on unmount.

5. Ignoring console.log Retention in DevTools

When DevTools is open, console.log(object) creates a strong reference from the console to that object (so you can inspect it later). Logging large objects in tight loops with DevTools open creates artificial leaks that disappear in production. Use console.log(object.id) or structured logging that doesn't retain object references.

Follow-up Questions

Seven follow-up questions with senior-level answers

1. "How would you differentiate between high memory usage and an actual memory leak?"

A leak is monotonically increasing memory that never plateaus, even after forcing GC. High usage may just be a large working set that stays constant. Plot heap size over time: a leak shows a positive slope; high usage shows a flat line at a high value. Additionally, after performing an undo action (close modal, navigate back), a leak shows memory doesn't return to baseline.

2. "What are GC roots in the browser?"

GC roots are entry points for reachability tracing. In Chrome:

  • Global object (window)
  • Active execution stack (local variables in running functions)
  • V8 internal handles (compiled code, built-in objects)
  • Registered callbacks (timers, observers, event listeners on live DOM)
  • Active Promises in microtask queue
  • Console retained objects (when DevTools is open)

3. "Can a Web Worker leak memory that affects the main thread?"

Indirectly, yes. If the main thread holds references to MessagePort or transferred objects, the Worker keeping its side alive prevents collection. Also, SharedArrayBuffer memory is reference-counted across threads — it's only freed when all threads release their reference. But a Worker's own heap is isolated; its internal leak won't grow the main thread's heap.

4. "How do closures interact with V8's hidden class system to cause leaks?"

V8 allocates a Context object for each closure scope. If multiple closures share the same scope, and only one is long-lived, the Context retains all variables — even those only used by short-lived closures that already ran. This is the "shared scope" problem: one long-lived callback keeps alive all sibling scope variables.

// Both closures share the same Context
function setup() {
  const hugeData = loadData(); // 10MB
  const id = hugeData.id;

  setTimeout(() => console.log(id), 1000);  // Short-lived
  element.onclick = () => console.log(id);  // Long-lived
  // hugeData is retained by the shared Context even though
  // neither closure uses it directly (V8 may not optimize this away)
}

5. "How would you set up memory leak monitoring for a production SPA?"

Three-layer approach:

  1. Client RUM: measureUserAgentSpecificMemory() reported every 5 min, correlated with session age and route
  2. Alerting: P95 memory at session-age-1hr exceeds threshold (e.g., 150MB) → alert engineering
  3. CI regression: memlab or Puppeteer-based test runs on every PR, fails if heap delta > threshold after N action cycles

6. "What's the difference between a heap snapshot and allocation sampling?"

A heap snapshot is a point-in-time census — it shows every object currently alive. Allocation sampling is a statistical record of where objects were created over a time window. Use snapshots to find "what's alive that shouldn't be" and sampling to find "what code path allocates the most." They answer different questions.

7. "How does React 18's concurrent rendering affect memory leaks?"

Concurrent rendering can start and abandon render work (via startTransition). If a component allocates during render (not in an effect), that allocation may be created multiple times if React restarts the render. This isn't a traditional leak (objects are short-lived), but it increases GC pressure. The real risk: if interrupted renders trigger subscription setups in effects that then get torn down rapidly, the subscription library may not handle rapid subscribe/unsubscribe cycles cleanly, leaving dangling callbacks.

Summary

Mental models and what NOT to say in an interview

Mental Models

  • The Water Tank: Memory flows in (allocations) and out (GC). A leak means the drain is partially blocked — water level rises monotonically until overflow (OOM).
  • The Reference Chain: Every leak is a chain from a GC root to a useless object. Your job is to find and break one link in that chain.
  • The Lifecycle Mismatch: Leaks occur when a reference's lifetime exceeds its usefulness. The fix is always to align reference lifetime with semantic lifetime.

What TO Say

  • "I'd first confirm it's a true leak by checking if heap grows monotonically after forced GC"
  • "The three-snapshot technique isolates objects that persist across action/undo cycles"
  • "Retained size in the retainer chain shows me the actual memory impact"
  • "In production, I'd use measureUserAgentSpecificMemory for continuous monitoring"
  • "The most common root causes are detached DOM, uncleaned listeners, and growing caches"

What NOT to Say

  • ❌ "JavaScript has garbage collection so memory leaks aren't really possible" — They absolutely are; GC only collects unreachable objects.
  • ❌ "Just use Chrome DevTools" without explaining the specific methodology
  • ❌ "React handles all memory management" — It handles unmounting, not resource cleanup.
  • ❌ "WeakMap solves all leaks" — It only helps when you have object keys; most leaks are from closures and listeners.
  • ❌ Confusing memory usage with memory leaks — high memory isn't a leak if it's stable.

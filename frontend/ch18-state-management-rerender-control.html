Hard React State Management Re-Renders Performance

Chapter 18: State Management & Re-Render Control

Key Takeaway: React re-renders a component when its state changes, its parent re-renders, or a consumed context value changes. The fix isn’t always React.memo — it’s understanding why the re-render happens and choosing the right strategy: state colocation (move state closer to where it’s used), context splitting (separate frequently-changing from rarely-changing values), referential stability (useMemo/useCallback for object/function identity), or external stores with selectors (Zustand, Jotai) that subscribe only to relevant slices.

Quick Answer (60 Seconds)

Structured response for time-pressured interviews

Framework: Triggers → Diagnose → Fix Hierarchy

/*
 * THE THREE RE-RENDER TRIGGERS:
 * 1. State change       → useState/useReducer setter called
 * 2. Parent re-render   → Parent renders, all children render (regardless of props)
 * 3. Context change     → Any consumed context value changes (by reference)
 *
 * DIAGNOSIS:
 * → React DevTools Profiler → Record → Interact → Read flamegraph
 * → "Why did this render?" shows trigger per component
 *
 * FIX HIERARCHY (cheapest first):
 * 1. Colocate state      → Move state to the component that uses it
 * 2. Component composition → children-as-props to skip re-renders
 * 3. Split context       → Separate fast-changing from slow-changing values
 * 4. React.memo          → Memoize expensive subtrees with stable props
 * 5. External store      → Zustand/Jotai with selectors for surgical updates
 */

The key insight: re-renders are not inherently expensive. React’s reconciliation is fast. The problem arises when re-renders trigger expensive computations, DOM mutations in large subtrees, or cascade through hundreds of components unnecessarily.

Why React Re-Renders

The three causes and a common misconception

The Three Causes

// CAUSE 1: State change — the component itself calls setState
function Counter() {
  const [count, setCount] = useState(0);
  // Calling setCount triggers a re-render of Counter
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}

// CAUSE 2: Parent re-render — parent renders, ALL children render
function Parent() {
  const [tick, setTick] = useState(0);
  // When Parent re-renders, Child re-renders — even if props haven't changed
  return <Child name="static" />;
}

// CAUSE 3: Context change — consumed context value changes
function ThemeConsumer() {
  const theme = useContext(ThemeContext);
  // When ThemeContext.Provider value changes, this re-renders
  return <div className={theme}>Themed</div>;
}

The Common Misconception

Props change alone does NOT trigger a re-render. A component re-renders because its parent re-rendered. React then checks if the new props differ (via React.memo) to skip a render — but the trigger was the parent, not the props. Without React.memo, the child renders regardless of whether props changed.

Re-Render vs DOM Update

// Re-render: React calls your component function again
// → Runs all hooks, creates new JSX (virtual DOM)
// → This is CHEAP for simple components

// DOM update (commit): React compares old vs new virtual DOM
// → Only touches actual DOM nodes that changed
// → This is where real performance cost lives

// A component can re-render 1000 times without a single DOM update
// if the returned JSX is identical each time

State Colocation

Moving state down — the cheapest optimization

Principle: State should live as close as possible to where it’s used. If only one component reads a piece of state, that state belongs in that component — not in a parent, not in context, not in a store.

Before: State Too High

// ❌ BAD: Search state lives in Dashboard, re-renders everything
function Dashboard() {
  const [search, setSearch] = useState('');
  const [data] = useState(initialData);

  return (
    <div>
      <SearchInput value={search} onChange={setSearch} />
      <ExpensiveChart data={data} />        {/* re-renders on every keystroke! */}
      <ExpensiveTable data={data} />        {/* re-renders on every keystroke! */}
      <Sidebar />                           {/* re-renders on every keystroke! */}
    </div>
  );
}

After: State Colocated

// ✅ GOOD: Search state lives in SearchInput — siblings don't re-render
function Dashboard() {
  const [data] = useState(initialData);

  return (
    <div>
      <SearchSection data={data} />         {/* only this re-renders */}
      <ExpensiveChart data={data} />        {/* stable! */}
      <ExpensiveTable data={data} />        {/* stable! */}
      <Sidebar />                           {/* stable! */}
    </div>
  );
}

function SearchSection({ data }) {
  const [search, setSearch] = useState('');
  const filtered = useMemo(
    () => data.filter(item => item.name.includes(search)),
    [data, search]
  );

  return (
    <div>
      <input value={search} onChange={e => setSearch(e.target.value)} />
      <SearchResults results={filtered} />
    </div>
  );
}

The “Lift Content Up” Pattern (Children as Props)

// ✅ ADVANCED: Parent owns state but children don't re-render
// Because children are passed as props (created by grandparent)

function App() {
  return (
    <AnimatedContainer>
      <ExpensiveChart />   {/* created here, not inside AnimatedContainer */}
      <ExpensiveTable />
    </AnimatedContainer>
  );
}

function AnimatedContainer({ children }) {
  const [frame, setFrame] = useState(0);

  useEffect(() => {
    const id = requestAnimationFrame(() => setFrame(f => f + 1));
    return () => cancelAnimationFrame(id);
  });

  // children were created by App, not by AnimatedContainer
  // So when AnimatedContainer re-renders, children elements are
  // referentially stable — React skips re-rendering them!
  return <div style={{ transform: `translateY(${frame}px)` }}>{children}</div>;
}

Why this works: JSX elements (<Component />) are objects. When a parent re-renders, it creates new element objects for its children. But if children are received as props, they were created by the grandparent and remain referentially identical — React skips rendering them.

Lifting vs Pushing State

When to lift state up vs push it down
Strategy When to Use Example
Lift state UP Multiple siblings need coordinated access to the same data Selected row in a table shared between table and detail panel
Push state DOWN Only one subtree uses the state; other subtrees are unaffected Search input filter used only in a dropdown

Over-Lifting: The Anti-Pattern

// ❌ ANTI-PATTERN: All state at the top "just in case"
function App() {
  const [searchTerm, setSearchTerm] = useState('');
  const [isModalOpen, setIsModalOpen] = useState(false);
  const [selectedTab, setSelectedTab] = useState(0);
  const [tooltipPos, setTooltipPos] = useState({ x: 0, y: 0 });
  const [dragState, setDragState] = useState(null);
  // Every state change here re-renders the ENTIRE app tree

  return (
    <div>
      <Header search={searchTerm} onSearch={setSearchTerm} />
      <TabPanel active={selectedTab} onChange={setSelectedTab} />
      <Canvas tooltip={tooltipPos} drag={dragState} />
      <Modal open={isModalOpen} onClose={() => setIsModalOpen(false)} />
    </div>
  );
}

// ✅ FIX: Each component owns its own state
function App() {
  return (
    <div>
      <Header />        {/* owns searchTerm internally */}
      <TabPanel />      {/* owns selectedTab internally */}
      <Canvas />        {/* owns tooltipPos, dragState internally */}
      <ModalTrigger />  {/* owns isModalOpen internally */}
    </div>
  );
}

Server State vs Client State

Server state (API data, cache) should live in a dedicated layer (React Query, SWR, Apollo) — not in React component state. It has different lifecycles: caching, background refetching, stale-while-revalidate. Mixing server state with UI state in the same useState leads to over-rendering and stale data bugs.

// ❌ Mixing server and client state
function Dashboard() {
  const [data, setData] = useState(null);      // server state
  const [filter, setFilter] = useState('');     // client state
  const [isLoading, setIsLoading] = useState(true); // server state

  useEffect(() => {
    fetch('/api/data').then(r => r.json()).then(d => {
      setData(d);       // triggers re-render
      setIsLoading(false); // triggers ANOTHER re-render (React 17)
    });
  }, []);
}

// ✅ Separate concerns
function Dashboard() {
  const { data, isLoading } = useQuery('dashboard', fetchDashboard);
  // Server state managed by React Query — handles cache, refetch, dedup
  // Component only holds CLIENT state (UI state)
  const [filter, setFilter] = useState('');
}

Context Splitting

Why large contexts cause re-render storms and how to fix them

The Problem: Monolithic Context

// ❌ One context with everything — ANY change re-renders ALL consumers
const AppContext = createContext();

function AppProvider({ children }) {
  const [user, setUser] = useState(null);           // changes rarely
  const [theme, setTheme] = useState('dark');       // changes rarely
  const [searchTerm, setSearchTerm] = useState(''); // changes on EVERY keystroke
  const [notifications, setNotifications] = useState([]); // changes often

  // This object is recreated every render → new reference every time
  const value = { user, setUser, theme, setTheme, searchTerm, setSearchTerm, notifications };

  return <AppContext.Provider value={value}>{children}</AppContext.Provider>;
}

// Every component that reads `useContext(AppContext)` re-renders
// when searchTerm changes — even if they only use `theme`

The Fix: Split Contexts by Update Frequency

// ✅ Separate contexts by change frequency
const UserContext = createContext();       // changes: on login/logout
const ThemeContext = createContext();      // changes: on toggle
const SearchContext = createContext();     // changes: on every keystroke

function UserProvider({ children }) {
  const [user, setUser] = useState(null);
  const value = useMemo(() => ({ user, setUser }), [user]);
  return <UserContext.Provider value={value}>{children}</UserContext.Provider>;
}

function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('dark');
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

function SearchProvider({ children }) {
  const [searchTerm, setSearchTerm] = useState('');
  // NOT memoized — changes on every keystroke anyway
  return (
    <SearchContext.Provider value={{ searchTerm, setSearchTerm }}>
      {children}
    </SearchContext.Provider>
  );
}

// Now: only SearchContext consumers re-render on keystroke
// ThemeContext consumers are unaffected

Selector Pattern with useSyncExternalStore

// Advanced: Context with selector (avoids re-render if selected value unchanged)
function createSelectableContext() {
  const Context = createContext();
  const listeners = new Set();
  let currentState;

  function Provider({ value, children }) {
    currentState = value;
    useEffect(() => {
      listeners.forEach(listener => listener());
    });
    return <Context.Provider value={value}>{children}</Context.Provider>;
  }

  function useSelector(selector) {
    return useSyncExternalStore(
      (callback) => {
        listeners.add(callback);
        return () => listeners.delete(callback);
      },
      () => selector(currentState),
      () => selector(currentState)
    );
  }

  return { Provider, useSelector };
}

// Usage: component only re-renders if selected slice changes
const { Provider, useSelector } = createSelectableContext();
function UserName() {
  const name = useSelector(state => state.user.name);
  // Only re-renders when user.name actually changes
  return <span>{name}</span>;
}

Context + useReducer Pattern

// Split state and dispatch into separate contexts
const StateContext = createContext();
const DispatchContext = createContext();

function AppProvider({ children }) {
  const [state, dispatch] = useReducer(reducer, initialState);

  return (
    <DispatchContext.Provider value={dispatch}>
      <StateContext.Provider value={state}>
        {children}
      </StateContext.Provider>
    </DispatchContext.Provider>
  );
}

// Components that only WRITE (dispatch actions) never re-render on state change
// because `dispatch` is referentially stable across renders
function AddButton() {
  const dispatch = useContext(DispatchContext); // stable reference!
  return <button onClick={() => dispatch({ type: 'ADD' })}>Add</button>;
}

React Context Limitations

Context cannot do selectors natively. If the context value is { a: 1, b: 2 } and you only read a, you still re-render when b changes. The useContextSelector RFC has been open since 2019, but may never ship as originally proposed — React 19's use(Context) combined with the React Compiler's auto-memoization partially addresses the problem (the compiler can skip re-renders when the selected value hasn't changed). Until then, use useSyncExternalStore or an external store for fine-grained subscriptions.

React.memo / useMemo / useCallback

When memoization helps, when it hurts, and rules of thumb

React.memo — Component-Level Memoization

// React.memo: Skip re-render if props haven't changed (shallow compare)
const ExpensiveChart = React.memo(function ExpensiveChart({ data, config }) {
  // Only re-renders if `data` or `config` reference changes
  return <svg>{/* complex rendering */}</svg>;
});

// Custom comparison for deeper control
const Row = React.memo(
  function Row({ item, onSelect }) {
    return <tr onClick={() => onSelect(item.id)}>{item.name}</tr>;
  },
  (prevProps, nextProps) => {
    // Return true to SKIP re-render, false to allow it
    return prevProps.item.id === nextProps.item.id
      && prevProps.item.updatedAt === nextProps.item.updatedAt;
  }
);

When React.memo Helps

Scenario Benefit
Expensive render (complex SVG, large list) High — skips costly work
Parent re-renders frequently, child props stable High — prevents cascade
Component renders same output for same props Medium — saves reconciliation

When React.memo Hurts

Scenario Problem
Props change every render (new objects/functions) Comparison cost + render cost — worse than no memo
Cheap component (renders in <1ms) Overhead of comparison exceeds saved work
Component always receives children (new elements) Children are new objects each render — memo never skips

useMemo — Value Memoization

// useMemo: Memoize COMPUTED VALUES to maintain referential stability
function FilteredList({ items, filter }) {
  // Without useMemo: new array reference every render
  // → If passed to a React.memo child, defeats the memo
  const filtered = useMemo(
    () => items.filter(item => item.category === filter),
    [items, filter]  // only recompute when these change
  );

  // Also for expensive computations
  const statistics = useMemo(
    () => computeExpensiveStats(items), // O(n²) calculation
    [items]
  );

  return <MemoizedTable data={filtered} stats={statistics} />;
}

useCallback — Function Memoization

// useCallback: Memoize FUNCTIONS to maintain referential stability
function TodoList({ todos }) {
  // Without useCallback: new function reference every render
  // → MemoizedTodoItem would re-render despite same logical behavior
  const handleToggle = useCallback((id) => {
    setTodos(prev => prev.map(t => t.id === id ? { ...t, done: !t.done } : t));
  }, []); // empty deps = stable forever (uses updater function)

  const handleDelete = useCallback((id) => {
    setTodos(prev => prev.filter(t => t.id !== id));
  }, []);

  return todos.map(todo => (
    <MemoizedTodoItem
      key={todo.id}
      todo={todo}
      onToggle={handleToggle}
      onDelete={handleDelete}
    />
  ));
}

Rules of Thumb

Apply memoization when:

  • React.memo: Component is expensive AND its parent re-renders frequently with stable props
  • useMemo: Value is passed to a memo’d child, is an expensive computation, or is a dependency of another hook
  • useCallback: Function is passed to a memo’d child or is a dependency of useEffect

Skip memoization when: The component is cheap, props change every render anyway, or you haven’t measured a problem.

Referential Stability

Object identity, useRef containers, and the React Compiler

The Identity Problem

// JavaScript: {} !== {} even with identical content
const a = { color: 'blue' };
const b = { color: 'blue' };
console.log(a === b); // false — different references

// In React: this creates a NEW object every render
function Parent() {
  // ❌ New object reference on every render
  const style = { color: 'blue', fontSize: 14 };
  return <MemoizedChild style={style} />; // memo defeated!
}

// Fix: Extract outside component or useMemo
const STYLE = { color: 'blue', fontSize: 14 }; // ✅ Stable reference

function Parent() {
  return <MemoizedChild style={STYLE} />; // memo works!
}

Common Referential Instability Traps

// ❌ TRAP 1: Inline objects as props
<Chart options={{ animate: true, duration: 300 }} />

// ❌ TRAP 2: Inline arrays
<Select options={['a', 'b', 'c']} />

// ❌ TRAP 3: Inline functions
<Button onClick={() => handleClick(id)} />

// ❌ TRAP 4: Spreading computed objects
<Component {...computeProps()} />

// ❌ TRAP 5: Array.map creating new arrays
<List items={data.map(transform)} />  // new array every render

useRef for Stable Containers

// useRef: Mutable container that persists across renders
// Changing .current does NOT trigger re-render

function useStableCallback(callback) {
  const ref = useRef(callback);
  // Update the ref on every render (latest closure)
  useLayoutEffect(() => {
    ref.current = callback;
  });
  // Return a stable function that reads from ref
  return useCallback((...args) => ref.current(...args), []);
}

// Usage: stable reference, always calls latest version
function SearchInput({ onSearch }) {
  const stableOnSearch = useStableCallback(onSearch);
  // stableOnSearch never changes identity
  // Safe to use in useEffect deps without re-triggering
  useEffect(() => {
    const debounced = debounce(stableOnSearch, 300);
    return () => debounced.cancel();
  }, [stableOnSearch]); // effectively empty — never changes
}

Factory Patterns

// Create stable objects/functions outside the component
const createChartConfig = (type) => ({
  responsive: true,
  animation: { duration: 300 },
  type,
});

// Memoize with a factory
function ChartWrapper({ type, data }) {
  const config = useMemo(() => createChartConfig(type), [type]);
  return <Chart config={config} data={data} />;
}

React Compiler (React Forget) — Auto-Memoization

The React Compiler (formerly “React Forget”) is a build-time tool that automatically inserts memoization. It analyzes component code at compile time, determines which values and functions need stable references, and wraps them automatically. This eliminates the need for manual useMemo and useCallback in most cases.

Status (2024): Shipped in production at Meta (Instagram). Available as babel-plugin-react-compiler (experimental). Not yet stable for general use, but actively being adopted. In interviews, present it as "shipping at Meta, available as an experimental Babel plugin" rather than purely theoretical.

// What you write (with React Compiler):
function TodoList({ todos, filter }) {
  const filtered = todos.filter(t => t.status === filter);
  const handleClick = (id) => selectTodo(id);

  return filtered.map(todo =>
    <TodoItem key={todo.id} todo={todo} onClick={handleClick} />
  );
}

// What the compiler outputs (conceptually):
function TodoList({ todos, filter }) {
  const filtered = useMemo(() => todos.filter(t => t.status === filter), [todos, filter]);
  const handleClick = useCallback((id) => selectTodo(id), []);

  return useMemo(() => filtered.map(todo =>
    <TodoItem key={todo.id} todo={todo} onClick={handleClick} />
  ), [filtered, handleClick]);
}

Automatic Batching

React 18 batching, flushSync, and the render reduction

What Changed in React 18

// React 17: Only batches inside React event handlers
function handleClick() {
  setCount(c => c + 1);  // ─┐
  setFlag(f => !f);      // ─┤ Batched → 1 re-render (React 17 ✓)
  setName('Alice');       // ─┘
}

// React 17: Does NOT batch in async code
setTimeout(() => {
  setCount(c => c + 1);  // → 1 re-render
  setFlag(f => !f);      // → 2nd re-render  (React 17 ✗)
  setName('Alice');       // → 3rd re-render  (React 17 ✗)
}, 1000);

// React 18: Batches EVERYWHERE — events, promises, timeouts, native handlers
setTimeout(() => {
  setCount(c => c + 1);  // ─┐
  setFlag(f => !f);      // ─┤ Batched → 1 re-render (React 18 ✓)
  setName('Alice');       // ─┘
}, 1000);

fetch('/api/data').then(() => {
  setData(result);     // ─┐
  setLoading(false);   // ─┤ Batched → 1 re-render (React 18 ✓)
  setError(null);      // ─┘
});

How Batching Reduces Renders

┌─────────────────────────────────────────────────────────────┐
│ REACT 17 (fetch handler):                                    │
│   setData()  → render → commit                              │
│   setLoading() → render → commit                            │
│   setError()  → render → commit                             │
│   Total: 3 renders, 3 commits                               │
│                                                              │
│ REACT 18 (fetch handler):                                    │
│   setData()  ─┐                                             │
│   setLoading() ─┤→ single render → single commit            │
│   setError()  ─┘                                            │
│   Total: 1 render, 1 commit                                 │
└─────────────────────────────────────────────────────────────┘

Opting Out with flushSync

import { flushSync } from 'react-dom';

function handleClick() {
  // Force immediate render (escape hatch — rarely needed)
  flushSync(() => {
    setCount(c => c + 1);
  });
  // DOM is updated here — can measure layout

  flushSync(() => {
    setFlag(f => !f);
  });
  // DOM updated again
}

// Use case: Need to read DOM measurements between state updates
// (e.g., scroll position after adding an item)
function addMessage(message) {
  flushSync(() => {
    setMessages(prev => [...prev, message]);
  });
  // DOM now contains the new message — safe to scroll
  listRef.current.scrollTop = listRef.current.scrollHeight;
}

flushSync is an escape hatch — it defeats batching and forces synchronous rendering. Use it only when you need DOM measurements between state updates. In most cases, useLayoutEffect or useEffect handles post-render DOM reading without forcing synchronous rendering.

Controlled vs Uncontrolled Components

Performance implications for forms and large inputs

Controlled: React Owns the Value

// Every keystroke → setState → re-render → DOM update
function ControlledForm() {
  const [name, setName] = useState('');
  const [email, setEmail] = useState('');
  const [bio, setBio] = useState('');

  // Typing in name input: 3 components re-render per keystroke
  // (if state is lifted to parent with other consumers)
  return (
    <form>
      <input value={name} onChange={e => setName(e.target.value)} />
      <input value={email} onChange={e => setEmail(e.target.value)} />
      <textarea value={bio} onChange={e => setBio(e.target.value)} />
    </form>
  );
}

Uncontrolled: DOM Owns the Value

// No re-renders until submit — DOM manages input state
function UncontrolledForm() {
  const nameRef = useRef();
  const emailRef = useRef();
  const bioRef = useRef();

  const handleSubmit = (e) => {
    e.preventDefault();
    // Read values only on submit — zero re-renders during typing
    const data = {
      name: nameRef.current.value,
      email: emailRef.current.value,
      bio: bioRef.current.value,
    };
    submitForm(data);
  };

  return (
    <form onSubmit={handleSubmit}>
      <input ref={nameRef} defaultValue="" />
      <input ref={emailRef} defaultValue="" />
      <textarea ref={bioRef} defaultValue="" />
      <button type="submit">Submit</button>
    </form>
  );
}

Hybrid Pattern: React Hook Form

// React Hook Form: Uncontrolled by default, controlled when needed
import { useForm } from 'react-hook-form';

function HybridForm() {
  const { register, handleSubmit, watch, formState: { errors } } = useForm();

  // Uncontrolled: register() uses refs — no re-renders on typing
  // Controlled: watch() subscribes to specific fields when needed
  const password = watch('password'); // only this triggers re-render

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register('email', { required: true })} />
      <input {...register('password', { minLength: 8 })} type="password" />
      <input
        {...register('confirmPassword', {
          validate: value => value === password || 'Passwords must match'
        })}
        type="password"
      />
      {errors.confirmPassword && <span>{errors.confirmPassword.message}</span>}
      <button type="submit">Submit</button>
    </form>
  );
}

// Other 50 fields in the form → zero re-renders during typing

Signals, Stores & Subscriptions

Zustand, Jotai, Valtio, and how subscription models solve context re-renders

Why External Stores Exist

React Context re-renders all consumers when the value changes. External stores use a subscription model: components subscribe to specific slices of state and only re-render when their selected slice changes. This gives you the fine-grained reactivity that Context cannot provide natively.

Zustand: Subscribe to Slices

import { create } from 'zustand';

// Create store — no Provider needed
const useDashboardStore = create((set, get) => ({
  user: null,
  searchTerm: '',
  notifications: [],
  filters: { status: 'all', priority: 'all' },

  setSearchTerm: (term) => set({ searchTerm: term }),
  addNotification: (n) => set(state => ({
    notifications: [...state.notifications, n]
  })),
  setFilter: (key, value) => set(state => ({
    filters: { ...state.filters, [key]: value }
  })),
}));

// Component subscribes to ONE slice — only re-renders when that slice changes
function SearchBar() {
  const searchTerm = useDashboardStore(state => state.searchTerm);
  const setSearchTerm = useDashboardStore(state => state.setSearchTerm);
  // Does NOT re-render when notifications or filters change
  return <input value={searchTerm} onChange={e => setSearchTerm(e.target.value)} />;
}

function NotificationBadge() {
  const count = useDashboardStore(state => state.notifications.length);
  // Only re-renders when notification count changes
  return <span className="badge">{count}</span>;
}

// Shallow comparison for object slices
import { shallow } from 'zustand/shallow';
function Filters() {
  const filters = useDashboardStore(state => state.filters, shallow);
  // Uses shallow equality — re-renders only when a filter value changes
  return <FilterPanel filters={filters} />;
}

Jotai: Atomic State (Bottom-Up)

import { atom, useAtom, useAtomValue, useSetAtom } from 'jotai';

// Atoms: independent pieces of state (like useState but shared)
const searchAtom = atom('');
const filtersAtom = atom({ status: 'all', priority: 'all' });
const userAtom = atom(null);

// Derived atoms: computed values that auto-track dependencies
const filteredItemsAtom = atom((get) => {
  const search = get(searchAtom);
  const filters = get(filtersAtom);
  const items = get(itemsAtom);
  return items.filter(item =>
    item.name.includes(search) && item.status === filters.status
  );
});

// Components subscribe to individual atoms
function SearchBar() {
  const [search, setSearch] = useAtom(searchAtom);
  return <input value={search} onChange={e => setSearch(e.target.value)} />;
}

// Read-only subscription (no setter)
function ItemCount() {
  const filtered = useAtomValue(filteredItemsAtom);
  return <span>{filtered.length} items</span>;
}

// Write-only subscription (no re-render on value change)
function ClearButton() {
  const setSearch = useSetAtom(searchAtom);
  return <button onClick={() => setSearch('')}>Clear</button>;
}

Valtio: Proxy-Based Reactivity

import { proxy, useSnapshot } from 'valtio';

// Mutable proxy — just mutate it like regular JavaScript
const state = proxy({
  user: null,
  searchTerm: '',
  notifications: [],
  filters: { status: 'all', priority: 'all' },
});

// Mutations: direct assignment (no reducers, no immutability)
function updateSearch(term) {
  state.searchTerm = term; // Valtio tracks which properties changed
}

function addNotification(n) {
  state.notifications.push(n); // Even push() is tracked
}

// useSnapshot: creates a read-only snapshot for rendering
// Only re-renders if accessed properties change
function SearchBar() {
  const snap = useSnapshot(state);
  // Valtio tracks that this component reads `searchTerm`
  // → only re-renders when searchTerm changes
  return <input value={snap.searchTerm} onChange={e => updateSearch(e.target.value)} />;
}

React Compiler

Automatic memoization, compile-time analysis, and its limitations

What React Compiler Does

The React Compiler (formerly “React Forget”) is a build-time tool that analyzes your component code and automatically inserts memoization where beneficial. It determines which values, functions, and JSX elements need stable references and wraps them in the equivalent of useMemo/useCallback without you writing them.

How It Works

// The compiler performs static analysis at build time:
// 1. Parses each component function
// 2. Builds a dependency graph of all variables
// 3. Identifies which expressions depend on which inputs
// 4. Groups expressions into "reactive blocks" with shared dependencies
// 5. Wraps each block in memoization with computed dependency arrays

// INPUT (what you write):
function ProductCard({ product, onAddToCart }) {
  const formattedPrice = formatCurrency(product.price);
  const handleClick = () => onAddToCart(product.id);
  const cardStyle = { border: product.inStock ? '1px solid green' : '1px solid red' };

  return (
    <div style={cardStyle}>
      <h3>{product.name}</h3>
      <p>{formattedPrice}</p>
      <button onClick={handleClick}>Add to Cart</button>
    </div>
  );
}

// OUTPUT (what the compiler generates — conceptually):
function ProductCard({ product, onAddToCart }) {
  const formattedPrice = useMemo(() => formatCurrency(product.price), [product.price]);
  const handleClick = useCallback(() => onAddToCart(product.id), [onAddToCart, product.id]);
  const cardStyle = useMemo(
    () => ({ border: product.inStock ? '1px solid green' : '1px solid red' }),
    [product.inStock]
  );

  return useMemo(() => (
    <div style={cardStyle}>
      <h3>{product.name}</h3>
      <p>{formattedPrice}</p>
      <button onClick={handleClick}>Add to Cart</button>
    </div>
  ), [cardStyle, product.name, formattedPrice, handleClick]);
}

What It Eliminates

Manual Pattern Compiler Handles?
useMemo for computed values ✅ Automatic
useCallback for event handlers ✅ Automatic
React.memo wrapper ✅ Automatic (via JSX memoization)
Extracting constants outside component ✅ Unnecessary
State architecture (colocation) ❌ Cannot fix
Context splitting ❌ Cannot fix
Subscription model selection ❌ Cannot fix

What the Compiler Can’t Fix

Architecture problems persist. If your state lives too high in the tree, the compiler will memoize efficiently but the parent still re-renders and still calls all children. If your context provides a monolithic value, all consumers still re-render. The compiler optimizes within a render — it doesn’t eliminate unnecessary renders caused by bad state topology.

Component Composition to Prevent Re-Renders

// Pattern: Move the stateful part into a wrapper, pass expensive content as children
// The children prop is created by the grandparent → stable reference

// ❌ BEFORE: ScrollTracker re-renders all children on scroll
function Page() {
  const [scrollY, setScrollY] = useState(0);
  useEffect(() => {
    const handler = () => setScrollY(window.scrollY);
    window.addEventListener('scroll', handler);
    return () => window.removeEventListener('scroll', handler);
  }, []);

  return (
    <div>
      <ScrollIndicator y={scrollY} />
      <ExpensiveContent />  {/* re-renders 60x/sec during scroll! */}
    </div>
  );
}

// ✅ AFTER: Composition isolates the stateful part
function Page() {
  return (
    <ScrollTracker>
      <ExpensiveContent />  {/* never re-renders during scroll */}
    </ScrollTracker>
  );
}

function ScrollTracker({ children }) {
  const [scrollY, setScrollY] = useState(0);
  useEffect(() => {
    const handler = () => setScrollY(window.scrollY);
    window.addEventListener('scroll', handler);
    return () => window.removeEventListener('scroll', handler);
  }, []);

  return (
    <div>
      <ScrollIndicator y={scrollY} />
      {children}  {/* children is a stable reference — skipped! */}
    </div>
  );
}

Windowing / Virtualization for Long Lists

// Only render visible items — not all 10,000 rows
import { useVirtualizer } from '@tanstack/react-virtual';

function VirtualizedTable({ items }) {
  const parentRef = useRef(null);

  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 40, // row height in px
    overscan: 5, // render 5 extra rows above/below viewport
  });

  return (
    <div ref={parentRef} style={{ height: '600px', overflow: 'auto' }}>
      <div style={{ height: `${virtualizer.getTotalSize()}px`, position: 'relative' }}>
        {virtualizer.getVirtualItems().map(virtualRow => (
          <div
            key={virtualRow.key}
            style={{
              position: 'absolute',
              top: 0,
              transform: `translateY(${virtualRow.start}px)`,
              height: `${virtualRow.size}px`,
              width: '100%',
            }}
          >
            <Row item={items[virtualRow.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}
// 10,000 items → only ~20 Row components in DOM at any time

Debouncing State Updates

// Debounce expensive downstream effects, not the input itself
function SearchWithDebounce() {
  const [inputValue, setInputValue] = useState('');       // updates instantly
  const [debouncedValue, setDebouncedValue] = useState(''); // updates after pause

  useEffect(() => {
    const timer = setTimeout(() => setDebouncedValue(inputValue), 300);
    return () => clearTimeout(timer);
  }, [inputValue]);

  return (
    <div>
      <input value={inputValue} onChange={e => setInputValue(e.target.value)} />
      {/* ExpensiveResults only re-renders every 300ms, not per keystroke */}
      <ExpensiveResults query={debouncedValue} />
    </div>
  );
}

// React 18+: useDeferredValue (built-in, concurrent-aware)
function SearchWithDeferred() {
  const [inputValue, setInputValue] = useState('');
  const deferredValue = useDeferredValue(inputValue);
  // React renders the input update at high priority
  // Then renders ExpensiveResults at lower priority (interruptible)
  return (
    <div>
      <input value={inputValue} onChange={e => setInputValue(e.target.value)} />
      <ExpensiveResults query={deferredValue} />
    </div>
  );
}

// ❌ "Performance optimization" that adds overhead with no benefit
const Button = React.memo(({ onClick, label }) => (
  <button onClick={onClick}>{label}</button>
));
// This component renders in <0.01ms
// The shallow prop comparison costs MORE than the render itself
// Net effect: slower, not faster

// ❌ Even worse: memo with inline functions (memo is useless)
function Parent() {
  return <MemoizedChild onClick={() => doSomething()} />;
  // New function every render → memo comparison always fails
  // You pay comparison cost AND re-render cost
}

// ✅ Only memo expensive components with stable props
const ExpensiveVisualization = React.memo(({ data, config }) => {
  // Complex SVG rendering, 5ms+ render time
  return <svg>{renderComplexChart(data, config)}</svg>;
});

Mistake 2: Inline Object/Function Props

// ❌ New object reference every render — defeats all downstream memos
function Dashboard() {
  return (
    <Chart
      options={{ animate: true, grid: true }}  {/* new object every render */}
      onHover={(point) => showTooltip(point)}  {/* new function every render */}

Mistake 4: Premature Optimization Before Profiling

// ❌ "Let me optimize first" — without knowing WHERE the problem is
function App() {
  // Adding useMemo/useCallback to every value "just in case"
  const config = useMemo(() => ({ theme: 'dark' }), []);
  const handleClick = useCallback(() => {}, []);
  const items = useMemo(() => [1, 2, 3], []);
  // None of these might be bottlenecks. You've added complexity for nothing.

  return <SimpleComponent config={config} onClick={handleClick} items={items} />;
}

// ✅ Profile first, optimize the measured bottleneck
// 1. Does it feel slow? No → don't optimize
// 2. Profile with React DevTools → identify slowest components
// 3. Apply targeted fix to THOSE components only
// 4. Re-profile to verify improvement

Mistake 5: Confusing Re-Render with DOM Update

// MISCONCEPTION: "My component re-rendered 50 times, it must be slow!"
// REALITY: A re-render that produces identical JSX → zero DOM mutations

function DisplayName({ name }) {
  // If this re-renders 50 times with the same `name` value:
  // → React calls this function 50 times (cheap: microseconds)
  // → React diffs old vs new virtual DOM (cheap: identical)
  // → React commits to DOM: ZERO changes (nothing happens)
  // Net cost: negligible unless the render function itself is expensive
  return <span>{name}</span>;
}

// The REAL cost hierarchy:
// 1. DOM mutations (layout, paint, composite) — EXPENSIVE
// 2. Component renders with heavy computation — MODERATE
// 3. Component renders returning same JSX — CHEAP
// 4. Component skipped by memo — FREE

// Optimization effort should follow this hierarchy:
// Reduce DOM mutations > Reduce expensive renders > Skip trivial renders

The key insight: React’s rendering is a two-phase process. The “render” phase (calling component functions, diffing) is cheap. The “commit” phase (DOM mutations) is expensive. Optimize the commit phase first by ensuring fewer DOM changes, then reduce unnecessary renders only where profiling shows actual cost.

React Compiler Reliance

Should you rely on the React Compiler? Use it as a safety net, not a crutch. The compiler handles referential stability automatically, but cannot fix architectural problems (state too high, monolithic contexts). Write clean component boundaries and proper state topology first — the compiler then makes it faster without effort.

Follow-Up Questions

Seven deep-dive questions with strong answers

Q1: “How do you determine if a re-render is actually a problem?”

Strong answer: A re-render is only a problem if it causes a perceivable performance issue. I use three criteria: (1) The render takes >16ms (drops a frame at 60fps), (2) The interaction feels sluggish to the user, (3) The Profiler shows expensive work being repeated unnecessarily. A component re-rendering 100 times with 0.01ms per render = 1ms total = irrelevant. I never optimize without measuring first.

Q2: “When would you choose Zustand over React Context?”

Strong answer: When the state updates frequently (more than a few times per second) AND multiple components across the tree consume different slices of it. Context forces all consumers to re-render on any change. Zustand lets each component subscribe to only its relevant slice via selectors. Additional triggers: need for middleware (persist, devtools), need to access state outside React (in event handlers, WebSocket callbacks), or when the Provider wrapper tree is getting deep.

Q3: “Can you explain why children-as-props prevents re-renders?”

Strong answer: When a component re-renders, it re-creates all JSX in its return statement — meaning child elements get new references and React must re-render them. But if children are received via props, they were created by the grandparent. Since the grandparent didn’t re-render, those element references are identical. React sees the same element object and skips rendering that subtree. It’s essentially free memoization through composition.

Q4: “How does React 18’s concurrent rendering affect re-render optimization?”

Strong answer: Concurrent rendering doesn’t reduce the number of re-renders, but it changes when they happen. With useTransition and useDeferredValue, low-priority renders can be interrupted by high-priority ones (like user input). This means a heavy re-render doesn’t block the main thread. The UI stays responsive even during expensive updates. It’s complementary to render optimization — you still want fewer renders, but concurrent mode ensures unavoidable renders don’t block interactions.

Q5: “What’s your approach to state architecture in a new large application?”

Strong answer: I categorize state into four buckets: (1) Server state → React Query/SWR (handles cache, refetch, dedup), (2) Global UI state → Zustand or minimal context (theme, auth, locale — changes rarely), (3) Feature state → colocated in feature components or feature-level stores, (4) Ephemeral UI state → local useState (hover, focus, animation frame). I start with state colocated as low as possible and only lift/extract when two components genuinely need to share. I never create global state “just in case.”

Q6: “How would you handle real-time data (WebSocket) without causing render storms?”

Strong answer: WebSocket messages can arrive 10-100x per second. I’d never pipe them directly into React state. Instead: (1) Buffer messages outside React in a ref or external store, (2) Batch updates on a requestAnimationFrame or fixed interval (e.g., 100ms), (3) Use Zustand/Jotai where components subscribe only to their relevant data slice, (4) For lists, use virtualization so only visible rows render, (5) For charts, update via imperative DOM manipulation (chart library API) rather than React state. The key is to decouple the data arrival rate from the render rate.

Q7: “What will the React Compiler NOT fix, and why does architecture still matter?”

Strong answer: The compiler auto-memoizes values, functions, and JSX elements — eliminating referential instability. But it cannot: (1) Move state to a better location (colocation), (2) Split a monolithic context into multiple contexts, (3) Choose between Context and an external store, (4) Implement virtualization for long lists, (5) Debounce or throttle state updates. These are architectural decisions that determine whether a render happens at all. The compiler only optimizes what happens within a render. You still need proper state topology.

Q8: “How do useFormStatus and useActionState (React 19) reduce form re-renders?”

Strong answer: useFormStatus reads submission state (pending, data, method) without re-rendering the entire form — only the component calling it re-renders. useActionState (renamed from useFormState) manages form state with a reducer-like pattern tied to Server Actions, handling optimistic updates and error states. Together they enable forms where the submit button shows "Submitting..." without re-rendering every input field — a pattern that previously required lifting state or using a context.

Cross-reference: For the internal lane mechanics behind useDeferredValue and startTransition (why they create concurrent renders at different priorities), see Ch16: Lanes, Priority & Scheduling. This chapter covers practical usage; Ch16 covers the scheduling internals.

 * - The function does expensive work (computation, allocation)
 * - The output causes many DOM mutations
 * - It cascades to hundreds of children
 *

 * React compares by reference (===). Two {color:'blue'} objects are different.
 * Stability of references determines whether memo/effect/selector triggers.

What NOT to Say

  • ❌ “I’d wrap everything in React.memo.” — Shows you don’t understand the cost or know better alternatives.
  • ❌ “Props changing causes re-renders.” — Wrong. Parent re-rendering causes the child to re-render; props are just data passed during that re-render.
  • ❌ “useMemo improves performance everywhere.” — It has overhead. Only useful when the computation is expensive or the value must be referentially stable.
  • ❌ “Just use Redux for everything.” — Ignores simpler solutions and modern alternatives. Shows inflexibility.
  • ❌ “Re-renders are always bad.” — They’re React’s mechanism for updating UI. Fast re-renders with no DOM change are essentially free.

One-Sentence Summary

The best re-render optimization is the one you don’t need — design your state topology so unnecessary re-renders never happen in the first place, then apply targeted memoization only where profiling shows actual cost.

Chapter 6: Module Systems & Bundling

"Explain the difference between CommonJS and ES Modules at the engine level. How does tree-shaking actually work?"
Key Takeaway: CommonJS uses synchronous require() with dynamic resolution and value copies. ES Modules use static imports with live bindings, enabling tree-shaking through compile-time dead code elimination. Understanding the module graph, circular dependency handling, and bundler internals (chunk splitting, scope hoisting) is essential for optimizing production builds.

Interviewer's Intent

What the interviewer is really evaluating

This question probes whether you understand modules at the engine level, not just the syntax. Interviewers want to see:

  • Deep understanding of CJS vs ESM semantics — not just "import vs require" but how each system resolves, caches, and binds values
  • Why tree-shaking requires static analysis — understanding that it's a compile-time optimization impossible with dynamic module systems
  • Production awareness — how bundler choices affect load time, caching, and debugging
  • Debugging capability — can you diagnose why a library isn't being tree-shaken, or why a circular dependency causes undefined values?
  • Architecture decisions — when to split chunks, how to structure exports for optimal bundling, micro-frontend trade-offs

Red flags interviewers watch for: Saying "they're basically the same thing," not knowing about live bindings, inability to explain why lodash imports bloat bundles but lodash-es doesn't.

60-Second Answer

Concise interview response

Use this as your opening, then dive deeper based on follow-ups.

"CommonJS and ES Modules differ fundamentally in three ways:

1. Resolution timing: CJS resolves dynamically at runtime — require() is a function call that can appear anywhere, even inside conditionals. ESM resolves statically at parse time — imports must be top-level declarations, enabling the engine to build the full dependency graph before execution.

2. Value semantics: CJS creates copies of exported values (the module.exports object is evaluated once and cached). ESM creates live bindings — importing modules get a live reference to the exporting module's variable, so mutations are visible across module boundaries.

3. Loading model: CJS is synchronous (blocks until the file is read and executed). ESM is asynchronous with three distinct phases: parsing (building the module graph), instantiation (creating bindings in memory), and evaluation (executing code to fill those bindings).

Tree-shaking works because ESM's static structure lets bundlers perform dead code elimination at build time. Since all imports/exports are known before execution, the bundler can trace which exports are actually consumed and eliminate unused ones. CJS can't be tree-shaken because require() calls could resolve to any string computed at runtime."

CommonJS require() — Synchronous, Dynamic

Module wrapper, require.cache, circular deps, dynamic requires

The Module Wrapper Function

Every CJS module is wrapped by Node.js before execution:

// What you write:
const fs = require('fs');
module.exports = { readFile: fs.readFile };

// What Node.js actually executes:
(function(exports, require, module, __filename, __dirname) {
    const fs = require('fs');
    module.exports = { readFile: fs.readFile };
})(module.exports, require, module, '/path/to/file.js', '/path/to');

Key insight: This wrapper is why exports, require, module, __filename, and __dirname are available without declaration. They're function parameters, not globals.

require.cache — Module Singleton Pattern

// First require: executes module, caches result
const a = require('./counter'); // Executes counter.js, stores in cache

// Second require: returns cached module.exports
const b = require('./counter'); // Returns same object from cache

console.log(a === b); // true — same reference

// Inspect the cache
console.log(require.cache[require.resolve('./counter')]);
// { id, exports, filename, loaded, children, paths }

// Force re-evaluation (dangerous in production)
delete require.cache[require.resolve('./counter')];
const c = require('./counter'); // Re-executes module
console.log(a === c); // false — new object

Circular Dependency Handling in CJS

// a.js
console.log('a.js: start');
exports.done = false;
const b = require('./b.js'); // Triggers b.js execution
console.log('a.js: b.done =', b.done);
exports.done = true;
console.log('a.js: end');

// b.js
console.log('b.js: start');
exports.done = false;
const a = require('./a.js'); // Gets PARTIAL exports (done = false)
console.log('b.js: a.done =', a.done); // false!
exports.done = true;
console.log('b.js: end');

// Output:
// a.js: start
// b.js: start
// b.js: a.done = false  <-- partial export!
// b.js: end
// a.js: b.done = true
// a.js: end

Danger: In circular dependencies, CJS returns a partially constructed module.exports object. This is a common source of "undefined" bugs in large codebases.

ES Modules — Static, Async, Live Bindings

Three phases, live bindings vs copies, TDZ in circular imports, import.meta

The Three Phases of ESM Loading

│              ESM Loading: Three Distinct Phases               │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Phase 1: PARSING (Construction)                             │
│  ┌───────────────────────────────────────────┐               │
│  │ • Fetch module source                      │               │

│                    ▼                                          │

│                    ▼                                          │

│  ┌───────────────────────────────────────────┐               │
│  │ • Execute module code top-to-bottom        │               │
│  │ • Fill in exported values                  │               │
│  │ • Post-order DFS (dependencies first)      │               │
│  │ • Each module evaluated exactly once       │               │
│  │ • Result: Fully initialized modules        │               │
│  └───────────────────────────────────────────┘               │

Live Bindings vs Value Copies

// counter.mjs (ES Module)
export let count = 0;
export function increment() {
    count++;
}

// main.mjs
import { count, increment } from './counter.mjs';

console.log(count); // 0
increment();
console.log(count); // 1 — LIVE BINDING! We see the updated value

// Compare with CJS equivalent:
// counter.cjs
let count = 0;
module.exports = { count, increment() { count++; } };

// main.cjs
const { count, increment } = require('./counter.cjs');
console.log(count); // 0
increment();
console.log(count); // 0 — COPY! Still the original value

Under the hood: ESM live bindings work because imports are indirect references to a memory location owned by the exporting module. When the export changes, all importers see the new value immediately — it's the same memory slot.

TDZ (Temporal Dead Zone) in Circular ESM Imports

// a.mjs
import { b } from './b.mjs';
console.log('a.mjs: b =', b); // Works: b is initialized by now

export const a = 'value-a';

// b.mjs
import { a } from './a.mjs';
console.log('b.mjs: a =', a); // ReferenceError! TDZ!
// 'a' binding exists but hasn't been initialized yet
// because a.mjs hasn't been evaluated when b.mjs runs

export const b = 'value-b';

Critical difference from CJS: CJS gives you a partial object (undefined values). ESM throws a ReferenceError because the binding exists but is in the Temporal Dead Zone — it's been allocated in Phase 2 but not yet assigned in Phase 3.

Interview tip: Mention that TypeScript's moduleResolution: "bundler" (TS 5.0+) aligns with how modern bundlers resolve modules — supporting exports field, extensionless imports, and conditional exports without requiring file extensions. It's now the recommended default for application code (libraries still need "node16" for compatibility).

Node.js ESM: Setting "type": "module" in package.json makes all .js files in that package ESM by default. Files that need CJS must use .cjs extension. Without this field, Node defaults to CJS. This is a common interview gotcha — many candidates struggle with the .mjs/.cjs extension dance and top-level await requirements.

Circular Dependencies Handling

CJS partial objects, ESM live binding resolution, practical examples

CJS: Partial Object Exposure

// models/user.js
const Post = require('./post');
class User {
    getPosts() { return Post.findByUser(this.id); }
}
module.exports = User;

// models/post.js
const User = require('./user'); // Gets PARTIAL User (possibly {})
class Post {
    getAuthor() { return User.findById(this.authorId); }
    // User might be {} here if user.js hasn't finished!
    static findByUser(id) { /* ... */ }
}
module.exports = Post;

// FIX: Lazy require inside methods
class Post {
    getAuthor() {
        const User = require('./user'); // Resolved at call time
        return User.findById(this.authorId);
    }
}

ESM: Live Binding Resolution

// evenOdd.mjs — circular deps that WORK in ESM
// even.mjs
import { odd } from './odd.mjs';
export function even(n) {
    if (n === 0) return true;
    return odd(n - 1); // Works! odd is a live binding to a function
}

// odd.mjs
import { even } from './even.mjs';
export function odd(n) {
    if (n === 0) return false;
    return even(n - 1); // Works! even is a live binding
}

// WHY this works: Function declarations are hoisted.
// By the time either function is CALLED, both are initialized.
// The bindings are wired up in Phase 2 (instantiation),
// and functions are hoisted during Phase 3 (evaluation).

// BUT this would FAIL:
// even.mjs
import { oddValue } from './odd.mjs';
export const evenValue = oddValue + 1; // ReferenceError!
// oddValue is in TDZ when even.mjs evaluates

Best practice: Avoid circular dependencies by extracting shared logic into a third module. If unavoidable, use function declarations (hoisted) rather than const arrow functions (TDZ-prone) for cross-module references.

Tree-Shaking Mechanics

Static analysis, why CJS can't be tree-shaken, DCE, AST-level analysis

Static Analysis Requirement

// ESM: Statically analyzable — bundler knows at compile time
import { map, filter } from 'lodash-es';
// Bundler can see: only map and filter are used
// Everything else in lodash-es can be eliminated

// CJS: NOT statically analyzable
const _ = require('lodash');
// What properties of _ are used? Can't know without execution
// Must include entire lodash library

Why CJS Can't Be Tree-Shaken

// Problem 1: Dynamic property access
const utils = require('./utils');
const method = getMethodName(); // Runtime value
utils[method](); // Which export is used? Unknown!

// Problem 2: Conditional requires
if (Math.random() > 0.5) {
    module.exports = require('./a');
} else {
    module.exports = require('./b');
}

// Problem 3: Mutating exports
const mod = require('./mod');
mod.newProp = 'added at runtime';
module.exports = mod; // Export object is mutable

ESM Static Structure Enables DCE

// utils.js — library code
export function used() { return 'I am used'; }
export function unused() { return 'I am dead code'; }
export const CONSTANT = 42;

// app.js — consumer
import { used, CONSTANT } from './utils.js';
console.log(used(), CONSTANT);

// After tree-shaking (conceptual output):
function used() { return 'I am used'; }
const CONSTANT = 42;
console.log(used(), CONSTANT);
// unused() is completely eliminated from the bundle

How Terser/esbuild Eliminate Dead Code (AST-Level)

// Step 1: Bundler marks exports as used/unused
// Module graph analysis:
//   app.js imports { used, CONSTANT } from utils.js
//   → used: USED, unused: UNUSED, CONSTANT: USED

// Step 2: Unused exports are not included in bundle
// The bundler simply doesn't emit code for 'unused'

// Step 3: Terser performs additional DCE on the result
// Before Terser:
function used() { return 'I am used'; }
const CONSTANT = 42;
const deadLocal = 'never referenced';
if (false) { console.log('unreachable'); }

// After Terser:
function used(){return'I am used'}
const CONSTANT=42;
// deadLocal removed (unreferenced)
// if(false) block removed (unreachable)

Key distinction: Tree-shaking (module-level unused export removal) and Dead Code Elimination (statement-level unreachable code removal) are often conflated but are different stages in the pipeline. Tree-shaking is done by the bundler; DCE is done by the minifier.

Side Effects & sideEffects Field

What constitutes a side effect, sideEffects field, CSS imports, module-level IIFEs

What Constitutes a Side Effect?

// SIDE EFFECTS — code that affects state beyond the module
import './polyfill.js';       // Modifies globals (Array.prototype)
import './styles.css';         // Inserts CSS into DOM
import './register-components'; // Registers with global registry

// Inside a module, side effects include:
export const x = 1;

// Side effect: modifies global
window.MY_LIB_VERSION = '1.0.0';

// Side effect: DOM manipulation
document.title = 'App Loaded';

// Side effect: network request
fetch('/api/analytics', { method: 'POST', body: '...' });

// NOT a side effect (pure):
export function add(a, b) { return a + b; }
export const PI = 3.14159;

package.json sideEffects Field

// package.json
{
    "name": "my-ui-library",
    "sideEffects": false
    // Tells bundler: "Every module in this package is pure.
    // If you don't use an export, you can safely remove
    // the entire module."
}

// With specific side-effectful files:
{
    "sideEffects": [
        "**/*.css",
        "./src/polyfills.js",
        "./src/register.js"
    ]
}

// What happens WITHOUT sideEffects: false
import { Button } from 'my-ui-library';
// Bundler must include ALL modules because any might have side effects

// What happens WITH sideEffects: false
import { Button } from 'my-ui-library';
// Bundler only includes Button and its dependencies

Why CSS Imports Need sideEffects

// components/Button.js
import './Button.css'; // This IS a side effect!
// The CSS file modifies global state (adds styles to document)
// If sideEffects: false and Button isn't imported,
// the CSS would be eliminated too — but what if other
// components depend on those styles?

// Solution in package.json:
{
    "sideEffects": ["**/*.css", "**/*.scss"]
}

// Or use CSS Modules (not side-effectful):
import styles from './Button.module.css';
// This is a VALUE import — tree-shakeable

Module-Level IIFE Problem

// This pattern DEFEATS tree-shaking:
export const myLib = (() => {
    // IIFE — bundler can't prove this is side-effect-free
    const internal = computeSomething();
    return {
        method1() { /* ... */ },
        method2() { /* ... */ }
    };
})();

// Even if you only use myLib.method1, the entire IIFE
// must be kept because:
// 1. computeSomething() might have side effects
// 2. The IIFE itself might modify global state

// Fix: Use pure annotations
export const myLib = /*#__PURE__*/ (() => {
    const internal = computeSomething();
    return { method1() {}, method2() {} };
})();
// /*#__PURE__*/ tells Terser: "this call has no side effects,
// safe to remove if result is unused"

Interview insight: The /*#__PURE__*/ annotation is how libraries like React mark createElement calls as side-effect-free, enabling tree-shaking of unused components.

// With retry logic for flaky networks
function lazyWithRetry(importFn, retries = 3) {
    return React.lazy(async () => {
        for (let i = 0; i < retries; i++) {
            try {
                return await importFn();
            } catch (err) {
                if (i === retries - 1) throw err;
                await new Promise(r => setTimeout(r, 1000 * (i + 1)));
            }
        }
    });
}

Error Boundaries for Chunk Failures

// Chunk load failures happen! (deploy during user session)
class ChunkErrorBoundary extends React.Component {
    state = { hasError: false, chunkError: false };

    static getDerivedStateFromError(error) {
        // Detect chunk load failure specifically
        const isChunkError = (
            error.name === 'ChunkLoadError' ||
            error.message?.includes('Loading chunk') ||
            error.message?.includes('Failed to fetch')
        );
        return { hasError: true, chunkError: isChunkError };
    }

    handleRetry = () => {
        if (this.state.chunkError) {
            // Force reload to get new chunk manifest
            window.location.reload();
        }
        this.setState({ hasError: false, chunkError: false });
    };

    render() {
        if (this.state.hasError) {
            return (
                <div class="error-fallback">
                    <p>{this.state.chunkError
                        ? 'A new version is available.'
                        : 'Something went wrong.'
                    }</p>
                    <button onClick={this.handleRetry}>
                        {this.state.chunkError ? 'Refresh' : 'Retry'}
                    </button>
                </div>
            );
        }
        return this.props.children;
    }
}

Production reality: When you deploy a new version, old chunk filenames (with content hashes) are deleted from the CDN. Users with stale HTML will try to load non-existent chunks. Always implement chunk error recovery.

// Webpack's core architecture:
// 1. Entry → builds dependency graph via require/import statements
// 2. Loaders → transform files (babel-loader, css-loader, etc.)

// Simplified Webpack compilation flow:
class Compiler {
    run() {
        this.hooks.beforeCompile.call();
        const compilation = this.newCompilation();

        // Build module graph
        for (const entry of this.entries) {
            this.addModuleTree(entry); // Recursively resolve deps
        }

        // Seal: optimize, split chunks, assign IDs
        compilation.seal();

        // Emit: write files to output directory
        this.emitAssets(compilation);
    }
}

Custom Tree-Shaking Analyzer

// Simple tree-shaking analyzer using AST parsing
import { parse } from '@babel/parser';
import traverse from '@babel/traverse';
import fs from 'fs';
import path from 'path';

class TreeShakeAnalyzer {
    constructor(entryPoint) {
        this.entryPoint = entryPoint;
        this.moduleGraph = new Map(); // file → { exports, imports }
        this.usedExports = new Map(); // file → Set of used export names
    }

    analyze() {
        this.buildGraph(this.entryPoint);
        this.markUsedExports(this.entryPoint);
        return this.getReport();
    }

    buildGraph(filePath) {
        if (this.moduleGraph.has(filePath)) return;

        const code = fs.readFileSync(filePath, 'utf-8');
        const ast = parse(code, {
            sourceType: 'module',
            plugins: ['typescript', 'jsx'],
        });

        const moduleInfo = { exports: new Set(), imports: [] };

        traverse(ast, {
            ExportNamedDeclaration(nodePath) {
                if (nodePath.node.declaration) {
                    const decl = nodePath.node.declaration;
                    if (decl.id) moduleInfo.exports.add(decl.id.name);
                    if (decl.declarations) {
                        decl.declarations.forEach(d =>
                            moduleInfo.exports.add(d.id.name)
                        );
                    }
                }
            },
            ExportDefaultDeclaration() {
                moduleInfo.exports.add('default');
            },
            ImportDeclaration(nodePath) {
                const source = nodePath.node.source.value;
                const specifiers = nodePath.node.specifiers.map(s => ({
                    imported: s.imported?.name || 'default',
                    local: s.local.name,
                }));
                moduleInfo.imports.push({ source, specifiers });
            },
        });

        this.moduleGraph.set(filePath, moduleInfo);

        // Recursively build graph for dependencies
        for (const imp of moduleInfo.imports) {
            const resolvedPath = this.resolve(imp.source, filePath);
            if (resolvedPath) this.buildGraph(resolvedPath);
        }
    }

    markUsedExports(filePath) {
        const info = this.moduleGraph.get(filePath);
        if (!info) return;

        for (const imp of info.imports) {
            const resolvedPath = this.resolve(imp.source, filePath);
            if (!resolvedPath) continue;

            if (!this.usedExports.has(resolvedPath)) {
                this.usedExports.set(resolvedPath, new Set());
            }

            for (const spec of imp.specifiers) {
                this.usedExports.get(resolvedPath).add(spec.imported);
            }

            this.markUsedExports(resolvedPath);
        }
    }

    getReport() {
        const report = [];
        for (const [file, info] of this.moduleGraph) {
            const used = this.usedExports.get(file) || new Set();
            const unused = [...info.exports].filter(e => !used.has(e));
            if (unused.length > 0) {
                report.push({ file, unused, total: info.exports.size });
            }
        }
        return report;
    }

    resolve(specifier, from) {
        if (!specifier.startsWith('.')) return null;
        return path.resolve(path.dirname(from), specifier + '.js');
    }
}

// Usage:
const analyzer = new TreeShakeAnalyzer('./src/index.js');
const report = analyzer.analyze();
console.table(report);
// [{ file: './src/utils.js', unused: ['helperFn'], total: 5 }]

Advanced Dynamic Import Patterns

// Pattern 1: Feature flag-based loading
async function loadFeature(featureFlags) {
    const modules = {};

    if (featureFlags.analytics) {
        modules.analytics = await import('./features/analytics');
    }
    if (featureFlags.experiments) {
        modules.experiments = await import('./features/ab-testing');
    }

    return modules;
}

// Pattern 2: Locale-based chunk loading
const LOCALE_MAP = {
    en: () => import('./locales/en.json'),
    fr: () => import('./locales/fr.json'),
    ja: () => import('./locales/ja.json'),
};

async function loadLocale(locale) {
    const loader = LOCALE_MAP[locale] || LOCALE_MAP.en;
    const { default: messages } = await loader();
    return messages;
}

// Pattern 3: Intersection Observer lazy loading
function lazyLoadOnVisible(importFn, elementId) {
    const observer = new IntersectionObserver((entries) => {
        if (entries[0].isIntersecting) {
            importFn().then(module => {
                module.default.init(document.getElementById(elementId));
            });
            observer.disconnect();
        }
    });

    observer.observe(document.getElementById(elementId));
}

Common Mistakes

5 critical mistakes that hurt bundle performance

Mistake 1: Barrel File Re-Export Bloat

// ❌ BAD: Barrel file that re-exports everything
// src/components/index.ts
export { Button } from './Button';
export { Modal } from './Modal';       // imports heavy animation lib
export { DataGrid } from './DataGrid'; // imports ag-grid (500KB)
export { Chart } from './Chart';       // imports d3 (200KB)

// Consumer only wants Button, but gets everything:
import { Button } from '@/components';
// Without proper sideEffects: false, entire barrel is included!

// ✅ GOOD: Direct imports
import { Button } from '@/components/Button';

// ✅ GOOD: If using barrel, ensure library has:
// package.json: "sideEffects": false
// AND use named exports (not default) for better tree-shaking

Mistake 2: Not Marking sideEffects in package.json

// ❌ BAD: Library without sideEffects declaration
{
    "name": "my-utils-library",
    "main": "dist/index.js",
    "module": "dist/index.esm.js"
    // No sideEffects field!
    // Bundler assumes ANY module might have side effects
    // Cannot safely eliminate unused modules
}

// ✅ GOOD: Explicit sideEffects declaration
{
    "name": "my-utils-library",
    "main": "dist/index.js",
    "module": "dist/index.esm.js",
    "sideEffects": false
    // Now bundler knows: if an export isn't used,
    // the entire module can be safely removed
}

// ✅ GOOD: With side-effectful exceptions
{
    "sideEffects": ["./dist/polyfills.js", "**/*.css"]
}

Mistake 3: Default Exports Preventing Tree-Shaking

// ❌ BAD: Default export of an object
// utils.js
export default {
    formatDate(d) { /* ... */ },
    formatCurrency(n) { /* ... */ },
    formatPercentage(n) { /* ... */ },
    // 20 more utility functions...
};

// Consumer:
import utils from './utils';
utils.formatDate(new Date());
// Bundler can't tree-shake! The entire object is the "default" export
// It can't know which properties are accessed at compile time

// ✅ GOOD: Named exports
export function formatDate(d) { /* ... */ }
export function formatCurrency(n) { /* ... */ }
export function formatPercentage(n) { /* ... */ }

// Consumer:
import { formatDate } from './utils';
// Only formatDate is included in the bundle

Mistake 4: Importing Entire lodash

// ❌ BAD: Import entire lodash (71KB gzipped!)
import _ from 'lodash';
_.debounce(fn, 300);

// ❌ STILL BAD: Named import from CJS lodash
import { debounce } from 'lodash';
// lodash is CJS — this still pulls the entire library!

// ✅ GOOD: Cherry-pick from path
import debounce from 'lodash/debounce';
// Only gets the debounce module (~1KB)

// ✅ BETTER: Use lodash-es (ESM version, tree-shakeable)
import { debounce } from 'lodash-es';
// With sideEffects: false, only debounce is bundled

// ✅ BEST: Use native or lightweight alternatives
// Instead of lodash.debounce:
function debounce(fn, ms) {
    let timer;
    return (...args) => {
        clearTimeout(timer);
        timer = setTimeout(() => fn(...args), ms);
    };
}

Mistake 5: Ignoring Chunk Duplication

// ❌ BAD: Same dependency in multiple async chunks
// Page A: import('chart.js') → chunk-a.js includes chart.js
// Page B: import('chart.js') → chunk-b.js ALSO includes chart.js
// User downloads chart.js TWICE if visiting both pages!

// Cause: splitChunks.minChunks defaults to 1 for async chunks
// Each dynamic import creates an isolated chunk

// ✅ GOOD: Configure shared chunk extraction
optimization: {
    splitChunks: {
        chunks: 'all', // Apply to both sync and async chunks
        cacheGroups: {
            shared: {
                minChunks: 2,        // Used by 2+ chunks
                name: 'shared',
                chunks: 'all',
                reuseExistingChunk: true,
                enforce: true,
            },
        },
    },
}

// ✅ ALSO: Use bundle analyzer to detect duplication
// Look for the same module appearing in multiple chunks
// npx webpack-bundle-analyzer dist/stats.json

Follow-up Questions

6 common follow-up questions with senior-level answers

Q1: "How would you migrate a large CJS codebase to ESM?"

Answer: Incrementally, not all at once. Start by adding "type": "module" to package.json and renaming CJS files to .cjs. Use a codemod (e.g., cjs-to-esm) for mechanical transforms. Key challenges: __dirname/__filename don't exist in ESM (use import.meta.url), dynamic requires need createRequire(), and JSON imports need assertions. Migrate leaf modules first, then work inward. Keep dual-publish support via the exports field.

Q2: "Why can't you tree-shake CommonJS even with bundler plugins?"

Answer: CJS's fundamental problem is that require() is a runtime function — its argument can be any expression computed at runtime. The module.exports object can be mutated, reassigned, or computed dynamically. Static analysis would need to solve the halting problem to determine which exports are used. Some bundlers (Webpack) attempt partial CJS tree-shaking for simple patterns like exports.foo = ..., but it's fundamentally limited and never complete.

Q3: "Explain how Vite achieves fast HMR."

Answer: Vite's HMR is fast because it operates at the ESM module level, not the bundle level. When a file changes: (1) Only that specific module is re-transformed via esbuild. (2) The HMR update is sent via WebSocket with just the module's URL. (3) The browser fetches only the changed module. (4) The HMR runtime invalidates the module and its immediate importers. No re-bundling occurs — the update is proportional to the change, not the app size. Webpack must rebuild entire chunks.

Q4: "How do you handle a library that doesn't support tree-shaking?"

Answer: Multiple strategies: (1) Use cherry-pick imports if available (import x from 'lib/x'). (2) Use babel-plugin-transform-imports to rewrite barrel imports to direct paths. (3) Use Webpack's resolve.alias to point to ESM builds if they exist. (4) Fork and add sideEffects: false + ESM exports. (5) As a last resort, use externals and load from CDN, or find a lighter alternative. Always measure with bundle analyzer first.

Q5: "What's the difference between code splitting and lazy loading?"

Answer: Code splitting is the bundler technique of dividing output into multiple chunks based on configuration (splitChunks, entry points). Lazy loading is the runtime pattern of deferring chunk download until it's needed. Code splitting doesn't imply lazy loading — you can split chunks but still load them all eagerly. Dynamic import() combines both: it creates a split point AND defers loading. Route-based splitting with React.lazy is the most common combination of both.

Q6: "How would you optimize initial load for a dashboard with 50+ charts?"

Answer: Layer the loading strategy: (1) Server-render or static-generate the shell/layout. (2) Load only above-the-fold chart components initially. (3) Use IntersectionObserver to lazy-load charts as they scroll into view. (4) Share the charting library in a vendor chunk (loaded once, cached). (5) Use requestIdleCallback to prefetch below-fold chunks. (6) Consider server-side rendering charts as SVG/PNG for initial paint, then hydrate with interactive versions. (7) Use React.memo + virtualization to avoid re-rendering off-screen charts.

What NOT to Say in Interviews

  • ❌ "CJS and ESM are basically the same, just different syntax" — They have fundamentally different semantics
  • ❌ "Tree-shaking removes unused code" — Be specific: it removes unused exports via static analysis; DCE removes unreachable code
  • ❌ "Just use import instead of require" — Switching syntax doesn't give tree-shaking if the library is CJS internally
  • ❌ "Webpack is slow, just use Vite" — This ignores Webpack's strengths (Module Federation, mature ecosystem, complex configurations)
  • ❌ "Code splitting is free" — Every split point adds a network request, increases complexity, and requires error handling for chunk failures
  • ❌ "Bundle size doesn't matter with fast networks" — 53% of mobile users abandon sites that take >3s to load; many markets have slow connections

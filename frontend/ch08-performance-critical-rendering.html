Hard Performance TTI Bundle Optimization

Chapter 8: Performance & Critical Rendering Path

TTI is dominated by JavaScript parse/compile/execute time on mobile. The path to <2s is: reduce JS shipped (code splitting, tree-shaking), defer non-critical JS (dynamic import, prefetch), optimize delivery (compression, CDN, preconnect), and eliminate render-blocking resources. Every kilobyte of JS costs ~3-4x more on mobile than equivalent HTML/CSS.

Metric evolution (2024): Lighthouse v10+ deprecated TTI in favor of TBT (Total Blocking Time) as the lab metric. In the field, INP (Interaction to Next Paint) replaced both TTI and FID. This chapter uses "TTI" as the interview framing question, but the optimization strategies target TBT/INP improvement — the underlying techniques are identical.

Scope note: This chapter focuses on loading performance strategy and delivery optimization. For browser rendering mechanics (pipeline, compositor, GPU layers), see Chapter 7.

Interviewer's Intent

What the interviewer is really evaluating
The Question: "A production SPA takes 6 seconds to become interactive on mobile. How would you reduce Time-to-Interactive to under 2 seconds?"

The interviewer wants to assess:

  • Systems thinking: Can you identify the full pipeline from server to pixels — DNS, TCP, TLS, TTFB, download, parse, compile, execute, layout, paint, composite?
  • Prioritization under constraints: Which optimizations yield the biggest impact for the least effort? (Pareto principle in performance)
  • Measurement mindset: Do you measure before optimizing? Do you understand lab vs field data?
  • Mobile-first awareness: Do you understand that a mid-range Android phone has 4-6x slower CPU than your MacBook Pro?
  • Production experience: Have you actually shipped performance improvements, not just read about them?

This question separates seniors who have optimized real production apps from those who only know the theory. The interviewer expects a structured approach: measure → identify bottlenecks → apply targeted fixes → verify improvement.

60-Second Answer

Concise answer for time-pressured interviews

Framework for reducing TTI from 6s to <2s:

  1. Measure first: Lighthouse on throttled 4G + real device testing. Identify: is it network-bound or CPU-bound?
  2. Reduce JavaScript: Code-split routes (React.lazy), tree-shake dead code, replace heavy libraries (moment→date-fns, lodash→lodash-es individual imports).
  3. Defer non-critical JS: Dynamic imports for below-fold, defer third-party scripts, use requestIdleCallback for analytics.
  4. Optimize delivery: Brotli compression (20-25% smaller than gzip), HTTP/2 multiplexing, CDN edge caching, preconnect to origins.
  5. Eliminate render-blocking: Inline critical CSS, async/defer scripts, font-display: optional for web fonts.
  6. Consider SSR/SSG: Server-render the critical path so users see content before JS hydrates.

Performance Budget

Setting and enforcing budgets that guarantee fast TTI

What Is a Performance Budget?

A performance budget is a set of limits on metrics that affect user experience. It's not aspirational — it's a hard constraint enforced in CI, like a failing test.

The 170KB Rule: To achieve <5s TTI on a mid-range phone over 3G (~400kbps effective throughput after TCP slow-start), your critical-path JavaScript budget is ~170KB compressed. This accounts for ~1.5s download + ~3.5s parse/compile/execute on a Moto G4-class device. This figure originates from Addy Osmani's research (~2018) using a Moto G4 baseline. Modern mid-range phones (2024) are ~2-3x faster, supporting 200-250KB budgets — but 170KB remains a safe aggressive target for global audiences.

How to Set a Budget

Granular vs Monolithic Chunks

┌─── Monolithic (Bad for Caching) ───┐    ┌─── Granular (Good for Caching) ────┐
│                                     │    │                                     │
│  vendor.js (500KB)                  │    │  framework.js (45KB)  ← rarely      │
│  ├── react (45KB)                   │    │  lib.lodash.js (25KB)   changes     │
│  ├── lodash (70KB)                  │    │  lib.chart.js (180KB)               │
│  ├── chart.js (180KB)              │    │  shared.js (30KB)                   │
│  └── ...200 more packages           │    │  vendor-misc.js (50KB)              │
│                                     │    │                                     │
│  One package update → entire        │    │  One update → only that chunk       │
│  500KB vendor cache invalidated     │    │  invalidated. Others stay cached.   │
└─────────────────────────────────────┘    └─────────────────────────────────────┘
Senior insight: The optimal number of initial chunks is 6-10 for HTTP/2. Too few = poor caching; too many = request overhead and compression inefficiency. Profile your specific app — there's no universal magic number.

Lazy Loading Below-the-Fold

Deferring off-screen content until needed

IntersectionObserver for Components

// Generic lazy-load wrapper using IntersectionObserver
function useLazyLoad(options = {}) {
  const [isVisible, setIsVisible] = useState(false);
  const ref = useRef(null);

  useEffect(() => {
    const observer = new IntersectionObserver(
      ([entry]) => {
        if (entry.isIntersecting) {
          setIsVisible(true);
          observer.disconnect(); // Load once only
        }
      },
      {
        rootMargin: '200px', // Start loading 200px before viewport
        threshold: 0,
        ...options
      }
    );

    if (ref.current) observer.observe(ref.current);
    return () => observer.disconnect();
  }, []);

  return { ref, isVisible };
}

// Usage in a component
function ProductPage() {
  const { ref: reviewsRef, isVisible: showReviews } = useLazyLoad();
  const { ref: relatedRef, isVisible: showRelated } = useLazyLoad();

  return (
    <main>
      {/* Above the fold — loads immediately */}
      <ProductHero />
      <ProductDetails />

      {/* Below the fold — lazy loaded */}
      <div ref={reviewsRef}>
        {showReviews && <Reviews productId={id} />}
      </div>

      <div ref={relatedRef}>
        {showRelated && <RelatedProducts />}
      </div>
    </main>
  );
}

Preload, Prefetch, Preconnect

Telling the browser what to fetch and when

Resource Hints Comparison

Hint Purpose Priority When
preconnect DNS + TCP + TLS handshake High Third-party origins you'll fetch from soon
dns-prefetch DNS lookup only Low Origins used later; fallback for preconnect
preload Fetch resource for current page High Critical fonts, hero images, key scripts
prefetch Fetch resource for next navigation Low (idle) Next page's JS chunks, data
modulepreload Preload + parse ES module High Critical JS modules (Vite/ESM apps)

Implementation

<head>
  <!-- Preconnect to critical third-party origins -->
  <link rel="preconnect" href="https://cdn.example.com" crossorigin>
  <link rel="preconnect" href="https://fonts.googleapis.com">
  <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

  <!-- DNS-prefetch as fallback (broader browser support) -->
  <link rel="dns-prefetch" href="https://analytics.example.com">

  <!-- Preload critical resources -->
  <link rel="preload" href="/fonts/inter-var.woff2" as="font"
        type="font/woff2" crossorigin>
  <link rel="preload" href="/api/critical-data" as="fetch"
        crossorigin>
  <link rel="preload" href="/hero-image.webp" as="image"
        fetchpriority="high">

  <!-- Prefetch next page's chunk -->
  <link rel="prefetch" href="/chunks/checkout.abc123.js">

  <!-- Module preload for ESM -->
  <link rel="modulepreload" href="/src/app.js">
</head>

fetchpriority Attribute

<!-- High priority: LCP image -->
<img src="hero.webp" fetchpriority="high" alt="Hero">

<!-- Low priority: below-fold images -->
<img src="footer-bg.webp" fetchpriority="low" loading="lazy" alt="">

<!-- High priority: critical async script -->
<script src="critical.js" async fetchpriority="high"></script>

<!-- Low priority: analytics -->
<script src="analytics.js" async fetchpriority="low"></script>
Senior insight: Limit preconnects to 4-6 origins max. Each preconnect consumes CPU and network resources. Preloading too many resources can actually hurt performance by competing with truly critical resources for bandwidth.

Speculation Rules API (Chrome 121+)

The modern replacement for <link rel="prefetch"> with much better developer ergonomics and prerendering support:

<!-- Declarative speculation rules (in <head> or injected dynamically) -->
<script type="speculationrules">
{
  "prerender": [
    { "where": { "href_matches": "/product/*" },
      "eagerness": "moderate" }
  ],
  "prefetch": [
    { "where": { "selector_matches": ".nav-link" },
      "eagerness": "conservative" }
  ]
}
</script>

<!-- Eagerness levels:
     - "immediate": start now
     - "eager": start on slight signal (link visible)
     - "moderate": start on hover (200ms)
     - "conservative": start on mousedown/touchstart
-->

Advantages over <link rel="prefetch">: supports full prerendering (instant navigation), rule-based matching (no manual link management), respects Save-Data header, and is cancellable. Can be feature-detected via HTMLScriptElement.supports('speculationrules').

FOUT / FOIT / FOFT Explained

┌─── FOIT (Flash of Invisible Text) ──────────────────────────────┐
│  [blank]──────────────────────────────[web font appears]         │
│  Problem: Users see nothing for up to 3 seconds                  │
│  Cause: font-display: block (or browser default)                 │
└──────────────────────────────────────────────────────────────────┘

┌─── FOUT (Flash of Unstyled Text) ────────────────────────────────┐
│  [system font]─────────────────────────[swap to web font]        │
│  Problem: Layout shift when fonts swap                           │
│  Cause: font-display: swap without size-adjust                   │
└──────────────────────────────────────────────────────────────────┘

┌─── FOFT (Flash of Faux Text) ────────────────────────────────────┐
│  [system font]──[roman loaded]──────[bold/italic loaded]         │
│  Strategy: Load roman first, synthesize bold, then swap          │
│  Benefit: Fastest text display with minimal reflows              │
└──────────────────────────────────────────────────────────────────┘

Service Workers & Cache Strategies

Offline-first architecture and intelligent caching

Cache Strategies

┌─── Cache-First (Cache Falling Back to Network) ──────────────────┐
│  Request → Cache hit? → Return cached                            │
│                    ↓ miss                                         │
│              Network → Cache response → Return                   │
│  Best for: Static assets, fonts, images (versioned URLs)         │
└──────────────────────────────────────────────────────────────────┘

┌─── Network-First (Network Falling Back to Cache) ────────────────┐
│  Request → Network OK? → Cache response → Return                 │
│                    ↓ fail/timeout                                 │
│              Cache → Return stale                                 │
│  Best for: API responses, HTML pages (freshness matters)         │
└──────────────────────────────────────────────────────────────────┘

┌─── Stale-While-Revalidate ───────────────────────────────────────┐
│  Request → Cache hit? → Return cached immediately                │
│                    ↓ (in parallel)                                │
│              Network → Update cache for next time                 │
│  Best for: Avatars, non-critical API data, semi-static content   │
└──────────────────────────────────────────────────────────────────┘

      onError(error) {

      }
    }
  );

Why streaming matters: Traditional SSR blocks until the entire page is rendered. A slow DB query delays everything. Target: <200ms (P75)

// INP measures responsiveness of ALL interactions, not just first
// Optimization strategies:

// 1. Break up long tasks (>50ms blocks the main thread)
function processLargeList(items) {
  const CHUNK_SIZE = 50;
  let index = 0;

  function processChunk() {
    const end = Math.min(index + CHUNK_SIZE, items.length);
    for (; index < end; index++) {
      processItem(items[index]);
    }
    if (index < items.length) {
      // Yield to main thread between chunks
      setTimeout(processChunk, 0);
      // Or better: scheduler.yield() when available
    }
  }
  processChunk();
}

      updateScrollPosition();

// scripts/check-bundle-size.js — Run in CI pipeline
const fs = require('fs');
const path = require('path');
const zlib = require('zlib');

const BUDGETS = {
  'main': 170 * 1024,      // 170KB gzipped
  'vendor': 120 * 1024,    // 120KB gzipped
  'total': 350 * 1024      // 350KB total gzipped JS
};

function getGzipSize(filePath) {
  const content = fs.readFileSync(filePath);
  return zlib.gzipSync(content).length;
}

function checkBudgets(distDir) {
  const jsFiles = fs.readdirSync(distDir)
    .filter(f => f.endsWith('.js'))
    .map(f => ({
      name: f,
      path: path.join(distDir, f),
      size: getGzipSize(path.join(distDir, f))
    }));

  let totalSize = 0;
  let violations = [];

  for (const file of jsFiles) {
    totalSize += file.size;

    // Check individual chunk budgets
    for (const [pattern, budget] of Object.entries(BUDGETS)) {
      if (pattern === 'total') continue;
      if (file.name.includes(pattern) && file.size > budget) {
        violations.push(
          `❌ ${file.name}: ${(file.size / 1024).toFixed(1)}KB > ` +
          `budget ${(budget / 1024).toFixed(1)}KB`
        );
      }
    }
  }

  // Check total budget
  if (totalSize > BUDGETS.total) {
    violations.push(
      `❌ Total JS: ${(totalSize / 1024).toFixed(1)}KB > ` +
      `budget ${(BUDGETS.total / 1024).toFixed(1)}KB`
    );
  }

  if (violations.length > 0) {
    console.error('⚠️  Performance budget violations:\n');
    violations.forEach(v => console.error(v));
    console.error('\nBundle breakdown:');
    jsFiles.forEach(f =>
      console.log(`  ${f.name}: ${(f.size / 1024).toFixed(1)}KB gzipped`)
    );
    process.exit(1);
  }

  console.log('✅ All budgets passed');
  console.log(`   Total JS: ${(totalSize / 1024).toFixed(1)}KB / ${(BUDGETS.total / 1024).toFixed(1)}KB`);
}

Image Component with Blur-Up

// components/OptimizedImage.jsx
import { useState, useRef, useEffect } from 'react';

export function OptimizedImage({
  src,
  alt,
  width,
  height,
  placeholder,  // Tiny base64 ~20px wide
  sizes = '100vw',
  priority = false,
  className = ''
}) {
  const [isLoaded, setIsLoaded] = useState(false);
  const imgRef = useRef(null);

  useEffect(() => {
    // Handle already-cached images
    if (imgRef.current?.complete) setIsLoaded(true);
  }, []);

  // Generate srcset for responsive breakpoints
  const widths = [400, 800, 1200, 1600];
  const srcSet = widths
    .filter(w => w <= width * 2) // Don't upscale beyond 2x
    .map(w => `${getImageUrl(src, w)} ${w}w`)
    .join(', ');

  return (
    <div
      className={`image-container ${className}`}
      style={{ aspectRatio: `${width} / ${height}`, position: 'relative' }}
    >
      {/* Blur placeholder */}
      {placeholder && !isLoaded && (
        <img
          src={placeholder}
          alt=""
          aria-hidden="true"
          style={{
            position: 'absolute', inset: 0,
            width: '100%', height: '100%',
            objectFit: 'cover', filter: 'blur(20px)',
            transform: 'scale(1.1)'
          }}
        />
      )}

      {/* Full image */}
      <img
        ref={imgRef}
        src={getImageUrl(src, 800)}
        srcSet={srcSet}
        sizes={sizes}
        alt={alt}
        width={width}
        height={height}
        loading={priority ? 'eager' : 'lazy'}
        fetchpriority={priority ? 'high' : undefined}
        decoding="async"
        onLoad={() => setIsLoaded(true)}
        style={{
          opacity: isLoaded ? 1 : 0,
          transition: 'opacity 0.3s ease'
        }}
      />
    </div>
  );
}

function getImageUrl(src, width) {
  // Adapt to your image CDN
  return `/cdn-cgi/image/width=${width},format=auto,quality=80/${src}`;
}

Common Mistakes

Performance anti-patterns that hurt TTI

Mistake 1: Importing Entire Libraries

// ❌ WRONG: Entire library imported
import _ from 'lodash';              // +71KB
import moment from 'moment';         // +232KB
import * as Icons from 'react-icons'; // +165KB

// ✅ CORRECT: Cherry-pick imports
import debounce from 'lodash/debounce';     // +1KB
import { format } from 'date-fns';          // +2KB
import { FiSearch } from 'react-icons/fi';  // +0.5KB

// Why it matters: Tree-shaking can't eliminate unused exports
// from CommonJS modules or barrel files that import everything.

Mistake 2: Not Code Splitting Routes

// ❌ WRONG: All routes in one bundle
import Home from './pages/Home';
import Product from './pages/Product';
import Admin from './pages/Admin';      // Admin users = 2%
import Settings from './pages/Settings'; // Rarely visited
import Reports from './pages/Reports';   // Visited monthly

// Every user downloads Admin, Settings, Reports on first load!

// ✅ CORRECT: Only load what's needed for current route
const Home = lazy(() => import('./pages/Home'));
const Product = lazy(() => import('./pages/Product'));
const Admin = lazy(() => import('./pages/Admin'));
const Settings = lazy(() => import('./pages/Settings'));
const Reports = lazy(() => import('./pages/Reports'));

Mistake 3: Render-Blocking Third-Party Scripts

<!-- ❌ WRONG: Synchronous third-party scripts in <head> -->
<head>
  <script src="https://analytics.example.com/tracker.js"></script>
  <script src="https://chat.example.com/widget.js"></script>
  <script src="https://ads.example.com/prebid.js"></script>
  <!-- Browser STOPS parsing HTML until each downloads + executes -->
</head>

<!-- ✅ CORRECT: Async/defer with priority management -->
<head>
  <!-- Preconnect to origins we'll need -->
  <link rel="preconnect" href="https://analytics.example.com">
</head>
<body>
  <!-- App content first -->

  <!-- Load third-party after main content -->
  <script async src="https://analytics.example.com/tracker.js"></script>
  <script>
    // Defer chat widget until user idle
    requestIdleCallback(() => {
      const s = document.createElement('script');
      s.src = 'https://chat.example.com/widget.js';
      document.body.appendChild(s);
    });
  </script>
</body>

Mistake 5: Client-Rendering When SSR Would Help

// ❌ WRONG: Client-rendering a content-heavy page
// User sees blank screen for 3-4 seconds while:
// 1. HTML shell downloads
// 2. JS bundle downloads + parses
// 3. React mounts
// 4. useEffect fires API call
// 5. Data fetches
// 6. Re-render with data

function ProductPage({ id }) {
  const [product, setProduct] = useState(null);
  useEffect(() => {
    fetch(`/api/products/${id}`).then(r => r.json()).then(setProduct);
  }, [id]);
  if (!product) return <Spinner />; // User sees this for 3-4s
  return <ProductDetails product={product} />;
}

// ✅ CORRECT: Server-render with data
// User sees full content at FCP (~1s), JS hydrates in background
export async function getServerSideProps({ params }) {
  const product = await fetchProduct(params.id);
  return { props: { product } };
}

function ProductPage({ product }) {
  // Already has data — no loading state needed on initial render
  return <ProductDetails product={product} />;
}
The waterfall trap: Client-rendering creates a request waterfall: HTML → JS → API → Render. Each step waits for the previous one. SSR/SSG collapses this to: HTML (with data) → Render → JS hydrates. The perceived performance difference is massive on slow connections.

Follow-up Questions

Deep-dive questions interviewers ask after the main answer

Q1: How do you measure TTI vs TBT, and which matters more?

Answer: TTI (Time to Interactive) marks when the page is reliably interactive — main thread idle for 5s with no long tasks. TBT (Total Blocking Time) sums all long task time between FCP and TTI. In lab testing, TBT is more reliable (less variance) and correlates well with field INP. Lighthouse uses TBT as a proxy because TTI is noisy. In the field, use INP (actual interaction latency) rather than TTI.

Q2: Your app has 30 third-party scripts. How do you manage them?

Answer: Audit with requestMap (shows third-party dependency graph). Categorize: critical (payment SDK), important (analytics), nice-to-have (chat widget). Strategy: (1) Load critical synchronously, (2) defer important to after TTI with requestIdleCallback, (3) lazy-load nice-to-have on user interaction, (4) Use a tag manager with trigger rules, (5) Consider Partytown to run third-party scripts in a Web Worker off the main thread.

Q3: How does HTTP/2 change your bundling strategy?

Answer: HTTP/1.1 penalized many requests (6 connections/origin limit), favoring large concatenated bundles. HTTP/2 multiplexes unlimited requests over one connection, making granular chunks viable. Optimal strategy shifts from "fewer, larger bundles" to "many small, cacheable chunks." However, there's still overhead per request (headers, stream management) and compression is less efficient on small files. Sweet spot: 6-25 initial chunks of 20-100KB each.

Q4: What's the cost of hydration, and how do you reduce it?

Answer: Hydration re-executes component logic to attach event listeners to server-rendered HTML. Cost: (1) Download component JS, (2) parse/compile, (3) execute to build virtual DOM, (4) reconcile with real DOM. For a complex page, this can be 1-3s on mobile. Mitigation strategies: (1) Partial hydration (only hydrate interactive islands), (2) Progressive hydration (hydrate on visibility/interaction), (3) React Server Components (zero client JS for static parts), (4) Resumability (Qwik — serialize state instead of replaying).

Q5: How do you handle performance for users on 2G/3G networks?

Answer: Use Network Information API (navigator.connection.effectiveType) for adaptive loading: (1) Reduce image quality on slow connections, (2) Skip non-essential features (animations, auto-play video), (3) Increase prefetch aggressiveness on fast connections, (4) Show data-saver mode with reduced imagery, (5) Use Save-Data header respect. The key insight: serve different experiences based on connection quality rather than one-size-fits-all.

// Adaptive loading based on network conditions
function useAdaptiveLoading() {
  const connection = navigator.connection || {};
  const { effectiveType, saveData } = connection;

  return {
    shouldLoadImages: !saveData && effectiveType !== '2g',
    imageQuality: effectiveType === '4g' ? 'high' : 'low',
    shouldAutoplay: effectiveType === '4g' && !saveData,
    shouldPrefetch: effectiveType === '4g',
    shouldLoadFonts: effectiveType !== '2g' && !saveData
  };
}

// Usage
function HeroSection() {
  const { shouldLoadImages, imageQuality } = useAdaptiveLoading();

  return (
    <section>
      {shouldLoadImages ? (
        <OptimizedImage quality={imageQuality} src="hero.jpg" />
      ) : (
        <div className="hero-placeholder" aria-label="Hero image">
          <p>Image hidden to save data</p>
        </div>
      )}
    </section>
  );
}

Q6: How do you prevent performance regressions in a large team?

Answer: Multi-layered approach: (1) Performance budgets enforced in CI — PRs that exceed budgets are blocked, (2) Lighthouse CI with trend tracking — detect gradual regressions even within budget, (3) RUM dashboards with alerting — P75 LCP exceeds threshold → alert, (4) Bundle size bot on PRs (shows size diff), (5) Performance review in code review checklist, (6) Regular performance audits (monthly), (7) Education — team-wide understanding of why import moment from 'moment' is a problem.

Q7: Explain the Critical Rendering Path and how to optimize it.

Answer: The Critical Rendering Path is the sequence of steps browser takes to convert HTML/CSS/JS into pixels:

│                                                                    │

Summary

Mental models, key principles, and what NOT to say

Mental Models

  • The Cost of JavaScript: 1KB of JS ≠ 1KB of CSS. JS must download + parse + compile + execute. On mobile, every KB of JS costs 3-4x more processing time than equivalent content in HTML/CSS.
  • Performance Budget as Constraint: Treat your JS budget like a financial budget. Every library you add has ongoing "maintenance cost" in bytes. Ask: "Is this worth N KB to my users?"
  • Measure → Identify → Fix → Verify: Never optimize without measuring first. The bottleneck is rarely where you think. Profile on real devices with real network conditions.
  • Progressive Disclosure: Load only what the user needs NOW. Everything else loads on demand — routes, components, images, data.
  • The Network is Unreliable: Design for the worst case first, then enhance. Mobile users on flaky 3G should still have a usable experience.

Key Principles to Demonstrate

  1. You measure before optimizing (data-driven, not gut-driven)
  2. You think about mobile-first performance (not your dev MacBook)
  3. You understand the full stack (network, server, browser, rendering)
  4. You prioritize by impact (Pareto: 20% of changes → 80% of improvement)
  5. You've shipped performance improvements in production

What NOT to Say in an Interview

  • ❌ "Just add a CDN" — Shows surface-level thinking. CDN helps TTFB but doesn't fix a 1.8MB JS bundle.
  • ❌ "Lazy load everything" — Shows you don't understand above-fold priority. LCP elements must load eagerly.
  • ❌ "We should rewrite in [framework X]" — Framework choice rarely determines performance. Architecture and loading strategy do.
  • ❌ "I'd minify the code" — Minification is table stakes (already done by default). Interviewers want architectural solutions, not build tool defaults.
  • ❌ "Caching solves it" — Only helps repeat visits. First visit TTI is the primary concern. Also doesn't address the root cause of too much JS.
  • ❌ "Lighthouse says 95, so we're fine" — Lab scores don't reflect real user experience. P75 field data from CrUX or RUM is what matters.

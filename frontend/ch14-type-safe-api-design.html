Chapter 14: Type-Safe API Design Patterns

“How would you design a type-safe, runtime-validated API layer for a large application?”

Key Takeaway: TypeScript types are erased at runtime — they can’t validate external data (API responses, user input, env vars). A type-safe API layer combines compile-time types with runtime validation schemas (Zod, io-ts) so that validated data is automatically typed. The holy grail is single-source-of-truth schemas that generate both runtime validators and TypeScript types, eliminating the drift between what the API actually returns and what your code believes it returns.

Interviewer’s Intent

When an interviewer asks about type-safe API design, they’re probing for:

  • Trust boundaries: Do you understand that external data is inherently untyped?
  • Schema-first thinking: Can you define contracts that serve both runtime and compile time?
  • Practical tooling: Do you know Zod, io-ts, tRPC, OpenAPI codegen, and when each is appropriate?
  • Error handling philosophy: Can you model errors as data, not exceptions?
  • Architecture awareness: How do you structure type safety across a full-stack or monorepo?
Senior signal: Juniors cast as on fetch responses. Seniors validate and parse at the boundary, letting types flow from validated schemas.

60-Second Answer

Concise interview response

“TypeScript types disappear at runtime, so every trust boundary — API responses, user input, environment variables — needs runtime validation. I use schema libraries like Zod as the single source of truth: define the schema once, infer the TypeScript type from it, and parse incoming data through it. This gives you both compile-time safety and runtime guarantees with zero type duplication.

For the API layer, I wrap fetch in a generic function that accepts request/response schemas, validates the response, and returns a typed Result<T, E> discriminated union instead of throwing. This composes well with React Query’s generics.

At scale, I reach for contract-first approaches — either OpenAPI codegen for REST APIs or tRPC for full-stack TypeScript projects where the router types flow directly to the client without code generation.”

Runtime vs Compile-Time Validation

Why TypeScript Types Aren’t Enough

TypeScript’s type system is structural and erased. After compilation, there is no runtime representation of your interfaces. This is fine for internal code, but dangerous at system boundaries:

  TS types safe here ──▶  BUT NOT HERE (external data)

The Trust Boundary Concept

A trust boundary is any point where data enters your application from an external source:

  • API responses (REST, GraphQL, WebSocket messages)
  • User input (forms, URL params, query strings)
  • Environment variables
  • Local storage / IndexedDB reads
  • Third-party SDK callbacks
  • Deserialized data (JSON.parse, postMessage)
// ❌ DANGEROUS: Type assertion on external data
interface User {
  id: number;
  name: string;
  email: string;
}

const response = await fetch('/api/user/1');
const user = (await response.json()) as User; // LIES!
// If the API returns { id: "abc" }, TypeScript won't catch it

// ✅ SAFE: Runtime validation at the boundary
import { z } from 'zod';

const UserSchema = z.object({
  id: z.number(),
  name: z.string(),
  email: z.string().email(),
});

type User = z.infer<typeof UserSchema>; // Types derived from schema

const response = await fetch('/api/user/1');
const data = await response.json();
const user = UserSchema.parse(data); // Throws ZodError if invalid
// `user` is now BOTH typed AND validated

Where Validation Belongs

Rule of thumb: Validate at the outermost boundary, then trust the data internally. Don’t re-validate inside every function call — that defeats the purpose of a type system. 
// Validation layer pattern
//
// External World → [Validation Layer] → Typed Internal World
//                       ▲
//                  Parse, don't validate
//                  (return typed data or error)

// The "parse, don't validate" philosophy:
// - Parsing: takes unknown input, returns typed output or error
// - Validation: takes typed input, returns boolean
// Parsing is strictly more powerful because it narrows types.

Parsing vs Validation

Key distinction: Parsing transforms unknown → T | Error. Validation checks T → boolean. Always prefer parsing at boundaries because it narrows types. Zod’s .parse() and .safeParse() are parsers, not validators.
Production recommendation: Default to safeParse() for data parsing — never throw in hot paths. Reserve .parse() (which throws) for fail-fast scenarios like startup config validation where an error means the process should crash immediately. The fetch wrapper example below uses safeParse for this reason. 
// safeParse returns a discriminated union — no exceptions
const result = UserSchema.safeParse(data);

if (result.success) {
  // result.data is fully typed as User
  console.log(result.data.email);
} else {
  // result.error is a ZodError with structured issues
  console.error(result.error.flatten());
}

// Composability: schemas compose like types
const PaginatedResponse = <T extends z.ZodTypeAny>(itemSchema: T) =>
  z.object({
    items: z.array(itemSchema),
    total: z.number(),
    page: z.number(),
    pageSize: z.number(),
  });

const PaginatedUsers = PaginatedResponse(UserSchema);
type PaginatedUsers = z.infer<typeof PaginatedUsers>;

Inferring Types from Schemas

Single Source of Truth Pattern

The core principle: define the schema, derive the type. Never maintain a separate interface alongside a schema.

// ❌ ANTI-PATTERN: Dual maintenance
interface User {
  id: number;
  name: string;
  email: string;
}

const UserSchema = z.object({
  id: z.number(),
  name: z.string(),
  email: z.string(),
});
// These WILL drift apart over time!

// ✅ CORRECT: Schema is the single source of truth
const UserSchema = z.object({
  id: z.number().int().positive(),
  name: z.string().min(1),
  email: z.string().email(),
  role: z.enum(['admin', 'user', 'viewer']),
  avatarUrl: z.string().url().nullable(),
  createdAt: z.coerce.date(),
});

// Type is DERIVED — always in sync
type User = z.infer<typeof UserSchema>;

// Partial types for updates
const UserUpdateSchema = UserSchema.partial().omit({ id: true, createdAt: true });
type UserUpdate = z.infer<typeof UserUpdateSchema>;

// Pick for specific use cases
const UserSummarySchema = UserSchema.pick({ id: true, name: true, avatarUrl: true });
type UserSummary = z.infer<typeof UserSummarySchema>;

Keeping Types and Runtime in Sync

// Schema transformations that affect the inferred type
const ApiUserSchema = z.object({
  id: z.number(),
  created_at: z.string().datetime(),  // API returns snake_case string
  full_name: z.string(),
});

// Transform at the boundary — types follow automatically
const UserSchema = ApiUserSchema.transform((apiUser) => ({
  id: apiUser.id,
  createdAt: new Date(apiUser.created_at),  // string → Date
  fullName: apiUser.full_name,               // snake_case → camelCase
}));

type User = z.infer<typeof UserSchema>;
// { id: number; createdAt: Date; fullName: string }
// The TRANSFORM is the source of truth for your internal type!

Avoiding Manual Type Duplication

Pattern: Export schemas from a shared module. Consumers import the schema for validation AND the inferred type for compile-time use. One import gives you both. 
// schemas/user.ts — THE source of truth
export const UserSchema = z.object({ /* ... */ });
export type User = z.infer<typeof UserSchema>;

export const CreateUserSchema = UserSchema.omit({ id: true, createdAt: true });
export type CreateUser = z.infer<typeof CreateUserSchema>;

// api/users.ts — uses both the type AND the schema
import { UserSchema, type User, CreateUserSchema, type CreateUser } from '../schemas/user';

async function createUser(input: CreateUser): Promise<User> {
  const validated = CreateUserSchema.parse(input); // runtime check
  const response = await fetch('/api/users', {
    method: 'POST',
    body: JSON.stringify(validated),
  });
  return UserSchema.parse(await response.json()); // validate response too!
}

Type-Safe Fetch Wrappers

Generic Fetch with Response Validation

import { z } from 'zod';

type HttpMethod = 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';

interface RequestConfig<TBody = unknown> {
  method: HttpMethod;
  url: string;
  body?: TBody;
  headers?: Record<string, string>;
  signal?: AbortSignal;
}

// Core type-safe fetch function
async function typedFetch<TResponse>(
  config: RequestConfig,
  responseSchema: z.ZodType<TResponse>
): Promise<TResponse> {
  const { method, url, body, headers, signal } = config;

  const response = await fetch(url, {
    method,
    headers: {
      'Content-Type': 'application/json',
      ...headers,
    },
    body: body ? JSON.stringify(body) : undefined,
    signal,
  });

  if (!response.ok) {
    throw new ApiError(response.status, await response.text());
  }

  const data = await response.json();
  return responseSchema.parse(data); // Runtime validation!
}

// Usage — fully typed, fully validated
const user = await typedFetch(
  { method: 'GET', url: '/api/users/1' },
  UserSchema
);
// typeof user === User (guaranteed by Zod)

  search: z.string().optional(),
  role: z.enum(['admin', 'user', 'viewer']).optional(),

  order: z.enum(['asc', 'desc']).default('desc'),

function buildQueryString<T extends z.ZodObject<any>>(
  schema: T,
  params: z.input<T>
): string {
  const validated = schema.parse(params);
  const searchParams = new URLSearchParams();

  for (const [key, value] of Object.entries(validated)) {
    if (value !== undefined && value !== null) {
      searchParams.set(key, String(value));
    }
  }

  return searchParams.toString();
}

Path Parameter Typing

// Extract path params from template literal types
type ExtractPathParams<T extends string> =
  T extends `${infer _Start}:${infer Param}/${infer Rest}`
    ? Param | ExtractPathParams<`/${Rest}`>
    : T extends `${infer _Start}:${infer Param}`
      ? Param
      : never;

type Params = ExtractPathParams<'/users/:userId/posts/:postId'>;
// 'userId' | 'postId'

// Type-safe URL builder
function buildUrl<T extends string>(
  template: T,
  params: Record<ExtractPathParams<T>, string | number>
): string {
  let url: string = template;
  for (const [key, value] of Object.entries(params)) {
    url = url.replace(`:${key}`, encodeURIComponent(String(value)));
  }
  return url;
}

// Usage — TypeScript enforces correct params
const url = buildUrl('/users/:userId/posts/:postId', {
  userId: 123,
  postId: 456,
});
// Error if you forget a param or add an extra one!

Generic API Client Patterns

Resource-Based Client

import { z } from 'zod';

// Generic CRUD resource client
function createResourceClient<
  TSchema extends z.ZodObject<any>,
  TCreate extends z.ZodObject<any>,
  TUpdate extends z.ZodObject<any>
>(config: {
  baseUrl: string;
  schema: TSchema;
  createSchema: TCreate;
  updateSchema: TUpdate;
}) {
  type Resource = z.infer<typeof config.schema>;
  type CreateInput = z.infer<typeof config.createSchema>;
  type UpdateInput = z.infer<typeof config.updateSchema>;

  const listSchema = z.object({
    items: z.array(config.schema),
    total: z.number(),
  });

  return {
    async list(params?: Record<string, string>): Promise<z.infer<typeof listSchema>> {
      const query = params ? '?' + new URLSearchParams(params).toString() : '';
      const res = await fetch(`${config.baseUrl}${query}`);
      return listSchema.parse(await res.json());
    },

    async get(id: string | number): Promise<Resource> {
      const res = await fetch(`${config.baseUrl}/${id}`);
      return config.schema.parse(await res.json());
    },

    async create(input: CreateInput): Promise<Resource> {
      const validated = config.createSchema.parse(input);
      const res = await fetch(config.baseUrl, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(validated),
      });
      return config.schema.parse(await res.json());
    },

    async update(id: string | number, input: UpdateInput): Promise<Resource> {
      const validated = config.updateSchema.parse(input);
      const res = await fetch(`${config.baseUrl}/${id}`, {
        method: 'PATCH',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(validated),
      });
      return config.schema.parse(await res.json());
    },

    async delete(id: string | number): Promise<void> {
      await fetch(`${config.baseUrl}/${id}`, { method: 'DELETE' });
    },
  };
}

// Usage
const usersClient = createResourceClient({
  baseUrl: '/api/users',
  schema: UserSchema,
  createSchema: CreateUserSchema,
  updateSchema: UpdateUserSchema,
});

const users = await usersClient.list({ role: 'admin' });
// users.items is typed as User[]

Interceptors with Typed Config

type Interceptor = {
  request?: (config: RequestConfig) => RequestConfig | Promise<RequestConfig>;
  response?: (response: Response) => Response | Promise<Response>;
  error?: (error: ApiError) => ApiError | Promise<never>;
};

class TypedApiClient {
  private interceptors: Interceptor[] = [];
  private baseUrl: string;

  constructor(baseUrl: string) {
    this.baseUrl = baseUrl;
  }

  use(interceptor: Interceptor): this {
    this.interceptors.push(interceptor);
    return this; // method chaining
  }

  async request<T>(config: RequestConfig, schema: z.ZodType<T>): Promise<T> {
    let finalConfig = { ...config, url: this.baseUrl + config.url };

    // Run request interceptors
    for (const { request } of this.interceptors) {
      if (request) finalConfig = await request(finalConfig);
    }

    let response = await fetch(finalConfig.url, {
      method: finalConfig.method,
      headers: finalConfig.headers,
      body: finalConfig.body ? JSON.stringify(finalConfig.body) : undefined,
    });

    // Run response interceptors
    for (const { response: respInterceptor } of this.interceptors) {
      if (respInterceptor) response = await respInterceptor(response);
    }

    if (!response.ok) {
      const error = new ApiError(response.status, await response.text());
      for (const { error: errHandler } of this.interceptors) {
        if (errHandler) await errHandler(error);
      }
      throw error;
    }

    return schema.parse(await response.json());
  }
}

// Configure with interceptors
const api = new TypedApiClient('https://api.example.com')
  .use({
    request: (config) => ({
      ...config,
      headers: { ...config.headers, Authorization: `Bearer ${getToken()}` },
    }),
  })
  .use({
    error: async (error) => {
      if (error.status === 401) await refreshToken();
      throw error;
    },
  });

Retry/Timeout Integration

interface RetryConfig {
  maxRetries: number;
  backoffMs: number;
  retryOn: number[]; // HTTP status codes to retry
}

async function withRetry<T>(
  fn: () => Promise<T>,
  config: RetryConfig
): Promise<T> {
  let lastError: unknown;

  for (let attempt = 0; attempt <= config.maxRetries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      lastError = error;
      if (
        error instanceof ApiError &&
        config.retryOn.includes(error.status) &&
        attempt < config.maxRetries
      ) {
        await sleep(config.backoffMs * Math.pow(2, attempt));
        continue;
      }
      throw error;
    }
  }

  throw lastError;
}

// Timeout wrapper with AbortController
function withTimeout<T>(
  fn: (signal: AbortSignal) => Promise<T>,
  timeoutMs: number
): Promise<T> {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), timeoutMs);

  return fn(controller.signal).finally(() => clearTimeout(timeout));
}

Error Types & Result Pattern

Discriminated Union for Errors

// The Result type — errors as data, not exceptions
type Result<T, E = ApiError> =
  | { success: true; data: T }
  | { success: false; error: E };

// Never-throw fetch wrapper
async function safeFetch<T>(
  config: RequestConfig,
  schema: z.ZodType<T>
): Promise<Result<T, ApiError>> {
  try {
    const response = await fetch(config.url, {
      method: config.method,
      headers: config.headers,
      body: config.body ? JSON.stringify(config.body) : undefined,
    });

    if (!response.ok) {
      return {
        success: false,
        error: new ApiError(response.status, await response.text()),
      };
    }

    const data = await response.json();
    const parsed = schema.safeParse(data);

    if (!parsed.success) {
      return {
        success: false,
        error: new ApiError(500, 'Response validation failed', parsed.error),
      };
    }

    return { success: true, data: parsed.data };
  } catch (e) {
    return {
      success: false,
      error: e instanceof ApiError ? e : new ApiError(0, 'Network error'),
    };
  }
}

Typed Error Codes & Hierarchy

// Typed error codes as a const enum alternative
const ErrorCode = {
  NETWORK_ERROR: 'NETWORK_ERROR',
  VALIDATION_ERROR: 'VALIDATION_ERROR',
  NOT_FOUND: 'NOT_FOUND',
  UNAUTHORIZED: 'UNAUTHORIZED',
  FORBIDDEN: 'FORBIDDEN',
  RATE_LIMITED: 'RATE_LIMITED',
  SERVER_ERROR: 'SERVER_ERROR',
} as const;

type ErrorCode = (typeof ErrorCode)[keyof typeof ErrorCode];

// Discriminated error union — exhaustive handling
type AppError =
  | { code: 'NETWORK_ERROR'; message: string }
  | { code: 'VALIDATION_ERROR'; message: string; fields: Record<string, string[]> }
  | { code: 'NOT_FOUND'; message: string; resource: string; id: string }
  | { code: 'UNAUTHORIZED'; message: string }
  | { code: 'FORBIDDEN'; message: string; requiredRole: string }
  | { code: 'RATE_LIMITED'; message: string; retryAfter: number }
  | { code: 'SERVER_ERROR'; message: string; traceId?: string };

// Exhaustive error handler
function handleError(error: AppError): string {
  switch (error.code) {
    case 'NETWORK_ERROR':
      return 'Check your internet connection';
    case 'VALIDATION_ERROR':
      return `Invalid fields: ${Object.keys(error.fields).join(', ')}`;
    case 'NOT_FOUND':
      return `${error.resource} with id ${error.id} not found`;
    case 'UNAUTHORIZED':
      return 'Please log in';
    case 'FORBIDDEN':
      return `Requires ${error.requiredRole} role`;
    case 'RATE_LIMITED':
      return `Too many requests. Retry in ${error.retryAfter}s`;
    case 'SERVER_ERROR':
      return `Server error${error.traceId ? ` (trace: ${error.traceId})` : ''}`;
    default:
      const _exhaustive: never = error;
      return _exhaustive; // Compile error if a case is missing
  }
}

Result Pattern vs try/catch

Why prefer Result?
  • try/catch loses type information — the caught error is unknown
  • Result forces callers to handle the error path — can’t accidentally ignore it
  • Composable: you can map, flatMap, unwrapOr on results
  • No hidden control flow — errors are just data in the return type
// Utility functions for Result
function mapResult<T, U, E>(
  result: Result<T, E>,
  fn: (data: T) => U
): Result<U, E> {
  if (result.success) return { success: true, data: fn(result.data) };
  return result;
}

function unwrapOr<T, E>(result: Result<T, E>, defaultValue: T): T {
  return result.success ? result.data : defaultValue;
}

// Usage in components
const result = await safeFetch({ method: 'GET', url: '/api/user' }, UserSchema);

if (result.success) {
  renderUser(result.data); // data is typed as User
} else {
  showError(handleError(result.error)); // error is typed as ApiError
}

Discriminated Union Responses

Typing API Responses

// API responses as discriminated unions
const SuccessResponseSchema = <T extends z.ZodTypeAny>(dataSchema: T) =>
  z.object({
    status: z.literal('success'),
    data: dataSchema,
    meta: z.object({
      requestId: z.string(),
      timestamp: z.string().datetime(),
    }).optional(),
  });

const ErrorResponseSchema = z.object({
  status: z.literal('error'),
  error: z.object({
    code: z.string(),
    message: z.string(),
    details: z.record(z.string(), z.array(z.string())).optional(),
  }),
});

const ApiResponseSchema = <T extends z.ZodTypeAny>(dataSchema: T) =>
  z.discriminatedUnion('status', [
    SuccessResponseSchema(dataSchema),
    ErrorResponseSchema,
  ]);

// Usage
const UserResponseSchema = ApiResponseSchema(UserSchema);
type UserResponse = z.infer<typeof UserResponseSchema>;
// { status: 'success'; data: User; meta?: {...} }
// | { status: 'error'; error: { code: string; message: string; ... } }

Pattern Matching on Response

async function fetchUser(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  const json = await res.json();
  const response = UserResponseSchema.parse(json);

  // TypeScript narrows based on discriminant
  switch (response.status) {
    case 'success':
      return response.data; // TypeScript knows: User
    case 'error':
      throw new AppError(response.error.code, response.error.message);
  }
}

// Exhaustive handling helper
function assertNever(x: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(x)}`);
}

function handleResponse<T>(
  response: { status: 'success'; data: T } | { status: 'error'; error: { code: string; message: string } }
): T {
  switch (response.status) {
    case 'success':
      return response.data;
    case 'error':
      throw new AppError(response.error.code, response.error.message);
    default:
      return assertNever(response); // Compile error if not exhaustive
  }
}

  z.object({ status: z.literal('success'), data: UserSchema }),
  z.object({ status: z.literal('not_found'), message: z.string() }),
  z.object({ status: z.literal('forbidden'), requiredRole: z.string() }),
]);

type UserEndpointResponse = z.infer<typeof UserEndpointResponse>;

// Each variant is narrowed independently
function render(response: UserEndpointResponse) {
  switch (response.status) {
    case 'success':
      return <UserProfile user={response.data} />;
    case 'not_found':
      return <NotFound message={response.message} />;
    case 'forbidden':
      return <AccessDenied role={response.requiredRole} />;
  }
}

// Optimistic updates with proper typing
function useUpdateUser() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: async ({ id, data }: { id: number; data: UserUpdate }) => {
      const res = await fetch(`/api/users/${id}`, {
        method: 'PATCH',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(UpdateUserSchema.parse(data)),
      });
      return UserSchema.parse(await res.json());
    },
    onMutate: async ({ id, data }) => {
      await queryClient.cancelQueries({ queryKey: queryKeys.users.detail(id) });
      const previous = queryClient.getQueryData<User>(queryKeys.users.detail(id));

      if (previous) {
        queryClient.setQueryData<User>(queryKeys.users.detail(id), {
          ...previous,
          ...data,
        });
      }

      return { previous };
    },
    onError: (_err, { id }, context) => {
      if (context?.previous) {
        queryClient.setQueryData(queryKeys.users.detail(id), context.previous);
      }
    },
  });
}

End-to-End Type Safety (tRPC Pattern)

How tRPC Achieves E2E Types

tRPC eliminates the API layer abstraction entirely. Instead of REST endpoints with separate client/server types, the server’s router type is the client’s API type — no code generation needed.

┌──────────────────────────────────────────────────────────┐
│                    tRPC ARCHITECTURE                       │
│                                                           │
│  SERVER                              CLIENT               │
│  ┌─────────────────┐                ┌─────────────────┐  │
│  │ Router          │  Type Export   │ Typed Client    │  │
│  │ ┌─────────────┐ │───────────────▶│                 │  │
│  │ │ user.get    │ │   (no codegen) │ trpc.user.get() │  │
│  │ │ user.create │ │                │ trpc.user.create│  │
│  │ │ post.list   │ │                │ trpc.post.list()│  │
│  │ └─────────────┘ │                └─────────────────┘  │
│  └─────────────────┘                                      │
│                                                           │
│  Types flow through TypeScript's module system            │
│  No HTTP schema, no code generation, no OpenAPI spec      │
└──────────────────────────────────────────────────────────┘

Router Definition

// server/trpc.ts
import { initTRPC } from '@trpc/server';
import { z } from 'zod';

const t = initTRPC.context<Context>().create();

export const router = t.router;
export const publicProcedure = t.procedure;
export const protectedProcedure = t.procedure.use(authMiddleware);

// server/routers/user.ts
export const userRouter = router({
  getById: publicProcedure
    .input(z.object({ id: z.number() }))
    .output(UserSchema)
    .query(async ({ input, ctx }) => {
      const user = await ctx.db.user.findUnique({ where: { id: input.id } });
      if (!user) throw new TRPCError({ code: 'NOT_FOUND' });
      return user; // Validated against UserSchema automatically
    }),

  create: protectedProcedure
    .input(CreateUserSchema)
    .output(UserSchema)
    .mutation(async ({ input, ctx }) => {
      return ctx.db.user.create({ data: input });
    }),

  list: publicProcedure
    .input(UserQuerySchema)
    .output(z.object({
      items: z.array(UserSchema),
      total: z.number(),
    }))
    .query(async ({ input, ctx }) => {
      const [items, total] = await Promise.all([
        ctx.db.user.findMany({
          skip: (input.page - 1) * input.pageSize,
          take: input.pageSize,
          where: input.search ? { name: { contains: input.search } } : undefined,
        }),
        ctx.db.user.count(),
      ]);
      return { items, total };
    }),
});

// server/root.ts
export const appRouter = router({
  user: userRouter,
  post: postRouter,
});

export type AppRouter = typeof appRouter; // ← THIS is the magic export

Validation Middleware

// Backend middleware that validates against the same schemas
import { apiRegistry, type ApiEndpoint } from '@myapp/contracts';

function createValidationMiddleware(endpoint: ApiEndpoint) {
  const config = apiRegistry[endpoint];

  return async (req: Request, res: Response, next: NextFunction) => {
    try {
      // Validate request
      if ('params' in config) req.params = config.params.parse(req.params);
      if ('query' in config) req.query = config.query.parse(req.query);
      if ('body' in config) req.body = config.body.parse(req.body);

      // Wrap response to validate outgoing data
      const originalJson = res.json.bind(res);
      res.json = (data: unknown) => {
        const validated = config.response.parse(data);
        return originalJson(validated);
      };

      next();
    } catch (error) {
      if (error instanceof z.ZodError) {
        res.status(400).json({
          status: 'error',
          error: { code: 'VALIDATION_ERROR', issues: error.flatten() },
        });
      } else {
        next(error);
      }
    }
  };
}

Monitoring Type Errors

// Client-side: log validation failures without crashing
function createMonitoredParser<T>(schema: z.ZodType<T>, endpoint: string) {
  return (data: unknown): T => {
    const result = schema.safeParse(data);

    if (result.success) return result.data;

    // Log the schema drift — don't crash in production
    reportError({
      type: 'SCHEMA_VALIDATION_FAILURE',
      endpoint,
      issues: result.error.issues,
      receivedData: JSON.stringify(data).slice(0, 1000), // truncate for safety
      timestamp: new Date().toISOString(),
    });

    // Decide: throw (strict) or return raw data (lenient)
    if (process.env.NODE_ENV === 'development') {
      throw result.error; // Fail loudly in dev
    }

    // In production, return data with a warning (graceful degradation)
    console.warn(`Schema validation failed for ${endpoint}`, result.error);
    return data as T; // Unsafe but keeps app running
  };
}

Team decision: The graceful degradation pattern above (return data as T on validation failure) is pragmatic but controversial. You're operating on potentially malformed data — some teams consider this unacceptable and prefer crashing with a clear error over silent data corruption. In an interview, acknowledge both approaches: "In my team we [chose X because Y]." The key insight is that this is a product decision (availability vs correctness tradeoff), not a purely technical one.

import { z } from 'zod';

// --- Schema Definitions ---
const UserSchema = z.object({
  id: z.number(),
  name: z.string(),
  email: z.string().email(),
  role: z.enum(['admin', 'user', 'viewer']),
  avatar: z.string().url().nullable(),
  createdAt: z.string().datetime(),
});
type User = z.infer<typeof UserSchema>;

// --- Result Type ---
type Result<T, E = Error> =
  | { ok: true; data: T }
  | { ok: false; error: E };

// --- API Error ---
class ApiError extends Error {
  constructor(
    public status: number,
    public code: string,
    message: string,
    public details?: unknown
  ) {
    super(message);
    this.name = 'ApiError';
  }
}

// --- Type-Safe Client ---
class TypeSafeApiClient {
  constructor(private baseUrl: string, private token?: string) {}

  private async request<T>(
    method: string,
    path: string,
    schema: z.ZodType<T>,
    body?: unknown
  ): Promise<Result<T, ApiError>> {
    try {
      const response = await fetch(`${this.baseUrl}${path}`, {
        method,
        headers: {
          'Content-Type': 'application/json',
          ...(this.token && { Authorization: `Bearer ${this.token}` }),
        },
        body: body ? JSON.stringify(body) : undefined,
      });

      if (!response.ok) {
        const errorBody = await response.json().catch(() => ({}));
        return {
          ok: false,
          error: new ApiError(
            response.status,
            errorBody.code ?? 'UNKNOWN',
            errorBody.message ?? response.statusText,
            errorBody.details
          ),
        };
      }

      const data = await response.json();
      const parsed = schema.safeParse(data);

      if (!parsed.success) {
        return {
          ok: false,
          error: new ApiError(
            0,
            'VALIDATION_ERROR',
            'Response did not match expected schema',
            parsed.error.flatten()
          ),
        };
      }

      return { ok: true, data: parsed.data };
    } catch (e) {
      return {
        ok: false,
        error: new ApiError(0, 'NETWORK_ERROR', e instanceof Error ? e.message : 'Unknown error'),
      };
    }
  }

  // Typed endpoint methods
  users = {
    get: (id: number) =>
      this.request('GET', `/users/${id}`, UserSchema),

    list: (params?: { page?: number; search?: string }) =>
      this.request('GET', `/users?${new URLSearchParams(params as any)}`,
        z.object({ items: z.array(UserSchema), total: z.number() })),

    create: (input: Omit<User, 'id' | 'createdAt'>) =>
      this.request('POST', '/users', UserSchema, input),

    update: (id: number, input: Partial<Omit<User, 'id' | 'createdAt'>>) =>
      this.request('PATCH', `/users/${id}`, UserSchema, input),

    delete: (id: number) =>
      this.request('DELETE', `/users/${id}`, z.object({ success: z.boolean() })),
  };
}

import { z } from 'zod';

// Simplified tRPC-like procedure builder
type ProcedureConfig<TInput, TOutput> = {
  input: z.ZodType<TInput>;
  output: z.ZodType<TOutput>;
  handler: (input: TInput) => Promise<TOutput>;
};

function procedure<TInput, TOutput>(
  config: ProcedureConfig<TInput, TOutput>
) {
  return {
    ...config,
    call: async (rawInput: unknown): Promise<TOutput> => {
      const input = config.input.parse(rawInput);
      const output = await config.handler(input);
      return config.output.parse(output);
    },
  };
}

// Define router
const userRouter = {
  getById: procedure({
    input: z.object({ id: z.number() }),
    output: UserSchema,
    handler: async ({ id }) => {
      return db.users.findById(id);
    },
  }),
  create: procedure({
    input: z.object({ name: z.string(), email: z.string().email() }),
    output: UserSchema,
    handler: async (input) => {
      return db.users.create(input);
    },
  }),
};

// Type-safe client (inferred from router definition)
type RouterType = typeof userRouter;

type TypedClient<T> = {
  [K in keyof T]: T[K] extends ProcedureConfig<infer I, infer O>
    ? (input: I) => Promise<O>
    : never;
};

function createClient<T extends Record<string, any>>(router: T): TypedClient<T> {
  const client = {} as any;
  for (const [key, proc] of Object.entries(router)) {
    client[key] = (input: unknown) => proc.call(input);
  }
  return client;
}

const client = createClient(userRouter);
const user = await client.getById({ id: 1 }); // Typed as User
Environment Config Validator 
// Validate environment variables at startup — crash early if misconfigured
const EnvSchema = z.object({
  NODE_ENV: z.enum(['development', 'staging', 'production']),
  API_URL: z.string().url(),
  API_KEY: z.string().min(1),
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url().optional(),
  PORT: z.coerce.number().int().positive().default(3000),
  LOG_LEVEL: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  ENABLE_CACHE: z.coerce.boolean().default(true),
  MAX_UPLOAD_SIZE_MB: z.coerce.number().positive().default(10),
});

type Env = z.infer<typeof EnvSchema>;

// Parse and validate at module load — fail fast
function loadEnv(): Env {
  const result = EnvSchema.safeParse(process.env);

  if (!result.success) {
    console.error('❌ Invalid environment variables:');
    console.error(result.error.flatten().fieldErrors);
    process.exit(1);
  }

  return Object.freeze(result.data);
}

export const env = loadEnv();

// Now `env.API_URL` is typed as string (guaranteed non-empty URL)
// `env.PORT` is typed as number (coerced from string)
// `env.REDIS_URL` is typed as string | undefined
Typed Form with Validation 
import { z } from 'zod';
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';

// Schema is the source of truth for form validation + types
const RegistrationSchema = z.object({
  username: z.string()
    .min(3, 'Username must be at least 3 characters')
    .max(20, 'Username must be at most 20 characters')
    .regex(/^[a-zA-Z0-9_]+$/, 'Only letters, numbers, and underscores'),
  email: z.string().email('Invalid email address'),
  password: z.string()
    .min(8, 'Password must be at least 8 characters')
    .regex(/[A-Z]/, 'Must contain an uppercase letter')
    .regex(/[0-9]/, 'Must contain a number'),
  confirmPassword: z.string(),
  acceptTerms: z.literal(true, {
    errorMap: () => ({ message: 'You must accept the terms' }),
  }),
}).refine((data) => data.password === data.confirmPassword, {
  message: 'Passwords do not match',
  path: ['confirmPassword'],
});

type RegistrationForm = z.infer<typeof RegistrationSchema>;

function RegistrationPage() {
  const { register, handleSubmit, formState: { errors } } = useForm<RegistrationForm>({
    resolver: zodResolver(RegistrationSchema),
  });

  const onSubmit = async (data: RegistrationForm) => {
    // `data` is fully typed AND validated
    const result = await api.users.register(data);
    // ...
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register('username')} />
      {errors.username && <span>{errors.username.message}</span>}

      <input type="email" {...register('email')} />
      {errors.email && <span>{errors.email.message}</span>}

      <input type="password" {...register('password')} />
      {errors.password && <span>{errors.password.message}</span>}

      <input type="password" {...register('confirmPassword')} />
      {errors.confirmPassword && <span>{errors.confirmPassword.message}</span>}

      <label>
        <input type="checkbox" {...register('acceptTerms')} />
        I accept the terms
      </label>
      {errors.acceptTerms && <span>{errors.acceptTerms.message}</span>}

      <button type="submit">Register</button>
    </form>
  );
}

Common Mistakes

1. Trusting API responses without validation 
// ❌ Trusting external data blindly
const users: User[] = await fetch('/api/users').then(r => r.json());
// If the API changes shape, your app breaks silently with runtime errors
// deep in component trees — far from the actual problem.

// ✅ Validate at the boundary
const raw = await fetch('/api/users').then(r => r.json());
const users = z.array(UserSchema).parse(raw);
// Fails fast at the boundary with a clear error message
2. Type assertions on fetch responses 
// ❌ `as` gives you a false sense of safety
const data = (await response.json()) as ApiResponse;
// TypeScript trusts you — but the runtime doesn't care about your assertion

// ❌ Even worse: double assertion
const data = (await response.json()) as unknown as ComplexType;
// This bypasses ALL type checking

// ✅ Parse, don't assert
const data = ApiResponseSchema.parse(await response.json());
// Runtime guarantee matches compile-time type
3. Duplicating types alongside schemas 
// ❌ Dual maintenance — these WILL drift apart
interface User {
  id: number;
  name: string;
  email: string;
  role: 'admin' | 'user'; // Someone added 'viewer' to schema but forgot here
}

const UserSchema = z.object({
  id: z.number(),
  name: z.string(),
  email: z.string(),
  role: z.enum(['admin', 'user', 'viewer']), // ← Drift!
});

// ✅ Single source of truth
const UserSchema = z.object({ /* ... */ });
type User = z.infer<typeof UserSchema>; // Always in sync
4. Over-engineering for simple APIs 
// ❌ Building a full tRPC-like system for 3 endpoints
// Sometimes a simple typed fetch wrapper is enough:

// ✅ Right-sized solution for a small app
async function getUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  return UserSchema.parse(await res.json());
}

// Scale up when:
// - You have 20+ endpoints
// - Multiple teams consume the same API
// - You need code generation or contract testing
5. Not handling unknown error shapes 
// ❌ Assuming error shape
try {
  await api.createUser(data);
} catch (error) {
  // error is `unknown` — you can't access .message safely
  showToast(error.message); // 💥 Runtime error if error isn't an Error

  // Even worse: assuming API error shape
  showFieldErrors(error.response.data.fields); // 💥💥
}

// ✅ Validate error shapes too
const ApiErrorSchema = z.object({
  code: z.string(),
  message: z.string(),
  fields: z.record(z.array(z.string())).optional(),
});

try {
  await api.createUser(data);
} catch (e) {
  const parsed = ApiErrorSchema.safeParse(e);
  if (parsed.success) {
    showFieldErrors(parsed.data.fields);
  } else {
    showToast('An unexpected error occurred');
  }
}

Bundle Size Impact

Real-world numbers: Zod adds ~14-15 kB gzipped (Zod 4 aims to reduce this significantly). For most apps this is negligible. For performance-critical landing pages, consider Valibot (~1-5 kB tree-shaken) or validate only on the server and trust the typed response in the client (accepting the risk).

Follow-up Questions

1. How do you handle API versioning with type safety?

Use discriminated unions per version or namespace schemas: v1.UserSchema, v2.UserSchema. At the boundary, detect the version (header, URL prefix) and parse with the corresponding schema. Transform older versions to the latest internal type so application code only deals with one shape.

2. What about performance? Isn’t runtime validation expensive?

Zod parsing is fast (~0.1-1ms for typical payloads). The cost is negligible compared to network latency. For hot paths (WebSocket messages at high frequency), you can validate in development and skip in production, or use a faster validator like Valibot. Profile before optimizing — network I/O dominates.

3. How do you test schemas themselves?

Use property-based testing (fast-check) to generate random valid/invalid data and verify schemas accept/reject correctly. Also use expect-type or tsd for compile-time type tests. Snapshot the schema’s inferred type to catch accidental breaking changes in PRs.

4. How do you handle optional vs nullable vs undefined?

Zod distinguishes: .optional() means the key can be missing, .nullable() means the value can be null, .nullish() means either. Be explicit about which your API uses. Transform at the boundary: .nullable().transform(v => v ?? defaultValue) keeps internal code simple.

5. Can you use this approach with GraphQL?

Yes. GraphQL codegen (graphql-codegen) generates TypeScript types from your schema + operations. For runtime validation, you can add Zod schemas for critical queries. The GraphQL type system provides compile-time safety; Zod adds runtime guarantees for the specific shape your component expects.

6. How do you handle file uploads with typed APIs?

File uploads break the JSON-only pattern. Define a schema for the metadata and handle the file separately via FormData. Type the upload endpoint differently: input: z.object({ file: z.instanceof(File), metadata: MetadataSchema }). The response schema remains the same pattern.

7. What about WebSocket/real-time data validation?

Use discriminated unions for message types: z.discriminatedUnion('type', [ChatMessageSchema, PresenceSchema, ErrorSchema]). Validate incoming messages at the WebSocket onmessage handler. For high-frequency messages (gaming, trading), consider validating only in dev mode or sampling in production to reduce overhead.

Summary

Mental Models

  • “Parse, don’t validate” — Transform unknown data into typed data at boundaries. Parsers narrow types; validators just return booleans.
  • “Schema as source of truth” — Define once (Zod schema), derive everything (TS type, validation, form rules, documentation).
  • “Trust boundary” — Internal code trusts the type system. External data is untrusted until parsed. Validation lives at the boundary, nowhere else.
  • “Errors as data” — Use Result<T, E> discriminated unions instead of try/catch. Makes error handling explicit, typed, and composable.
  • “Types flow, not duplicate” — Whether it’s tRPC (types flow from server to client) or Zod (types flow from schema to code), never maintain parallel type definitions.

What NOT to Say

  • “I just use as to cast the response.” — Shows no understanding of runtime safety.
  • “TypeScript guarantees the API response is correct.” — Types are erased at runtime; they guarantee nothing about external data.
  • “I validate inside every function.” — Over-validation defeats the type system. Validate at boundaries only.
  • “We just write interfaces and keep them in sync manually.” — Manual sync doesn’t scale. Senior engineers automate this.
  • “Runtime validation is too expensive.” — It’s negligible (sub-ms) compared to network latency. Profile, don’t assume.

Key Takeaways

  1. TypeScript types are compile-time only — external data needs runtime validation
  2. Use schema libraries (Zod, Valibot) as the single source of truth for types + validation
  3. Validate at trust boundaries, then trust types internally
  4. Model errors as discriminated unions (Result pattern), not exceptions
  5. Choose the right tool: tRPC for TS monorepos, OpenAPI codegen for multi-language, Zod wrappers for simple apps

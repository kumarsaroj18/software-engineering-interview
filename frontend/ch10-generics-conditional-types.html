Chapter 10: Generics & Conditional Types

"Explain generics, conditional types, and infer. How would you build a type-safe event emitter?"

Key Takeaway: Generics provide type parameters that flow through a computation. Conditional types (T extends U ? X : Y) enable type-level branching. The infer keyword extracts types from positions within other types. Together they form TypeScript's type-level programming language — enabling patterns like extracting function return types, building recursive type transformations, and creating fully type-safe APIs that infer types from usage.

Interviewer's Intent

What the interviewer is really testing

This question probes three distinct competencies:

  • Type-level programming skill: Can you think about types as a computation that runs at compile time? Do you understand that TypeScript's type system is Turing-complete (bounded by a recursion depth limit of ~50 without tail-call optimization, ~1000 with)?
  • Ability to design type-safe APIs: Can you create APIs where the types flow through and the consumer gets full autocomplete and error checking without manual annotations?
  • Understanding of type inference flow: Do you know where TypeScript infers types, how inference sites work, and when you need explicit annotations vs. when inference handles it?

60-Second Answer

Concise interview response

Use this as your opening. Then dive deeper based on follow-ups.

Generics are type parameters — they let functions, classes, and interfaces work with any type while preserving type information through the computation. Think of them as "type arguments" that flow through like values do at runtime.

Conditional types (T extends U ? X : Y) are the ternary operator at the type level. They enable branching logic in types — choosing different output types based on what the input type is.

The infer keyword is pattern matching for types. It lets you extract a type from a position within another type — like extracting the return type from a function signature or the element type from an array.

For a type-safe event emitter, I'd define an event map as a generic parameter, then use keyof to constrain event names and indexed access types to infer the correct payload type for each event's handler:

interface EventMap {
  login: { userId: string; timestamp: number };
  logout: { reason: string };
}

class TypedEmitter<Events extends Record<string, unknown>> {
  on<K extends keyof Events>(
    event: K,
    handler: (payload: Events[K]) => void
  ): this { /* ... */ return this; }

  emit<K extends keyof Events>(
    event: K,
    payload: Events[K]
  ): void { /* ... */ }
}

const emitter = new TypedEmitter<EventMap>();
emitter.on('login', (payload) => {
  // payload is { userId: string; timestamp: number }
  console.log(payload.userId);
});
// emitter.emit('login', { reason: 'x' }); // ❌ Type error

Generic Constraints (extends)

Constraining type parameters for safety and inference

Basic Constraints

Without constraints, a generic type parameter can be anything. The extends keyword narrows what types are acceptable:

// Without constraint — T could be anything
function broken<T>(arg: T): number {
  return arg.length; // ❌ Property 'length' does not exist on type 'T'
}

// With constraint — T must have a length property
function withLength<T extends { length: number }>(arg: T): number {
  return arg.length; // ✅ Safe
}

withLength("hello");     // T = string, returns 5
withLength([1, 2, 3]);   // T = number[], returns 3
withLength({ length: 7 }); // T = { length: number }, returns 7
// withLength(42);        // ❌ number has no 'length'

Multiple Constraints with Intersection

interface Serializable {
  serialize(): string;
}

interface Loggable {
  log(level: string): void;
}

// T must satisfy BOTH interfaces
function process<T extends Serializable & Loggable>(item: T): string {
  item.log('info');
  return item.serialize();
}

keyof Constraint

// K is constrained to keys of T
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: 'Alice', age: 30, email: 'a@b.com' };
const name = getProperty(user, 'name');  // type: string
const age = getProperty(user, 'age');    // type: number
// getProperty(user, 'foo');             // ❌ 'foo' is not in keyof user

Constraint Narrows the Type Parameter

Important: The constraint is a minimum guarantee, not the actual type. T retains its full type — it doesn't collapse to the constraint.

function clone<T extends object>(source: T): T {
  return { ...source }; // Returns T, not just 'object'
}

const original = { x: 1, y: 2, label: 'point' };
const copy = clone(original);
// copy has type { x: number; y: number; label: string } — not just 'object'

Common Constraint Patterns

// Constructor constraint
type Constructor<T = unknown> = new (...args: any[]) => T;

function createInstance<T>(Ctor: Constructor<T>): T {
  return new Ctor();
}

// Function constraint
type AnyFunction = (...args: any[]) => any;

function memoize<T extends AnyFunction>(fn: T): T {
  const cache = new Map();
  return ((...args: any[]) => {
    const key = JSON.stringify(args);
    if (!cache.has(key)) cache.set(key, fn(...args));
    return cache.get(key);
  }) as T;
}

// Recursive constraint (self-referential)
interface TreeNode<T extends TreeNode<T>> {
  parent: T | null;
  children: T[];
}

Generic Inference

How TypeScript infers type arguments from usage

Inference Sites

TypeScript infers generic type arguments from inference sites — positions where the type parameter appears in the function signature:

function identity<T>(x: T): T {
  return x;
}

// T inferred from the argument
const a = identity(42);        // T = number (inferred from parameter)
const b = identity<string>("hi"); // T = string (explicit)

Multiple Inference Sites

function merge<T>(a: T, b: T): T {
  return { ...a, ...b };
}

// Both arguments are inference sites for T
// TS uses the "best common type" algorithm
merge({ x: 1 }, { x: 2 });           // T = { x: number }
merge({ x: 1 }, { x: 2, y: 3 });     // ❌ Type error without widening

// Fix: use separate type parameters
function merge2<T, U>(a: T, b: U): T & U {
  return { ...a, ...b };
}

Multiple Inference Candidates

// When the same type parameter appears in multiple positions,
// TS collects candidates and picks the best one

function firstOrDefault<T>(arr: T[], defaultValue: T): T {
  return arr.length > 0 ? arr[0] : defaultValue;
}

// T has two inference candidates: number (from arr) and number (from default)
firstOrDefault([1, 2, 3], 0);  // T = number ✅

// Conflicting candidates — widened to union
firstOrDefault([1, 2, 3], "fallback");  // ❌ string not assignable to number

Inference Priority

TypeScript uses these rules for inference priority:

  1. Explicit type arguments always win
  2. Contextual typing (callback return types) has high priority
  3. Co-variant positions (return types) are preferred over contra-variant (parameters)
  4. Later inference sites can refine earlier ones
// Inference from callback return type (contextual typing)
declare function createState<T>(init: () => T): { get(): T; set(v: T): void };

// T inferred from what the callback returns
const state = createState(() => ({ count: 0, label: 'hello' }));
state.get().count; // number ✅
state.set({ count: 1, label: 'world' }); // ✅

// Inference flows "backwards" into the callback parameter
declare function map<T, U>(arr: T[], fn: (item: T) => U): U[];

const lengths = map(['hello', 'world'], (s) => s.length);
// T = string (from array), U = number (from callback return)
// s is inferred as string without annotation

NoInfer<T> — Controlling Inference Sites (TS 5.4)

Sometimes you want to prevent a position from being an inference site — forcing inference from other positions only:

// Problem: T inferred from BOTH params — no validation
function createFSM<S extends string>(initial: S, states: S[]) {}
createFSM("typo", ["idle", "loading", "error"]); // ✅ No error — T widens to union

// Solution: NoInfer blocks inference from 'initial'
function createFSM<S extends string>(initial: NoInfer<S>, states: S[]) {}
createFSM("loading", ["idle", "loading", "error"]); // ✅ S inferred from states
createFSM("typo", ["idle", "loading", "error"]);    // ❌ "typo" not in S

// Another common use: default values
function createSignal<T>(value: T, defaultValue: NoInfer<T>) {}
createSignal(42, "oops"); // ❌ Error — T=number from first arg, string doesn't match

Interview tip: NoInfer<T> is increasingly asked about in 2024 interviews. It shows you understand the inference algorithm deeply enough to control it, not just use it. Pair it with your knowledge of inference sites from above.

Conditional Types

Type-level branching with extends

Basic Syntax

// Syntax: T extends U ? TrueType : FalseType
// "If T is assignable to U, resolve to TrueType, otherwise FalseType"

type IsString<T> = T extends string ? true : false;

type A = IsString<string>;   // true
type B = IsString<number>;   // false
type C = IsString<"hello">;  // true (literal extends string)

Nesting Conditional Types

type TypeName<T> =
  T extends string ? "string" :
  T extends number ? "number" :
  T extends boolean ? "boolean" :
  T extends undefined ? "undefined" :
  T extends Function ? "function" :
  "object";

type T0 = TypeName<string>;      // "string"
type T1 = TypeName<() => void>;  // "function"
type T2 = TypeName<string[]>;    // "object"

Practical Examples

// IsArray — checks if T is an array type
type IsArray<T> = T extends readonly any[] ? true : false;

type X = IsArray<number[]>;       // true
type Y = IsArray<readonly string[]>; // true
type Z = IsArray<string>;         // false

// NonNullable implementation
type MyNonNullable<T> = T extends null | undefined ? never : T;

type Safe = MyNonNullable<string | null | undefined>; // string

// Flatten one level
type Flatten<T> = T extends Array<infer U> ? U : T;

type Flat = Flatten<number[]>;   // number
type NoOp = Flatten<string>;     // string

Relationship to Ternary Operator

  RUNTIME                          TYPE-LEVEL
  ───────                          ──────────
  condition ? a : b                T extends U ? X : Y

  if (x instanceof Array)         T extends Array<any>
    return x[0]                     ? T[number]
  else                              : T
    return x

  Evaluated at runtime             Evaluated at compile time
  Produces values                  Produces types
  Can have side effects            Pure (no side effects)

Distributive Conditional Types

When and how conditional types distribute over unions

When Distribution Happens

A conditional type distributes over a union when the checked type is a naked type parameter (not wrapped in anything):

type ToArray<T> = T extends any ? T[] : never;

// T is "naked" — distribution happens
type Result = ToArray<string | number>;
// Distributes: ToArray<string> | ToArray<number>
// = string[] | number[]
// NOT (string | number)[]

How Distribution Works Step-by-Step

  Input: ToArray<string | number>

  Step 1: Distribute over union members
    → ToArray<string> | ToArray<number>

  Step 2: Evaluate each member
    → (string extends any ? string[] : never)
    | (number extends any ? number[] : never)

  Step 3: Resolve
    → string[] | number[]

Preventing Distribution

// Wrap in tuple to prevent distribution
type ToArrayNonDist<T> = [T] extends [any] ? T[] : never;

type Result2 = ToArrayNonDist<string | number>;
// = (string | number)[]  — no distribution!

// Why? [string | number] is NOT a naked type parameter
// It's a tuple containing the union

Exclude & Extract Implementation

// Exclude: remove members from a union
type MyExclude<T, U> = T extends U ? never : T;

type E1 = MyExclude<'a' | 'b' | 'c', 'a'>;
// Distributes:
//   'a' extends 'a' ? never : 'a'  → never
// | 'b' extends 'a' ? never : 'b'  → 'b'
// | 'c' extends 'a' ? never : 'c'  → 'c'
// = 'b' | 'c'

// Extract: keep only members assignable to U
type MyExtract<T, U> = T extends U ? T : never;

type E2 = MyExtract<string | number | boolean, string | boolean>;
// = string | boolean

Practical Examples

// Filter object keys by value type
type KeysOfType<T, V> = {
  [K in keyof T]: T[K] extends V ? K : never;
}[keyof T];

interface User {
  id: number;
  name: string;
  email: string;
  age: number;
  isAdmin: boolean;
}

type StringKeys = KeysOfType<User, string>; // "name" | "email"
type NumberKeys = KeysOfType<User, number>; // "id" | "age"

// Discriminated union filtering
type SuccessEvents = Extract<
  | { type: 'success'; data: unknown }
  | { type: 'error'; message: string }
  | { type: 'loading' },
  { type: 'success' }
>;
// = { type: 'success'; data: unknown }

The infer Keyword

Pattern matching and type extraction

Pattern Matching in Types

The infer keyword declares a type variable within a conditional type's extends clause. It "captures" whatever type occupies that position:

// infer R captures the return type
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

type A = MyReturnType<() => string>;           // string
type B = MyReturnType<(x: number) => boolean>; // boolean
type C = MyReturnType<string>;                  // never (not a function)

Extracting Parameters

// Capture all parameters as a tuple
type MyParameters<T> = T extends (...args: infer P) => any ? P : never;

type Params = MyParameters<(a: string, b: number) => void>;
// [a: string, b: number]

// First parameter only
type FirstParam<T> = T extends (first: infer F, ...rest: any[]) => any
  ? F
  : never;

type First = FirstParam<(x: string, y: number) => void>; // string

Extracting Promise Inner Type

// Unwrap one level
type Awaited1<T> = T extends Promise<infer U> ? U : T;

type R1 = Awaited1<Promise<string>>;          // string
type R2 = Awaited1<Promise<Promise<number>>>; // Promise<number> (one level)

// Recursively unwrap (like built-in Awaited)
type DeepAwaited<T> = T extends Promise<infer U> ? DeepAwaited<U> : T;

type R3 = DeepAwaited<Promise<Promise<Promise<string>>>>; // string

Extracting Array Element Type

type ElementType<T> = T extends readonly (infer E)[] ? E : T;

type El1 = ElementType<string[]>;          // string
type El2 = ElementType<readonly number[]>; // number
type El3 = ElementType<[string, number]>;  // string | number (tuple → union)
type El4 = ElementType<boolean>;           // boolean (not an array)

Multiple infer Positions

// Extract key and value types from a Map
type MapTypes<T> = T extends Map<infer K, infer V>
  ? { key: K; value: V }
  : never;

type M = MapTypes<Map<string, number>>; // { key: string; value: number }

// Extract head and tail of a tuple
type Head<T extends any[]> = T extends [infer H, ...any[]] ? H : never;
type Tail<T extends any[]> = T extends [any, ...infer R] ? R : never;

type H = Head<[1, 2, 3]>; // 1
type T = Tail<[1, 2, 3]>; // [2, 3]

infer in Template Literal Types

// Parse dot-separated paths
type Split<S extends string, D extends string> =
  S extends `${infer Head}${D}${infer Tail}`
    ? [Head, ...Split<Tail, D>]
    : [S];

type Parts = Split<'user.profile.name', '.'>; // ['user', 'profile', 'name']

// Extract route params
type ExtractParams<T extends string> =
  T extends `${string}:${infer Param}/${infer Rest}`
    ? { [K in Param | keyof ExtractParams<Rest>]: string }
    : T extends `${string}:${infer Param}`
      ? { [K in Param]: string }
      : {};

type RouteParams = ExtractParams<'/users/:id/posts/:postId'>;
// { id: string; postId: string }

Recursive Conditional Types

Deep type operations and recursive patterns

Deep Type Operations

// DeepPartial — make all properties optional recursively
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

interface Config {
  server: {
    host: string;
    port: number;
    ssl: {
      enabled: boolean;
      cert: string;
    };
  };
  database: {
    url: string;
    pool: { min: number; max: number };
  };
}

// All nested properties become optional
type PartialConfig = DeepPartial<Config>;
const patch: PartialConfig = {
  server: { ssl: { enabled: true } }  // ✅ No need for host, port, cert
};

Recursive Type Limits

Warning: TypeScript has a recursion depth limit (~50 levels pre-4.5, ~1000 with tail-call optimization). Exceeding it causes "Type instantiation is excessively deep and possibly infinite" errors.

// This will hit the recursion limit with large inputs
type TupleOfSize<
  N extends number,
  Acc extends any[] = []
> = Acc['length'] extends N
  ? Acc
  : TupleOfSize<N, [...Acc, unknown]>;

type T5 = TupleOfSize<5>;    // [unknown, unknown, unknown, unknown, unknown]
// type T1000 = TupleOfSize<1000>; // ❌ Might hit limit depending on TS version

Tail-Call Optimization (TS 4.5+)

TypeScript 4.5 introduced tail-call elimination for recursive conditional types. The recursion must be in "tail position" — the result of the recursive call is returned directly:

// ✅ Tail-recursive — the recursive call IS the result
type ReverseStr<
  S extends string,
  Acc extends string = ''
> = S extends `${infer First}${infer Rest}`
  ? ReverseStr<Rest, `${First}${Acc}`>  // tail position
  : Acc;

type Rev = ReverseStr<'hello'>; // 'olleh'

// ❌ NOT tail-recursive — wraps the recursive result
type BadReverse<S extends string> =
  S extends `${infer First}${infer Rest}`
    ? `${BadReverse<Rest>}${First}`  // NOT tail position (wraps result)
    : '';

Practical Recursive Types

// Paths — get all dot-notation paths of an object
type Paths<T, Prefix extends string = ''> = T extends object
  ? {
      [K in keyof T & string]: K extends string
        ? Prefix extends ''
          ? K | Paths<T[K], K>
          : `${Prefix}.${K}` | Paths<T[K], `${Prefix}.${K}`>
        : never;
    }[keyof T & string]
  : never;

type ConfigPaths = Paths<Config>;
// "server" | "server.host" | "server.port" | "server.ssl" | ...

// DeepFlatten — flatten nested arrays to any depth
type DeepFlatten<T> = T extends readonly (infer U)[]
  ? DeepFlatten<U>
  : T;

type Flat = DeepFlatten<number[][][]>; // number

// JSON-compatible types (recursive definition)
type JSONValue =
  | string
  | number
  | boolean
  | null
  | JSONValue[]
  | { [key: string]: JSONValue };

Type-Level Programming

TypeScript's type system as a programming language

Types as a Programming Language

TypeScript's type system is Turing-complete. You can perform loops (recursion), branching (conditional types), data structures (tuples, mapped types), and even arithmetic (via tuple length). But just because you can doesn't mean you should.

  TYPE-LEVEL PROGRAMMING PRIMITIVES
  ──────────────────────────────────
  Variables       → Type parameters (T, U, K)
  Functions       → Generic types: type F<T> = ...
  If/else         → Conditional types: T extends U ? X : Y
  Pattern match   → infer keyword
  Loop            → Recursive conditional types
  Data structures → Tuples ([A, B, C]), mapped types
  Arithmetic      → Tuple length manipulation
  String ops      → Template literal types

Type-Level Arithmetic (Tuple Manipulation)

// Addition via tuple concatenation (reuses TupleOfSize from above)
type Add<A extends number, B extends number> =
  [...TupleOfSize<A>, ...TupleOfSize<B>]['length'] extends infer R
    ? R extends number ? R : never
    : never;

type Sum = Add<3, 4>;  // 7

// Subtraction via tuple difference
type Subtract<A extends number, B extends number> =
  TupleOfSize<A> extends [...TupleOfSize<B>, ...infer Rest]
    ? Rest['length']
    : never;

type Diff = Subtract<10, 3>; // 7

// Comparison
type IsGreater<A extends number, B extends number> =
  TupleOfSize<A> extends [...TupleOfSize<B>, ...infer Rest]
    ? Rest extends []
      ? false
      : true
    : false;

type GT = IsGreater<5, 3>;  // true
type EQ = IsGreater<3, 3>;  // false

Type-Level String Parsing

// Parse a simple CSS color format
type ParseHex<S extends string> =
  S extends `#${infer R}`
    ? R extends `${infer A}${infer B}${infer C}${infer D}${infer E}${infer F}`
      ? { r: `${A}${B}`; g: `${C}${D}`; b: `${E}${F}` }
      : never
    : never;

type Color = ParseHex<'#ff8800'>;
// { r: 'ff'; g: '88'; b: '00' }

// Parse query string
type ParseQS<S extends string> =
  S extends `${infer Key}=${infer Value}&${infer Rest}`
    ? { [K in Key]: Value } & ParseQS<Rest>
    : S extends `${infer Key}=${infer Value}`
      ? { [K in Key]: Value }
      : {};

type Query = ParseQS<'name=alice&age=30&city=nyc'>;
// { name: 'alice' } & { age: '30' } & { city: 'nyc' }

Building Complex Utility Types

Advanced utility type implementations

DeepPartial<T>

type DeepPartial<T> = T extends Function
  ? T  // Don't recurse into functions
  : T extends object
    ? { [K in keyof T]?: DeepPartial<T[K]> }
    : T;

// Handles edge cases: arrays, Maps, Sets
type DeepPartialAdvanced<T> =
  T extends Function ? T :
  T extends Map<infer K, infer V> ? Map<K, DeepPartialAdvanced<V>> :
  T extends Set<infer U> ? Set<DeepPartialAdvanced<U>> :
  T extends Array<infer U> ? Array<DeepPartialAdvanced<U>> :
  T extends object ? { [K in keyof T]?: DeepPartialAdvanced<T[K]> } :
  T;

DeepReadonly<T>

type DeepReadonly<T> =
  T extends Function ? T :
  T extends Map<infer K, infer V> ? ReadonlyMap<K, DeepReadonly<V>> :
  T extends Set<infer U> ? ReadonlySet<DeepReadonly<U>> :
  T extends Array<infer U> ? readonly DeepReadonly<U>[] :
  T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } :
  T;

// Usage
type FrozenConfig = DeepReadonly<Config>;
// All nested properties are readonly — any mutation is a compile error

PathType (Dot-Notation Access Typing)

// Get the type at a dot-separated path
type PathType<T, P extends string> =
  P extends `${infer Key}.${infer Rest}`
    ? Key extends keyof T
      ? PathType<T[Key], Rest>
      : never
    : P extends keyof T
      ? T[P]
      : never;

interface AppState {
  user: {
    profile: { name: string; avatar: string };
    settings: { theme: 'dark' | 'light'; lang: string };
  };
  posts: Array<{ id: number; title: string }>;
}

type Theme = PathType<AppState, 'user.settings.theme'>; // 'dark' | 'light'
type Name = PathType<AppState, 'user.profile.name'>;    // string

// Type-safe getter function
function get<T, P extends Paths<T>>(obj: T, path: P): PathType<T, P> {
  return path.split('.').reduce((o: any, k) => o?.[k], obj);
}

Type-Safe Event Emitter (Full Implementation)

// Define event map interface
interface AppEvents {
  'user:login': { userId: string; timestamp: number };
  'user:logout': { reason: 'manual' | 'timeout' | 'error' };
  'data:loaded': { items: unknown[]; total: number };
  'error': { code: number; message: string };
}

// Type-safe emitter class
class TypedEventEmitter<Events extends Record<string, unknown>> {
  private listeners = new Map<string, Set<Function>>();

  on<K extends keyof Events & string>(
    event: K,
    handler: (payload: Events[K]) => void
  ): () => void {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, new Set());
    }
    this.listeners.get(event)!.add(handler);

    // Return unsubscribe function
    return () => {
      this.listeners.get(event)?.delete(handler);
    };
  }

  once<K extends keyof Events & string>(
    event: K,
    handler: (payload: Events[K]) => void
  ): () => void {
    const wrapper = (payload: Events[K]) => {
      unsub();
      handler(payload);
    };
    const unsub = this.on(event, wrapper);
    return unsub;
  }

  emit<K extends keyof Events & string>(
    event: K,
    payload: Events[K]
  ): void {
    this.listeners.get(event)?.forEach(handler => handler(payload));
  }

  removeAllListeners<K extends keyof Events & string>(event?: K): void {
    if (event) {
      this.listeners.delete(event);
    } else {
      this.listeners.clear();
    }
  }
}

// Usage — fully type-safe

  // console.log(payload.foo);       // ❌ Property 'foo' does not exist

Strict Omit (Errors on Invalid Keys)

// Built-in Omit allows any string — no error for typos
type UnsafeResult = Omit<User, 'naem'>; // No error! 'naem' is just ignored

// Strict version that requires valid keys
type StrictOmit<T, K extends keyof T> = Omit<T, K>;

// type Bad = StrictOmit<User, 'naem'>; // ❌ Type error!
type Good = StrictOmit<User, 'name'>;   // ✅ { id; email; age; isAdmin }

// Even stricter — also preserves exact types
type ExactOmit<T, K extends keyof T> = {
  [P in Exclude<keyof T, K>]: T[P];
};

Generic Function Overloads

When generics aren't enough and overloads are needed

When Generics Aren't Enough

Generics express "same type flows through." Overloads express "different input shapes produce different output shapes" when the relationship isn't expressible with conditional types:

// Problem: return type depends on input in complex ways
// Generic approach — loses precision
function parseGeneric<T>(input: string, format: T): unknown {
  // Can't express: format='json' → object, format='number' → number
  return undefined;
}

// Overload approach — precise per case
function parse(input: string, format: 'json'): object;
function parse(input: string, format: 'number'): number;
function parse(input: string, format: 'boolean'): boolean;
function parse(input: string, format: string): unknown;
function parse(input: string, format: string): unknown {
  switch (format) {
    case 'json': return JSON.parse(input);
    case 'number': return Number(input);
    case 'boolean': return input === 'true';
    default: return input;
  }
}

const obj = parse('{"a":1}', 'json');    // object
const num = parse('42', 'number');        // number

Overload Resolution Order

TypeScript tries overloads top-to-bottom and uses the first match. Put the most specific overloads first.

Note: This "top-to-bottom" rule applies to call resolution. In declaration merging (Ch13), later declarations get higher priority — the opposite direction. Don't confuse these two contexts.

// ❌ Wrong order — generic overload catches everything
function bad(x: any): any;
function bad(x: string): string;  // Never reached!
function bad(x: any) { return x; }

// ✅ Correct order — specific first
function good(x: string): string;
function good(x: number): number;
function good(x: any): any;
function good(x: any) { return x; }

Conditional Return Types vs Overloads

// Conditional return type — single signature, type-level logic
function createElement<T extends string>(
  tag: T
): T extends 'input' ? HTMLInputElement
  : T extends 'div' ? HTMLDivElement
  : T extends 'span' ? HTMLSpanElement
  : HTMLElement {
  return document.createElement(tag) as any;
}

// vs. Overloads — multiple signatures
function createElement2(tag: 'input'): HTMLInputElement;
function createElement2(tag: 'div'): HTMLDivElement;
function createElement2(tag: 'span'): HTMLSpanElement;
function createElement2(tag: string): HTMLElement;
function createElement2(tag: string): HTMLElement {
  return document.createElement(tag);
}

Practical Comparison

Aspect Generics + Conditionals Overloads
Extensibility New cases need type update Add new overload signature
Implementation Single function body Single body + multiple sigs
Error messages Can be cryptic Clear "no matching overload"
Composability Works with other generics Hard to compose/wrap
Dynamic inputs Resolves at type level Picks broadest match

Higher-Kinded Types (Workarounds)

Advanced / Library Authors Only: HKTs are rarely asked in FAANG interviews and the TypeScript encoding is convoluted. This section is primarily relevant for library authors (fp-ts, Effect) or if an interviewer specifically mentions category theory/functor abstractions. Presenting this unprompted in an interview can backfire — focus on practical generics and conditional types instead.

Abstracting over type constructors in TypeScript

What Are Higher-Kinded Types?

A higher-kinded type (HKT) is a type that takes another type constructor as a parameter — a "type of types." Think of it as a generic that accepts not just string or number, but Array or Promise themselves (the container, not the contained):

  Regular Generic:    Array<string>    — Array is applied to string
  Higher-Kinded:      Functor<Array>   — Functor is applied to Array itself

  Kind system:
    string         : *           (a concrete type)
    Array<string>  : *           (a concrete type)
    Array          : * → *       (takes one type, produces a type)
    Map            : * → * → *   (takes two types)
    Functor        : (* → *) → * (takes a type constructor!)

Why TypeScript Doesn't Support HKTs Natively

TypeScript's type parameter system only supports * (concrete types). You can't write type Functor<F<_>>. The generic parameter F can only be a concrete type, not a type constructor.

Workaround: Interface Extension Pattern

// Step 1: Define a "type class" registry
interface TypeRegistry<A = unknown> {
  Array: Array<A>;
  Promise: Promise<A>;
  Set: Set<A>;
}

// Step 2: Use string keys to reference type constructors
type Apply<F extends keyof TypeRegistry, A> = TypeRegistry<A>[F];

// Step 3: Write generic code over type constructors
type MapOver<F extends keyof TypeRegistry, Items extends any[]> = {
  [K in keyof Items]: Apply<F, Items[K]>;
};

type Wrapped = MapOver<'Promise', [string, number, boolean]>;
// [Promise<string>, Promise<number>, Promise<boolean>]

type InSets = MapOver<'Set', [string, number]>;
// [Set<string>, Set<number>]

Workaround: Generic Type Maps

// Encode HKTs via a "URI" pattern (inspired by fp-ts)
const URI = Symbol('URI');

interface HKT<URI, A> {
  readonly _URI: URI;
  readonly _A: A;
}

// Each type constructor declares its URI
interface ArrayHKT extends HKT<'Array', unknown> {
  readonly type: Array<this['_A']>;
}

interface PromiseHKT extends HKT<'Promise', unknown> {
  readonly type: Promise<this['_A']>;
}

// "Kind" type applies a type constructor to an argument
type Kind<F extends { type: unknown; _A: unknown }, A> =
  (F & { _A: A })['type'];

type Result1 = Kind<ArrayHKT, string>;   // string[]
type Result2 = Kind<PromiseHKT, number>; // Promise<number>

Comparison with fp-ts Approach

// fp-ts uses a similar pattern with URIs and module augmentation
// Simplified version of how fp-ts defines Functor:

interface URI2HKT<A> {} // Augmented by each module

type URIS = keyof URI2HKT<unknown>;
type HKT2<URI extends URIS, A> = URI2HKT<A>[URI];

// Functor interface
interface Functor<F extends URIS> {
  map: <A, B>(fa: HKT2<F, A>, f: (a: A) => B) => HKT2<F, B>;
}

// Trade-off: complex types but enables truly generic FP code
// Most teams should prefer simpler patterns unless building an FP library

Full Event Emitter (Production-Ready)

type EventHandler<T = unknown> = (payload: T) => void;
type WildcardHandler<Events> = (
  event: keyof Events,
  payload: Events[keyof Events]
) => void;

class EventEmitter<Events extends Record<string, unknown>> {
  private handlers = new Map<keyof Events | '*', Set<Function>>();

  on<K extends keyof Events>(event: K, handler: EventHandler<Events[K]>): this;
  on(event: '*', handler: WildcardHandler<Events>): this;
  on(event: string, handler: Function): this {
    if (!this.handlers.has(event)) {
      this.handlers.set(event, new Set());
    }
    this.handlers.get(event)!.add(handler);
    return this;
  }

  off<K extends keyof Events>(event: K, handler: EventHandler<Events[K]>): this;
  off(event: '*', handler: WildcardHandler<Events>): this;
  off(event: string, handler: Function): this {
    this.handlers.get(event)?.delete(handler);
    return this;
  }

  emit<K extends keyof Events>(event: K, payload: Events[K]): this {
    // Notify specific handlers
    this.handlers.get(event)?.forEach((h) => h(payload));
    // Notify wildcard handlers
    this.handlers.get('*')?.forEach((h) => h(event, payload));
    return this;
  }

  once<K extends keyof Events>(event: K, handler: EventHandler<Events[K]>): this {
    const wrapper: EventHandler<Events[K]> = (payload) => {
      this.off(event, wrapper);
      handler(payload);
    };
    return this.on(event, wrapper);
  }

  listenerCount(event: keyof Events): number {
    return this.handlers.get(event)?.size ?? 0;
  }

  removeAllListeners(event?: keyof Events): this {
    if (event) {
      this.handlers.delete(event);
    } else {
      this.handlers.clear();
    }
    return this;
  }
}

Common Mistakes

Five pitfalls to avoid with generics and conditional types

1. Over-Constraining Generics

// ❌ Over-constrained — forces callers to match exact shape
function bad<T extends { id: number; name: string; email: string }>(item: T) {
  return item.id;
}

// ✅ Constrain only what you need
function good<T extends { id: number }>(item: T) {
  return item.id;
}

// Now ANY object with an `id` works
good({ id: 1, name: 'Alice', extra: true }); // ✅

2. Forgetting Distribution Behavior

// ❌ Unexpected distribution
type IsNever<T> = T extends never ? true : false;
type Oops = IsNever<never>; // never! (not true)
// Why? `never` is an empty union — distributing over nothing yields never

// ✅ Prevent distribution for never-checks
type IsNeverFixed<T> = [T] extends [never] ? true : false;
type Fixed = IsNeverFixed<never>; // true ✅

// ❌ Forgetting that conditional distributes
type Nullable<T> = T extends any ? T | null : never;
type Bad = Nullable<string | number>; // string | number | null
// Each member gets null: (string | null) | (number | null) = string | number | null
// This happens to be the same, but for other cases distribution matters!

3. Using any as Default Type Parameter

// ❌ any as default defeats the purpose of generics
function fetch<T = any>(url: string): Promise<T> {
  return window.fetch(url).then(r => r.json());
}
const data = fetch('/api'); // Promise<any> — no safety!

// ✅ Use unknown and require explicit type
function fetchTyped<T = unknown>(url: string): Promise<T> {
  return window.fetch(url).then(r => r.json());
}
const safe = fetchTyped<User[]>('/api/users'); // Promise<User[]>

// ✅ Even better — validate at runtime
function fetchValidated<T>(url: string, schema: Schema<T>): Promise<T> {
  return window.fetch(url)
    .then(r => r.json())
    .then(data => schema.parse(data));
}

4. Too Many Type Parameters

// ❌ Unreadable — too many type params
function transform<T, U, V, W, X>(
  input: T,
  step1: (a: T) => U,
  step2: (b: U) => V,
  step3: (c: V) => W,
  step4: (d: W) => X
): X {
  return step4(step3(step2(step1(input))));
}

// ✅ Use function composition or pipe
function pipe<A, B>(a: A, ab: (a: A) => B): B;
function pipe<A, B, C>(a: A, ab: (a: A) => B, bc: (b: B) => C): C;
function pipe<A, B, C, D>(a: A, ab: (a: A) => B, bc: (b: B) => C, cd: (c: C) => D): D;
function pipe(initial: unknown, ...fns: Function[]): unknown {
  return fns.reduce((acc, fn) => fn(acc), initial);
}

5. Not Using Inference (Manual Annotations Everywhere)

// ❌ Redundant type annotations — let inference do its job
const result: Array<string> = ['hello', 'world'].map<string>(
  (item: string): string => item.toUpperCase()
);

// ✅ Let TypeScript infer
const result2 = ['hello', 'world'].map(item => item.toUpperCase());
// TypeScript infers: string[]

// ❌ Specifying type parameter that could be inferred
function identity<T>(x: T): T { return x; }
const x: string = identity<string>('hello'); // Redundant <string>

// ✅ Let inference flow
const y = identity('hello'); // y: string — inferred!

Rule of thumb: If you're writing the same type in both the type parameter and the argument, you're probably duplicating what inference would give you for free.

Trade-offs

When to use which approach
Approach Pros Cons Use When
Complex types Maximum safety, catches bugs at compile time, great DX for consumers Hard to maintain, slow compilation, cryptic errors for authors Library APIs, shared infrastructure code
Simple + assertions Easy to read, fast compilation, easy to maintain Runtime errors possible, less IDE support, trust-based Application code, small teams, prototypes
Generics Type flows through, reusable, composable Can be over-used, confusing when nested, inference sometimes fails When the same logic applies to multiple types
Overloads Clear per-case types, good error messages, explicit Verbose, hard to compose, doesn't scale to many cases Small number of distinct input/output shapes
Conditional types Dynamic output types, works with generics, powerful Hard to debug, distribution surprises, limits on recursion When output type depends on input type programmatically
Union types Simple, well-understood, narrowing support Less precise than conditional return, no "computed" types When all possible types are known statically
Type safety Catches errors early, documents intent, refactor-safe Slower compilation, steeper learning curve, boilerplate Always in shared code; selectively in app code
Compilation speed Fast feedback, better DX, CI/CD efficiency May sacrifice type precision, runtime errors possible Large codebases where tsc takes >30s

Senior insight: The right answer is almost always "it depends on the audience." Library code serving 1000 developers justifies complex types. Application code read by 5 teammates should prefer simplicity.

Follow-up Questions

7 common follow-ups with concise answers

1. "How do you debug complex conditional types?"

Use type aliases as "breakpoints" — assign intermediate results to named types and hover over them in the IDE. Use the type _Debug = YourComplexType pattern. For distribution issues, wrap in tuples to test both distributed and non-distributed forms. The VS Code "Type Challenges" extension can also help visualize.

2. "What's the difference between extends in generics vs. conditional types?"

In generics (T extends U), it's a constraint — "T must be assignable to U." In conditional types (T extends U ? X : Y), it's a test — "is T assignable to U?" The syntax is identical but the semantics differ: constraint restricts what you can pass, conditional branches on what was passed.

3. "When would you use infer vs. indexed access types?"

// Indexed access — when you know the structure
type ReturnViaIndex = ((...args: any[]) => string) extends ((...args: any[]) => infer R) ? R : never;

// But for known shapes, indexed access is simpler:
type ArrayElement = string[][number]; // string

// Use infer when:
// 1. The position isn't directly indexable
// 2. You're pattern-matching a complex structure
// 3. You need to extract from a function signature

4. "How do variance annotations (in/out) relate to generics?"

TypeScript 4.7 added explicit variance annotations. out T means T is covariant (only appears in output positions), in T means contravariant (input positions). They help TypeScript check structural compatibility faster and catch variance errors earlier:

interface Producer<out T> {
  get(): T;
  // put(value: T): void; // ❌ Error: T used in 'in' position
}

interface Consumer<in T> {
  accept(value: T): void;
  // get(): T; // ❌ Error: T used in 'out' position
}

5. "How do you handle generic types with React's forwardRef?"

// Problem: forwardRef doesn't preserve generic parameters
// Solution: Type assertion pattern

interface GenericListProps<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}

// Workaround for forwardRef with generics
function GenericListInner<T>(
  props: GenericListProps<T> & { ref?: React.Ref<HTMLUListElement> }
) {
  return <ul ref={props.ref}>{props.items.map(props.renderItem)}</ul>;
}

// Or use the newer React.forwardRef pattern with type assertion
const GenericList = React.forwardRef(GenericListInner) as <T>(
  props: GenericListProps<T> & { ref?: React.Ref<HTMLUListElement> }
) => React.ReactElement;

6. "What are template literal types and how do they compose with conditionals?"

// Template literals create new string literal types
type EventName<T extends string> = `on${Capitalize<T>}`;
type ChangeEvent = EventName<'change'>; // 'onChange'

// Combined with conditionals and infer for parsing
type ParseEvent<T extends string> =
  T extends `on${infer E}`
    ? Uncapitalize<E>
    : T;

type Parsed = ParseEvent<'onClick'>; // 'click'

// Powerful composition: auto-generate event handler types
type Handlers<Events extends Record<string, unknown>> = {
  [K in keyof Events as `on${Capitalize<string & K>}`]: (
    payload: Events[K]
  ) => void;
};

type AppHandlers = Handlers<{ click: MouseEvent; scroll: Event }>;
// { onClick: (payload: MouseEvent) => void; onScroll: (payload: Event) => void }

7. "How do you test complex types?"

// Type-level testing utilities
type Expect<T extends true> = T;
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2)
    ? true
    : false;

// Write type-level test cases
type TestCases = [
  Expect<Equal<MyReturnType<() => string>, string>>,
  Expect<Equal<MyReturnType<() => void>, void>>,
  Expect<Equal<IsNeverFixed<never>, true>>,
  Expect<Equal<IsNeverFixed<string>, false>>,
];

// If any test fails, you get a compile error
// Libraries: tsd, expect-type, @type-challenges/utils

Key Points to Hit in Your Answer

  • Generics preserve type information through computations
  • Constraints (extends) narrow what's acceptable while keeping the full type
  • Conditional types are the ternary operator at type level
  • Distribution happens with naked type parameters in conditionals
  • infer is pattern matching — it captures types from positions
  • Recursive types enable deep transformations (with depth limits)
  • The event emitter pattern demonstrates generics + keyof + indexed access
  • Know when complexity is justified vs. when simpler types suffice

What NOT to Say

  • Don't say: "Generics are like templates in C++." — They're structurally typed and erased, not monomorphized.
  • Don't say: "You should always use the most type-safe approach." — Over-engineering types has real costs (compilation speed, maintainability, error readability).
  • Don't say: "I use any when generics get complicated." — This reveals you give up rather than finding the right abstraction level.
  • Don't say: "Conditional types always distribute." — Only naked type parameters distribute. Show you understand the nuance.
  • Don't say: "TypeScript's type system can do anything." — It has practical limits (recursion depth, compilation speed, error readability). Acknowledge trade-offs.
  • Don't confuse: Constraints (T extends U in generics) with conditional tests (T extends U ? X : Y). Same keyword, different semantics.

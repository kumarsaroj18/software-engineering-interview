Hard React Lanes Priority Scheduling

Chapter 16: Lanes, Priority & Scheduling

Key Takeaway: Lanes are a bitmask-based priority system replacing the old expiration time model. Each update is assigned a lane (SyncLane for user input, TransitionLane for non-urgent updates, IdleLane for background work). React can interrupt a lower-priority render when a higher-priority update arrives, restart the render with the new update included, and prevent starvation of lower-priority lanes through entanglement and expiration.

Interviewer Intent

Why interviewers ask about Lanes & Scheduling

When an interviewer asks "How does React's Lane model work for priority scheduling? What happens when a high-priority update interrupts a low-priority render?", they want to assess:

  • Whether you understand React's concurrent rendering at the scheduler level
  • Your grasp of bitmask-based priority systems and why they replaced expiration times
  • Can you explain interrupt/restart mechanics without hand-waving
  • Do you understand the real-world implications for app performance
  • Are you familiar with starvation prevention and entanglement concepts

Signal they're looking for: Deep systems-level understanding of React's internals, not just API-level knowledge of useTransition or Suspense.

Quick Answer

30-second answer for time-pressured interviews

React uses a 31-bit integer where each bit represents a "lane" — a priority level. Updates are assigned lanes based on their origin: user clicks get SyncLane (highest priority), transitions get TransitionLanes, and background work gets IdleLane. When a high-priority update arrives during a low-priority render, React checks shouldYield(), abandons the in-progress work, and restarts the render loop from the fiber root with the higher-priority lanes included. Lower-priority lanes are prevented from starving through expiration timestamps and entanglement — a mechanism that forces certain lanes to always render together.

Interview tip: Mention that lanes replaced expirationTime because bitmasks allow multiple independent priority levels to be tracked simultaneously without creating ordering constraints.

Lane Bit Representation

How lanes are encoded as a 31-bit integer bitmask

Lanes use a 31-bit integer (JavaScript's bitwise operators work on 32-bit signed integers, so React uses 31 bits to avoid the sign bit). Each lane occupies exactly one bit position.

Note: The lane values below are simplified for clarity. The actual React source interleaves hydration lanes (SyncHydrationLane, InputContinuousHydrationLane, etc.) between the primary lanes, shifting bit positions. The conceptual model and bitmask operations remain the same — what matters for interviews is understanding the priority ordering, bitwise mechanics, and scheduling behavior, not memorizing exact bit positions.

// Simplified lane representation (conceptual model)
// Each lane is a single bit in a 31-bit integer
export const NoLanes    = /*                        */ 0b0000000000000000000000000000000;
export const NoLane     = /*                        */ 0b0000000000000000000000000000000;
export const SyncLane   = /*                        */ 0b0000000000000000000000000000001;
export const InputContinuousLane = /*               */ 0b0000000000000000000000000000100;
export const DefaultLane = /*                       */ 0b0000000000000000000000000010000;
export const TransitionLane1 = /*                   */ 0b0000000000000000000000001000000;
export const TransitionLane2 = /*                   */ 0b0000000000000000000000010000000;
export const IdleLane   = /*                        */ 0b0100000000000000000000000000000;
export const OffscreenLane = /*                     */ 0b1000000000000000000000000000000;

Merging Lanes with Bitwise OR

Multiple lanes are combined into a single integer using the OR operator. This allows React to track which lanes have pending work:

// Merging lanes — combining pending work
function mergeLanes(a, b) {
  return a | b;
}

// Example: SyncLane | DefaultLane
// 0b0000000000000000000000000000001
// 0b0000000000000000000000000010000
// Result: 0b0000000000000000000000000010001
const pendingLanes = mergeLanes(SyncLane, DefaultLane); // 17

Checking Lanes with Bitwise AND

// Checking if a specific lane is included in a set
function includesSomeLane(set, subset) {
  return (set & subset) !== NoLanes;
}

// Check if SyncLane is in our pendingLanes
includesSomeLane(pendingLanes, SyncLane); // true
includesSomeLane(pendingLanes, IdleLane); // false

// Removing a lane from a set
function removeLanes(set, subset) {
  return set & ~subset;
}

// After processing SyncLane, remove it
const remaining = removeLanes(pendingLanes, SyncLane);
// Result: 0b0000000000000000000000000010000 (only DefaultLane)

function getHighestPriorityLane(lanes) {
  // Returns the rightmost bit (lowest position = highest priority)
  return lanes & -lanes;

Priority Assignment

How React assigns lanes to updates based on context

When you call setState, React doesn't immediately re-render. Instead, it assigns a lane to the update based on the execution context:

// Simplified requestUpdateLane logic
function requestUpdateLane(fiber) {
  // 1. Check if we're inside flushSync
  if (isFlushingSyncQueue) {
    return SyncLane;
  }

  // 2. Check if we're inside a transition
  const transition = ReactCurrentBatchConfig.transition;
  if (transition !== null) {
    // Claim the next available transition lane
    return claimNextTransitionLane();
  }

  // 3. Check the current event priority
  const updateLane = getCurrentUpdatePriority();
  if (updateLane !== NoLane) {
    return updateLane;
  }

  // 4. Check the current event in the browser
  const eventLane = getCurrentEventPriority();
  return eventLane;
}

// getCurrentEventPriority maps DOM events to lanes:
function getCurrentEventPriority() {
  const currentEvent = window.event;
  if (currentEvent === undefined) {
    return DefaultLane;
  }
  // Discrete events: click, keydown, input, focus, blur
  // → DiscreteEventPriority → SyncLane
  // Continuous events: drag, mousemove, scroll, wheel
  // → ContinuousEventPriority → InputContinuousLane
  return getEventPriority(currentEvent.type);
}

Update Queue Lanes

How update queues store and process lane information

Each fiber maintains an update queue. Every update in the queue is tagged with the lane it was assigned:

// Update object structure
const update = {
  lane: TransitionLane1,       // Which lane this update belongs to
  action: newStateOrReducer,   // The setState argument
  hasEagerState: false,
  eagerState: null,
  next: null,                  // Linked list pointer
};

// Fiber stores lanes info
fiber.lanes = mergeLanes(fiber.lanes, update.lane);
// Also propagate up to ancestors
fiber.alternate.lanes = mergeLanes(fiber.alternate.lanes, update.lane);

Processing Updates by Lane Subset

During render, React only processes updates that match the currently rendering lanes:

// Simplified processUpdateQueue
function processUpdateQueue(fiber, renderLanes) {
  const queue = fiber.updateQueue;
  let update = queue.firstBaseUpdate;
  let newState = queue.baseState;

  while (update !== null) {
    const updateLane = update.lane;

    if (!isSubsetOfLanes(renderLanes, updateLane)) {
      // This update has lower priority than what we're rendering
      // SKIP it — save for later
      cloneUpdate(update); // preserve for next render pass
    } else {
      // This update is included in current render
      newState = computeNewState(newState, update);
    }
    update = update.next;
  }

  fiber.memoizedState = newState;
}

// isSubsetOfLanes: checks if updateLane is within renderLanes
function isSubsetOfLanes(set, subset) {
  return (set & subset) === subset;
}

mergeLanes in Practice

// When an update is enqueued, its lane is merged into the fiber's lanes
function enqueueUpdate(fiber, update) {
  const pending = fiber.updateQueue.shared.pending;
  // ... add to circular linked list ...

  // Mark this fiber and its ancestors as having pending work
  // at this lane
  markUpdateLaneFromFiberToRoot(fiber, update.lane);
}

function markUpdateLaneFromFiberToRoot(fiber, lane) {
  // Mark the fiber itself
  fiber.lanes = mergeLanes(fiber.lanes, lane);
  if (fiber.alternate) {
    fiber.alternate.lanes = mergeLanes(fiber.alternate.lanes, lane);
  }
  // Walk up to root, marking childLanes
  let parent = fiber.return;
  while (parent !== null) {
    parent.childLanes = mergeLanes(parent.childLanes, lane);
    if (parent.alternate) {
      parent.alternate.childLanes = mergeLanes(parent.alternate.childLanes, lane);
    }
    parent = parent.return;
  }
}

Why mark ancestors? The childLanes field on each fiber lets React bail out early during traversal. If a fiber's childLanes doesn't include the current render lanes, React can skip the entire subtree — a crucial optimization.

Interrupt & Restart

What happens when a high-priority update interrupts a low-priority render

This is the core of concurrent React. When a high-priority update arrives while a low-priority render is in progress:

// Simplified workLoop (concurrent mode)
function workLoopConcurrent() {
  // Render fiber-by-fiber, checking for interrupts between each unit
  while (workInProgress !== null && !shouldYield()) {
    performUnitOfWork(workInProgress);
  }
}

// shouldYield checks:
// 1. Has the time slice expired? (5ms default)
// 2. Is there higher-priority work pending?
function shouldYield() {
  const currentTime = getCurrentTime();
  if (currentTime >= deadline) {
    // Time slice expired — yield unconditionally
    // Note: React previously checked scheduling.isInputPending() here,
    // but that API was removed from Chrome in 2024. Current React simply
    // yields when the time slice (5ms) expires, relying on the MessageChannel
    // macrotask boundary to let pending input events fire.
    return true;
  }
  return false;
}

// Key function: ensureRootIsScheduled
function ensureRootIsScheduled(root) {
  const nextLanes = getNextLanes(root, root === workInProgressRoot
    ? workInProgressRootRenderLanes
    : NoLanes
  );

  const existingCallbackPriority = root.callbackPriority;
  const newCallbackPriority = getHighestPriorityLane(nextLanes);

  // If higher priority work arrived, cancel the existing task
  if (newCallbackPriority > existingCallbackPriority) {
    cancelCallback(existingCallbackNode);
    // Schedule new, higher-priority task
  }

  let schedulerPriorityLevel;
  if (includesSyncLane(nextLanes)) {
    // Sync work — schedule as Immediate
    schedulerPriorityLevel = ImmediateSchedulerPriority;
  } else {
    // Map lane to scheduler priority
    schedulerPriorityLevel = lanesToSchedulerPriority(nextLanes);
  }

  const newCallbackNode = scheduleCallback(
    schedulerPriorityLevel,
    performConcurrentWorkOnRoot.bind(null, root)
  );
  root.callbackNode = newCallbackNode;
  root.callbackPriority = newCallbackPriority;
}

// prepareFreshStack discards incomplete work
function prepareFreshStack(root, lanes) {
  root.finishedWork = null;
  root.finishedLanes = NoLanes;

  // Reset the work-in-progress tree
  workInProgressRoot = root;
  workInProgress = createWorkInProgress(root.current, null);
  workInProgressRootRenderLanes = lanes;
  // All in-progress state from the interrupted render is lost
}

Critical concept: When a higher-priority update preempts an in-progress render, the work is discarded and React restarts from the root with the new priority. However, when React merely yields (time slice expired, no higher-priority work), the workInProgress pointer is preserved and work resumes from where it left off in the next time slice. The discard-and-restart only happens on true preemption. This is why render functions must be pure: they might be called multiple times due to interruptions.

Starvation Prevention

How React ensures lower-priority work eventually gets done

If high-priority updates keep arriving, lower-priority lanes could theoretically starve. React prevents this with two mechanisms:

1. Lane Expiration

// Each lane has an expiration time
function markStarvedLanesAsExpired(root, currentTime) {
  const pendingLanes = root.pendingLanes;
  const expirationTimes = root.expirationTimes;

  let lanes = pendingLanes;
  while (lanes > 0) {
    const index = pickArbitraryLaneIndex(lanes);
    const lane = 1 << index;
    const expirationTime = expirationTimes[index];

    if (expirationTime === NoTimestamp) {
      // This lane just became pending — assign expiration
      expirationTimes[index] = computeExpirationTime(lane, currentTime);
    } else if (expirationTime <= currentTime) {
      // This lane has EXPIRED — mark it
      root.expiredLanes |= lane;
    }

    lanes &= ~lane;
  }
}

// Expiration timeouts by priority:
// SyncLane:            250ms
// InputContinuousLane: 500ms
// DefaultLane:         5000ms
// TransitionLanes:     5000ms
// RetryLanes:          5000ms
// IdleLane:            Never (no expiration)

2. Expired Lanes Get Sync Priority

// In getNextLanes, expired lanes are treated as highest priority
function getNextLanes(root, wipLanes) {
  const pendingLanes = root.pendingLanes;
  if (pendingLanes === NoLanes) return NoLanes;

  // Check for expired lanes FIRST
  const expiredLanes = root.expiredLanes;
  if (expiredLanes !== NoLanes) {
    // Expired lanes are processed synchronously — cannot be interrupted
    return expiredLanes;
  }

  // ... normal priority selection logic
}

Key point: Once a lane expires, it gets promoted to synchronous priority. This guarantees eventual completion. IdleLane is the exception — it never expires and can be starved indefinitely (which is by design for truly optional background work).

Entanglement

When lanes must render together and why

Entanglement means certain lanes are "linked" and must always be included together in a render. If lane A is entangled with lane B, rendering A also requires rendering B.

// Entanglement is stored as an array of lane masks
// root.entanglements[laneIndex] = set of lanes entangled with this lane

function entangleTransitions(root, fiber, lane) {
  const updateQueue = fiber.updateQueue;
  const sharedQueue = updateQueue.shared;

  if (isTransitionLane(lane)) {
    let queueLanes = sharedQueue.lanes;
    // Mark all lanes in this queue as entangled with each other
    queueLanes = mergeLanes(queueLanes, lane);
    sharedQueue.lanes = queueLanes;

    // Entangle with the root
    root.entangledLanes |= queueLanes;
    const entanglements = root.entanglements;
    let lanes = queueLanes;
    while (lanes > 0) {
      const index = pickArbitraryLaneIndex(lanes);
      const entangledLane = 1 << index;
      // Each lane in the group becomes entangled with ALL lanes in the group
      entanglements[index] |= queueLanes;
      lanes &= ~entangledLane;
    }
  }
}

// When selecting lanes to render, include entangled lanes
function getEntangledLanes(root, renderLanes) {
  let entangledLanes = renderLanes;
  const allEntangledLanes = root.entangledLanes;

  if (allEntangledLanes !== NoLanes) {
    const entanglements = root.entanglements;
    let lanes = entangledLanes & allEntangledLanes;
    while (lanes > 0) {
      const index = pickArbitraryLaneIndex(lanes);
      const lane = 1 << index;
      // Pull in entangled lanes
      entangledLanes |= entanglements[index];
      lanes &= ~lane;
    }
  }
  return entangledLanes;
}

Comparison: Expiration Times vs Lanes

Why lanes replaced the old expirationTime model

React originally used an expirationTime number for priority. The lane model replaced it in React 17+ (internal) for significant architectural reasons:

Aspect expirationTime Model Lanes Model
Data structure Single number (ms timestamp) 31-bit bitmask
Comparison Linear: A > B means higher priority Bitwise: independent priority groups
Batch selection All work ≥ threshold processed together Arbitrary subsets selected via bitmask
IO-bound vs CPU-bound Cannot distinguish Separate lane groups (Retry vs Default)
Multiple transitions All collapse to same priority Each gets own lane — independent
Suspense integration Awkward — hijacks priority number Natural — RetryLanes are separate bits
Hydration priority Special-cased hacks SelectiveHydrationLane is just another bit

Problems with expirationTime

// with expirationTime >= X. You can't say "render X but skip Y"

// Problem 3: Suspense rebasing

Scheduler Priorities

The scheduler package's priority queue and how it maps to lanes

React's scheduler package is a separate abstraction from lanes. It manages a priority queue of tasks using its own priority levels:

Lane → Scheduler Priority Mapping

// How React maps lanes to scheduler priorities
function lanesToSchedulerPriority(lanes) {
  const lane = getHighestPriorityLane(lanes);

  if (lane === SyncLane) {
    return ImmediatePriority;
  }
  if (lane === InputContinuousLane) {
    return UserBlockingPriority;
  }
  if (lane === DefaultLane) {
    return NormalPriority;
  }
  if (lane & TransitionLanes) {
    return NormalPriority;
  }
  if (lane & RetryLanes) {
    return NormalPriority;
  }
  if (lane === IdleLane || lane === OffscreenLane) {
    return IdlePriority;
  }
  return NormalPriority;
}

Scheduler's Priority Queue

// The scheduler uses a min-heap based on sortIndex (expiration time)
// Each task has: { id, callback, priorityLevel, startTime, expirationTime, sortIndex }

function scheduleCallback(priorityLevel, callback) {
  const currentTime = getCurrentTime();
  const startTime = currentTime; // or + delay for delayed tasks
  const timeout = getTimeoutByPriority(priorityLevel);
  const expirationTime = startTime + timeout;

  const newTask = {
    id: taskIdCounter++,
    callback,
    priorityLevel,
    startTime,
    expirationTime,
    sortIndex: -1,
  };

  // Push to taskQueue (min-heap sorted by expirationTime)
  newTask.sortIndex = expirationTime;
  push(taskQueue, newTask);

  // Request host callback (MessageChannel or setTimeout)
  if (!isHostCallbackScheduled) {
    requestHostCallback(flushWork);
  }

  return newTask;
}

Production Performance

How lanes affect your app and identifying priority issues

How Lanes Affect Your App

  • Input responsiveness: SyncLane ensures user input never waits for background renders to complete
  • Smooth transitions: TransitionLanes let heavy UI updates happen without blocking interactions
  • Automatic batching: Multiple setState calls in the same event share a lane, batching into one render
  • Selective hydration: Clicking an unhydrated Suspense boundary promotes it to SelectiveHydrationLane

Identifying Priority Issues in React DevTools Profiler

// Signs of priority problems in the Profiler:

// 1. Long "render" times on SyncLane

// 2. Multiple interrupted renders for the same transition

    // React processes this IMMEDIATELY

        if (value && `Item ${i}`.includes(value)) {
          items.push(`Item ${i}`);
        }
      }
      setList(items);
      renderCount.current.transition++;
    });
  }

  return (
    <div>
      <input
        value={urgent}
        onChange={handleInput}
        placeholder="Type to filter 20k items..."
      />
      <p>Sync renders: {renderCount.current.sync}</p>
      <p>Transition renders: {renderCount.current.transition}</p>
      <p>{isPending ? 'Filtering...' : `${list.length} results`}</p>
      <ul>
        {list.slice(0, 100).map((item, i) => (
          <li key={i}>{item}</li>
        ))}
      </ul>
    </div>

// Educational: showing how different contexts produce different lanes
function LaneAssignmentVisualization() {
  const [log, setLog] = useState([]);

  const addLog = (source, expectedLane) => {
    setLog(prev => [...prev, { source, expectedLane, time: Date.now() }]);
  };

  // Click handler → SyncLane
  const handleClick = () => {
    addLog('click handler', 'SyncLane');
  };

  // Inside startTransition → TransitionLane
  const handleTransition = () => {
    startTransition(() => {
      addLog('startTransition', 'TransitionLane');
    });
  };

  // Inside useEffect → DefaultLane
  useEffect(() => {
    addLog('useEffect', 'DefaultLane');
  }, []);

  // Inside setTimeout → DefaultLane (no event context)
  const handleTimeout = () => {
    setTimeout(() => {
      addLog('setTimeout callback', 'DefaultLane');
    }, 0);
  };

  // flushSync → SyncLane (forced)
  const handleFlushSync = () => {
    startTransition(() => {
      // Even inside a transition, flushSync forces SyncLane
      flushSync(() => {
        addLog('flushSync inside transition', 'SyncLane');
      });
    });
  };

  return (
    <div>
      <button onClick={handleClick}>Click (SyncLane)</button>
      <button onClick={handleTransition}>Transition</button>
      <button onClick={handleTimeout}>setTimeout</button>
      <button onClick={handleFlushSync}>flushSync</button>

        {log.map((entry, i) => (
          <li key={i}>
            {entry.source} → {entry.expectedLane}
          </li>
        ))}
      </ul>
    </div>
  );

Common Mistakes

5 critical mistakes developers make with React's priority system

Mistake 1: Marking Urgent Updates as Transitions

// ❌ WRONG: User sees delayed feedback for critical action
function PaymentForm() {
  const [isPending, startTransition] = useTransition();

  function handleSubmit() {
    startTransition(() => {
      // Payment submission should NOT be a transition!
      // User expects immediate feedback
      setSubmitting(true);
      submitPayment(formData);
    });
  }
}

// ✓ CORRECT: Use SyncLane for user-critical actions
function PaymentForm() {
  function handleSubmit() {
    // setState in event handler = SyncLane (immediate)
    setSubmitting(true);
    submitPayment(formData);
  }
}

Mistake 2: Not Using Transitions for Heavy Renders

// ❌ WRONG: Heavy filtering blocks the input
function SearchPage() {
  const [query, setQuery] = useState('');

  function handleChange(e) {
    // Both updates get SyncLane — the heavy filter
    // blocks the input from updating
    setQuery(e.target.value);
    setFilteredResults(heavyFilter(e.target.value, largeDataset));
  }
}

// ✓ CORRECT: Separate urgent from non-urgent
function SearchPage() {
  const [query, setQuery] = useState('');
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    setQuery(e.target.value); // SyncLane — immediate
    startTransition(() => {
      setFilteredResults(heavyFilter(e.target.value, largeDataset));
    }); // TransitionLane — interruptible
  }
}

Mistake 3: Misunderstanding Batching in Concurrent Mode

// ❌ WRONG assumption: each setState triggers a separate render
function Counter() {
  function handleClick() {
    setA(1); // Does NOT trigger render here
    setB(2); // Does NOT trigger render here
    setC(3); // Does NOT trigger render here
    // All three are batched into ONE render (same event, same lane)
  }

  // But what about async boundaries?
  async function handleAsync() {
    setA(1);       // Batched...
    await fetch(); // ...async boundary...
    setB(2);       // In React 18+: STILL batched! (same DefaultLane)
    setC(3);       // All three may end up in one render
  }
}

// ✓ CORRECT understanding:
// React 18 batches ALL setState calls that share a lane,
// regardless of async boundaries. Only different lanes
// produce separate renders.

Mistake 4: Over-Using flushSync

// ❌ WRONG: Forcing sync rendering unnecessarily
function AnimatedList({ items }) {
  useEffect(() => {
    items.forEach((item, i) => {
      // Forces each update to be synchronous — defeats concurrency
      flushSync(() => {
        setVisibleItems(prev => [...prev, item]);
      });
    });
  }, [items]);
}

// ✓ CORRECT: Let React batch and schedule naturally
function AnimatedList({ items }) {
  useEffect(() => {
    // Single state update — React handles the rendering
    setVisibleItems(items);
    // If animation needed, use CSS transitions or requestAnimationFrame
  }, [items]);
}

// flushSync is appropriate for:
// - Measuring DOM after update (scrollTo, focus)
// - Third-party library integration requiring sync DOM state
// - Accessibility: screen reader announcements that must be immediate

Mistake 5: Ignoring Starvation Signals

// ❌ WRONG: Causing excessive interruptions
function RealTimeChat() {
  useEffect(() => {
    const ws = new WebSocket(url);
    ws.onmessage = (e) => {
      // Every message (100/sec) triggers SyncLane update
      // This starves ALL transitions in the app
      setMessages(prev => [...prev, JSON.parse(e.data)]);
    };
  }, []);
}

// ✓ CORRECT: Batch high-frequency updates, use appropriate priority
function RealTimeChat() {
  const bufferRef = useRef([]);

  useEffect(() => {
    const ws = new WebSocket(url);
    ws.onmessage = (e) => {
      bufferRef.current.push(JSON.parse(e.data));
    };

    // Flush buffer at reasonable intervals using transition
    const interval = setInterval(() => {
      if (bufferRef.current.length > 0) {
        const batch = bufferRef.current;
        bufferRef.current = [];
        startTransition(() => {
          setMessages(prev => [...prev, ...batch]);
        });
      }
    }, 100);

    return () => { ws.close(); clearInterval(interval); };
  }, []);
}

Rule of thumb: If your app has transitions that take 5+ seconds to commit, something is causing starvation. Check for high-frequency sync-priority updates, heavy synchronous computations in event handlers, or excessive flushSync usage.

Trade-offs

Comparing scheduling strategies and their implications
Approach Pros Cons Best For
Sync Rendering (SyncLane for everything) Simple mental model, predictable order, no tearing Blocks main thread, janky UI on heavy updates Simple apps, critical paths where consistency matters more than responsiveness
Concurrent Rendering (Transitions) Responsive input, interruptible, better perceived performance More complex, potential for stale UI, more re-renders Complex UIs, heavy computations, search/filter scenarios
TransitionLane (startTransition) Explicit opt-in, clear intent, framework-managed priority Extra API surface, not all updates benefit Non-urgent UI updates derived from user actions
DefaultLane (normal setState) No extra code, good enough for most updates Can block if heavy, higher priority than transitions Standard state updates that should render promptly
Fine-grained Priority (many lanes) Maximum control, independent scheduling per update type Hard to reason about, debugging complexity Framework internals (React itself), not user code
Coarse Priority (sync vs transition) Easy to understand, covers 90% of cases Cannot express nuanced priority differences Application-level code, most real-world scenarios

When to Use Each Priority Level

// SyncLane (default in event handlers) — Use for:
// • Text input value updates (user must see what they typed)
// • Toggle visibility (open/close modals)
// • Form validation feedback
// • Focus management

// TransitionLane (startTransition) — Use for:
// • Search result filtering
// • Tab switching with heavy content
// • Navigation in client-side routers
// • Dashboard data re-aggregation
// • Any "secondary" UI update triggered by a user action

// DefaultLane (useEffect, setTimeout) — Use for:
// • Data fetching results
// • Subscription updates
// • Timer-based state changes
// • Effects that update state

// IdleLane — Reserved for React internals:
// • Offscreen pre-rendering
// • Speculative rendering of hidden routes

Practical guidance: Most apps only need two priority levels in practice — "urgent" (default event handler behavior) and "non-urgent" (startTransition). The fine-grained lane system exists for React's internal scheduling; you rarely need to think about individual lanes in application code.

Follow-up Questions

7 likely follow-up questions with strong answers

Q1: "Can two transitions run concurrently?"

Answer: Not truly concurrently (JavaScript is single-threaded), but they can be scheduled independently. Each startTransition claims a different TransitionLane. If Transition A is rendering and Transition B arrives, React can choose to include both in the same render pass (if they're entangled) or handle them separately. Multiple transition lanes allow React to track which transitions are complete independently — important for showing stale content while a specific transition is pending.

Q2: "What's the relationship between lanes and time slicing?"

Answer: Lanes determine what work to do; time slicing determines when to yield. During a concurrent render (non-Sync lanes), React yields every ~5ms (the time slice). Between slices, it checks if higher-priority lanes have pending work. If so, it interrupts. SyncLane renders are NOT time-sliced — they run to completion without yielding, because user input feedback must be immediate.

Q3: "How does Suspense interact with lanes?"

Answer: When a component suspends (throws a Promise), React remembers which lanes were being rendered. When the Promise resolves, React schedules a retry at a RetryLane. RetryLanes have lower priority than user-interactive lanes but higher than idle, ensuring data resolution happens promptly but doesn't block user interaction. The retry lane can be entangled with the original lane that caused the suspension.

Q4: "Why doesn't React use Web Workers for concurrent rendering?"

Answer: React needs synchronous access to the DOM for commits and to the component tree for state reads. Web Workers cannot access the DOM. React's approach is cooperative multitasking on the main thread: render work is broken into small units, and the scheduler yields between them. This is why render must be pure — React needs to be able to abandon and restart work without side effects leaking.

Q5: "How does useDeferredValue differ from startTransition internally?"

Answer: startTransition marks the source of an update as low priority — the setState inside it gets a TransitionLane. useDeferredValue creates a derived value that updates at transition priority. Internally, useDeferredValue triggers a re-render at TransitionLane when the source value changes, passing the new value to the deferred copy. The key difference: startTransition controls when an update happens; useDeferredValue controls when a value is consumed.

Q6: "What happens to in-progress work when React interrupts?"

Answer: It's completely discarded. React calls prepareFreshStack(), which resets workInProgress to a fresh clone of the current tree. Any partially-built fiber nodes, any hooks that ran during the interrupted render — all gone. This is why:

  • Render must be pure (no side effects to leak)
  • useRef mutations in render are dangerous (may happen multiple times)
  • Strict Mode double-renders to catch impurity

Q7: "Can lanes cause visual inconsistency (tearing)?"

Answer: React's design prevents tearing within a single render. All components in one commit see the same state for a given lane. However, useDeferredValue intentionally shows "stale" data — this is controlled inconsistency, not tearing. True tearing was a risk with external stores (Redux), which led to useSyncExternalStore — it forces sync re-renders when external state changes during a concurrent render to maintain consistency.

Depth signal: Mentioning useSyncExternalStore and why it exists shows you understand the practical boundaries of the lane system — not just the happy path.

Q8: "How does useOptimistic (React 19) interact with lanes?"

Answer: useOptimistic creates an update at a special priority — the optimistic value is applied immediately (SyncLane-level for instant feedback), while the "real" update resolves asynchronously. When the async action completes (or fails), the optimistic state is automatically reverted and replaced with the real result. Under the hood, this leverages the lane system's ability to commit partial work: the optimistic update commits to DOM immediately while the underlying transition processes at TransitionLane priority. If the transition fails, React reverts by replaying state without the optimistic update.

Key Points to Hit in Your Answer

  • Lanes are bitmasks — explain OR/AND operations briefly
  • Priority is position-based: lower bit = higher priority
  • Interruption means complete discard + restart, not pause/resume
  • Starvation is prevented by expiration (5s default for transitions)
  • Entanglement ensures consistency across related updates
  • The scheduler is separate from lanes — maps lanes to task priorities

What NOT to Say

Avoid these common misconceptions:

  • ❌ "React pauses and resumes the render" — It DISCARDS and RESTARTS
  • ❌ "Lanes are like thread priorities" — JavaScript is single-threaded; lanes are cooperative scheduling
  • ❌ "Higher lane number = higher priority" — It's the opposite; lower bit position = higher priority
  • ❌ "useTransition makes things faster" — It makes the UI MORE RESPONSIVE, not faster. Total work is the same or more
  • ❌ "Concurrent mode is opt-in per component" — It's a root-level decision (createRoot vs render). Components opt into TRANSITIONS, not concurrency itself
  • ❌ "Each setState is a separate render" — React 18 auto-batches all updates in the same lane
  • ❌ "Lanes are exposed as a public API" — They're internal; startTransition/useDeferredValue are the public interface

One-Paragraph Summary

React's lane model is a bitmask-based priority scheduling system where each of 31 bits represents a priority level. Updates are assigned lanes based on their execution context (event type, transition wrapper, etc.). During concurrent rendering, React processes work fiber-by-fiber, yielding every ~5ms. If a higher-priority lane has pending work, the current render is abandoned and restarted with the higher-priority lanes. Lower-priority work is protected from indefinite starvation through lane expiration (promoting to sync priority after a timeout) and entanglement (ensuring related updates render together for consistency). The public APIs — startTransition and useDeferredValue — let developers signal which updates are non-urgent, allowing React's scheduler to prioritize user interactions.

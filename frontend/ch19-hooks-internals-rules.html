Hooks Internals & Rules

"How do React hooks work internally? Why must they be called in the same order, and what breaks if you don't?"
Key Takeaway: Hooks aren't magic — each Fiber holds a singly linked list of plain Hook objects, and every hook call (useState, useEffect, useRef, ...) simply reads the next node in that list, in the exact order the calls happen. There is no name-based or identity-based matching at all — position in the call sequence is the hook's identity. This single fact explains the Rules of Hooks, why conditional hook calls corrupt state, why closures over stale state happen, and why useRef feels different from useState.

Interviewer's Intent

What the interviewer is really testing
This question tests three capabilities simultaneously:
  • Mechanism, not memorization: "don't call hooks conditionally" is a rule most candidates can recite; explaining why — the linked-list, call-order matching — is what separates a rule-follower from someone who understands the system.
  • Real debugging experience: have you actually hit "Rendered more hooks than during the previous render" in production, and can you describe what code caused it and how you fixed it?
  • Closure discipline: can you explain the stale closure problem precisely — which render's state/props a given closure "sees," and why — rather than just knowing "add it to the dependency array" as a magic incantation?
Red flags for interviewers: "hooks work by tracking variable names" (they don't — order, not naming, is the mechanism); not knowing why useRef doesn't trigger re-renders while useState does, despite both persisting a value across renders; being unable to explain what Strict Mode's double-invocation in development is actually for.

60-Second Answer

Structured response for time-pressured interviews

Each Fiber node has a memoizedState field that, for function components, points to the head of a singly linked list of Hook objects — one node per hook call, in the exact order those calls appear in the function body. On the first render (mount), each hook call creates and appends a new node. On every subsequent render (update), React walks the same linked list from the start, and each hook call simply advances a cursor to the next node — there is no lookup by name, key, or any other identity; the Nth hook call in this render is matched to the Nth node created during mount, purely by position.

This is exactly why hooks must be called unconditionally, in the same order, on every render: an if statement around a hook call means that call might not happen on some renders, shifting every subsequent hook's position by one and causing them to read the wrong node's state — or, if React detects a hook-count mismatch across renders, throwing outright rather than silently corrupting state.

useState's node stores an update queue and the current memoized value; useEffect's node stores the effect callback, its cleanup, and its dependency array for comparison; useRef's node simply stores a stable { current } object that never changes identity across renders and, critically, mutating .current does not schedule a re-render at all.

Hooks Linked List (fiber.memoizedState)

The actual data structure, simplified 
// Simplified shape of a single Hook node (React internals)
const hook = {
  memoizedState: null,   // the hook's current value (e.g. useState's stored value)
  baseState: null,       // state before pending updates are applied
  baseQueue: null,       // linked list of updates not yet processed
  queue: null,           // the update queue (dispatch pushes here for useState/useReducer)
  next: null,            // pointer to the NEXT hook called in this component — the whole mechanism
};
Fiber.memoizedState ──▶ Hook(useState #1) ──▶ Hook(useEffect #1) ──▶ Hook(useRef #1) ──▶ null
                              │                     │                     │
                         [count, setCount]     {create, destroy,    {current: domNode}
                                                 deps: [...]}

Component body, top to bottom:
  const [count, setCount] = useState(0);   // creates/reads Hook node #1
  useEffect(() => { ... }, [count]);       // creates/reads Hook node #2
  const ref = useRef(null);                // creates/reads Hook node #3
Mount vs update dispatcher: React actually swaps out the entire hook implementation between mount and update internally (HooksDispatcherOnMount vs HooksDispatcherOnUpdate) — on mount, useState's implementation creates a new node and appends it; on update, a completely different implementation walks the existing list and reads the next node. This is why hook behavior can subtly differ between "first render" and "every render after" in ways that trip up naive reimplementations.

Hook Resolution by Call Order

There is no name, key, or identity — only position 
// ❌ This is the exact mechanism the Rules of Hooks protect against
function Profile({ userId, showBio }) {
  const [name, setName] = useState('');

  if (showBio) {
    const [bio, setBio] = useState(''); // Hook node #2 ONLY exists on renders where showBio is true
  }

  const [avatar, setAvatar] = useState(null);
  // When showBio is true:  node order is [name, bio, avatar]  → avatar is node #3
  // When showBio is false: node order is [name, avatar]        → avatar is node #2
  // If showBio FLIPS between renders, `avatar`'s hook call now reads
  // whatever node happens to be at that position — which held `bio`'s state
  // on the previous render. React's dev-mode hook-count check usually throws
  // here rather than silently misattributing state, but the underlying cause
  // is exactly this positional mismatch, not a special-cased error condition.
}

The fix is never to make the hook call itself conditional — instead, call the hook unconditionally and branch on what you do with its value:

// ✅ Hook call itself is unconditional; only its VALUE's relevance is conditional
function Profile({ userId, showBio }) {
  const [name, setName] = useState('');
  const [bio, setBio] = useState(''); // always called — always node #2, regardless of showBio
  const [avatar, setAvatar] = useState(null); // always node #3

  return (
    <>
      {showBio && <p>{bio}</p>}
    </>
  );
}

useState Internals (Queue, Dispatch, Reducer)

useState is useReducer with a built-in reducer

Internally, useState(initial) is implemented as useReducer(basicStateReducer, initial), where basicStateReducer simply returns the action if it's not a function, or calls it with the previous state if it is (the "functional update" form, setCount(c => c + 1)). The hook's node holds a queue — a linked list of pending updates — and calling dispatch (the setCount function) doesn't apply the update synchronously; it appends an update object to that queue and schedules a re-render. The queued updates are only actually processed, in order, the next time the component renders.

// Simplified mount-time implementation
function mountState(initialState) {
  const hook = mountWorkInProgressHook(); // creates and appends a new Hook node
  hook.memoizedState = hook.baseState = initialState;
  const queue = { pending: null, dispatch: null };
  hook.queue = queue;

  const dispatch = (action) => {
    // Appends {action} to the circular pending queue and schedules work —
    // does NOT synchronously recompute memoizedState here
    const update = { action, next: null };
    queue.pending = enqueue(queue.pending, update);
    scheduleUpdateOnFiber(/* ... */);
  };
  queue.dispatch = dispatch;

  return [hook.memoizedState, dispatch];
}

// Simplified update-time implementation
function updateState() {
  const hook = updateWorkInProgressHook(); // walks to the NEXT existing node
  let newState = hook.baseState;
  let update = hook.queue.pending?.next;
  while (update) {
    newState = typeof update.action === 'function' ? update.action(newState) : update.action;
    update = update.next;
  }
  hook.memoizedState = newState;
  return [hook.memoizedState, hook.queue.dispatch];
}
Why functional updates (setCount(c => c + 1)) are safer in rapid-fire scenarios: because the queue can accumulate multiple pending updates before a render actually processes them (e.g., multiple dispatch calls in the same event handler, or React 18's automatic batching across microtasks), each update function receives the result of the previous update in the queue, not a closure-captured stale value — this is what makes three consecutive setCount(c => c + 1) calls correctly increment by 3, while three setCount(count + 1) calls (closing over the same stale count) would not.

useEffect Internals (Effect Tags, Destroy/Create)

Effects live in a separate circular list, processed after commit

An effect's Hook node stores { create, destroy, deps, tag }. During the render phase, React compares the new deps array against the previous one (via Object.is per element) — if any element differs (or no deps array was passed at all), the effect is tagged for execution this commit. Effects are collected into the Fiber's own circular effect list, separate from the hooks list, and processed in the commit phase: layout effects (useLayoutEffect) run synchronously right after DOM mutations but before the browser paints; passive effects (useEffect) are scheduled to run asynchronously after paint, so they don't block visual updates.

Commit phase, effect execution order for `useEffect`:

  1. For EVERY effect whose deps changed, run its previous render's `destroy` (cleanup) FIRST
     — all cleanups across the whole tree run before any new `create` runs
  2. THEN run each changed effect's new `create` function
  3. This happens AFTER the browser has painted (passive effects don't block paint)

  useLayoutEffect follows the same destroy-then-create order, but BEFORE paint,
  synchronously blocking the browser from showing the frame until effects finish
Common misconception: cleanup functions don't run "when the component unmounts" exclusively — they run before every re-execution of that same effect (i.e., whenever its dependencies change), and again on actual unmount. An effect with a non-empty dependency array can have its cleanup invoked many times over a component's life, not just once at the end.

useRef — Why It's a Stable Container

Same linked-list mechanism, but no update queue at all 
// Simplified mount-time implementation of useRef
function mountRef(initialValue) {
  const hook = mountWorkInProgressHook(); // same linked-list node as any other hook
  const ref = { current: initialValue };
  hook.memoizedState = ref;
  return ref;
}

// Simplified update-time implementation — note there's no dispatch, no queue at all
function updateRef() {
  const hook = updateWorkInProgressHook();
  return hook.memoizedState; // returns the SAME object reference created at mount, forever
}

useRef uses the exact same positional linked-list mechanism as every other hook — its node just holds a plain mutable object with no update queue and no re-render scheduling attached to mutating .current. This is the entire explanation for why refs "persist across renders without causing re-renders": the object identity never changes (same node, same object, every render), and nothing in React ever inspects .current's value to decide whether to schedule work.

Custom Hooks — Composition Without Wrappers

A custom hook is just a function that calls other hooks — no extra Fiber, no wrapper node 
function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);
  useEffect(() => {
    const handler = () => setWidth(window.innerWidth);
    window.addEventListener('resize', handler);
    return () => window.removeEventListener('resize', handler);
  }, []);
  return width;
}

function Layout() {
  const width = useWindowWidth(); // inlines TWO hook calls (useState + useEffect) into Layout's own list
  // Layout's hook list is: [useState(from useWindowWidth), useEffect(from useWindowWidth), ...]
}

When Layout calls useWindowWidth(), the useState and useEffect calls inside useWindowWidth append nodes directly onto Layout's own Fiber hook list — there's no separate Fiber or wrapper node for the custom hook itself. This is why hook composition is "free": nesting custom hooks ten levels deep produces the same flat linked list on the actual component's Fiber as if you'd inlined every hook call by hand, with zero additional runtime indirection.

This is also precisely why the Rules of Hooks apply transitively: a custom hook calling hooks conditionally has exactly the same effect as the consuming component doing so directly, because they share one flat list.

Rules of Hooks — What Actually Breaks

Two rules, both direct consequences of the linked-list mechanism
  1. Only call hooks at the top level. Never inside conditions, loops, or nested (non-hook, non-component) functions — because those constructs can change whether/how-many-times a hook call executes between renders, shifting every subsequent hook's position in the list.
  2. Only call hooks from React function components or custom hooks. Regular JS functions aren't guaranteed to be called in a stable, render-tied sequence associated with a specific Fiber, so there's no linked list for them to append to.

The eslint-plugin-react-hooks package enforces rule #1 statically, via AST analysis at lint time — it doesn't run your code, it pattern-matches hook calls appearing inside if/for/while/nested-function syntax nodes. React itself has a lightweight runtime check as a backstop: it counts hooks per render and throws "Rendered more hooks than during the previous render" if the count increases — but this only catches count increases, not every possible reordering (e.g., swapping the order of two always-called hooks around a conditional produces the same count but different attribution, and isn't caught by count comparison alone).

Strict Mode Double-Invocation

Deliberately surfacing non-idempotent renders and effects, development-only

In development, <StrictMode> intentionally renders each component function twice in a row (discarding one result) and, for effects, runs an extra mount → unmount → mount cycle immediately after the initial commit. This has no effect in production builds — it's a deliberate development-only stress test designed to surface two classes of bugs before they reach users:

  • Non-idempotent render logic: a component body that mutates something outside itself (a module-level variable, a shared cache) during render will visibly misbehave when called twice — pure render functions are unaffected either way.
  • Missing or incorrect effect cleanup: an effect that assumes "I only run once, ever" (e.g., opening a WebSocket with no cleanup) breaks immediately and obviously under the extra mount/unmount/mount cycle, instead of silently leaking in production the first time the component happens to remount for an unrelated reason.
Practical framing: if double-invocation "breaks" your component, your component had a latent bug that would eventually surface anyway (React remounts components far more often than developers assume — route changes, key changes, Suspense re-suspension, list reordering without keys). Strict Mode just makes it happen immediately and deterministically in development instead of intermittently in production.

Closure Stale State Problem

Which render's values a closure "sees," precisely 
// ❌ Classic stale closure: the setTimeout callback captures `count`
// from the SPECIFIC render in which the effect ran, forever
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setTimeout(() => {
      console.log(count); // always logs the value from THIS render — never updates
    }, 3000);
    return () => clearTimeout(id);
  }, []); // empty deps — effect runs once, closure over count=0 is captured forever

  return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}

Each render of a function component executes the entire function body fresh, creating brand-new closures for every function defined inside it — including effect callbacks. Each of those closures captures the specific props/state values as they existed during that particular render's execution, via ordinary JS lexical scoping; there is no special React magic keeping a closure "live" against future state changes. An effect with [] deps only ever runs its create function once, so the closure it captured is permanently bound to that first render's values.

// ✅ Fix 1: include the dependency, so the effect re-creates its closure with fresh values
useEffect(() => {
  const id = setTimeout(() => console.log(count), 3000);
  return () => clearTimeout(id);
}, [count]); // re-runs (with a NEW closure) every time count changes

// ✅ Fix 2: read the latest value via a ref, decoupling "latest value" from "reactive dependency"
function Counter() {
  const [count, setCount] = useState(0);
  const countRef = useRef(count);
  countRef.current = count; // updated on every render, read imperatively

  useEffect(() => {
    const id = setTimeout(() => console.log(countRef.current), 3000); // always current
    return () => clearTimeout(id);
  }, []);
}

useEffectEvent (Experimental)

An officially-supported answer to "I want the latest value, without it being a reactive dependency"

Status (2024): useEffectEvent is experimental/unstable and was not included in the React 19 stable release. It was removed from the React 19 docs. In interviews, frame it as "an upcoming API React is developing" rather than "shipped in React 19." The underlying pattern (ref-based latest value) is the production workaround today.

The ref-based workaround above is exactly the pattern useEffectEvent formalizes: it lets you extract non-reactive logic out of an effect into an "Effect Event" that always sees the latest props/state (like a ref would), without needing to be listed in the effect's dependency array and without re-triggering the effect when those values change.

function ChatRoom({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    showNotification('Connected!', theme); // always reads the LATEST theme, never stale
  });

  useEffect(() => {
    const connection = createConnection(roomId);
    connection.on('connected', () => onConnected());
    connection.connect();
    return () => connection.disconnect();
    // `theme` is used inside onConnected but is intentionally NOT a dependency here —
    // theme changes should NOT reconnect the chat room, only roomId changes should
  }, [roomId]);
}
Why this needs to be a distinct primitive rather than "just don't list it as a dependency": omitting a value from the dependency array while still closing over it directly (without useEffectEvent) reintroduces the exact stale-closure bug from the previous section — useEffectEvent's implementation guarantees the function body always executes against the latest render's values, specifically by re-assigning its underlying implementation on every render (similar in spirit to the manual ref-reassignment pattern) while keeping a stable identity for the returned function itself.

React 19 use() Hook

The one hook allowed to break the "top level only" rule

use() can read the value of a Promise (suspending the component via the Suspense mechanism from Chapter 20 until it resolves) or a Context. Unlike every other hook, use() can be called conditionally, inside loops, and after early returns — because its resolution doesn't depend on positional matching. For Promises, it throws to the nearest Suspense boundary. For Context, while it still creates a hook node internally, the resolution is idempotent — reading from the nearest provider gives the same result regardless of call position, so React can safely exempt it from ordering constraints.

function Message({ messagePromise, show }) {
  if (!show) return null;             // early return BEFORE a hook call — illegal for useState, fine for use()
  const message = use(messagePromise); // conditionally reached, and that's explicitly supported
  return <p>{message}</p>;
}
Don't overgeneralize this exception in an interview. use() is a deliberate, narrow carve-out for exactly two use cases (Promises and Context) with their own resolution mechanism independent of the hooks linked list — it does not mean "the Rules of Hooks are being relaxed generally." useState, useEffect, and all other classic hooks remain strictly positional and must still follow the top-level-only rule.

Production Anti-Patterns

Real bugs traced back to the mechanisms above 
// ❌ Early return BEFORE hooks — a genuinely common production bug,
// often introduced by a well-intentioned "guard clause" refactor
function UserProfile({ user }) {
  if (!user) return <LoginPrompt />; // hooks below this line become conditional!

  const [isEditing, setIsEditing] = useState(false); // only called when `user` is truthy
  const [draft, setDraft] = useState(user.bio);
  // If `user` flips from truthy to falsy/back across renders (e.g. after an
  // async auth check resolves), the number and identity of hook calls
  // for THIS component changes between renders → hook-count mismatch

  return <Editor draft={draft} />;
}

// ✅ Hooks first, unconditionally; guard clause AFTER
function UserProfile({ user }) {
  const [isEditing, setIsEditing] = useState(false);
  const [draft, setDraft] = useState(user?.bio ?? '');

  if (!user) return <LoginPrompt />;

  return <Editor draft={draft} />;
}
// ❌ useRef misused to hold DERIVED state that should trigger re-renders
function SearchBox({ items, query }) {
  const filteredRef = useRef(items.filter((i) => i.name.includes(query)));
  // filteredRef.current is computed ONCE, at mount — mutating it later
  // doesn't re-render, and re-assigning it during render doesn't either,
  // reliably, since refs are explicitly exempt from render scheduling
  return <List items={filteredRef.current} />; // stale after the first render
}

// ✅ Derived state belongs in useMemo (or plain computation), not a ref
function SearchBox({ items, query }) {
  const filtered = useMemo(() => items.filter((i) => i.name.includes(query)), [items, query]);
  return <List items={filtered} />;
}

Code Examples

Minimal hook dispatcher reimplementation, for building intuition 
// A drastically simplified, single-component version of React's hook mechanism,
// useful for building intuition about the linked list — not production code.
let currentlyRenderingFiber = null;
let workInProgressHook = null;

function mountWorkInProgressHook() {
  const hook = { memoizedState: null, next: null };
  if (workInProgressHook === null) {
    currentlyRenderingFiber.memoizedState = hook; // first hook — becomes the list head
  } else {
    workInProgressHook.next = hook; // append to the tail
  }
  workInProgressHook = hook;
  return hook;
}

function useStateSimplified(initial) {
  const hook = mountWorkInProgressHook();
  hook.memoizedState = initial;
  const setState = (value) => {
    hook.memoizedState = value;
    scheduleRerender(currentlyRenderingFiber);
  };
  return [hook.memoizedState, setState];
}

// On an UPDATE render, a parallel `updateWorkInProgressHook()` walks the
// EXISTING list (fiber.memoizedState → hook.next → hook.next → ...) instead
// of creating new nodes — this is the entire "same order every render" contract.

Common Mistakes

Mistakes even experienced React engineers make
  • Early returns before all hook calls — the single most common real-world Rules of Hooks violation, often introduced during a refactor that adds a guard clause without checking what's below it.
  • Believing the ESLint rule catches every possible violation — it's a static AST check; dynamically conditional hook-calling patterns hidden behind indirection (e.g., calling a custom hook only inside a callback) can sometimes slip past it.
  • Treating useRef as a general-purpose "instance variable" for state that should affect rendering — refs are explicitly exempt from scheduling a re-render; derived/display state belongs in useState/useMemo.
  • "Fixing" a stale closure by adding a value to a dependency array when it actually shouldn't be reactive — this re-runs the whole effect (including its cleanup/re-subscription) more often than intended, when a ref or useEffectEvent was the correct tool instead.
  • Disabling Strict Mode to make an effect "stop breaking" instead of fixing the missing cleanup it was surfacing — the underlying bug still exists in production, just less deterministically triggered.

Trade-offs

Decisions worth stating out loud
  • Positional hook identity vs a hypothetical name-based system: position-based matching is extremely cheap at runtime (no map lookups, no key comparisons) but imposes the strict ordering rules this chapter covers; a name-based system (which no mainstream framework actually uses for this) would relax ordering constraints at the cost of runtime lookup overhead and naming-collision complexity.
  • Ref-based "latest value" access vs useEffectEvent: the manual ref pattern works today across all supported React versions with no new API; useEffectEvent is more explicit about intent and slightly safer against misuse, but is a newer, more narrowly-versioned API to depend on.
  • Strict Mode's double-invocation cost: genuinely doubles render-function execution time in development only — a real (if usually negligible) DX cost in exchange for catching non-idempotent-render and missing-cleanup bugs before production.

React 19 Hooks Landscape

New hooks that expand the hooks model beyond the positional linked list

React 19 introduced several hooks that interact with form action boundaries rather than the traditional positional linked list:

  • useFormStatus() — reads the submission state (pending, data, method, action) of the nearest parent <form>. Only the component calling it re-renders on status change, not the entire form.
  • useActionState(action, initialState) — manages state through a form action (renamed from useFormState). Returns [state, formAction, isPending]. Ties a reducer-like pattern to Server Actions.
  • useOptimistic(state, updateFn) — creates an optimistic value that's shown immediately and automatically reverts when the async action completes/fails. Paired with transitions for instant UI feedback.

These hooks are positional (they still follow Rules of Hooks), but their resolution depends on form action boundaries and async action lifecycles — expanding the hooks model beyond pure parent-child render propagation.

Follow-up Interview Questions

Q1: Does calling the same number of hooks, but in a different order, between renders cause an error?

Strong answer: not necessarily an explicit thrown error — React's built-in runtime safeguard primarily compares hook count across renders, not the specific hook type at each position in all cases. Swapping the call order of, say, two useState calls around a conditional could silently misattribute state between them rather than throw, which is precisely why this class of bug is more dangerous and harder to detect than a straightforward count mismatch — it's also why the ESLint static rule matters more than relying on the runtime check alone.

Q2: Why doesn't mutating a ref's .current property trigger a re-render, given that it's stored on the same Fiber as state?

Strong answer: re-renders are triggered explicitly by a hook's dispatch function calling scheduleUpdateOnFiber (as shown in the useState internals) — it's an intentional side effect of calling setState, not something that happens automatically whenever any value on the Fiber changes. A ref's node has no dispatch/queue at all; mutating .current is a plain JS object property assignment with nothing wired to the scheduler, by design.

Q3: If two different custom hooks each call useState once, and a component calls both, how many hook nodes appear on that component's Fiber?

Strong answer: two — one per useState call, appended in the order the custom hooks are invoked in the component body. Custom hooks are not a boundary or namespace for hook storage; every hook call anywhere in the call chain reachable from the rendering component appends directly to that same flat linked list on that component's Fiber, in strict call order.

Q4: Why is use() exempt from the Rules of Hooks when it's still a hook?

Strong answer: because its resolution mechanism isn't the fixed-position linked list at all — use() resolves a Promise via the Suspense boundary lookup mechanism or a Context via the Context provider tree lookup, both of which are found dynamically at the point of the call based on the current component tree structure, not by matching against a pre-existing node created during an earlier mount. There's no "wrong node" it could read, because it isn't reading from the hooks list in the first place.

Q5: A component's effect has an empty dependency array but the interviewer says it still logs a stale prop value after the prop changes multiple times. Why, precisely?

Strong answer: an empty dependency array means the effect's create function only runs once, at mount — the closure created at that moment captured whatever the prop's value was during that specific render, and since the effect never re-runs, that closure (and the stale value it captured) is never replaced. This is the textbook stale-closure bug from this chapter's dedicated section, and the fix is either adding the prop to the dependency array (if the effect should legitimately re-run when it changes) or reading the latest value via a ref/useEffectEvent (if it shouldn't).

Summary

Key mental models for the interview:

  • Hooks are a linked list on the Fiber, matched purely by call order. There is no name-based identity — position is identity.
  • Custom hooks don't create their own storage. Their internal hook calls append directly to the calling component's own flat list.
  • useRef is the same mechanism as any hook, minus the update queue. That's the entire reason mutating it doesn't trigger a re-render.
  • Closures capture the specific render's values, permanently, via ordinary JS scoping. "Stale closure" bugs are a direct consequence, not a React quirk — the fix is either re-running the effect (dependency array) or reading a mutable container (ref/useEffectEvent) instead of the closed-over value.
  • use() is a deliberate, narrow exception, not a general relaxation of the Rules of Hooks — it resolves dynamically against Suspense/Context, not the positional list.

What NOT to say in an interview:

  • ❌ "Hooks are matched by variable name" — there is no name tracking at runtime at all; it's purely positional.
  • ❌ "Strict Mode's double rendering is a bug/annoyance to disable" — it's a deliberate, development-only tool for surfacing non-idempotent renders and missing effect cleanup.
  • ❌ "useEffectEvent/refs are hacks to get around the dependency array" — they're the correct tool specifically when a value needs to be read at its latest value without being part of what triggers the effect to re-run.
  • ❌ "use() means the Rules of Hooks are being phased out" — it's a narrowly-scoped exception for Promises/Context, not a general change to how useState/useEffect/etc. work.

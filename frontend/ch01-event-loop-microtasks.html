Hard Event Loop Microtasks V8 Performance

How does the JavaScript event loop actually work, and why can a microtask starve the rendering pipeline?

Key Takeaway: The event loop processes all microtasks before yielding to the rendering pipeline. A synchronous microtask loop (e.g., recursive Promise resolution) will indefinitely block painting, rAF callbacks, and user input — even though the code is "asynchronous."

Interviewer's Intent

What they're really testing:

  • Do you understand the event loop at the specification level, not just "JavaScript is single-threaded"?
  • Can you explain the difference between microtasks and macrotasks and their scheduling implications?
  • Do you know why asynchronous code can still block the UI?
  • Have you debugged rendering jank caused by microtask starvation in production?
  • Can you reason about scheduling priorities (user input > animation > background work)?

This question separates engineers who say "JavaScript is async and non-blocking" from those who understand that JavaScript is fundamentally synchronous, single-threaded, and relies on a cooperative scheduling model where the event loop orchestrates task execution, microtask draining, and rendering opportunities.

At the senior level, interviewers expect you to explain when the browser can paint, why Promises execute before setTimeout, and how to structure code so that heavy computation doesn't freeze the UI.

60-Second Interview Answer

Use this in the interview:

"The JavaScript event loop is a continuous cycle that processes work in a specific order. Each iteration:

1. Execute one macrotask — from the task queue (setTimeout, I/O, user events).
2. Drain the entire microtask queue — all Promises, queueMicrotask, MutationObserver callbacks run to completion before anything else.
3. Render if needed — the browser checks if it's time to repaint (~16ms for 60fps), runs requestAnimationFrame callbacks, then performs style/layout/paint.
4. Optionally run requestIdleCallback — if there's time remaining in the frame.

The critical insight is step 2: microtasks are drained completely before rendering. If a microtask schedules another microtask recursively, the rendering pipeline starves — the page freezes even though the code appears asynchronous. This is why Promise.resolve().then() in a loop can block the UI just as badly as a synchronous while loop.

For heavy computation, I use setTimeout or scheduler.yield() to break work into macrotasks, giving the browser rendering opportunities between chunks. For animation, I use requestAnimationFrame which runs right before paint. For background work, requestIdleCallback runs only when the main thread is idle."

V8 Execution Model

How V8 fits within the browser's event loop

V8 is a JavaScript engine, not a runtime. It provides:

  • Call Stack — executes JavaScript synchronously
  • Heap — memory allocation for objects
  • Microtask Queue — V8 manages this directly

The browser (or Node.js) provides the event loop, task queues, timers, and I/O. V8 exposes hooks that the embedder uses to drain microtasks after each call stack empties.

V8's JIT Pipeline — Why execution speed matters for the event loop

V8 compiles JavaScript through multiple tiers:

  1. Ignition (Interpreter) — bytecode execution, fast startup
  2. Sparkplug — fast baseline compiler (no optimization)
  3. Maglev — mid-tier optimizing compiler
  4. TurboFan — full optimizing compiler with speculative optimization

Long-running synchronous functions block the event loop regardless of how optimized they are. The only way to yield control is to return from the current call stack. No amount of JIT optimization fixes a fundamentally blocking algorithm.

Call Stack & Execution Contexts

Execution Context structure

Every function invocation creates an Execution Context pushed onto the call stack:

  • Variable Environment — let, const, var bindings
  • Lexical Environment — block-scoped bindings + outer reference
  • this binding — determined by call site

The call stack is LIFO. JavaScript can only run one function at a time. The event loop cannot process the next task until the call stack is completely empty.

function main() {
  console.log('1');       // Pushed to stack, executes, popped
  setTimeout(() => {
    console.log('2');     // Callback queued as macrotask
  }, 0);
  Promise.resolve().then(() => {
    console.log('3');     // Callback queued as microtask
  });
  console.log('4');       // Pushed to stack, executes, popped
}

main();
// Output: 1, 4, 3, 2
// Explanation:
// - main() runs synchronously: logs 1, schedules setTimeout, schedules Promise, logs 4
// - Call stack empties → microtask queue drains → logs 3
// - Event loop picks next macrotask → logs 2
Stack overflow and the event loop

A stack overflow (RangeError: Maximum call stack size exceeded) is a synchronous problem — it means you've pushed too many frames without returning. The event loop never gets a chance to intervene because the call stack never empties.

// This overflows the stack synchronously — event loop cannot help
function infinite() {
  return infinite(); // No yield point, stack grows unbounded
}

// This does NOT overflow — each call is a separate macrotask
function safeRecursion(n) {
  if (n <= 0) return;
  console.log(n);
  setTimeout(() => safeRecursion(n - 1), 0); // Yields to event loop
}

Task Queue (Macrotasks)

What are macrotasks and where do they come from?

Macrotasks (officially just "tasks" in the HTML spec) are queued by the browser when external events occur or when APIs like setTimeout fire. Each event loop iteration processes exactly one macrotask before checking for rendering opportunities.

Sources of macrotasks:

Source Example Notes
Timer APIs setTimeout, setInterval Minimum 4ms delay after nested calls (HTML spec)
User interaction click, keydown, scroll Each event dispatch is a separate task
I/O completion XMLHttpRequest load, fetch response Callback queued when response arrives
MessageChannel port.postMessage() Used by React's scheduler for yielding
History API popstate Navigation events
postMessage window.postMessage() Cross-origin or self-messaging

Key Insight: The HTML spec allows the browser to choose which task queue to service next, but does not mandate priority ordering. In practice, Chromium's implementation prioritizes user interaction tasks over timer tasks — this is an implementation detail, not a specification guarantee. This is why in Chrome a setTimeout callback may be delayed if click events are queued, but other browsers may schedule differently.

Why only one macrotask per loop iteration?

The HTML specification states that each event loop iteration picks one task, then runs microtasks, then optionally renders. This ensures the browser gets regular opportunities to:

  • Run requestAnimationFrame callbacks
  • Recalculate styles and layout
  • Paint pixels to the screen

If the browser processed all queued macrotasks before rendering, a burst of setTimeout callbacks could freeze the UI just like synchronous code.

Microtask Queue

What are microtasks and why are they drained completely?

Microtasks are higher-priority callbacks that execute after the current task completes but before the browser yields to rendering. The entire microtask queue is drained before anything else happens.

Sources of microtasks:

  • Promise.then(), Promise.catch(), Promise.finally()
  • queueMicrotask()
  • MutationObserver callbacks
  • async/await continuations (after await)
console.log('script start');

setTimeout(() => console.log('setTimeout'), 0);

Promise.resolve()
  .then(() => console.log('promise 1'))
  .then(() => console.log('promise 2'));

queueMicrotask(() => console.log('queueMicrotask'));

console.log('script end');

// Output:
// script start
// script end
// promise 1
// queueMicrotask
// promise 2
// setTimeout

// Why: script runs (macrotask) → microtask queue drains fully → next macrotask
Microtask checkpoint — when exactly does it run?

The microtask checkpoint runs in multiple places, not just "after a macrotask":

  1. After a macrotask completes (call stack empties)
  2. After a microtask completes (to handle newly queued microtasks)
  3. After each callback in certain APIs (e.g., after each MutationObserver delivery)

This means microtasks queued during microtask processing are executed in the same drain cycle. The ordering can be subtle — it depends on when each microtask is enqueued relative to others:

// Subtle ordering — queueMicrotask vs chained .then()
Promise.resolve()
  .then(() => {
    console.log('micro 1');
    // queueMicrotask appends to the queue RIGHT NOW
    queueMicrotask(() => console.log('micro 1.1'));
  })
  .then(() => console.log('micro 2'));

// Output: micro 1, micro 1.1, micro 2
// All complete before any rendering opportunity
//
// Why this order?
// 1. The first .then(cb1) is queued as a microtask
// 2. cb1 runs → logs 'micro 1' → queueMicrotask appends 'micro 1.1' to the queue
// 3. cb1 returns → the intermediate Promise resolves → NOW .then(cb2) is enqueued
// 4. Queue state: ['micro 1.1', 'micro 2'] — 1.1 was enqueued first
// 5. Drain continues: logs 'micro 1.1', then 'micro 2'
//
// Key insight: queueMicrotask() enqueues immediately during cb1 execution,
// but the chained .then(cb2) only enqueues AFTER cb1 returns and the
// Promise resolution machinery runs.

Danger Zone: If a microtask always queues another microtask, the drain never completes. The browser can never render. The page is frozen.

Event Loop Phases (Browser vs Node.js)

Browser Event Loop — The complete cycle

The HTML specification defines the event loop processing model as:

┌─────────────────────────────────────────────────────────────┐
│                   EVENT LOOP ITERATION                       │
│                                                             │
│  1. Pick one task from a task queue                         │
│     ┌──────────────────────────────┐                       │
│     │  Execute task (call stack)    │                       │
│     └──────────────┬───────────────┘                       │
│                    │                                        │
│  2. Drain microtask queue (completely)                      │
│     ┌──────────────────────────────┐                       │
│     │  Run ALL microtasks           │◄──── loops until     │
│     │  (including newly queued)     │      queue is empty  │
│     └──────────────┬───────────────┘                       │
│                    │                                        │
│  3. Rendering opportunity? (approx every 16.6ms)           │
│     ┌──────────────────────────────┐                       │
│     │  a. Run requestAnimationFrame │                       │
│     │  b. Recalculate Style         │                       │
│     │  c. Layout                    │                       │
│     │  d. Paint                     │                       │
│     │  e. Composite                 │                       │
│     └──────────────┬───────────────┘                       │
│                    │                                        │
│  4. If idle time remains in frame:                         │
│     ┌──────────────────────────────┐                       │
│     │  Run requestIdleCallback      │                       │
│     └──────────────────────────────┘                       │
│                                                             │
│  ──── Repeat ────                                          │
└─────────────────────────────────────────────────────────────┘

Important: Step 3 is NOT guaranteed every iteration. The browser decides when to render based on display refresh rate, page visibility, and whether visual changes occurred. A background tab may never get rendering opportunities.

Node.js Event Loop — libuv phases

Node.js uses libuv and has a different phase structure. Since Node 11+, microtasks drain after every individual callback within a phase — not just at phase boundaries. This makes Node's behavior much closer to the browser's model:

┌───────────────────────────────────────────────────────────┐
│                   Node.js Event Loop                       │
│                                                           │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  Timers Phase: setTimeout, setInterval              │ │
│  │                                                     │ │
│  │  callback1 → [drain microtasks] →                   │ │
│  │  callback2 → [drain microtasks] → ...               │ │
│  └─────────────────────┬───────────────────────────────┘ │
│                        ▼                                  │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  Pending I/O: system-level callbacks                │ │
│  │  callback → [drain microtasks] → ...                │ │
│  └─────────────────────┬───────────────────────────────┘ │
│                        ▼                                  │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  Idle / Prepare (internal use)                      │ │
│  └─────────────────────┬───────────────────────────────┘ │
│                        ▼                                  │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  Poll: I/O events, new connections                  │ │
│  │  callback → [drain microtasks] → ...                │ │
│  └─────────────────────┬───────────────────────────────┘ │
│                        ▼                                  │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  Check: setImmediate                                │ │
│  │  callback → [drain microtasks] → ...                │ │
│  └─────────────────────┬───────────────────────────────┘ │
│                        ▼                                  │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  Close callbacks: socket.on('close')                │ │
│  │  callback → [drain microtasks] → ...                │ │
│  └─────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────┘

Key difference from pre-Node 11: Before Node 11, microtasks only drained between phases — meaning two timer callbacks in the same phase would both execute before any microtask ran. Since Node 11+, microtasks drain after each individual callback, matching browser semantics. process.nextTick() is a separate queue that drains before Promise microtasks at each checkpoint.

// Demonstrates Node 11+ per-callback microtask draining
setTimeout(() => {
  console.log('timer1');
  Promise.resolve().then(() => console.log('microtask from timer1'));
}, 0);
setTimeout(() => {
  console.log('timer2');
}, 0);

// Node 11+ output (same as browser):
//   timer1
//   microtask from timer1
//   timer2
//
// Pre-Node 11 output (drained between phases, not callbacks):
//   timer1
//   timer2
//   microtask from timer1
Browser vs Node.js — practical differences
Aspect Browser Node.js
Rendering Integrated into event loop N/A (no rendering)

Timer precision Clamped to 4ms (nested), 1ms (top-level) 1ms minimum
I/O model Web APIs (fetch, XHR) libuv (epoll, kqueue, IOCP)

requestAnimationFrame Timing

Where rAF sits in the event loop

requestAnimationFrame callbacks run just before the browser performs style recalculation, layout, and paint — in the rendering step of the event loop. They do NOT go into the task queue or microtask queue.

// rAF is called once per frame, right before paint
requestAnimationFrame(() => {
  console.log('rAF');  // Runs at rendering time, ~16.6ms intervals
});

setTimeout(() => {
  console.log('timeout');  // Runs as a macrotask
}, 0);

Promise.resolve().then(() => {
  console.log('microtask');  // Runs after current task, before render
});

// Typical output: microtask → timeout → rAF
// (rAF waits for next render opportunity; timeout runs in next event loop iteration)

Frame budget: At 60fps, each frame has ~16.6ms. Your JavaScript (macrotask + microtasks) plus rendering must complete within this budget. If JavaScript takes 20ms, the frame is dropped — the user perceives jank.

rAF scheduling guarantees and gotchas
  • One call per frame: rAF callbacks run once per rendering opportunity, not per event loop iteration.
  • Batched execution: All rAF callbacks queued before the current frame are executed together. A rAF callback that schedules another rAF runs it in the next frame.
  • Not fired in background tabs: To save resources, browsers pause rAF when the tab is hidden.
  • Timestamp parameter: The callback receives a DOMHighResTimeStamp — use it instead of Date.now() for animation timing.
// Smooth animation pattern
function animate(timestamp) {
  // Use timestamp for frame-independent animation
  const elapsed = timestamp - startTime;
  const progress = Math.min(elapsed / duration, 1);
  
  element.style.transform = `translateX(${progress * 300}px)`;
  
  if (progress < 1) {
    requestAnimationFrame(animate); // Schedule next frame
  }
}

const startTime = performance.now();
const duration = 1000; // 1 second animation
requestAnimationFrame(animate);

requestIdleCallback

Scheduling non-urgent work during idle periods

requestIdleCallback runs when the browser has idle time — after all tasks, microtasks, and rendering are complete, and there's still time before the next frame deadline.

│◄────────────── Frame (16.6ms) ──────────────►│
│                                               │
│ Task │ Microtasks │ rAF │ Style/Layout/Paint │ Idle │
│  5ms │    2ms     │ 1ms │       4ms          │ 4.6ms│
│                                               │      │
│                                          requestIdleCallback
│                                          runs here
        
// Schedule low-priority work
requestIdleCallback((deadline) => {
  // deadline.timeRemaining() tells you how much idle time is left
  while (deadline.timeRemaining() > 0 && tasks.length > 0) {
    processTask(tasks.shift());
  }
  
  // If more work remains, schedule for next idle period
  if (tasks.length > 0) {
    requestIdleCallback(processRemainingTasks);
  }
}, { timeout: 2000 }); // Force execution within 2s even if no idle time

Caution: requestIdleCallback is NOT suitable for urgent UI updates. It may be delayed indefinitely if the main thread stays busy. Safari has never shipped requestIdleCallback (as of 2024, it remains unimplemented). Use a polyfill based on requestAnimationFrame + MessageChannel, or use scheduler.yield() (shipped in Chrome 129+, Sept 2024) for cooperative yielding.

React's Scheduler — inspired by requestIdleCallback

React's internal scheduler was initially based on requestIdleCallback but switched to MessageChannel for more consistent scheduling. It implements its own priority queue with 5 levels:

  • Immediate — synchronous-like (user input)
  • UserBlocking — 250ms expiration
  • Normal — 5000ms expiration
  • Low — 10000ms expiration
  • Idle — never expires (until nothing else to do)

This approach allows React to yield to the browser between work units while maintaining control over scheduling priorities — something requestIdleCallback alone couldn't provide.

Microtask Starvation

How microtasks can freeze the entire page

Because the microtask queue must fully drain before the browser can render, a recursive microtask chain prevents painting, user interaction, and even macrotask processing:

// ⚠️ THIS FREEZES THE PAGE
function recursiveMicrotask() {
  Promise.resolve().then(() => {
    // Do some work...
    doExpensiveComputation();
    
    // Schedule more work as a microtask — BAD!
    recursiveMicrotask(); // Rendering never gets a chance
  });
}
recursiveMicrotask();
// The page is now frozen. No clicks, no scrolling, no painting.

This is functionally equivalent to:

// Equally bad — but more obviously wrong
while (true) {
  doExpensiveComputation();
}

The trap: Developers assume that because Promises are "asynchronous," recursive Promise chains won't block. But microtasks are only async in the sense that they defer until the current synchronous code completes — they still block the rendering pipeline.

The fix — yielding to the macrotask queue

To prevent starvation, break work into macrotasks so the browser gets rendering opportunities between chunks:

// ✅ CORRECT — yields to the event loop between chunks
function processItemsYielding(items) {
  let index = 0;
  
  function processChunk() {
    const deadline = performance.now() + 5; // 5ms time budget per chunk
    
    while (index < items.length && performance.now() < deadline) {
      processItem(items[index]);
      index++;
    }
    
    if (index < items.length) {
      // Use setTimeout (macrotask) to yield — browser can render between chunks
      setTimeout(processChunk, 0);
    }
  }
  
  processChunk();
}

// ✅ Modern approach — scheduler.yield() (Chrome 129+, Sept 2024)
async function processItemsModern(items) {
  for (const item of items) {
    processItem(item);
    
    // Yield to the event loop, letting browser render
    if (needsYield()) {
      await scheduler.yield(); // or: await new Promise(r => setTimeout(r, 0));
    }
  }
}
Real-world starvation scenario — MutationObserver feedback loop 
// ⚠️ MutationObserver microtask that triggers DOM mutation,
//    which triggers another MutationObserver microtask...
const observer = new MutationObserver((mutations) => {
  // This callback is a microtask
  for (const mutation of mutations) {
    // Modifying the DOM inside the observer callback
    // triggers another MutationObserver delivery (microtask)
    mutation.target.dataset.processed = 'true'; // Triggers observer again!
  }
});

observer.observe(element, { attributes: true, subtree: true });
element.setAttribute('data-init', 'true'); // Starts infinite microtask loop

Fix: Use a flag to prevent re-entrant processing, or disconnect/reconnect the observer:

let isProcessing = false;
const observer = new MutationObserver((mutations) => {
  if (isProcessing) return; // Prevent re-entrant calls
  isProcessing = true;
  
  for (const mutation of mutations) {
    mutation.target.dataset.processed = 'true';
  }
  
  isProcessing = false;
});

setTimeout vs queueMicrotask vs Promise.resolve

Scheduling API comparison table
API Queue Type Timing Rendering Use Case
queueMicrotask(fn) Microtask After current task, before render Blocks rendering Cleanup, batching state changes
Promise.resolve().then(fn) Microtask Same as queueMicrotask Blocks rendering Async chains
setTimeout(fn, 0) Macrotask Next event loop iteration (≥1ms, ≥4ms nested) Allows rendering Yielding to browser, chunking work
requestAnimationFrame(fn) rAF queue Before next paint (~16.6ms) Part of render step Visual updates, animations
requestIdleCallback(fn) Idle queue When idle time available After rendering Analytics, prefetching, non-urgent
MessageChannel Macrotask Next iteration (no 4ms clamp) Allows rendering Scheduler implementations (React)
scheduler.postTask(fn) Priority task Based on priority Allows rendering Priority-aware scheduling (new API)
When to use each — decision guide 
// ✅ Use queueMicrotask for synchronous-like cleanup
// that must run before the browser does anything else
element.addEventListener('click', () => {
  updateState();
  queueMicrotask(() => {
    // Runs immediately after this handler, before any rendering
    // Good for: batching DOM reads, notifying subscribers
    notifySubscribers();
  });
});

// ✅ Use setTimeout(fn, 0) to yield to the browser
// Allows rendering between chunks of work
function processLargeArray(items) {
  const CHUNK_SIZE = 100;
  let i = 0;
  function chunk() {
    const end = Math.min(i + CHUNK_SIZE, items.length);
    while (i < end) process(items[i++]);
    if (i < items.length) setTimeout(chunk, 0); // Yield!
  }
  chunk();
}

// ✅ Use MessageChannel for faster yielding (no 4ms clamp)
const channel = new MessageChannel();
channel.port1.onmessage = () => { /* next chunk of work */ };
channel.port2.postMessage(null); // Schedules macrotask without timer delay

// ✅ Use rAF for anything that changes visual state
requestAnimationFrame(() => {
  element.style.transform = `translateX(${x}px)`;
});
The 4ms timer clamping — why setTimeout(fn, 0) isn't instant

The HTML spec mandates that after 5 levels of nested setTimeout calls, the minimum delay is clamped to 4ms. This is why setTimeout(fn, 0) doesn't actually run after 0ms in practice.

// Demonstration of timer clamping
function measureTimerDelay(depth = 0) {
  const start = performance.now();
  setTimeout(() => {
    console.log(`Depth ${depth}: ${(performance.now() - start).toFixed(2)}ms`);
    if (depth < 10) measureTimerDelay(depth + 1);
  }, 0);
}
measureTimerDelay();
// Depth 0: ~0.1ms
// Depth 1: ~0.1ms
// ...
// Depth 5+: ~4ms (clamping kicks in)

This is why React uses MessageChannel instead of setTimeout — MessageChannel doesn't have the 4ms clamping, providing more responsive scheduling.

Web Workers & Off-Main-Thread

When the event loop isn't enough — true parallelism

The event loop is cooperative — all JavaScript on the main thread shares one call stack. For CPU-intensive work that can't be chunked (e.g., image processing, complex calculations, data parsing), Web Workers provide true parallel execution on separate threads.

Production Incident — Promise Chain Starvation in a Real-Time Dashboard

Symptoms
  • Real-time trading dashboard becomes unresponsive after 10-15 minutes of use
  • Click handlers stop firing; animations freeze
  • Browser tab eventually shows "Page Unresponsive" dialog
  • CPU shows 100% on the main thread
  • Only happens in production (high data volume), not development
Root Cause

A WebSocket message handler processed incoming market data using async/await in a tight loop. Under low volume, each iteration completed before new messages arrived. Under production load (1000+ messages/second), the pattern caused microtask starvation:

// ⚠️ THE PROBLEMATIC CODE
webSocket.onmessage = async (event) => {
  const updates = JSON.parse(event.data);
  
  // Each update processed as microtask chain
  for (const update of updates) {
    await processUpdate(update);    // Microtask
    await updateStore(update);      // Microtask
    await notifySubscribers(update); // Microtask — schedules React re-renders
  }
};

// With 1000+ messages/sec, each containing 50+ updates,
// the microtask queue grows faster than it drains.
// The browser NEVER gets a chance to paint or process user input.
Investigation
  1. Performance tab: Recorded a 5-second trace. Saw a single massive "Task" lasting 4800ms with no rendering frames.
  2. Call tree: 98% of time in microtask processing — thousands of Promise resolutions stacked.
  3. Network tab: WebSocket messages arriving faster than they could be processed.
  4. Performance.measure(): Added timing around the message handler — individual messages took 2-5ms, but accumulated without yielding.
Resolution 
// ✅ THE FIX — Batch + yield pattern
class MessageProcessor {
  #queue = [];
  #isProcessing = false;
  #frameDeadline = 8; // ms — leave headroom for rendering

  enqueue(messages) {
    this.#queue.push(...messages);
    if (!this.#isProcessing) this.#scheduleProcessing();
  }

  #scheduleProcessing() {
    this.#isProcessing = true;
    // Use MessageChannel for fast yielding without 4ms clamp
    const channel = new MessageChannel();
    channel.port1.onmessage = () => this.#processChunk();
    channel.port2.postMessage(null);
  }

  #processChunk() {
    const start = performance.now();
    
    while (this.#queue.length > 0) {
      if (performance.now() - start > this.#frameDeadline) {
        // Yield to browser — allow rendering and input
        this.#scheduleProcessing();
        return;
      }
      
      const update = this.#queue.shift();
      this.#processSynchronously(update); // No await — synchronous batch
    }
    
    // All caught up — flush React updates in one batch
    flushSync(() => notifySubscribers());
    this.#isProcessing = false;
  }

  #processSynchronously(update) {
    // Process without async — no microtask overhead
    store.set(update.symbol, update.price);
  }
}

webSocket.onmessage = (event) => {
  const updates = JSON.parse(event.data);
  processor.enqueue(updates);
};
Lessons Learned
  • async/await in hot paths is dangerous. Each await creates a microtask. In high-throughput scenarios, the microtask queue grows unbounded.
  • Always budget your frame time. If you can't guarantee completion within 8-10ms, implement a yielding strategy.
  • Batch before notifying. Don't trigger React re-renders for each individual data point. Collect changes, then flush once.
  • Use MessageChannel, not setTimeout. It yields without the 4ms clamping penalty.
  • Test with production data volumes. Event loop starvation often only manifests at scale.

Yielding strategy — cooperative multitasking pattern 
/**
 * Process a large dataset without blocking the main thread.
 * Uses cooperative scheduling — processes items in time-boxed chunks.
 */
function processInChunks(items, processFn, options = {}) {
  const {
    chunkTimeMs = 8,     // Time budget per chunk (leave room for 60fps rendering)
    onProgress = null,    // Progress callback
    onComplete = null,    // Completion callback
    signal = null         // AbortSignal for cancellation
  } = options;
  
  return new Promise((resolve, reject) => {
    let index = 0;
    const results = [];
    const total = items.length;
    
    function processChunk() {
      // Check for cancellation
      if (signal?.aborted) {
        reject(new DOMException('Aborted', 'AbortError'));
        return;
      }
      
      const chunkStart = performance.now();
      
      while (index < total) {
        // Check if we've exceeded our time budget
        if (performance.now() - chunkStart > chunkTimeMs) {
          // Yield to the browser via macrotask
          onProgress?.(index / total);
          setTimeout(processChunk, 0);
          return;
        }
        
        results.push(processFn(items[index], index));
        index++;
      }
      
      // All done
      onProgress?.(1);
      onComplete?.(results);
      resolve(results);
    }
    
    processChunk();
  });
}

// Usage

  largeArray,
  (item) => expensiveTransform(item),
  {
    chunkTimeMs: 8,
    onProgress: (pct) => updateProgressBar(pct),
    signal: controller.signal
  }
);

// Cancel if needed

/**
 * Uses navigator.scheduling.isInputPending() to detect
 * when user input is waiting — yield immediately in that case.
 * (Chrome 87+)
 */
function processWithInputAwareness(items, processFn) {
  let index = 0;
  
  function processChunk() {
    while (index < items.length) {
      // Check if user has pending input — yield immediately
      if (navigator.scheduling?.isInputPending?.({ includeContinuous: true })) {

        setTimeout(processChunk, 0);
        return;
      }
      
      processFn(items[index]);
      index++;
    }
  }

}

Common Mistakes

Mistake 1: Assuming async/await is non-blocking

The mistake: "I used async/await so it won't block the UI."

Reality: async/await is syntactic sugar over Promises. The code between await points runs synchronously. A CPU-intensive function doesn't become non-blocking just because you await it.

// ⚠️ STILL BLOCKS — the expensive work runs synchronously
async function processData(data) {
  const result = await heavyComputation(data); // Blocks until heavyComputation returns!
  return result;
}

// heavyComputation runs synchronously on the main thread.
// The "await" only helps if the function returns a Promise that
// resolves later (e.g., after a network request or Worker message).
Mistake 2: Using setInterval for animations

The mistake: Using setInterval(fn, 16) for smooth animations.

Reality: Timer callbacks are macrotasks — they don't align with the browser's refresh rate. They can drift, stack up, or fire at the wrong time relative to paint.

// ⚠️ BAD — not synchronized with display refresh
setInterval(() => {
  element.style.left = `${x++}px`; // May cause jank
}, 16);

// ✅ GOOD — synchronized with paint cycle
function animate() {
  element.style.left = `${x++}px`;
  requestAnimationFrame(animate); // Fires at display refresh rate
}
requestAnimationFrame(animate);
Mistake 3: Reading layout after writing (layout thrashing)

The mistake: Interleaving DOM writes and reads forces the browser to synchronously recalculate layout mid-script.

// ⚠️ FORCES SYNCHRONOUS LAYOUT — extremely expensive
items.forEach(item => {
  item.style.width = '100px';           // Write (invalidates layout)
  const height = item.offsetHeight;      // Read (forces synchronous layout!)
  item.style.height = `${height * 2}px`; // Write (invalidates again)
});

// ✅ BATCH READS, THEN WRITES
const heights = items.map(item => item.offsetHeight); // All reads first
items.forEach((item, i) => {
  item.style.width = '100px';
  item.style.height = `${heights[i] * 2}px`; // All writes together
});
Mistake 4: Not cleaning up recurring microtask sources

The mistake: MutationObservers or Promise-based polling that outlives its intended scope.

// ⚠️ Memory leak + unnecessary microtask processing
useEffect(() => {
  const observer = new MutationObserver(callback);
  observer.observe(ref.current, { childList: true, subtree: true });
  // Missing cleanup!
});

// ✅ Always disconnect
useEffect(() => {
  const observer = new MutationObserver(callback);
  observer.observe(ref.current, { childList: true, subtree: true });
  return () => observer.disconnect(); // Cleanup on unmount
}, []);
Mistake 5: Confusing concurrency with parallelism

The mistake: "Promise.all runs things in parallel."

Reality: Promise.all provides concurrency (multiple operations in-flight) but NOT parallelism (simultaneous CPU execution). All JavaScript still runs on one thread. The "parallelism" is only for I/O waiting — the network requests go out simultaneously, but their callbacks execute one at a time.

// These network requests are concurrent (in-flight simultaneously)
// but their response handlers execute sequentially on the main thread
const [users, posts] = await Promise.all([
  fetch('/users').then(r => r.json()),  // Concurrent I/O
  fetch('/posts').then(r => r.json())   // Concurrent I/O
]);

// For TRUE CPU parallelism, use Workers
const results = await Promise.all([
  worker1.process(chunk1), // Actual parallel execution
  worker2.process(chunk2)  // on separate threads
]);

Microtask vs Macrotask — choosing the right queue
  • Use microtask (queueMicrotask) when you need code to run after the current synchronous work but before any rendering or other tasks. Example: batching multiple synchronous state updates into a single notification.
  • Use macrotask (setTimeout) when you need to yield to the browser. Example: processing a large array in chunks while keeping the page responsive.
  • The trap: Using microtasks for "defer this work" when you actually need "yield to the browser" — they look similar but behave very differently.

Follow-up Interview Questions

Q1: What's the difference between setTimeout(fn, 0) and queueMicrotask(fn)?

Strong answer: setTimeout(fn, 0) schedules a macrotask — the callback runs in a future event loop iteration, after the browser has had a chance to render. queueMicrotask(fn) schedules a microtask — the callback runs before the event loop yields to the browser, in the current microtask drain. This means microtasks run sooner but can delay rendering if overused.

Q2: Can you starve the rendering pipeline with async/await? How?

Strong answer: Yes. If an async function awaits a synchronously resolving Promise (like Promise.resolve()) in a loop, each iteration is a microtask. Since all microtasks drain before rendering, a tight async loop starves the paint cycle. The fix is to yield to a macrotask (setTimeout or MessageChannel) periodically.

Q3: Why does React use MessageChannel instead of setTimeout or requestIdleCallback?

Strong answer: setTimeout has a minimum 4ms delay when nested beyond 5 levels (per HTML spec), making it too slow for React's scheduling needs. requestIdleCallback has unpredictable timing and isn't supported in all environments. MessageChannel provides immediate macrotask scheduling without timer clamping — it yields to the browser for rendering but resumes work as quickly as possible.

Q4: Explain the difference between concurrency and parallelism in JavaScript.

Strong answer: JavaScript's main thread provides concurrency through the event loop — multiple asynchronous operations can be in-flight simultaneously (network requests, timers), but their JavaScript callbacks execute one at a time on the single thread. True parallelism (simultaneous execution) requires Web Workers, each with their own event loop and call stack. Promise.all is concurrent I/O, not parallel computation.

Q5: How would you ensure smooth 60fps animations while processing data?

Strong answer: Use requestAnimationFrame for all visual updates — it synchronizes with the display refresh rate. For data processing, use time-boxed chunking: process items in a loop until a time budget (e.g., 8ms) is exceeded, then yield via setTimeout or MessageChannel. For heavy computation, move it to a Web Worker. CSS animations (transforms, opacity) can run on the compositor thread without JavaScript involvement.

Q6: What happens if you call setState in a microtask vs a macrotask in React 18?

Strong answer: In React 18, automatic batching means both are batched — regardless of whether updates originate in a React event handler, setTimeout, Promise, or native event. In React 17, only updates within React synthetic event handlers and lifecycle methods were batched; updates in setTimeout, Promises, or native event handlers triggered separate re-renders.

React 18's mechanism works by tracking an execution context: when setState is called, React marks the update on the fiber but doesn't immediately schedule a re-render. Instead, it schedules a single flush (via its internal scheduler using MessageChannel) that processes all pending updates together. For urgent (sync-lane) updates this flush is scheduled as a microtask; for transitions, React's scheduler handles the timing with lower priority. The key point: React doesn't literally wait for "the microtask queue to drain" — it uses its own scheduling infrastructure to coalesce updates, which may or may not align with microtask boundaries depending on the update's lane priority.

Q7: How does the browser decide when to render?

Strong answer: The browser aims for 60fps (one frame every 16.6ms) but rendering is not guaranteed every iteration. The browser decides to render when: (1) there are pending style/layout changes, (2) there are rAF callbacks waiting, (3) enough time has passed since the last paint, and (4) the page is visible. Background tabs, display:none content, and pages with no visual changes may skip rendering entirely.

Summary

Key mental models for the interview:

  • One macrotask → drain all microtasks → maybe render → repeat. This is the event loop in one sentence.
  • Microtasks are greedy. They run to completion and prevent rendering. Use them for batching, not for deferring heavy work.
  • Yielding = scheduling a macrotask. setTimeout, MessageChannel, or postMessage give the browser a rendering opportunity.
  • rAF is for visual changes. It runs at the right time relative to paint — not "approximately 16ms" like setTimeout.
  • The event loop doesn't provide parallelism. For true parallel computation, use Web Workers.
  • React's scheduler is a userland event loop. It implements priority queues and cooperative yielding on top of the browser's event loop using MessageChannel.

What NOT to say in an interview:

  • ❌ "JavaScript is asynchronous" — it's not. The event loop provides an asynchronous programming model, but JS execution is synchronous.
  • ❌ "setTimeout(fn, 0) runs immediately" — it doesn't. It runs in the next macrotask, after microtasks drain and potentially after rendering.
  • ❌ "Promises run in parallel" — they don't. They provide concurrent I/O, not parallel computation.
  • ❌ "async/await makes code non-blocking" — only if the awaited operation is truly asynchronous (network, timer, Worker). CPU-bound work still blocks.

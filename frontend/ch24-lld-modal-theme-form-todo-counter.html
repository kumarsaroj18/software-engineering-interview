LLD — Modal, Theme Switcher, Form, Todo & Counter

"Build a Modal, a Theme Switcher, a Form with real-time validation, a Todo list with persistence, and a Counter with re-render optimization."
Key Takeaway: These five components look simple but each one hides a senior-level trap: modals need portals and focus management, not just conditional rendering; theme switchers need to avoid FOUC and work under SSR; forms need to isolate re-renders per field; todo lists need a reducer-shaped mental model plus resilient persistence; counters are a vehicle for demonstrating memo/useCallback discipline, not React knowledge itself. Interviewers are grading your instinct for edge cases and API design, not whether you can render a <button>.

Interviewer's Intent

Why these five specifically, and what "good" looks like

Chapter 23 covered the LLD round's general strategy (clarify → design → implement → optimize). This chapter applies that strategy to five components that show up constantly in 45-60 minute frontend rounds because each has a "hidden requirement" that separates a mid-level solution from a senior one:

Scoring rubric an interviewer actually uses: Did you ask about scale/constraints before coding? Did you build the primitive (portal, reducer, hook) rather than reach for a library? Did you handle at least 2 edge cases unprompted? Did you explain a trade-off without being asked "why not X instead"?

Component 4: Modal / Dialog

Requirements & Constraints

Clarifying questions to ask before coding:

  • Can modals be nested (a confirm dialog opened from within another modal)?
  • Does content need to animate in/out, or is a hard show/hide acceptable?
  • Should closing be blockable (e.g., "unsaved changes" confirm)?
  • Is this rendered inside a scrollable ancestor with overflow: hidden or transform (which breaks position: fixed)?

Core requirements: render above all other content regardless of DOM position, trap keyboard focus inside while open, restore focus to the trigger element on close, close on Escape and outside click, lock body scroll, and be screen-reader accessible as a dialog.

Native <dialog> element — know when to use it

The HTML <dialog> element with .showModal() provides many modal features for free:

function NativeModal({ isOpen, onClose, title, children }) {
  const dialogRef = useRef(null);

  useEffect(() => {
    const dialog = dialogRef.current;
    if (isOpen) {
      dialog.showModal(); // Puts in top layer (no z-index issues), traps focus, adds backdrop
    } else {
      dialog.close();
    }
  }, [isOpen]);

  return (
    <dialog
      ref={dialogRef}
      onClose={onClose}  // Fires on Escape automatically
      onClick={(e) => { if (e.target === dialogRef.current) onClose(); }} // backdrop click
      aria-labelledby="dialog-title"
    >
      <h2 id="dialog-title">{title}</h2>
      {children}
      <button onClick={onClose}>Close</button>
    </dialog>
  );
}

/* CSS: dialog::backdrop { background: rgba(0,0,0,0.5); } */

Built-in behaviors: top-layer rendering (no z-index wars), focus trapping, Escape dismissal, ::backdrop pseudo-element, inert on background content.

When to use native <dialog>: Simpler cases, no animation needs, all modern browsers (Chrome 37+, Firefox 98+, Safari 15.4+). When to use a custom portal: Complex enter/exit animations, nested modal stacks with custom transitions, or when you need fine-grained control over focus restoration behavior.

Interview tip: Always mention you know <dialog> exists. Then explain why you might still build a custom solution: "Native dialog handles the simple case well, but for our design system we needed animated transitions, nested stacks, and imperative control — so we built a portal-based solution on top."

React Portal — Why It's Required

A modal rendered in-place inside a deeply nested component tree inherits every ancestor's overflow, z-index, and transform context. A single ancestor with transform: translateX(0) (common for animation) creates a new containing block, silently breaking position: fixed centering. createPortal renders the modal's DOM subtree into a different DOM node — typically document.body — while keeping it in the same React tree for event bubbling, context, and state.

import { createPortal } from 'react-dom';

function ModalPortal({ children }) {
  const elRef = useRef(null);
  if (!elRef.current) {
    elRef.current = document.createElement('div');
    elRef.current.setAttribute('data-modal-root', '');
  }

  useEffect(() => {
    const root = document.getElementById('modal-root') ?? document.body;
    root.appendChild(elRef.current);
    return () => {
      elRef.current.remove();
    };
  }, []);

  return createPortal(children, elRef.current);
}
Interview follow-up bait: "Why not just render the modal at the bottom of your JSX tree instead of using a portal?" Answer: because React events still bubble through the React tree, not the DOM tree, when using a portal — so onClick handlers on ancestors still fire correctly. But CSS cascade and DOM-based layout (stacking context, clipping) follow the actual DOM position, which is why the portal is necessary specifically for those.
Focus Trap Implementation

WCAG requires that keyboard focus cannot leave an open modal via Tab/Shift+Tab. The trap must: capture the previously focused element, move focus into the modal on open, cycle focus between the first and last focusable elements, and restore focus to the trigger on close.

const FOCUSABLE_SELECTOR =
  'a[href], button:not([disabled]), textarea, input, select, [tabindex]:not([tabindex="-1"])';

function useFocusTrap(containerRef, isActive) {
  useEffect(() => {
    if (!isActive) return;

    const previouslyFocused = document.activeElement;
    const container = containerRef.current;
    const focusables = () => Array.from(container.querySelectorAll(FOCUSABLE_SELECTOR));

    // Move focus into the modal — prefer an explicit autofocus target
    const initial = container.querySelector('[data-autofocus]') || focusables()[0];
    initial?.focus();

    function handleKeydown(e) {
      if (e.key !== 'Tab') return;
      const nodes = focusables();
      if (nodes.length === 0) return;
      const first = nodes[0];
      const last = nodes[nodes.length - 1];

      if (e.shiftKey && document.activeElement === first) {
        e.preventDefault();
        last.focus();
      } else if (!e.shiftKey && document.activeElement === last) {
        e.preventDefault();
        first.focus();
      }
    }

    container.addEventListener('keydown', handleKeydown);
    return () => {
      container.removeEventListener('keydown', handleKeydown);
      previouslyFocused?.focus?.(); // Restore focus on close/unmount
    };
  }, [isActive, containerRef]);
}
Common bug: Computing focusables() once outside the keydown handler. If the modal's content changes (an accordion expands, revealing new focusable elements), a stale list breaks the trap. Recompute it on every keydown.
Escape Key, Outside Click & Scroll Lock 
function useDismiss(isOpen, onClose, containerRef) {
  useEffect(() => {
    if (!isOpen) return;

    function handleKey(e) {
      if (e.key === 'Escape') onClose();
    }
    function handlePointerDown(e) {
      if (containerRef.current && !containerRef.current.contains(e.target)) {
        onClose();
      }
    }

    document.addEventListener('keydown', handleKey);
    // pointerdown (not click) avoids closing when a drag/selection ends outside
    document.addEventListener('pointerdown', handlePointerDown);
    return () => {
      document.removeEventListener('keydown', handleKey);
      document.removeEventListener('pointerdown', handlePointerDown);
    };
  }, [isOpen, onClose, containerRef]);
}

function useScrollLock(isActive) {
  useEffect(() => {
    if (!isActive) return;
    const { overflow, paddingRight } = document.body.style;
    const scrollbarWidth = window.innerWidth - document.documentElement.clientWidth;

    document.body.style.overflow = 'hidden';
    // Prevent layout shift from the disappearing scrollbar
    if (scrollbarWidth > 0) {
      document.body.style.paddingRight = `${scrollbarWidth}px`;
    }
    return () => {
      document.body.style.overflow = overflow;
      document.body.style.paddingRight = paddingRight;
    };
  }, [isActive]);
}

Nested modals & stacking: maintain a module-level counter (or a context-provided stack) of currently-open modals. Only the topmost modal should respond to Escape, and scroll-lock should only be released when the last modal in the stack closes — a naive per-modal cleanup would unlock scrolling while an outer modal is still open.

Complete Implementation 
import { createContext, useContext, useEffect, useId, useRef, useState } from 'react';
import { createPortal } from 'react-dom';

const ModalStackContext = createContext(null);

export function ModalStackProvider({ children }) {
  const [stack, setStack] = useState([]); // array of modal ids, top = last

  const push = (id) => setStack((s) => [...s, id]);
  const pop = (id) => setStack((s) => s.filter((x) => x !== id));
  const isTop = (id) => stack[stack.length - 1] === id;

  return (
    <ModalStackContext.Provider value={{ push, pop, isTop, depth: stack.length }}>
      {children}
    </ModalStackContext.Provider>
  );
}

export function Modal({ isOpen, onClose, title, children, initialFocusRef }) {
  const id = useId();
  const dialogRef = useRef(null);
  const stack = useContext(ModalStackContext);

  useEffect(() => {
    if (!isOpen) return;
    stack?.push(id);
    return () => stack?.pop(id);
  }, [isOpen, id, stack]);

  const isTopMost = stack ? stack.isTop(id) : true;

  useFocusTrap(dialogRef, isOpen);
  useDismiss(isOpen && isTopMost, onClose, dialogRef);
  useScrollLock(isOpen && (stack ? stack.depth === 1 : true));

  if (!isOpen) return null;

  return createPortal(
    <div className="modal-overlay" data-testid="modal-overlay">
      <div
        ref={dialogRef}
        className="modal-dialog"
        role="dialog"
        aria-modal="true"
        aria-labelledby={`${id}-title`}
      >
        <header className="modal-header">
          <h2 id={`${id}-title`}>{title}</h2>
          <button
            aria-label="Close dialog"
            onClick={onClose}
            className="modal-close"
          >
            ×
          </button>
        </header>
        <div className="modal-body">{children}</div>
      </div>
    </div>,
    document.body
  );
}

// Usage
function ConfirmDeleteExample() {
  const [open, setOpen] = useState(false);
  return (
    <ModalStackProvider>
      <button onClick={() => setOpen(true)}>Delete account</button>
      <Modal isOpen={open} onClose={() => setOpen(false)} title="Confirm deletion">
        <p>This cannot be undone.</p>
        <button data-autofocus onClick={() => setOpen(false)}>Cancel</button>
        <button onClick={() => { /* delete */ setOpen(false); }}>Delete</button>
      </Modal>
    </ModalStackProvider>
  );
}

Enter/exit animation note: to animate exit, you cannot unmount immediately on close — you need a brief "closing" state that unmounts only after the CSS transition's transitionend fires (or use a library like Framer Motion's AnimatePresence which handles this exit-before-unmount timing for you).

Edge Cases
  • Modal opened with no focusable children: the trap must fall back to focusing the dialog container itself (give it tabIndex={-1}) rather than throwing when focusables() is empty.
  • Trigger element removed from DOM while modal is open (e.g., it was a row in a list that got deleted): guard the focus-restore call with optional chaining and verify the element is still connected (el.isConnected).
  • Modal contains an <iframe> or third-party widget that manages its own focus — the trap can fight with it. Document this as a known limitation rather than trying to solve it generically.
  • Server-side rendering: document.body doesn't exist during SSR. Guard the portal target lookup and render null until mounted (useEffect-gated mounted flag), matching the hydration-safety pattern from the theme switcher below.

Component 5: Theme Switcher (Dark / Light)

Requirements & Architecture Decision

Requirements: instant, flash-free theme on load; respects prefers-color-scheme when the user hasn't chosen explicitly; persists an explicit choice across reloads; works correctly with SSR (no hydration mismatch); doesn't force every themed component to re-render on toggle.

Key architectural decision: theming is a CSS problem, not a React state problem. React should only own which theme name is active — the actual visual change should happen via CSS custom properties scoped to a data-theme attribute on <html>, so toggling doesn't re-render your component tree at all.
CSS Custom Properties Strategy 
:root[data-theme="light"] {
  --bg: #ffffff;
  --text: #111111;
  --accent: #2563eb;
}

:root[data-theme="dark"] {
  --bg: #0f1115;
  --text: #e6e6e6;
  --accent: #60a5fa;
}

body {
  background: var(--bg);
  color: var(--text);
  transition: background 0.15s ease, color 0.15s ease;
}

Every component reads colors via var(--bg) etc. Switching themes is one attribute mutation (documentElement.dataset.theme = 'dark') — the browser repaints affected properties without React re-rendering a single component.

Flash of Unstyled/Wrong Content (FOUC) Prevention

If the theme is applied inside a useEffect, there's a visible flash: the page paints with the default theme, then useEffect runs (after paint) and flips it. The fix is a tiny inline, render-blocking script placed in <head> — before React even loads — that reads storage/media query and sets the attribute synchronously.

<script>
  (function () {
    try {
      var stored = localStorage.getItem('theme');
      var theme = stored || (matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light');
      document.documentElement.setAttribute('data-theme', theme);
    } catch (e) {
      document.documentElement.setAttribute('data-theme', 'light');
    }
  })();
</script>
Why this must be inline and synchronous: an external script file is fetched asynchronously and would still allow a flash. It must be a blocking inline <script> executed before the first paint, placed as early as possible in <head>.
System Preference Sync & Context API 
const ThemeContext = createContext(null);

function getSystemTheme() {
  return matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light';
}

export function ThemeProvider({ children }) {
  // Read the value the inline script already applied — avoids a mismatch re-render
  // SSR-safe: guard against 'document' being undefined during server rendering
  const [theme, setTheme] = useState(
    () => typeof document !== 'undefined'
      ? document.documentElement.getAttribute('data-theme') || 'light'
      : 'light'
  );
  const [isExplicit, setIsExplicit] = useState(
    () => typeof localStorage !== 'undefined' ? localStorage.getItem('theme') != null : false
  );

  useEffect(() => {
    document.documentElement.setAttribute('data-theme', theme);
  }, [theme]);

  // Follow system changes ONLY if the user hasn't made an explicit choice
  useEffect(() => {
    if (isExplicit) return;
    const mql = matchMedia('(prefers-color-scheme: dark)');
    const handler = (e) => setTheme(e.matches ? 'dark' : 'light');
    mql.addEventListener('change', handler);
    return () => mql.removeEventListener('change', handler);
  }, [isExplicit]);

  const setExplicitTheme = (next) => {
    setTheme(next);
    setIsExplicit(true);
    localStorage.setItem('theme', next);
  };

  const resetToSystem = () => {
    setIsExplicit(false);
    localStorage.removeItem('theme');
    setTheme(getSystemTheme());
  };

  return (
    <ThemeContext.Provider value={{ theme, setExplicitTheme, resetToSystem, isExplicit }}>
      {children}
    </ThemeContext.Provider>
  );
}

export const useTheme = () => useContext(ThemeContext);
SSR Considerations & Hydration Safety

On the server, localStorage and matchMedia don't exist, so the server-rendered HTML has no way to know the user's real preference — it must render a neutral default (or the inline script's job, which only runs client-side, handles it post-load). Two rules keep hydration mismatch-free:

  • The server always renders data-theme="light" (or omits the attribute) as a fixed default — never try to guess the client's preference server-side from a cookie unless you actually read a theme cookie on every request.
  • The initial React state must read from the DOM attribute the inline script already set (document.documentElement.getAttribute('data-theme')), not recompute from matchMedia — otherwise React's first client render can disagree with what's already painted, causing an actual (if brief) re-flash even without a hydration warning.
Complete Implementation 
function ThemeToggle() {
  const { theme, setExplicitTheme } = useTheme();
  return (
    <button
      role="switch"
      aria-checked={theme === 'dark'}
      aria-label="Toggle color theme"
      onClick={() => setExplicitTheme(theme === 'dark' ? 'light' : 'dark')}
    >
      {theme === 'dark' ? '🌙' : '☀️'}
    </button>
  );
}

// app entry (index.html <head>) must include the inline script from above,
// then:
function App() {
  return (
    <ThemeProvider>
      <ThemeToggle />
      <Page />
    </ThemeProvider>
  );
}
Edge Cases
  • localStorage throws (Safari private mode, disabled storage): wrap every access in try/catch and fall back to in-memory-only theming for that session.
  • Multiple tabs open: listen to the storage event to sync a theme change made in one tab to all others in the same origin.
  • Third-party embedded widgets (iframes) don't inherit :root CSS variables — you must postMessage the theme into the iframe if it needs to match.
  • Print stylesheets: dark theme should not apply when printing — add a @media print override that forces light variables regardless of data-theme.

Component 6: Form with Real-Time Validation

Requirements & Controlled vs Uncontrolled Trade-off

Requirements: validate on blur (not on every keystroke — too noisy) after first blur, then re-validate live on change; support field-level and form-level errors; support async validation (e.g., username availability) without racing stale responses; keep typing latency imperceptible even in large forms (no full-form re-render per keystroke).

ControlledUncontrolled
Value ownershipReact state is source of truthDOM is source of truth, read via ref/FormData
Re-renders per keystrokeYes (unless isolated) No
Real-time validation/formattingEasy (React sees every change)Requires manual event listeners
Best forRich validation, conditional fieldsLarge simple forms, file inputs

The pattern below is controlled per-field but isolates re-renders so that typing in one field never re-renders sibling fields or the parent form.

Custom useForm Hook & Per-Field Re-Render Isolation

The trick to avoiding a full-form re-render on every keystroke: the form's state lives in a single useReducer, but each <Field> subscribes to only its own slice via a context selector pattern, so a change to email doesn't re-render the password field.

function formReducer(state, action) {
  switch (action.type) {
    case 'CHANGE':
      return {
        ...state,
        values: { ...state.values, [action.name]: action.value },
        touched: state.touched[action.name] ? state.touched : { ...state.touched, [action.name]: false },
      };
    case 'BLUR':
      return {
        ...state,
        touched: { ...state.touched, [action.name]: true },
        errors: { ...state.errors, [action.name]: action.validate(state.values[action.name]) },
      };
    case 'SET_ERROR':
      return { ...state, errors: { ...state.errors, [action.name]: action.error } };
    case 'SUBMIT_START':
      return { ...state, isSubmitting: true };
    case 'SUBMIT_END':
      return { ...state, isSubmitting: false, errors: action.errors ?? state.errors };
    default:
      return state;
  }
}

function useForm({ initialValues, validators = {}, onSubmit }) {
  const [state, dispatch] = useReducer(formReducer, {
    values: initialValues,
    errors: {},
    touched: {},
    isSubmitting: false,
  });

  const handleChange = (name, value) => dispatch({ type: 'CHANGE', name, value });

  const handleBlur = (name) =>
    dispatch({ type: 'BLUR', name, validate: validators[name] ?? (() => undefined) });

  const handleSubmit = async (e) => {
    e.preventDefault();
    const errors = {};
    for (const name of Object.keys(validators)) {
      const err = validators[name](state.values[name]);
      if (err) errors[name] = err;
    }
    if (Object.keys(errors).length > 0) {
      dispatch({ type: 'SUBMIT_END', errors });
      return;
    }
    dispatch({ type: 'SUBMIT_START' });
    try {
      await onSubmit(state.values);
      dispatch({ type: 'SUBMIT_END', errors: {} });
    } catch (err) {
      dispatch({ type: 'SUBMIT_END', errors: { form: err.message } });
    }
  };

  return { state, handleChange, handleBlur, handleSubmit };
}
Isolating re-renders further: for very large forms (50+ fields), a single useReducer at the top still re-renders every field on every keystroke because they all read from the same state. The industry-standard fix (used by React Hook Form) is to keep field values in an uncontrolled ref map and only trigger re-renders for the specific field whose error/touched status changed, using a subscription model rather than context broadcast.
Schema-Based Validation (Zod) & Async Validation 
import { z } from 'zod';

const signupSchema = z.object({
  email: z.string().email('Enter a valid email'),
  password: z.string().min(8, 'At least 8 characters'),
  username: z.string().min(3),
});

function zodFieldValidator(schema, field) {
  return (value) => {
    const result = schema.shape[field].safeParse(value);
    return result.success ? undefined : result.error.issues[0].message;
  };
}

// Async validation with race-condition prevention
function useAsyncFieldValidation(checkFn, delay = 400) {
  const [status, setStatus] = useState('idle'); // idle | checking | valid | invalid
  const requestId = useRef(0);

  const check = useDebouncedCallback(async (value) => {
    const id = ++requestId.current;
    setStatus('checking');
    const ok = await checkFn(value);
    if (id !== requestId.current) return; // A newer request superseded this one
    setStatus(ok ? 'valid' : 'invalid');
  }, delay);

  return { status, check };
}

// Usage: check username availability without racing
function UsernameField() {
  const { status, check } = useAsyncFieldValidation(
    (value) => fetch(`/api/username-available?u=${value}`).then((r) => r.json()).then((d) => d.available)
  );
  return (
    <div>
      <input onChange={(e) => check(e.target.value)} aria-describedby="username-status" />
      <span id="username-status" aria-live="polite">
        {status === 'checking' && 'Checking…'}
        {status === 'invalid' && 'Username taken'}
        {status === 'valid' && 'Available'}
      </span>
    </div>
  );
}

Field-level vs form-level errors: field errors block only that field's submission-readiness and render inline via aria-describedby; form-level errors (e.g., "network error, try again") render once at the top and don't block individual fields from showing their own valid state.

Accessibility 
function Field({ name, label, value, error, touched, onChange, onBlur }) {
  const errorId = `${name}-error`;
  return (
    <div className="field">
      <label htmlFor={name}>{label}</label>
      <input
        id={name}
        name={name}
        value={value}
        aria-invalid={touched && !!error}
        aria-describedby={touched && error ? errorId : undefined}
        onChange={(e) => onChange(name, e.target.value)}
        onBlur={() => onBlur(name)}
      />
      {touched && error && (
        <p id={errorId} role="alert" className="field-error">
          {error}
        </p>
      )}
    </div>
  );
}

role="alert" on the error message causes screen readers to announce it immediately when it appears, without the field needing to be re-focused. aria-invalid and aria-describedby associate the error text with the input for assistive tech.

Complete Implementation 
function SignupForm() {
  const { state, handleChange, handleBlur, handleSubmit } = useForm({
    initialValues: { email: '', password: '', username: '' },
    validators: {
      email: zodFieldValidator(signupSchema, 'email'),
      password: zodFieldValidator(signupSchema, 'password'),
      username: zodFieldValidator(signupSchema, 'username'),
    },
    onSubmit: async (values) => {
      await fetch('/api/signup', { method: 'POST', body: JSON.stringify(values) });
    },
  });

  return (
    <form onSubmit={handleSubmit} noValidate>
      {state.errors.form && <p role="alert">{state.errors.form}</p>}
      <Field
        name="email"
        label="Email"
        value={state.values.email}
        error={state.errors.email}
        touched={state.touched.email}
        onChange={handleChange}
        onBlur={handleBlur}
      />
      <Field
        name="password"
        label="Password"
        value={state.values.password}
        error={state.errors.password}
        touched={state.touched.password}
        onChange={handleChange}
        onBlur={handleBlur}
      />
      <button type="submit" disabled={state.isSubmitting}>
        {state.isSubmitting ? 'Creating account…' : 'Sign up'}
      </button>
    </form>
  );
}
Edge Cases
  • Validate-on-first-blur, then live: before a field is touched, don't show errors even if the value is already invalid (avoids showing "Required" on an empty field the instant the form mounts).
  • Paste events bypass individual keystrokes — validation triggered on onChange still fires correctly since onChange fires once with the full pasted value, but debounced async checks should still debounce it rather than firing once per pasted character (which doesn't happen, but is a common wrong assumption).
  • Submitting while an async check is pending: disable submit while status === 'checking' for any field with async validation, not just while the form's own isSubmitting flag is true.
  • Browser autofill sets input values without firing React's synthetic onChange in some browsers — validate current DOM values on submit as a fallback, not only state that was populated via onChange.

Component 7: Todo List with LocalStorage

Requirements & Why useReducer

Requirements: add/toggle/delete/edit todos, filter (all/active/completed), bulk operations (clear completed, toggle all), persist across reloads, remain usable if storage is unavailable, and support drag-to-reorder.

A todo list has more state transitions than state values — "toggle this one, then re-derive the filtered view, then persist" is a sequence of related updates. useReducer makes each transition an explicit, testable, named action instead of scattered setTodos(todos.map(...)) calls repeated across handlers.

Reducer Design & usePersist Hook 
function todosReducer(state, action) {
  switch (action.type) {
    case 'ADD':
      return [...state, { id: crypto.randomUUID(), text: action.text, completed: false, createdAt: Date.now() }];
    case 'TOGGLE':
      return state.map((t) => (t.id === action.id ? { ...t, completed: !t.completed } : t));
    case 'EDIT':
      return state.map((t) => (t.id === action.id ? { ...t, text: action.text } : t));
    case 'DELETE':
      return state.filter((t) => t.id !== action.id);
    case 'TOGGLE_ALL':
      return state.map((t) => ({ ...t, completed: action.value }));
    case 'CLEAR_COMPLETED':
      return state.filter((t) => !t.completed);
    case 'REORDER':
      return action.reordered;
    case 'HYDRATE':
      return action.todos;
    default:
      return state;
  }
}

// Sync reducer state to localStorage without blocking every dispatch on I/O
function usePersistedReducer(reducer, initialState, storageKey) {
  const [state, dispatch] = useReducer(reducer, initialState, (init) => {
    try {
      const raw = localStorage.getItem(storageKey);
      return raw ? JSON.parse(raw) : init;
    } catch {
      return init; // Corrupt JSON or storage disabled — fall back silently
    }
  });

  const writeTimeout = useRef(null);
  useEffect(() => {
    clearTimeout(writeTimeout.current);
    writeTimeout.current = setTimeout(() => {
      try {
        localStorage.setItem(storageKey, JSON.stringify(state));
      } catch {
        // Storage full or disabled — the UI already reflects the change,
        // it just won't survive a reload. Surface a non-blocking warning.
      }
    }, 300); // Debounce writes during rapid interactions (e.g., toggling many items)
    return () => clearTimeout(writeTimeout.current);
  }, [state, storageKey]);

  return [state, dispatch];
}
Why debounce the write, not the state update: the UI must reflect every dispatch immediately (state updates are synchronous via the reducer), but persisting to localStorage — a synchronous, blocking API — on every single keystroke-driven edit would jank rapid interactions. Debouncing only the write, not the render, keeps both fast.
Optimistic Updates & Graceful Degradation

If todos are also synced to a server, apply the change to local state immediately (optimistic), then reconcile with the server response. On failure, roll back and surface an error — don't leave the UI in a state the server never confirmed.

async function toggleWithSync(dispatch, todo) {
  dispatch({ type: 'TOGGLE', id: todo.id }); // Optimistic — instant feedback

Graceful degradation when storage is disabled (private browsing, quota exceeded, corporate policy): detect it once at startup, keep the app fully functional in-memory for the session, and show a persistent but dismissible banner rather than silently failing every write.

Drag & Drop Reordering 
function useDragReorder(items, onReorder) {
  const dragIndex = useRef(null);

  const onDragStart = (index) => (e) => {
    dragIndex.current = index;
    e.dataTransfer.effectAllowed = 'move';
  };

  const onDragOver = (index) => (e) => {
    e.preventDefault(); // Required to allow dropping
  };

  const onDrop = (index) => (e) => {
    e.preventDefault();
    const from = dragIndex.current;
    if (from === null || from === index) return;
    const next = [...items];
    const [moved] = next.splice(from, 1);
    next.splice(index, 0, moved);
    onReorder(next);
    dragIndex.current = null;
  };

  return { onDragStart, onDragOver, onDrop };
}
Accessibility gap: native drag-and-drop is mouse/touch-only. A complete implementation adds keyboard reordering (e.g., Alt+ArrowUp/Alt+ArrowDown on a focused item) and announces the new position via an aria-live region — interviewers who ask "is this accessible?" are checking for exactly this gap.
Complete Implementation (Filtering, Search & Bulk Ops) 
function TodoApp() {
  const [todos, dispatch] = usePersistedReducer(todosReducer, [], 'todos-v1');
  const [filter, setFilter] = useState('all'); // all | active | completed
  const [query, setQuery] = useState('');

  const visible = useMemo(() => {
    return todos
      .filter((t) => (filter === 'active' ? !t.completed : filter === 'completed' ? t.completed : true))
      .filter((t) => t.text.toLowerCase().includes(query.toLowerCase()));
  }, [todos, filter, query]);

  const remaining = useMemo(() => todos.filter((t) => !t.completed).length, [todos]);

  return (
    <div>
      <input
        placeholder="Search todos…"
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        aria-label="Search todos"
      />
      <TodoInput onAdd={(text) => dispatch({ type: 'ADD', text })} />

      <ul>
        {visible.map((todo) => (
          <TodoItem key={todo.id} todo={todo} dispatch={dispatch} />
        ))}
      </ul>

      <footer>
        <span>{remaining} items left</span>
        <button onClick={() => setFilter('all')}>All</button>
        <button onClick={() => setFilter('active')}>Active</button>
        <button onClick={() => setFilter('completed')}>Completed</button>
        <button onClick={() => dispatch({ type: 'CLEAR_COMPLETED' })}>Clear completed</button>
      </footer>
    </div>
  );
}

const TodoItem = memo(function TodoItem({ todo, dispatch }) {
  return (
    <li>
      <input
        type="checkbox"
        checked={todo.completed}
        onChange={() => dispatch({ type: 'TOGGLE', id: todo.id })}
      />
      <span style={{ textDecoration: todo.completed ? 'line-through' : 'none' }}>{todo.text}</span>
      <button onClick={() => dispatch({ type: 'DELETE', id: todo.id })} aria-label={`Delete ${todo.text}`}>
        ×
      </button>
    </li>
  );
});

dispatch from useReducer is referentially stable across renders, so passing it directly to memo(TodoItem) doesn't break memoization the way passing a fresh inline callback would — this is one of the practical reasons to prefer useReducer over several useState+ inline handlers when list items are memoized.

Edge Cases
  • Empty text submission: trim and reject whitespace-only todos at the input level, not the reducer, so the reducer stays a pure trusted-input transform.
  • Multi-tab editing: listen for the storage event and dispatch a HYDRATE action so a todo added in one tab appears in others without requiring a manual refresh.
  • Very large lists (1000+ todos): the search/filter useMemo is O(n) per keystroke — fine at this scale, but pair with virtualization (Component 3, Ch. 23) once the visible list itself gets long, not the filtering logic.
  • Reordering while filtered: dragging within a filtered view must splice the reorder into the underlying unfiltered array, not the filtered one, or completed/hidden items will jump position when the filter is cleared.

Component 8: Counter with Re-Render Optimization

Requirements & Interview Extension Points

The base ask — "build a counter" — takes 30 seconds. The interview happens entirely in the extensions the interviewer layers on: "now render 500 of these in a grid," "now the parent re-renders every 16ms from a WebSocket tick — the counters shouldn't visibly lag," "now add an onCountChange callback prop." Each extension is designed to tempt a premature-optimization mistake or expose a missing one.

The Un-Optimized Baseline (Correct Starting Point)

Without optimization, every 16ms tick re-renders Dashboard, which re-creates a new onCountChange arrow function for all 500 children and re-renders every Counter even though none of their own state changed.

useCallback, React.memo & Extracting Components 
const Counter = memo(function Counter({ initial = 0, onCountChange }) {
  const [count, setCount] = useState(initial);

  const increment = useCallback(() => {
    setCount((c) => {
      const next = c + 1;
      onCountChange?.(next);
      return next;
    });
  }, [onCountChange]);

  const decrement = useCallback(() => {
    setCount((c) => {
      const next = c - 1;
      onCountChange?.(next);
      return next;
    });
  }, [onCountChange]);

  return (
    <div>
      <button onClick={decrement}>-</button>
      <span>{count}</span>
      <button onClick={increment}>+</button>
    </div>
  );
});

function Dashboard() {
  const [, forceTick] = useReducer((x) => x + 1, 0);
  useEffect(() => {
    const id = setInterval(forceTick, 16);
    return () => clearInterval(id);
  }, []);

  // Stable per-index callback so `memo` actually short-circuits
  const handlers = useRef(new Map());
  const getHandler = (i) => {
    if (!handlers.current.has(i)) {
      handlers.current.set(i, (c) => console.log(i, c));
    }
    return handlers.current.get(i);
  };

  return (
    <div>
      {Array.from({ length: 500 }).map((_, i) => (
        <Counter key={i} onCountChange={getHandler(i)} />
      ))}
    </div>
  );
}
The trap interviewers set: wrapping Counter in memo alone does nothing here if Dashboard still passes a fresh (c) => console.log(i, c) closure on every render — memo's shallow prop comparison sees a new function reference and re-renders anyway. useCallback in the child is irrelevant; the fix has to happen at the call site that creates the prop.

Follow-up: "onCountChange fires on mount — how do you prevent that?"

// Common interview follow-up: onCountChange should only fire on user interaction,
// not on the initial mount when count is set to 'initial'
const Counter = memo(function Counter({ initial = 0, onCountChange }) {
  const [count, setCount] = useState(initial);
  const isFirstRender = useRef(true);

  useEffect(() => {
    if (isFirstRender.current) {
      isFirstRender.current = false;
      return; // Skip the mount notification
    }
    onCountChange?.(count);
  }, [count, onCountChange]);

  return (
    <div role="group" aria-label="Counter">
      <button onClick={() => setCount(c => c - 1)}>-</button>
      <output aria-live="polite">{count}</output>
      <button onClick={() => setCount(c => c + 1)}>+</button>
    </div>
  );
});
useReducer vs useState & Batching

For a single independent counter, useState is simpler and equally correct — reach for useReducer only once the counter grows extra transitions (min/max clamping, step size, reset-with-history) that would otherwise scatter across multiple setCount calls with duplicated logic.

function counterReducer(state, action) {
  switch (action.type) {
    case 'increment':
      return { ...state, count: Math.min(state.count + state.step, state.max) };
    case 'decrement':
      return { ...state, count: Math.max(state.count - state.step, state.min) };
    case 'reset':
      return { ...state, count: state.initial };
    default:
      return state;
  }
}

Automatic batching (React 18+): multiple setState calls inside the same event handler, timeout, or promise callback are batched into a single re-render — this used to only happen inside React event handlers pre-18. In a counter that calls both setCount and onCountChange (which might itself trigger a parent setState) within one click, both updates commit together, not as two separate renders.

Complete Implementation 
const Counter = memo(function Counter({ step = 1, min = -Infinity, max = Infinity, initial = 0, onCountChange }) {
  const [state, dispatch] = useReducer(counterReducer, { count: initial, step, min, max, initial });

  useEffect(() => {
    onCountChange?.(state.count);
  }, [state.count, onCountChange]);

  return (
    <div role="group" aria-label="Counter">
      <button onClick={() => dispatch({ type: 'decrement' })} aria-label="Decrement">-</button>
      <output aria-live="polite">{state.count}</output>
      <button onClick={() => dispatch({ type: 'increment' })} aria-label="Increment">+</button>
      <button onClick={() => dispatch({ type: 'reset' })}>Reset</button>
    </div>
  );
});

Notice onCountChange moved to a useEffect reacting to state.count rather than being called imperatively inside the dispatch action — this keeps the reducer a pure function (no side effects inside it) and decouples "notify the parent" from "compute the next state," which interviewers specifically probe for ("should a reducer call a prop function?").

Edge Cases
  • Rapid double-clicks past max/min: the reducer's clamping (Math.min/Math.max) must happen inside the reducer, not in the click handler, so it's correct even under React 18 batching where several increments might process from a stale closure otherwise.
  • Controlled counter (value/onChange from parent): once a parent wants to own the count, the component must switch to a fully controlled pattern — this is a common "now make it controlled" follow-up, and mixing both controlled and uncontrolled modes in one component is the mistake to avoid (pick one, or explicitly support both via a documented "is value provided?" branch).
  • onCountChange in a useEffect firing on mount: if the parent doesn't expect an initial notification, guard with a ref flag to skip the first effect run, or document that mount always notifies (know which behavior you're choosing and say so).

Common LLD Mistakes

Mistakes that cost points across all five components
  • Skipping accessibility until asked: role, aria-*, and focus management are graded even when not explicitly requested — senior candidates build them in from the start.
  • Optimizing before measuring: wrapping everything in memo/useMemo/useCallback pre-emptively, then being unable to explain why a specific one is necessary.
  • Mutating state directly (todos.push(...), array[i] = x) instead of returning new references — breaks both memo comparisons and React's change detection.
  • Ignoring cleanup: forgetting to remove event listeners, clear intervals, or unlock scroll when a component unmounts mid-interaction.
  • Treating localStorage as infallible: not handling quota errors, disabled storage, or corrupt JSON on read.
  • Not asking about scale: building a 10-item solution when the interviewer's follow-up ("what if there are 10,000?") was actually the point of the question.

The Pattern: What Every Interviewer Evaluates

The five components reduce to four repeating skills
  1. State shape design before rendering: in every component above, the hardest part was deciding what state to hold and in what shape (reducer actions, context split, ref vs state) — not the JSX.
  2. Escape hatches used deliberately: portals, refs, and effects are used exactly where React's declarative model can't reach (DOM position, focus, subscriptions to browser APIs) and nowhere else.
  3. Accessibility as a first-class requirement: every component includes ARIA roles, keyboard support, and focus management without being asked.
  4. Correctness under real-world hostility: disabled storage, unmounted components, stale closures, and race conditions are handled explicitly, not assumed away.
If you internalize one thing from these two LLD chapters: an interviewer is pattern-matching your solution against "have they built this before, for real users, and hit the edge case that bit them in production?" — the fastest way to signal yes is to mention the edge case unprompted, then show the one line of code that handles it.

Trade-offs

Decisions worth stating out loud during the round
  • Portal vs in-place render for Modal: portals solve stacking/clipping correctly but complicate testing (content lives outside the component's DOM subtree) and server-rendering (no document.body during SSR).
  • CSS variables vs CSS-in-JS theming: CSS variables avoid React re-renders entirely on toggle but push more logic into the stylesheet; CSS-in-JS keeps theme logic in JS but couples every themed component to a re-render when the theme context changes.
  • Debounced persistence vs write-through: debouncing reduces I/O and jank but creates a small window where a crash/tab-close loses the last few hundred milliseconds of change; write-through is safer but slower under rapid interaction.
  • memo everywhere vs selectively: blanket memoization adds a shallow-comparison cost to every render, which can net-negative for cheap components; it pays off specifically for expensive subtrees re-rendered by an unrelated, frequently-updating parent.

import { renderHook, act } from '@testing-library/react';
import { useDebouncedValue } from './useDebouncedValue';

describe('useDebouncedValue', () => {
  beforeEach(() => jest.useFakeTimers());
  afterEach(() => jest.useRealTimers());

  it('returns initial value immediately', () => {
    const { result } = renderHook(() => useDebouncedValue('hello', 300));
    expect(result.current).toBe('hello');
  });

  it('does not update before delay expires', () => {
    const { result, rerender } = renderHook(
      ({ value }) => useDebouncedValue(value, 300),
      { initialProps: { value: 'hello' } }
    );

    rerender({ value: 'world' });
    act(() => jest.advanceTimersByTime(200)); // 200ms < 300ms delay
    expect(result.current).toBe('hello'); // Still old value
  });

  it('updates after delay expires', () => {
    const { result, rerender } = renderHook(
      ({ value }) => useDebouncedValue(value, 300),
      { initialProps: { value: 'hello' } }
    );

    rerender({ value: 'world' });
    act(() => jest.advanceTimersByTime(300));
    expect(result.current).toBe('world'); // Updated
  });

  it('resets timer on rapid changes (only last value fires)', () => {
    const { result, rerender } = renderHook(
      ({ value }) => useDebouncedValue(value, 300),
      { initialProps: { value: 'a' } }
    );

    rerender({ value: 'ab' });
    act(() => jest.advanceTimersByTime(100));
    rerender({ value: 'abc' });
    act(() => jest.advanceTimersByTime(100));
    rerender({ value: 'abcd' });
    act(() => jest.advanceTimersByTime(300));

    expect(result.current).toBe('abcd'); // Only final value
  });

  it('cleans up timer on unmount', () => {
    const { unmount } = renderHook(() => useDebouncedValue('test', 300));
    unmount();
    // No act warnings or state-update-on-unmounted errors
    expect(() => jest.runAllTimers()).not.toThrow();
  });
});

Follow-up Interview Questions

Q1: How would you make the Modal work correctly with React Server Components?

Strong answer: the Modal must be a Client Component ("use client") because it uses useState, useEffect, refs, and document access — none of which exist on the server. The trigger button and modal content can still be composed from a Server Component parent by passing the modal's children as a React node (the "server component passed as children to a client component" pattern), keeping the modal's contents server-rendered where possible while only the Modal shell itself is client-side.

Q2: The theme switcher flashes the wrong theme specifically on the very first visit (no localStorage entry yet) on a slow connection. Why, and how do you fix it?

Strong answer: on first visit there's no stored preference, so the inline script falls back to matchMedia — if that call itself is somehow delayed relative to first paint (rare, but possible if the script isn't placed early enough in <head>, e.g., after a blocking stylesheet), a flash can still occur. The fix is ensuring the inline theme script is the very first thing in <head>, before any <link rel="stylesheet">, so it runs before the browser has anything to paint.

Q3: Your form's async username-availability check occasionally shows a stale result. Walk through the race condition and the fix.

Strong answer: if the user types "ab", triggering a check, then quickly types "abc" before the first request resolves, both requests are in flight; if the "ab" response arrives after the "abc" response, it overwrites the correct, more recent result with a stale one. The fix is a monotonically increasing request ID (or an AbortController per keystroke) — only the response matching the latest issued request ID is allowed to update state, exactly as shown in the useAsyncFieldValidation hook above.

Q4: How would you test the focus trap without a real browser?

Strong answer: using React Testing Library with jsdom, render the Modal open, assert document.activeElement equals the expected initial-focus element, simulate Tab key presses via userEvent.tab() repeatedly past the last focusable element, and assert focus wraps to the first. Also assert that closing the modal restores focus to the originally-focused trigger element — this is the part most implementations get wrong and the part a good test suite catches.

Q5: The todo list needs to support 10,000 items with instant search. What changes?

Strong answer: the useMemo-based filter is still O(n) per keystroke, which is fine computationally (10k simple string comparisons is sub-millisecond), but rendering 10k <li> elements is not — pair the existing filter logic with the virtualization approach from Chapter 23's Infinite Scroll component so only visible rows mount, and debounce the search input itself so filtering doesn't run on every single keystroke during fast typing.

Q6: Why does the Counter example move the onCountChange call into a useEffect instead of calling it inside the click handler?

Strong answer: calling a prop callback inside a reducer or directly inside the state updater couples "compute next state" with "notify the outside world," which breaks if React ever batches, replays, or double-invokes the updater (as Strict Mode does in development for reducers). Moving the notification to an effect keyed on the resulting state value guarantees it fires exactly once per committed state change, regardless of how many times the updater function itself was invoked internally.

Summary

Key mental models for the interview:

  • Modal = Portal + Focus Trap + Scroll Lock. Conditional rendering alone is not a modal.
  • Theming is a CSS problem wearing a React costume. Store the preference in React; apply it via a DOM attribute and CSS variables so toggling doesn't re-render your tree.
  • Forms are reducers with fields. Model changes as named transitions (CHANGE, BLUR, SUBMIT) rather than scattered setState calls.
  • Todo lists are reducers with persistence. Debounce the write, not the render; degrade gracefully when storage fails.
  • Counters teach restraint. Start unoptimized, add memo/useCallback only once a real re-render cost is demonstrated, and remember the optimization must happen at the call site creating the prop, not just in the child.

What NOT to say in an interview:

  • ❌ "I'll just use a library for this" when the interviewer explicitly asked you to build the primitive — naming the library your production code would use is fine, using it here defeats the purpose of the round.
  • ❌ "This doesn't need accessibility, it's just a demo" — LLD rounds grade accessibility as a default expectation, not an extra.
  • ❌ "memo everywhere is always safe" — it isn't free; you should be able to justify each one.
  • ❌ "localStorage always works" — ignoring quota/availability failures is a signal of not having shipped this to real users.

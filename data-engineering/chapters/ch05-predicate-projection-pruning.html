Interviewer Intent

Why interviewers ask this question

This question separates senior engineers who understand physical execution from those who only write logical SQL. The interviewer wants to verify:

  • Cost awareness — Can you explain why a query costs $0.05 vs $50 on the same table?
  • I/O minimization instinct — Do you reflexively think about bytes scanned, not just row counts?
  • Columnar format internals — Can you explain Parquet row groups, column chunks, and page-level statistics?
  • Optimizer mechanics — Do you understand how the query planner decides to push predicates below joins or into storage?
  • Nested data expertise — BigQuery, Dremel, and Protocol Buffers are FAANG staples; can you prune nested fields?
  • Production debugging — Can you diagnose why a query isn't benefiting from pushdown using EXPLAIN plans?
  • Incident response — Have you seen real cost explosions from missing pushdowns?

At senior+ levels, the interviewer expects you to connect these optimizations to dollar cost, SLA compliance, and cluster sizing.

What a strong answer demonstrates
  • Precise definitions with physical-layer reasoning (not just "it filters early")
  • Concrete numbers: bytes scanned before/after, cost reduction percentages
  • Cross-engine knowledge: Spark, BigQuery, Snowflake, PostgreSQL, Trino
  • Awareness of when pushdown cannot happen (UDFs, complex expressions, certain joins)
  • Connection to file formats: Parquet, ORC, Delta, Iceberg metadata layers
  • Real production war stories with quantified business impact

Quick Answer (60-Second Version)

Elevator pitch

Predicate pushdown moves filter conditions (WHERE clauses) as close to the storage layer as possible — skipping entire files, row groups, or partitions before data reaches the compute engine. Projection pushdown reads only the columns referenced in the query, exploiting columnar storage formats where each column is stored independently. Nested pruning extends projection pushdown into struct/record types, reading only the specific sub-fields needed from deeply nested Protocol Buffer or JSON columns.

Together, these three optimizations routinely reduce bytes scanned by 90–99%, directly cutting cloud costs and query latency.

Predicate Pushdown

Definition & mechanism

Predicate pushdown (also called filter pushdown) is a query optimization where filter predicates (WHERE conditions) are evaluated at the storage/scan layer rather than after data reaches the compute engine. The optimizer "pushes" the predicate down through the logical plan — below joins, aggregations, and projections — until it sits directly above the table scan operator. 


-- Logical plan BEFORE predicate pushdown:
--   Project(user_id, amount)
--     Filter(region = 'us-east-1')
--       Join(orders ⋈ users)
--         Scan(orders)   ← reads ALL rows
--         Scan(users)    ← reads ALL rows

-- Logical plan AFTER predicate pushdown:
--   Project(user_id, amount)
--     Join(orders ⋈ users)
--       Filter(region = 'us-east-1')
--         Scan(orders)   ← predicate pushed to scan
--       Scan(users)

At the physical layer, pushdown manifests differently depending on the engine:

  • Parquet/ORC: min/max statistics in column chunk headers allow entire row groups to be skipped
  • BigQuery: storage API evaluates predicates server-side, returning only matching rows
  • PostgreSQL: index scans replace sequential scans when predicates match indexed columns
  • Spark: Data source V2 API passes Filter objects to the connector

PostgreSQL — predicate pushdown via index scans 

-- Without pushdown (sequential scan):
EXPLAIN ANALYZE
SELECT user_id, amount
FROM orders
WHERE region = 'us-east-1' AND created_at > '2024-01-01';

-- Seq Scan on orders  (cost=0.00..1850000.00 rows=50000000)
--   Filter: (region = 'us-east-1' AND created_at > '2024-01-01')
--   Rows Removed by Filter: 49500000
--   Execution Time: 45000 ms

-- With proper index (predicate pushed to index scan):
CREATE INDEX idx_orders_region_date ON orders(region, created_at);

EXPLAIN ANALYZE

FROM orders
WHERE region = 'us-east-1' AND created_at > '2024-01-01';

-- Index Scan using idx_orders_region_date on orders
--   Index Cond: (region = 'us-east-1' AND created_at > '2024-01-01')
--   Execution Time: 120 ms   ← 375x faster

-- Clustering by (region, created_at) sorts data blocks, enabling block skipping
When predicate pushdown CANNOT happen
  • UDFs in predicates: WHERE my_udf(col) = 'value' — opaque to optimizer
  • Implicit type casts: WHERE string_col = 123 — prevents index/stats usage
  • Non-deterministic functions: WHERE col > RANDOM()
  • Predicates on derived columns: WHERE YEAR(date_col) = 2024 vs WHERE date_col BETWEEN '2024-01-01' AND '2024-12-31'
  • After OUTER JOINs: Predicates on the nullable side can't always be pushed below the join
  • LIKE with leading wildcard: WHERE col LIKE '%suffix' — can't use sorted statistics
  • OR conditions across columns: WHERE col_a = 1 OR col_b = 2 — limits row group skipping

-- WRONG: prevents pushdown
SELECT * FROM orders WHERE YEAR(order_date) = 2024;

-- RIGHT: enables pushdown
SELECT * FROM orders
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01';

-- WRONG: UDF blocks pushdown
SELECT * FROM orders WHERE normalize_region(region) = 'US_EAST';

-- RIGHT: push raw predicate, transform after
SELECT * FROM orders WHERE region IN ('us-east-1', 'us-east-2');

Projection Pushdown

Definition & why columnar storage makes this critical

Projection pushdown ensures the storage layer reads only the columns referenced in the query's SELECT, WHERE, JOIN, and GROUP BY clauses. In row-oriented storage this saves minimal I/O (entire rows are read regardless). In columnar storage — Parquet, ORC, BigQuery Capacitor — each column is stored in separate byte ranges, so skipping unreferenced columns eliminates entire I/O operations. 


# Row-oriented storage (PostgreSQL heap, CSV)
# Reading 3 columns still reads the full row tuple
┌────────────────────────────────────────────────┐
│ Row 1: [col1|col2|col3|...|col200]  ← all 200 │
│ Row 2: [col1|col2|col3|...|col200]             │
│ ...                                            │
└────────────────────────────────────────────────┘
# Even SELECT col1, col2, col3 reads all 200 columns per row

# Columnar storage (Parquet, ORC, BigQuery)
# Each column stored independently
┌──────────┐ ┌──────────┐ ┌──────────┐     ┌──────────────┐
│ col1     │ │ col2     │ │ col3     │ ... │ col200       │
│ chunk    │ │ chunk    │ │ chunk    │     │ chunk        │
│ (5 MB)   │ │ (5 MB)   │ │ (5 MB)   │     │ (5 MB)       │
└──────────┘ └──────────┘ └──────────┘     └──────────────┘
# SELECT col1, col2, col3 reads only 15 MB out of 1000 MB
# Projection pushdown: 98.5% I/O reduction

# Columns needed: user_id (8 MB) + amount (6 MB) + region (3 MB) = 17 MB
# Columns skipped: order_date + items[] + metadata = 111 MB
# Per row group savings: 111/128 = 87% I/O eliminated
BigQuery Capacitor — projection at the storage server

BigQuery's Capacitor format stores each column (and nested sub-column) in separate column stripes. When a query references only 5 of 200 columns, the storage servers never read the other 195 columns from disk. This is why BigQuery charges by bytes scanned — projection pushdown directly reduces your bill. 


-- Table: events (200 columns, 50 TB total)
-- Columns: event_id (2%), timestamp (1%), user_id (3%), 
--          payload (STRUCT with 50 sub-fields, 60% of storage)

-- BAD: reads all 200 columns
SELECT * FROM `project.dataset.events`
WHERE DATE(timestamp) = '2024-02-15';
-- Bytes processed: 140 GB (full day partition, all columns)
-- Cost: $0.70

-- GOOD: projection pushdown
SELECT event_id, user_id, timestamp
FROM `project.dataset.events`
WHERE DATE(timestamp) = '2024-02-15';
-- Bytes processed: 8.4 GB (only 3 columns from day partition)
-- Cost: $0.042  ← 94% cost reduction
Spark — verifying projection in physical plan 

# Spark automatically applies projection pushdown to Parquet
df = spark.read.parquet("s3://warehouse/events/")

# Only these columns will be read from Parquet files
result = df.select("event_id", "user_id", "timestamp") \
           .filter(df.timestamp > "2024-02-15")

result.explain(True)
# == Physical Plan ==
# FileScan parquet [event_id,user_id,timestamp]
#       ReadSchema: struct<event_id:string,user_id:string,timestamp:timestamp>
#       PartitionFilters: []
#       PushedFilters: [GreaterThan(timestamp,2024-02-15)]
#
# Note: ReadSchema shows ONLY 3 columns — projection pushed down
# The 197 other columns are never read from S3

# Common mistake that breaks projection pushdown:
df_all = spark.read.parquet("s3://warehouse/events/")
df_all.cache()  # Caches ALL columns in memory
df_all.select("event_id", "user_id").show()  # Too late — already cached everything
SELECT * is the enemy of projection pushdown

The single most common anti-pattern in data engineering is SELECT * in production pipelines. It defeats projection pushdown entirely and causes:

  • 10–100x more bytes scanned (especially with nested columns)
  • Proportionally higher cloud costs
  • Larger shuffle sizes in distributed engines
  • OOM errors from materializing unused wide columns
  • Schema coupling — downstream breaks when upstream adds columns

-- Anti-pattern: CTEs with SELECT *
WITH base AS (
  SELECT * FROM events  -- reads ALL 200 columns
)
SELECT user_id, COUNT(*) 
FROM base 
GROUP BY user_id;
-- Even though only user_id is needed, all 200 columns are scanned

-- Fixed: explicit column list
WITH base AS (
  SELECT user_id FROM events  -- projection pushdown: reads 1 column
)
SELECT user_id, COUNT(*) 
FROM base 
GROUP BY user_id;
-- 98% fewer bytes scanned

Nested / Struct Pruning

Why nested pruning matters at FAANG scale

FAANG companies store events as deeply nested Protocol Buffers or JSON structures serialized into columnar formats. A single event_payload column might contain 50+ sub-fields, each stored as a separate leaf column in Parquet/Capacitor. Nested pruning reads only the specific sub-fields referenced in the query, skipping the rest of the nested structure. 


# Nested structure example — e-commerce event proto
# message Event {
#   string event_id = 1;
#   int64 timestamp = 2;
#   UserInfo user = 3;           ← STRUCT with 10 fields
#   DeviceInfo device = 4;       ← STRUCT with 8 fields
#   PageView page_view = 5;      ← STRUCT with 12 fields
#   Purchase purchase = 6;       ← STRUCT with 15 fields (items[], payment, shipping)
#   repeated Experiment experiments = 7;  ← ARRAY of STRUCTs
# }
#
# Total leaf columns when flattened: 60+
# Storage per day: 500 GB
#   - event_id + timestamp: 10 GB (2%)
#   - user.*: 50 GB (10%)
#   - device.*: 40 GB (8%)
#   - page_view.*: 80 GB (16%)
#   - purchase.*: 200 GB (40%)
#   - experiments[]: 120 GB (24%)
Nested pruning visualization 

# Query: SELECT event_id, user.country, purchase.total_amount
#         FROM events WHERE user.country = 'US'

# WITHOUT nested pruning — reads entire structs:
┌─────────────────────────────────────────────────────────────┐
│  Read: event_id (5 GB)                                      │
│  Read: user.* (ALL 10 sub-fields = 50 GB) ← WASTEFUL       │

│  Total I/O: 18 GB                                           │
└─────────────────────────────────────────────────────────────┘

# Reduction: 255 GB → 18 GB = 93% less I/O
# At $5/TB: $1.27 → $0.09 per query
BigQuery nested column storage (Dremel encoding)

BigQuery uses Dremel encoding (repetition + definition levels) to store nested and repeated fields. Each leaf field in a nested structure is stored as an independent column stripe with its own repetition/definition level vectors. 


-- BigQuery table with nested STRUCT
CREATE TABLE `project.dataset.events` (
  event_id STRING,
  timestamp TIMESTAMP,
  user STRUCT<
    user_id STRING,
    country STRING,
    device_type STRING,
    session_id STRING,
    experiments ARRAY<STRUCT<
      experiment_id STRING,
      variant STRING,
      enrolled_at TIMESTAMP
    >>
  >,
  purchase STRUCT<
    order_id STRING,
    total_amount NUMERIC,
    currency STRING,
    items ARRAY<STRUCT<
      sku STRING,
      quantity INT64,
      price NUMERIC,
      category STRING
    >>,
    payment STRUCT<
      method STRING,
      card_last4 STRING,
      processor_response STRING
    >>
  >
);

-- Nested pruning in action:
SELECT
  event_id,
  user.country,
  purchase.total_amount
FROM `project.dataset.events`
WHERE user.country = 'US'
  AND DATE(timestamp) = '2024-02-15';

-- BigQuery reads ONLY these leaf columns from Capacitor:
--   event_id, user.country, purchase.total_amount, timestamp
-- All other nested sub-fields (user.device_type, purchase.items[], 
-- purchase.payment.*, user.experiments[]) are NOT read.
-- Bytes processed: 18 GB vs 255 GB without pruning
Parquet nested types (repetition & definition levels) 

# Parquet stores nested fields using Dremel-style encoding
# Each leaf column gets:
#   - Values (the actual data)
#   - Definition levels (how many optional fields are defined)
#   - Repetition levels (which repeated field level is repeating)

# Schema:
# message Event {
#   required binary event_id;
#   optional group user {
#     optional binary country;
#     optional binary device_type;
#     repeated group experiments {
#       optional binary experiment_id;
#       optional binary variant;
#     }
#   }
# }

# Physical column layout in Parquet:
# event_id                        → column chunk at offset 0
# user.country                    → column chunk at offset X
# user.device_type                → column chunk at offset Y
# user.experiments.experiment_id  → column chunk at offset Z
# user.experiments.variant        → column chunk at offset W

# Reads: event_id chunk + user.country chunk
# Skips: user.device_type + user.experiments.* chunks
Protocol Buffers & nested pruning

At Google/Meta/Netflix, event data is often stored as serialized Protocol Buffers in columnar storage. The proto schema defines the nested structure; the storage layer (Capacitor, Parquet) decomposes it into leaf columns. 


# PySpark reading nested Parquet with struct pruning

# Schema (from Proto):
# root
#  |-- event_id: string
#  |-- user: struct
#  |    |-- user_id: string
#  |    |-- country: string
#  |    |-- preferences: struct
#  |         |-- language: string
#  |         |-- currency: string
#  |         |-- notifications: array
#  |              |-- element: struct
#  |                   |-- channel: string
#  |                   |-- enabled: boolean
#  |-- purchase: struct
#       |-- total: decimal
#       |-- items: array
#            |-- element: struct
#                 |-- sku: string
#                 |-- qty: integer
#                 |-- price: decimal

# GOOD: nested pruning — only reads user.country leaf column
df = spark.read.parquet("s3://data-lake/events/")
result = df.select(
    "event_id",
    "user.country",          # Reads only user.country chunk
    "purchase.total"         # Reads only purchase.total chunk
).filter(col("user.country") == "US")

result.explain(True)
# ReadSchema: struct<event_id:string,
#   user:struct<country:string>,
#   purchase:struct<total:decimal(10,2)>>
# Note: Only referenced nested fields appear in ReadSchema

# BAD: reads entire struct
result_bad = df.select(
    "event_id",
    "user",          # Reads ALL of user.* (10 sub-fields)
    "purchase"       # Reads ALL of purchase.* (15 sub-fields)
)
# ReadSchema includes all nested fields — no pruning
Spark nested pruning configuration 

# Spark 3.x nested pruning settings
spark.conf.set("spark.sql.optimizer.nestedSchemaPruning.enabled", "true")  # default: true
spark.conf.set("spark.sql.optimizer.nestedPredicatePushdown.enabled", "true")  # Spark 3.3+

# Verify nested pruning is working:
df = spark.read.parquet("s3://data-lake/events/")
pruned = df.select("event_id", "user.country", "purchase.total")

# Check the scan node's ReadSchema
pruned.explain(True)
# Expected: ReadSchema shows ONLY the referenced leaf fields
# If you see the full struct, nested pruning is disabled or blocked

# 1. Using map-type columns (not struct) — maps can't be pruned
# 2. UDFs that take the entire struct as input
# 3. Older Spark versions (< 2.4) lack nested pruning
# 4. Certain data source connectors don't support it

│  │      ]                                                        │  │
│  │    }, ...                                                     │  │
│  │  ]                                                            │  │

# Reading strategy:
# 1. Read footer (last bytes) → get schema + row group metadata
# 2. Use column stats to skip row groups (predicate pushdown)
# 3. Seek to only needed column chunk offsets (projection pushdown)
# 4. Within column chunks, use page-level stats for fine-grained skipping

Key Parquet features for pushdown:

  • Dictionary encoding: Low-cardinality columns (region, status) get dictionary-encoded, enabling fast predicate evaluation on dictionary indices
  • Page-level column index (Parquet 2.0): Fine-grained min/max per page allows skipping within a column chunk
  • Bloom filters (Parquet 1.12+): Probabilistic filter for high-cardinality equality predicates
  • Sorted row groups: If data is sorted by a column, min/max ranges don't overlap → maximum skip rate

BigQuery Capacitor — nested columnar with Dremel encoding

Capacitor is Google's proprietary columnar format used by BigQuery. It extends the Dremel paper's concepts with additional optimizations:

  • Nested columnar: Each leaf field (even deeply nested) is a separate column stripe

Runtime Filters / Dynamic Pruning

What are runtime filters?

Runtime filters (also called dynamic partition pruning or dynamic filtering) are predicates generated during query execution based on the results of one side of a join. Unlike static predicate pushdown (known at planning time), runtime filters are discovered at execution time and propagated back to the scan operators. 


# Static vs Dynamic Predicate Pushdown
#
# STATIC (compile-time):
#   Query: SELECT * FROM orders WHERE region = 'us-east-1'
#   Optimizer knows 'us-east-1' at plan time → pushes to scan
#
# DYNAMIC (runtime):
#   Query: SELECT * FROM orders o
#          JOIN regions r ON o.region_id = r.id
#          WHERE r.name = 'US East'
#
#   At plan time: optimizer doesn't know which region_ids match 'US East'
#   At runtime:
#     1. Scan regions WHERE name='US East' → finds id=42
#     2. Build runtime filter: orders.region_id IN (42)
#     3. Push filter back to orders scan → skip partitions/row-groups
#
# ┌──────────────────────────────────────────────────────────────┐
# │  Without runtime filter:                                      │
# │    Scan orders (ALL partitions) ─┐                           │
# │                                   ├─ Hash Join ─→ result     │
# │    Scan regions (filtered) ──────┘                           │
# │    Shuffle: 500 GB                                           │
# ├──────────────────────────────────────────────────────────────┤
# │  With runtime filter:                                         │
# │    Scan regions (filtered) → build filter {id=42}            │
# │         │                                                     │
# │         ↓ propagate filter                                   │
# │    Scan orders (region_id=42 only) ─┐                        │
# │                                      ├─ Hash Join ─→ result  │
# │    Scan regions (filtered) ─────────┘                        │
# │    Shuffle: 5 GB  (100x reduction)                           │
# └──────────────────────────────────────────────────────────────┘

Semi-join reduction

Semi-join reduction is a generalization of runtime filters. The optimizer converts certain join patterns into semi-joins that produce a filter set, then pushes that filter to the opposite side of the join. 


-- Semi-join reduction example
-- Original query:
SELECT o.order_id, o.amount
FROM orders o
WHERE o.customer_id IN (
  SELECT c.customer_id
  FROM customers c
  WHERE c.segment = 'enterprise'
);

-- Optimizer rewrites as:
-- 1. Scan customers WHERE segment='enterprise' → collect customer_ids
-- 2. Build bloom filter / hash set from customer_ids
-- 3. Push bloom filter to orders scan
-- 4. Scan orders, applying bloom filter at storage layer

-- Trino/Presto dynamic filtering:
-- SET SESSION enable_dynamic_filtering = true;
-- Trino builds a bloom filter from the build side of a join
-- and pushes it to the probe side's table scan connector


# Spark semi-join reduction with broadcast
from pyspark.sql.functions import broadcast

# Small dimension table (enterprise customers)
enterprise_customers = spark.sql("""
  SELECT customer_id FROM customers WHERE segment = 'enterprise'
""")

# Large fact table
orders = spark.read.parquet("s3://warehouse/orders/")

# Spark applies runtime filter when broadcasting the small side
result = orders.join(
    broadcast(enterprise_customers),
    "customer_id"
).select("order_id", "amount", "customer_id")

# BroadcastHashJoin [customer_id]

Common Mistakes

Mistake 1: SELECT * in production pipelines

The #1 cost-inflating pattern. Even when using CTEs or views that later select specific columns, most engines evaluate the innermost scan first. If that scan is SELECT *, all columns are read from storage. 


-- BAD: CTE with SELECT * defeats projection pushdown
WITH raw AS (
  SELECT * FROM events WHERE date = '2024-02-15'
)
SELECT event_id, user_id FROM raw;
-- BigQuery still reads ALL columns in the CTE scan

-- GOOD: explicit columns from the start
WITH raw AS (
  SELECT event_id, user_id FROM events WHERE date = '2024-02-15'
)
SELECT event_id, user_id FROM raw;
-- Only 2 columns read from storage
Mistake 2: Functions on partition/filter columns 

-- BAD: function on partition column prevents partition pruning
SELECT * FROM events
WHERE YEAR(event_date) = 2024 AND MONTH(event_date) = 2;
-- BigQuery/Spark cannot prune partitions — scans ALL partitions

-- GOOD: direct comparison on partition column
SELECT * FROM events
WHERE event_date BETWEEN '2024-02-01' AND '2024-02-28';
-- Partition pruning works: reads only 28 partitions

-- BAD: CAST prevents predicate pushdown to Parquet stats
SELECT * FROM orders WHERE CAST(amount AS STRING) = '100.00';
-- Cannot use min/max statistics on numeric column

-- GOOD: compare in native type
SELECT * FROM orders WHERE amount = 100.00;
-- Row group skipping via min/max statistics works
Mistake 3: Reading entire struct when only one field is needed 

# BAD: selecting the entire struct column breaks nested pruning
df = spark.read.parquet("s3://data-lake/events/")
result = df.select("event_id", "user")  # reads ALL user.* sub-fields
user_country = result.select("event_id", "user.country")

# GOOD: select leaf field directly for nested pruning
df = spark.read.parquet("s3://data-lake/events/")
result = df.select("event_id", "user.country")  # reads ONLY user.country
# 90% less I/O if user struct has 10 fields
Mistake 4: Caching before filtering 

# BAD: cache entire dataset, then filter (negates all pushdown)
df = spark.read.parquet("s3://warehouse/events/")
df.cache()  # reads and caches ALL columns, ALL rows
result = df.filter(col("region") == "us-east-1").select("user_id")
# Already read 10 TB into memory — filter is too late

# GOOD: filter and project BEFORE caching
df = spark.read.parquet("s3://warehouse/events/")
filtered = df.filter(col("region") == "us-east-1").select("user_id")
filtered.cache()  # caches only 50 MB (filtered + projected)
Mistake 5: Implicit type coercion breaking pushdown 

-- BAD: string compared to integer — implicit cast
SELECT * FROM orders WHERE order_id = 12345;
-- If order_id is STRING, this forces CAST(order_id AS INT) on every row
-- Bloom filters and min/max stats cannot be used

-- GOOD: match types exactly
SELECT * FROM orders WHERE order_id = '12345';
-- String comparison uses dictionary encoding and bloom filters

-- BAD: timestamp precision mismatch
SELECT * FROM events WHERE event_time = '2024-02-15';
-- TIMESTAMP column compared to DATE string — may not use partition pruning

-- GOOD: explicit type matching
SELECT * FROM events WHERE DATE(event_time) = DATE '2024-02-15';
-- Or use the partition column directly:
SELECT * FROM events WHERE event_date = '2024-02-15';
Mistake 6: OR conditions that prevent row group elimination 

-- BAD: OR across different columns limits skip potential
SELECT * FROM orders
WHERE region = 'us-east-1' OR amount > 10000;
-- A row group with region=['eu-west'] but amount=[500..50000]
-- CANNOT be skipped (amount range includes > 10000)
-- Result: most row groups must be read

-- BETTER: UNION ALL if possible (separate pushdowns per branch)
SELECT * FROM orders WHERE region = 'us-east-1'
UNION ALL
SELECT * FROM orders WHERE amount > 10000 AND region != 'us-east-1';
-- Each branch gets independent predicate pushdown

-- BEST: redesign query to avoid cross-column OR
-- Often the OR indicates a need for separate queries or views
Mistake 7: Ignoring data sorting/clustering 

# Predicate pushdown with min/max statistics ONLY works well
# when data is sorted by the filter column.

# UNSORTED data — poor row group skipping:
# Row Group 0: region = [ap-south, us-west]   ← wide range, can't skip
# Row Group 1: region = [eu-central, us-east] ← wide range, can't skip
# Row Group 2: region = [ap-east, us-west]    ← wide range, can't skip
# Query: WHERE region = 'us-east-1'
# Result: must read ALL row groups (ranges overlap)

# SORTED data — excellent row group skipping:
# Row Group 0: region = [ap-east, ap-south]   ← skip (max < us-east-1)
# Row Group 1: region = [eu-central, eu-west] ← skip (max < us-east-1)
# Row Group 2: region = [us-east-1, us-east-2] ← READ (contains target)
# Row Group 3: region = [us-west-1, us-west-2] ← skip (min > us-east-1)
# Query: WHERE region = 'us-east-1'
# Result: read 1 of 4 row groups (75% skip rate)

# FIX: sort data on write by common filter columns
# Spark:
df.sort("region", "event_date").write.parquet("s3://output/")
# Delta Lake:
# OPTIMIZE table ZORDER BY (region, event_date)
# BigQuery:
# CREATE TABLE ... CLUSTER BY region, event_date

Trade-offs

Sorting for predicate pushdown vs write amplification
  • Pro: Sorted data maximizes row-group skipping (non-overlapping min/max ranges)
  • Con: Global sorting requires full shuffle on write (expensive for streaming)
  • Con: Z-ORDER / clustering requires periodic OPTIMIZE jobs (write amplification)
  • Trade-off: Sort by most-queried column first; accept suboptimal skipping for secondary columns
  • Mitigation: Use Iceberg's sort-on-write + automatic compaction for incremental sorting
Small row groups vs large row groups
  • Small row groups (16-32 MB): More granular statistics, better skip rates, but more metadata overhead and less compression efficiency
  • Large row groups (128-256 MB): Better compression, less metadata, but coarser predicate evaluation (skip or read large chunks)
  • Default: 128 MB is the sweet spot for most workloads
  • Exception: Point-lookup workloads benefit from smaller row groups (8-32 MB)
Nested columns vs flattened schema
  • Nested (Proto/STRUCT): Natural schema evolution, single table, nested pruning reduces I/O — but SELECT * is catastrophic
  • Flattened: Simpler queries, obvious column projection, no nested pruning needed — but 200-column tables are unwieldy, schema changes require migrations
  • Hybrid: Top-level columns for frequently queried fields + nested STRUCT for rarely-accessed payload (best of both worlds)
Partition granularity: too few vs too many partitions
  • Too few partitions (yearly): Large partition sizes reduce pruning effectiveness; still reading months of data for daily queries
  • Too many partitions (per-minute): "Small files problem" — millions of tiny files, slow planning, poor compression, metadata overhead
  • Sweet spot: Daily partitions for event data (100 MB - 10 GB per partition file)
  • Rule of thumb: Each partition should contain at least 100 MB of data after compression

# Partition sizing guide:
# ┌───────────────────────────────────────────────────────────────┐
# │  Data Volume/Day  │  Partition By    │  Expected File Size    │
# ├───────────────────┼──────────────────┼────────────────────────┤
# │  < 100 MB         │  monthly/weekly  │  ~500 MB - 2 GB        │
# │  100 MB - 10 GB   │  daily           │  ~100 MB - 10 GB       │
# │  10 GB - 1 TB     │  daily + cluster │  ~128 MB row groups    │
# │  > 1 TB           │  hourly + cluster│  ~128 MB row groups    │
# └───────────────────┴──────────────────┴────────────────────────┘
Bloom filters: memory cost vs skip rate
  • Pro: Enable equality predicate pushdown on high-cardinality columns (user_id, session_id) where min/max stats are useless
  • Con: Adds storage overhead (1-5% per column), loaded into memory during scans
  • Con: Only useful for equality predicates, not range queries
  • When to use: High-cardinality columns frequently filtered with = or IN
  • When to skip: Range predicates, low-cardinality (min/max stats suffice), rarely-filtered columns
Materialized views vs pushdown optimization
  • Materialized views: Pre-compute common queries, fastest reads, but storage cost + staleness + maintenance overhead
  • Pushdown optimization: No extra storage, always fresh, but limited by data layout and query patterns
  • Decision framework: If pushdown brings scan under 1 GB, pushdown wins. If queries repeatedly scan 100+ GB despite pushdown, consider MVs or summary tables.

Follow-up Questions

Q1: How does predicate pushdown interact with JOIN ordering?

The optimizer must decide whether to push a predicate below a join. For INNER JOINs, predicates on either table can be pushed below freely. For LEFT OUTER JOINs, predicates on the preserved (left) table can be pushed below the join, but predicates on the nullable (right) table cannot — they would change the join semantics from "keep unmatched lefts with NULLs" to "only keep matching lefts." 


-- LEFT JOIN: predicate on right table CANNOT be pushed below join
SELECT o.*, c.name
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.id
WHERE c.country = 'US';  -- This converts LEFT JOIN to INNER JOIN!

-- To preserve LEFT JOIN semantics, move predicate to ON clause:
SELECT o.*, c.name
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.id AND c.country = 'US';
-- Now unmatched orders get NULL customer fields (LEFT JOIN preserved)
Q2: Can you push predicates through UNION ALL / window functions?

UNION ALL: Predicates can be pushed through if the predicate column exists in all branches with compatible types. Most optimizers do this automatically.

Window functions: Predicates CANNOT be pushed below a window function because the window needs all rows in its frame to compute correctly. However, predicates on partition keys that are also window PARTITION BY columns can sometimes be pushed. 


-- Predicate pushdown through UNION ALL (works):
SELECT * FROM (
  SELECT id, region, amount FROM orders_2023
  UNION ALL
  SELECT id, region, amount FROM orders_2024
) WHERE region = 'us-east-1';
-- Optimizer pushes region='us-east-1' to BOTH branches

-- Predicate BLOCKED by window function:
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts) AS rn
  FROM events
) WHERE rn = 1 AND region = 'us-east-1';
-- rn=1 CANNOT be pushed (window needs all rows)
-- region='us-east-1' CAN be pushed in some optimizers (same partition key)
Q3: How do you handle predicate pushdown with late-arriving data?

Late-arriving data (events with old timestamps arriving after their partition was written) creates a tension: new data goes to old partitions, requiring either:

  • Append to existing partitions: Maintains pushdown but may create small files
  • Dual partitioning: Partition by both event_time and processing_time; queries on event_time still prune correctly
  • Compaction jobs: Periodically merge small files in old partitions to restore optimal row-group sizes
  • Iceberg approach: Append to snapshot, metadata tracks which files contain which time ranges; planning still prunes correctly via manifest stats
Q4: What's the difference between predicate pushdown and data skipping?

Predicate pushdown: The query optimizer pushes filter expressions to the scan operator, which evaluates them during I/O. Broad term covering all push-to-storage patterns.

Data skipping: A specific implementation technique where min/max statistics (or bloom filters) at the file/row-group/page level allow entire data units to be skipped without reading their contents. Data skipping is one mechanism through which predicate pushdown achieves I/O reduction.

Other pushdown mechanisms include: index scans (PostgreSQL), partition elimination (directory-based), storage-server-side filtering (BigQuery), and connector-level filtering (Spark Data Source V2).

Q5: How does encryption interact with pushdown?

Column-level encryption (Parquet modular encryption, BigQuery column-level security):

  • Statistics in column headers may be encrypted → cannot evaluate predicates without decryption key
  • Parquet modular encryption supports encrypting data while keeping statistics in plaintext (configurable)
  • If stats are encrypted: predicate pushdown still works if the reader has the column key
  • If entire column is encrypted and reader lacks the key: column is skipped (treated as non-existent) — projection pushdown naturally excludes it
  • BigQuery column-level security: authorized users get pushdown; unauthorized users get permission errors
Q6: Compare pushdown effectiveness: Parquet vs ORC vs Avro
  • Parquet: Excellent predicate pushdown (row-group stats + page-level column index), excellent projection pushdown (columnar), good nested pruning (Dremel encoding)
  • ORC: Excellent predicate pushdown (3-level stats + built-in bloom filters), excellent projection pushdown (columnar), decent nested pruning (struct support)
  • Avro: NO predicate pushdown (row-oriented, no column stats), NO projection pushdown (must deserialize full row), NO nested pruning — avoid for analytical workloads
  • Summary: Avro for streaming/message passing; Parquet/ORC for analytical storage. Parquet dominates in the cloud ecosystem (BigQuery, Snowflake, Databricks)

Summary

Key takeaways
  • Predicate pushdown moves WHERE filters to the storage layer, skipping files/row-groups/pages via min/max statistics. Enables 40-99% I/O reduction on sorted data.
  • Projection pushdown reads only referenced columns from columnar storage. Eliminates 80-99% of bytes on wide tables (100+ columns).
  • Nested pruning extends projection to struct sub-fields. Critical for Proto/JSON-heavy FAANG tables where payload columns dominate storage.
  • Partition pruning eliminates entire directory trees before any file I/O. The coarsest and most effective optimization layer (90-99% reduction).
  • Runtime filters generate pushdown predicates at execution time from join results. Bridges the gap between static optimization and dynamic data properties.
  • Combined effect: These optimizations compound multiplicatively. A query touching 50 TB can be reduced to 100 MB (99.9998% reduction) with proper table design and query patterns.
  • Cost impact: In pay-per-scan systems (BigQuery on-demand), pushdown directly equals dollar savings. A single SELECT * on a nested table can cost 100x more than an optimized query.
  • Debugging: Always verify pushdown via EXPLAIN plans (Spark PushedFilters/ReadSchema, PostgreSQL Index Cond, BigQuery bytes_processed, Trino dynamicFilter).

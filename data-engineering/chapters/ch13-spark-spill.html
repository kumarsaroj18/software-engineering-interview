Why Are Spark Jobs Spilling to Disk?

Diagnose and resolve memory pressure that forces Spark to serialize intermediate data to local disk.

Shuffle Memory

Interviewer Intent

When an interviewer asks "Why are Spark jobs spilling to disk?", they are probing for:

  • Memory architecture fluency — Can you articulate Spark's unified memory model, the split between execution and storage memory, and how spark.memory.fraction governs the available heap?
  • Root-cause analysis — Do you understand the multiple causes of spill: data skew, insufficient parallelism, excessive broadcast thresholds, large aggregation state, or misconfigured executor memory?
  • Shuffle internals — Can you explain sort-based shuffle, ExternalAppendOnlyMap, ExternalSorter, and the conditions that trigger a spill to disk?
  • Performance impact awareness — Do you recognize that spill is not binary failure but a graduated degradation, and can you quantify its I/O cost (serialization + disk write + re-read + deserialization)?
  • Data skew handling — Have you dealt with real-world skew scenarios where one partition is 100x larger than peers, and can you discuss salting, AQE skew join, and custom partitioners?
  • Debugging methodology — Can you navigate Spark UI task metrics to identify which stages spill, correlate Spill (Memory) vs Spill (Disk), and trace back to the causal operator?
  • Production judgment — Can you weigh trade-offs between adding memory, increasing parallelism, enabling AQE, or redesigning the pipeline — and choose appropriately given cost and SLA constraints?

This question separates candidates who merely configure Spark from those who can diagnose cascading memory pressure in production systems processing terabytes daily.

Quick Answer (60-Second Version)

Spark spills to disk when a task's in-memory data structures — sort buffers, hash maps for aggregations, or shuffle buffers — exceed the execution memory available to that task. Spark's unified memory manager divides the JVM heap (after subtracting 300 MB reserved) into a unified region (default 60% via spark.memory.fraction) shared between execution memory (shuffles, joins, sorts) and storage memory (cached RDDs/DataFrames). When execution memory is exhausted — typically because of data skew causing one partition to be 100x larger than peers, too few shuffle partitions concentrating data, or large aggregation state — Spark's ExternalAppendOnlyMap or ExternalSorter serializes in-memory records to local disk files, then reads them back during the merge phase.

The performance impact is severe: spill introduces serialization overhead, disk I/O (often on the same drives serving shuffle data), and deserialization on re-read — typically degrading task runtime by 3–10x. The fix depends on root cause: increase spark.sql.shuffle.partitions to reduce per-task data volume, enable AQE to dynamically handle skew, salt skewed keys, increase executor memory, or fix the upstream data distribution.

Spark Memory Model

Unified Memory Management (Since Spark 1.6)

Before Spark 1.6, execution and storage memory were statically partitioned — if execution memory was full but storage was empty, Spark would still spill. The unified memory manager introduced dynamic sharing between these two pools, significantly reducing unnecessary spills.

spark.memory.storageFraction 0.5 Initial boundary within unified memory for storage; execution can borrow from storage but storage cannot evict execution

Execution vs Storage: The Eviction Asymmetry

The critical insight for understanding spill is the eviction asymmetry:

  • Execution can evict storage — If execution memory needs space and storage is using memory beyond its initial fraction, execution can forcibly evict cached blocks (they get dropped or written to disk).
  • Storage cannot evict execution — Once execution memory is occupied (by active shuffle/sort buffers), storage requests must wait or fail. This ensures in-progress computations are never interrupted.
  • Spill happens when execution cannot grow further — Even after evicting all available storage memory, if execution still doesn't have enough room, the operator spills to disk.

Practical Memory Calculation

# Example: spark.executor.memory = 8g
heap = 8 * 1024  # 8192 MB
reserved = 300   # MB
usable = heap - reserved  # 7892 MB

unified_memory = usable * 0.6  # 4735 MB (spark.memory.fraction)
user_memory = usable * 0.4     # 3157 MB

# Within unified memory:
storage_initial = unified_memory * 0.5  # 2368 MB
execution_initial = unified_memory * 0.5  # 2368 MB

# But execution can grow up to full unified_memory (4735 MB)
# by evicting cached data from storage
# Per-task execution memory (with 4 cores):
per_task_execution = execution_initial / 4  # ~592 MB per task initially

Off-Heap Memory

Off-heap memory bypasses JVM garbage collection entirely, providing predictable allocation without GC pauses:

  • Managed via sun.misc.Unsafe or Platform-specific allocators
  • Used by Project Tungsten for binary row format storage
  • Not subject to GC pressure — critical for large aggregations
  • Requires explicit memory management (risk of leaks if misconfigured)
  • Configured separately: spark.memory.offHeap.size adds to the unified pool
# Enabling off-heap memory
spark.conf.set("spark.memory.offHeap.enabled", "true")
spark.conf.set("spark.memory.offHeap.size", "4g")
# Total unified memory = on-heap unified + off-heap
# = (heap - 300MB) * 0.6 + 4GB

Shuffle Spill

Sort-Based Shuffle (Default Since Spark 1.2)

Spark's default shuffle implementation is sort-based shuffle (replacing the earlier hash-based shuffle). During a shuffle write, each map task:

  1. Inserts records into an in-memory buffer (PartitionedAppendOnlyMap or PartitionedPairBuffer)
  2. When the buffer reaches a threshold, sorts records by (partitionId, key)
  3. Writes sorted records to a single shuffle file with an index file tracking partition boundaries
  4. If memory pressure occurs during step 1, spills intermediate sorted runs to disk
  5. Final output merges all spill files into one sorted shuffle output file

ExternalAppendOnlyMap — The Spill Mechanism

For aggregation operations (reduceByKey, groupByKey, aggregateByKey), Spark uses ExternalAppendOnlyMap:

Spill Triggers — When Does It Happen?

A spill is triggered when all of the following conditions align:

  • Memory threshold exceeded — The current in-memory collection surpasses its allocated memory grant from the TaskMemoryManager
  • Memory acquisition fails — The TaskMemoryManager cannot grant more memory because:
    • The execution pool is full (all unified memory consumed by execution)
    • Other tasks on the same executor hold memory they cannot release
    • Storage memory has already been fully evicted
  • Spill-to-disk policy — Rather than OOM, Spark gracefully spills sorted data to local disk

Disk I/O Impact

The performance cost of spilling is substantial and compounds:

Operation Typical Cost Notes
Serialization (spill write) CPU-bound, ~200 MB/s Kryo faster than Java serialization
Disk write 100–500 MB/s (SSD) Competes with shuffle write I/O
Disk read (merge phase) 100–500 MB/s (SSD) Multiple spill files read simultaneously
Deserialization (merge read) CPU-bound, ~200 MB/s Object recreation adds GC pressure
Merge-sort across spills O(N log K) comparisons K = number of spill files

Rule of thumb: A task that spills runs 3–10x slower than one that fits in memory. Multiple spills compound: if a task spills 5 times, it re-reads data 5 times during the final merge.

Spill (Memory) vs Spill (Disk) in Spark UI

  • Spill (Memory) — The total size of deserialized data that was spilled across all spill events. This is the in-memory size before serialization.
  • Spill (Disk) — The total bytes actually written to disk. Always smaller than Spill (Memory) due to serialization + compression.
  • Ratio — A typical ratio is 3:1 to 5:1 (Memory:Disk), depending on data compressibility and serializer efficiency.

Per-Task Memory Accounting

Execution memory is shared among all active tasks on an executor. With spark.executor.cores = N tasks running concurrently:

  • Fair share per task: execution_memory / N (initial grant)
  • Maximum per task: execution_memory / 1 (if only one task is active)
  • Minimum per task: execution_memory / (2 × N) (hard floor to prevent starvation)

This means: with 5 cores and 4 GB execution memory, each task gets between 400 MB and 4 GB depending on concurrent load. A burst of wide-row data on one task while others are idle may not spill — but the same data with all 5 tasks active will.

Common Sizing Mistakes

Mistake Symptom Fix
executor.memory too large (>32 GB) Long GC pauses, reduced throughput Cap at 20–28 GB; use more executors instead
Too many cores per executor (>5) Per-task memory too low, frequent spill Use 4–5 cores per executor for optimal balance

Data Skew

The Problem: One Partition 100x Larger

Data skew is the single most common cause of Spark spill in production. It occurs when the distribution of keys used in shuffle operations (joins, groupBy, window functions) is highly non-uniform:

Common Skew Causes in Production

  • NULL or default values — Joining on a column with millions of NULLs routes all NULLs to one partition
  • Power-law distributions — Top merchants account for 80% of transactions; joining on merchant_id creates massive skew
  • Date-based hot partitions — Current day's data is 100x larger than historical days in incremental processing
  • Synthetic IDs — "unknown", "other", or catch-all categories aggregating millions of records
  • Upstream schema changes — New partner adding millions of records with same partner_id

Key Salting

Salting splits a hot key into N sub-keys, distributing its data across N partitions:

from pyspark.sql import functions as F

# Before: partner_id = "MEGA_PARTNER" has 500M rows
# After salting: spread across 100 partitions

salt_range = 100

# Salt the skewed (large) table
large_df = large_df.withColumn(
    "salt", (F.rand() * salt_range).cast("int")
).withColumn(
    "salted_key", F.concat(F.col("partner_id"), F.lit("_"), F.col("salt"))
)

# Explode the small (dimension) table to match all salts
small_df = small_df.crossJoin(
    spark.range(salt_range).withColumnRenamed("id", "salt")
).withColumn(
    "salted_key", F.concat(F.col("partner_id"), F.lit("_"), F.col("salt"))
)

# Join on salted key — now spread across 100 partitions
result = large_df.join(small_df, on="salted_key", how="inner")

# Drop helper columns
result = result.drop("salt", "salted_key")

AQE Skew Handling (Spark 3.0+)

Adaptive Query Execution automatically detects and handles skew at runtime:

  • Detection: After shuffle write completes, AQE examines partition sizes from map output statistics
  • Threshold: A partition is skewed if its size > spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes (default 256 MB) AND > spark.sql.adaptive.skewJoin.skewedPartitionFactor × median partition size (default 5x)
  • Action: Splits the skewed partition into sub-partitions and duplicates the matching partition from the other side of the join
# AQE Skew Join Configuration
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256m")
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "128m")

Custom Partitioner

For RDD-based pipelines or when AQE is insufficient, a custom partitioner can distribute known hot keys:

from pyspark import Partitioner

class SkewAwarePartitioner(Partitioner):
    """Routes hot keys to dedicated partitions, distributes others normally."""

    def __init__(self, num_partitions, hot_keys):
        self._num_partitions = num_partitions
        self._hot_keys = hot_keys
        # Reserve first N partitions for hot keys (spread each across multiple)
        self._hot_spread = 10  # each hot key gets 10 partitions
        self._reserved = len(hot_keys) * self._hot_spread
        self._normal_partitions = num_partitions - self._reserved

    @property
    def numPartitions(self):
        return self._num_partitions

    def getPartition(self, key):
        if key in self._hot_keys:
            idx = self._hot_keys.index(key)
            base = idx * self._hot_spread
            return base + (hash(str(key) + str(id(key))) % self._hot_spread)
        else:
            return self._reserved + (hash(key) % self._normal_partitions)

# Usage:
hot_keys = ["MEGA_PARTNER", "NULL_BUCKET", "UNKNOWN"]
rdd = rdd.partitionBy(500, SkewAwarePartitioner(500, hot_keys))

GC Pressure & Object Overhead

JVM Object Headers — The Hidden Memory Tax

Java objects carry substantial overhead that inflates in-memory data size far beyond the raw data:

Data Raw Size JVM Object Size Overhead Factor
int (primitive) 4 bytes 4 bytes 1x
Integer (boxed) 4 bytes 16 bytes 4x
String ("hello") 5 bytes ~56 bytes 11x
HashMap entry ~16 bytes (key+val) ~96 bytes 6x
Spark Row (10 fields) ~80 bytes raw ~400 bytes 5x

This means a 1 GB Parquet file can expand to 5–8 GB in JVM heap when deserialized into Java objects. This inflation is the reason "Spill (Memory)" in Spark UI is always much larger than "Spill (Disk)" — the disk version is serialized back to a compact format.

Project Tungsten — Addressing Object Overhead

Project Tungsten (Spark 1.4+, mature in 2.x) directly addresses JVM object overhead through:

  • Binary row format (UnsafeRow) — Stores data in a flat, binary format without Java object wrappers. A row with 10 fields occupies a contiguous byte array, not 10+ separate heap objects.
  • Cache-aware computation — Algorithms designed for CPU cache-line efficiency (sequential memory access patterns)
  • Code generation (Whole-Stage CodeGen) — Fuses multiple operators into a single optimized function, eliminating virtual method calls and object allocation per row
  • Off-heap memory management — Allocates memory outside JVM heap using sun.misc.Unsafe, avoiding GC entirely for managed data
  • Explicit memory management — Pages of binary data with manual lifecycle control (allocate/free) rather than relying on GC
Traditional Java Objects:
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│ Object  │→ │ Object  │→ │ Object  │→ │ Object  │  (scattered in heap)
│ Header  │  │ Header  │  │ Header  │  │ Header  │
│ 16 bytes│  │ 16 bytes│  │ 16 bytes│  │ 16 bytes│
│ + data  │  │ + data  │  │ + data  │  │ + data  │

└────────────────────────────────────────────────────────────────┘

GC Impact on Spark Performance

Garbage collection directly impacts Spark task throughput:

  • Minor GC (Young Gen) — Typically 20–200 ms; acceptable if infrequent. Spark tasks pause but resume quickly.
  • Major/Full GC (Old Gen) — 1–30+ seconds; catastrophic for task throughput. Causes executor heartbeat timeouts and task failures if > 120s.
  • GC overhead limit — JVM throws OOM if >98% of time is spent in GC. Common with severely undersized heaps.

GC Tuning for Spark

Strategy Configuration When to Use
G1GC (default in Spark 3.x) -XX:+UseG1GC Heaps > 4 GB; provides predictable pause times
Increase Young Gen ratio -XX:NewRatio=2 Short-lived objects dominate (most Spark workloads)
G1 region size -XX:G1HeapRegionSize=16m Large heaps (>16 GB); aligns with Spark's allocation patterns
Initiating heap occupancy -XX:InitiatingHeapOccupancyPercent=35 Start concurrent marking earlier to avoid Full GC
GC logging -Xlog:gc*:file=gc.log:time Always enable in production for diagnostics
Off-heap (avoid GC entirely) spark.memory.offHeap.enabled=true Large aggregations / joins with high spill

Broadcast Threshold

How Broadcast Join Avoids Shuffle

A broadcast join (BroadcastHashJoin) sends the smaller table to all executors, allowing the join to execute locally without any shuffle. This eliminates the shuffle write/read phase entirely — and thus eliminates the possibility of shuffle spill for that join.

Sort-Merge Join (Shuffle Required):
┌──────────┐         ┌──────────┐
│  Table A │──shuffle─│  Table B │──shuffle─→ Join (may spill)
│  100 GB  │  write  │  500 MB  │  write
└──────────┘         └──────────┘

Broadcast Hash Join (No Shuffle):
┌──────────┐                     ┌──────────┐
│  Table A │ ← broadcast(B)──── │  Table B │
│  100 GB  │  (sent to all      │  500 MB  │
│  (stays) │   executors)       │  (small) │
└──────────┘                     └──────────┘
No shuffle write/read → No spill from this join

spark.sql.autoBroadcastJoinThreshold

Spark automatically broadcasts a table if its estimated size (from catalog statistics or file size) is below this threshold:

Parameter Default Impact
spark.sql.autoBroadcastJoinThreshold 10 MB Tables below this size are auto-broadcast

When Broadcast Threshold Is Exceeded — Forced Shuffle Join

When both tables exceed the broadcast threshold, Spark falls back to Sort-Merge Join (SMJ), which requires:

  1. Shuffle both tables by the join key — repartitions data so matching keys are co-located
  2. Sort each partition by the join key — requires in-memory sort buffers
  3. Merge sorted streams — iterate through both sorted partitions simultaneously

Each step can cause spill: the shuffle write buffers, the sort operation, and intermediate state during merge.

The Broadcast Memory Trap

Increasing the broadcast threshold reduces shuffle spill but introduces a different memory problem:

  • Broadcast variables are stored in storage memory on every executor
  • A 2 GB broadcast table × 200 executors = 400 GB total memory consumed cluster-wide
  • Storage memory consumed by broadcasts reduces memory available for execution (which can increase spill from other operations)
  • Multiple broadcast joins in the same query compound the problem

Broadcast Threshold Tuning Guidelines

Scenario Recommended Threshold Rationale
Small dimension tables (<50 MB) 50–100 MB Safe to broadcast; minimal memory impact per executor
Medium tables (50–500 MB) Consider case-by-case Must balance shuffle cost vs. memory consumption on all executors
Large tables (>500 MB) Keep default (10 MB) or disable Broadcasting 500 MB+ to every executor exhausts storage memory
Memory-constrained executors Lower (5–10 MB) Preserve execution memory for shuffle/sort operations
Multiple joins in query Lower per-table threshold Cumulative broadcast memory across joins can exceed limits

Forcing or Disabling Broadcast

AQE Solutions

Adaptive Query Execution Overview (Spark 3.0+)

AQE re-optimizes the query plan at runtime based on accurate statistics collected after each shuffle stage completes. This addresses the fundamental problem that compile-time statistics (from the Hive metastore or file sizes) are often inaccurate.

Traditional Query Planning:
  Compile-time stats → Fixed plan → Execute (may be suboptimal)

AQE Query Planning:
  Compile-time stats → Initial plan → Execute Stage 1
    → Collect runtime statistics from shuffle map output
    → Re-optimize remaining stages based on ACTUAL data sizes
    → Execute Stage 2 (optimized) → Collect stats → Re-optimize ...

AQE Feature 1: Coalescing Post-Shuffle Partitions

After a shuffle, AQE examines actual partition sizes and merges small adjacent partitions to reduce task overhead and improve resource utilization:

  • Problem: spark.sql.shuffle.partitions = 200 (default) creates 200 partitions even if total shuffle data is only 100 MB → 200 tasks processing 500 KB each (massive overhead)
  • Solution: AQE coalesces partitions to reach advisoryPartitionSizeInBytes (default 64 MB)
  • Result: 100 MB / 64 MB = 2 partitions instead of 200 → dramatically less scheduling overhead
# AQE Coalescing Configuration
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.initialPartitionNum", "2000")
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "128m")
spark.conf.set("spark.sql.adaptive.coalescePartitions.minPartitionSize", "1m")

# Strategy: set initial partitions HIGH (e.g., 2000)
# Let AQE coalesce down to optimal count based on actual data
# This handles both large and small datasets without manual tuning

AQE Feature 2: Skew Join Optimization

AQE detects skewed partitions after shuffle write and automatically splits them:

Before AQE Skew Handling:
Partition 42: ████████████████████ 5 GB → Single task, spills to disk, 45 min

After AQE Skew Handling:
Partition 42a: ████ 1 GB  → Task A (joins with duplicated right-side partition)
Partition 42b: ████ 1 GB  → Task B (joins with duplicated right-side partition)
Partition 42c: ████ 1 GB  → Task C (joins with duplicated right-side partition)
Partition 42d: ████ 1 GB  → Task D (joins with duplicated right-side partition)
Partition 42e: ████ 1 GB  → Task E (joins with duplicated right-side partition)
Total time: ~9 min (parallel) instead of 45 min (serial + spill)

AQE Feature 3: Converting Sort-Merge Join to Broadcast Hash Join

If runtime statistics reveal that one side of a join is actually much smaller than compile-time estimates predicted, AQE can switch from Sort-Merge Join to Broadcast Hash Join:

  • Filter pushdown may reduce a table from 10 GB (estimated) to 5 MB (actual)
  • AQE detects this after the filter stage executes and sees the actual shuffle output size
  • Converts to broadcast join → eliminates shuffle on the large side entirely

AQE Limitations

  • Only works at shuffle boundaries — Cannot help with spill within a single stage (e.g., large aggregation before shuffle)
  • Requires shuffle — AQE collects statistics from shuffle map output; operations without shuffle don't benefit
  • Skew join only for SortMergeJoin — Does not apply to ShuffledHashJoin or BroadcastHashJoin
  • Does not address root cause — AQE mitigates symptoms; the underlying data distribution issue remains
  • Overhead of re-planning — Small queries may see slight overhead from runtime re-optimization (negligible for large jobs)

Partition Count Heuristics

Choosing the right number of partitions is critical for preventing spill:

  • Target partition size: 100–200 MB per partition for shuffle operations
  • Minimum parallelism: At least 2–3× total executor cores for even utilization
  • Maximum partitions: Avoid > 100,000 partitions (driver metadata overhead)
# Partition count calculation
total_data_size_mb = 500_000  # 500 GB total shuffle data
target_partition_size_mb = 128  # Target 128 MB per partition

optimal_partitions = total_data_size_mb / target_partition_size_mb  # ~3906

# Also consider cluster parallelism
total_cores = num_executors * cores_per_executor  # e.g., 200 * 5 = 1000
min_partitions = total_cores * 2  # 2000 (at least 2 waves)

# Use the larger value
recommended = max(optimal_partitions, min_partitions)  # 3906
# Round up to nice number
spark.conf.set("spark.sql.shuffle.partitions", "4000")

Root Cause Analysis

Why did 200 new partner_ids cause 500 GB spill?

1. The join: orders_df.join(partners_df, on="partner_id")
   - orders_df: 2.1 billion rows, shuffled by partner_id
   - 200 shuffle partitions (default)

2. Hash("MEGA_RETAIL_001") % 200 = partition 42
   → 380M rows (89 GB) routed to single partition

3. Executor memory: 20 GB heap → ~7 GB execution memory
   → 7 GB / 5 cores = ~1.4 GB per task

4. Task processing partition 42:
   - Needs to sort 89 GB for sort-merge join
   - Has 1.4 GB execution memory
   - Spills 60+ times during sort phase
   - Each spill: serialize → write → reset → continue
   - Merge phase: read back all 60 spill files simultaneously

5. Secondary effect: GC pressure
   - Deserializing 89 GB creates billions of Java objects
   - GC pauses of 10-30 seconds every few minutes
   - Effective throughput drops to 40% due to GC

# Step 1: Profile data to identify skewed keys

    .select("partner_id")
    .collect()
)

    "join_key",
    F.when(
        F.col("partner_id").isin(skewed_key_list),

)

        F.col("partner_id").isin(skewed_key_list),

            F.concat(F.col("partner_id"), F.lit(f"_{i}"))

)

                        "gc_time_ms": metrics.get("JVM GC Time", 0),
                        "duration_ms": task_info.get("Finish Time") - task_info.get("Launch Time")
                    })

    return spill_events

from pyspark.sql import functions as F

def detect_skew(df, key_column, skew_factor=10):
    """
    Detect data skew on a given key column.

    Args:
        df: Input DataFrame
        key_column: Column to check for skew
        skew_factor: Ratio threshold (max/median) to flag as skewed

    Returns:
        DataFrame with skew analysis, list of skewed keys
    """
    # Compute key distribution
    key_dist = df.groupBy(key_column).agg(
        F.count("*").alias("row_count"),
        F.sum(F.lit(1)).alias("total_rows")
    )

    # Calculate statistics
    stats = key_dist.agg(
        F.expr("percentile_approx(row_count, 0.5)").alias("median_count"),
        F.max("row_count").alias("max_count"),
        F.avg("row_count").alias("avg_count"),
        F.stddev("row_count").alias("stddev_count"),
        F.count("*").alias("num_keys")
    ).collect()[0]

    median_count = stats.median_count
    max_count = stats.max_count
    skew_ratio = max_count / median_count if median_count > 0 else float('inf')

    print(f"=== Skew Analysis for '{key_column}' ===")
    print(f"  Total keys: {stats.num_keys:,}")
    print(f"  Median rows/key: {median_count:,}")
    print(f"  Max rows/key: {max_count:,}")
    print(f"  Avg rows/key: {stats.avg_count:,.0f}")
    print(f"  Stddev: {stats.stddev_count:,.0f}")
    print(f"  Skew ratio (max/median): {skew_ratio:.1f}x")
    print(f"  Status: {'⚠️  SKEWED' if skew_ratio > skew_factor else '✅ OK'}")

    # Identify skewed keys
    skew_threshold = median_count * skew_factor
    skewed_keys_df = key_dist.filter(F.col("row_count") > skew_threshold) \
        .orderBy(F.desc("row_count"))

    if skewed_keys_df.count() > 0:
        print(f"\n  Skewed keys (>{skew_factor}x median):")
        skewed_keys_df.show(20, truncate=False)

    return skewed_keys_df

2. Adaptive Salting Implementation

def salt_skewed_join(large_df, small_df, join_key, skewed_keys, salt_buckets=100):
    """
    Perform a salted join for skewed keys while preserving normal join
    efficiency for non-skewed keys.

    Args:
        large_df: The large (fact) DataFrame
        small_df: The small (dimension) DataFrame
        join_key: Column name to join on
        skewed_keys: List of keys identified as skewed
        salt_buckets: Number of salt partitions for each skewed key

    Returns:
        Joined DataFrame
    """
    # Split large DataFrame into skewed and non-skewed portions
    large_skewed = large_df.filter(F.col(join_key).isin(skewed_keys))
    large_normal = large_df.filter(~F.col(join_key).isin(skewed_keys))

    # Split small DataFrame similarly
    small_skewed = small_df.filter(F.col(join_key).isin(skewed_keys))
    small_normal = small_df.filter(~F.col(join_key).isin(skewed_keys))

    # --- Handle non-skewed portion (normal join) ---
    result_normal = large_normal.join(small_normal, on=join_key, how="inner")

    # --- Handle skewed portion (salted join) ---
    # Add random salt to large side
    large_salted = large_skewed.withColumn(
        "_salt", (F.rand() * salt_buckets).cast("int")
    ).withColumn(
        "_salted_key",
        F.concat(F.col(join_key), F.lit("_"), F.col("_salt"))
    )

    # Explode small side across all salt values
    salt_array = F.array([F.lit(i) for i in range(salt_buckets)])
    small_exploded = small_skewed.withColumn(
        "_salt", F.explode(salt_array)
    ).withColumn(
        "_salted_key",
        F.concat(F.col(join_key), F.lit("_"), F.col("_salt"))
    )

    # Join on salted key
    result_skewed = large_salted.join(
        small_exploded,
        on="_salted_key",
        how="inner"
    ).drop("_salt", "_salted_key")

    # Handle duplicate columns from join
    # (small_df columns appear twice — remove duplicates)
    for col_name in small_df.columns:
        if col_name != join_key and col_name in large_df.columns:
            result_skewed = result_skewed.drop(small_exploded[col_name])

    # Union both results
    result = result_normal.unionByName(result_skewed, allowMissingColumns=True)

    return result

3. Repartition Tuning

def auto_repartition(df, target_partition_size_mb=128, min_partitions=None):
    """
    Automatically repartition a DataFrame based on estimated data size.

    Args:
        df: Input DataFrame
        target_partition_size_mb: Target size per partition in MB
        min_partitions: Minimum partition count (for parallelism)

    Returns:
        Repartitioned DataFrame
    """
    # Estimate data size using sample
    sample_fraction = 0.01
    sample_count = df.sample(sample_fraction).count()
    estimated_total = sample_count / sample_fraction

    # Estimate row size (sample 100 rows, serialize, measure)
    sample_rows = df.limit(100).toPandas()
    avg_row_size_bytes = sample_rows.memory_usage(deep=True).sum() / len(sample_rows)

    estimated_size_mb = (estimated_total * avg_row_size_bytes) / (1024 * 1024)

    # Calculate optimal partitions
    optimal_by_size = int(estimated_size_mb / target_partition_size_mb) + 1

    if min_partitions:
        optimal = max(optimal_by_size, min_partitions)
    else:
        optimal = optimal_by_size

    # Cap at reasonable limits
    optimal = max(optimal, 1)
    optimal = min(optimal, 50000)

    print(f"Auto-repartition: est. size={estimated_size_mb:.0f}MB, "
          f"partitions={optimal} (target {target_partition_size_mb}MB each)")

    return df.repartition(optimal)

4. AQE Configuration Template

def configure_aqe_anti_spill(spark, data_size_gb, skew_expected=True):
    """
    Configure AQE optimally for spill reduction based on workload characteristics.

    Args:
        spark: SparkSession
        data_size_gb: Estimated total shuffle data size in GB
        skew_expected: Whether data skew is expected
    """
    # Enable AQE
    spark.conf.set("spark.sql.adaptive.enabled", "true")

    # Coalescing: start with many partitions, let AQE merge
    initial_partitions = max(2000, int(data_size_gb * 1024 / 128) * 2)
    spark.conf.set("spark.sql.shuffle.partitions", str(initial_partitions))
    spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
    spark.conf.set("spark.sql.adaptive.coalescePartitions.initialPartitionNum",
                   str(initial_partitions))

    # Target partition size: 128 MB (sweet spot for most workloads)
    spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "128m")
    spark.conf.set("spark.sql.adaptive.coalescePartitions.minPartitionSize", "4m")

    # Skew handling
    if skew_expected:
        spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
        spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")
        spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256m")

    # Local shuffle reader (avoid extra shuffle for certain plans)
    spark.conf.set("spark.sql.adaptive.localShuffleReader.enabled", "true")

    print(f"AQE configured: {initial_partitions} initial partitions, "
          f"128MB target, skew={'enabled' if skew_expected else 'disabled'}")

5. Memory Configuration Template

def configure_executor_memory(spark, node_memory_gb, node_cores,
                               workload_type="balanced"):
    """
    Calculate and set optimal executor memory configuration.

    Args:
        spark: SparkSession (or use for generating spark-submit args)
        node_memory_gb: Total RAM per worker node
        node_cores: Total CPU cores per worker node
        workload_type: "balanced", "memory_heavy", "cpu_heavy"

    Returns:
        dict of recommended configuration
    """
    # Reserve for OS and YARN AM
    os_reserve_gb = max(1, node_memory_gb * 0.05)
    available_memory_gb = node_memory_gb - os_reserve_gb

    # Executor sizing (max 5 cores per executor for good GC behavior)
    cores_per_executor = min(5, node_cores - 1)
    executors_per_node = (node_cores - 1) // cores_per_executor

    memory_per_executor_gb = available_memory_gb / executors_per_node

    # Overhead: 10% for balanced, 15% for memory-heavy
    overhead_fraction = 0.15 if workload_type == "memory_heavy" else 0.10
    overhead_gb = max(0.384, memory_per_executor_gb * overhead_fraction)

    heap_gb = memory_per_executor_gb - overhead_gb

    # Cap heap at 28 GB to avoid GC issues
    if heap_gb > 28:
        offheap_gb = heap_gb - 20
        heap_gb = 20
    else:
        offheap_gb = 0

    config = {
        "spark.executor.memory": f"{int(heap_gb)}g",
        "spark.executor.memoryOverhead": f"{int(overhead_gb * 1024)}m",
        "spark.executor.cores": str(cores_per_executor),
        "spark.memory.fraction": "0.6",
        "spark.memory.storageFraction": "0.3" if workload_type == "memory_heavy" else "0.5",
    }

    if offheap_gb > 0:
        config["spark.memory.offHeap.enabled"] = "true"
        config["spark.memory.offHeap.size"] = f"{int(offheap_gb)}g"

    # Apply configuration
    for key, value in config.items():
        spark.conf.set(key, value)

    print(f"=== Executor Memory Configuration ===")
    print(f"  Node: {node_memory_gb}GB RAM, {node_cores} cores")
    print(f"  Executors per node: {executors_per_node}")
    print(f"  Config: {config}")

    return config

# Usage:
# config = configure_executor_memory(spark, node_memory_gb=128, node_cores=16,
#                                     workload_type="memory_heavy")

6. Spill Monitoring Query

def check_spill_from_history_server(spark, app_id):
    """
    Query Spark History Server REST API for spill metrics.
    Useful for post-hoc analysis and alerting.
    """
    import requests

    history_server = "http://spark-history:18080"
    url = f"{history_server}/api/v1/applications/{app_id}/stages"

    response = requests.get(url)
    stages = response.json()

    spill_summary = []
    for stage in stages:
        if stage.get("diskBytesSpilled", 0) > 0:
            spill_summary.append({
                "stage_id": stage["stageId"],
                "stage_name": stage.get("name", "unknown"),
                "disk_spill_gb": stage["diskBytesSpilled"] / (1024**3),
                "memory_spill_gb": stage["memoryBytesSpilled"] / (1024**3),
                "num_tasks": stage["numTasks"],
                "duration_sec": (stage.get("completionTime", 0) -
                                stage.get("submissionTime", 0)) / 1000
            })

    if spill_summary:
        print(f"⚠️  Spill detected in {len(spill_summary)} stages:")
        for s in sorted(spill_summary, key=lambda x: -x["disk_spill_gb"]):
            print(f"  Stage {s['stage_id']} ({s['stage_name']}): "
                  f"{s['disk_spill_gb']:.1f} GB disk spill, "
                  f"{s['duration_sec']:.0f}s duration")
    else:
        print("✅ No spill detected in any stage.")

    return spill_summary

Common Mistakes

# Mistake Why It Causes Spill Correct Approach
1 Using default spark.sql.shuffle.partitions = 200 for large datasets 500 GB / 200 partitions = 2.5 GB per partition; far exceeds per-task execution memory Set to data_size / 128MB or use AQE with high initial count
2 Ignoring NULL keys in joins All NULL keys hash to the same partition, creating massive skew Filter NULLs before join, or replace with random unique values
3 Using groupByKey() instead of reduceByKey() groupByKey shuffles ALL values to reducers before combining; reduceByKey combines map-side first Use reduceByKey, aggregateByKey, or DataFrame groupBy().agg()
4 Collecting large results to driver then re-distributing Forces all data through driver memory; subsequent re-parallelization may be skewed Keep data distributed; use broadcast() for small reference data
5 Over-caching (persisting too many DataFrames) Storage memory crowds out execution memory; cached blocks cannot be evicted by execution in practice (LRU competition) Only cache DataFrames reused multiple times; unpersist() when done
6 Not enabling AQE in Spark 3.x Misses automatic coalescing and skew handling that would prevent spill Always enable AQE: spark.sql.adaptive.enabled = true
7 Using coalesce() before a shuffle operation Reduces partitions without redistributing data; creates large partitions that spill during subsequent shuffle Use repartition() to evenly distribute, or place coalesce after final computation
8 Too many cores per executor (>5) Execution memory shared among more tasks; per-task memory drops below useful threshold Use 4-5 cores per executor; trade off executor count vs. per-task memory
9 Broadcasting a table that's larger than expected Stale statistics show 10 MB but actual is 2 GB; broadcast consumes storage memory on all executors Refresh table statistics; use ANALYZE TABLE ... COMPUTE STATISTICS
10 Applying window functions without partition clause ROW_NUMBER() OVER (ORDER BY col) routes ALL data to one partition for global sort Always include PARTITION BY to distribute window computation
11 Using UDFs with large closures UDF closures are serialized per task; large captured variables multiply memory usage across tasks Use broadcast variables for large reference data in UDFs; prefer built-in functions
12 Explode before join (instead of after) Exploding arrays 100x multiplies row count before shuffle, causing partition sizes to explode Join first on the parent key, then explode arrays in the result

Trade-offs

Strategy Reduces Spill By Trade-off / Cost
Increase executor memory More execution memory per task → fewer spills Higher cloud cost; GC pressure increases with heap > 28 GB; diminishing returns without addressing root cause
Increase shuffle partitions Smaller partitions → each task processes less data More tasks = more scheduling overhead; too many small tasks waste driver resources; doesn't fix skew
Key salting Distributes hot keys across N partitions Explodes dimension table N×; increases total shuffle volume; code complexity; must maintain salt logic
Enable AQE Runtime optimization for skew and partition sizing Slight planning overhead; doesn't address all spill causes (intra-stage); requires Spark 3.0+
Broadcast join Eliminates shuffle entirely for small-side table Memory consumed on every executor; fails for large tables; broadcast timeout for slow networks
Off-heap memory Bypasses GC; provides predictable memory for execution Memory leaks possible if misconfigured; harder to debug; not counted by some monitoring tools
Reduce cores per executor More memory per concurrent task Fewer tasks in parallel per executor; may underutilize CPU; need more executors for same throughput
Pre-aggregate before join Reduces row count → smaller shuffle volume Changes semantics if not careful; may lose detail needed downstream; requires pipeline redesign
Bucketed tables Pre-shuffled on disk → no shuffle at query time Write-time cost; bucket count must match across tables; inflexible for ad-hoc queries; storage overhead
Filter early (predicate pushdown) Less data enters shuffle stages Requires data to be filterable; not always possible if all data is needed for aggregation

Decision Framework

Is spill caused by data skew?
├── YES → Is the skew on known hot keys?
│         ├── YES → Salt those keys + AQE as safety net
│         └── NO (dynamic) → Enable AQE skew join; add monitoring
└── NO → Is it uniform spill across all tasks?
          ├── YES → Per-task data too large
          │         ├── Can you add partitions? → Increase shuffle.partitions
          │         ├── Can you add memory? → Increase executor.memory
          │         └── Can you reduce data? → Filter/pre-aggregate/broadcast
          └── NO → Check for:
                    - Over-caching (free storage memory)
                    - Large broadcast variables (reduce threshold)
                    - UDF memory leaks (switch to built-ins)
                    - Executor GC thrashing (off-heap or reduce heap)

Follow-up Questions

Interviewers typically follow up with these deeper questions after the initial spill discussion:

Memory Architecture

  • "What happens if you set spark.memory.fraction to 0.9?" — User memory drops to 10%; UDFs, accumulators, and internal metadata may OOM. Safe range is 0.5–0.75.
  • "Why can execution evict storage but not vice versa?" — Execution represents active computation (in-flight sort/shuffle); interrupting it would lose partial work. Storage is recoverable (re-compute or re-read from disk).
  • "How does off-heap interact with container memory limits?" — Off-heap is outside JVM heap but inside the container. Container = heap + memoryOverhead + offHeap. YARN/K8s kills container if total exceeds allocation.

Shuffle Internals

  • "What's the difference between shuffle spill and disk-based shuffle?" — All shuffle writes go to disk (shuffle files). Spill is additional: the in-memory sort/aggregation buffer overflows before producing the final shuffle output.
  • "How many spill files can a task create?" — Unbounded in theory. Each time the in-memory buffer fills (~5 MB initial, grows with memory grants), it spills. A task processing 50 GB with 1 GB memory may spill 50+ times.
  • "Does Spark compress spill files?" — Yes, controlled by spark.shuffle.spill.compress (default true) using the codec in spark.io.compression.codec (default lz4).

Skew & Distribution

  • "How would you handle skew in a window function?" — Window functions partition data similarly to groupBy. Salt the partition key, compute windows on salted partitions, then reconcile (complex for ranking functions; simpler for running aggregates).
  • "What if both sides of a join are skewed on the same key?" — Neither side is small enough to broadcast. Salt both sides: large_A salted + small lookup exploded for each salt. Or use partial-broadcast for the specific hot key range.
  • "Can skew cause OOM even with spill enabled?" — Yes. If the final merge of all spill files still requires more memory than available (e.g., too many open file handles, or combiner state for one key is huge), the task OOMs.

Production & Operations

  • "How would you set up alerting for spill?" — Parse Spark event logs for diskBytesSpilled metric; alert when total exceeds threshold (e.g., >50 GB) or when max task spill exceeds per-task threshold (e.g., >5 GB).
  • "Your job spills 100 GB but meets SLA. Should you fix it?" — Depends on cost and trend. 100 GB spill on SSD with headroom may be acceptable. But track if it's growing — today's 100 GB becomes next month's SLA breach after data growth.
  • "How do you handle spill on a streaming job (Structured Streaming)?" — Similar principles but complicated by state management. Spill in stateful operations (aggregations, stream-stream joins) indicates state size exceeding memory. Solutions: increase memory, add watermarks to bound state, use RocksDB state backend.

Advanced

  • "Explain the relationship between spill and shuffle service." — External shuffle service stores shuffle files independently of executors. Spill files are task-local and not managed by shuffle service. If an executor dies, spill files are lost (task retries from scratch), but shuffle output files survive via external shuffle service.
  • "How does Project Tungsten reduce the need for spill?" — Tungsten's binary format (UnsafeRow) eliminates JVM object overhead (5x memory reduction). Same 10 GB of data occupies ~2 GB in Tungsten format vs 10 GB as Java objects. This directly reduces memory pressure and spill frequency.
  • "What's the maximum practical executor memory before you should scale out instead of up?" — Generally 28–32 GB heap. Beyond this, G1GC struggles with pause times, and the benefit of per-task memory plateaus. Better to add executors (scale out) than make individual executors larger.

Summary

Concept Key Takeaway
What is spill? When in-memory execution buffers (sort, hash map, shuffle) exceed available task memory, Spark serializes data to local disk and re-reads it during merge — 3-10x performance degradation.
Memory model Unified memory (60% of heap - 300MB) splits between execution and storage; execution can evict storage but not vice versa. Per-task share = execution_memory / active_tasks.
Root cause #1: Data skew One partition 100x larger than peers overwhelms single task's memory. Fix: salting, AQE skew join, custom partitioner.
Root cause #2: Too few partitions Default 200 partitions for 500 GB = 2.5 GB/partition. Fix: increase to data_size/128MB or use AQE coalescing with high initial count.
Root cause #3: Memory configuration Heap too small, too many cores per executor, or broadcast variables consuming storage. Fix: right-size executors (20 GB heap, 5 cores), use off-heap for heavy workloads.
AQE Spark 3.0+ runtime optimization: coalesces small partitions, splits skewed partitions, converts join strategies. Enable always as baseline protection.
Broadcast threshold Tables below 10 MB (default) are auto-broadcast, eliminating shuffle. Increase cautiously — broadcast memory multiplied across all executors.
GC pressure JVM object overhead inflates data 5x in memory. Tungsten binary format and off-heap allocation reduce GC impact. G1GC with 28 GB max heap.
Debugging Spark UI → Stage → Task metrics: compare max vs median for Shuffle Read, Spill (Memory/Disk), Duration, GC Time. Max >> median = skew.
Production approach Enable AQE + set partitions high + monitor spill metrics + alert on degradation. Investigate root cause (skew vs. volume vs. config) before throwing resources at the problem.

Interview Response Framework

  1. What is spill (20 seconds) — Define spill, mention execution memory exhaustion, ExternalSorter/ExternalAppendOnlyMap.
  2. Memory model (40 seconds) — Unified memory, execution vs storage, fraction config, per-task share.
  3. Root causes (60 seconds) — Data skew (most common), partition count, memory config, broadcast impact.

MVCC Internals

Explain MVCC from first principles.

MVCC PostgreSQL

Interviewer Intent

When an interviewer asks you to "explain MVCC from first principles," they are probing for:

  • Conceptual clarity — Can you articulate why keeping multiple versions of a row solves concurrency problems that locking alone cannot?
  • Implementation depth — Do you know how PostgreSQL physically stores tuple versions, manages transaction IDs, and determines visibility?
  • Operational maturity — Can you diagnose MVCC-related production issues like table bloat, wraparound, and long-running transactions blocking vacuum?
  • Cross-engine awareness — Do you understand the trade-offs between PostgreSQL's append-only heap versus InnoDB's undo-log approach?
  • Isolation-level fluency — Can you map each SQL isolation level to specific MVCC snapshot mechanics?

This is not a textbook recitation question. The interviewer wants evidence that you have debugged real MVCC problems in production systems handling billions of rows.

Quick Answer (60-Second Version)

Multi-Version Concurrency Control (MVCC) is a technique where every write creates a new version of a row rather than overwriting it in place. Readers see a consistent snapshot of the database at a specific point in time, so they never block writers and writers never block readers. In PostgreSQL, each row (tuple) carries metadata — xmin (creating transaction), xmax (deleting transaction), and infomask bits — that the visibility engine evaluates against the reader's snapshot to decide which version is "live." Dead versions accumulate until VACUUM reclaims them. The cost of this design is space amplification (bloat) and the operational burden of timely vacuuming.

Why MVCC Exists

The Fundamental Problem: Readers vs. Writers

In a lock-based concurrency model (e.g., SQL Server's default READ COMMITTED with shared locks), a reader acquiring a shared lock on a row blocks any writer attempting an exclusive lock on the same row, and vice versa. Under high concurrency, this creates contention that degrades throughput exponentially.

-- Lock-based world: Session A blocks Session B
-- Session A (reader)
BEGIN;
SELECT balance FROM accounts WHERE id = 42;  -- acquires shared lock
-- holds lock until end of statement or transaction

-- Session B (writer) — BLOCKED until Session A releases
UPDATE accounts SET balance = balance - 100 WHERE id = 42;

MVCC Eliminates Read-Write Contention

With MVCC, the database maintains multiple physical versions of each row. A reader sees the version that was committed at the time its snapshot was taken. A concurrent writer creates a new version without disturbing the old one. Neither blocks the other.

-- MVCC world: no blocking
-- Session A sees the old version (balance = 1000)
BEGIN;
SELECT balance FROM accounts WHERE id = 42;  -- snapshot sees xmin=100, committed

-- Session B proceeds immediately
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 42;
-- creates new tuple version with xmin=200
COMMIT;

Time-Travel Queries & Analytical Consistency

MVCC's version history enables:

  • Consistent long-running analytics — A 30-minute reporting query sees a stable snapshot even as OLTP writes continue.
  • Point-in-time recovery — Combined with WAL, MVCC versions provide the foundation for PITR.
  • Time-travel semantics — Snowflake's AT(TIMESTAMP => ...) and BigQuery's FOR SYSTEM_TIME AS OF are direct applications of retained versions.

The Trade-Off

MVCC trades space for concurrency. Dead tuples accumulate and must be reclaimed (VACUUM in PostgreSQL, purge threads in InnoDB). If reclamation falls behind, tables bloat, indexes grow, and query performance degrades — a theme we will revisit in the VACUUM and Bloat sections.

Version Chains & Tuple Structure

PostgreSQL Heap Tuple Layout

Every row in a PostgreSQL heap page is a "heap tuple" with a fixed-size header (23 bytes minimum) followed by user data. The MVCC-critical fields in the header are:

-- Inspecting tuple header fields directly
SELECT ctid, xmin, xmax, cmin, cmax,
       t_infomask::bit(16) AS infomask,
       t_infomask2::bit(16) AS infomask2
FROM heap_page_items(get_raw_page('accounts', 0));
FieldSizePurpose
t_xmin4 bytesTransactionId that inserted this tuple
t_xmax4 bytesTransactionId that deleted/updated this tuple (0 if live)
t_cid4 bytesCommand ID within the transaction (cmin/cmax combined)
t_ctid6 bytesCurrent tuple ID — points to self if latest, or to next version in HOT chain
t_infomask2 bytes16 status bits: committed, aborted, has-null, has-varwidth, etc.
t_infomask22 bytesNumber of attributes + HOT-updated flag + heap-only tuple flag

xmin and xmax Semantics

INSERT sets xmin to the inserting transaction's XID. xmax remains 0.

DELETE sets xmax to the deleting transaction's XID on the existing tuple. No new tuple is created.

UPDATE is a DELETE + INSERT: the old tuple gets xmax set, and a new tuple is created with a new xmin. The old tuple's t_ctid points to the new tuple (forming a version chain).

-- Observe version chain after an UPDATE
BEGIN;
-- Original tuple at (0,1): xmin=100, xmax=0, ctid=(0,1)
UPDATE accounts SET balance = 500 WHERE id = 42;
-- Old tuple at (0,1): xmin=100, xmax=200, ctid=(0,2)
-- New tuple at (0,2): xmin=200, xmax=0, ctid=(0,2)
COMMIT;

cmin and cmax — Intra-Transaction Visibility

Within a single transaction that performs multiple statements, cmin and cmax (stored as a combined t_cid with a "combo CID" mechanism for edge cases) track which command created or deleted a tuple. This allows a cursor opened by statement 1 to correctly see or hide rows modified by statement 3 of the same transaction.

Infomask Bits (Key Flags)

# Key t_infomask bits (from htup_details.h)
HEAP_XMIN_COMMITTED  = 0x0100  # xmin transaction committed
HEAP_XMIN_INVALID    = 0x0200  # xmin transaction aborted
HEAP_XMAX_COMMITTED  = 0x0400  # xmax transaction committed
HEAP_XMAX_INVALID    = 0x0800  # xmax transaction aborted/not set
HEAP_XMIN_FROZEN     = 0x0300  # xmin is frozen (always visible)
HEAP_UPDATED         = 0x2000  # tuple was result of an update
HEAP_HOT_UPDATED     = 0x4000  # tuple has been HOT-updated

These "hint bits" are critical for performance. Without them, every visibility check would require a CLOG (pg_xact) lookup. Once set, subsequent reads skip the CLOG entirely — but setting hint bits dirties the page, generating additional WAL in full_page_writes mode.

Version Chain Traversal

When an index scan finds a TID (e.g., (0,1)), the executor follows the t_ctid chain until it finds a version visible to the current snapshot. In non-HOT chains, each version has its own index entry. In HOT chains (covered later), only the root tuple is indexed.

# Pseudocode: version chain traversal
def find_visible_version(tid, snapshot):
    tuple = heap_fetch(tid)
    while True:
        if is_visible(tuple, snapshot):
            return tuple
        if tuple.t_ctid == tuple.ctid:  # points to self = end of chain
            return None  # no visible version
        tuple = heap_fetch(tuple.t_ctid)

Snapshots & Visibility Rules

What a Snapshot Contains

A PostgreSQL snapshot (SnapshotData struct) captures the state of all in-flight transactions at snapshot creation time:

-- Inspect current snapshot
SELECT txid_current_snapshot();
-- Returns: '100:104:100,102'
-- Format: xmin:xmax:xip_list
-- xmin = lowest still-active XID (all XIDs below are visible/aborted)
-- xmax = first unassigned XID (all XIDs >= are invisible)
-- xip_list = active XIDs between xmin and xmax
Snapshot FieldMeaning
xminAll transactions with XID < xmin are completed (committed or aborted)
xmaxAll transactions with XID >= xmax have not yet started
xip[]Array of XIDs between xmin and xmax that were in-progress at snapshot time
subxip[]Subtransaction XIDs that are in-progress
curcidCommand ID for intra-transaction visibility

The Visibility Algorithm

For every tuple encountered during a scan, PostgreSQL runs HeapTupleSatisfiesMVCC() (or variant). The simplified logic:

# Simplified HeapTupleSatisfiesMVCC
def is_visible(tuple, snapshot):
    # Step 1: Is the inserting transaction visible?
    if tuple.xmin == my_xid:
        # My own insert — visible if cmin < current command
        if tuple.cmin >= snapshot.curcid:
            return False
        # But check if I also deleted it
        if tuple.xmax == my_xid and tuple.cmax < snapshot.curcid:
            return False
        return True

    if not xmin_committed(tuple):
        # Inserter aborted or still running
        if xmin_aborted(tuple):
            return False  # definitely invisible
        if tuple.xmin in snapshot.xip:
            return False  # inserter was in-progress at snapshot time
        if tuple.xmin >= snapshot.xmax:
            return False  # inserter started after snapshot
        # else: inserter committed before snapshot — need CLOG check
        if not transaction_committed(tuple.xmin):
            set_xmin_aborted(tuple)  # set hint bit
            return False
        set_xmin_committed(tuple)  # set hint bit

    # Step 2: Is the deleting transaction visible?
    if tuple.xmax == 0 or xmax_aborted(tuple):
        return True  # not deleted, or deleter aborted

    if tuple.xmax == my_xid:
        return tuple.cmax >= snapshot.curcid  # I deleted it — visible if before my delete cmd

    if tuple.xmax in snapshot.xip:
        return True  # deleter was in-progress — deletion not yet visible

    if tuple.xmax >= snapshot.xmax:
        return True  # deleter started after my snapshot

    # Deleter committed before my snapshot
    if transaction_committed(tuple.xmax):
        set_xmax_committed(tuple)
        return False
    else:
        set_xmax_aborted(tuple)
        return True

CLOG (pg_xact) — The Transaction Status Oracle

The commit log stores 2 bits per transaction ID: IN_PROGRESS, COMMITTED, ABORTED, or SUB_COMMITTED. It lives in pg_xact/ (formerly pg_clog/) as 256KB segment files, each covering 2^23 transactions.

# CLOG segment files
ls -la $PGDATA/pg_xact/
# 0000  0001  0002 ... each 256KB, 4 txns per byte

Frequent CLOG lookups are expensive (shared buffer pool access with potential I/O). This is why hint bits are essential — they cache the CLOG result directly in the tuple header, eliminating repeated lookups for hot tuples.

Snapshot Timing: When Is It Taken?

  • READ COMMITTED — New snapshot at the start of each statement.
  • REPEATABLE READ — Single snapshot at the start of the first statement in the transaction.
  • SERIALIZABLE — Same as REPEATABLE READ, plus predicate lock tracking.

Isolation Levels with MVCC

Read Committed (Default)

Each statement gets a fresh snapshot. This means two SELECTs in the same transaction can return different results if a concurrent transaction commits between them.

-- Read Committed behavior
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- Statement 1: snapshot taken at t1
SELECT count(*) FROM orders;  -- returns 1000

-- Meanwhile, another session inserts 50 rows and commits

-- Statement 2: NEW snapshot at t2
SELECT count(*) FROM orders;  -- returns 1050 (non-repeatable read!)
COMMIT;

UPDATE visibility rule: In READ COMMITTED, if an UPDATE's WHERE clause finds a row that has been modified by a concurrent committed transaction, PostgreSQL re-evaluates the WHERE condition against the new version. This is the "EvalPlanQual" mechanism — a crucial subtlety that prevents lost updates.

-- EvalPlanQual in action
-- Session A:
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 42 AND balance >= 100;
-- Session A sees balance=1000, updates to 900

-- Session B (concurrent, READ COMMITTED):
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 42 AND balance >= 100;
-- Blocks on Session A's row lock...
-- Session A commits.
-- Session B re-evaluates: balance is now 900 (>=100), so it proceeds → 800
COMMIT;

Repeatable Read

A single snapshot is taken at the start of the first query and reused for all subsequent statements. The transaction sees a frozen view of the database.

-- Repeatable Read behavior
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT count(*) FROM orders;  -- returns 1000 (snapshot at t1)

-- Another session inserts 50 rows and commits

SELECT count(*) FROM orders;  -- STILL returns 1000 (same snapshot)

-- Attempting to update a row modified by another committed txn:
UPDATE orders SET status = 'shipped' WHERE id = 500;
-- ERROR: could not serialize access due to concurrent update
COMMIT;

Unlike READ COMMITTED, REPEATABLE READ does not do EvalPlanQual re-evaluation. If the target row was modified after the snapshot, the transaction aborts with a serialization error.

Serializable (SSI — Serializable Snapshot Isolation)

PostgreSQL's SERIALIZABLE level uses Serializable Snapshot Isolation (SSI), based on the academic work by Cahill, Röhm, and Fekete (2008). It detects "dangerous structures" — cycles in the serialization graph — using predicate locks (SIRead locks).

-- SSI detecting write skew
-- Rule: at least one doctor must be on-call
-- Session A (SERIALIZABLE):
BEGIN;
SELECT count(*) FROM doctors WHERE on_call = true;  -- returns 2
-- Predicate lock on: doctors WHERE on_call = true
UPDATE doctors SET on_call = false WHERE id = 1;
COMMIT;

-- Session B (SERIALIZABLE, concurrent):
BEGIN;
SELECT count(*) FROM doctors WHERE on_call = true;  -- returns 2 (own snapshot)
-- Predicate lock on: doctors WHERE on_call = true
UPDATE doctors SET on_call = false WHERE id = 2;
COMMIT;
-- ERROR: could not serialize access due to read/write dependencies

SSI Internals: Predicate Locks & rw-Dependencies

SSI tracks three types of dependencies between transactions:

  • wr-dependency — T2 reads a version written by T1
  • ww-dependency — T2 overwrites a version written by T1
  • rw-antidependency — T1 reads a version that T2 later overwrites (T1's read is "stale")

A "dangerous structure" occurs when there are two consecutive rw-antidependencies in the serialization graph (a "pivot" transaction). SSI aborts one of the involved transactions to break the cycle.

-- View predicate locks (SIRead locks)
SELECT locktype, relation::regclass, page, tuple, pid,
       mode, granted
FROM pg_locks
WHERE mode = 'SIReadLock';

VACUUM Deep Dive

Why VACUUM Is Necessary

PostgreSQL's append-only MVCC design means dead tuples (versions no longer visible to any active snapshot) accumulate in heap pages. Without VACUUM:

  • Tables grow unbounded (bloat)
  • Sequential scans read dead tuples, wasting I/O
  • Index entries point to dead tuples, increasing index size and scan cost
  • Transaction ID wraparound threatens data loss (2^31 XIDs ≈ 2 billion)

Lazy VACUUM (Standard)

The default VACUUM performs a three-phase process:

  1. Heap scan — Scan pages, collect TIDs of dead tuples into a TID array (limited by maintenance_work_mem).
  2. Index vacuum — For each index, scan the entire index and remove entries pointing to dead TIDs.
  3. Heap vacuum — Mark dead tuple slots as free in the heap pages, update the Free Space Map (FSM).
-- Manual VACUUM with verbose output
VACUUM (VERBOSE) accounts;
-- INFO: vacuuming "public.accounts"
-- INFO: scanned index "accounts_pkey" to remove 15000 row versions
-- INFO: table "accounts": removed 15000 dead item identifiers in 200 pages
-- INFO: table "accounts": found 15000 removable, 50000 nonremovable row versions
--       in 500 out of 1000 pages

Aggressive VACUUM (Anti-Wraparound)

When a table's relfrozenxid (oldest unfrozen XID) ages past vacuum_freeze_min_age (default 50M transactions) or the table age exceeds autovacuum_freeze_max_age (default 200M), PostgreSQL triggers an aggressive vacuum that freezes old tuples by setting their infomask to HEAP_XMIN_FROZEN.

-- Check table freeze age
SELECT relname,
       age(relfrozenxid) AS xid_age,
       pg_size_pretty(pg_table_size(oid)) AS size
FROM pg_class
WHERE relkind = 'r'
ORDER BY age(relfrozenxid) DESC
LIMIT 10;

-- Emergency: approaching wraparound
-- If age > 2 billion - autovacuum_freeze_max_age, PostgreSQL
-- will refuse new writes and shut down to prevent wraparound!

Autovacuum Tuning

Autovacuum is a background launcher that spawns worker processes based on activity thresholds:

-- Key autovacuum parameters
ALTER TABLE high_churn_table SET (
  autovacuum_vacuum_threshold = 50,          -- min dead tuples before vacuum
  autovacuum_vacuum_scale_factor = 0.01,     -- fraction of table (default 0.2 is too high for large tables)
  autovacuum_vacuum_cost_delay = 2,          -- ms to sleep per cost unit (default 2ms; 0 for aggressive)
  autovacuum_vacuum_cost_limit = 1000,       -- cost limit per round (default 200 is conservative)
  autovacuum_analyze_threshold = 50,
  autovacuum_analyze_scale_factor = 0.005
);

-- Global settings for high-throughput systems
-- postgresql.conf
-- autovacuum_max_workers = 6          (default 3)
-- autovacuum_naptime = 15s            (default 1min)
-- vacuum_cost_limit = 2000            (default 200)
-- maintenance_work_mem = 2GB          (default 64MB → more TIDs per pass)

The Autovacuum Decision Formula

# Autovacuum triggers when:
dead_tuples >= threshold + scale_factor * reltuples

# Example for a 10M row table with defaults:
# 50 + 0.2 * 10,000,000 = 2,000,050 dead tuples before vacuum fires!
# With tuned settings:
# 50 + 0.01 * 10,000,000 = 100,050 dead tuples → much more responsive

Free Space Map (FSM)

The FSM tracks available space in each heap page, stored as a binary tree in <relfilenode>_fsm. After VACUUM frees space, it updates the FSM so future INSERTs can reuse pages instead of extending the table.

-- Inspect FSM
CREATE EXTENSION pg_freespacemap;
SELECT blkno, avail
FROM pg_freespace('accounts')
WHERE avail > 0
ORDER BY blkno
LIMIT 20;

Visibility Map (VM)

The VM stores 2 bits per heap page:

  • All-visible — Every tuple on the page is visible to all current and future transactions. Index-only scans can skip heap fetches for these pages.
  • All-frozen — Every tuple is frozen. Aggressive vacuum can skip these pages entirely.
-- Inspect visibility map
CREATE EXTENSION pg_visibility;
SELECT blkno, all_visible, all_frozen
FROM pg_visibility('accounts')
WHERE NOT all_visible
LIMIT 20;

-- Pages not all-visible = pages that need vacuum attention
SELECT count(*) AS dirty_pages
FROM pg_visibility('accounts')
WHERE NOT all_visible;

HOT Updates (Heap-Only Tuples)

The Index Maintenance Problem

In standard PostgreSQL updates, every index on the table gets a new entry for the new tuple version — even if the indexed columns didn't change. For a table with 10 indexes, a single-column non-indexed update creates 10 new index entries plus the new heap tuple. This amplifies write I/O dramatically.

How HOT Works

Heap-Only Tuple (HOT) updates avoid index entry creation when:

  1. The update does not modify any indexed column
  2. The new tuple version fits on the same heap page as the old version

When both conditions are met:

  • The old tuple's t_ctid points to the new tuple (intra-page chain)
  • The old tuple gets HEAP_HOT_UPDATED flag set
  • The new tuple gets HEAP_ONLY_TUPLE flag set
  • No index entries are created for the new version
-- Check HOT update ratio
SELECT relname,
       n_tup_upd,
       n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 0
ORDER BY n_tup_upd DESC
LIMIT 10;

-- Goal: HOT ratio > 90% for high-update tables

HOT Chain Pruning

When a subsequent operation accesses a page with a HOT chain, PostgreSQL performs "page pruning" — it removes dead intermediate versions from the chain and redirects the line pointer (item ID) of the root tuple directly to the live version. This is a mini-vacuum that happens without any explicit VACUUM call.

-- Before pruning: chain (0,1) → (0,2) → (0,3) [live]
-- Index still points to (0,1)
-- After pruning: LP[1] redirects directly to (0,3)
-- Dead versions (0,1) and (0,2) are freed on the page

-- fillfactor controls space reservation for HOT updates
ALTER TABLE accounts SET (fillfactor = 80);
-- 20% of each page is reserved for HOT updates
-- Trade-off: more pages (larger table) but way fewer index writes

When HOT Fails

  • Indexed column modified — Any index needs a new entry, so HOT is impossible.
  • No room on page — If the page is full (no free space from fillfactor), the new tuple goes to a different page, requiring index updates.
  • TOAST columns — If the update changes a TOASTed column's length significantly, the tuple might not fit.

Optimizing for HOT

-- Strategy 1: Lower fillfactor on frequently-updated tables
ALTER TABLE sessions SET (fillfactor = 70);

-- Strategy 2: Remove unnecessary indexes
-- Each additional index reduces HOT eligibility when its columns are updated
DROP INDEX IF EXISTS idx_sessions_updated_at;  -- if only used for rare queries

-- Strategy 3: Partial indexes instead of full indexes
CREATE INDEX idx_orders_pending ON orders(created_at)
WHERE status = 'pending';
-- Reduces index maintenance for updates that change status away from 'pending'

Table & Index Bloat

What Causes Bloat

  • Long-running transactions — Hold back the global xmin horizon, preventing vacuum from reclaiming any tuples newer than that XID.
  • Abandoned replication slots — Logical replication slots with unconsumed changes prevent vacuum from cleaning referenced tuples.
  • Autovacuum falling behind — If the update rate exceeds vacuum throughput, dead tuples accumulate faster than they're reclaimed.
  • HOT failures — When HOT can't be used, new tuple versions consume additional page space.
  • Bulk deletes without vacuum — Deleting millions of rows leaves dead tuples until vacuum runs.

Detecting Bloat: pg_stat_user_tables

-- Dead tuple ratio
SELECT schemaname, relname,
       n_live_tup,
       n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_vacuum,
       last_autovacuum,
       vacuum_count,
       autovacuum_count
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC;

Detecting Bloat: Table Size vs. Expected Size

-- Compare actual size to estimated minimum size
-- Using pgstattuple extension
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT * FROM pgstattuple('accounts');
-- table_len        | 8192000000   (actual table size)
-- tuple_count      | 10000000     (live tuples)
-- tuple_len        | 4800000000   (live tuple data)
-- dead_tuple_count | 5000000      (dead tuples!)
-- dead_tuple_len   | 2400000000   (dead data)
-- free_space       | 500000000    (already freed by vacuum)
-- free_percent     | 6.1

-- Bloat ratio
SELECT round(100.0 * dead_tuple_len / table_len, 1) AS bloat_pct
FROM pgstattuple('accounts');
-- bloat_pct: 29.3% → significant bloat

-- 1. Kill long-running idle transactions

       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag

);

SET statement_timeout = '30s';  -- per session
ALTER DATABASE analytics SET statement_timeout = '5min';  -- per database

MVCC in Other Engines

InnoDB (MySQL) — Undo Log Approach

Unlike PostgreSQL's append-only heap, InnoDB updates rows in-place and stores previous versions in a separate undo log (rollback segment).

  • Clustered index — The primary key index IS the table. Updates modify the row in the B+tree leaf page.
  • Undo log — Before overwriting, the old version is written to the undo tablespace. A pointer in the row header (DB_ROLL_PTR) links to the undo record.
  • Version chain — Readers follow DB_ROLL_PTR backward through undo records to find the version matching their read view.
  • Purge thread — Background thread removes undo records that are no longer needed by any active read view (analogous to VACUUM).
-- InnoDB: check undo log usage
SELECT name, count
FROM information_schema.innodb_metrics
WHERE name LIKE '%undo%' OR name LIKE '%purge%';

-- History list length = unpurged undo records
SHOW ENGINE INNODB STATUS\G
-- History list length: 15234  ← high = purge falling behind

Bloat locationHeap pages + indexesUndo tablespace (separate from data)

Oracle — Rollback Segments

Oracle's approach is similar to InnoDB (predates it, as InnoDB was inspired by Oracle's design):

  • Updates in-place with before-images stored in UNDO tablespace
  • Consistent reads reconstruct from undo; if undo is overwritten → ORA-01555: snapshot too old
  • Automatic Undo Management (AUM) with UNDO_RETENTION parameter
  • No equivalent of PostgreSQL's bloat problem in the data tablespace, but undo tablespace can grow

Snowflake — Time Travel & Fail-Safe

Snowflake implements MVCC at the micro-partition level rather than the row level:

  • Micro-partitions are immutable columnar files (50-500MB compressed)
  • An UPDATE creates new micro-partitions; old ones are retained for the Time Travel period
  • DATA_RETENTION_TIME_IN_DAYS (0-90 days) controls how long old versions are kept
  • After Time Travel expires, data enters 7-day Fail-Safe (Snowflake-managed, no user access)
  • No VACUUM needed — garbage collection is automatic based on retention policies
-- Snowflake Time Travel
SELECT * FROM orders
AT(TIMESTAMP => '2024-01-15 10:00:00'::timestamp);

-- Undrop a table (within Time Travel period)
UNDROP TABLE accidentally_deleted_orders;

-- Clone at a point in time (zero-copy)
CREATE TABLE orders_snapshot CLONE orders
AT(OFFSET => -3600);  -- 1 hour ago

BigQuery — Snapshot Isolation

BigQuery provides snapshot isolation semantics with automatic versioning:

  • Tables store history for 7 days (FOR SYSTEM_TIME AS OF decorator)
  • Internally uses immutable columnar storage with metadata-level versioning
  • No user-facing MVCC configuration — fully managed
  • DML operations (INSERT, UPDATE, DELETE) are metadata operations on columnar files
-- BigQuery time travel
SELECT * FROM `project.dataset.orders`
FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 2 HOUR);

-- Restore a table from a point in time
CREATE OR REPLACE TABLE `project.dataset.orders` AS
SELECT * FROM `project.dataset.orders`
FOR SYSTEM_TIME AS OF '2024-01-15 10:00:00 UTC';

Real Incident: Long-Running Transaction Blocked VACUUM for 3 Days

The Setup

System: E-commerce platform, PostgreSQL 14, 500M row orders table, ~50K updates/minute (order status changes). Autovacuum running with slightly tuned settings. Read replicas serving analytics dashboards.

The Trigger

A data engineer ran an ad-hoc analytical query from a reporting tool connected directly to the primary (not the replica). The tool held an open transaction (idle in transaction) for 72 hours due to a forgotten session in a Jupyter notebook:

-- The forgotten transaction (opened Friday evening)
BEGIN;  -- xid = 850,000,000
SELECT count(*) FROM orders WHERE created_at > now() - interval '90 days';
-- ... engineer went home for the weekend
-- Transaction stayed open with snapshot holding xmin = 850,000,000

The Cascade

  1. Hour 0-6: Autovacuum runs but cannot reclaim any tuples with xmin > 850,000,000 because the open transaction's snapshot considers them potentially visible. Dead tuples accumulate.
  2. Hour 6-24: Orders table grows from 80GB to 200GB. Autovacuum keeps running (consuming I/O) but reclaiming nothing meaningful. Sequential scan times increase.
  3. Hour 24-48: Table reaches 500GB. B-tree indexes on the orders table grow proportionally (dead index entries cannot be removed). Buffer cache hit ratio drops from 99% to 85%.
  4. Hour 48-72: Average query latency on the orders table degrades from 50ms to 5+ seconds. API timeouts spike. PagerDuty fires.

Lessons Learned

  • A single idle transaction can cripple an entire database within hours on high-write tables.
  • backend_xmin monitoring is non-negotiable for production PostgreSQL.
  • Regular VACUUM only marks space reusable — the OS file doesn't shrink. Use pg_repack for actual file size reduction.
  • Analytics workloads must be isolated to read replicas with hot_standby_feedback = off (accept occasional query cancellations on replica vs. blocking vacuum on primary).

Monitoring Script: MVCC Health Dashboard

#!/usr/bin/env python3
"""MVCC health monitoring script for PostgreSQL."""

import psycopg2
import json
from datetime import datetime

def get_mvcc_health(dsn: str) -> dict:
    """Collect MVCC health metrics from PostgreSQL."""
    conn = psycopg2.connect(dsn)
    conn.autocommit = True
    cur = conn.cursor()

    metrics = {}

    # 1. Oldest open transaction
    cur.execute("""
        SELECT pid, usename, state,
               age(backend_xmin) AS xmin_age,
               extract(epoch FROM now() - xact_start) AS tx_seconds
        FROM pg_stat_activity
        WHERE backend_xmin IS NOT NULL
        ORDER BY age(backend_xmin) DESC
        LIMIT 1
    """)
    row = cur.fetchone()
    if row:
        metrics['oldest_xmin'] = {
            'pid': row[0], 'user': row[1], 'state': row[2],
            'xmin_age': row[3], 'duration_seconds': float(row[4] or 0)
        }

    # 2. Top bloated tables
    cur.execute("""
        SELECT relname, n_dead_tup, n_live_tup,
               round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
               pg_table_size(relid) AS size_bytes
        FROM pg_stat_user_tables
        WHERE n_dead_tup > 10000
        ORDER BY n_dead_tup DESC
        LIMIT 5
    """)
    metrics['bloated_tables'] = [
        {'table': r[0], 'dead_tuples': r[1], 'live_tuples': r[2],
         'dead_pct': float(r[3] or 0), 'size_bytes': r[4]}
        for r in cur.fetchall()
    ]

    # 3. XID wraparound risk
    cur.execute("""
        SELECT datname, age(datfrozenxid) AS age
        FROM pg_database
        ORDER BY age DESC LIMIT 1
    """)
    row = cur.fetchone()
    if row:
        metrics['wraparound'] = {
            'database': row[0],
            'age': row[1],
            'pct_to_wraparound': round(row[1] / 2147483647 * 100, 2)
        }

    # 4. Autovacuum status
    cur.execute("""
        SELECT count(*) FROM pg_stat_activity
        WHERE query LIKE 'autovacuum:%'
    """)
    metrics['autovacuum_workers_active'] = cur.fetchone()[0]

    # 5. Replication slot lag
    cur.execute("""
        SELECT slot_name, active,
               pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS lag_bytes
        FROM pg_replication_slots
        ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC
    """)
    metrics['replication_slots'] = [
        {'slot': r[0], 'active': r[1], 'lag_bytes': r[2]}
        for r in cur.fetchall()
    ]

    cur.close()
    conn.close()

    metrics['timestamp'] = datetime.utcnow().isoformat()
    return metrics

if __name__ == '__main__':
    dsn = "host=localhost dbname=production user=monitoring"
    health = get_mvcc_health(dsn)
    print(json.dumps(health, indent=2, default=str))

    # Alert conditions
    if health.get('oldest_xmin', {}).get('xmin_age', 0) > 10_000_000:
        print("ALERT: Oldest xmin age exceeds 10M transactions!")
    if health.get('wraparound', {}).get('pct_to_wraparound', 0) > 50:
        print("CRITICAL: XID wraparound risk above 50%!")

Common Mistakes

Mistake 1: Disabling Autovacuum on "Important" Tables

What people do: Set autovacuum_enabled = false because "vacuum causes I/O spikes during peak hours."

Why it's wrong: Without autovacuum, dead tuples accumulate indefinitely. The table bloats, queries slow down, and eventually you face XID wraparound — which forces an emergency vacuum that's far more disruptive than regular autovacuum ever would be.

Correct approach: Tune autovacuum parameters (lower cost_delay, raise cost_limit) to make it run faster and less intrusively. Never disable it.

Mistake 2: Using VACUUM FULL as Regular Maintenance

What people do: Schedule nightly VACUUM FULL on all tables.

Why it's wrong: VACUUM FULL takes an AccessExclusiveLock, blocking all reads and writes for the entire duration (can be hours for large tables). It also doubles disk space temporarily (rewrites to a new file before deleting the old one).

Correct approach: Regular VACUUM for routine maintenance. Use pg_repack for online table compaction when bloat is severe. Reserve VACUUM FULL only for small tables during maintenance windows.

Mistake 3: Ignoring Replication Slot Lag

What people do: Create logical replication slots and forget to monitor them.

Why it's wrong: An inactive or lagging replication slot prevents VACUUM from reclaiming tuples that the slot's consumer hasn't yet processed. The slot's xmin or catalog_xmin holds back the global horizon indefinitely.

Correct approach: Monitor pg_replication_slots for lag. Set max_slot_wal_keep_size (PG 13+) to limit WAL retention. Drop abandoned slots promptly.

Mistake 4: Running Analytics on Primary with Long Transactions

What people do: Connect BI tools directly to primary and run multi-hour reports.

Why it's wrong: Long-running transactions hold a snapshot that prevents vacuum from advancing. Even a SELECT-only transaction in READ COMMITTED holds backend_xmin for the duration of each statement, but in REPEATABLE READ, it holds for the entire transaction.

Correct approach: Route analytics to streaming replicas. Set idle_in_transaction_session_timeout. Use statement_timeout for defense in depth.

Mistake 5: Not Setting fillfactor on High-Update Tables

What people do: Leave fillfactor at 100% (default) on tables with frequent updates.

Why it's wrong: Without reserved space on pages, HOT updates fail because the new tuple can't fit on the same page. Every update creates new index entries across all indexes — massive write amplification.

Correct approach: Set fillfactor to 70-80% on tables with frequent non-indexed column updates. Monitor HOT update ratio in pg_stat_user_tables.

Mistake 6: Assuming VACUUM Returns Space to the OS

What people do: Run VACUUM and expect df -h to show more free disk space.

Why it's wrong: Standard VACUUM only marks space as reusable within the table file. The file size stays the same. Only pages at the physical end of the file that become entirely empty are truncated (returned to OS).

Correct approach: Understand that VACUUM reclaims space for reuse by future INSERTs. If you need to actually shrink the file, use pg_repack or VACUUM FULL. Better yet, design with partitioning so you can DROP entire partitions.

Mistake 7: Confusing Serializable with SELECT FOR UPDATE

What people do: Use SERIALIZABLE isolation thinking it will prevent all race conditions like SELECT FOR UPDATE does.

Why it's wrong: SERIALIZABLE (SSI) detects conflicts retroactively and aborts transactions. It doesn't acquire locks proactively. If your application can't handle serialization failures and retry, you'll get random errors. Conversely, SELECT FOR UPDATE is a pessimistic lock that blocks rather than aborts.

Correct approach: Use SERIALIZABLE + retry logic for complex invariants. Use SELECT FOR UPDATE for simple "read-modify-write" patterns where you want blocking behavior.

When NOT to Use MVCC-Heavy Patterns

  • Counter tables with extreme contention — Use advisory locks or external counters (Redis) instead of UPDATE-heavy patterns.
  • Queue tables with high throughput — Consider SKIP LOCKED + DELETE patterns, or dedicated queue systems (SQS, Kafka).
  • Bulk ETL loads — Use COPY + TRUNCATE/partition swap instead of row-by-row UPDATEs that generate enormous dead tuple counts.
  • Append-only audit logs — INSERT-only tables don't generate dead tuples; MVCC overhead is minimal.

Follow-Up Questions

Q: How does PostgreSQL handle XID wraparound, and what happens if it fails?

PostgreSQL uses 32-bit XIDs with modular arithmetic — XID A is "in the past" relative to B if (B - A) < 2^31. To prevent a live XID from wrapping into the "future" zone, aggressive VACUUM freezes old tuples (replacing their xmin with FrozenTransactionId = 2). If a table's age(relfrozenxid) reaches autovacuum_freeze_max_age (default 200M), emergency autovacuum fires. If it reaches ~2 billion, PostgreSQL shuts down to prevent data corruption — the DBA must run vacuum in single-user mode. PostgreSQL 14+ is working toward 64-bit XIDs to eliminate this risk entirely.

Q: Explain the difference between VACUUM and VACUUM FREEZE.

VACUUM reclaims dead tuples and freezes tuples older than vacuum_freeze_min_age (50M transactions by default). VACUUM FREEZE sets vacuum_freeze_min_age = 0, forcing all tuples to be frozen regardless of age. This is useful before long periods of inactivity or when you want to guarantee no future wraparound vacuum on a static table.

Q: How do logical replication slots interact with VACUUM?

Logical replication slots maintain a catalog_xmin that prevents VACUUM from removing catalog tuples needed by the slot's decoder, and an xmin that holds back regular tuple cleanup. If a logical subscriber goes offline, its slot's xmin ages indefinitely, blocking vacuum on the publisher. Mitigations: max_slot_wal_keep_size, monitoring slot lag, and auto-drop of inactive slots (PG 16+ inactive_replication_slot_timeout).

Q: What is the "snapshot too old" error in PostgreSQL?

PostgreSQL 9.5+ introduced old_snapshot_threshold — if a snapshot is older than this setting, and the page it needs to read has been vacuumed since the snapshot was taken, PostgreSQL raises ERROR: snapshot too old rather than returning potentially incorrect results. This allows vacuum to proceed without being blocked by ancient snapshots, at the cost of aborting stale readers. Similar in concept to Oracle's ORA-01555.

Q: How does SSI handle read-only transactions?

In PostgreSQL's SSI implementation, transactions explicitly declared as READ ONLY with DEFERRABLE are guaranteed never to be aborted due to serialization failures. PostgreSQL may delay the start of such transactions until it can guarantee a safe snapshot. Read-only transactions that are not deferrable can still be aborted if they participate in a dangerous structure, but they don't acquire predicate locks on writes (only on reads).

Q: How does MVCC work with partitioned tables?

Each partition is an independent table with its own relfrozenxid, visibility map, and FSM. Autovacuum schedules partitions independently based on their individual dead tuple counts. A common pitfall: the parent table's relfrozenxid is the minimum across all partitions — one neglected partition can trigger wraparound alerts for the entire partitioned table. Each partition needs appropriate autovacuum tuning.

Q: What are "hint bits" and why do they matter for write amplification?

Hint bits are cached CLOG lookup results stored directly in the tuple header's t_infomask. The first reader of a tuple after commit/abort sets these bits, which dirties the page. In full_page_writes = on mode (the safe default), this dirty page generates a full-page WAL record on the next checkpoint. For read-heavy workloads hitting cold pages, this "hint bit write amplification" can significantly increase WAL volume. Mitigations: larger shared_buffers, wal_compression, and the wal_skip_threshold optimization.

Q: Compare MVCC garbage collection in PostgreSQL vs. CockroachDB.

CockroachDB uses an LSM-tree storage engine (Pebble, a RocksDB variant) where MVCC versions are stored as timestamped keys. GC happens during compaction — when SSTable files are merged, versions below the GC threshold (configurable per table with gc.ttlseconds) are dropped. This is more similar to Snowflake's retention approach than PostgreSQL's explicit VACUUM. The trade-off: compaction has its own I/O and CPU costs, but there's no equivalent to XID wraparound or the need for a separate vacuum process.

Summary

Key Takeaways

  • MVCC trades space for concurrency — readers never block writers by maintaining multiple row versions, but dead versions must be cleaned up.
  • PostgreSQL's implementation is append-only — updates create new heap tuples; old ones become dead. This differs from InnoDB/Oracle's in-place update with undo logs.
  • Visibility is determined by tuple metadata — xmin, xmax, infomask bits, and the reader's snapshot together decide which version is "live."
  • Isolation levels map to snapshot timing — Read Committed = per-statement, Repeatable Read = per-transaction, Serializable = per-transaction + predicate lock enforcement.
  • VACUUM is non-negotiable — Without it, tables bloat, performance degrades, and XID wraparound threatens data integrity. Tune it, monitor it, never disable it.
  • HOT updates are your best friend — Proper fillfactor and index design can eliminate 90%+ of index write amplification.
  • Monitor the xmin horizon — Long-running transactions and abandoned replication slots are the #1 cause of production MVCC issues.

  2. How it works — Tuple versioning, snapshots, visibility rules (60 seconds)
  3. Operational implications — VACUUM, bloat, wraparound (60 seconds)
  4. Production experience — A real incident you've handled (60 seconds)

"MVCC keeps old row versions so readers see a consistent snapshot without blocking writers; the cost is dead tuple accumulation that VACUUM must continuously reclaim."

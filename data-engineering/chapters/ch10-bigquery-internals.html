How Does BigQuery Execute SQL Differently from PostgreSQL?

Hard
BigQuery Dremel
Previous: Warehouse Design Next: Snowflake Internals

Interviewer Intent

When a FAANG interviewer asks "How does BigQuery execute SQL differently from PostgreSQL?", they are probing for multiple layers of understanding:

  • Distributed systems knowledge: Can you articulate how a massively parallel processing (MPP) engine differs from a single-node RDBMS at the architecture level?
  • Storage-compute separation: Do you understand why BigQuery can scale independently and what trade-offs that introduces?
  • Columnar vs row-based execution: Can you explain how Capacitor's columnar format changes I/O patterns, compression, and query planning?
  • Cost awareness: Do you understand the pricing model and how architectural decisions (partitioning, clustering, nested pruning) directly impact cost?
  • Production experience: Have you debugged real BigQuery performance issues, read execution plans, and optimized slot usage?
  • Trade-off articulation: Can you explain when PostgreSQL is actually better than BigQuery and vice versa?

This question separates candidates who have merely used BigQuery's SQL interface from those who understand the distributed execution engine underneath. A senior Data Engineer should be able to trace a query from submission through Dremel's execution tree to final result materialization.

Quick Answer

BigQuery is a serverless, columnar, massively parallel analytics engine built on Google's Dremel technology. Unlike PostgreSQL — a single-node, row-oriented OLTP database — BigQuery separates storage (Capacitor files on Colossus/GCS) from compute (dynamically allocated slots), executes queries via a multi-level serving tree (root → mixers → leaf nodes), and prices queries by bytes scanned rather than compute time. It has no indexes, no VACUUM, no connection limits, and no traditional query optimizer with cost-based index selection. Instead, it relies on columnar pruning, partitioning, clustering, and massive parallelism to achieve sub-minute latency on petabyte-scale datasets.

One-liner: PostgreSQL optimizes single-node execution with indexes and buffer pools; BigQuery optimizes distributed execution with columnar storage, slot parallelism, and shuffle-based data movement.

Serverless Architecture

BigQuery's serverless model is fundamentally different from PostgreSQL's process-per-connection architecture. Understanding this separation is critical for senior engineers.

Separation of Compute and Storage

In PostgreSQL, data files live on the same machine as the query executor. The buffer pool caches pages in shared memory, and sequential/random I/O patterns directly affect query latency. Scaling requires either vertical scaling (bigger machine) or read replicas.

BigQuery completely decouples these layers:

  • Storage layer: Data is stored in Capacitor columnar format on Google's distributed file system (Colossus). Storage is managed, replicated, and encrypted automatically. You pay for storage separately (~$0.02/GB/month for active, ~$0.01/GB/month for long-term).
  • Compute layer: Query execution uses dynamically allocated "slots" — units of computational capacity that combine CPU, memory, and network resources. Slots are drawn from a shared pool (on-demand) or reserved capacity (flat-rate).
  • Network layer: Jupiter network fabric provides petabit-scale bisection bandwidth between storage and compute, making remote storage access nearly as fast as local disk for sequential reads.

Slot-Based Execution

A "slot" in BigQuery is an abstraction over a unit of computational work. Each slot represents approximately 0.5 CPU core with associated memory. Key properties:

  • On-demand projects get up to 2,000 slots by default (burstable)
  • Flat-rate reservations guarantee dedicated slots (100+ slot increments)
  • Slots are allocated dynamically across query stages
  • A single query can use thousands of slots in parallel
  • Slots are stateless — they pull data from Colossus as needed

Multi-Tenancy

BigQuery serves thousands of projects simultaneously on shared infrastructure. This multi-tenant model introduces important behaviors:

  • Fair scheduling: On-demand queries share a slot pool. During peak usage, individual queries may receive fewer slots, causing slower execution but never failure.
  • Isolation via reservations: Flat-rate customers get guaranteed slot capacity isolated from other tenants. Queries within a reservation compete only with each other.
  • No "noisy neighbor" for storage: Since Colossus handles storage separately, one tenant's heavy writes don't affect another tenant's read performance.
  • Automatic scaling: Unlike PostgreSQL where you must provision for peak load, BigQuery automatically scales compute to match query complexity.

PostgreSQL contrast: PostgreSQL uses a process-per-connection model with shared buffers. Each connection consumes memory and a system process. Typical limits are 100-500 concurrent connections before requiring connection pooling (PgBouncer). There is no multi-tenancy — resource isolation requires separate database clusters.

Dremel Execution Tree

BigQuery's execution engine is derived from Google's Dremel paper (2010). Unlike PostgreSQL's single-process volcano-style iterator model, Dremel uses a multi-level serving tree that distributes work across thousands of nodes simultaneously.

Tree Structure

                    │  Root Server │  (Query coordination, final aggregation)
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐

Root Server

The root server is the entry point for query execution. Its responsibilities include:

  • Receiving the parsed and optimized query plan
  • Distributing work to mixer nodes
  • Performing final aggregation (e.g., final GROUP BY merge)
  • Applying final ORDER BY and LIMIT operations
  • Returning results to the client
  • Coordinating query cancellation and timeout

Mixer Nodes

Mixers serve as intermediate aggregation layers. In a typical query:

  • Partial aggregation: Leaf nodes compute local aggregates (e.g., partial SUM, partial COUNT). Mixers combine these partial results, reducing data volume before it reaches the root.
  • Multi-level fan-in: For extremely large queries, multiple mixer levels can exist, creating a deeper tree that handles higher cardinality aggregations efficiently.
  • Shuffle boundaries: Mixers handle data redistribution when operations require repartitioning (e.g., JOIN, GROUP BY on high-cardinality keys).

Leaf Nodes

Leaf nodes perform the bulk of computation:

  • Columnar scanning: Read only the required columns from Capacitor files on Colossus. A query selecting 3 columns from a 200-column table reads ~1.5% of the data.
  • Predicate pushdown: Filters are applied during the scan phase, eliminating rows before they enter memory. Capacitor metadata (min/max values, bloom filters) enables skipping entire file segments.
  • Local computation: Projections, expressions, and partial aggregations execute on the leaf before data is sent upstream.
  • Parallel execution: Thousands of leaf nodes process different partitions of the data simultaneously.

Multi-Level Aggregation Example

Consider a query: SELECT country, COUNT(*) FROM events GROUP BY country on a 10TB table:

  1. Leaf nodes (3,000+): Each scans a portion of the country column, computes a local hash map of {country → count}, and sends partial results upstream.
  2. Mixer nodes (50-100): Each receives partial maps from ~30-60 leaf nodes, merges them into larger partial maps, reducing total data from millions of entries to thousands.
  3. Root server: Merges the final ~50-100 partial maps into the complete result set (~200 countries).

This multi-level approach means the root never processes raw data — it only handles pre-aggregated results, keeping memory usage bounded regardless of input size.

PostgreSQL Contrast

PostgreSQL executes queries in a single process using the volcano iterator model. Each operator (SeqScan, HashJoin, Sort) pulls tuples from its child operator one at a time. Parallelism is limited to Parallel Seq Scan with a small number of workers (typically 2-8). There is no multi-level aggregation tree — a parallel aggregate uses a single Gather node that collects results from all workers.

Capacitor Storage Format

Capacitor is BigQuery's proprietary columnar storage format, evolved from the encoding described in the Dremel paper. It is conceptually similar to Apache Parquet but optimized for Google's infrastructure.

Columnar Layout

Unlike PostgreSQL's heap files where each page contains complete rows, Capacitor stores each column independently: 


PostgreSQL Heap Page:                  Capacitor File:
┌────────────────────────┐             ┌────────────────────┐
│ Row 1: [A1,B1,C1,...Z1]│             │ Column A: [A1,A2,A3...]│
│ Row 2: [A2,B2,C2,...Z2]│             │ Column B: [B1,B2,B3...]│
│ Row 3: [A3,B3,C3,...Z3]│             │ Column C: [C1,C2,C3...]│
│ ...                    │             │ ...                    │
└────────────────────────┘             │ Column Z: [Z1,Z2,Z3...]│
                                       └────────────────────────┘

Benefits of columnar storage for analytics:

  • I/O reduction: A query touching 5 of 200 columns reads only 2.5% of the stored data.
  • Better compression: Values in a single column share the same data type and often similar values, enabling 5-10x better compression than row-oriented storage.
  • Vectorized processing: Columnar data can be processed using SIMD instructions, operating on hundreds of values per CPU cycle.

Nested Encoding: Repetition and Definition Levels

BigQuery natively supports nested and repeated data (STRUCT, ARRAY) without requiring joins. Capacitor encodes this using the Dremel paper's repetition and definition level scheme:

  • Repetition level (r): Indicates which repeated field in the path has repeated to produce this value. A value of 0 means a new top-level record.
  • Definition level (d): Indicates how many optional/repeated fields in the path are actually defined (not NULL). This distinguishes between a NULL nested field vs a NULL leaf value. 

Schema: record { name (required), links { forward (repeated) } }

Data:
  Record 1: { name: "Alice", links: { forward: [10, 20] } }
  Record 2: { name: "Bob",   links: NULL }
  Record 3: { name: "Carol", links: { forward: [30] } }

Encoding of links.forward column:
  Value   r   d
  10      0   2    (new record, fully defined)
  20      1   2    (repeated forward, fully defined)
  NULL    0   0    (new record, links is NULL)
  30      0   2    (new record, fully defined)

This encoding allows BigQuery to store deeply nested JSON-like structures in columnar format without flattening, and to reconstruct nested objects efficiently during query execution.

Dictionary Encoding

Capacitor uses dictionary encoding for low-cardinality columns:

  • A dictionary maps unique values to integer IDs (e.g., "US" → 0, "UK" → 1, "DE" → 2).
  • The column data stores only the integer IDs, using minimal bits (e.g., 8 bits for up to 256 unique values).
  • Predicates can be evaluated directly on dictionary IDs without decoding string values.
  • For high-cardinality columns, Capacitor falls back to direct encoding with run-length or bit-packing optimizations.

File Metadata and Pruning

Each Capacitor file contains rich metadata that enables aggressive pruning:

  • Min/max statistics: Per-column, per-block min and max values allow the query engine to skip entire blocks that cannot satisfy a predicate.
  • Null counts: Quick determination of whether a column segment contains any non-null values.
  • Row counts: Used for optimizing COUNT(*) queries without reading data.
  • Bloom filters: Probabilistic membership tests that enable skipping blocks for equality predicates.

PostgreSQL contrast: PostgreSQL stores data in 8KB heap pages with optional TOAST for large values. It relies on indexes (B-tree, GIN, GiST) for selective access. Without indexes, it performs sequential scans reading all columns regardless of the query's SELECT list.

Shuffle Service

The shuffle is one of BigQuery's most critical differentiators from both PostgreSQL and other MPP databases. It enables large-scale data redistribution between query stages without writing to disk.

Jupiter Network Fabric

Google's Jupiter network provides over 1 Petabit/sec of bisection bandwidth within a datacenter. This means:

  • Any compute node can communicate with any other at near-local speeds.
  • Data movement between query stages does not require disk serialization as an intermediate step.
  • The network is non-blocking — thousands of simultaneous shuffles from different queries can proceed without congestion.

In-Memory Shuffle

BigQuery's shuffle service operates as a distributed in-memory buffer:

  1. Producer stage: Slots that finish computing their partition write shuffle output to the shuffle service's memory buffers, tagged with destination partition keys.
  2. Shuffle service: A distributed RAM-based storage layer that holds intermediate data. It automatically manages memory pressure and replication for fault tolerance.
  3. Consumer stage: Slots in the next query stage pull their assigned partitions from the shuffle service when they are ready to process. 

Query Stage 1 (Scan + Hash)          Query Stage 2 (Aggregate)
┌──────────────────────┐             ┌──────────────────────┐
│ Slot A: scan part 1  │──┐     ┌──▶│ Slot X: agg key=0-99 │
│ Slot B: scan part 2  │──┤     │   │ Slot Y: agg key=100+ │
│ Slot C: scan part 3  │──┤     │   └──────────────────────┘
└──────────────────────┘  │     │
                           ▼     │
                  ┌─────────────────┐
                  │  Shuffle Service │
                  │  (In-Memory)     │
                  │                   │
                  │  Partition 0-99 ──┼───▶ Slot X
                  │  Partition 100+ ──┼───▶ Slot Y
                  └─────────────────┘

No Disk Spill in Standard Path

Unlike Spark or Hadoop MapReduce, BigQuery's standard execution path does not spill shuffle data to disk:

  • The shuffle service has enough aggregate RAM to hold intermediate data for concurrent queries across the cluster.
  • If a query's shuffle volume is exceptionally large, BigQuery may use persistent shuffle (writing to Colossus), but this is rare and handled transparently.
  • This no-spill design means shuffle-heavy operations (large JOINs, high-cardinality GROUP BYs) complete much faster than equivalent disk-based shuffles.

Implications for Query Design

  • JOIN performance: Large hash joins that would be catastrophically slow in disk-based MPP systems are routine in BigQuery because shuffle data stays in RAM.
  • Skew handling: BigQuery automatically detects shuffle skew (one partition significantly larger than others) and can re-split hot partitions across multiple slots.
  • Pipeline overlap: Producer and consumer stages can overlap — consumers start pulling data as soon as producers begin writing, creating a streaming pipeline effect.

PostgreSQL contrast: PostgreSQL has no shuffle concept. For parallel queries, Hash Join uses shared memory hash tables. A parallel Gather node collects results from workers through shared memory queues. Cross-node data movement does not exist in single-node PostgreSQL. In Citus (distributed PostgreSQL), shuffles write to disk and are a major performance bottleneck.

Slot Scheduling

BigQuery's slot scheduler determines how computational resources are allocated to queries. Understanding slot behavior is essential for performance tuning and capacity planning.

How Slots Map to Query Stages

A single query is decomposed into multiple stages, and each stage can use a different number of slots:

  • Scan stages: Typically use the most slots because parallelism is limited only by the number of storage files to read. A scan of a large table might use 2,000+ slots.
  • Compute stages: Slot count depends on data volume and computational complexity. Aggregation stages may use fewer slots than scan stages if data has been significantly reduced.
  • Write stages: Usually the fewest slots, as the final result set is typically small. 

Query: SELECT country, SUM(revenue) FROM sales
       WHERE year = 2024 GROUP BY country ORDER BY 2 DESC LIMIT 10

Stage 1 (Scan + Filter):     2,000 slots → Read year column, filter, read revenue+country
Stage 2 (Partial Aggregate):   500 slots → Local GROUP BY per slot
Stage 3 (Shuffle + Merge):     100 slots → Global GROUP BY, sort, limit
Stage 4 (Write):                 1 slot  → Write final 10 rows to result buffer

Fair Scheduling

When multiple queries compete for the same slot pool, BigQuery uses fair scheduling:

  • On-demand: All queries in a project share a burst pool. During contention, slots are divided roughly equally among active queries. A single large query cannot starve smaller ones.
  • Reservations: Queries within a reservation share that reservation's guaranteed slots. An admin can create multiple reservations with different slot counts for different workloads (e.g., ETL vs interactive analytics).
  • Priority tiers: Within a reservation, assignments can have priority (INTERACTIVE vs BATCH). INTERACTIVE queries get preferential slot access; BATCH queries use idle slots and can be preempted.

Reservations vs On-Demand

Aspect On-Demand Flat-Rate (Reservations)
Pricing $6.25 per TB scanned ~$2,000/month per 100 slots
Slot availability Best-effort, burstable Guaranteed allocation
Cost predictability Variable (data-dependent) Fixed monthly cost
Concurrency Throttled under load Controlled by reservation size
Best for Ad-hoc queries, low volume Predictable workloads, high volume
Idle cost $0 when not querying Paying for reserved slots 24/7

Slot Utilization Monitoring

Senior engineers should monitor slot utilization to right-size reservations:

  • INFORMATION_SCHEMA.JOBS shows total_slot_ms per query — actual slot-milliseconds consumed.
  • Peak slot usage = total_slot_ms / elapsed_ms gives average parallelism during execution.
  • Reservation admin views show slot utilization over time, helping identify over-provisioning or under-provisioning.
  • A query's execution plan shows per-stage slot counts and wait times, indicating contention.

PostgreSQL contrast: PostgreSQL has no concept of slots. Resource management uses max_connections, max_parallel_workers, and work_mem settings. There is no dynamic resource allocation — you must pre-provision for peak load. Resource groups (available in some forks like Greenplum) provide limited query-level resource isolation.

Query Stages & Execution

BigQuery decomposes every query into a directed acyclic graph (DAG) of stages. Understanding stages is essential for reading execution plans and diagnosing performance issues.

Reading Stages

The first stages in any query involve reading data from Colossus:

  • Column selection: Only columns referenced in SELECT, WHERE, JOIN, GROUP BY, and ORDER BY clauses are read.
  • Partition pruning: If the table is partitioned and the query filters on the partition column, only relevant partitions are scanned.
  • Cluster pruning: For clustered tables, block-level metadata is used to skip blocks where the clustered column's range doesn't match the filter.
  • Predicate pushdown: Simple predicates (equality, range comparisons) are pushed into the storage layer and evaluated during decompression.

Compute Stages

After data is read, compute stages perform transformations:

  • Filter evaluation: Complex predicates that cannot be pushed to storage (e.g., UDF-based filters, cross-column comparisons).
  • Projection & expression evaluation: Computing derived columns, type casts, and function applications.
  • Aggregation: Partial and full GROUP BY operations, window functions, and DISTINCT processing.
  • Join execution: Hash joins (broadcast or shuffle-based), with the smaller table typically broadcast to all slots processing the larger table.
  • Sort operations: ORDER BY processing, typically in the final stages after data volume has been reduced.

Write Stages

The final stage writes results:

  • Result table: For CREATE TABLE AS SELECT or INSERT INTO, data is written back to Capacitor files on Colossus.
  • Temporary result: For interactive queries, results are written to a temporary table cached for 24 hours.
  • Streaming buffer: For DML operations, mutations go through a streaming buffer before being merged into base Capacitor files.

Parallel Pipeline Execution

Unlike traditional batch processing where stages execute sequentially, BigQuery pipelines stages: 


Time ──────────────────────────────────────────────────▶

Stage 1 (Scan):    ████████████████░░░░░░░░░░░░░░░░░░░
Stage 2 (Agg):    ░░░░░░░████████████████░░░░░░░░░░░░
Stage 3 (Join):    ░░░░░░░░░░░░░████████████████░░░░░░
Stage 4 (Write):   ░░░░░░░░░░░░░░░░░░░░░░░██████████░

                   └─── Overlap! Stages don't wait for
                        full completion before starting ──┘

This pipelining means:

  • Stage 2 begins processing as soon as Stage 1 starts producing output via the shuffle service.
  • Total query time is less than the sum of individual stage times.
  • Memory pressure is reduced because not all intermediate data needs to be materialized simultaneously.

Execution Plan Reading

BigQuery's execution plan (visible in the Console UI or via INFORMATION_SCHEMA.JOBS) shows:

  • Stage ID: Sequential identifier for each stage
  • Input/Output rows: How many rows entered and left each stage
  • Slot time: Total compute time consumed (slot-milliseconds)
  • Wait time: Time slots spent waiting (indicates contention)
  • Shuffle bytes: Data volume sent between stages
  • Parallelism: Number of workers active in each stage

PostgreSQL contrast: PostgreSQL's EXPLAIN ANALYZE shows a single execution tree with per-operator timings. There are no stages, no shuffle, and parallelism is represented by Gather/Gather Merge nodes. The plan is a tree (not a DAG) and executes in a pull-based iterator model rather than a push-based pipeline.

Nested & Repeated Data

BigQuery's first-class support for nested and repeated data is a key differentiator from PostgreSQL. It fundamentally changes data modeling patterns for analytics workloads.

STRUCT Type

A STRUCT groups related fields into a single column: 

-- Table definition with nested STRUCTs
CREATE TABLE analytics.events (
  event_id STRING,
  event_time TIMESTAMP,
  user STRUCT<
    id STRING,
    name STRING,
    geo STRUCT<
      country STRING,
      city STRING,
      lat FLOAT64,
      lng FLOAT64
    >
  >,
  device STRUCT<
    type STRING,
    os STRING,
    browser STRING
  >,
  page STRUCT<
    url STRING,
    title STRING,
    referrer STRING
  >
);

-- Querying nested fields
SELECT
  user.geo.country,
  COUNT(*) as event_count
FROM analytics.events
WHERE device.type = 'mobile'
GROUP BY user.geo.country;

ARRAY Type (Repeated Fields)

Arrays allow one-to-many relationships within a single row, eliminating the need for joins: 

-- Table with repeated fields
CREATE TABLE analytics.orders (
  order_id STRING,
  customer_id STRING,
  order_date DATE,
  items ARRAY<STRUCT<
    product_id STRING,
    product_name STRING,
    quantity INT64,
    unit_price NUMERIC,
    tags ARRAY<STRING>
  >>,
  shipping STRUCT<
    address STRING,
    city STRING,
    tracking_numbers ARRAY<STRING>
  >
);

-- Querying arrays with UNNEST
SELECT
  o.order_id,
  item.product_name,
  item.quantity * item.unit_price AS line_total
FROM analytics.orders o,
  UNNEST(o.items) AS item
WHERE item.quantity > 5;

UNNEST Operations

UNNEST flattens an array into rows, enabling standard SQL operations on repeated data:

  • Cross join UNNEST: Produces one row per array element, duplicating parent fields. Used for filtering or aggregating within arrays.
  • Correlated UNNEST: Used in WHERE EXISTS or subqueries to filter parent rows based on array contents.
  • UNNEST with OFFSET: Provides positional index of array elements for order-dependent operations. 
-- Find orders containing a specific product
SELECT order_id, order_date
FROM analytics.orders
WHERE EXISTS (
  SELECT 1 FROM UNNEST(items) AS item
  WHERE item.product_id = 'SKU-12345'
);

-- Aggregate within arrays
SELECT
  order_id,
  (SELECT SUM(i.quantity * i.unit_price) FROM UNNEST(items) i) AS order_total,
  ARRAY_LENGTH(items) AS item_count
FROM analytics.orders;

Nested Pruning in Capacitor

This is where BigQuery's columnar storage shines with nested data:

  • Each leaf field in a nested schema is stored as a separate column in Capacitor. user.geo.country is an independent column from user.geo.city.
  • Querying SELECT user.geo.country FROM events reads ONLY the user.geo.country column — not the entire user struct.
  • This nested pruning means wide, deeply nested schemas have minimal cost when queries touch few fields.
  • Repeated fields (arrays) use repetition levels to reconstruct the array structure without storing redundant parent data.
Critical insight: Using SELECT user.* on a struct with 50 sub-fields reads all 50 columns. Using SELECT user.geo.country reads only 1 column. This difference can mean scanning 200MB vs 10GB — directly affecting both performance and cost.

PostgreSQL Contrast

PostgreSQL supports JSONB for semi-structured data, but with significant differences:

  • JSONB is stored as a single binary blob per row — there is no columnar sub-field access. Accessing one key reads the entire JSONB value.
  • PostgreSQL arrays exist but lack BigQuery's deep integration with the columnar storage engine.
  • GIN indexes on JSONB provide fast lookups but don't offer the I/O savings of columnar nested pruning.
  • In PostgreSQL, the equivalent of BigQuery's nested modeling typically requires normalized tables with JOINs — adding complexity and I/O.

BigQuery Cost Model

Understanding BigQuery's cost model is essential for senior engineers because architectural decisions directly translate to dollar costs. This is fundamentally different from PostgreSQL where cost is fixed (hardware + licenses) regardless of query patterns.

Bytes Scanned Pricing (On-Demand)

In on-demand mode, BigQuery charges based on the amount of data processed (bytes read from storage):

  • Rate: $6.25 per TB scanned (as of 2024)
  • Minimum charge: 10 MB per query (even if less is read)
  • Free tier: First 1 TB of processing per month is free
  • Cached results: Queries that hit the 24-hour cache cost $0
  • DML: INSERT, UPDATE, DELETE, MERGE charge for bytes processed

What Counts as "Bytes Scanned"

  • Column selection: Only columns in your query are counted. SELECT 2 of 100 columns = ~2% of table size billed.
  • Partition pruning: Filtered partitions are not scanned and not billed.
  • Clustering: Blocks that don't match cluster key filters are skipped and not billed.
  • Compressed size: You are billed on uncompressed logical bytes, NOT the physical compressed size. A column compressed 10:1 still bills for the full uncompressed size.

LIMIT Does NOT Reduce Cost

Critical misconception: Adding LIMIT 10 to a query does NOT reduce bytes scanned. BigQuery must scan all matching data, perform the full computation, and then return only 10 rows. The scan cost is identical with or without LIMIT. 
-- These two queries cost EXACTLY the same:
SELECT * FROM bigdata.events;                    -- Scans 5 TB
SELECT * FROM bigdata.events LIMIT 10;           -- STILL scans 5 TB

-- To actually reduce cost, use partition/cluster filters:
SELECT * FROM bigdata.events
WHERE event_date = '2024-01-15'                  -- Partition prune: scans 50 GB
  AND user_country = 'US'                        -- Cluster prune: scans 5 GB
LIMIT 10;

Flat-Rate vs On-Demand Decision Framework

Factor Choose On-Demand Choose Flat-Rate
Monthly scan volume < 50 TB/month > 50 TB/month
Query patterns Sporadic, ad-hoc Continuous ETL pipelines
Budget requirement Variable OK Fixed budget required
Performance SLA Best-effort acceptable Guaranteed slots needed
Concurrency Low (< 20 concurrent) High (50+ concurrent)

Cost Control Strategies

  1. Partitioning: Time-based partitioning on event date means queries with date filters only scan relevant days. A 3-year table filtered to 1 day scans ~0.09% of total data.
  2. Clustering: Within each partition, data is sorted by cluster key columns. Filters on these columns skip entire blocks, reducing scan by 50-90%.
  3. Column projection: Select only needed columns. SELECT * on a 200-column table is 100x more expensive than selecting 2 columns.
  4. Materialized views: Pre-compute expensive aggregations. BigQuery automatically routes queries to MVs when applicable.
  5. Query result caching: Identical queries within 24 hours return cached results at $0 cost (unless underlying data changed).
  6. Custom cost controls: Set per-user, per-project daily byte quotas. Queries exceeding the limit are rejected. 
-- Estimate query cost before running (dry run)
-- In bq CLI:
-- bq query --dry_run --use_legacy_sql=false 'SELECT ...'

-- Check bytes billed after execution
SELECT
  job_id,
  total_bytes_billed,
  total_bytes_billed / POW(1024, 4) * 6.25 AS estimated_cost_usd
FROM `region-us`.INFORMATION_SCHEMA.JOBS
WHERE creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR)
ORDER BY total_bytes_billed DESC
LIMIT 20;

PostgreSQL Contrast

PostgreSQL has no per-query cost in monetary terms. You pay for the server (or managed service like RDS/Aurora) regardless of query patterns. This means:

  • A bad query doesn't cost more money — it costs time and blocks other queries
  • There's no financial incentive to select fewer columns (though I/O still matters)
  • Capacity planning is based on peak concurrent load, not data volume scanned
  • Cost optimization focuses on right-sizing instances, not query rewriting

Key Differences from PostgreSQL

This section provides a comprehensive comparison for engineers transitioning between the two systems or designing architectures that use both.

No Indexes

BigQuery has no user-created indexes of any kind — no B-trees, no hash indexes, no GIN/GiST indexes. Instead, it relies on:

  • Partition pruning: Coarse-grained data skipping based on partition column values
  • Cluster block pruning: Fine-grained skipping based on sorted block metadata
  • Capacitor metadata: Per-column min/max, bloom filters, null counts
  • Brute-force parallelism: Scanning 1TB across 2,000 slots takes seconds

This design works because BigQuery's workload is full-table analytics where indexes would be counterproductive (reading an index for a query returning 30% of rows is slower than a sequential scan).

No VACUUM

PostgreSQL requires VACUUM to reclaim dead tuple space from MVCC updates and prevent transaction ID wraparound. BigQuery has no equivalent because:

  • Immutable storage: Capacitor files are immutable. Updates create new files; old versions are garbage collected automatically.
  • No MVCC overhead: BigQuery uses snapshot isolation at the storage layer without per-row version tracking.
  • Automatic compaction: Background processes merge small files and remove obsolete data without user intervention.
  • No bloat: Table size reflects actual live data, not dead rows awaiting vacuum.

No Connection Limits

PostgreSQL's process-per-connection model limits concurrent connections (typically 100-500 before requiring PgBouncer). BigQuery:

  • Is API-based — no persistent connections to manage
  • Handles thousands of concurrent queries across a project
  • Has no connection pooling requirement
  • Rate-limits at the API level (100 concurrent queries default) rather than at connection level

Different Optimization Model

Aspect PostgreSQL BigQuery
Query planner Cost-based optimizer with statistics Rule-based + dynamic re-optimization during execution
Plan caching Prepared statements cache plans No plan caching; each query re-optimized
Join strategy selection Nested loop, hash, merge based on row estimates Broadcast or shuffle hash join based on table size
Statistics pg_statistic, manual ANALYZE Automatic, continuously updated column statistics
Hints Not native (pg_hint_plan extension) No hints — system decides execution strategy
Execution model Pull-based (volcano iterator) Push-based (DAG of stages)
Adaptive execution No (plan fixed at execution start) Yes (can re-partition mid-query on skew detection)
Point lookups Sub-millisecond with index ~1-2 second minimum (query overhead)

Transaction Model

  • PostgreSQL: Full ACID transactions with row-level locking, serializable isolation, savepoints, and multi-statement transactions spanning minutes or hours.
  • BigQuery: Single-statement transactions for DML. MERGE is atomic. Multi-statement transactions exist but are limited (max 100 DML statements, 20-minute timeout). No row-level locking — uses table-level snapshot isolation.

When PostgreSQL Wins

  • Point lookups and OLTP workloads (sub-millisecond responses)
  • High-frequency small writes (thousands of individual INSERTs/sec)
  • Complex multi-table transactions with referential integrity
  • Low-latency requirement (< 100ms query response)
  • Small dataset analytics (< 100GB) where BigQuery's overhead dominates
  • Local development and testing without cloud dependency

When BigQuery Wins

  • Analytical queries on TB-PB scale data
  • Serverless operation with zero maintenance
  • Ad-hoc exploration of large datasets by non-DBA analysts
  • Semi-structured/nested data at scale (avoiding complex star schemas)
  • Variable workloads where pay-per-query is more efficient than provisioned capacity
  • Cross-dataset queries joining multiple data sources

Production Incident: Nested Data Scan Explosion

This real-world scenario demonstrates how understanding BigQuery internals prevents costly mistakes. It illustrates the difference between scanning 2TB (wrong approach) vs 20GB (correct approach) for the same analytical result.

Context

An e-commerce company stores clickstream events in BigQuery with the following schema: 

CREATE TABLE analytics.clickstream (
  event_id STRING,
  event_timestamp TIMESTAMP,
  session_id STRING,
  user STRUCT<
    user_id STRING,
    account_type STRING,
    preferences STRUCT<
      language STRING,
      currency STRING,
      notification_settings ARRAY<STRUCT<
        channel STRING,
        enabled BOOL,
        frequency STRING
      >>
    >,
    purchase_history ARRAY<STRUCT<
      order_id STRING,
      amount NUMERIC,
      items ARRAY<STRUCT<
        sku STRING,
        name STRING,
        price NUMERIC,
        attributes JSON
      >>
    >>
  >,
  page STRUCT<
    url STRING,
    title STRING,
    content_hash STRING,
    metadata JSON
  >,
  device STRUCT<
    fingerprint STRING,
    user_agent STRING,
    screen_resolution STRING,
    installed_plugins ARRAY<STRING>
  >
)
PARTITION BY DATE(event_timestamp)
CLUSTER BY session_id;

The table contains 2 years of data, ~500 billion rows, totaling 80TB uncompressed. The deeply nested user.purchase_history field alone accounts for 40TB due to repeated item arrays with JSON attributes.

The Incident: 2TB Query

A data analyst needed to find the number of mobile sessions per country for the last 30 days. They wrote: 

-- BAD QUERY: Scans 2TB, costs ~$12.50
SELECT
  user.preferences.language AS country_proxy,
  COUNT(DISTINCT session_id) AS unique_sessions
FROM analytics.clickstream
WHERE
  DATE(event_timestamp) BETWEEN '2024-06-01' AND '2024-06-30'
  AND device.type = 'mobile'  -- ERROR: device.type doesn't exist!
GROUP BY 1;

The query failed because device.type doesn't exist in the schema. The analyst then tried: 

-- WORSE QUERY: Scans 2TB because of SELECT user.*
SELECT
  user.*,
  session_id,
  device.user_agent
FROM analytics.clickstream
WHERE
  DATE(event_timestamp) BETWEEN '2024-06-01' AND '2024-06-30'
  AND device.user_agent LIKE '%Mobile%'
LIMIT 100;

Why this scans 2TB:

  • user.* expands to ALL nested fields within the user struct, including the massive purchase_history array with its nested items and JSON attributes.
  • The 30-day partition filter reduces the scan from 80TB to ~3.3TB, but reading all user sub-columns still processes 2TB of that partition range.
  • LIMIT 100 does NOT reduce bytes scanned — BigQuery still reads the full 2TB and returns only 100 rows.
  • This single query cost ~$12.50 and completed in 45 seconds.

The Fix: 20GB Query with Nested Pruning

-- GOOD QUERY: Scans only 20GB, costs ~$0.12
SELECT
  user.preferences.language AS user_language,
  COUNT(DISTINCT session_id) AS unique_sessions
FROM analytics.clickstream
WHERE
  DATE(event_timestamp) BETWEEN '2024-06-01' AND '2024-06-30'
  AND REGEXP_CONTAINS(device.user_agent, r'(?i)mobile|android|iphone')
GROUP BY 1
ORDER BY unique_sessions DESC;

Why this scans only 20GB:

  • Partition pruning narrows to 30 days of data (~3.3TB total).
  • Column selection reads only 3 leaf columns: user.preferences.language, session_id, and device.user_agent — skipping the 40TB purchase_history entirely.
  • These 3 columns in the 30-day partition total ~20GB uncompressed.
  • Cost reduction: 100x (from $12.50 to $0.12).
  • Performance improvement: from 45 seconds to 3 seconds.

Root Cause Analysis

Issue Impact Fix
SELECT user.* on deeply nested struct Reads all 15+ sub-columns including arrays Select only specific leaf fields needed
LIMIT 100 used as cost control Zero cost reduction, false sense of safety Use partition filters and column selection
No dry-run before execution No advance warning of 2TB scan Always run dry-run for ad-hoc queries
Schema exploration via SELECT * Extremely expensive on wide nested tables Use INFORMATION_SCHEMA.COLUMNS or bq show

Prevention Measures Implemented

  1. Custom quota: Set per-user daily scan limit to 5TB, rejecting queries that would exceed this.
  2. Authorized views: Created flattened views that expose only commonly-needed columns, preventing accidental SELECT * on the raw table.
  3. Query template library: Provided pre-written queries for common analyses with correct column selection.
  4. Monitoring alert: Set up alerts on INFORMATION_SCHEMA.JOBS for queries scanning > 500GB.
  5. Training: Documented that SELECT struct.* reads all sub-columns and that LIMIT doesn't reduce cost.

Slot Analysis for Capacity Planning

-- Calculate required flat-rate slots based on historical usage
WITH hourly_usage AS (
  SELECT
    TIMESTAMP_TRUNC(creation_time, HOUR) AS hour,
    SUM(total_slot_ms) / (3600 * 1000) AS avg_slots
  FROM `region-us`.INFORMATION_SCHEMA.JOBS
  WHERE
    creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
    AND job_type = 'QUERY'
    AND state = 'DONE'
  GROUP BY 1
)
SELECT
  -- P50 = baseline reservation
  APPROX_QUANTILES(avg_slots, 100)[OFFSET(50)] AS p50_slots,
  -- P90 = recommended reservation
  APPROX_QUANTILES(avg_slots, 100)[OFFSET(90)] AS p90_slots,
  -- P99 = peak (might need autoscaling)
  APPROX_QUANTILES(avg_slots, 100)[OFFSET(99)] AS p99_slots,
  MAX(avg_slots) AS max_slots,
  -- Cost comparison
  APPROX_QUANTILES(avg_slots, 100)[OFFSET(90)] * 20 AS monthly_cost_at_p90
FROM hourly_usage;

-- Per-project slot consumption (for chargeback)

  SUM(total_slot_ms) / 1000 / 3600 AS total_slot_hours,

Common Mistakes

These are mistakes frequently made by engineers transitioning from PostgreSQL to BigQuery, or by those who don't understand the execution model.

1. Using SELECT * on Nested Tables

  • Mistake: SELECT * FROM events LIMIT 10 for "quick exploration"
  • Impact: Reads every column including deeply nested arrays, costing 10-100x more than necessary
  • Fix: Use SELECT column_name FROM INFORMATION_SCHEMA.COLUMNS WHERE table_name = 'events' to explore schema, then select specific fields

2. Relying on LIMIT for Cost Control

  • Mistake: Adding LIMIT 100 thinking it reduces bytes scanned
  • Impact: Full table scan occurs regardless; LIMIT only truncates output
  • Fix: Use partition filters, column selection, and dry runs to control cost

3. Not Using Partition Filters

  • Mistake: Querying a partitioned table without filtering on the partition column
  • Impact: Full table scan across all partitions (potentially petabytes)
  • Fix: Enable require_partition_filter on large tables; always include partition predicates
-- Enable mandatory partition filtering
ALTER TABLE analytics.events
SET OPTIONS (require_partition_filter = TRUE);

4. Treating BigQuery Like an OLTP Database

  • Mistake: Running thousands of small queries per minute, single-row lookups
  • Impact: Each query has 1-2 seconds of scheduling overhead; API rate limits hit quickly
  • Fix: Batch small lookups into single queries; use Bigtable or Firestore for point lookups

5. Ignoring Clustering Opportunities

  • Mistake: Partitioning a table but not clustering on frequently-filtered columns
  • Impact: Queries that filter on non-partition columns still scan entire partitions
  • Fix: Cluster on columns commonly used in WHERE/JOIN clauses (up to 4 columns)

6. Cross-Join from Improper UNNEST

  • Mistake: Using CROSS JOIN UNNEST(array1), UNNEST(array2) without correlation
  • Impact: Cartesian product between arrays; 100 x 100 elements = 10,000 rows per input row
  • Fix: Use correlated subqueries or ensure UNNEST operations are properly scoped
-- BAD: Cartesian product between two arrays
SELECT *
FROM my_table,
  UNNEST(array_a) AS a,
  UNNEST(array_b) AS b;

-- GOOD: Separate subqueries for each array
SELECT
  (SELECT SUM(a) FROM UNNEST(array_a) a) AS sum_a,
  (SELECT SUM(b) FROM UNNEST(array_b) b) AS sum_b
FROM my_table;

7. Not Understanding Slot Contention

  • Mistake: Running 50 complex queries simultaneously on on-demand pricing
  • Impact: Each query gets fewer slots, dramatically increasing wall-clock time
  • Fix: Stagger heavy queries; use reservations for production pipelines; monitor slot utilization

8. Storing Data Inefficiently

  • Mistake: Storing high-cardinality STRING columns that could be INT64; using JSON strings instead of native STRUCT/ARRAY
  • Impact: Higher storage costs, worse compression, slower queries
  • Fix: Use appropriate types; leverage native nested types instead of JSON strings; consider dictionary-friendly cardinality

9. Not Using Approximate Functions

  • Mistake: Using COUNT(DISTINCT x) on high-cardinality columns across billions of rows
  • Impact: Memory-intensive exact computation; possible slot OOM on extreme cardinality
  • Fix: Use APPROX_COUNT_DISTINCT(x) for dashboards where ±1% error is acceptable

10. Joining Large Tables Without Filtering First

  • Mistake: SELECT * FROM table_a JOIN table_b ON ... without WHERE clauses on either table
  • Impact: Massive shuffle volume; both tables fully scanned; expensive and slow
  • Fix: Apply filters (especially partition filters) before the JOIN; reduce data volume early

Trade-offs

Every architectural decision in BigQuery represents a trade-off. Senior engineers should articulate these clearly in interviews.

Serverless vs Self-Managed

Benefit Trade-off
Zero operational overhead No control over execution environment, versions, or patches
Automatic scaling Cannot guarantee latency SLAs for specific queries
Pay-per-query flexibility Unpredictable costs if queries are not carefully controlled
Multi-tenant efficiency Noisy neighbor effects on on-demand tier during peak

Columnar vs Row Storage

Benefit Trade-off
Excellent compression (5-10x) Point lookups require reading and reconstructing from columns
Scan only needed columns Writing individual rows is expensive (requires file rewrite)
Vectorized processing Random access patterns perform poorly
Efficient for analytics Inefficient for OLTP (single-row read/write)

No Indexes vs Index-Based Access

Benefit Trade-off
No index maintenance overhead Cannot achieve sub-millisecond point lookups
No index selection decisions Every query pays scan cost proportional to data size
Write performance is predictable Read performance depends on parallelism, not data structure
Simpler data management Must rely on partitioning/clustering for selective access

Nested Data vs Normalized Schema

Benefit Trade-off
No JOINs needed for related data Data duplication across records (storage cost)
Single-table queries are simpler Updates to nested data require full row rewrite
Better scan locality Deeply nested schemas are harder to understand and query
Natural fit for event data SELECT * becomes dangerous on wide nested tables

On-Demand vs Flat-Rate Pricing

Benefit Trade-off
On-demand: pay only when querying Costs spike unpredictably with data growth or new analysts
Flat-rate: predictable budget Paying for idle slots during off-hours
On-demand: no capacity planning Burst slot availability not guaranteed
Flat-rate: guaranteed performance Must right-size reservations or waste money

Separation of Storage and Compute

Benefit Trade-off
Scale compute independently of data size Network latency between compute and storage (mitigated by Jupiter)
Storage never limits query concurrency Cannot exploit data locality like co-located systems
Multiple compute engines can read same data Cold start latency for first query (slot allocation)
Storage costs scale linearly, not with compute Shuffle-heavy queries still need network bandwidth

Follow-up Questions

These are common follow-up questions an interviewer might ask after your initial answer, along with concise response frameworks.

Q: "How would you debug a slow BigQuery query?"

  1. Check the execution plan for stage-level timings and shuffle volumes
  2. Look at bytes scanned — is partition/cluster pruning working?
  3. Check slot utilization — is the query slot-starved (high wait time)?
  4. Look for data skew — one stage taking 10x longer than others
  5. Check for anti-patterns: SELECT *, missing partition filters, cross joins from UNNEST
  6. Compare total_slot_ms vs wall clock time to assess parallelism efficiency

Q: "When would you NOT use BigQuery?"

  • Low-latency point lookups (< 100ms) — use Bigtable or Spanner
  • High-frequency small writes (10K+ individual inserts/sec) — use Pub/Sub → streaming
  • Complex OLTP transactions — use Cloud SQL or Spanner
  • Small datasets (< 1GB) where query overhead dominates
  • Workloads requiring exact row-level locking semantics
  • Real-time serving layer for web applications

Q: "How does BigQuery handle data skew in JOINs?"

  • Automatic skew detection during shuffle phase
  • Hot partitions are dynamically re-split across additional slots
  • For known skew, manual mitigation: filter out hot keys and process separately
  • Broadcast join for small tables (avoids shuffle entirely)
  • Approximate aggregate functions reduce memory pressure from skewed groups

Q: "Explain BigQuery's consistency model"

  • Strongly consistent for all read-after-write operations within the same region
  • DML operations are atomic at the statement level
  • Streaming inserts have a brief eventual consistency window (seconds)
  • Table snapshots provide point-in-time reads (time travel up to 7 days)
  • No dirty reads — snapshot isolation for concurrent queries

Q: "How would you migrate a PostgreSQL workload to BigQuery?"

  1. Schema redesign: Denormalize star schemas into nested tables where beneficial
  2. Remove index dependencies: Replace indexed lookup patterns with partition/cluster design
  3. Rewrite procedural logic: Convert stored procedures to BigQuery scripting or Dataflow pipelines
  4. Rethink ETL: Move from row-at-a-time processing to batch/streaming ingestion
  5. Query rewrite: Replace PostgreSQL-specific functions, adapt UNNEST patterns for arrays
  6. Cost modeling: Profile query patterns to choose on-demand vs flat-rate

Q: "What's the difference between BigQuery and Snowflake architecturally?"

  • Both separate storage and compute, but Snowflake uses virtual warehouses (user-managed clusters) vs BigQuery's fully serverless slots
  • Snowflake has explicit cluster suspend/resume; BigQuery is always-on with per-query billing
  • BigQuery's shuffle is in-memory (Jupiter); Snowflake uses remote disk for large shuffles
  • BigQuery natively supports nested/repeated data; Snowflake uses VARIANT (semi-structured)
  • BigQuery's pricing is per-byte-scanned or per-slot-second; Snowflake is per-credit (time-based)

Q: "How does BigQuery achieve fault tolerance?"

  • Data is stored with 3+ replicas on Colossus — no data loss from node failures
  • Query execution: if a slot fails, the stage is re-executed on a different slot
  • Shuffle service holds replicated copies of intermediate data
  • No single point of failure — root server, mixers, and leaves are all replaceable
  • Long-running queries checkpoint progress; partial re-execution on failure

Summary

BigQuery and PostgreSQL represent fundamentally different philosophies in database design. Here are the key takeaways for your interview:

Architecture

  • BigQuery separates storage (Colossus) from compute (slots); PostgreSQL couples them on a single node
  • BigQuery uses a multi-level Dremel tree for massively parallel execution; PostgreSQL uses single-process volcano iteration with limited parallel workers
  • BigQuery's shuffle service enables in-memory data redistribution at petabit scale; PostgreSQL has no equivalent

Storage

  • BigQuery uses Capacitor columnar format with nested encoding (repetition/definition levels); PostgreSQL uses row-oriented heap files
  • BigQuery has no indexes — relies on partitioning, clustering, and parallel scan; PostgreSQL requires indexes for efficient selective access
  • BigQuery storage is immutable (no VACUUM needed); PostgreSQL requires regular VACUUM for MVCC cleanup

Execution

  • BigQuery decomposes queries into a DAG of stages with shuffle boundaries; PostgreSQL executes a single operator tree
  • BigQuery dynamically allocates thousands of slots per query; PostgreSQL is limited to configured parallel workers (typically 2-8)
  • BigQuery pipelines stages for overlap; PostgreSQL processes operators in a strict pull-based order

Cost & Operations

  • BigQuery charges per byte scanned (on-demand) or per slot reserved (flat-rate); PostgreSQL has fixed infrastructure cost
  • BigQuery is fully serverless with zero maintenance; PostgreSQL requires tuning, vacuuming, connection management, and capacity planning
  • BigQuery cost optimization = fewer bytes scanned (columns, partitions, clusters); PostgreSQL cost optimization = right-sized instances and proper indexing

When to Choose Each

  • BigQuery: Analytics on TB-PB data, serverless operation, variable workloads, nested data, ad-hoc exploration
  • PostgreSQL: OLTP, sub-millisecond lookups, complex transactions, small-medium datasets, local development
  • Both together: PostgreSQL as operational DB → Change Data Capture → BigQuery as analytical warehouse (common FAANG pattern)
Interview tip: Demonstrate that you understand WHY BigQuery makes these architectural choices (massive parallelism over single-node optimization), not just WHAT the differences are. Connect each design decision to the workload it serves: BigQuery trades point-lookup latency for aggregate-query throughput at any scale.

Why Does a Query Suddenly Become Slow After Months of Working Correctly?

Statistics Drift Plan Cache

Interviewer Intent

Why interviewers ask this question

This question is a litmus test for production maturity. It separates engineers who have lived through performance regressions from those who only write queries in development. The interviewer wants to verify:

  • Root-cause thinking — Can you enumerate the reasons a stable query degrades, rather than just saying "the data grew"?
  • Optimizer internals — Do you understand how the planner chooses plans and why it might choose a different plan today than yesterday?
  • Statistics awareness — Can you explain how stale statistics cause plan regressions and how autovacuum/auto-analyze interact?
  • Systematic debugging — Do you have a structured investigation workflow, or do you thrash randomly?
  • Cross-engine knowledge — Can you discuss this across PostgreSQL, SQL Server, MySQL, and distributed engines?
  • Production war stories — Have you personally debugged a sudden slowdown and can you describe the timeline, root cause, and fix?
  • Prevention mindset — Do you set up monitoring and guardrails to catch regressions early?

At FAANG senior+ levels, the interviewer expects you to connect query regressions to SLA breaches, on-call incidents, and data platform reliability.

What a strong answer demonstrates
  • A taxonomy of root causes (statistics, skew, plan cache, cardinality, indexes, bloat, resources)
  • Deep understanding of how query planners use statistics and when they become stale
  • Knowledge of parameter sniffing / prepared statement plan caching across engines
  • Concrete debugging steps using EXPLAIN ANALYZE, pg_stat_user_tables, auto_explain
  • Awareness that "the query didn't change" doesn't mean "the plan didn't change"
  • Real numbers: table growth thresholds, autovacuum timing, n_distinct cliff effects
  • Prevention strategies: monitoring plan changes, pg_stat_statements, query regression alerts

Quick Answer (60-Second Version)

Elevator pitch

A query becomes suddenly slow because the execution plan changed, even though the SQL text remained identical. The most common triggers are:

  1. Statistics drift — table grew past a threshold but autovacuum hasn't re-analyzed; the planner's row estimates are stale, causing it to pick an inferior plan.
  2. Data skew — a new hot key or seasonal pattern creates non-uniform distribution that the planner doesn't account for.
  3. Plan cache poisoning — a cached plan was optimized for atypical parameter values (parameter sniffing) and is now being reused for common values.
  4. Cardinality estimation errors — correlated columns or multi-column filters cause the optimizer to drastically underestimate result sizes, choosing nested loops where hash joins are needed.
  5. Index degradation — bloat, fragmentation, or missing indexes for new access patterns force sequential scans.
  6. Vacuum falling behind — dead tuple accumulation forces index scans to visit dead rows, or table bloat causes sequential scans to read far more pages.
  7. Resource exhaustion — work_mem exceeded causes hash/sort spills to disk; noisy neighbors consume shared_buffers or I/O bandwidth.

The key insight: the query text is constant, but the plan is not. Plans depend on statistics, parameter values, available memory, and data distribution — all of which change over time.

Statistics Drift

How statistics become stale

The query planner relies on table statistics (row counts, column histograms, n_distinct estimates, most-common-values lists) to estimate cardinality at each plan node. When these statistics no longer reflect reality, the planner makes wrong decisions. 


# PostgreSQL autovacuum/auto-analyze thresholds:
#
# Default trigger formula for auto-analyze:
#   threshold = autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × n_tuples
#   Default:   50 + 0.10 × n_tuples
#
# Example with table growth:
# ┌──────────────────┬──────────────┬─────────────────┬──────────────────────┐
# │  Table Size      │  n_tuples    │  Analyze After   │  Staleness Window   │
# ├──────────────────┼──────────────┼─────────────────┼──────────────────────┤
# │  10K rows        │  10,000      │  1,050 changes   │  Minutes (fast)      │
# │  1M rows         │  1,000,000   │  100,050 changes │  Hours               │
# │  100M rows       │  100,000,000 │  10,000,050      │  Days to weeks!      │
# │  1B rows         │  1,000,000,000│ 100,000,050     │  Weeks to months!    │
# └──────────────────┴──────────────┴─────────────────┴──────────────────────┘
#
# The larger the table, the longer statistics remain stale.
# A 100M-row table needs 10M row changes before auto-analyze triggers!
The n_distinct cliff effect

PostgreSQL estimates n_distinct during ANALYZE by sampling a fraction of the table. For large tables, it may set n_distinct = -1 (meaning "unique per row") or a fixed estimate that becomes wrong as new distinct values appear. 


-- Check current statistics for a column:
SELECT
  schemaname, tablename, attname,
  n_distinct,
  most_common_vals,
  most_common_freqs,
  histogram_bounds
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'customer_id';

-- Example scenario:
-- Month 1: 500K distinct customers, n_distinct estimated as 500000
-- Month 6: 5M distinct customers, but n_distinct still says 500000
-- Impact: planner thinks a customer_id filter returns 1/500K of rows
--         but actually returns 1/5M → overestimates selectivity by 10x
--         → chooses Seq Scan when Index Scan would be better

-- n_distinct = -1 means "as many distinct values as rows"
-- n_distinct = -0.5 means "half as many distinct values as rows"
-- Positive values are absolute counts (can become stale)

-- Fix: manually set n_distinct for problematic columns
ALTER TABLE orders ALTER COLUMN customer_id SET (n_distinct = -1);
ANALYZE orders;
Histogram staleness after data growth

PostgreSQL builds histograms with default_statistics_target buckets (default: 100). When data distribution shifts — e.g., a new product category becomes dominant, or timestamps move past the old histogram range — the planner's selectivity estimates degrade. 


-- Scenario: orders table, amount column
-- Old histogram (from 6 months ago):
--   bounds: [0.01, 5.00, 10.00, 25.00, 50.00, 100.00, 250.00, 500.00, 1000.00]
-- New reality: Black Friday introduced amounts up to $50,000
-- Planner estimates WHERE amount > 1000 returns ~0 rows
-- Actually returns 2M rows → nested loop chosen → disaster

-- Increase statistics target for critical columns:
ALTER TABLE orders ALTER COLUMN amount SET STATISTICS 1000;
ANALYZE orders;
-- Now 1000 histogram buckets capture the new distribution

-- Verify histogram after analyze:
SELECT histogram_bounds
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'amount';
-- Should now include ranges up to 50000
Autovacuum timing issues

Even when autovacuum is enabled, it can fall behind due to:

  • Long-running transactions — prevent vacuuming of rows visible to old snapshots
  • autovacuum_max_workers — default 3 workers shared across all databases; large clusters starve small tables
  • I/O throttling — autovacuum_vacuum_cost_limit rate-limits vacuum to avoid I/O storms, but delays statistics refresh
  • Table-level locks — DDL operations or ACCESS EXCLUSIVE locks block autovacuum on that table
  • Partitioned tables — each partition is analyzed independently; parent statistics may lag

-- Check when a table was last analyzed:
SELECT
  relname,
  last_analyze,
  last_autoanalyze,
  n_live_tup,
  n_dead_tup,
  n_mod_since_analyze
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- If n_mod_since_analyze is high relative to n_live_tup,
-- statistics are likely stale.

-- Force immediate analyze on critical tables:
ANALYZE VERBOSE orders;

-- Tune per-table autovacuum for high-churn tables:
ALTER TABLE orders SET (
  autovacuum_analyze_threshold = 1000,
  autovacuum_analyze_scale_factor = 0.02  -- 2% instead of 10%
);

Data Skew

How new skewed values cause plan regressions

A query plan is optimized for the expected data distribution. When a new high-frequency value appears (a viral product, a bot account, a bulk import), the plan that was optimal for uniform distribution becomes catastrophically slow for the skewed case. 


-- Example: e-commerce orders table
-- Original distribution: each seller_id has ~1000 orders (uniform)
-- Plan: Index Scan on idx_orders_seller → Nested Loop Join → fast (5ms)

-- After onboarding a mega-seller (Amazon Marketplace scenario):
-- seller_id = 'MEGA_CORP' now has 15M orders (other sellers still ~1000)
-- Same plan: Index Scan returns 15M rows → Nested Loop does 15M iterations
-- Result: 5ms → 180 seconds (36,000x slower)

-- The planner estimated ~1000 rows based on avg frequency in MCV list
-- But the actual value wasn't in the most_common_vals yet (stale stats)

-- Check MCV list:
SELECT most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'seller_id';
-- If MEGA_CORP isn't in most_common_vals, planner uses default estimate
Seasonal patterns and time-based skew

Queries filtered on time ranges can hit skew when certain time periods have drastically different data volumes or distributions: 


# Seasonal skew examples:
#
# ┌────────────────────────────────────────────────────────────────┐
# │  Pattern             │  Normal        │  Skewed Period          │
# ├──────────────────────┼────────────────┼─────────────────────────┤
# │  E-commerce orders   │  50K/day       │  Black Friday: 5M/day   │
# │  Tax filing events   │  10K/day       │  April 15: 2M/day       │
# │  Sports streaming    │  100K/hour     │  Super Bowl: 20M/hour   │
# │  Social media posts  │  1M/day        │  Breaking news: 50M/day │
# │  Payment txns        │  200K/hour     │  Month-end: 3M/hour     │
# └──────────────────────┴────────────────┴─────────────────────────┘
#
# Impact on queries:
# - A reporting query that processes "yesterday's data" works fine 
#   for months, then suddenly times out on Nov 26 (Black Friday)
# - The plan was optimized for 50K rows; getting 5M rows causes:
#   * Hash table exceeds work_mem → spills to disk
#   * Nested loops chosen for "small" result → processes 5M iterations
#   * Bitmap heap scan exceeds effective_cache_size estimate
Hot keys in distributed systems

In distributed query engines (Spark, Presto, BigQuery), data skew causes straggler tasks — one partition holds 1000x more data than others, and the entire query waits for that single slow task. 


# Spark: detecting and handling skewed joins
from pyspark.sql import functions as F

# Detect skew: check key distribution
orders_df.groupBy("customer_id") \
    .count() \
    .orderBy(F.desc("count")) \
    .show(20)
# customer_id  | count
# BOT_ACCOUNT  | 45,000,000   ← extreme skew!
# NORMAL_USER1 | 1,200
# NORMAL_USER2 | 980

# Without skew handling:
# - 200 tasks finish in 30 seconds
# - 1 task (BOT_ACCOUNT) takes 45 minutes
# - Total query time: 45 minutes (straggler)

# Fix 1: Spark AQE skew join optimization (Spark 3.0+)
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256MB")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")

# Fix 2: Salt the key for manual skew handling
import random
salt_range = 100  # split hot key across 100 partitions

orders_salted = orders_df.withColumn(
    "salt", F.when(
        F.col("customer_id") == "BOT_ACCOUNT",
        F.lit(random.randint(0, salt_range - 1))
    ).otherwise(F.lit(0))
).withColumn(
    "join_key", F.concat("customer_id", F.lit("_"), "salt")
)
Detecting skew before it causes incidents 

-- PostgreSQL: monitor for skew using pg_stats
-- Check if most_common_freqs shows extreme values:
SELECT
  attname,
  most_common_vals[1:5] AS top_values,
  most_common_freqs[1:5] AS top_frequencies,
  -- If top frequency > 5%, that value is a skew candidate
  CASE WHEN most_common_freqs[1] > 0.05
       THEN 'SKEW WARNING: top value has ' ||
            round(most_common_freqs[1] * 100, 1) || '% of rows'
       ELSE 'OK'
  END AS skew_status
FROM pg_stats
WHERE tablename = 'orders'
  AND most_common_freqs IS NOT NULL
ORDER BY most_common_freqs[1] DESC NULLS LAST;

-- Monitor for new hot keys appearing over time:
-- Compare current distribution vs last week's baseline
SELECT
  customer_id,
  COUNT(*) AS order_count,
  COUNT(*) * 100.0 / SUM(COUNT(*)) OVER () AS pct_of_total
FROM orders
WHERE created_at > NOW() - INTERVAL '7 days'
GROUP BY customer_id
HAVING COUNT(*) > 10000  -- flag any customer with >10K orders/week
ORDER BY order_count DESC
LIMIT 20;

Parameter Sniffing / Plan Cache

What is parameter sniffing?

When a parameterized query (prepared statement, stored procedure) is first executed, the optimizer creates a plan based on the first set of parameter values it sees. This plan is then cached and reused for all subsequent executions, regardless of the parameter values. If the first call used atypical values, the cached plan is suboptimal for the common case. 


# Parameter sniffing timeline:
#
# Day 1: Application starts, first call:
#   EXECUTE get_orders($1) → $1 = 'RARE_CUSTOMER' (10 orders)
#   Planner sees: estimated 10 rows → chooses Index Scan + Nested Loop
#   Plan cached ✓
#
# Day 1-90: All subsequent calls reuse cached plan:
#   $1 = 'NORMAL_CUSTOMER' (500 orders)  → Index Scan OK (500 loops, 50ms)
#   $1 = 'ACTIVE_CUSTOMER' (5000 orders) → Index Scan OK (5000 loops, 400ms)
#   Everyone happy, SLA met.
#
# Day 91: New mega-customer onboarded:
#   $1 = 'MEGA_CORP' (2M orders) → Index Scan + Nested Loop (2M iterations!)
#   Same cached plan → 2M random I/O reads → 180 seconds
#   SLA breach! Pager fires!
#
# Root cause: plan was optimized for 10 rows, applied to 2M rows.
PostgreSQL prepared statements and generic plans

PostgreSQL has a unique behavior: after 5 executions of a prepared statement with custom (parameter-specific) plans, it switches to a generic plan if the generic plan's cost is not significantly worse. This transition can cause sudden performance changes. 


-- PostgreSQL plan caching behavior:
-- Executions 1-5: custom plan (uses actual parameter values)
-- Execution 6+: generic plan (uses placeholder $1, $2, etc.)
--   IF generic cost <= 1.1 × average custom cost → use generic
--   ELSE → continue with custom plans

-- Example: prepared statement
PREPARE get_orders(text) AS
  SELECT * FROM orders WHERE customer_id = $1;

-- First 5 calls: custom plan each time (fast, parameter-specific)
EXECUTE get_orders('RARE_CUSTOMER');    -- 10 rows, Index Scan
EXECUTE get_orders('NORMAL_CUSTOMER');  -- 500 rows, Index Scan
EXECUTE get_orders('ACTIVE_CUSTOMER'); -- 5000 rows, still Index Scan
EXECUTE get_orders('NORMAL_CUSTOMER');  -- 500 rows, Index Scan
EXECUTE get_orders('NORMAL_CUSTOMER');  -- 500 rows, Index Scan

-- 6th call: PG evaluates generic plan
-- Generic plan uses column statistics (average selectivity)
-- If table has 50M rows and 1M distinct customers → avg 50 rows/customer
-- Generic plan: Index Scan (good for most cases)
-- BUT if n_distinct is wrong (stale stats say 10K distinct customers)
-- → avg 5000 rows/customer → Seq Scan chosen for generic plan!

-- Diagnose: check if generic plan is in use
EXPLAIN (ANALYZE) EXECUTE get_orders('RARE_CUSTOMER');
-- Look for "$1" in the plan output — indicates generic plan

-- Force custom plans (PostgreSQL 12+):
SET plan_cache_mode = 'force_custom_plan';
-- Or per-statement:
DEALLOCATE get_orders;
-- And re-prepare to reset the counter
SQL Server parameter sniffing 

-- SQL Server: classic parameter sniffing scenario
-- The plan is compiled on FIRST execution and cached in plan cache

-- Stored procedure:
CREATE PROCEDURE GetOrdersByStatus @status VARCHAR(20)
AS
  SELECT o.order_id, o.amount, c.name
  FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id
  WHERE o.status = @status;
GO

-- First call after server restart or plan eviction:
EXEC GetOrdersByStatus @status = 'cancelled';  -- 0.1% of rows
-- Plan: Nested Loop + Index Seek (optimized for tiny result set)
-- Cached!

-- Subsequent call with common value:
EXEC GetOrdersByStatus @status = 'completed';  -- 85% of rows
-- REUSES the Nested Loop plan → disaster on 85% of table
-- Should use Hash Join + Clustered Index Scan for large sets

-- FIXES:

-- Fix 1: OPTION (RECOMPILE) — fresh plan every time (CPU cost)
CREATE PROCEDURE GetOrdersByStatus @status VARCHAR(20)
AS
  SELECT o.order_id, o.amount, c.name
  FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id
  WHERE o.status = @status
  OPTION (RECOMPILE);
GO

-- Fix 2: OPTIMIZE FOR UNKNOWN — uses average statistics
CREATE PROCEDURE GetOrdersByStatus @status VARCHAR(20)
AS
  SELECT o.order_id, o.amount, c.name
  FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id
  WHERE o.status = @status
  OPTION (OPTIMIZE FOR (@status UNKNOWN));
GO

-- Fix 3: Plan guides or query store forcing
-- Force a known-good plan via Query Store:
EXEC sp_query_store_force_plan @query_id = 42, @plan_id = 7;
When plan cache invalidation causes regressions

Plan caches are invalidated by various events. After invalidation, the next execution compiles a fresh plan — which might be worse than the previous one if statistics have drifted or data distribution has changed since the original plan was compiled. 


# Plan cache invalidation triggers:
#
# PostgreSQL:
#   - ANALYZE (refreshes statistics → may change generic plan choice)
#   - DDL changes (ALTER TABLE, CREATE INDEX, DROP INDEX)
#   - DEALLOCATE statement
#   - Server restart
#   - shared_buffers pressure (plan eviction)
#   - pg_stat_statements reset
#
# SQL Server:
#   - UPDATE STATISTICS
#   - Schema changes (any DDL on referenced objects)
#   - sp_recompile
#   - Memory pressure (plan eviction from cache)
#   - Server restart
#   - DBCC FREEPROCCACHE
#   - Recompile hints
#   - Statistics auto-update threshold crossed
#
# MySQL:
#   - Table definition changes
#   - FLUSH TABLES
#   - Server restart
#   - Optimizer hints change
#
# Irony: running ANALYZE to fix stale statistics can itself cause
# a plan regression if the new statistics lead to a worse plan
# choice than the "wrong but lucky" old plan.

Cardinality Estimation Errors

How underestimation causes nested loops on large sets

The most catastrophic plan regression pattern: the optimizer underestimates the number of rows at a join node and chooses a nested loop join (optimal for small outer sets) instead of a hash join (optimal for large sets). A 1000x underestimate can turn a 200ms query into a 45-minute disaster. 


-- The planner's decision threshold (simplified):
--
-- Estimated outer rows < ~1000 → Nested Loop (O(n×m) but low startup)
-- Estimated outer rows > ~10000 → Hash Join (O(n+m) but hash build cost)
--
-- When estimation is wrong:
-- Estimated: 500 rows → NL chosen → cost model says 500 × index_seek = fast
-- Actual: 2,000,000 rows → NL executes 2M index seeks → catastrophic

-- Example EXPLAIN showing the mismatch:
EXPLAIN (ANALYZE, BUFFERS) 
SELECT o.order_id, p.product_name
FROM orders o
JOIN products p ON o.product_id = p.product_id
WHERE o.created_at > '2024-01-01'
  AND o.region = 'us-east-1'
  AND o.status = 'pending';

-- Output showing cardinality error:
-- Nested Loop (cost=0.85..4521.30 rows=450 width=48)
--              (actual time=0.05..185000.00 rows=2100000 loops=1)
--                                    ^^^^^^^^^^^^^^^^^^^^^^^^
--   → estimated 450 rows, actual 2.1M rows = 4667x underestimate!
--   → Nested Loop doing 2.1M iterations instead of expected 450
--
--   -> Index Scan using idx_orders_composite on orders o
--      (cost=0.43..2250.65 rows=450 width=16)
--      (actual time=0.03..12000.00 rows=2100000 loops=1)
--        Filter: (region = 'us-east-1' AND status = 'pending')
--        Rows Removed by Filter: 8500000
--
--   -> Index Scan using products_pkey on products p
--      (cost=0.42..5.04 rows=1 width=36)
--      (actual time=0.02..0.03 rows=1 loops=2100000)
--                                       ^^^^^^^^^^^^ 2.1M iterations!
Correlated columns problem

Standard query optimizers assume column values are independent. When columns are correlated (e.g., city and zip_code, make and model, department and salary band), the optimizer multiplies selectivities independently, producing drastically wrong estimates. 


-- Correlated columns example:
-- Table: employees (1M rows)
-- department has 20 distinct values (selectivity = 1/20 = 5%)
-- job_title has 200 distinct values (selectivity = 1/200 = 0.5%)
--
-- Query:
SELECT * FROM employees
WHERE department = 'Engineering' AND job_title = 'Senior SWE';
--
-- Optimizer's independence assumption:
--   selectivity = 5% × 0.5% = 0.025%
--   estimated rows = 1,000,000 × 0.025% = 250 rows
--
-- Reality (correlated: 'Senior SWE' only exists in Engineering):
--   actual rows = 45,000 rows (180x underestimate!)
--
-- Impact: Nested Loop chosen for "250 rows" → processes 45K rows
-- Should have been: Hash Join for 45K rows

-- PostgreSQL fix: extended statistics (CREATE STATISTICS)
CREATE STATISTICS emp_dept_title_stats (dependencies, ndistinct, mcv)
ON department, job_title FROM employees;
ANALYZE employees;

-- Verify improved estimates:
EXPLAIN SELECT * FROM employees
WHERE department = 'Engineering' AND job_title = 'Senior SWE';
-- Now shows ~45000 rows instead of 250
Multi-join amplification of estimation errors

Cardinality errors compound across joins. A 10x error at the first join becomes 100x at the second join and 1000x at the third. This is why complex queries (5+ joins) are most vulnerable to sudden plan regressions. 


# Error amplification across joins:
#
# ┌─────────┬──────────────┬──────────────┬─────────────────────────┐
# │  Node   │  Estimated   │  Actual      │  Cumulative Error       │
# ├─────────┼──────────────┼──────────────┼─────────────────────────┤
# │  Scan A │  1,000       │  10,000      │  10x                    │
# │  Join B │  500         │  50,000      │  100x (10x × 10x)       │
# │  Join C │  100         │  100,000     │  1000x (error compounds)│
# │  Join D │  50          │  500,000     │  10000x                 │
# └─────────┴──────────────┴──────────────┴─────────────────────────┘
#
# At Join D, the planner thinks 50 rows → Nested Loop
# Reality: 500K rows with Nested Loop = catastrophic
#
# This is why complex queries can run fine for months and then
# suddenly break: a small statistics drift at one table cascades
# through the join graph until it tips a join from Hash → NL.
Tipping points: when estimates cross plan boundaries

Query plans don't degrade linearly — they have tipping points where the optimizer switches between fundamentally different strategies. A table growing from 99K to 101K rows might cross a threshold that flips the plan from Index Scan to Seq Scan, causing a 100x slowdown overnight. 


-- PostgreSQL cost-based tipping points:
--
-- Index Scan vs Seq Scan:
--   When selectivity > ~5-15% of table, Seq Scan becomes cheaper
--   (depends on random_page_cost vs seq_page_cost ratio)
--
-- Nested Loop vs Hash Join:
--   When outer relation estimated > ~1000 rows, Hash Join preferred
--   (depends on cpu_tuple_cost and effective_cache_size)
--
-- Sort vs Hash Aggregate:
--   When distinct values exceed work_mem capacity, Sort spills

-- Demonstrate the tipping point:
SET enable_hashjoin = on;
SET enable_nestloop = on;

-- With accurate stats (50K estimated, 50K actual):
EXPLAIN ANALYZE SELECT ... -- Hash Join, 200ms

-- After data growth + stale stats (500 estimated, 50K actual):
EXPLAIN ANALYZE SELECT ... -- Nested Loop, 45 seconds!

-- The plan "suddenly" changed because the estimate crossed the NL→HJ boundary.
-- From the operator's perspective: "nothing changed, query just got slow overnight"

Index Degradation

B-tree fragmentation and bloat

B-tree indexes in PostgreSQL can become bloated over time due to page splits, deleted entries that aren't reclaimed, and non-HOT updates. A bloated index forces more I/O per lookup, eventually making the planner prefer a Seq Scan over using the bloated index. 


-- Check index bloat in PostgreSQL:
SELECT
  schemaname || '.' || relname AS table_name,
  indexrelname AS index_name,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
  idx_scan AS times_used,
  idx_tup_read,
  idx_tup_fetch,
  CASE WHEN idx_scan = 0 THEN 'UNUSED'
       ELSE 'ACTIVE'
  END AS usage_status
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY pg_relation_size(indexrelid) DESC;

-- Estimate bloat using pgstattuple extension:
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT * FROM pgstatindex('idx_orders_customer_id');
-- Key outputs:
--   tree_level: 3        (depth of B-tree)
--   index_size: 4 GB     (total size on disk)
--   leaf_pages: 500000
--   empty_pages: 150000  ← 30% empty = significant bloat!
--   deleted_pages: 50000 ← dead pages not yet reclaimed
--   avg_leaf_density: 45% ← should be ~90% for healthy index
--   fragment_percent: 35% ← page ordering doesn't match logical order

-- When bloat > 50%, REINDEX becomes necessary:
-- Impact on query performance:
-- Healthy index (90% density): 3 page reads for 1 lookup
-- Bloated index (45% density): 6 page reads for 1 lookup (2x I/O)
-- If bloat is extreme, planner may switch to Seq Scan entirely
Missing indexes for new access patterns

Applications evolve: new features add new WHERE clauses, new JOIN conditions, or new ORDER BY requirements. The existing indexes don't cover these new patterns, causing sequential scans on tables that grew from 1M to 100M rows. 


-- Common scenario:
-- Original query (Day 1): WHERE customer_id = $1
-- Index exists: idx_orders_customer_id → fast

-- New feature (Month 6): WHERE customer_id = $1 AND status = $2
-- No composite index → index scan on customer_id + filter on status
-- When status='pending' is 90% of a customer's orders, this is fine
-- When status='completed' is 0.1% of orders → still scanning all customer rows

-- Detect missing indexes with pg_stat_user_tables:
SELECT
  relname,
  seq_scan,
  seq_tup_read,
  idx_scan,
  CASE WHEN seq_scan > 0
    THEN round(seq_tup_read::numeric / seq_scan, 0)
    ELSE 0
  END AS avg_rows_per_seq_scan,
  n_live_tup
FROM pg_stat_user_tables
WHERE seq_scan > 100  -- tables with frequent seq scans
  AND n_live_tup > 100000  -- large tables (small tables are fine with seq scan)
ORDER BY seq_tup_read DESC;

-- Use pg_stat_statements to find slow queries:
SELECT
  query,
  calls,

Index selection changes after data growth

As a table grows, the cost calculus for index usage changes. An index that was beneficial at 1M rows might be deemed too expensive at 100M rows if the selectivity of the indexed column decreases. 


# Index cost-effectiveness vs table size:
#
# ┌─────────────────┬────────────┬─────────────┬───────────────────────┐
# │  Table Size     │  Index Size│  Selectivity │  Planner Decision     │
# ├─────────────────┼────────────┼─────────────┼───────────────────────┤
# │  1M rows        │  50 MB     │  5% (50K)   │  Index Scan (fast)    │
# │  10M rows       │  500 MB    │  5% (500K)  │  Index Scan (OK)      │
# │  100M rows      │  5 GB      │  5% (5M)    │  Bitmap Scan or Seq?  │
# │  1B rows        │  50 GB     │  5% (50M)   │  Seq Scan (index too  │
# │                 │            │             │  expensive for 50M    │
# │                 │            │             │  random I/O reads)    │
# └─────────────────┴────────────┴─────────────┴───────────────────────┘
#
# At 100M+ rows with 5% selectivity:
# - Random I/O for 5M index lookups is slower than sequential read of entire table
# - Planner switches from Index Scan → Sequential Scan
# - Query goes from 200ms (index, warm cache) to 30s (full scan)
#
# The "sudden" slowdown happens when the table crosses the tipping point
# where random_page_cost × estimated_rows > seq_page_cost × total_pages

Vacuum & Bloat Issues

Dead tuple accumulation and its impact on queries

In PostgreSQL's MVCC model, UPDATE and DELETE operations don't immediately remove old row versions. These dead tuples remain on disk until VACUUM reclaims them. As dead tuples accumulate, queries must read through dead rows during sequential scans and index scans, causing progressive slowdown. 


-- Check dead tuple accumulation:
SELECT
  relname,
  n_live_tup,
  n_dead_tup,
  round(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
  last_vacuum,
  last_autovacuum,
  last_analyze,
  last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 100000
ORDER BY n_dead_tup DESC;

-- Example output showing problems:
-- relname  | n_live_tup | n_dead_tup | dead_pct | last_autovacuum
-- orders   | 50,000,000 | 45,000,000 | 47.4%    | 3 days ago
--
-- 47% dead tuples means:
-- - Table is nearly 2x its necessary size on disk
-- - Sequential scans read 2x as many pages
-- - Index scans hit dead tuples → recheck visible → wasted I/O
-- - Buffer cache is 47% polluted with dead data

-- Impact on query performance:
-- Clean table (50M rows, 40 GB): Seq Scan reads 40 GB, 12 seconds
-- Bloated table (50M live + 45M dead, 76 GB): Seq Scan reads 76 GB, 23 seconds
-- Same query, same result, nearly 2x slower!
Autovacuum falling behind

Autovacuum can fall behind for several reasons, creating a feedback loop where the more behind it gets, the harder it is to catch up: 


# Why autovacuum falls behind:
#
# 1. High-churn tables with default settings:
#    - Table: 100M rows, 500K updates/hour
#    - Default scale_factor: 0.20 → trigger at 20M dead tuples
#    - At 500K/hour, takes 40 hours to accumulate 20M dead tuples
#    - Vacuum then takes 6+ hours on 100M-row table
#    - Net result: always 20-40M dead tuples present
#
# 2. Long-running transactions holding back xmin:
#    - Transaction started 3 hours ago, still open
#    - Vacuum cannot remove any tuples newer than that xmin
#    - Dead tuples accumulate faster than vacuum can process
#    - One forgotten pg_dump or idle transaction blocks ALL vacuums
#
# 3. Insufficient autovacuum workers:
#    - Default: 3 workers for entire database cluster
#    - If 10 tables need vacuuming simultaneously, 7 wait in queue
#    - High-priority tables (heavily updated) compete with large tables
#
# 4. Cost-based vacuum throttling:
#    - Default cost_limit: 200 (shared across all workers)
#    - On large tables, this means vacuum processes ~60 MB/second
#    - A 200 GB table takes 55+ minutes to vacuum at default throttle
#    - During that time, more dead tuples accumulate
Table bloat causing plan changes 

-- Bloat affects the planner's cost calculations:
-- pg_class.relpages = physical pages on disk (includes dead space)
-- pg_class.reltuples = estimated live rows
--
-- When bloat is severe:
-- relpages is 2-5x what it should be for the live data
-- Cost of Seq Scan = seq_page_cost × relpages
-- This inflated cost can make Index Scan look cheaper even when
-- selectivity suggests Seq Scan should win → suboptimal plan!

-- Check table bloat:

  schemaname, relname,
  pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
  pg_size_pretty(pg_relation_size(relid)) AS table_size,
  n_live_tup,
  n_dead_tup,
  -- Estimated ideal size based on live tuples:

FROM pg_stat_user_tables

-- Severe bloat scenario:
-- actual table_size: 120 GB
-- estimated_ideal_size: 40 GB

Transaction ID wraparound emergency

The most severe vacuum-related emergency: if autovacuum can't complete anti-wraparound vacuum before the 2-billion transaction ID limit, PostgreSQL will shut down entirely to prevent data corruption. Before this happens, it forces aggressive vacuuming that can make all queries slow. 


-- Monitor transaction ID age:
SELECT
  relname,
  age(relfrozenxid) AS xid_age,
  -- Warning threshold: 200M (autovacuum_freeze_max_age default)
  -- Danger threshold: 1.2B (approaching wraparound)
  -- Emergency: 2B (database shuts down)
  CASE
    WHEN age(relfrozenxid) > 1200000000 THEN 'CRITICAL'
    WHEN age(relfrozenxid) > 500000000 THEN 'WARNING'
    ELSE 'OK'
  END AS status,
  pg_size_pretty(pg_relation_size(oid)) AS table_size
FROM pg_class
WHERE relkind = 'r'
ORDER BY age(relfrozenxid) DESC
LIMIT 10;

-- When XID age exceeds autovacuum_freeze_max_age (default 200M):
-- PostgreSQL launches aggressive vacuum that:
-- - Ignores cost_limit (runs at full speed)
-- - Competes with queries for I/O
-- - Can cause all queries to slow down simultaneously
-- - Cannot be cancelled without risking wraparound

-- Prevention:
-- 1. Ensure no long-running transactions (check pg_stat_activity)
-- 2. Tune autovacuum to vacuum more frequently on high-churn tables
-- 3. Monitor xid_age in your alerting system
-- 4. Kill idle-in-transaction sessions automatically:
SET idle_in_transaction_session_timeout = '10min';

Spill to Disk

work_mem exhaustion and hash join spill

Hash joins build an in-memory hash table on the inner relation. When this table exceeds work_mem, it spills to disk — partitioning data into temporary files and processing them in batches. This can turn a 200ms in-memory hash join into a 30-second disk-bound operation. 


-- PostgreSQL: detect hash join spill in EXPLAIN ANALYZE
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.order_id, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE o.created_at > '2024-01-01';

-- When work_mem is sufficient (no spill):
-- Hash Join (cost=... rows=500000 actual time=50..200 rows=500000)
--   Hash Cond: (o.customer_id = c.customer_id)
--   -> Seq Scan on orders o ...
--   -> Hash (cost=... rows=1000000)
--        Buckets: 1048576  Batches: 1  Memory Usage: 80 MB
--                          ^^^^^^^^^
--        Batches=1 means everything fit in memory ✓

-- When work_mem is exhausted (spill to disk):
-- Hash Join (cost=... rows=500000 actual time=50..28000 rows=500000)
--   Hash Cond: (o.customer_id = c.customer_id)
--   -> Seq Scan on orders o ...
--   -> Hash (cost=... rows=1000000)
--        Buckets: 131072  Batches: 16  Memory Usage: 40 MB
--                         ^^^^^^^^^^
--        Batches=16 means 16 passes over data on disk!
--        Temp files written: 1.2 GB  ← disk I/O penalty

-- Why this becomes sudden:
-- Month 1: customers table = 500K rows → Hash = 40 MB → fits in work_mem (64 MB)
-- Month 6: customers table = 2M rows → Hash = 160 MB → exceeds work_mem!
-- Result: Batches goes from 1 to 4 → 3x-10x slower overnight

-- Check current work_mem:
SHOW work_mem;  -- default is often 4 MB (WAY too low for analytics)

-- Set appropriate work_mem for the session:
SET work_mem = '256MB';  -- per-operation, not per-connection total

-- Scenario: your OLTP query relies on hot data being in shared_buffers
-- A large analytics query does a sequential scan of a 100 GB table
-- This evicts YOUR frequently-accessed pages from the buffer cache
-- Next time your query runs: cold cache → disk reads → 10x slower

-- PostgreSQL buffer cache inspection (pg_buffercache extension):
CREATE EXTENSION IF NOT EXISTS pg_buffercache;

SELECT
  c.relname,
  COUNT(*) AS buffers_cached,
  pg_size_pretty(COUNT(*) * current_setting('block_size')::int) AS cached_size,
  ROUND(100.0 * COUNT(*) / (
    SELECT setting::int FROM pg_settings WHERE name = 'shared_buffers'
  ), 2) AS pct_of_cache
FROM pg_buffercache b
JOIN pg_class c ON b.relfilenode = c.relfilenode
WHERE c.relname IS NOT NULL
GROUP BY c.relname
ORDER BY buffers_cached DESC
LIMIT 15;

ON orders (customer_id, status, created_at DESC);
-- This index serves the query directly, regardless of statistics

-- 3. Add extended statistics for correlated columns:
CREATE STATISTICS orders_status_customer_stats (dependencies, mcv)
ON customer_id, status FROM orders;
ANALYZE orders;

-- 4. Monitoring: alert on statistics freshness
-- Add to monitoring system (Datadog/Prometheus):
-- Alert when n_mod_since_analyze / n_live_tup > 0.05 (5%)

-- 5. Scheduled ANALYZE for critical tables after bulk operations:
-- In the ETL pipeline, add:
-- AFTER bulk_import: ANALYZE orders;

-- 6. Connection pool: force plan recompilation after ANALYZE
-- Recycle all connections in pgBouncer after emergency ANALYZE:
-- pgbouncer: RECONNECT orders_db
Lessons learned
  • Autovacuum thresholds don't scale — at 100M rows, 10% scale_factor means 10M changes before re-analyze. Tune per-table for critical paths.
  • Bulk imports need explicit ANALYZE — always run ANALYZE after large data loads, don't rely on autovacuum timing.
  • Monitor statistics age — alert on n_mod_since_analyze / n_live_tup ratio exceeding 5% for critical tables.
  • The "uniform distribution" assumption kills — when one status value goes from 2% to 35%, the planner's independence assumption produces wildly wrong estimates.
  • Composite indexes provide plan stability — an index on (customer_id, status, created_at) gives the same plan regardless of statistics accuracy.
  • Generic plans in PG need monitoring — when connections recycle, new generic plans may be chosen based on stale statistics.
  • Test with production data volumes — this bug would never appear in dev (10K rows) or staging (1M rows).

Monitoring script: detect statistics drift before incidents 

#!/usr/bin/env python3
"""
Statistics Drift Monitor — alerts before stale stats cause plan regressions.
Run as a cron job every 15 minutes or as a Prometheus exporter.
"""
import psycopg2
import json
from datetime import datetime, timedelta

CONN_STRING = "host=localhost dbname=production user=monitor"
STALENESS_THRESHOLD_PCT = 5.0   # alert if >5% of rows modified since analyze
DEAD_TUPLE_THRESHOLD_PCT = 20.0  # alert if >20% dead tuples
CRITICAL_TABLES = ['orders', 'customers', 'events', 'payments']


def check_statistics_health(conn):
    """Check statistics freshness for critical tables."""
    alerts = []
    with conn.cursor() as cur:
        cur.execute("""
            SELECT
                relname,
                n_live_tup,
                n_dead_tup,
                n_mod_since_analyze,
                last_autoanalyze,
                last_analyze,
                COALESCE(
                    round(n_mod_since_analyze * 100.0 /
                          GREATEST(n_live_tup, 1), 2),
                    0
                ) AS staleness_pct,
                COALESCE(
                    round(n_dead_tup * 100.0 /
                          GREATEST(n_live_tup + n_dead_tup, 1), 2),
                    0
                ) AS dead_pct
            FROM pg_stat_user_tables
            WHERE relname = ANY(%s)
            ORDER BY staleness_pct DESC;
        """, (CRITICAL_TABLES,))

        for row in cur.fetchall():
            table, live, dead, mods, last_aa, last_a, stale_pct, dead_pct = row

            if stale_pct > STALENESS_THRESHOLD_PCT:
                alerts.append({
                    'severity': 'WARNING',
                    'table': table,
                    'message': f'Statistics {stale_pct}% stale '
                               f'({mods:,} mods since last analyze)',
                    'action': f'ANALYZE {table};',
                    'last_analyze': str(last_a or last_aa)
                })

            if dead_pct > DEAD_TUPLE_THRESHOLD_PCT:
                alerts.append({
                    'severity': 'WARNING',
                    'table': table,
                    'message': f'{dead_pct}% dead tuples '
                               f'({dead:,} dead / {live:,} live)',
                    'action': f'VACUUM (VERBOSE) {table};',
                })

    return alerts


def check_plan_regressions(conn):
    """Detect queries whose execution time increased significantly."""
    alerts = []
    with conn.cursor() as cur:
        # Requires pg_stat_statements with track_planning = on
        cur.execute("""
            SELECT
                queryid,
                LEFT(query, 100) AS query_preview,
                calls,
                mean_exec_time,
                max_exec_time,
                temp_blks_written,
                -- Compare recent performance vs historical
                CASE WHEN mean_exec_time > 5000 AND calls > 10
                     THEN 'SLOW'
                     ELSE 'OK'
                END AS status
            FROM pg_stat_statements
            WHERE mean_exec_time > 5000  -- queries averaging > 5 seconds
              AND calls > 10             -- with meaningful call volume
            ORDER BY mean_exec_time DESC
            LIMIT 20;
        """)
        for row in cur.fetchall():
            qid, preview, calls, avg_ms, max_ms, temp_blks = row[:6]
            alerts.append({
                'severity': 'CRITICAL' if avg_ms > 30000 else 'WARNING',
                'query_id': qid,
                'message': f'Query avg {avg_ms:.0f}ms, max {max_ms:.0f}ms, '
                           f'{calls} calls, temp_blks={temp_blks}',
                'query': preview
            })

    return alerts


def check_index_health(conn):
    """Detect unused or bloated indexes."""
    alerts = []
    with conn.cursor() as cur:
        cur.execute("""
            SELECT
                schemaname || '.' || relname AS table_name,
                indexrelname,
                idx_scan,
                pg_relation_size(indexrelid) AS index_bytes
            FROM pg_stat_user_indexes
            WHERE idx_scan = 0
              AND pg_relation_size(indexrelid) > 100 * 1024 * 1024  -- > 100 MB
            ORDER BY pg_relation_size(indexrelid) DESC;
        """)
        for row in cur.fetchall():
            table, idx, scans, size_bytes = row
            alerts.append({
                'severity': 'INFO',
                'message': f'Unused index {idx} on {table} '
                           f'({size_bytes / 1024 / 1024:.0f} MB)',
                'action': f'DROP INDEX CONCURRENTLY {idx};'
            })

    return alerts


if __name__ == '__main__':
    conn = psycopg2.connect(CONN_STRING)
    all_alerts = []
    all_alerts.extend(check_statistics_health(conn))
    all_alerts.extend(check_plan_regressions(conn))
    all_alerts.extend(check_index_health(conn))
    conn.close()

    if all_alerts:
        print(json.dumps(all_alerts, indent=2, default=str))
        # Send to Slack/PagerDuty/Datadog as appropriate
    else:
        print("All checks passed.")
Automated ANALYZE after bulk operations 

#!/usr/bin/env python3
"""
Post-bulk-load ANALYZE wrapper.
Call this after any ETL pipeline that inserts/updates >1% of a table.
"""
import psycopg2
import time
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)


def smart_analyze(conn, table_name, columns=None, verbose=True):
    """
    Run ANALYZE on a table, optionally targeting specific columns.
    Measures impact and logs statistics changes.
    """
    with conn.cursor() as cur:
        # Capture pre-analyze state
        cur.execute("""
            SELECT n_mod_since_analyze, last_analyze
            FROM pg_stat_user_tables
            WHERE relname = %s;
        """, (table_name,))
        pre_state = cur.fetchone()
        logger.info(
            f"Pre-ANALYZE: {table_name} has "
            f"{pre_state[0]:,} modifications since last analyze "
            f"(last: {pre_state[1]})"
        )

        # Run ANALYZE
        start = time.time()
        if columns:
            col_list = ', '.join(columns)
            sql = f"ANALYZE {'VERBOSE' if verbose else ''} {table_name} ({col_list})"
        else:
            sql = f"ANALYZE {'VERBOSE' if verbose else ''} {table_name}"

        cur.execute(sql)
        duration = time.time() - start
        logger.info(f"ANALYZE {table_name} completed in {duration:.2f}s")

        # Verify post-analyze state
        cur.execute("""
            SELECT n_mod_since_analyze, last_analyze
            FROM pg_stat_user_tables
            WHERE relname = %s;
        """, (table_name,))
        post_state = cur.fetchone()
        logger.info(
            f"Post-ANALYZE: n_mod_since_analyze reset to {post_state[0]}, "
            f"last_analyze = {post_state[1]}"
        )

    conn.commit()
    return duration


def bulk_load_with_analyze(conn, table_name, data_source, key_columns):
    """
    Pattern: bulk load data, then immediately ANALYZE affected columns.
    Prevents the "stale statistics after bulk import" problem.
    """
    with conn.cursor() as cur:
        # Get row count before
        cur.execute(f"SELECT COUNT(*) FROM {table_name}")
        count_before = cur.fetchone()[0]

        # Perform bulk load (example: COPY)
        logger.info(f"Starting bulk load into {table_name}...")
        with open(data_source, 'r') as f:
            cur.copy_expert(
                f"COPY {table_name} FROM STDIN WITH CSV HEADER",
                f
            )
        conn.commit()

        # Get row count after
        cur.execute(f"SELECT COUNT(*) FROM {table_name}")
        count_after = cur.fetchone()[0]
        rows_loaded = count_after - count_before
        logger.info(f"Loaded {rows_loaded:,} rows into {table_name}")

        # Always ANALYZE after bulk load
        pct_change = rows_loaded * 100.0 / max(count_before, 1)
        if pct_change > 1.0:
            logger.info(
                f"Table changed by {pct_change:.1f}% — "
                f"running ANALYZE on key columns"
            )
            smart_analyze(conn, table_name, columns=key_columns)
        else:
            logger.info(f"Small load ({pct_change:.2f}%), skipping ANALYZE")

    return rows_loaded
Query plan regression detector using pg_stat_statements 

-- Create a baseline table to track query performance over time:
CREATE TABLE IF NOT EXISTS query_performance_baseline (
  snapshot_time TIMESTAMPTZ DEFAULT NOW(),
  queryid BIGINT,
  query TEXT,
  calls BIGINT,
  mean_exec_time FLOAT,
  p99_exec_time FLOAT,
  shared_blks_hit BIGINT,
  shared_blks_read BIGINT,
  temp_blks_written BIGINT,
  rows_per_call FLOAT
);

-- Snapshot current performance (run hourly via cron):
INSERT INTO query_performance_baseline
SELECT
  NOW(),
  queryid,
  LEFT(query, 500),
  calls,
  mean_exec_time,
  max_exec_time,  -- approximation of p99
  shared_blks_hit,
  shared_blks_read,
  temp_blks_written,
  CASE WHEN calls > 0 THEN rows::float / calls ELSE 0 END
FROM pg_stat_statements
WHERE calls > 100  -- only track frequently-called queries
  AND mean_exec_time > 10;  -- only track non-trivial queries

-- Detect regressions (compare last hour vs 24-hour baseline):
WITH recent AS (
  SELECT queryid, mean_exec_time, temp_blks_written, snapshot_time
  FROM query_performance_baseline
  WHERE snapshot_time > NOW() - INTERVAL '1 hour'
),
baseline AS (
  SELECT
    queryid,
    AVG(mean_exec_time) AS baseline_avg_ms,
    AVG(temp_blks_written) AS baseline_temp_blks
  FROM query_performance_baseline
  WHERE snapshot_time BETWEEN NOW() - INTERVAL '25 hours'
    AND NOW() - INTERVAL '2 hours'
  GROUP BY queryid
)
SELECT
  r.queryid,
  b.baseline_avg_ms,
  r.mean_exec_time AS current_avg_ms,
  round((r.mean_exec_time / NULLIF(b.baseline_avg_ms, 0))::numeric, 1)
    AS regression_factor,
  r.temp_blks_written,
  b.baseline_temp_blks
FROM recent r
JOIN baseline b ON r.queryid = b.queryid
WHERE r.mean_exec_time > 3 * b.baseline_avg_ms  -- 3x slower = regression
  AND b.baseline_avg_ms > 50  -- ignore sub-50ms queries
ORDER BY regression_factor DESC;

Common Mistakes

Mistake 1: Blaming the query text when the plan changed

The most common error in debugging sudden slowdowns: developers focus on the SQL text ("but we didn't change anything!") instead of examining the execution plan. The query is constant, but the plan depends on statistics, parameter values, and system state. 


# Wrong approach:
# "The query hasn't changed in 6 months, so it must be a hardware issue"
# → Leads to expensive infrastructure upgrades that don't fix the problem

# Right approach:
# 1. EXPLAIN ANALYZE the slow query NOW
# 2. Compare with the plan from when it was fast (auto_explain logs)
# 3. Identify WHERE the plan differs (join type, scan type, row estimates)
# 4. Ask: "What changed to make the planner choose differently?"
#    - Statistics? (ANALYZE)
#    - Data distribution? (skew)
#    - Table size? (crossed a tipping point)
#    - Plan cache? (parameter sniffing)
Mistake 2: Running ANALYZE without checking the real root cause

ANALYZE is often the fix, but running it blindly can sometimes make things worse. If the new statistics lead the planner to choose a genuinely suboptimal plan (e.g., the old plan was good despite inaccurate statistics), you need to understand why. 


-- Scenario: query was fast with "wrong" statistics
-- Old stats: estimated 100 rows → Index Scan → fast (lucky)
-- New stats (after ANALYZE): estimated 500K rows → Seq Scan → slow (correct estimate, wrong decision)
--
-- Why? The Seq Scan is actually slower because:
-- - Data is on SSD (random_page_cost should be 1.1, not default 4.0)
-- - Table is fully cached in shared_buffers
-- - The Index Scan was actually optimal despite high selectivity

-- Fix: adjust cost parameters to reflect actual hardware:
SET random_page_cost = 1.1;    -- SSD (default 4.0 assumes spinning disk)
SET effective_cache_size = '24GB';  -- actual available cache
-- Now planner correctly prefers Index Scan even with accurate statistics
Mistake 3: Increasing work_mem globally instead of per-query 

-- Problem: query spills to disk, so someone sets work_mem = 2GB globally
-- Impact: 200 concurrent connections × 2GB = 400GB memory demand!
-- Result: OOM killer, connection failures, worse performance overall

-- BAD:
ALTER SYSTEM SET work_mem = '2GB';  -- affects ALL queries on ALL connections

-- GOOD: set work_mem per-session or per-transaction for heavy queries:
-- In application code:
BEGIN;
SET LOCAL work_mem = '512MB';  -- only for this transaction
SELECT ... complex query ...;
COMMIT;
-- work_mem reverts to default after COMMIT

-- BETTER: use connection pool with role-based settings:
-- Analytics role gets high work_mem:
ALTER ROLE analytics_user SET work_mem = '512MB';
-- OLTP role keeps low work_mem:
ALTER ROLE app_user SET work_mem = '16MB';

Trade-offs

Plan stability vs plan optimality
  • Stable plans (force hints/fixed plans): Predictable latency, no surprise regressions, but may be suboptimal as data changes. Requires manual plan review as data grows.
  • Adaptive plans (let optimizer choose): Optimal for current data, but vulnerable to sudden plan changes when statistics shift. Requires robust monitoring.
  • Compromise: Let the optimizer choose, but alert on plan changes >3x regression. Use hints only as emergency fixes while investigating root cause.
  • Spark AQE approach: Best of both — compile-time plan is a starting point, runtime adaptation handles actual cardinality. Only available in modern engines.
Frequent ANALYZE vs I/O overhead
  • Frequent ANALYZE (every 1% change): Always-fresh statistics, minimal plan regressions, but consumes I/O and CPU for sampling. On 1B-row tables, ANALYZE itself takes minutes.
  • Infrequent ANALYZE (default 10% threshold): Less overhead, but statistics can be stale for days on large tables. Vulnerable to distribution shifts between ANALYZEs.
  • Targeted ANALYZE: Only analyze columns used in WHERE/JOIN clauses of critical queries. Faster than full-table ANALYZE, keeps critical statistics fresh.
  • Recommendation: Lower threshold to 1-2% for customer-facing query tables; keep 10% for internal/batch tables where latency isn't critical.
Composite indexes vs flexibility
  • Composite index (a, b, c): Optimal for queries filtering on a, (a,b), or (a,b,c). Provides plan stability regardless of cardinality estimates. But only helps leftmost-prefix queries.
  • Single-column indexes (a), (b), (c): More flexible — optimizer can combine with BitmapAnd. But plan depends heavily on cardinality estimates being correct. Vulnerable to plan regressions when estimates drift.
  • Trade-off: For critical queries with known access patterns, composite indexes provide insurance against plan regressions. For ad-hoc analytics, single-column indexes + bitmap combine give flexibility.
work_mem: memory vs spill risk
  • High work_mem (256MB+): Prevents spill for most operations. But with 100+ concurrent connections, total memory demand can exceed available RAM → OOM risk.
  • Low work_mem (4-16MB): Safe for high-concurrency OLTP. But analytical queries will spill to disk, creating unpredictable latency spikes when data grows past the threshold.
  • Dynamic approach: Low default (16MB) + per-role overrides (analytics: 256MB). Or use connection pooling with separate pools for OLTP (low mem) vs analytics (high mem).
  • Formula: work_mem × max_parallel_workers_per_gather × max_connections should not exceed 50% of available RAM.
Autovacuum aggressiveness vs write throughput
  • Aggressive autovacuum: Low dead tuple percentage, fresh statistics, healthy tables. But vacuum competes with writes for I/O. On write-heavy tables, aggressive vacuum can reduce INSERT throughput by 10-20%.
  • Conservative autovacuum: Minimal impact on write throughput. But dead tuples accumulate, table bloat grows, and eventually vacuum takes much longer when it finally triggers (vicious cycle).
  • Best practice: Moderate aggression (1-2% threshold, 1000 cost_limit) for most tables. Very aggressive (0.1%, 2000 cost_limit) for tables with XID wraparound risk. Schedule manual VACUUM during off-peak hours for extreme cases.
Query rewriting vs infrastructure scaling
  • Query/index optimization: Addresses root cause, cheap, sustainable. But requires expertise, time to diagnose, and may not help if the query is already optimal and data simply outgrew the hardware.
  • Hardware scaling: Quick fix, buys time. But expensive, doesn't address inefficiency, and you'll hit the next cliff sooner. A bad plan on bigger hardware is still a bad plan.
  • Decision framework: If EXPLAIN shows a bad plan (NL where HJ needed, full scan where index possible), fix the plan first. If EXPLAIN shows an optimal plan but data exceeds hardware capacity (I/O bandwidth saturated, table larger than RAM), then scale. Usually it's 80% bad plans, 20% legitimate scaling needs.

Follow-up Questions

Q1: How would you prevent this from happening in a CI/CD pipeline?

Build regression detection into the deployment pipeline:

  • Query regression tests: Run critical queries against a staging database with production-scale data. Alert if latency exceeds baseline + 2 standard deviations.
  • EXPLAIN plan comparison: Capture EXPLAIN plans in staging vs production. Flag plan changes (different join types, scan types) for human review before deploy.
  • Statistics snapshot: After each deployment, snapshot pg_stats for critical tables. If statistics are significantly different from last deploy, auto-trigger ANALYZE.
  • Load testing with skewed data: Include worst-case parameter values (hot keys, NULL-heavy filters) in performance test suites.
  • Canary deploys: Route 5% of traffic to new version, monitor p99 latency. Auto-rollback if regression detected.

# CI/CD query regression check:
def check_query_regression(query, params, baseline_ms, threshold_factor=3.0):
    """Run in staging, compare against baseline."""
    import time
    conn = get_staging_connection()
    cur = conn.cursor()

    # Warm cache
    cur.execute(query, params)

    # Measure
    times = []
    for _ in range(5):
        start = time.time()
        cur.execute(query, params)
        cur.fetchall()
        times.append((time.time() - start) * 1000)

    p95 = sorted(times)[int(len(times) * 0.95)]

    if p95 > baseline_ms * threshold_factor:
        raise RegressionError(
            f"Query p95={p95:.0f}ms exceeds "
            f"{threshold_factor}x baseline ({baseline_ms}ms)"
        )
    return p95
Q2: How does this differ in distributed query engines (BigQuery, Snowflake)?

Distributed engines have different mechanisms but similar root causes:

  • BigQuery: No persistent plan cache (re-optimizes every query). Main causes of sudden slowdown: slot contention (shared multi-tenant resources), shuffle explosion from data skew, clustering key becoming ineffective after data growth.
  • Snowflake: Micro-partition pruning depends on natural clustering. If data ingestion changes (new ETL, different ordering), pruning effectiveness degrades. Also: warehouse auto-suspend/resume cold start, result cache invalidation.
  • Redshift: Similar to PostgreSQL (uses statistics, has ANALYZE). Additional: distribution key skew causing leader node bottleneck, WLM queue contention, commit queue buildup.
  • Key difference: In serverless engines, you don't control vacuum/autovacuum. The "sudden slow" is more often resource contention or data organization degradation than statistics drift.

Q4: Can you explain the relationship between VACUUM and ANALYZE?

They are separate operations that are often confused:

  • VACUUM: Reclaims space from dead tuples. Makes pages available for reuse. Does NOT update statistics (row estimates, histograms). Prevents XID wraparound.
  • ANALYZE: Samples the table and updates pg_stats (n_distinct, most_common_vals, histogram_bounds). Does NOT reclaim any space. Enables better plan choices.
  • VACUUM ANALYZE: Does both in one command. Autovacuum can trigger either independently based on separate thresholds.
  • Common confusion: "I ran VACUUM but the query is still slow" — VACUUM doesn't fix bad plans caused by stale statistics. You needed ANALYZE.
  • Autovacuum triggers: vacuum_threshold + scale_factor × n_tuples for dead tuples; analyze_threshold + scale_factor × n_tuples for modifications.
Q5: How do you handle this in a microservices environment with many databases?

At scale (50+ services, each with their own database), manual monitoring is impossible:

  • Centralized query observatory: Collect pg_stat_statements from all databases into a central metrics store (Prometheus/Thanos). Unified dashboards across all services.
  • Automated remediation: If staleness > threshold, auto-trigger ANALYZE via a management sidecar. If dead_pct > 30%, page on-call and schedule vacuum.
  • Standardized per-table configs: Terraform/Ansible-managed autovacuum settings per table classification (high-churn, read-heavy, mixed). Don't rely on defaults for any production table.
  • Query governance: Central registry of "critical queries" (checkout, payment, auth). These get enhanced monitoring: plan capture, regression alerts, automatic explain logging.
  • Shared DBA tooling: Internal CLI/bot that any team can run: "analyze my table", "show my bloat", "explain my slow query". Lowers the expertise barrier for application teams.
Q6: What is the difference between plan regression and query regression?
  • Plan regression: The execution plan changed (different join algorithm, different scan type, different join order). Same query text, different plan → performance change. Root cause is usually statistics drift, plan cache, or data distribution change.
  • Query regression: Broader term — any degradation in query performance. Can be caused by plan regression, OR by resource contention, data growth (more I/O even with same plan), lock waits, network issues, etc.
  • Key distinction: Plan regression is identifiable by comparing EXPLAIN output. Query regression without plan regression means the plan is the same but something external changed (more data, less resources, more contention).
  • Debugging approach differs: Plan regression → fix statistics/indexes/hints. Non-plan regression → fix resources/contention/data management.

Summary

Key takeaways
  • The query text is constant, but the plan is not. Execution plans depend on statistics, parameter values, available memory, and data distribution — all of which change over time.
  • Statistics drift is the #1 cause. Large tables (100M+ rows) can have stale statistics for days because autovacuum's default 10% threshold requires millions of changes to trigger. Always run ANALYZE after bulk operations.
  • Cardinality errors create tipping points. A 10x underestimate can flip a plan from Hash Join (fast) to Nested Loop (catastrophic). These transitions are discontinuous — fine one day, 100x slower the next.
  • Parameter sniffing poisons plan caches. The first execution's parameters determine the plan for all subsequent executions. Atypical first-call values create permanently bad cached plans.
  • Data skew amplifies all issues. Hot keys, seasonal patterns, and non-uniform distributions invalidate the optimizer's independence assumptions and uniform distribution models.
  • work_mem boundaries cause cliff effects. Hash joins and sorts perform well until they exceed work_mem, then suddenly spill to disk with 10-100x latency increase.
  • Vacuum debt compounds. Dead tuples make tables larger → sequential scans slower → buffer cache less effective → more disk I/O → everything degrades gradually then suddenly.
  • Composite indexes provide plan stability. An index that exactly matches the query pattern gives consistent plans regardless of statistics accuracy.
  • Monitoring is prevention. Track statistics freshness, plan changes, spill events, and dead tuple ratios. Alert before users notice, not after SLA breach.

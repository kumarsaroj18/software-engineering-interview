Hard Query Engine Optimizer

How Does a SQL Query Actually Execute Inside a Distributed Query Engine?

Key Takeaway: A SQL query traverses five major phases—parsing, logical planning, optimization, physical planning, and distributed execution—each offering distinct opportunities for performance tuning. Understanding this pipeline is critical for diagnosing why a query that "should be fast" runs slowly in production.

What the Interviewer Is Really Evaluating

Why this question separates senior from staff-level engineers

This question is a "depth probe." The interviewer wants to see whether you can go beyond surface-level SQL syntax and explain the machinery underneath. At the Senior/Staff level, you are expected to troubleshoot query performance across distributed systems—and that requires understanding the full execution pipeline.

The interviewer is assessing:

  • Systems thinking: Can you trace a query from text to distributed execution across hundreds of nodes?
  • Optimizer intuition: Do you understand why the engine chose a hash join over a sort-merge join?
  • Debugging skill: When a query regresses from 30 seconds to 5 minutes, can you pinpoint the root cause?
  • Cross-engine literacy: Can you contrast how BigQuery, Snowflake, Spark SQL, and PostgreSQL handle the same query differently?
  • Production awareness: Do you know how statistics staleness, data skew, and partition pruning affect real workloads?

A strong answer demonstrates the full pipeline with concrete examples from at least two engines, discusses trade-offs at each phase, and connects theory to production debugging scenarios.

60-Second Interview Answer

Concise answer you can deliver under pressure

"A SQL query goes through five phases. First, the parser tokenizes the SQL text and builds an Abstract Syntax Tree, validating syntax. Second, a logical plan is generated—a tree of relational algebra operators like Scan, Filter, Project, Join, and Aggregate. Third, the optimizer rewrites this plan using heuristic rules (predicate pushdown, constant folding) and then a cost-based optimizer enumerates candidate plans, using table statistics and cardinality estimates to pick the cheapest. Fourth, the physical plan maps logical operators to concrete algorithms—hash join vs. sort-merge join, hash aggregate vs. sort aggregate. Finally, in a distributed engine, the execution layer partitions the plan into stages separated by shuffle/exchange boundaries, distributes fragments across worker nodes, and executes them using either a Volcano iterator model, vectorized batch processing, or compiled push-based execution. Runtime optimizations like Adaptive Query Execution in Spark can re-optimize mid-flight based on actual data statistics observed during shuffles."

This answer hits all five phases in under 60 seconds. Now let's go deep on each.

Parsing & Grammar

The parser applies SQL grammar rules (typically LALR(1) or recursive descent) to build a tree structure. PostgreSQL uses a Bison-generated parser with ~200 grammar rules. Spark SQL uses ANTLR4.

Engine Parsers: PostgreSQL uses gram.y (Bison/Yacc). Spark SQL uses ANTLR4 with SqlBase.g4. BigQuery and Snowflake use proprietary parsers that extend standard SQL with their dialect-specific extensions (QUALIFY, PIVOT, FLATTEN).

Semantic Analysis (Binding Phase)

After parsing, the analyzer resolves identifiers against the catalog:

  • Resolves table names to physical storage locations
  • Resolves column names and checks type compatibility
  • Expands SELECT * to explicit column lists
  • Validates function signatures and return types
  • Resolves implicit type casts (e.g., INT compared to BIGINT)

Interview trap: Candidates often skip the binding phase. Without catalog resolution, the engine cannot determine column types, which are required for choosing comparison operators and hash functions downstream.

Logical Plan

Relational algebra operators: Scan, Filter, Project, Join, Aggregate

The logical plan represents the query as a tree of relational algebra operators, independent of any physical implementation. This abstraction allows the optimizer to reason about equivalences and transformations.

Core Relational Operators

Operator Symbol Description SQL Equivalent
Scan (TableScan) R Read all rows from a relation FROM table
Selection (Filter) σ Filter rows by predicate WHERE / HAVING
Projection π Select specific columns SELECT col1, col2
Join ⋈ Combine rows from two relations JOIN ... ON
Aggregation γ Group and compute aggregates GROUP BY + SUM/COUNT
Sort τ Order tuples ORDER BY
Limit λ Restrict output cardinality LIMIT / TOP

Key insight: The logical plan is declarative—it specifies WHAT to compute, not HOW. The same logical plan can map to dozens of different physical execution strategies. This separation of concerns is what makes query optimizers possible.

Unresolved vs. Resolved Plans

Spark Catalyst distinguishes between:

  • Unresolved Plan: References column names as strings, tables not yet looked up
  • Analyzed Plan: All references resolved, types assigned, implicit casts added
  • Optimized Plan: Rule-based transformations applied

Query Rewriting (Rule-Based Optimization)

Constant folding, predicate pushdown, common subexpression elimination

Before the cost-based optimizer runs, a series of heuristic rewrite rules transform the logical plan. These rules are always beneficial regardless of data distribution or table sizes.

Key Rewrite Rules

1. Predicate Pushdown

Move filter predicates as close to the data source as possible, reducing the number of rows flowing through the plan.

BEFORE:                              AFTER:
─────────                            ─────────
  Filter(created_at >= '2024-01-01')   Join
      │                                 / \
    Join                               /   \
    / \                        Filter(≥)  Scan(customers)
   /   \                           │
Scan(orders) Scan(customers)   Scan(orders)
        
-- Before pushdown: filter applied AFTER join (processes all rows)
-- After pushdown: filter applied BEFORE join (eliminates rows early)

-- In BigQuery, partition pruning is a form of predicate pushdown:
SELECT * FROM `project.dataset.events`
WHERE _PARTITIONDATE >= '2024-01-01'  -- Pushed to storage layer
  AND event_type = 'purchase';         -- Pushed to column reader

2. Constant Folding

Evaluate constant expressions at compile time:

-- Before constant folding
WHERE created_at >= CAST('2024-01-01' AS DATE) + INTERVAL '7' DAY

-- After constant folding
WHERE created_at >= '2024-01-08'

3. Projection Pruning (Column Pruning)

Only read columns that are actually referenced downstream. Critical for columnar formats (Parquet, ORC) where entire column chunks can be skipped.

BEFORE: Scan(orders) → reads ALL 50 columns
AFTER:  Scan(orders[order_id, customer_id, amount, created_at]) → reads 4 columns

Impact on Parquet: Skip 46 column chunks per row group
Typical speedup: 5-20x for wide tables

4. Common Subexpression Elimination

-- Before
SELECT
  UPPER(TRIM(name)) AS display_name,
  LENGTH(UPPER(TRIM(name))) AS name_length
FROM customers;

-- After (internally): compute UPPER(TRIM(name)) once, reuse
-- The optimizer creates a temporary reference for the shared expression

5. Boolean Expression Simplification

-- Before
WHERE (status = 'active' AND status = 'active') OR (1 = 0)
-- After
WHERE status = 'active'

6. Subquery Decorrelation

Transform correlated subqueries into joins—one of the most impactful rewrites:

-- Before (correlated subquery - executes once per outer row)
SELECT * FROM orders o
WHERE o.amount > (
  SELECT AVG(amount) FROM orders WHERE customer_id = o.customer_id
);

-- After (decorrelated - single pass with window or join)
SELECT o.* FROM orders o
JOIN (
  SELECT customer_id, AVG(amount) as avg_amt
  FROM orders GROUP BY customer_id
) agg ON o.customer_id = agg.customer_id
WHERE o.amount > agg.avg_amt;

Cost-Based Optimizer (CBO)

Statistics, cardinality estimation, plan enumeration, cost models

While rule-based rewrites are "always good," the CBO must choose between alternatives that depend on data characteristics. A hash join is better for large unsorted inputs; a merge join is better when both sides are pre-sorted. The CBO uses statistics to make these decisions.

Cardinality Estimation

The most critical (and error-prone) component. Estimates how many rows each operator will produce.

Selectivity Estimation Formulas:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Equality predicate:    sel(col = value) = 1 / NDV(col)
Range predicate:       sel(col > value) = (max - value) / (max - min)
AND combination:       sel(A AND B) = sel(A) × sel(B)  [independence assumption]
OR combination:        sel(A OR B) = sel(A) + sel(B) - sel(A) × sel(B)
JOIN selectivity:      sel(R.a = S.b) = 1 / max(NDV(R.a), NDV(S.b))
LIKE prefix:           sel(col LIKE 'abc%') ≈ 1 / NDV(col)  [heuristic]

Cardinality after filter:
  |σ_p(R)| = |R| × sel(p)

Cardinality after join:
  |R ⋈ S| = (|R| × |S|) / max(NDV(R.join_col), NDV(S.join_col))

The Independence Assumption is often WRONG. If you filter on city = 'Seattle' AND state = 'WA', the optimizer estimates sel = (1/1000) × (1/50) = 1/50000. The real selectivity is ~1/1000 because city implies state. This causes massive underestimates leading to nested-loop joins on large datasets. PostgreSQL 10+ added extended statistics (CREATE STATISTICS) to handle correlated columns.

Cost Model

The optimizer assigns a numeric cost to each physical plan and picks the minimum. Costs model three resource dimensions:

Total Cost = w_io × C_io + w_cpu × C_cpu + w_net × C_network

Where:
━━━━━━

C_io (I/O Cost):
  Sequential scan:  C_io = pages × seq_page_cost
  Random I/O:       C_io = pages × random_page_cost
  (PostgreSQL: seq_page_cost = 1.0, random_page_cost = 4.0)

C_cpu (CPU Cost):
  Per-tuple:        C_cpu = tuples × cpu_tuple_cost
  Per-operator:     C_cpu += tuples × cpu_operator_cost
  (PostgreSQL: cpu_tuple_cost = 0.01, cpu_operator_cost = 0.0025)

C_network (Distributed Only):
  Shuffle cost:     C_net = rows × avg_row_size × network_cost_per_byte
  Broadcast cost:   C_net = |small_table| × num_nodes × network_cost_per_byte

Hash Join Cost:
  Build phase:  C = |build_side| × (cpu_tuple_cost + cpu_operator_cost)
  Probe phase:  C = |probe_side| × (cpu_tuple_cost + cpu_operator_cost)
  Total:        C = C_build + C_probe + C_io(read both tables)

Sort-Merge Join Cost:
  Sort phase:   C = |R| × log(|R|) + |S| × log(|S|) [if not pre-sorted]
  Merge phase:  C = |R| + |S|
  Total:        C = C_sort_R + C_sort_S + C_merge

Plan Enumeration

For N tables, there are (2N-2)! / (N-1)! possible join orderings. With N=10 tables, that's ~17 billion plans. Optimizers use:

  • Dynamic Programming (PostgreSQL, Spark): Bottom-up, optimal for ≤12 tables. Considers all pair-wise joins, memoizes sub-plans.
  • Greedy/Heuristic (large queries): PostgreSQL switches to GEQO (Genetic Query Optimizer) for >12 tables.
  • Cascades Framework (SQL Server, newer engines): Top-down, rule-based exploration with memoization. More extensible.
-- PostgreSQL: force the optimizer to show its work
SET enable_hashjoin = off;  -- disable hash joins to see alternatives
SET enable_mergejoin = off; -- force nested loop

-- Check if CBO is using histograms
SELECT * FROM pg_stats
WHERE tablename = 'orders' AND attname = 'created_at';

-- Spark SQL: enable CBO (off by default in older versions)
SET spark.sql.cbo.enabled = true;
SET spark.sql.cbo.joinReorder.enabled = true;

-- Collect statistics for CBO
ANALYZE TABLE orders COMPUTE STATISTICS FOR ALL COLUMNS;

Staff-level insight: In Snowflake, you never manually collect statistics—the system maintains them automatically via micro-partition metadata (min/max, NDV, null count per micro-partition). This is why Snowflake doesn't expose ANALYZE TABLE or histogram commands.

1. Volcano / Iterator Model

Each operator implements a next() method that returns one tuple at a time. The root operator "pulls" data by calling next() on its child, which recursively calls its children.

// Pseudo-code: Volcano Iterator Model
interface Operator {
    void open();
    Row next();    // Returns null when exhausted
    void close();
}

class FilterOperator implements Operator {
    Operator child;
    Predicate predicate;

    Row next() {
        while (true) {
            Row row = child.next();
            if (row == null) return null;  // exhausted
            if (predicate.evaluate(row)) return row;
        }
    }
}

class HashJoinOperator implements Operator {
    Operator buildChild, probeChild;
    HashMap<Key, List<Row>> hashTable;

    void open() {
        // Build phase: materialize entire build side
        buildChild.open();
        Row row;
        while ((row = buildChild.next()) != null) {
            Key k = extractKey(row);
            hashTable.computeIfAbsent(k, ArrayList::new).add(row);
        }
        probeChild.open();
    }

    Row next() {
        // Probe phase: stream probe side
        Row probeRow = probeChild.next();
        if (probeRow == null) return null;
        Key k = extractKey(probeRow);
        List<Row> matches = hashTable.get(k);
        // ... emit joined rows
    }
}

Volcano model bottleneck: For a query with 5 operators processing 100M rows, that's 500M virtual function calls just for next(). Each call causes instruction cache misses and branch mispredictions. This overhead dominates for in-memory workloads.

2. Vectorized Execution (Batch Processing)

Process data in batches (typically 1024-4096 rows). Each batch is a columnar array, enabling SIMD instructions and better cache utilization.

3. Compiled / Push-Based (Whole-Stage Code Generation)

Instead of interpreting a tree of operators, generate actual code (Java bytecode in Spark, LLVM IR in HyPer) that fuses multiple operators into a single tight loop.

// Spark Whole-Stage CodeGen output (simplified)
// Instead of: Scan → Filter → Project → Aggregate (4 operator calls per row)
// Generates a single fused function:

public void processPartition(Iterator<InternalRow> input) {
    // All operators fused into one loop - no virtual dispatch
    long sum = 0;
    int count = 0;

    while (input.hasNext()) {
        InternalRow row = input.next();

        // Filter (inlined)
        long created_at = row.getLong(3);
        if (created_at < 1704067200000L) continue;  // 2024-01-01 epoch ms

        // Project + Aggregate (inlined)
        long amount = row.getLong(2);
        sum += amount;
        count++;
    }

    // Emit aggregate result
    output.write(sum, count);
}

Spark CodeGen in practice: Check your Spark UI's "Details" for any stage. If you see WholeStageCodegen wrapping your operators, code generation is active. Operators that break codegen: SortMergeJoin (needs materialization), External Sort, any operator that spills to disk.

Runtime Optimizations

Runtime filters, Adaptive Query Execution (AQE), dynamic partition pruning

Traditional optimizers make all decisions at compile time based on statistics. Runtime optimizations adjust the plan during execution based on actual observed data.

Spark Adaptive Query Execution (AQE)

Introduced in Spark 3.0, AQE re-optimizes the plan at shuffle boundaries (materialization points) when actual row counts differ from estimates.

Runtime Bloom Filters

BigQuery and Spark use bloom filters built during the join's build phase to filter the probe side at scan time:

  • Build a bloom filter from the smaller join side's keys
  • Push the bloom filter down to the scan of the larger side
  • Skip row groups / micro-partitions whose keys are definitely not in the filter
  • False positive rate ~1% with typical sizing

Snowflake's runtime pruning: Snowflake uses "pruning" extensively — each micro-partition (50-500MB compressed) has min/max metadata for every column. At runtime, the engine checks join keys against micro-partition ranges to skip irrelevant data without bloom filters.

-- Same logical query on each engine
SELECT customer_id, SUM(amount) as total
FROM orders
WHERE created_at >= '2024-01-01'
GROUP BY customer_id
HAVING SUM(amount) > 10000
ORDER BY total DESC
LIMIT 100;

PostgreSQL Execution

Limit (100 rows)
  → Top-N HeapSort (sort on total DESC, keep top 100)
    → HashAggregate (group by customer_id, filter sum > 10000)
      → Seq Scan on orders (filter: created_at >= '2024-01-01')
         OR
      → Index Scan using idx_orders_created_at
         (if selectivity < ~5% of table)

Single process, single thread. work_mem bounds hash table size.
If hash table exceeds work_mem → spill to disk (batch mode).

BigQuery Execution

Stage 1 (Leaf Servers - thousands parallel):
  → Column scan from Colossus (only amount, customer_id, created_at)
  → Partition pruning via _PARTITIONDATE
  → Partial aggregate per shard

Stage 2 (Mixer/Shuffle):
  → Shuffle by hash(customer_id)
  → Final aggregate
  → Filter HAVING
  → Top-100 sort

Slots dynamically allocated. No disk spill visible to user.
Charged by bytes scanned (amount + customer_id + created_at columns only).

Snowflake Execution

1. Query compilation (cloud services layer)
2. Micro-partition pruning:
   → Zone maps eliminate partitions where max(created_at) < '2024-01-01'
   → Example: 1000 micro-partitions → 200 remain after pruning
3. Scan + partial aggregate (parallel across warehouse nodes)
   → Each node handles a subset of micro-partitions
   → Columnar scan: only read 3 columns
4. Redistribute by hash(customer_id) across nodes
5. Final aggregate + HAVING filter
6. Top-100 sort + return to client

Result cache checked first — if same query ran recently, instant return.

Spark SQL Execution

Stage 1 (Map tasks - one per Parquet file/partition):
  → FileScan parquet [customer_id, amount, created_at]
  → Filter (pushed to Parquet reader: row group pruning)
  → Partial HashAggregate (per partition)
  → WholeStageCodegen wraps all above

--- Shuffle (hash on customer_id, 200 partitions default) ---

Stage 2 (Reduce tasks):
  → ShuffleRead
  → Final HashAggregate
  → Filter (HAVING)
  → TakeOrderedAndProject (top 100 by total DESC)
  → WholeStageCodegen wraps all above

With AQE: if partitions are skewed or too small, coalesce/split dynamically.

Key difference: PostgreSQL uses a single-threaded execution with no parallelism for most queries. BigQuery and Snowflake automatically parallelize across hundreds of nodes. Spark requires explicit cluster provisioning but gives you control over parallelism (number of executors, cores, memory).

Production Incident: The Cardinality Estimation Cliff

Query ran fine for 6 months, then suddenly took 10x longer

Real incident pattern — this scenario appears regularly at FAANG companies and is a common interview discussion topic.

Timeline

Optimizer's reasoning:
  "orders WHERE category = 'electronics'" → 200M × 0.05 = 10M rows (estimated)
  Actual: 200M × 0.35 = 70M rows

  With 10M estimated rows on probe side:
    → Nested Loop with Index Scan on dimension table seems cheap
    → Cost = 10M × (index_lookup_cost) = 10M × 4.0 = 40M

  With 70M actual rows:
    → Nested Loop = 70M × 4.0 = 280M cost (7x worse!)
    → Hash Join would be: 70M + 100K (build dim) = 70.1M cost

The Fix (and Prevention)

-- Immediate fix: update statistics with higher granularity
-- PostgreSQL
ALTER TABLE orders ALTER COLUMN product_category
  SET STATISTICS 1000;  -- default is 100, increase histogram buckets
ANALYZE orders;

-- Verify the plan changed
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT o.*, p.name FROM orders o
JOIN products p ON o.product_id = p.id
WHERE o.product_category = 'electronics';

-- Spark SQL: if CBO is enabled, recompute
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS product_category;

-- Long-term prevention:
-- 1. Schedule ANALYZE after large batch loads
-- 2. Monitor plan changes with pg_stat_statements
-- 3. Use extended statistics for correlated columns
CREATE STATISTICS orders_category_date (dependencies)
  ON product_category, created_at FROM orders;

How Each Engine Would Handle This

  • PostgreSQL: Plan fixed at compile time. Stale stats → wrong plan. Must re-ANALYZE.
  • BigQuery: Auto-maintains stats. Less likely to hit this, but can still occur with heavily skewed data. Slot-based execution means even a "bad" plan just uses more slots.
  • Snowflake: Zone maps updated per micro-partition automatically. Unlikely to hit this for partition pruning. Join strategy might still be suboptimal.
  • Spark SQL (AQE): After Stage 1 shuffle materializes, AQE observes actual row count (70M vs estimated 10M) and re-optimizes. The join strategy switches at runtime. This is the ideal behavior.

Interview gold: Telling this story demonstrates you've debugged real production issues. Key signals: knowing that statistics go stale, understanding the cascading effect on plan choice, and knowing engine-specific mitigations (AQE, extended statistics, auto-ANALYZE).

Code Examples: Same Query, Different Plans

SQL examples showing how different structures produce different execution plans

Example 1: JOIN Order Matters

-- Query A: Small table driving large table (optimal)
SELECT c.name, COUNT(*) as order_count
FROM customers c                          -- 100K rows (driving table)
JOIN orders o ON c.id = o.customer_id     -- 200M rows
WHERE c.country = 'US'                    -- filters customers to ~30K
GROUP BY c.name;

-- Plan: BroadcastHashJoin
--   Build side: customers filtered to 30K rows (broadcast to all executors)
--   Probe side: orders (200M rows, partitioned across executors)
--   No shuffle needed for orders!

-- Query B: Same result, but written differently
SELECT c.name, COUNT(*) as order_count
FROM orders o                             -- 200M rows (driving table)
JOIN customers c ON o.customer_id = c.id  -- 100K rows
WHERE c.country = 'US'
GROUP BY c.name;

-- Smart optimizer: produces same plan (join reordering)
-- Naive executor: might shuffle orders first → 200M row shuffle!

Example 2: Subquery vs JOIN vs EXISTS

-- Version A: Correlated subquery (potentially N+1 execution)
SELECT * FROM orders o
WHERE o.amount > (
  SELECT AVG(amount) FROM orders WHERE customer_id = o.customer_id
);

-- PostgreSQL plan (may use):
-- Seq Scan on orders
--   Filter: amount > (SubPlan 1)
--   SubPlan 1: Aggregate (executes ONCE PER ROW of outer query!)
-- Danger: 200M rows × 1 subplan execution = 200M aggregate queries

-- Version B: Window function (single pass)
SELECT * FROM (
  SELECT *, AVG(amount) OVER (PARTITION BY customer_id) as avg_amt
  FROM orders
) sub
WHERE amount > avg_amt;

-- Plan: Single Seq Scan → Window (Sort + Running Avg) → Filter
-- Much better: one pass through the data

-- Version C: Self-join with pre-aggregation
SELECT o.* FROM orders o
JOIN (
  SELECT customer_id, AVG(amount) as avg_amt
  FROM orders GROUP BY customer_id
) agg ON o.customer_id = agg.customer_id
WHERE o.amount > agg.avg_amt;

-- Plan: HashAggregate (build) → HashJoin (probe with full orders table)
-- Good for distributed: aggregate can be done with partial+final pattern

Example 3: Partition Pruning Effectiveness

-- Query A: Partition column in WHERE (excellent pruning)
SELECT * FROM events
WHERE event_date = '2024-06-15'  -- Prunes to 1 partition
  AND user_id = 12345;

-- BigQuery: scans ~1/365th of the table
-- Snowflake: scans micro-partitions where min(event_date) <= '2024-06-15'
--            AND max(event_date) >= '2024-06-15'

-- Query B: Function on partition column (NO pruning!)
SELECT * FROM events
WHERE YEAR(event_date) = 2024 AND MONTH(event_date) = 6
  AND DAY(event_date) = 15
  AND user_id = 12345;

-- Disaster: wrapping partition column in a function prevents pruning
-- Full table scan even though logically equivalent to Query A!

-- Query C: Expression that DOES allow pruning (engine-dependent)
SELECT * FROM events
WHERE event_date BETWEEN '2024-06-15' AND '2024-06-15'
  AND user_id = 12345;
-- Most engines handle BETWEEN correctly for pruning

Pitfalls that trip up even experienced engineers

Trade-offs in Query Execution Design

Key architectural decisions and their implications

1. Compile Time vs. Runtime Optimization

Approach Pros Cons Used By
Compile-time only Predictable, low overhead, easier debugging Cannot adapt to estimation errors, data skew PostgreSQL, MySQL
Runtime adaptive Handles stale stats, skew, dynamic workloads More complex, re-optimization overhead, harder to debug Spark AQE, BigQuery, Snowflake

2. Push vs. Pull Execution

Model Pros Cons
Pull (Volcano) Simple implementation, natural backpressure, easy to add operators Virtual call overhead, poor cache utilization, no SIMD
Push (compiled) Tight loops, cache-friendly, SIMD potential, no virtual dispatch Complex implementation, compilation latency, harder to cancel mid-stream
Vectorized Balance of both: batch amortizes overhead, SIMD-friendly, still interpretable Batch size tuning, memory overhead for buffers

3. Shuffle vs. Broadcast

Strategy Pros Cons Use When
Shuffle (repartition) Works for any size; enables parallel join Network I/O proportional to data; disk spill; latency Both sides large; no table fits in memory
Broadcast No shuffle of large side; very fast for large-small joins Memory pressure if "small" side is actually large; OOM risk One side < broadcast threshold (10MB Spark, varies by engine)

4. Statistics Freshness vs. Overhead

  • Manual ANALYZE: No overhead until run; risk of stale stats (PostgreSQL default)
  • Auto-vacuum ANALYZE: Triggers after N% row changes; moderate overhead (PostgreSQL with autovacuum)
  • Continuous/automatic: Always fresh; storage metadata overhead (BigQuery, Snowflake)
  • Runtime sampling: Sample at execution time; adds latency but always accurate (some experimental systems)

5. Memory vs. Disk Trade-off

Memory Budget Decision Tree:
━━━━━━━━━━━━━━━━━━━━━━━━━━━

Hash table fits in memory?
├── YES → In-memory hash join/aggregate (fastest)
│         └─ Risk: OOM if estimate wrong
└── NO  → Spill strategy:
          ├── Grace Hash Join (partition + spill)
          │   └─ 2-3x slower, but bounded memory
          ├── External Sort-Merge
          │   └─ Disk I/O bound, but handles any size
          └── Hybrid (Spark): try in-memory, fall back to spill

PostgreSQL: work_mem controls per-operation memory (default 4MB)
Spark: spark.executor.memory + spark.memory.fraction (unified pool)
Snowflake: automatic, warehouse-sized (no user tuning)
BigQuery: automatic, slot-based allocation

Interview insight: When discussing trade-offs, demonstrate that you understand there is no universally "best" choice. The optimal strategy depends on data size, distribution, available resources, latency requirements, and workload patterns. Staff engineers choose based on workload characteristics, not dogma.

Follow-up Questions the Interviewer May Ask

Prepare for these depth probes
  1. "How would you handle a skewed join where one key has 90% of the data?"

    Answer framework: Identify the hot key, salt the join (append random suffix to hot key, replicate the other side), or use AQE skew handling. In BigQuery, this is handled automatically by dynamic work rebalancing. In Spark, enable spark.sql.adaptive.skewJoin.enabled.

  2. "Why might a query be fast in PostgreSQL but slow in Spark for small data?"

    Answer: Spark has high startup overhead (JVM launch, DAG scheduling, shuffle setup). For <100MB datasets, the overhead dominates. PostgreSQL processes immediately with no distributed coordination. Spark shines at TB+ scale.

  3. "How does the optimizer decide between a hash join and sort-merge join?"

    Answer: CBO compares estimated costs. Hash join: O(build) + O(probe), needs memory for build side. Sort-merge: O(N log N + M log M) for sorting + O(N+M) for merge, but can exploit existing sort order. If inputs are pre-sorted (index or previous sort), merge join avoids sort cost. If memory is limited, merge join streams without materializing a hash table.

  4. "What happens when a hash table spills to disk?"

    Answer: Grace Hash Join — partition both inputs by hash into B buckets. Process one bucket pair at a time. Each bucket is small enough for memory. Recursive partitioning if a single bucket still too large. 2-3x slower than in-memory due to extra I/O passes.

  5. "How does BigQuery achieve sub-second queries on petabyte tables?"

    Answer: (1) Capacitor columnar format enables reading only needed columns. (2) Dremel tree with thousands of leaf servers provides massive parallelism. (3) Aggressive caching and materialized views. (4) Partition pruning eliminates irrelevant data. (5) Slots are shared across the org — not waiting for cluster provisioning.

  6. "Explain whole-stage code generation in Spark."

    Answer: Instead of interpreting a tree of operators (virtual dispatch per row), Spark generates Java bytecode that fuses multiple operators into a single function. The generated code is a tight loop with no virtual calls, keeping data in CPU registers. This eliminates interpretation overhead and enables JIT optimizations. Boundaries: shuffles, sorts, and broadcast builds break codegen stages.

  7. "How do you decide the number of shuffle partitions?"

    Answer: Target ~128MB-256MB per partition for optimal parallelism vs. overhead balance. Formula: total_shuffle_data / target_partition_size. For 100GB shuffle: 100GB / 200MB = 500 partitions. Too few → memory pressure and skew sensitivity. Too many → scheduling overhead and small file problem. AQE coalesces automatically in Spark 3.0+.

  8. "What is the difference between logical and physical optimization?"

    Answer: Logical optimization transforms the plan using algebraic equivalences (same result, fewer operations) — predicate pushdown, join reorder. Physical optimization selects concrete algorithms (hash vs. merge join) and execution strategies (broadcast vs. shuffle) based on cost estimates. Logical is "what to compute," physical is "how to compute it."

Summary

Key points to remember
  1. Five phases: Parse → Logical Plan → Optimize → Physical Plan → Distributed Execution. Know what happens at each boundary.
  2. Parsing converts SQL text to an AST via tokenization and grammar rules. Semantic analysis resolves names and types against the catalog.
  3. Logical plan is a tree of relational algebra operators (Scan, Filter, Project, Join, Aggregate) independent of physical implementation.
  4. Rule-based rewriting applies always-beneficial transformations: predicate pushdown, projection pruning, constant folding, subquery decorrelation.
  5. Cost-based optimization uses table statistics and cardinality estimation to enumerate and compare plan alternatives. The independence assumption is its Achilles' heel.
  6. Physical planning maps logical operators to algorithms: hash join vs. sort-merge vs. nested loop, hash aggregate vs. sort aggregate.
  7. Three execution models: Volcano (row-at-a-time, simple), Vectorized (batch, SIMD-friendly), Compiled (fused code, fastest for CPU-bound).
  8. Distributed execution splits the plan into stages at shuffle/exchange boundaries. Data redistribution (shuffle) is the most expensive operation in distributed queries.
  9. Runtime optimizations (AQE, DPP, runtime bloom filters) adapt the plan during execution based on actual data, fixing estimation errors.
  10. Stale statistics are the #1 cause of query performance regressions. Always ANALYZE after bulk loads, or use engines with automatic stats maintenance.
  11. Cross-engine literacy: PostgreSQL is single-node Volcano; BigQuery is serverless vectorized Dremel tree; Snowflake is vectorized push with automatic scaling; Spark is whole-stage codegen with AQE.
  12. Debugging: EXPLAIN ANALYZE (PostgreSQL), Spark UI SQL tab, BigQuery Execution Details, Snowflake Query Profile. Always compare estimated vs. actual row counts.

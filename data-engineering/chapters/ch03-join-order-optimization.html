How Do Query Optimizers Determine Join Order?

Join Algorithms Cardinality

Interviewer Intent

What is the interviewer really testing?

When a senior Data Engineer is asked "How do query optimizers determine join order?", the interviewer is probing multiple dimensions:

  • Depth of systems knowledge — Can you explain the internal mechanics of a query optimizer beyond "it picks the best plan"?
  • Cost model understanding — Do you know what factors (I/O, CPU, memory, network) contribute to plan cost?
  • Practical debugging ability — Have you actually diagnosed slow queries caused by suboptimal join ordering in production?
  • Cross-engine awareness — Can you contrast how PostgreSQL, Spark, BigQuery, and Snowflake each handle this differently?
  • Scale reasoning — Do you understand why join order matters exponentially more as table count grows (N! possible orderings)?
  • Trade-off articulation — Can you explain when to let the optimizer decide vs. when to override it?

This question separates candidates who merely write SQL from those who understand why their SQL performs the way it does at scale.

Quick Answer

30-second elevator pitch

Query optimizers determine join order through cost-based enumeration. They estimate the cardinality (row count) of each intermediate join result using table statistics (histograms, NDV, null fractions), then enumerate possible join orderings — using dynamic programming for small table counts (<12) or heuristic/genetic algorithms for larger counts. Each candidate plan is scored by a cost model that accounts for I/O, CPU, memory, and (in distributed systems) shuffle/network cost. The optimizer picks the plan with the lowest estimated total cost.

The critical insight: for N tables, there are (2N-2)! / (N-1)! possible join trees. A 10-table join has ~17 billion possible orderings. The optimizer must prune this search space efficiently while avoiding plans that produce massive intermediate results.

In practice, join order optimization fails when: (1) statistics are stale or missing, (2) the independence assumption between columns is violated, or (3) correlated predicates cause cardinality underestimation that cascades through the plan.

Join Algorithms Explained

Nested Loop Join

The nested loop join (NLJ) is the simplest algorithm: for each row in the outer table, scan the inner table for matching rows.

# Pseudocode: Nested Loop Join
def nested_loop_join(outer_table, inner_table, join_key):
    results = []
    for outer_row in outer_table:          # O(|outer|)
        for inner_row in inner_table:      # O(|inner|) per outer row
            if outer_row[join_key] == inner_row[join_key]:
                results.append(merge(outer_row, inner_row))
    return results
    # Total cost: O(|outer| * |inner|)

When Optimizers Choose NLJ

  • Small outer table — When the outer (driving) table has very few rows (typically <1000 after filtering)
  • Indexed inner table — When an index exists on the join key of the inner table, converting the inner scan to O(log N) lookups
  • Non-equi joins — For inequality joins (<, >, BETWEEN) where hash join cannot be used
  • LATERAL / correlated subqueries — Where the inner query depends on the outer row

Hash Join

The hash join operates in two phases: build and probe. It is the workhorse algorithm for equi-joins on large tables.

# Pseudocode: Hash Join (Build + Probe)
def hash_join(build_table, probe_table, join_key):
    # Phase 1: BUILD — hash the smaller table into memory
    hash_table = {}
    for row in build_table:                   # O(|build|)
        key = row[join_key]
        hash_table.setdefault(key, []).append(row)
    
    # Phase 2: PROBE — stream the larger table
    results = []
    for row in probe_table:                   # O(|probe|)
        key = row[join_key]
        if key in hash_table:                 # O(1) average lookup
            for match in hash_table[key]:
                results.append(merge(row, match))
    return results
    # Total cost: O(|build| + |probe|)

Memory Implications and Spill-to-Disk

The build side hash table must fit in work_mem (PostgreSQL) or the executor's memory budget. When it doesn't:

  • Grace Hash Join — Partitions both tables by hash into buckets, processes each bucket pair independently
  • Hybrid Hash Join — Keeps one partition in memory, spills the rest
  • Spark — Spills partitions to disk via ExternalAppendOnlyUnsafeRowArray, configurable via spark.sql.autoBroadcastJoinThreshold

Build Side Selection is Critical

The optimizer always puts the smaller table on the build side. If it gets this wrong (due to bad cardinality estimates), the hash table won't fit in memory, causing spill and potentially 10-100x slowdown.

Sort-Merge Join

Sort-merge join sorts both inputs on the join key, then merges them with a two-pointer technique. Efficient when data is already sorted (index scans, preceding ORDER BY).

# Pseudocode: Sort-Merge Join (Two-Finger Approach)
def sort_merge_join(left_table, right_table, join_key):
    # Phase 1: SORT both tables (skip if already sorted)
    left_sorted = sort(left_table, key=join_key)    # O(L log L)
    right_sorted = sort(right_table, key=join_key)  # O(R log R)
    
    # Phase 2: MERGE with two pointers
    results = []
    i, j = 0, 0
    while i < len(left_sorted) and j < len(right_sorted):
        left_key = left_sorted[i][join_key]
        right_key = right_sorted[j][join_key]
        
        if left_key == right_key:
            # Handle duplicates: collect all matches
            j_start = j
            while j < len(right_sorted) and right_sorted[j][join_key] == left_key:
                results.append(merge(left_sorted[i], right_sorted[j]))
                j += 1
            i += 1
            j = j_start  # Reset for next left duplicate
        elif left_key < right_key:
            i += 1
        else:
            j += 1
    return results
    # Total cost: O(L log L + R log R + L + R)

When Optimizers Choose Sort-Merge

  • Pre-sorted data — Both inputs come from index scans or prior sorts (eliminates sort phase cost)
  • Range joins — For BETWEEN, <, > conditions where hash cannot be used
  • Very large tables — When neither fits in memory but both can be sorted externally
  • Merge-join-able operators — Equality on sortable data types

Dynamic Programming (System R Approach)

The classic approach from IBM's System R (1979) uses bottom-up dynamic programming:

# System R Dynamic Programming Join Enumeration
# Key insight: optimal plan for subset S can be built from
# optimal plans of S's sub-partitions

def dp_join_enumeration(tables, join_graph):
    """
    Bottom-up DP for optimal join ordering.
    Time: O(3^N) for N tables (much better than N!)
    Space: O(2^N) to store optimal sub-plans
    """
    N = len(tables)
    # dp[S] = (best_cost, best_plan) for joining table set S
    dp = {}
    
    # Base case: single table access paths
    for i, table in enumerate(tables):
        subset = frozenset([i])
        dp[subset] = best_access_path(table)  # seq scan vs index scan
    
    # Build up: enumerate subsets of increasing size
    for size in range(2, N + 1):
        for subset in combinations_of_size(range(N), size):
            subset = frozenset(subset)
            best_cost = float('inf')
            best_plan = None
            
            # Try all ways to partition subset into two non-empty parts
            for left, right in partition_pairs(subset):
                # Only consider connected pairs (join predicate exists)
                if not connected(left, right, join_graph):
                    continue
                
                left_plan = dp[left]
                right_plan = dp[right]
                
                # Try each join algorithm
                for algo in [HASH_JOIN, MERGE_JOIN, NESTED_LOOP]:
                    cost = estimate_cost(left_plan, right_plan, algo)
                    if cost < best_cost:
                        best_cost = cost
                        best_plan = JoinPlan(left_plan, right_plan, algo)
            
            dp[subset] = (best_cost, best_plan)
    
    # Return optimal plan for joining all tables
    return dp[frozenset(range(N))]

Greedy and Genetic Algorithms for Large N

When N exceeds 10-12 tables, DP becomes impractical. Optimizers switch to heuristic approaches:

Greedy Heuristic

# Greedy Join Ordering (used as fallback)
def greedy_join_order(tables, join_graph):
    """
    At each step, pick the cheapest next join.
    Time: O(N^2) — fast but suboptimal
    """
    remaining = set(tables)
    # Start with the pair that produces smallest intermediate result
    best_pair = min(
        all_connected_pairs(remaining, join_graph),
        key=lambda pair: estimate_join_cardinality(*pair)
    )
    current_result = join(*best_pair)
    remaining -= set(best_pair)
    
    while remaining:
        # Pick next table that minimizes intermediate cardinality
        next_table = min(
            [t for t in remaining if connected(current_result, t, join_graph)],
            key=lambda t: estimate_join_cardinality(current_result, t)
        )
        current_result = join(current_result, next_table)
        remaining.remove(next_table)
    
    return current_result

Genetic Query Optimization (PostgreSQL GEQO)

PostgreSQL's GEQO (Genetic Query Optimizer) activates for queries with ≥ 12 tables (configurable via geqo_threshold):

  • Encodes join orderings as "genes" (permutations)
  • Crossover: combines parts of two good orderings
  • Mutation: randomly swaps join positions
  • Selection: keeps lowest-cost individuals
  • Runs for geqo_generations iterations (default: same as number of tables)
-- PostgreSQL GEQO configuration
SET geqo = on;                    -- Enable genetic optimizer
SET geqo_threshold = 12;          -- Switch to GEQO at 12+ tables
SET geqo_effort = 5;              -- 1-10, controls generations/pool size
SET geqo_generations = 0;         -- 0 = use default heuristic
SET geqo_pool_size = 0;           -- 0 = use default (2^(effort+1))
SET geqo_seed = 0.0;              -- Random seed for reproducibility

Why Left-Deep Trees Dominate in Row-Store OLTP

  • Pipelining: Each join's output streams directly into the next join's probe phase — no materialization needed
  • Memory: Only one hash table active at a time (the build side of the current join)
  • Simplicity: Smaller search space (N! vs super-exponential) allows exhaustive DP

Why Bushy Trees Win in Distributed Engines

  • Parallelism: Independent subtrees execute concurrently on different nodes
  • Intermediate reduction: Joining selective pairs first can dramatically reduce data before the final join
  • Spark/BigQuery: Both explore bushy trees because network shuffle cost dominates

Cardinality Estimation

How Cardinality Estimates Drive Join Order

Cardinality estimation is the single most critical input to join order optimization. If the optimizer mis-estimates how many rows a join produces, it will choose the wrong algorithm, the wrong join order, and potentially the wrong build side — each mistake compounding the next.

The Basic Selectivity Formula

# Simplified cardinality estimation for equi-join
def estimate_join_cardinality(left_table, right_table, join_col):
    """
    Basic formula (assumes uniform distribution):
    |A ⋈ B| = |A| * |B| / max(NDV(A.key), NDV(B.key))
    
    Where NDV = Number of Distinct Values
    """
    left_rows = left_table.row_count
    right_rows = right_table.row_count
    
    left_ndv = left_table.stats[join_col].n_distinct
    right_ndv = right_table.stats[join_col].n_distinct
    
    # Selectivity = 1 / max(NDV_left, NDV_right)
    selectivity = 1.0 / max(left_ndv, right_ndv)
    
    estimated_rows = left_rows * right_rows * selectivity
    return estimated_rows

Independence Assumption Failures

The most common source of estimation errors: optimizers assume predicates on different columns are statistically independent.

-- Classic independence assumption failure
SELECT count(*)
FROM customers
WHERE country = 'Japan' AND city = 'Tokyo';

-- Optimizer's estimate (assuming independence):
-- P(country='Japan') = 0.05
-- P(city='Tokyo')    = 0.01
-- P(both)            = 0.05 * 0.01 = 0.0005  → 500 rows (from 1M)
--
-- Reality (correlated!):
-- P(city='Tokyo' | country='Japan') ≈ 0.30
-- Actual rows: 0.05 * 0.30 * 1M = 15,000 rows
--
-- Estimation error: 30x underestimate!

Real-World Correlation Patterns That Break Estimates

  • Geographic correlation: country + city, state + zip_code
  • Temporal correlation: order_date + ship_date (ship always after order)
  • Business logic correlation: account_type + credit_limit, department + salary_band
  • Foreign key implied correlation: After joining, predicates on the FK table are correlated with the PK table's columns

BigQuery

Automatic Optimization with Slot-Based Cost Model

BigQuery's optimizer is fully automatic — no user hints for join order. Key characteristics:

  • Distributed cost model: Accounts for slot-hours (CPU), shuffle bytes, and memory per slot
  • Automatic repartitioning: Decides whether to broadcast or hash-partition each join side
  • No explicit ANALYZE: Maintains statistics automatically from metadata
  • Bushy trees allowed: Can parallelize independent join subtrees

BigQuery Cost Model Priorities

  1. Minimize shuffle bytes — Moving data between slots is expensive
  2. Broadcast small tables — If table < ~100MB, broadcast to avoid shuffle
  3. Filter pushdown — Apply WHERE clauses before joins to reduce data
  4. Partition pruning — Eliminate partitions before considering join order
Snowflake

Micro-Partition Pruning Informs Join Order

Snowflake's optimizer is unique because its micro-partition metadata heavily influences join ordering:

  • Micro-partition statistics: Min/max values, NDV, null count per micro-partition (16MB chunks)
  • Pruning-aware costing: A join that allows pruning 90% of a fact table's partitions is dramatically cheaper
  • Automatic clustering: Tables clustered on join keys have better locality → cheaper merge joins
  • Result caching: Prior query results cached, effectively making some "joins" free

Catalyst Join Reorder Rule

# Spark Catalyst Join Reorder (simplified logic)
# Located in: sql/catalyst/src/main/scala/org/apache/spark/sql/
#             catalyst/optimizer/CostBasedJoinReorder.scala

class CostBasedJoinReorder:
    """
    Rule that reorders inner joins using DP when:
    1. spark.sql.cbo.enabled = true
    2. spark.sql.cbo.joinReorder.enabled = true
    3. All tables have statistics collected
    4. Number of tables <= dp.threshold (default 12)
    """
    
    def apply(self, plan):
        # Extract all inner joins from the plan
        joins = extract_inner_joins(plan)
        
        if len(joins) <= 1:
            return plan
        
        if len(joins) > self.dp_threshold:
            # Fall back to star-schema heuristic
            return star_join_reorder(plan)
        
        # DP enumeration (considers bushy trees!)
        items = [(table, table.stats.sizeInBytes) for table in joins.tables]
        conditions = joins.conditions
        
        return dp_join_reorder(items, conditions)

# Star-Schema Heuristic (for large N):
# 1. Identify fact table (largest)
# 2. Join all dimension tables to fact in order of selectivity
# 3. Most selective dimension first (minimizes intermediate size)

Why "Small Joins Big"

Build Side Selection

The principle "small joins big" is the most important heuristic in join optimization. It means: always make the smaller table the build side (inner) of a hash join.

┌─────────────────────────────────────────────────────────────┐
│         WHY BUILD SIDE SELECTION MATTERS                      │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  CORRECT: Small builds, Big probes                           │
│  ══════════════════════════════════                           │
│  dim_customer (1M rows, 50MB)  → BUILD hash table in memory  │
│  fact_orders (100M rows, 5GB)  → PROBE (stream, no memory)   │
│                                                              │
│  Memory needed: 50MB (fits in work_mem easily)               │
│  I/O: Sequential scan of both tables (efficient)             │
│  Time: O(1M + 100M) = ~101M operations                      │
│                                                              │
│  ─────────────────────────────────────────────────────────── │
│                                                              │
│  WRONG: Big builds, Small probes                             │
│  ═══════════════════════════════                              │
│  fact_orders (100M rows, 5GB)  → BUILD hash table (5GB!)     │
│  dim_customer (1M rows, 50MB)  → PROBE                       │
│                                                              │
│  Memory needed: 5GB (exceeds work_mem → SPILL TO DISK!)      │
│  Spill: Multiple batches, random I/O, 10-100x slower         │
│  Time: Same O(101M) ops BUT with disk spill overhead         │
│                                                              │
│  RESULT: Same logical answer, 10-50x performance difference  │
└─────────────────────────────────────────────────────────────┘
Memory Pressure and Spill Implications

When the build side exceeds available memory:

  1. PostgreSQL: Hash join switches to multi-batch mode. Tuples are partitioned by hash into batches. Only one batch at a time fits in work_mem. Each additional batch requires re-reading probe-side tuples from disk.
  2. Spark: ShuffledHashJoinExec spills build-side partitions to disk via UnsafeExternalSorter. Configurable via spark.sql.autoBroadcastJoinThreshold (default 10MB).
  3. Snowflake: Automatically spills to remote storage (S3/Azure Blob). "Bytes spilled to local/remote storage" in query profile.

Intermediate Result Minimization

Beyond build-side memory, joining small tables first minimizes intermediate result sizes throughout the plan:

┌─────────────────────────────────────────────────────────────┐
│    INTERMEDIATE RESULT SIZE: ORDER MATTERS                    │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Tables:                                                     │
│    fact_orders:   100M rows                                  │
│    dim_customer:  1M rows  (with WHERE country='US' → 200K)  │
│    dim_product:   50K rows (with WHERE category='Electronics'│
│                             → 5K rows)                       │
│                                                              │
│  BAD ORDER: fact first                                       │
│  Step 1: fact ⋈ customer  = 100M * 200K/1M = 20M rows      │
│  Step 2: 20M ⋈ product   = 20M * 5K/50K    = 2M rows       │
│  Peak intermediate: 20M rows (must materialize/shuffle)      │
│                                                              │
│  GOOD ORDER: small dims first, then fact                     │
│  Step 1: customer(200K) ⋈ fact = 20M rows                   │
│  — Wait, this is the same! The KEY is filter pushdown:       │
│                                                              │
│  BEST: Push filters, join most selective dim first           │
│  Step 1: fact WHERE date_range → 10M rows (partition prune)  │
│  Step 2: 10M ⋈ product(5K)   → 1M rows (most selective!)    │
│  Step 3: 1M ⋈ customer(200K) → 800K rows                    │
│  Peak intermediate: 1M rows ← 20x less data shuffled!       │
└─────────────────────────────────────────────────────────────┘

The principle: Join the most selective dimension table first to reduce the intermediate result size before joining less selective dimensions. This minimizes memory usage, shuffle volume, and CPU across the entire plan.

The Fix (Immediate + Long-Term)

-- IMMEDIATE FIX (applied in 5 minutes, query dropped to 90 seconds):
-- 1. Force analyze on the new partitions
ANALYZE fact_sales_2024_q2;
ANALYZE fact_sales;  -- parent table too

-- 2. Temporarily force join order while stats propagate

SET geqo = off;  -- Force DP enumeration

-- Re-run the query with corrected stats → optimizer picks Hash Joins
-- Query time: 90 seconds (back to normal range)

-- LONG-TERM FIXES:
-- 1. Added to data migration runbook:
--    "ALWAYS run ANALYZE on new partitions immediately after load"

-- 2. Automated stats freshness monitoring:
CREATE OR REPLACE FUNCTION check_stale_stats()
RETURNS TABLE(tablename text, last_analyze timestamptz, staleness interval) AS $$
  SELECT
    schemaname || '.' || relname,
    last_analyze,
    now() - last_analyze as staleness
  FROM pg_stat_user_tables
  WHERE n_live_tup > 1000000
    AND (last_analyze IS NULL OR last_analyze < now() - interval '6 hours')
  ORDER BY n_live_tup DESC;
$$ LANGUAGE sql;

-- 3. Pre-migration checklist hook:
-- Run after every partition add/drop:
DO $$
DECLARE
    part record;
BEGIN
    FOR part IN
        SELECT inhrelid::regclass AS partition_name
        FROM pg_inherits
        WHERE inhparent = 'fact_sales'::regclass
    LOOP
        EXECUTE format('ANALYZE %s', part.partition_name);
    END LOOP;
END $$;
Lessons Learned
  • Statistics are the optimizer's eyes. Stale stats = blind optimizer. Always ANALYZE after bulk operations.
  • Partition-level stats are separate. Analyzing the parent doesn't always update partition stats (depends on version).
  • GEQO amplifies bad estimates. Genetic algorithms optimize relative to the cost model — if the cost model's inputs are wrong, GEQO finds the "best" bad plan.
  • Monitor estimation accuracy, not just query time. A 3x estimation error today becomes a 30x error tomorrow as data grows.
  • Have an emergency playbook: Know how to force join order (join_collapse_limit=1) and disable GEQO as immediate mitigations.

  HashJoin(o p)
  HashJoin(o c)
  SeqScan(o)
  IndexScan(d dim_date_pkey)
  SeqScan(p)
  SeqScan(c)
  Set(work_mem "512MB")

-- Leading((((d o) p) c)):

Follow-up Questions

Questions the Interviewer May Ask Next
  1. "How does Adaptive Query Execution (AQE) in Spark change join order at runtime?"

    AQE collects runtime statistics at shuffle boundaries. After a shuffle completes, it knows the actual partition sizes. If one side is much smaller than estimated, AQE can convert a SortMergeJoin to BroadcastHashJoin. It can also split/coalesce partitions and optimize skewed joins by splitting hot partitions.

  2. "What happens with 50+ table joins in data warehouse ETL?"

    No optimizer can enumerate 50! orderings. Approaches: (1) Snowflake/BigQuery use sophisticated heuristics with pruning; (2) Break the query into CTEs or temp tables to give the optimizer manageable chunks; (3) Use materialized intermediate results; (4) Star schema detection heuristics (fact table identified, dims joined in selectivity order).

  3. "How do you handle join order with data skew?"

    Skew breaks both estimation (average selectivity is wrong for hot keys) and execution (one partition gets all the data). Solutions: Spark AQE skew join (splits large partitions), salting (add random suffix to hot keys), or two-pass approach (separate hot keys from cold keys, process independently).

  4. "Explain the difference between rule-based and cost-based optimization."

    Rule-based (RBO): Fixed heuristics (e.g., "always use index if available", "join small tables first"). Predictable but can't adapt to actual data. Cost-based (CBO): Estimates actual cost using statistics, picks lowest-cost plan. Better plans but depends on accurate statistics. Modern systems use both: rules for transformations (predicate pushdown, projection pruning) then CBO for physical decisions (join order, algorithm).

  5. "How would you design a statistics collection pipeline for a data lake?"

    Challenge: Data lakes (Parquet/Delta/Iceberg) lack built-in stats collection. Design: (1) Trigger ANALYZE after each write/compaction; (2) Store column stats in table metadata (Delta statistics, Iceberg manifests); (3) Compute NDV using HyperLogLog for efficiency; (4) Sample-based histograms for large columns; (5) Freshness SLA: stats no older than 1 partition write.

  6. "What is the relationship between join order and partition pruning?"

    They're deeply linked: the optimizer should join dimension tables first (especially those with selective filters) because the join result can derive partition boundaries for the fact table. Example: dim_date WHERE year=2024 → derive fact_table partition year=2024 → prune 90% of fact partitions before the expensive join. Snowflake calls this "dynamic partition pruning."

  7. "Can you explain semi-join reduction and its role in distributed joins?"

    Semi-join reduction: Before the full join, send just the join keys from the smaller table to filter the larger table's partitions. This reduces shuffle volume at the cost of an extra pass. Used in: BigQuery (automatic), Spark (broadcast semi-join pushdown), distributed PostgreSQL (Citus). Especially valuable when the join is selective (few matches in the large table).

  8. "How do parameterized queries affect join order optimization?"

    Challenge: With bind parameters, the optimizer doesn't know the actual values at plan time. PostgreSQL uses "generic plans" after 5 executions (average cost). This can be catastrophic if parameter values have very different selectivities (e.g., country='US' vs country='Liechtenstein'). Solutions: plan_cache_mode=force_custom_plan, or partition by high-cardinality parameters.

Database Locking Mechanisms

Key Takeaway: Locks coordinate concurrent access — shared locks allow multiple readers, exclusive locks isolate writers, and intent locks make multigranularity compatibility checks O(1) instead of scanning every row lock. MVCC eliminates most read-write contention, but write-write conflicts, DDL, and explicit `SELECT FOR UPDATE` still need locks, so deadlock prevention (consistent lock ordering, short transactions, `lock_timeout`) and monitoring (`pg_locks`, wait-for graphs) remain essential production skills.

Interviewer Intent

  • Concurrency fundamentals — Can you explain how multiple transactions safely share data?
  • Lock taxonomy — Do you know the difference between shared, exclusive, intent, and update locks?
  • Granularity awareness — Can you reason about row-level vs page-level vs table-level locks and their throughput implications?
  • Deadlock reasoning — Can you identify, prevent, and resolve deadlock scenarios?
  • Production debugging — Have you diagnosed lock contention in real systems using pg_locks, sys.dm_tran_locks, or equivalent?
  • Distributed context — Can you connect locking concepts to modern data platforms (BigQuery, Snowflake, Delta Lake)?
  • MVCC interaction — Do you understand when MVCC eliminates lock needs and when explicit locks are still required?

At senior+ levels, the interviewer expects you to connect locking behavior to pipeline throughput, ETL/OLTP conflicts, and distributed system design.

  • Awareness of how MVCC and locking complement each other

Quick Answer (60-Second Version)

Elevator pitch

Database locks are synchronization primitives that control concurrent access to shared data. A shared (S) lock allows multiple readers; an exclusive (X) lock gives a single writer sole access. Intent locks (IS, IX) signal coarse-grained intention to lock at a finer granularity, enabling the multigranularity protocol that avoids scanning every row lock when checking table-level compatibility.

Locks operate at different granularities: row, page, table, or database. Finer granularity increases concurrency but raises memory overhead. When too many fine-grained locks accumulate, lock escalation promotes them to a coarser level.

Deadlocks occur when two or more transactions hold locks and each waits for a lock held by another, forming a cycle in the wait-for graph. Databases detect deadlocks by checking this graph (or via timeouts) and abort one of the participating transactions to break the cycle. The victim selection strategy is database-specific.

Modern MVCC systems (PostgreSQL, Oracle, Snowflake) eliminate read-write conflicts by giving readers a consistent snapshot without acquiring shared locks. However, exclusive locks are still required for writes, DDL operations, and explicit SELECT FOR UPDATE scenarios.

Lock Types

Shared (S) Lock

A shared lock permits concurrent reads. Multiple transactions can hold S locks on the same resource simultaneously. An S lock blocks exclusive lock requests but allows other shared lock requests. 


-- PostgreSQL: implicit S lock during SELECT under Read Committed
-- (In MVCC systems, readers don't actually acquire row-level S locks;
--  instead they read a snapshot. S locks appear at table level as AccessShareLock.)

-- SQL Server: explicit S lock during SELECT under default isolation
SELECT customer_name FROM customers WHERE customer_id = 42;
-- Acquires S lock on the row (released immediately under Read Committed)

-- S lock held for duration under Repeatable Read / Serializable:
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
SELECT balance FROM accounts WHERE id = 100;
-- S lock held until COMMIT — blocks any X lock on this row
COMMIT;
Exclusive (X) Lock

An exclusive lock provides sole access for writes. Only one transaction can hold an X lock on a resource. It blocks all other lock requests (both S and X) on that resource. 


-- Any DML statement acquires X locks on affected rows:
UPDATE accounts SET balance = balance - 100 WHERE id = 42;
-- X lock on row id=42 held until COMMIT/ROLLBACK

DELETE FROM orders WHERE order_id = 9001;
-- X lock on the deleted row until transaction ends

INSERT INTO events (id, data) VALUES (1, 'test');
-- X lock on the new row (prevents phantom reads in Serializable)

-- PostgreSQL: RowExclusiveLock on the table + X on individual rows
-- SQL Server: IX on table/page + X on row
Intent Shared (IS) Lock

An intent shared lock on a higher-level resource (table or page) signals that the transaction intends to acquire shared locks on lower-level resources (rows). This enables efficient compatibility checking — the database doesn't need to scan all row locks to determine if a table-level exclusive lock can be granted. 


# Multigranularity protocol example:
#
# Transaction T1: SELECT * FROM orders WHERE id = 5;
#   1. Acquire IS lock on TABLE orders        (intent to read a row)
#   2. Acquire IS lock on PAGE containing id=5 (if page-level exists)
#   3. Acquire S lock on ROW id=5             (actual read lock)
#
# Transaction T2: LOCK TABLE orders IN EXCLUSIVE MODE;
#   1. Try to acquire X lock on TABLE orders
#   2. Check: any IS/IX/S/X held on table?
#   3. IS found from T1 → X request BLOCKED
#   (Without IS, database would need to scan ALL row locks)
Intent Exclusive (IX) Lock

An intent exclusive lock on a higher-level resource signals that the transaction intends to acquire exclusive locks on lower-level resources. IX is compatible with IS and other IX locks (multiple transactions can read or write different rows in the same table) but incompatible with S, SIX, and X locks at the same level. 


# Transaction T1: UPDATE orders SET status='shipped' WHERE id = 5;
#   1. Acquire IX lock on TABLE orders
#   2. Acquire IX lock on PAGE
#   3. Acquire X lock on ROW id=5
#
# Transaction T2: UPDATE orders SET status='cancelled' WHERE id = 99;
#   1. Acquire IX lock on TABLE orders   ← COMPATIBLE with T1's IX
#   2. Acquire IX lock on PAGE (different page) ← no conflict
#   3. Acquire X lock on ROW id=99       ← no conflict
#
# Both transactions proceed concurrently because IX + IX is compatible.
# They modify different rows — no actual conflict exists.
Update (U) Lock

An update lock is a hybrid used during the read phase of an UPDATE statement. It prevents the classic conversion deadlock: two transactions both acquire S locks on a row, then both try to upgrade to X — neither can because the other holds S. A U lock is compatible with S but not with other U or X locks, ensuring only one transaction can be in the "about to update" state. 


-- SQL Server update lock scenario:
-- Without U locks (deadlock-prone):
--   T1: S lock on row → tries to upgrade to X → blocked by T2's S
--   T2: S lock on row → tries to upgrade to X → blocked by T1's S
--   DEADLOCK!

-- With U locks (SQL Server default for UPDATE):
--   T1: U lock on row (read phase of UPDATE)
--   T2: tries U lock → BLOCKED (U + U incompatible)
--   T1: upgrades U → X (write phase)
--   T1: COMMIT → releases X
--   T2: acquires U → upgrades to X → completes

-- Explicit U lock hint in SQL Server:
SELECT * FROM accounts WITH (UPDLOCK) WHERE id = 42;
-- Acquires U lock — signals "I will update this soon"

-- PostgreSQL equivalent: SELECT ... FOR UPDATE
SELECT * FROM accounts WHERE id = 42 FOR UPDATE;
-- Acquires a RowShareLock on the table + row-level exclusive lock on the row
Schema (Sch) and Bulk Update (BU) Locks

Schema Stability (Sch-S): Prevents table schema from being modified while a query references it. Acquired by every DML/SELECT statement.

Schema Modification (Sch-M): Acquired by DDL statements (ALTER TABLE, DROP INDEX). Blocks all other access to the table — the most restrictive lock.

Bulk Update (BU): Used by bulk-load operations (BULK INSERT, bcp) with TABLOCK hint. Allows concurrent bulk inserts but blocks normal DML. 


-- PostgreSQL DDL lock escalation:
-- Adding a column with DEFAULT acquires AccessExclusiveLock
ALTER TABLE orders ADD COLUMN priority INT DEFAULT 0;
-- Blocks ALL concurrent queries on orders until complete

-- PostgreSQL 11+ optimization: non-volatile defaults don't rewrite table
-- But lock is still held during catalog update (brief but exclusive)

-- Safe pattern for large tables:
ALTER TABLE orders ADD COLUMN priority INT;  -- no default, instant
-- Then backfill in batches:
UPDATE orders SET priority = 0 WHERE id BETWEEN 1 AND 100000;
-- Smaller batches = shorter X locks = less blocking

Lock Granularity

Row-level locking

The finest practical granularity. Each individual row can be independently locked, maximizing concurrency. Two transactions modifying different rows in the same table never block each other. Used by PostgreSQL, MySQL InnoDB, Oracle, and modern OLTP databases. 


# Row-level locking characteristics:
# ┌──────────────────────────────────────────────────────────────────┐
# │  Pros:                                                           │
# │  • Maximum concurrency — independent row access                  │
# │  • Minimal blocking for mixed read/write workloads               │
# │  • Ideal for OLTP (many small transactions on different rows)    │
# │                                                                  │
# │  Cons:                                                           │
# │  • Memory overhead — each lock consumes ~100-200 bytes           │
# │  • Lock manager bookkeeping for millions of rows                 │
# │  • Can lead to lock escalation under bulk operations             │
# │  • Deadlock detection more complex (more edges in wait-for graph)│
# └──────────────────────────────────────────────────────────────────┘
#
# Memory calculation (SQL Server):
#   Each lock structure: ~96 bytes
#   UPDATE on 1M rows: 96 bytes × 1,000,000 = ~96 MB in lock memory
#   Default lock memory: 40% of buffer pool
#   If buffer pool = 16 GB → lock memory cap = 6.4 GB → ~67M locks
Page-level locking

Locks an entire data page (typically 8 KB in SQL Server, 8 KB in PostgreSQL). A compromise between row and table granularity. Less memory overhead than row locks but reduces concurrency when multiple hot rows reside on the same page. 


# Page-level locking characteristics:
# ┌──────────────────────────────────────────────────────────────────┐
# │  • SQL Server uses page-level locks as intermediate granularity  │
# │  • Typical page: 8 KB, holding ~50-200 rows                     │
# │  • One lock protects all rows on the page                        │
# │                                                                  │
# │  When databases choose page locks:                               │
# │  • Scan touching many rows on same page (range scan)             │
# │  • Lock escalation threshold not yet met but row locks expensive │
# │  • Heap tables with no clustered index (SQL Server)              │
# │                                                                  │
# │  PostgreSQL note:                                                │
# │  • PostgreSQL does NOT have explicit page-level row locks        │
# │  • It uses page-level cleanup locks (VACUUM) but row-level xmax │
# │  • Buffer pins serve a similar purpose for I/O coordination      │
# └──────────────────────────────────────────────────────────────────┘
Table-level locking

Table-level locks protect table-wide operations. Depending on the lock mode, they may still allow concurrent reads or writes — PostgreSQL defines eight table-level lock modes ranging from AccessShareLock (compatible with nearly everything) to AccessExclusiveLock (blocks all access). Explicit LOCK TABLE, DDL operations, and bulk loads use table-level locks. 


-- PostgreSQL table-level lock modes (from least to most restrictive):
-- 1. AccessShareLock          — SELECT
-- 2. RowShareLock             — SELECT FOR UPDATE/SHARE
-- 3. RowExclusiveLock         — INSERT, UPDATE, DELETE
-- 4. ShareUpdateExclusiveLock — VACUUM, CREATE INDEX CONCURRENTLY
-- 5. ShareLock                — CREATE INDEX (non-concurrent)
-- 6. ShareRowExclusiveLock    — CREATE TRIGGER, some ALTER TABLE
-- 7. ExclusiveLock            — REFRESH MATERIALIZED VIEW CONCURRENTLY
-- 8. AccessExclusiveLock      — DROP TABLE, ALTER TABLE, VACUUM FULL

-- Explicit table lock:
BEGIN;
LOCK TABLE orders IN SHARE MODE;
-- All concurrent INSERTs/UPDATEs/DELETEs are blocked
-- But SELECTs proceed freely
SELECT sum(amount) FROM orders;  -- consistent snapshot
COMMIT;

-- Exclusive table lock (blocks everything):
BEGIN;
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;
-- Even SELECTs are blocked — use sparingly!
ALTER TABLE orders ADD COLUMN new_col INT;
COMMIT;
Database-level locking

The coarsest granularity. Some database systems support maintenance modes that effectively prevent normal concurrent access to an entire database, although true database-wide locks are uncommon in most enterprise databases. Used during database restore, schema migration scripts, or single-user maintenance modes. 


-- SQL Server: set database to single-user mode
ALTER DATABASE analytics SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
-- All other connections terminated and blocked
-- Perform maintenance...
ALTER DATABASE analytics SET MULTI_USER;

-- PostgreSQL: prevent new connections during maintenance
-- (No true database-level lock; use pg_hba.conf or connection limits)
ALTER DATABASE warehouse CONNECTION LIMIT 0;  -- block new connections
-- Existing connections remain active
-- Perform maintenance...
ALTER DATABASE warehouse CONNECTION LIMIT -1;  -- unlimited again

-- SQLite: database-level locking is the ONLY option
-- SHARED lock for readers, EXCLUSIVE lock for writers
-- Only one writer at a time for the entire database file
Multigranularity locking protocol

The multigranularity protocol uses intent locks to efficiently combine locks at different levels of the hierarchy. Before acquiring a fine-grained lock, the transaction must acquire intent locks on all ancestor resources in the hierarchy. 


# Lock hierarchy: DATABASE → TABLE → PAGE → ROW
#
# Protocol rules:
# 1. To acquire S or IS on a node, must hold IS or IX on parent
# 2. To acquire X, IX, or SIX on a node, must hold IX or SIX on parent
# 3. Locks are released in bottom-up order (or all at commit in 2PL)
#
# Example: UPDATE orders SET status='done' WHERE id = 42;
#
# Step 1: IX on DATABASE (intent to write somewhere in this DB)
# Step 2: IX on TABLE orders (intent to write in this table)
# Step 3: IX on PAGE containing row 42
# Step 4: X on ROW id=42 (actual exclusive lock)
#
# ┌─────────────────────────────────────────────────────────────┐
# │  DATABASE ─── IX                                            │
# │    └── TABLE orders ─── IX                                  │
# │          └── PAGE 7 ─── IX                                  │
# │                └── ROW id=42 ─── X                          │
# └─────────────────────────────────────────────────────────────┘
#
# When T2 wants: LOCK TABLE orders IN EXCLUSIVE MODE;
# Check TABLE orders: IX held by T1 → X request INCOMPATIBLE → WAIT
# (No need to scan individual row locks!)
#
# This is the key insight: intent locks make table-level compatibility
# checking O(1) instead of O(n) where n = number of locked rows.

Lock Compatibility Matrix

Standard compatibility matrix (S, X, IS, IX, SIX) 

# Lock Compatibility Matrix
# ─────────────────────────────────────────────────────────────────
# "Y" = Compatible (both can be held simultaneously)
# "N" = Incompatible (requester must wait)
#
# ┌──────────────┬──────┬──────┬──────┬──────┬──────┐
# │  Requested → │  IS  │  IX  │   S  │  SIX │   X  │
# │  Held ↓      │      │      │      │      │      │
# ├──────────────┼──────┼──────┼──────┼──────┼──────┤
# │  IS          │  Y   │  Y   │  Y   │  Y   │  N   │
# │  IX          │  Y   │  Y   │  N   │  N   │  N   │
# │  S           │  Y   │  N   │  Y   │  N   │  N   │
# │  SIX         │  Y   │  N   │  N   │  N   │  N   │
# │  X           │  N   │  N   │  N   │  N   │  N   │
# └──────────────┴──────┴──────┴──────┴──────┴──────┘
#
# Key observations:
# 1. X is incompatible with everything (total exclusion)
# 2. IS is the most permissive (only conflicts with X)
# 3. IX + IX = compatible (multiple writers to different rows)
# 4. IX + S = incompatible (writer intent conflicts with full read lock)
# 5. SIX = S + IX combined (read whole table + modify some rows)
#    → only compatible with IS (readers of individual rows)

#
# ┌─────────────────────────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
# │ Requested →             │ AS  │ RS  │ RE  │ SUE │ S   │ SRE │ E   │ AE  │
# │ Held ↓                  │     │     │     │     │     │     │     │     │
# ├─────────────────────────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤
# │ AccessShare (AS)        │  Y  │  Y  │  Y  │  Y  │  Y  │  Y  │  Y  │  N  │
# │ RowShare (RS)           │  Y  │  Y  │  Y  │  Y  │  Y  │  Y  │  N  │  N  │
# │ RowExclusive (RE)       │  Y  │  Y  │  Y  │  Y  │  N  │  N  │  N  │  N  │
# │ ShareUpdateExcl (SUE)   │  Y  │  Y  │  Y  │  N  │  N  │  N  │  N  │  N  │
# │ Share (S)               │  Y  │  Y  │  N  │  N  │  Y  │  N  │  N  │  N  │
# │ ShareRowExcl (SRE)      │  Y  │  Y  │  N  │  N  │  N  │  N  │  N  │  N  │
# │ Exclusive (E)           │  Y  │  N  │  N  │  N  │  N  │  N  │  N  │  N  │
# │ AccessExclusive (AE)    │  N  │  N  │  N  │  N  │  N  │  N  │  N  │  N  │
# └─────────────────────────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
#
# Common operations → lock mode:
# SELECT                          → AccessShareLock
# SELECT FOR UPDATE               → RowShareLock
# INSERT/UPDATE/DELETE            → RowExclusiveLock
# VACUUM (non-FULL), ANALYZE     → ShareUpdateExclusiveLock
# CREATE INDEX (non-concurrent)  → ShareLock
# CREATE INDEX CONCURRENTLY      → ShareUpdateExclusiveLock
# ALTER TABLE (most forms)       → AccessExclusiveLock
# DROP TABLE                     → AccessExclusiveLock
Practical implications of the matrix 

-- Scenario 1: ETL writer vs OLTP readers
-- ETL: INSERT INTO orders SELECT ... (acquires RowExclusiveLock on table)
-- OLTP: SELECT * FROM orders WHERE id=42 (acquires AccessShareLock)
-- Matrix: RowExclusive + AccessShare = COMPATIBLE ✓
-- Both proceed concurrently (MVCC provides snapshot isolation for reader)

-- Scenario 2: VACUUM vs DDL (dangerous!)
-- VACUUM: acquires ShareUpdateExclusiveLock
-- ALTER TABLE: needs AccessExclusiveLock
-- Matrix: SUE + AE = INCOMPATIBLE
-- ALTER TABLE waits for VACUUM to finish
-- Problem: VACUUM on large table can take hours → DDL blocked for hours

-- Scenario 3: Concurrent CREATE INDEX
-- Non-concurrent: acquires ShareLock → blocks INSERT/UPDATE/DELETE
CREATE INDEX idx_orders_date ON orders(order_date);
-- ALL writes blocked until index build completes!

-- Concurrent (preferred for production):
CREATE INDEX CONCURRENTLY idx_orders_date ON orders(order_date);
-- Acquires ShareUpdateExclusiveLock → only blocks VACUUM and DDL
-- Writes proceed normally during index build (takes longer but non-blocking)

-- Scenario 4: Two concurrent ALTER TABLE statements
-- Both need AccessExclusiveLock → second waits for first
-- Dangerous: if first ALTER is slow, second blocks, and ALL queries
-- that arrive after the second ALTER also queue behind it!

Deadlocks

What causes a deadlock

A deadlock occurs when two or more transactions form a cycle of dependencies: each holds a resource the other needs, and neither can proceed. The four necessary conditions (Coffman conditions) are:

  • Mutual exclusion — resources cannot be shared (X locks)
  • Hold and wait — transaction holds one lock while waiting for another
  • No preemption — locks cannot be forcibly taken from a holder
  • Circular wait — a cycle exists in the wait-for graph

-- Classic deadlock scenario:
-- T1: Transfer $100 from account A to account B
-- T2: Transfer $50 from account B to account A

-- T1:
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';  -- X lock on A
-- (context switch)

-- T2:
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 'B';   -- X lock on B
UPDATE accounts SET balance = balance + 50 WHERE id = 'A';   -- WAIT (T1 holds X on A)

-- T1 (continues):
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';  -- WAIT (T2 holds X on B)

-- DEADLOCK: T1 waits for B (held by T2), T2 waits for A (held by T1)
-- Cycle: T1 → B → T2 → A → T1
Detection via wait-for graph

The wait-for graph (WFG) is a directed graph where nodes represent transactions and edges represent "waits for" relationships. A cycle in the WFG indicates a deadlock. Most databases run a background deadlock detector thread that periodically traverses this graph. 


# Wait-For Graph for the deadlock above:
#
#   T1 ──waits for B──→ T2
#   ↑                     │
#   └──── waits for A ────┘
#
# Cycle detected: T1 → T2 → T1
#
# Detection algorithms:
#
# 1. Per-backend trigger (PostgreSQL)
#    - When a backend has waited longer than deadlock_timeout (default 1s),
#      PostgreSQL performs a deadlock check by examining the wait-for graph
#    - NOT a periodic background thread — triggered per-backend on demand
#    - O(V + E) where V = waiting transactions, E = wait edges
#
# 2. Continuous edge tracking (SQL Server)
#    - Lock manager maintains WFG incrementally
#    - Checks for cycles on every new wait edge
#    - Faster detection but slightly more overhead per lock request
#
# 3. Timeout-based (simpler systems, distributed databases)
#    - If a transaction waits longer than threshold → assume deadlock
#    - Simple but may abort transactions that aren't actually deadlocked
#    - Used when maintaining a global WFG is impractical (distributed)
#
# PostgreSQL deadlock detection timeline:
#   T=0:     Transaction starts waiting for lock
#   T=1s:    Backend's deadlock_timeout fires → triggers deadlock check
#   T=1.001s: WFG traversal finds cycle (or doesn't)
#   T=1.002s: Victim selected → ERROR: deadlock detected
Victim selection

When a deadlock is detected, the database must abort one transaction (the "victim") to break the cycle. Different databases use different cost heuristics: 


# Victim selection strategies:
#
# PostgreSQL:
#   - Aborts one of the transactions participating in the detected deadlock
#   - The exact choice is implementation-specific rather than cost-based
#   - In practice, typically the transaction whose backend triggered the check
#   - No user-controllable priority setting
#
# SQL Server:
#   - DEADLOCK_PRIORITY setting (LOW, NORMAL, HIGH, or -10 to 10)
#   - Among equal priorities: picks the cheapest to rollback
#   - Cost = amount of log generated (work done so far)
#   - SET DEADLOCK_PRIORITY LOW; — volunteer as victim
#
# Oracle:
#   - Aborts the statement (not entire transaction) that detected the deadlock
#   - Application must handle ORA-00060 and retry
#
# MySQL InnoDB:
#   - Picks transaction with fewest undo log records (least work to rollback)
#   - innodb_lock_wait_timeout (default 50s) for general lock waits


-- SQL Server: control victim selection
-- Mark ETL transactions as expendable:
SET DEADLOCK_PRIORITY LOW;
BEGIN TRANSACTION;
-- If this deadlocks with an OLTP transaction, this one dies
INSERT INTO staging_table SELECT * FROM source;
COMMIT;

-- Mark critical OLTP as protected:
SET DEADLOCK_PRIORITY HIGH;
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - amount WHERE id = @id;
COMMIT;
Prevention: consistent ordering

The most reliable deadlock prevention technique is consistent lock ordering: all transactions acquire locks on resources in the same global order. If every transaction locks account A before account B, the circular wait condition cannot form. 


# Deadlock prevention via consistent ordering (application level):

def transfer_funds(from_account, to_account, amount):
    """Transfer funds with deadlock-free locking order."""
    # Always lock the lower-ID account first
    first_id = min(from_account, to_account)
    second_id = max(from_account, to_account)

    with db.transaction():
        # Lock in consistent order (by account ID)
        row1 = db.execute(
            "SELECT balance FROM accounts WHERE id = %s FOR UPDATE",
            (first_id,)
        )
        row2 = db.execute(
            "SELECT balance FROM accounts WHERE id = %s FOR UPDATE",
            (second_id,)
        )

        # Now perform the transfer
        db.execute(
            "UPDATE accounts SET balance = balance - %s WHERE id = %s",
            (amount, from_account)
        )
        db.execute(
            "UPDATE accounts SET balance = balance + %s WHERE id = %s",
            (amount, to_account)
        )

# With this ordering:
# Transfer(A→B): locks A, then B
# Transfer(B→A): locks A, then B (NOT B then A!)
# No cycle possible → no deadlock
Prevention: lock timeout 

-- PostgreSQL: set lock timeout to fail fast instead of deadlocking
SET lock_timeout = '5s';  -- fail if lock not acquired within 5 seconds

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
-- If another transaction holds the lock for > 5s:
-- ERROR: canceling statement due to lock timeout

-- Difference between lock_timeout and statement_timeout:
-- lock_timeout: time waiting to ACQUIRE a lock
-- statement_timeout: total execution time of the statement
-- deadlock_timeout: time before deadlock detection check runs

-- Recommended production settings:
ALTER DATABASE mydb SET lock_timeout = '10s';
ALTER DATABASE mydb SET statement_timeout = '30s';
ALTER DATABASE mydb SET deadlock_timeout = '1s';  -- default

-- MySQL InnoDB:
SET innodb_lock_wait_timeout = 10;  -- seconds (default: 50)

-- SQL Server:
SET LOCK_TIMEOUT 5000;  -- milliseconds (default: -1 = wait forever)
Deadlocks in data engineering pipelines 

# Common deadlock patterns in ETL/ELT:
#
# 1. Concurrent partition loads:
#    Pipeline A: INSERT INTO fact_table PARTITION (date='2024-01-15')
#    Pipeline B: INSERT INTO fact_table PARTITION (date='2024-01-16')
#    Both need IX on table → compatible, but if either needs table-level
#    operations (statistics update, index maintenance) → potential deadlock
#
# 2. Merge/Upsert on overlapping key ranges:
#    MERGE INTO target USING source ON target.id = source.id
#    Two concurrent MERGE statements with overlapping IDs can deadlock
#    if they lock rows in different orders (depends on index scan order)
#
# 3. Parent-child foreign key locks:
#    T1: DELETE FROM orders WHERE customer_id = 42; (locks parent check)
#    T2: INSERT INTO orders (customer_id) VALUES (42); (locks FK check)
#    FK enforcement acquires S locks on parent → potential cycles
#
# 4. Index maintenance deadlocks:
#    UPDATE touches column in index A (locks index A entry, then table row)
#    Another UPDATE touches same row via index B (locks index B, then row)
#    Different index traversal orders → different lock acquisition orders
#
# Prevention for pipelines:
# • Partition data so concurrent jobs never touch same rows
# • Use SERIALIZABLE isolation with retry logic (pessimistic but safe)
# • Set short lock_timeout + retry at application level
# • Process records in primary key order within each batch

Lock Escalation

SQL Server lock escalation behavior

Lock escalation is the process of converting many fine-grained locks (row or page) into fewer coarse-grained locks (table). SQL Server triggers escalation when a single transaction exceeds a threshold of locks on a single table. 


# SQL Server lock escalation thresholds:
#
# Default trigger: ~5,000 locks on a single table
# (Actually dynamic: based on memory pressure and lock count)
#
# Escalation path: ROW → TABLE (skips page in modern versions)
#
# ┌────────────────────────────────────────────────────────────────┐
# │  Timeline of escalation:                                       │
# │                                                                │
# │  T=0:    UPDATE orders SET status='x' WHERE date='2024-01-15' │
# │  T=1:    Row lock #1 acquired                                  │
# │  T=2:    Row lock #2 acquired                                  │
# │  ...                                                           │
# │  T=5000: Row lock #5000 acquired                               │
# │  T=5001: ESCALATION TRIGGERED                                  │
# │          - Attempt to acquire TABLE-level X lock                │
# │          - If successful: release all 5000 row locks            │
# │          - If blocked: keep row locks, retry at ~7500           │
# │                                                                │
# │  After escalation:                                             │
# │  - ONE table lock replaces thousands of row locks               │
# │  - Memory freed in lock manager                                 │
# │  - BUT: entire table is now exclusively locked                  │
# │  - ALL concurrent queries on this table are blocked!            │
# └────────────────────────────────────────────────────────────────┘


-- SQL Server: control lock escalation at table level
-- Disable escalation entirely (risky — can exhaust lock memory):
ALTER TABLE orders SET (LOCK_ESCALATION = DISABLE);

-- Escalate to partition level instead of table (SQL Server 2008+):
ALTER TABLE orders SET (LOCK_ESCALATION = AUTO);
-- With partitioned table: escalates to partition lock, not table lock
-- Non-partitioned table: behaves like TABLE mode

-- Force table-level escalation (default):
ALTER TABLE orders SET (LOCK_ESCALATION = TABLE);

-- Monitor escalation events:
SELECT * FROM sys.dm_exec_query_stats
WHERE total_lock_escalation_count > 0;

-- Trace lock escalation in real-time:
-- Extended Events session:
CREATE EVENT SESSION lock_escalation ON SERVER
ADD EVENT sqlserver.lock_escalation
ADD TARGET package0.ring_buffer;
Why SQL Server escalates — memory pressure 

# Lock memory management in SQL Server:
#
# Each lock structure: ~96 bytes (lock resource) + ~64 bytes (lock owner)
# Bulk update of 10M rows: ~160 bytes × 10,000,000 = 1.6 GB of lock memory!
#
# SQL Server's lock memory pool:
# • Dynamically allocated from buffer pool memory
# • Default: up to 40% of SQL Server memory for locks
# • If lock memory nears capacity → aggressive escalation
# • If escalation fails → ERROR 1204 (lock resources exhausted)
#
# Production scenario:
# ┌────────────────────────────────────────────────────────────────┐
# │  ETL job: DELETE FROM events WHERE event_date < '2024-01-01'   │
# │  Table has 500M rows matching predicate                         │
# │                                                                │
# │  Without escalation:                                           │
# │  500M × 160 bytes = 80 GB lock memory (impossible!)            │
# │                                                                │
# │  With escalation (at 5000 locks):                              │
# │  1 table lock = 160 bytes                                      │
# │  But entire table locked → all queries blocked for hours        │
# │                                                                │
# │  Solution: batch the delete                                    │
# │  WHILE EXISTS (SELECT 1 FROM events WHERE event_date < '...')  │
# │    DELETE TOP (10000) FROM events WHERE event_date < '...'     │
# │    -- Stays under 5000-lock threshold, no escalation           │
# │    -- Brief X locks released between batches                   │
# └────────────────────────────────────────────────────────────────┘
PostgreSQL: no lock escalation

PostgreSQL does not perform lock escalation. Row-level lock information is recorded in tuple headers using the xmax field together with infomask bits, rather than in a separate lock table. This avoids per-row memory allocation regardless of how many rows are locked. 


# PostgreSQL lock architecture — why no escalation is needed:
#
# ┌────────────────────────────────────────────────────────────────┐
# │  Row-level "locks" in PostgreSQL:                              │
# │                                                                │
# │  • NOT stored in a lock table / lock manager                   │
# │  • Recorded in tuple headers (xmax field + infomask bits)      │
# │  • xmax = transaction ID or MultiXactId that locked/deleted row│
# │  • Infomask bits encode lock mode (FOR UPDATE vs FOR SHARE)    │
# │  • No per-row memory allocation for locks!                     │
# │                                                                │
# │  UPDATE orders SET status='x' WHERE date = '2024-01-15';      │
# │  • 10 million rows updated                                    │
# │  • Zero additional lock memory consumed                        │
# │  • Each row's xmax set to current transaction ID               │
# │  • Other transactions check xmax to see if row is locked       │
# │                                                                │
# │  Table-level locks (in shared lock table):                     │
# │  • Only ONE entry per transaction per table                    │
# │  • RowExclusiveLock on 'orders' table                          │
# │  • Regardless of whether you update 1 row or 10M rows          │
# │  • Lock table memory: O(transactions × tables), not O(rows)    │
# └────────────────────────────────────────────────────────────────┘
#
# Implications for data engineering:
# • Bulk operations in PostgreSQL don't cause escalation surprises
# • No "suddenly the whole table is locked" behavior
# • BUT: long-running transactions hold xmax references → VACUUM can't clean
# • Trade-off: no escalation but potential table bloat from dead tuples

Advisory Locks

PostgreSQL pg_advisory_lock overview

Advisory locks are application-level locks managed by PostgreSQL but with no connection to actual data. They provide a mechanism for applications to coordinate using the database as a distributed lock manager. The database doesn't enforce them automatically — the application must explicitly check and acquire them. 


-- Advisory lock functions in PostgreSQL:
--
-- Session-level (held until session ends or explicitly released):
SELECT pg_advisory_lock(key);           -- blocking acquire
SELECT pg_advisory_lock(key1, key2);    -- two-integer key
SELECT pg_try_advisory_lock(key);       -- non-blocking (returns true/false)
SELECT pg_advisory_unlock(key);         -- explicit release
SELECT pg_advisory_unlock_all();        -- release all session locks

-- Transaction-level (released at COMMIT/ROLLBACK):
SELECT pg_advisory_xact_lock(key);      -- blocking acquire
SELECT pg_try_advisory_xact_lock(key);  -- non-blocking

-- Shared advisory locks (multiple holders allowed):
SELECT pg_advisory_lock_shared(key);
SELECT pg_try_advisory_lock_shared(key);

-- Key space: bigint (single 64-bit key) or (int, int) pair
-- Lock storage: in-memory, in PostgreSQL's lock table
-- No WAL logging, no persistence — survives only as long as session

# Solution: advisory lock as a distributed mutex

import psycopg2
import hashlib

def get_lock_key(job_name: str) -> int:
    """Generate a consistent lock key from job name."""
    # Hash job name to a bigint key
    h = hashlib.md5(job_name.encode()).hexdigest()
    return int(h[:15], 16)  # 60-bit positive integer

def run_etl_with_advisory_lock(job_name: str, conn_string: str):
    """Run ETL job with advisory lock to prevent concurrent execution."""
    lock_key = get_lock_key(job_name)

    conn = psycopg2.connect(conn_string)
    conn.autocommit = True  # advisory locks work outside transactions
    cur = conn.cursor()

    # Try to acquire lock (non-blocking)
    cur.execute("SELECT pg_try_advisory_lock(%s)", (lock_key,))
    acquired = cur.fetchone()[0]

    if not acquired:
        print(f"Job '{job_name}' is already running (lock {lock_key} held)")
        conn.close()
        return False  # skip this run

    try:
        print(f"Acquired lock {lock_key} for job '{job_name}'")
        # === Run the actual ETL logic ===
        execute_pipeline(job_name)
        return True
    finally:
        # Release the lock
        cur.execute("SELECT pg_advisory_unlock(%s)", (lock_key,))
        conn.close()

Use case: distributed locking for microservices 

# Using PostgreSQL advisory locks as a lightweight distributed lock
# (alternative to Redis/ZooKeeper for small-scale systems)

import contextlib
import psycopg2
from psycopg2.extensions import ISOLATION_LEVEL_AUTOCOMMIT

@contextlib.contextmanager
def distributed_lock(lock_name: str, conn_string: str, timeout_ms: int = 5000):
    """
    Context manager for distributed locking via PostgreSQL advisory locks.
    
    Advantages over Redis SETNX:
    - Session-level advisory locks auto-release on connection drop (no stale locks)
    - Transaction-level advisory locks release at COMMIT/ROLLBACK
    - ACID guarantees on lock state
    - No separate infrastructure to maintain
    
    Disadvantages:
    - Tied to PostgreSQL availability
    - Higher latency than Redis (~1ms vs ~0.1ms)
    - Connection per lock holder
    
    Note: lock_timeout does NOT apply to advisory lock waits.
    We use pg_try_advisory_lock with a polling loop instead.
    """
    lock_key = hash(lock_name) & 0x7FFFFFFFFFFFFFFF  # positive bigint
    
    conn = psycopg2.connect(conn_string)
    conn.set_isolation_level(ISOLATION_LEVEL_AUTOCOMMIT)
    cur = conn.cursor()
    
    # Advisory locks ignore lock_timeout, so poll with pg_try_advisory_lock
    import time as _time
    deadline = _time.time() + (timeout_ms / 1000.0)
    acquired = False
    while _time.time() < deadline:
        cur.execute("SELECT pg_try_advisory_lock(%s)", (lock_key,))
        acquired = cur.fetchone()[0]
        if acquired:
            break
        _time.sleep(0.05)  # 50ms poll interval
    
    if not acquired:
        conn.close()
        raise TimeoutError(f"Could not acquire lock '{lock_name}' within {timeout_ms}ms")
    
    try:
        yield  # Critical section
    finally:
        try:
            cur.execute("SELECT pg_advisory_unlock(%s)", (lock_key,))
        except Exception:
            pass  # Connection drop auto-releases session-level locks
        conn.close()

# Usage:
with distributed_lock("daily-revenue-calculation", CONN_STRING):
    # Only one instance runs this code across all workers
    compute_daily_revenue()
    write_to_warehouse()

MVCC vs Pure Locking

How MVCC reduces the need for read locks

In a pure two-phase locking (2PL) system, readers acquire shared locks that block writers, and writers acquire exclusive locks that block readers. This creates severe contention in mixed workloads. MVCC (Multi-Version Concurrency Control) eliminates this by keeping multiple versions of each row — readers see a consistent snapshot without acquiring locks on the data. 


# Pure 2PL (SQL Server default under Read Committed without RCSI):
#
# ┌──────────────────┬───────────────────────────────────────────┐
# │  Reader (T1)     │  Writer (T2)                              │
# ├──────────────────┼───────────────────────────────────────────┤
# │  SELECT balance  │                                           │
# │  → Acquire S     │                                           │
# │  → Read: $1000   │                                           │
# │  → Release S     │  UPDATE balance = 900                     │
# │                  │  → Acquire X (succeeds, S released)       │
# │  SELECT balance  │  → Write: $900                            │
# │  → Acquire S     │  → X held until COMMIT                   │
# │  → BLOCKED! ←────│─── X held by T2                          │
# │  (waits...)      │  COMMIT                                   │
# │  → Read: $900    │  → Release X                              │
# └──────────────────┴───────────────────────────────────────────┘
# Reader blocked by writer — bad for mixed workloads!

# MVCC (PostgreSQL, Oracle, MySQL InnoDB):
#
# ┌──────────────────┬───────────────────────────────────────────┐
# │  Reader (T1)     │  Writer (T2)                              │
# ├──────────────────┼───────────────────────────────────────────┤
# │  SELECT balance  │                                           │
# │  → No lock!      │                                           │
# │  → Read v1: $1000│                                           │
# │                  │  UPDATE balance = 900                     │
# │                  │  → Acquire X on row (for other writers)   │
# │                  │  → Create new version v2: $900            │
# │  SELECT balance  │  → X held until COMMIT                   │
# │  → No lock!      │                                           │
# │  → Read v1: $1000│  (reads old version — snapshot isolation) │
# │  → NOT BLOCKED!  │  COMMIT                                   │
# └──────────────────┴───────────────────────────────────────────┘
# Reader never blocked by writer — massive concurrency improvement!
When locks are still needed under MVCC

MVCC doesn't eliminate all locking. Several scenarios still require explicit locks: 


-- 1. Write-write conflicts (X locks still required):
-- T1: UPDATE accounts SET balance = 900 WHERE id = 42; -- X lock on row
-- T2: UPDATE accounts SET balance = 800 WHERE id = 42; -- WAITS for T1's X
-- MVCC doesn't help: both want to MODIFY the same current row

-- 2. SELECT FOR UPDATE (explicit pessimistic lock):
BEGIN;
SELECT balance FROM accounts WHERE id = 42 FOR UPDATE;
-- Acquires X lock — prevents concurrent modifications
-- Use case: read-then-write patterns that need atomicity
-- E.g., check balance >= amount, then debit
UPDATE accounts SET balance = balance - 100 WHERE id = 42;
COMMIT;

-- 3. Serializable isolation (PostgreSQL SSI):
-- Uses predicate locks (SIReadLock) to detect serialization anomalies
-- Not blocking locks — but track read sets for conflict detection
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN;
SELECT sum(balance) FROM accounts WHERE branch = 'NYC';
-- PostgreSQL records "this transaction read WHERE branch='NYC'"
-- If concurrent transaction inserts/modifies matching rows → abort one

-- 4. DDL operations (schema locks):
ALTER TABLE orders ADD COLUMN priority INT;
-- AccessExclusiveLock on table — blocks ALL operations including SELECT
-- MVCC cannot provide a "schema snapshot" — DDL needs full exclusion

-- 5. Foreign key checks:
INSERT INTO orders (customer_id, amount) VALUES (42, 100);
-- Acquires RowShareLock on customers table (prevents customer deletion)
-- Without this: concurrent DELETE FROM customers WHERE id=42 would
-- leave orphan orders

-- 6. VACUUM and maintenance:
VACUUM orders;
-- ShareUpdateExclusiveLock on table — blocks DDL but not DML
-- Needs exclusive access to clean dead tuples (not conflicting with MVCC reads)

# │  Aspect               │  Pure 2PL             │  MVCC + Locks           │
# ├────────────────────────┼───────────────────────┼─────────────────────────┤
# │  Readers vs writers    │  Block each other     │  Never block            │
# │  Writers vs writers    │  Block each other     │  Block each other       │

BigQuery slot contention

BigQuery doesn't use traditional row/table locks. Instead, contention manifests as slot contention (compute resources) and table mutation conflicts (concurrent DML on the same table). 


# BigQuery concurrency model:
#
# ┌──────────────────────────────────────────────────────────────────┐
# │  READS: No locks. Snapshot isolation via immutable columnar files│
# │         Multiple queries can read the same table simultaneously  │
# │         Each sees a consistent snapshot at query start time      │
# │                                                                  │
# │  WRITES (DML): Serialized conflict detection                    │
# │  • BigQuery serializes conflicting mutations internally          │
# │  • Concurrent DML is supported, but operations modifying         │
# │    overlapping data may be delayed or fail with serialization    │
# │    errors                                                        │
# │  • Rate-limited: subject to DML quotas per table (not a flat cap)│
# │                                                                  │
# │  STREAMING INSERTS: No table lock (append-only buffer)           │
# │  • Rows buffered in streaming buffer, eventually materialized    │
# │  • No conflict with batch DML or queries                         │
# │                                                                  │
# │  SLOT CONTENTION:                                                │
# │  • On-demand: 2000 slots shared across project                   │
# │  • If all slots busy: query queues (no error, just latency)      │
# │  • Flat-rate: dedicated slots per reservation                    │

Spark write conflicts on Delta Lake 

# Delta Lake: optimistic concurrency control (not locking)
#
# ┌──────────────────────────────────────────────────────────────────┐
# │  Delta Lake uses OPTIMISTIC CONCURRENCY:                         │
# │  • No locks acquired before writing                              │
# │  • At commit time: check if concurrent writes conflict           │
# │  • If conflict detected: FAIL the commit (ConcurrentModification)│
# │  • Application must retry                                        │
# │                                                                  │
# │  Conflict rules:                                                 │
# │  • Two APPEND operations → NEVER conflict (different files)      │
# │  • APPEND vs UPDATE/DELETE → conflict only if touching same files│
# │  • Two UPDATEs on same partition → may conflict if they modify   │
# │    overlapping files or rows within the same snapshot            │
# │  • UPDATE + OPTIMIZE → may conflict                              │
# │                                                                  │
# │  Conflict detection mechanism:                                   │
# │  1. Transaction reads current version (snapshot) at start        │
# │  2. Transaction writes new files                                 │
# │  3. At commit: check if snapshot version is still current        │
# │  4. If not: check if any new commits touch the same files/rows   │
# │  5. If overlap: ConcurrentModificationException → retry          │
# └──────────────────────────────────────────────────────────────────┘


# Delta Lake write conflict handling:
from delta.tables import DeltaTable
from pyspark.sql.functions import col
import time

def safe_merge_with_retry(spark, target_path, source_df, merge_key,
                          max_retries=3, backoff_base=5):
    """
    Perform Delta Lake MERGE with retry on concurrent modification.
    """
    for attempt in range(max_retries):
        try:
            target = DeltaTable.forPath(spark, target_path)
            target.alias("t").merge(
                source_df.alias("s"),
                f"t.{merge_key} = s.{merge_key}"
            ).whenMatchedUpdateAll() \
             .whenNotMatchedInsertAll() \
             .execute()
            return  # Success
        except Exception as e:
            if "ConcurrentModificationException" in str(e) or \
               "ConcurrentAppendException" in str(e):
                wait_time = backoff_base * (2 ** attempt)
                print(f"Write conflict (attempt {attempt + 1}), "
                      f"retrying in {wait_time}s...")
                time.sleep(wait_time)
            else:
                raise  # Non-retryable error
    raise RuntimeError(f"Failed after {max_retries} retries due to conflicts")

Root cause analysis 

-- ROOT CAUSE: ETL and OLTP competing for row-level X locks
-- on the same table with different lock acquisition orders.

-- ETL pattern (batch sequential order by internal ID):
BEGIN;
UPDATE orders
SET status = staging.status, amount = staging.amount
FROM staging_orders staging
WHERE orders.id = staging.id
  AND orders.id BETWEEN 1000001 AND 1100000;  -- batch by ID range
-- Locks rows 1000001..1100000 in ID order
COMMIT;

-- OLTP pattern (random access by customer request):
BEGIN;
SELECT * FROM orders WHERE id = 1050000 FOR UPDATE;
-- Application logic (50-200ms)
UPDATE orders SET status = 'shipped' WHERE id = 1050000;
-- Also triggers FK check: SELECT ... FROM customers WHERE id = X FOR SHARE
COMMIT;

-- The deadlock:
-- 1. ETL locks row 1050000 (in its batch range)
-- 2. OLTP request arrives: tries to lock row 1050000 → WAITS
-- 3. ETL continues: hits FK check → needs shared lock on customers row 42
-- 4. Different OLTP request: already holds lock on customers row 42
--    (doing: UPDATE customers SET last_order_date = now() WHERE id = 42)
--    and is waiting for orders row 1050100 (in ETL's batch)
-- 5. CYCLE: ETL → customers.42 → OLTP_2 → orders.1050100 → ETL
-- 6. PostgreSQL detects deadlock → kills ETL (more work to rollback)
-- 7. ETL retries → same scenario repeats with new batch overlap

-- Why this wasn't caught before:
-- • ETL previously ran at 04:00 (zero OLTP traffic)
-- • Cron schedule changed to 02:00 (overlaps with west-coast users)
-- • No lock_timeout set on ETL connection
-- • No deadlock monitoring/alerting
Fix and prevention measures 

-- FIX 1: Temporal separation (immediate)
-- Move ETL back to 04:00-05:00 UTC (no OLTP traffic)
-- Schedule via Airflow with SLA check:
--   Only run if API request rate < 10 req/min

-- FIX 2: Reduce lock hold time (medium-term)
-- Before: single transaction updating 100K rows (holds locks for minutes)
-- After: micro-batches of 1000 rows with explicit commits
-- NOTE: DO $$ blocks cannot use COMMIT; use application-level loop instead.

-- Option A: Use a PROCEDURE (PostgreSQL 11+) for in-database batching:
CREATE OR REPLACE PROCEDURE batch_update_orders(p_batch_size INT DEFAULT 1000)
LANGUAGE plpgsql AS $$
DECLARE
  batch_start BIGINT := 1;
  max_id BIGINT;
BEGIN
  SELECT max(id) INTO max_id FROM staging_orders;
  WHILE batch_start <= max_id LOOP
    UPDATE orders o
    SET status = s.status, amount = s.amount
    FROM staging_orders s
    WHERE o.id = s.id
      AND o.id >= batch_start
      AND o.id < batch_start + p_batch_size;
    COMMIT;  -- Allowed in procedures (not in DO blocks)
    batch_start := batch_start + p_batch_size;
    PERFORM pg_sleep(0.1);  -- 100ms breathing room for OLTP
  END LOOP;
END $$;

Lessons learned
  • Never share tables between ETL and OLTP without lock budgeting — use separate schemas, read replicas, or temporal separation
  • Set lock_timeout on all connections — fail fast rather than cascade
  • Batch DML with intermediate commits — 1K-10K rows per transaction, not 100K+
  • Monitor deadlock frequency — alert when deadlocks/hour exceeds baseline
  • Prefer optimistic concurrency for OLTP — version columns avoid long lock holds
  • Add pg_sleep between ETL batches — gives OLTP transactions time to complete
  • Consider read replicas for analytics queries — zero lock contention with primary
  • Log and alert on pg_stat_activity.wait_event = 'Lock' — early warning before deadlocks

    lc.root_blocked_pid,
    lc.blocked_pid,
    blocking.pid,
    lc.depth + 1,
    lc.chain || blocking.pid

  JOIN pg_locks blocking
    ON blocking.locktype = blocked.locktype
    AND blocking.relation = blocked.relation
    AND blocking.pid != blocked.pid
    AND blocking.granted = true
  WHERE lc.depth < 10
    AND NOT blocking.pid = ANY(lc.chain)  -- prevent infinite loops
)

Example 1: Deadlock-free batch update pattern 

"""
Deadlock-free batch update pattern for large tables.
Key principles:
1. Process in consistent primary key order
2. Small batch sizes (avoid lock escalation)
3. Explicit commit between batches (release locks)
4. Retry logic for transient deadlocks
"""
import psycopg2
import time
from contextlib import contextmanager

@contextmanager
def get_connection(dsn):
    conn = psycopg2.connect(dsn)
    conn.autocommit = False
    try:
        yield conn
    finally:
        conn.close()

def batch_update_safe(dsn: str, batch_size: int = 5000,
                      sleep_between: float = 0.05,
                      max_retries: int = 3):
    """
    Update rows in small batches with deadlock retry.
    
    Pattern avoids:
    - Lock escalation (batch_size < 5000)
    - Deadlocks (consistent PK ordering)
    - Long lock holds (commit per batch)
    - Starving OLTP (sleep between batches)
    """
    total_updated = 0
    last_id = 0

    while True:
        for attempt in range(max_retries):
            try:
                with get_connection(dsn) as conn:
                    with conn.cursor() as cur:
                        # Set lock timeout to fail fast
                        cur.execute("SET lock_timeout = '5s'")

                        # Update one batch in PK order
                        cur.execute("""
                            UPDATE orders
                            SET status = 'archived',
                                updated_at = now()
                            WHERE id IN (
                                SELECT id FROM orders
                                WHERE status = 'completed'
                                  AND completed_at < now() - interval '90 days'
                                  AND id > %s
                                ORDER BY id
                                LIMIT %s
                                FOR UPDATE SKIP LOCKED
                            )
                            RETURNING id
                        """, (last_id, batch_size))

                        rows = cur.fetchall()
                        if not rows:
                            print(f"Done. Total updated: {total_updated}")
                            conn.commit()
                            return total_updated

                        last_id = rows[-1][0]
                        total_updated += len(rows)
                        conn.commit()  # Release all locks

                        print(f"Batch complete: {len(rows)} rows "
                              f"(total: {total_updated}, last_id: {last_id})")

                break  # Success, exit retry loop

            except psycopg2.errors.DeadlockDetected:
                print(f"Deadlock on attempt {attempt + 1}, retrying...")
                time.sleep(backoff_time(attempt))
            except psycopg2.errors.LockNotAvailable:
                print(f"Lock timeout on attempt {attempt + 1}, retrying...")
                time.sleep(backoff_time(attempt))
        else:
            raise RuntimeError(f"Failed after {max_retries} retries at id={last_id}")

        # Breathing room for OLTP between batches
        time.sleep(sleep_between)

def backoff_time(attempt: int) -> float:
    """Exponential backoff with jitter."""
    import random
    return min(30, (2 ** attempt) + random.uniform(0, 1))

"""
Airflow DAG using advisory locks to prevent concurrent pipeline runs
on the same target table.
"""
from airflow import DAG
from airflow.operators.python import PythonOperator
from airflow.exceptions import AirflowSkipException
from datetime import datetime, timedelta
import psycopg2

DAG_ID = "daily_orders_etl"
LOCK_KEY = abs(hash(DAG_ID)) % (2**63)  # Consistent lock key from DAG name

default_args = {
    'owner': 'data-engineering',
    'retries': 2,
    'retry_delay': timedelta(minutes=5),
}

def acquire_pipeline_lock(**context):
    """Acquire advisory lock or skip if another instance is running."""
    conn = psycopg2.connect(context['params']['conn_string'])
    conn.autocommit = True
    cur = conn.cursor()

    cur.execute("SELECT pg_try_advisory_lock(%s)", (LOCK_KEY,))
    acquired = cur.fetchone()[0]

    if not acquired:
        conn.close()
        raise AirflowSkipException(
            f"Pipeline {DAG_ID} already running (lock {LOCK_KEY} held)"
        )

    # Store connection in XCom for release later
    # (In practice, store PID and reconnect in release task)
    context['ti'].xcom_push(key='lock_pid', value=conn.info.backend_pid)
    # Don't close connection — lock released on disconnect
    # Better: use transaction-level lock within the ETL transaction

def run_etl(**context):
    """Main ETL logic — runs only if lock acquired."""
    conn = psycopg2.connect(context['params']['conn_string'])
    try:
        with conn.cursor() as cur:
            # Acquire transaction-level advisory lock
            cur.execute("SELECT pg_advisory_xact_lock(%s)", (LOCK_KEY,))

            # ETL operations
            cur.execute("""
                INSERT INTO orders_warehouse
                SELECT * FROM orders_staging
                WHERE process_date = %s
                ON CONFLICT (order_id) DO UPDATE
                SET status = EXCLUDED.status,
                    amount = EXCLUDED.amount,
                    updated_at = now()
            """, (context['ds'],))

            rows = cur.rowcount
            conn.commit()
            print(f"ETL complete: {rows} rows upserted")
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()  # Advisory xact lock auto-released on commit/rollback

def release_pipeline_lock(**context):
    """Explicitly release advisory lock (safety net)."""
    conn = psycopg2.connect(context['params']['conn_string'])
    conn.autocommit = True
    cur = conn.cursor()
    cur.execute("SELECT pg_advisory_unlock(%s)", (LOCK_KEY,))
    conn.close()

with DAG(DAG_ID, default_args=default_args,
         schedule_interval='@daily',
         start_date=datetime(2024, 1, 1),
         catchup=False,
         params={'conn_string': 'postgresql://etl@db:5432/warehouse'}) as dag:

    lock = PythonOperator(task_id='acquire_lock', python_callable=acquire_pipeline_lock)
    etl = PythonOperator(task_id='run_etl', python_callable=run_etl)
    unlock = PythonOperator(task_id='release_lock', python_callable=release_pipeline_lock,
                            trigger_rule='all_done')  # Always release, even on failure

    lock >> etl >> unlock

Example 4: Optimistic locking pattern (version column) 

"""
Optimistic locking: avoid database locks entirely for OLTP updates.
Use a version column to detect concurrent modifications.
"""
import psycopg2
from dataclasses import dataclass
from typing import Optional

class OptimisticLockError(Exception):
    """Raised when a concurrent modification is detected."""
    pass

@dataclass
class Order:
    id: int
    status: str
    amount: float
    version: int  # Incremented on every update

def get_order(conn, order_id: int) -> Optional[Order]:
    """Read order with its current version."""
    with conn.cursor() as cur:
        cur.execute(
            "SELECT id, status, amount, version FROM orders WHERE id = %s",
            (order_id,)
        )
        row = cur.fetchone()
        if row:
            return Order(id=row[0], status=row[1], amount=row[2], version=row[3])
        return None

def update_order_optimistic(conn, order: Order, new_status: str,
                            max_retries: int = 3) -> Order:
    """
    Update order using optimistic locking.
    
    No SELECT FOR UPDATE needed — version column detects conflicts.
    This pattern eliminates row-level X locks during the read phase,
    dramatically reducing deadlock risk in high-contention scenarios.
    """
    for attempt in range(max_retries):
        with conn.cursor() as cur:
            cur.execute("""
                UPDATE orders
                SET status = %s,
                    version = version + 1,
                    updated_at = now()
                WHERE id = %s
                  AND version = %s
                RETURNING id, status, amount, version
            """, (new_status, order.id, order.version))

            row = cur.fetchone()

            if row:
                conn.commit()
                return Order(id=row[0], status=row[1],
                            amount=row[2], version=row[3])
            else:
                # Version mismatch — someone else updated first
                conn.rollback()

                if attempt < max_retries - 1:
                    # Re-read and retry with fresh version
                    order = get_order(conn, order.id)
                    if order is None:
                        raise ValueError(f"Order {order.id} no longer exists")
                    # Apply business logic validation on fresh data
                    continue

    raise OptimisticLockError(
        f"Order {order.id} was modified by another transaction "
        f"after {max_retries} retries"
    )

Common Mistakes

Mistake 1: Long-running transactions holding locks

The #1 cause of lock contention in production. A transaction that stays open for minutes (or hours) holds all its locks for the entire duration, blocking every other transaction that needs conflicting access. 


-- BAD: open transaction, do slow work, then commit
BEGIN;
SELECT * FROM orders WHERE id = 42 FOR UPDATE;
-- ... application does HTTP call to payment service (500ms - 30s) ...
-- ... lock held the entire time! ...
UPDATE orders SET status = 'paid' WHERE id = 42;
COMMIT;

-- GOOD: minimize lock hold time
-- Do all slow work BEFORE acquiring locks:
-- 1. Read data (MVCC snapshot, no lock)
SELECT * FROM orders WHERE id = 42;
-- 2. Call external service (no transaction open)
-- result = call_payment_service(order)
-- 3. Short transaction for the actual update:
BEGIN;
UPDATE orders SET status = 'paid', version = version + 1
WHERE id = 42 AND version = 5;  -- optimistic check
COMMIT;  -- Lock held for ~1ms, not 30s
Mistake 2: Missing lock_timeout in production 

-- BAD: default lock_timeout = 0 (wait forever!)
-- One stuck transaction can cascade-block hundreds of connections:
--
-- DDL waiting for idle-in-transaction:
--   ALTER TABLE orders ADD COLUMN x INT;  -- waits for AccessExclusiveLock
-- All subsequent queries queue behind the DDL:
--   SELECT * FROM orders WHERE id = 1;  -- blocked!
--   SELECT * FROM orders WHERE id = 2;  -- blocked!
--   INSERT INTO orders ...              -- blocked!
--   (Connection pool exhausted in minutes)

-- GOOD: always set lock_timeout
SET lock_timeout = '5s';
ALTER TABLE orders ADD COLUMN x INT;
-- If blocked for > 5s: ERROR: canceling statement due to lock timeout
-- Application can retry during off-peak

-- Set globally for safety:
ALTER SYSTEM SET idle_in_transaction_session_timeout = '300000';  -- 5 min
-- Prevents forgotten transactions from blocking DDL indefinitely
Mistake 3: SELECT FOR UPDATE when unnecessary 

-- BAD: using FOR UPDATE "just in case"
BEGIN;
SELECT * FROM orders WHERE customer_id = 42 FOR UPDATE;
-- Locks ALL orders for customer 42 (could be hundreds of rows)
-- Only needed one specific order
-- Other transactions updating this customer's orders: BLOCKED

-- GOOD: lock only what you'll modify
BEGIN;
SELECT * FROM orders WHERE id = 9001 FOR UPDATE;
-- Locks exactly one row
UPDATE orders SET status = 'shipped' WHERE id = 9001;
COMMIT;

-- BETTER: use optimistic locking if contention is low
UPDATE orders SET status = 'shipped', version = version + 1
WHERE id = 9001 AND version = current_version;

-- ALSO BAD: FOR UPDATE with LIMIT but without ORDER BY
SELECT * FROM orders WHERE status = 'pending'
FOR UPDATE LIMIT 10;
-- Which 10 rows? Nondeterministic → different transactions may
-- lock overlapping sets → deadlock risk

-- GOOD: deterministic ordering for SKIP LOCKED patterns
SELECT * FROM orders WHERE status = 'pending'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 10;
Mistake 4: Mixing DDL with DML in same transaction 

-- BAD: DDL + DML in one transaction (holds AccessExclusiveLock for duration)
BEGIN;
ALTER TABLE orders ADD COLUMN priority INT DEFAULT 0;
-- AccessExclusiveLock acquired → ALL queries on orders blocked
UPDATE orders SET priority = 1 WHERE status = 'urgent';
-- Could take minutes on large table
-- All queries still blocked!
CREATE INDEX idx_priority ON orders(priority);
-- Even longer...
COMMIT;
-- Table was locked for potentially 30+ minutes

-- GOOD: separate DDL from DML
-- Step 1: instant DDL (lock held briefly)
ALTER TABLE orders ADD COLUMN priority INT;  -- no default, instant
-- Step 2: backfill in batches (brief locks)
-- (use batch update pattern from code examples)
-- Step 3: concurrent index creation (non-blocking)
CREATE INDEX CONCURRENTLY idx_priority ON orders(priority);
-- Step 4: add default for future inserts
ALTER TABLE orders ALTER COLUMN priority SET DEFAULT 0;
Mistake 5: Ignoring lock ordering in application code 

# BAD: no consistent lock ordering → deadlock-prone
def process_transfer(from_id, to_id, amount):
    with db.transaction():
        # Lock source account
        db.execute("SELECT ... FROM accounts WHERE id=%s FOR UPDATE", from_id)
        # Lock destination account
        db.execute("SELECT ... FROM accounts WHERE id=%s FOR UPDATE", to_id)
        # If concurrent: transfer(A→B) and transfer(B→A) → DEADLOCK

# GOOD: always lock in consistent order (e.g., lower ID first)
def process_transfer_safe(from_id, to_id, amount):
    with db.transaction():
        ids = sorted([from_id, to_id])
        for account_id in ids:
            db.execute(
                "SELECT ... FROM accounts WHERE id=%s FOR UPDATE",
                account_id
            )
        # Now safe to proceed — no cycle possible
        db.execute("UPDATE accounts SET balance=balance-%s WHERE id=%s",
                   amount, from_id)
        db.execute("UPDATE accounts SET balance=balance+%s WHERE id=%s",
                   amount, to_id)
Mistake 6: Not using SKIP LOCKED for queue processing 

-- BAD: multiple workers fight over same rows
-- Worker 1:
SELECT * FROM job_queue WHERE status='pending' ORDER BY id LIMIT 1 FOR UPDATE;
-- Worker 2:
SELECT * FROM job_queue WHERE status='pending' ORDER BY id LIMIT 1 FOR UPDATE;
-- Worker 2 BLOCKED waiting for Worker 1 to finish the same row!
-- Only one worker active at a time — defeats purpose of multiple workers

-- GOOD: SKIP LOCKED lets each worker grab a different row
-- Worker 1:
SELECT * FROM job_queue WHERE status='pending'
ORDER BY id LIMIT 1
FOR UPDATE SKIP LOCKED;  -- grabs row 1

-- Worker 2 (concurrent):
SELECT * FROM job_queue WHERE status='pending'
ORDER BY id LIMIT 1
FOR UPDATE SKIP LOCKED;  -- skips row 1 (locked), grabs row 2

-- All workers proceed concurrently, each on different rows
-- Zero contention, zero blocking, zero deadlocks

Trade-offs

Fine-grained vs coarse-grained locks
  • Row locks (fine): Maximum concurrency — unrelated rows never conflict. But higher memory usage per lock, more complex deadlock graphs, and increased lock manager CPU.
  • Table locks (coarse): Minimal memory, simple deadlock detection, fast lock acquisition. But severely limits concurrency — all operations on the table serialize.
  • Decision: Use row-level for OLTP (many concurrent small transactions). Use table-level for bulk ETL on dedicated tables. Never mix without temporal separation or timeouts.
Pessimistic vs optimistic concurrency control
  • Pessimistic (SELECT FOR UPDATE): Guarantees no conflict at update time. Higher throughput under high contention because conflicts are prevented rather than detected-and-retried. But increases lock hold time and deadlock risk.
  • Optimistic (version column): No locks during read phase — maximum concurrency. But under high contention, retry storms can waste more resources than locks would. Each retry re-reads and re-computes.
  • Decision: Optimistic for low-to-moderate contention (most web apps). Pessimistic for high contention on specific hot rows (inventory, seat booking).

# Decision matrix:
# ┌─────────────────────┬──────────────────┬──────────────────────┐
# │  Scenario           │  Pessimistic     │  Optimistic          │
# ├─────────────────────┼──────────────────┼──────────────────────┤
# │  Low contention     │  Overhead waste  │  ✓ Best choice       │
# │  High contention    │  ✓ Best choice   │  Retry storms        │
# │  Long business logic│  Blocks others   │  ✓ No locks held     │
# │  Hot rows           │  ✓ Serializes    │  Too many retries    │
# │  Distributed system │  Hard to do      │  ✓ Natural fit       │
# └─────────────────────┴──────────────────┴──────────────────────┘
Lock timeout: strict vs lenient
  • Strict timeout (1-5s): Prevents cascade blocking, fails fast, enables retry-at-application-level. But may reject legitimate operations during brief contention spikes.
  • Lenient timeout (30s-5min): Tolerates brief contention without failing. But allows blocking chains to build up, risks connection pool exhaustion.
  • Decision: API/OLTP: strict (3-10s). ETL: moderate (30-60s). DDL migrations: strict (5-10s) with retry loop. Never use 0 (infinite) in production.
Advisory locks vs external lock services
  • PostgreSQL advisory locks: Zero additional infrastructure, session-level locks auto-release on disconnect, transactional semantics available. But tied to PostgreSQL availability, connection per lock holder, ~1ms latency.
  • Redis (SETNX + TTL): Sub-millisecond latency, language-agnostic, works across any services. But no auto-release on crash (relies on TTL expiry), potential split-brain with Redlock, requires Redis infrastructure.
  • ZooKeeper/etcd: Consensus-based correctness, ephemeral nodes auto-cleanup, well-suited for leader election. But operational complexity, higher latency (~5-10ms), additional infrastructure.
  • Decision: If you already have PostgreSQL and need coordination among services that connect to it — advisory locks. If cross-service with high throughput — Redis. If correctness-critical distributed coordination — ZooKeeper/etcd.
MVCC snapshot bloat vs lock-based blocking
  • MVCC (no read locks): Readers never block writers. But long-running read transactions prevent VACUUM from cleaning dead tuples → table bloat → degraded performance over time.
  • Lock-based (readers block writers): No table bloat issue. But mixed read/write workloads suffer from contention, lower throughput.
  • Decision: MVCC is almost always better for mixed workloads. Mitigate bloat with: short transactions, read replicas for long analytics queries, and aggressive VACUUM tuning.
Batched commits vs single large transaction
  • Single transaction: Atomicity guarantee — all-or-nothing. Simpler error handling (just ROLLBACK). But holds locks for duration, memory pressure, lock escalation risk.
  • Batched commits: Short lock holds, no escalation, concurrent-friendly. But no atomicity across batches (partial completion on failure), requires application-level progress tracking.
  • Decision: If all-or-nothing semantics are required (financial), use single transaction with appropriate isolation. For ETL/backfills where idempotent retry is possible, batch with progress checkpointing.

Follow-up Questions

Q1: How does PostgreSQL handle deadlocks differently from SQL Server?

PostgreSQL: Deadlock detection is triggered per-backend — when a backend has waited longer than deadlock_timeout (default 1s), it performs a deadlock check by examining the wait-for graph via DFS. Victim is one of the transactions participating in the cycle; the exact choice is implementation-specific rather than cost-based. No user-controllable priority setting.

SQL Server: Deadlock detection is proactive — the lock manager maintains the wait-for graph incrementally and checks for cycles every 5 seconds (or more frequently under contention). Victim selection is cost-based: the transaction with the least log generated (cheapest to rollback) is chosen, unless DEADLOCK_PRIORITY overrides. 


-- PostgreSQL: tune deadlock detection
ALTER SYSTEM SET deadlock_timeout = '500ms';  -- faster detection (more CPU)
-- Lower values: faster detection, more frequent (wasteful) WFG traversals
-- Higher values: less CPU, but longer wait before detection

-- SQL Server: trace deadlock graphs
DBCC TRACEON(1222, -1);  -- log deadlock graphs to error log
-- Or use Extended Events: system_health session captures deadlocks
SELECT XEvent.query('(event/data/value/deadlock)[1]')
FROM (
  SELECT CAST(target_data AS XML) AS TargetData
  FROM sys.dm_xe_session_targets st
  JOIN sys.dm_xe_sessions s ON s.address = st.event_session_address
  WHERE s.name = 'system_health'
    AND st.target_name = 'ring_buffer'
) AS Data
CROSS APPLY TargetData.nodes('//event[@name="xml_deadlock_report"]') AS XEventData(XEvent);
Q2: What happens when CREATE INDEX blocks on a busy table?

Standard CREATE INDEX acquires a ShareLock on the table, blocking all INSERT/UPDATE/DELETE operations for the duration of the index build. On large tables, this can take hours — effectively taking the table offline for writes.

CREATE INDEX CONCURRENTLY avoids this by using a multi-phase approach: it acquires only ShareUpdateExclusiveLock (compatible with DML) and builds the index while allowing concurrent modifications. The tradeoff: it takes longer, cannot run inside a transaction block, and may fail (leaving an INVALID index that must be dropped and recreated). 


-- Safe index creation on production tables:
CREATE INDEX CONCURRENTLY idx_orders_status ON orders(status);

-- Check for invalid indexes (from failed concurrent creation):
SELECT indexrelid::regclass, indisvalid
FROM pg_index
WHERE NOT indisvalid;

-- If invalid: drop and recreate
DROP INDEX CONCURRENTLY idx_orders_status;
CREATE INDEX CONCURRENTLY idx_orders_status ON orders(status);
Q3: How do you handle locking in a read-replica architecture?

Read replicas receive WAL records from the primary and replay them. If a replay needs to modify a page that a long-running query on the replica is reading, a conflict occurs. PostgreSQL handles this with max_standby_streaming_delay — queries on the replica are cancelled if they block replay for too long. 


# PostgreSQL streaming replica lock conflicts:
#
# Primary: UPDATE orders SET status='done' WHERE id=42;
#   → WAL record: "modify page 7 of orders"
#
# Replica: long-running SELECT scanning page 7 of orders
#   → Replay BLOCKED (can't modify page while query reads it)
#
# After max_standby_streaming_delay (default: 30s):
#   → Query on replica CANCELLED
#   → ERROR: canceling statement due to conflict with recovery
#
# Mitigation strategies:
# 1. Increase max_standby_streaming_delay (allows more query time)
# 2. Set hot_standby_feedback = on (primary delays VACUUM)
#    ⚠️ Can cause bloat on primary!
# 3. Use multiple replicas: one for fast queries, one for long analytics
# 4. Use logical replication (no replay conflicts, but different trade-offs)
Q4: What is a SIX (Shared + Intent Exclusive) lock and when is it used?

A SIX lock is held when a transaction reads an entire table (S lock) while simultaneously modifying some rows within it (IX for those rows). It's equivalent to holding S + IX on the same resource. The compatibility matrix shows SIX is only compatible with IS — meaning other transactions can read individual rows but cannot write to any row or read the entire table with S. 


-- Scenario requiring SIX lock:
-- "Read all rows in a table, update rows matching a condition"
BEGIN;
-- Conceptually: read full table (needs S) + update some rows (needs IX)
-- Combined: SIX lock on table

-- SQL Server: this manifests as SIX when using cursors or
-- when the optimizer chooses a table scan for the UPDATE:
UPDATE orders
SET discount = 0.10
WHERE total > (SELECT AVG(total) FROM orders);
-- Inner SELECT reads entire table (S intent)
-- UPDATE modifies qualifying rows (IX intent)
-- Combined table lock: SIX

-- In PostgreSQL, this is represented as RowExclusiveLock at table level
-- (PostgreSQL doesn't use explicit SIX terminology)
Q5: How does Delta Lake handle concurrent OPTIMIZE and write operations?

Delta Lake OPTIMIZE compacts small files into larger ones. Since Delta uses optimistic concurrency, a concurrent write (INSERT/UPDATE) that touches files being compacted will conflict at commit time. Delta Lake 2.0+ introduced file-level conflict detection: OPTIMIZE only conflicts with writes that modified the same set of files. 


# Delta Lake OPTIMIZE conflict scenarios:
#
# ┌──────────────────────────────────────────────────────────────────┐
# │  Operation A         │  Operation B        │  Conflict?          │
# ├──────────────────────┼─────────────────────┼─────────────────────┤
# │  OPTIMIZE partition1 │  INSERT partition1   │  Only if same files │
# │  OPTIMIZE partition1 │  INSERT partition2   │  No conflict ✓      │
# │  OPTIMIZE partition1 │  UPDATE partition1   │  Yes → retry        │
# │  OPTIMIZE partition1 │  OPTIMIZE partition1 │  Yes → one wins     │
# │  OPTIMIZE            │  APPEND (new files)  │  No conflict ✓      │
# └──────────────────────┴─────────────────────┴─────────────────────┘

# Best practice: run OPTIMIZE during low-write windows
# Or partition OPTIMIZE by time:
spark.sql("""
  OPTIMIZE delta.`s3://warehouse/events/`
  WHERE event_date = '2024-01-15'
""")

Q6: Can you have a deadlock with only one table?

Yes. A single-table deadlock occurs when two transactions update different rows in different orders, or when index traversal causes lock acquisition in different orders for different access paths. 


-- Single-table deadlock example:
-- T1:
BEGIN;
UPDATE accounts SET balance = 100 WHERE id = 1;  -- X lock on row 1
UPDATE accounts SET balance = 200 WHERE id = 2;  -- WAITS for T2

-- T2 (concurrent):
BEGIN;
UPDATE accounts SET balance = 300 WHERE id = 2;  -- X lock on row 2
UPDATE accounts SET balance = 400 WHERE id = 1;  -- WAITS for T1 → DEADLOCK

-- Also possible with a single UPDATE via different index paths:
-- If table has indexes on (col_a) and (col_b):
-- T1 scans via idx_col_a: locks rows in col_a order
-- T2 scans via idx_col_b: locks rows in col_b order
-- Same rows, different order → deadlock

-- Prevention: add ORDER BY to UPDATE subquery, or use consistent access path

Summary

Key takeaways
  • Lock modes — Shared (S) for reads, Exclusive (X) for writes, Intent (IS/IX) for hierarchical efficiency, Update (U) to prevent conversion deadlocks.
  • Granularity — Row-level maximizes concurrency; table-level minimizes overhead. The multigranularity protocol uses intent locks to make compatibility checking O(1).
  • Compatibility matrix — The foundational tool for reasoning about concurrency. IX+IX compatible (different rows), IX+S incompatible (writer intent vs full reader), X incompatible with everything.
  • Deadlocks — Circular wait in the lock graph. Detected via WFG traversal (PostgreSQL, SQL Server) or timeout (distributed systems). Prevented by consistent lock ordering and short transactions.
  • Lock escalation — SQL Server promotes row→table at ~5000 locks (memory protection). PostgreSQL doesn't escalate (row locks in tuple header = zero extra memory). Critical difference for bulk ETL design.
  • Advisory locks — Application-level coordination via PostgreSQL. Ideal for job deduplication, distributed locking, and rate limiting without external infrastructure.
  • MVCC interaction — MVCC eliminates read-lock needs (readers never block writers). Locks still needed for: write-write conflicts, DDL, FOR UPDATE, foreign keys.
  • Distributed systems — BigQuery uses table mutation locks, Snowflake has table-level DML locks, Delta Lake uses optimistic concurrency with file-level conflict detection.
  • Production essentials — Always set lock_timeout, batch large DML, use SKIP LOCKED for queues, monitor pg_locks/pg_stat_activity, prefer optimistic locking for OLTP.

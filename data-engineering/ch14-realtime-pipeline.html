Hard Kafka Flink

Design a Real-Time Event Processing Pipeline

Key Takeaway: Real-time pipelines require reasoning about event time vs processing time, watermarks for completeness, stateful windowed aggregations, and exactly-once guarantees — all while handling backpressure and out-of-order data.

Interviewer Intent

When a FAANG interviewer asks you to design a real-time event processing pipeline, they are probing multiple dimensions simultaneously:

  • Temporal reasoning: Can you distinguish event time from processing time, and do you understand why this matters for correctness?
  • Distributed systems intuition: How do you handle out-of-order data, late arrivals, and clock skew across thousands of producers?
  • Framework depth: Do you know when to reach for Flink vs Kafka Streams vs Spark Structured Streaming — and why?
  • Windowing semantics: Can you articulate tumbling, sliding, and session windows with their firing policies?
  • State management at scale: How do you manage terabytes of operator state with exactly-once guarantees?
  • Production readiness: Backpressure handling, monitoring, alerting, graceful degradation — the details that separate a whiteboard design from a production system.
  • Trade-off articulation: Latency vs completeness, state size vs accuracy, throughput vs exactly-once — senior engineers must reason about these trade-offs explicitly.

This is not a question about drawing boxes and arrows. The interviewer wants to see you reason through the hard parts — watermarks, state backends, checkpointing, reprocessing — with specificity and production experience.

Quick Answer

A production real-time event processing pipeline consists of:

  1. Ingestion layer: Kafka (or Kinesis/Pulsar) as a durable, partitioned event log with configurable retention.
  2. Processing engine: Apache Flink for logical record-at-a-time streaming with pipelined execution, event-time semantics, keyed state, and exactly-once state consistency via distributed snapshots (inspired by Chandy-Lamport). End-to-end exactly-once requires cooperation from both source (replayable) and sink (idempotent or transactional).
  3. Windowing & watermarks: Assign events to windows based on event time; use watermarks to track progress and trigger window computations; configure allowed lateness for stragglers.
  4. State management: RocksDB state backend for large state with incremental checkpointing; heap for low-latency small state.
  5. Sink layer: Write results to downstream systems (OLAP stores, caches, alerting) with idempotent writes for end-to-end exactly-once.
  6. Observability: Monitor consumer lag, checkpoint duration, watermark advancement, backpressure metrics, and state size growth.

The key insight: completeness and latency are fundamentally at odds. A 5-minute watermark delay gives you more complete results but adds 5 minutes of latency. The art is choosing the right trade-off for your use case — and building mechanisms (late-firing, side outputs, reprocessing) to handle the edge cases.

Event Time vs Processing Time

The Core Distinction

Every event in a streaming system carries two timestamps that tell fundamentally different stories:

Concept Definition Example
Event Time When the event actually occurred at the source User clicked "Buy" at 14:03:22 UTC
Processing Time When the event is observed by the processing engine Flink operator reads the record at 14:03:27 UTC
Ingestion Time When the event enters the streaming platform (Kafka) Kafka broker appends the record at 14:03:24 UTC

Why This Matters

If you window by processing time, your results are non-deterministic — they depend on network delays, consumer lag, and reprocessing speed. Consider this scenario:

  • A mobile app generates a purchase event at 14:00:00 (event time).
  • The device is in a tunnel; the event reaches Kafka at 14:05:30 (ingestion time).
  • Your Flink job processes it at 14:05:32 (processing time).

If you're computing "revenue per minute" and window by processing time, this purchase lands in the 14:05 bucket — 5 minutes late. Your 14:00 revenue figure is permanently undercounted. Event-time processing fixes this by placing the event in the 14:00 window where it logically belongs.

Clock Skew in Distributed Systems

In practice, event times are not perfectly reliable either:

  • NTP drift: Server clocks can drift 10–100ms between NTP syncs. Across a fleet of 10,000 producers, you'll see meaningful skew.
  • Mobile/IoT devices: Users can set their device clock incorrectly. A phone set to 2019 will produce events with timestamps 7 years in the past.
  • Timezone confusion: Producers that embed local time without timezone info create ambiguous timestamps.
  • Batch uploads: IoT devices that buffer events offline and upload in bulk create bursts of "old" events with valid event times.

Defensive Strategies

# Strategy 1: Bounded event-time skew validation
def validate_event_time(event, current_watermark):
    """Reject events with clearly invalid timestamps."""
    max_future_drift = timedelta(minutes=5)
    max_past_drift = timedelta(hours=24)

    now = datetime.utcnow()
    event_time = event.timestamp

    if event_time > now + max_future_drift:
        # Future event — likely clock skew
        route_to_dead_letter(event, reason="future_timestamp")
        return None

    if event_time < current_watermark - max_past_drift:
        # Too old — beyond allowed lateness
        route_to_dead_letter(event, reason="excessive_lateness")
        return None

    return event
// Strategy 2: Flink timestamp assigner with bounded disorder
public class BoundedEventTimeAssigner
    implements WatermarkStrategy<Event> {

  @Override
  public WatermarkGenerator<Event> createWatermarkGenerator(
      WatermarkGeneratorSupplier.Context context) {
    return new BoundedOutOfOrdernessWatermarks<>(
        Duration.ofSeconds(30)  // allow 30s of disorder
    );
  }

  @Override
  public TimestampAssigner<Event> createTimestampAssigner(
      TimestampAssignerSupplier.Context context) {
    return (event, recordTimestamp) -> event.getEventTime();
  }
}

When to Use Processing Time

Processing time is not always wrong. Use it when:

  • You need the lowest possible latency and can tolerate approximation (e.g., real-time dashboards that will be corrected by batch).
  • The source has no reliable event timestamp (some legacy systems).
  • You're measuring system health (throughput, latency) rather than business metrics.

Windowing Strategies

Why Windows?

Unbounded streams have no natural "end." Windows impose finite boundaries on infinite data, enabling aggregations (count, sum, avg) that require a defined scope. The choice of window type directly impacts result semantics, latency, and resource consumption.

Tumbling Windows

Fixed-size, non-overlapping, aligned windows. Every event belongs to exactly one window.

// Flink: 1-minute tumbling window on event time
DataStream<Event> events = ...;

events
    .keyBy(Event::getUserId)
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .aggregate(new CountAggregator())
    .addSink(new KafkaSink<>());
PropertyTumbling Window
OverlapNone — windows are contiguous and non-overlapping
Event assignmentEach event belongs to exactly one window
Use casesHourly aggregations, daily reports, minute-level metrics
State costLow — only one active window per key at a time

Sliding Windows

Fixed-size windows that advance by a configurable slide interval. Windows overlap, so a single event may contribute to multiple windows.

// Flink: 5-minute window, sliding every 1 minute
events
    .keyBy(Event::getUserId)
    .window(SlidingEventTimeWindows.of(
        Time.minutes(5),  // window size
        Time.minutes(1)   // slide interval
    ))
    .aggregate(new ClickRateAggregator());
PropertySliding Window
OverlapYes — window_size / slide_interval concurrent windows
Event assignmentEach event belongs to (window_size / slide) windows
Use casesMoving averages, trending topics, rolling metrics
State costHigh — 5x state if size=5min, slide=1min

Session Windows

Dynamic windows defined by a gap of inactivity. No fixed size — a session ends when no events arrive within the gap duration. This models user sessions naturally.

// Flink: session window with 30-minute inactivity gap
events
    .keyBy(Event::getUserId)
    .window(EventTimeSessionWindows.withGap(Time.minutes(30)))
    .process(new SessionAnalyzer());

// Dynamic gap based on event properties
events
    .keyBy(Event::getUserId)
    .window(EventTimeSessionWindows.withDynamicGap(
        new SessionWindowTimeGapExtractor<Event>() {
          @Override
          public long extract(Event event) {
            // Premium users get longer sessions
            return event.isPremium()
                ? 45 * 60 * 1000L   // 45 minutes
                : 30 * 60 * 1000L;  // 30 minutes
          }
        }
    ))
    .aggregate(new SessionMetrics());
PropertySession Window
SizeVariable — determined by data
MergingYes — late events can merge previously separate sessions
Use casesUser session analysis, clickstream, activity tracking
State costUnpredictable — depends on session length and merge frequency

Early and Late Firings

Windows don't have to fire only once. A sophisticated pipeline uses multiple trigger strategies:

// Flink: custom trigger with early firings every 10 seconds
events
    .keyBy(Event::getCategory)
    .window(TumblingEventTimeWindows.of(Time.hours(1)))
    .trigger(ContinuousEventTimeTrigger.of(Time.seconds(10)))
    .aggregate(new RevenueAggregator());

// Accumulation modes:
// ACCUMULATING: each firing includes all data seen so far
// DISCARDING: each firing only includes new data since last fire
  • Early firings: Emit partial/speculative results before the window closes — useful for dashboards that need "current hour so far" metrics.
  • On-time firing: The main result when the watermark passes the window end.
  • Late firings: Updates after the on-time result when late data arrives within the allowed lateness period.

Window Lifecycle

# Timeline of a 1-hour tumbling window [14:00, 15:00)
#
# 14:00:00  Window created (first event arrives)
# 14:10:00  Early firing #1 (speculative result)
# 14:20:00  Early firing #2 (speculative result)
# ...
# 15:00:00  Watermark passes 15:00 → ON-TIME firing
# 15:00:01  Window enters "allowed lateness" period
# 15:03:00  Late event arrives → LATE firing (updated result)
# 15:05:00  Allowed lateness expires → window state purged
# 15:05:01+ Any later events → dropped or routed to side output

Watermarks

What is a Watermark?

A watermark is a monotonically advancing assertion that says: "I believe no more events with event time ≤ W(t) will arrive." It's the mechanism by which a streaming engine tracks event-time progress and decides when to fire windows.

Crucially, watermarks are heuristic — they can be wrong. A watermark represents confidence rather than certainty; the engine accepts that some events may still arrive after the watermark has passed. An event may arrive after its watermark has passed (a "late" event). The system must handle this gracefully.

Watermark Generation Strategies

Strategy How It Works Trade-off
Bounded Out-of-Orderness W(t) = max_event_time_seen - max_delay Simple but conservative; fixed delay regardless of actual disorder
Per-Partition Watermarks Track watermark per Kafka partition; global = min(all partitions) One slow partition holds back entire pipeline
Idle Source Detection Mark idle partitions and exclude them from min-watermark calculation Prevents idle partitions from stalling; must detect "idle" correctly
Punctuation-Based Sources emit explicit watermark markers in the stream Perfect watermarks possible; requires source cooperation
Custom/ML-Based Learn the lateness distribution and adjust dynamically Adaptive but complex; risk of model drift

Flink Watermark Implementation

// Per-partition watermark strategy with idle detection
WatermarkStrategy<Event> strategy = WatermarkStrategy
    .<Event>forBoundedOutOfOrderness(Duration.ofSeconds(30))
    .withTimestampAssigner((event, ts) -> event.getEventTimeMs())
    .withIdleness(Duration.ofMinutes(2));  // mark source idle after 2min

DataStream<Event> stream = env
    .fromSource(kafkaSource, strategy, "kafka-events");

// Custom watermark generator for multi-modal lateness
public class AdaptiveWatermarkGenerator
    implements WatermarkGenerator<Event> {

  private long maxTimestamp = Long.MIN_VALUE;
  private final long maxOutOfOrderness;
  private long lastEmittedWatermark = Long.MIN_VALUE;

  public AdaptiveWatermarkGenerator(Duration maxDelay) {
    this.maxOutOfOrderness = maxDelay.toMillis();
  }

  @Override
  public void onEvent(Event event, long eventTimestamp,
                      WatermarkOutput output) {
    maxTimestamp = Math.max(maxTimestamp, eventTimestamp);
  }

  @Override
  public void onPeriodicEmit(WatermarkOutput output) {
    long newWatermark = maxTimestamp - maxOutOfOrderness;
    if (newWatermark > lastEmittedWatermark) {
      lastEmittedWatermark = newWatermark;
      output.emitWatermark(new Watermark(newWatermark));
    }
  }
}

Allowed Lateness

Even with watermarks, some events arrive late. Allowed lateness defines how long a window keeps its state after the watermark passes its end:

events
    .keyBy(Event::getRegion)
    .window(TumblingEventTimeWindows.of(Time.minutes(5)))
    .allowedLateness(Time.minutes(10))  // keep state 10 min after window closes
    .sideOutputLateData(lateOutputTag)  // events beyond allowed lateness
    .aggregate(new MetricsAggregator());

Watermark Propagation in a DAG

# Watermark flow in a multi-operator Flink job:
#
#  Source-1 (W=14:02:30)  ──┐
#                            ├──► Union ──► Window (fires when W ≥ window_end)
#  Source-2 (W=14:02:15)  ──┘       │
#                                    └── Global W = min(14:02:30, 14:02:15)
#                                                 = 14:02:15
#
# The slowest source dictates the global watermark.
# If Source-2 goes idle, we must detect this to avoid stalling.

Monitoring Watermarks

  • Watermark lag: current_processing_time - current_watermark. If this grows, your pipeline is falling behind.
  • Late events ratio: late_events / total_events. If > 5%, your watermark may be too aggressive.
  • Watermark advancement rate: Should track real-time (1 second of watermark per 1 second of wall clock). If slower, you're building debt.

State Management

Why State Matters

Streaming computations that go beyond stateless transformations (map, filter) require state. Aggregations, joins, deduplication, pattern detection — all require remembering something across events. In Flink, state can grow to terabytes per operator, making state management the single most critical production concern.

Types of State

State TypeScopeUse Case
Keyed State Per-key (partitioned by keyBy) Per-user counters, per-session accumulators, windowed aggregations
Operator State Per-operator instance (parallel subtask) Kafka consumer offsets, source split assignments, broadcast state
Broadcast State Replicated to all operator instances Dynamic rules, configuration updates, feature flags

State Backends

    .setBlockCacheSize("512mb")
    .setWriteBufferSize("128mb")

    .setCompactionStyle(CompactionStyle.LEVEL);

// HashMapStateBackend — for small state, low latency

Checkpointing

Checkpoints are Flink's mechanism for fault tolerance — periodic, consistent snapshots of all operator state and source positions:

// Production checkpoint configuration
env.enableCheckpointing(60_000);  // every 60 seconds
env.getCheckpointConfig().setCheckpointingMode(
    CheckpointingMode.EXACTLY_ONCE);
env.getCheckpointConfig().setMinPauseBetweenCheckpoints(30_000);
env.getCheckpointConfig().setCheckpointTimeout(600_000);  // 10 min timeout
env.getCheckpointConfig().setMaxConcurrentCheckpoints(1);
env.getCheckpointConfig().setTolerableCheckpointFailureNumber(3);

// Incremental checkpoints with RocksDB
env.getCheckpointConfig().setExternalizedCheckpointCleanup(
    ExternalizedCheckpointCleanup.RETAIN_ON_CANCELLATION);

// Checkpoint storage
env.getCheckpointConfig().setCheckpointStorage(
    "s3://my-bucket/flink-checkpoints/");

State TTL (Time-to-Live)

Without TTL, state grows unbounded. Configure TTL to automatically expire stale state:

// State with TTL — expire inactive keys after 24 hours
StateTtlConfig ttlConfig = StateTtlConfig.newBuilder(Time.hours(24))
    .setUpdateType(StateTtlConfig.UpdateType.OnReadAndWrite)
    .setStateVisibility(
        StateTtlConfig.StateVisibility.NeverReturnExpired)
    .cleanupInRocksdbCompactFilter(1000)  // clean during compaction
    .build();

ValueStateDescriptor<UserSession> descriptor =
    new ValueStateDescriptor<>("user-session", UserSession.class);
descriptor.enableTimeToLive(ttlConfig);

// Access in ProcessFunction
ValueState<UserSession> sessionState =
    getRuntimeContext().getState(descriptor);

Kafka as Event Backbone

Core Architecture

Apache Kafka serves as the durable, scalable, ordered event log at the center of most real-time architectures. Understanding its internals is essential for designing reliable pipelines.

# Kafka topology overview:
#
# Producers ──► Topic: "user-events" ──► Consumer Groups
#                  │
#                  ├── Partition 0: [msg0, msg3, msg6, msg9, ...]
#                  ├── Partition 1: [msg1, msg4, msg7, msg10, ...]
#                  └── Partition 2: [msg2, msg5, msg8, msg11, ...]
#
# Key insight: ordering guaranteed WITHIN a partition, not across partitions.
# Partition assignment: Kafka's default partitioner uses murmur2(key) % num_partitions

Topics and Partitions

ConceptRoleScaling Implication
Topic Logical channel for a category of events One topic per event type (user-clicks, orders, payments)
Partition Unit of parallelism and ordering Max consumer parallelism = number of partitions
Segment Physical file on disk (within a partition) Segment size controls retention granularity and compaction
Replica Durability copy on another broker RF=3 means 3 copies; ISR (in-sync replicas) must ack writes

Consumer Groups and Offset Management

// Kafka consumer configuration for exactly-once with Flink
Properties kafkaProps = new Properties();
kafkaProps.setProperty("bootstrap.servers", "kafka-1:9092,kafka-2:9092");
kafkaProps.setProperty("group.id", "flink-event-processor");
kafkaProps.setProperty("auto.offset.reset", "earliest");
kafkaProps.setProperty("enable.auto.commit", "false");  // Flink manages offsets
kafkaProps.setProperty("isolation.level", "read_committed");  // for EOS

KafkaSource<Event> source = KafkaSource.<Event>builder()
    .setProperties(kafkaProps)
    .setTopics("user-events")
    .setStartingOffsets(OffsetsInitializer.committedOffsets(
        OffsetResetStrategy.EARLIEST))
    .setDeserializer(new EventDeserializer())
    .build();

Offset Management Strategies

  • Auto-commit (at-most-once): Offsets committed on interval regardless of processing success. Data loss possible on crash.
  • Manual commit after processing (at-least-once): Commit after successful processing. Duplicates possible on crash between process and commit.
  • Flink checkpoint-based (exactly-once): Offsets stored in Flink's checkpoint alongside operator state. Atomically restored on failure.
  • Transactional (exactly-once produce): Kafka transactions ensure atomic writes across multiple partitions/topics.

Log Compaction

# Compaction vs Deletion retention:
#
# DELETION (default): segments deleted after retention.ms
#   Topic: user-clicks, retention: 7 days
#   → Old segments deleted; full event history lost
#
# COMPACTION: keeps latest value per key forever
#   Topic: user-profiles (compacted)
#   Key=user-123: {v1} → {v2} → {v3}
#   After compaction: only {v3} retained
#   → Useful for changelogs, materialized views, state rebuilding
#
# Config:
# cleanup.policy=compact
# min.compaction.lag.ms=3600000  # don't compact last hour
# delete.retention.ms=86400000  # tombstones kept 24h

Production Kafka Sizing

# Back-of-envelope calculation:
#
# Given:
#   - 500K events/sec peak
#   - Average event size: 1 KB
#   - Retention: 7 days
#   - Replication factor: 3
#
# Throughput: 500K * 1KB = 500 MB/s ingress

Latency Milliseconds (single-digit ms possible) 100ms–seconds (micro-batch interval) Milliseconds (within JVM process)

Scalability Scales to millions of events/sec per job Scales well but limited by micro-batch overhead Scales with Kafka partition count

When to Choose Each

Choose Flink when:

  • You need sub-second latency with exactly-once guarantees
  • Your state is large (GBs–TBs per operator) and needs incremental checkpointing
  • You need complex event processing (CEP), session windows, or async I/O
  • You're building a dedicated streaming platform team

Choose Spark Structured Streaming when:

  • Your team already uses Spark for batch processing
  • 100ms–1s latency is acceptable
  • You want unified batch and streaming APIs (Delta Lake, Iceberg)
  • You're on Databricks and want managed infrastructure

Choose Kafka Streams when:

  • Your processing is relatively simple (filter, map, aggregate)
  • You want to embed stream processing in a microservice
  • You don't want to manage a separate processing cluster
  • Your state fits on local disk of application instances

Micro-Batch vs True Streaming — The Latency Tax

# Spark Structured Streaming — micro-batch model
# Each "trigger" processes all events accumulated since last batch

spark.readStream \

    .load() \

        window(col("event_time"), "5 minutes"),

    .outputMode("update") \

Handling Out-of-Order Events

Why Out-of-Order is the Norm

In distributed systems, out-of-order arrival is the default, not the exception. Causes include:

  • Multi-path routing: Events from the same user may traverse different network paths with different latencies.
  • Partition rebalancing: Kafka consumer group rebalances pause consumption temporarily; ordering within each partition is preserved, but events from different partitions may appear to arrive in a different relative order to the new consumer assignment.
  • Producer retries: A producer retrying a failed send may deliver event N+1 before event N's retry succeeds.
  • Geographic distribution: Events from a user in Tokyo and another in NYC arrive at different times despite occurring simultaneously.
  • Offline/batch upload: Mobile devices or IoT sensors that buffer events and upload in bursts.

The Three Lines of Defense

1. Watermarks — Primary Mechanism

Watermarks define the boundary between "on-time" and "late." Events arriving before the watermark passes their window end are on-time; events arriving after are late.

// Configure watermark with 30-second tolerance for disorder
WatermarkStrategy<Event> strategy = WatermarkStrategy
    .<Event>forBoundedOutOfOrderness(Duration.ofSeconds(30))
    .withTimestampAssigner((event, ts) -> event.getTimestamp());

// This means: watermark = max_event_time - 30s
// Events within 30s of the latest seen event are "on-time"

2. Allowed Lateness — Second Chance

Even after the watermark passes a window's end, the window can remain open for additional time to accept late events:

events
    .keyBy(Event::getSessionId)
    .window(TumblingEventTimeWindows.of(Time.minutes(5)))
    .allowedLateness(Time.minutes(10))
    .aggregate(new SessionAggregator());

// Timeline for window [14:00, 14:05):
// watermark passes 14:05 → window fires (on-time result)
// 14:05 to 14:15 → late events accepted, window re-fires
// after 14:15 → events dropped (or routed to side output)

3. Side Outputs — Safety Net

Events that arrive beyond the allowed lateness are routed to a side output for separate handling:

// Define a tag for late events
final OutputTag<Event> lateEvents =
    new OutputTag<Event>("late-events") {};

SingleOutputStreamOperator<Result> mainStream = events
    .keyBy(Event::getUserId)
    .window(TumblingEventTimeWindows.of(Time.hours(1)))
    .allowedLateness(Time.minutes(30))
    .sideOutputLateData(lateEvents)
    .process(new WindowProcessor());

// Collect late events for reprocessing or alerting
DataStream<Event> lateStream = mainStream.getSideOutput(lateEvents);

lateStream
    .addSink(new KafkaSink<>("late-events-topic"))  // reprocessing topic for late events
    .name("late-events-sink");

Reprocessing Strategy for Late Data

# Lambda architecture approach for late data:
#
# 1. Speed layer (Flink): processes events in real-time
#    - Best-effort results with watermark-based completeness
#    - Late events beyond allowed lateness go to DLQ
#
# 2. Batch layer (Spark): nightly recomputation
#    - Reprocesses ALL events (including late arrivals)
#    - Produces "corrected" results that overwrite speed layer
#
# 3. Serving layer: merges speed + batch results
#    - Recent: speed layer results (approximate)
#    - Historical: batch layer results (complete)

# Alternative: Kappa architecture
# - Single stream processing with long retention
# - Reprocess by resetting consumer offsets
# - Simpler but requires Kafka retention ≥ correction window

Measuring Disorder

# Analyze your event stream's lateness distribution
# to set appropriate watermark bounds

from pyspark.sql import functions as F

events_df = spark.read.format("kafka").load()

lateness_stats = events_df.select(
    (F.col("processing_time") - F.col("event_time")).alias("lateness")
).agg(
    F.percentile_approx("lateness", 0.50).alias("p50_lateness"),
    F.percentile_approx("lateness", 0.95).alias("p95_lateness"),
    F.percentile_approx("lateness", 0.99).alias("p99_lateness"),
    F.percentile_approx("lateness", 0.999).alias("p999_lateness"),
    F.max("lateness").alias("max_lateness")
)

# p50=200ms, p95=2s, p99=30s, p999=5min, max=2hours

Backpressure & Flow Control

What is Backpressure?

Backpressure occurs when a downstream operator cannot process data as fast as the upstream operator produces it. Without flow control, this leads to unbounded buffer growth, OOM crashes, or data loss. A well-designed streaming system propagates backpressure gracefully.

Flink's Credit-Based Flow Control

Flink uses a credit-based system inspired by TCP flow control:

# Flink network buffer flow:
#
# Upstream Task          Network           Downstream Task
# ┌─────────────┐      ┌─────────┐      ┌─────────────────┐
# │ Output Buffers │──►│ Netty   │──►│ Input Buffers     │
# │ (per channel)  │    │ Channel │    │ (exclusive+floating)│
# └─────────────┘      └─────────┘      └─────────────────┘
#        ▲                                       │
#        └──── Credits (available buffer count) ──┘
#
# 1. Downstream grants credits = number of available input buffers
# 2. Upstream sends data only if credits > 0
# 3. When downstream processes a buffer, it sends new credit upstream
# 4. If downstream is slow → no credits → upstream blocks → backpressure
// Tuning Flink network buffers for backpressure handling
Configuration config = new Configuration();

// Buffers per channel (upstream → downstream link)
config.setInteger(
    "taskmanager.network.memory.buffers-per-channel", 2);

// Floating buffers shared across channels (absorb bursts)
config.setInteger(
    "taskmanager.network.memory.floating-buffers-per-gate", 8);

// Network memory fraction (of total task manager memory)
config.setString(
    "taskmanager.memory.network.fraction", "0.1");
config.setString(
    "taskmanager.memory.network.min", "128mb");
config.setString(
    "taskmanager.memory.network.max", "1gb");

Diagnosing Backpressure

# Flink Web UI indicators:
#
# 1. Task status colors:
#    - GREEN: healthy (buffers available)
#    - YELLOW: backpressured (output buffers full)
#    - RED: severely backpressured (sustained > 10s)
#
# 2. Key metrics:
#    - outPoolUsage > 0.9 → output buffers full → downstream is slow
#    - inPoolUsage > 0.9 → input buffers full → this operator is slow
#    - busyTimeMsPerSecond → how much time operator spends processing
#    - backPressuredTimeMsPerSecond → time spent waiting for output buffers
#
# 3. Finding the bottleneck:
#    - Walk downstream from first backpressured operator
#    - The operator with high busyTime but LOW outPoolUsage is the bottleneck
#    - It's consuming input fast but its downstream is slow

Production Incident: Watermark Too Tight

Real Incident: Streaming pipeline fell behind by 6 hours because the watermark was too tight, dropping 15% of late events during peak traffic.

Context

  • System: Flink job processing ad-impression events for billing reconciliation.
  • Scale: 2M events/sec from mobile SDKs across 40 countries.
  • Watermark config: BoundedOutOfOrderness = 10 seconds.
  • Allowed lateness: 30 seconds.
  • Window: 1-minute tumbling windows for impression counting.

The Trigger: Holiday Traffic Spike

# Black Friday traffic pattern:
#
# Normal day:  ~800K events/sec
# Black Friday: ~2.5M events/sec (3x spike)
#
# What happened:
# 1. Mobile SDK buffers events locally when network is congested
# 2. During peak shopping hours, cellular networks were saturated
# 3. Devices buffered 30-120 seconds of events
# 4. When network recovered, buffered events arrived in bursts
# 5. These events had event_times 30-120s in the past
# 6. Watermark (10s tolerance) had already advanced past them
# 7. Allowed lateness (30s) caught SOME but not all
# 8. Events > 40s late were DROPPED

Impact

MetricNormalDuring Incident
Late event ratio0.3%15.2%
Revenue undercounting$0$2.3M over 6 hours
Consumer lag~500ms6 hours (cascading)
Checkpoint duration12sFailed (timeout)
Alerts firing047 (alert fatigue)

Root Cause Analysis

# The cascade of failures:
#
# 1. INITIAL: Late events dropped → undercounting
#    └─► Watermark too tight for actual disorder during peak
#
# 2. SECONDARY: Dropped events routed to DLQ → DLQ Kafka topic
#    └─► DLQ consumer couldn't keep up → lag growing
#
# 3. TERTIARY: Operators buffering more state → checkpoint size grew
#    └─► Checkpoint timeout (10 min) exceeded → checkpoints failing
#
# 4. QUATERNARY: Without successful checkpoints, no progress committed
#    └─► If job crashed now, would replay from last checkpoint (6h ago)
#
# 5. OPERATIONAL: 47 alerts firing simultaneously
#    └─► On-call engineer overwhelmed → delayed response

Resolution Steps

  1. Immediate (30 min): Increased allowed lateness to 5 minutes via Flink REST API + savepoint restart.
  2. Short-term (2 hours): Scaled up Flink parallelism from 32 to 64 TaskManagers to chew through backlog. Note: scaling resolved the throughput backlog but did not recover events that had already been dropped due to the watermark configuration.
  3. Catchup (4 hours): Pipeline caught up to real-time after processing backlog at 2x speed.
  4. Reconciliation (next day): Batch job reprocessed the affected 6-hour window from Kafka (7-day retention) to produce corrected billing numbers. This was the only way to restore correctness for the dropped events.

Prevention Measures Implemented

// 1. Adaptive watermark based on observed lateness distribution
// Instead of fixed 10s, dynamically adjust based on p99 lateness.
// Note: this heuristic uses wall-clock time minus event time, which mixes
// processing time with event time. Alternative approaches track purely
// event-time disorder between consecutive events.
public class AdaptiveWatermark implements WatermarkGenerator<Event> {
  private final DescriptiveStatistics latencyStats =
      new DescriptiveStatistics(10_000);  // sliding window of 10K samples
  private long maxTimestamp = Long.MIN_VALUE;

  @Override
  public void onEvent(Event event, long eventTimestamp,
                      WatermarkOutput output) {
    long lateness = System.currentTimeMillis() - eventTimestamp;
    latencyStats.addValue(lateness);
    maxTimestamp = Math.max(maxTimestamp, eventTimestamp);
  }

  @Override
  public void onPeriodicEmit(WatermarkOutput output) {
    // Use p99 lateness as watermark delay, capped at 5 minutes
    long p99Lateness = (long) Math.min(
        latencyStats.getPercentile(99),
        5 * 60 * 1000L
    );
    output.emitWatermark(new Watermark(maxTimestamp - p99Lateness));
  }
}

// 2. Alert on late-event ratio, not just lag
// If late_events / total_events > 5% for 5 minutes → page

// 3. Separate DLQ processing pipeline with independent scaling

// 4. Checkpoint timeout scaled proportionally to state size

Lessons Learned

  • Watermarks must account for worst-case, not average-case lateness. 10s works in steady state but fails during traffic spikes when network congestion causes buffering.
  • Allowed lateness is your second line of defense — size it generously. For many production workloads, modestly increasing allowed lateness is often cheaper than losing business-critical events, though it does increase retained state proportionally.
  • Monitor the late-event ratio as a leading indicator. By the time consumer lag is hours, the damage is already done.
  • Design for reprocessing from day one. The batch reconciliation job saved us because Kafka retention was sufficient and the sink was idempotent.
  • Alerting must be actionable. 47 simultaneous alerts is noise. One alert that says "late-event ratio > 5% — consider increasing watermark tolerance" is signal.

Flink Windowed Aggregation (Java)

import org.apache.flink.api.common.eventtime.WatermarkStrategy;
import org.apache.flink.connector.kafka.source.KafkaSource;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;
import org.apache.flink.streaming.api.windowing.assigners.TumblingEventTimeWindows;
import org.apache.flink.streaming.api.windowing.time.Time;

public class RealtimeRevenueJob {

  public static void main(String[] args) throws Exception {
    StreamExecutionEnvironment env =
        StreamExecutionEnvironment.getExecutionEnvironment();

    // Checkpoint config
    env.enableCheckpointing(60_000);
    env.setStateBackend(new EmbeddedRocksDBStateBackend(true));
    env.getCheckpointConfig().setCheckpointStorage(
        "s3://data-platform/checkpoints/revenue-job");

    // Kafka source with watermarks
    KafkaSource<OrderEvent> source = KafkaSource.<OrderEvent>builder()
        .setBootstrapServers("kafka-prod:9092")
        .setTopics("order-events")
        .setGroupId("revenue-aggregator")
        .setStartingOffsets(OffsetsInitializer.committedOffsets(
            OffsetResetStrategy.EARLIEST))
        .setDeserializer(new OrderEventDeserializer())
        .build();

    WatermarkStrategy<OrderEvent> watermark = WatermarkStrategy
        .<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(30))
        .withTimestampAssigner((event, ts) -> event.getOrderTimestamp())
        .withIdleness(Duration.ofMinutes(2));

    // Late data side output
    final OutputTag<OrderEvent> lateOrders =
        new OutputTag<OrderEvent>("late-orders") {};

    // Processing pipeline
    SingleOutputStreamOperator<RevenueMetric> revenue = env
        .fromSource(source, watermark, "kafka-orders")
        .filter(order -> order.getStatus() == OrderStatus.COMPLETED)
        .keyBy(OrderEvent::getRegion)
        .window(TumblingEventTimeWindows.of(Time.minutes(5)))
        .allowedLateness(Time.minutes(10))
        .sideOutputLateData(lateOrders)
        .aggregate(
            new RevenueAggregator(),
            new RevenueWindowFunction()
        );

    // Main output → OLAP store
    revenue.addSink(new ClickHouseSink<>("revenue_5min"))
        .name("clickhouse-sink");

    // Late data → reprocessing topic
    revenue.getSideOutput(lateOrders)
        .addSink(new KafkaSink<>("late-orders-dlq"))
        .name("late-orders-dlq");

    env.execute("Realtime Revenue Aggregation");
  }
}

// Aggregate function: incremental aggregation for efficiency
public class RevenueAggregator
    implements AggregateFunction<OrderEvent, RevenueAccumulator, RevenueAccumulator> {

  @Override
  public RevenueAccumulator createAccumulator() {
    return new RevenueAccumulator(0L, BigDecimal.ZERO, 0L);
  }

  @Override
  public RevenueAccumulator add(OrderEvent event, RevenueAccumulator acc) {
    return new RevenueAccumulator(
        acc.getOrderCount() + 1,
        acc.getTotalRevenue().add(event.getAmount()),
        Math.max(acc.getMaxOrderValue(), event.getAmount().longValue())
    );
  }

  @Override
  public RevenueAccumulator getResult(RevenueAccumulator acc) {
    return acc;
  }

  @Override
  public RevenueAccumulator merge(RevenueAccumulator a, RevenueAccumulator b) {
    return new RevenueAccumulator(
        a.getOrderCount() + b.getOrderCount(),
        a.getTotalRevenue().add(b.getTotalRevenue()),
        Math.max(a.getMaxOrderValue(), b.getMaxOrderValue())
    );
  }
}

Kafka Streams Topology (Java)

import org.apache.kafka.streams.*;
import org.apache.kafka.streams.kstream.*;
import java.time.Duration;
import java.util.Properties;

public class ClickStreamTopology {

  public static void main(String[] args) {
    Properties props = new Properties();
    props.put(StreamsConfig.APPLICATION_ID_CONFIG, "click-analytics");
    props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
    props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, "exactly_once_v2");
    props.put(StreamsConfig.STATE_DIR_CONFIG, "/data/kafka-streams/state");
    props.put(StreamsConfig.NUM_STREAM_THREADS_CONFIG, 4);

    StreamsBuilder builder = new StreamsBuilder();

    // Source: user click events
    KStream<String, ClickEvent> clicks = builder.stream(
        "user-clicks",
        Consumed.with(Serdes.String(), clickEventSerde)
            .withTimestampExtractor(new ClickEventTimestampExtractor())
    );

    // Branch: separate page views from button clicks (using split() API, KS 3.0+)
    Map<String, KStream<String, ClickEvent>> branches = clicks.split(Named.as("click-"))
        .branch((key, event) -> event.getType() == ClickType.PAGE_VIEW,
            Branched.as("page-views"))
        .branch((key, event) -> event.getType() == ClickType.BUTTON_CLICK,
            Branched.as("button-clicks"))
        .defaultBranch(Branched.as("other"));

    KStream<String, ClickEvent> pageViews = branches.get("click-page-views");
    KStream<String, ClickEvent> buttonClicks = branches.get("click-button-clicks");

    // Windowed aggregation: page views per URL per minute
    KTable<Windowed<String>, Long> pageViewCounts = pageViews
        .groupBy((key, event) -> event.getUrl(),
            Grouped.with(Serdes.String(), clickEventSerde))
        .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
        .count(Materialized.as("page-view-counts"));

    // Session window: user sessions with 30-min inactivity gap
    KTable<Windowed<String>, SessionMetrics> userSessions = clicks
        .groupByKey()
        .windowedBy(SessionWindows.ofInactivityGapWithNoGrace(
            Duration.ofMinutes(30)))
        .aggregate(
            SessionMetrics::new,
            (key, event, metrics) -> metrics.addClick(event),
            (key, left, right) -> left.merge(right),
            Materialized.with(Serdes.String(), sessionMetricsSerde)
        );

    // Output: write results to output topics
    pageViewCounts.toStream()
        .map((windowedKey, count) -> KeyValue.pair(
            windowedKey.key(),
            new PageViewCount(windowedKey.key(), count,
                windowedKey.window().start())))
        .to("page-view-metrics",
            Produced.with(Serdes.String(), pageViewCountSerde));

    KafkaStreams streams = new KafkaStreams(builder.build(), props);
    streams.start();

    Runtime.getRuntime().addShutdownHook(
        new Thread(streams::close));
  }
}

Common Mistakes

MistakeWhy It's WrongCorrect Approach
Using processing time for business metrics Results are non-deterministic and change with reprocessing speed, consumer lag, or restarts Use event time with proper watermarks; processing time only for system metrics
Setting watermark too tight Drops legitimate late events during traffic spikes when network latency increases Analyze p99/p999 lateness distribution; set watermark to p99 + safety margin
No allowed lateness configured Events arriving even 1ms after watermark are immediately dropped Configure allowed lateness based on business requirements; use side outputs for data beyond
Unbounded state without TTL State grows forever → checkpoint size grows → eventually OOM or checkpoint timeout Configure State TTL; use session windows with gap timeout; monitor state size growth
Checkpoint interval too short Constant checkpointing creates I/O pressure and reduces throughput Set interval to 1–5 minutes; min-pause-between-checkpoints = interval / 2
Not handling idle partitions One idle Kafka partition holds back the global watermark → all windows stall Configure withIdleness() in watermark strategy; detect and mark idle sources
Synchronous external calls in operators One slow DB lookup blocks the entire operator chain → backpressure cascade Use Flink Async I/O or batch lookups; cache frequently accessed data in state
Ignoring Kafka partition count Max parallelism limited by partition count; can't add more consumers than partitions Plan partition count for peak load (not current); over-partition rather than under
Not testing with disordered data Pipeline works perfectly with ordered test data; fails in production with real disorder Generate test data with realistic lateness distributions; chaos-test with clock skew
Single-point-of-failure sinks If the sink is down, backpressure propagates all the way to the source Buffer to Kafka before slow sinks; use circuit breakers; implement fallback paths
Confusing at-least-once with exactly-once Flink's exactly-once only covers internal state; sinks need idempotent writes or transactions End-to-end exactly-once requires: source replay + checkpoint + idempotent/transactional sink

Trade-offs

Latency vs Completeness

ChoiceLatencyCompletenessUse Case
Tight watermark (5s) ~5s end-to-end ~95% (many late events dropped) Real-time dashboards with batch correction
Moderate watermark (30s) ~30s end-to-end ~99% (few late events) Fraud detection, alerting
Conservative watermark (5min) ~5min end-to-end ~99.9% (very few late events) Billing, financial reconciliation
Wait forever (no watermark advancement) Unbounded (never fires) 100% (theoretically) Never — this defeats the purpose of streaming

Key insight: You cannot have both zero latency and perfect completeness. The watermark delay is the knob that trades one for the other. Design your system with correction mechanisms (late firings, batch reconciliation) rather than trying to achieve perfect completeness in the streaming layer.

The Fundamental Tension

Every real-time pipeline design is a negotiation between three competing goals. You can optimize for two at the expense of the third:

  • Low Latency: Results available quickly after events occur.
  • Completeness: All events (including late arrivals) are included in results.
  • Low Resource Cost: Minimal state, compute, and storage overhead.

Pick any two. Want low latency + completeness? Pay for large state and long allowed lateness. Want low cost + completeness? Accept batch processing with higher latency. Want low latency + low cost? Accept approximate/incomplete results.

Summary

Key Takeaways for the Interview

  1. Event time is non-negotiable for correct business metrics. Processing time gives convenience but sacrifices determinism.
  2. Watermarks are heuristic assertions about event-time progress. They enable window firing but can be wrong — design for late data.
  3. Windows provide finite boundaries on infinite streams. Choose tumbling for simplicity, sliding for moving averages, session for user activity.
  4. State is your biggest operational challenge. Choose RocksDB for large state, configure TTL, monitor growth, and test checkpoint/restore.
  5. Kafka is the durable backbone. Understand partitions (ordering + parallelism), consumer groups, offset management, and compaction.
  6. Flink excels at complex streaming; Spark at batch/streaming unification; Kafka Streams at embedded simplicity.
  7. Backpressure is inevitable. Design for it with proper buffer sizing, async I/O, and graceful degradation strategies.
  8. The latency-completeness trade-off is fundamental. You cannot have both — choose based on business requirements and build correction mechanisms.
  9. End-to-end exactly-once requires cooperation between source (replay), engine (checkpoints), and sink (idempotent/transactional).
  10. Always design for reprocessing. Bugs happen. Retain source data, make sinks idempotent, and have a batch reconciliation path.

# Key design decisions:
# • Kafka retention ≥ max reprocessing window (7-30 days)
# • Checkpoint interval: 1-5 min (balance durability vs throughput)
# • Watermark: set to p99 lateness + safety margin
# • Allowed lateness: 10-30x watermark delay
# • Sinks: idempotent writes (upsert on primary key)
# • DLQ: separate pipeline for late/failed events
# • Monitoring: watermark lag, consumer lag, late-event ratio, state size

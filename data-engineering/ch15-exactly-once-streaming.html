How Do You Guarantee Exactly-Once Processing?

Key Takeaway: True exactly-once is impossible in distributed systems. We achieve "effectively exactly-once" through the combination of idempotent producers, transactional processing with checkpoints, and idempotent sinks — making duplicates invisible to the end result.

Interviewer Intent

When an interviewer asks "How do you guarantee exactly-once processing in a streaming system?", they are probing several dimensions of your distributed systems expertise:

  • Theoretical Foundation: Do you understand that true exactly-once delivery is impossible in distributed systems (per the Two Generals Problem and FLP impossibility result), and that what we actually achieve is "effectively exactly-once" through a combination of at-least-once delivery plus idempotent processing?
  • Systems Thinking: Can you reason about the end-to-end pipeline—source, processing engine, and sink—and identify where duplicates or data loss can occur at each stage?
  • Framework Expertise: Are you familiar with how Apache Kafka, Apache Flink, and Apache Spark implement exactly-once guarantees through transactions, checkpointing, and two-phase commit protocols?
  • Production Experience: Have you dealt with real failures—checkpoint corruption, offset rewinds, duplicate writes—and can you describe the mitigations you implemented?
  • Trade-off Awareness: Do you understand the latency, throughput, and complexity costs of exactly-once guarantees, and can you articulate when at-least-once with deduplication might be preferable?
  • Sink-Side Guarantees: Can you design idempotent sinks using upserts, deduplication tables, or conditional writes that prevent duplicate effects even when the same message is delivered multiple times?

A senior data engineer should demonstrate both breadth (knowing the landscape of techniques) and depth (being able to configure, debug, and optimize exactly-once pipelines in production).

Quick Answer

Exactly-once processing in streaming is achieved through effective exactly-once: combining at-least-once delivery with mechanisms that ensure duplicate processing has no additional effect. The three pillars are:

  1. Checkpointing with atomic offset commits: The processing engine periodically snapshots its state along with the source offsets it has consumed. On recovery, processing resumes from the last consistent snapshot, replaying messages but applying them idempotently.
  2. Transactional writes: Using Kafka transactions or two-phase commit protocols to atomically commit processed results and consumer offsets together, ensuring no gap between "processed" and "acknowledged."
  3. Idempotent sinks: Designing downstream stores to handle duplicate writes gracefully—through upserts keyed on event IDs, conditional inserts, or deduplication tables that track which events have already been applied.

In practice: Kafka provides transactional producers and read_committed consumers. Flink uses distributed snapshots (Chandy-Lamport algorithm) with barrier alignment and TwoPhaseCommitSinkFunction. The combination of these mechanisms across source, engine, and sink delivers end-to-end exactly-once semantics.

Delivery Semantics

The Three Guarantees

Distributed messaging systems offer three levels of delivery guarantees, each with distinct trade-offs in complexity, performance, and correctness:

Semantic Guarantee Failure Behavior Use Case
At-Most-Once Messages delivered zero or one time On failure, message is lost (fire-and-forget) Metrics, logging where loss is acceptable
At-Least-Once Messages delivered one or more times On failure, message is retried (potential duplicates) Most pipelines with idempotent consumers
Exactly-Once Messages processed with exactly one effect On failure, replay + dedup ensures single effect Financial transactions, billing, inventory

At-Most-Once: Fire and Forget

The simplest delivery model commits the consumer offset before processing the message. If the consumer crashes after committing but before processing, the message is permanently lost. This is appropriate only when occasional data loss is acceptable— such as real-time metrics dashboards or debug logging. 


Producer ──▶ Broker ──▶ Consumer
                         │
                    commit offset
                         │
                    process message  ← crash here = message lost

At-Least-Once: Retry on Failure

The consumer processes the message first, then commits the offset. If it crashes after processing but before committing, the message will be redelivered on restart. This guarantees no data loss but introduces the possibility of duplicates. 


Producer ──▶ Broker ──▶ Consumer
                         │
                    process message
                         │
                    commit offset  ← crash here = message reprocessed

Most production streaming pipelines use at-least-once delivery combined with idempotent processing to achieve effective exactly-once behavior. This is the most practical approach because:

  • It guarantees no data loss under any failure scenario
  • Duplicates can be handled at the sink layer
  • It has lower latency than full transactional exactly-once
  • It works across heterogeneous systems that may not support transactions

The Impossibility of True Exactly-Once

True exactly-once delivery—where a message is physically transmitted exactly one time across a network—is impossible in distributed systems. This follows from fundamental results in distributed computing:

  • Two Generals Problem: Two parties communicating over an unreliable channel cannot achieve common knowledge of message delivery. Any acknowledgment can itself be lost, requiring further acknowledgments ad infinitum.
  • FLP Impossibility: In an asynchronous system with even one faulty process, no deterministic algorithm can guarantee consensus. Since exactly-once requires consensus on whether a message was processed, it cannot be guaranteed in all cases.
  • Network Partitions: During a partition, the sender cannot distinguish between "message lost" and "acknowledgment lost," making it impossible to know whether exactly one delivery occurred.

Effective Exactly-Once: The Practical Solution

What modern streaming systems call "exactly-once" is more precisely effectively exactly-once or exactly-once semantics (EOS). The message may be physically delivered multiple times, but the system ensures that the effect of processing is applied exactly once. This is achieved through:

  1. Idempotent operations: Processing the same message multiple times produces the same result as processing it once. Example: setting a value (PUT) vs. incrementing a counter (non-idempotent without additional mechanisms).
  2. Transactional boundaries: Atomically committing the processing result and the consumer offset together, so either both succeed or both fail.
  3. Deterministic replay: On failure recovery, replaying from the last checkpoint produces identical results, and the sink can detect and discard duplicates.

Key Insight

"Exactly-once" in streaming does not mean a message is delivered exactly one time. It means the observable effect on downstream state is as if each message was processed exactly once. The implementation always involves at-least-once delivery combined with deduplication or transactional guarantees.

Where Each Semantic Applies

Scenario Acceptable Semantic Reasoning
Click-stream analytics At-Most-Once / At-Least-Once Approximate counts are acceptable; duplicates skew slightly
Payment processing Exactly-Once Double-charging customers is unacceptable
Sensor data ingestion At-Least-Once Idempotent upserts by sensor ID + timestamp handle duplicates
Order fulfillment Exactly-Once Shipping duplicate items has real cost
Log aggregation At-Least-Once Duplicate log lines are tolerable; loss is not
Inventory updates Exactly-Once Over-decrementing inventory causes stock-out errors

Kafka Transactions

Overview

Apache Kafka introduced transactions in version 0.11 (KIP-98) to enable exactly-once semantics for read-process-write patterns. Kafka transactions allow a producer to atomically write to multiple partitions and commit consumer offsets in a single atomic operation. If any part fails, the entire transaction is aborted and no partial results are visible to consumers reading at isolation.level=read_committed.

Transactional Producer

A Kafka transactional producer is configured with a unique transactional.id. This ID enables Kafka to fence zombie instances—if a producer with the same transactional ID starts up (e.g., after a restart), it will abort any pending transactions from the previous instance before proceeding. 


// Kafka Transactional Producer Configuration
Properties props = new Properties();
props.put("bootstrap.servers", "kafka-broker-1:9092,kafka-broker-2:9092");
props.put("transactional.id", "payment-processor-txn-001");
props.put("enable.idempotence", "true");  // Required for transactions
props.put("acks", "all");                  // Required for transactions
props.put("max.in.flight.requests.per.connection", "5");
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();

Read-Process-Write Pattern

The canonical exactly-once pattern in Kafka reads from input topics, processes the data, writes results to output topics, and commits the consumer offsets—all within a single transaction. This guarantees that either all operations succeed atomically, or none of them take effect. 


// Read-Process-Write with Kafka Transactions
KafkaConsumer<String, String> consumer = createConsumer();
consumer.subscribe(Collections.singletonList("payments-input"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));

    if (records.isEmpty()) continue;

    producer.beginTransaction();
    try {
        for (ConsumerRecord<String, String> record : records) {
            // Process the payment event
            PaymentResult result = processPayment(record.value());

            // Write result to output topic within the transaction
            producer.send(new ProducerRecord<>(
                "payments-processed",
                record.key(),
                result.toJson()
            ));
        }

        // Atomically commit offsets and produced messages
        Map<TopicPartition, OffsetAndMetadata> offsets = getConsumedOffsets(records);
        producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());
        producer.commitTransaction();

    } catch (ProducerFencedException | OutOfOrderSequenceException e) {
        // Fatal errors - cannot recover, must shut down
        producer.close();
        throw e;
    } catch (KafkaException e) {
        // Abort transaction and retry
        producer.abortTransaction();
        resetConsumerToLastCommittedOffsets(consumer);
    }
}

How Kafka Transactions Work Internally

Kafka's transaction protocol involves several components working together:

  1. Transaction Coordinator: A broker-side component (one per transactional.id, partitioned by hash) that manages the transaction lifecycle. It stores transaction metadata in an internal __transaction_state topic.
  2. Transaction Log: The __transaction_state internal topic stores the state machine for each transaction: Empty → Ongoing → PrepareCommit → CompleteCommit (or PrepareAbort → CompleteAbort).
  3. Producer ID and Epoch: Each transactional producer gets a unique PID (Producer ID) and an epoch number. The epoch is incremented on each initTransactions() call, fencing any older instances with the same transactional.id.
  4. Control Messages: Transaction commit/abort markers are written to each partition involved in the transaction. Consumers with isolation.level=read_committed filter out messages from aborted transactions and buffer messages from ongoing transactions until commit.

Isolation Level: read_committed

For exactly-once guarantees to work end-to-end in Kafka, consumers must be configured with isolation.level=read_committed. This ensures they only see messages from committed transactions: 


// Consumer configuration for exactly-once reads
Properties consumerProps = new Properties();
consumerProps.put("bootstrap.servers", "kafka-broker-1:9092");
consumerProps.put("group.id", "payment-consumer-group");
consumerProps.put("isolation.level", "read_committed");  // Critical for EOS
consumerProps.put("enable.auto.commit", "false");         // Manual offset management
consumerProps.put("auto.offset.reset", "earliest");

With read_committed, the consumer's poll() will not return messages that are part of an open or aborted transaction. The Last Stable Offset (LSO) tracks the earliest offset of any open transaction on a partition—consumers cannot read beyond this point until the transaction resolves.

Warning: LSO Lag

Long-running transactions or stuck producers can cause the LSO to lag behind the log end offset (LEO), blocking read_committed consumers from making progress. Configure transaction.timeout.ms (default 60s) to bound this lag. Monitor the records-lag metric on read_committed consumers to detect this condition.

Idempotent Producer (enable.idempotence=true)

Kafka's idempotent producer eliminates duplicates caused by producer retries. Each message batch is assigned a sequence number; the broker deduplicates based on (PID, partition, sequence number). This is a prerequisite for transactions and provides per-partition exactly-once for individual produce calls:

  • Handles network retries transparently—duplicate sends are detected and discarded
  • Ensures in-order delivery per partition even with max.in.flight.requests.per.connection=5
  • Requires acks=all to prevent data loss on leader failover
  • The broker maintains a sliding window of 5 sequence numbers per PID/partition

Checkpointing

Flink Distributed Snapshots (Chandy-Lamport Algorithm)

Apache Flink achieves exactly-once processing guarantees through distributed snapshots based on the Chandy-Lamport algorithm. This approach captures a globally consistent snapshot of all operator states and in-flight messages without stopping the pipeline.

How Flink Checkpointing Works

  1. Barrier Injection: The JobManager periodically injects checkpoint barriers into the source streams. These barriers are special markers that flow through the data stream alongside regular records.
  2. Barrier Alignment: When an operator with multiple inputs receives a barrier on one input, it buffers records from that input until barriers arrive on all inputs. This ensures the snapshot captures a consistent cut across all streams.
  3. State Snapshot: Once barriers are aligned, the operator snapshots its state (key-value state, window contents, timers) to the configured state backend (RocksDB, filesystem, or heap).
  4. Async Persistence: The snapshot is written asynchronously to durable storage (HDFS, S3, GCS) while the operator continues processing. This minimizes the performance impact of checkpointing.
  5. Completion: When all operators have acknowledged their snapshots, the checkpoint is marked complete. On failure, the job restores from the last complete checkpoint. 

Checkpoint Barrier Flow:

Source 1: ──── data ──── |barrier n| ──── data ──── |barrier n+1| ────▶
                              │
Operator A: ──── data ── |barrier n| ──── [snapshot state] ──── data ──▶
                              │
Source 2: ──── data ──── |barrier n| ──── data ──── |barrier n+1| ────▶
                              │
Operator B: ──── data ── |barrier n| ──── [snapshot state] ──── data ──▶
                              │
Sink:      ──── data ──── |barrier n| ── [commit to external system] ──▶

Unaligned Checkpoints (Flink 1.11+)

Traditional barrier alignment can cause backpressure when one input is slower than others. Flink 1.11 introduced unaligned checkpoints that include in-flight data (buffered records) in the snapshot rather than waiting for alignment:

  • Barriers overtake buffered records rather than waiting behind them
  • In-flight records between the barrier position and the buffer are included in the snapshot
  • Eliminates checkpoint-induced backpressure at the cost of larger snapshot sizes
  • Particularly beneficial for jobs with high parallelism and data skew

Flink Checkpoint Configuration


// Flink Checkpoint Configuration for Exactly-Once
StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

// Enable checkpointing every 30 seconds
env.enableCheckpointing(30000, CheckpointingMode.EXACTLY_ONCE);

// Advanced checkpoint configuration
CheckpointConfig config = env.getCheckpointConfig();
config.setMinPauseBetweenCheckpoints(10000);       // Min 10s between checkpoints
config.setCheckpointTimeout(120000);                // Timeout after 2 minutes
config.setMaxConcurrentCheckpoints(1);              // Only one at a time
config.setTolerableCheckpointFailureNumber(3);      // Allow 3 failures before job fails

// Retain checkpoints on job cancellation for manual recovery
config.setExternalizedCheckpointCleanup(
    CheckpointConfig.ExternalizedCheckpointCleanup.RETAIN_ON_CANCELLATION
);

// Use RocksDB state backend for large state
env.setStateBackend(new EmbeddedRocksDBStateBackend());

// Store checkpoints on S3

Spark Structured Streaming Checkpointing

Spark Structured Streaming uses a write-ahead log (WAL) and checkpoint directory to achieve exactly-once guarantees. The checkpoint stores:

  • Offset ranges: Which offsets from each source partition have been committed
  • State data: Aggregation state for stateful operations (watermarks, windows)
  • Commit log: Which micro-batches have been successfully written to the sink

Exactly-Once with Stateful Processing

Checkpointing is especially critical for stateful operations where operator state must be consistent with the processed input:

  • Windowed aggregations: Window contents are part of the checkpoint. On recovery, the window is restored and reprocessing does not double-count events that were already in the window.
  • Session windows: Active sessions and their accumulated state are snapshotted. Recovery restores the exact session boundaries.
  • Keyed state: Per-key state (counters, accumulators, last-seen values) is checkpointed alongside the offset. Replay from checkpoint produces identical state transitions.
  • Process functions with timers: Registered timers and their associated state are included in checkpoints. On recovery, timers fire at the correct times relative to event-time watermarks.

Key Insight

Checkpointing alone does not provide exactly-once to external systems. It guarantees exactly-once within the processing engine's state. For end-to-end exactly-once, you also need either idempotent sinks or two-phase commit protocols to coordinate with external systems.

Idempotent Sinks

The Principle

An idempotent sink produces the same result whether an operation is applied once or multiple times. This is the most robust approach to exactly-once because it works regardless of the delivery guarantee provided by the upstream system. Even with at-least-once delivery, an idempotent sink ensures no duplicate effects.

Database Upserts

The most common idempotent sink pattern uses database upserts (INSERT ON CONFLICT UPDATE or MERGE) keyed on a natural business key or event ID: 


-- PostgreSQL: Idempotent upsert for payment events
INSERT INTO processed_payments (
    payment_id,
    customer_id,
    amount,
    currency,
    status,
    processed_at,
    kafka_offset,
    kafka_partition
)
VALUES ($1, $2, $3, $4, $5, NOW(), $6, $7)
ON CONFLICT (payment_id)
DO UPDATE SET
    status = EXCLUDED.status,
    processed_at = EXCLUDED.processed_at,
    kafka_offset = EXCLUDED.kafka_offset
WHERE processed_payments.kafka_offset < EXCLUDED.kafka_offset;
-- Only update if the incoming offset is newer (prevents out-of-order overwrites)
        

-- MySQL: Idempotent upsert using INSERT ... ON DUPLICATE KEY
INSERT INTO order_events (
    event_id,
    order_id,
    event_type,
    payload,
    created_at
)
VALUES (?, ?, ?, ?, NOW())
ON DUPLICATE KEY UPDATE
    event_type = VALUES(event_type),
    payload = VALUES(payload),
    created_at = VALUES(created_at);

Deduplication Tables

When the sink operation is not naturally idempotent (e.g., incrementing a counter, appending to a log), use a deduplication table to track processed event IDs: 


-- Deduplication with transactional check-and-insert
BEGIN;

-- Check if we've already processed this event
SELECT 1 FROM processed_events WHERE event_id = $1;

-- If not found, process it
INSERT INTO processed_events (event_id, processed_at)
VALUES ($1, NOW());

-- Apply the non-idempotent operation
UPDATE account_balances
SET balance = balance + $2
WHERE account_id = $3;

COMMIT;
        

# Python implementation with deduplication table
class IdempotentSink:
    def __init__(self, db_pool):
        self.db_pool = db_pool

    async def process_event(self, event):
        async with self.db_pool.acquire() as conn:
            async with conn.transaction():
                # Check dedup table
                exists = await conn.fetchval(
                    "SELECT 1 FROM processed_events WHERE event_id = $1",
                    event.event_id
                )
                if exists:
                    # Already processed - skip silently
                    return

                # Record the event as processed
                await conn.execute(
                    "INSERT INTO processed_events (event_id, processed_at) VALUES ($1, NOW())",
                    event.event_id
                )

                # Apply the business logic (non-idempotent operation)
                await conn.execute(
                    "UPDATE account_balances SET balance = balance + $1 WHERE account_id = $2",
                    event.amount,
                    event.account_id
                )

Dedup Table Maintenance

Deduplication tables grow indefinitely unless pruned. Strategies for managing their size:

  • Time-based TTL: Delete entries older than the maximum replay window (e.g., if Kafka retention is 7 days, keep dedup entries for 8 days)
  • Partition by date: Use date-partitioned tables and drop old partitions (much faster than row-level deletes)
  • Offset-based pruning: Once all consumers have advanced past a certain offset, events at or below that offset will never be replayed 

-- Partition dedup table by date for efficient pruning
CREATE TABLE processed_events (
    event_id VARCHAR(64) NOT NULL,
    processed_at TIMESTAMP NOT NULL DEFAULT NOW(),
    PRIMARY KEY (event_id, processed_at)
) PARTITION BY RANGE (processed_at);

-- Create daily partitions
CREATE TABLE processed_events_20240101
    PARTITION OF processed_events
    FOR VALUES FROM ('2024-01-01') TO ('2024-01-02');

-- Drop old partitions (instant operation)
DROP TABLE processed_events_20231225;

BigQuery Streaming Buffer Deduplication

Google BigQuery's streaming insert API provides built-in deduplication through insertId. Records with the same insertId are deduplicated within a time window (best effort, approximately 1 minute): 


# BigQuery streaming insert with deduplication
from google.cloud import bigquery

client = bigquery.Client()
table_ref = client.dataset("payments").table("transactions")

def write_to_bigquery(events):
    rows_to_insert = []
    for event in events:
        rows_to_insert.append({
            "insertId": event.event_id,  # Deduplication key
            "json": {
                "payment_id": event.payment_id,
                "amount": event.amount,
                "currency": event.currency,
                "customer_id": event.customer_id,
                "processed_at": event.timestamp.isoformat(),
            }
        })

    errors = client.insert_rows_json(
        table_ref,
        rows_to_insert,
        row_ids=[r["insertId"] for r in rows_to_insert]
    )

    if errors:
        raise BigQueryInsertError(f"Failed to insert rows: {errors}")

BigQuery Dedup Limitations

BigQuery's insertId deduplication is best-effort and only works within the streaming buffer (before data is committed to columnar storage). For stronger guarantees, combine with a periodic MERGE statement that deduplicates the committed data: 


-- BigQuery: Periodic deduplication merge
MERGE INTO `project.dataset.payments_final` AS target
USING (
    SELECT *,
        ROW_NUMBER() OVER (PARTITION BY payment_id ORDER BY processed_at DESC) as rn
    FROM `project.dataset.payments_staging`
    WHERE DATE(processed_at) >= DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)
) AS source
ON target.payment_id = source.payment_id
WHEN MATCHED AND source.rn = 1 THEN
    UPDATE SET
        amount = source.amount,
        status = source.status,
        processed_at = source.processed_at
WHEN NOT MATCHED AND source.rn = 1 THEN
    INSERT (payment_id, amount, status, processed_at)
    VALUES (source.payment_id, source.amount, source.status, source.processed_at);

Conditional Writes in DynamoDB

DynamoDB conditional expressions provide atomic check-and-write that enables idempotent sinks: 


# DynamoDB conditional write for idempotency
import boto3
from botocore.exceptions import ClientError

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('processed_events')

def idempotent_write(event):
    try:
        table.put_item(
            Item={
                'event_id': event['event_id'],
                'payload': event['payload'],
                'processed_at': int(time.time()),
                'ttl': int(time.time()) + 86400 * 7  # 7-day TTL
            },
            ConditionExpression='attribute_not_exists(event_id)'
        )
        # First time processing - apply business logic
        apply_business_logic(event)
        return True
    except ClientError as e:
        if e.response['Error']['Code'] == 'ConditionalCheckFailedException':
            # Already processed - idempotent skip
            return False
        raise

Two-Phase Commit in Streaming

Overview

Two-phase commit (2PC) is a distributed consensus protocol that coordinates commits across multiple participants to ensure atomicity. In streaming, 2PC enables exactly-once delivery to external systems that support transactions (databases, Kafka, etc.) by tying the external commit to the checkpoint completion.

The Two Phases

  1. Phase 1 - Pre-commit (Prepare): During checkpointing, the sink operator pre-commits (prepares) the transaction in the external system but does not finalize it. Data is written but not yet visible to readers.
  2. Phase 2 - Commit: After the checkpoint completes successfully (all operators have acknowledged), the JobManager notifies the sink to commit the prepared transaction. Only then does the data become visible. 

Two-Phase Commit Timeline:

Checkpoint Triggered
    │
    ├─── Operator snapshots state
    │
    ├─── Sink: pre-commit (BEGIN + write + PREPARE)
    │         └── Data written but NOT visible
    │
    ├─── All operators acknowledge checkpoint
    │
    ├─── Checkpoint marked COMPLETE
    │
    └─── Sink: commit (COMMIT PREPARED)
              └── Data becomes visible to readers

On Failure (before checkpoint complete):
    └─── Sink: abort (ROLLBACK PREPARED)
              └── Pre-committed data is discarded

Flink TwoPhaseCommitSinkFunction

Flink provides the abstract class TwoPhaseCommitSinkFunction that implements the 2PC protocol integrated with Flink's checkpointing mechanism: 


// Flink Two-Phase Commit Sink for PostgreSQL
public class PostgresTwoPhaseCommitSink
    extends TwoPhaseCommitSinkFunction<PaymentEvent, Connection, Void> {

    @Override
    protected Connection beginTransaction() throws Exception {
        // Phase 0: Start a new transaction
        Connection conn = dataSource.getConnection();
        conn.setAutoCommit(false);
        return conn;
    }

    @Override
    protected void invoke(Connection transaction, PaymentEvent event, Context context)
        throws Exception {
        // Write data within the transaction (not yet visible)
        PreparedStatement stmt = transaction.prepareStatement(
            "INSERT INTO payments (payment_id, amount, status) VALUES (?, ?, ?) " +
            "ON CONFLICT (payment_id) DO UPDATE SET status = EXCLUDED.status"
        );
        stmt.setString(1, event.getPaymentId());
        stmt.setBigDecimal(2, event.getAmount());
        stmt.setString(3, event.getStatus());
        stmt.executeUpdate();
    }

    @Override
    protected void preCommit(Connection transaction) throws Exception {
        // Phase 1: Prepare the transaction (flush all writes)
        // For databases supporting PREPARE TRANSACTION:
        transaction.prepareStatement(
            "PREPARE TRANSACTION 'flink_checkpoint_" + getCurrentCheckpointId() + "'"
        ).execute();
    }

    @Override
    protected void commit(Connection transaction) {
        // Phase 2: Commit after checkpoint succeeds
        try {
            transaction.prepareStatement(
                "COMMIT PREPARED 'flink_checkpoint_" + getCurrentCheckpointId() + "'"
            ).execute();
        } catch (SQLException e) {
            throw new RuntimeException("Failed to commit prepared transaction", e);
        }
    }

    @Override
    protected void abort(Connection transaction) {
        // Abort if checkpoint fails
        try {
            transaction.prepareStatement(
                "ROLLBACK PREPARED 'flink_checkpoint_" + getCurrentCheckpointId() + "'"
            ).execute();
        } catch (SQLException e) {
            log.warn("Failed to rollback prepared transaction", e);
        }
    }
}

Critical: transaction.timeout.ms

The Kafka transaction.timeout.ms on the sink must be greater than the Flink checkpoint interval. If a transaction times out before the checkpoint completes, Kafka will abort it and data will be lost. Set it to at least 2x the checkpoint interval. Note: the Kafka broker's transaction.max.timeout.ms (default 15 minutes) caps this value.

Limitations of 2PC in Streaming

  • Blocking: Prepared transactions hold locks on the external system. Long checkpoint intervals mean long lock durations.
  • External system support required: The sink must support distributed transactions (PREPARE TRANSACTION). Not all databases/systems support this.
  • Recovery complexity: On job restart, the sink must be able to recover and either commit or abort any in-doubt (prepared but not committed) transactions from the previous run.
  • Increased latency: Data is not visible until the checkpoint completes and the commit phase executes, adding end-to-end latency equal to the checkpoint interval.
  • Coordinator failure: If the Flink JobManager fails after pre-commit but before commit, prepared transactions remain in-doubt until the job restarts and resolves them.

Deduplication Patterns

Event ID Tracking

The simplest deduplication approach assigns a globally unique ID to each event at the source and tracks which IDs have been processed. This works well when:

  • Events have natural unique identifiers (order_id, transaction_id)
  • The deduplication window is bounded (you don't need to remember all IDs forever)
  • The processing rate allows for per-event lookups

// Flink Event ID Deduplication with KeyedState
public class DeduplicationFunction
    extends KeyedProcessFunction<String, PaymentEvent, PaymentEvent> {

    // State to track processed event IDs with TTL
    private ValueState<Boolean> processedState;

    @Override
    public void open(Configuration parameters) {
        ValueStateDescriptor<Boolean> descriptor =
            new ValueStateDescriptor<>("processed", Boolean.class);

        // Configure state TTL for automatic cleanup
        StateTtlConfig ttlConfig = StateTtlConfig.newBuilder(Time.hours(24))
            .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
            .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
            .cleanupInRocksdbCompactFilter(1000)
            .build();
        descriptor.enableTimeToLive(ttlConfig);

        processedState = getRuntimeContext().getState(descriptor);
    }

    @Override
    public void processElement(PaymentEvent event, Context ctx,
        Collector<PaymentEvent> out) throws Exception {

        // Check if already processed
        Boolean processed = processedState.value();
        if (processed != null && processed) {
            // Duplicate - skip
            ctx.output(duplicateTag, event);
            return;
        }

        // Mark as processed
        processedState.update(true);

        // Emit for downstream processing
        out.collect(event);
    }
}

Bloom Filters for High-Volume Deduplication

When tracking millions of event IDs, exact set membership becomes expensive. Bloom filters provide space-efficient probabilistic deduplication with a configurable false positive rate (duplicate events incorrectly identified as new): 


// Bloom Filter Deduplication (space-efficient, probabilistic)
public class BloomFilterDedup
    extends KeyedProcessFunction<String, Event, Event> {

    private transient BloomFilter<String> bloomFilter;
    private ValueState<byte[]> bloomFilterState;

    @Override
    public void open(Configuration parameters) {
        bloomFilterState = getRuntimeContext().getState(
            new ValueStateDescriptor<>("bloom-filter", byte[].class)
        );
    }

    @Override
    public void processElement(Event event, Context ctx,
        Collector<Event> out) throws Exception {

        // Restore or create bloom filter
        byte[] serialized = bloomFilterState.value();
        if (serialized != null) {
            bloomFilter = deserializeBloomFilter(serialized);
        } else {
            // 10M expected insertions, 0.01% false positive rate
            bloomFilter = BloomFilter.create(
                Funnels.stringFunnel(Charsets.UTF_8),
                10_000_000,
                0.0001
            );
        }

        String eventId = event.getEventId();

        if (bloomFilter.mightContain(eventId)) {
            // Possible duplicate - send to secondary exact check or skip
            ctx.output(possibleDuplicateTag, event);
            return;
        }

        // Definitely new - add to filter and emit
        bloomFilter.put(eventId);
        bloomFilterState.update(serializeBloomFilter(bloomFilter));
        out.collect(event);
    }
}

Bloom Filter Trade-offs

Bloom filters have false positives (marking a new event as duplicate) but never false negatives (never letting a true duplicate through). For exactly-once, this means occasional data loss (false positive = dropped event). Use a two-tier approach: Bloom filter as fast check, then exact lookup for positives.

Time-Windowed Deduplication

Many streaming systems only need to deduplicate within a time window (e.g., the last 5 minutes). This bounds memory usage and is appropriate when the source guarantees that duplicates arrive within a known time skew: 


// Time-windowed deduplication using Flink's window state
public class WindowedDedup extends ProcessWindowFunction<
    Event, Event, String, TimeWindow> {

    @Override
    public void process(String key, Context context,
        Iterable<Event> elements, Collector<Event> out) {

        // Within each window, deduplicate by event ID
        Map<String, Event> seen = new HashMap<>();
        for (Event event : elements) {
            seen.putIfAbsent(event.getEventId(), event);
        }

        // Emit only unique events
        seen.values().forEach(out::collect);
    }
}

Redis-Based Deduplication

Redis provides fast, centralized deduplication that works across multiple consumer instances. The SET NX (set if not exists) command with TTL provides atomic check-and-mark: 


# Redis-based deduplication with TTL
import redis
import hashlib

class RedisDeduplicator:
    def __init__(self, redis_url, ttl_seconds=3600):
        self.redis = redis.Redis.from_url(redis_url)
        self.ttl = ttl_seconds
        self.prefix = "dedup:"

    def is_duplicate(self, event_id: str) -> bool:
        """
        Returns True if event was already processed (duplicate).
        Uses SET NX for atomic check-and-mark.
        """
        key = f"{self.prefix}{event_id}"
        # SET NX returns True if key was set (new event), False if exists (duplicate)
        is_new = self.redis.set(key, "1", nx=True, ex=self.ttl)
        return not is_new

    def process_event(self, event):
        if self.is_duplicate(event["event_id"]):
            # Already processed - skip
            metrics.increment("dedup.duplicates_skipped")
            return None

        # Process the event
        result = self._apply_business_logic(event)
        metrics.increment("dedup.events_processed")
        return result

    def batch_check(self, event_ids: list) -> dict:
        """
        Check multiple event IDs in a single pipeline call.
        Returns dict of {event_id: is_duplicate}
        """
        pipe = self.redis.pipeline()
        for eid in event_ids:
            pipe.set(f"{self.prefix}{eid}", "1", nx=True, ex=self.ttl)
        results = pipe.execute()
        return {eid: not is_new for eid, is_new in zip(event_ids, results)}

End-to-End Exactly-Once

The Three-Layer Model

End-to-end exactly-once is not a property of any single component. It requires coordinated guarantees across three layers of the streaming pipeline: 


End-to-End Exactly-Once = Source Guarantee + Processing Guarantee + Sink Guarantee

Source Requirements

For exactly-once to work, the source must be replayable. The processing engine must be able to re-read data from a known position after a failure. Sources that support this:

  • Apache Kafka: Durable log with offset-based replay. Consumers can seek to any offset within retention. The gold standard for replayable sources.
  • AWS Kinesis: Shard iterators with sequence numbers. Supports replay within retention period (default 24h, max 365 days).
  • Apache Pulsar: Durable log with cursor-based replay. Supports both exclusive and shared subscriptions with exactly-once.
  • File-based (S3/GCS/HDFS): Files are immutable and always replayable. Track processed files in checkpoint state.
  • Database CDC: WAL-based CDC (Debezium) produces a replayable stream with LSN/GTID positions.

Sources that do not support replay (and thus cannot participate in exactly-once): UDP streams, webhooks without replay, MQTT with QoS 0.

Processing Layer Requirements

The processing engine must maintain consistent state and support deterministic replay:

  • Consistent checkpoints: Atomically snapshot operator state and source positions so recovery resumes from a consistent point.
  • Deterministic processing: Given the same input from the same offset, the engine produces the same output. Non-deterministic operations (wall-clock time, random values, external calls) must be captured in state or made deterministic.
  • Exactly-once state updates: Internal state is updated exactly once per event, enforced by the checkpoint/restore mechanism.

Non-Determinism Breaks Exactly-Once

If processing logic uses System.currentTimeMillis(), random numbers, or makes external API calls with side effects, replay may produce different results. Use event-time (from the message) instead of wall-clock time, seed random generators from message content, and guard external calls with the dedup pattern.

Sink Requirements

The sink is where exactly-once is most challenging because you're writing to an external system outside the processing engine's transactional boundary. Two approaches:

Approach 1: Transactional Sink (2PC)

Coordinate the sink's transaction with the checkpoint using two-phase commit. The sink writes are only made visible (committed) when the checkpoint completes.

  • Requires the external system to support transactions (Kafka, PostgreSQL, MySQL)
  • Adds latency equal to checkpoint interval before data is visible
  • Complex failure recovery (in-doubt transactions)

Approach 2: Idempotent Sink

Design the write operation so that applying it multiple times has the same effect as applying it once. On replay/reprocessing, duplicate writes are harmless.

  • Works with any storage system that supports upserts or conditional writes
  • Lower latency (writes visible immediately)
  • Simpler implementation and recovery
  • Requires careful key design and event ID propagation

Root Cause Analysis

  1. Primary cause: The PostgreSQL sink used a plain INSERT statement without ON CONFLICT handling. When events were replayed after the checkpoint restore, each produced a new row with a new auto-generated primary key.
  2. Contributing factor: The internal transaction ID was generated using UUID.randomUUID() at processing time rather than being derived deterministically from the event ID. This meant replayed events got new transaction IDs and were treated as new payments by the downstream gateway.
  3. Contributing factor: The checkpoint timeout (120s) was too aggressive for the state size. Large RocksDB snapshots to S3 regularly took 90-100s under normal conditions, leaving little margin for S3 latency spikes.
  4. Detection gap: No real-time duplicate detection was in place. The anomaly was only detected through customer complaints 27 minutes after the duplicates were processed.

  • Checkpoint health dashboard: Tracking checkpoint duration, size, failure rate, and time-since-last-successful-checkpoint
  • Offset lag monitoring: Alert if consumer lag exceeds the checkpoint interval (indicates potential replay window growing)
  • Sink duplicate rate metric: Counter on ON CONFLICT DO UPDATE matches (indicates replayed events hitting the upsert path)

Lesson Learned

Never rely solely on exactly-once checkpointing for correctness. Checkpointing provides exactly-once for internal state, but external sinks must independently guarantee idempotency. The sink is your last line of defense against duplicates—design it to be safe regardless of how many times the same event is delivered.

Kafka Transactional Producer (Complete)


import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.TopicPartition;
import org.apache.kafka.common.errors.ProducerFencedException;
import java.time.Duration;
import java.util.*;

/**
 * Complete exactly-once Kafka read-process-write loop.
 * Demonstrates transactional producer with consumer offset commits.
 */
public class ExactlyOnceKafkaProcessor {

    private final KafkaProducer<String, String> producer;
    private final KafkaConsumer<String, String> consumer;
    private final String outputTopic;

    public ExactlyOnceKafkaProcessor(String bootstrapServers,
        String inputTopic, String outputTopic, String groupId) {

        this.outputTopic = outputTopic;

        // Producer config - transactional
        Properties producerProps = new Properties();
        producerProps.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, bootstrapServers);
        producerProps.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG,
            "eos-processor-" + groupId);
        producerProps.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        producerProps.put(ProducerConfig.ACKS_CONFIG, "all");
        producerProps.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);
        producerProps.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
            "org.apache.kafka.common.serialization.StringSerializer");
        producerProps.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
            "org.apache.kafka.common.serialization.StringSerializer");

        this.producer = new KafkaProducer<>(producerProps);
        this.producer.initTransactions();

        // Consumer config - read_committed
        Properties consumerProps = new Properties();
        consumerProps.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, bootstrapServers);
        consumerProps.put(ConsumerConfig.GROUP_ID_CONFIG, groupId);
        consumerProps.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");
        consumerProps.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
        consumerProps.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        consumerProps.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
            "org.apache.kafka.common.serialization.StringDeserializer");
        consumerProps.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
            "org.apache.kafka.common.serialization.StringDeserializer");

        this.consumer = new KafkaConsumer<>(consumerProps);
        this.consumer.subscribe(Collections.singletonList(inputTopic));
    }

    public void run() {
        try {
            while (true) {
                ConsumerRecords<String, String> records =
                    consumer.poll(Duration.ofMillis(200));

                if (records.isEmpty()) continue;

                producer.beginTransaction();
                try {
                    // Process each record and produce output
                    for (ConsumerRecord<String, String> record : records) {
                        String result = processRecord(record);
                        producer.send(new ProducerRecord<>(
                            outputTopic, record.key(), result
                        ));
                    }

                    // Commit offsets within the transaction
                    Map<TopicPartition, OffsetAndMetadata> offsets =
                        computeOffsets(records);
                    producer.sendOffsetsToTransaction(
                        offsets, consumer.groupMetadata()
                    );

                    // Atomic commit: output messages + offset advancement
                    producer.commitTransaction();

                } catch (ProducerFencedException e) {
                    // Another instance took over - shut down
                    throw e;
                } catch (Exception e) {
                    // Abort and retry from last committed offset
                    producer.abortTransaction();
                    resetToCommittedOffsets();
                }
            }
        } finally {
            producer.close();
            consumer.close();
        }
    }

    private Map<TopicPartition, OffsetAndMetadata> computeOffsets(
        ConsumerRecords<String, String> records) {
        Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
        for (TopicPartition partition : records.partitions()) {
            List<ConsumerRecord<String, String>> partRecords =
                records.records(partition);
            long lastOffset = partRecords.get(partRecords.size() - 1).offset();
            offsets.put(partition, new OffsetAndMetadata(lastOffset + 1));
        }
        return offsets;
    }

    private void resetToCommittedOffsets() {
        Set<TopicPartition> assignment = consumer.assignment();
        Map<TopicPartition, OffsetAndMetadata> committed =
            consumer.committed(assignment);
        for (Map.Entry<TopicPartition, OffsetAndMetadata> entry :
            committed.entrySet()) {
            if (entry.getValue() != null) {
                consumer.seek(entry.getKey(), entry.getValue().offset());
            }
        }
    }

    private String processRecord(ConsumerRecord<String, String> record) {
        // Business logic here
        return "{\"processed\": true, \"original\": " + record.value() + "}";
    }
}

Idempotent Sink Implementation (JDBC)


import org.apache.flink.streaming.api.functions.sink.RichSinkFunction;
import org.apache.flink.configuration.Configuration;
import java.sql.*;

/**
 * Idempotent JDBC sink that uses upserts for exactly-once delivery.
 * Handles duplicates gracefully via ON CONFLICT clause.
 */
public class IdempotentJdbcSink extends RichSinkFunction<PaymentResult> {

    private final String jdbcUrl;
    private final String upsertSql;
    private transient Connection connection;
    private transient PreparedStatement statement;
    private int batchCount = 0;
    private static final int BATCH_SIZE = 500;

    public IdempotentJdbcSink(String jdbcUrl) {
        this.jdbcUrl = jdbcUrl;
        this.upsertSql =
            "INSERT INTO payment_results " +
            "(event_id, payment_id, customer_id, amount, status, " +
            " source_partition, source_offset, processed_at) " +
            "VALUES (?, ?, ?, ?, ?, ?, ?, NOW()) " +
            "ON CONFLICT (event_id) DO UPDATE SET " +
            "  status = EXCLUDED.status, " +
            "  processed_at = EXCLUDED.processed_at " +
            "WHERE payment_results.source_offset < EXCLUDED.source_offset";
    }

    @Override
    public void open(Configuration parameters) throws Exception {
        connection = DriverManager.getConnection(jdbcUrl);
        connection.setAutoCommit(false);
        statement = connection.prepareStatement(upsertSql);
    }

    @Override
    public void invoke(PaymentResult result, Context context) throws Exception {
        statement.setString(1, result.getEventId());
        statement.setString(2, result.getPaymentId());
        statement.setString(3, result.getCustomerId());
        statement.setBigDecimal(4, result.getAmount());
        statement.setString(5, result.getStatus());
        statement.setInt(6, result.getSourcePartition());
        statement.setLong(7, result.getSourceOffset());
        statement.addBatch();
        batchCount++;

        if (batchCount >= BATCH_SIZE) {
            flush();
        }
    }

    private void flush() throws SQLException {
        if (batchCount > 0) {
            statement.executeBatch();
            connection.commit();
            batchCount = 0;
        }
    }

    @Override
    public void close() throws Exception {
        flush();
        if (statement != null) statement.close();
        if (connection != null) connection.close();
    }
}

Deduplication with Flink Keyed State


import org.apache.flink.api.common.state.*;
import org.apache.flink.api.common.time.Time;
import org.apache.flink.streaming.api.functions.KeyedProcessFunction;
import org.apache.flink.util.Collector;
import org.apache.flink.util.OutputTag;

/**
 * Stateful deduplication using Flink keyed state with TTL.
 * Events are keyed by event_id; duplicates within the TTL window are filtered.
 */
public class StatefulDeduplication
    extends KeyedProcessFunction<String, PaymentEvent, PaymentEvent> {

    private static final OutputTag<PaymentEvent> DUPLICATE_TAG =
        new OutputTag<PaymentEvent>("duplicates") {};

    private transient ValueState<Long> firstSeenState;

    @Override
    public void open(Configuration parameters) {
        // State descriptor with TTL
        ValueStateDescriptor<Long> descriptor =
            new ValueStateDescriptor<>("first-seen-timestamp", Long.class);

        // Auto-expire after 24 hours (matches max expected replay window)
        StateTtlConfig ttlConfig = StateTtlConfig.newBuilder(Time.hours(24))
            .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
            .setStateVisibility(
                StateTtlConfig.StateVisibility.NeverReturnExpired)
            .cleanupFullSnapshot()
            .cleanupInRocksdbCompactFilter(1000)
            .build();

        descriptor.enableTimeToLive(ttlConfig);
        firstSeenState = getRuntimeContext().getState(descriptor);
    }

    @Override
    public void processElement(PaymentEvent event, Context ctx,
        Collector<PaymentEvent> out) throws Exception {

        Long firstSeen = firstSeenState.value();

        if (firstSeen != null) {
            // Duplicate detected - route to side output for monitoring
            ctx.output(DUPLICATE_TAG, event);
            // Increment duplicate counter metric
            getRuntimeContext()
                .getMetricGroup()
                .counter("duplicates-filtered")
                .inc();
            return;
        }

        // First time seeing this event - record and emit
        firstSeenState.update(ctx.timerService().currentProcessingTime());
        out.collect(event);
    }
}

    .name("Deduplication Filter");

Common Mistakes

1. Assuming Checkpointing Alone Provides End-to-End Exactly-Once

The mistake: Engineers configure Flink with EXACTLY_ONCE checkpoint mode and assume the entire pipeline has exactly-once guarantees, ignoring the sink behavior.

The reality: Checkpointing guarantees exactly-once for internal state only. If the sink is not idempotent or transactional, replayed events after recovery will create duplicates in the external system.

Fix: Always pair checkpointing with either an idempotent sink (upserts) or a two-phase commit sink. Test by manually killing the job and verifying no duplicates appear in the sink after restart.

2. Using Non-Deterministic Logic in Processing

The mistake: Using System.currentTimeMillis(), UUID.randomUUID(), or calling external APIs with side effects in the processing function.

The reality: On replay, non-deterministic operations produce different results. A payment that was marked "processed at 14:05" will now be "processed at 14:20" (the replay time), causing inconsistencies or bypassing deduplication logic that relies on deterministic IDs.

Fix: Derive all output values deterministically from the input event. Use event timestamps instead of wall-clock time. Generate IDs using UUID.nameUUIDFromBytes() with event content as input.

3. Setting transaction.timeout.ms Too Low

The mistake: Using the default Kafka transaction timeout (60s) with a Flink checkpoint interval of 60s or higher.

The reality: If the checkpoint takes longer than the transaction timeout, Kafka aborts the transaction and all uncommitted messages are lost. This silently converts your exactly-once pipeline to at-most-once.

Fix: Set transaction.timeout.ms to at least 2x the checkpoint interval. Ensure the broker's transaction.max.timeout.ms is high enough to accommodate this value.

4. Ignoring the Deduplication Table Size

The mistake: Creating a dedup table that tracks all event IDs forever, leading to unbounded growth that degrades query performance and increases storage costs.

The reality: A dedup table processing 10K events/second will accumulate 864M rows per day. Without pruning, lookups become slow and the table becomes a bottleneck.

Fix: Partition the dedup table by time. Set TTL based on the maximum replay window (e.g., Kafka retention period + buffer). Use efficient indexes on (event_id, processed_at).

5. Not Testing Failure Recovery

The mistake: Developing and testing the happy path only. Never simulating failures to verify exactly-once behavior under crash-recovery scenarios.

The reality: Exactly-once bugs only manifest during failures. Your pipeline may work perfectly for months and then produce duplicates on the first checkpoint failure.

Fix: Build chaos testing into your CI/CD pipeline. Regularly kill Flink TaskManagers, pause Kafka brokers, and inject S3 latency. Verify output correctness after each simulated failure with automated duplicate detection queries.

6. Confusing Kafka Idempotent Producer with End-to-End Exactly-Once

The mistake: Setting enable.idempotence=true and believing the entire pipeline now has exactly-once guarantees.

The reality: Idempotent producer only deduplicates producer retries to Kafka. It does not provide exactly-once for the consume-process-produce cycle. You still need transactions for read-process-write atomicity.

Fix: Understand the scope: idempotent producer prevents duplicate writes to Kafka. Transactions provide atomic read + write + offset commit. End-to-end exactly-once requires both plus sink-side guarantees.

7. Using read_uncommitted Consumers Downstream

The mistake: Configuring transactional producers but forgetting to set isolation.level=read_committed on all downstream consumers.

The reality: The default isolation level is read_uncommitted. Consumers with this setting will read messages from aborted transactions, completely negating the exactly-once guarantee.

Fix: Set isolation.level=read_committed on every consumer that reads from topics written by transactional producers. Add integration tests that verify aborted transactions are not visible.

Complexity Higher (transactions, 2PC, checkpoint tuning, state backend management) Medium (idempotent sinks, dedup tables, but simpler failure recovery)
Operational Burden Higher (monitor checkpoints, manage savepoints, tune timeouts, handle in-doubt txns) Lower (fewer moving parts; dedup table is the main operational concern)

Cross-System Compatibility Limited (requires transactional support in all systems involved) Broad (works with any system that supports upserts or conditional writes)
Recovery Time Faster (restore from checkpoint = instant correct state) Slower (replay + dedup = reprocessing time proportional to replay window)

When Exactly-Once Is Worth the Cost

  • Financial transactions: Double-charging, duplicate payments, or incorrect balances have direct monetary impact and regulatory consequences.
  • Inventory management: Duplicate decrements cause phantom stock-outs; duplicate increments cause overselling.
  • User-facing notifications: Sending duplicate emails, SMS, or push notifications erodes user trust.
  • Compliance and audit trails: Regulatory requirements may mandate exactly-once processing for transaction recording.

When At-Least-Once + Dedup Is Sufficient

  • Analytics and metrics: Small counting errors from occasional duplicates are acceptable in dashboards and reports.
  • Event archival: Storing raw events where downstream consumers can deduplicate at query time (e.g., SELECT DISTINCT).
  • Heterogeneous sinks: When writing to systems that don't support transactions (S3, Elasticsearch, most NoSQL stores without conditional writes).
  • High-throughput, low-value events: IoT sensor data, clickstream, application logs where individual event loss or duplication is acceptable.

Follow-up Questions

Q: How would you handle exactly-once when writing to a system that doesn't support transactions or upserts?

Strong answer: Use an append-only write with a dedup layer. Write events with their event_id to the append-only store. Add a compaction or dedup process that runs periodically to remove duplicates. For S3, use a staging → commit pattern: write to a staging prefix, and on checkpoint completion, atomically rename/move to the final prefix. For systems like Elasticsearch, leverage document IDs (PUT with the same ID is idempotent).

Q: What happens if your Flink job needs to be redeployed with a code change that modifies the state schema?

Strong answer: Take a savepoint before stopping. For compatible schema changes (adding fields with defaults), Flink handles migration automatically with Avro or POJO serializers. For incompatible changes, use the State Processor API to read the old savepoint, transform state to the new schema, and write a new savepoint. Then start the new job version from the migrated savepoint. Always test schema evolution in a staging environment first.

Q: How do you guarantee exactly-once across multiple microservices communicating via Kafka?

Strong answer: Use the transactional outbox pattern: each service writes its output to a local outbox table in the same database transaction as its state change. A CDC connector (Debezium) tails the outbox and publishes to Kafka. Downstream services use idempotent consumers keyed on the event_id. This gives you per-service exactly-once without distributed transactions spanning multiple services. For the consuming side, each service maintains its own dedup state.

Q: How do you monitor whether your exactly-once guarantees are actually holding in production?

Strong answer: Multiple layers: (1) Track checkpoint success rate and duration in Flink metrics; alert on failures. (2) Monitor consumer lag to detect replay windows. (3) Add a "duplicate hit" counter in the idempotent sink that increments on ON CONFLICT matches. (4) Run periodic reconciliation queries comparing source event counts with sink row counts. (5) Inject synthetic events with known IDs and verify exactly one instance appears in the sink. (6) Monitor the dedup table hit rate—a sudden spike indicates unexpected replays.

Q: Can you achieve exactly-once with Apache Spark Structured Streaming? How does it differ from Flink?

Strong answer: Yes, through micro-batch processing. Spark achieves exactly-once by tracking committed offsets and batch IDs in the checkpoint directory. If a batch fails, it's re-executed from the same offsets. The key difference: Spark's micro-batch model processes data in discrete batches (not continuous), so latency is bounded by the trigger interval (typically seconds). Flink processes event-by-event with lower latency. For sinks, Spark relies on idempotent writes or the foreachBatch API with manual transaction management. Delta Lake's MERGE provides built-in dedup for Spark.

Q: How would you handle exactly-once processing with out-of-order events and late arrivals?

Strong answer: Separate concerns: (1) Use event-time processing with watermarks to handle ordering—events before the watermark are processed normally, late events trigger allowed-lateness logic. (2) For exactly-once, the dedup key should be the event_id regardless of arrival order. (3) For aggregations, use retraction/update streams: when a late event arrives and changes a window result, emit a retraction of the old result and the corrected value. (4) The sink must handle retractions (e.g., subtract old value, add new value) or use upserts that overwrite with the latest computation.

Q: What's the difference between Kafka's exactly-once and Flink's exactly-once?

Strong answer: Kafka's EOS is about atomic read-process-write within the Kafka ecosystem—it guarantees that consuming from topic A, processing, and producing to topic B happens atomically via transactions. It's limited to Kafka-to-Kafka pipelines. Flink's EOS is broader: it maintains consistent internal state via distributed snapshots and can coordinate with external systems through 2PC sinks. Flink can guarantee exactly-once to PostgreSQL, S3, or any system with an appropriate sink connector. Flink uses Kafka transactions as one possible sink mechanism but extends beyond Kafka.

Summary

Key Takeaways

  1. True exactly-once delivery is impossible in distributed systems. What we achieve is "effectively exactly-once" through at-least-once delivery combined with idempotent processing.
  2. End-to-end exactly-once requires three layers: a replayable source (Kafka), consistent checkpointing in the processing engine (Flink/Spark), and an idempotent or transactional sink.
  3. Kafka transactions provide atomic read-process-write within the Kafka ecosystem using transactional producers, read_committed consumers, and producer fencing via transactional.id.
  4. Flink checkpointing (Chandy-Lamport algorithm) creates consistent distributed snapshots that enable exactly-once for internal state. Pair with 2PC or idempotent sinks for external systems.
  5. Idempotent sinks are the most practical approach for most systems: database upserts, conditional writes, and deduplication tables handle replayed events without additional coordination overhead.
  6. Two-phase commit extends exactly-once to external systems that support distributed transactions, but adds latency and operational complexity.
  7. Deduplication patterns (event ID tracking, bloom filters, Redis, time-windowed dedup) provide defense-in-depth and work across heterogeneous systems.
  8. Trade-offs are significant: exactly-once costs 3-20% throughput, adds latency, and increases operational complexity. Choose it only when duplicate effects have real business impact (payments, inventory, compliance).
  9. Test failure recovery: exactly-once bugs only manifest during failures. Chaos testing and automated duplicate detection are essential for validating guarantees in production.
  10. Monitor continuously: track checkpoint health, consumer lag, dedup hit rates, and run periodic reconciliation to verify guarantees hold.

  3. Describe specific mechanisms — Kafka transactions, Flink checkpoints, idempotent upserts. Pick 1-2 and go deep.
  4. Discuss trade-offs — Latency vs correctness, complexity vs simplicity. Show you understand when NOT to use exactly-once.

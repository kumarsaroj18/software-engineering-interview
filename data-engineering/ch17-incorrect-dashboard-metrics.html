Your Dashboard Shows Incorrect Metrics After Deployment. How Do You Debug It?

Key Takeaway: Incorrect dashboard metrics after deployment usually stem from JOIN type changes, NULL handling bugs, schema evolution, duplicate events, or late-arriving data — investigate systematically with reconciliation queries and data contracts.

Interviewer Intent

When an interviewer asks "Your dashboard shows incorrect metrics after deployment—how do you debug it?", they are evaluating several critical competencies of a senior data engineer:

  • Systematic Debugging: Can you methodically isolate the problem across the entire data pipeline—from source ingestion, through transformation logic, to the final presentation layer—rather than guessing randomly?
  • Data Quality Awareness: Do you understand the common root causes of metric drift: schema changes, NULL propagation, duplicate events, late-arriving data, CDC issues, and JOIN logic errors?
  • Validation Patterns: Are you familiar with industry-standard data validation frameworks (Great Expectations, dbt tests, Monte Carlo) and can you design reconciliation checks that catch discrepancies before they reach dashboards?
  • Production Mindset: Have you dealt with real incidents where metrics were silently wrong for hours or days? Can you describe the detection, triage, root-cause analysis, and prevention measures you implemented?
  • Communication Under Pressure: Can you explain the impact of incorrect metrics to business stakeholders, provide accurate ETAs for resolution, and articulate what safeguards you will put in place to prevent recurrence?
  • Prevention Over Detection: Do you think about data contracts, schema registries, CI/CD validation gates, and automated reconciliation as preventive measures rather than relying solely on reactive alerting?
  • Trade-off Reasoning: Can you balance freshness vs accuracy, completeness vs latency, and strictness vs flexibility in your data quality framework?

A senior data engineer should demonstrate both the technical depth to diagnose complex data issues and the operational maturity to prevent them from recurring in production systems.

Quick Answer

When a dashboard shows incorrect metrics after deployment, I follow a structured debugging approach that moves from symptoms to root cause:

  1. Identify the scope: Which metrics are affected? Since when? Is it all data or specific segments (regions, date partitions, customer cohorts)?
  2. Compare before/after: Run the same query against pre-deployment and post-deployment code. Diff the results to quantify the discrepancy.
  3. Check the deployment diff: Review what changed—JOIN types, WHERE clauses, column references, aggregation logic, filter conditions, or model dependencies.
  4. Validate upstream data: Confirm source row counts, check for schema changes, verify CDC stream health, and look for duplicate or missing events.
  5. Reconcile layer by layer: Compare counts at source, staging, warehouse, and mart layers to pinpoint where data diverges.
  6. Root cause and fix: Common culprits include JOIN type changes (LEFT→INNER dropping rows), new NULLable columns breaking aggregations, duplicate events from at-least-once delivery, late-arriving data missing incremental windows, and schema evolution without backward compatibility.
  7. Prevent recurrence: Add data quality tests (dbt tests, Great Expectations), reconciliation checks, data contracts, and CI/CD validation gates.

The key insight is that incorrect dashboard metrics are almost always a data pipeline problem, not a visualization problem. The debugging workflow must trace data lineage from source to dashboard, comparing actual values against expected values at each layer.

Data Validation Patterns

Data validation is the first line of defense against incorrect metrics. A mature data platform implements validation at multiple layers—ingestion, transformation, and serving—to catch issues before they propagate to dashboards.

Great Expectations

Great Expectations is a Python-based data validation framework that defines expectations as declarative assertions about your data. It integrates with Airflow, Spark, and pandas:

  • Column-level expectations: expect_column_values_to_not_be_null, expect_column_values_to_be_between, expect_column_values_to_be_in_set
  • Table-level expectations: expect_table_row_count_to_be_between, expect_table_column_count_to_equal
  • Distribution expectations: expect_column_mean_to_be_between, expect_column_stdev_to_be_between for detecting statistical anomalies
  • Cross-table expectations: Custom expectations that compare row counts or aggregates between source and target tables

The power of Great Expectations lies in its ability to generate validation suites from profiling existing data, then alert when new data violates learned patterns. This catches both explicit bugs and subtle distribution shifts.

dbt Tests

dbt provides built-in and custom tests that run as part of the transformation pipeline. Tests execute as SQL queries that should return zero rows if the assertion passes:

  • Schema tests: unique, not_null, accepted_values, relationships (referential integrity)
  • Custom singular tests: SQL queries in the tests/ directory that validate business logic (e.g., revenue should never be negative)
  • dbt-utils tests: equal_rowcount, expression_is_true, recency (data freshness)
  • dbt-expectations: A package that brings Great Expectations-style tests to dbt, including distribution checks and outlier detection

The critical practice is running dbt test in CI/CD before merging model changes, and again in production after each dbt run. Failed tests should block downstream models from materializing stale or incorrect data.

Statistical Bounds

Beyond exact-match validation, statistical monitoring detects anomalies that rule-based tests miss. This is especially important for metrics that naturally fluctuate:

  • Z-score alerting: Flag metrics that deviate more than 3 standard deviations from their historical mean for the same day-of-week or hour-of-day
  • Moving average comparison: Compare today's value against a 7-day or 28-day rolling average. A sudden 30% deviation warrants investigation
  • Seasonal decomposition: Use STL decomposition to separate trend, seasonal, and residual components. Alert on residuals exceeding thresholds
  • Interquartile range (IQR): Define acceptable range as [Q1 - 1.5×IQR, Q3 + 1.5×IQR]. Values outside this range trigger validation failures

Row Count Checks

The simplest and most effective validation is comparing row counts across pipeline stages. A row count mismatch between source and target is the fastest signal that something went wrong:

  • Source vs staging: After ingestion, count rows in staging and compare against the source system's count for the same time window
  • Pre-transform vs post-transform: For 1:1 transformations (no aggregation), input and output row counts should match exactly
  • Day-over-day stability: If yesterday had 1M events and today has 300K, either traffic dropped legitimately or data is missing
  • Partition-level counts: Check each date partition individually. A single missing partition can cause metrics to drop without affecting overall counts significantly

Row count checks are cheap to implement, fast to execute, and catch a surprising number of issues including dropped partitions, failed CDC streams, and accidentally filtered data.

Reconciliation

Reconciliation is the practice of comparing data between two systems or pipeline stages to ensure consistency. In a multi-layer data platform, reconciliation acts as an end-to-end integrity check that catches issues no single-layer test can detect.

Source vs Target Row Counts

The most fundamental reconciliation compares total row counts between the operational source and the analytical target for a given time window:

  • Exact match: For append-only data (events, logs), the count in the warehouse should exactly match the count in the source for completed partitions
  • Bounded tolerance: For mutable data with CDC, allow a small tolerance (e.g., ±0.1%) to account for in-flight transactions during the snapshot
  • Segmented reconciliation: Break counts by date, region, or entity type. An overall match can mask offsetting errors (e.g., +1000 in region A, -1000 in region B)
  • Automated scheduling: Run reconciliation queries hourly or daily. Store results in a metadata table and alert on drift exceeding thresholds

Aggregate Comparisons

Beyond row counts, aggregate reconciliation compares computed metrics between source and target:

  • SUM validation: Compare SUM(revenue) in the source transactional database against the mart table. They should match within rounding tolerance
  • COUNT DISTINCT: Verify that the number of unique customers, orders, or sessions matches between systems
  • MIN/MAX bounds: The minimum and maximum values for key columns should be consistent. A MAX(order_date) in the warehouse that's older than the source indicates missing recent data
  • Group-by reconciliation: Compare aggregates by category. This catches issues where total sums match but individual segments are wrong due to misclassification

Hash-Based Validation

For row-level integrity without transferring all data, hash-based validation computes checksums on both sides and compares them:

  • Row-level hashing: Compute MD5 or SHA-256 of concatenated column values for each row. Compare hash sets between source and target to find mismatched rows
  • Partition-level hashing: Compute a deterministic hash for each partition (e.g., hash over a deterministic serialization of partition contents). If partition hashes match, all rows are identical. For large datasets, this avoids transferring or concatenating the full partition contents
  • Column-level checksums: Compute deterministic checksums or hashes per column and compare between systems. For example, hashing sorted column values or using order-independent aggregate functions (like XOR of hashes). This is fast and catches most data-level corruption without row-by-row comparison
  • Incremental reconciliation: Only hash rows modified since the last reconciliation run. This makes hash-based validation feasible for large tables

Hash-based validation is particularly valuable when migrating between systems (e.g., Oracle to BigQuery) or when validating that a refactored pipeline produces identical output.

Schema Evolution Issues

Schema evolution is one of the most insidious causes of incorrect metrics because changes propagate silently through the pipeline. A column rename, type change, or new nullable field can break downstream logic without causing any explicit errors.

New Nullable Column

When a source system adds a new nullable column, several failure modes emerge:

  • Aggregation breakage: If the new column is used in a SUM() or AVG() without COALESCE, NULL values silently produce NULL results instead of expected numbers
  • JOIN key corruption: If the new column becomes part of a composite JOIN key, NULL values cause rows to drop (NULL ≠ NULL in SQL)
  • Filter expansion: A WHERE clause like status != 'cancelled' excludes NULL status values. If the new schema makes status nullable, legitimate rows are silently filtered out
  • Type coercion: Some warehouses auto-cast NULL to 0 for numeric columns, while others preserve NULL. This inconsistency causes different results depending on the execution engine

Type Change

Column type changes can cause subtle data corruption that doesn't trigger schema validation errors but produces incorrect values:

  • Integer to float: Changing a DECIMAL(10,2) column to FLOAT introduces binary floating-point representation. While individual values appear correct, SUM() aggregations over millions of rows accumulate rounding errors that cause totals to drift from the precise decimal result — potentially by several dollars on large revenue datasets
  • String to timestamp: If the format specification doesn't match all source values, some rows get NULL timestamps and are excluded from time-based aggregations
  • Numeric precision loss: Changing DECIMAL(18,6) to DECIMAL(10,2) silently truncates values. Revenue of $1,234,567.891234 becomes $1,234,567.89
  • Boolean interpretation: Source changes from string ('true'/'false') to boolean (1/0). If downstream code still compares against string literals, all rows fail the filter

Field Rename

Field renames are particularly dangerous in loosely-typed systems like JSON/Avro where column references are string-based:

  • Silent NULL: In Spark/Presto, referencing a non-existent column in a JSON struct returns NULL rather than raising an error. A renamed field produces NULL values that propagate through all downstream calculations
  • Partial rename: The source renames user_id to customer_id but only in new records. Historical data retains the old name, causing schema-on-read failures or NULL for historical rows
  • Case sensitivity: A rename from userId to userid may or may not break depending on the warehouse's case sensitivity settings. Identifier case sensitivity varies across engines (e.g., Snowflake defaults to case-insensitive for unquoted identifiers but preserves case in quoted ones; BigQuery treats column names as case-insensitive). Schema changes involving only letter case should be tested carefully against each engine's specific behavior
  • Cascading breakage: A single field rename can break dozens of downstream models, views, and dashboards that reference it. Without column-level lineage tracking, identifying all affected assets requires manual investigation

Backward Compatibility

Maintaining backward compatibility during schema evolution requires deliberate practices:

  • Schema registry: Use Confluent Schema Registry or AWS Glue Schema Registry to enforce compatibility rules (BACKWARD, FORWARD, FULL) on schema changes
  • Additive-only changes: Only allow adding new columns (not removing or renaming). Deprecated columns are marked but retained for a transition period
  • Default values: New columns must have explicit defaults so that existing code continues to function correctly without modification
  • Version fields: Include a schema_version column so that transformation logic can branch based on the schema version of each record
  • Data contracts: Define explicit contracts between producers and consumers specifying column names, types, nullability, and valid value ranges. Changes require contract negotiation, not unilateral modification

Null Handling Bugs

NULL handling is arguably the most common source of incorrect metrics in analytical pipelines. SQL's three-valued logic (TRUE, FALSE, UNKNOWN) means that NULLs don't behave like zero or empty string—they propagate in ways that silently corrupt aggregations and filters.

NULL in Aggregations

SQL aggregate functions handle NULL in specific ways that can produce misleading results:

  • SUM ignores NULLs: SUM(revenue) skips NULL rows. If 20% of rows have NULL revenue due to a schema change, the total silently drops by 20% without any error
  • COUNT(*) vs COUNT(column): COUNT(*) counts all rows including those with NULLs, while COUNT(revenue) excludes NULLs. Using the wrong variant produces incorrect averages: SUM(revenue) / COUNT(*) is wrong if revenue has NULLs
  • AVG and NULL: AVG(revenue) divides by the count of non-NULL values. If NULLs represent zero-revenue transactions, AVG artificially inflates the result
  • MIN/MAX with NULLs: Both ignore NULLs, which is usually correct. But MAX(updated_at) returning a stale timestamp because recent rows have NULL timestamps is a common freshness-check failure
  • GROUP BY with NULL: NULL is treated as a single group. If a dimension column becomes nullable, a new "NULL" group appears that may not be handled by downstream logic or dashboard filters

COALESCE and IFNULL

Defensive NULL handling using COALESCE is essential but introduces its own pitfalls:

  • COALESCE(revenue, 0): Converts NULL to 0 for aggregation. This is correct when NULL means "no revenue" but wrong when NULL means "revenue unknown"—the distinction matters for accuracy
  • Multi-column COALESCE: COALESCE(new_col, old_col, 0) handles schema migrations gracefully by falling through column renames
  • IFNULL vs COALESCE: IFNULL takes exactly two arguments (MySQL/BigQuery). COALESCE is ANSI SQL and accepts multiple fallback values. Prefer COALESCE for portability
  • Performance impact: Wrapping every column in COALESCE can prevent predicate pushdown and partition pruning in some engines. Apply defensively but not indiscriminately
  • Type mismatch: COALESCE(varchar_col, 0) may fail or produce unexpected type coercion depending on the engine. Ensure fallback values match the column type

Outer JOIN Introducing NULLs

JOINs are the primary mechanism by which NULLs enter analytical queries unexpectedly:

  • LEFT JOIN + aggregation: A LEFT JOIN produces NULL values for all columns from the right table when no match exists. If you then SUM a right-table column without COALESCE, NULLs silently reduce the total
  • LEFT→INNER change: Converting a LEFT JOIN to INNER JOIN drops all unmatched rows entirely. This is the classic cause of "metrics dropped after deployment" when a developer "cleans up" a query
  • FULL OUTER JOIN NULLs: Both sides can be NULL. A FULL OUTER JOIN between orders and payments produces NULL order_ids for unmatched payments and NULL payment_ids for unmatched orders—both need explicit handling
  • Multi-table JOIN cascading: In a chain of LEFT JOINs (A LEFT JOIN B LEFT JOIN C), if B has no match, then C also has no match. NULLs cascade through the entire chain, potentially nullifying all derived columns
  • Anti-join pattern: WHERE right_table.id IS NULL after a LEFT JOIN identifies unmatched rows. If this pattern is accidentally removed during refactoring, the query returns all rows instead of just unmatched ones

Duplicate Events

Duplicate events are endemic in distributed systems because at-least-once delivery is the default guarantee for most message brokers and event streaming platforms. Without explicit deduplication, metrics inflate silently—revenue doubles, user counts spike, and conversion rates become meaningless.

At-Least-Once Producing Duplicates

Understanding where duplicates originate is essential for choosing the right dedup strategy:

  • Producer retries: When a Kafka producer doesn't receive an ACK (network timeout), it retries the send. If the original message was actually persisted, you now have duplicates in the topic. Enable idempotent producers (enable.idempotence=true) to prevent this at the broker level
  • Consumer reprocessing: A consumer crashes after processing a message but before committing the offset. On restart, it reprocesses the same messages. This is inherent to at-least-once semantics
  • CDC replay: Debezium connectors that restart from an earlier offset re-emit events that were already captured. The same INSERT appears twice in the target
  • Webhook retries: Third-party systems retry webhook deliveries on timeout. Your ingestion endpoint receives the same payment event multiple times
  • Airflow task retries: A failed Airflow task that partially wrote data retries and writes the same rows again. Without idempotent writes, duplicates accumulate

Deduplication Strategies

Different pipeline architectures call for different deduplication approaches:

  • Event-level dedup key: Every event should have a globally unique event_id (UUID or composite of entity_id + timestamp + sequence). Dedup by this key at ingestion or transformation time
  • Exactly-once sinks: Use MERGE/UPSERT operations that are inherently idempotent. Writing the same event twice with the same primary key overwrites rather than duplicates
  • Streaming dedup window: In Flink or Spark Structured Streaming, deduplicate within a time window using dropDuplicates("event_id") with a watermark. Events arriving outside the window are treated as new
  • Bloom filter pre-check: For high-volume streams where maintaining a full dedup set is expensive, use a Bloom filter to probabilistically detect duplicates with configurable false-positive rates
  • Database constraints: Add UNIQUE constraints on natural keys. Bulk inserts use INSERT ... ON CONFLICT DO NOTHING (Postgres) or MERGE (Snowflake/BigQuery) to silently drop duplicates

QUALIFY ROW_NUMBER Pattern

The most common SQL-based deduplication technique uses window functions to select one representative row from each group of duplicates:

  • Basic pattern: QUALIFY ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY ingested_at DESC) = 1 keeps the most recently ingested version of each event
  • Tie-breaking: When the ORDER BY column has ties, add secondary sort keys (e.g., ORDER BY ingested_at DESC, _file_name DESC) to ensure deterministic results
  • Soft-delete aware: For CDC data, order by the operation timestamp and keep the latest state: QUALIFY ROW_NUMBER() OVER (PARTITION BY pk ORDER BY op_timestamp DESC) = 1. Then filter out DELETE operations if needed
  • Performance consideration: QUALIFY with ROW_NUMBER requires sorting the entire partition. For very large tables, materializing deduplicated data incrementally (processing only new arrivals) is more efficient than full-table dedup on every run
  • Engine support: QUALIFY is natively supported in Snowflake, BigQuery, Redshift (since late 2023), and recent Databricks Runtime versions. In engines without QUALIFY (PostgreSQL), use a CTE with ROW_NUMBER and filter in the outer query: WITH ranked AS (...) SELECT * FROM ranked WHERE rn = 1

Late-Arriving Data

Late-arriving data occurs when events reach the pipeline after the processing window for their event_time has already closed. This is especially common in mobile applications (devices offline for hours), IoT sensors (buffered uploads), and cross-timezone batch exports. The result is incomplete metrics for past periods that were already reported to stakeholders.

Partition Already Closed

In partitioned data lakes, once a partition is written and downstream queries execute, late data for that partition creates inconsistency:

  • Immutable partitions: If partitions are treated as immutable after creation, late data is simply lost. The 2024-01-15 partition was finalized at midnight, but events from that day arrive at 3 AM—they have nowhere to go
  • Overwrite risk: Appending to a closed partition can cause double-counting if downstream models have already processed it. The mart table now has the old aggregate plus new rows arrive, but the aggregate isn't recomputed
  • Partition grace period: Keep partitions writable for a grace period (e.g., 72 hours). After the grace period, late data goes to a "late arrivals" staging table for manual or batch reprocessing
  • Bi-temporal modeling: Store both event_time (when it happened) and processing_time (when we received it). This allows reprocessing by processing_time windows while correctly attributing metrics to event_time

Incremental Model Missed It

Incremental models (dbt incremental, Spark append mode) only process new data since the last run. Late-arriving data that falls outside the incremental window is permanently excluded:

  • is_incremental() lookback: In dbt, use a lookback window larger than your expected late-arrival window: WHERE event_time >= (SELECT MAX(event_time) - INTERVAL '3 days' FROM {{ this }}). This reprocesses recent partitions to capture late data. Trade-off: a larger lookback improves completeness but increases processing cost because recent partitions are repeatedly recomputed on every run
  • Merge strategy: Use incremental_strategy='merge' with a unique key so that reprocessed rows update existing records rather than creating duplicates
  • Processing watermark: Track the maximum event_time processed by each model. When late data arrives with event_time below the watermark, trigger a targeted reprocessing of affected partitions
  • Freshness monitoring: Use dbt source freshness to detect when sources have data gaps. A source that usually updates every hour but hasn't updated in 6 hours likely indicates missing late data

Reprocessing Window

Designing a reprocessing strategy for late data requires balancing completeness against cost:

  • Rolling reprocess: Every day, reprocess the last N days of data. This automatically captures late arrivals within the window. Cost scales with N × daily_volume
  • Event-triggered reprocess: When late data arrives, identify affected partitions and trigger targeted reprocessing only for those partitions. More efficient but requires infrastructure to detect late arrivals
  • SLA-based cutoff: Define an SLA that says "metrics are preliminary for 72 hours and final after 7 days." Late data within 72 hours triggers reprocessing; after 7 days, it goes to a correction log but doesn't update dashboards
  • Lambda architecture: Maintain a speed layer (real-time, potentially incomplete) and a batch layer (complete but delayed). The serving layer merges both, with the batch layer eventually overwriting speed layer approximations

CDC Issues

Change Data Capture (CDC) pipelines introduce unique failure modes because they must faithfully replicate the sequence of mutations (INSERT, UPDATE, DELETE) from operational databases into analytical systems. Any disruption in ordering, completeness, or schema alignment produces incorrect point-in-time snapshots in the warehouse.

Debezium Lag

Debezium is the most widely used open-source CDC connector, but operational issues can cause it to fall behind the source database's transaction log:

  • WAL retention exhaustion: If Debezium falls too far behind and the database recycles WAL segments (PostgreSQL) or binlog files (MySQL), the connector cannot resume from its saved position. It must perform a full snapshot, which can take hours and produces duplicate data for the snapshot period
  • Large transactions: A bulk UPDATE affecting millions of rows generates a massive batch of CDC events. If the connector's memory is insufficient, it may OOM or produce backpressure that delays all subsequent events
  • Connector restart lag: After a restart, Debezium replays events from the last committed offset. The gap between "last committed" and "actually processed by downstream" produces duplicates that must be handled idempotently
  • Network partitions: Temporary connectivity loss between Debezium and the database causes gaps in the CDC stream. Events that occurred during the partition are lost unless the connector has WAL-based recovery

Schema Drift

When the source database schema changes (DDL), the CDC stream must handle the transition:

  • Column addition: New columns appear as NULL in historical events but have values in new events. Downstream consumers must handle both schemas simultaneously
  • Column removal: Debezium's schema history may still reference the dropped column. If the target table has a NOT NULL constraint on that column, inserts fail
  • Type change: A column changed from VARCHAR(50) to VARCHAR(200) in the source. If the target table wasn't updated, values are silently truncated
  • Schema registry conflicts: Avro-encoded CDC events with schema registry may fail compatibility checks when schemas evolve. This blocks the entire CDC pipeline until the compatibility rule is relaxed or the schema is manually registered

Out-of-Order CDC Events

CDC events can arrive out of order due to Kafka partition routing, connector parallelism, or network reordering:

  • Multi-partition topics: If CDC events for the same entity are spread across multiple Kafka partitions (e.g., hashed by table name rather than primary key), updates for the same row can be processed out of order
  • UPDATE before INSERT: If an UPDATE event for a row arrives before its INSERT event (due to reordering), an UPSERT-based sink handles this correctly, but an INSERT-only sink fails with a "row not found" error
  • Last-writer-wins resolution: Use the event's transaction timestamp (source.ts_ms in Debezium) to resolve conflicts. Only apply an event if its timestamp is newer than the current row's timestamp
  • Sequence numbers: Debezium provides source.lsn (Postgres) or source.file + source.pos (MySQL) that represent the monotonically increasing position in the transaction log. For MySQL, both fields are needed because the position resets with each new binlog file. Use these for ordering rather than wall-clock timestamps

Delete Handling

DELETE events in CDC require special handling because analytical systems often need historical data that the source system has removed:

  • Tombstone events: Debezium emits a DELETE event followed by a tombstone (null value) for log compaction. Consumers must distinguish between "record deleted" and "record never existed"
  • Soft delete in warehouse: Rather than physically deleting warehouse rows, set an is_deleted flag and deleted_at timestamp. This preserves historical analytics while reflecting the source's current state
  • Hard delete propagation: If the warehouse physically deletes rows, any downstream mart that has already aggregated the deleted row will show inflated historical metrics. Reprocessing is required
  • GDPR/compliance deletes: Legal requirements may mandate hard deletion from all systems within a time window. This requires tracking lineage to identify every table containing the affected data and triggering coordinated deletes

Backfill & Reprocessing

Backfills are necessary when historical data needs correction, a new model needs to be materialized for past periods, or a data loss event requires recovery. However, backfills are also one of the most dangerous operations because they can overwrite correct production data with incorrect data if not handled carefully.

Overwriting Production with Test Data

One of the most common backfill disasters occurs when test or development data accidentally overwrites production tables:

  • Wrong target database: A developer runs a backfill script pointed at the production database instead of dev. The script TRUNCATES the table and reloads with a subset of test data. Dashboards immediately show catastrophically wrong metrics
  • Shared infrastructure: When dev and prod share the same warehouse (different schemas/datasets), a misconfigured dbt profile or environment variable can route backfill writes to production
  • Prevention: Use separate service accounts with write access only to their designated environment. Implement database-level DENY rules that prevent dev credentials from writing to prod schemas
  • Recovery: Maintain time-travel capabilities (Snowflake Time Travel, BigQuery snapshot decorators, Delta Lake time travel) to restore tables to their pre-backfill state within the retention window

Missing Partition Guards

Backfills that don't properly scope their writes can corrupt data outside the intended range:

  • Full table overwrite: Using INSERT OVERWRITE without a partition filter replaces the entire table. If the backfill source only contains data for January, all other months are deleted
  • Static partition overwrite: In Spark, spark.sql.sources.partitionOverwriteMode=static (the default) replaces ALL partitions. Set to dynamic to only overwrite partitions present in the DataFrame
  • Date range guards: Always include explicit date range filters in backfill queries: WHERE dt BETWEEN '2024-01-01' AND '2024-01-31'. This prevents accidental processing of data outside the backfill window
  • Dry-run validation: Before executing a backfill, run it in dry-run mode that logs which partitions would be affected and how many rows would be written. Compare against expectations before committing

Idempotent Backfills

An idempotent backfill produces the same result regardless of how many times it runs. This property is essential for safe retry and recovery:

  • DELETE + INSERT pattern: First delete existing data for the target partition, then insert the new data. Running twice produces the same result. Wrap in a transaction for atomicity
  • MERGE/UPSERT pattern: Use MERGE with a match key to update existing rows and insert new ones. This handles partial backfills where some rows already exist
  • Partition-level atomicity: Write new partition data to a staging location, validate it, then atomically swap the partition pointer. If the backfill fails mid-way, the original partition remains intact
  • Backfill metadata: Record which partitions were backfilled, when, by whom, and from which source version. This audit trail enables debugging and rollback
  • Concurrency control: Prevent multiple backfills from running simultaneously on overlapping partitions. Use distributed locks (e.g., Airflow sensors, database advisory locks) to serialize conflicting operations

Production Incident: Revenue Dashboard 30% Drop

This section describes a real production incident that illustrates how a seemingly innocuous code change can cause significant metric discrepancies.

The Symptom

On Monday morning after a Friday deployment, the finance team reported that the revenue dashboard showed a 30% drop in daily revenue compared to the previous week. The business team was alarmed—had something catastrophic happened to sales over the weekend?

Initial Triage

  • Scope identification: The revenue drop was consistent across all days since Friday's deployment. Pre-deployment days showed normal values. This immediately pointed to the deployment as the cause
  • Source verification: Checked the transactional database directly: SELECT SUM(amount) FROM orders WHERE order_date = '2024-01-20' returned the expected ~$3.2M. The warehouse mart table showed only ~$2.2M for the same date
  • Layer-by-layer comparison: Raw staging table had correct row counts. The intermediate model int_orders_enriched showed 30% fewer rows than staging. The problem was in the enrichment layer

Root Cause

The deployment included a refactoring of the int_orders_enriched dbt model. A developer changed a LEFT JOIN to an INNER JOIN while "cleaning up" the query, reasoning that "all orders should have a matching customer record": 

-- BEFORE (correct)
SELECT
  o.order_id,
  o.amount,
  o.order_date,
  c.customer_segment
FROM staging.orders o
LEFT JOIN staging.customers c
  ON o.customer_id = c.customer_id

-- AFTER (incorrect)
SELECT
  o.order_id,
  o.amount,
  o.order_date,
  c.customer_segment
FROM staging.orders o
INNER JOIN staging.customers c
  ON o.customer_id = c.customer_id

The assumption that "all orders have a matching customer" was wrong. Approximately 30% of orders came from guest checkouts (no customer record), B2B API integrations (customer records in a different system), and recently created customers whose records hadn't yet been replicated via CDC. The INNER JOIN silently dropped all these orders.

Why It Wasn't Caught

  • No row count test: There was no dbt test comparing the output row count of int_orders_enriched against its source staging.orders
  • CI ran on subset: The CI environment used a small sample dataset where all orders happened to have matching customers. The 30% mismatch only existed in production
  • No metric monitoring: There was no automated alert on revenue deviation exceeding a threshold. The issue was discovered manually 60 hours after deployment
  • Code review gap: The reviewer approved the LEFT→INNER change because the PR description said "all orders should have customers" without verifying this assumption against production data

Resolution

  1. Immediate fix: Reverted the JOIN type back to LEFT JOIN and re-ran the dbt model to restore correct metrics within 30 minutes of diagnosis
  2. Data correction: Triggered a full refresh of all downstream mart tables that depended on int_orders_enriched to ensure no stale aggregations remained
  3. Stakeholder communication: Notified finance team that the revenue drop was a data pipeline bug, not an actual business decline. Provided corrected figures for the affected days

Prevention Measures Implemented

  • Row count test: Added dbt_utils.equal_rowcount test comparing int_orders_enriched against staging.orders to catch any future row drops. (This is valid because the enrichment is a 1:1 transformation that should preserve every source row; for aggregation or filtering models, use bounded-count tests instead)
  • Revenue bounds test: Added a singular test that asserts daily revenue is within 30% of the 7-day rolling average. Deviations trigger pipeline failure and alert
  • CI with production data sample: Modified CI to test against a representative production sample (10% random sample) that includes edge cases like guest checkouts
  • JOIN audit policy: Established a team policy that any change from LEFT to INNER JOIN requires an accompanying query proving that the JOIN produces zero unmatched rows in production
  • Automated metric monitoring: Deployed a daily reconciliation job that compares warehouse revenue against the source transactional database and alerts within 1 hour if deviation exceeds 1%

Lessons Learned

  • Assumptions are dangerous: Never change JOIN semantics based on assumptions about data completeness. Verify with production queries first. The developer should have run this query before changing the JOIN: 
    -- Verification query: how many orders have no matching customer?
SELECT COUNT(*) AS unmatched_orders
FROM staging.orders o
LEFT JOIN staging.customers c
  ON o.customer_id = c.customer_id
WHERE c.customer_id IS NULL;
    This would have shown ~30% of orders had no match, immediately invalidating the assumption
  • Silent failures are worst: The query didn't error—it produced fewer rows silently. Data quality tests must validate not just correctness of present data but completeness of expected data
  • CI must reflect production: Test datasets must include the edge cases and data quality issues present in production. Pristine test data gives false confidence
  • 60 hours is too long: Critical business metrics should have automated anomaly detection that catches discrepancies within hours, not days

Debugging Workflow

When a dashboard shows incorrect metrics after deployment, follow this systematic workflow to minimize time-to-resolution and avoid chasing false leads:

Step 1: Define the Discrepancy

  • Quantify the error: "Revenue is 30% lower" is actionable; "something looks wrong" is not
  • Identify the time boundary: When did correct metrics end and incorrect ones begin?
  • Determine the scope: All metrics or specific ones? All segments or specific regions/products?
  • Check if the dashboard itself changed (filter defaults, date ranges, cached data)

Step 2: Correlate with Deployments

  • List all deployments in the window between "last known good" and "first known bad"
  • Include not just code deployments but infrastructure changes, schema migrations, and config updates
  • Check dbt run logs for model changes, Airflow DAG modifications, and upstream source changes
  • Verify that no one ran a manual backfill or ad-hoc data fix during the window

Step 3: Layer-by-Layer Reconciliation

  • Source layer: Query the operational database directly. Does it show the expected values for the affected time period?
  • Ingestion layer: Check raw/staging tables. Do row counts match the source? Are there gaps in event timestamps?
  • Transformation layer: Compare intermediate model outputs against their inputs. Where do row counts diverge? Which transformation introduces the error?
  • Serving layer: Check the final mart/reporting table. Does its content match what the dashboard displays? Rule out caching or dashboard-level issues

Step 4: Isolate the Root Cause

  • Once you know which layer diverges, examine the transformation logic for that layer
  • Run the transformation manually with debug logging to see exactly which rows are included/excluded
  • Compare the current code against the previous version (git diff) focusing on JOINs, WHEREs, and GROUP BYs
  • Check for data issues: NULLs in JOIN keys, duplicates, schema changes in source data

Step 5: Validate the Fix

  • Write a query that demonstrates the bug: show the missing/extra/incorrect rows
  • Apply the fix and verify that the same query now shows correct results
  • Run the full pipeline and compare output metrics against the source of truth
  • Add a regression test that would have caught this issue before it reached production

Step 6: Communicate and Prevent

  • Notify affected stakeholders with: what happened, impact window, corrected data availability
  • Write a post-mortem documenting: timeline, root cause, impact, resolution, and prevention
  • Implement automated checks that would catch this class of issue in the future
  • Update runbooks with the debugging steps that proved effective

    SUM(amount) AS total_revenue

  SELECT
    order_date,
    total_revenue,
    AVG(total_revenue) OVER (
      ORDER BY order_date
      ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING

Reconciliation SQL

Production-grade reconciliation queries that compare source and warehouse data:

Row Count Reconciliation

-- Reconciliation: Source vs Warehouse row counts by date
WITH source_counts AS (
  SELECT
    DATE(created_at) AS dt,
    COUNT(*) AS source_rows,
    SUM(amount) AS source_revenue,
    COUNT(DISTINCT customer_id) AS source_customers
  FROM source_db.orders
  WHERE created_at >= CURRENT_DATE - INTERVAL '7 days'
  GROUP BY DATE(created_at)
),

warehouse_counts AS (
  SELECT
    order_date AS dt,
    COUNT(*) AS warehouse_rows,
    SUM(amount) AS warehouse_revenue,
    COUNT(DISTINCT customer_id) AS warehouse_customers
  FROM analytics.fct_orders
  WHERE order_date >= CURRENT_DATE - INTERVAL '7 days'
  GROUP BY order_date
)

SELECT
  COALESCE(s.dt, w.dt) AS dt,
  s.source_rows,
  w.warehouse_rows,
  s.source_rows - COALESCE(w.warehouse_rows, 0) AS row_diff,
  ROUND(
    100.0 * (s.source_rows - COALESCE(w.warehouse_rows, 0)) / NULLIF(s.source_rows, 0),
    2
  ) AS row_diff_pct,
  s.source_revenue,
  w.warehouse_revenue,
  ROUND(s.source_revenue - COALESCE(w.warehouse_revenue, 0), 2) AS revenue_diff,
  ROUND(
    100.0 * (s.source_revenue - COALESCE(w.warehouse_revenue, 0)) / NULLIF(s.source_revenue, 0),
    2
  ) AS revenue_diff_pct
FROM source_counts s
FULL OUTER JOIN warehouse_counts w ON s.dt = w.dt
ORDER BY dt DESC;

Duplicate Detection Query

-- Find duplicate events by event_id
WITH duplicates AS (
  SELECT
    event_id,
    COUNT(*) AS occurrence_count,
    MIN(ingested_at) AS first_seen,
    MAX(ingested_at) AS last_seen,
    TIMESTAMPDIFF(MINUTE, MIN(ingested_at), MAX(ingested_at)) AS duplicate_window_minutes
  FROM raw.events
  WHERE event_date >= CURRENT_DATE - INTERVAL '1 day'
  GROUP BY event_id
  HAVING COUNT(*) > 1
)

SELECT
  COUNT(*) AS total_duplicate_groups,
  SUM(occurrence_count - 1) AS total_extra_rows,
  AVG(occurrence_count) AS avg_duplicates_per_event,
  MAX(occurrence_count) AS max_duplicates,
  AVG(duplicate_window_minutes) AS avg_duplicate_window_min
FROM duplicates;

-- Detect schema changes between consecutive loads
WITH current_schema AS (
  SELECT
    column_name,
    data_type,
    is_nullable,
    ordinal_position
  FROM information_schema.columns
  WHERE table_schema = 'staging'
    AND table_name = 'orders'
),

expected_schema AS (
  SELECT
    column_name,
    data_type,
    is_nullable,
    ordinal_position
  FROM data_contracts.expected_schemas
  WHERE table_name = 'staging.orders'
    AND contract_version = (
      SELECT MAX(contract_version)
      FROM data_contracts.expected_schemas
      WHERE table_name = 'staging.orders'
    )
)

-- Columns in actual but not in contract (additions)
SELECT 'ADDED' AS change_type, c.column_name, c.data_type, NULL AS expected_type
FROM current_schema c
LEFT JOIN expected_schema e ON c.column_name = e.column_name
WHERE e.column_name IS NULL

UNION ALL

-- Columns in contract but not in actual (removals)
SELECT 'REMOVED' AS change_type, e.column_name, NULL AS actual_type, e.data_type
FROM expected_schema e
LEFT JOIN current_schema c ON e.column_name = c.column_name
WHERE c.column_name IS NULL

UNION ALL

-- Type mismatches
SELECT 'TYPE_CHANGED' AS change_type, c.column_name, c.data_type, e.data_type
FROM current_schema c
JOIN expected_schema e ON c.column_name = e.column_name
WHERE c.data_type != e.data_type;

Common Mistakes

These are the mistakes senior data engineers frequently see (or make) when debugging and preventing incorrect dashboard metrics:

Debugging Mistakes

  • Blaming the dashboard first: Engineers spend hours investigating Looker/Tableau caching, filter configurations, and visualization bugs when the issue is almost always in the data pipeline. Start at the source and work forward
  • Not quantifying the discrepancy: "The numbers look wrong" is not actionable. Always compute the exact delta: "Revenue is $1.02M lower than expected, representing 30% of orders from the guest checkout segment"
  • Checking only totals: Overall row counts or sums can appear correct while hiding offsetting errors. A segment gaining 10K rows while another loses 10K shows correct totals but incorrect segments. Always reconcile at granular levels
  • Assuming the source is correct: Sometimes the source system itself has bugs—duplicate events, retroactive updates, or timezone issues. Validate the source against business expectations, not just against itself
  • Fixing without understanding: Applying a quick fix (e.g., "just add COALESCE") without understanding why NULLs appeared. The underlying cause (schema change, CDC failure, missing data) will produce different symptoms next time

Prevention Mistakes

  • Testing only happy path: dbt tests that validate column types and uniqueness but don't check row counts, metric bounds, or cross-table consistency. The most dangerous bugs produce valid-looking data with wrong values
  • Static thresholds: Setting alert thresholds like "revenue must exceed $2M" fails during weekends, holidays, or seasonal dips. Use relative thresholds (deviation from rolling average) that adapt to natural patterns
  • Alert fatigue: Too many low-priority alerts cause teams to ignore all alerts. Tier your data quality checks: P0 (blocks pipeline), P1 (alerts on-call), P2 (logged for weekly review)
  • No data contracts: Allowing upstream producers to change schemas without notifying consumers. A single column rename can break dozens of downstream models silently
  • Incremental-only with no lookback: Incremental models that process only new data without a lookback window permanently miss late-arriving events. Always include at least a 24-72 hour lookback
  • Testing in isolation: Running dbt tests that validate each model independently but never testing end-to-end metric accuracy against the source of truth

Operational Mistakes

  • No deployment rollback plan: Deploying model changes without the ability to quickly revert. If a dbt model change breaks metrics, you need to restore the previous version within minutes, not hours
  • Manual backfills without safeguards: Running ad-hoc INSERT/UPDATE statements in production without partition guards, row count validation, or rollback capability
  • Shared credentials between environments: Dev and production using the same database credentials allows accidental cross-environment writes. Use separate service accounts with environment-specific permissions
  • No post-deployment validation: Deploying model changes and assuming success if the dbt run completes without errors. Always run reconciliation checks after deployment to verify output correctness

Trade-offs

Data quality engineering involves fundamental trade-offs. Understanding these helps you make informed decisions appropriate to your organization's priorities:

Freshness vs Accuracy

  • Real-time with approximation: Streaming dashboards can show metrics within seconds but may include duplicates, miss late data, or show pre-dedup counts. Suitable for operational monitoring where directional accuracy is sufficient
  • Batch with completeness: Daily batch processing allows full deduplication, late-arrival handling, and reconciliation but introduces 24+ hour latency. Suitable for financial reporting where accuracy is non-negotiable
  • Hybrid approach: Show real-time preliminary metrics with a "provisional" badge, then replace with reconciled batch metrics after a delay. This gives both speed and eventual accuracy

Strictness vs Flexibility

  • Strict validation (fail fast): Any data quality violation halts the pipeline. This prevents bad data from reaching dashboards but causes cascading downstream failures and stale data. Appropriate for financial/regulatory data
  • Lenient validation (warn and continue): Log violations and alert but continue processing. Bad data reaches dashboards but the pipeline stays running. Appropriate for exploratory analytics and non-critical metrics
  • Tiered strictness: Critical columns (revenue, customer_id) have strict validation. Non-critical columns (utm_source, device_type) have lenient validation. This balances reliability with availability

Testing Depth vs Pipeline Speed

  • Comprehensive testing: Running 200+ dbt tests after every model refresh adds 15-30 minutes to pipeline execution but catches subtle issues. Appropriate for daily batch runs with generous SLA windows
  • Minimal testing: Running only critical tests (uniqueness, not-null on primary keys) keeps pipeline fast but misses data drift and metric anomalies. Appropriate for hourly micro-batch runs with tight SLAs
  • Async testing: Run the pipeline and serve data immediately, then run comprehensive tests asynchronously. If tests fail, roll back to the previous version. This gives both speed and coverage but adds complexity

Deduplication: Exact vs Probabilistic

  • Exact dedup (hash/key-based): Guarantees no duplicates but requires maintaining state (seen event IDs) that grows with data volume. Memory-intensive for high-cardinality streams
  • Probabilistic dedup (Bloom filter): Bounded memory with configurable false-positive rate. May incorrectly mark unique events as duplicates (data loss) but never lets true duplicates through. Suitable for metrics where 0.1% loss is acceptable
  • Windowed dedup: Only dedup within a time window (e.g., 1 hour). Events with the same ID arriving days apart are treated as separate. Trades completeness for bounded resource usage

Schema Enforcement: Strict vs Schema-on-Read

  • Schema-on-write (strict): Reject data that doesn't conform to the registered schema. Prevents data quality issues at ingestion but may drop valid events during schema transitions
  • Schema-on-read (flexible): Accept all data into raw storage, apply schema during transformation. More resilient to source changes but pushes validation downstream where it's harder to debug
  • Schema evolution with compatibility: Accept schema changes that maintain backward/forward compatibility. Reject breaking changes. This balances flexibility with safety

Reconciliation Frequency vs Cost

  • Real-time reconciliation: Compare every micro-batch against source within minutes. Catches issues fast but doubles query load on source systems and increases warehouse compute costs
  • Daily reconciliation: Run comprehensive reconciliation once per day during off-peak hours. Low cost but issues may persist for up to 24 hours before detection
  • Event-driven reconciliation: Trigger reconciliation only after deployments, backfills, or schema changes. Targeted and cost-effective but misses issues caused by gradual data drift

Follow-up Questions

After the initial discussion, interviewers often probe deeper with these follow-up questions. Prepare structured answers for each:

Detection and Alerting

  • "How would you detect incorrect metrics before stakeholders notice?" Implement automated reconciliation that runs after every pipeline execution, comparing key metrics against source systems. Set up anomaly detection using statistical bounds (z-score, rolling average deviation) that alert the on-call engineer within an hour of detecting drift. Additionally, use dbt test failures to block downstream model refreshes.
  • "What's your alerting strategy for data quality?" Tier alerts by severity: P0 alerts page on-call for >5% deviation in revenue metrics, P1 alerts Slack for schema changes or row count anomalies, P2 creates tickets for gradual drift or minor completeness issues. Avoid alert fatigue by suppressing during known maintenance windows and deduplicating related alerts.
  • "How do you handle false positive alerts?" Maintain a suppression list for known patterns (holiday dips, end-of-quarter spikes). Use day-of-week and seasonality-aware thresholds. When a false positive occurs, tune the threshold and document the pattern. Track alert precision monthly—if precision drops below 70%, the alerting is too aggressive.

Architecture and Prevention

  • "How would you design a data quality framework from scratch?" Layer the framework: (1) Schema validation at ingestion using schema registry, (2) Freshness and completeness checks via dbt source freshness, (3) Business logic tests in dbt models, (4) Cross-system reconciliation in a dedicated quality DAG, (5) Statistical anomaly detection on served metrics. Each layer catches different failure modes.
  • "How do data contracts prevent this class of issue?" Data contracts formalize the interface between producers and consumers. The producer commits to schema stability, freshness SLAs, and value constraints. Breaking changes require a contract version bump and consumer acknowledgment. This prevents the "surprise schema change" that causes silent metric corruption.
  • "How do you validate data quality in CI/CD before deployment?" Run dbt models against a production-representative sample in CI. Execute all tests including row count comparisons, metric bounds, and JOIN completeness checks. Compare output metrics of the PR branch against main branch. Flag any metric deviating by more than 1% for manual review before merge.

Incident Response

  • "The CEO is asking about the revenue drop in 30 minutes. What do you do?" First, confirm whether the drop is a data issue or a real business event by querying the source system directly. If it's a data issue, communicate immediately: "We've identified a data pipeline issue affecting revenue reporting since [date]. Actual revenue is unaffected. We expect corrected numbers within [ETA]." Provide the source-of-truth number from the operational database as an interim figure.
  • "How do you handle a situation where you can't quickly determine if the metric change is real or a bug?" Run reconciliation between source and warehouse. If they match, the change is real—escalate to the business team. If they don't match, it's a pipeline issue—investigate the transformation layer. While investigating, communicate uncertainty explicitly: "We're validating whether this represents actual business change or a data issue. ETA for confirmation: [time]."
  • "How do you prevent the same incident from recurring?" Implement the specific test that would have caught this issue (e.g., row count comparison for JOIN changes). Add it to CI so it runs on every PR. Conduct a blameless post-mortem documenting timeline, root cause, and prevention. Update the team's code review checklist to include JOIN-type change verification.

Scale and Complexity

  • "How do you handle data quality at scale with 1000+ models?" Prioritize by business impact: identify the 50 critical models that drive executive dashboards and apply comprehensive testing. Use automated profiling (Great Expectations auto-profiling, Monte Carlo) for the long tail. Implement column-level lineage to propagate quality scores downstream and identify which models are affected by upstream issues.
  • "How do you debug incorrect metrics in a complex DAG with 20+ dependencies?" Use binary search on the DAG: run reconciliation at the midpoint. If correct there, the issue is downstream; if incorrect, it's upstream. Repeat until you find the exact model where data diverges. Column-level lineage tools (dbt Explorer, DataHub) help identify which specific transformation introduced the error.
  • "What's your approach when multiple issues compound?" Isolate each issue independently. For example, if you find both duplicates AND missing rows, fix duplicates first (dedup), then assess whether the remaining count matches expectations. Log each issue separately in the post-mortem because they may have different root causes and different prevention measures.

Summary

Debugging incorrect dashboard metrics after deployment requires a systematic, layer-by-layer approach that traces data from source to visualization. The key principles are:

Core Debugging Framework

  • Quantify first: Define the exact discrepancy (metric, magnitude, time window, affected segments) before investigating
  • Correlate with changes: Identify all deployments, schema changes, and infrastructure modifications in the affected time window
  • Reconcile layer by layer: Compare source → staging → transformation → mart → dashboard to pinpoint where data diverges
  • Verify assumptions: Never trust assumptions about data completeness (e.g., "all orders have customers"). Validate with production queries

Common Root Causes

  • JOIN type changes: LEFT→INNER silently drops unmatched rows
  • NULL propagation: New nullable columns corrupt aggregations
  • Duplicate events: At-least-once delivery inflates metrics
  • Late-arriving data: Incremental models miss events outside their window
  • Schema evolution: Field renames, type changes, and new columns break logic
  • CDC failures: Lag, reordering, and missed deletes produce stale snapshots
  • Backfill accidents: Overwriting production data or missing partition guards

Prevention Stack

  • Data validation: dbt tests, Great Expectations suites, and statistical anomaly detection at every pipeline layer
  • Reconciliation: Automated source-vs-warehouse comparison for row counts, aggregates, and hash-based integrity
  • Data contracts: Formal agreements between producers and consumers that prevent unilateral breaking changes
  • CI/CD validation: Run tests against production-representative data in CI before merging model changes
  • Monitoring and alerting: Tiered alerts with statistical thresholds that detect anomalies within hours, not days

Key Takeaways for the Interview

  • Lead with structure: show the interviewer you have a repeatable debugging methodology
  • Demonstrate breadth: mention multiple root causes and explain how to differentiate them
  • Show production experience: reference real incidents and lessons learned
  • Emphasize prevention: great engineers build systems that detect issues automatically
  • Communicate trade-offs: explain when you'd choose speed over accuracy or vice versa

Snowflake Internals

Explain how Snowflake works internally.

Snowflake Micro-partitions

Interviewer Intent

When an interviewer asks you to "explain how Snowflake works internally," they are probing for:

  • Architectural fluency — Can you articulate the three-layer shared-data architecture and explain why decoupling storage from compute was a paradigm shift from MPP systems like Redshift or Teradata?
  • Storage internals — Do you understand micro-partitions, columnar format, immutable files, and how zone maps enable partition pruning without explicit partitioning?
  • Compute model — Can you explain virtual warehouses, multi-cluster scaling, credit consumption, and why "T-shirt sizing" matters for cost optimization?
  • Query optimization — Do you know the three-layer caching hierarchy (result cache → metadata cache → warehouse local SSD cache) and how the query optimizer leverages partition pruning?
  • Operational maturity — Have you dealt with real production issues like runaway auto-scaling costs, suboptimal clustering keys, or time-travel storage bloat?
  • Cost awareness — Can you quantify credit consumption, storage costs, and the financial implications of design decisions like warehouse sizing and clustering?

This question separates candidates who merely write SQL on Snowflake from those who understand the system deeply enough to architect cost-effective, high-performance data platforms at scale.

Quick Answer (60-Second Version)

Snowflake is a cloud-native data warehouse built on a shared-data architecture with three independent layers: (1) a storage layer that persists all data as immutable, compressed, columnar micro-partitions on cloud object storage (S3/GCS/Azure Blob); (2) a compute layer of ephemeral virtual warehouses — independent MPP clusters that read from storage, cache data locally on SSD, and scale elastically without affecting each other; and (3) a cloud services layer that handles metadata management, query optimization, transaction coordination, access control, and result caching. This separation means you can scale compute independently of storage, run multiple independent workloads with strong isolation by using separate virtual warehouses, and pay only for active compute time while storage costs stay minimal. Micro-partitions (approximately 50–500 MB of uncompressed data each) are automatically organized with zone maps that enable aggressive pruning, eliminating the need for manual partitioning or index creation.

Shared-Data Architecture

Why Shared-Data?

Traditional MPP databases (Teradata, Greenplum, Redshift) use a shared-nothing architecture where each node owns a slice of the data. This creates tight coupling between storage and compute — scaling requires redistribution, and mixed workloads (ETL + analytics) compete for the same resources.

Snowflake chose a shared-data model: all compute nodes read from a single, shared storage layer. This decoupling enables:

  • Independent scaling of storage and compute
  • Workload isolation — ETL warehouses don't affect BI query warehouses
  • Significantly less administration than traditional MPP systems — no vacuuming, no index management, no data redistribution — although warehouse sizing, clustering, and cost management still require operational tuning
  • Instant elasticity — spin up warehouses in seconds, auto-suspend when idle

Shared-Nothing vs. Shared-Data Comparison

Aspect Shared-Nothing (Redshift) Shared-Data (Snowflake)
Storage-Compute coupling Tightly coupled to nodes Fully decoupled
Scaling Resize cluster (data redistribution) Add/remove warehouses instantly
Concurrency Shared queue, WLM slots Independent warehouses, unlimited
Data distribution Manual DISTKEY/SORTKEY Automatic micro-partitioning
Maintenance VACUUM, ANALYZE, key tuning Near-zero (auto clustering optional)
Cost model Per-node-hour (always on) Per-second compute + cheap storage

Data Flow: Write Path

  1. Client submits DML (INSERT, COPY, MERGE) to the cloud services layer.
  2. Cloud services parses, optimizes, and routes the query to the assigned virtual warehouse.
  3. The warehouse executes the operation, producing new micro-partitions.
  4. New micro-partitions are written as immutable files to object storage.
  5. Cloud services updates the metadata catalog (zone maps, partition references, table version).
  6. Old micro-partitions (if any were replaced) are marked for time-travel retention, then eventual deletion.

Data Flow: Read Path

  1. Client submits a query to the cloud services layer.
  2. Cloud services checks the result cache — if an identical query was run within 24h and data hasn't changed, return cached result instantly (no warehouse needed).
  3. If no cache hit, the optimizer generates an execution plan with partition pruning based on zone maps.
  4. The plan is distributed to warehouse nodes; each node checks its local SSD cache for required micro-partitions.
  5. Cache misses trigger reads from object storage (remote I/O).
  6. Results are aggregated and returned to the client.

Storage Layer

Cloud Object Storage as Foundation

Snowflake stores all table data, metadata files, and temporary/intermediate results on the cloud provider's native object storage:

  • AWS — Amazon S3
  • Azure — Azure Blob Storage
  • GCP — Google Cloud Storage

This design choice provides virtually unlimited storage capacity, 11 nines of durability, and extremely low cost (~$23/TB/month on S3 Standard). The trade-off is higher latency compared to local disk — which Snowflake mitigates through aggressive caching and columnar pruning.

Micro-partitions: The Fundamental Unit

Every table in Snowflake is horizontally divided into micro-partitions — contiguous units of storage containing approximately 50 to 500 MB of uncompressed data. Key properties:

  • Immutable — Once written, a micro-partition is never modified. DML operations create new micro-partitions and mark old ones for deletion.
  • Columnar — Data within each micro-partition is stored in a column-major format, enabling efficient projection pushdown.
  • Independently compressed — Each column segment uses encoding and compression techniques automatically selected by Snowflake based on data type and distribution (the specific algorithms are abstracted from users).
  • Self-describing — Each file contains a header with schema information, zone maps, and metadata pointers.
  • Automatically created — No user intervention required; Snowflake chooses partition boundaries based on ingestion order.

Columnar Format Internals

Within each micro-partition, data is organized in a columnar layout. The internal format is proprietary (not Parquet or ORC), but conceptually each file contains:

┌────────────────────────────────────────────────────┐
│              MICRO-PARTITION FILE                    │
├────────────────────────────────────────────────────┤
│  File Header (schema, version, encryption info)     │
├────────────────────────────────────────────────────┤
│  Column 1 Data   [compressed segment]              │
│  Column 1 Nulls  [bitmap]                          │
├────────────────────────────────────────────────────┤
│  Column 2 Data   [compressed segment]              │
│  Column 2 Nulls  [bitmap]                          │
├────────────────────────────────────────────────────┤
│  ...                                               │
├────────────────────────────────────────────────────┤
│  Column N Data   [compressed segment]              │
│  Column N Nulls  [bitmap]                          │
├────────────────────────────────────────────────────┤
│  Zone Map / Min-Max Statistics                      │
│  (per column: min, max, distinct count, null count) │
├────────────────────────────────────────────────────┤
│  File Footer (offsets, checksums)                   │
└────────────────────────────────────────────────────┘

Compression Strategies

Snowflake automatically selects compression per column segment based on data characteristics:

Data Pattern Compression Used Typical Ratio
Low cardinality (status codes, enums) Dictionary encoding 10–50x
Sequential integers (IDs, timestamps) Delta encoding + bit-packing 8–20x
Repeated values (run-length patterns) Run-Length Encoding (RLE) 20–100x
General text / mixed data LZ4 or ZSTD 3–5x
Floating point columns Byte-shuffle + ZSTD 2–4x

Immutability and Copy-on-Write

The immutability model is central to Snowflake's ACID guarantees, time-travel, and zero-maintenance design:

-- When you run an UPDATE:
UPDATE orders SET status = 'shipped' WHERE order_id = 12345;

-- Snowflake does NOT modify any existing micro-partition.
-- Instead:
-- 1. Identifies the micro-partition(s) containing the affected rows
-- 2. Creates NEW micro-partition(s) with the updated data
-- 3. Atomically updates the metadata pointer to reference the new partitions
-- 4. Old partitions remain accessible for Time Travel (up to 90 days)
-- 5. After Time Travel + 7-day Fail-Safe, old partitions are purged

Storage Cost Implications

Understanding the storage model is critical for cost control:

  • Active storage: ~$23/TB/month (S3 Standard) or $40/TB/month (Snowflake on-demand pricing)
  • Time Travel storage: Retains old micro-partitions; cost = delta between versions × retention days
  • Fail-Safe storage: Additional 7 days beyond Time Travel (non-configurable for permanent tables)
  • Frequent small updates: Generate many new micro-partitions and retain old ones → storage amplification
-- Check storage breakdown
SELECT table_name,
       active_bytes / POWER(1024, 3) AS active_gb,
       time_travel_bytes / POWER(1024, 3) AS time_travel_gb,
       failsafe_bytes / POWER(1024, 3) AS failsafe_gb,
       (active_bytes + time_travel_bytes + failsafe_bytes) / POWER(1024, 3) AS total_gb
FROM snowflake.account_usage.table_storage_metrics
WHERE table_catalog = 'MY_DB'
ORDER BY total_gb DESC
LIMIT 20;

Compute Layer

Virtual Warehouses

A virtual warehouse is an independent MPP compute cluster provisioned on demand. It consists of cloud virtual machines managed by Snowflake on the underlying cloud platform, with local SSD for caching, networked together for distributed query execution. Key concepts:

  • T-shirt sizes: XS, S, M, L, XL, 2XL, 3XL, 4XL — each size allocates progressively more compute resources (CPU, memory, parallelism)
  • Linear credit scaling: Each size approximately doubles the available compute capacity and credits/hour (XS=1, S=2, M=4, ... 4XL=128 credits/hour)
  • No shared state: Each warehouse operates independently — no cross-warehouse contention
  • Per-second billing: Minimum 60-second charge, then per-second after that

Warehouse Sizing Guidelines

Workload Recommended Size Rationale
Simple BI queries (few GB scanned) XS – S Low data volume, latency not critical
Complex analytics (100+ GB scanned) M – L More nodes = more parallel I/O and compute
Large ETL (COPY/MERGE, TB-scale) L – XL Throughput-bound; larger cluster finishes faster, may cost the same total credits
Data science (ML training SQL) M – XL Depends on data volume; Snowpark may benefit from larger clusters
High-concurrency dashboard serving S – M with multi-cluster Scale-out via clusters rather than scale-up

Multi-Cluster Warehouses

Multi-cluster warehouses provide horizontal scaling for concurrent workloads. Rather than a single cluster queuing queries, Snowflake can spawn additional clusters on demand:

-- Create a multi-cluster warehouse
CREATE WAREHOUSE bi_warehouse
  WAREHOUSE_SIZE = 'MEDIUM'
  MIN_CLUSTER_COUNT = 1
  MAX_CLUSTER_COUNT = 4
  SCALING_POLICY = 'STANDARD'   -- or 'ECONOMY'
  AUTO_SUSPEND = 300
  AUTO_RESUME = TRUE;

-- STANDARD policy: new cluster added when a query is queued
-- ECONOMY policy: new cluster added only when enough queries
--                 are queued to keep it busy for 6+ minutes

Auto-Scale and Auto-Suspend

Snowflake's elasticity is governed by two mechanisms:

  • Auto-suspend: Warehouse suspends (stops billing) after N seconds of inactivity (configurable, minimum 60s). Resuming a suspended warehouse may reuse previously cached data if the underlying infrastructure is still available, but cache persistence across suspend/resume cycles is not guaranteed.
  • Auto-resume: When a query arrives at a suspended warehouse, it resumes automatically in ~1-2 seconds (provisioning happens ahead of time for active accounts).
-- Optimal configuration for different workloads
-- ETL warehouse: quick suspend since jobs are bursty
ALTER WAREHOUSE etl_wh SET
  AUTO_SUSPEND = 60
  AUTO_RESUME = TRUE;

-- BI warehouse: longer suspend preserves cache for repeat queries
ALTER WAREHOUSE bi_wh SET
  AUTO_SUSPEND = 600
  AUTO_RESUME = TRUE;

-- Dev warehouse: aggressive suspend to control costs
ALTER WAREHOUSE dev_wh SET
  AUTO_SUSPEND = 60
  AUTO_RESUME = TRUE
  WAREHOUSE_SIZE = 'XSMALL';

Credit Consumption Model

Understanding credits is essential for cost optimization:

-- Check credit usage by warehouse over the past 7 days
SELECT warehouse_name,
       SUM(credits_used) AS total_credits,
       SUM(credits_used) * 3.00 AS estimated_cost_usd,  -- ~$2-4/credit depending on edition
       COUNT(DISTINCT DATE_TRUNC('hour', start_time)) AS active_hours
FROM snowflake.account_usage.warehouse_metering_history
WHERE start_time >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY warehouse_name
ORDER BY total_credits DESC;

-- Identify idle warehouses that should be suspended sooner
SELECT warehouse_name,
       AVG(DATEDIFF('second', end_time, 
           LEAD(start_time) OVER (PARTITION BY warehouse_name ORDER BY start_time)))
         AS avg_gap_seconds,
       COUNT(*) AS query_count
FROM snowflake.account_usage.query_history
WHERE start_time >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY warehouse_name
HAVING avg_gap_seconds > 300;

Local SSD Cache (Warehouse Cache)

Each node in a virtual warehouse has local NVMe SSD storage used as a read-through cache for micro-partitions fetched from object storage. Properties:

  • LRU eviction policy when cache fills
  • Partitions are distributed across nodes to balance work and maximize cache locality
  • Survives query boundaries (persists as long as the warehouse is active)
  • Not guaranteed to persist across suspend/resume cycles
  • Typical hit ratio for BI workloads with good temporal locality: high (varies by workload)
-- Monitor cache effectiveness via Query Profile
-- Look for: "Percentage Scanned from Cache" in the TableScan operator
-- Values close to 100% indicate warm cache; close to 0% means cold reads

-- You can also check at the account level:
SELECT warehouse_name,
       AVG(bytes_scanned) AS avg_bytes_scanned,
       AVG(bytes_spilled_to_local_storage) AS avg_local_spill,
       AVG(bytes_spilled_to_remote_storage) AS avg_remote_spill
FROM snowflake.account_usage.query_history
WHERE start_time >= DATEADD('day', -1, CURRENT_TIMESTAMP())
  AND warehouse_name IS NOT NULL
GROUP BY warehouse_name;

Cloud Services Layer

The Brain of Snowflake

The cloud services layer is a shared, always-on set of services that coordinates everything outside of raw query execution. It runs on Snowflake-managed infrastructure and is included in compute pricing (with an overage charge if it exceeds 10% of daily warehouse compute).

Core Components

  • Metadata Store — A distributed transactional metadata service that tracks:
    • Table-to-micro-partition mappings
    • Zone maps (min/max/NDV/null count per column per partition)
    • Table versions for time-travel
    • Schema definitions and object hierarchy
    • Access control policies (RBAC, column masking, row access)
  • Query Optimizer — A cost-based optimizer (CBO) that:
    • Performs partition pruning using zone maps (most impactful optimization)
    • Determines join strategies (hash join, merge join, broadcast vs. redistribute)
    • Injects projection pushdown and filter pushdown
    • Uses metadata and execution statistics to optimize distributed query execution
    • Does NOT require explicit statistics collection (unlike PostgreSQL's ANALYZE)
  • Transaction Manager — Provides ACID semantics:
    • Snapshot Isolation (SI) as the default and only isolation level
    • Multi-statement transactions with BEGIN/COMMIT/ROLLBACK
    • Conflict detection on overlapping DML to the same micro-partitions
    • Atomicity through metadata-level pointer swaps (no in-place updates)
  • Access Control Engine — Evaluates permissions at query planning time:
    • Role-Based Access Control (RBAC) with role hierarchy
    • Dynamic Data Masking (column-level)
    • Row Access Policies (row-level security)
    • Object Tagging and governance metadata
  • Result Cache — Stores query results for 24 hours:
    • Key = query text + database/schema context + role + parameters
    • Invalidated when underlying data changes
    • Served without consuming warehouse credits
    • Particularly effective for dashboard queries with stable data

Cloud Services Billing

Cloud services compute is free up to 10% of your daily warehouse credit usage. If cloud services exceed this threshold (common with heavy metadata operations, DDL storms, or frequent SHOW/DESCRIBE commands), the overage is billed at the same credit rate.

-- Monitor cloud services credits
SELECT DATE_TRUNC('day', start_time) AS day,
       SUM(credits_used_cloud_services) AS cs_credits,
       SUM(credits_used_compute) AS compute_credits,
       ROUND(cs_credits / NULLIF(compute_credits, 0) * 100, 2) AS cs_pct
FROM snowflake.account_usage.warehouse_metering_history
WHERE start_time >= DATEADD('day', -30, CURRENT_TIMESTAMP())
GROUP BY day
ORDER BY day DESC;

-- If cs_pct consistently > 10%, investigate:
-- - Excessive INFORMATION_SCHEMA queries
-- - Large numbers of small queries (each needs planning)
-- - Frequent DDL operations
-- - External functions with high invocation counts

Some queries can be answered entirely or partially from metadata without scanning micro-partition data — these are extremely efficient:

Micro-partition Deep Dive

Physical Characteristics

Micro-partitions are Snowflake's proprietary file format (not Parquet or ORC). Their design targets the sweet spot between granularity and I/O efficiency:

Property Value Rationale
Uncompressed data size ~50–500 MB Large enough for efficient object storage I/O; small enough for fine-grained pruning
Uncompressed row count ~50,000–500,000 rows Depends on row width and data types
Column storage Independent segments Only referenced columns are read (projection pushdown)
Encryption AES-256, per-file key End-to-end encryption; keys managed by Snowflake + optional customer-managed keys
Mutability Immutable (write-once) Enables time-travel, zero-copy cloning, safe concurrent access

Automatic Partitioning

Unlike Hive (partition by column), BigQuery (partition by date), or Redshift (DISTKEY + SORTKEY), Snowflake requires no explicit partitioning declaration. As data is loaded, Snowflake automatically groups rows into micro-partitions based on insertion order:

-- Loading data: micro-partitions are created automatically
COPY INTO events
FROM @my_stage/events/
FILE_FORMAT = (TYPE = 'PARQUET')
MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;

-- Result: Snowflake creates N micro-partitions where:
-- N ≈ (total uncompressed bytes) / (target partition size ~16MB uncompressed per column)
-- Each partition contains rows in the order they appeared in the source files

Zone Maps (Min/Max Metadata)

Every micro-partition stores metadata about each column's value range within that partition. This metadata is called the zone map (or partition-level statistics):

Micro-partition #4827:
┌─────────────────────────────────────────────────────────────┐
│ Column          │ Min        │ Max        │ NDV  │ Nulls    │
├─────────────────┼────────────┼────────────┼──────┼──────────┤
│ order_date      │ 2024-01-15 │ 2024-01-15 │ 1    │ 0        │
│ customer_id     │ 1001       │ 9999       │ 4200 │ 0        │
│ order_amount    │ 5.99       │ 24999.00   │ 3800 │ 12       │
│ status          │ 'cancelled'│ 'shipped'  │ 4    │ 0        │
│ region          │ 'APAC'     │ 'APAC'     │ 1    │ 0        │
└─────────────────────────────────────────────────────────────┘

Key observations:

  • order_date: min=max → all rows in this partition are from 2024-01-15. A query filtering on a different date can skip this entire partition.
  • region: min=max='APAC' → perfect clustering for region-based queries.
  • customer_id: wide range → poor clustering for customer-based queries; many partitions will overlap.

How Zone Maps Enable Pruning

-- This query benefits from zone map pruning:
SELECT * FROM orders
WHERE order_date = '2024-03-15'
  AND region = 'EMEA';

-- Snowflake's optimizer evaluates zone maps:
-- Partition #4827: order_date range [2024-01-15, 2024-01-15] → SKIP (no overlap)
-- Partition #4828: order_date range [2024-03-15, 2024-03-15], region = 'NA' → SKIP
-- Partition #4829: order_date range [2024-03-15, 2024-03-16], region = 'EMEA' → SCAN
-- Result: only partitions with overlapping ranges are read

Partition Overlap and Natural Clustering

The effectiveness of pruning depends on how well a column's values are clustered within partitions (minimal overlap between partitions):

GOOD clustering (date column with sequential loads):
Partition 1: [2024-01-01, 2024-01-01]   ← no overlap
Partition 2: [2024-01-02, 2024-01-02]
Partition 3: [2024-01-03, 2024-01-03]
→ Query for one date scans exactly one partition (perfect pruning)

BAD clustering (customer_id with random distribution):
Partition 1: [1001, 9998]   ← massive overlap
Partition 2: [1005, 9999]
Partition 3: [1002, 9997]
→ Query for customer_id = 5000 must scan ALL partitions (no pruning)

Measuring Partition Efficiency

-- Check how many partitions a query needs to scan
-- After running a query, check the Query Profile for:
-- "Partitions scanned" vs "Partitions total"

-- Example output from Query Profile:
-- TableScan[ORDERS]
--   Partitions total: 12,450
--   Partitions scanned: 45    ← excellent pruning (0.36%)
--   Bytes scanned: 1.2 GB     ← from local cache ideally

-- Programmatic check:
SELECT query_id,
       partitions_scanned,
       partitions_total,
       ROUND(partitions_scanned / partitions_total * 100, 2) AS scan_pct,
       bytes_scanned / POWER(1024, 3) AS gb_scanned
FROM snowflake.account_usage.query_history
WHERE query_text ILIKE '%orders%'
  AND start_time >= DATEADD('hour', -1, CURRENT_TIMESTAMP())
ORDER BY start_time DESC;

Pruning & Clustering

Natural Clustering

When data is loaded in chronological order (the most common pattern), date/timestamp columns are naturally clustered — each micro-partition contains a narrow range of dates. This provides excellent pruning for time-range queries out of the box, with zero configuration.

Natural clustering degrades when:

  • Data is loaded from many sources in arbitrary order
  • Frequent DML (INSERT/UPDATE/DELETE) fragments the logical ordering
  • Joins or transformations shuffle row order during ETL
  • Late-arriving data gets appended to new partitions instead of its logical time range

CLUSTER BY: Explicit Clustering Keys

When natural clustering is insufficient for your dominant query patterns, you can define a clustering key. This instructs Snowflake's automatic reclustering service to reorganize micro-partitions in the background:

-- Define a clustering key on a table
ALTER TABLE events CLUSTER BY (event_date, region);

-- Multi-column keys: order matters (leftmost column is primary sort dimension)
-- Similar concept to a composite index, but applies to partition organization

-- Expressions are supported:
ALTER TABLE events CLUSTER BY (DATE_TRUNC('day', event_timestamp), region);

-- Remove clustering key (stop reclustering):
ALTER TABLE events DROP CLUSTERING KEY;

How Reclustering Works

Reclustering is an automatic, background maintenance process:

  1. Snowflake identifies micro-partitions with overlapping ranges for the clustering key columns.
  2. It reads those partitions, sorts the data by the clustering key, and writes new, better-organized partitions.
  3. Old partitions are retained for time-travel, then purged after the retention window.
  4. This process is incremental — Snowflake doesn't reorganize the entire table at once.
  5. You are charged serverless compute credits for the reclustering work.

Reclustering Cost Considerations

-- Monitor reclustering credits consumed
SELECT table_name,
       SUM(credits_used) AS recluster_credits,
       SUM(num_bytes_reclustered) / POWER(1024, 3) AS gb_reclustered,
       SUM(num_rows_reclustered) / 1e6 AS million_rows_reclustered
FROM snowflake.account_usage.automatic_clustering_history
WHERE start_time >= DATEADD('day', -30, CURRENT_TIMESTAMP())
GROUP BY table_name
ORDER BY recluster_credits DESC;

-- Cost rule of thumb:
-- High-churn tables with clustering keys can incur significant ongoing costs
-- A table receiving 100GB/day of new data with a clustering key might spend
-- 5-20 credits/day on reclustering depending on how "unsorted" new data is

SYSTEM$CLUSTERING_INFORMATION

This system function returns clustering quality metrics for a table:

-- Check clustering depth and overlap
SELECT SYSTEM$CLUSTERING_INFORMATION('events', '(event_date, region)');

-- Returns JSON like:
-- {
--   "cluster_by_keys": "LINEAR(event_date, region)",
--   "total_partition_count": 12450,
--   "total_constant_partition_count": 8200,  ← partitions where all rows share same key value
--   "average_overlaps": 2.3,                 ← lower is better (1.0 = perfect)
--   "average_depth": 1.8,                    ← lower is better (1.0 = perfect)
--   "partition_depth_histogram": {
--     "00000": 0,
--     "00001": 8200,   ← 8200 partitions at depth 1 (no overlap)
--     "00002": 3100,   ← 3100 partitions at depth 2
--     "00003": 1000,
--     "00004": 150,
--     "00016+": 0      ← 0 highly overlapping partitions (good!)
--   }
-- }

-- Interpretation:
-- average_depth close to 1 → excellent clustering, minimal scanning
-- average_depth > 5 → poor clustering, consider CLUSTER BY
-- total_constant_partition_count / total_partition_count → ratio of perfectly sorted partitions

Choosing Clustering Keys

Guidelines for selecting effective clustering keys:

Guideline Rationale
Use columns from dominant WHERE clauses Pruning only helps if queries filter on clustered columns
Prefer medium cardinality (100–100K distinct values) Too low = no pruning benefit; too high = too many overlapping partitions
Put the most selective column first Leftmost column determines the primary sort dimension
Use DATE_TRUNC for timestamps Reduces cardinality from billions of microseconds to thousands of days
Limit to 3–4 columns maximum More columns = harder to maintain good clustering across all dimensions
Avoid clustering small tables (<1 TB) Cost of reclustering may exceed scan savings for small tables

Pruning in Action: Before and After Clustering

-- Before clustering (no CLUSTER BY defined):
-- Query: SELECT * FROM events WHERE event_date = '2024-06-15' AND region = 'EU'
-- Query Profile shows:
--   Partitions total: 50,000
--   Partitions scanned: 12,000   ← scanning 24% of table
--   Execution time: 45 seconds

-- After clustering on (event_date, region):
ALTER TABLE events CLUSTER BY (event_date, region);
-- Wait for automatic reclustering to complete (hours to days for large tables)

-- Same query:
--   Partitions total: 50,000
--   Partitions scanned: 48       ← scanning 0.096% of table (250x improvement)
--   Execution time: 2 seconds

Time Travel & Fail-Safe

Time Travel Overview

Snowflake's Time Travel enables accessing historical data at any point within a configurable retention window. This is possible because micro-partitions are immutable — old versions are retained rather than overwritten.

Edition Max Retention Default
Standard 1 day 1 day
Enterprise 90 days 1 day
Business Critical 90 days 1 day 
-- Set retention at table level
ALTER TABLE orders SET DATA_RETENTION_TIME_IN_DAYS = 30;

-- Set retention at schema/database level (applies to new tables)
ALTER SCHEMA analytics SET DATA_RETENTION_TIME_IN_DAYS = 14;

-- Transient tables: max 1 day retention, no Fail-Safe
CREATE TRANSIENT TABLE staging_events (...) DATA_RETENTION_TIME_IN_DAYS = 0;

-- Temporary tables: session-scoped, no Fail-Safe, max 1 day retention
CREATE TEMPORARY TABLE session_results (...);

Querying Historical Data

-- AT: query at a specific point in time
SELECT * FROM orders AT(TIMESTAMP => '2024-06-01 10:00:00'::TIMESTAMP_LTZ);

-- AT with offset (seconds ago)
SELECT * FROM orders AT(OFFSET => -3600);  -- 1 hour ago

-- AT with statement ID (before a specific query ran)
SELECT * FROM orders AT(STATEMENT => '01b2c3d4-0001-abcd-0000-00000000abcd');

-- BEFORE: query just before a specific point
SELECT * FROM orders BEFORE(TIMESTAMP => '2024-06-01 10:00:00'::TIMESTAMP_LTZ);
SELECT * FROM orders BEFORE(STATEMENT => '01b2c3d4-0001-abcd-0000-00000000abcd');

-- Practical use: recover from accidental UPDATE
-- Step 1: identify what changed
SELECT * FROM orders AT(OFFSET => -300)  -- 5 minutes ago
EXCEPT
SELECT * FROM orders;

-- Step 2: restore the old data
INSERT INTO orders
SELECT * FROM orders AT(OFFSET => -300)
WHERE order_id NOT IN (SELECT order_id FROM orders);

UNDROP: Object Recovery

-- Recover a dropped table
DROP TABLE orders;
-- Oops! Recover it:
UNDROP TABLE orders;

-- Recover a dropped schema
DROP SCHEMA analytics;
UNDROP SCHEMA analytics;

-- Recover a dropped database
DROP DATABASE production;
UNDROP DATABASE production;

-- Caveat: UNDROP only works within the Time Travel retention window
-- After retention expires, objects move to Fail-Safe (not user-accessible)

Fail-Safe

After the Time Travel retention window expires, Snowflake retains data for an additional 7 days in Fail-Safe. This is a disaster-recovery mechanism with critical differences from Time Travel:

  • Not user-accessible — Only Snowflake support can recover data from Fail-Safe
  • Not free — You pay storage costs for Fail-Safe data
  • Non-configurable — Always 7 days for permanent tables; 0 days for transient/temporary tables
  • Last resort — Used for catastrophic data loss scenarios only

Storage Cost of Time Travel

-- Time Travel storage = sum of all changed micro-partitions retained
-- Example: 
--   Table has 1000 partitions (100 GB active)
--   Daily UPDATE touches 200 partitions → new 200 partitions created
--   With 30-day retention: storing up to 30 × 200 = 6000 old partitions
--   Potential Time Travel storage: ~600 GB (6x the active data!)

-- Monitor Time Travel and Fail-Safe costs:
SELECT table_name,
       ROUND(active_bytes / POWER(1024, 3), 2) AS active_gb,
       ROUND(time_travel_bytes / POWER(1024, 3), 2) AS tt_gb,
       ROUND(failsafe_bytes / POWER(1024, 3), 2) AS fs_gb,
       ROUND((time_travel_bytes + failsafe_bytes) / NULLIF(active_bytes, 0), 2) 
         AS overhead_ratio
FROM snowflake.account_usage.table_storage_metrics
WHERE active_bytes > 0
ORDER BY (time_travel_bytes + failsafe_bytes) DESC
LIMIT 20;

-- Strategy to control Time Travel costs:
-- 1. Use TRANSIENT tables for staging/temporary data (no Fail-Safe, max 1-day TT)
-- 2. Reduce retention for high-churn tables with frequent DML
-- 3. Prefer batch INSERT over many small UPDATEs (fewer partition rewrites)
-- 4. Use TEMPORARY tables for session-scoped work

Query Processing

Three-Layer Caching Hierarchy

Snowflake employs a multi-tier caching strategy that dramatically reduces both latency and cost:

┌─────────────────────────────────────────────────────────────┐
│  Layer 1: RESULT CACHE (Cloud Services Layer)               │
│  • Stores complete query results for 24 hours               │
│  • Served without warehouse credits                         │
│  • Invalidated when underlying data changes                 │
│  • Key: query text + context (db, schema, role, params)     │
│  • Hit rate for dashboard queries: varies by workload         │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: METADATA CACHE (Cloud Services Layer)             │
│  • Stores zone maps, table statistics, partition metadata   │
│  • Enables pruning decisions without reading data           │
│  • Answers COUNT(*), MIN(), MAX() from metadata alone       │
│  • Always available, no additional cost                     │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: WAREHOUSE CACHE (Local SSD on Compute Nodes)      │
│  • Caches micro-partition data read from object storage     │
│  • LRU eviction; partitions distributed for cache locality   │
│  • Lost on suspend/resize; persists across queries          │
│  • Reduces object storage reads significantly for warm tables  │
├─────────────────────────────────────────────────────────────┤
│  Layer 4: REMOTE I/O (Object Storage — S3/GCS/Azure)        │
│  • Cold reads from cloud object storage                     │
│  • Highest latency in the cache hierarchy                   │
│  • Throughput scales with warehouse size (more nodes)        │
└─────────────────────────────────────────────────────────────┘

Query Execution Flow

  1. Parse & Plan — Cloud services parses SQL, resolves objects, checks permissions, runs the cost-based optimizer.
  2. Result Cache Check — If the exact query (same text, context, and parameters) was run within 24h and data hasn't changed, return the cached result immediately. No warehouse needed.
  3. Partition Pruning — The optimizer evaluates zone maps against predicates to identify which micro-partitions to scan. This step can reduce I/O by orders of magnitude.
  4. Distribute to Warehouse — The execution plan is sent to the warehouse; partitions are assigned to nodes to balance work and maximize cache locality.
  5. Local Cache Check — Each node checks if its assigned partitions are already in SSD cache. Cache hits avoid network I/O to object storage.
  6. Remote Fetch — For cache misses, nodes fetch micro-partition files from object storage in parallel. Larger warehouses have more nodes and thus more aggregate bandwidth.
  7. Execution — Vectorized processing on columnar data with SIMD optimizations. Intermediate results spill to local SSD if memory is exhausted, then to object storage as a last resort.
  8. Aggregation & Return — Results flow from worker nodes to a coordinator node, then back to the client via cloud services.

Spilling: The Performance Killer

When a warehouse node's memory is insufficient for an operation (large hash join, sort, or aggregation), data "spills" to disk:

  • Spill to local storage — Data overflows to local SSD. Moderate performance impact (SSD is fast but slower than memory).
  • Spill to remote storage — Local SSD is also full; data spills to object storage. Severe performance impact — can slow queries by 10–100x.
-- Identify queries that spill
SELECT query_id,
       query_text,
       warehouse_size,
       bytes_spilled_to_local_storage / POWER(1024, 3) AS local_spill_gb,
       bytes_spilled_to_remote_storage / POWER(1024, 3) AS remote_spill_gb,
       total_elapsed_time / 1000 AS elapsed_sec
FROM snowflake.account_usage.query_history
WHERE bytes_spilled_to_remote_storage > 0
  AND start_time >= DATEADD('day', -7, CURRENT_TIMESTAMP())
ORDER BY bytes_spilled_to_remote_storage DESC
LIMIT 20;

-- Fix for spilling:
-- 1. Increase warehouse size (more memory per node + more nodes)
-- 2. Rewrite query to reduce intermediate result sizes (filter earlier)
-- 3. Break large joins into smaller steps
-- 4. Use CLUSTER BY to improve join locality

-- Result cache is used when ALL of these are true:
-- 1. Exact same query text (including whitespace and comments!)
-- 2. Same database, schema, and role context
-- 3. No underlying data changes since last execution
-- 4. No non-deterministic functions (CURRENT_TIMESTAMP, RANDOM, etc.)

Vectorized Execution Engine

Snowflake processes data in vectors (batches of column values) rather than row-by-row:

  • Batch sizes optimized for CPU cache lines and SIMD instruction widths
  • Columnar processing enables CPU-efficient operations (SIMD instructions allow multiple values to be processed in parallel within a single CPU instruction)
  • Late materialization — only construct full rows at the very end, after all filtering is applied
  • Pipeline-breaking operators (sort, hash join build) materialize intermediate results; other operators stream through the pipeline

Real Production Incident: Auto-Scaling Cost Spike

Scenario

A fintech company running their data platform on Snowflake experienced a 4x cost spike during their nightly ETL window. The monthly bill jumped from $45K to $180K before the issue was identified and resolved.

Architecture Context

  • Multi-cluster warehouse for BI dashboards: size M, min_clusters=1, max_clusters=6, STANDARD scaling policy
  • Nightly ETL (Airflow-orchestrated) ran on a separate XL warehouse
  • BI dashboards used by a global team across US, EU, and APAC time zones
  • 30+ Looker dashboards with auto-refresh every 5 minutes

What Happened

Timeline:
02:00 UTC — Nightly ETL starts on etl_wh (XL). Normal.
02:05 UTC — ETL begins MERGE operations on core fact tables.
02:05 UTC — MERGE invalidates result cache for all dashboards using those tables.
02:06 UTC — Dashboard auto-refreshes hit bi_wh. Previously cached results are gone.
02:06 UTC — 30 dashboards × 5 queries each = 150 queries suddenly need full execution.
02:07 UTC — STANDARD scaling policy detects queuing. Scales from 1 → 2 clusters.
02:08 UTC — Queries still queuing (cold cache + full table scans). Scales to 3.
02:10 UTC — Scales to 4 clusters. All running cold (no SSD cache populated yet).
02:10–04:00 — 4 clusters running continuously. Each query does full remote I/O.
              Dashboard refreshes every 5 min keep clusters alive.
04:00 UTC — ETL completes. But clusters remain at 4 because dashboards keep querying.
06:00 UTC — US business hours begin. Even more dashboard queries. Stays at max clusters.
08:00 UTC — Pattern repeats nightly for 2 weeks before detection.

Daily cost:
Before: 1 cluster × 4 credits/hr × ~10 active hrs = 40 credits ($120/day)
After:  4 clusters × 4 credits/hr × 18 active hrs = 288 credits ($864/day)

Root Cause Analysis

  1. Result cache invalidation storm — ETL MERGE operations changed the underlying data, invalidating all cached dashboard results simultaneously.
  2. STANDARD scaling policy too aggressive — The policy adds clusters the moment any query queues, without considering whether the spike is transient.
  3. Cold cache amplification — New clusters have empty SSD caches. Every query needs full remote I/O from object storage, running significantly slower than cache-warm execution. This keeps the cluster busy longer, preventing scale-down.
  4. Dashboard refresh interval too short — 5-minute refresh on 30 dashboards created a sustained query load that prevented auto-suspend.

Resolution

-- 1. Switch to ECONOMY scaling policy (waits for sustained queuing)
ALTER WAREHOUSE bi_wh SET
  SCALING_POLICY = 'ECONOMY'
  MAX_CLUSTER_COUNT = 3;  -- Reduced from 6

-- 2. Stagger ETL to avoid mass cache invalidation
-- In Airflow: split MERGE operations into 6 batches with 10-min gaps
-- This means only ~5 dashboards lose cache at a time

-- 3. Add resource monitors with alerts
CREATE RESOURCE MONITOR bi_cost_monitor
  WITH CREDIT_QUOTA = 100  -- per day
  TRIGGERS
    ON 75 PERCENT DO NOTIFY
    ON 90 PERCENT DO NOTIFY
    ON 100 PERCENT DO SUSPEND;  -- hard stop

ALTER WAREHOUSE bi_wh SET RESOURCE_MONITOR = bi_cost_monitor;

-- 4. Increase dashboard refresh interval to 15 minutes (business agreed)

-- 5. Pre-warm the cache after ETL completes
-- Added an Airflow task that runs key dashboard queries after MERGE
-- This populates both result cache and SSD cache before users arrive

Monitoring Queries Added

-- Alert on multi-cluster scale-out events
SELECT warehouse_name,
       cluster_number,
       DATE_TRUNC('hour', start_time) AS hour,
       SUM(credits_used) AS credits
FROM snowflake.account_usage.warehouse_metering_history
WHERE start_time >= DATEADD('day', -1, CURRENT_TIMESTAMP())
  AND cluster_number > 1  -- additional clusters beyond the first
GROUP BY 1, 2, 3
ORDER BY hour, cluster_number;

-- Track result cache hit rate by warehouse
SELECT warehouse_name,
       COUNT_IF(bytes_scanned = 0 AND warehouse_name IS NOT NULL) AS cache_hits,
       COUNT(*) AS total_queries,
       ROUND(cache_hits / total_queries * 100, 2) AS cache_hit_pct
FROM snowflake.account_usage.query_history
WHERE start_time >= DATEADD('day', -1, CURRENT_TIMESTAMP())
  AND warehouse_name = 'BI_WH'
GROUP BY warehouse_name;

Lessons Learned

  • STANDARD vs. ECONOMY scaling — STANDARD is appropriate for latency-sensitive workloads with unpredictable spikes. ECONOMY is better for cost-sensitive workloads that can tolerate brief queuing.
  • ETL and BI cache interaction — Design ETL schedules with cache invalidation impact in mind. Batch mutations to minimize the blast radius.
  • Resource monitors are strongly recommended — Without hard credit limits, auto-scaling can generate unbounded costs.
  • Cold cache is expensive — A newly-scaled cluster has no SSD cache. Plan for the cost of warming it up.
  • Dashboard refresh rates compound costs — Each refresh that misses cache consumes full warehouse compute. Align refresh rates with data freshness requirements.

Common Mistakes

1. Using a Single Warehouse for All Workloads

Mistake: Running ETL, BI queries, and ad-hoc analytics on the same warehouse.

Why it's wrong: ETL workloads are throughput-optimized (large scans, heavy writes) while BI workloads are latency-sensitive. A long-running MERGE will queue dashboard queries, and auto-scaling to handle both creates cost inefficiency.

Correct approach: Dedicate separate warehouses per workload class. Size ETL warehouses for throughput (larger, shorter auto-suspend) and BI warehouses for concurrency (multi-cluster, longer auto-suspend for cache retention).

2. Over-Clustering (Too Many Clustering Keys)

Mistake: Adding clustering keys to every table, or using high-cardinality columns as clustering keys.

Why it's wrong: Reclustering is an ongoing cost — every DML operation triggers background reclustering. High-cardinality keys (e.g., user_id with millions of values) create minimal pruning benefit because zone map ranges will still overlap heavily.

Correct approach: Only cluster tables > 1 TB with clear query patterns. Use medium-cardinality columns or expressions (DATE_TRUNC). Monitor reclustering credits and compare against scan savings.

3. Ignoring Time Travel Storage Costs

Mistake: Setting 90-day retention on high-churn tables without understanding the storage implications.

Why it's wrong: If a table receives daily updates touching 20% of partitions, 90-day retention means storing ~18x the active data in old micro-partitions. For a 500 GB table, that's 9 TB of time-travel storage ($360/month on Snowflake).

Correct approach: Set retention proportional to recovery needs. Use TRANSIENT tables for staging. Monitor TABLE_STORAGE_METRICS regularly. Consider 1-7 day retention for high-churn tables.

4. Not Using the Result Cache Effectively

Mistake: Adding CURRENT_TIMESTAMP() or other non-deterministic functions to dashboard queries, or using dynamic SQL that changes query text each execution.

Why it's wrong: Any change in query text (even whitespace) or any non-deterministic function prevents result cache hits. This forces full query execution on every dashboard refresh.

Correct approach: Parameterize date ranges with fixed values computed outside the query. Standardize query text across dashboard tools. Use materialized views for frequently-accessed aggregations.

5. Treating Snowflake Like an OLTP Database

Mistake: Running thousands of single-row INSERTs, frequent point UPDATEs, or high-frequency micro-transactions.

Why it's wrong: Each DML statement creates new micro-partitions. Thousands of single-row INSERTs create thousands of tiny micro-partitions (far below the optimal 50-500 MB range), degrading scan performance and increasing metadata overhead.

Correct approach: Batch data into staging tables and load with COPY or INSERT INTO...SELECT. Use streams and tasks for micro-batch processing (minimum 1-minute intervals). For true OLTP needs, use a purpose-built OLTP database and sync to Snowflake.

6. Auto-Suspend Set Too Long (or Never)

Mistake: Leaving warehouses running 24/7 with AUTO_SUSPEND = 0 (disabled) or very long timeouts.

Why it's wrong: You pay per-second for active warehouses. A Medium warehouse running idle for 20 hours/day wastes 80 credits ($240/day). Multiply by 10 warehouses and you're burning $2,400/day on idle compute.

Correct approach: Set AUTO_SUSPEND = 60-300 seconds for most workloads. Only use longer timeouts when SSD cache warmth provides measurable query performance benefits that outweigh the idle cost.

7. Confusing Warehouse Size with Concurrency

Mistake: Scaling up warehouse size (S → XL) to handle more concurrent dashboard users.

Why it's wrong: Scaling UP adds more compute power per query (useful for complex/large queries) but does NOT increase concurrency capacity significantly. A single-cluster XL warehouse still processes queries sequentially when resources are saturated.

Correct approach: For concurrency, scale OUT with multi-cluster warehouses. A multi-cluster M warehouse (max 4 clusters) handles more concurrent users than a single-cluster XL, often at lower cost.

8. Not Leveraging Projection Pushdown

Mistake: Using SELECT * in production queries or views.

Why it's wrong: Snowflake's columnar format means unneeded columns are never read from storage. SELECT * forces reading ALL column segments from every scanned micro-partition, increasing I/O by 5-50x for wide tables.

Correct approach: Always specify only needed columns. This reduces bytes scanned, improves cache efficiency, and can enable metadata-only query execution for MIN/MAX/COUNT.

Follow-up Questions

Architecture & Design

  • Q: How does Snowflake achieve ACID transactions without traditional locking?
    A: Snowflake uses optimistic concurrency with snapshot isolation. Transactions operate on a consistent snapshot of metadata pointers. At commit time, the system checks for conflicts (overlapping writes to the same micro-partitions). If a conflict is detected, the later transaction is aborted and must retry. This works because micro-partitions are immutable — commits are atomic metadata pointer swaps.
  • Q: How does zero-copy cloning work?
    A: A CLONE operation creates a new metadata entry pointing to the same micro-partitions as the source. No data is copied. Both source and clone share physical storage until one of them is modified, at which point new micro-partitions are created (copy-on-write). Storage cost only accrues for the delta between them.
  • Q: What happens when you resize a running warehouse?
    A: On scale-up, new nodes are added and begin participating in new queries. Running queries continue on the original nodes. On scale-down, nodes are removed after their current work completes. SSD cache on removed nodes is lost. Partition assignment is updated, which may cause temporary cache misses on the remaining nodes.

Performance & Optimization

  • Q: How would you optimize a query that scans 90% of partitions?
    A: (1) Check if the predicate columns align with natural clustering or existing CLUSTER BY. (2) If not, evaluate adding a CLUSTER BY with those columns. (3) Ensure predicates are sargable (no functions wrapping the column). (4) Consider materializing filtered subsets for frequently-accessed slices. (5) Check if query rewriting (pushing filters earlier) reduces intermediate data.
  • Q: When would you NOT use Snowflake?
    A: (1) Sub-second OLTP workloads with point lookups — use PostgreSQL/DynamoDB. (2) Real-time streaming with <1s latency — use Kafka + Flink. (3) Unstructured data processing (images, audio) — use object storage + specialized compute. (4) Cost-prohibitive for always-on, constant workloads — Redshift RA3 reserved instances may be cheaper. (5) Graph traversals — use a graph database.
  • Q: How does Snowflake handle data skew in joins?
    A: Snowflake uses adaptive join strategies. For hash joins, it monitors partition sizes during the build phase. If a single join key has disproportionate rows (skew), it can apply skew-handling techniques like splitting the hot key across multiple nodes. The Query Profile will show uneven partition sizes in the join operator if skew is a problem.

Operations & Cost Management

  • Q: How do you handle a warehouse that's consuming more credits than expected?
    A: (1) Check WAREHOUSE_METERING_HISTORY for credit trends. (2) Examine QUERY_HISTORY for expensive queries (high bytes_scanned, long duration). (3) Check for spilling (sign of undersized warehouse or bad queries). (4) Verify auto-suspend is configured. (5) Look for multi-cluster scale-out events. (6) Set up RESOURCE_MONITOR with alerts and hard limits.
  • Q: How would you design a cost-effective multi-tenant architecture on Snowflake?
    A: (1) Use a shared database with Row Access Policies for tenant isolation. (2) Assign different warehouses per tenant tier (premium tenants get larger warehouses). (3) Use Resource Monitors per tenant/warehouse. (4) Consider Reader Accounts for external customers who only need query access. (5) Monitor per-tenant costs via query tagging (QUERY_TAG session parameter).
  • Q: What's the difference between Snowpipe and COPY INTO?
    A: COPY INTO is a user-triggered bulk load command that runs on a user-managed warehouse. Snowpipe is an event-driven, serverless continuous ingestion service that loads files within minutes of arrival (triggered by cloud event notifications or REST API). Snowpipe uses a dedicated compute pool billed per-file at a lower rate than warehouse credits, but has higher per-byte cost than batch COPY for large volumes.

Advanced Internals

  • Q: How does Snowflake's metadata store achieve consistency?
    A: Snowflake's metadata service provides strict transactional guarantees with multi-key ACID semantics (FoundationDB has been publicly discussed in engineering contexts). It atomically updates metadata pointers during DML (swapping old partition references for new ones). This is what enables instant table versioning, zero-copy cloning, and Time Travel — all metadata operations that reference immutable physical files.
  • Q: How might Snowflake distribute partitions across warehouse nodes for caching?
    A: A commonly discussed model is consistent hashing — each micro-partition's file path is hashed to determine which warehouse node "owns" it for caching purposes. When a query needs that partition, it's routed to the owning node (which likely has it cached). On resize events, the hash ring is updated minimally — only partitions mapping to added/removed nodes need to migrate, preserving most of the cache. Note: Snowflake does not publicly document its specific implementation.
  • Q: How does Snowflake handle concurrent DML on the same table?
    A: Concurrent INSERTs always succeed (they write to non-overlapping new partitions). Concurrent UPDATEs/DELETEs/MERGEs can conflict if they touch overlapping micro-partitions. Snowflake detects conflicts at commit time using partition-level granularity — if two transactions rewrote the same partition, the second to commit fails with a serialization error and must retry.

Hard Star Schema Modeling

How Would You Design a Warehouse for Petabyte-Scale Analytics?

Key Takeaway: A petabyte-scale warehouse needs mastery across three domains: logical design (star schemas with clearly defined grain, conformed dimensions, the right SCD strategy per attribute), physical design (time-based partitioning, clustering on high-cardinality filter columns, materialized views for hot paths), and operational design (medallion layering, cost governance). Physical design decisions like partitioning and clustering often matter more than logical modeling at this scale — a missing partition filter has turned $5K/month warehouses into $80K/month incidents.

Interviewer Intent

When an interviewer asks you to design a warehouse for petabyte-scale analytics, they are evaluating multiple dimensions of your expertise:

  • Dimensional modeling fluency — Can you articulate why star schemas dominate analytics workloads and when snowflake schemas are appropriate?
  • Scalability thinking — Do you understand how partitioning, clustering, and columnar storage enable sub-second queries over petabytes?
  • Cost awareness — Can you balance performance against cloud billing realities (storage tiering, slot reservations, on-demand pricing)?
  • Production maturity — Have you dealt with slowly changing dimensions, fact table grain decisions, and schema evolution at scale?
  • Trade-off articulation — Can you reason about normalization vs. denormalization, freshness vs. cost, and query performance vs. storage efficiency?

This question separates candidates who have only read about data warehousing from those who have built and operated warehouses serving thousands of analysts at FAANG scale.

Quick Answer

A petabyte-scale analytical warehouse requires:

  1. Dimensional model — Star schema with conformed dimensions, clearly defined grain per fact table, and surrogate keys for dimension versioning.
  2. Physical optimization — Time-based partitioning on fact tables, clustering on high-cardinality filter columns, and columnar storage (Parquet/ORC or native columnar engines).
  3. Layered architecture — Bronze (raw), Silver (cleaned/conformed), Gold (business-ready aggregates) with clear ownership boundaries.
  4. SCD strategy — Type 2 for critical dimensions (customer, product), Type 1 for corrections, with audit columns and effective date ranges.
  5. Cost controls — Storage lifecycle policies, materialized views for hot aggregates, slot-based reservations for predictable workloads, and partition pruning enforcement.
  6. Governance — Column-level lineage, data contracts between producers and consumers, and automated data quality checks at each layer boundary.

The key insight: at petabyte scale, physical design decisions (partitioning, clustering, compression) often matter more than logical design — but without a sound logical model, physical optimizations become unmaintainable.

Star Schema

The star schema remains the foundational pattern for analytical warehouses. Its simplicity — a central fact table surrounded by denormalized dimension tables — enables query engines to exploit broadcast joins, partition pruning, and predicate pushdown efficiently.

Fact Tables

Fact tables store the measurable events of your business. At petabyte scale, every design decision on the fact table has amplified consequences:

  • Grain — The grain defines what one row represents. A transaction-grain fact table stores one row per atomic business event (one purchase, one click, one API call). Declaring grain first prevents the most common modeling errors.
  • Measures — Additive (revenue, quantity), semi-additive (account balance — additive across all dimensions except time), and non-additive (ratios, percentages — store components separately).
  • Foreign keys — Every dimension is referenced by a surrogate key (integer or hash). Natural keys are stored for lineage but never used for joins in production queries.
  • Degenerate dimensions — Transaction numbers, order IDs that live directly in the fact table without a separate dimension.

Dimension Tables

Dimensions provide the "who, what, where, when, why" context for facts:

  • Wide and denormalized — A customer dimension might have 50+ columns spanning demographics, segmentation, acquisition channel, and lifetime metrics.
  • Conformed dimensions — Shared across multiple fact tables. A single dim_date table serves every star in the warehouse, enabling cross-process reporting.
  • Role-playing dimensions — The same physical dimension (e.g., dim_date) referenced multiple times by a fact table (order_date_key, ship_date_key, delivery_date_key).
  • Junk dimensions — Low-cardinality flags and indicators combined into a single dimension to avoid fact table bloat.

Surrogate Keys

Surrogate keys serve multiple critical purposes:

  • Enable SCD Type 2 tracking — multiple rows per natural key, each with a unique surrogate.
  • Insulate the warehouse from source system key changes (mergers, migrations).
  • Provide consistent integer keys that compress better and join faster than composite natural keys.
  • At FAANG scale, surrogate keys may be generated using identity columns, distributed ID generators (e.g., Snowflake sequences), or deterministic techniques (hash of natural key + timestamp) when coordination-free generation across distributed systems is required. Hashes are also commonly used for change detection and business-key mapping.

Grain Declaration

The grain is the single most important design decision. Examples:

  • fact_orders — One row per order line item per order.
  • fact_page_views — One row per page view per session per user.
  • fact_daily_inventory — One row per product per warehouse per day (periodic snapshot).

Mixing grains in a single fact table is the #1 modeling antipattern. It produces double-counting, incorrect aggregations, and confused analysts.

Snowflake Schema

A snowflake schema normalizes dimension tables into sub-dimensions, creating a multi-level hierarchy. While star schemas are preferred for most analytics, snowflake schemas have legitimate use cases at scale.

Normalized Dimensions

In a snowflake schema, a dim_product might be split into:

  • dim_product (product_key, product_name, brand_key, category_key)
  • dim_brand (brand_key, brand_name, parent_company)
  • dim_category (category_key, category_name, department_key)
  • dim_department (department_key, department_name)

Each normalized table reduces redundancy but adds joins to every query that needs the full hierarchy.

When to Use Snowflake vs. Star

Criterion Star Schema Snowflake Schema
Query simplicity Fewer joins, easier for analysts More joins, requires documentation
Storage efficiency Some redundancy in dimensions Minimal redundancy
Dimension size Fine for most dimension sizes Better when dimensions have large hierarchies or high redundancy
ETL complexity Simpler — single dimension load More complex — dependency ordering
Update frequency Denormalized updates cascade Localized updates to sub-dimensions
Modern engines (BQ, Snowflake) Preferred — engines optimize flat scans Less benefit — joins add latency

FAANG reality: Most FAANG warehouses use star schemas for analyst-facing layers (Gold) and may use normalized forms in Silver/staging layers where ETL correctness matters more than query performance.

Hybrid Approach

In practice, you often see a hybrid:

  • Core dimensions (date, customer, product) remain denormalized stars.
  • Very large dimensions with deeply nested hierarchies (geographic taxonomy with 8 levels, organizational hierarchy) get snowflaked.
  • Bridge tables handle many-to-many relationships (customer ↔ account, product ↔ promotion).

Slowly Changing Dimensions

Dimensions change over time — customers move, products get reclassified, employees change departments. SCDs define how the warehouse captures these changes while preserving historical accuracy.

Type 1 — Overwrite

  • Simply overwrite the old value with the new value.
  • No history preserved — previous state is lost.
  • Use for: corrections, typo fixes, non-analytically-significant changes.
  • Example: Fixing a misspelled customer name.
-- SCD Type 1: Overwrite
UPDATE dim_customer
SET customer_city = 'San Francisco',
    updated_at = CURRENT_TIMESTAMP
WHERE customer_natural_key = 'CUST-12345';

Type 2 — Add New Row

  • Insert a new row with a new surrogate key; mark the old row as expired.
  • Full history preserved — can query "as of" any point in time.
  • Requires: surrogate_key, effective_from, effective_to, is_current flag.
  • Use for: any change that affects analytics (customer segment, product category, employee department).
  • At FAANG scale, Type 2 dimensions can grow 10-50x the source cardinality.
-- SCD Type 2: Close existing row
UPDATE dim_customer
SET effective_to = CURRENT_DATE - INTERVAL '1 day',
    is_current = FALSE,
    updated_at = CURRENT_TIMESTAMP
WHERE customer_natural_key = 'CUST-12345'
  AND is_current = TRUE;

-- SCD Type 2: Insert new version
INSERT INTO dim_customer (
  customer_sk, customer_natural_key, customer_name,
  customer_city, customer_segment,
  effective_from, effective_to, is_current, created_at
)
VALUES (
  GENERATE_SURROGATE_KEY('CUST-12345', CURRENT_DATE),
  'CUST-12345', 'Jane Smith',
  'San Francisco', 'Enterprise',
  CURRENT_DATE, '9999-12-31', TRUE, CURRENT_TIMESTAMP
);

Type 3 — Add New Column

  • Add a "previous" column alongside the current column.
  • Limited history — only captures one prior state.
  • Use for: planned transitions where you need to compare old vs. new (org restructure, territory realignment).
-- SCD Type 3: Column for previous value
ALTER TABLE dim_customer ADD COLUMN previous_segment VARCHAR(50);
ALTER TABLE dim_customer ADD COLUMN segment_change_date DATE;

UPDATE dim_customer
SET previous_segment = customer_segment,
    customer_segment = 'Enterprise',
    segment_change_date = CURRENT_DATE
WHERE customer_natural_key = 'CUST-12345';

Type 4 — History Table

  • Maintain a "current" dimension table and a separate "history" dimension table.
  • Current table stays small and fast; history table captures all versions.
  • Use for: very high-frequency changes where Type 2 would bloat the primary dimension.
  • Useful when current-state lookups are significantly more common than historical analysis, and when high-frequency changes would make the primary dimension excessively large with Type 2.
-- Type 4: Current table (fast lookups)
CREATE TABLE dim_customer_current (
  customer_sk       BIGINT PRIMARY KEY,
  customer_natural_key VARCHAR(20),
  customer_name     VARCHAR(200),
  customer_segment  VARCHAR(50),
  customer_city     VARCHAR(100),
  updated_at        TIMESTAMP
);

-- Type 4: History table (full audit trail)
CREATE TABLE dim_customer_history (
  history_sk        BIGINT PRIMARY KEY,
  customer_natural_key VARCHAR(20),
  customer_name     VARCHAR(200),
  customer_segment  VARCHAR(50),
  customer_city     VARCHAR(100),
  effective_from    DATE,
  effective_to      DATE,
  change_reason     VARCHAR(200),
  created_at        TIMESTAMP
);

Type 6 — Hybrid (1 + 2 + 3)

  • Combines Type 1 (current value column), Type 2 (versioned rows), and Type 3 (previous value column).
  • Every row has: current_value, historical_value (from that version), plus full row versioning.
  • Enables both "as-was" and "as-is" analysis without complex self-joins.
  • Use for: critical dimensions where analysts need both perspectives (revenue by current segment vs. segment at time of transaction).
-- Type 6: Hybrid approach
CREATE TABLE dim_customer_type6 (
  customer_sk           BIGINT PRIMARY KEY,
  customer_natural_key  VARCHAR(20),
  customer_name         VARCHAR(200),
  -- Type 2 versioned value (historical)
  historical_segment    VARCHAR(50),
  -- Type 1 current value (always up-to-date)
  current_segment       VARCHAR(50),
  -- Type 3 previous value
  previous_segment      VARCHAR(50),
  effective_from        DATE,
  effective_to          DATE,
  is_current            BOOLEAN,
  updated_at            TIMESTAMP
);

-- When segment changes: insert new row AND update all rows' current_segment
-- Step 1: Close current row
UPDATE dim_customer_type6
SET effective_to = CURRENT_DATE - 1, is_current = FALSE
WHERE customer_natural_key = 'CUST-12345' AND is_current = TRUE;

-- Step 2: Insert new version
INSERT INTO dim_customer_type6 VALUES (
  NEW_SK(), 'CUST-12345', 'Jane Smith',
  'Enterprise', 'Enterprise', 'Mid-Market',
  CURRENT_DATE, '9999-12-31', TRUE, CURRENT_TIMESTAMP
);

-- Step 3: Update current_segment on ALL historical rows (Type 1 overwrite)
UPDATE dim_customer_type6
SET current_segment = 'Enterprise'
WHERE customer_natural_key = 'CUST-12345';

Implementation Patterns at Scale

  • MERGE/UPSERT — Use MERGE INTO statements to atomically handle inserts and updates in a single pass.
  • Hash-based change detection — Compute MD5/SHA of all tracked columns to detect actual changes vs. no-op updates.
  • Batch windows — Process SCD updates in daily or hourly batches to amortize the cost of full-table scans on large dimensions.
  • Late-arriving dimensions — Insert placeholder "unknown" rows with surrogate key -1; backfill when the actual dimension data arrives.
  • Partition-level updates — Where dimensions are partitioned appropriately, partition-level rewrites can significantly reduce update costs. Otherwise, MERGE operations are the standard implementation strategy for SCD Type 2.

Fact Table Types

Different business processes require different fact table structures. Choosing the wrong type leads to incorrect metrics, expensive queries, and confused stakeholders.

Transactional Fact Tables

  • Grain: One row per atomic business event (one click, one purchase, one API call).
  • Characteristics: Append-only, immutable, highest volume, most granular.
  • Measures: Fully additive (quantity, revenue, duration).
  • Volume: At FAANG scale, these tables commonly reach billions of rows per day.
  • Example: fact_clicks — one row per user click with timestamp, page_key, user_key, device_key, session_id.
CREATE TABLE fact_orders (
  order_line_sk     BIGINT,
  order_date_key    INT REFERENCES dim_date(date_key),
  customer_key      BIGINT REFERENCES dim_customer(customer_sk),
  product_key       BIGINT REFERENCES dim_product(product_sk),
  store_key         INT REFERENCES dim_store(store_key),
  promotion_key     INT REFERENCES dim_promotion(promotion_key),
  -- Degenerate dimension
  order_number      VARCHAR(30),
  -- Measures
  quantity          INT,
  unit_price        DECIMAL(12,2),
  discount_amount   DECIMAL(12,2),
  net_revenue       DECIMAL(12,2),
  tax_amount        DECIMAL(12,2),
  -- Metadata
  etl_batch_id      BIGINT,
  loaded_at         TIMESTAMP
)
PARTITION BY RANGE (order_date_key)
CLUSTER BY (customer_key, product_key);

Periodic Snapshot Fact Tables

  • Grain: One row per entity per time period (daily, weekly, monthly).
  • Characteristics: Captures cumulative state at regular intervals; rows are dense (one per period even if no activity).
  • Measures: Semi-additive (balance, inventory level — cannot sum across time).
  • Use cases: Account balances, inventory levels, subscription counts, pipeline stages.
  • Example: fact_daily_inventory — one row per product per warehouse per day.
CREATE TABLE fact_daily_inventory (
  snapshot_date_key   INT REFERENCES dim_date(date_key),
  product_key         BIGINT REFERENCES dim_product(product_sk),
  warehouse_key       INT REFERENCES dim_warehouse(warehouse_key),
  -- Semi-additive measures (additive across product/warehouse, NOT across time)
  quantity_on_hand    INT,
  quantity_on_order   INT,
  quantity_reserved   INT,
  days_of_supply      DECIMAL(8,2),
  inventory_value     DECIMAL(14,2),
  -- Metadata
  loaded_at           TIMESTAMP
)
PARTITION BY RANGE (snapshot_date_key);

Accumulating Snapshot Fact Tables

  • Grain: One row per lifecycle instance (one order, one claim, one application).
  • Characteristics: Rows are updated as the entity progresses through milestones; multiple date keys per row.
  • Measures: Lag metrics between milestones (days_to_ship, days_to_deliver).
  • Use cases: Order fulfillment, insurance claims, loan applications, hiring pipelines.
  • Example: fact_order_fulfillment — one row per order tracking through placed → picked → shipped → delivered.
CREATE TABLE fact_order_fulfillment (
  order_key               BIGINT PRIMARY KEY,
  customer_key            BIGINT,
  -- Multiple date role-playing dimensions
  order_placed_date_key   INT,
  order_picked_date_key   INT,      -- NULL until picked
  order_shipped_date_key  INT,      -- NULL until shipped
  order_delivered_date_key INT,     -- NULL until delivered
  order_returned_date_key INT,      -- NULL unless returned
  -- Lag measures (computed on update)
  days_to_pick            INT,
  days_to_ship            INT,
  days_to_deliver         INT,
  total_fulfillment_days  INT,
  -- Status
  current_status          VARCHAR(20),
  -- Measures
  order_amount            DECIMAL(12,2),
  shipping_cost           DECIMAL(8,2),
  loaded_at               TIMESTAMP,
  updated_at              TIMESTAMP
);

Factless Fact Tables

  • Grain: Records the occurrence (or non-occurrence) of a relationship between dimensions.
  • Characteristics: No numeric measures — the row itself is the fact. May include a count column of 1 for aggregation convenience.
  • Use cases:
    • Coverage/eligibility: Which promotions were available to which customers on which dates (even if not used).
    • Event tracking: Student attendance (who attended which class on which day).
    • Negative analysis: "Which customers were eligible for the promotion but did NOT purchase?" — answered by subtracting the transactional fact from the factless coverage fact.
-- Factless fact: promotion coverage
CREATE TABLE fact_promotion_coverage (
  date_key        INT REFERENCES dim_date(date_key),
  customer_key    BIGINT REFERENCES dim_customer(customer_sk),
  promotion_key   INT REFERENCES dim_promotion(promotion_key),
  product_key     BIGINT REFERENCES dim_product(product_sk),
  -- Optional: convenience column for counting
  event_count     INT DEFAULT 1
)
PARTITION BY RANGE (date_key);

-- Query: Customers eligible but did NOT purchase
SELECT pc.customer_key, pc.promotion_key
FROM fact_promotion_coverage pc
LEFT JOIN fact_orders fo
  ON pc.customer_key = fo.customer_key
  AND pc.promotion_key = fo.promotion_key
  AND pc.date_key = fo.order_date_key
WHERE fo.order_line_sk IS NULL;

Partitioning & Clustering

At petabyte scale, partitioning and clustering are not optional optimizations — they are architectural requirements. Without them, every query scans the entire dataset, resulting in unacceptable latency and cost.

Time Partitioning

The most common and effective partitioning strategy for fact tables:

  • Daily partitions — Standard for most transactional facts. One partition per day, typically on the event timestamp or date key.
  • Hourly partitions — For very high-volume streaming facts (clickstream, IoT telemetry) where daily partitions would be excessively large. Choose granularity based on data volume and query patterns rather than a fixed partition size target.
  • Monthly partitions — For slowly-growing dimensions or periodic snapshots where daily would create too many small files.
-- BigQuery: Time-partitioned table
CREATE TABLE `project.dataset.fact_events`
(
  event_id        STRING,
  event_timestamp TIMESTAMP,
  user_id         STRING,
  event_type      STRING,
  properties      JSON,
  revenue         NUMERIC
)
PARTITION BY DATE(event_timestamp)
OPTIONS (
  partition_expiration_days = 730,  -- Auto-delete after 2 years
  require_partition_filter = TRUE    -- Force partition pruning
);

-- Snowflake: Automatic clustering (time-based)
CREATE TABLE fact_events (
  event_id        VARCHAR(36),
  event_timestamp TIMESTAMP_NTZ,
  user_id         VARCHAR(50),
  event_type      VARCHAR(100),
  properties      VARIANT,
  revenue         NUMBER(12,2)
)
CLUSTER BY (TO_DATE(event_timestamp), event_type);

Hash Partitioning

Distributes data evenly across partitions based on a hash of one or more columns:

  • Eliminates data skew when no natural time dimension exists.
  • Enables parallel processing — each partition can be scanned independently.
  • Common in Redshift (DISTKEY) and traditional MPP systems.
  • Less common in BigQuery/Snowflake which handle distribution automatically.
-- Redshift: Hash distribution on customer_id for co-located joins
CREATE TABLE fact_orders (
  order_id        BIGINT,
  customer_id     BIGINT,
  order_date      DATE,
  amount          DECIMAL(12,2)
)
DISTKEY(customer_id)
SORTKEY(order_date);

-- The dim_customer table uses the same DISTKEY for co-located joins
CREATE TABLE dim_customer (
  customer_id     BIGINT,
  customer_name   VARCHAR(200),
  segment         VARCHAR(50)
)
DISTKEY(customer_id)
SORTKEY(customer_id);

Clustering Keys

Clustering organizes data within partitions to improve filter performance:

  • Column order matters — Place the most frequently filtered column first. The clustering is applied left-to-right.
  • High-cardinality columns benefit most — user_id, product_id, region provide better pruning than boolean flags.
  • Complementary to partitioning — Partition on time (coarse), cluster on entity keys (fine-grained).
  • Limit to 4 columns — Diminishing returns beyond 4 clustering columns in most engines.
-- BigQuery: Clustering within time partitions
CREATE TABLE `project.dataset.fact_page_views`
(
  view_timestamp  TIMESTAMP,
  user_id         STRING,
  page_path       STRING,
  country_code    STRING,
  device_type     STRING,
  session_id      STRING,
  duration_ms     INT64
)
PARTITION BY DATE(view_timestamp)
CLUSTER BY user_id, country_code, page_path;

-- Query that benefits from both partition pruning AND cluster pruning:
SELECT user_id, COUNT(*) as views, AVG(duration_ms) as avg_duration
FROM `project.dataset.fact_page_views`
WHERE DATE(view_timestamp) BETWEEN '2025-01-01' AND '2025-01-31'  -- partition pruning
  AND country_code = 'US'                                          -- cluster pruning
  AND user_id = 'user-abc-123'                                     -- cluster pruning
GROUP BY user_id;

BigQuery Clustering Deep Dive

  • BigQuery automatically re-clusters data in the background — no manual maintenance required.
  • For highly selective queries, clustering can substantially reduce bytes scanned (and therefore cost). The improvement depends on filter selectivity and data distribution.
  • Cluster columns must be top-level, non-repeated fields (STRING, INT64, NUMERIC, DATE, TIMESTAMP, BOOL).
  • Use INFORMATION_SCHEMA.TABLE_STORAGE to monitor clustering effectiveness.
-- Monitor clustering ratio in BigQuery
SELECT
  table_name,
  total_rows,
  total_logical_bytes / POW(1024, 3) AS logical_gb,
  total_physical_bytes / POW(1024, 3) AS physical_gb,
FROM `project.dataset.INFORMATION_SCHEMA.TABLE_STORAGE`
WHERE table_name = 'fact_page_views';

Snowflake Micro-Partitions

Snowflake takes a unique approach — all tables are automatically divided into immutable micro-partitions (approximately 50-500 MB of uncompressed data each):

  • Automatic — No explicit partition DDL needed. Snowflake manages partitioning internally.
  • Clustering — Defined via CLUSTER BY to control the physical ordering within micro-partitions.
  • Pruning metadata — Each micro-partition stores min/max statistics per column, enabling partition elimination without reading data.
  • Reclustering — Background process that re-organizes micro-partitions when data becomes fragmented from many DML operations.
-- Snowflake: Monitor clustering depth
SELECT SYSTEM$CLUSTERING_INFORMATION('fact_orders', '(order_date, customer_id)');

-- Snowflake: Check clustering effectiveness
SELECT
  table_name,
  clustering_key,
  total_constant_partition_count,
  total_partition_count,
  average_overlaps,
  average_depth
FROM TABLE(INFORMATION_SCHEMA.AUTOMATIC_CLUSTERING_HISTORY(
  DATE_RANGE_START => DATEADD('day', -7, CURRENT_DATE()),
  TABLE_NAME => 'fact_orders'
));

Partitioning Strategy Decision Framework

Factor Recommendation
Table < 1 GB No partitioning needed — full scan is fast enough
Table 1-100 GB Single partition key (usually date) + clustering
Table 100 GB - 10 TB Date partition + 2-3 clustering keys + partition expiration
Table > 10 TB Date partition + aggressive clustering + materialized views for hot paths + mandatory partition filters
Queries always filter by time Time-based partitioning (95% of cases)
Queries filter by tenant/customer Hash partition by tenant + time-based clustering OR composite

Materialized Views & Aggregation Tables

When queries repeatedly aggregate petabytes of raw data into the same summaries, pre-computation becomes essential. Materialized views and aggregation tables trade storage and freshness for dramatic query performance improvements.

Pre-Computation Strategy

  • Identify hot paths — Use query logs to find the top 20 most expensive/frequent queries. These are candidates for materialized views.
  • Aggregate at business-meaningful grains — Daily revenue by region, hourly active users by platform, weekly retention cohorts.
  • Layer aggregations — Raw (grain) → hourly → daily → weekly → monthly. Each layer is 10-100x smaller than the previous.
  • Cost-benefit threshold — Materialize when: (query frequency × query cost) > (storage cost + refresh cost).

Materialized Views in Practice

-- BigQuery: Materialized view with automatic refresh
CREATE MATERIALIZED VIEW `project.dataset.mv_daily_revenue`
OPTIONS (
  enable_refresh = TRUE,
  max_staleness = INTERVAL "0:30:0" HOUR TO SECOND
)
AS
SELECT
  DATE(order_timestamp) AS order_date,
  region,
  product_category,
  COUNT(*) AS order_count,
  SUM(revenue) AS total_revenue,
  AVG(revenue) AS avg_order_value,
  APPROX_COUNT_DISTINCT(customer_id) AS approx_unique_customers
FROM `project.dataset.fact_orders`
GROUP BY 1, 2, 3;
-- Note: BigQuery materialized views have restrictions on supported
-- aggregates. COUNT(DISTINCT) may require APPROX_COUNT_DISTINCT instead.
-- Always verify engine-specific MV restrictions.

-- Snowflake: Materialized view
CREATE MATERIALIZED VIEW mv_daily_revenue AS
SELECT
  order_date,
  region,
  product_category,
  COUNT(*) AS order_count,
  SUM(revenue) AS total_revenue,
  AVG(revenue) AS avg_order_value,
  COUNT(DISTINCT customer_id) AS unique_customers
FROM fact_orders
GROUP BY 1, 2, 3;

Refresh Strategies

Strategy Freshness Cost Use Case
Full refresh Depends on schedule High — recomputes everything Small aggregation tables, complex logic
Incremental refresh Near real-time (minutes) Low — only processes new data Append-only fact tables, simple aggregations
Automatic (engine-managed) Engine decides Moderate — optimized by engine BigQuery/Snowflake native materialized views
Partition-aware refresh Partition-level Medium — refreshes affected partitions Large tables with time-partitioned data

Incremental Refresh Pattern

-- Incremental aggregation: only process new partitions
-- Step 1: Find the last processed watermark
DECLARE last_processed DATE;
SET last_processed = (
  SELECT MAX(order_date) FROM agg_daily_revenue
);

-- Step 2: Aggregate only new data
INSERT INTO agg_daily_revenue
SELECT
  DATE(order_timestamp) AS order_date,
  region,
  product_category,
  COUNT(*) AS order_count,
  SUM(revenue) AS total_revenue,
  AVG(revenue) AS avg_order_value,
  COUNT(DISTINCT customer_id) AS unique_customers
FROM fact_orders
WHERE DATE(order_timestamp) > last_processed
GROUP BY 1, 2, 3;

-- Step 3: Handle late-arriving data by re-processing recent window
MERGE INTO agg_daily_revenue target
USING (
  SELECT
    DATE(order_timestamp) AS order_date,
    region,
    product_category,
    COUNT(*) AS order_count,
    SUM(revenue) AS total_revenue,
    AVG(revenue) AS avg_order_value,
    COUNT(DISTINCT customer_id) AS unique_customers
  FROM fact_orders
  WHERE DATE(order_timestamp) >= DATE_SUB(CURRENT_DATE(), INTERVAL 3 DAY)
  GROUP BY 1, 2, 3
) source
ON target.order_date = source.order_date
  AND target.region = source.region
  AND target.product_category = source.product_category
WHEN MATCHED THEN UPDATE SET
  order_count = source.order_count,
  total_revenue = source.total_revenue,
  avg_order_value = source.avg_order_value,
  unique_customers = source.unique_customers
WHEN NOT MATCHED THEN INSERT VALUES (
  source.order_date, source.region, source.product_category,
  source.order_count, source.total_revenue,
  source.avg_order_value, source.unique_customers
);

Aggregation Table Design Patterns

  • Rollup hierarchy — Create aggregates at each level of a dimension hierarchy (city → state → country → global) as separate tables or views.
  • Cube tables — Pre-compute all combinations of a small set of dimensions (region × category × channel) for dashboard backing tables.
  • Approximate aggregates — Use HyperLogLog for distinct counts, T-Digest for percentiles when exact values are not required.
  • Semantic layer — Tools like dbt metrics, Looker derived tables, or Cube.js abstract aggregation logic from physical storage.

Medallion Architecture

The Medallion (or Multi-Hop) architecture organizes data into progressively refined layers. Originally popularized by Databricks, it has become a standard pattern across cloud data platforms.

Bronze Layer (Raw)

  • Purpose: Land raw data exactly as received from sources — no transformations, no deduplication.
  • Format: Often stored as JSON, Avro, or raw Parquet reflecting the source schema.
  • Properties: Append-only, immutable, full-fidelity copy of source data. Business transformations are avoided; only ingestion-related processing (metadata enrichment, format conversion, decompression) is typically applied.
  • Retention: Long retention (1-7 years) for replay capability and auditing.
  • Schema: Schema-on-read; may include a metadata envelope (source_system, ingestion_timestamp, batch_id).
-- Bronze table: raw events as ingested
CREATE TABLE bronze.raw_events (
  ingestion_timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  source_system       VARCHAR(50),
  source_table        VARCHAR(100),
  batch_id            VARCHAR(36),
  raw_payload         VARIANT,  -- JSON as received
  file_name           VARCHAR(500),
  file_row_number     INT
)
PARTITION BY (TO_DATE(ingestion_timestamp));

Silver Layer (Cleaned/Conformed)

  • Purpose: Clean, deduplicate, validate, and conform data to enterprise standards.
  • Transformations: Type casting, null handling, deduplication, schema enforcement, join enrichment.
  • Properties: Typed schemas, validated constraints, conformed naming conventions.
  • Organization: Tables mirror business entities (customers, orders, products) not source systems.
  • SCD handling: Type 2 dimensions are typically built at this layer.
-- Silver table: cleaned and conformed orders
CREATE TABLE silver.orders (
  order_id            VARCHAR(36) NOT NULL,
  customer_id         VARCHAR(36) NOT NULL,
  order_timestamp     TIMESTAMP_NTZ NOT NULL,
  order_status        VARCHAR(20) NOT NULL,
  currency_code       VARCHAR(3) DEFAULT 'USD',
  subtotal            NUMBER(12,2),
  tax_amount          NUMBER(12,2),
  shipping_amount     NUMBER(12,2),
  total_amount        NUMBER(12,2),
  -- Data quality metadata
  dq_score            NUMBER(3,2),  -- 0.00 to 1.00
  dq_flags            ARRAY,
  -- Lineage
  source_system       VARCHAR(50),
  bronze_batch_id     VARCHAR(36),
  processed_at        TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP()
)
CLUSTER BY (TO_DATE(order_timestamp), customer_id);

Gold Layer (Business-Ready)

  • Purpose: Business-logic-enriched, consumption-ready datasets optimized for specific use cases.
  • Structure: Dimensional models (star schemas), aggregation tables, feature stores, metric tables.
  • Properties: Documented business logic, SLAs on freshness, governed access controls.
  • Consumers: BI dashboards, ML feature pipelines, executive reports, data products.
  • Ownership: Typically owned by analytics engineering teams or domain teams.
-- Gold table: dimensional model for analytics
CREATE TABLE gold.fact_revenue (
  revenue_date_key    INT,

  product_key         BIGINT,

CLUSTER BY (customer_key, product_key);

When to Use Medallion Architecture

  • Good fit: Large organizations with multiple data sources, need for data lineage, regulatory compliance requirements, teams at different maturity levels consuming different layers.
  • Overkill: Small teams with <5 data sources, single-use-case warehouses, real-time-only workloads.
  • Alternative: ELT with staging → warehouse → marts (dbt-style) — essentially the same concept with different naming.

Criticisms and Pitfalls

  • Over-engineering: Teams create bronze/silver/gold for every table regardless of complexity, adding latency and cost without value.
  • Naming confusion: "Silver" means different things to different teams — is it cleaned? conformed? enriched? All three?
  • Duplication waste: Storing 3 copies of every dataset triples storage costs. Apply selectively.
  • Latency accumulation: Poorly designed sequential refresh schedules can accumulate latency across layers. Modern orchestration platforms often trigger downstream layers immediately after upstream completion, but pipeline design requires attention to end-to-end timing.
  • Organizational boundaries: Layer ownership disputes — who owns Silver? Platform team or domain teams?
  • Not a substitute for data contracts: Layers don't prevent schema breaking changes from upstream. You still need explicit contracts.

Cost Optimization

At petabyte scale, warehouse costs can easily reach six or seven figures monthly. Cost optimization is not a one-time exercise — it requires continuous monitoring, governance, and architectural decisions that compound over time.

Storage Tiering

  • Hot storage: Frequently accessed data (last 30-90 days). Full performance, highest cost. Keep fact tables and active dimensions here.
  • Warm storage: Occasionally accessed (90 days - 1 year). Reduced cost, slightly higher latency. Historical aggregates, reference data.
  • Cold storage: Rarely accessed (1+ years). Lowest cost, highest latency. Compliance data, raw archives, audit trails.
  • BigQuery: Automatic long-term storage pricing (50% reduction after 90 days of no edits).
  • Snowflake: Time travel storage costs separate from active storage; Fail-safe adds 7 additional days of non-queryable backup.
-- BigQuery: Check storage billing breakdown
SELECT
  table_name,
  ROUND(active_logical_bytes / POW(1024, 4), 4) AS active_tb,
  ROUND(long_term_logical_bytes / POW(1024, 4), 4) AS long_term_tb,
  ROUND((active_logical_bytes * 0.02 +
         long_term_logical_bytes * 0.01) / POW(1024, 4), 2) AS est_monthly_cost_usd
FROM `project.region-us.INFORMATION_SCHEMA.TABLE_STORAGE`
WHERE total_logical_bytes > 0
ORDER BY total_logical_bytes DESC
LIMIT 20;

Compression

  • Columnar formats — Parquet and ORC achieve 3-10x compression over row-based formats through dictionary encoding, run-length encoding, and delta encoding.
  • Column data types — Choose the most appropriate data type for business semantics. Appropriate numeric types (INT32 vs INT64) and low-cardinality categorical columns typically provide the greatest compression benefits.
  • Sort order — Sorting data before writing improves compression by increasing value locality (run-length encoding becomes effective).
  • Dictionary encoding — Low-cardinality columns (status, country_code, category) compress 50-100x with dictionary encoding.
# PySpark: Optimize Parquet compression
df.repartition(200) \

Lifecycle Policies

  • Partition expiration: Automatically delete old partitions after retention period (BigQuery: partition_expiration_days).
  • Table cloning: Use zero-copy clones for development/testing instead of full copies.
  • Time travel reduction: Reduce time travel retention for non-critical tables (e.g., Snowflake supports up to 90 days on Enterprise+ edition; Standard edition defaults to 1 day).
  • Archive and drop: Export cold data to object storage (GCS/S3) before dropping from the warehouse.

  • Query budgets: Set per-query byte limits (BigQuery: maximum_bytes_billed) to prevent accidental full-table scans.

  • Query review: Require peer review for queries scanning > 1 TB; automated alerts for queries exceeding cost thresholds.
  • Materialization ROI: Track cost savings from materialized views vs. their refresh costs; deprecate under-utilized MVs.

Production Incident: $5K to $80K/Month Query Cost Explosion

Scenario: A 50TB fact table in BigQuery saw warehouse query costs grow from $5,000/month to $80,000/month over 6 weeks due to missing partitioning.

Timeline

  1. Week 0: A new fact_user_interactions table was created by a product analytics team. The table was created without partitioning or clustering — a simple CREATE TABLE with no physical optimization.
  2. Weeks 1-2: Table grew from 500 GB to 5 TB as user interaction data loaded daily. Queries were fast initially because data was small. Monthly cost: ~$5,000 (on-demand billing).
  3. Weeks 3-4: Table reached 20 TB. Every dashboard query and ad-hoc analysis performed full-table scans. Latency increased from 5 seconds to 45 seconds. Cost jumped to $35,000.
  4. Weeks 5-6: Table hit 50 TB. Analysts created additional queries to work around slow dashboards (caching copies, redundant aggregations). Cost exploded to $80,000. SLA breaches triggered incident.

Root Cause Analysis

The cost explosion resulted from a combination of factors that compounded each other:

  • No partition filter requirement: The table was created without require_partition_filter = TRUE, so every query scanned all 50 TB.
  • No partitioning at all: The table lacked any PARTITION BY clause — even time-based queries scanned everything.
  • No clustering: Common filter columns (user_id, event_type, platform) were not clustered, preventing any scan reduction.
  • No cost alerts: Billing alerts were set at the project level ($100K) not the dataset level, so the incremental growth wasn't caught early.
  • Self-serve culture without guardrails: The team had full DDL permissions without mandatory schema review.

Resolution

-- Step 1: Create properly designed replacement table
CREATE TABLE `project.dataset.fact_user_interactions_v2`
(
  interaction_id    STRING NOT NULL,
  event_timestamp   TIMESTAMP NOT NULL,
  user_id           STRING NOT NULL,
  event_type        STRING,
  platform          STRING,
  page_path         STRING,
  properties        JSON,
  session_id        STRING,
  duration_ms       INT64,
  revenue           NUMERIC
)
PARTITION BY DATE(event_timestamp)
CLUSTER BY user_id, event_type, platform
OPTIONS (
  partition_expiration_days = 730,
  require_partition_filter = TRUE,
  description = 'Partitioned user interactions - migrated from unpartitioned table'
);

-- Step 2: Backfill data (partition by partition to avoid memory issues)
DECLARE process_date DATE DEFAULT DATE('2024-01-01');
DECLARE end_date DATE DEFAULT CURRENT_DATE();

WHILE process_date <= end_date DO
  INSERT INTO `project.dataset.fact_user_interactions_v2`
  SELECT *
  FROM `project.dataset.fact_user_interactions`
  WHERE DATE(event_timestamp) = process_date;

  SET process_date = DATE_ADD(process_date, INTERVAL 1 DAY);
END WHILE;

-- Step 3: Validate counts match
SELECT 'original' AS source, COUNT(*) AS cnt
FROM `project.dataset.fact_user_interactions`
UNION ALL
SELECT 'migrated' AS source, COUNT(*) AS cnt
FROM `project.dataset.fact_user_interactions_v2`;

-- Step 4: Swap table names
ALTER TABLE `project.dataset.fact_user_interactions`
  RENAME TO `project.dataset.fact_user_interactions_deprecated`;
ALTER TABLE `project.dataset.fact_user_interactions_v2`
  RENAME TO `project.dataset.fact_user_interactions`;

Preventive Measures Implemented

  • Policy: All fact tables > 10 GB must have partitioning. Enforced via Terraform/IaC that rejects unpartitioned table definitions.
  • Alerts: Dataset-level cost alerts at 50%, 80%, and 100% of monthly budget.
  • Automated scanning: Weekly job that identifies unpartitioned tables exceeding 1 TB and creates tickets.
  • Query governance: maximum_bytes_billed set at 5 TB for all service accounts; analysts capped at 1 TB per query.
  • Schema review: All new table DDL requires review from the data platform team before deployment to production datasets.

SCD Type 2 — Full MERGE Implementation

-- ============================================
-- SCD TYPE 2: MERGE pattern for dim_customer
-- Source: staging.stg_customers (daily extract)
-- Target: warehouse.dim_customer
-- ============================================

-- Step 1: Detect changes using hash comparison
CREATE TEMP TABLE customer_changes AS
WITH source AS (
  SELECT
    customer_id AS customer_natural_key,
    customer_name,
    email_domain,
    signup_date,
    customer_segment,
    acquisition_channel,
    country_code,
    state_province,
    city,
    postal_code,
    -- Hash of all tracked columns for change detection
    MD5(CONCAT(
      COALESCE(customer_name, ''),
      COALESCE(customer_segment, ''),
      COALESCE(country_code, ''),
      COALESCE(state_province, ''),
      COALESCE(city, ''),
      COALESCE(postal_code, '')
    )) AS row_hash
  FROM staging.stg_customers
),
target AS (
  SELECT
    customer_natural_key,
    MD5(CONCAT(
      COALESCE(customer_name, ''),
      COALESCE(customer_segment, ''),
      COALESCE(country_code, ''),
      COALESCE(state_province, ''),
      COALESCE(city, ''),
      COALESCE(postal_code, '')
    )) AS row_hash
  FROM warehouse.dim_customer
  WHERE is_current = TRUE
)
SELECT s.*
FROM source s
LEFT JOIN target t ON s.customer_natural_key = t.customer_natural_key
WHERE t.customer_natural_key IS NULL        -- New customers
   OR s.row_hash != t.row_hash;             -- Changed customers

-- Step 2: Close existing current rows for changed customers
UPDATE warehouse.dim_customer
SET effective_to = CURRENT_DATE - INTERVAL '1 day',
    is_current = FALSE,
    updated_at = CURRENT_TIMESTAMP
WHERE customer_natural_key IN (
  SELECT customer_natural_key FROM customer_changes
)
AND is_current = TRUE;

-- Step 3: Insert new versions
INSERT INTO warehouse.dim_customer (
  customer_sk, customer_natural_key, customer_name,
  email_domain, signup_date, customer_segment,
  acquisition_channel, country_code, state_province,
  city, postal_code, effective_from, effective_to,
  is_current, source_system, created_at, updated_at
)
SELECT
  -- Deterministic surrogate key
  ABS(FARM_FINGERPRINT(CONCAT(customer_natural_key, CAST(CURRENT_DATE AS STRING)))),
  customer_natural_key,
  customer_name,
  email_domain,
  signup_date,
  customer_segment,
  acquisition_channel,
  country_code,
  state_province,
  city,
  postal_code,
  CURRENT_DATE,           -- effective_from
  '9999-12-31',           -- effective_to
  TRUE,                   -- is_current
  'crm_system',           -- source_system
  CURRENT_TIMESTAMP,      -- created_at
  CURRENT_TIMESTAMP       -- updated_at
FROM customer_changes;

-- models/gold/fact_revenue.sql
-- dbt model with incremental materialization

{{
  config(
    materialized='incremental',
    partition_by={
      "field": "order_date",
      "data_type": "date",
      "granularity": "day"
    },
    cluster_by=["customer_key", "product_key"],
    unique_key="order_line_sk",
    incremental_strategy="merge"
  )
}}

WITH orders AS (
  SELECT * FROM {{ ref('stg_orders') }}
  {% if is_incremental() %}
  WHERE order_date >= DATE_SUB(
    (SELECT MAX(order_date) FROM {{ this }}),
    INTERVAL 3 DAY  -- Reprocess 3-day window for late arrivals
  )
  {% endif %}
),

customers AS (
  SELECT * FROM {{ ref('dim_customer') }}
  WHERE is_current = TRUE
),

products AS (
  SELECT * FROM {{ ref('dim_product') }}
  WHERE is_current = TRUE
)

SELECT
  {{ dbt_utils.generate_surrogate_key(['o.order_id', 'o.line_number']) }} AS order_line_sk,
  d.date_key AS order_date_key,
  o.order_date,
  c.customer_sk AS customer_key,
  p.product_sk AS product_key,
  o.order_number,
  o.line_number AS order_line_number,
  o.quantity,
  o.unit_price,
  o.quantity * o.unit_price AS gross_revenue,
  o.discount_amount,
  (o.quantity * o.unit_price) - o.discount_amount AS net_revenue,
  o.tax_amount,
  p.unit_cost * o.quantity AS cost_of_goods,
  ((o.quantity * o.unit_price) - o.discount_amount) - (p.unit_cost * o.quantity) AS gross_profit,
  CURRENT_TIMESTAMP() AS loaded_at

FROM orders o

Common Mistakes

  • Mixed grain in a single fact table

    Storing header-level and line-level data in the same table. Revenue gets double-counted when aggregating at the header level. Always declare grain explicitly and keep one grain per table.

  • Using natural keys for joins instead of surrogates

    Natural keys change (company merges, system migrations). Fact tables joined on natural keys break when source systems change. Surrogate keys insulate the warehouse from upstream volatility.

  • Over-normalizing the Gold layer

    Applying 3NF to analytical tables forces excessive joins that kill query performance. Analysts should never need more than 3-4 joins for a standard report. Denormalize for consumption.

  • No partition filter enforcement

    Without require_partition_filter = TRUE (BigQuery) or equivalent guardrails, a single SELECT * without a WHERE clause scans petabytes and costs thousands of dollars.

  • Treating all dimensions as SCD Type 2

    Not every change needs history. A customer's typo-corrected name doesn't warrant a new dimension row. Over-applying Type 2 bloats dimensions 10-50x and slows joins.

  • Ignoring late-arriving facts and dimensions

    Data arrives out of order. Without a strategy (placeholder rows, reprocessing windows, partition overwrite), late data either gets lost or corrupts existing aggregations.

  • No conformed dimensions

    Each team creates their own customer table with different keys and definitions. Cross-functional reporting becomes impossible. Invest in conformed dimensions early — they're the backbone of an enterprise warehouse.

  • Clustering on low-cardinality columns

    Clustering on a boolean or a column with 5 distinct values provides minimal benefit. Cluster on columns with thousands to millions of distinct values that appear frequently in WHERE clauses.

  • No data quality checks between layers

    Data flows from Bronze to Gold without validation. Null keys, orphan foreign keys, and duplicate rows propagate to dashboards. Implement checks (dbt tests, Great Expectations) at each layer boundary.

  • Building the warehouse before understanding the business process

    Starting with technology (let's use Snowflake!) instead of business requirements (what decisions does this warehouse support?). The Kimball approach starts with business processes, not tables.

Trade-offs

Normalization vs. Denormalization

Aspect Normalized (3NF/Snowflake) Denormalized (Star)
Query performance Slower — multiple joins required Faster — fewer, wider tables
Storage Less redundancy More redundancy (but storage is cheap)
ETL complexity More dependencies, ordering matters Simpler loads, parallel possible
Update anomalies Fewer — single point of truth More — must update multiple locations
Analyst productivity Lower — requires deep schema knowledge Higher — intuitive, self-service friendly
Modern engine optimization Less effective — join-heavy plans More effective — scan + filter optimized

Decision framework: Use normalized models in staging/silver for correctness. Use denormalized stars in gold/consumption for performance. The cost of storage is negligible compared to the cost of slow analyst queries at FAANG scale.

Query Performance vs. Storage

  • More materialized views = faster queries, more storage, more refresh compute, more staleness risk.
  • Fewer wide columns = less storage, but queries need more joins or post-processing.
  • Pre-computed aggregates = instant dashboards, but rigid (new dimensions require new aggregates).
  • Rule of thumb: If a query runs >100 times/day and scans >100 GB, materialize it. If it runs <5 times/day, the full scan is cheaper than maintaining the materialized view.

Freshness vs. Cost

Freshness Target Architecture Relative Cost
Real-time (<1 min) Streaming ingestion + incremental MVs $$$$$ (5x baseline)
Near real-time (1-15 min) Micro-batch + streaming buffer tables $$$ (3x baseline)
Hourly Scheduled batch + partition overwrite $$ (1.5x baseline)
Daily Nightly batch ETL $ (baseline)
Weekly/Monthly Scheduled aggregation jobs $ (0.5x baseline)

Decision framework: Start with daily freshness. Upgrade to near-real-time only for use cases that demonstrably lose business value with stale data (fraud detection, dynamic pricing, real-time personalization). Most dashboard consumers don't actually need real-time — they need "fresh enough to make today's decisions."

Build vs. Buy

  • Build (custom warehouse on Spark/Iceberg): Maximum flexibility, no vendor lock-in, but requires significant engineering investment (5-10 senior engineers minimum).
  • Buy (BigQuery/Snowflake/Redshift): Faster time-to-value, managed infrastructure, but vendor lock-in, less control over performance tuning, and potentially higher costs at extreme scale.
  • FAANG pattern: Most FAANG companies run custom internal systems (Mesa, Dremel, Hive) for core workloads but increasingly adopt managed services for satellite teams and new initiatives.

Follow-up Questions

Expect these follow-up questions in a FAANG interview after your initial answer:

Architecture & Modeling

  • "How would you handle a many-to-many relationship between customers and accounts in a star schema?" (Bridge table with weighting factors)
  • "Your fact table has 200 columns. How do you decide which columns become dimensions vs. degenerate dimensions vs. junk dimensions?" (Cardinality analysis, query patterns, business meaning)
  • "How do you model a business process that has multiple simultaneous grains — e.g., a shipment with header, line item, and package levels?" (Separate fact tables per grain, linked by degenerate dimensions)
  • "Walk me through how you'd migrate from a monolithic fact table to a medallion architecture without downtime." (Shadow pipeline, dual-write period, consumer migration waves)

Scale & Performance

  • "Your 50 TB fact table has a hot partition (today's data) that receives 1M inserts/minute. How do you prevent it from degrading query performance?" (Streaming buffer, separate hot/cold tables, merge on schedule)
  • "How would you design the warehouse to support both low-latency dashboard queries (<2s) and heavy ad-hoc analytical queries (minutes)?" (Workload isolation: separate compute/warehouses, priority queues, materialized views for dashboards)
  • "Your clustering is degrading over time due to heavy DML. What's your maintenance strategy?" (Scheduled reclustering, partition compaction, monitoring clustering depth)

Operations & Cost

  • "A business user wants to add a new dimension to an existing fact table with 3 years of history. Walk me through the process." (Backfill strategy, partition-by-partition update, validation, consumer communication)
  • "How do you handle schema evolution when upstream sources add/remove columns?" (Schema registry, backward/forward compatibility, column deprecation policy)
  • "Your warehouse costs doubled last quarter. Walk me through your investigation and remediation process." (Query audit logs, bytes scanned analysis, user attribution, materialization candidates, partition enforcement)
  • "How would you implement row-level security in a shared warehouse serving multiple business units?" (Column/row-level policies, authorized views, tag-based access control)

Advanced Topics

  • "Compare Kimball dimensional modeling vs. Data Vault 2.0 for a large enterprise. When would you choose each?" (Kimball for analytics-first, DV2 for integration-first with many sources and audit requirements)
  • "How would you implement a universal semantic layer that serves both SQL analysts and ML engineers from the same warehouse?" (Feature store integration, metric layer, shared definitions, multiple consumption interfaces)
  • "Describe how you'd handle a warehouse migration from on-prem (Teradata/Netezza) to cloud (BigQuery/Snowflake) for a 500 TB warehouse." (Phased migration, dual-run validation, lift-and-shift then optimize, workload comparison testing)

Summary

Designing a warehouse for petabyte-scale analytics requires mastery across three domains:

Logical Design

  • Star schemas with clearly defined grain per fact table remain the gold standard for analytical performance.
  • Conformed dimensions enable enterprise-wide consistency; SCD Type 2 preserves history for critical business attributes.
  • Choose fact table types deliberately: transactional for events, periodic snapshot for state, accumulating for lifecycle processes.

Physical Design

  • Partition on time (95% of cases); cluster on high-cardinality filter columns; enforce partition filters to prevent cost disasters.
  • Materialized views and aggregation tables trade storage for performance — measure ROI continuously.
  • Compression, columnar formats, and sort order compound to reduce storage and scan costs 10-100x.

Operational Design

  • Medallion architecture (Bronze/Silver/Gold) provides clear data quality progression — apply it where complexity warrants the overhead.
  • Cost governance requires multi-layered controls: partition enforcement, query budgets, resource monitors, and chargeback visibility.
  • Schema evolution, late-arriving data, and dimension versioning are ongoing operational challenges that need automated solutions.

The senior-level signal: You don't just know these patterns — you can articulate when each is appropriate, what trade-offs it introduces, and how you've operated it at scale in production. The best answer demonstrates that you've felt the pain of petabyte-scale data and developed judgment about which optimizations matter most for the specific business context.

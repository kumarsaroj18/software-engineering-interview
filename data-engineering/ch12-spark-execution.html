Spark Execution

Explain how Spark executes a job.

DAG Catalyst

Interviewer Intent

When an interviewer asks "Explain how Spark executes a job," they are probing for:

  • End-to-end execution understanding — Can you trace the full lifecycle from user code submission through DAG construction, optimization, physical planning, stage splitting, task scheduling, and result collection?
  • Optimizer fluency — Do you understand Catalyst's four-phase pipeline and how logical plans become physical plans with concrete join strategies and scan operators?
  • Distributed systems reasoning — Can you explain shuffle mechanics, fault tolerance via lineage, speculative execution, and why wide dependencies create stage boundaries?
  • Performance intuition — Do you know how Tungsten's memory management, whole-stage code generation, and Adaptive Query Execution eliminate bottlenecks at scale?
  • Production debugging skills — Have you used the Spark UI to diagnose skew, spill, GC pressure, and stragglers? Can you relate executor metrics to root causes?
  • Join strategy knowledge — Can you articulate when Spark chooses BroadcastHashJoin vs SortMergeJoin, the thresholds involved, and how AQE can switch strategies at runtime?
  • Operational maturity — Have you dealt with real production incidents involving OOM, data skew, shuffle service failures, or driver bottlenecks?

This question separates candidates who merely call df.write.parquet() from those who can architect, tune, and troubleshoot petabyte-scale Spark pipelines — the caliber expected at FAANG for senior data engineering roles.

Quick Answer (60-Second Version)

When you call an action (e.g., .count(), .write), Spark's driver constructs a DAG of transformations from your lazy DataFrame/RDD operations. The Catalyst optimizer converts this logical plan through four phases — analysis, logical optimization, physical planning, and code generation — producing an optimized physical plan. The DAG scheduler splits the physical plan at shuffle boundaries (wide dependencies) into stages, where each stage contains tasks equal to the number of input partitions. The task scheduler dispatches tasks to executors across the cluster, respecting data locality. Executors run tasks using Tungsten's off-heap memory manager and whole-stage code generation for CPU efficiency. Intermediate shuffle data is written to local disk, read by downstream stages, and if any task fails, Spark recomputes it from its lineage (the DAG) rather than replaying logs. Adaptive Query Execution (AQE) further refines this at runtime by coalescing partitions, switching join strategies, and handling skew based on actual shuffle statistics.

The Driver

The driver is the JVM process that runs your main() function. Its responsibilities include:

  • SparkSession creation — Initializes the SparkContext, which establishes a connection to the cluster manager and negotiates executor resources.
  • Logical plan construction — Converts your DataFrame/SQL operations into an unresolved logical plan (a tree of relational operators).
  • Optimization — Runs the Catalyst optimizer pipeline to produce an optimized physical plan.
  • DAG scheduling — Splits the physical plan into stages at shuffle boundaries and computes task locality preferences.
  • Task dispatch — Sends serialized task closures to executors via the scheduler backend.
  • Result aggregation — Collects results from executors (e.g., for .collect(), .count()).
  • Metadata tracking — Maintains the web UI, event log, and accumulator updates.

Executors

Executors are long-running JVM processes on worker nodes. Each executor:

  • Runs multiple task threads concurrently (controlled by spark.executor.cores).
  • Manages a Block Manager that caches RDD partitions in memory or disk.
  • Writes shuffle output to local disk for consumption by other executors.
  • Reports heartbeats and task metrics back to the driver every 10 seconds.
  • Has a fixed memory pool split between execution (shuffles, joins, sorts) and storage (cached data).

DAG & Lazy Evaluation

Transformations vs Actions

Spark operations fall into two categories:

Category Behavior Examples
Transformations Lazy — define a new RDD/DataFrame but don't compute anything filter, map, select, join, groupBy, withColumn
Actions Eager — trigger actual computation and return results count, collect, write, show, take, foreach

Why Lazy Evaluation?

Laziness is not a limitation — it's a deliberate design choice that enables:

  • Optimization opportunity — Catalyst sees the entire computation graph before executing, enabling predicate pushdown, projection pruning, and join reordering that would be impossible with eager evaluation.
  • Pipelining — Multiple narrow transformations can be fused into a single pass over the data (no intermediate materialization).
  • Reduced I/O — Filters pushed before expensive operations eliminate unnecessary data reads.
  • Fault tolerance — The lineage DAG serves as the recovery plan; Spark never needs write-ahead logs for intermediate results.

The Lineage Graph (DAG)

Every transformation creates a new node in the Directed Acyclic Graph. Each node records:

  • The parent RDD(s) it depends on
  • The function to compute this RDD from its parents
  • Partitioning metadata (how many partitions, what partitioner)
  • Preferred locations for data locality
# Example: building a DAG (nothing executes until .count())
raw = spark.read.parquet("s3://data-lake/events/")      # Scan node
filtered = raw.filter(col("event_date") >= "2024-01-01") # Filter node
projected = filtered.select("user_id", "event_type")     # Project node
grouped = projected.groupBy("event_type").count()        # Aggregate node

# This triggers execution — the entire DAG runs
result = grouped.count()  # Action!

Narrow vs Wide Dependencies

Dependency Type Definition Examples Impact
Narrow Each parent partition maps to at most one child partition map, filter, union, coalesce Can pipeline; no shuffle needed
Wide Each parent partition may contribute to multiple child partitions groupBy, join, repartition, distinct Requires shuffle; creates stage boundary

DAG Construction Walkthrough

# Real-world ETL example showing DAG structure
orders = spark.read.parquet("s3://warehouse/orders/")
customers = spark.read.parquet("s3://warehouse/customers/")

# Stage 1: Narrow transformations (pipelined)
recent_orders = orders \
    .filter(col("order_date") >= "2024-01-01") \
    .select("order_id", "customer_id", "amount", "order_date")

# Stage 1 (continued): Narrow transformations on second input
active_customers = customers \
    .filter(col("status") == "active") \
    .select("customer_id", "customer_name", "segment")

# SHUFFLE BOUNDARY — creates Stage 2
joined = recent_orders.join(
    active_customers,
    on="customer_id",
    how="inner"
)

# Stage 2 (continued): Narrow transformation after join
enriched = joined.withColumn(
    "amount_bucket",
    when(col("amount") > 1000, "high")
    .when(col("amount") > 100, "medium")
    .otherwise("low")
)

# SHUFFLE BOUNDARY — creates Stage 3
summary = enriched.groupBy("segment", "amount_bucket") \
    .agg(
        count("order_id").alias("order_count"),
        sum("amount").alias("total_amount")
    )

# ACTION triggers execution of all 3 stages
summary.write.parquet("s3://warehouse/segment_summary/")

Catalyst Optimizer

Overview

Catalyst is Spark SQL's extensible query optimizer, built on Scala's pattern matching and functional programming. It transforms your DataFrame/SQL operations through four phases to produce highly optimized JVM bytecode:

┌────────────────┐    ┌────────────────────┐    ┌─────────────────┐    ┌───────────────┐
│   ANALYSIS     │───▶│ LOGICAL            │───▶│   PHYSICAL      │───▶│    CODE       │
│                │    │ OPTIMIZATION       │    │   PLANNING      │    │  GENERATION   │
│ Resolve refs,  │    │ Predicate pushdown │    │ Choose join     │    │ Whole-stage   │
│ type checking, │    │ Constant folding,  │    │ strategies,     │    │ codegen,      │
│ catalog lookup │    │ Column pruning,    │    │ cost-based      │    │ Janino        │
│                │    │ Simplify exprs     │    │ selection       │    │ compilation   │
└────────────────┘    └────────────────────┘    └─────────────────┘    └───────────────┘
  Unresolved Plan       Optimized Logical          Physical Plan         Generated Java
                             Plan                (with strategies)          Bytecode

Phase 1: Analysis

The analyzer resolves references using the catalog (Hive metastore, Unity Catalog, or in-memory catalog):

  • Attribute resolution — Maps column names to specific input relations.
  • Relation resolution — Looks up table/view definitions in the catalog.
  • Type coercion — Inserts implicit casts (e.g., comparing INT with BIGINT).
  • Function resolution — Resolves function names to implementations (built-in or UDF).
  • Star expansion — Expands SELECT * to explicit column references.
-- Before analysis: unresolved
SELECT t.* FROM events t WHERE t.ts > '2024-01-01'

-- After analysis: resolved with types
Project [event_id#12L, user_id#13, event_type#14, ts#15]
  Filter (cast(ts#15 as date) > 2024-01-01)
    UnresolvedRelation [events]  →  Relation[event_id#12L, user_id#13, ...] parquet

Phase 2: Logical Optimization

Catalyst applies rule-based optimizations in multiple passes (a fixed-point computation). Key rules include:

Rule What It Does Impact
Predicate Pushdown Moves filters below joins/aggregations, closer to data sources Reduces data read from storage by orders of magnitude
Column Pruning Drops columns not needed by downstream operators Reduces I/O and memory pressure in columnar formats
Constant Folding Evaluates constant expressions at plan time Eliminates runtime computation (e.g., 1 + 1 → 2)
Boolean Simplification Simplifies true AND x → x, false OR x → x Reduces expression evaluation overhead
Combine Filters Merges adjacent Filter nodes into one Reduces plan tree depth
Null Propagation Short-circuits expressions that always produce NULL Eliminates dead computation paths
Subquery Elimination Rewrites correlated subqueries as joins Enables parallel execution of formerly sequential plans 
# Example: Catalyst pushes filter below join
df = orders.join(customers, "customer_id") \
    .filter(col("order_date") >= "2024-01-01") \
    .select("order_id", "customer_name")

# Physical plan shows filter pushed to orders scan:
# == Physical Plan ==
# *(2) Project [order_id, customer_name]
# +- *(2) BroadcastHashJoin [customer_id], [customer_id]
#    :- *(1) Filter (order_date >= 2024-01-01)    ← PUSHED DOWN
#    :  +- *(1) ColumnarToRow
#    :     +- FileScan parquet [order_id, customer_id, order_date]
#    :        PushedFilters: [GreaterThanOrEqual(order_date, 2024-01-01)]
#    +- BroadcastExchange
#       +- *(3) Project [customer_id, customer_name]
#          +- *(3) FileScan parquet [customer_id, customer_name]

Phase 3: Physical Planning

The physical planner converts the optimized logical plan into one or more physical plans, then selects the best using a cost model:

  • Join strategy selection — Chooses between BroadcastHashJoin, SortMergeJoin, ShuffledHashJoin based on table sizes and spark.sql.autoBroadcastJoinThreshold (default 10 MB).
  • Aggregation strategy — Partial aggregation (map-side combine) vs full shuffle aggregation.
  • Sort implementation — In-memory sort vs external sort based on data size vs available memory.
  • Scan planning — Chooses between file scan, bucket scan, or cached data scan.
  • Partition pruning — Static pruning at plan time or dynamic pruning at runtime (DPP).

Phase 4: Code Generation

Spark uses whole-stage code generation (WholeStageCodegen) to compile entire query stages into single Java functions:

  • Traditional volcano model — Each operator calls next() on its child, producing one row at a time. This causes virtual function dispatch overhead and poor CPU cache utilization.
  • Whole-stage codegen — Fuses operators within a stage into a single tight loop that processes rows without virtual calls. Uses the Janino compiler to produce bytecode at runtime.

Tungsten Engine

Motivation

Before Tungsten (pre-Spark 1.4), Spark stored data as Java objects on the JVM heap. This caused:

  • Memory overhead — A Java String "hello" occupies ~56 bytes (vs 5 bytes raw). Object headers, padding, and pointer chasing waste 2–5× memory.
  • GC pressure — Billions of short-lived objects trigger long GC pauses that stall all executor threads.
  • Cache misses — Pointer-heavy object graphs scatter data across the heap, defeating CPU L1/L2/L3 cache prefetching.
  • Serialization cost — Shuffles required full Java serialization/deserialization of each object.

Tungsten addresses all four problems with a custom memory management and execution backend.

Off-Heap Memory Management

Tungsten allocates memory outside the JVM heap using sun.misc.Unsafe (or java.nio.DirectByteBuffer):

  • Explicit allocation and deallocation — no GC involvement.
  • Memory pages managed by Spark's TaskMemoryManager per task.
  • Memory is accounted precisely, enabling graceful spill-to-disk when limits are reached.
  • Configurable via spark.memory.offHeap.enabled=true and spark.memory.offHeap.size.

Binary Storage Format (UnsafeRow)

Tungsten stores rows in a compact binary format called UnsafeRow:

UnsafeRow Layout (example: 3 columns — INT, STRING, DOUBLE):

┌───────────────┬────────────────────────────────┬───────────────────┐
│ Null Bitmap   │ Fixed-width values region       │ Variable-length   │
│ (1 bit/field) │ (8 bytes per field)             │ data region       │
├───────────────┼────────────────────────────────┼───────────────────┤
│ 0b000         │ [42][offset+len][3.14159...]    │ ["hello"]         │
│ (3 bits)      │ INT   STRING ref   DOUBLE       │                   │
└───────────────┴────────────────────────────────┴───────────────────┘

Benefits:
- Fixed offsets for O(1) field access (no deserialization needed)
- Contiguous memory layout for CPU cache-friendly access
- Direct binary comparison for sort operations
- No object creation — operates directly on byte arrays

Cache-Friendly Data Structures

Tungsten's data structures are designed for modern CPU architectures:

  • Cache-conscious hash maps — Open-addressing hash tables with linear probing store keys/values in contiguous memory, maximizing L1/L2 cache hits during hash joins.
  • Pointer-free sorting — Sort operations compare binary key prefixes inline (no pointer dereference), falling back to full comparison only on prefix collision.
  • Sequential memory access — Scan operations iterate over contiguous byte arrays rather than chasing pointers across the heap.

Whole-Stage Code Generation

WholeStageCodegen eliminates the iterator model overhead by generating a single Java method for an entire pipeline stage:

Traditional Volcano Model (per-row virtual dispatch):

  Aggregate.next()
    → Project.next()
      → Filter.next()
        → Scan.next()
          → return Row(...)
        → if predicate(row): return row
      → return project(row)
    → update aggregate(row)

≈ 4 virtual method calls per row × 1 billion rows = catastrophic overhead

Whole-Stage Codegen (tight loop):

  while (scan.hasNext()) {
    row = scan.next();
    if (row.getInt(3) >= 20240101) {           // filter inlined
      long key = row.getLong(0);                // project inlined
      aggregateBuffer.update(key, row.getDouble(2));  // agg inlined
    }
  }

≈ 0 virtual calls, CPU branch prediction friendly, vectorization-ready

Tungsten Sort

For shuffle operations, Tungsten sort uses a specialized algorithm:

  • Records stored in serialized binary form (no deserialization during sort).
  • Sort key prefix (8 bytes) stored alongside pointer in a compact array.
  • Comparison uses prefix first (cache-friendly), full record only on tie.
  • External merge sort with efficient spill-to-disk when memory is exhausted.
  • Enabled by default via spark.shuffle.manager=sort (only option since Spark 2.0).

Jobs, Stages, Tasks

The Execution Hierarchy

Application (one SparkSession)
  └── Job 1 (triggered by action: .write())
  │     └── Stage 0 (ResultStage)
  │     │     └── Task 0.0 (partition 0)
  │     │     └── Task 0.1 (partition 1)
  │     │     └── ... Task 0.N
  │     └── Stage 1 (ShuffleMapStage)
  │           └── Task 1.0 (partition 0)
  │           └── Task 1.1 (partition 1)
  │           └── ... Task 1.M
  └── Job 2 (triggered by action: .count())
        └── Stage 2 ...

Jobs

Every action triggers exactly one job. A single application can have many jobs (e.g., a notebook with multiple .show() or .write() calls):

# This creates 3 jobs:
df = spark.read.parquet("s3://data/events/")
df.cache()          # Job 0: materialize cache
df.count()          # Job 1: count action
df.write.parquet("s3://output/")  # Job 2: write action

Stages

The DAG scheduler splits each job into stages at shuffle boundaries (wide dependencies). Within a stage, all transformations have narrow dependencies and can be pipelined:

  • ShuffleMapStage — Produces shuffle output (map side of a shuffle). Its tasks write shuffle files to local disk.
  • ResultStage — The final stage that produces the action's result (e.g., collected rows, written files).
# How many stages? Count the shuffle boundaries + 1
orders = spark.read.parquet("...")          # ─┐
  .filter(col("date") >= "2024-01-01")     #  │ Stage 0
  .select("order_id", "customer_id", "amt")# ─┘

customers = spark.read.parquet("...")       # ─┐
  .filter(col("active") == True)           #  │ Stage 1
  .select("customer_id", "name")           # ─┘

joined = orders.join(customers, "customer_id")  # SHUFFLE → Stage 2

result = joined.groupBy("name") \
    .agg(sum("amt"))                       # SHUFFLE → Stage 3

result.write.parquet("...")                # Action triggers all stages

# Total: 4 stages (2 scan stages + join stage + aggregation stage)

Tasks

Each stage is divided into tasks — the smallest unit of work. The number of tasks equals the number of input partitions for that stage:

Stage Type Number of Tasks Determined By
Scan stage Number of input file splits File size ÷ spark.sql.files.maxPartitionBytes (128 MB default)
Shuffle read stage spark.sql.shuffle.partitions Default 200; tune to cluster cores × 2–3
Repartitioned stage Specified partition count User-specified via .repartition(N)

Task Lifecycle

1. DAG Scheduler creates TaskSet for the stage
2. Task Scheduler assigns tasks to executors (respecting locality)
3. Driver serializes task closure (function + partition info)
4. Executor deserializes task and creates a TaskRunner thread
5. TaskRunner executes the generated code on its partition
6. For ShuffleMapStage: writes shuffle output to local disk
   For ResultStage: sends results back to driver
7. Executor reports task completion + metrics to driver
8. DAG Scheduler marks stage complete when all tasks succeed

Task Scheduling and Locality

Spark prefers to schedule tasks where data already resides:

Locality Level Description Wait Time
PROCESS_LOCAL Data is in the executor's memory (cached RDD) Immediate
NODE_LOCAL Data is on the same node (HDFS block, local shuffle file) 3s default
RACK_LOCAL Data is on a node in the same rack 3s default
ANY Data must be fetched from a remote node Fallback

Configure locality wait via spark.locality.wait (default 3s). For clusters with fast networks (cloud), reducing this to 0–1s can improve overall throughput by avoiding idle executors waiting for locality.

Shuffle Deep Dive

What is a Shuffle?

A shuffle is the mechanism Spark uses to redistribute data across partitions when a wide dependency requires each output partition to read from multiple input partitions. It is the most expensive operation in Spark — involving disk I/O, network transfer, and serialization/deserialization.

Shuffle Operation (groupBy example):

STAGE 1 (Map Side / Shuffle Write)          STAGE 2 (Reduce Side / Shuffle Read)
┌─────────────┐                             ┌─────────────┐
│ Partition 0  │──── key A ────────────────▶│ Partition 0  │ (all key A rows)
│ [A,B,C,A,B] │──── key B ─────────┐       │             │

Shuffle Write (Map Side)

Each map task produces shuffle output by:

  1. Partitioning — Computes the target partition for each record using the partitioner (hash or range).
  2. Sorting — Sorts records by (partition_id, optional_key) within an in-memory buffer.
  3. Spilling — When the buffer exceeds spark.shuffle.spill.initialMemoryThreshold, spills sorted runs to disk.
  4. Merging — Merges all spill files + remaining in-memory data into final shuffle files.
  5. Writing — Produces one data file + one index file per map task (consolidated format since Spark 1.4).
Shuffle File Layout (per map task):

shuffle_0_0_0.data     ← Concatenated sorted records for all reduce partitions
shuffle_0_0_0.index    ← Byte offsets for each reduce partition's data

Index file enables reduce tasks to seek directly to their portion
without reading the entire file.

Shuffle Read (Reduce Side)

Each reduce task:

  1. Fetches its partition's data from all map tasks (via BlockTransferService over Netty).
  2. Buffers fetched blocks in memory (controlled by spark.reducer.maxSizeInFlight, default 48 MB).
  3. Merges sorted blocks if sort-based aggregation is required.
  4. Processes the merged stream through downstream operators.

Remote fetches happen in parallel (5 concurrent requests per reduce task by default, controlled by spark.reducer.maxReqsInFlight).

Sort-Based Shuffle (Default)

Since Spark 2.0, the only shuffle implementation is sort-based shuffle (SortShuffleManager):

  • All records sorted by partition ID in a single pass.
  • One output file per map task (regardless of reduce partition count) — eliminates the N×M file explosion of the old hash-based shuffle.
  • Index file allows random access to any partition's data.
  • For aggregation operations (like reduceByKey), a map-side combine is performed during the sort.

Tungsten Sort Optimization

When conditions are met, Spark uses Tungsten's unsafe sort:

  • Requirements: No aggregation, no ordering required within partitions, serialized record size fits in a page.
  • Mechanism: Stores serialized records in off-heap pages. Sort operates on 8-byte pointers (partition_id + page_offset) — never deserializes records.
  • Benefit: 3–5× faster sort for large shuffles due to cache-efficient memory access and zero deserialization.

Join Strategies in Spark

Overview of Join Strategies

Spark's physical planner selects from five join implementations based on data characteristics:

Strategy Mechanism When Chosen Shuffle Required?
BroadcastHashJoin (BHJ) Small table broadcast to all executors; hash table probed by large table One side ≤ autoBroadcastJoinThreshold (10 MB) No shuffle for broadcast side
ShuffledHashJoin (SHJ) Both sides shuffled by join key; smaller side built as hash table One side fits in memory per partition; preferSortMergeJoin=false Yes (both sides)
SortMergeJoin (SMJ) Both sides shuffled and sorted by join key; merge-join scan Default for large-large equi-joins Yes (both sides)
BroadcastNestedLoopJoin (BNLJ) Broadcast small side; nested loop comparison Non-equi joins when one side is small No shuffle for broadcast side
CartesianProduct Full cross join Cross joins or non-equi joins where neither side is broadcastable Depends

BroadcastHashJoin (BHJ)

The fastest join strategy — eliminates shuffle entirely for one side:

# Automatic: Spark broadcasts tables ≤ 10 MB by default
small_df = spark.read.parquet("s3://data/dim_countries/")  # 2 MB
large_df = spark.read.parquet("s3://data/fact_events/")    # 500 GB

# Spark auto-selects BroadcastHashJoin
joined = large_df.join(small_df, "country_id")

# Force broadcast with hint (override size threshold)
from pyspark.sql.functions import broadcast

joined = large_df.join(broadcast(small_df), "country_id")

# Adjust threshold
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "50m")  # 50 MB
BroadcastHashJoin Execution:

1. Driver collects small DataFrame to driver memory
2. Driver broadcasts serialized hash table to all executors
3. Each executor stores broadcast in BlockManager (memory)
4. Large side tasks probe the hash table — NO SHUFFLE of large side

   Executor 1: [Large partition 0] ──probe──▶ [Broadcast HashTable]
   Executor 2: [Large partition 1] ──probe──▶ [Broadcast HashTable]
   Executor 3: [Large partition 2] ──probe──▶ [Broadcast HashTable]

SortMergeJoin (SMJ)

The default strategy for joining two large tables:

SortMergeJoin Execution:

Phase 1: Shuffle both sides by join key
  Orders (500 GB) ──shuffle by customer_id──▶ 200 partitions
  Customers (50 GB) ──shuffle by customer_id──▶ 200 partitions

Phase 2: Sort each partition by join key
  Partition 42 of Orders:   [cust_1, cust_1, cust_3, cust_5, ...]
  Partition 42 of Customers: [cust_1, cust_2, cust_3, cust_4, cust_5, ...]

Phase 3: Merge-join (single pass, both sorted)
  Two pointers advance through sorted streams
  O(N + M) per partition — highly efficient for large datasets

ShuffledHashJoin (SHJ)

An alternative when one side is moderately small (fits in memory per partition) but too large to broadcast:

# ShuffledHashJoin: both sides shuffled, smaller builds hash table
# Faster than SMJ when skipping sort is possible
# Requires: spark.sql.join.preferSortMergeJoin = false

spark.conf.set("spark.sql.join.preferSortMergeJoin", "false")

# SHJ chosen when one side per-partition size fits in memory
# Avoids sort overhead but requires more memory than SMJ

Join Strategy Selection Rules

Decision Tree (simplified):

1. Is it an equi-join?
   ├── YES:
   │   ├── Is one side ≤ broadcast threshold (or has broadcast hint)?
   │   │   └── YES → BroadcastHashJoin
   │   │   └── NO → Continue...
   │   ├── Is preferSortMergeJoin = false AND one side fits in memory?
   │   │   └── YES → ShuffledHashJoin
   │   │   └── NO → SortMergeJoin (default)
   │
   └── NO (non-equi join):
       ├── Is one side ≤ broadcast threshold?
       │   └── YES → BroadcastNestedLoopJoin
       │   └── NO → CartesianProduct (expensive!)

Join Performance Comparison

Strategy Time Complexity Network Cost Memory Requirement Best For
BHJ O(N) per partition Broadcast only Small table fits in executor memory Dimension-fact joins
SMJ O(N log N + M log M) Full shuffle both sides Spill-friendly (streaming merge) Large-large joins
SHJ O(N + M) Full shuffle both sides Smaller side per-partition in memory Medium-large joins
BNLJ O(N × M) Broadcast only Small table in memory Non-equi joins, small tables

    .bucketBy(256, "customer_id") \
    .sortBy("customer_id") \
    .saveAsTable("orders_bucketed")

    .bucketBy(256, "customer_id") \

customers_b = spark.table("customers_bucketed")
joined = orders_b.join(customers_b, "customer_id")  # Direct SortMergeJoin, 0 shuffle

Adaptive Query Execution (AQE)

Why AQE?

Static query optimization has fundamental limitations:

  • Stale statistics — Table stats collected at ANALYZE time may not reflect current data distribution.
  • Cardinality estimation errors — Complex predicates, UDFs, and correlated columns make accurate estimation nearly impossible.
  • Runtime data characteristics — Actual shuffle partition sizes and skew patterns are unknowable at plan time.

AQE (enabled by default in Spark 3.2+) addresses these by re-optimizing the query plan between stages, using actual runtime statistics from completed shuffle map stages.

# Enable AQE (default true since Spark 3.2)
spark.conf.set("spark.sql.adaptive.enabled", "true")

# Individual features
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.localShuffleReader.enabled", "true")

Feature 1: Coalesce Shuffle Partitions

Problem: You set spark.sql.shuffle.partitions=200 for large stages, but smaller stages produce many tiny partitions (e.g., after a selective filter). Tiny tasks have more scheduling overhead than computation time.

Before AQE coalescing (200 partitions, many tiny):
  Partition sizes: [2MB, 1MB, 3MB, 0.5MB, 2MB, 1MB, ...]
  → 200 tasks, many finish in milliseconds (scheduling overhead dominates)

After AQE coalescing:
  Adjacent small partitions merged: [64MB, 64MB, 64MB, 58MB, ...]
  → 8 tasks, each with meaningful work

Controlled by:
  spark.sql.adaptive.advisoryPartitionSizeInBytes = 64MB (target size)
  spark.sql.adaptive.coalescePartitions.minPartitionSize = 1MB

Feature 2: Dynamic Join Strategy Switch

Problem: At plan time, Spark estimates a table at 500 MB (too large to broadcast). After filters execute, the actual shuffle output is only 8 MB — small enough for BroadcastHashJoin.

Original plan (based on statistics):
  SortMergeJoin (both sides estimated > 10 MB)
    ├── Shuffle (orders filtered)  [estimated: 500 MB]
    └── Shuffle (customers)        [estimated: 50 MB]

After Stage 0 completes, AQE observes:
  Actual orders filtered size: 8 MB (selective filter eliminated most data)

AQE re-plans:
  BroadcastHashJoin (orders now small enough to broadcast)
    ├── Broadcast (orders filtered)  [actual: 8 MB] ← converted!
    └── Local shuffle read (customers)

Result: Eliminates shuffle for customers side, massive speedup!

Feature 3: Skew Join Optimization

Problem: A single partition has 100× the data of others, creating a straggler task that dominates stage runtime.

Before AQE skew handling:
  Partition sizes: [50MB, 45MB, 52MB, 48MB, 5000MB, 47MB, ...]
                                                ↑ SKEWED (100× median)
  Stage runtime = time of slowest task ≈ runtime of 5 GB partition

After AQE skew handling:
  1. Detects partition 4 is skewed (size > median × skewedPartitionFactor)
  2. Splits partition 4 into ~100 sub-partitions of 50 MB each
  3. Replicates the matching partition from the other join side
  4. Runs 100 parallel tasks instead of 1 straggler

  Partition 4 → [50MB, 50MB, 50MB, ... × 100] (each paired with replicated data)

Controlled by:
  spark.sql.adaptive.skewJoin.skewedPartitionFactor = 5 (default)
  spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes = 256MB

df.explain(mode="formatted")

# Look for:
# AdaptiveSparkPlan isFinalPlan=true
#   +- CustomShuffleReader coalesced    ← partition coalescing active
#   +- BroadcastHashJoin               ← dynamically switched from SMJ
#   +- SkewedJoin                      ← skew optimization active

Feature 4: Dynamic Partition Pruning (DPP)

Although technically separate from AQE, DPP works at runtime to prune partitions of fact tables based on the result of dimension table filters:

-- DPP Example: prune fact table partitions at runtime
SELECT f.*
FROM fact_sales f
JOIN dim_date d ON f.date_key = d.date_key
WHERE d.year = 2024

-- Without DPP: Scan all date partitions of fact_sales, then filter
-- With DPP: Execute dim_date filter first, broadcast matching date_keys,
--           then scan ONLY fact_sales partitions matching year=2024

Fault Tolerance

Lineage-Based Recovery

Unlike traditional databases that use write-ahead logs (WAL), Spark achieves fault tolerance through the DAG lineage. If a partition is lost (executor crash, disk failure), Spark recomputes only the lost partition from its parent partitions:

Lineage-based recovery:

Original execution:
  [Scan part 0] → [Filter] → [Map] → [Result part 0] ✓
  [Scan part 1] → [Filter] → [Map] → [Result part 1] ✓
  [Scan part 2] → [Filter] → [Map] → [Result part 2] ✗ (executor crashed)

Recovery:
  [Scan part 2] → [Filter] → [Map] → [Result part 2] ✓ (recomputed on new executor)

Key insight: Only partition 2 is recomputed.
Partitions 0 and 1 are untouched — no global rollback.

Task-Level Retry

Individual task failures are retried before failing the entire stage:

  • Max attempts: spark.task.maxFailures (default 4) — task retried up to 4 times.
  • Failure causes: OOM, fetch failure, JVM crash, killed by YARN.
  • Relaunch location: Failed task may be relaunched on a different executor (blacklisting the failed one).
  • Speculative execution: If enabled (spark.speculation=true), Spark launches duplicate tasks for slow-running (straggler) tasks and takes the first result.
# Task retry configuration
spark.conf.set("spark.task.maxFailures", "4")        # Retry 3 times (4 attempts total)
spark.conf.set("spark.task.reaper.enabled", "true")  # Kill zombie tasks

# Speculative execution (useful for stragglers)
spark.conf.set("spark.speculation", "true")
spark.conf.set("spark.speculation.multiplier", "1.5")    # 1.5× median runtime
spark.conf.set("spark.speculation.quantile", "0.75")     # After 75% tasks complete

# Executor blacklisting (avoid repeatedly failing executors)
spark.conf.set("spark.excludeOnFailure.enabled", "true")
spark.conf.set("spark.excludeOnFailure.task.maxTaskAttemptsPerExecutor", "2")

Stage-Level Retry

If a reduce task cannot fetch shuffle data (because the map-side executor died and its shuffle files are lost), Spark retries the entire parent stage:

FetchFailedException scenario:

1. Stage 0 (ShuffleMapStage) completes — shuffle files on executors A, B, C
2. Executor B crashes (loses its shuffle files)
3. Stage 1 tasks try to fetch from B → FetchFailedException
4. DAG Scheduler resubmits Stage 0 (only the tasks that were on B)
5. New executor D re-runs those map tasks, produces new shuffle files
6. Stage 1 retries fetch from D → succeeds

Controlled by:
  spark.stage.maxConsecutiveAttempts = 4 (default)

Mitigation: Enable External Shuffle Service to decouple shuffle file
lifecycle from executor lifecycle.

Checkpointing

For very long lineage chains (iterative algorithms), recomputation from the start is expensive. Checkpointing materializes an RDD to reliable storage (HDFS/S3), truncating the lineage:

# Set checkpoint directory (must be reliable distributed storage)
spark.sparkContext.setCheckpointDir("s3://checkpoints/app-001/")

# Checkpoint an RDD/DataFrame to truncate lineage
df_iteration_100 = run_iteration(df_iteration_99)
df_iteration_100.checkpoint()  # Materializes to S3, clears lineage

# Use cases:
# - Iterative ML algorithms (PageRank, gradient descent)
# - Very long ETL pipelines with 50+ stages
# - Streaming state stores

# Two types:
# 1. Reliable checkpoint — writes to distributed storage (survives driver failure)
# 2. Local checkpoint — writes to executor local storage (faster, less durable)
df.localCheckpoint()  # Faster but lost if executor dies

Driver Failure Recovery

The driver is a single point of failure. If it crashes:

  • Without external orchestration — Application is lost. Executors are terminated by the cluster manager.
  • With cluster mode — YARN/K8s can restart the driver (but application state is lost).
  • Structured Streaming — Recoverable from checkpoint directory. Re-reads offsets and re-processes from last committed batch.
  • Best practice — Run long-lived streaming apps in cluster mode with automatic restart policies.

Production Incident: OOM from Skewed Shuffle Partition

Scenario

A daily ETL pipeline joining user events with a device dimension table started failing with java.lang.OutOfMemoryError: Java heap space on 3 of 200 executors after a data source migration added a new high-cardinality device key.

Timeline

Day 0:  Pipeline runs normally. 500M events/day, 200 shuffle partitions.
        Join on device_id. Largest partition: ~800 MB. Executors: 8 GB heap.

Day 1:  Upstream source adds new IoT device type. These devices all report
        with device_id = "UNREGISTERED" (placeholder for unknown devices).
        50M of 500M events now have device_id = "UNREGISTERED".

Day 2:  Pipeline OOMs. Single partition (hash("UNREGISTERED") % 200)
        receives 50M rows (~12 GB) — exceeds 8 GB executor memory.
        3 executors crash attempting this partition. Stage retried 4×, fails.

Resolution Options

Option 1: Enable AQE Skew Join (Recommended for Spark 3.x)

spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256m")

# AQE automatically:
# 1. Detects partition 142 is 12 GB (> 5× median 510 MB AND > 256 MB)
# 2. Splits it into ~24 sub-partitions of ~512 MB each
# 3. Replicates the device dimension's matching partition
# 4. Runs 24 parallel tasks instead of 1 OOM task

Option 2: Salting (Manual Skew Handling)

from pyspark.sql.functions import lit, rand, concat, col, explode, array

SALT_BUCKETS = 20

# Salt the skewed key in the large table
events_salted = events.withColumn(
    "salt",
    (rand() * SALT_BUCKETS).cast("int")
).withColumn(
    "device_id_salted",
    concat(col("device_id"), lit("_"), col("salt"))
)

# Explode the dimension table to match all salt values
salt_array = array([lit(i) for i in range(SALT_BUCKETS)])
devices_exploded = devices.withColumn(
    "salt", explode(salt_array)
).withColumn(
    "device_id_salted",
    concat(col("device_id"), lit("_"), col("salt"))
)

# Join on salted key — "UNREGISTERED" now distributed across 20 partitions
joined = events_salted.join(
    devices_exploded,
    "device_id_salted",
    "inner"
).drop("salt", "device_id_salted")

Option 3: Isolate and Broadcast Skewed Key

# Separate skewed and non-skewed data
skewed_events = events.filter(col("device_id") == "UNREGISTERED")
normal_events = events.filter(col("device_id") != "UNREGISTERED")

# Broadcast join for skewed portion (dimension lookup is small)
skewed_joined = skewed_events.join(
    broadcast(devices.filter(col("device_id") == "UNREGISTERED")),
    "device_id"
)

# Normal SortMergeJoin for the rest
normal_joined = normal_events.join(devices, "device_id")

# Combine results
result = skewed_joined.unionByName(normal_joined)

  • Circuit breaker — Fail fast with clear error message when detected skew exceeds threshold, rather than OOM after 30 minutes.
  • Data contract with upstream — Require notification when new high-cardinality keys are introduced.

Repartition vs Coalesce

# repartition(N) — FULL SHUFFLE, creates exactly N partitions
# Use when: increasing partitions or redistributing by a key

# Increase parallelism for a compute-heavy operation
df_repartitioned = df.repartition(500)  # Full shuffle to 500 partitions

# Repartition by key — co-locates data for downstream joins
df_by_key = df.repartition(200, "customer_id")
# All rows with same customer_id in same partition
# Subsequent groupBy("customer_id") requires NO additional shuffle!

# coalesce(N) — NO SHUFFLE, reduces partitions by merging
# Use when: decreasing partitions (e.g., before write to avoid small files)

# After a filter that reduces data significantly
filtered = df.filter(col("amount") > 1000)  # 1% of data remains
# 200 partitions now mostly empty — coalesce to fewer
coalesced = filtered.coalesce(10)  # Merge into 10 partitions, no shuffle

# COMMON PATTERN: reduce output files before writing
result \
    .coalesce(50) \
    .write \
    .mode("overwrite") \
    .parquet("s3://output/result/")
# Produces exactly 50 output files instead of 200+

# WARNING: coalesce can create uneven partitions
# If 200 partitions coalesced to 10, each gets ~20 merged partitions
# If original partitions were skewed, coalesced ones will be too
# In that case, use repartition() for even distribution

Caching Strategies

from pyspark import StorageLevel

# Cache in memory (deserialized Java objects — fastest, most memory)
df.cache()  # Equivalent to: df.persist(StorageLevel.MEMORY_ONLY)

# Cache in memory serialized (less memory, slightly slower access)
df.persist(StorageLevel.MEMORY_ONLY_SER)

# Cache with disk spillover (recommended for large datasets)
df.persist(StorageLevel.MEMORY_AND_DISK)

# Cache serialized with disk spillover (best memory efficiency)
df.persist(StorageLevel.MEMORY_AND_DISK_SER)

# When to cache:
# 1. DataFrame used multiple times in the same job
# 2. Expensive computation that shouldn't be repeated
# 3. Interactive exploration (notebook environment)

# Example: cache a joined dataset used for multiple aggregations
base = orders.join(customers, "customer_id") \
    .filter(col("order_date") >= "2024-01-01")

base.cache()
base.count()  # Trigger cache materialization

# Now these use cached data (no re-reading from S3, no re-joining)
by_segment = base.groupBy("segment").agg(sum("amount"))
by_date = base.groupBy("order_date").agg(count("order_id"))
top_customers = base.groupBy("customer_id").agg(sum("amount")).orderBy(col("sum(amount)").desc())

# ALWAYS unpersist when done to free memory for other operations
base.unpersist()

# Check what's cached
spark.catalog.isCached("base")  # For registered tables
# Or check Storage tab in Spark UI

Common Mistakes

Mistake Why It's Wrong Correct Approach
Using .collect() on large DataFrames Pulls all data to driver memory — OOM for anything over a few GB Use .take(N), .show(N), or write results to storage
Leaving shuffle.partitions=200 for all workloads 200 is arbitrary — too few for TB-scale data, too many for MB-scale data Set to 2–3× total cores, or enable AQE coalescing
Using Python UDFs instead of built-in functions Python UDFs serialize data to Python process (10–100× slower), disable whole-stage codegen Use Spark SQL functions. If UDF needed, use Pandas UDFs (vectorized)
Caching everything "just in case" Wastes storage memory, triggers evictions of actually useful cached data, causes GC pressure Cache only DataFrames used > 2× in same job, unpersist when done
Using repartition() before write when coalesce() suffices Unnecessary full shuffle when only reducing partitions Use coalesce(N) when only reducing; repartition() only when increasing or rebalancing
Ignoring data skew One partition with 100× data = one task takes 100× longer, negating all parallelism Enable AQE skew join, or use salting/isolation for known hot keys
Not enabling AQE in Spark 3.x Missing free performance wins: partition coalescing, join strategy switching, skew handling Always enable: spark.sql.adaptive.enabled=true
Broadcasting tables that are too large Broadcast exceeding driver memory causes OOM; 1 GB broadcast × 100 executors = 100 GB network Keep broadcasts under 200–500 MB; prefer SortMergeJoin for larger tables
Running .count() to "trigger" lazy evaluation for debugging Unnecessary full computation; use .take(1) or .limit(1).collect() instead For plan inspection, use .explain() (doesn't execute). For triggering, use minimal action
Not using the External Shuffle Service with dynamic allocation When executors are removed, their shuffle files are lost → FetchFailedException → stage retry Always enable spark.shuffle.service.enabled=true with dynamic allocation
Repeated reads from cloud storage in a loop Each iteration re-reads from S3/GCS (high latency, cost per request) Cache the DataFrame before entering a loop, unpersist after
Using .distinct() when .dropDuplicates(subset) suffices .distinct() shuffles ALL columns; .dropDuplicates(["key"]) shuffles only the key columns Use .dropDuplicates() with explicit columns when full-row uniqueness isn't needed

Follow-up Questions

Architecture & Execution

  • "What happens if the driver runs out of memory?" — The application crashes. Common causes: collecting too much data to driver (.collect()), too many broadcast variables accumulated, or accumulator state explosion. Mitigation: increase spark.driver.memory, avoid .collect(), or use cluster mode for automatic restart.
  • "How does dynamic allocation work?" — Spark requests executors from the cluster manager as pending tasks queue up (spark.dynamicAllocation.schedulerBacklogTimeout=1s). It releases executors after idle timeout (executorIdleTimeout=60s). Requires External Shuffle Service so released executors don't lose shuffle files.
  • "Explain the difference between client mode and cluster mode." — Client mode: driver runs on the submitting machine (your laptop/gateway). Cluster mode: driver runs inside the cluster (YARN container, K8s pod). Cluster mode is required for production — the driver survives gateway failures and benefits from data locality.
  • "What is speculative execution and when would you enable it?" — Spark launches a duplicate copy of a slow-running task on a different executor. First to finish wins; the other is killed. Enable when: heterogeneous hardware (some nodes slower), cloud spot instances (preemption causes delays). Disable when: tasks are intentionally slow (writing to slow external systems) or resource-constrained clusters.

Optimization & Tuning

  • "How do you choose the right number of shuffle partitions?" — Target 128–256 MB per partition. Formula: total_shuffle_data_size / target_partition_size. For a 100 GB shuffle with 200 MB target: 500 partitions. With AQE enabled, set a higher initial value (e.g., 2000) and let AQE coalesce — this handles variable data sizes automatically.
  • "When would you NOT use AQE?" — When you need deterministic execution plans (regulatory audit requirements), when the re-optimization overhead matters (sub-second latency queries), or when running Spark 2.x (AQE requires Spark 3.0+).
  • "Explain predicate pushdown in Spark." — Catalyst pushes filter predicates as close to the data source as possible. For Parquet, this means (1) partition pruning (skip entire directories), (2) row group filtering via min/max statistics, and (3) page-level filtering via column indexes. For JDBC sources, Spark pushes predicates into the SQL query sent to the database.
  • "What is Dynamic Partition Pruning (DPP)?" — At runtime, Spark uses the result of one side of a join (typically the dimension filter) to prune partitions on the other side (the fact table). This avoids reading irrelevant fact table partitions. Requires: partition key = join key, one side has a selective filter. Controlled by spark.sql.optimizer.dynamicPartitionPruning.enabled=true.
  • "How do you handle a join between two very large tables?" — SortMergeJoin is the default and most scalable strategy. Optimize by: (1) bucketing both tables by join key (eliminates shuffle), (2) increasing shuffle partitions to keep per-partition size manageable, (3) filtering before joining to reduce data volume, (4) using AQE to handle runtime skew.

Debugging & Operations

  • "How do you detect and fix data skew?" — Detection: Spark UI shows task duration distribution (long tail), shuffle read size (max ≫ median). Fix: AQE skew join (automatic), salting (manual), isolate + broadcast hot keys, pre-aggregate before join. Prevention: upstream data quality monitoring, alerts on key cardinality changes.
  • "What causes FetchFailedException?" — Executor holding shuffle files crashed or was removed. The reduce task can't fetch its shuffle data. Resolution: enable External Shuffle Service (decouples file lifecycle from executor), increase spark.shuffle.io.maxRetries, investigate node health (disk full, OOM killer).
  • "How do you debug a slow Spark job?" — Systematic approach: (1) Jobs tab — identify slowest job, (2) Stages tab — identify slowest stage, (3) Task metrics — check for skew (max vs median), spill, GC time, (4) SQL tab — compare estimated vs actual rows, (5) Event timeline — look for idle gaps (fetch wait, GC). Fix the dominant bottleneck first.
  • "What is GC tuning in Spark and when do you do it?" — When GC time exceeds 10% of task time (visible in Spark UI). Options: use G1GC (-XX:+UseG1GC), increase spark.executor.memory, reduce cached data, enable off-heap Tungsten memory, switch to Kryo serialization to reduce object count.
  • "Explain the role of the External Shuffle Service." — A long-running process on each node (independent of executors) that serves shuffle files. Benefits: (1) enables dynamic allocation (executors can be removed without losing shuffle data), (2) improves fault tolerance (shuffle files survive executor crashes), (3) enables push-based shuffle (Spark 3.2+) for better performance.

Advanced Topics

  • "What is Photon?" — Databricks' native C++ execution engine that replaces Spark's JVM-based execution. Uses vectorized processing (operates on column batches, not individual rows), SIMD instructions, and pre-compiled operators instead of code generation. Can be 2–8× faster than standard Spark for scan/filter/join heavy workloads.
  • "How does Spark handle out-of-core processing (data larger than memory)?" — External sort spills sorted runs to disk and merge-sorts them. External hash aggregation spills hash table entries when memory is full. SortMergeJoin is inherently streaming (bounded memory). The key metric: if you see shuffle spill in the UI, the operation went out-of-core — not a failure, but slower than in-memory.
  • "What changes in Spark 4.0?" — Spark Connect (client-server architecture), ANSI SQL compliance by default, Variant data type for semi-structured data, improved Python API (type hints, pandas-native operations), removal of deprecated Mesos support, and new streaming state management backend.

Key Takeaways for Interviews

Concept One-Liner
Lazy evaluation Transformations build a DAG; only actions trigger execution — enabling full-graph optimization.
Catalyst Four-phase optimizer (analysis → logical → physical → codegen) that turns declarative operations into efficient bytecode.
Tungsten Custom memory management with off-heap binary format (UnsafeRow) and whole-stage code generation for CPU efficiency.
Shuffle Most expensive operation — redistributes data across the network. Minimize by filtering early, broadcasting small tables, and bucketing.
Stages & Tasks Shuffles create stage boundaries. Each stage has tasks = partitions. Tasks are the unit of parallelism and retry.
AQE Runtime re-optimization using actual statistics — coalesces partitions, switches joins, splits skewed data.
Fault tolerance Lineage-based: lost partitions recomputed from parent RDDs. No WAL overhead for intermediate data.
Join selection BHJ for small-large (no shuffle); SMJ for large-large (scalable); AQE can switch at runtime.

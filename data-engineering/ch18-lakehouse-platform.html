Hard Lakehouse Iceberg

Design a Modern Lakehouse Platform for a Global Organization

Key Takeaway: A modern lakehouse combines the flexibility of data lakes with the reliability of data warehouses using open table formats (Delta Lake/Iceberg/Hudi), a medallion architecture for progressive data refinement, and strong governance for metadata, lineage, and access control.

Interviewer Intent

When a FAANG interviewer asks you to design a modern lakehouse platform, they are evaluating your ability to synthesize multiple complex domains into a cohesive architecture:

  • Architectural reasoning: Can you articulate why lakehouses emerged and how they resolve the data lake vs data warehouse dichotomy?
  • Open table format mastery: Do you understand the internals of Delta Lake, Apache Iceberg, and Apache Hudi — not just surface-level features but the mechanics of metadata layers, transaction logs, and file organization?
  • Data platform design: Can you design a multi-layer architecture (medallion) that balances raw data preservation with performance for analytics?
  • Governance at scale: How do you handle access control, PII masking, lineage tracking, and compliance across petabytes of data spread globally?
  • Cost consciousness: Senior engineers must reason about storage tiering, compute elasticity, and operational costs — not just technical elegance.
  • Production maturity: Have you dealt with real lakehouse problems — small files, partition explosions, schema drift, catalog inconsistencies?
  • Vendor strategy: Can you make and defend decisions about open-source vs managed services, single-vendor vs multi-vendor, cloud-specific vs cloud-agnostic?

This question separates senior data engineers who have operated platforms at scale from those who have only consumed them. The interviewer expects you to drive the conversation proactively, covering ingestion, storage, compute, governance, and operations without prompting.

Quick Answer

A production lakehouse platform for a global organization consists of:

  1. Storage layer: Object storage (S3/GCS/ADLS) as the single source of truth, with an open table format (Iceberg/Delta/Hudi) providing ACID transactions, schema evolution, and time travel on top of Parquet/ORC files.
  2. Medallion architecture: Bronze (raw ingestion, append-only), Silver (cleansed, conformed, deduplicated), Gold (business-level aggregates, dimensional models) — with data contracts enforcing quality between layers.
  3. Compute layer: Decoupled engines (Spark, Trino, Flink, dbt) querying the same tables through a shared catalog — no data duplication across tools.
  4. Catalog & governance: Centralized metadata catalog (Unity Catalog, Hive Metastore, Nessie) with fine-grained access control, column-level masking, and automated lineage tracking.
  5. Ingestion: Hybrid batch + streaming pipelines using CDC (Debezium), file drops, and API connectors — all landing in Bronze with full schema preservation.
  6. Operations: Automated compaction, partition lifecycle management, storage tiering, and data quality monitoring to keep the platform healthy at petabyte scale.

The key insight: a lakehouse is not a product — it is an architecture pattern that combines the low-cost, schema-flexible storage of a data lake with the ACID transactions, performance optimizations, and governance features traditionally exclusive to data warehouses. The open table format is the technology that makes this convergence possible.

Data Lake vs Data Warehouse vs Lakehouse

The Historical Divide

Why Data Lakes Failed as Platforms

Data lakes solved the cost and flexibility problem but introduced critical gaps that prevented them from replacing warehouses:

  • No ACID transactions: Concurrent writes could corrupt data. A failed job left partial results with no rollback mechanism.
  • No schema enforcement: "Schema-on-read" became "schema-never" — consumers discovered data quality issues at query time.
  • No time travel: Overwritten data was gone forever. Debugging pipeline issues required expensive re-ingestion.
  • No indexing or statistics: Every query was a full scan. Performance was unpredictable and slow for interactive workloads.
  • Governance vacuum: No row/column-level security, no audit logs, no lineage — compliance was manual and error-prone.

Why Lakehouse Emerged Now

Three technological developments converged around 2018-2020:

  1. Open table formats matured: Delta Lake (2019), Apache Iceberg (2017 at Netflix, donated to Apache 2018), Apache Hudi (2016 from Uber) — all reached production readiness, proving ACID transactions on object storage were possible.
  2. Object storage became fast enough: S3 request rates went from ~300-800 rps per prefix to 3,500+ PUT / 5,500+ GET per prefix (July 2018 improvement). High-throughput columnar reads became viable.
  3. Compute engines decoupled: Spark, Trino, Flink, and Dremio all adopted catalog-based access patterns, making engine interoperability practical through shared metadata.

Important nuance: A lakehouse does not replace a data warehouse for all use cases. Sub-second interactive dashboards with thousands of concurrent users may still benefit from a serving layer (StarRocks, ClickHouse, Pinot) fed from the lakehouse. The lakehouse is the platform; specialized engines are acceleration layers.

Open Table Formats

Open table formats are the core technology enabling the lakehouse pattern. They add a metadata layer between compute engines and physical files, providing ACID semantics, schema management, and performance optimizations without proprietary lock-in.

Delta Lake

Created by Databricks (2019), Delta Lake uses a JSON-based transaction log stored alongside data files in the same directory.

Transaction Log Architecture

# Delta Lake directory structure:
#
# s3://lakehouse/tables/orders/
# ├── _delta_log/
# │   ├── 00000000000000000000.json    ← initial commit
# │   ├── 00000000000000000001.json    ← add files
# │   ├── 00000000000000000002.json    ← update operation
# │   ├── ...
# │   ├── 00000000000000000010.checkpoint.parquet  ← checkpoint (every 10 commits by default, configurable)
# │   └── _last_checkpoint                         ← pointer to latest checkpoint
# ├── part-00000-abc123.snappy.parquet
# ├── part-00001-def456.snappy.parquet
# └── year=2024/month=01/
#     ├── part-00000-ghi789.snappy.parquet
#     └── part-00001-jkl012.snappy.parquet
#
# Each JSON log entry contains:
# {
#   "add": {"path": "part-00000-abc.parquet", "size": 1048576,
#           "partitionValues": {"year": "2024"}, "stats": {...}},
#   "remove": {"path": "old-file.parquet", "deletionTimestamp": 1700000000},
#   "metaData": {"schemaString": "...", "partitionColumns": [...]}
# }

Key Delta Lake Features

  • ACID transactions: Optimistic concurrency control using the transaction log. Conflicting writes are detected at commit time (not at read time) using file-level conflict resolution.
  • Time travel: Query any historical version by snapshot ID or timestamp. Retention controlled by delta.logRetentionDuration (default 30 days). Note: time travel also depends on delta.deletedFileRetentionDuration (default 7 days) — if VACUUM has removed the underlying data files, time travel to those versions will fail even if log entries exist.
  • Z-ORDER clustering: Co-locates related data in the same files using a Z-order space-filling curve, dramatically improving multi-dimensional filter performance.
  • Change Data Feed (CDF): Tracks row-level changes (insert/update/delete) between versions, enabling efficient incremental reads without scanning all files.
  • Liquid Clustering (v3.1+): Replaces static partitioning and Z-ORDER with adaptive, incremental clustering that rebalances data as write patterns change.
-- Delta Lake time travel examples
-- Query table as of specific version
SELECT * FROM orders VERSION AS OF 42;

-- Query table as of timestamp
SELECT * FROM orders TIMESTAMP AS OF '2024-01-15T10:00:00Z';

-- Show table history
DESCRIBE HISTORY orders;

-- Restore table to previous version
RESTORE TABLE orders TO VERSION AS OF 42;

-- Z-ORDER optimization
OPTIMIZE orders
ZORDER BY (customer_id, order_date);

-- This physically reorganizes files so that rows with similar
-- customer_id AND order_date values are co-located.
-- Queries filtering on these columns skip 80-95% of files.

Apache Iceberg

Created at Netflix (2017), donated to Apache (2018). Iceberg uses a tree-structured metadata hierarchy that provides O(1) snapshot access and hidden partitioning.

Metadata Layer Architecture

# Iceberg metadata hierarchy:
#
#                    ┌──────────────────┐
#                    │  Catalog         │  (Hive Metastore, Nessie,
#                    │  (current-table) │   REST, Glue)
#                    └────────┬─────────┘
#                             │ points to
#                             ▼
#                    ┌──────────────────┐
#                    │  Metadata File   │  metadata/v3.metadata.json
#                    │  (table state)   │
#                    │                  │  • schema (current + history)
#                    │                  │  • partition spec (current + history)
#                    │                  │  • snapshot list
#                    │                  │  • properties
#                    └────────┬─────────┘
#                             │ current-snapshot-id
#                             ▼
#                    ┌──────────────────┐
#                    │  Snapshot        │  snap-12345-abc.avro
#                    │                  │
#                    │  • snapshot-id   │
#                    │  • timestamp     │
#                    │  • manifest-list │
#                    └────────┬─────────┘
#                             │
#                             ▼
#                    ┌──────────────────┐
#                    │  Manifest List   │  snap-12345-manifests.avro
#                    │                  │
#                    │  Array of:       │
#                    │  • manifest path │
#                    │  • partition info│
#                    │  • added files   │
#                    │  • deleted files │
#                    └────────┬─────────┘
#                             │
#                     ┌───────┴───────┐
#                     ▼               ▼
#            ┌─────────────┐  ┌─────────────┐
#            │ Manifest 1  │  │ Manifest 2  │
#            │             │  │             │
#            │ Data files: │  │ Data files: │
#            │ • path      │  │ • path      │
#            │ • partition │  │ • partition │
#            │ • record cnt│  │ • record cnt│
#            │ • col stats │  │ • col stats │
#            │   (min/max) │  │   (min/max) │
#            └─────────────┘  └─────────────┘
#
# Key insight: Manifest files store per-file statistics
# (min/max per column), enabling partition pruning AND
# file pruning within partitions without listing S3.

Hidden Partitioning

Unlike Hive-style partitioning where users must know the partition scheme, Iceberg applies partition transforms transparently:

-- Iceberg hidden partitioning: users query naturally,
-- engine applies partition pruning automatically

-- Table definition with partition transforms
CREATE TABLE events (
  event_id    BIGINT,
  event_time  TIMESTAMP,
  user_id     BIGINT,
  event_type  STRING,
  payload     STRING
)
USING iceberg
PARTITIONED BY (
  days(event_time),     -- partition by day (derived from timestamp)
  bucket(16, user_id)   -- hash-bucket user_id into 16 buckets
);

-- User writes a simple filter — NO partition column reference needed:
SELECT * FROM events
WHERE event_time BETWEEN '2024-03-01' AND '2024-03-07'
  AND user_id = 42;

-- Iceberg automatically:
-- 1. Converts date range → partition values (days 19783-19789)
-- 2. Converts user_id=42 → bucket(16, 42) = bucket 10
-- 3. Prunes manifests that don't contain these partitions
-- 4. Prunes data files using column-level min/max stats

Schema Evolution & Partition Evolution

-- Schema evolution (non-breaking, no rewrite required)
ALTER TABLE events ADD COLUMNS (
  device_type STRING AFTER event_type,
  geo_country STRING
);

-- Rename column (uses internal IDs, not names)
ALTER TABLE events RENAME COLUMN payload TO event_payload;

-- Partition evolution: change partition scheme WITHOUT rewriting data
-- Old data keeps old partitioning; new data uses new scheme
ALTER TABLE events
SET PARTITION SPEC (
  months(event_time),    -- changed from days() to months()
  bucket(32, user_id)    -- changed from 16 to 32 buckets
);

-- Both old (daily) and new (monthly) partitions coexist
-- Query engine handles both transparently

Apache Hudi

Created at Uber (2016) for incremental data processing. Hudi's key differentiator is native support for record-level upserts and incremental queries — designed for CDC workloads from the start.

Copy-on-Write vs Merge-on-Read

# Hudi storage types:
#
# COPY-ON-WRITE (CoW):
# ┌─────────────────────────────────────────────────────────────┐
# │ Write path: Update → Read existing file → Merge → Write    │
# │             new complete file → Mark old as replaced        │
# │                                                             │
# │ Pros: Read-optimized (no merge at query time)              │
# │ Cons: Write amplification (rewrite entire file for 1 row)  │
# │ Best for: Read-heavy workloads, BI dashboards              │
# │                                                             │
# │ File layout:                                                │
# │ base/  → [file1_v2.parquet] [file2_v3.parquet]            │
# │          (always up-to-date, no log files)                 │
# └─────────────────────────────────────────────────────────────┘
#
# MERGE-ON-READ (MoR):
# ┌─────────────────────────────────────────────────────────────┐
# │ Write path: Update → Append delta to log file              │
# │             (periodically compact log into base file)       │
# │                                                             │
# │ Pros: Fast writes (append-only logs)                       │
# │ Cons: Slower reads (must merge base + logs at query time)  │
# │ Best for: Write-heavy workloads, CDC ingestion             │
# │                                                             │
# │ File layout:                                                │
# │ base/  → [file1_v1.parquet] + [.file1_v1.log.1.avro]     │
# │          (base file)           (delta log — updates)       │
# │                                                             │
# │ Read paths:                                                 │
# │ • Snapshot query: merge base + all logs (freshest, slower) │
# │ • Read-optimized: base files only (stale, faster)          │
# └─────────────────────────────────────────────────────────────┘

Hudi Timeline

Hudi maintains a timeline of all operations (commits, compactions, cleans) as metadata, enabling incremental processing:

# Hudi timeline example:
# .hoodie/
# ├── 20240101120000.commit           ← completed commit
# ├── 20240101130000.commit
# ├── 20240101140000.deltacommit      ← MoR delta commit
# ├── 20240101150000.compaction.requested
# ├── 20240101150000.compaction.completed
# ├── 20240101160000.clean.requested
# └── 20240101160000.clean.completed
#
# Incremental query: "give me all changes since 20240101130000"
# → Returns only records that changed (inserts, updates, deletes)
# → Perfect for downstream ETL that needs to process only new data
# Hudi incremental read in PySpark
df_incremental = spark.read.format("hudi") \
    .option("hoodie.datasource.query.type", "incremental") \
    .option("hoodie.datasource.read.begin.instanttime", "20240101130000") \
    .option("hoodie.datasource.read.end.instanttime", "20240101160000") \
    .load("s3://lakehouse/tables/orders/")

# Returns only rows that changed between those two instants
# Columns include: _hoodie_commit_time, _hoodie_operation (INSERT/UPDATE/DELETE)

Industry trend (2024+): Iceberg is increasingly becoming the preferred open table format for multi-engine lakehouses. Snowflake (Iceberg tables), AWS (native Iceberg in Athena/EMR/Glue), Databricks (UniForm for Iceberg compatibility), and Google (BigLake) have all converged on Iceberg interoperability. If starting a new lakehouse from scratch, Iceberg offers the broadest engine support and least vendor lock-in.

Medallion Architecture Deep Dive

The medallion (multi-hop) architecture organizes data in progressive layers of refinement, from raw ingestion to business-ready aggregates. Each layer has distinct responsibilities, quality guarantees, and access patterns. Note: this is the most widely adopted layering pattern, but not the only one — some organizations use additional layers (Raw, Curated, Serving, Sandbox) or organize primarily by domain rather than refinement stage.

Architecture Overview

Data Contracts Between Layers

Data contracts are formal agreements that define the expectations between producers and consumers at each layer boundary:

# Example data contract: Bronze → Silver for orders
# File: contracts/silver/orders.contract.yaml

contract:
  name: silver_orders
  version: 2.1.0
  owner: data-platform-team
  domain: commerce

schema:
  type: iceberg
  fields:
    - name: order_id
      type: bigint
      nullable: false
      description: "Unique order identifier"
      tests:
        - unique
        - not_null
    - name: customer_id
      type: bigint
      nullable: false
      foreign_key: silver.customers.customer_id
    - name: order_date
      type: timestamp
      nullable: false
      tests:
        - not_null
        - accepted_range:
            min: "2020-01-01"
            max: "{{ current_date }}"
    - name: total_amount
      type: decimal(18,2)
      nullable: false
      tests:
        - positive
    - name: currency
      type: string
      nullable: false
      tests:
        - accepted_values: [USD, EUR, GBP, JPY]
    - name: status
      type: string
      nullable: false
      tests:
        - accepted_values: [pending, confirmed, shipped, delivered, cancelled]

quality:
  freshness:
    max_delay: 15m
    check_column: _ingested_at
  completeness:
    min_row_count: 1000  # at least 1000 new orders per batch
    max_null_percentage:
      customer_id: 0%
      total_amount: 0%
  uniqueness:
    columns: [order_id]
    scope: full_table
  consistency:
    - type: referential
      column: customer_id
      reference: silver.customers.customer_id
      max_orphan_percentage: 0.1%

sla:
  update_frequency: every_15_minutes
  availability: 99.9%
  notification_channel: "#data-quality-alerts"

breaking_changes:
  policy: "versioned"
  notification: 7_days_advance
  migration_window: 30_days

Bronze Layer Patterns

# Bronze ingestion pattern: append-only with metadata enrichment
from pyspark.sql import functions as F
from datetime import datetime

def ingest_to_bronze(
    spark,
    source_df,
    target_path: str,
    source_system: str,
    batch_id: str
):
    """
    Ingest raw data to Bronze layer with metadata enrichment.
    Never modifies data — append only with provenance tracking.
    """
    bronze_df = source_df \
        .withColumn("_ingested_at", F.current_timestamp()) \
        .withColumn("_source_system", F.lit(source_system)) \
        .withColumn("_batch_id", F.lit(batch_id)) \
        .withColumn("_ingest_date", F.current_date()) \
        .withColumn("_raw_filename", F.input_file_name())

    # Write as append-only (never overwrite Bronze)
    bronze_df.writeTo(target_path) \
        .using("iceberg") \
        .partitionedBy("_ingest_date") \
        .append()

    return bronze_df.count()


# CDC Bronze ingestion (Debezium format)
def ingest_cdc_to_bronze(spark, kafka_df, target_path: str):
    """
    Ingest CDC events from Debezium via Kafka to Bronze.
    Preserves the full CDC envelope (before/after/op/ts_ms).
    """
    parsed_df = kafka_df \
        .selectExpr("CAST(value AS STRING) as json_payload") \
        .select(
            F.from_json("json_payload", cdc_schema).alias("cdc")
        ) \
        .select(
            "cdc.payload.before",
            "cdc.payload.after",
            "cdc.payload.op",        # c=create, u=update, d=delete
            "cdc.payload.ts_ms",
            "cdc.payload.source.table",
            "cdc.payload.source.db"
        ) \
        .withColumn("_ingested_at", F.current_timestamp()) \
        .withColumn("_kafka_offset", F.col("offset")) \
        .withColumn("_kafka_partition", F.col("partition"))

    parsed_df.writeTo(target_path) \
        .using("iceberg") \
        .append()

Silver Layer Patterns

# Silver layer: deduplication, cleansing, and conforming
def bronze_to_silver_orders(spark, bronze_path: str, silver_table_name: str):
    """
    Transform Bronze orders to Silver:
    1. Deduplicate by order_id (keep latest by _ingested_at)
    2. Validate and cast types
    3. Standardize timestamps to UTC
    4. Upsert into Silver (MERGE for idempotency)
    """
    # Read incremental Bronze data (since last checkpoint)
    bronze_df = spark.read.format("iceberg") \
        .option("start-snapshot-id", last_processed_snapshot) \
        .load(bronze_path)

    # Deduplicate within batch (keep latest ingestion)
    from pyspark.sql.window import Window
    dedup_window = Window.partitionBy("order_id") \
        .orderBy(F.desc("_ingested_at"))

    cleansed_df = bronze_df \
        .withColumn("_row_num", F.row_number().over(dedup_window)) \
        .filter("_row_num = 1") \
        .drop("_row_num") \
        .select(
            F.col("order_id").cast("bigint"),
            F.col("customer_id").cast("bigint"),
            F.to_utc_timestamp("order_date", "source_timezone").alias("order_date"),
            F.col("total_amount").cast("decimal(18,2)"),
            F.upper("currency").alias("currency"),
            F.lower("status").alias("status"),
            F.current_timestamp().alias("_processed_at")
        ) \
        .filter("order_id IS NOT NULL") \
        .filter("total_amount > 0")

    # MERGE into Silver (upsert: insert new, update existing)
    silver_table = spark.table(silver_table_name)
    silver_table.alias("target").merge(
        cleansed_df.alias("source"),
        "target.order_id = source.order_id"
    ).whenMatchedUpdate(
        condition="source._processed_at > target._processed_at",
        set={
            "status": "source.status",
            "total_amount": "source.total_amount",
            "_processed_at": "source._processed_at"
        }
    ).whenNotMatchedInsertAll() \
     .execute()

    SELECT
        DATE(o.order_date) AS revenue_date,
        c.region,
        c.country,
        o.currency,
        o.total_amount,
        o.status
    FROM {{ ref('silver_orders') }} o
    INNER JOIN {{ ref('silver_customers') }} c
        ON o.customer_id = c.customer_id
    WHERE o.status IN ('confirmed', 'shipped', 'delivered')
    {% if is_incremental() %}
        AND o._processed_at > (SELECT MAX(_processed_at) FROM {{ this }})
        -- NOTE: In production, consider a lookback window to handle late-arriving data:
        -- AND o._processed_at > (SELECT MAX(_processed_at) - INTERVAL 2 HOURS FROM {{ this }})
    {% endif %}
),

daily_agg AS (
    SELECT
        revenue_date,
        region,
        country,
        currency,
        COUNT(*)              AS order_count,
        SUM(total_amount)     AS gross_revenue,
        AVG(total_amount)     AS avg_order_value,
        PERCENTILE(total_amount, 0.5) AS median_order_value
    FROM order_facts
    GROUP BY 1, 2, 3, 4
)

SELECT
    revenue_date,
    region,
    country,
    currency,
    order_count,
    gross_revenue,
    avg_order_value,
    median_order_value,
    CURRENT_TIMESTAMP() AS _computed_at
FROM daily_agg

Best practice: Gold tables should be optimized for specific consumption patterns. If BI tools query by date and region, partition by date and cluster by region. If ML models need full scans, a flat denormalized table with minimal partitioning is better. One Silver table can feed multiple Gold tables optimized for different access patterns.

from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine

analyzer = AnalyzerEngine()

def scan_column_for_pii(sample_values: list) -> dict:
    """Scan a sample of column values for PII entities."""
    pii_results = {}
    for value in sample_values:
        if value is None:
            continue
        results = analyzer.analyze(text=str(value), language="en")
        for result in results:
            entity_type = result.entity_type
            pii_results[entity_type] = pii_results.get(entity_type, 0) + 1
    return pii_results

GDPR Right to Erasure: In a lakehouse, deleting a user's data requires row-level deletes across potentially thousands of files in multiple tables. Iceberg and Delta support row-level deletes, but the operation can be expensive. Design a deletion_requests table that queues requests, processes them in batch during off-peak hours, and verifies deletion across all layers (Bronze through Gold). Consider pseudonymization as an alternative where regulations allow.

# API ingestion with pagination, rate limiting, and idempotency
import requests
import time
from datetime import datetime, timedelta
from tenacity import retry, stop_after_attempt, wait_exponential

class APIIngester:
    """Generic API ingestion with cursor-based pagination."""

    def __init__(self, base_url: str, api_key: str, rate_limit_rps: int = 10):
        self.base_url = base_url
        self.session = requests.Session()
        self.session.headers["Authorization"] = f"Bearer {api_key}"
        self.rate_limit_interval = 1.0 / rate_limit_rps
        self.last_request_time = 0

    def _rate_limit(self):
        elapsed = time.time() - self.last_request_time
        if elapsed < self.rate_limit_interval:
            time.sleep(self.rate_limit_interval - elapsed)
        self.last_request_time = time.time()

    @retry(stop=stop_after_attempt(5), wait=wait_exponential(min=1, max=60))
    def _fetch_page(self, endpoint: str, params: dict) -> dict:
        self._rate_limit()
        response = self.session.get(f"{self.base_url}/{endpoint}", params=params)
        response.raise_for_status()
        return response.json()

    def ingest_incremental(
        self,
        endpoint: str,
        since: datetime,
        cursor_field: str = "updated_at",
        page_size: int = 1000
    ) -> list:
        """Fetch all records updated since given timestamp."""
        all_records = []
        cursor = None
        total_pages = 0

        while True:
            params = {
                "since": since.isoformat(),
                "limit": page_size,
                "sort": cursor_field,
                "order": "asc"
            }
            if cursor:
                params["after"] = cursor

            page = self._fetch_page(endpoint, params)
            records = page.get("data", [])

            if not records:
                break

            all_records.extend(records)
            cursor = records[-1].get("id")
            total_pages += 1

            # Safety: prevent infinite loops
            if total_pages > 10000:
                raise RuntimeError(f"Too many pages ({total_pages}), possible infinite loop")

        return all_records

# Automated partition lifecycle management
from pyspark.sql import SparkSession
from datetime import datetime, timedelta

def manage_partition_lifecycle(spark: SparkSession, table: str):
    """
    Manage table lifecycle:
    1. Expire old snapshots (free metadata)
    2. Remove orphaned files (free storage)
    3. Compact small files (improve query perf)
    4. Rewrite old partitions to cold storage format
    """

    # 1. Expire snapshots older than 7 days
    spark.sql(f"""
        CALL lakehouse.system.expire_snapshots(
            table => '{table}',
            older_than => TIMESTAMP '{(datetime.now() - timedelta(days=7)).isoformat()}',
            retain_last => 10
        )
    """)

    # 2. Remove orphaned files (files not referenced by any snapshot)
    spark.sql(f"""
        CALL lakehouse.system.remove_orphan_files(
            table => '{table}',
            older_than => TIMESTAMP '{(datetime.now() - timedelta(days=3)).isoformat()}'
        )
    """)

    # 3. Compact small files (target 128-256 MB per file)
    spark.sql(f"""
        CALL lakehouse.system.rewrite_data_files(
            table => '{table}',
            strategy => 'binpack',
            options => map(
                'target-file-size-bytes', '134217728',
                'min-file-size-bytes', '67108864',
                'max-file-size-bytes', '268435456',
                'min-input-files', '5',
                'partial-progress.enabled', 'true',
                'partial-progress.max-commits', '10'
            )
        )
    """)

    # 4. Sort-compact for frequently filtered columns
    spark.sql(f"""
        CALL lakehouse.system.rewrite_data_files(
            table => '{table}',
            strategy => 'sort',
            sort_order => 'order_date ASC NULLS LAST, customer_id ASC',
            where => 'order_date >= current_date() - INTERVAL 30 DAYS',
            options => map(
                'target-file-size-bytes', '134217728',

#
# 1. MICRO-BATCH INGESTION WITHOUT COMPACTION
#    • Writing every 5 minutes → 288 write operations per table per day
#    • Each write creates files matching the parallelism level
#    • 288 writes × 10 files avg = 2,880 files/day per table
#    • 6 tables × 2,880 × 180 days = 3.1M files (theoretical max)
#
# 2. NO FILE SIZE MONITORING
#    • Average file size: 2.3 MB (target should be 128-256 MB)
#    • Total data volume: ~4.8 TB across 2.1M files
#    • If properly compacted: ~38,000 files (at 128 MB each)
#    • File count was 55x higher than optimal

#    • Iceberg manifest files track every data file

#    • Query planning must read ALL manifests to build scan plan

# Emergency compaction procedure (during incident)
from pyspark.sql import SparkSession
from concurrent.futures import ThreadPoolExecutor
import logging

logger = logging.getLogger("compaction-emergency")

def emergency_compaction(spark: SparkSession, table: str):
    """
    Emergency compaction for severely fragmented tables.
    Strategy: compact partition-by-partition to avoid OOM on full-table plan.
    """

    # Step 1: Get list of partitions with excessive file counts
    partitions = spark.sql(f"""
        SELECT partition, file_count, total_size_mb
        FROM (
            SELECT
                partition,
                COUNT(*) as file_count,
                SUM(file_size_in_bytes) / 1048576 as total_size_mb
            FROM lakehouse.{table}.files
            GROUP BY partition
        )
        WHERE file_count > 100
        ORDER BY file_count DESC
    """).collect()

    logger.info(f"Found {len(partitions)} partitions needing compaction")

    # Step 2: Compact each partition individually (avoids full-table plan)
    for idx, part in enumerate(partitions):
        partition_filter = part["partition"]
        file_count = part["file_count"]

        logger.info(
            f"[{idx+1}/{len(partitions)}] Compacting partition "
            f"{partition_filter} ({file_count} files)"
        )

        try:
            spark.sql(f"""
                CALL lakehouse.system.rewrite_data_files(
                    table => '{table}',
                    strategy => 'binpack',
                    where => "{partition_filter}",
                    options => map(
                        'target-file-size-bytes', '134217728',
                        'min-input-files', '5',
                        'max-concurrent-file-group-rewrites', '5',
                        'partial-progress.enabled', 'true',
                        'partial-progress.max-commits', '5'
                    )
                )
            """)
        except Exception as e:
            logger.error(f"Failed to compact {partition_filter}: {e}")
            continue

    # Step 3: Expire old snapshots (free metadata bloat)
    spark.sql(f"""
        CALL lakehouse.system.expire_snapshots(
            table => '{table}',
            older_than => TIMESTAMP '2024-03-01T00:00:00Z',
            retain_last => 5,
            max_concurrent_deletes => 100
        )
    """)

    # Step 4: Rewrite manifests (consolidate manifest files)
    spark.sql(f"""
        CALL lakehouse.system.rewrite_manifests(
            table => '{table}'
        )
    """)

    logger.info(f"Compaction complete for {table}")

Prevention: Automated Compaction Service

# Production compaction service (runs continuously)
# Monitors all tables and triggers compaction when thresholds are breached

class CompactionService:
    """
    Automated compaction service for lakehouse tables.
    Runs as a persistent service, monitoring table health metrics.
    """

    THRESHOLDS = {
        "max_files_per_partition": 200,
        "min_avg_file_size_mb": 64,
        "max_snapshots": 100,
        "max_orphan_age_days": 3,
        "compaction_interval_hours": 4,
    }

    def __init__(self, spark: SparkSession, tables: list):
        self.spark = spark
        self.tables = tables

    def check_table_health(self, table: str) -> dict:
        """Assess table health and return metrics."""
        metrics = self.spark.sql(f"""
            SELECT
                COUNT(*) as total_files,
                AVG(file_size_in_bytes) / 1048576 as avg_file_size_mb,
                MIN(file_size_in_bytes) / 1048576 as min_file_size_mb,
                MAX(file_size_in_bytes) / 1048576 as max_file_size_mb,
                SUM(CASE WHEN file_size_in_bytes < 16777216 THEN 1 ELSE 0 END) as small_files,
                COUNT(DISTINCT partition) as partition_count
            FROM lakehouse.{table}.files
        """).first()

        snapshot_count = self.spark.sql(f"""
            SELECT COUNT(*) as cnt FROM lakehouse.{table}.snapshots
        """).first()["cnt"]

        return {
            "table": table,
            "total_files": metrics["total_files"],
            "avg_file_size_mb": metrics["avg_file_size_mb"],
            "small_files": metrics["small_files"],
            "small_file_ratio": metrics["small_files"] / max(metrics["total_files"], 1),
            "snapshot_count": snapshot_count,
            "needs_compaction": (
                metrics["avg_file_size_mb"] < self.THRESHOLDS["min_avg_file_size_mb"]
                or metrics["small_files"] > 1000
            ),
            "needs_snapshot_expiry": snapshot_count > self.THRESHOLDS["max_snapshots"]
        }

    def run_maintenance_cycle(self):
        """Run one maintenance cycle across all monitored tables."""
        for table in self.tables:
            health = self.check_table_health(table)

            if health["needs_compaction"]:
                logger.info(f"Compacting {table}: {health['small_files']} small files")
                self._compact_table(table)

            if health["needs_snapshot_expiry"]:
                logger.info(f"Expiring snapshots for {table}: {health['snapshot_count']}")
                self._expire_snapshots(table)

            # Always remove orphans
            self._remove_orphans(table)

            # Emit metrics for monitoring
            self._emit_metrics(health)

Delta Lake MERGE (Upsert Pattern)

-- Delta Lake MERGE: idempotent upsert from Bronze to Silver
-- Handles inserts, updates, and soft deletes in a single statement

MERGE INTO silver.orders AS target
USING (
    -- Source: deduplicated Bronze changes since last checkpoint
    WITH ranked_changes AS (
        SELECT *,
            ROW_NUMBER() OVER (
                PARTITION BY order_id
                ORDER BY _ingested_at DESC, _cdc_timestamp DESC
            ) AS _rank
        FROM bronze.orders
        WHERE _ingested_at > '{{ last_processed_timestamp }}'
    )
    SELECT * FROM ranked_changes WHERE _rank = 1
) AS source
ON target.order_id = source.order_id

-- Update existing orders (only if source is newer)
WHEN MATCHED
    AND source._cdc_operation = 'UPDATE'
    AND source._cdc_timestamp > target._cdc_timestamp
THEN UPDATE SET
    target.status = source.status,
    target.total_amount = source.total_amount,
    target.ship_date = source.ship_date,
    target._cdc_operation = source._cdc_operation,
    target._cdc_timestamp = source._cdc_timestamp,
    target._processed_at = current_timestamp()

-- Soft delete (mark as deleted, don't remove)
WHEN MATCHED
    AND source._cdc_operation = 'DELETE'
THEN UPDATE SET
    target.status = 'deleted',
    target._cdc_operation = 'DELETE',
    target._cdc_timestamp = source._cdc_timestamp,
    target._processed_at = current_timestamp()

-- Insert new orders
WHEN NOT MATCHED
    AND source._cdc_operation IN ('INSERT', 'UPDATE')
THEN INSERT (
    order_id, customer_id, order_date, ship_date,
    status, total_amount, currency, region, country,
    _source_system, _cdc_operation, _cdc_timestamp, _processed_at, _batch_id
)
VALUES (
    source.order_id, source.customer_id, source.order_date, source.ship_date,
    source.status, source.total_amount, source.currency, source.region, source.country,
    source._source_system, source._cdc_operation, source._cdc_timestamp,
    current_timestamp(), '{{ batch_id }}'
);

-- Post-merge: optimize recently written files
OPTIMIZE silver.orders
WHERE order_date >= current_date() - INTERVAL 7 DAYS
ZORDER BY (customer_id, order_date);

Common Mistakes

1. No Compaction Strategy

Mistake: Teams deploy ingestion pipelines without automated compaction, leading to millions of small files that degrade query performance exponentially over time.

Fix: Implement compaction as a first-class service from day one. Schedule bin-packing to run every 4-6 hours on hot tables, with alerts on average file size and total file count.

2. Over-Partitioning

Mistake: Partitioning by high-cardinality columns (e.g., user_id, session_id) creates thousands of partitions with tiny files in each.

Fix: Partition by low-cardinality time dimensions (day/month). Use bucketing or Z-ORDER for high-cardinality filter columns. Rule of thumb: each partition should contain at least 128 MB of data.

3. Treating Lakehouse Like a Database

Mistake: Running frequent single-row updates/deletes as you would with PostgreSQL. Each operation creates a new snapshot and potentially rewrites entire files.

Fix: Batch mutations. Collect changes in a staging area and apply them as a single MERGE operation. For Hudi, use MoR storage type for write-heavy tables.

4. Ignoring Schema Evolution

Mistake: Breaking downstream consumers by renaming columns, changing types, or dropping columns without coordination.

Fix: Use data contracts. Iceberg's ID-based schema evolution allows safe renames. Define breaking vs non-breaking changes in your governance policy. Version your schemas.

5. No Data Quality Gates Between Layers

Mistake: Propagating corrupt, incomplete, or duplicate data from Bronze through Silver to Gold without validation.

Fix: Implement quality gates at each layer transition. Bronze→Silver requires deduplication checks, null validation, and type casting. Silver→Gold requires referential integrity, business rule validation, and reconciliation with source systems.

6. Vendor Lock-In Through Proprietary Features

Mistake: Building deep dependencies on vendor-specific features (Databricks-only Delta features, Snowflake-specific SQL) that prevent multi-engine access.

Fix: Use the open-source core of your table format. Test that tables are readable by at least two engines (e.g., Spark + Trino). Keep proprietary features at the compute layer, not the storage layer.

7. Skipping Metadata Catalog

Mistake: Building a lakehouse with hundreds of tables but no discovery mechanism. Teams cannot find existing data and create redundant datasets.

Fix: Deploy a metadata catalog (DataHub, Unity Catalog, OpenMetadata) early. Automate metadata collection from table format metadata, dbt docs, and pipeline orchestrators.

8. No Cost Attribution

Mistake: Running a lakehouse at $500K/year in cloud costs with no visibility into which teams, tables, or pipelines drive the spend.

Fix: Implement cost tagging from day one. Tag all resources (S3 prefixes, compute jobs, catalog entries) with team/domain ownership. Build cost dashboards that show spend per table and per pipeline.

9. Mixing Governance Levels in One Table

Mistake: Storing PII and non-PII data in the same table without column-level access controls, making it impossible to grant broad read access.

Fix: Design tables with governance boundaries in mind. Either use column-level masking (Unity Catalog, Trino access control) or separate sensitive columns into restricted tables joined by foreign key.

10. Ignoring Time Zones

Mistake: Ingesting timestamps in local time zones without standardizing to UTC. This causes incorrect joins, duplicate windows, and wrong aggregation boundaries in a global organization.

Fix: Convert all timestamps to UTC at the Bronze→Silver boundary. Store the original timezone as a separate column if needed for display. Use event_time_utc for all partitioning and windowing.

Key Architecture Trade-offs

  • Freshness vs Cost: Real-time ingestion (Flink CDC every second) costs 5-10x more in compute than hourly micro-batch. Most BI use cases do not need sub-minute freshness. Match ingestion frequency to actual business SLAs, not aspirational ones.
  • Normalization vs Denormalization: Silver layer should be normalized (single source of truth per entity). Gold layer should be denormalized (pre-joined for query performance). This increases storage slightly but dramatically reduces query complexity and cost.
  • Open format vs Managed service: Open formats (Iceberg on S3) give maximum flexibility but require operational investment. Managed services (Snowflake, BigQuery) handle operations but lock you in. Hybrid approach: use open formats for the platform, with managed OLAP engines as acceleration layers.
  • Governance strictness vs Developer velocity: Strict governance (every column tagged, every access approved, every change reviewed) slows innovation. Too-loose governance creates compliance risks and data quality issues. Implement governance in tiers: strict for Gold/PII, moderate for Silver, minimal for Bronze/sandbox.
  • Compaction frequency vs Write amplification: Frequent compaction keeps files optimal but adds compute cost and write amplification. Infrequent compaction saves compute but degrades read performance. Balance: compact when small file ratio exceeds 30% or average file size drops below 64 MB.

Follow-up Questions

Senior candidates should be prepared for these deep-dive follow-ups:

Architecture & Design

  • "How would you handle schema conflicts when 50 microservices are publishing to your Bronze layer?" — Schema registry (Confluent, Glue) with backward/forward compatibility rules. Schema-on-write validation at ingestion. Breaking changes require versioned topics.
  • "Your CEO wants a real-time dashboard showing revenue by region, updated every 10 seconds. How do you architect this?" — Don't query the lakehouse at 10s intervals. Use a streaming pipeline (Flink) that maintains materialized state in a serving layer (Redis, ClickHouse, or Pinot). Lakehouse is the source of truth for reprocessing, not the serving layer.
  • "How do you handle late-arriving data that needs to update already-computed Gold aggregates?" — Re-aggregate affected time windows. Use watermarks to define "late" cutoff. For extreme late arrivals, implement a reconciliation job that periodically recomputes Gold from Silver for the last N days.

Table Formats & Storage

  • "Explain how Iceberg handles concurrent writers without locks." — Optimistic concurrency: each writer reads the current metadata pointer, computes changes, and attempts an atomic swap of the metadata file reference in the catalog. If another writer committed first, the operation retries (validating no conflicting changes to the same files).
  • "A table has 10 PB of data and you need to change the partition scheme. What are your options?" — Iceberg: partition evolution (coexist old + new schemes, zero rewrite). Delta/Hudi: must rewrite all data (prohibitively expensive at 10 PB). Alternative: create a new table with the new scheme and backfill incrementally over weeks.
  • "How does Z-ORDER actually work? Why is it better than sorting on one column?" — Z-ORDER interleaves bits from multiple columns into a single value using a space-filling curve. This clusters data along multiple dimensions simultaneously, so filters on any subset of Z-ORDER columns benefit from data skipping (min/max statistics).

Operations & Production

  • "You deployed a bad transformation that corrupted Silver data for the last 3 hours. How do you recover?" — Time travel: restore the table to the last known-good snapshot. Replay the correction from Bronze (which is immutable). Notify downstream consumers via data quality alerts.
  • "How do you test lakehouse pipeline changes before deploying to production?" — Iceberg branching (catalog-level branches/tags), or environment-level isolation with shared Bronze. Run the new pipeline version on a branch, compare outputs with production, promote once validated.
  • "Your Spark job writing to Iceberg occasionally fails with 'CommitFailedException.' Why?" — Optimistic concurrency conflict. Two jobs modified overlapping files concurrently. Fix: increase retry count, reduce job overlap (schedule sequentially or partition workload), use Iceberg's conflict resolution policies.

Governance & Compliance

  • "A user exercises their GDPR Right to Erasure. Walk me through the technical implementation." — Queue deletion request → identify all tables containing user data (lineage graph) → execute row-level DELETE across Bronze/Silver/Gold → expire affected snapshots → verify deletion via audit query → generate compliance certificate.
  • "How do you prevent a junior analyst from accidentally querying raw PII data?" — Catalog-enforced access control. PII columns tagged at ingestion. Default policy masks PII for all non-privileged roles. Column-level access grants require approval workflow with data steward review.

Cost & Performance

  • "Your lakehouse costs $2M/year and the CFO wants 40% reduction. Where do you cut?" — Audit: (1) Storage tiering for cold Bronze data (30-40% storage savings), (2) Spot instances for Spark jobs (60-70% compute savings), (3) Compaction to reduce API call costs, (4) Decommission unused Gold tables (usage-based cleanup), (5) Right-size compute clusters based on actual utilization.
  • "Query A ran in 5 seconds last week but now takes 5 minutes. What changed?" — Check: (1) File count growth (compaction needed?), (2) Partition values (new data added to scanned partitions?), (3) Statistics stale (column stats not updated after schema change?), (4) Concurrent workload (resource contention?), (5) Plan regression (engine upgrade changed optimizer behavior?).

Summary

Key Takeaways

  1. A lakehouse is an architecture, not a product. It combines cheap object storage with open table formats (Iceberg/Delta/Hudi) to deliver warehouse-like capabilities without warehouse-like costs or lock-in.
  2. Open table formats are the enabling technology. They add ACID transactions, schema evolution, time travel, and performance optimizations on top of Parquet files in S3. Iceberg is emerging as the industry standard for multi-engine interoperability.
  3. Medallion architecture provides progressive refinement. Bronze preserves raw data for reprocessing. Silver cleanses and conforms. Gold aggregates for consumption. Data contracts enforce quality between layers.
  4. Governance must be designed in, not bolted on. Centralized catalog, column-level access control, PII tagging, lineage tracking, and audit logging are non-negotiable for a production platform.
  5. Operational excellence separates good lakehouses from data swamps. Automated compaction, snapshot expiration, orphan cleanup, and monitoring are not optional — they are required for the platform to function at scale.
  6. Cost optimization is a design concern. Storage tiering, compute auto-scaling (with spot instances), and file size management can reduce costs by 60-80% compared to naive configurations.
  7. Choose your table format based on ecosystem alignment. Iceberg for multi-engine/vendor-neutral. Delta for Databricks-centric. Hudi for CDC-heavy workloads. All three are converging in capability.
  8. Ingestion patterns must match business SLAs. Not everything needs real-time. Match CDC (seconds), micro-batch (minutes), and full-load (hours/daily) to actual freshness requirements.
  9. Plan for operations from day zero. The 2M small files incident is not hypothetical — it happens to every lakehouse that does not implement compaction proactively. Build the maintenance service before it becomes an emergency.
  10. The lakehouse does not replace everything. Use specialized serving engines (ClickHouse, Pinot, Redis) for sub-second interactive workloads. The lakehouse is the platform of record; serving layers are acceleration tiers.

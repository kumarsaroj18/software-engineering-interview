Hard Idempotency Retries Distributed Systems

Duplicate Records After Enabling Retries — How Would You Fix It?

Key Takeaway: Retries are necessary for resilience, but without idempotency guarantees, every retry is a potential duplicate. The fix is never "disable retries" — it's making your writes idempotent through idempotency keys, database constraints, and conditional operations.

Interviewer's Intent

What they're really testing:

  • Do you understand that retries and idempotency are inseparable concerns?
  • Can you design systems that are safe to retry at every layer (client, server, message broker)?
  • Do you know the trade-offs between different idempotency strategies?
  • Have you dealt with this in production — payment systems, order processing, event-driven architectures?
  • Can you think across network boundaries — client retries, load balancer retries, framework retries?

This question tests whether you understand that at-least-once delivery is the reality of distributed systems. Networks fail, pods restart, timeouts trigger retries — and if your service isn't prepared, every retry creates a duplicate. The interviewer wants to see that you think about this from the ground up, not as an afterthought.

60-Second Interview Answer

Use this in the interview:

"Retries without idempotency guarantees are a recipe for duplicates. When we enabled Spring Retry, network timeouts that previously caused failures now triggered 3 retries — each potentially creating a new record because the server couldn't distinguish a retry from a new request.

The fix is multi-layered:

1. Idempotency keys — client generates a unique key per logical operation. Server stores it and returns the cached result on duplicates.
2. Database unique constraints — a natural business key (order_id + item_id) or a dedicated idempotency_key column prevents duplicates at the storage layer.
3. Conditional writes — use INSERT ... ON CONFLICT DO NOTHING or compare-and-swap with version columns.
4. Transactional outbox — for event publishing, store the event in the same transaction as the write, then publish asynchronously.

The critical insight is that retries can happen at every layer — HTTP client, load balancer, Spring Retry, Kafka consumer. Each layer needs its own idempotency story."

The fundamental problem: ambiguous failures 
  Scenario: Client sends POST /orders

  Case 1: Request never reached server
  ──────────────────────────────────────
  Client ──✗── Server         Result: No record created
           ↑                  Safe to retry? ✅ YES
     Network failure

  Case 2: Server processed, response lost
  ──────────────────────────────────────────
  Client ──── Server          Result: Record CREATED
         ✗──                  Safe to retry? ❌ NO (duplicate!)
           ↑
     Response lost (timeout)

  Case 3: Server crashed mid-processing
  ──────────────────────────────────────────
  Client ──── Server          Result: Unknown (partial write?)
         ✗──                  Safe to retry? ⚠️ DEPENDS
           ↑
     Connection reset

  THE PROBLEM: The client CANNOT distinguish Case 1 from Case 2.
  From the client's perspective, both look like a timeout.

Key Insight: In distributed systems, failure is ambiguous. A timeout doesn't tell you whether the operation succeeded or failed. This is why you must design for safe retries from the start — not bolt them on later.

@Service
public class PaymentService {

    @Retryable(
        retryFor = {TransientException.class, SocketTimeoutException.class},
        noRetryFor = {ValidationException.class},
        maxAttempts = 3,
        backoff = @Backoff(delay = 1000, multiplier = 2, maxDelay = 10000)
    )
    public PaymentResult charge(PaymentRequest request) {
        return paymentGateway.process(request);
    }

    @Recover
    public PaymentResult chargeFallback(TransientException e, PaymentRequest request) {
        log.error("Payment failed after all retries for request: {}", request.getId(), e);
        return PaymentResult.failed("Service temporarily unavailable");
    }

    // A separate @Recover is needed for each retried exception type
    @Recover
    public PaymentResult chargeFallback(SocketTimeoutException e, PaymentRequest request) {
        log.error("Payment timed out after all retries for request: {}", request.getId(), e);
        return PaymentResult.failed("Service temporarily unavailable");
    }
}

The critical ordering: @Retryable OUTSIDE @Transactional 
// ❌ WRONG: Retry inside transaction
// Transaction starts → attempt 1 fails → tx marked for rollback
// → attempt 2 runs inside a DEAD transaction → always fails
@Service
public class OrderService {

    @Transactional
    @Retryable(maxAttempts = 3) // ❌ Retries inside the same transaction!
    public Order createOrder(OrderRequest request) {
        Order order = orderRepository.save(new Order(request));
        inventoryService.reserve(order); // Throws on timeout
        return order;
    }
}

// ✅ CORRECT: Retry wraps the transaction — use separate beans (safest)
// Each retry gets a FRESH transaction, with no aspect ordering ambiguity.
// See the separate-beans pattern below.

Critical: The ordering of AOP aspects matters. Both @Retryable and @Transactional default to Ordered.LOWEST_PRECEDENCE, so when placed on the same method the execution order is undefined. The safest approach is to separate the concerns: put @Retryable on a method in one bean that calls a @Transactional method on a different bean. If you must use both on the same class, set explicit @Order values and verify with: logging.level.org.springframework.retry=DEBUG

// Safest pattern: separate beans, no ordering ambiguity
@Service
public class OrderFacade {

    @Autowired
    private OrderService orderService; // separate bean

    @Retryable(
        retryFor = TransientException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 500, multiplier = 2)
    )
    public Order createOrderWithRetry(OrderRequest request) {
        return orderService.createOrder(request); // each retry = fresh transaction
    }
}

public class OrderService {

    @Transactional
    public Order createOrder(OrderRequest request) {

Spring Retry with RetryTemplate — programmatic control 
@Configuration
public class RetryConfig {

    @Bean
    public RetryTemplate retryTemplate() {
        return RetryTemplate.builder()
            .maxAttempts(3)
            .exponentialBackoff(1000, 2.0, 10000)
            .retryOn(TransientDataAccessException.class)
            .retryOn(OptimisticLockingFailureException.class)
            .traversingCauses() // Check cause chain, not just top-level exception
            .withListener(new RetryListenerSupport() {
                @Override
                public <T, E extends Throwable> void onError(
                        RetryContext ctx, RetryCallback<T, E> callback, Throwable t) {
                    log.warn("Retry attempt {} failed: {}", 
                        ctx.getRetryCount(), t.getMessage());
                    meterRegistry.counter("retry.attempts", 
                        "method", String.valueOf(ctx.getAttribute("method")),
                        // null-safe: getAttribute returns null if not set
                        "attempt", String.valueOf(ctx.getRetryCount()),
                        "exception", t.getClass().getSimpleName()).increment();
                }
            })
            .build();
    }
}

@Service
public class OrderService {

    private final RetryTemplate retryTemplate;

    public Order createOrderWithRetry(OrderRequest request) {
        return retryTemplate.execute(context -> {
            context.setAttribute("method", "createOrder");
            return createOrder(request);
        }, context -> {
            // Recovery callback — all retries exhausted
            log.error("All retries exhausted for order: {}", request.getId());
            throw new OrderCreationFailedException(request.getId(), context.getLastThrowable());
        });
    }
}

Why Duplicates Happen — The Mechanics

Timeline of a duplicate creation 
  Timeline: Duplicate order creation with retries enabled
  ═══════════════════════════════════════════════════════

  t=0ms    Client sends POST /orders {item: "laptop", qty: 1}
  t=50ms   Server begins processing
  t=100ms  Server inserts: INSERT INTO orders(id, item, qty) VALUES(gen_id(), 'laptop', 1)
  t=150ms  Server calls payment service...
  t=5000ms Payment service is slow — client hits 5s timeout
  
  ─── CLIENT PERSPECTIVE: "Request failed (timeout)" ───
  
  t=5001ms Client RETRIES: POST /orders {item: "laptop", qty: 1}  ← SAME request!
  t=5050ms Server begins processing (doesn't know this is a retry)
  t=5100ms Server inserts: INSERT INTO orders(id, item, qty) VALUES(gen_id(), 'laptop', 1)
           ↑ DUPLICATE! New ID generated — DB sees this as a new record
  
  t=5200ms Meanwhile, original request's payment succeeds!
  t=5300ms Original request commits: order #1 ← PAID
  t=5400ms Retry request's payment also succeeds
  t=5500ms Retry request commits: order #2 ← ALSO PAID!

  Result: Customer charged TWICE, two orders shipped.
All the ways duplicates sneak in
Retry Source When It Happens Example Visibility
Client retry User clicks "Submit" twice, or JS retry logic Double-click on "Place Order" button High (obvious UX issue)
Load balancer retry 502/503 from one instance, LB retries on another Some load balancers or service meshes (e.g., Envoy, Istio) retry on connection errors — behavior depends on configuration Low (silent, logged as separate request)
Spring Retry Transient exception triggers @Retryable DB deadlock → retry → re-insert Medium (visible in retry logs)
HTTP client retry Only when explicitly configured — RestTemplate and WebClient do not retry by default Connection reset to downstream service (if retry configured on Feign/WebClient) Low (buried in HTTP client config)
Kafka consumer retry Consumer fails, offset not committed, message redelivered OOM during processing → consumer restart Medium (consumer lag visible)
Kubernetes restart Pod killed during processing, request retried by client OOMKilled during order processing Low (pod events only)

Idempotency Patterns

What makes an operation idempotent?

Definition: An operation is idempotent if executing it multiple times produces the same result as executing it once. Formally: f(f(x)) = f(x)

HTTP Method Idempotent? Safe? Example
GET ✅ Yes ✅ Yes Read orders — no side effects
PUT ✅ Yes ❌ No Set order status to SHIPPED (same result each time)
DELETE ✅ Yes ❌ No Delete order #123 (second delete is a no-op)
POST ❌ No ❌ No Create order — each call may create new record!
PATCH ⚠️ Depends ❌ No balance += 10 (not idempotent) vs balance = 100 (idempotent)
Idempotency strategies — choosing the right one

No universal ranking: The right strategy depends on the business operation. A database unique constraint prevents duplicate inserts but cannot replay a previous response. An idempotency key table can do both — which is why payment APIs (Stripe, PayPal, Adyen) universally use dedicated idempotency stores rather than relying on constraints alone.

  ┌─────────────────────────────────────────────────────────────────┐
  │ Database unique constraint (natural key)                         │
  │    "INSERT ... ON CONFLICT DO NOTHING"                           │
  │    Prevents duplicate inserts; cannot replay previous response   │
  │    Best for: simple CRUD where dedup is sufficient               │
  ├─────────────────────────────────────────────────────────────────┤
  │ Idempotency key table (server-side dedup)                        │
  │    Store (key → response) mapping in same transaction            │
  │    Prevents duplicates AND replays exact original response       │
  │    Best for: payment APIs, any operation needing response replay  │
  ├─────────────────────────────────────────────────────────────────┤
  │ Conditional write (compare-and-swap)                             │
  │    "UPDATE ... WHERE version = X" / "IF NOT EXISTS"              │
  │    Best for: updates and state transitions, not creates          │
  ├─────────────────────────────────────────────────────────────────┤
  │ Client-generated ID (UUID)                                       │
  │    Client creates UUID, sends with request                       │
  │    Widely used and effective when clients are trusted            │
  │    Best for: mobile apps, SPAs, trusted first-party clients      │
  ├─────────────────────────────────────────────────────────────────┤
  │ Deduplication window (time-based fingerprint)                    │
  │    Reject duplicate payloads within N minutes                    │
  │    Heuristic only — not true idempotency (see fingerprinting)    │
  │    Best for: fallback when clients cannot send explicit keys      │
  └─────────────────────────────────────────────────────────────────┘

// 1. Idempotency key entity
@Entity
@Table(name = "idempotency_keys")
public class IdempotencyKey {

    @Id
    private String key;

    @Enumerated(EnumType.STRING)
    private Status status; // PROCESSING, COMPLETE, FAILED

    @Column(columnDefinition = "TEXT")
    private String responseBody;

    private Integer responseStatus;
    private String responseContentType;

    @Column(name = "created_at")
    private Instant createdAt;

    @Column(name = "expires_at")
    private Instant expiresAt;

    public enum Status {
        PROCESSING, COMPLETE, FAILED
    }
}
-- Schema with proper indexing
CREATE TABLE idempotency_keys (
    key             VARCHAR(255) PRIMARY KEY,
    status          VARCHAR(20) NOT NULL DEFAULT 'PROCESSING',
    response_body   TEXT,
    response_status INTEGER,
    response_content_type VARCHAR(100),
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMP NOT NULL DEFAULT (NOW() + INTERVAL '24 hours')
);

-- Separate index for cleanup (PostgreSQL does not support inline INDEX in CREATE TABLE)
CREATE INDEX idx_idempotency_expires ON idempotency_keys (expires_at);

-- Scheduled cleanup (run every hour)
DELETE FROM idempotency_keys WHERE expires_at < NOW();
// 2. Idempotency interceptor (Spring HandlerInterceptor)
@Component
public class IdempotencyInterceptor implements HandlerInterceptor {

    private static final String IDEMPOTENCY_HEADER = "Idempotency-Key";
    private final IdempotencyKeyRepository repository;

    @Override
    public boolean preHandle(HttpServletRequest request, 
                            HttpServletResponse response, 
                            Object handler) throws Exception {
        
        // Only apply to non-idempotent methods
        if (!"POST".equalsIgnoreCase(request.getMethod())) {
            return true;
        }

        String key = request.getHeader(IDEMPOTENCY_HEADER);
        if (key == null || key.isBlank()) {
            return true; // No idempotency key — proceed normally
        }

        Optional<IdempotencyKey> existing = repository.findById(key);
        
        if (existing.isPresent()) {
            IdempotencyKey record = existing.get();
            
            switch (record.getStatus()) {
                case COMPLETE:
                    // Return cached response — no duplicate processing
                    response.setStatus(record.getResponseStatus());
                    response.setContentType(record.getResponseContentType());
                    response.getWriter().write(record.getResponseBody());
                    return false; // Short-circuit — don't call controller
                    
                case PROCESSING:
                    // Another request with same key is still in-flight
                    response.setStatus(HttpStatus.CONFLICT.value());
                    response.getWriter().write(
                        "{\"error\": \"Request with this idempotency key is still processing\"}");
                    return false;
                    
                case FAILED:
                    // Previous attempt failed — allow retry
                    repository.delete(record);
                    break;
            }
        }

        // First time seeing this key — create PROCESSING record
        IdempotencyKey newKey = new IdempotencyKey();
        newKey.setKey(key);
        newKey.setStatus(IdempotencyKey.Status.PROCESSING);
        newKey.setCreatedAt(Instant.now());
        newKey.setExpiresAt(Instant.now().plus(Duration.ofHours(24)));
        
        try {
            repository.save(newKey);
        } catch (DataIntegrityViolationException e) {
            // Race condition — another thread just created it
            response.setStatus(HttpStatus.CONFLICT.value());
            response.getWriter().write(
                "{\"error\": \"Duplicate request detected\"}");
            return false;
        }

        // Store key in request attribute for post-processing
        request.setAttribute("idempotencyKey", key);
        return true;
    }
    // Note: a more scalable alternative to findById + save is a single
    // INSERT ... ON CONFLICT DO NOTHING, which avoids one round-trip
    // and eliminates the race window between the two operations.
}

// 3. Response wrapper to capture and store the response
// ⚠️ Production note: if the controller throws a 500, beforeBodyWrite may
// not be called, leaving the row in PROCESSING indefinitely. Add a
// HandlerInterceptor.afterCompletion() or @ControllerAdvice exception handler
// to mark the key as FAILED on error, so clients can safely retry.
@Component
public class IdempotencyResponseAdvice implements ResponseBodyAdvice<Object> {

    private final IdempotencyKeyRepository repository;

    @Override
    public boolean supports(MethodParameter param, Class converterType) {
        return true;
    }

    @Override
    public Object beforeBodyWrite(Object body, MethodParameter param,
                                  MediaType contentType, Class converterType,
                                  ServerHttpRequest request, ServerHttpResponse response) {
        
        String key = ((ServletServerHttpRequest) request)
            .getServletRequest().getAttribute("idempotencyKey") != null 
            ? (String) ((ServletServerHttpRequest) request)
                .getServletRequest().getAttribute("idempotencyKey") 
            : null;
            
        if (key != null) {
            repository.findById(key).ifPresent(record -> {
                record.setStatus(IdempotencyKey.Status.COMPLETE);
                record.setResponseBody(toJson(body));
                record.setResponseStatus(
                    ((ServletServerHttpResponse) response).getServletResponse().getStatus());
                record.setResponseContentType(contentType.toString());
                repository.save(record);
            });
        }
        
        return body;
    }
}
Stripe's approach to idempotency (industry standard) 
// How Stripe handles idempotency — simplified recreation
// Reference: https://stripe.com/docs/api/idempotent_requests

@RestController
@RequestMapping("/api/payments")
public class PaymentController {

    @PostMapping
    public ResponseEntity<PaymentResponse> createPayment(
            @RequestHeader(value = "Idempotency-Key", required = true) String idempotencyKey,
            @RequestBody PaymentRequest request) {
        
        // Stripe's rules:
        // 1. Key is scoped to the API key (multi-tenant safe)
        // 2. Key expires after 24 hours
        // 3. If request body differs for same key → 400 error
        // 4. If still processing → 409 Conflict
        // 5. If complete → return the EXACT original status code and response body
        //    (not just a generic 200 — if the original returned 201, the replay returns 201)
        
        return paymentService.processIdempotent(idempotencyKey, request);
    }
}

@Service
public class PaymentService {

    @Transactional
    public ResponseEntity<PaymentResponse> processIdempotent(
            String key, PaymentRequest request) {
        
        // Lock row to prevent race conditions
        Optional<IdempotencyKey> existing = 
            idempotencyRepo.findByKeyForUpdate(key); // SELECT ... FOR UPDATE
        
        if (existing.isPresent()) {
            IdempotencyKey record = existing.get();
            
            // Stripe validates request body matches — prevents key reuse
            String requestFingerprint = sha256(toJson(request));
            if (!requestFingerprint.equals(record.getRequestFingerprint())) {
                throw new IdempotencyKeyReusedException(
                    "Idempotency key already used with different parameters");
            }
            
            if (record.getStatus() == Status.COMPLETE) {
                return ResponseEntity
                    .status(record.getResponseStatus())
                    .body(fromJson(record.getResponseBody(), PaymentResponse.class));
            }
        }
        
        // Process the payment (first time or retry after failure)
        PaymentResponse result = processPayment(request);
        
        // Store result atomically
        saveIdempotencyResult(key, request, result);
        
        return ResponseEntity.status(HttpStatus.CREATED).body(result);
    }
}

Database Unique Constraints — The Last Line of Defense

Natural keys vs surrogate keys for deduplication

Deduplication vs Idempotency: INSERT ... ON CONFLICT DO NOTHING prevents duplicate rows — it is deduplication. True idempotency also means replaying the exact original response to the caller. A unique constraint alone cannot do that. For operations where the client needs the original response (e.g., the created order ID), pair the constraint with an idempotency key table.

CREATE TABLE orders (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    cart_id         BIGINT NOT NULL,
    amount          DECIMAL(10,2) NOT NULL,
    status          VARCHAR(20) NOT NULL,
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    
    -- Natural dedup: one order per cart per user
    UNIQUE (user_id, cart_id)
);

-- Insert with conflict handling (PostgreSQL)
INSERT INTO orders (user_id, cart_id, amount, status)
VALUES (123, 456, 99.99, 'CREATED')
ON CONFLICT (user_id, cart_id) DO NOTHING
RETURNING id;
-- Returns empty if duplicate — caller knows it was already created

-- Strategy 2: Idempotency key column
CREATE TABLE orders (
    id              BIGSERIAL PRIMARY KEY,
    idempotency_key VARCHAR(255) UNIQUE NOT NULL,  -- ← client-provided
    user_id         BIGINT NOT NULL,
    amount          DECIMAL(10,2) NOT NULL,
    status          VARCHAR(20) NOT NULL,
    created_at      TIMESTAMP NOT NULL DEFAULT NOW()
);

@Service
public class OrderService {

    @Transactional
    public OrderResult createOrder(String idempotencyKey, OrderRequest request) {
        // Check if already processed
        Optional<Order> existing = orderRepository.findByIdempotencyKey(idempotencyKey);
        if (existing.isPresent()) {
            log.info("Duplicate request detected: key={}", idempotencyKey);
            return OrderResult.alreadyExists(existing.get());
        }

        // Create order with idempotency key
        Order order = Order.builder()
            .idempotencyKey(idempotencyKey)
            .userId(request.getUserId())
            .amount(request.getAmount())
            .status(OrderStatus.CREATED)
            .build();

        try {
            order = orderRepository.saveAndFlush(order); // Force immediate INSERT
            return OrderResult.created(order);
        } catch (DataIntegrityViolationException e) {
            // Race condition: another thread inserted between our check and insert
            // This is fine — fetch and return the existing order
            Order existingOrder = orderRepository.findByIdempotencyKey(idempotencyKey)
                .orElseThrow(() -> new IllegalStateException("Constraint violation but no record found"));
            return OrderResult.alreadyExists(existingOrder);
        }
    }
}

public interface OrderRepository extends JpaRepository<Order, Long> {

        INSERT INTO orders (idempotency_key, user_id, amount, status, created_at)

        """, nativeQuery = true)
    int insertIfNotExists(@Param("key") String key, 
                          @Param("userId") Long userId,
                          @Param("amount") BigDecimal amount);
    // Returns 1 if inserted, 0 if duplicate
}

Transactional Outbox Pattern

The dual-write problem that the Outbox pattern solves 
  ❌ The Dual-Write Problem:
  ══════════════════════════

  @Transactional
  public void createOrder(Order order) {
      orderRepository.save(order);           // Write #1: Database
      kafkaTemplate.send("orders", event);   // Write #2: Kafka
  }

  What can go wrong:
  ┌─────────────────────────────────────────────────────────┐
  │ Scenario 1: DB succeeds, Kafka fails                     │
  │ → Order exists but no event published                    │
  │ → Downstream services never know about it                │
  │                                                          │
  │ Scenario 2: Kafka succeeds, DB rolls back                │
  │ → Event published for non-existent order                 │
  │ → Downstream services process phantom event              │
  │                                                          │
  │ Scenario 3: Both succeed, but app crashes before commit  │
  │ → DB rolls back (autocommit=false), Kafka already sent   │
  │ → Same as Scenario 2                                     │
  └─────────────────────────────────────────────────────────┘

  ✅ Outbox Pattern Solution:
  ════════════════════════════

  @Transactional  ← SINGLE atomic transaction
  public void createOrder(Order order) {
      orderRepository.save(order);           // Write #1: Database
      outboxRepository.save(outboxEvent);    // Write #2: Same Database (outbox table)
  }
  // Kafka is written LATER by a background poller or CDC

  ┌──────────────────────┐      ┌─────────────────────┐
  │ orders table         │      │ outbox_events table  │
  │                      │      │                      │
  │ id: 1               │      │ id: 1                │
  │ amount: 99.99       │      │ aggregate_id: 1      │
  │ status: CREATED     │      │ event_type: ORDER    │
  │                      │      │ payload: {...}       │
  │ (same transaction)   │      │ published: false     │
  └──────────────────────┘      └──────────┬───────────┘
                                           │
                         CDC/Poller reads ──┘
                                           │
                                           ▼
                                    ┌─────────────┐
                                    │   Kafka     │
                                    │  (eventual) │
                                    └─────────────┘

Outbox guarantees atomicity, not exactly-once delivery: The Outbox pattern ensures the database write and the event intent are committed together — the event will eventually be published. However, the publisher may deliver the event more than once (e.g., if it crashes after publishing but before marking the row as published). Consumers must still implement their own idempotency. Interviewers frequently ask this follow-up.

@Component
public class OutboxPublisher {

    @Scheduled(fixedDelay = 1000) // Poll every second
    @Transactional
    public void publishPendingEvents() {
        List<OutboxEvent> pending = outboxRepository
            .findTop100ByPublishedFalseOrderByCreatedAtAsc();
        
        for (OutboxEvent event : pending) {
            try {
                kafkaTemplate.send(
                    event.getAggregateType().toLowerCase() + ".events",
                    event.getAggregateId(),
                    event.getPayload()
                ).get(5, TimeUnit.SECONDS); // Synchronous send for simplicity.
                // Many production implementations use async publishing with
                // producer confirms to avoid blocking the polling thread.
                
                event.setPublished(true);
                event.setPublishedAt(Instant.now());
                outboxRepository.save(event);
            } catch (Exception e) {
                log.warn("Failed to publish event {}: {}", event.getId(), e.getMessage());
                break; // Preserve ordering — don't skip failed events
            }
        }
    }

    // Cleanup old published events
    @Scheduled(cron = "0 0 */6 * * *") // Every 6 hours
    @Transactional
    public void cleanupPublishedEvents() {
        Instant cutoff = Instant.now().minus(Duration.ofDays(7));
        int deleted = outboxRepository.deleteByPublishedTrueAndPublishedAtBefore(cutoff);
        log.info("Cleaned up {} published outbox events", deleted);
    }
}

Dead Letter Queue (DLQ) strategy for permanent failures 
@Configuration
public class KafkaRetryConfig {

    @Bean
    public DefaultErrorHandler errorHandler(KafkaTemplate<String, String> kafkaTemplate) {
        // Retry 3 times with backoff, then send to DLQ
        DeadLetterPublishingRecoverer recoverer = 
            new DeadLetterPublishingRecoverer(kafkaTemplate,
                (record, ex) -> new TopicPartition(
                    record.topic() + ".DLQ", record.partition()));

        DefaultErrorHandler handler = new DefaultErrorHandler(
            recoverer,
            new ExponentialBackOff(1000L, 2.0) // 1s, 2s, 4s
        );
        
        // Don't retry on these — send directly to DLQ
        handler.addNotRetryableExceptions(
            DeserializationException.class,
            ValidationException.class,
            NullPointerException.class
        );
        
        return handler;
    }
}

  One commonly recommended ordering of resilience patterns:
  ═════════════════════════════════════════════════════════

  Request ──▶ [Rate Limiter] ──▶ [Circuit Breaker] ──▶ [Retry] ──▶ [Timeout] ──▶ Service
                                        │                    │
                                        │ Open? ─── Fallback │ Max attempts? ─── @Recover
                                        │                    │
                                        
  Why this order matters:
  • Rate Limiter: Don't overwhelm the system — reject early
  • Circuit Breaker: Don't retry when service is known-down
  • Retry: Only retry transient failures when circuit is closed
  • Timeout: Each individual attempt has a deadline

Real Production Incident

The $47,000 duplicate charge incident

Severity: P0 — Financial loss, customer trust impact, regulatory reporting required

Context

E-commerce platform, Black Friday traffic. Team enabled Spring Retry on payment processing to handle increased gateway timeouts.

Timeline

  11:00 — Deployment: Added @Retryable(maxAttempts=3) to PaymentService.charge()
  11:30 — Traffic ramps up, payment gateway latency increases (P95: 2s → 8s)
  11:45 — Gateway starts timing out (5s timeout, 8s actual)
  11:46 — Retries kick in: 3 attempts × 1000 concurrent requests = 3000 charge attempts
  11:47 — Some original requests complete (delayed, not failed)
  11:48 — Retry attempts ALSO complete → duplicate charges
  12:15 — Customer support flooded with "charged twice" complaints
  12:30 — P0 declared, retries disabled (hotfix)
  13:00 — Damage assessment: 847 duplicate charges, $47,382 total

Root Cause

// The problematic code
@Service
public class PaymentService {

    @Retryable(maxAttempts = 3, backoff = @Backoff(delay = 1000))
    @Transactional
    public PaymentResult charge(Order order) {
        // ❌ Problem 1: No idempotency key sent to payment gateway
        PaymentResult result = paymentClient.charge(
            order.getAmount(), 
            order.getUserPaymentMethod()
        );
        
        // ❌ Problem 2: Each retry creates a NEW payment intent
        // because there's no deduplication on the gateway side
        
        Payment payment = new Payment(order.getId(), result.getTransactionId());
        paymentRepository.save(payment);
        
        return result;
    }
}

What Went Wrong

  1. No idempotency key sent to the payment gateway — each retry was a new charge
  2. Timeout ≠ failure — the original request was still being processed when the retry fired
  3. No deduplication at the database level — each payment got a new transaction ID
  4. @Retryable inside @Transactional — retry created a new transaction, not reusing the old one (correct ordering, but business logic was wrong)

Resolution

// Fixed implementation
@Service
public class PaymentService {

    @Retryable(
        retryFor = {SocketTimeoutException.class, ConnectionResetException.class},
        noRetryFor = {PaymentDeclinedException.class},
        maxAttempts = 3,
        backoff = @Backoff(delay = 2000, multiplier = 2)
    )
    @Transactional
    public PaymentResult charge(Order order) {
        // ✅ Fix 1: Generate deterministic idempotency key from the logical business operation
        // Keys should be derived from the business intent, not the retry attempt.
        String idempotencyKey = "order-" + order.getId() + "-charge";
        
        // ✅ Fix 2: Check if already charged (local dedup)
        Optional<Payment> existingPayment = paymentRepository
            .findByOrderIdAndStatus(order.getId(), PaymentStatus.COMPLETED);
        if (existingPayment.isPresent()) {
            return PaymentResult.alreadyCharged(existingPayment.get());
        }
        
        // ✅ Fix 3: Send idempotency key to gateway
        PaymentResult result = paymentClient.charge(
            ChargeRequest.builder()
                .amount(order.getAmount())
                .paymentMethod(order.getUserPaymentMethod())
                .idempotencyKey(idempotencyKey) // ← Gateway deduplicates!
                .build()
        );
        
        // ✅ Fix 4: Unique constraint on (order_id, status)
        Payment payment = new Payment(order.getId(), result.getTransactionId());
        paymentRepository.save(payment);
        
        return result;
    }
}

Preventive Measures Added

  • Mandatory idempotency key for all payment gateway calls (enforced by linter)
  • Database unique constraint: UNIQUE (order_id) with a partial index for completed payments — e.g., CREATE UNIQUE INDEX ON payments (order_id) WHERE status = 'COMPLETED' — avoids false conflicts if multiple statuses (FAILED, REFUNDED) are valid per order
  • Monitoring alert: "duplicate payment count > 0 in last 5 minutes"
  • Circuit breaker on payment gateway (open at 50% failure rate)
  • Increased gateway timeout from 5s to 15s (aligned with actual P99)

Pattern: Distributed lock for cross-service deduplication 
@Service
public class DistributedIdempotencyService {

    private final StringRedisTemplate redis;
    private final Duration lockTtl = Duration.ofMinutes(5);

    /**
     * Acquire a distributed lock for the idempotency key.
     * Returns true if this is the first processor, false if duplicate.
     */
    public boolean tryAcquire(String idempotencyKey) {
        Boolean acquired = redis.opsForValue().setIfAbsent(
            "idemp:" + idempotencyKey,
            "PROCESSING",  // sentinel value; replaced by JSON on completion
            lockTtl
        );
        return Boolean.TRUE.equals(acquired);
    }

    /**
     * Mark processing as complete (extend TTL for cached response).
     */
    public void markComplete(String idempotencyKey, String responseJson) {
        redis.opsForValue().set(
            "idemp:" + idempotencyKey,
            responseJson,
            Duration.ofHours(24) // Keep result for 24h
        );
    }

    /**
     * Release lock on failure (allow retry).
     * ⚠️ Unconditional delete() is unsafe: if the TTL expires and another
     * request acquires the lock, this delete would remove the new owner's lock.
     * Production implementations should use a token (e.g., a random value set
     * at acquire time) and only delete if the token matches — or use a library
     * like Redisson which handles this correctly with Lua scripts.
     */
    public void release(String idempotencyKey) {
        // Safe only if TTL has not expired and no other request has acquired the lock.
        // For production use, prefer Redisson RLock or a token-based check.
        redis.delete("idemp:" + idempotencyKey);
    }

    /**
     * Get cached response if already processed.
     * The stored value is a JSON response body (set by markComplete).
     * During processing, the key exists but maps to a sentinel value.
     */
    public Optional<String> getCachedResponse(String idempotencyKey) {
        String value = redis.opsForValue().get("idemp:" + idempotencyKey);
        // A completed entry starts with '{' (JSON); a processing sentinel is "PROCESSING"
        if (value != null && value.startsWith("{")) {
            return Optional.of(value);
        }
        return Optional.empty();
    }
}

// Usage in service
@Service
public class OrderService {

    @Transactional
    public OrderResult createOrder(String idempotencyKey, OrderRequest request) {
        // Check Redis first (fast path)
        Optional<String> cached = idempotencyService.getCachedResponse(idempotencyKey);
        if (cached.isPresent()) {
            return fromJson(cached.get(), OrderResult.class);
        }

        // Try to acquire the lock
        if (!idempotencyService.tryAcquire(idempotencyKey)) {
            throw new DuplicateRequestException("Request already being processed");
        }

        try {
            Order order = orderRepository.save(Order.from(request));
            OrderResult result = OrderResult.created(order);
            
            // Cache the result in Redis
            idempotencyService.markComplete(idempotencyKey, toJson(result));
            
            return result;
        } catch (Exception e) {
            // Release lock so the client can retry
            idempotencyService.release(idempotencyKey);
            throw e;
        }
    }
}
Pattern: Conditional INSERT with returning clause 
// PostgreSQL-specific: atomic INSERT with deduplication
@Repository
public class OrderRepositoryCustomImpl implements OrderRepositoryCustom {

    @PersistenceContext
    private EntityManager em;

    /**
     * Atomically insert an order if not already exists.
     * Returns the order (new or existing) and whether it was newly created.
     */
    public InsertResult<Order> insertIfNotExists(Order order) {
        // Use native query for ON CONFLICT ... DO UPDATE with a trick
        // to distinguish insert from no-op
        String sql = """
            WITH inserted AS (
                INSERT INTO orders (idempotency_key, user_id, amount, status, created_at)
                VALUES (:key, :userId, :amount, :status, NOW())
                ON CONFLICT (idempotency_key) DO NOTHING
                RETURNING *, TRUE as is_new
            )
            SELECT * FROM inserted
            UNION ALL
            SELECT *, FALSE as is_new FROM orders 
            WHERE idempotency_key = :key 
              AND NOT EXISTS (SELECT 1 FROM inserted)
            """;

        Object[] result = (Object[]) em.createNativeQuery(sql)
            .setParameter("key", order.getIdempotencyKey())
            .setParameter("userId", order.getUserId())
            .setParameter("amount", order.getAmount())
            .setParameter("status", order.getStatus().name())
            .getSingleResult();

        boolean isNew = (Boolean) result[result.length - 1];
        Order resultOrder = mapToOrder(result);
        
        return new InsertResult<>(resultOrder, isNew);
    }
}
Pattern: Request fingerprinting for deduplication without explicit keys

Heuristic deduplication, not true idempotency: Request fingerprinting is a best-effort fallback for clients that cannot send explicit idempotency keys. It is not a substitute for proper idempotency. Fingerprints can collide or diverge due to JWT token rotation, JSON field ordering differences, whitespace, or timestamps embedded in the body. Use it as a short-window duplicate filter, not as a reliability guarantee.

@Component
public class RequestFingerprintGenerator {

    /**
     * Generate a deterministic fingerprint for a request.
     * Same request body + user + endpoint = same fingerprint.
     * Useful when clients don't send idempotency keys.
     */
    public String generate(HttpServletRequest request, byte[] body) {
        StringBuilder sb = new StringBuilder();
        sb.append(request.getMethod());
        sb.append("|");
        sb.append(request.getRequestURI());
        sb.append("|");
        sb.append(request.getHeader("Authorization")); // Ties to user
        sb.append("|");
        sb.append(new String(body, StandardCharsets.UTF_8));
        
        return DigestUtils.sha256Hex(sb.toString());
    }
}

// Automatic deduplication filter for all POST endpoints
@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 10)
public class AutoDeduplicationFilter extends OncePerRequestFilter {

    private final StringRedisTemplate redis;
    private final RequestFingerprintGenerator fingerprintGen;
    private final Duration window = Duration.ofSeconds(5); // 5s dedup window

    @Override
    protected void doFilterInternal(HttpServletRequest request, 
                                    HttpServletResponse response, 
                                    FilterChain chain) throws IOException, ServletException {
        if (!"POST".equals(request.getMethod())) {
            chain.doFilter(request, response);
            return;
        }

        // Read body (need ContentCachingRequestWrapper)
        ContentCachingRequestWrapper wrappedRequest = 
            new ContentCachingRequestWrapper(request);
        
        chain.doFilter(wrappedRequest, response);
        
        // After processing, store fingerprint (for next 5s dedup window)
        String fingerprint = fingerprintGen.generate(wrappedRequest, 
            wrappedRequest.getContentAsByteArray());
        redis.opsForValue().setIfAbsent("dedup:" + fingerprint, "1", window);
    }

    @Override
    protected boolean shouldNotFilter(HttpServletRequest request) {
        // Skip if client provides explicit idempotency key
        return request.getHeader("Idempotency-Key") != null;
    }
}

Common Mistakes

Mistakes that cause duplicate records in production
# Mistake Why It's Dangerous Fix
1 Enabling retries without idempotency Every retry is a potential duplicate write Always pair @Retryable with an idempotency strategy
2 Using auto-generated IDs for dedup BIGSERIAL / UUID generates new ID each time — can't detect duplicates Use a natural business key or client-provided idempotency key
3 Check-then-insert without locking Race condition: two threads both pass the check, both insert Use INSERT ... ON CONFLICT or SELECT FOR UPDATE
4 Retrying after timeout without idempotency Timeout means "unknown" — the original request may still complete Timeouts are frequently retried in practice; the key requirement is that the operation is idempotent before retrying
5 Not sending idempotency key to external APIs Your retry + their retry = exponential duplicates Always forward idempotency keys to downstream services
6 Idempotency key with too-short TTL Key expires before retry happens → duplicate accepted TTL should be >= max retry window (e.g., 24h for Stripe)
7 Ignoring Kafka consumer rebalancing Partition reassignment → message redelivery → duplicate processing Store processed event IDs in same transaction as business logic
8 Retrying non-idempotent increment operations balance += 10 retried 3 times = balance += 30 Use absolute sets (balance = X) or versioned updates

// Exponential backoff with full jitter (AWS recommended)
public long calculateBackoff(int attempt, long baseDelay, long maxDelay) {
    long exponentialDelay = (long) (baseDelay * Math.pow(2, attempt));
    long cappedDelay = Math.min(exponentialDelay, maxDelay);
    // Full jitter: random value between 0 and capped delay
    return ThreadLocalRandom.current().nextLong(0, cappedDelay + 1);
}

Follow-up Interview Questions

Questions the interviewer will ask next
Q: "How do you handle idempotency for operations that have side effects beyond the database?"
Use the Outbox pattern — write the business state and the side-effect intent in the same transaction. A background process then performs the side effects (send email, publish event, call API). If it fails, it retries from the outbox. The side effect itself should also be idempotent (e.g., email service deduplicates by message ID).
Q: "What happens when your idempotency key store (Redis) goes down?"
Depends on your consistency requirements. Options: (1) Fall back to database-level dedup (unique constraint), (2) Reject all requests until Redis recovers (fail-closed), (3) Accept duplicates and reconcile later (fail-open). For payments, always fail-closed. For analytics events, fail-open is acceptable.
Q: "How would you implement exactly-once processing with Kafka?"
Kafka provides exactly-once semantics within the Kafka cluster through: (1) idempotent producer (deduplicates retried produce requests using sequence numbers), and (2) transactional producer + read_committed consumer isolation (offset commits are part of the transaction, so a consumer only sees committed messages). For end-to-end exactly-once including your database write, you need consumer-side deduplication: store the processed event ID in the same database transaction as the business write. These are two distinct strategies — Kafka transactions handle broker-side exactly-once; application-level deduplication handles end-to-end exactly-once. See Chapter 5 for deep dive.
Q: "Should the client or server generate the idempotency key?"
Client generates, server validates. The client knows the user's intent — if they click "Submit" once, that's one key. If they intentionally submit a new order, that's a new key. Server can't distinguish intent. But the server must validate: reject empty keys, enforce format, and compare request bodies for the same key (Stripe's approach).
Q: "How do you handle partial failures in a saga with retries?"
Each saga step must be idempotent and have a compensating action. If step 3 fails and retries exhaust, trigger compensation for steps 1 and 2. Each compensation must also be idempotent (can be retried safely). Use a saga orchestrator that tracks step state and persists its own state atomically.
Q: "What's the difference between at-most-once, at-least-once, and exactly-once?"
At-most-once: fire and forget, may lose messages. At-least-once: retry until acknowledged, may create duplicates. Exactly-once: at-least-once delivery + idempotent processing = appears exactly-once. True exactly-once in distributed systems is extremely difficult to guarantee end-to-end — network partitions mean a sender can never be certain whether a message was received and processed, a consequence of the Two Generals Problem. We simulate exactly-once semantics through idempotency at the application layer.

Summary

Interview Takeaways:

  1. Retries without idempotency = duplicates. They are inseparable concerns.
  2. Failures are ambiguous — a timeout doesn't tell you if the operation succeeded. Design for this reality.
  3. @Retryable must wrap @Transactional, not the other way around. Each retry needs a fresh transaction.
  4. The Outbox pattern solves the dual-write problem — write business state and events in one transaction.
  5. Idempotency keys should be client-generated, server-validated, stored atomically with the business write.
  6. Database unique constraints are your last line of defense — even if application-level dedup fails.
  7. Use exponential backoff with jitter to prevent thundering herd on retries.
  8. Circuit breakers wrap retries — don't retry when the downstream is known-dead.
  9. For Kafka: store processed event IDs in the same transaction as business logic for consumer-side dedup.

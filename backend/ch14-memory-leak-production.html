Hard Heap Dumps Profiling

How Would You Investigate a Memory Leak That Only Appears After Several Days in Production?

Key Takeaway: A Java memory leak is a reference leak, not a true unreachable-memory leak — objects stay reachable via unintended references (ThreadLocals, static collections, unregistered listeners) even though the GC is working correctly. Multi-day leaks require comparative heap dumps (day 1 vs day 5) and dominator-tree analysis to find what's growing, not a single snapshot.

Interviewer Intent

What is the interviewer really evaluating?

This question is designed to test several dimensions of senior engineering expertise simultaneously:

  • JVM memory model understanding — Do you know where objects live, how generational GC works, and the difference between heap and off-heap memory?
  • Production debugging methodology — Can you investigate a live system without taking it down or losing evidence?
  • Tool proficiency — Are you familiar with heap dump analysis, flight recorders, and native memory tracking?
  • Pattern recognition — Can you identify which category of leak this is from symptoms alone?
  • Risk management — Do you understand the operational risks of debugging in production (heap dumps freezing the JVM, etc.)?
  • Communication under pressure — Can you explain your investigation plan clearly while an incident is happening?

The "only appears after several days" aspect is critical — it rules out simple issues and points to slow accumulation patterns like growing collections, ThreadLocal leaks, or classloader leaks during hot redeployments.

At the FAANG level, interviewers expect you to discuss the full lifecycle: detection via monitoring, evidence collection, root cause analysis, fix, and prevention mechanisms.

Quick Answer

30-second elevator pitch

What is a Java memory leak? Objects remain reachable via unintended references even though the application no longer needs them. The garbage collector works correctly — it simply cannot collect objects that are still reachable. A "leak" in Java is a reference leak, not a true unreachable-memory leak like in C/C++.

TL;DR: I would approach this systematically: (1) Confirm the leak using heap metrics trending over days — look for monotonically increasing Old Gen usage that GC cannot reclaim. (2) Enable -XX:+HeapDumpOnOutOfMemoryError proactively and take comparative heap dumps at day 1 vs day 5. (3) Analyze with Eclipse MAT — inspect the dominator tree, find the largest retained-size objects, and trace GC roots to identify what's holding references. (4) Common culprits for multi-day leaks: ThreadLocals not cleaned in request filters, static Maps/Lists used as caches without eviction, listener registrations without deregistration, and connection/stream handles not closed in error paths. (5) Fix with proper lifecycle management (try-finally, @PreDestroy, WeakReferences for caches), then validate with a soak test reproducing production traffic patterns over 7+ days.

JVM Memory Model

Heap: Young Generation & Old Generation

The JVM heap is divided into generational spaces optimized for object lifetimes:

# Typical production heap layout (G1GC, 8GB heap)
# ┌─────────────────────────────────────────────────────────────────┐
# │                        JVM Process Memory                        │
# ├──────────────────────────────────┬──────────────────────────────┤
# │            Heap (8GB)            │        Non-Heap              │
# ├────────────┬─────────────────────┼──────────────────────────────┤
# │ Young Gen  │    Old Generation   │  Metaspace │ Code Cache     │
# │  (~2GB)    │      (~6GB)         │  (256MB)   │  (240MB)       │
# ├────┬───────┤                     │            │                │
# │Eden│ S0|S1 │                     │            │                │
# └────┴───────┴─────────────────────┴────────────┴────────────────┘
  • Young Generation (Eden + Survivor Spaces) — Short-lived objects. Minor GC collects here frequently (~100ms pauses). Objects surviving multiple minor GCs get promoted to Old Gen.
  • Note: Young/Old are logical concepts. G1 uses equal-sized regions that dynamically serve as either. ZGC and Shenandoah have their own layouts. The generational model remains useful for understanding leak behavior regardless of physical implementation.
  • Old Generation (Tenured) — Long-lived objects. Full GC is expensive (seconds of pause). In a memory leak, this is where leaked objects accumulate.
  • Promotion rate — Objects surviving -XX:MaxTenuringThreshold (default 15 for G1) minor GCs get promoted. A leak causes higher-than-normal promotion rates.

Metaspace

Metaspace replaced PermGen in Java 8+. It stores class metadata, method bytecodes, and constant pools in native memory (not heap).

# Monitor metaspace usage
jcmd <pid> VM.metaspace

# Typical output showing leak symptoms:
# MaxMetaspaceSize: unlimited
# CompressedClassSpaceSize: 1073741824
# Used:  340MB    ← growing over time = classloader leak
# Committed: 360MB
# Reserved: 1GB

Leak pattern: Hot redeployments in application servers (Tomcat, Jetty) without proper cleanup cause classloader leaks. Each redeployment loads classes into a new classloader, but static references or ThreadLocals prevent the old classloader from being garbage collected.

// Classic classloader leak: static reference holding class from child classloader
public class MemoryLeakFilter implements Filter {
    // BAD: Static field holds reference to webapp classloader
    private static final Map<String, Object> cache = new ConcurrentHashMap<>();

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
        // Objects stored here pin the webapp classloader
        cache.put(req.getRemoteAddr(), new RequestContext(req));
        chain.doFilter(req, res);
    }
    // No cleanup on undeploy → classloader leak
}
Native Memory & Off-Heap

Native memory is allocated outside the JVM heap and is NOT subject to garbage collection:

  • Direct ByteBuffers — Allocated via ByteBuffer.allocateDirect(). Used by NIO channels, Netty, and many I/O frameworks. Limited by -XX:MaxDirectMemorySize.
  • JNI allocations — Memory allocated by native code via malloc(). Invisible to JVM monitoring unless NMT is enabled.
  • Thread stacks — Each thread consumes -Xss (default 512KB–1MB). 1000 threads = ~1GB of native memory.
  • Memory-mapped files — MappedByteBuffer maps files into process address space. Not freed until GC collects the buffer object.
  • Compressed class space — Native memory for compressed class pointers (if enabled).
# Enable Native Memory Tracking (5-10% overhead)
java -XX:NativeMemoryTracking=detail -jar app.jar

# Baseline at startup
jcmd <pid> VM.native_memory baseline

# Compare after 5 days
jcmd <pid> VM.native_memory detail diff

# Sample output showing native leak:
# Total: reserved=12GB, committed=10GB  (+2GB since baseline)
#
# -                  Internal (reserved=2500MB, committed=2500MB)
#                             (malloc=2500MB #450000)  ← suspicious!
#                             (+1800MB since baseline)  ← LEAK!
// Direct ByteBuffer leak example
public class DirectBufferLeak {
    // BAD: Direct buffers never explicitly freed
    public byte[] readFromChannel(SocketChannel channel) throws IOException {
        // Allocates native memory — only freed when GC collects this object
        ByteBuffer buffer = ByteBuffer.allocateDirect(64 * 1024);
        channel.read(buffer);
        buffer.flip();
        byte[] data = new byte[buffer.remaining()];
        buffer.get(data);
        // buffer goes out of scope but native memory lingers until GC
        // collects the buffer's Java reference and triggers the Cleaner.
        // Timing is unpredictable — may not occur for days under low GC pressure.
        return data;
    }

    // GOOD: Reuse pooled direct buffers
    // Note: This intentionally keeps one 64KB buffer per thread permanently.
    // Acceptable for fixed-size thread pools. Memory freed only when thread dies.
    private static final ThreadLocal<ByteBuffer> BUFFER_POOL =
        ThreadLocal.withInitial(() -> ByteBuffer.allocateDirect(64 * 1024));

    public byte[] readFromChannelFixed(SocketChannel channel) throws IOException {
        ByteBuffer buffer = BUFFER_POOL.get();
        buffer.clear();
        channel.read(buffer);
        buffer.flip();
        byte[] data = new byte[buffer.remaining()];
        buffer.get(data);
        return data;
    }
}

Types of Memory Leaks in Java

Static Collections Growing Unbounded

The most common leak pattern in production. A static collection accumulates entries without any eviction or size limit:

// LEAK: Static map grows forever
public class AuditService {
    // This map is never cleared, never evicted, and lives for the lifetime of the JVM
    private static final Map<String, AuditEntry> auditLog = new ConcurrentHashMap<>();

    public void recordAction(String userId, String action) {
        // 10,000 requests/day × 365 days = 3.65 million entries
        // Each AuditEntry ~2KB = 7.3 GB leaked
        auditLog.put(userId + "_" + System.nanoTime(), new AuditEntry(userId, action, Instant.now()));
    }

    // No eviction, no size cap, no TTL
}

// FIX: Use bounded cache with eviction
public class AuditServiceFixed {
    private static final Cache<String, AuditEntry> auditCache = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(Duration.ofHours(1))
        .build();

    public void recordAction(String userId, String action) {
        auditCache.put(userId + "_" + System.nanoTime(), new AuditEntry(userId, action, Instant.now()));
    }
}

Why it takes days to manifest: At 1000 requests/hour, a map growing by 500 bytes/entry takes ~5 days to consume 60MB — enough to shift Old Gen baseline but not trigger OOM immediately.

ThreadLocal Not Cleaned Up

ThreadLocals are particularly dangerous in thread-pool environments (Tomcat, Jetty) because threads are reused across requests:

// LEAK: ThreadLocal set but never removed
public class RequestContextFilter implements Filter {
    private static final ThreadLocal<RequestContext> CONTEXT = new ThreadLocal<>();

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        // Thread pool reuses threads — previous value NOT automatically cleared
        CONTEXT.set(new RequestContext(
            ((HttpServletRequest) req).getHeader("X-Request-Id"),
            ((HttpServletRequest) req).getHeader("Authorization"),
            new HashMap<>(),  // attributes map grows per request
            new ArrayList<>()  // breadcrumbs list grows per request
        ));

        chain.doFilter(req, res);
        // BUG: No finally block to remove!
        // If chain.doFilter() throws, CONTEXT is never cleaned
    }

    public static RequestContext current() {
        return CONTEXT.get();
    }
}

// Why it leaks after days:
// - Tomcat has 200 threads in its pool
// - Each thread accumulates RequestContext objects
// - RequestContext.attributes map grows if downstream code adds to it
// - After 5 days: 200 threads × 50MB accumulated state = 10GB
// FIX: Always clean up in finally block
public class RequestContextFilterFixed implements Filter {
    private static final ThreadLocal<RequestContext> CONTEXT = new ThreadLocal<>();

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        try {
            CONTEXT.set(new RequestContext(
                ((HttpServletRequest) req).getHeader("X-Request-Id")
            ));
            chain.doFilter(req, res);
        } finally {
            CONTEXT.remove();  // CRITICAL: Always remove, even on exception
        }
    }
}
Listener/Callback Not Deregistered

Event-driven architectures leak when listeners outlive their intended scope:

// LEAK: Observer never deregistered
@Component
public class PriceUpdateWidget {
    @Autowired
    private EventBus eventBus;

    @PostConstruct
    public void init() {
        // Registers a strong reference to 'this'
        eventBus.register(this);
    }

    @Subscribe
    public void onPriceUpdate(PriceUpdateEvent event) {
        // handle event
    }

    // No @PreDestroy to unregister!
    // If this bean is prototype-scoped or in a child context that gets refreshed,
    // the old instance is never GC'd because eventBus holds a reference
}

// FIX: Proper lifecycle management
@Component
public class PriceUpdateWidgetFixed {
    @Autowired
    private EventBus eventBus;

    @PostConstruct
    public void init() {
        eventBus.register(this);
    }

    @PreDestroy
    public void cleanup() {
        eventBus.unregister(this);  // Remove strong reference
    }
}

Spring-specific trap: ApplicationListener beans in a child ApplicationContext that register with the parent context. When the child context is refreshed (e.g., Spring Cloud Config refresh), listeners from the old context remain registered.

ClassLoader Leaks (Redeployment)

Each webapp classloader holds references to all classes it loaded. A single pinned reference prevents the entire classloader (and all its classes) from being collected:

// Common pinning patterns that cause classloader leaks:

// 1. JDBC driver registered in webapp classloader
//    DriverManager holds static reference → pins classloader
Class.forName("com.mysql.cj.jdbc.Driver"); // Registers in DriverManager

// 2. Logging framework with webapp classloader
//    java.util.logging.Level instances hold classloader reference
Logger.getLogger("com.myapp"); // Level class loaded by webapp classloader

// 3. ThreadLocal referencing webapp class
public class WebAppThreadLocal {
    // Thread outlives webapp → pins classloader
    private static final ThreadLocal<MyWebAppClass> TL = new ThreadLocal<>();
}

// 4. Shutdown hooks referencing webapp classes
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    // Lambda captures webapp classloader
    myService.cleanup();
}));
# Detecting classloader leaks
jcmd <pid> GC.class_stats

WHERE retainedHeapSize > 50000000
Connection/Stream Not Closed

Resource leaks that bypass try-with-resources, especially in error paths:

// LEAK: Connection not closed on exception
public class ReportService {
    @Autowired
    private DataSource dataSource;

    public Report generateReport(String query) throws SQLException {
        Connection conn = dataSource.getConnection();
        PreparedStatement stmt = conn.prepareStatement(query);
        ResultSet rs = stmt.executeQuery();

        // If processResults() throws RuntimeException,
        // connection is never returned to pool
        Report report = processResults(rs);

        rs.close();
        stmt.close();
        conn.close();  // Never reached on exception!
        return report;
    }

    // After days: pool exhausted, new requests block, timeouts cascade
}

// FIX: try-with-resources guarantees cleanup
public class ReportServiceFixed {
    @Autowired
    private DataSource dataSource;

    public Report generateReport(String query) throws SQLException {
        try (Connection conn = dataSource.getConnection();
             PreparedStatement stmt = conn.prepareStatement(query);
             ResultSet rs = stmt.executeQuery()) {
            return processResults(rs);
        }
        // All resources closed even on exception
    }
}

Cache Without Eviction Policy

In-memory caches that grow indefinitely are a slow-burning leak:

// LEAK: HashMap used as cache without bounds
@Service
public class UserProfileCache {
    // Grows forever — one entry per unique user who ever logged in
    private final Map<Long, UserProfile> cache = new ConcurrentHashMap<>();

    public UserProfile getProfile(Long userId) {
        return cache.computeIfAbsent(userId, id -> {
            // Fetches from DB and caches permanently
            return userRepository.findById(id).orElse(null);
        });
    }
    // 1 million users × 5KB each = 5GB after months in production
}

// FIX: Bounded cache with TTL
@Service
public class UserProfileCacheFixed {
    private final Cache<Long, UserProfile> cache = Caffeine.newBuilder()
        .maximumSize(50_000)                    // Hard cap
        .expireAfterAccess(Duration.ofMinutes(30)) // TTL on access
        .expireAfterWrite(Duration.ofHours(2))     // TTL on write
        .recordStats()                             // Enable monitoring
        .removalListener((key, value, cause) ->
            log.debug("Evicted user {} due to {}", key, cause))
        .build();

    public UserProfile getProfile(Long userId) {
        return cache.get(userId, id -> userRepository.findById(id).orElse(null));
    }
}
Native Memory Leaks (JNI, Netty Direct Buffers)

These are invisible to standard heap monitoring — the JVM heap looks fine but the process RSS keeps growing:

// LEAK: Netty ByteBuf not released
public class NettyLeakHandler extends ChannelInboundHandlerAdapter {
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        ByteBuf buf = (ByteBuf) msg;
        // Process the buffer...
        processData(buf);

        // BUG: Forgot to release!
        // buf.release(); // MISSING!

        // In Netty, ByteBuf uses reference counting
        // If not released, direct memory is never freed
        // Process RSS grows while heap stays stable
    }
}

// FIX: Always release in finally or use ReferenceCountUtil
public class NettyFixedHandler extends ChannelInboundHandlerAdapter {
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        ByteBuf buf = (ByteBuf) msg;
        try {
            processData(buf);
        } finally {
            ReferenceCountUtil.release(msg);  // Decrements refcount, frees if 0
        }
    }
}

Investigation Tools

jmap — Heap Dump & Histogram

jmap provides heap snapshots and quick histograms. Use with caution in production — heap dumps pause the JVM.

# Class histogram with live objects (forces a Full GC via :live flag,
# but output is much smaller than a full heap dump)
jmap -histo:live <pid> | head -30

# Output shows top objects by count and size:
#  num     #instances    #bytes  class name
# ─────────────────────────────────────────────
#    1:      3456789   345678900  [B  (byte arrays)
#    2:      2345678   234567800  java.lang.String
#    3:      1234567   198765432  com.example.RequestContext  ← SUSPICIOUS
#    4:       890123    89012300  java.util.HashMap$Node

# Full heap dump (WARNING: pauses JVM for seconds to minutes)
jmap -dump:format=b,file=/var/dumps/heap-$(date +%Y%m%d-%H%M%S).hprof <pid>

# Live objects only (forces Full GC first)
jmap -dump:live,format=b,file=/var/dumps/heap-live.hprof <pid>

Production considerations:

  • Heap dump pauses the JVM for the entire duration (8GB heap → 30-60s pause)
  • Needs disk space >= heap size (8GB heap → 8GB+ hprof file)
  • Take dump from a node already removed from the load balancer
  • Consider jcmd as a safer alternative (more granular control)

Eclipse MAT — Memory Analyzer Tool

The gold standard for heap dump analysis. Key features for leak investigation:

# Open heap dump in MAT (GUI or headless)
# GUI: File → Open Heap Dump → select .hprof file

# Headless analysis for production (generates HTML report)
./ParseHeapDump.sh /var/dumps/heap.hprof \
  org.eclipse.mat.api:suspects \
  org.eclipse.mat.api:overview \
  org.eclipse.mat.api:top_components

Key MAT concepts:

  • Dominator Tree — Shows objects ranked by retained size. The dominator of an object X is the last GC root on all paths to X. If the dominator is freed, X becomes garbage.
  • Retained Size vs Shallow Size — Shallow = object's own memory. Retained = memory freed if this object is GC'd (includes all dominated objects).
  • GC Roots — Objects that cannot be garbage collected: thread stacks, static fields, JNI references, system classes.
  • Leak Suspects Report — Automatic analysis identifying likely leak sources.
  • OQL (Object Query Language) — SQL-like queries on the heap.
# Useful MAT OQL queries:

# Find all ThreadLocal values
SELECT tl.value FROM INSTANCEOF java.lang.ThreadLocal$ThreadLocalMap$Entry tl
WHERE tl.value != null

# Find large HashMaps (potential unbounded caches)
SELECT m, m.size, m.@retainedHeapSize 
FROM java.util.HashMap m 
WHERE m.size > 10000

# Find objects holding references to specific class
SELECT * FROM INSTANCEOF com.example.RequestContext

# Classloader leak detection
SELECT cl, cl.@retainedHeapSize 
FROM INSTANCEOF java.lang.ClassLoader cl
WHERE cl.@retainedHeapSize > 50000000
JFR — Java Flight Recorder

Low-overhead continuous profiling. Ideal for production because it's always-on with <2% overhead:

# Enable JFR at startup (always-on, circular buffer)
java -XX:StartFlightRecording=\
  disk=true,\
  maxage=7d,\
  maxsize=1g,\
  dumponexit=true,\
  filename=/var/jfr/app.jfr,\
  settings=profile \
  -jar application.jar

# Dump current recording without stopping it
jcmd <pid> JFR.dump name=1 filename=/tmp/leak-investigation.jfr

# Start targeted recording for allocation profiling
jcmd <pid> JFR.start \
  name=alloc-profile \
  duration=300s \
  filename=/tmp/alloc.jfr \
  settings=profile \
  jdk.ObjectAllocationInNewTLAB#enabled=true \
  jdk.ObjectAllocationOutsideTLAB#enabled=true

Key JFR events for leak investigation:

  • jdk.OldObjectSample — Samples of objects that survived into Old Gen (shows allocation stack trace)
  • jdk.ObjectAllocationInNewTLAB — Allocation site profiling
  • jdk.GCHeapSummary — Heap usage before/after each GC
  • jdk.MetaspaceAllocationFailure — Metaspace pressure
  • jdk.GarbageCollection — GC pause times and types
async-profiler — Allocation Profiling

async-profiler can profile allocations with near-zero overhead, producing flame graphs showing where memory is being allocated:

# Attach to running JVM and profile allocations for 60 seconds
./asprof -d 60 -e alloc -f /tmp/alloc-flamegraph.html <pid>

# Profile only objects surviving to Old Gen (TLAB-based)
./asprof -d 300 -e alloc --alloc 1m -f /tmp/old-gen-alloc.html <pid>

# Profile with specific allocation size threshold (ignore small objects)
./asprof -d 60 -e alloc --alloc 512k -f /tmp/large-alloc.html <pid>

# Live heap profiling (shows objects currently alive, not just allocated)
./asprof -d 60 -e live -f /tmp/live-heap.html <pid>

Reading the flame graph: Width represents bytes allocated. The stack traces show you exactly which code paths are allocating memory that survives into Old Gen. Look for wide bars in unexpected places.

Taking and Analyzing Heap Dumps

Capturing Heap Dumps Safely in Production

Taking a heap dump is an invasive operation. Follow this procedure to minimize impact:

# Step 1: Remove node from load balancer (no new traffic)
aws elbv2 deregister-targets \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789:targetgroup/my-app/abc123 \
  --targets Id=i-0abc123def456

# Step 2: Wait for in-flight requests to drain (30-60s)
sleep 60

# Step 3: Take heap dump
# Option A: jmap (simple)
jmap -dump:live,format=b,file=/var/dumps/heap-$(hostname)-$(date +%Y%m%d-%H%M%S).hprof $(pgrep -f 'application.jar')

# Option B: jcmd (preferred, more control)
jcmd $(pgrep -f 'application.jar') GC.heap_dump /var/dumps/heap.hprof

# Option C: Trigger via JMX (useful for remote debugging)
# Connect via JConsole → MBeans → com.sun.management → HotSpotDiagnostic → dumpHeap

# Step 4: Compress and copy off the instance
gzip /var/dumps/heap.hprof
aws s3 cp /var/dumps/heap.hprof.gz s3://my-debug-bucket/incidents/2024-01-15/

# Step 5: Re-register node (or let it be replaced by ASG)
aws elbv2 register-targets \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789:targetgroup/my-app/abc123 \
  --targets Id=i-0abc123def456

The dominator tree is the most powerful tool for finding leaks. It shows which objects "dominate" (keep alive) the most memory:

Retained Size vs Shallow Size

Understanding this distinction is crucial for interpreting heap dumps correctly:

Concept Definition Example
Shallow Size Memory consumed by the object itself (its fields) A HashMap with 1M entries: shallow = 56 bytes (just the object header + fields)
Retained Size Memory freed if this object is GC'd (includes all objects reachable only through it) Same HashMap: retained = 200MB (includes all Entry nodes, keys, and values)
Deep Size Total size of object graph reachable from this object (may overlap with other retainers) If values are shared with another map, deep > retained 
// Visualizing the difference:
//
// Object A (shallow: 32 bytes, retained: 1 GB)
//   └─ Object B (shallow: 32 bytes, retained: 999 MB)
//       └─ byte[999_000_000]  (shallow: 999 MB, retained: 999 MB)
//
// If only A references B, and only B references the byte array:
//   - Freeing A frees A + B + byte[] = 1 GB (retained size of A)
//   - The byte[] has high shallow AND retained size
//   - A has low shallow but high retained size
//
// LESSON: Sort by RETAINED size to find leak roots.
// Sort by SHALLOW size to find the actual memory consumers.

@Order(Ordered.HIGHEST_PRECEDENCE)
public class RequestCorrelationFilter extends OncePerRequestFilter {

    private static final ThreadLocal<CorrelationContext> CONTEXT = new ThreadLocal<>();

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                     HttpServletResponse response,
                                     FilterChain filterChain) throws ServletException, IOException {

        CorrelationContext ctx = new CorrelationContext();
        ctx.setRequestId(UUID.randomUUID().toString());
        ctx.setUserId(request.getHeader("X-User-Id"));
        ctx.setTraceId(request.getHeader("X-Trace-Id"));
        ctx.setStartTime(Instant.now());
        // FIX 1: Bounded attributes map
        ctx.setAttributes(new LinkedHashMap<>(16, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<String, Object> eldest) {
                return size() > 100;  // Hard cap at 100 attributes
            }
        });

        CONTEXT.set(ctx);

        try {
            filterChain.doFilter(request, response);
        } finally {
            // FIX 2: ALWAYS clean up, no matter what
            CONTEXT.remove();
        }
    }

    public static CorrelationContext current() {
        return CONTEXT.get();
    }

Production-Ready Code Patterns

ThreadLocal with try-finally Cleanup 
/**
 * Safe ThreadLocal pattern using AutoCloseable for guaranteed cleanup.
 * Works with try-with-resources for scope-bounded ThreadLocal usage.
 */
public class SafeThreadLocalScope<T> implements AutoCloseable {

    private final ThreadLocal<T> threadLocal;

    private SafeThreadLocalScope(ThreadLocal<T> threadLocal, T value) {
        this.threadLocal = threadLocal;
        this.threadLocal.set(value);
    }

    public static <T> SafeThreadLocalScope<T> open(ThreadLocal<T> tl, T value) {
        return new SafeThreadLocalScope<>(tl, value);
    }

    public T get() {
        return threadLocal.get();
    }

    @Override
    public void close() {
        threadLocal.remove();
    }
}

// Usage in a filter:
@Component
public class SafeRequestFilter extends OncePerRequestFilter {

    private static final ThreadLocal<RequestContext> CONTEXT = new ThreadLocal<>();

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                     HttpServletResponse response,
                                     FilterChain chain) throws ServletException, IOException {
        try (SafeThreadLocalScope<RequestContext> scope =
                 SafeThreadLocalScope.open(CONTEXT, buildContext(request))) {
            chain.doFilter(request, response);
        }
        // CONTEXT.remove() is GUARANTEED by AutoCloseable
    }

    public static RequestContext current() {
        return CONTEXT.get();
    }

    private RequestContext buildContext(HttpServletRequest request) {
        return new RequestContext(
            request.getHeader("X-Request-Id"),
            Instant.now()
        );
    }
}

WeakReference Caches 
/**
 * WeakHashMap-based cache: entries are eligible for GC when keys
 * are no longer strongly referenced elsewhere.
 *
 * CAVEAT: Not thread-safe! Wrap with Collections.synchronizedMap or use Caffeine.
 */
public class WeakCache<K, V> {
    private final Map<K, V> cache = Collections.synchronizedMap(new WeakHashMap<>());

    public V get(K key) {
        return cache.get(key);
    }

    public void put(K key, V value) {
        cache.put(key, value);
    }
}

/**
 * Production-grade: Caffeine cache with weak values
 * Entries are GC'd when the value is no longer strongly referenced.
 */
@Configuration
public class CacheConfig {

    @Bean
    public Cache<String, UserSession> sessionCache() {
        return Caffeine.newBuilder()
            .weakValues()                              // GC-friendly
            .maximumSize(100_000)                      // Hard upper bound
            .expireAfterAccess(Duration.ofMinutes(30)) // Idle TTL
            .expireAfterWrite(Duration.ofHours(4))     // Absolute TTL
            .recordStats()                             // Metrics for Micrometer
            .removalListener((key, value, cause) -> {
                if (cause.wasEvicted()) {
                    log.debug("Session {} evicted: {}", key, cause);
                }
            })
            .build();
    }

    /**
     * SoftReference-based cache: JVM will clear these before throwing OOM.
     * Good for optional caching where data can be re-fetched.
     */
    @Bean
    public Cache<Long, ExpensiveResult> computationCache() {
        return Caffeine.newBuilder()
            .softValues()                              // Cleared under memory pressure
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofHours(1))
            .build();
    }
}

    private static final Logger log = LoggerFactory.getLogger(LeakAwareConnectionWrapper.class);
    private static final AtomicInteger OPEN_CONNECTIONS = new AtomicInteger(0);

    private final Connection delegate;
    private final String allocationStackTrace;
    private final Instant checkedOutAt;
    private volatile boolean closed = false;

    public LeakAwareConnectionWrapper(Connection delegate) {
        this.delegate = delegate;
        this.checkedOutAt = Instant.now();
        this.allocationStackTrace = Arrays.stream(Thread.currentThread().getStackTrace())
            .skip(2)
            .limit(10)
            .map(StackTraceElement::toString)
            .collect(Collectors.joining("\n  at "));
        int count = OPEN_CONNECTIONS.incrementAndGet();
        if (count > 15) {  // Warning threshold
            log.warn("High open connection count: {}. Latest from:\n  at {}",
                count, allocationStackTrace);
        }
    }

    @Override
    public void close() throws Exception {
        if (!closed) {
            closed = true;
            OPEN_CONNECTIONS.decrementAndGet();
            delegate.close();
        }
    }

    // Called by a scheduled task to detect leaks
    public void checkForLeak() {
        if (!closed && Duration.between(checkedOutAt, Instant.now()).toMinutes() > 5) {
            log.error("PROBABLE CONNECTION LEAK! Checked out {} ago from:\n  at {}",
                Duration.between(checkedOutAt, Instant.now()), allocationStackTrace);
        }
    }
}

@Component
public class EventProcessingService implements DisposableBean {

    private final EventBus eventBus;
    private final ScheduledExecutorService scheduler;
    private final Cache<String, ProcessedEvent> eventCache;
    private final List<Subscription> subscriptions = new CopyOnWriteArrayList<>();

    public EventProcessingService(EventBus eventBus) {
        this.eventBus = eventBus;
        this.scheduler = Executors.newScheduledThreadPool(2,
            new ThreadFactoryBuilder().setNameFormat("event-processor-%d").setDaemon(true).build());
        this.eventCache = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofHours(1))
            .build();
    }

    @PostConstruct
    public void init() {
        // Register with event bus
        eventBus.register(this);

        // Start background tasks
        scheduler.scheduleAtFixedRate(this::processBacklog, 0, 30, TimeUnit.SECONDS);
        scheduler.scheduleAtFixedRate(this::reportMetrics, 0, 60, TimeUnit.SECONDS);

        // Subscribe to external topics
        subscriptions.add(messageBroker.subscribe("orders.*", this::onOrder));
        subscriptions.add(messageBroker.subscribe("payments.*", this::onPayment));
    }

    @PreDestroy
    @Override
    public void destroy() {
        // 1. Unregister from event bus
        eventBus.unregister(this);

        // 2. Cancel all subscriptions
        subscriptions.forEach(Subscription::cancel);
        subscriptions.clear();

        // 3. Shut down executor gracefully
        scheduler.shutdown();
        try {
            if (!scheduler.awaitTermination(30, TimeUnit.SECONDS)) {
                scheduler.shutdownNow();
                log.warn("Scheduler did not terminate within 30s, forced shutdown");
            }
        } catch (InterruptedException e) {
            scheduler.shutdownNow();
            Thread.currentThread().interrupt();
        }

        // 4. Invalidate cache
        eventCache.invalidateAll();
        eventCache.cleanUp();

        log.info("EventProcessingService destroyed cleanly");
    }

    @Subscribe
    public void onEvent(DomainEvent event) {
        eventCache.put(event.getId(), process(event));
    }

    private void onOrder(Message msg) { /* ... */ }
    private void onPayment(Message msg) { /* ... */ }
    private ProcessedEvent process(DomainEvent event) { return null; /* ... */ }

/**
 * Defensive resource management for complex workflows
 * where multiple resources must be managed together.
 */
public class BatchExportService {

    private static final Logger log = LoggerFactory.getLogger(BatchExportService.class);

    /**
     * Pattern 1: try-with-resources for simple cases
     */
    public void exportSimple(String query, Path outputFile) throws IOException, SQLException {
        try (Connection conn = dataSource.getConnection();
             PreparedStatement stmt = conn.prepareStatement(query);
             ResultSet rs = stmt.executeQuery();
             BufferedWriter writer = Files.newBufferedWriter(outputFile)) {

            while (rs.next()) {
                writer.write(formatRow(rs));
                writer.newLine();
            }
        }
        // ALL resources closed, even on exception
    }

    /**
     * Pattern 2: Cleaner API for resources that outlive a method call
     * (Java 9+ java.lang.ref.Cleaner)
     */
    private static final Cleaner CLEANER = Cleaner.create();

    public class ManagedBuffer {
        private ByteBuffer directBuffer;
        private final Cleaner.Cleanable cleanable;

        public ManagedBuffer(int size) {
            this.directBuffer = ByteBuffer.allocateDirect(size);
            // Safety net: if user forgets to close, Cleaner will free it
            ByteBuffer bufferRef = this.directBuffer;
            this.cleanable = CLEANER.register(this, () -> {
                // Release direct buffer's native memory
                // ⚠️ sun.nio.ch.DirectBuffer is JDK-internal API.
                // Requires --add-opens java.base/sun.nio.ch=ALL-UNNAMED on Java 9+.
                // For portable code, rely on GC-triggered cleanup or Netty's buffer pooling.
                if (bufferRef instanceof sun.nio.ch.DirectBuffer db) {
                    db.cleaner().clean();
                }
            });
        }

        public void close() {
            cleanable.clean();  // Explicit cleanup (preferred)
        }
    }

    /**
     * Pattern 3: Resource tracking for debugging
     */
    public class TrackedInputStream extends FilterInputStream {

        private static final Set<TrackedInputStream> OPEN_STREAMS =
            Collections.newSetFromMap(new ConcurrentHashMap<>());

        private final String allocationSite;
        private final Instant openedAt;
        private volatile boolean closed = false;

        public TrackedInputStream(InputStream in) {
            super(in);
            this.openedAt = Instant.now();
            this.allocationSite = Thread.currentThread().getStackTrace()[2].toString();
            OPEN_STREAMS.add(this);
        }

        @Override
        public void close() throws IOException {
            if (!closed) {
                closed = true;
                OPEN_STREAMS.remove(this);
                super.close();
            }
        }

        // Call periodically to detect leaks
        public static void reportLeaks() {
            OPEN_STREAMS.stream()
                .filter(s -> Duration.between(s.openedAt, Instant.now()).toMinutes() > 5)
                .forEach(s -> log.warn("Stream leak! Opened {} ago at {}",
                    Duration.between(s.openedAt, Instant.now()), s.allocationSite));
        }
    }

Common Mistakes

Mistakes candidates make when answering this question
Mistake Why It's Wrong What to Say Instead
"Just increase the heap size" Masks the leak, delays the inevitable, makes Full GC pauses worse "Increasing heap buys time for investigation but doesn't fix the root cause. A 10GB leak in an 8GB heap becomes a 10GB leak in a 16GB heap — it just takes longer to OOM."
"Take a heap dump immediately" A single dump shows state, not growth. You need comparison over time. "I'd take comparative dumps — one at baseline and one when degraded — to see what objects accumulated."
"Use jstack to find the leak" jstack shows thread state (deadlocks, blocked), not memory. Wrong tool. "jstack is for threading issues. For memory leaks I'd use jmap histogram, Eclipse MAT for deep analysis, or JFR for allocation profiling."
Only mentioning heap leaks Native memory leaks (Netty, JNI, direct buffers) are invisible to heap tools "I'd first determine if it's a heap leak or native leak by comparing JVM heap metrics with process RSS. If RSS grows but heap is stable, it's a native memory issue requiring NMT or jemalloc profiling."
"Use finalize() to clean up" finalize() is deprecated, unpredictable, creates GC pressure, and can resurrect objects "I'd use try-with-resources, AutoCloseable, or java.lang.ref.Cleaner (Java 9+) as a safety net — never finalize()."
Not considering production constraints Can't freely restart, can't attach debuggers, heap dumps cause pauses "Before taking a heap dump in production, I'd drain the node from the load balancer, ensure sufficient disk space, and coordinate with the on-call team since it will pause the JVM for potentially minutes."
"Just restart the service periodically" Acceptable as mitigation while investigating, but not a long-term solution "Scheduled restarts can mitigate impact while we investigate, but the root cause must be found and fixed. Restarts during investigation can destroy evidence."
Forgetting to verify the fix A fix without soak testing is an assumption, not a solution "After the fix, I'd run a soak test simulating 7+ days of production traffic to confirm Old Gen usage stabilizes and doesn't grow monotonically."
Not mentioning monitoring/prevention Senior engineers think about systemic improvements, not just point fixes "Beyond the fix, I'd add Prometheus alerts for Old Gen growth rate, enable JFR always-on recording, and add a leak regression test to CI."
Confusing retained size with shallow size Shallow size of a HashMap is 56 bytes, but retained size can be gigabytes "In the dominator tree, I'd sort by retained heap size to find which objects, when freed, would release the most memory. The shallow size of a collection is trivial; what matters is everything it retains."

GC Algorithm Trade-offs for Leak-Prone Systems 
# G1GC (default since Java 9): Best general-purpose choice
# + Handles large heaps well (8-64GB)
# + Mixed GC reclaims Old Gen incrementally
# - Full GC still possible under extreme pressure
java -XX:+UseG1GC -XX:MaxGCPauseMillis=200

# ZGC (Java 15+): Ultra-low pause regardless of heap size
# + Pauses < 10ms even with 16TB heap
# + Concurrent compaction (no STW Full GC)
# - 5-15% CPU/throughput overhead vs G1, varies by workload
#   (generational ZGC, JDK 21+, trends toward the lower end)
# - Slightly higher memory footprint
java -XX:+UseZGC -XX:+ZGenerational  # Java 21+

# Shenandoah: Similar to ZGC, available on more platforms
# + Sub-10ms pauses
# + Concurrent evacuation
# - Not available in Oracle JDK
java -XX:+UseShenandoahGC

# IMPORTANT: GC choice doesn't FIX leaks — it only affects HOW the system
# degrades. G1 will Full GC more frequently. ZGC will use more CPU.
# The leak must still be found and fixed.
Heap Size: Too Small vs Too Large
  • Too small (e.g., 2GB for a leaky app) — OOM happens faster (hours instead of days), but easier to detect. Smaller heap dumps are faster to analyze. Full GC is faster.
  • Too large (e.g., 32GB for the same app) — Masks the leak for weeks/months. Full GC when it happens is catastrophic (30+ second pauses). Heap dumps are enormous (30GB+ files). Analysis tools may not have enough RAM.
  • Right-sized — Set heap to expected working set × 2-3x. Monitor post-GC Old Gen as the true usage metric. Alert when post-GC Old Gen exceeds 70% capacity.
# Golden rule: if post-Full-GC heap usage grows over time, you have a leak.
# The heap size only determines how long before it becomes critical.
#
# Example monitoring query (PromQL):
# Post-GC heap = heap used immediately after a Full GC event
jvm_memory_used_bytes{area="heap"} and on() 
  changes(jvm_gc_pause_seconds_count{action="end of major GC"}[1m]) > 0

Follow-up Questions

Questions the interviewer might ask next
  1. "How would you reproduce this in a test environment?"

    Set up a soak test with production-like traffic patterns (including error scenarios). Use a smaller heap (-Xmx1g) to accelerate the timeline. Enable allocation profiling. Run for 48-72 hours while monitoring post-GC heap growth. Key: include the error paths that trigger the leak (e.g., requests that throw exceptions).

  2. "What if the leak only happens under specific traffic patterns?"

    Replay production access logs (with sanitized data) against the test environment. Use traffic shadowing/mirroring to replay real traffic. Correlate heap growth timing with specific API endpoints or user actions using JFR's OldObjectSample events.

  3. "How do you handle this in a containerized environment (Kubernetes)?"

    Set JVM heap to ~75% of container memory limit (leave room for metaspace, threads, native). Use init containers or sidecars to upload heap dumps. Mount debug volumes for JFR recordings. Use ephemeral containers for on-demand diagnostics. Configure OOM killer behavior via resource limits.

  4. "The heap looks fine but the container keeps getting OOM-killed. What's happening?"

    This is a native memory leak. The JVM heap is within bounds, but native memory (direct buffers, JNI, thread stacks, metaspace) is growing beyond the container's memory limit. Use NMT to track native allocations. Check thread count growth. Monitor direct buffer usage via JMX java.nio:type=BufferPool.

  5. "How would you prevent this class of bug from reaching production?"

    Static analysis (SpotBugs/PMD rules for unclosed resources, FindBugs ThreadLocal detector). Code review checklist for ThreadLocal usage. Mandatory soak tests in CI/CD for services with stateful components. Runtime leak detection in staging (smaller heaps, aggressive GC). Architecture review for any component that stores per-request state.

  6. "What's the difference between a memory leak in Java vs C/C++?"

    In C/C++, leaked memory is truly unreachable (malloc without free). In Java, leaked objects are still reachable — they're held by unintended references. Java leaks are "reference leaks" — the GC works correctly, but the programmer maintains references longer than intended. This makes Java leaks harder to detect (no "definitely lost" category like Valgrind) but easier to diagnose (heap dumps show the reference chain).

  7. "How would you investigate if the leak is in a third-party library?"

    Heap dump analysis doesn't care about code ownership — the dominator tree reveals the retaining path regardless. If the retained objects are from a library: check the library's issue tracker, upgrade to latest version, review the library's lifecycle requirements (e.g., Netty requires explicit release of ByteBuf). Worst case: wrap the library call with defensive cleanup or use a classloader-isolated module.

  8. "Can you have a memory leak with G1GC/ZGC?"

    Absolutely. GC algorithms determine how efficiently unreachable objects are collected and how long pauses are. They cannot collect reachable objects. A reference leak (object kept alive by unintended reference) is invisible to all GC algorithms. The GC works perfectly — it's the application that's broken.

Summary

Key Takeaways
  • Memory leaks in Java are reference leaks — objects remain reachable through unintended reference chains. The GC is working correctly; the code is holding references too long.
  • Multi-day leaks have specific patterns: ThreadLocals in pooled threads, static collections without eviction, listeners never deregistered, classloaders pinned by lingering references.
  • Systematic investigation workflow: Confirm (metrics trending), characterize (heap vs native), collect evidence (comparative dumps), analyze (MAT dominator tree + GC roots), fix, validate (soak test).
  • Production safety: Drain traffic before taking dumps. Always have -XX:+HeapDumpOnOutOfMemoryError configured. Use JFR always-on for retrospective analysis.
  • Retained size is king: Sort by retained heap in the dominator tree to find leak roots. Follow the path to GC roots to understand WHY objects can't be collected.
  • Don't forget native memory: If RSS grows but heap is stable, use NMT, check direct buffer pools, and count threads. Netty ByteBuf reference counting is a common source.
  • Prevention beats detection: Bounded caches (Caffeine), try-with-resources for all Closeable objects, @PreDestroy for listener cleanup, leak detection thresholds on connection pools, and automated soak tests in CI/CD.

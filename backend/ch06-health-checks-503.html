Medium Kubernetes Load Balancers

Your Application Passes All Health Checks, but Users Still Receive 503 Errors. What Could Be the Reason?

Key Takeaway: Health checks verify that your application process is alive — not that it can serve real traffic. A 503 occurs when the infrastructure layer (load balancer, ingress, service mesh, or Kubernetes itself) determines that no backend can handle the request, even though the application reports itself as healthy. The gap between "alive" and "able to serve" is where 503s hide.

Interviewer's Intent

What they're really testing:

  • Do you understand the difference between liveness, readiness, and startup probes — and how misconfiguring them causes production outages?
  • Can you explain the full request path from client → DNS → LB → ingress → service mesh → pod — and where 503s originate at each layer?
  • Do you know how Kubernetes networking works internally (kube-proxy, iptables/IPVS, endpoint propagation delays)?
  • Have you dealt with rolling deployment gaps where old pods are terminating but new pods aren't ready?
  • Can you design health checks that accurately reflect application capacity, not just process liveness?
  • Do you understand graceful shutdown — preStop hooks, connection draining, and terminationGracePeriodSeconds?
  • Can you debug this in production using kubectl, metrics, and distributed tracing?

Senior-level differentiator: Junior engineers say "the server is overloaded." Mid-level engineers mention thread pool exhaustion. Senior engineers draw the full request path, identify the exact layer returning 503, explain the Kubernetes endpoint propagation delay, and describe how to implement health checks that reflect true serving capacity.

60-Second Answer

Concise answer for time-pressured interviews

Interview opener:

"Health checks passing only means the application process is alive and the health endpoint responds. A 503 means 'service unavailable' — returned by an intermediary when it cannot route to a healthy backend. The most common reasons for this gap:

1. Shallow health checks: The /health endpoint returns 200 because the JVM is up, but all Tomcat threads are blocked on a slow downstream service. The app is alive but cannot serve new requests.

2. Readiness vs Liveness confusion: Liveness probe passes (don't kill me), but the readiness probe should be failing (don't send me traffic). If readiness checks are too shallow, Kubernetes keeps sending traffic to pods that can't handle it.

3. Infrastructure-layer limits: Ingress controller connection limits, service mesh circuit breakers (Envoy returning 503), rate limiting at the API gateway, or load balancer max-connections — all return 503 independent of app health.

4. Rolling deployment race: During deployment, old pods are terminating (removed from endpoints) but new pods haven't passed readiness yet. Briefly, zero backends are available.

5. Endpoint propagation delay: Kubernetes endpoint updates are eventually consistent. A pod marked unready may still receive traffic for seconds while iptables/IPVS rules propagate.

The fix is multi-layered: deep readiness checks that verify thread availability and downstream connectivity, proper graceful shutdown with preStop hooks, and capacity-aware health indicators."

Kubernetes Health Probes

Liveness vs Readiness vs Startup — how each works and what happens when they fail

The Three Probe Types

# Complete probe configuration for a Spring Boot application
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
spec:
  template:
    spec:
      containers:
      - name: payment-service
        image: payment-service:2.1.0
        ports:
        - containerPort: 8080

        # STARTUP PROBE — Only runs during container startup
        # Prevents liveness/readiness from killing slow-starting apps
        startupProbe:
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5
          failureThreshold: 30      # 30 × 5s = 150s max startup time
          # After startup succeeds, liveness + readiness take over

        # LIVENESS PROBE — "Should I restart this container?"
        # Only checks if the process is deadlocked/hung
        livenessProbe:
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          initialDelaySeconds: 0     # Starts after startup probe succeeds
          periodSeconds: 10
          failureThreshold: 3        # 3 failures = restart container
          timeoutSeconds: 3
          # DANGER: If this fails, Kubernetes KILLS the pod

        # READINESS PROBE — "Should I send traffic to this pod?"
        # Checks if the app can handle requests RIGHT NOW
        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: 8080
          initialDelaySeconds: 0
          periodSeconds: 5
          failureThreshold: 3        # 3 failures = remove from Service endpoints
          successThreshold: 1        # 1 success = add back to endpoints
          timeoutSeconds: 3
          # Safe: just stops traffic, doesn't kill the pod

What Happens When Each Probe Fails

Probe On Failure Impact Recovery
Startup Kill container, restart CrashLoopBackOff if app never starts Container restart with backoff
Liveness Kill container, restart In-flight requests dropped, connections reset Container restart (all state lost)
Readiness Remove from Service endpoints No new traffic routed, existing connections may continue Automatic: added back when probe succeeds again

Critical mistake: Using the same endpoint for both liveness and readiness. If your readiness check includes a database connectivity check and the DB goes down, the liveness probe ALSO fails → Kubernetes kills all your pods → cascading failure. The DB being down doesn't mean your process is broken — it means you can't serve requests right now.

Spring Boot Actuator Probe Groups

# application.yml — Separate liveness from readiness
management:
  endpoint:
    health:
      probes:
        enabled: true       # Enables /actuator/health/liveness and /readiness
      show-details: always
      group:
        liveness:
          include: livenessState
          # Only checks: Is the JVM alive? No external deps!
        readiness:
          include: readinessState, db, redis, customThreadPool
          # Checks: Can this pod serve traffic right now?
          # Only include dependencies whose failure prevents serving CORE requests.
          # Don't fail readiness for non-critical services (recommendations, analytics).
  health:
    livenessstate:
      enabled: true
    readinessstate:
      enabled: true

Cause 1: Thread Pool Exhausted (App is "Alive" but Can't Accept More)

Most common cause in production.

// Scenario: All 200 Tomcat threads are stuck waiting on a slow downstream service
// Health check: GET /actuator/health → 200 OK (runs on its own thread)
// Real request: GET /api/payments → waits in accept queue → timeout → 503

// Why health check passes (without separate management port):
// - Health endpoint is lightweight (no I/O to downstream)
// - It DOES use the same Tomcat worker thread pool as real traffic
// - But it completes in ~1ms, so under partial exhaustion it still gets through
// - At 100% saturation with deep queuing, health checks can ALSO timeout
// - FIX: Use a separate management port (8081) to fully isolate probes

// But real requests:
// - Need a Tomcat worker thread (all 200 are blocked on downstream HTTP calls)
// - New requests queue in the OS TCP accept queue (backlog = 100 by default)
// - After accept queue is full → connection refused → LB returns 503
# Tomcat defaults that hide this problem:
server:
  tomcat:
    threads:
      max: 200              # Only 200 worker threads
      min-spare: 10
    accept-count: 100       # TCP backlog queue size
    connection-timeout: 20000  # 20s — way too long for a stuck downstream
    max-connections: 8192   # Max simultaneous connections

Cause 2: Ingress Controller / Load Balancer Connection Limits

# NGINX Ingress Controller has its own limits:
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    # These cause 503 INDEPENDENT of application health:
    nginx.ingress.kubernetes.io/proxy-connect-timeout: "5"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "60"
    nginx.ingress.kubernetes.io/upstream-max-fails: "3"        # ← Mark upstream as down after 3 fails
    nginx.ingress.kubernetes.io/upstream-fail-timeout: "30"    # ← Keep it down for 30s
    nginx.ingress.kubernetes.io/limit-connections: "100"       # ← Max 100 concurrent connections per pod
    nginx.ingress.kubernetes.io/limit-rps: "50"                # ← Rate limit: 50 req/s per IP

The trap: NGINX's upstream-max-fails uses its OWN health checking. If 3 requests to a pod timeout (even though the Kubernetes readiness probe is passing), NGINX marks that upstream as unavailable for 30 seconds. Result: 503 even though kubectl get pods shows all pods Ready.

  replicas: 2
  strategy:
    type: RollingUpdate

# T=0: Start pod v2-A (maxSurge=1)

Cause 6: DNS Resolution Failures to Downstream

// Real request flow: App → DNS lookup for payment-gateway.prod → TIMEOUT → 503

// - CoreDNS pods overwhelmed (ndots:5 causes 10x DNS queries)
// - DNS cache expired + upstream DNS unreachable
// - /etc/resolv.conf search domains causing cascading lookups

// The health check doesn't test DNS because it doesn't make outbound calls!
# Kubernetes default ndots:5 multiplies DNS queries:
# Request for "payment-gateway.prod" generates:
#   1. payment-gateway.prod.my-namespace.svc.cluster.local  ← NXDOMAIN
#   2. payment-gateway.prod.svc.cluster.local               ← NXDOMAIN

#   4. payment-gateway.prod.my-domain.com                   ← NXDOMAIN
#   5. payment-gateway.prod                                 ← Finally resolves!

# Fix: Use FQDN with trailing dot, or reduce ndots
dnsConfig:
  options:
    - name: ndots

# Pod with aggressive CPU limits:

    cpu: 250m        # Request 0.25 cores

# - Health check: tiny CPU cost, responds in 1ms → ✅
# - Real request: needs CPU for JSON serialization, encryption, business logic
# - CFS scheduler throttles the pod at 500m

Endpoint Propagation Delay — The Hidden 503 Cause


┌─────────────────────────────────────────────────────────────────────────────┐
│       ENDPOINT UPDATE PROPAGATION TIMELINE                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │

Why this matters for 503s: When a pod starts terminating, it's removed from Endpoints. But iptables rules on other nodes still have the old pod's IP. Requests sent to the terminating pod get connection refused → the upstream (ingress/LB) returns 503. This is why you need a preStop hook with a sleep — to keep the pod alive long enough for iptables to propagate.

IPVS vs iptables — Performance at Scale

# iptables problems at scale:
# - Rules are evaluated linearly: O(n) where n = number of services × endpoints
# - 10,000 services = 40,000+ iptables rules
# - Rule regeneration takes seconds (locks iptables during update)
# - During regeneration: packets can be dropped → 503

# IPVS advantages:
# - Hash-based lookup: O(1) regardless of service count
# - Kernel-space load balancing (faster than userspace)
# - Supports weighted routing, least-connections, etc.
# - Rule updates are incremental (no full regeneration)

# Check which mode your cluster uses:
kubectl get configmap kube-proxy -n kube-system -o yaml | grep mode
# mode: "ipvs"  ← good for large clusters
# mode: ""      ← defaults to iptables

EndpointSlices — Reducing Propagation Delay

# Kubernetes 1.21+ uses EndpointSlices instead of Endpoints
# Benefits:
# - Endpoints object = ALL pod IPs in one object (doesn't scale)
# - EndpointSlice = max 100 endpoints per slice (scalable)
# - Smaller watch payloads → faster propagation
# - Topology-aware routing → prefer same-zone pods

# Check EndpointSlices:

// =============================================================
// LIVENESS: Only check if the JVM/process is fundamentally broken
// =============================================================
@Component
public class LivenessHealthIndicator implements HealthIndicator {
    
    private final AtomicBoolean deadlockDetected = new AtomicBoolean(false);
    
    @Scheduled(fixedRate = 10000)  // Check every 10s
    public void detectDeadlocks() {
        ThreadMXBean threadBean = ManagementFactory.getThreadMXBean();
        long[] deadlockedThreads = threadBean.findDeadlockedThreads();
        deadlockDetected.set(deadlockedThreads != null && deadlockedThreads.length > 0);
    }
    
    @Override
    public Health health() {
        if (deadlockDetected.get()) {
            return Health.down()
                .withDetail("reason", "Deadlock detected")
                .build();
        }
        
        // Check if event loop / main thread is responsive
        // (this method being called already proves basic JVM health)
        return Health.up().build();
    }
}

// READINESS: Check if the pod can serve REAL traffic RIGHT NOW
// =============================================================
@Component
public class ReadinessHealthIndicator implements HealthIndicator {
    
    private final TomcatWebServer tomcatWebServer;
    private final DataSource dataSource;
    private final RedisConnectionFactory redisFactory;
    
    // Thresholds
    private static final double THREAD_UTILIZATION_THRESHOLD = 0.85;
    private static final double CONNECTION_POOL_THRESHOLD = 0.90;
    
    public ReadinessHealthIndicator(
            ApplicationContext ctx,
            DataSource dataSource,
            RedisConnectionFactory redisFactory) {
        // Get Tomcat instance from Spring context
        ServletWebServerApplicationContext webCtx = (ServletWebServerApplicationContext) ctx;
        this.tomcatWebServer = (TomcatWebServer) webCtx.getWebServer();
        this.dataSource = dataSource;
        this.redisFactory = redisFactory;
    }
    
    @Override
    public Health health() {
        Health.Builder builder = Health.up();
        boolean ready = true;
        
        // Check 1: Tomcat thread pool utilization
        Executor executor = tomcatWebServer.getTomcat()
            .getConnector().getProtocolHandler().getExecutor();
        if (executor instanceof ThreadPoolExecutor tpe) {
            int active = tpe.getActiveCount();
            int max = tpe.getMaximumPoolSize();
            double utilization = (double) active / max;
            
            builder.withDetail("tomcat.activeThreads", active);
            builder.withDetail("tomcat.maxThreads", max);
            builder.withDetail("tomcat.utilization", 
                String.format("%.1f%%", utilization * 100));
            
            if (utilization > THREAD_UTILIZATION_THRESHOLD) {
                builder.down().withDetail("reason", 
                    "Thread pool utilization above " + 
                    (THREAD_UTILIZATION_THRESHOLD * 100) + "%");
                ready = false;
            }
        }
        
        // Check 2: Database connection pool
        if (dataSource instanceof HikariDataSource hikari) {
            HikariPoolMXBean pool = hikari.getHikariPoolMXBean();
            int active = pool.getActiveConnections();
            int max = hikari.getMaximumPoolSize();
            double connUtilization = (double) active / max;
            
            builder.withDetail("db.activeConnections", active);
            builder.withDetail("db.maxConnections", max);
            
            if (connUtilization > CONNECTION_POOL_THRESHOLD) {
                builder.down().withDetail("reason", 
                    "DB connection pool above " + 
                    (CONNECTION_POOL_THRESHOLD * 100) + "%");
                ready = false;
            }
        }
        
        // Check 3: Can we reach the database? (quick check)
        try (Connection conn = dataSource.getConnection()) {
            if (!conn.isValid(2)) {  // 2 second timeout
                builder.down().withDetail("reason", "DB connection not valid");
                ready = false;
            }
        } catch (SQLException e) {
            builder.down().withDetail("reason", "DB unreachable: " + e.getMessage());
            ready = false;
        }
        
        // Check 4: Redis connectivity
        try {
            redisFactory.getConnection().ping();
            builder.withDetail("redis", "UP");
        } catch (Exception e) {
            builder.down().withDetail("reason", "Redis unreachable: " + e.getMessage());
            ready = false;
        }
        
        return ready ? builder.build() : builder.status(Status.DOWN).build();
    }
}

Graceful Shutdown Implementation

@Component
@Slf4j
public class GracefulShutdownHandler {
    // NOTE: This is an educational example showing the mechanism.
    // Spring Boot 2.3+ server.shutdown=graceful handles this natively.
    // Use this pattern only if you need custom shutdown logic beyond what Spring provides.
    
    private final AtomicBoolean shuttingDown = new AtomicBoolean(false);
    private final AtomicInteger activeRequests = new AtomicInteger(0);
    private final CountDownLatch shutdownLatch = new CountDownLatch(1);
    
    /**
     * Servlet filter that tracks in-flight requests
     * and rejects new ones during shutdown
     */
    @Bean
    public FilterRegistrationBean<Filter> shutdownFilter() {
        FilterRegistrationBean<Filter> registration = new FilterRegistrationBean<>();
        registration.setFilter((request, response, chain) -> {
            if (shuttingDown.get()) {
                HttpServletResponse httpResponse = (HttpServletResponse) response;
                httpResponse.setStatus(503);
                httpResponse.setHeader("Connection", "close");
                httpResponse.setHeader("Retry-After", "5");
                httpResponse.getWriter().write(
                    "{\"error\":\"Service shutting down, retry on another instance\"}");
                return;
            }
            
            activeRequests.incrementAndGet();
            try {
                chain.doFilter(request, response);
            } finally {
                if (activeRequests.decrementAndGet() == 0 && shuttingDown.get()) {
                    shutdownLatch.countDown();
                }
            }
        });
        registration.setOrder(Ordered.HIGHEST_PRECEDENCE);
        return registration;
    }
    
    /**
     * Called when SIGTERM is received (via Spring lifecycle)
     */
    @PreDestroy
    public void onShutdown() {
        log.info("Shutdown signal received. Active requests: {}", activeRequests.get());
        shuttingDown.set(true);
        
        // Wait for in-flight requests to complete (max 25s)
        try {
            if (activeRequests.get() > 0) {
                log.info("Waiting for {} in-flight requests to complete...", 
                    activeRequests.get());
                boolean drained = shutdownLatch.await(25, TimeUnit.SECONDS);
                if (!drained) {
                    log.warn("Timed out waiting for requests. {} still active.", 
                        activeRequests.get());
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            log.warn("Interrupted during shutdown drain");
        }
        
        log.info("Graceful shutdown complete.");
    }
    
    public boolean isShuttingDown() {
        return shuttingDown.get();
    }
}

        applicationReady.set(allPassed);
    }
    
    @Override

        if (!applicationReady.get()) {
            return Health.down()
                .withDetail("reason", "Application startup checks not complete")
                .build();
        }
        return Health.up().build();
    }
}

Common Mistakes

Anti-patterns that lead to 503s despite green health checks

Mistake #1: Same endpoint for liveness and readiness

# BAD: Both probes hit the same endpoint
livenessProbe:
  httpGet:
    path: /actuator/health     # ← Includes DB check!
readinessProbe:
  httpGet:
    path: /actuator/health     # ← Same endpoint

# What happens when DB goes down:
# 1. /actuator/health returns 503 (DB is down)
# 2. Readiness fails → pod removed from endpoints (correct!)
# 3. Liveness ALSO fails → Kubernetes KILLS the pod (wrong!)
# 4. Pod restarts → DB still down → fails again → CrashLoopBackOff
# 5. ALL pods enter CrashLoopBackOff → total outage
# 
# The DB being down doesn't mean the JVM is broken!
# Liveness should NEVER check external dependencies.

Mistake #2: Health check on same port/thread pool as application

# BAD: Health probe competes with real traffic for threads
livenessProbe:
  httpGet:
    path: /health
    port: 8080        # ← Same port as application!

# When all 200 Tomcat threads are busy:
# - Health probe request queues behind real requests
# - Probe times out → Kubernetes thinks pod is dead → kills it
# - This makes the situation WORSE (restarts reduce capacity)
# 
# FIX: Use a separate management port (8081)
management:
  server:
    port: 8081        # ← Dedicated port with its own thread pool

Mistake #3: No timeout on downstream calls

// BAD: Default RestTemplate has NO timeout
RestTemplate restTemplate = new RestTemplate();
// Connect timeout: infinite
// Read timeout: infinite
// One slow downstream service → ALL threads stuck → 503

// GOOD: Always set timeouts + circuit breaker
@Bean
public RestTemplate restTemplate() {
    var factory = new SimpleClientHttpRequestFactory();
    factory.setConnectTimeout(3000);    // 3s connect
    factory.setReadTimeout(5000);       // 5s read
    return new RestTemplate(factory);
}

Mistake #4: Aggressive liveness probe timing

# BAD: Liveness probe too sensitive
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  periodSeconds: 2         # Check every 2s
  failureThreshold: 1      # Kill after 1 failure!
  timeoutSeconds: 1        # 1s timeout

# During a GC pause (G1 can pause for 200-500ms normally):
# - One probe takes > 1s due to GC → failure
# - failureThreshold=1 → immediate kill
# - Result: healthy pods killed during normal GC
#
# FIX: Generous liveness, strict readiness
livenessProbe:
  periodSeconds: 10
  failureThreshold: 3      # 3 × 10s = 30s before kill
  timeoutSeconds: 5
readinessProbe:
  periodSeconds: 5
  failureThreshold: 1      # Quick traffic removal (safe)

Mistake #5: No preStop hook + no graceful shutdown

# What happens without preStop:
# T=0.000s: Pod gets SIGTERM
# T=0.000s: kube-proxy starts removing iptables rules (takes 3-7s)
# T=0.001s: Spring Boot receives SIGTERM, starts shutdown
# T=0.500s: Server socket closed, no new connections accepted
# T=0.500s - T=7.000s: iptables still routing traffic to this pod!
#            → Connection refused → 503 for 6+ seconds
#
# With preStop: sleep 10:
# T=0.000s: preStop starts (sleep 10)
# T=0.000s: kube-proxy starts removing iptables rules
# T=7.000s: iptables rules fully propagated (pod removed from routing)
# T=10.00s: preStop completes, SIGTERM sent to app
# T=10.50s: App stops accepting connections (but no traffic coming anyway)
# Result: ZERO dropped requests during shutdown

Mistake #6: Health check doesn't verify thread availability

// BAD: Health check says "UP" even when no threads are available
@GetMapping("/health")
public String health() {
    return "UP";  // Meaningless! Doesn't reflect serving capacity.
}

// GOOD: Health check reflects actual capacity
@Override
public Health health() {
    ThreadPoolExecutor executor = getTomcatExecutor();
    double utilization = (double) executor.getActiveCount() 
                        / executor.getMaximumPoolSize();
    
    if (utilization > 0.85) {
        return Health.outOfService()
            .withDetail("threads.utilization", utilization)
            .withDetail("threads.active", executor.getActiveCount())
            .withDetail("threads.max", executor.getMaximumPoolSize())
            .build();
    }
    return Health.up().build();
}

Mistake #7: CPU limits too tight (throttling)

# BAD: CPU limit = CPU request (no burst capacity)
resources:
  requests:
    cpu: 250m
  limits:
    cpu: 250m       # ← Pod WILL be throttled under any load spike

# The health probe uses almost no CPU → always passes
# Real requests need CPU for JSON parsing, encryption, logging
# CFS scheduler throttles → requests take 10x longer → timeout → 503

# GOOD: Remove CPU limits for latency-sensitive services
# (popularized by Google SRE; debated for multi-tenant clusters
#  where limits help prevent noisy-neighbor issues)
# Or set limit = 4-8x request for burst capacity
resources:
  requests:
    cpu: 500m       # Scheduler uses this for placement
  limits:
    # cpu: not set  # ← No CPU limit! Let it burst.
    memory: 1536Mi  # Memory limit is fine (OOM is catastrophic)

Trade-offs

Design decisions and their consequences
Decision Benefit Cost When to Choose
Deep readiness checks (DB, Redis, threads) Accurate serving capacity signal Higher probe latency; cascade risk if dependency flaps Always for critical services; use timeouts on dependency checks
Separate management port Probes never compete with traffic Extra port to expose and configure in K8s Always in production; skip for local dev
preStop: sleep 10 Zero dropped requests during rollout Slower deployments (10s added per pod termination) Always for user-facing services; skip for batch jobs
maxUnavailable: 0 Never reduce capacity during deploy Requires extra resources (maxSurge pods need nodes) Critical services with strict SLA; use maxUnavailable=1 for dev
No CPU limits No throttling; better tail latency Noisy neighbor risk; harder capacity planning Latency-sensitive services; use limits for batch/background
Thread pool health indicator Prevents 503s from overloaded pods Pods marked unready under load → reduced capacity When you have enough replicas to absorb the re-routing
Bulkhead per downstream One slow dep can't exhaust all threads Complexity; need to size each bulkhead correctly When you call 3+ downstream services with varying latency
Circuit breaker (fail fast) Frees threads immediately on downstream failure Requests fail fast (might be worse than slow for some UX) Non-critical paths with fallback; critical paths need retry

The fundamental trade-off: Deep health checks give Kubernetes better signal about pod readiness, but they also make your pods more likely to be marked unready. If ALL pods fail readiness simultaneously (e.g., shared DB goes down), you get 503 because zero endpoints are available. The solution: don't include shared dependencies in ALL pods' readiness unless you have a fallback.

Follow-up Questions

Questions interviewers ask to go deeper
Q: "How would you handle a scenario where all pods fail readiness simultaneously because a shared database is down?"
This is the cascading readiness failure problem. Options: (1) Use a degraded state — if DB is down, serve cached responses and mark readiness as UP with a warning. (2) Only check DB in readiness for write endpoints; read endpoints can serve from cache. (3) Use a circuit breaker on the DB check itself — if DB has been down for > 60s, stop checking and return UP (accept degraded service is better than no service). (4) Split into separate deployments: one for reads (always ready) and one for writes (needs DB). The key insight: some service is better than no service.
Q: "What's the difference between a 502 and a 503 in this context?"
502 Bad Gateway: The proxy/ingress established a connection to the upstream pod but received an invalid response (e.g., connection reset mid-response, pod died mid-request). 503 Service Unavailable: The proxy/ingress couldn't find ANY available upstream to route to (all endpoints removed, or connection refused by all backends). In practice during deployments: 503 = no backends available (endpoint propagation); 502 = pod was killed mid-response (no graceful shutdown).
Q: "How would you implement canary deployments to avoid the rolling update 503 gap?"
Canary avoids the gap because you don't terminate old pods until new ones are proven: (1) Deploy new version as a separate Deployment with 1 replica. (2) Route 5% traffic via weighted routing (Istio VirtualService or ingress canary annotation). (3) Monitor error rates and latency for 10 minutes. (4) If clean, gradually shift traffic 5% → 25% → 50% → 100%. (5) Only then scale down old Deployment. Zero gap because old pods stay up until new pods are fully handling traffic. Tools: Argo Rollouts, Flagger, Istio traffic shifting.
Q: "How do you handle long-running requests during pod termination?"
Set terminationGracePeriodSeconds longer than your longest expected request. For example, if you have endpoints that take up to 60s: set terminationGracePeriodSeconds: 90, preStop: sleep 10, leaving 80s for graceful drain. In the app, on SIGTERM: (1) Return 503 for new health checks (readiness), (2) Stop accepting new requests, (3) Wait for in-flight requests to complete (with timeout), (4) Exit. For WebSocket connections: send a "reconnect" frame before closing. For streaming responses: complete the current chunk then close.
Q: "What if the health check endpoint itself is slow?"
If your readiness check takes > 3s (the timeout), Kubernetes treats it as a failure. Solutions: (1) Cache health status — run checks in a background thread every 5s, health endpoint returns cached result in < 1ms. (2) Async health checks — Spring Boot supports this with ReactiveHealthIndicator. (3) Reduce check scope — don't ping every dependency; use a pre-computed "canServe" boolean. (4) Increase timeoutSeconds — but this delays failure detection. Best practice: health endpoint should respond in < 100ms always.
Q: "How do you prevent Kubernetes from sending traffic during JVM warmup?"
JVM warmup (JIT compilation, class loading, cache priming) means the first N requests are slow. Solutions: (1) Startup probe with warm-up logic — don't pass until you've served N warm-up requests. (2) Readiness probe delay — delay readiness by 30s after startup for JIT to kick in. (3) Custom warmup bean — on startup, make synthetic requests to hot paths before marking ready. (4) CDS/AOT (Spring Boot 3.x) — reduce warmup with Ahead-of-Time compilation. (5) GraalVM native image — no warmup needed (instant peak performance).
Q: "How does this differ in a serverless/Lambda context?"
In Lambda, there's no long-running health check — but the equivalent problem is cold starts. The "health check passes but 503" equivalent is: (1) Lambda provisioned concurrency is exhausted → 429 throttling. (2) Lambda is alive but VPC ENI attachment takes 10s → timeout. (3) Lambda invoked successfully but downstream (inside VPC) is unreachable. Solutions: Provisioned concurrency, SnapStart (Java), reduce package size, keep-alive pings.

Summary

Key Takeaways:

  1. Health checks passing ≠ serving capacity. A pod can be "alive" (liveness ✅) and even "ready" (readiness ✅) but unable to serve due to thread exhaustion, CPU throttling, or downstream failures that the health check doesn't test.
  2. 503s originate at many layers — app (thread pool full), ingress (no backends / connection limit), service mesh (circuit breaker), gateway (rate limit), or Kubernetes itself (endpoint propagation delay).
  3. Separate liveness from readiness. Liveness = "is the process broken?" (restart if yes). Readiness = "can this pod serve traffic right now?" (stop routing if no). Never check external dependencies in liveness.
  4. Use a separate management port (8081) for health probes so they never compete with real traffic for Tomcat worker threads.
  5. Deep readiness checks should verify: thread pool utilization < 85%, DB connection pool available, critical downstream reachable. Fail readiness = stop traffic before users see 503s.
  6. Rolling deployments need: maxUnavailable: 0, preStop: sleep 10 (for iptables propagation), server.shutdown=graceful, and terminationGracePeriodSeconds > preStop + drain time.
  7. Bulkhead pattern prevents one slow downstream from consuming all threads. Allocate thread pools per downstream service so failures are isolated.
  8. Set aggressive timeouts on all downstream calls (3-5s, not 30s). Combined with circuit breakers, this prevents thread pile-up — the #1 cause of "healthy but 503."
  9. CPU throttling is invisible. Pods pass health checks but real requests timeout because CFS scheduler limits CPU. Monitor container_cpu_cfs_throttled_seconds_total. Consider removing CPU limits for latency-sensitive services.
  10. Debug with layers: Check ingress logs → Envoy stats → endpoint list → thread dump → resource metrics. Identify WHERE the 503 originates before fixing.

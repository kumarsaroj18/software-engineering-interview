Medium HikariCP Connection Pools

Why Can a HikariCP Connection Pool Become Exhausted Even When the Database CPU Is Below 20%?

Key Takeaway: Pool exhaustion is almost never about database capacity — it's about how long your application holds connections. A pool of 10 connections handling 5ms queries can serve 2,000 req/s, but a single @Transactional method calling a slow REST API holds a connection for seconds, starving the entire pool. The database sits idle while your application queues.

Interviewer's Intent

What they're really testing:

  • Do you understand that connection pool exhaustion ≠ database overload?
  • Can you distinguish between hold time (how long a connection is borrowed) vs query time (actual DB work)?
  • Do you know how @Transactional interacts with connection pools in Spring?
  • Can you diagnose a "SQLTransientConnectionException: Connection is not available" in production?
  • Do you understand the pool sizing formula and why bigger pools are often worse?
  • Have you dealt with connection leaks, and do you know how to detect them?
  • Can you reason about thread-to-connection ratios and deadlock scenarios?

Common trap: Junior candidates immediately say "increase the pool size" — this is almost always the wrong first answer. The interviewer wants you to explain why connections aren't being returned, not how to add more.

60-Second Interview Answer

Use this in the interview:

"A HikariCP pool exhausts when connections are held longer than necessary, not when the database is overloaded. The DB CPU being low actually confirms this — the database is idle because connections are borrowed but not actively executing queries.

The top causes are:
1. @Transactional wrapping HTTP calls — a method annotated @Transactional grabs a connection at entry, then calls a slow REST API for 2 seconds. The connection is held idle the entire time.
2. Connection leaks — connections borrowed but never returned due to exception paths that bypass close().
3. Long-running transactions — batch operations or report queries holding connections for minutes.
4. Propagation.REQUIRES_NEW — nested transactions that hold 2+ connections per request thread, effectively halving pool capacity.
5. Thread deadlocks on pool — all threads hold one connection and need a second, but the pool is empty.

Key insight: Pool throughput = poolSize / avgHoldTime. A pool of 10 with 5ms hold time → 2,000 req/s. The same pool with 2s hold time → 5 req/s. The database CPU doesn't change — it's the application's hold pattern that determines exhaustion."

Connection Lifecycle in HikariCP

How connections are created, borrowed, returned, and evicted 
  ┌─────────────────────────────────────────────────────────────────────┐
  │                    HikariCP Connection Lifecycle                     │
  ├─────────────────────────────────────────────────────────────────────┤
  │                                                                     │
  │   ┌──────────┐    getConnection()    ┌──────────────┐              │
  │   │  Thread  │ ───────────────────► │  ConcurrentBag │              │
  │   └──────────┘                       │  (Pool Store)  │              │
  │        │                             └───────┬────────┘              │
  │        │                                     │                       │
  │        │         ┌───────────────────────────┼────────────┐         │
  │        │         │ Try borrow in this order: │            │         │
  │        │         │ 1. Thread-local (last used by this thread)       │
  │        │         │ 2. Shared list (CAS operation)         │         │
  │        │         │ 3. handoffQueue (wait for return)      │         │
  │        │         │ 4. Timeout → SQLException              │         │
  │        │         └────────────────────────────────────────┘         │
  │        │                                                             │
  │        ▼              connection.close()                             │
  │   ┌──────────┐    (proxied — returns to pool)    ┌──────────┐      │
  │   │ Use Conn │ ──────────────────────────────► │ Returned  │      │
  │   └──────────┘                                   └──────────┘      │
  │                                                                     │
  └─────────────────────────────────────────────────────────────────────┘

  Connection States (PoolEntry):
  ═══════════════════════════════
  NOT_IN_USE  → Available for borrowing
  IN_USE      → Currently held by a thread
  REMOVED     → Marked for eviction (maxLifetime reached)
  RESERVED    → Being validated before handoff

Key Internals

ConcurrentBag — HikariCP's secret weapon. Unlike traditional pools that use a blocking queue (causing lock contention), HikariCP uses a lock-free ConcurrentBag with thread-local affinity:

// Simplified HikariCP ConcurrentBag.borrow() logic
public T borrow(long timeout, TimeUnit timeUnit) throws InterruptedException {
    // 1. Try thread-local list first (no synchronization needed)
    final List<Object> list = threadList.get();
    for (int i = list.size() - 1; i >= 0; i--) {
        final Object entry = list.remove(i);
        final T bagEntry = weakThreadLocals ? ((WeakReference<T>) entry).get() : (T) entry;
        if (bagEntry != null && bagEntry.compareAndSet(STATE_NOT_IN_USE, STATE_IN_USE)) {
            return bagEntry;  // Fast path — no contention
        }
    }

    // 2. Scan shared list with CAS
    final int waiting = waiters.incrementAndGet();
    try {
        for (T bagEntry : sharedList) {
            if (bagEntry.compareAndSet(STATE_NOT_IN_USE, STATE_IN_USE)) {
                if (waiting > 1) listener.addBagItem(waiting - 1);
                return bagEntry;
            }
        }
        // 3. Wait on handoff queue (this is where threads block during exhaustion)
        listener.addBagItem(waiting);
        T bagEntry = handoffQueue.poll(timeout, timeUnit);
        return bagEntry;  // null = timeout = SQLTransientConnectionException
    } finally {
        waiters.decrementAndGet();
    }
}

Connection Creation

// HikariCP creates connections asynchronously via HouseKeeper
// minimumIdle connections are maintained at all times
// New connections created when:
//   1. Pool initializes (minimumIdle connections)
//   2. Connection evicted (maxLifetime exceeded)
//   3. Demand exceeds available (up to maximumPoolSize)

// Key: connection creation is ASYNC — if all connections are in-use
// and pool is at max, new requests BLOCK on handoffQueue

Connection Eviction

maxLifetime (default: 30 min) — Connections are retired after this duration to prevent stale connections, DNS changes, and firewall timeouts. HikariCP adds a random jitter (±2.5%) to prevent mass eviction storms.

idleTimeout (default: 10 min) — Idle connections beyond minimumIdle are removed after this duration.

keepaliveTime (default: 0/disabled) — Periodic validation of idle connections.

Why This Matters for Exhaustion

The critical insight: a connection in IN_USE state cannot be evicted, cannot be borrowed by another thread, and counts against maximumPoolSize. If your code holds a connection for 5 seconds (e.g., waiting on an HTTP call inside @Transactional), that's one less connection for 5 seconds × your request rate = massive queuing.

Pool Sizing Theory

The HikariCP wiki formula and why small pools win

The Formula

HikariCP's recommended formula:

connections = ((core_count * 2) + effective_spindle_count)

For a 4-core server with SSD (1 spindle): (4 * 2) + 1 = 9 connections

For a 4-core server with 4 HDDs: (4 * 2) + 4 = 12 connections

  Why Small Pools Are Better — The Counter-Intuitive Truth
  ═════════════════════════════════════════════════════════

  Scenario: PostgreSQL on 4-core machine, SSD storage

  Pool Size = 50 connections:
  ┌─────────────────────────────────────────┐
  │ • 50 threads competing for 4 CPU cores  │
  │ • Massive context switching overhead    │
  │ • Lock contention on shared buffers     │
  │ • WAL write contention                  │
  │ • Effective throughput: ~1,800 TPS      │
  └─────────────────────────────────────────┘

  Pool Size = 10 connections:
  ┌─────────────────────────────────────────┐
  │ • 10 threads, low context switching     │
  │ • Minimal lock contention               │
  │ • Each query gets more CPU time         │
  │ • Lower latency per query               │
  │ • Effective throughput: ~2,200 TPS      │
  └─────────────────────────────────────────┘

  Result: FEWER connections = MORE throughput
  (up to the point where DB cores are idle)

Throughput Formula

// Pool throughput (requests/second the pool can handle):
// throughput = poolSize / avgConnectionHoldTime

// Example 1: Fast queries
// poolSize = 10, avgHoldTime = 5ms
// throughput = 10 / 0.005 = 2,000 req/s ✓

// Example 2: @Transactional wrapping HTTP call
// poolSize = 10, avgHoldTime = 2000ms (waiting for REST API)
// throughput = 10 / 2.0 = 5 req/s ✗ (POOL EXHAUSTED)

// Example 3: After increasing pool to 100 (wrong fix)
// poolSize = 100, avgHoldTime = 2000ms
// throughput = 100 / 2.0 = 50 req/s
// But now DB has 100 connections competing → query latency increases
// → hold time increases → still exhausts, just slower

Why Increasing Pool Size Is Usually Wrong

The "bigger pool" trap:

  • More connections = more memory on DB server (~10MB per connection in PostgreSQL)
  • More concurrent queries = more lock contention = slower queries = longer hold times
  • Creates a negative feedback loop: more connections → slower DB → longer hold → need more connections
  • Multiple application instances: 5 pods × 50 connections = 250 DB connections (PostgreSQL default max is 100!)
  • Masks the real problem — you're treating the symptom, not the cause

All Causes of Pool Exhaustion with Low DB CPU

Cause 1: Long-running transactions holding connections

Impact: HIGH — Each long transaction removes one connection from the pool for its entire duration.

// PROBLEM: Batch processing in a single transaction
@Transactional
public void generateMonthlyReport() {
    List<Order> orders = orderRepository.findByMonth(YearMonth.now()); // 500K rows
    
    for (Order order : orders) {
        ReportLine line = calculateMetrics(order); // CPU work, 10ms each
        reportRepository.save(line);               // DB write
    }
    // Connection held for: 500,000 × 10ms = 83 MINUTES
    // DB CPU: low (queries are fast, just too many)
    // Pool impact: 1 connection locked for 83 minutes
}

// FIX: Chunk processing with separate transactions
@Service
public class ReportService {
    @Autowired private PlatformTransactionManager txManager;
    
    public void generateMonthlyReport() {
        List<Long> orderIds = getOrderIds(YearMonth.now()); // Quick query
        
        Lists.partition(orderIds, 500).forEach(chunk -> {
            TransactionTemplate tx = new TransactionTemplate(txManager);
            tx.execute(status -> {
                List<Order> orders = orderRepository.findAllById(chunk);
                orders.forEach(order -> {
                    reportRepository.save(calculateMetrics(order));
                });
                return null;
            });
            // Connection returned after each chunk of 500
        });
    }
}
Cause 2: Connection leaks (borrowed but never returned)

Impact: CRITICAL — Leaked connections are never returned. Pool slowly drains to zero over hours/days.

// LEAK PATTERN 1: Manual DataSource usage without try-with-resources
public User findUser(Long id) {
    Connection conn = dataSource.getConnection();
    PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE id = ?");
    ps.setLong(1, id);
    ResultSet rs = ps.executeQuery();
    if (rs.next()) {
        return mapUser(rs);
    }
    conn.close(); // NEVER REACHED if rs.next() throws or returns false early!
    return null;
}

// LEAK PATTERN 2: Exception in @Transactional with manual connection
@Transactional
public void processPayment(PaymentRequest req) {
    Connection reportConn = reportDataSource.getConnection(); // Second datasource
    try {
        paymentRepository.save(new Payment(req));
        generateReceipt(reportConn, req); // If this throws...
    } finally {
        // Developer forgot this finally block
        // reportConn is LEAKED — never returned to report pool
    }
}

// LEAK PATTERN 3: Reactive/async code with connections
public CompletableFuture<User> findUserAsync(Long id) {
    Connection conn = dataSource.getConnection(); // Borrowed on thread-1
    return CompletableFuture.supplyAsync(() -> {
        // Runs on ForkJoinPool thread — different thread!
        // If exception here, conn never closed
        return queryUser(conn, id);
    }); // conn.close() never called if future is cancelled/timed out
}

// FIX: Always use try-with-resources or let Spring manage connections
public User findUserFixed(Long id) {
    try (Connection conn = dataSource.getConnection();
         PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE id = ?")) {
        ps.setLong(1, id);
        try (ResultSet rs = ps.executeQuery()) {
            return rs.next() ? mapUser(rs) : null;
        }
    }  // Connection ALWAYS returned, even on exception
}

Cause 3: Deadlocks between threads waiting for connections

Impact: CRITICAL — All pool connections held, all threads blocked waiting for more. Complete deadlock.

// DEADLOCK SCENARIO: Nested @Transactional with REQUIRES_NEW
// Pool size: 10, Tomcat threads: 200

@Service
public class OrderService {
    
    @Transactional  // Borrows Connection #1
    public void placeOrder(OrderRequest req) {
        Order order = orderRepository.save(new Order(req));  // Uses Connection #1
        
        // This needs a NEW connection (REQUIRES_NEW suspends outer tx)
        auditService.logOrderCreated(order);  // Needs Connection #2
        
        inventoryService.reserve(order);  // Also REQUIRES_NEW → Connection #3
    }
}

@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)  // Borrows Connection #2
    public void logOrderCreated(Order order) {
        auditRepository.save(new AuditLog("ORDER_CREATED", order.getId()));
    }
}

// DEADLOCK SCENARIO:
// With pool size = 10 and 10 concurrent requests:
// - All 10 threads borrow Connection #1 (pool empty)
// - All 10 threads need Connection #2 for REQUIRES_NEW
// - Pool is empty → all 10 threads WAIT
// - No thread can finish → no connection will be returned
// - DEADLOCK: connectionTimeout fires after 30s → all fail

// FIX: Use REQUIRED (same connection) or async pattern
@Transactional(propagation = Propagation.REQUIRED)  // Reuses parent connection
public void logOrderCreated(Order order) {
    auditRepository.save(new AuditLog("ORDER_CREATED", order.getId()));
}

  Thread-2:  [Holds Conn-2]  ──► WAITING for any connection (REQUIRES_NEW)
  Thread-3:  [Holds Conn-3]  ──► WAITING for any connection (REQUIRES_NEW)
  ...
  Thread-10: [Holds Conn-10] ──► WAITING for any connection (REQUIRES_NEW)

  Pool Status: 10/10 IN_USE, 0 available, 10 threads in handoffQueue
  Result: DEADLOCK — no thread can proceed, no connection will be freed

  Prevention Rule:
  Max concurrent requests ≤ poolSize / max_connections_per_request
  If each request needs 2 connections: max_concurrent = poolSize / 2 = 5
Cause 4: @Transactional on methods calling external services

Impact: HIGH — The #1 cause of pool exhaustion in Spring Boot microservices.

// THE CLASSIC ANTI-PATTERN
@Service
public class PaymentService {
    
    @Transactional  // ← Connection borrowed HERE (before any DB work)
    public PaymentResult processPayment(PaymentRequest req) {
        
        // 1. Quick DB read (2ms)
        Account account = accountRepository.findById(req.getAccountId()).orElseThrow();
        
        // 2. Call payment gateway REST API (avg 800ms, P99 = 5 seconds!)
        GatewayResponse response = paymentGateway.charge(req.getAmount(), account.getToken());
        //    ↑↑↑ CONNECTION IS HELD IDLE FOR 800ms-5s WHILE WAITING FOR HTTP RESPONSE ↑↑↑
        
        // 3. Quick DB write (3ms)
        Payment payment = new Payment(account, response.getTransactionId(), req.getAmount());
        paymentRepository.save(payment);
        
        return new PaymentResult(payment);
    }
    // Total connection hold time: 2ms + 800ms + 3ms ≈ 805ms
    // Actual DB time: 5ms (0.6% of hold time!)
    // Connection idle for 99.4% of the time it's borrowed
}

// IMPACT CALCULATION:
// Pool size: 10 connections
// Avg hold time: 800ms (dominated by HTTP call)
// Max throughput: 10 / 0.8 = 12.5 requests/second
// At 50 req/s: pool exhausts in seconds
// DB CPU: nearly 0% (only doing 5ms of work per request)

// ═══════════════════════════════════════════════════════════════
// FIX: Separate the HTTP call from the transaction
// ═══════════════════════════════════════════════════════════════

@Service
public class PaymentService {
    
    public PaymentResult processPayment(PaymentRequest req) {
        
        // 1. Read account (short transaction, auto-committed)
        Account account = accountRepository.findById(req.getAccountId()).orElseThrow();
        
        // 2. Call payment gateway — NO connection held!
        GatewayResponse response = paymentGateway.charge(req.getAmount(), account.getToken());
        
        // 3. Write result (short transaction)
        return savePaymentResult(account, response, req);
    }
    
    @Transactional  // Only holds connection for the 3ms write
    protected PaymentResult savePaymentResult(Account account, GatewayResponse response, PaymentRequest req) {
        Payment payment = new Payment(account, response.getTransactionId(), req.getAmount());
        paymentRepository.save(payment);
        return new PaymentResult(payment);
    }
    // New hold time: 3ms
    // New max throughput: 10 / 0.003 = 3,333 requests/second (266x improvement!)
}

Spring Boot gotcha: When spring.jpa.open-in-view=true (the DEFAULT!), a connection is borrowed at the start of the HTTP request and held until the response is sent. This means ANY slow operation in your controller holds a connection — even if it's not in a @Transactional method.

# ALWAYS disable open-in-view in production
spring:
  jpa:
    open-in-view: false  # Default is TRUE — dangerous for connection pools

Cause 6: REQUIRES_NEW nesting (holds multiple connections per request) 
// PROBLEM: Each REQUIRES_NEW suspends the parent and borrows a NEW connection
@Service
public class TransferService {
    
    @Transactional  // Connection #1
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        accountRepository.debit(fromId, amount);
        accountRepository.credit(toId, amount);
        
        // Each of these needs its own connection (REQUIRES_NEW)
        notificationService.sendDebitNotification(fromId, amount);   // Connection #2
        notificationService.sendCreditNotification(toId, amount);    // Connection #2 (reused after first returns)
        auditService.logTransfer(fromId, toId, amount);              // Connection #2
        fraudService.checkPattern(fromId, amount);                    // Connection #2
    }
}

// Connection #1 held by all 10 threads = 10 connections
// Connection #2 needed by all 10 threads = 10 more connections needed
// Pool size 10 → DEADLOCK (same as Cause 3)

@Transactional  // Connection #1

Cause 7: Slow queries not causing CPU (waiting on locks, I/O) 
-- Queries that take seconds but don't use CPU:

-- 1. Row-level lock wait (another transaction holds the lock)
UPDATE accounts SET balance = balance - 100 WHERE id = 42;
-- If another transaction is updating the same row, this WAITS
-- DB CPU: idle (just waiting for lock release)
-- Connection: held for entire wait duration

-- 2. Disk I/O wait (cold data not in buffer pool)
SELECT * FROM audit_logs WHERE created_at > '2024-01-01' ORDER BY created_at;
-- 500GB table, 8GB buffer pool → sequential disk scan
-- DB CPU: low (waiting for disk reads)
-- Connection: held for 30+ seconds

-- 3. Lock escalation / table lock
ALTER TABLE large_table ADD COLUMN new_col VARCHAR(255);
-- DDL takes an ACCESS EXCLUSIVE lock — blocks ALL other queries on this table
-- All connections waiting for this table: held but idle

-- 4. Waiting for WAL flush (synchronous_commit = on)
INSERT INTO orders VALUES (...);
-- Must wait for WAL write to disk before returning
-- On slow storage: 5-20ms per commit
-- DB CPU: low (waiting for fsync)

-- Diagnostic query: Find queries waiting on locks
SELECT 
    pid,
    now() - pg_stat_activity.query_start AS duration,
    query,
    state,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE state != 'idle'
  AND wait_event IS NOT NULL
ORDER BY duration DESC;
Cause 8: Connection validation overhead 
# Connection validation can add latency to every borrow

spring:
  datasource:
    hikari:
      # This sends "SELECT 1" or JDBC isValid() on EVERY borrow:
      connection-test-query: "SELECT 1"  # AVOID — use JDBC4 validation instead
      
      # JDBC4 validation (isValid) — much faster, uses TCP ping:
      # No connection-test-query needed — HikariCP uses isValid() by default
      
      # But validation still has a cost:
      # - Network round-trip to DB: 0.5-2ms per validation
      # - Under high throughput: 2000 borrows/sec × 1ms = 2 seconds of validation/sec
      # - Each validation briefly holds the connection in RESERVED state
      
      # The real danger: validation timeout
      validation-timeout: 5000  # Default: 5 seconds
      # If DB is slow to respond to isValid():
      # - Connection sits in RESERVED state for up to 5s
      # - Other threads can't borrow it
      # - Pool appears exhausted even though connections exist

HikariCP optimization: HikariCP skips validation if the connection was used less than 500ms ago (configurable via internal housekeeping). This means under sustained load, most borrows skip validation entirely. The risk is during idle-to-active transitions.

Custom Leak Detection with Micrometer

@Configuration
public class ConnectionLeakMonitor {
    
    @Bean
    public BeanPostProcessor hikariMetricsPostProcessor(MeterRegistry registry) {
        return new BeanPostProcessor() {
            @Override
            public Object postProcessAfterInitialization(Object bean, String beanName) {
                if (bean instanceof HikariDataSource ds) {
                    ds.setMetricsTrackerFactory(new MicrometerMetricsTrackerFactory(registry));
                    
                    // Custom gauge: connections that have been active > 30 seconds
                    Gauge.builder("hikaricp.connections.long_running",
                            ds.getHikariPoolMXBean(),
                            pool -> pool.getActiveConnections())  // Simplified
                        .tag("pool", ds.getPoolName())
                        .register(registry);
                }
                return bean;
            }
        };
    }
}

        return (Connection) Proxy.newProxyInstance(
            conn.getClass().getClassLoader(),
            new Class[]{Connection.class},
            (proxy, method, args) -> {
                if ("close".equals(method.getName())) {
                    long duration = System.nanoTime() - start;
                    borrowDurationTimer.record(duration, TimeUnit.NANOSECONDS);
                    if (duration > TimeUnit.SECONDS.toNanos(30)) {
                        leakCounter.increment();
                        log.warn("Connection held for {}s by thread {}",
                            TimeUnit.NANOSECONDS.toSeconds(duration),
                            Thread.currentThread().getName());
                    }
                }
                return method.invoke(conn, args);
            });
    }
}

@Service
public class PaymentService {
    
    @Transactional  // ← Connection borrowed at entry
    public PaymentResult processPayment(PaymentRequest req) {
        Account account = accountRepository.findById(req.getAccountId()).orElseThrow();
        
        // NEW CODE ADDED IN v2.34:
        FraudResult fraud = fraudCheckClient.checkTransaction(  // ← HTTP call, 200ms-8s
            account.getId(), req.getAmount(), req.getMerchant()
        );
        if (fraud.isRejected()) {
            throw new FraudRejectedException(fraud.getReason());
        }
        // END NEW CODE
        
        Payment payment = paymentRepository.save(new Payment(account, req));
        return new PaymentResult(payment);
    }
    // Connection held for entire fraud check duration (200ms-8s)
}

Why It Wasn't Caught in Testing

  • Unit tests: Fraud client was mocked — returned in 0ms
  • Integration tests: WireMock stub returned in 5ms
  • Staging: Only 10 req/s — pool of 10 was sufficient at 200ms hold time (50 req/s capacity)
  • Production: 200 req/s + fraud API degradation (P99=8s) → pool capacity dropped to 1.25 req/s

The bug only manifests under production load + downstream degradation — the combination that load tests rarely simulate.

The Fix

@Service
public class PaymentService {
    
    // NO @Transactional on the orchestration method
    public PaymentResult processPayment(PaymentRequest req) {
        // 1. Read (auto-commit, connection borrowed and returned immediately)
        Account account = accountRepository.findById(req.getAccountId()).orElseThrow();
        
        // 2. Fraud check — NO connection held
        FraudResult fraud = fraudCheckClient.checkTransaction(
            account.getId(), req.getAmount(), req.getMerchant()
        );
        if (fraud.isRejected()) {
            throw new FraudRejectedException(fraud.getReason());
        }
        
        // 3. Write — short transaction (3ms)
        return completePayment(account, req);
    }
    
    @Transactional  // Connection held only for the DB write
    public PaymentResult completePayment(Account account, PaymentRequest req) {
        Payment payment = paymentRepository.save(new Payment(account, req));
        accountRepository.updateBalance(account.getId(), req.getAmount().negate());
        return new PaymentResult(payment);
    }
}

// Temporary diagnostic: Add AOP to measure @Transactional hold time
@Aspect
@Component
@Profile("debug")  // Only enable when debugging
public class TransactionHoldTimeAspect {
    
    private static final Logger log = LoggerFactory.getLogger(TransactionHoldTimeAspect.class);
    private final Timer holdTimer;
    
    public TransactionHoldTimeAspect(MeterRegistry registry) {
        this.holdTimer = Timer.builder("transaction.hold.time")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(registry);
    }
    
    @Around("@annotation(org.springframework.transaction.annotation.Transactional)")
    public Object measureHoldTime(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            return pjp.proceed();
        } finally {
            long duration = System.nanoTime() - start;
            long durationMs = TimeUnit.NANOSECONDS.toMillis(duration);
            
            holdTimer.record(duration, TimeUnit.NANOSECONDS);
            
            if (durationMs > 1000) {  // Log any transaction > 1 second
                log.warn("Long transaction: {}ms in {}.{}()",
                    durationMs,
                    pjp.getSignature().getDeclaringType().getSimpleName(),
                    pjp.getSignature().getName());
            }
        }
    }
}

Separate Read/Write Connection Pools

@Configuration
public class DataSourceConfig {
    
    @Bean
    @Primary
    @ConfigurationProperties("spring.datasource.write")
    public DataSource writeDataSource() {
        HikariDataSource ds = new HikariDataSource();
        ds.setPoolName("write-pool");
        ds.setMaximumPoolSize(10);         // Small: writes need consistency
        ds.setConnectionTimeout(3000);
        ds.setLeakDetectionThreshold(5000);
        return ds;
    }
    
    @Bean
    @ConfigurationProperties("spring.datasource.read")
    public DataSource readDataSource() {
        HikariDataSource ds = new HikariDataSource();
        ds.setPoolName("read-pool");
        ds.setMaximumPoolSize(20);          // Larger: reads are more frequent
        ds.setConnectionTimeout(2000);
        ds.setReadOnly(true);               // Connection-level read-only hint
        ds.setLeakDetectionThreshold(10000);
        return ds;
    }
    
    @Bean
    public DataSource routingDataSource(
            @Qualifier("writeDataSource") DataSource writeDs,
            @Qualifier("readDataSource") DataSource readDs) {
        
        var router = new AbstractRoutingDataSource() {
            @Override
            protected Object determineCurrentLookupKey() {
                return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
                    ? "read" : "write";
            }
        };
        
        router.setTargetDataSources(Map.of("write", writeDs, "read", readDs));
        router.setDefaultTargetDataSource(writeDs);
        return router;
    }
}

Connection-Scoping Pattern: Minimize Hold Time

// PATTERN: Separate read, process, write phases
@Service
public class OrderProcessingService {
    
    private final OrderRepository orderRepository;
    private final InventoryClient inventoryClient;   // HTTP client
    private final PaymentClient paymentClient;       // HTTP client
    private final TransactionTemplate txTemplate;
    
    // Orchestration method — NO @Transactional
    public OrderResult processOrder(OrderRequest request) {
        
        // Phase 1: READ (short connection borrow, auto-commit)
        Order order = orderRepository.findById(request.getOrderId())
            .orElseThrow(() -> new OrderNotFoundException(request.getOrderId()));
        List<OrderItem> items = order.getItems();  // Eager loaded in query
        
        // Phase 2: EXTERNAL CALLS (no connection held!)
        InventoryResult inventory = inventoryClient.reserve(items);  // 200ms
        if (!inventory.isAvailable()) {
            return OrderResult.outOfStock(inventory.getUnavailableItems());
        }
        
        PaymentResult payment = paymentClient.charge(order.getTotal()); // 500ms
        if (!payment.isSuccess()) {
            inventoryClient.release(items);  // Compensate
            return OrderResult.paymentFailed(payment.getReason());
        }
        
        // Phase 3: WRITE (short transaction, ~5ms)
        return txTemplate.execute(status -> {
            order.setStatus(OrderStatus.CONFIRMED);
            order.setPaymentId(payment.getTransactionId());
            orderRepository.save(order);
            
            eventPublisher.publish(new OrderConfirmedEvent(order));
            return OrderResult.success(order);
        });
        
        // Total connection hold time: ~7ms (read 2ms + write 5ms)
        // Total method time: ~707ms (dominated by HTTP calls)
        // Connection utilization: 1% of method duration (99% improvement!)
    }
}

Programmatic Transaction Management for Complex Flows

@Service
public class BatchImportService {
    
    private final PlatformTransactionManager txManager;
    private final JdbcTemplate jdbcTemplate;
    
    // Process 100K records without holding a connection for the entire batch
    public ImportResult importRecords(List<Record> records) {
        int success = 0;
        int failed = 0;
        
        // Process in chunks of 500
        for (List<Record> chunk : Lists.partition(records, 500)) {
            TransactionTemplate tx = new TransactionTemplate(txManager);
            tx.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
            tx.setTimeout(10);  // 10 second timeout per chunk
            
            try {
                Integer inserted = tx.execute(status -> {
                    // Connection held only for this chunk (~50ms)
                    return jdbcTemplate.batchUpdate(
                        "INSERT INTO records (id, data, created_at) VALUES (?, ?, ?)",
                        new BatchPreparedStatementSetter() {
                            @Override
                            public void setValues(PreparedStatement ps, int i) throws SQLException {
                                Record r = chunk.get(i);
                                ps.setLong(1, r.getId());
                                ps.setString(2, r.getData());
                                ps.setTimestamp(3, Timestamp.from(Instant.now()));
                            }
                            @Override
                            public int getBatchSize() { return chunk.size(); }
                        }
                    ).length;
                });
                success += inserted;
            } catch (Exception e) {
                failed += chunk.size();
                log.warn("Chunk failed: {}", e.getMessage());
            }
            // Connection returned after each chunk!
        }
        
        return new ImportResult(success, failed);
    }
}

Common Mistakes

Table of mistakes, symptoms, and fixes
# Mistake Symptom Fix
1 @Transactional on controller methods Connection held for entire request including serialization, compression Move @Transactional to service layer, keep transactions short
2 @Transactional wrapping HTTP calls Pool exhaustion under load; DB CPU is low Restructure: read → call API → write (separate transactions)
3 Increasing pool size as first fix Temporarily helps, then same problem at slightly higher load Find WHY connections are held long; fix hold time, not pool size
4 REQUIRES_NEW without pool math Intermittent deadlocks under moderate load Use REQUIRED, or ensure poolSize ≥ threads × connections_per_request
5 No connectionTimeout configured Threads block for 30s (default) before failing — cascading timeouts Set connectionTimeout=3000ms — fail fast
6 spring.jpa.open-in-view=true (default!) Connection held from request start to response end Set open-in-view=false; use DTOs and eager fetching
7 No leak detection threshold Slow leak goes undetected for days until production incident Set leak-detection-threshold=10000 (10s) in all environments
8 Same pool for OLTP and reporting queries One report query holds a connection for 30s, starves API traffic Separate read/write pools; route reports to read replica
9 Not accounting for rolling deployments During deploy, old + new pods exceed DB max_connections poolSize × (maxPods + surge) ≤ DB max_connections - reserved
10 Connection-test-query instead of JDBC4 isValid() Extra query on every borrow; doubles validation overhead Remove connection-test-query; HikariCP uses isValid() by default
11 maxLifetime > DB/firewall idle timeout Borrowed connections are already dead (reset by firewall) Set maxLifetime 2-3 minutes LESS than DB wait_timeout or firewall idle timeout
12 Manual DataSource.getConnection() without try-with-resources Connection leaks on exception paths; gradual pool drain Always use try-with-resources or let Spring/JPA manage connections

Follow-up Interview Questions

Likely follow-ups and how to answer
Q: "How do you decide the right pool size for a new service?"
Start with the HikariCP formula: (cores × 2) + spindles for the database server. For most microservices with short transactions, 10 connections is plenty. Then validate: measure connection hold time under load. If P99 hold time is 5ms and you need 1000 req/s, you need at least 5 connections (1000 × 0.005). Add 50% headroom. Also account for: number of pods, rolling deployments, and DB max_connections. Formula: poolPerPod ≤ (db_max_connections - reserved) / (maxPods + surgeCount).
Q: "What happens when you set the pool size too large?"
Counter-intuitively, throughput decreases. More concurrent queries on the database means more context switching, more lock contention (especially on shared buffers and WAL), higher cache miss rate, and longer individual query times. This increases hold time, which creates a negative feedback loop. The PostgreSQL wiki documents this — a benchmark showed 50 connections performing worse than 10 on a 4-core server.
Q: "How does Spring Boot's @Transactional actually acquire a connection?"
When a @Transactional method is entered, Spring's TransactionInterceptor calls the PlatformTransactionManager, which calls DataSource.getConnection(). This happens before the first line of your method executes. The connection is bound to the current thread via TransactionSynchronizationManager (ThreadLocal). It's released when the method returns (commit) or throws (rollback). Key point: the connection is borrowed at method entry, not at the first query.
Q: "Can virtual threads (Project Loom) solve pool exhaustion?"
Partially. Virtual threads solve thread pool exhaustion (you can have millions of virtual threads), but they don't solve connection pool exhaustion. If you have 10,000 virtual threads all needing a database connection, and your pool has 10 connections, 9,990 virtual threads will still wait. However, virtual threads make the wait non-blocking — they don't pin platform threads. The real fix is still reducing hold time. One caveat: synchronized blocks inside virtual threads can pin the carrier thread — use ReentrantLock instead.
Q: "How do you handle pool exhaustion gracefully in production?"
Three strategies: (1) Fail fast — set connectionTimeout to 3s so requests fail quickly rather than queuing for 30s, (2) Circuit breaker — after N timeouts, open the circuit and return a degraded response without even trying to get a connection, (3) Backpressure — use a semaphore or bulkhead to limit concurrent requests to the DB-dependent code path, shedding excess load at the API layer before it reaches the pool.
Q: "What's the difference between connectionTimeout and socketTimeout?"
connectionTimeout is how long a thread waits to borrow a connection from the pool (HikariCP setting). socketTimeout is how long the JDBC driver waits for a response from the database after sending a query (JDBC/driver setting). Pool exhaustion causes connectionTimeout. A hung database query causes socketTimeout. Both should be configured: connectionTimeout=3s, socketTimeout=30s typically.
Q: "You have a Spring Boot service with 200 Tomcat threads and a pool of 10. Is this a problem?"
Not necessarily — it depends on hold time. If queries take 2ms, the pool can serve 5,000 req/s (10/0.002), which handles 200 concurrent threads easily. The ratio only becomes a problem when hold time increases: if each request holds a connection for 100ms, pool throughput drops to 100 req/s — only 100 Tomcat threads can be actively served, and the other 100 queue. The rule: maxPoolSize / avgHoldTime ≥ expectedConcurrency.
Q: "How would you detect a connection leak that only happens in a specific error path?"
Four approaches: (1) Enable leak-detection-threshold — HikariCP logs the stack trace of where the connection was borrowed, (2) Monitor hikaricp_connections_active over days — leaks show a monotonic increase pattern (staircase graph), (3) Check pg_stat_activity for growing 'idle in transaction' connections, (4) Use integration tests with a tiny pool (size=1) and timeout=1s — leaked connections make subsequent tests fail immediately, catching the leak in CI.

Summary

Key Takeaways:

  1. Pool exhaustion ≠ database overload. Low DB CPU confirms connections are being held without doing work — look at what your application is doing between borrowing and returning the connection.
  2. Pool throughput = poolSize / avgHoldTime. A pool of 10 with 5ms hold time serves 2,000 req/s. The same pool with 2s hold time serves only 5 req/s. Fix hold time, not pool size.
  3. @Transactional grabs a connection at method entry. Any slow operation inside that method (HTTP calls, file I/O, computation) holds the connection idle. Restructure: read → external call → write.
  4. REQUIRES_NEW holds multiple connections per thread. With pool=10 and 2 connections per request, max safe concurrency is 5. Size your pool for the worst-case connections-per-request.
  5. Smaller pools are usually faster. The HikariCP formula is (cores×2)+spindles. More connections = more DB contention = slower queries = longer hold time = worse exhaustion.
  6. Set connectionTimeout low (3s). Fail fast. Don't let 200 Tomcat threads queue for 30 seconds — that's 200 threads doing nothing for 30s, cascading timeouts to callers.
  7. Always enable leak detection. Set leak-detection-threshold=10000. It costs nothing and catches leaks before they become P1 incidents.
  8. Thread dump is your best friend. Take a dump during exhaustion — it shows exactly where threads holding connections are stuck (HTTP client? lock? computation?).
  9. Monitor pending threads, not just active connections. Active=max is a symptom; pending>0 is the pain your users feel.
  10. Disable open-in-view. Spring Boot's spring.jpa.open-in-view=true (default!) holds a connection for the entire HTTP request lifecycle.

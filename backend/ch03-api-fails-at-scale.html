Hard Thread Pools Load Testing Performance

REST API Works at Low Traffic but Fails at 10,000 Requests/Second

Key Takeaway: At scale, every shared resource becomes a bottleneck. The investigation order matters: thread pools → connection pools → database → network/OS limits → application code. Most failures at 10K req/s come from resource exhaustion, not logic bugs.

Interviewer's Intent

What they're really testing:

  • Can you systematically diagnose performance issues rather than guessing?
  • Do you understand the full request path — from Linux kernel to Spring to DB?
  • Do you know where bottlenecks occur at each order of magnitude (100 → 1K → 10K)?
  • Can you use profiling tools: thread dumps, flame graphs, Prometheus, Grafana?
  • Do you understand the difference between CPU-bound and I/O-bound workloads?

60-Second Interview Answer

Use this in the interview:

"When a REST API breaks at 10K concurrent requests, I investigate in a specific order based on where exhaustion typically happens first:

1. Tomcat thread pool — default is 200 threads. At 10K req/s with 100ms avg latency, Little's Law says you need L = 10,000 × 0.1 = 1,000 threads in-flight simultaneously. With only 200 available, requests queue up and eventually get rejected or time out.
2. Connection pool (HikariCP) — default is 10 connections. Even with 200 Tomcat threads, only 10 can query the DB simultaneously. Others block on getConnection().
3. Database — 10K requests hitting a DB with 100 max connections creates lock contention, slow queries, and I/O saturation.
4. OS limits — file descriptors (ulimit), ephemeral port exhaustion, TCP backlog queue, TIME_WAIT accumulation.
5. Downstream services — if each request calls 3 downstream APIs, you're making 30K outbound HTTP calls.

My first action would be taking a thread dump during the failure — it immediately shows where threads are stuck. Then I'd check connection pool metrics and DB slow query logs."

Capacity Estimation Model

Little's Law — the math behind concurrency limits

Little's Law: L = λ × W
Where: L = concurrent requests in system, λ = arrival rate (req/s), W = avg response time (seconds)

  Example: Can our API handle 10,000 req/s?
  ══════════════════════════════════════════

  Given:
  • Tomcat threads: 200 (default)
  • Avg response time: 50ms (0.05s)
  • HikariCP pool: 10 connections

  Max throughput with Tomcat threads:
  λ_max = L / W = 200 / 0.05 = 4,000 req/s  ← BOTTLENECK!
  
  But wait — with HikariCP pool of 10:
  λ_max = 10 / 0.05 = 200 req/s  ← REAL BOTTLENECK!
  
  ╔═════════════════════════════════════════════════════════════╗
  ║ Even with 200 Tomcat threads, if each request holds a DB   ║
  ║ connection for 50ms, effective throughput = 200 req/s.     ║
  ║ 190 threads are just WAITING for a connection.             ║
  ╚═════════════════════════════════════════════════════════════╝

  To handle 10,000 req/s at 50ms latency:
  • Need L = 10000 × 0.05 = 500 concurrent requests in-flight
  • Tomcat threads: ≥ 500 (or use async/reactive)
  • DB connections: 500 × (% time holding conn)
    If ~30% of response time is DB: 500 × 0.3 ≈ 150 connections (rough estimate;
    actual need depends on query overlap, batching, and cache hit rate)
Bottleneck progression as load increases 
  Load →   100 req/s    1,000 req/s    10,000 req/s    100,000 req/s
           ─────────    ───────────    ────────────    ─────────────
  
  Thread   ✅ Fine       ⚠️ Pressure   ❌ Exhausted    ❌ Exhausted
  Pool     (20 active)  (180 active)  (200 stuck)    (need reactive)
  
  Conn     ✅ Fine       ⚠️ Contention ❌ Exhausted    ❌ Exhausted
  Pool     (3 active)   (10 active)   (10+190 wait)  (need sharding)
  
  Database ✅ Fine       ✅ Fine        ⚠️ Lock waits   ❌ Saturated
           (low IOPS)   (some waits)  (CPU 80%)      (need replicas)
  
  Network  ✅ Fine       ✅ Fine        ⚠️ Ports fill   ❌ Exhausted
           (few conns)  (200 conns)   (TIME_WAIT)    (ephem ports)
  
  GC       ✅ Fine       ✅ Fine        ⚠️ More allocs  ❌ STW pauses
           (minor GC)   (minor GC)   (full GC 1/hr)  (full GC/min)
  
  CPU      ✅ Fine       ✅ Fine        ⚠️ 70-80%       ❌ Saturated
           (5%)         (30%)        (context sw.)   (need scale-out)

Thread Pool Exhaustion — The First Wall

Tomcat thread pool internals 
# Default Spring Boot Tomcat settings
server:
  tomcat:
    threads:
      max: 200          # Max worker threads
      min-spare: 10     # Threads kept alive when idle
    accept-count: 100   # OS-level TCP backlog queue
    max-connections: 8192 # Max concurrent connections (NIO connector default)

  Tomcat NIO Architecture (Spring Boot default):
  ═══════════════════════════════════════════════

  Incoming TCP connections
        │
        ▼
  ┌─────────────────────────────────────────────────┐
  │  Acceptor Thread (1)                             │
  │  Accepts TCP connections from OS backlog         │
  │  max-connections: 8192 (NIO selector limit)      │
  └──────────────────────┬──────────────────────────┘
                         │
                         ▼
  ┌─────────────────────────────────────────────────┐
  │  Poller Thread (1-2)                             │
  │  Monitors sockets for readable data (NIO)       │
  │  Non-blocking — handles thousands of connections │
  └──────────────────────┬──────────────────────────┘
                         │ Socket has data ready
                         ▼
  ┌─────────────────────────────────────────────────┐
  │  Worker Thread Pool (10-200)                     │
  │  Executes your @Controller methods              │
  │  BLOCKING — each thread handles ONE request     │
  │                                                  │
  │  Thread-1: GET /api/orders (querying DB...)     │
  │  Thread-2: POST /api/payments (calling Stripe..)│
  │  Thread-3: GET /api/users (waiting on Redis...) │
  │  ...                                             │
  │  Thread-200: PUT /api/cart (blocked on DB conn) │
  │                                                  │
  │  ❌ Thread-201: NO THREAD AVAILABLE!             │
  │  → Request sits in accept-count queue (100 max) │
  │  → Queue full → connection refused/dropped/timed out │
  └─────────────────────────────────────────────────┘

Quick Diagnosis: If 180+ threads are in TIMED_WAITING on HikariPool.getConnection(), your bottleneck is the connection pool, not the thread pool. Increasing Tomcat threads would only create more threads waiting for connections.

Connection Pool Bottlenecks

HikariCP — why 10 connections is the default and when it's not enough 
  HikariCP Request Flow:
  ═══════════════════════

  200 Tomcat threads competing for 10 DB connections:

  Thread-1 ──┐
  Thread-2 ──┤
  Thread-3 ──┤
  ...        ├──▶ HikariPool (size=10) ──▶ PostgreSQL
  Thread-198 ┤       │                      (max_connections=100)
  Thread-199 ┤       │
  Thread-200 ┘       │
                     │
              ┌──────┴──────┐
              │ 10 active   │ ← Actually executing queries
              │ 190 WAITING │ ← Blocked on getConnection()
              │             │   (timeout: 30s default)
              │ After 30s:  │
              │ SQLException│ ← "Connection is not available"
              └─────────────┘
        
// The exception you'll see in logs:
// java.sql.SQLTransientConnectionException: HikariPool-1 - Connection is not available,
// request timed out after 30000ms.
// Active: 10, Idle: 0, Waiting: 190, Total: 10

// HikariCP pool size heuristic (commonly cited from HikariCP wiki):
// connections ≈ ((core_count * 2) + effective_spindle_count)
// For SSD with 4-core DB server: (4 * 2) + 1 = 9 ≈ 10 (the default!)
// ⚠️ This is a starting point, not a rule. Actual pool size should be
// determined through load testing with your specific query patterns.

// BUT: this assumes queries are fast (< 5ms average)
// If avg query time = 50ms and you need 1000 req/s throughput:
// connections_needed = throughput × query_time = 1000 × 0.05 = 50
Tuning HikariCP for high throughput 
# application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50          # Match calculated need
      minimum-idle: 10               # Keep warm connections
      connection-timeout: 5000       # Fail fast (not 30s default!)
      # Should be well below your HTTP timeout so users get a clear error
      # rather than hanging until the gateway times out
      idle-timeout: 300000           # 5 min idle before close
      max-lifetime: 1800000          # 30 min max connection age
      leak-detection-threshold: 10000 # Alert if connection held > 10s
      # ⚠️ Intended for debugging — enable temporarily during investigations.
      # Permanent use in production may generate false positives under load.
      
      # Critical: register MBeans for monitoring
      register-mbeans: true
      pool-name: OrderServicePool

Database Bottlenecks

PostgreSQL under 10K req/s — what breaks first
Bottleneck Symptom How to Detect Fix
Lock contention Queries slow, lock_timeout errors pg_stat_activity shows wait_event = Lock Reduce tx duration, use skip locked, partition hot tables
Connection limit too many connections error SELECT count(*) FROM pg_stat_activity PgBouncer, connection pooling at DB level
Slow queries P99 latency spikes, CPU on DB pg_stat_statements, slow query log Add indexes, rewrite queries, read replicas
Sequential scans Disk I/O saturated, high read bytes EXPLAIN ANALYZE shows Seq Scan Create appropriate B-tree/GIN indexes
WAL write bottleneck INSERT/UPDATE slow, fsync delays pg_stat_wal, disk IOPS at limit Faster disk (io2), batch writes, async commit (⚠️ trades durability — only if losing last few transactions is acceptable)
Essential PostgreSQL diagnostic queries 
-- 1. Active connections and what they're doing
SELECT pid, state, wait_event_type, wait_event, 
       now() - query_start as duration, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC
LIMIT 20;

-- 2. Lock contention — who is blocking whom (PostgreSQL 9.6+)
SELECT pid, usename, state,
       wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by,
       query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- 3. Top slow queries (requires pg_stat_statements extension)
SELECT query, calls, mean_exec_time, total_exec_time,
       rows / calls as avg_rows
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- 4. Table bloat and dead tuples (need VACUUM)
SELECT relname, n_dead_tup, n_live_tup,
       round(n_dead_tup::numeric / NULLIF(n_live_tup, 0) * 100, 2) as dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY n_dead_tup DESC;

Network & OS Limits

Linux kernel limits that bite at 10K connections
Limit Default Impact at 10K Fix
File descriptors (ulimit -n) 1024 Each connection = 1 fd. 1024 max = 1024 connections! ulimit -n 65535 or /etc/security/limits.conf
Ephemeral ports 28,232 ports (32768-60999) Outbound connections use ephemeral ports. TIME_WAIT holds them for 60s net.ipv4.ip_local_port_range, connection reuse
TCP backlog (somaxconn) 128 (legacy) / 4096 (Linux 5.4+) Queue for pending TCP connections. Overflow = dropped SYN net.core.somaxconn = 65535
TIME_WAIT sockets 60s timeout 10K short-lived connections/s without keep-alive = 600K TIME_WAIT sockets net.ipv4.tcp_tw_reuse = 1, keep-alive connections
Conntrack table 65536 entries NAT/firewall tracks connections. Table full = dropped packets net.netfilter.nf_conntrack_max = 1000000
Essential sysctl tuning for high-throughput services 
# /etc/sysctl.conf — EXAMPLE tuning for 10K+ connections
# ⚠️ These values are starting points. Validate on your workload and kernel version.

# File descriptors
fs.file-max = 2097152

# TCP connection queue
net.core.somaxconn = 65535
net.core.netdev_max_backlog = 65535
net.ipv4.tcp_max_syn_backlog = 65535

# Ephemeral port range
net.ipv4.ip_local_port_range = 1024 65535

# TIME_WAIT handling
net.ipv4.tcp_tw_reuse = 1              # ⚠️ Only affects OUTBOUND connections (client-side)
# Does NOT help with TIME_WAIT on server (listening) sockets
net.ipv4.tcp_fin_timeout = 15          # Controls FIN_WAIT_2 duration, NOT TIME_WAIT
# Note: TIME_WAIT is hardcoded at 60s in the Linux kernel and cannot be changed via sysctl

# TCP keepalive (detect dead connections faster)
net.ipv4.tcp_keepalive_time = 60
net.ipv4.tcp_keepalive_intvl = 10
net.ipv4.tcp_keepalive_probes = 3

# Buffer sizes for high-bandwidth
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# Connection tracking (if behind NAT/firewall)
net.netfilter.nf_conntrack_max = 1000000

CPU-Bound vs I/O-Bound — Different Solutions

Identifying whether you're CPU-bound or I/O-bound 
  CPU-Bound (compute limited):          I/O-Bound (waiting on external):
  ══════════════════════════════          ═══════════════════════════════

  Symptoms:                              Symptoms:
  • CPU at 90-100%                       • CPU at 10-30%
  • Threads in RUNNABLE state            • Threads in WAITING/TIMED_WAITING
  • GC pressure (allocation rate)        • Connection pool exhaustion
  • Slow JSON serialization              • Slow downstream responses
  • Complex business logic               • DB query latency
  
  Solution:                              Solution:
  • Scale OUT (more pods)                • Scale connection pools
  • Optimize algorithms                  • Async I/O (WebFlux, Virtual Threads)
  • Cache computed results               • Cache external call results
  • Reduce object allocation             • Circuit breakers + timeouts
  • Consider GraalVM native              • Read replicas for DB
  
  Thread pool sizing:                    Thread pool sizing:
  • threads ≈ cores × target_utilization  • threads ≈ CPU cores × (1 + wait/compute)
  • More threads = context switch waste  • More threads = better utilization while waiting
The optimal thread pool formula 
// Brian Goetz's formula (Java Concurrency in Practice):
// threads = N_cpu × U_cpu × (1 + W/C)
// Where:
//   N_cpu = number of CPU cores
//   U_cpu = target CPU utilization (0.0 to 1.0)
//   W/C   = ratio of wait time to compute time

// Example: 4-core server, 80% target utilization, 
//          avg request: 5ms compute + 45ms I/O wait
// threads = 4 × 0.8 × (1 + 45/5) = 4 × 0.8 × 10 = 32

// For a typical Spring Boot app (80% I/O wait):
// W/C = 80/20 = 4
// threads = 4 × 0.8 × (1 + 4) = 16 (per-core: 4)

// For 10K req/s at 50ms avg response time:
// Concurrent requests = 10000 × 0.05 = 500
// Need at minimum 500 threads (or use non-blocking I/O)

// ⚠️ With virtual threads (Java 21+): use unbounded pool
// Virtual threads are cheap — no need to optimize pool size
spring.threads.virtual.enabled=true  // Spring Boot 3.2+

Load Testing — Reproducing the Failure

k6 load test script for 10K concurrent users 
// k6 load test — ramp to 10,000 concurrent users
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate, Trend } from 'k6/metrics';

const errorRate = new Rate('errors');
const responseTime = new Trend('response_time');

export const options = {
  stages: [
    { duration: '1m', target: 100 },    // Warm up
    { duration: '2m', target: 1000 },   // Ramp to 1K
    { duration: '2m', target: 5000 },   // Ramp to 5K
    { duration: '5m', target: 10000 },  // Sustain 10K
    { duration: '2m', target: 0 },      // Cool down
  ],
  thresholds: {
    http_req_duration: ['p(95)<500', 'p(99)<2000'],
    errors: ['rate<0.01'],  // Less than 1% error rate
  },
};

export default function () {
  const res = http.get('http://api.example.com/api/orders?userId=123', {
    headers: { 'Authorization': 'Bearer test-token' },
    timeout: '5s',
  });

  check(res, {
    'status is 200': (r) => r.status === 200,
    'response time < 500ms': (r) => r.timings.duration < 500,
  });

  errorRate.add(res.status !== 200);
  responseTime.add(res.timings.duration);

  sleep(Math.random() * 0.5); // Simulate real user think time
}
# Run the test
k6 run --out json=results.json load_test.js

// Gatling load test in Java
public class OrderApiSimulation extends Simulation {

    HttpProtocolBuilder httpProtocol = http
        .baseUrl("http://api.example.com")
        .acceptHeader("application/json")
        .header("Authorization", "Bearer test-token");

    ScenarioBuilder scenario = scenario("High Load Orders")
        .exec(
            http("Get Orders")
                .get("/api/orders")
                .queryParam("userId", "#{userId}")

                .check(responseTimeInMillis().lt(500))

        setUp(

                rampUsersPerSec(10).to(100).during(Duration.ofMinutes(1)),

                rampUsersPerSec(1000).to(5000).during(Duration.ofMinutes(2)),

            global().responseTime().percentile(95.0).lt(500),
            global().failedRequests().percent().lt(1.0)
         );
    }
}

Real Production Incident

The cascade: how one slow query took down the entire API

Severity: P1 — Complete API outage for 23 minutes during peak traffic

Context

E-commerce product catalog API. Normal load: 2,000 req/s. Flash sale started, traffic spiked to 12,000 req/s. API went from healthy to 100% error rate in 90 seconds.

Timeline

  14:00 — Flash sale starts, traffic: 2K → 8K req/s (expected)
  14:01 — P95 latency creeps from 50ms → 200ms

Root Cause Chain

  Missing index on sale_items table
       │
       ▼
  Sequential scan on 10M rows (2s per query)
       │
       ▼
  Each request holds DB connection for 2s (was 50ms)
       │
       ▼
  HikariCP pool (50 conn) saturated: 50 ÷ 2s = 25 req/s throughput!
       │
       ▼
  190 Tomcat threads blocked waiting for connection (30s timeout)
       │
       ▼
  Tomcat thread pool exhausted (200/200)
       │
       ▼
  TCP accept-queue overflow → 503 for all requests
       │
       ▼
  Health checks fail → K8s removes pods from Service → Complete outage

Lessons Learned

  • Connection pool timeout should be LOW — Changed from 30s → 3s. Fail fast, don't block all threads.
  • Always load test with production data volumes — The missing index only mattered at 10M rows.
  • Circuit breaker on the query layer — Added Resilience4j bulkhead limiting concurrent DB calls to 30 (leaving headroom).
  • Separate read/write pools — Catalog reads shouldn't compete with order writes for connections.
  • Index coverage checks in CI — Added a test: "no query should seq scan tables > 100K rows."

Pattern: Async controller with CompletableFuture (pre-Virtual Threads) 
// Release Tomcat thread immediately — non-blocking response
@RestController
public class OrderController {

    private final Executor asyncExecutor;
    private final OrderService orderService;

    public OrderController(@Qualifier("asyncPool") Executor asyncExecutor,
                           OrderService orderService) {
        this.asyncExecutor = asyncExecutor;
        this.orderService = orderService;
    }

    // Tomcat thread freed immediately; response written when CompletableFuture completes
    // ⚠️ This moves blocking work to asyncExecutor — it does NOT eliminate blocking.
    // If asyncExecutor threads also block on DB/network, total throughput is unchanged.
    // The benefit is freeing Tomcat threads so health checks and other endpoints still respond.
    @GetMapping("/api/orders/{id}")
    public CompletableFuture<Order> getOrder(@PathVariable Long id) {
        return CompletableFuture.supplyAsync(
            () -> orderService.findById(id), asyncExecutor);
    }

    // DeferredResult with timeout handling
    @GetMapping("/api/orders")
    public DeferredResult<List<Order>> listOrders(@RequestParam Long userId) {
        DeferredResult<List<Order>> result = new DeferredResult<>(5000L);
        result.onTimeout(() -> result.setErrorResult(
            ResponseEntity.status(504).body("Gateway timeout")));
        
        asyncExecutor.execute(() -> {
            try {
                result.setResult(orderService.findByUserId(userId));
            } catch (Exception e) {
                result.setErrorResult(e);
            }
        });
        return result;
    }
}

@Configuration
public class AsyncConfig {
    @Bean("asyncPool")
    public Executor asyncExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(50);
        executor.setMaxPoolSize(200);
        executor.setQueueCapacity(500);
        executor.setRejectedExecutionHandler(new CallerRunsPolicy());
        executor.setThreadNamePrefix("async-");
        executor.initialize();
        return executor;
    }
}
Pattern: Virtual Threads (Java 21+ / Spring Boot 3.2+) 
# application.yml — enable virtual threads
spring:
  threads:
    virtual:
      enabled: true  # Each request gets a virtual thread
      # Millions feasible if other resources (memory, FDs, DB connections) permit
// With virtual threads enabled, Tomcat uses virtual threads per-request.
// No thread pool sizing needed — virtual threads are cheap (~1KB stack).
// Blocking calls (JDBC, HTTP) automatically yield the carrier thread.

// Before virtual threads: 200 platform threads → 200 concurrent requests
// After virtual threads: millions of virtual threads → limited only by connections

// ⚠️ Gotcha: Virtual threads don't help if the bottleneck is DB connections!
// You still need HikariCP tuning. The threads aren't the limit — connections are.

// Pinning issue (JDK 21): synchronized blocks pin the virtual thread to carrier thread
// Note: JDK 24+ largely fixed this, but avoiding long blocking inside synchronized
// remains good practice for portability across JDK versions.
// BAD (on JDK 21):
synchronized (lock) {
    jdbcTemplate.query(...);  // Carrier thread pinned during I/O!
}

// GOOD (portable across JDK versions): Use ReentrantLock instead
private final ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    jdbcTemplate.query(...);  // Virtual thread can unmount
} finally {
    lock.unlock();
}
Pattern: Caching to bypass the database entirely 
@Service
public class ProductCatalogService {

    private final Cache<Long, Product> localCache; // Caffeine (L1)
    private final RedisTemplate<String, Product> redis; // Redis (L2)
    private final ProductRepository repository; // PostgreSQL (L3)

    public ProductCatalogService() {
        this.localCache = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofMinutes(5))
            .recordStats()
            .build();
    }

    public Product getProduct(Long id) {
        // L1: In-memory (< 1ms, no network)
        Product cached = localCache.getIfPresent(id);
        if (cached != null) return cached;

        // L2: Redis (1-3ms, network hop)
        String redisKey = "product:" + id;
        cached = redis.opsForValue().get(redisKey);
        if (cached != null) {
            localCache.put(id, cached);
            return cached;
        }

        // L3: Database (5-50ms, connection required)
        Product product = repository.findById(id)
            .orElseThrow(() -> new NotFoundException("Product not found: " + id));
        
        redis.opsForValue().set(redisKey, product, Duration.ofMinutes(30));
        localCache.put(id, product);
        
        return product;
    }

    // At 10K req/s with 95% L1 hit rate AND 95% L2 hit rate:
    // 10,000 × 5% miss L1 = 500 req/s reach Redis
    // 500 × 5% miss L2 = 25 req/s reach the database
    // DB load reduced from 10,000 → 25 req/s (400x reduction)!
}
Pattern: Bulkhead — isolate critical paths 
// Resilience4j Bulkhead: limit concurrent calls to protect resources
// Two types:
//   SemaphoreBulkhead — limits concurrency via semaphore (same thread, lower overhead)
//   ThreadPoolBulkhead — isolates with a dedicated thread pool (full isolation, higher cost)
// Interview tip: know when to use which. Semaphore is usually sufficient for DB protection.
@Configuration
public class BulkheadConfig {

    @Bean
    public BulkheadRegistry bulkheadRegistry() {
        BulkheadConfig config = BulkheadConfig.custom()
            .maxConcurrentCalls(30)     // Max 30 concurrent DB calls
            .maxWaitDuration(Duration.ofMillis(500)) // Wait max 500ms for a slot
            .build();
        return BulkheadRegistry.of(config);
    }
}

@Service
public class OrderService {

    @Bulkhead(name = "database", fallbackMethod = "getOrderFallback")
    public Order getOrder(Long id) {
        return orderRepository.findById(id).orElseThrow();
    }

    private Order getOrderFallback(Long id, BulkheadFullException e) {
        // Return from cache or return a degraded response
        return cacheService.getStaleOrder(id)
            .orElseThrow(() -> new ServiceUnavailableException("High load - try again"));
    }
}

Common Mistakes

Anti-patterns that cause failures at scale
# Mistake Why It Fails at 10K Fix
1 Increasing Tomcat threads without increasing DB pool More threads = more contention for same 10 connections Tune pools together: thread pool / conn pool ratio
2 No connection timeout on HikariCP Threads wait 30s for a connection, Tomcat pool fills up Set connection-timeout: 3000 — fail fast
3 N+1 queries in JPA 100 users = 100 queries. 10K users = 10K queries per request Use @EntityGraph, JOIN FETCH, or batch fetching
4 Synchronous calls to downstream services inside request Each downstream call adds latency; timeout accumulates Parallel async calls with CompletableFuture.allOf()
5 No caching layer Every request hits DB — 10K req/s directly to PostgreSQL Add L1 (Caffeine) + L2 (Redis) cache for read-heavy endpoints
6 Health check queries hitting the same pool Health checks contend with real traffic for connections Separate health check connection or simple socket check
7 Unbounded result sets (SELECT * FROM orders WHERE user_id = ?) Power users with 50K orders = huge memory allocation per request Always paginate: LIMIT 50 OFFSET ? or cursor-based
8 Blocking I/O inside synchronized blocks With virtual threads, pins carrier thread; with platform threads, holds monitor during slow I/O Use ReentrantLock or restructure to minimize lock scope

Trade-offs — Scaling Strategies

Horizontal vs vertical scaling decision matrix
Strategy When to Use Pros Cons
Scale UP (vertical) CPU-bound, single-thread bottleneck Simple, no code changes Expensive, ceiling limit, single point of failure
Scale OUT (horizontal) I/O-bound, stateless services Linear scaling, HA, cost-effective Need stateless design, more operational complexity
Caching (L1+L2) Read-heavy, tolerance for staleness 10-100x throughput boost, reduces DB load Invalidation complexity, memory cost, stale data risk
Read replicas Read-heavy, need fresh data Scales reads, isolates writes Replication lag, connection management complexity
Async/reactive (WebFlux) Many concurrent connections, I/O-heavy 10K+ connections per instance, low memory Complex programming model, debugging harder, ecosystem gaps
Virtual Threads (Java 21) I/O-bound, existing blocking code Simple model, scales like reactive, keeps blocking code JDK 21+ required, pinning issues, library support

Follow-up Interview Questions

Likely follow-ups and how to answer
Q: "How would you handle a sudden traffic spike without pre-scaling?"
Three layers of defense: (1) Rate limiting at the API gateway — shed excess load gracefully, (2) Circuit breakers — prevent cascade when downstream can't handle load, (3) Auto-scaling on latency/CPU metrics — scale pods before thread pools exhaust. Also: graceful degradation — serve cached/stale responses rather than 503.
Q: "Your API has 50ms latency at P50 but 5 seconds at P99. What's happening?"
Bimodal latency usually means: (1) GC pauses (check GC logs for STW > 1s), (2) Lock contention (1% of requests hit a hot row), (3) Connection pool wait (most get a connection instantly, few wait for full pool), (4) Slow query triggered by specific data patterns (e.g., users with 10K orders). I'd check the P99 requests specifically — are they a specific user/endpoint?
Q: "Would you choose WebFlux or Virtual Threads for a new high-throughput service?"
For a new Spring Boot service in 2026+: Virtual Threads. They give you reactive-level scalability with imperative code. WebFlux only if you need streaming/SSE or your entire stack is already reactive (R2DBC, reactive Redis). The debugging and testing story for virtual threads is much better.
Q: "How do you prevent one slow endpoint from affecting all others?"
Bulkhead pattern: separate thread pools per endpoint group. Critical endpoints (checkout) get a dedicated pool with guaranteed capacity. Non-critical endpoints (analytics) get a smaller pool and degrade gracefully. Alternatively: separate services for different SLA tiers.

Summary

Interview Takeaways:

  1. Investigate in order: thread pool → connection pool → database → OS limits → code
  2. Use Little's Law to calculate capacity: L = λ × W. Know your numbers.
  3. Default Tomcat (200 threads) + HikariCP (10 connections) = ~200 req/s effective throughput
  4. First action during failure: thread dump — it shows exactly where threads are stuck
  5. Flame graphs distinguish CPU-bound (profile CPU) from I/O-bound (profile wall clock)
  6. Caching is the #1 throughput multiplier — 95% cache hit = 20x DB load reduction
  7. Virtual Threads (Java 21) solve thread-per-request scalability without reactive complexity
  8. Connection pool timeout must be low (3-5s) — fail fast, not fill up thread pool
  9. Separate read/write paths — don't let catalog reads starve payment writes

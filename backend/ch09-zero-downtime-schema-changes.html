How Would You Safely Deploy a Breaking Database Schema Change Without Downtime?

Key Takeaway: Use the Expand-Contract (parallel change) pattern — never make destructive schema changes in a single deployment. Instead, expand the schema to support both old and new code, migrate data, then contract by removing deprecated elements once all consumers have moved on.

Interviewer Intent

What the interviewer is really evaluating

This question tests whether you understand the operational realities of deploying schema changes in a distributed system with multiple application instances. The interviewer wants to see:

  • Awareness of the deployment gap: During rolling deployments, old and new application versions coexist — both must work against the same database schema.
  • Knowledge of safe migration patterns: Expand-Contract, dual-write, backfill strategies, and versioned migrations.
  • Tool proficiency: Familiarity with Flyway, Liquibase, or similar migration frameworks in a CI/CD pipeline.
  • Incident awareness: Understanding what goes wrong when teams skip these patterns — broken queries, data loss, extended outages.
  • Communication skills: Ability to explain a multi-step deployment plan to stakeholders who want "just rename the column."

Senior engineers are expected to have done this, not just read about it. The interviewer may probe for war stories, timelines, and rollback strategies.

Quick Answer

30-second interview response

"I use the Expand-Contract pattern. First, I expand the schema by adding the new structure alongside the old one — for example, adding a new column without removing the old one. I deploy application code that writes to both old and new locations (dual-write). Then I run a backfill migration to populate the new structure with historical data. Once all application instances use the new schema and data is verified, I contract by removing the deprecated column in a subsequent release. This ensures zero downtime because at every step, both old and new application versions can function correctly against the database."

This answer demonstrates understanding of the core pattern. The sections below expand on each aspect with production-grade detail.

Expand-Contract Pattern

The fundamental pattern for zero-downtime schema evolution

Also known as: Parallel Change, Expand-Migrate-Contract, or the "Three-Phase Migration" pattern.

The Three Phases

Phase Schema State Application State Duration
1. Expand Add new column/table alongside old Write to both, read from old 1 deployment cycle
2. Migrate Both structures exist, data synced Write to both, read from new Hours to days
3. Contract Remove old column/table Only uses new structure 1 deployment cycle

Example 1: Renaming a Column

Suppose you need to rename users.full_name to users.display_name (better domain language).

Phase 1 — Expand (Release N)

-- V2023.09.01__expand_add_display_name_column.sql
ALTER TABLE users ADD COLUMN display_name VARCHAR(255);

-- Trigger to keep columns in sync during transition
-- Note: Sync can also be done in application code (dual-write) instead of triggers.
-- Many teams prefer app-level dual-writes because triggers hide logic and complicate CDC.
CREATE OR REPLACE FUNCTION sync_name_columns()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' OR TG_OP = 'UPDATE' THEN
    IF NEW.display_name IS NULL AND NEW.full_name IS NOT NULL THEN
      NEW.display_name := NEW.full_name;
    ELSIF NEW.full_name IS NULL AND NEW.display_name IS NOT NULL THEN
      NEW.full_name := NEW.display_name;
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync_name
  BEFORE INSERT OR UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION sync_name_columns();

Phase 1 — Backfill

-- V2023.09.02__backfill_display_name.sql
-- Batch update to avoid locking entire table
DO $$
DECLARE
  batch_size INT := 10000;
  rows_updated INT;
BEGIN
  LOOP
    UPDATE users
    SET display_name = full_name
    WHERE display_name IS NULL
      AND id IN (
        SELECT id FROM users
        WHERE display_name IS NULL
        LIMIT batch_size
        FOR UPDATE SKIP LOCKED
      );
    GET DIAGNOSTICS rows_updated = ROW_COUNT;
    EXIT WHEN rows_updated = 0;
    PERFORM pg_sleep(0.1); -- throttle to reduce replication lag
    RAISE NOTICE 'Updated % rows', rows_updated;
  END LOOP;
END $$;

Phase 2 — Migrate Application (Release N+1)

// Entity now reads from new column, writes to both
// ⚠️ Choose ONE sync strategy: app dual-write OR DB trigger, not both.
// If using the trigger above, mark legacy field as read-only:
//   @Column(name = "full_name", insertable = false, updatable = false)
@Entity
@Table(name = "users")
public class User {

    @Column(name = "display_name")
    private String displayName;

    // Keep writing to old column for rollback safety (app-level dual-write)
    @Column(name = "full_name")
    private String fullNameLegacy;

    public void setDisplayName(String value) {
        this.displayName = value;
        this.fullNameLegacy = value; // dual-write
    }
}

Phase 3 — Contract (Release N+2)

-- V2023.10.01__contract_remove_old_full_name.sql
-- Only run after ALL pods are on Release N+1 or later
DROP TRIGGER IF EXISTS trg_sync_name ON users;
DROP FUNCTION IF EXISTS sync_name_columns();
ALTER TABLE users DROP COLUMN IF EXISTS full_name;

Example 2: Changing Column Type (INT → BIGINT)

This is common when an ID column approaches INTEGER overflow (~2.1 billion).

Phase 1 — Expand

-- V2024.01.01__expand_order_id_bigint.sql
ALTER TABLE orders ADD COLUMN order_id_new BIGINT;

-- Trigger for new inserts
CREATE OR REPLACE FUNCTION sync_order_id()
RETURNS TRIGGER AS $$
BEGIN
  NEW.order_id_new := NEW.order_id::BIGINT;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync_order_id
  BEFORE INSERT OR UPDATE ON orders
  FOR EACH ROW EXECUTE FUNCTION sync_order_id();

Phase 2 — Backfill + Swap

-- Backfill in batches
UPDATE orders SET order_id_new = order_id::BIGINT
WHERE order_id_new IS NULL AND id BETWEEN 1 AND 1000000;

-- After full backfill and app migration:
ALTER TABLE orders RENAME COLUMN order_id TO order_id_old;
ALTER TABLE orders RENAME COLUMN order_id_new TO order_id;

Phase 3 — Contract

-- V2024.02.01__contract_remove_old_order_id.sql
DROP TRIGGER IF EXISTS trg_sync_order_id ON orders;
DROP FUNCTION IF EXISTS sync_order_id();
ALTER TABLE orders DROP COLUMN IF EXISTS order_id_old;

Example 3: Splitting a Table

Splitting users into users + user_profiles for performance.

Phase 1 — Create new table, dual-write

-- V2024.03.01__expand_create_user_profiles.sql
CREATE TABLE user_profiles (
  user_id BIGINT PRIMARY KEY REFERENCES users(id),
  bio TEXT,
  avatar_url VARCHAR(512),
  location VARCHAR(255),
  website VARCHAR(512),
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Backfill from existing users table
INSERT INTO user_profiles (user_id, bio, avatar_url, location, website)
SELECT id, bio, avatar_url, location, website
FROM users
WHERE bio IS NOT NULL OR avatar_url IS NOT NULL;

Phase 2 — Application reads from new table

@Service
public class UserProfileService {

    @Autowired
    private UserProfileRepository profileRepo;

    @Autowired
    private UserRepository userRepo; // legacy

    @Transactional
    public void updateProfile(Long userId, ProfileDTO dto) {
        // Write to new table
        UserProfile profile = profileRepo.findByUserId(userId)
            .orElse(new UserProfile(userId));
        profile.setBio(dto.getBio());
        profile.setAvatarUrl(dto.getAvatarUrl());
        profileRepo.save(profile);

        // Dual-write to old table for rollback safety
        User user = userRepo.findById(userId).orElseThrow();
        user.setBio(dto.getBio());
        user.setAvatarUrl(dto.getAvatarUrl());
        userRepo.save(user);
    }
}

Phase 3 — Remove columns from original table

-- V2024.04.01__contract_remove_profile_from_users.sql
ALTER TABLE users DROP COLUMN IF EXISTS bio;
ALTER TABLE users DROP COLUMN IF EXISTS avatar_url;
ALTER TABLE users DROP COLUMN IF EXISTS location;
ALTER TABLE users DROP COLUMN IF EXISTS website;

Timing matters: Never execute the Contract phase until you are 100% certain no running application instance reads from the old structure. In Kubernetes, this means waiting for all old pods to terminate after a rolling deployment completes.

Triggers vs. application dual-write: The examples above use database triggers for synchronization. Many teams prefer application-level dual-writes instead, because triggers hide business logic, complicate debugging, and can cause surprises with CDC/replication tooling. Choose the approach that fits your team's conventions.

Backward Compatibility

What's safe vs. what's breaking

Not all schema changes are equal. Understanding which operations are backward-compatible helps you decide which ones need the full Expand-Contract treatment.

Safety Classification

Operation Safety Level Reason Pattern Needed
Add nullable column ✅ Safe Old code ignores unknown columns Direct migration
Add column with default ✅ Safe Old code ignores it, new rows get default Direct migration
Add new table ✅ Safe No existing code references it Direct migration
Add index ⚠️ Caution Can lock table; use CONCURRENTLY CREATE INDEX CONCURRENTLY
Remove column ❌ Breaking Old code SELECTs/INSERTs it Expand-Contract
Rename column ❌ Breaking Old code references old name Expand-Contract
Change column type ❌ Breaking (usually) May fail casting or truncate data Expand-Contract
Add NOT NULL constraint ❌ Breaking Old code may insert NULLs Add with DEFAULT first, then constraint
Drop table ❌ Breaking Any reference causes failure Expand-Contract
Modify enum values ⚠️ Depends Adding is safe, removing is breaking Add=direct, Remove=Expand-Contract

The Golden Rule

If the schema change could cause any currently-deployed code to fail, it is a breaking change and requires the Expand-Contract pattern.

In a rolling deployment, "currently deployed" includes the version you're replacing — it will still be running for several minutes during rollout.

PostgreSQL-Specific Safe Operations

-- Safe: Add nullable column (no table rewrite in PG 11+)
ALTER TABLE orders ADD COLUMN notes TEXT;

-- Safe: Add column with non-volatile constant default (PG 11+ does NOT rewrite table)
-- Examples: DEFAULT 0, DEFAULT 'ACTIVE', DEFAULT false
ALTER TABLE orders ADD COLUMN status VARCHAR(20) DEFAULT 'PENDING';
-- ⚠️ Volatile functions like NOW() DO trigger a table rewrite in older behavior.
-- For timestamps, use DEFAULT clock_timestamp() cautiously or backfill after adding nullable.

-- Safe: Create index without blocking writes
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders(customer_id);
-- ⚠️ Cannot run inside a transaction block! Flyway wraps migrations in
-- transactions by default. Use a separate non-transactional migration file,
-- or in Flyway, disable transactions for this migration.

-- UNSAFE on large tables: many type changes require a full table rewrite
-- and blocking locks (though some binary-compatible changes like
-- VARCHAR(50)→VARCHAR(100) are metadata-only in PostgreSQL).
ALTER TABLE orders ALTER COLUMN amount TYPE NUMERIC(12,2);

-- UNSAFE: Adding NOT NULL without default rewrites table
ALTER TABLE orders ALTER COLUMN status SET NOT NULL;

MySQL/InnoDB Considerations

-- MySQL 8.0+: INSTANT algorithm for adding columns
-- Before 8.0.29: limited to adding columns at the END of the table only.
-- Since 8.0.29: columns can be added/dropped INSTANT at any position.
-- ⚠️ Real limitation (any version): a table can accumulate at most 64
-- "row versions" from INSTANT ADD/DROP operations before MySQL falls
-- back to a full table rebuild (INPLACE/COPY) on the next such change.
-- Some operations (e.g. adding a column with FULLTEXT/SPATIAL index) also
-- silently fall back to INPLACE or COPY regardless of version.
ALTER TABLE orders ADD COLUMN notes TEXT, ALGORITHM=INSTANT;

-- pt-online-schema-change for type changes (Percona Toolkit)
-- This creates a shadow table, copies data, then swaps
pt-online-schema-change --alter "MODIFY COLUMN amount DECIMAL(12,2)" \
  --execute D=mydb,t=orders

Migration Tools: Flyway & Liquibase Patterns

Versioned migrations for multi-version deployments

Flyway Configuration for Expand-Contract

Flyway's versioned migrations map naturally to the Expand-Contract phases. The key is structuring your version numbers to make the deployment order explicit.

# Directory structure
src/main/resources/db/migration/
├── V2024.01.01.1__expand_add_email_verified.sql    # Phase 1: Expand
├── V2024.01.01.2__backfill_email_verified.sql      # Phase 1: Backfill
├── V2024.01.15.1__contract_email_status.sql        # Phase 3: Contract (later release)
└── R__create_reporting_views.sql                    # Repeatable migration

Flyway Spring Boot Configuration

# application.yml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true
    baseline-version: '0'
    # Handles intentionally removed or skipped migrations without failing
    ignore-migration-patterns: '*:missing'
    # Validate checksums to prevent tampering
    validate-on-migrate: true
    # Use a lock to prevent concurrent migration execution
    lock-retry-count: 50
    # Separate schema for migration metadata
    schemas: public
    table: flyway_schema_history

  datasource:
    url: jdbc:postgresql://localhost:5432/myapp
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 20
      connection-timeout: 5000

Multi-Version Deployment Support

Problem: During a rolling deployment, pod A runs migration V5 (expand), but pod B hasn't restarted yet and only knows about V4. Pod B must still function against the V5 schema.

Solution: Expand migrations only ADD structures. Old code simply ignores new columns/tables it doesn't know about.

// Flyway callback to verify schema compatibility
@Component
public class SchemaCompatibilityCallback implements Callback {

    @Override
    public boolean supports(Event event, Context context) {
        return event == Event.AFTER_MIGRATE;
    }

    @Override
    public boolean canHandleInTransaction(Event event, Context context) {
        return true;
    }

    @Override
    public void handle(Event event, Context context) {
        // Verify the schema is compatible with current application version
        try (Statement stmt = context.getConnection().createStatement()) {
            ResultSet rs = stmt.executeQuery(
                "SELECT column_name FROM information_schema.columns " +
                "WHERE table_name = 'users' AND column_name = 'username'"
            );
            if (!rs.next()) {
                throw new FlywayException(
                    "Required column 'users.username' not found. " +
                    "Schema incompatible with application version."
                );
            }
        } catch (SQLException e) {
            throw new FlywayException("Schema validation failed", e);
        }
    }
}

Liquibase Patterns

Liquibase uses changesets with preconditions, which can be more expressive for complex migrations.

# db/changelog/2024/01-expand-username.yaml
databaseChangeLog:
  - changeSet:
      id: expand-add-username
      author: team-platform
      comment: "Phase 1: Add new username column alongside userName"
      preConditions:
        - onFail: MARK_RAN
        - not:
            - columnExists:
                tableName: users
                columnName: username
      changes:
        - addColumn:
            tableName: users
            columns:
              - column:
                  name: username
                  type: VARCHAR(255)
                  constraints:
                    nullable: true
      rollback:
        - dropColumn:
            tableName: users
            columnName: username

  - changeSet:
      id: backfill-username
      author: team-platform
      comment: "Phase 1: Backfill username from userName"
      preConditions:
        - onFail: MARK_RAN
        - columnExists:
            tableName: users
            columnName: username
        - columnExists:
            tableName: users
            columnName: userName
      changes:
        - sql:
            sql: "UPDATE users SET username = userName WHERE username IS NULL"
      rollback:
        - sql:
            sql: "UPDATE users SET username = NULL"

Repeatable Migrations

Use repeatable migrations for objects that should be recreated on every change (views, functions, stored procedures):

-- R__user_summary_view.sql (Flyway repeatable migration)
-- This gets re-executed whenever the file checksum changes
CREATE OR REPLACE VIEW user_summary AS
SELECT
  u.id,
  u.username,  -- Uses new column name
  u.email,
  up.bio,
  up.avatar_url,
  COUNT(o.id) as order_count,
  MAX(o.created_at) as last_order_date
FROM users u
LEFT JOIN user_profiles up ON up.user_id = u.id
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.username, u.email, up.bio, up.avatar_url;

Dual-Write Pattern

Writing to old AND new schema during transition

The dual-write pattern ensures data consistency during the migration window. Every write operation updates both the old and new schema locations simultaneously.

When to Use Dual-Write

  • Column renames where both old and new code must function
  • Table splits where data must exist in both locations
  • Type changes where both representations must stay in sync
  • Any scenario where rollback must be instantaneous (just switch read source)

Implementation Pattern

@Service
@Slf4j
public class OrderDualWriteService {

    private final JdbcTemplate jdbc;
    private final MeterRegistry metrics;

    @Value("${migration.orders.read-from-new:false}")
    private boolean readFromNew;

    @Transactional
    public Order createOrder(CreateOrderRequest request) {
        Order order = new Order();
        order.setCustomerId(request.getCustomerId());
        order.setAmount(request.getAmount());
        order.setStatus(OrderStatus.PENDING);

        // Write to BOTH schemas within same transaction
        Long orderId = insertIntoOldSchema(order);
        insertIntoNewSchema(orderId, order);

        metrics.counter("orders.dual_write.success").increment();
        log.debug("Dual-write completed for order {}", orderId);

        // Read from whichever schema is "primary"
        return readFromNew ? readFromNewSchema(orderId) : readFromOldSchema(orderId);
    }

    private Long insertIntoOldSchema(Order order) {
        KeyHolder keyHolder = new GeneratedKeyHolder();
        jdbc.update(connection -> {
            PreparedStatement ps = connection.prepareStatement(
                "INSERT INTO orders (customer_id, amount, status, created_at) " +
                "VALUES (?, ?, ?, NOW())",
                Statement.RETURN_GENERATED_KEYS
            );
            ps.setLong(1, order.getCustomerId());
            ps.setBigDecimal(2, order.getAmount());
            ps.setString(3, order.getStatus().name());
            return ps;
        }, keyHolder);
        return keyHolder.getKey().longValue();
    }

    private void insertIntoNewSchema(Long orderId, Order order) {
        jdbc.update(
            "INSERT INTO orders_v2 (id, customer_id, amount_cents, status, created_at) " +
            "VALUES (?, ?, ?, ?, NOW())",
            orderId,
            order.getCustomerId(),
            order.getAmount().multiply(BigDecimal.valueOf(100)).longValue(),
            order.getStatus().name()
        );
    }

    private Order readFromOldSchema(Long orderId) {
        return jdbc.queryForObject(
            "SELECT * FROM orders WHERE id = ?",
            new OrderRowMapper(),
            orderId
        );
    }

    private Order readFromNewSchema(Long orderId) {
        return jdbc.queryForObject(
            "SELECT * FROM orders_v2 WHERE id = ?",
            new OrderV2RowMapper(),
            orderId
        );
    }
}

Consistency Verification

Always verify that dual-writes are consistent. Run a background job that compares records:

@Scheduled(fixedDelay = 60000) // Every minute
public void verifyDualWriteConsistency() {
    List<Long> sampleIds = jdbc.queryForList(
        "SELECT id FROM orders ORDER BY RANDOM() LIMIT 100",
        Long.class
    );

    int mismatches = 0;
    for (Long id : sampleIds) {
        Order oldRecord = readFromOldSchema(id);
        Order newRecord = readFromNewSchema(id);

        if (!isConsistent(oldRecord, newRecord)) {
            mismatches++;
            log.warn("Dual-write inconsistency detected for order {}. " +
                     "Old: {}, New: {}", id, oldRecord, newRecord);
            metrics.counter("dual_write.inconsistency").increment();

            // Auto-repair: copy from source of truth (old) to new
            repairNewSchemaRecord(id, oldRecord);
        }
    }

    metrics.gauge("dual_write.mismatch_rate",
        (double) mismatches / sampleIds.size());

    if (mismatches > sampleIds.size() * 0.01) { // >1% mismatch
        alerting.fire("dual-write-inconsistency-high",
            "Mismatch rate: " + mismatches + "/" + sampleIds.size());
    }
}

private boolean isConsistent(Order old, Order newRec) {
    if (old == null || newRec == null) return old == newRec;
    return old.getCustomerId().equals(newRec.getCustomerId())
        && old.getAmount().compareTo(
            BigDecimal.valueOf(newRec.getAmountCents(), 2)) == 0
        && old.getStatus().equals(newRec.getStatus());
}

Dual-Write Pitfalls

Transaction boundaries matter! Both writes MUST be in the same database transaction. If you write to old, commit, then write to new and that fails — you have inconsistent data.

Cross-database caveat: If the new schema lives in another database or service, single-transaction dual-write isn't possible. In that case, use outbox/event-based synchronization or CDC for eventual consistency.

Performance impact: Dual-writes double your write load. Monitor connection pool usage, replication lag, and response times during the migration window. Consider off-peak hours for the backfill.

Feature Flags for Schema Transitions

Toggle which schema path code uses

Feature flags decouple deployment from activation. You can deploy dual-write code, but only enable the new schema path gradually.

Flag Strategy for Schema Migration

Flag Phase 1 (Expand) Phase 2 (Migrate) Phase 3 (Contract)
schema.orders.dual-write ON ON OFF (removed)
schema.orders.read-from-new OFF ON (gradual) ON (removed)
schema.orders.write-only-new OFF OFF ON → remove flag

Spring Boot Feature Flag Implementation

@Configuration
public class SchemaFeatureFlags {

    @Bean
    public FeatureFlagService schemaFlags(Environment env) {
        return new FeatureFlagService(env);
    }
}

@Component
@RefreshScope // Supports runtime toggle without restart
public class FeatureFlagService {

    @Value("${feature.schema.orders.dual-write:false}")
    private boolean ordersDualWrite;

    @Value("${feature.schema.orders.read-from-new:false}")
    private boolean ordersReadFromNew;

    @Value("${feature.schema.orders.write-only-new:false}")
    private boolean ordersWriteOnlyNew;

    public boolean isOrdersDualWriteEnabled() {
        return ordersDualWrite;
    }

    public boolean shouldReadFromNewOrdersSchema() {
        return ordersReadFromNew;
    }

    public boolean isLegacyWriteDisabled() {
        return ordersWriteOnlyNew;
    }
}

Flag-Aware Repository

@Repository
@Slf4j
public class OrderRepositoryAdapter implements OrderRepository {

    private final OrderLegacyRepository legacy;
    private final OrderNewRepository newRepo;
    private final FeatureFlagService flags;

    @Override
    @Transactional
    public Order save(Order order) {
        Order saved;

        if (flags.isLegacyWriteDisabled()) {
            // Phase 3: Only write to new schema
            saved = newRepo.save(toNewEntity(order));
        } else if (flags.isOrdersDualWriteEnabled()) {
            // Phase 1-2: Write to both
            saved = legacy.save(toLegacyEntity(order));
            newRepo.save(toNewEntity(order));
        } else {
            // Pre-migration: Only old schema
            saved = legacy.save(toLegacyEntity(order));
        }

        return saved;
    }

    @Override
    @Transactional(readOnly = true)
    public Optional<Order> findById(Long id) {
        if (flags.shouldReadFromNewOrdersSchema()) {
            return newRepo.findById(id).map(this::fromNewEntity);
        }
        return legacy.findById(id).map(this::fromLegacyEntity);
    }
}

Gradual Rollout with Percentage-Based Flags

@Component
public class GradualSchemaRollout {

    @Value("${feature.schema.orders.new-read-percentage:0}")
    private int readPercentage; // 0-100

    private final Random random = new Random();

    public boolean shouldUseNewSchema(Long entityId) {
        // Deterministic: same entity always goes to same schema
        // Avoids read-your-write issues
        int bucket = Math.abs(entityId.hashCode() % 100);
        return bucket < readPercentage;
    }
}

// Usage in repository:
@Override
public Optional<Order> findById(Long id) {
    if (gradualRollout.shouldUseNewSchema(id)) {
        return newRepo.findById(id).map(this::fromNewEntity);
    }
    return legacy.findById(id).map(this::fromLegacyEntity);
}

Pro tip: Use deterministic bucketing (based on entity ID hash) rather than random selection. This ensures the same record is always read from the same source, preventing read-your-write inconsistencies.

Important: Begin percentage rollout only after verifying the backfill is 100% complete and data is consistent between old and new schemas. Reading from the new schema before backfill finishes will return NULL/missing data.

Deployment Strategies for Schema Changes

Blue-Green vs Rolling vs Canary — how they interact with schema migrations 
  Rolling Deployment with Schema Change (DANGEROUS without expand-contract):
  ═════════════════════════════════════════════════════════════════════════

  Time ──────────────────────────────────────────────────────▶

  DB:     [old schema]──────── migration runs ────────[new schema]
                                     │
  Pod v1: ████████████████████       │  ████ (terminating)
                                     │        ↑ uses OLD column that's now gone!
  Pod v2:                  ██████████████████████████████████
                                     │        ↑ uses NEW column
                                     │
                              DANGER ZONE: old pods + new schema = 500 errors

  Safe Approach: Expand-Contract with Rolling Deployment:
  ══════════════════════════════════════════════════════════

  Phase 1: EXPAND (add new, keep old)
  DB:     [old schema] → [old + new columns exist]
  Pod v1: ████████████████████████████████  (reads/writes old column — still works!)
  Pod v2:            ████████████████████████████████  (reads/writes new column)

  Phase 2: MIGRATE (backfill data)
  DB:     [old + new columns, data synced]
  Pod v2: ████████████████████████████████████████████  (all pods on v2 now)

  Phase 3: CONTRACT (remove old)
  DB:     [new schema only] — safe because no pod uses old column
  Pod v2: ████████████████████████████████████████████

Real Production Incident

The 8-minute outage: DROP COLUMN during rolling deployment

Severity: P1 — 500 errors for all order-related endpoints for 8 minutes

Context

Microservices platform, 12 pods running order-service. Team decided to rename orders.customer_name to orders.buyer_name. A junior engineer wrote a single migration that dropped the old column and added the new one.

Timeline

  14:00 — Deploy starts. Flyway migration runs first:
           ALTER TABLE orders DROP COLUMN customer_name;
           ALTER TABLE orders ADD COLUMN buyer_name VARCHAR(255);
  14:01 — Migration completes. Pod-1 (new code) starts, uses buyer_name ✅
  14:02 — Pods 2-12 still running OLD code, querying customer_name
           → "ERROR: column 'customer_name' does not exist" 
           → 500 errors on all 11 old pods
  14:03 — Load balancer routes 11/12 requests to old pods → 91% error rate
  14:05 — Alert fires: "Error rate > 50%"
  14:07 — On-call identifies the issue via error logs
  14:08 — Emergency: kubectl rollout undo deployment/order-service
           But DB migration already ran — old code STILL can't find the column!
  14:09 — DBA manually adds column back: ALTER TABLE orders ADD COLUMN customer_name VARCHAR(255);
  14:10 — Old pods recover. Error rate drops to 0.

Root Cause

-- The WRONG migration (single step, destructive)
-- V5__rename_customer_to_buyer.sql
ALTER TABLE orders DROP COLUMN customer_name;
ALTER TABLE orders ADD COLUMN buyer_name VARCHAR(255);
-- ❌ This is a breaking change! Old code immediately fails.

What Should Have Been Done

-- V5__expand_add_buyer_name.sql (Phase 1: EXPAND)
ALTER TABLE orders ADD COLUMN buyer_name VARCHAR(255);

-- Application v2 writes to BOTH columns (dual-write)
-- Backfill old data:
UPDATE orders SET buyer_name = customer_name WHERE buyer_name IS NULL;

-- After ALL pods are on v2 and stable for days:
-- V6__contract_drop_customer_name.sql (Phase 3: CONTRACT)
ALTER TABLE orders DROP COLUMN customer_name;

Key lesson: Database schema changes should generally be rolled forward (fix with a new migration) rather than rolled back. Destructive rollbacks (restoring a dropped column) may not recover lost data and require DBA intervention. Design migrations to be additive so rollback means simply deploying the old application code — not undoing the schema change.

Preventive Measures

  • CI check: Added a linter that rejects migrations containing DROP COLUMN, RENAME COLUMN, or ALTER COLUMN ... TYPE without a paired expand migration
  • Mandatory staging test: Run old app version against new schema in CI before merging
  • Migration review checklist: PR template requires confirming backward compatibility
  • Separation of concerns: Schema migrations are now in a separate repo/pipeline from app deployment

Production-Ready Code Examples

Complete Flyway expand-contract migration set 
-- V10__expand_rename_email.sql
-- Goal: rename users.email_address to users.email
-- Phase 1: Add new column

ALTER TABLE users ADD COLUMN email VARCHAR(255);

-- Backfill in batches to avoid locking entire table
DO $$
DECLARE
  batch_size INT := 10000;
  updated INT;
BEGIN
  LOOP
    UPDATE users 
    SET email = email_address 
    WHERE id IN (
      SELECT id FROM users
      WHERE email IS NULL
      LIMIT batch_size
      FOR UPDATE SKIP LOCKED
    );
    
    GET DIAGNOSTICS updated = ROW_COUNT;
    EXIT WHEN updated = 0;
    
    PERFORM pg_sleep(0.1); -- Throttle to avoid overwhelming DB
  END LOOP;
END $$;

-- Add constraint after backfill
ALTER TABLE users ALTER COLUMN email SET NOT NULL;
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);

-- Add trigger to keep both columns in sync during transition
CREATE OR REPLACE FUNCTION sync_email_columns() RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' OR TG_OP = 'UPDATE' THEN
    IF NEW.email IS NOT NULL AND NEW.email_address IS DISTINCT FROM NEW.email THEN
      NEW.email_address := NEW.email;
    ELSIF NEW.email_address IS NOT NULL AND NEW.email IS DISTINCT FROM NEW.email_address THEN
      NEW.email := NEW.email_address;
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync_email
  BEFORE INSERT OR UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION sync_email_columns();
-- V11__contract_remove_email_address.sql (run weeks later)
-- Phase 3: Remove old column (ONLY after all code uses new column)

DROP TRIGGER IF EXISTS trg_sync_email ON users;
DROP FUNCTION IF EXISTS sync_email_columns();
DROP INDEX IF EXISTS idx_users_email_address;
ALTER TABLE users DROP COLUMN email_address;
Spring Boot entity supporting both schema versions 
// During transition: entity maps both columns
@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // New column (primary after migration)
    @Column(name = "email")
    private String email;

    // Old column (kept during transition for backward compatibility)
    @Column(name = "email_address", insertable = false, updatable = false)
    private String emailAddress;

    // Dual-write: setter updates both
    public void setEmail(String email) {
        this.email = email;
        this.emailAddress = email; // Sync for old code reading this column
    }

    // Getter always returns from new column
    public String getEmail() {
        return email != null ? email : emailAddress; // Fallback during migration
    }
}

// After contract phase: simplified entity
@Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "email", nullable = false)
    private String email;
}
Safe column type change (INT → BIGINT) 
-- Changing orders.amount from INT to BIGINT (breaking if done directly)
-- Direct approach: ALTER TABLE orders ALTER COLUMN amount TYPE BIGINT;
-- This takes an ACCESS EXCLUSIVE lock on large tables — minutes of downtime!

-- Safe approach: expand-contract with concurrent index creation

-- V20__expand_amount_bigint.sql
ALTER TABLE orders ADD COLUMN amount_big BIGINT;

-- Backfill (batched, non-blocking)
UPDATE orders SET amount_big = amount WHERE amount_big IS NULL; -- do in batches

-- Add trigger for dual-write sync
CREATE OR REPLACE FUNCTION sync_amount() RETURNS TRIGGER AS $$
BEGIN
  NEW.amount_big := NEW.amount;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
CREATE TRIGGER trg_sync_amount BEFORE INSERT OR UPDATE ON orders
  FOR EACH ROW EXECUTE FUNCTION sync_amount();

-- V21__contract_swap_amount.sql (after all code uses amount_big)
ALTER TABLE orders DROP COLUMN amount;
ALTER TABLE orders RENAME COLUMN amount_big TO amount;
DROP TRIGGER trg_sync_amount ON orders;
DROP FUNCTION sync_amount();

Common Mistakes

Schema migration anti-patterns
# Mistake Impact Fix
1 DROP COLUMN in same deploy as code change Old pods fail immediately on rolling deploy Expand-contract: add new first, remove old weeks later
2 RENAME COLUMN directly Same as DROP — old code references old name Add new column, dual-write, migrate, drop old
3 ALTER COLUMN TYPE on large table ACCESS EXCLUSIVE lock — blocks all reads/writes for minutes Add new column with target type, backfill, swap
4 Adding NOT NULL without default on existing column Fails if any NULL rows exist; blocks on large tables Add nullable first, backfill, then add constraint
5 CREATE INDEX without CONCURRENTLY Blocks writes (SHARE lock) for the duration of the index build (minutes on large tables) Prefer CREATE INDEX CONCURRENTLY for large production tables
6 Running backfill in single UPDATE statement Locks all rows, WAL bloat, replication lag Batch updates (10K rows per batch, with sleep between)
7 No rollback plan for migrations Broken migration requires emergency manual SQL Write paired rollback migration scripts for every expand

Trade-offs

Migration strategy comparison
Approach Complexity Downtime Risk Rollback Safety Best For
Expand-Contract High (3 phases) Zero Good (expand phases reversible; contract phases require backup to restore dropped data) Breaking changes on critical tables
Blue-Green + instant cutover Medium Seconds (DNS switch) Good (switch back to blue) Small databases, infrequent deploys
Maintenance window Low Planned (minutes-hours) Medium (restore from backup) Internal tools, low-traffic services
Shadow tables + swap Very High Seconds (rename) Good (rename back) Massive tables needing restructuring (gh-ost, pt-online-schema-change)

Follow-up Interview Questions

Questions the interviewer will ask next
Q: "How would you handle a migration that needs to run on a table with 500M rows?"
Never alter in place. Use pt-online-schema-change (MySQL) or pg_repack (PostgreSQL) for online table rebuilds. For backfills: batch in 10K chunks with throttling, run during off-peak, monitor replication lag. Consider doing it over days with a background job rather than a one-time migration.
Q: "What if you need to split one table into two?"
Phase 1: Create new table, dual-write to both old and new. Phase 2: Backfill new table from old. Phase 3: Update reads to query new table. Phase 4: Stop writing to old table. Phase 5: Drop old table (weeks later). Each phase is a separate deployment with its own migration.
Q: "How do you coordinate schema changes across multiple microservices that share a database?"
Ideally: don't share databases. If you must, the schema owner service controls migrations. Other services must tolerate additive changes (new columns/tables) without code changes. Use schema versioning and API contracts rather than direct table access.
Q: "How do you test that a migration is backward-compatible?"
In CI: (1) Apply the migration to a test DB, (2) Run the CURRENT (old) app's integration tests against the new schema, (3) If they pass, the migration is backward-compatible. This catches DROP/RENAME issues before they reach production.
Q: "What tools exist for zero-downtime schema changes?"
PostgreSQL: pg_repack, Flyway, Liquibase. MySQL: pt-online-schema-change, gh-ost (GitHub's online schema migration tool), Flyway. General: Flyway/Liquibase for version management, feature flags for code transition, custom tooling for backfills.

Summary

Interview Takeaways:

  1. Never make destructive schema changes (DROP, RENAME, ALTER TYPE) in the same deploy as code changes.
  2. Use the Expand-Contract pattern: add new → migrate data → remove old. Each phase is a separate deployment.
  3. During rolling deploys, old and new code coexist — the schema must work with both versions simultaneously.
  4. Prefer CREATE INDEX CONCURRENTLY for large production tables where write availability matters. Regular CREATE INDEX blocks writes for the duration of the build.
  5. Backfill in batches with throttling — never a single UPDATE statement on large tables.
  6. Use triggers for dual-write sync during the transition period (remove after contract phase).
  7. Test backward compatibility in CI — run old app tests against new schema before merging.
  8. The contract phase should be a manual trigger, not automatic — give yourself days/weeks to confirm stability.
  9. Consider tools like gh-ost (MySQL) or pg_repack (PostgreSQL) for large table restructuring.

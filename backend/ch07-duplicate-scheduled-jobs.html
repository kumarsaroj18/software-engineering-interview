Preventing Duplicate Scheduled Job Execution

Key Takeaway: Spring's @Scheduled has no built-in cluster awareness — every pod runs the same cron independently. Use distributed locks (ShedLock), leader election (K8s Lease API), or externalize scheduling (Kubernetes CronJob) to guarantee exactly-once execution.

Interviewer's Intent

What the interviewer is really evaluating

Why this question? Duplicate job execution is one of the most common production incidents after horizontal scaling. Interviewers use this question to probe whether candidates understand:

  • Distributed systems awareness — Do you recognize that in-process scheduling is node-local?
  • Coordination primitives — Can you compare leader election vs. distributed locks vs. external orchestration?
  • Production readiness — Do you consider clock skew, lock expiry, failover, and idempotency?
  • Technology selection — Can you choose the right tool based on infrastructure constraints?
  • Failure modes — What happens when the lock holder crashes mid-execution?

A strong answer demonstrates knowledge of at least two distinct approaches, explains trade-offs, and mentions idempotency as a safety net regardless of the coordination strategy chosen.

60-Second Answer

Concise interview response

"When you scale a Spring Boot app horizontally, @Scheduled fires on every pod because it's JVM-local — there's no cluster coordination. I'd fix this with one of three strategies depending on the stack:

1. ShedLock — A lightweight library that uses a shared store (PostgreSQL, Redis, MongoDB) to acquire a lock before each scheduled execution. Only the pod that gets the lock runs the task. Minimal code change: add one annotation.

2. Kubernetes CronJob — Move the schedule out of the app entirely. K8s ensures only one Job pod is spawned per cron tick. Best when you can decouple the task from the main deployment.

3. Leader Election — One pod is elected leader (via K8s Lease API or a Redis lock) and only the leader's scheduler is active. Good for multiple scheduled tasks where you want a single 'scheduler' pod.

Regardless of approach, I'd also make the job idempotent — use a deduplication key or upsert logic — so that even if coordination fails, running twice doesn't produce duplicate side effects."

Why @Scheduled Runs on Every Pod

Understanding the root cause

Spring's @Scheduled annotation is processed by ScheduledAnnotationBeanPostProcessor, which registers tasks in a local ThreadPoolTaskScheduler. There is no network communication, no shared state, and no concept of "other instances."

Critical insight: Spring Framework deliberately does not include distributed scheduling. Each ApplicationContext is independent. When you deploy 5 replicas, you get 5 independent schedulers — all firing at the same cron expression.

Why This Is Not a Bug

Spring's design philosophy treats each application context as self-contained. Distributed coordination requires infrastructure dependencies (databases, Redis, ZooKeeper) that Spring doesn't want to mandate. The framework provides the building blocks; you choose the coordination strategy.

Leader Election Patterns

Choosing one pod to own scheduling responsibility

Leader election ensures that exactly one instance in a cluster is designated as the "leader" and is responsible for executing scheduled tasks. If the leader fails, another instance takes over.

Leader Election vs. Distributed Lock: Leader election is a long-lived assignment (one pod is leader until it fails). Distributed locks are short-lived and acquired per-task-execution. Both prevent duplicates, but leader election is better when you have many scheduled tasks on the same service.

Pattern 1: Database-based Leader Election

Use a database row as a lease. The leader periodically renews its lease; if it expires, another pod claims leadership.

-- Leader election table
CREATE TABLE scheduler_leader (
    id VARCHAR(64) PRIMARY KEY,
    leader_id VARCHAR(255) NOT NULL,
    last_heartbeat TIMESTAMP NOT NULL,
    lease_duration_ms BIGINT NOT NULL DEFAULT 30000
);

-- Claim leadership (atomic upsert)
INSERT INTO scheduler_leader (id, leader_id, last_heartbeat, lease_duration_ms)
VALUES ('MAIN_SCHEDULER', 'pod-abc-123', NOW(), 30000)
ON CONFLICT (id) DO UPDATE
SET leader_id = 'pod-abc-123',
    last_heartbeat = NOW()
WHERE scheduler_leader.last_heartbeat < NOW() - INTERVAL '30 seconds'
   OR scheduler_leader.leader_id = 'pod-abc-123';
@Component
public class DatabaseLeaderElection {

    private final JdbcTemplate jdbc;
    private final String podId = System.getenv("HOSTNAME");
    private volatile boolean isLeader = false;

    @Scheduled(fixedRate = 10_000) // Heartbeat every 10s
    public void tryAcquireLeadership() {
        int updated = jdbc.update("""
            INSERT INTO scheduler_leader (id, leader_id, last_heartbeat)
            VALUES ('MAIN', ?, NOW())
            ON CONFLICT (id) DO UPDATE
            SET leader_id = ?, last_heartbeat = NOW()
            WHERE scheduler_leader.last_heartbeat < NOW() - INTERVAL '30 seconds'
               OR scheduler_leader.leader_id = ?
            """, podId, podId, podId);

        isLeader = (updated > 0);
        log.info("Leadership status: {} for pod {}", isLeader, podId);
    }

    public boolean isLeader() {
        return isLeader;
    }
}

Pattern 2: Redis-based Leader Election

Use Redis SET with NX and EX to acquire a lease with automatic expiry.

@Component
public class RedisLeaderElection {

    private final StringRedisTemplate redis;
    private final String podId = System.getenv("HOSTNAME");
    private static final String LEADER_KEY = "scheduler:leader";
    private static final Duration LEASE_DURATION = Duration.ofSeconds(30);
    private volatile boolean isLeader = false;

    // ⚠️ Note: The get() + expire() pattern below has a small race window.
    // For production, use a Lua script to atomically check ownership + renew:
    //   if redis.call('get', KEY) == myId then redis.call('pexpire', KEY, ttl); return 1 end
    @Scheduled(fixedRate = 10_000)
    public void tryAcquireLeadership() {
        // Try to set leader key (only succeeds if not exists)
        Boolean acquired = redis.opsForValue()
            .setIfAbsent(LEADER_KEY, podId, LEASE_DURATION);

        if (Boolean.TRUE.equals(acquired)) {
            isLeader = true;
        } else {
            // Check if we're the current leader and renew
            String currentLeader = redis.opsForValue().get(LEADER_KEY);
            if (podId.equals(currentLeader)) {
                redis.expire(LEADER_KEY, LEASE_DURATION);
                isLeader = true;
            } else {
                isLeader = false;
            }
        }
    }

    public boolean isLeader() {
        return isLeader;
    }
}

Pattern 3: ZooKeeper Leader Election

Apache Curator provides a robust LeaderLatch recipe built on ZooKeeper's ephemeral sequential nodes.

@Component
public class ZookeeperLeaderElection implements SmartLifecycle {

    private final CuratorFramework curator;
    private LeaderLatch leaderLatch;

    @PostConstruct
    public void init() throws Exception {
        leaderLatch = new LeaderLatch(curator, "/scheduler/leader",
            System.getenv("HOSTNAME"));
        leaderLatch.start();
    }

    public boolean isLeader() {
        return leaderLatch.hasLeadership();
    }

    @PreDestroy
    public void shutdown() throws Exception {
        leaderLatch.close(); // Graceful release
    }

    @Override
    public void stop() {
        try { shutdown(); } catch (Exception e) { /* log */ }
    }

    @Override
    public boolean isRunning() {
        return leaderLatch.getState() == LeaderLatch.State.STARTED;
    }
}

    @Bean

@Component
public class SchedulerLeaderHandler {

    private volatile boolean isLeader = false;

    @EventListener
    public void onGranted(OnGrantedEvent event) {
        log.info("Leadership GRANTED: {}", event.getRole());
        isLeader = true;
    }

    @EventListener
    public void onRevoked(OnRevokedEvent event) {
        log.info("Leadership REVOKED: {}", event.getRole());
        isLeader = false;
    }

    public boolean isLeader() {
        return isLeader;
    }
}

Using Leader Election with @Scheduled

@Component
@RequiredArgsConstructor
public class ConditionalScheduler {

    private final LeaderElection leaderElection;
    private final ReportService reportService;

    @Scheduled(cron = "0 0 9 * * MON-FRI")
    public void generateDailyReport() {
        if (!leaderElection.isLeader()) {
            log.debug("Not leader, skipping scheduled task");
            return;
        }
        log.info("Leader executing daily report generation");
        reportService.generateAndSend();
    }
}

ShedLock Deep Dive

The most popular solution for Spring scheduled task coordination

ShedLock is a lightweight library that ensures scheduled tasks run at most once across a cluster. It does NOT provide distributed job scheduling — it only prevents multiple executions of the same task.

How it works: Before a task executes, ShedLock tries to acquire a lock in a shared store. If the lock is already held (and hasn't expired), the task is skipped on that instance. The lock is released after execution or after lockAtMostFor expires.

                .build()

}

Usage with Annotations

@Component
public class ScheduledTasks {

    @Scheduled(cron = "0 0 9 * * MON-FRI")
    @SchedulerLock(
        name = "dailyReportGeneration",
        lockAtMostFor = "5m",   // Max lock hold time (safety net)
        lockAtLeastFor = "2m"   // Min lock hold time (prevent rapid re-execution)
    )
    public void generateDailyReport() {
        // Guaranteed to run on only ONE pod
        reportService.generateAndSendToAllUsers();
    }

    @Scheduled(fixedRate = 60_000)
    @SchedulerLock(
        name = "staleSessionCleanup",
        lockAtMostFor = "10m",
        lockAtLeastFor = "30s"
    )
    public void cleanupStaleSessions() {
        sessionRepository.deleteExpired();
    }
}

lockAtMostFor vs lockAtLeastFor:

  • lockAtMostFor — Safety net. If the task crashes without releasing the lock, it expires after this duration. Set this to be longer than the task's worst-case execution time.
  • lockAtLeastFor — Prevents rapid re-execution. Even if the task finishes in 1 second, the lock is held for at least this duration. Prevents other pods from running the same task within the same cron window due to slight clock differences.

Lock Providers Comparison

Provider Consistency Performance Infrastructure Best For
JDBC (PostgreSQL) Strong (ACID) Good Already have DB Most applications
Redis Strong locally, but locks can be lost on failover (no durability guarantee during Redis restart/Sentinel failover) Excellent Redis instance or cluster High-frequency tasks where occasional double-exec is tolerable
MongoDB Strong (with WriteConcern.MAJORITY) Good Mongo replica set Already using Mongo
ZooKeeper Strong (linearizable) Good ZK ensemble Mission-critical tasks

Quartz Scheduler Clustering

Enterprise-grade clustered scheduling with JDBC JobStore

Quartz Scheduler has built-in clustering support using a shared database (JDBC JobStore). Unlike ShedLock, which only prevents duplicate execution, Quartz provides full job scheduling, triggering, misfire handling, and failover.

Job Definition

@Component
public class DailyReportJob implements Job {

    @Autowired
    private ReportService reportService;

    @Override
    public void execute(JobExecutionContext context) throws JobExecutionException {
        log.info("Executing daily report on instance: {}",
            context.getScheduler().getSchedulerInstanceId());
        reportService.generateAndSend();
    }
}

@Configuration
public class QuartzConfig {

    @Bean
    public JobDetail dailyReportJobDetail() {
        return JobBuilder.newJob(DailyReportJob.class)
            .withIdentity("dailyReport", "reports")
            .storeDurably()
            .requestRecovery(true)  // Re-execute on failover
            .build();
    }

    @Bean
    public Trigger dailyReportTrigger() {
        return TriggerBuilder.newTrigger()
            .forJob(dailyReportJobDetail())
            .withIdentity("dailyReportTrigger", "reports")
            .withSchedule(CronScheduleBuilder
                .cronSchedule("0 0 9 ? * MON-FRI")
                .withMisfireHandlingInstructionFireAndProceed())
            .build();
    }
}

When to use Quartz over ShedLock:

  • You need complex trigger types (cron, interval, calendar exclusions)
  • You need misfire handling (what happens if no pods were up during the scheduled time)
  • You need job persistence and recovery after crashes
  • You need to manage jobs dynamically (add/remove/pause at runtime)

If you just want to prevent duplicates on simple @Scheduled methods, ShedLock is much simpler.

Kubernetes-native Solutions

Leveraging the platform to solve scheduling

If you're running on Kubernetes, you can move scheduling responsibility out of the application and into the platform. This eliminates the coordination problem entirely.

Option 1: Kubernetes CronJob

Kubernetes CronJob creates a new Pod on the defined schedule. Only one Pod is created per cron tick, so there's no duplication by design.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-report-generator
  namespace: production
spec:
  schedule: "0 9 * * 1-5"  # 9 AM weekdays (UTC)
  concurrencyPolicy: Forbid  # Don't start new if previous still running
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  startingDeadlineSeconds: 300  # If missed by 5min, skip this cycle
  jobTemplate:
    spec:
      backoffLimit: 3
      activeDeadlineSeconds: 600  # Kill if runs longer than 10 min
      template:
        metadata:
          labels:
            app: report-generator
            type: cronjob
        spec:
          restartPolicy: OnFailure
          serviceAccountName: report-generator-sa
          containers:
          - name: report-generator
            image: myapp:1.2.3
            command: ["java", "-jar", "app.jar", "--spring.profiles.active=cronjob"]
            env:
            - name: TASK_NAME
              value: "dailyReport"
            resources:
              requests:
                memory: "512Mi"
                cpu: "250m"
              limits:
                memory: "1Gi"
                cpu: "500m"

concurrencyPolicy options:

  • Forbid — Skip the new run if the previous one hasn't finished (safest for reports)
  • Replace — Kill the old run and start a new one
  • Allow — Let multiple runs overlap (rarely appropriate)

Spring Boot CronJob Runner

@SpringBootApplication
public class CronJobApplication implements CommandLineRunner {

    @Autowired
    private ReportService reportService;

    @Value("${TASK_NAME:dailyReport}")
    private String taskName;

    public static void main(String[] args) {
        // Run once and exit — K8s handles the schedule
        System.exit(SpringApplication.exit(
            SpringApplication.run(CronJobApplication.class, args)));
    }

    @Override
    public void run(String... args) {
        switch (taskName) {
            case "dailyReport" -> reportService.generateAndSend();
            case "cleanup" -> cleanupService.run();
            default -> throw new IllegalArgumentException("Unknown task: " + taskName);
        }
    }
}

Option 2: Single-Replica Scheduler Deployment

Deploy the scheduler as a separate Deployment with replicas: 1. Only one pod runs the scheduled tasks.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: scheduler
  namespace: production
spec:
  replicas: 1  # Exactly one scheduler pod
  strategy:
    type: Recreate  # Don't run two during rolling update
  selector:
    matchLabels:
      app: myapp
      role: scheduler
  template:
    metadata:
      labels:
        app: myapp
        role: scheduler
    spec:
      containers:
      - name: scheduler
        image: myapp:1.2.3
        env:
        - name: SPRING_PROFILES_ACTIVE
          value: "scheduler"
        - name: SCHEDULER_ENABLED
          value: "true"
@Configuration
@Profile("scheduler")
@EnableScheduling
public class SchedulerProfile {
    // @Scheduled beans only active with scheduler profile
}

@Configuration
@Profile("!scheduler")
public class WorkerProfile {
    // No @EnableScheduling — workers don't run cron tasks
}

Limitations of single-replica: During a deployment rollout, there's a window where zero schedulers are running (Recreate strategy) or you must accept missed executions. This approach trades simplicity for reduced availability of the scheduler.

Option 3: Leader Election Sidecar

Redis Distributed Locks

SET NX EX, Redisson, Redlock, and fencing tokens

Redis provides fast, in-memory distributed locking. While simpler than ZooKeeper, Redis locks have subtle pitfalls around failover and split-brain scenarios that you must understand for production use.

Basic Redis Lock: SET NX EX

# Acquire lock (atomic: set-if-not-exists with expiry)
SET scheduler:daily-report $RANDOM_TOKEN NX EX 300

# Release lock (only if we still own it — use Lua script)
EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then \
        return redis.call('del', KEYS[1]) \
      else \
        return 0 \
      end" 1 scheduler:daily-report $RANDOM_TOKEN

Never use DEL without checking ownership! If your lock expires while you're still processing (GC pause, slow I/O), another pod acquires it. A blind DEL would release the other pod's lock. Always use the Lua script pattern above.

Java Implementation with Spring Data Redis

@Component
public class RedisDistributedLock {

    private final StringRedisTemplate redis;
    private static final String UNLOCK_SCRIPT = """
        if redis.call('get', KEYS[1]) == ARGV[1] then
            return redis.call('del', KEYS[1])
        else
            return 0
        end
        """;

    public Optional<String> tryAcquire(String lockKey, Duration ttl) {
        String token = UUID.randomUUID().toString();
        Boolean acquired = redis.opsForValue()
            .setIfAbsent(lockKey, token, ttl);
        return Boolean.TRUE.equals(acquired) ? Optional.of(token) : Optional.empty();
    }

    public boolean release(String lockKey, String token) {
        RedisScript<Long> script = RedisScript.of(UNLOCK_SCRIPT, Long.class);
        Long result = redis.execute(script,
            Collections.singletonList(lockKey),
            token);
        return result != null && result == 1L;
    }
}

// Usage in scheduler
@Component
@RequiredArgsConstructor
public class LockProtectedScheduler {

    private final RedisDistributedLock lock;
    private final ReportService reportService;

    @Scheduled(cron = "0 0 9 * * MON-FRI")
    public void generateReport() {
        Optional<String> token = lock.tryAcquire(
            "lock:daily-report", Duration.ofMinutes(10));

        if (token.isEmpty()) {
            log.debug("Another pod holds the lock, skipping");
            return;
        }

        try {
            reportService.generateAndSend();
        } finally {
            lock.release("lock:daily-report", token.get());
        }
    }
}

@Component
@RequiredArgsConstructor
public class RedissonScheduler {

    private final RedissonClient redisson;
    private final ReportService reportService;

    @Scheduled(cron = "0 0 9 * * MON-FRI")
    public void generateReport() {
        RLock lock = redisson.getLock("scheduler:daily-report");

        // tryLock: wait 0s, lease 5 minutes
        boolean acquired = false;
        try {
            acquired = lock.tryLock(0, 5, TimeUnit.MINUTES);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return;
        }

        if (!acquired) {
            log.debug("Lock not acquired, another instance is processing");
            return;
        }

        try {
            reportService.generateAndSend();
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}

The Redlock Algorithm

For Redis deployments without strong consistency (no Sentinel/Cluster failover guarantees), Redlock uses N independent Redis masters (typically 5) and requires a majority (N/2+1) to agree on the lock.

┌─────────────────────────────────────────────────────────────┐
│                    Redlock Algorithm                          │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Client attempts SET NX on all 5 independent Redis nodes:    │
│                                                              │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────┐ │
│  │Redis 1  │ │Redis 2  │ │Redis 3  │ │Redis 4  │ │  5  │ │
│  │  ✅     │ │  ✅     │ │  ✅     │ │  ❌     │ │ ❌  │ │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────┘ │
│                                                              │
│  3 out of 5 succeeded (majority) → Lock acquired ✅         │
│  Must complete within: TTL - time_to_acquire                 │
│                                                              │
└─────────────────────────────────────────────────────────────┘

Redlock controversy: Martin Kleppmann's 2016 analysis argues Redlock is unsafe under process pauses (GC) and clock drift, even with majority agreement. For correctness-critical systems (financial transactions), prefer a consensus-based system (ZooKeeper, etcd) or use fencing tokens (shown below) as an additional safety layer. Redlock remains popular for distributed scheduling where occasional double-execution is tolerable with idempotent tasks.

// Redisson Redlock (multi-master)
@Component
public class RedlockScheduler {

    @Autowired
    private RedissonClient redisson1, redisson2, redisson3;

    @Scheduled(cron = "0 0 9 * * MON-FRI")
    public void generateReport() {
        RLock lock1 = redisson1.getLock("scheduler:report");
        RLock lock2 = redisson2.getLock("scheduler:report");
        RLock lock3 = redisson3.getLock("scheduler:report");

        RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);

        try {
            if (redLock.tryLock(0, 5, TimeUnit.MINUTES)) {
                try {
                    reportService.generateAndSend();
                } finally {
                    redLock.unlock();
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

Fencing Tokens

Fencing tokens protect against a scenario where a client holds a lock, gets paused (GC, network), the lock expires, another client acquires it, and then both clients try to write.

How fencing works: Each lock acquisition returns a monotonically increasing token. The downstream resource (database, API) rejects operations with a token lower than the highest it has seen.

public class FencedLock {
    private final StringRedisTemplate redis;

    public OptionalLong tryAcquireWithFence(String lockKey, Duration ttl) {
        // Atomically increment and set lock
        String script = """
            if redis.call('set', KEYS[1], ARGV[1], 'NX', 'EX', ARGV[2]) then
                return redis.call('incr', KEYS[2])
            else
                return nil
            end
            """;

        Long fenceToken = redis.execute(
            RedisScript.of(script, Long.class),
            List.of(lockKey, lockKey + ":fence"),
            UUID.randomUUID().toString(),
            String.valueOf(ttl.getSeconds())
        );

        return fenceToken != null ? OptionalLong.of(fenceToken) : OptionalLong.empty();
    }
}

// Usage: pass fence token to downstream writes
public void processWithFence(long fenceToken) {
    int updated = jdbc.update("""
        UPDATE reports SET status = 'SENT', fence_token = ?
        WHERE id = ? AND fence_token < ?
        """, fenceToken, reportId, fenceToken);

    if (updated == 0) {
        log.warn("Stale fence token {}, another instance already processed", fenceToken);
    }
}

Production Incident: Duplicate Report Emails

50,000 users received 3× duplicate emails after autoscaling

Incident Severity: P2 — Customer-facing duplicate communications

Timeline

Root Cause Analysis

// THE PROBLEMATIC CODE
@Component

Why It Wasn't Caught Earlier

  • Development: single instance → no duplication
  • Staging: 2 replicas, but manually deployed at different times → cron schedules rarely overlapped exactly
  • Production: initially 2 replicas with sticky timing. HPA scaling to 5 pods caused all to align on the same cron second.

The Fix (Applied in 30 minutes)

    name = "sendDailyReports",
    lockAtMostFor = "30m",
    lockAtLeastFor = "5m"
)

Long-term Improvements

// LONG-TERM: Idempotent email sending with deduplication
@Scheduled(cron = "0 0 9 * * *")
@SchedulerLock(name = "sendDailyReports", lockAtMostFor = "30m")
public void sendDailyReports() {
    String batchId = "daily-report-" + LocalDate.now();

    // Check if already processed today
    if (reportBatchRepo.existsByBatchId(batchId)) {
        log.info("Batch {} already processed, skipping", batchId);
        return;
    }

    List<User> users = userRepo.findByReportEnabled(true);
    for (User user : users) {
        String dedupeKey = batchId + ":" + user.getId();

        // Idempotent send — email service deduplicates by key
        emailService.sendIdempotent(dedupeKey, user.getEmail(), buildReport(user));
    }

    // Mark batch as complete
    reportBatchRepo.save(new ReportBatch(batchId, Instant.now(), users.size()));
}

Lessons Learned

  1. Defense in depth: Use both coordination (ShedLock) AND idempotency (deduplication keys)
  2. Test with realistic replica counts: CI/CD should run scheduled task tests with multiple instances
  3. Feature flags for scheduled tasks: Ability to disable any scheduled task without a deployment
  4. Audit trail: Log which pod executed which batch with a correlation ID
  5. Alerting: Monitor for duplicate sends using the deduplication key collision rate

Example 2: Redis Leader Election with Spring Boot

// --- RedisLeaderElectionService.java ---
@Service
@Slf4j
public class RedisLeaderElectionService implements DisposableBean {

    private final StringRedisTemplate redis;
    private final String instanceId;
    private final AtomicBoolean leader = new AtomicBoolean(false);

    private static final String LEADER_KEY = "app:scheduler:leader";
    private static final Duration LEASE_TTL = Duration.ofSeconds(30);
    private static final Duration HEARTBEAT_INTERVAL = Duration.ofSeconds(10);

    private final ScheduledExecutorService executor =
        Executors.newSingleThreadScheduledExecutor();

    public RedisLeaderElectionService(StringRedisTemplate redis) {
        this.redis = redis;
        this.instanceId = System.getenv().getOrDefault("HOSTNAME",
            InetAddress.getLocalHost().getHostName());

        // Start heartbeat
        executor.scheduleAtFixedRate(this::heartbeat,
            0, HEARTBEAT_INTERVAL.getSeconds(), TimeUnit.SECONDS);
    }

    private void heartbeat() {
        try {
            Boolean acquired = redis.opsForValue()
                .setIfAbsent(LEADER_KEY, instanceId, LEASE_TTL);

            if (Boolean.TRUE.equals(acquired)) {
                leader.set(true);
                log.debug("Acquired leadership: {}", instanceId);
                return;
            }

            // Check if we already own it → renew
            String currentLeader = redis.opsForValue().get(LEADER_KEY);
            if (instanceId.equals(currentLeader)) {
                redis.expire(LEADER_KEY, LEASE_TTL);
                leader.set(true);
            } else {
                if (leader.getAndSet(false)) {
                    log.info("Lost leadership to: {}", currentLeader);
                }
            }
        } catch (Exception e) {
            log.error("Leader election heartbeat failed", e);
            leader.set(false);
        }
    }

    public boolean isLeader() {
        return leader.get();
    }

    @Override
    public void destroy() {
        executor.shutdown();
        // Release leadership gracefully
        if (leader.get()) {
            String script = """
                if redis.call('get', KEYS[1]) == ARGV[1] then
                    return redis.call('del', KEYS[1])
                end
                return 0
                """;
            redis.execute(RedisScript.of(script, Long.class),
                List.of(LEADER_KEY), instanceId);
        }
    }
}

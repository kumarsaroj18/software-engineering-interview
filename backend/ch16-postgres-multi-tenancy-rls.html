Hard Multi-Tenancy PostgreSQL RLS

How Would You Design Multi-Tenancy in PostgreSQL, and When Would You Use Row-Level Security?

Key Takeaway: Multi-tenancy has three implementation strategies — separate databases, separate schemas, and shared tables with a tenant ID column — each with different isolation, cost, and operational trade-offs. Row-Level Security (RLS) is PostgreSQL's built-in enforcement layer that makes shared-table multi-tenancy safe at the database level, eliminating the risk of tenant data leaks caused by missing application-layer WHERE clauses.

Interviewer Intent

What the interviewer is really evaluating

This question tests your ability to design systems that serve multiple customers from shared infrastructure — a core challenge in SaaS products. The interviewer wants to see:

  • Awareness of isolation models: You understand the spectrum from hard database-per-tenant isolation to soft shared-table isolation and can articulate the trade-offs.
  • Security depth: You know that application-level tenant filtering is fragile and that RLS provides a defense-in-depth layer directly in the database.
  • Operational thinking: You consider how the choice affects schema migrations, connection pooling, backup strategies, and tenant onboarding costs.
  • Performance intuition: You understand how indexes, partitioning, and connection pool configuration interact with the chosen strategy.
  • Real experience: You can describe a data-leak incident or near-miss caused by a missing WHERE tenant_id = ? clause and how RLS would have prevented it.

Senior engineers are expected to have opinions here — not just recite options. The interviewer will probe for why you would choose one approach for a startup with 10 tenants versus an enterprise platform with 10,000.

Quick Answer

30-second interview response

"There are three main strategies. Database-per-tenant gives the strongest isolation and is ideal for enterprise customers with strict compliance requirements, but it's expensive to operate at scale. Schema-per-tenant keeps tenants in the same Postgres instance but in separate namespaces — good for mid-market SaaS. Shared tables with a tenant_id column is the most cost-efficient and scales to thousands of tenants, but it requires rigorous application-level filtering, which is error-prone. That's where Row-Level Security comes in — I'd always enable RLS on shared tables as a safety net. You define policies that automatically append a WHERE tenant_id = current_setting('app.tenant_id') filter to every query, so even if the application forgets the filter, the database enforces it."

This answer shows you know all three strategies, can justify the choice, and understand RLS as a security mechanism rather than just a performance trick. The sections below expand on each with production-grade SQL and Spring Boot integration.

Multi-Tenancy Strategies

Strategy 1 — Database-per-Tenant

Model: Each tenant gets a completely separate PostgreSQL database (or even separate server). No shared objects at the database level.

  Database-per-Tenant Architecture:
  ══════════════════════════════════════════════════════════════

  App Server
      │
      ├── tenant_id=acme    → postgres://acme-db:5432/acme
      ├── tenant_id=globex  → postgres://globex-db:5432/globex
      └── tenant_id=initech → postgres://initech-db:5432/initech

  Each database:
  ┌──────────────────────┐
  │  users               │
  │  orders              │  ← identical schema, no tenant_id column needed
  │  invoices            │
  └──────────────────────┘

  Connection routing via tenant registry:
  ┌─────────────────┐      ┌──────────────────────────┐
  │  Request        │─────▶│  TenantRoutingDataSource  │
  │  (tenant=acme)  │      │  resolves connection URL  │
  └─────────────────┘      └──────────────────────────┘

Implementation: Dynamic DataSource Routing in Spring Boot

// TenantContext: stores current tenant in a ThreadLocal
public class TenantContext {
    private static final ThreadLocal<String> CURRENT_TENANT = new ThreadLocal<>();

    public static void setTenantId(String tenantId) {
        CURRENT_TENANT.set(tenantId);
    }

    public static String getTenantId() {
        return CURRENT_TENANT.get();
    }

    public static void clear() {
        CURRENT_TENANT.remove();
    }
}

// AbstractRoutingDataSource: routes connections by tenant
@Component
public class TenantRoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        String tenantId = TenantContext.getTenantId();
        if (tenantId == null) {
            throw new IllegalStateException("No tenant set in current thread context");
        }
        return tenantId;
    }
}

// Configuration: register one DataSource per tenant at startup
@Configuration
public class MultiTenantDataSourceConfig {

    @Autowired
    private TenantRegistry tenantRegistry; // loads tenant DB configs from DB or config service

    @Bean
    public DataSource dataSource() {
        Map<Object, Object> dataSources = new HashMap<>();

        for (TenantConfig tenant : tenantRegistry.getAllTenants()) {
            HikariConfig config = new HikariConfig();
            config.setJdbcUrl(tenant.getJdbcUrl());
            config.setUsername(tenant.getDbUsername());
            config.setPassword(tenant.getDbPassword());
            config.setMaximumPoolSize(10); // per-tenant pool — monitor total connections!
            config.setPoolName("pool-" + tenant.getTenantId());
            dataSources.put(tenant.getTenantId(), new HikariDataSource(config));
        }

        TenantRoutingDataSource routingDataSource = new TenantRoutingDataSource();
        routingDataSource.setTargetDataSources(dataSources);
        routingDataSource.setDefaultTargetDataSource(dataSources.values().iterator().next());
        return routingDataSource;
    }
}

// Filter: extract tenant from JWT and set in context
@Component
@Order(1)
public class TenantResolutionFilter implements Filter {

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest request = (HttpServletRequest) req;
        try {
            String tenantId = extractTenantFromJwt(request);
            TenantContext.setTenantId(tenantId);
            chain.doFilter(req, res);
        } finally {
            TenantContext.clear(); // CRITICAL: always clear to avoid ThreadLocal leaks
        }
    }

    private String extractTenantFromJwt(HttpServletRequest request) {
        String token = request.getHeader("Authorization");
        // Parse JWT claims — tenant_id is stored as a custom claim
        return JwtUtils.getClaim(token, "tenant_id");
    }
}

Trade-offs

AspectDetail
✅ IsolationComplete — no SQL bug can cross tenant boundaries
✅ ComplianceEasy to meet GDPR "right to erasure" — just drop the database
✅ PerformanceDedicated resources; one tenant's query load can't starve another
❌ CostN databases × overhead — idle connections, storage, backups multiply with tenant count
❌ MigrationsSchema changes must run against every tenant database (Flyway multi-tenant runner needed)
❌ Connection poolAt 1000 tenants × 10 pool size = 10,000 DB connections — PostgreSQL typically maxes out around 500–1000

Connection pool explosion: Database-per-tenant with a large number of tenants quickly exhausts PostgreSQL's max_connections. Use PgBouncer in transaction-mode pooling in front of each tenant DB to reduce live connections.

Strategy 2 — Schema-per-Tenant

Model: All tenants share one PostgreSQL instance, but each has a private schema (namespace). The application sets search_path to the tenant's schema on each connection.

  Schema-per-Tenant Architecture:
  ══════════════════════════════════════════════════════════════

  Single PostgreSQL Instance
  ┌─────────────────────────────────────────────────────────┐
  │                                                         │
  │  schema: acme        schema: globex     schema: public  │
  │  ┌──────────────┐    ┌──────────────┐   ┌───────────┐  │
  │  │ users        │    │ users        │   │ shared    │  │
  │  │ orders       │    │ orders       │   │ config    │  │
  │  │ invoices     │    │ invoices     │   └───────────┘  │
  │  └──────────────┘    └──────────────┘                  │
  └─────────────────────────────────────────────────────────┘

  App sets: SET search_path TO acme, public;
  Query:    SELECT * FROM users; → resolves to acme.users

Setting search_path per connection in Spring Boot

// Hibernate multi-tenant connection provider using schema isolation
@Component
public class SchemaPerTenantConnectionProvider
        implements MultiTenantConnectionProvider {

    @Autowired
    private DataSource dataSource; // single datasource for the shared PG instance

    @Override
    public Connection getAnyConnection() throws SQLException {
        return dataSource.getConnection();
    }

    @Override
    public Connection getConnection(String tenantIdentifier) throws SQLException {
        Connection conn = dataSource.getConnection();
        // Validate tenant name to prevent SQL injection via search_path
        if (!tenantIdentifier.matches("^[a-z0-9_]{1,63}$")) {
            throw new IllegalArgumentException("Invalid tenant identifier: " + tenantIdentifier);
        }
        // Switch schema context for this connection
        conn.createStatement().execute(
            "SET search_path TO " + tenantIdentifier + ", public"
        );
        return conn;
    }

    @Override
    public void releaseConnection(String tenantIdentifier, Connection conn)
            throws SQLException {
        // Reset to public schema before returning to pool
        conn.createStatement().execute("SET search_path TO public");
        conn.close();
    }

    // ... other required overrides
}

Strategy 3 — Shared Tables with tenant_id Column

Model: All tenants share the same tables. Every table has a tenant_id column and the application (or RLS policy) filters by it on every query.

  Shared-Table Architecture:
  ══════════════════════════════════════════════════════════════

  Single PostgreSQL Instance, Single Schema
  ┌─────────────────────────────────────────────────────────┐
  │                                                         │
  │  Table: orders                                          │
  │  ┌──────────┬────────────┬────────┬──────────────────┐  │
  │  │ id       │ tenant_id  │ amount │ status           │  │
  │  ├──────────┼────────────┼────────┼──────────────────┤  │
  │  │ 1001     │ acme       │ 250.00 │ paid             │  │
  │  │ 1002     │ globex     │ 99.00  │ pending          │  │
  │  │ 1003     │ acme       │ 75.00  │ pending          │  │
  │  │ 1004     │ initech    │ 500.00 │ paid             │  │
  │  └──────────┴────────────┴────────┴──────────────────┘  │
  │                  ↑                                       │
  │   EVERY query must filter on this column                 │
  │   (enforced by app layer OR by RLS policy)               │
  └─────────────────────────────────────────────────────────┘

Base Schema Setup

-- Tenants registry
CREATE TABLE tenants (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    slug        VARCHAR(63) UNIQUE NOT NULL,  -- 'acme', 'globex'
    name        VARCHAR(255) NOT NULL,
    plan        VARCHAR(50) NOT NULL DEFAULT 'starter',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    is_active   BOOLEAN NOT NULL DEFAULT TRUE
);

-- All data tables include tenant_id
CREATE TABLE orders (
    id          BIGSERIAL,
    tenant_id   UUID NOT NULL REFERENCES tenants(id),
    customer_id BIGINT NOT NULL,
    amount      NUMERIC(12, 2) NOT NULL,
    status      VARCHAR(50) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    -- Composite primary key keeps tenant_id in every index
    PRIMARY KEY (tenant_id, id)
);

-- Composite index: tenant_id first for all queries that filter by tenant
CREATE INDEX idx_orders_tenant_status
    ON orders (tenant_id, status, created_at DESC);

CREATE TABLE invoices (
    id          BIGSERIAL,
    tenant_id   UUID NOT NULL REFERENCES tenants(id),
    order_id    BIGINT NOT NULL,
    total       NUMERIC(12, 2) NOT NULL,
    due_date    DATE NOT NULL,
    PRIMARY KEY (tenant_id, id)
);

CREATE INDEX idx_invoices_tenant_order
    ON invoices (tenant_id, order_id);

Hybrid approach: Many mature SaaS platforms use a tiered model — large enterprise tenants get dedicated databases (premium tier), mid-market tenants get schema isolation, and self-serve/free tenants share tables. Tenant tier is stored in the registry and the routing layer dispatches accordingly.

Row-Level Security (RLS)

How RLS works inside PostgreSQL

RLS is a PostgreSQL feature (introduced in 9.5) that attaches security policies to tables. When enabled, the query planner automatically injects the policy's predicate as an additional filter on every SELECT, INSERT, UPDATE, and DELETE — before the query executes. The application cannot bypass this filter without explicitly being granted the BYPASSRLS privilege.

  Without RLS:
  ════════════════════════════════════════════════════════════

  App Query:  SELECT * FROM orders WHERE status = 'pending'
                                         ↓
  Planner:    SCAN orders WHERE status = 'pending'
              ↑ returns rows from ALL tenants if app forgot tenant filter!

  With RLS enabled + policy:
  ════════════════════════════════════════════════════════════

  App Query:  SELECT * FROM orders WHERE status = 'pending'
                                         ↓
  Planner:    SCAN orders
              WHERE status = 'pending'
              AND tenant_id = current_setting('app.tenant_id')::uuid
              ↑ policy predicate injected automatically by PostgreSQL
              ↑ even if app omits it, tenant isolation is enforced

  Execution flow:
  ┌─────────────┐    ┌─────────────────────┐    ┌──────────────────────┐
  │ App sends   │───▶│ Postgres checks RLS  │───▶│ Policy predicate     │
  │ query       │    │ is enabled on table  │    │ merged with WHERE    │
  └─────────────┘    └─────────────────────┘    └──────────┬───────────┘
                                                            │
                                              ┌─────────────▼───────────┐
                                              │ Filtered result set      │
                                              │ (only current tenant)    │
                                              └─────────────────────────┘

Enabling RLS

-- Step 1: Enable RLS on the table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- Step 2: Force RLS even for the table owner
-- (without this, table owners bypass policies by default)
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

-- Repeat for every tenant-scoped table
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;

ALTER TABLE users ENABLE ROW LEVEL SECURITY;
ALTER TABLE users FORCE ROW LEVEL SECURITY;

The current_setting mechanism

RLS policies need to know which tenant is active. PostgreSQL's current_setting() reads from a session-local variable set by the application at the start of each request.

-- Application sets this at connection acquisition time:
SET LOCAL app.tenant_id = 'a1b2c3d4-e5f6-7890-abcd-ef1234567890';

-- Policy reads it:
current_setting('app.tenant_id')::uuid

-- 'missing_ok' variant avoids errors when variable is not set
-- (returns NULL instead of raising exception — useful in migrations)
current_setting('app.tenant_id', true)::uuid

Writing RLS Policies

SELECT, INSERT, UPDATE, DELETE policies

Basic read/write policy

-- CREATE POLICY syntax:
-- CREATE POLICY policy_name ON table_name
--   [AS {PERMISSIVE | RESTRICTIVE}]
--   [FOR {ALL | SELECT | INSERT | UPDATE | DELETE}]
--   [TO role_name]
--   [USING (predicate)]         -- checked on existing rows (SELECT, UPDATE, DELETE)
--   [WITH CHECK (predicate)];   -- checked on new rows (INSERT, UPDATE)

-- Policy for SELECT: tenant can only read their own rows
CREATE POLICY tenant_isolation_select ON orders
    FOR SELECT
    USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- Policy for INSERT: tenant can only insert rows tagged with their tenant_id
CREATE POLICY tenant_isolation_insert ON orders
    FOR INSERT
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- Policy for UPDATE: can only update own rows AND can only update to own tenant_id
CREATE POLICY tenant_isolation_update ON orders
    FOR UPDATE
    USING  (tenant_id = current_setting('app.tenant_id')::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- Policy for DELETE: can only delete own rows
CREATE POLICY tenant_isolation_delete ON orders
    FOR DELETE
    USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- Alternatively, combine all into one ALL policy:
CREATE POLICY tenant_isolation ON orders
    FOR ALL
    USING  (tenant_id = current_setting('app.tenant_id')::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

Admin bypass policy (for internal tooling)

-- Create a dedicated admin role that can see all tenants
-- (used for support tooling, cross-tenant reports, migrations)
CREATE ROLE app_admin;
CREATE ROLE app_user;

-- Policy: app_user role sees only their tenant; app_admin sees all
CREATE POLICY tenant_isolation ON orders
    FOR ALL
    TO app_user  -- applies only to this role
    USING  (tenant_id = current_setting('app.tenant_id')::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- app_admin has no restricting policy, so it sees all rows
-- (or grant BYPASSRLS explicitly)
ALTER ROLE app_admin BYPASSRLS;

-- Verify policies on a table:
SELECT policyname, cmd, roles, qual, with_check
FROM pg_policies
WHERE tablename = 'orders';

PERMISSIVE vs RESTRICTIVE policies

-- PERMISSIVE (default): multiple policies are OR-ed together
-- A row is visible if ANY permissive policy allows it
CREATE POLICY owner_policy ON documents
    AS PERMISSIVE
    FOR SELECT
    USING (owner_id = current_user_id());

CREATE POLICY shared_policy ON documents
    AS PERMISSIVE
    FOR SELECT
    USING (is_public = TRUE);
-- Result: user sees their own docs OR any public doc

-- RESTRICTIVE: policies are AND-ed with permissive policies
-- A row is visible only if ALL restrictive policies AND any permissive policy allows it
CREATE POLICY tenant_boundary ON documents
    AS RESTRICTIVE
    FOR SELECT
    USING (tenant_id = current_setting('app.tenant_id')::uuid);
-- Result: user sees (their own docs OR public docs) AND only within their tenant
-- This is the right pattern for multi-tenancy: RESTRICTIVE for tenant boundary,
-- PERMISSIVE for ownership/sharing rules within a tenant

Row-level security with JOINs

-- RLS is applied per-table. In a JOIN, each table's policy is checked independently.
-- This query automatically respects RLS on BOTH orders and invoices:

SELECT o.id, o.amount, i.due_date
FROM   orders o
JOIN   invoices i ON i.order_id = o.id
                 AND i.tenant_id = o.tenant_id
WHERE  o.status = 'paid';

-- PostgreSQL injects:
--   orders.tenant_id    = current_setting('app.tenant_id')::uuid
--   invoices.tenant_id  = current_setting('app.tenant_id')::uuid
-- No cross-tenant data can leak through JOIN even if you forget the explicit filter.

Checking the query plan — verify RLS is applied

-- Always verify policies are being used in the plan
SET app.tenant_id = 'a1b2c3d4-e5f6-7890-abcd-ef1234567890';

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'pending';

-- Look for the RLS filter in the output:
-- Filter: ((tenant_id = (current_setting('app.tenant_id'))::uuid) AND ((status)::text = 'pending'::text))
-- If you don't see the tenant_id filter — RLS is NOT active (check ENABLE + FORCE)
Advanced: Partial policies and role-specific rules 
-- Use case: support staff can read any tenant's data in read-only mode
-- but cannot modify data outside their own tenant assignment

CREATE ROLE support_staff;

-- Support can SELECT any row (no tenant restriction)
CREATE POLICY support_read_all ON orders
    FOR SELECT
    TO support_staff
    USING (TRUE);  -- no restriction — sees everything

-- Support cannot INSERT/UPDATE/DELETE
-- (simply don't create permissive write policies for support_staff)
-- Without a matching write policy, writes are denied by default

-- Tenant users retain the standard isolation policy
CREATE POLICY tenant_isolation ON orders
    FOR ALL
    TO app_user
    USING  (tenant_id = current_setting('app.tenant_id')::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
-- Use case: within a tenant, users can only see their own orders
-- unless they have the 'admin' role within that tenant

CREATE POLICY user_order_isolation ON orders
    AS PERMISSIVE
    FOR SELECT
    TO app_user
    USING (
        tenant_id = current_setting('app.tenant_id')::uuid
        AND (
            -- User sees their own orders always
            owner_user_id = current_setting('app.user_id')::bigint
            OR
            -- Tenant admins see all tenant orders
            current_setting('app.user_role') = 'admin'
        )
    );

RLS with Spring Boot

Setting the session variable on every connection

The core challenge: you must execute SET LOCAL app.tenant_id = '...' at the start of every database transaction, before any SQL runs. The right place is a Hibernate interceptor or a JPA EntityManager callback.

Approach 1: Hibernate EmptyInterceptor

// Interceptor fires before every transaction begins
@Component
public class TenantRlsInterceptor extends EmptyInterceptor {

    @Override
    public void afterTransactionBegin(Transaction tx) {
        String tenantId = TenantContext.getTenantId();
        if (tenantId != null) {
            // Use the underlying JDBC connection to set the session variable
            // This fires inside the transaction boundary (SET LOCAL — resets on commit/rollback)
            Session session = (Session) tx; // cast to Hibernate Session
            session.doWork(connection -> {
                try (PreparedStatement ps = connection.prepareStatement(
                        "SELECT set_config('app.tenant_id', ?, true)")) {
                    ps.setString(1, tenantId);
                    ps.execute();
                }
            });
        }
    }
}

// Register the interceptor
@Configuration
public class HibernateConfig {

    @Autowired
    private TenantRlsInterceptor tenantRlsInterceptor;

    @Bean
    public HibernatePropertiesCustomizer hibernatePropertiesCustomizer() {
        return props -> props.put("hibernate.session_factory.interceptor", tenantRlsInterceptor);
    }
}

Approach 2: Spring's ConnectionPreparer (recommended for JPA/Spring Data)

// DataSource wrapper that sets tenant_id on every borrowed connection
@Component
public class TenantAwareDataSource extends DelegatingDataSource {

    public TenantAwareDataSource(DataSource delegate) {
        super(delegate);
    }

    @Override
    public Connection getConnection() throws SQLException {
        Connection conn = super.getConnection();
        applyTenantContext(conn);
        return conn;
    }

    @Override
    public Connection getConnection(String username, String password) throws SQLException {
        Connection conn = super.getConnection(username, password);
        applyTenantContext(conn);
        return conn;
    }

    private void applyTenantContext(Connection conn) throws SQLException {
        String tenantId = TenantContext.getTenantId();
        if (tenantId != null) {
            // set_config(key, value, is_local)
            // is_local=true: variable is reset at end of transaction (safe for pooled connections)
            // is_local=false: variable persists for entire session (risky with pooling!)
            try (PreparedStatement ps = conn.prepareStatement(
                    "SELECT set_config('app.tenant_id', ?, true)")) {
                ps.setString(1, tenantId);
                ps.execute();
            }
        }
    }
}

// Configuration
@Configuration
public class DataSourceConfig {

    @Bean
    @Primary
    public DataSource dataSource(
            @Qualifier("rawDataSource") DataSource rawDataSource) {
        return new TenantAwareDataSource(rawDataSource);
    }

    @Bean("rawDataSource")
    public DataSource rawDataSource() {
        HikariConfig config = new HikariConfig();
        config.setJdbcUrl("jdbc:postgresql://localhost:5432/myapp");
        config.setUsername("app_user");
        config.setPassword("secret");
        config.setMaximumPoolSize(20);
        // IMPORTANT: reset app.tenant_id when connection returns to pool
        config.setConnectionInitSql("SELECT 1"); // optional init check
        return new HikariDataSource(config);
    }
}

Approach 3: @Transactional with AOP (cleanest for service layer)

// Custom annotation to declare tenant-scoped operations
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Transactional  // also makes it transactional
public @interface TenantScoped { }

// AOP aspect: sets tenant context before @TenantScoped methods
@Aspect
@Component
@Order(1) // run before @Transactional opens the connection
public class TenantContextAspect {

    @Around("@annotation(TenantScoped)")
    public Object setTenantContext(ProceedingJoinPoint pjp) throws Throwable {
        String tenantId = TenantContext.getTenantId();
        if (tenantId == null) {
            throw new TenantContextMissingException(
                "No tenant in context for " + pjp.getSignature().toShortString()
            );
        }
        // TenantAwareDataSource will pick up the value from TenantContext
        return pjp.proceed();
    }
}

// Usage in service layer — clean, no boilerplate
@Service
@Slf4j
public class OrderService {

    @Autowired
    private OrderRepository orderRepository;

    @TenantScoped
    public List<Order> getActiveOrders() {
        // RLS enforced at DB level; no manual tenant filter needed in query
        return orderRepository.findByStatus(OrderStatus.ACTIVE);
    }

    @TenantScoped
    public Order createOrder(CreateOrderRequest request) {
        Order order = new Order();
        order.setTenantId(UUID.fromString(TenantContext.getTenantId()));
        order.setCustomerId(request.getCustomerId());
        order.setAmount(request.getAmount());
        order.setStatus(OrderStatus.PENDING);
        return orderRepository.save(order); // RLS WITH CHECK ensures correct tenant_id
    }
}

Full request lifecycle with RLS

  HTTP Request Lifecycle with RLS:
  ══════════════════════════════════════════════════════════════

  1. HTTP Request arrives
     │
  2. TenantResolutionFilter
     │  → extracts tenant_id from JWT claim
     │  → TenantContext.setTenantId("a1b2c3d4-...")
     │
  3. Controller → Service (@TenantScoped)
     │  → AOP verifies TenantContext is set
     │
  4. @Transactional opens transaction
     │  → HikariCP borrows a connection from pool
     │
  5. TenantAwareDataSource.getConnection()
     │  → executes: SELECT set_config('app.tenant_id', 'a1b2c3d4-...', true)
     │  → variable is LOCAL to this transaction
     │
  6. JPA/Hibernate executes query
     │  → SELECT * FROM orders WHERE status = 'active'
     │
  7. PostgreSQL planner merges RLS policy
     │  → actual scan: orders WHERE status='active'
     │                        AND tenant_id='a1b2c3d4-...'
     │
  8. Result returned to app — contains ONLY this tenant's rows
     │
  9. Transaction commits/rolls back
     │  → SET LOCAL variable automatically cleared
     │
  10. Connection returned to HikariCP pool
      → no tenant state leaks to next borrower

Critical: use SET LOCAL, not SET SESSION. SET LOCAL scopes the variable to the current transaction and automatically resets when the transaction ends. If you use SET SESSION (or set_config(..., false)), the variable persists on the pooled connection and the next request that borrows it will run with the previous tenant's identity — a data leak.

Performance & Indexing

Index design for shared-table multi-tenancy

In a shared-table model, every query filter includes tenant_id. Your indexes must lead with tenant_id to be useful — otherwise PostgreSQL performs a full table scan and then filters by tenant in memory.

Composite indexes: tenant_id first

-- BAD: index on status alone — full table scan + filter by tenant
CREATE INDEX idx_orders_status ON orders (status);
-- Query: WHERE tenant_id = ? AND status = 'pending'
-- Plan: Seq Scan on orders (Filter: tenant_id=... AND status=...)
--       reads ALL rows across all tenants, then filters

-- GOOD: tenant_id first in the composite index
CREATE INDEX idx_orders_tenant_status ON orders (tenant_id, status);
-- Plan: Index Scan using idx_orders_tenant_status
--       (tenant_id = ?) → narrow index range for that tenant
--       then filter by status within that range

-- For time-range queries (most SaaS dashboards):
CREATE INDEX idx_orders_tenant_status_time
    ON orders (tenant_id, status, created_at DESC);

-- For full-text or pattern searches scoped to a tenant:
CREATE INDEX idx_orders_tenant_customer
    ON orders (tenant_id, customer_id)
    INCLUDE (amount, status); -- covering index avoids heap fetch

-- Partial index: only index active tenants' pending orders
-- (useful when a large % of data is archived/cancelled)
CREATE INDEX idx_orders_active_pending
    ON orders (tenant_id, created_at DESC)
    WHERE status IN ('pending', 'processing');

Table partitioning by tenant_id

For very large tables (billions of rows), consider declarative partitioning by tenant. Postgres can perform partition pruning — skipping partitions not belonging to the current tenant entirely.

-- Partition orders by tenant_id (hash partitioning for even distribution)
CREATE TABLE orders (
    id          BIGSERIAL,
    tenant_id   UUID NOT NULL,
    customer_id BIGINT NOT NULL,
    amount      NUMERIC(12,2) NOT NULL,
    status      VARCHAR(50) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (tenant_id, id)
) PARTITION BY HASH (tenant_id);

-- Create N partitions (start small, increase as data grows)
CREATE TABLE orders_p0 PARTITION OF orders FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE orders_p1 PARTITION OF orders FOR VALUES WITH (MODULUS 8, REMAINDER 1);
CREATE TABLE orders_p2 PARTITION OF orders FOR VALUES WITH (MODULUS 8, REMAINDER 2);
CREATE TABLE orders_p3 PARTITION OF orders FOR VALUES WITH (MODULUS 8, REMAINDER 3);
CREATE TABLE orders_p4 PARTITION OF orders FOR VALUES WITH (MODULUS 8, REMAINDER 4);
CREATE TABLE orders_p5 PARTITION OF orders FOR VALUES WITH (MODULUS 8, REMAINDER 5);
CREATE TABLE orders_p6 PARTITION OF orders FOR VALUES WITH (MODULUS 8, REMAINDER 6);
CREATE TABLE orders_p7 PARTITION OF orders FOR VALUES WITH (MODULUS 8, REMAINDER 7);

-- Indexes on each partition (inherited automatically in PG 11+)
CREATE INDEX ON orders (tenant_id, status, created_at DESC);

-- Verify partition pruning:
EXPLAIN SELECT * FROM orders WHERE tenant_id = 'a1b2c3d4-...' AND status = 'paid';
-- Should show: Append → Seq Scan on orders_p3  (only 1 of 8 partitions scanned)
-- "Partition Filters" line confirms pruning is active

RLS performance: the policy predicate cost

-- RLS policies add a predicate to every query.
-- Verify the planner uses the index:

SET app.tenant_id = 'a1b2c3d4-e5f6-7890-abcd-ef1234567890';

EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT id, amount FROM orders WHERE status = 'pending' LIMIT 20;

-- Good plan (index scan, policy predicate pushed down):
-- Index Scan using idx_orders_tenant_status on orders
--   Index Cond: ((tenant_id = '...'::uuid) AND (status = 'pending'))
--   Rows Removed by Index Recheck: 0
--   Buffers: shared hit=4

-- Bad plan (seq scan — missing tenant_id index):
-- Seq Scan on orders
--   Filter: ((tenant_id = '...'::uuid) AND (status = 'pending'))
--   Rows Removed by Filter: 4580000  ← reading entire table!

-- current_setting() is evaluated once per query, not per row — low overhead
-- But always verify with EXPLAIN ANALYZE after enabling RLS on a production table

PgBouncer and session variables

PgBouncer in transaction mode breaks SET SESSION variables. In transaction pooling mode, the same server connection is shared across multiple client sessions between transactions. A SET SESSION app.tenant_id on one transaction would persist to the next client's transaction.

Always use SET LOCAL (or set_config(..., true)), which scopes the variable to the current transaction and is automatically reset when the transaction ends — safe with both session and transaction pooling.

-- SAFE with PgBouncer transaction pooling:
BEGIN;
SELECT set_config('app.tenant_id', 'a1b2c3d4-...', true);  -- LOCAL: resets on COMMIT/ROLLBACK
SELECT * FROM orders; -- RLS uses the locally-scoped variable
COMMIT; -- variable is cleared; connection returned to pool safely

-- UNSAFE with PgBouncer transaction pooling:
SET SESSION app.tenant_id = 'a1b2c3d4-...';  -- persists on the server connection!
-- Next client borrowing this connection inherits the previous tenant's variable

Real Production Incident

The tenant data leak: a missing WHERE clause exposed 3,000 customer records

Severity: P0 — Cross-tenant data exposure. Customer records from tenant A were visible to tenant B for approximately 20 minutes. GDPR notification required.

Context

B2B SaaS platform using shared-table multi-tenancy with application-layer tenant filtering. A new engineer added a "recently active customers" endpoint for the dashboard.

The Faulty Code

// New endpoint: returns last 10 active customers
// Engineer forgot to add tenant filter — looked reasonable in isolation
@GetMapping("/dashboard/recent-customers")
public List<CustomerDTO> getRecentCustomers() {
    // BUG: no tenant_id filter — returns customers from ALL tenants!
    return customerRepository.findTop10ByOrderByLastActiveAtDesc()
        .stream()
        .map(customerMapper::toDTO)
        .collect(toList());
}

// The JPA repository method generated this SQL:
// SELECT * FROM customers ORDER BY last_active_at DESC LIMIT 10
// No WHERE tenant_id = ?  ← data from all 47 tenants returned

Timeline

  09:15 — New feature deployed to production
  09:22 — Tenant "Acme Corp" user opens dashboard
           → sees 10 most recently active customers platform-wide
           → 7 of the 10 belong to different tenants
  09:31 — Acme Corp's admin notices unfamiliar customer names, emails support
  09:35 — Support ticket escalated to on-call engineer
  09:41 — Engineer identifies the missing WHERE clause
  09:42 — Hotfix deployed: added .findTop10ByTenantIdOrderByLastActiveAtDesc(tenantId)
  09:43 — Endpoint returns correct, scoped results
  09:45 — Incident declared resolved (data exposure window: ~20 min)
  10:30 — Post-mortem begins; GDPR team notified
  Next week — RLS enabled on customers table as preventive control

What Should Have Prevented This

-- If RLS had been active, the query would have been safe automatically:
-- Application query (no WHERE clause):
--   SELECT * FROM customers ORDER BY last_active_at DESC LIMIT 10

-- PostgreSQL with RLS enabled would execute:
--   SELECT * FROM customers
--   WHERE tenant_id = current_setting('app.tenant_id')::uuid  ← injected by policy
--   ORDER BY last_active_at DESC
--   LIMIT 10

-- The missing application filter is irrelevant — the DB enforces it regardless.

-- Enable RLS as the fix:
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;
ALTER TABLE customers FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON customers
    FOR ALL
    TO app_user
    USING  (tenant_id = current_setting('app.tenant_id')::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

Corrected Application Code

// After RLS: query is still safe even without explicit tenant filter
// (but best practice: keep the filter in application code AND rely on RLS)
@GetMapping("/dashboard/recent-customers")
public List<CustomerDTO> getRecentCustomers() {
    String tenantId = TenantContext.getTenantId(); // belt-and-suspenders
    return customerRepository
        .findTop10ByTenantIdOrderByLastActiveAtDesc(UUID.fromString(tenantId))
        .stream()
        .map(customerMapper::toDTO)
        .collect(toList());
}
// With RLS: even if tenantId filter is forgotten, DB policy catches it.
// Defence in depth: app layer filters + DB layer enforces.

Preventive Measures Added After Incident

  • RLS on all tenant-scoped tables — enabled as a mandatory architectural control, not optional.
  • Integration test suite — every repository test runs with a different tenant context and asserts cross-tenant data is invisible.
  • Code review checklist — PR template for new data-access methods requires a checkbox confirming tenant scoping is handled.
  • Static analysis rule — custom ArchUnit rule flags any JPA repository method that doesn't include TenantId in its name or that queries tables registered as tenant-scoped.

// ─── Entity ───────────────────────────────────────────────────
@Entity
@Table(name = "orders")
@IdClass(OrderId.class)  // composite PK: (tenant_id, id)
public class Order {

    @Id
    @Column(name = "tenant_id", nullable = false)
    private UUID tenantId;

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE,
                    generator = "orders_id_seq")
    @SequenceGenerator(name = "orders_id_seq",
                       sequenceName = "orders_id_seq",
                       allocationSize = 50)
    @Column(name = "id")
    private Long id;

    @Column(name = "customer_id", nullable = false)
    private Long customerId;

    @Column(name = "amount", nullable = false)
    private BigDecimal amount;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false)
    private OrderStatus status = OrderStatus.PENDING;

    @Column(name = "created_at", nullable = false, updatable = false)
    private OffsetDateTime createdAt = OffsetDateTime.now();

    // getters, setters, equals/hashCode omitted for brevity
}

// ─── Repository ────────────────────────────────────────────────
public interface OrderRepository extends JpaRepository<Order, OrderId> {

    // RLS ensures these only return current-tenant rows
    // — but keeping tenantId in the method name clarifies intent for reviewers
    List<Order> findByTenantIdAndStatus(UUID tenantId, OrderStatus status);

    @Query("SELECT o FROM Order o WHERE o.tenantId = :tenantId " +
           "AND o.createdAt BETWEEN :from AND :to " +
           "ORDER BY o.createdAt DESC")
    Page<Order> findByTenantIdInDateRange(
        @Param("tenantId") UUID tenantId,
        @Param("from") OffsetDateTime from,
        @Param("to") OffsetDateTime to,
        Pageable pageable
    );

    // Cross-tenant aggregate (used by admin service with app_admin role — BYPASSRLS)
    @Query(value = "SELECT tenant_id, COUNT(*) AS order_count, SUM(amount) AS total_revenue " +
                   "FROM orders WHERE created_at >= :since GROUP BY tenant_id",
           nativeQuery = true)
    List<Object[]> getRevenueByTenant(@Param("since") OffsetDateTime since);
}

// ─── Service ───────────────────────────────────────────────────
@Service
@Slf4j
public class OrderService {

    @Autowired private OrderRepository orderRepo;
    @Autowired private CustomerRepository customerRepo;

    @TenantScoped
    public Page<Order> listOrders(OrderFilter filter, Pageable pageable) {
        UUID tenantId = UUID.fromString(TenantContext.getTenantId());
        return orderRepo.findByTenantIdInDateRange(
            tenantId, filter.getFrom(), filter.getTo(), pageable);
    }

    @TenantScoped
    @Transactional
    public Order placeOrder(PlaceOrderRequest request) {
        UUID tenantId = UUID.fromString(TenantContext.getTenantId());

        // Verify customer belongs to this tenant (RLS also enforces this)
        Customer customer = customerRepo.findById(new CustomerId(tenantId, request.getCustomerId()))
            .orElseThrow(() -> new CustomerNotFoundException(request.getCustomerId()));

        Order order = new Order();
        order.setTenantId(tenantId);
        order.setCustomerId(customer.getId());
        order.setAmount(request.getAmount());
        order.setStatus(OrderStatus.PENDING);

        Order saved = orderRepo.save(order);
        log.info("Order {} placed for tenant {}", saved.getId(), tenantId);
        return saved;
    }
}
Schema migration runner for multiple tenants (database-per-tenant) 
// Runs Flyway migrations across all tenant databases on startup or via admin endpoint
@Service
@Slf4j
public class MultiTenantMigrationRunner {

    @Autowired
    private TenantRegistry tenantRegistry;

    @PostConstruct
    public void migrateAllTenants() {
        List<TenantConfig> tenants = tenantRegistry.getAllTenants();
        log.info("Starting migrations for {} tenants", tenants.size());

        List<String> failed = new ArrayList<>();

        for (TenantConfig tenant : tenants) {
            try {
                migrateOneTenant(tenant);
            } catch (Exception e) {
                log.error("Migration failed for tenant {}: {}", tenant.getTenantId(), e.getMessage());
                failed.add(tenant.getTenantId());
                // Don't rethrow — continue with remaining tenants
            }
        }

        if (!failed.isEmpty()) {
            throw new MigrationException("Migrations failed for tenants: " + failed);
        }
        log.info("All tenant migrations completed successfully");
    }

    private void migrateOneTenant(TenantConfig tenant) {
        Flyway flyway = Flyway.configure()
            .dataSource(tenant.getJdbcUrl(), tenant.getDbUsername(), tenant.getDbPassword())
            .schemas(tenant.getSchema()) // for schema-per-tenant; omit for DB-per-tenant
            .locations("classpath:db/migration")
            .baselineOnMigrate(true)
            .outOfOrder(false)
            .validateOnMigrate(true)
            .load();

        MigrateResult result = flyway.migrate();
        log.info("Tenant {}: {} migrations applied (current version: {})",
            tenant.getTenantId(),
            result.migrationsExecuted,
            result.targetSchemaVersion);
    }
}

Common Mistakes

The mistakes interviewers are looking for you to know
#MistakeImpactFix
1 Using SET SESSION instead of SET LOCAL for tenant variable Previous tenant's ID leaks to next request via pooled connection Always use set_config('app.tenant_id', ?, true) (is_local = true)
2 Not calling FORCE ROW LEVEL SECURITY Table owner (often the migration user) bypasses all policies silently Always pair ENABLE with FORCE ROW LEVEL SECURITY
3 Missing tenant_id as the leading column in indexes Seq scans on large shared tables; all-tenant data read then filtered All indexes on tenant-scoped tables start with (tenant_id, ...)
4 Not setting app.tenant_id before a query runs (e.g., in background jobs) RLS policy returns NULL from current_setting — all rows filtered out or error thrown Background jobs must set tenant context explicitly before each tenant's work unit
5 Cross-tenant foreign keys in shared-table model FK from orders.customer_id to customers.id (without tenant_id) allows cross-tenant references Use composite FKs: FOREIGN KEY (tenant_id, customer_id) REFERENCES customers(tenant_id, id)
6 Not validating tenant identifier in schema-per-tenant before interpolation SQL injection via malicious tenant slug in SET search_path TO {tenant} Validate with strict regex ^[a-z0-9_]{1,63}$ before use; prefer allowlist from DB
7 Applying RLS after data is already in production Rows with NULL tenant_id become invisible to all users — silent data loss Backfill all NULLs, add NOT NULL constraint, then enable RLS; test with all roles first
8 Not testing RLS with the correct application role Tests pass because they run as the table owner (BYPASSRLS) — policies never actually tested Run tests under SET ROLE app_user to simulate actual application permissions

Follow-up Interview Questions

Questions the interviewer will ask next
Q: "How would you handle a tenant that suddenly grows to 10× normal data volume and starts degrading other tenants' performance?"
This is the "noisy neighbor" problem. Short-term: identify the tenant via pg_stat_activity filtered by app.tenant_id in query text; use pg_cancel_backend to kill runaway queries. Medium-term: add query-level resource limits with statement_timeout and lock_timeout per application role. Long-term: migrate that tenant to a dedicated database (which is why the routing layer should support this without code changes). Also consider table partitioning by tenant_id so heavy tenants don't bloat shared autovacuum jobs.
Q: "How would you implement a feature where tenant admins can grant other users in their tenant elevated access?"
Extend the session context to include a user role: set_config('app.user_role', 'admin', true). Modify RLS policies to check both tenant_id and user_role: USING (tenant_id = current_setting('app.tenant_id')::uuid AND (owner_id = ... OR current_setting('app.user_role') = 'admin')). The JWT claim carries both tenant_id and the user's role within that tenant. Never trust the client to provide these — always derive from the server-side JWT or session.
Q: "How would you support cross-tenant data sharing (e.g., a shared vendor catalog)?"
Use a separate table without tenant_id for truly global data (e.g., global_products) and don't enable RLS on it. For partial sharing (tenant A shares specific records with tenant B), add a shared_with_tenant_id column or a separate join table, and write a PERMISSIVE policy alongside the tenant isolation RESTRICTIVE policy. The key is to separate "what you own" from "what is shared with you" at the schema level, not just the application level.
Q: "How would you perform a GDPR 'right to erasure' request in a shared-table model?"
Use the app_admin role (BYPASSRLS) to delete or anonymize all rows where tenant_id = ? across all tables. The challenge is referential integrity — use cascading deletes or process tables in dependency order. For "soft" erasure (pseudonymization), update PII fields to a hashed value rather than deleting rows, which preserves aggregate metrics without personal data. Log the erasure event in an audit table with the timestamp and requestor.
Q: "What happens to RLS when you use read replicas for reporting queries?"
RLS policies are replicated to standby servers. The policy still executes on the replica when a query runs there. However, the app.tenant_id session variable must be set on the replica's connection just as on the primary. If you route reporting queries to a read replica via a separate DataSource, ensure the same TenantAwareDataSource wrapper applies set_config on replica connections too.
Q: "How would you audit which tenant accessed what data?"
Use PostgreSQL's pgaudit extension to log all DML statements with session context (which captures the app.tenant_id variable). Alternatively, write a BEFORE trigger on sensitive tables that inserts into an audit log, capturing the current tenant from current_setting, the operation type, row old/new values, and a timestamp. Store audit logs in a separate schema with APPEND-ONLY access to prevent tampering.

Summary

Interview Takeaways:

  1. There are three multi-tenancy strategies: database-per-tenant (strongest isolation, highest cost), schema-per-tenant (balanced), and shared tables (cheapest, scales to 100k+ tenants). Choose based on tenant count, compliance, and budget.
  2. Shared-table is the most common in modern SaaS — but it requires rigorous tenant filtering. Every table needs a tenant_id column and every query must filter by it.
  3. Row-Level Security is a database-level safety net, not a replacement for application-layer filtering. Use both: app code for performance clarity, RLS as the enforcement backstop that prevents data leaks from bugs.
  4. Always use SET LOCAL / set_config(..., true) to scope the tenant variable to the current transaction — never SET SESSION, which leaks across pooled connections.
  5. Call FORCE ROW LEVEL SECURITY — without it, the table owner bypasses all policies silently.
  6. Lead all indexes with tenant_id. An index on (status) is useless in a shared-table model; (tenant_id, status) enables efficient per-tenant scans.
  7. Use composite primary keys (tenant_id, id) and composite foreign keys to prevent cross-tenant references at the constraint level.
  8. Test RLS by setting SET ROLE app_user in test transactions — the table owner bypasses RLS and will give you false confidence that policies work.
  9. For large tenants or compliance-heavy customers, build your architecture to support hybrid tiering: route enterprise tenants to dedicated databases without application code changes.

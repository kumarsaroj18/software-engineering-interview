Hard Concurrency Locking

Why Might Optimistic Locking Still Fail in a High-Concurrency Environment?

Key Takeaway: Optimistic locking assumes low contention. When many threads compete for the same rows, version-check failures trigger retry storms → retry amplification exhausts connection pools → pool exhaustion cascades to unrelated endpoints → full system unavailability. For true hot-spot resources, pessimistic locking or queue-based serialization avoids this failure mode entirely.

Interviewer Intent

What the interviewer is really asking

This question tests whether you understand the limits of optimistic concurrency control — not just how it works, but when it breaks down. Senior engineers must demonstrate:

  • Deep understanding of CAS-like semantics — Conditional updates at the database level via version columns.
  • Failure-mode reasoning — Knowing that "no locks" doesn't mean "no contention."
  • Quantitative thinking — Can you estimate retry rates given N concurrent writers on M hot rows?
  • Solution repertoire — Ability to pivot to pessimistic locking, partitioning, event sourcing, or queue serialization when optimistic locking becomes a liability.
  • Production experience — Real war stories of optimistic locking meltdowns (flash sales, counter increments, inventory deductions).
  • Trade-off articulation — Explaining why you'd choose one strategy over another for a given workload profile.

The interviewer wants to see that you don't blindly apply optimistic locking as a "best practice" but can reason about when it becomes an anti-pattern.

Quick Answer

30-second elevator pitch

Optimistic locking uses a version column (or conditional update) to detect concurrent modifications at commit time. It works well under low contention because most transactions succeed on the first attempt. However, in high-concurrency environments — especially with hot rows like inventory counters or wallet balances — the probability of version conflicts rises rapidly — driven by contention level, transaction duration, arrival rate, and overlap window. Each failed transaction must retry, creating a retry storm that amplifies load. The result: higher latency, wasted work, potential livelock, and in extreme cases, retry amplification can exhaust connection pools and cascade into full system unavailability. Solutions include pessimistic locking for known hot rows, partitioned counters, SELECT FOR UPDATE SKIP LOCKED for queue-like workloads, or moving to event sourcing where conflicts are resolved at the domain level.

Optimistic vs Pessimistic Locking

How optimistic locking works — JPA @Version, CAS, and the lost update problem

The Optimistic Locking Model

Optimistic locking is a concurrency control strategy that assumes conflicts are rare. Instead of acquiring a lock before reading, it allows all readers to proceed and checks for conflicts only at write time.

┌─────────────────────────────────────────────────────────────────┐
│                   OPTIMISTIC LOCKING FLOW                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Thread A                          Thread B                      │
│  ────────                          ────────                      │
│  1. SELECT item WHERE id=42        1. SELECT item WHERE id=42    │
│     → version = 5, qty = 100         → version = 5, qty = 100   │
│                                                                  │
│  2. Business logic: qty - 1        2. Business logic: qty - 1    │
│     → new qty = 99                    → new qty = 99             │
│                                                                  │
│  3. UPDATE item                    3. UPDATE item                │
│     SET qty=99, version=6             SET qty=99, version=6      │
│     WHERE id=42 AND version=5         WHERE id=42 AND version=5  │
│     → rows affected = 1 ✓            → rows affected = 0 ✗      │
│                                       → OptimisticLockException  │
│                                                                  │
│  Result: qty=99, version=6         Must RETRY from step 1        │
└─────────────────────────────────────────────────────────────────┘

JPA @Version Annotation

In JPA/Hibernate, optimistic locking is implemented via the @Version annotation:

@Entity
@Table(name = "inventory_item")
public class InventoryItem {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Version
    private Long version;

    private String sku;
    private int quantity;
    private BigDecimal price;

    // When Hibernate flushes, it generates:
    // UPDATE inventory_item
    //   SET quantity = ?, version = version + 1
    //   WHERE id = ? AND version = ?
    // If 0 rows updated → throws OptimisticLockException
}

Conditional Update (CAS-Like) Semantics

Optimistic locking follows the same principle as Compare-And-Swap: it performs a conditional UPDATE that succeeds only if the version matches the previously observed value. Unlike hardware CAS, this is implemented via SQL WHERE clauses:

-- Conditional update pattern: succeeds only if current state matches expected state
UPDATE account
SET balance = balance - 100.00,
    version = version + 1
WHERE id = :accountId
  AND version = :expectedVersion;

-- Check rows affected
-- If 0 → someone else modified the row → retry or abort

The Lost Update Problem (Without Locking)

Without any locking, you get the classic lost update:

┌────────────────────────────────────────────────────────┐
│              LOST UPDATE (NO LOCKING)                   │
├────────────────────────────────────────────────────────┤
│                                                         │
│  Initial: balance = $1000                               │
│                                                         │
│  Thread A: withdraw $200       Thread B: withdraw $300  │
│  READ  balance → $1000        READ  balance → $1000    │
│  CALC  $1000 - $200 = $800    CALC  $1000 - $300 = $700│
│  WRITE balance = $800         WRITE balance = $700      │
│                                                         │
│  Final: balance = $700 (lost $200 withdrawal!)          │
│  Expected: balance = $500                               │
└────────────────────────────────────────────────────────┘

Optimistic locking detects this conflict. Pessimistic locking prevents it. The choice between them depends on contention levels.

When Optimistic Locking Shines

Characteristic Optimistic Pessimistic
Lock acquisition cost None (check at commit) Lock overhead per read
Throughput under low contention High Lower (lock waits)
Deadlock risk None Possible
Scalability Excellent when conflicts rare Limited by lock granularity
Failure mode Retry storm under contention Timeout/deadlock detection

Why Optimistic Locking Fails Under High Concurrency

All failure scenarios — retry storms, hot rows, long transactions, ABA problem

Core insight: Under high concurrency, optimistic locking's conflict rate increases rapidly with the number of concurrent writers on the same row. With N simultaneous writers, at most 1 succeeds per round — giving a worst-case failure rate of (N-1)/N per attempt.

Failure Scenario 1: Hot Rows

When many transactions target the same row (inventory counter, account balance, global sequence), the version number becomes a serialization bottleneck — except without the fairness guarantees of actual serialization.

// Example: 1000 concurrent requests all decrementing the same inventory row
// Round 1: 1000 attempt, 1 succeeds, 999 fail → retry
// Round 2: 999 attempt, 1 succeeds, 998 fail → retry
// Round 3: 998 attempt, 1 succeeds, 997 fail → retry
// ...
// Total attempts: 1000 + 999 + 998 + ... + 1 = 500,500 attempts for 1000 updates
// Wasted work: 499,500 failed attempts (99.8% waste)

Failure Scenario 2: Long Transactions

The longer a transaction holds its read version, the higher the probability that another transaction will commit first. Conflict probability increases with:

  • Transaction duration (Δt): Longer read-to-commit windows give more opportunity for other writers to intervene.
  • Write rate (λ): Higher arrival rate of writes to the same row means more competition per unit time.
  • Number of concurrent writers (N): More active writers increase the chance of overlap.
┌──────────────────────────────────────────────────────────────┐
│           LONG TRANSACTION FAILURE — QUALITATIVE              │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  Short tx (5ms) + few writers (3)   → conflict rare          │
│  Short tx (5ms) + many writers (100) → conflict likely       │
│  Long tx (500ms) + few writers (3)   → conflict moderate     │
│  Long tx (500ms) + many writers (50) → conflict near certain │
│                                                               │
│  Rule of thumb: if (write_rate × tx_duration × writers)      │
│  is large, optimistic locking will produce excessive retries.│
│                                                               │
│  Key insight: You can reduce conflicts by shortening          │
│  transactions (move non-DB work outside the tx) or by         │
│  reducing the number of writers targeting the same row.       │
└──────────────────────────────────────────────────────────────┘

Failure Scenario 3: Non-Monotonic Version Identifiers

With standard numeric version counters (the JPA default), each update strictly increments the version, so a stale read can never accidentally match a future version. However, if you use a non-monotonic versioning scheme — such as content hashes or certain timestamp representations — values can theoretically repeat, allowing a stale check to succeed incorrectly:

// Why monotonically increasing versions avoid this:
// version: 1 → 2 → 3 → 4 → ...
// A stale reader holding version=2 can never accidentally match version=4
// because version only ever moves forward.

// Risk with content-hash or checksum-based versioning:
// If version = hash(mutable_fields_only), the hash could repeat
// when a row is modified and then reverted to its original values.
// This is uncommon in practice but a design consideration.

// Best practice: Always use a monotonically increasing numeric version.
// If you need to detect specific state, add a separate audit/event trail.

Interview context: Interviewers rarely ask about ABA in the context of JPA optimistic locking specifically, since @Version uses monotonic increments by default. However, you may be asked about it in distributed systems where version tokens are UUIDs, vector clocks, or Lamport timestamps — in those contexts, ensuring monotonicity is a real design concern.

Failure Scenario 4: Version Field Not Checked in All Paths

A common bug: some code paths update the row without checking the version, bypassing optimistic locking entirely.

// DANGEROUS: Native query bypasses @Version check
@Modifying
@Query("UPDATE InventoryItem SET quantity = :qty WHERE id = :id")
void unsafeUpdate(@Param("id") Long id, @Param("qty") int qty);
// This DOES NOT check version! Lost updates guaranteed.

// ALSO DANGEROUS: Bulk JPQL/HQL updates bypass the persistence context
// and @Version checks entirely, even though they look like "managed" JPA code.
@Modifying
@Query("UPDATE InventoryItem i SET i.quantity = i.quantity - 1 WHERE i.id = :id")
void bulkDecrement(@Param("id") Long id);
// No version check, no OptimisticLockException — behaves like native SQL.

// SAFE: Let JPA manage the version
@Transactional
public void safeUpdate(Long id, int newQty) {
    InventoryItem item = repository.findById(id)
        .orElseThrow();
    item.setQuantity(newQty);
    // JPA flush will include: WHERE version = :readVersion
}

Failure Scenario 5: Read-Your-Writes Violations in Replicated Databases

With read replicas, you might read a stale version from a replica and then write to the primary:

┌──────────────────────────────────────────────────────────────┐
│        REPLICA LAG + OPTIMISTIC LOCKING = CONFUSION          │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  Primary (version=7)     Replica (version=5, lagging)        │
│  ──────────────────      ────────────────────────────        │
│                                                               │
│  Thread A:                                                    │
│  1. READ from replica → version=5                            │
│  2. UPDATE on primary WHERE version=5 → FAILS (actual is 7)  │
│                                                               │
│  Thread A sees a "conflict" that isn't a real conflict —     │
│  it's just stale reads. This causes unnecessary retries.      │
│                                                               │
│  Fix: Read from primary for rows you intend to update,       │
│       or use session-sticky routing.                          │
└──────────────────────────────────────────────────────────────┘

Failure Scenario 6: Phantom Conflicts from Unrelated Field Updates

A single @Version per entity means any field change bumps the version — even unrelated fields:

// Thread A: updates item.description (cosmetic change)
// Thread B: updates item.quantity (critical business logic)
// Both read version=5 → one will fail, even though they touched different fields

// Solution: Use field-level optimistic locking (Hibernate @OptimisticLock)
// NOTE: @OptimisticLock is Hibernate-specific, NOT part of the JPA standard.
// If portability across JPA providers matters, this approach won't transfer.
@Entity
public class InventoryItem {
    @Version
    private Long version;

    @OptimisticLock(excluded = true) // Hibernate-only annotation
    private String description;

    @OptimisticLock(excluded = true) // Hibernate-only annotation
    private LocalDateTime lastViewedAt;

    // Only quantity and price changes trigger version increment
    private int quantity;
    private BigDecimal price;
}

Portability note: @org.hibernate.annotations.OptimisticLock(excluded = true) is a Hibernate-specific extension. Standard JPA does not support field-level version exclusion. Use this judiciously and document which fields are excluded, as it can silently allow concurrent writes to those fields without conflict detection.

Retry Storms and Thundering Herd

How retry amplification turns optimistic locking into a denial-of-service on your own database

The fundamental problem: When an optimistic lock fails, the standard advice is "just retry." But under high contention, retries create more contention, which creates more failures, which creates more retries — a positive feedback loop.

Worst-Case Model of Retry Amplification

┌──────────────────────────────────────────────────────────────┐
│         RETRY AMPLIFICATION MODEL (WORST CASE)                │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  Assumptions: N writers arrive simultaneously, contend for    │
│  the same row, exactly 1 succeeds per round, all others      │
│  retry immediately. Real-world behavior is better due to      │
│  staggered arrivals and backoff, but this bounds the worst    │
│  case.                                                        │
│                                                               │
│  Round 1: N attempts → 1 success, (N-1) retries              │
│  Round 2: (N-1) attempts → 1 success, (N-2) retries          │
│  Round 3: (N-2) attempts → 1 success, (N-3) retries          │
│  ...                                                          │
│  Round k: (N-k+1) attempts → 1 success                       │
│                                                               │
│  Total attempts = N + (N-1) + (N-2) + ... + 1 = N(N+1)/2    │
│  Total wasted = N(N+1)/2 - N = N(N-1)/2                     │
│                                                               │
│  For N=100:  Total attempts = 5,050 (50x amplification)      │
│  For N=1000: Total attempts = 500,500 (500x amplification)   │
│  For N=10000: Total attempts = 50,005,000 (5000x!)           │
│                                                               │
│  Worst-case latency for last writer: N rounds × tx_time      │
│  With tx_time=50ms, N=1000: last writer waits ~50 seconds    │
└──────────────────────────────────────────────────────────────┘

Thundering Herd Effect

When a retry fires, it doesn't fire alone. If 999 transactions failed simultaneously, they all retry at roughly the same time (especially with fixed-delay retries):

// ANTI-PATTERN: Fixed-delay retry causes thundering herd
@Retryable(value = OptimisticLockException.class, maxAttempts = 5,
           backoff = @Backoff(delay = 100)) // All 999 retry at t+100ms!
public void decrementInventory(Long itemId) {
    InventoryItem item = repo.findById(itemId).orElseThrow();
    item.setQuantity(item.getQuantity() - 1);
    repo.save(item); // flush triggers version check
}

// The thundering herd timeline:
// t=0ms:    1000 concurrent requests arrive
// t=50ms:   1 succeeds, 999 get OptimisticLockException
// t=150ms:  999 retry simultaneously → 1 succeeds, 998 fail
// t=250ms:  998 retry simultaneously → 1 succeeds, 997 fail
// ... system under sustained maximum load for 50+ seconds

CPU and I/O Waste

Each failed-and-retried transaction wastes:

  • Database I/O: SELECT (read), UPDATE attempt (write), rollback
  • Network round-trips: 2-3 per failed attempt
  • Connection pool slots: Held during the entire retry cycle
  • Application CPU: Business logic re-computation, serialization/deserialization
  • GC pressure: Short-lived objects from failed transactions

Connection Pool Exhaustion

│            CONNECTION POOL DEATH SPIRAL                        │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  Pool size: 20 connections                                    │
│  Retry delay: 100ms                                           │

│  1. 20 connections in use for first batch                     │

│  4. Retry requests + waiting requests fight for 20 slots     │

Livelock vs Deadlock

Pessimistic locking risks deadlock (two transactions wait for each other forever). Optimistic locking risks livelock (transactions keep retrying but never succeed due to constant interference). Livelock is harder to detect because the system appears "busy" — threads are running, queries are executing — but no useful work completes.

// Livelock scenario: Two threads repeatedly conflict
// Thread A and Thread B both update rows X and Y
// Round 1: A updates X (v1→v2), B updates Y (v1→v2)
//          A tries Y (expects v1, actual v2) → FAIL
//          B tries X (expects v1, actual v2) → FAIL
// Round 2: A reads X(v2),Y(v2), B reads X(v2),Y(v2)
//          A updates X (v2→v3), B updates X (v2→v3) → one fails
//          ... cycle continues indefinitely without jitter

Solutions for High-Contention Scenarios

Pessimistic locking, partitioning, event sourcing, queue serialization, SKIP LOCKED

Solution 1: Pessimistic Locking for Known Hot Rows

When you know a row is hot, acquire the lock upfront to serialize access and eliminate wasted retries:

@Repository
public interface InventoryRepository extends JpaRepository<InventoryItem, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT i FROM InventoryItem i WHERE i.id = :id")
    Optional<InventoryItem> findByIdForUpdate(@Param("id") Long id);
}

@Service
@Transactional
public class InventoryService {

    public boolean decrementStock(Long itemId) {
        // Acquires SELECT ... FOR UPDATE — serializes writers
        InventoryItem item = inventoryRepo.findByIdForUpdate(itemId)
            .orElseThrow(() -> new ItemNotFoundException(itemId));

        if (item.getQuantity() <= 0) {
            return false; // Out of stock
        }

        item.setQuantity(item.getQuantity() - 1);
        return true;
        // Lock released at transaction commit
    }
}

Trade-off: Pessimistic locking serializes access (lower throughput under low contention) but avoids retry amplification by serializing access to the row — each writer waits in line rather than racing and failing. Transactions may still timeout or deadlock, but you eliminate the N(N+1)/2 wasted-attempt problem.

Solution 2: SELECT FOR UPDATE SKIP LOCKED

For queue-like workloads where any available row will do, SKIP LOCKED avoids blocking on locked rows:

-- Worker pattern: grab the next available task
-- Each worker gets a different unlocked row — no contention!
SELECT id, payload, status
FROM task_queue
WHERE status = 'PENDING'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- If all pending rows are locked by other workers, returns empty set
-- Worker can sleep and retry later — no blocking, no exceptions
@Repository
public interface TaskQueueRepository extends JpaRepository<Task, Long> {

    @Query(value = """
        SELECT * FROM task_queue
        WHERE status = 'PENDING'
        ORDER BY created_at
        LIMIT 1
        FOR UPDATE SKIP LOCKED
        """, nativeQuery = true)
    Optional<Task> findNextAvailableTask();
}

@Service
public class TaskWorker {

    @Transactional
    public Optional<Task> processNext() {
        return taskRepo.findNextAvailableTask()
            .map(task -> {
                task.setStatus(TaskStatus.PROCESSING);
                task.setWorkerNode(nodeId);
                task.setStartedAt(Instant.now());
                return taskRepo.save(task);
            });
    }
}

Solution 3: Partitioned Counters

Split one hot counter into N shards to reduce per-shard contention by a factor of N:

@Entity
@Table(name = "inventory_shard")
public class InventoryShard {
    @Id
    private Long id;
    private Long itemId;
    private int shardIndex;  // 0..N-1
    private int quantity;    // This shard's allocation

    @Version
    private Long version;
}

@Service
public class ShardedInventoryService {

    private static final int SHARD_COUNT = 16;

    @Transactional
    public boolean decrementStock(Long itemId) {
        // Pick a random shard to reduce collision probability
        int shard = ThreadLocalRandom.current().nextInt(SHARD_COUNT);

        Optional<InventoryShard> shardOpt = shardRepo
            .findByItemIdAndShardIndex(itemId, shard);

        if (shardOpt.isPresent() && shardOpt.get().getQuantity() > 0) {
            shardOpt.get().setQuantity(shardOpt.get().getQuantity() - 1);
            return true;
        }

        // This shard is empty — try others
        for (int i = 0; i < SHARD_COUNT; i++) {
            if (i == shard) continue;
            Optional<InventoryShard> alt = shardRepo
                .findByItemIdAndShardIndex(itemId, i);
            if (alt.isPresent() && alt.get().getQuantity() > 0) {
                alt.get().setQuantity(alt.get().getQuantity() - 1);
                return true;
            }
        }
        return false; // Truly out of stock
    }

    public int getTotalStock(Long itemId) {
        return shardRepo.sumQuantityByItemId(itemId); // SELECT SUM(quantity)
    }
}

Solution 4: Event Sourcing

Instead of updating a mutable row, append immutable events. This reduces update conflicts on mutable rows, though optimistic concurrency may still be enforced at the event stream level (e.g., EventStoreDB and Axon use expected stream versions to prevent conflicting appends):

// Appending events reduces row-level contention compared to UPDATE-based approaches.
// However, event stores typically enforce an expected stream version on append
// to prevent two writers from appending conflicting events to the same aggregate.
@Entity
@Table(name = "inventory_event")
public class InventoryEvent {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long eventId;      // Monotonically increasing

    private Long itemId;
    private String eventType;  // STOCK_ADDED, STOCK_RESERVED, STOCK_RELEASED
    private int quantityDelta; // +10, -1, +1
    private Instant occurredAt;
    private String correlationId;
}

@Service
public class EventSourcedInventoryService {

    @Transactional
    public boolean reserveStock(Long itemId, String orderId) {
        // Calculate current stock from events (or use materialized view)
        int currentStock = eventRepo.sumDeltaByItemId(itemId);

        if (currentStock <= 0) {
            return false;
        }

        // Append event — INSERT rather than UPDATE on mutable state,
        // reducing (but not eliminating) contention compared to row-level locking
        InventoryEvent event = new InventoryEvent();
        event.setItemId(itemId);
        event.setEventType("STOCK_RESERVED");
        event.setQuantityDelta(-1);
        event.setOccurredAt(Instant.now());
        event.setCorrelationId(orderId);
        eventRepo.save(event);
        return true;
    }
    // Note: You still need a constraint to prevent overselling!
    // Use a CHECK constraint or serializable isolation on the projection table.
}

Solution 5: Queue-Based Serialization

Funnel all writes through a single-threaded consumer to eliminate contention entirely:

// Producer: publish intent to a queue (fast, non-blocking)
@Service
public class InventoryRequestPublisher {

    private final KafkaTemplate<String, InventoryCommand> kafka;

    public CompletableFuture<Boolean> requestDecrement(Long itemId, String orderId) {
        InventoryCommand cmd = new InventoryCommand(itemId, -1, orderId);
        // Partition by itemId → all writes for same item go to same partition
        // → single consumer thread processes them sequentially
        kafka.send("inventory-commands", String.valueOf(itemId), cmd);
        return pendingResults.register(orderId); // Await async result
    }
}

// Consumer: single-threaded per partition → no contention
// IMPORTANT: This guarantee requires:
//   1. Messages partitioned by itemId (same key → same partition)
//   2. Exactly one consumer per partition (concurrency = partition count)
//   3. No consumer rebalancing mid-processing
// If any of these assumptions are violated, concurrent updates can still occur.
@KafkaListener(topics = "inventory-commands", concurrency = "1")
public void handleCommand(InventoryCommand cmd) {
    // Only one thread ever updates this item (given correct partitioning) → no lock needed
    InventoryItem item = repo.findById(cmd.getItemId()).orElseThrow();
    if (item.getQuantity() + cmd.getDelta() >= 0) {
        item.setQuantity(item.getQuantity() + cmd.getDelta());
        repo.save(item);
        resultPublisher.publish(cmd.getOrderId(), true);
    } else {
        resultPublisher.publish(cmd.getOrderId(), false);
    }
}

How Hibernate Implements @Version

When you annotate a field with @Version, Hibernate automatically:

  1. Includes WHERE version = :readVersion in every UPDATE/DELETE
  2. Increments the version on successful flush
  3. Throws OptimisticLockException if 0 rows were affected
@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Version
    private Integer version; // Supports int, Integer, long, Long, short, Short, Timestamp

    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    private BigDecimal totalAmount;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderLine> lines = new ArrayList<>();
}

// Generated SQL on flush:
// UPDATE orders
// SET status='CONFIRMED', total_amount=99.99, version=4
// WHERE id=123 AND version=3
//
// If rows_affected == 0:
//   Hibernate throws StaleObjectStateException(entityName, id)
//   which the JPA layer wraps as javax.persistence.OptimisticLockException

Version Field Types

Type Increment Strategy Notes
int / Integer +1 per flush Most common, wraps at Integer.MAX_VALUE
long / Long +1 per flush Recommended for high-write entities
short / Short +1 per flush Wraps at 32767 — avoid for production
Timestamp Current time per flush Clock skew issues, millisecond granularity

Caution with Timestamp versions: Timestamp-based @Version fields are susceptible to precision issues (two commits within the same millisecond resolution), clock skew in distributed environments, and inconsistent behavior across JPA providers and databases. Prefer numeric versions for reliable conflict detection.

Proper Exception Handling

@Service
@Slf4j
public class OrderService {

    private final OrderRepository orderRepo;
    private final MeterRegistry metrics;

    /**
     * Confirms an order with optimistic locking and retry.
     * Catches the specific exception hierarchy correctly.
     */
    @Transactional
    public Order confirmOrder(Long orderId) {
        try {
            Order order = orderRepo.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));

            order.setStatus(OrderStatus.CONFIRMED);
            order.setConfirmedAt(Instant.now());
            return orderRepo.saveAndFlush(order); // Force immediate flush

        } catch (OptimisticLockException e) {
            // JPA standard exception
            metrics.counter("order.optimistic_lock.failure").increment();
            throw new ConcurrentModificationException(
                "Order " + orderId + " was modified concurrently", e);

        } catch (StaleObjectStateException e) {
            // Hibernate-specific (caught before wrapping in some configurations)
            metrics.counter("order.optimistic_lock.failure").increment();
            throw new ConcurrentModificationException(
                "Order " + orderId + " version mismatch", e);
        }
    }
}

Retry with Exponential Backoff and Jitter

@Service
@Slf4j
public class ResilientInventoryService {

    private static final int MAX_RETRIES = 5;
    private static final long BASE_DELAY_MS = 50;
    private static final long MAX_DELAY_MS = 2000;
    // NOTE: There is no universally correct retry count.
    // Choose based on: contention level (how many concurrent writers?),
    // SLA requirements (max acceptable latency?), and whether the operation
    // is idempotent (safe to repeat without side effects?).

    private final InventoryRepository inventoryRepo;
    private final MeterRegistry metrics;
    private final TransactionTemplate txTemplate;

    /**
     * Decrements stock with retry + exponential backoff + jitter.
     * Each retry starts a NEW transaction (critical!).
     */
    public boolean decrementWithRetry(Long itemId) {
        for (int attempt = 1; attempt <= MAX_RETRIES; attempt++) {
            try {
                Boolean result = txTemplate.execute(status -> {
                    InventoryItem item = inventoryRepo.findById(itemId)
                        .orElseThrow();
                    if (item.getQuantity() <= 0) return false;
                    item.setQuantity(item.getQuantity() - 1);
                    inventoryRepo.saveAndFlush(item);
                    return true;
                });
                metrics.counter("inventory.decrement.success",
                    "attempt", String.valueOf(attempt)).increment();
                return Boolean.TRUE.equals(result);

            } catch (OptimisticLockException | CannotAcquireLockException e) {
                // OptimisticLockException = version mismatch (optimistic conflict)
                // CannotAcquireLockException = lock acquisition timeout (typically
                //   from pessimistic locks or deadlock detection). These are different
                //   failure modes but both may warrant a retry with a fresh transaction.
                metrics.counter("inventory.decrement.retry",
                    "attempt", String.valueOf(attempt),
                    "exception", e.getClass().getSimpleName()).increment();

                if (attempt == MAX_RETRIES) {
                    log.error("Failed to decrement item {} after {} attempts",
                        itemId, MAX_RETRIES);
                    throw new StockDecrementFailedException(itemId, e);
                }

                long delay = calculateBackoff(attempt);
                log.warn("Optimistic lock conflict on item {}, attempt {}/{}, "
                    + "retrying in {}ms", itemId, attempt, MAX_RETRIES, delay);
                sleep(delay);
            }
        }
        return false; // Unreachable
    }

    /**
     * Exponential backoff with full jitter (AWS-recommended approach).
     * delay = random_between(0, min(cap, base * 2^attempt))
     */
    private long calculateBackoff(int attempt) {
        long exponentialDelay = Math.min(MAX_DELAY_MS,
            BASE_DELAY_MS * (1L << attempt));
        // Full jitter: random between 0 and the exponential delay
        return ThreadLocalRandom.current().nextLong(0, exponentialDelay + 1);
    }

    private void sleep(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("Interrupted during retry backoff", e);
        }
    }
}

Critical: Each retry must execute in a new transaction. If you retry within the same transaction, the EntityManager is already in a dirty state and will throw on flush. Use TransactionTemplate or @Transactional(propagation = REQUIRES_NEW) on the inner method.

The Fix: Multi-Layered Approach

/**
 * Post-incident architecture for flash sales:
 * 1. Pre-allocated tokens (Redis) — rate limit at the edge
 * 2. Pessimistic locking with timeout — serialize the critical path
 * 3. Queue-based ordering — decouple request from processing
 */
@Service
public class FlashSaleService {

    private final RedisTemplate<String, String> redis;
    private final InventoryRepository inventoryRepo;

    /**
     * Layer 1: Redis atomic decrement as a fast pre-check.
     * Only allows up to N requests through to the database.
     */
    public boolean tryAcquireToken(String saleId) {
        String key = "flash-sale:" + saleId + ":remaining";
        Long remaining = redis.opsForValue().decrement(key);
        if (remaining != null && remaining >= 0) {
            return true; // Token acquired
        }
        // Restore the count if we went negative
        redis.opsForValue().increment(key);
        return false; // Sold out at Redis layer
    }

    /**
     * Layer 2: Only token holders reach the database.
     * Use pessimistic lock since we KNOW this is a hot row.
     */
    @Transactional(timeout = 5) // 5-second timeout to prevent indefinite blocking
    public PurchaseResult completePurchase(Long itemId, Long userId) {
        InventoryItem item = inventoryRepo.findByIdForUpdate(itemId)
            .orElseThrow();

        if (item.getQuantity() <= 0) {
            return PurchaseResult.SOLD_OUT;
        }

        item.setQuantity(item.getQuantity() - 1);
        inventoryRepo.save(item);

        // Create order record
        orderService.createOrder(userId, itemId);
        return PurchaseResult.SUCCESS;
    }
}

// SET flash-sale:summer2024:remaining 100
// This ensures at most 100 requests ever hit the database

Exponential backoff with jitter for retry 
public class RetryWithBackoff {

    public <T> T executeWithRetry(Supplier<T> operation,
                                    int maxRetries,
                                    long baseDelayMs) {
        int attempt = 0;
        while (true) {
            try {
                return operation.get();
            } catch (OptimisticLockingFailureException e) {
                attempt++;
                if (attempt >= maxRetries) {
                    throw new RetriesExhaustedException(
                        "Failed after " + maxRetries + " attempts", e);
                }
                // Exponential backoff with full jitter
                long maxDelay = baseDelayMs * (1L << attempt); // 2^attempt * base
                long delay = ThreadLocalRandom.current().nextLong(0, maxDelay);
                try {
                    Thread.sleep(delay);
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    throw new RuntimeException("Retry interrupted", ie);
                }
            }
        }
    }
}

Common Mistakes

Mistakes that make optimistic locking worse in production

Mistake 1: Retrying without backoff or jitter

The mistake: Immediate retry on OptimisticLockingFailureException with no delay.

Why it fails: All conflicting threads retry simultaneously, causing the same conflict again (thundering herd). Exponential backoff with random jitter is essential to spread retries across time.

Mistake 2: Using optimistic locking on hot rows

The mistake: Using @Version on a row that thousands of requests update per second (global counter, inventory of a viral product).

Why it fails: Conflict rate approaches 100%. The retry amplification (N(N+1)/2 total attempts for N concurrent requests) creates a self-inflicted DDoS. Solution: partition the hot row (sharded counters), use atomic operations (UPDATE SET stock = stock - 1 with a CHECK constraint), or switch to pessimistic locking with SKIP LOCKED for queue-like access patterns.

Mistake 3: Holding the transaction open too long

The mistake: Reading the entity, doing expensive computation or calling external services, then writing back — all within one @Transactional method.

Why it fails: The longer the transaction, the higher the probability another transaction modifies the same row before you commit. Move expensive operations outside the transaction boundary: read → compute (no TX) → short TX (read-verify-write).

Mistake 4: Not handling the ABA problem

The mistake: Assuming version checks catch all semantic conflicts.

Why it fails: If value goes A→B→A and version increments correctly (1→2→3), your read of "A at version 1" correctly fails when it finds version 3. But if your business logic only checks the value (not version), it might incorrectly assume no change happened. Always rely on the version column, not value comparison.

Mistake 5: Forgetting to version the right entity in aggregate roots

The mistake: Versioning only the child entity when the business invariant spans the aggregate root.

Why it fails: Two transactions can modify different children of the same aggregate without conflicting, even though the aggregate's invariant is violated. Solution: increment the aggregate root's version whenever any child is modified (DDD pattern: modify aggregates only through the root).

Trade-Offs

Optimistic vs Pessimistic vs Event Sourcing vs Queue Serialization
Strategy Throughput Contention Handling Complexity Best For
Optimistic Locking High (no lock waits) Retry on conflict Low-Medium Low-moderate contention, read-heavy workloads
Pessimistic Locking Lower (threads wait) Serialize access Low High contention, short critical sections
SKIP LOCKED High Skip contested rows Low Queue-like processing, job workers
Sharded Counters Very High Partition hot data Medium Counters, inventory, rate limiting
Event Sourcing High (append-only) No conflicts (append) High Audit trails, complex business events
Serialized Queue Limited by consumer No conflicts (ordered) Medium Strict ordering requirements, financial systems

Rule of thumb: If contention is <5% of requests, optimistic locking is ideal. Between 5-20%, consider pessimistic locking or SKIP LOCKED. Above 20%, you need architectural changes (sharding, queuing, event sourcing) — no locking strategy will save you.

Follow-Up Questions

Q1: Why might optimistic locking fail even with REPEATABLE READ isolation?

Strong answer: It depends on the database engine. In PostgreSQL, REPEATABLE READ uses true snapshot isolation — it will throw a serialization error if you try to update a row modified after your snapshot started, which works synergistically with optimistic locking. In MySQL/InnoDB, REPEATABLE READ uses MVCC for reads but still allows "last writer wins" for updates — your UPDATE sees the latest committed version, not your snapshot. So InnoDB's REPEATABLE READ does NOT prevent lost updates without explicit optimistic locking (@Version) or SELECT FOR UPDATE.

Q2: How do you decide between optimistic and pessimistic locking?

Strong answer: It's primarily a contention probability decision. Optimistic locking assumes conflicts are rare — it optimizes for the happy path (no lock acquisition overhead) but pays a high cost on conflict (retry entire transaction). Pessimistic locking assumes conflicts are likely — it pays upfront (lock wait) but guarantees progress without retries. Secondarily, consider transaction duration: optimistic is better for long-running operations (no lock held), pessimistic for short critical sections. Also consider user experience: optimistic locking can report "conflict, please retry" which may be acceptable for some UIs.

Q3: What is the retry amplification problem and how do you solve it?

Strong answer: With N concurrent requests on the same row, optimistic locking produces N(N-1)/2 total retries in the worst case — only one succeeds per round, the rest all fail and retry, creating another round of N-1 competing, then N-2, etc. This is O(N²) total database operations. Solutions: (1) exponential backoff with jitter to temporally spread retries, (2) cap maximum retry attempts (fail fast), (3) switch to pessimistic locking or SKIP LOCKED for hot rows, (4) partition the data so fewer requests target the same row, (5) use a queue to serialize access.

Q4: How does @Version interact with batch updates and bulk operations?

Strong answer: JPA/Hibernate @Version only works for entity-level operations (find → modify → flush). Bulk JPQL/HQL updates (UPDATE Entity SET ... WHERE ...) bypass version checking entirely — Hibernate doesn't increment the version automatically. If you use bulk updates, you must manually add "AND version = :expectedVersion" and "SET version = version + 1" to your query. Spring Data's @Modifying queries have the same limitation. This is a common source of lost updates in systems that mix entity operations with bulk operations.

Q5: How would you handle optimistic locking in a microservices saga?

Strong answer: In a saga spanning multiple services, each service applies optimistic locking independently on its own data. If Service B's optimistic lock fails, it signals the saga orchestrator, which must issue compensating transactions to Service A (which already committed). The key challenge is that you can't atomically commit across services, so you need: (1) idempotent operations in each step, (2) compensating transactions for rollback, (3) a decision on whether to retry the failed step or abort the entire saga. Some teams use a reservation pattern — reserve (lock) resources in all services first, then confirm, reducing the compensation complexity.

Q6: What's the difference between SELECT FOR UPDATE and @Version?

Strong answer: SELECT FOR UPDATE is pessimistic — it acquires a row-level lock immediately, blocking other transactions from reading (FOR UPDATE) or writing that row until you commit. @Version is optimistic — it allows concurrent access freely but detects conflicts at write time via a conditional UPDATE. SELECT FOR UPDATE guarantees no conflict but reduces concurrency. @Version maximizes concurrency but requires retry logic. SELECT FOR UPDATE NOWAIT / SKIP LOCKED are hybrids — they provide pessimistic guarantees without blocking (fail fast or skip).

Relationship to Transaction Isolation Levels

How optimistic locking complements (not replaces) database isolation levels

Common interview follow-up: "How does optimistic locking relate to transaction isolation levels?" This trips up candidates who conflate the two.

Optimistic locking and transaction isolation levels address different aspects of concurrency control:

Concern Isolation Levels Optimistic Locking
What it controls Visibility of uncommitted/concurrent changes during a transaction Whether a write succeeds based on version expectations
Lost update prevention Only SERIALIZABLE fully prevents lost updates in all databases Detects lost updates at write time via version check
Implementation MVCC snapshots, lock-based, or SSI (Serializable Snapshot Isolation) Application-level conditional UPDATE
Scope All reads/writes within a transaction Specific entities annotated with @Version

Key Points

  • READ COMMITTED (default in PostgreSQL, Oracle): Does NOT prevent lost updates. Optimistic locking is essential here to detect concurrent modifications.
  • REPEATABLE READ (default in MySQL/InnoDB): Prevents non-repeatable reads via MVCC snapshots, but does NOT prevent lost updates in all engines. In PostgreSQL, REPEATABLE READ will throw a serialization error on conflict. In MySQL/InnoDB, it silently allows the last writer to win unless you use SELECT FOR UPDATE or @Version.
  • SERIALIZABLE: Prevents all anomalies including lost updates, but at significant throughput cost. Using SERIALIZABLE everywhere eliminates the need for optimistic locking but is rarely practical for high-throughput systems.

Bottom line: In most production systems running READ COMMITTED or REPEATABLE READ, optimistic locking (or pessimistic locking) is still needed to prevent lost updates. Isolation levels alone are not sufficient unless you use SERIALIZABLE.

Summary

Key mental models for the interview:

  • Optimistic locking = CAS (Compare-And-Swap) at the database level. Read version, do work, write-if-version-matches. Simple concept, complex at scale.
  • Low contention = optimistic. High contention = pessimistic or redesign. The break-even point is typically around 5-10% conflict rate.
  • Retry amplification is O(N²). N concurrent conflicting requests produce N(N-1)/2 total retries. Always use backoff with jitter.
  • Isolation levels don't eliminate the need for application-level locking. READ COMMITTED and InnoDB REPEATABLE READ both allow lost updates without @Version.
  • PostgreSQL REPEATABLE READ throws serialization errors; MySQL silently allows last-writer-wins. Know your database's behavior.
  • Hot rows need architectural solutions, not more retries. Sharded counters, queues, or SKIP LOCKED.

What NOT to say in an interview:

  • ❌ "Just retry until it works" — shows no understanding of amplification, thundering herd, or when to give up.
  • ❌ "Optimistic locking is always better because it's non-blocking" — wrong at high contention; pessimistic may give higher throughput.
  • ❌ "SERIALIZABLE isolation solves everything" — technically true but shows no awareness of the throughput cost.
  • ❌ "We don't need locking because we use transactions" — transactions provide isolation between reads and writes, but don't prevent lost updates at READ COMMITTED.

Hard Spring AOP Proxy Transactions

Why can @Transactional fail even when no exception is thrown?

Key Takeaway: @Transactional works through AOP proxies. If the proxy is bypassed (self-invocation, private methods, final classes), Spring never sees the call — and the transaction never begins.

Interviewer's Intent

What they're really testing:

  • Do you understand Spring's proxy-based AOP model, not just the annotation?
  • Can you explain why something fails, not just that it fails?
  • Have you debugged transaction issues in production?
  • Do you understand the difference between framework magic and actual behavior?

This question separates engineers who've memorized the @Transactional annotation from those who understand how Spring's transaction infrastructure actually works at the bytecode level. Interviewers want to see that you can reason about proxy boundaries, AOP interceptors, and the subtle ways declarative transactions can silently fail.

60-Second Interview Answer

Use this in the interview:

"@Transactional relies on Spring AOP proxies. The transaction only activates when the method is called through the proxy. There are several scenarios where the proxy is bypassed or misconfigured:

1. Self-invocation — calling a @Transactional method from within the same class bypasses the proxy entirely.
2. Private/final methods — CGLIB can't override them, so the advice is never applied.
3. Checked exceptions — by default, Spring only rolls back on unchecked exceptions (RuntimeException). A checked exception commits the transaction.
4. Wrong propagation — SUPPORTS or NOT_SUPPORTED won't start a new transaction if none exists.
5. Async boundaries — @Async methods run on a different thread, outside the caller's transaction context.

I've hit most of these in production. The self-invocation one is particularly insidious because everything appears to work until you check the database under load."

How Spring Creates Transactions Internally

The Big Picture — What happens when you add @Transactional

When Spring Boot starts, it performs the following at bean initialization time:

  1. Component Scanning — finds your @Service class
  2. BeanPostProcessor — InfrastructureAdvisorAutoProxyCreator detects @Transactional
  3. Proxy Creation — wraps your bean in a CGLIB (or JDK dynamic) proxy
  4. Advice Registration — attaches TransactionInterceptor as around-advice

At runtime, every call to a @Transactional method goes through this proxy, which:

  1. Looks up the PlatformTransactionManager
  2. Calls getTransaction() with the appropriate TransactionDefinition
  3. Executes your method
  4. On success → commit()
  5. On RuntimeException → rollback()

TransactionSynchronizationManager — The Thread-Local Magic

Spring stores all transaction state in ThreadLocal variables via TransactionSynchronizationManager:

public abstract class TransactionSynchronizationManager {
    // Each thread gets its own transaction resources
    private static final ThreadLocal<Map<Object, Object>> resources =
        new NamedThreadLocal<>("Transactional resources");

    private static final ThreadLocal<Set<TransactionSynchronization>> synchronizations =
        new NamedThreadLocal<>("Transaction synchronizations");

    private static final ThreadLocal<String> currentTransactionName =
        new NamedThreadLocal<>("Current transaction name");

    private static final ThreadLocal<Boolean> currentTransactionReadOnly =
        new NamedThreadLocal<>("Current transaction read-only status");

    private static final ThreadLocal<Integer> currentTransactionIsolationLevel =
        new NamedThreadLocal<>("Current transaction isolation level");

    private static final ThreadLocal<Boolean> actualTransactionActive =
        new NamedThreadLocal<>("Actual transaction active");
}

Critical Implication: Because transaction state is thread-local, any code that runs on a different thread (thread pools, @Async, CompletableFuture, reactive streams) operates outside the current transaction. The transaction context does NOT propagate across threads.

Spring AOP Proxy Mechanism

JDK Dynamic Proxy vs CGLIB — When does Spring use which?
Aspect JDK Dynamic Proxy CGLIB Proxy
Mechanism Implements the same interfaces Generates a subclass at runtime
Requirement Target must implement an interface No interface needed (default in Spring Boot)
Final methods N/A (interface methods) ❌ Cannot proxy final methods
Private methods ❌ Not in interface ❌ Not visible to subclass

Spring Boot default No (since Spring Boot 2.0) ✅ Yes (proxyTargetClass=true)
How CGLIB proxy generation works — bytecode level

When Spring creates a CGLIB proxy for your service, it essentially generates something like this at runtime:

// This is what Spring generates (simplified)
public class OrderService$$EnhancerBySpringCGLIB extends OrderService {

    private MethodInterceptor interceptor; // TransactionInterceptor

    @Override
    public void placeOrder(Order order) {
        // The interceptor wraps the call with transaction logic
        interceptor.intercept(this, 
            OrderService.class.getMethod("placeOrder", Order.class),
            new Object[]{order},
            methodProxy);
    }
}

// Inside TransactionInterceptor.invoke():
public Object invoke(MethodInvocation invocation) {
    TransactionInfo txInfo = createTransactionIfNecessary(tm, txAttr, methodId);
    Object retVal;
    try {
        retVal = invocation.proceed(); // calls YOUR actual method
    } catch (Throwable ex) {
        completeTransactionAfterThrowing(txInfo, ex);
        throw ex;
    }
    commitTransactionAfterReturning(txInfo);
    return retVal;
}

Key Insight: The proxy is a subclass. This means final methods can't be overridden, and private methods aren't visible to the subclass. The interceptor advice is simply never applied to these methods.

Why Transactions Fail Silently — All Scenarios

1. Self-Invocation (The #1 trap in interviews)

When a method in the same class calls another @Transactional method, it uses this reference — bypassing the proxy entirely.

@Service
public class OrderService {

    // ❌ This does NOT run in a transaction!
    public void processAllOrders(List<Order> orders) {
        for (Order order : orders) {
            this.placeOrder(order); // Direct call — proxy bypassed!
        }
    }

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
        paymentService.charge(order); // If this fails, save is NOT rolled back!
    }
}

Fix Options:

// Fix 1: Inject self (proxy-aware)
@Service
public class OrderService {
    @Autowired
    private OrderService self; // Spring injects the PROXY, not 'this'

    public void processAllOrders(List<Order> orders) {
        for (Order order : orders) {
            self.placeOrder(order); // ✅ Goes through proxy
        }
    }

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
        paymentService.charge(order);
    }
}

// Fix 2: Extract to a separate service
@Service
public class OrderProcessingService {
    @Autowired
    private OrderService orderService;

    public void processAllOrders(List<Order> orders) {
        for (Order order : orders) {
            orderService.placeOrder(order); // ✅ External call through proxy
        }
    }
}

// Fix 3: Use ApplicationContext (less clean)
@Service
public class OrderService implements ApplicationContextAware {
    private ApplicationContext ctx;

    public void processAllOrders(List<Order> orders) {
        OrderService proxy = ctx.getBean(OrderService.class);
        for (Order order : orders) {
            proxy.placeOrder(order); // ✅ Gets proxy from container
        }
    }
}
2. Checked Exceptions — Silent commit on failure

By default, Spring only rolls back on unchecked exceptions (RuntimeException and its subclasses). Checked exceptions cause a commit.

@Transactional
public void transferMoney(Account from, Account to, BigDecimal amount) 
        throws InsufficientFundsException {  // ← Checked exception
    
    from.debit(amount);
    accountRepository.save(from);
    
    to.credit(amount);
    accountRepository.save(to);
    
    if (from.getBalance().compareTo(BigDecimal.ZERO) < 0) {
        // ❌ This COMMITS the debit! Transaction is NOT rolled back.
        throw new InsufficientFundsException("Not enough funds");
    }
}

Fix:

// Option 1: Declare rollbackFor explicitly
@Transactional(rollbackFor = Exception.class)
public void transferMoney(Account from, Account to, BigDecimal amount) 
        throws InsufficientFundsException {
    // Now rolls back on ALL exceptions, checked and unchecked
}

// Option 2: Wrap checked exceptions as unchecked
@Transactional
public void transferMoney(Account from, Account to, BigDecimal amount) {
    try {
        externalBankService.validate(from, amount);
    } catch (BankValidationException e) {
        throw new TransferFailedException("Validation failed", e); // RuntimeException
    }
}

// Option 3: Use noRollbackFor for specific unchecked exceptions
@Transactional(noRollbackFor = {OptimisticLockException.class})
public void updateWithRetry(Entity entity) {
    // OptimisticLockException won't trigger rollback
}
3. Wrong Propagation Level 
// ❌ SUPPORTS — no transaction created if caller doesn't have one
@Transactional(propagation = Propagation.SUPPORTS)
public void auditLog(String message) {
    // If called without an existing transaction, this runs WITHOUT a transaction
    auditRepository.save(new AuditEntry(message));
}

// ❌ NOT_SUPPORTED — suspends existing transaction!
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public void sendNotification(User user) {
    // This deliberately runs OUTSIDE any transaction
    // But if you forget this is non-transactional, updates here won't roll back
    notificationRepository.markAsSent(user.getId());
}
Propagation Existing Tx? Behavior Risk
REQUIRED Yes → join / No → create Default, safest Low
REQUIRES_NEW Always creates new, suspends existing Independent commit Medium (suspended tx holds connection)
SUPPORTS Yes → join / No → none Optional High — may run without tx
NOT_SUPPORTED Always non-transactional Suspends existing High — no rollback
MANDATORY Must exist → join / No → exception Fails fast Low (safe guard)
NEVER Must NOT exist → exception if exists Fails fast Low
NESTED Yes → savepoint / No → create Partial rollback Medium (not all DBs support savepoints)
4. Final Methods (CGLIB cannot override) 
@Service
public class PaymentService {

    // ❌ CGLIB cannot generate subclass override for final method
    @Transactional
    public final void processPayment(Payment payment) {
        paymentRepository.save(payment);
        ledgerService.recordEntry(payment);
        // Transaction advice is NEVER applied — this runs without a transaction
    }
}

No compile-time warning! Spring will silently skip the transactional advice on final methods. There's no error at startup — the method simply executes without transaction boundaries. Some static analysis tools (like IntelliJ's inspections) can catch this.

5. Private Methods 
@Service
public class InventoryService {

    public void restockAll(List<Item> items) {
        items.forEach(this::restockItem);
    }

    // ❌ Private method — invisible to CGLIB subclass proxy
    @Transactional
    private void restockItem(Item item) {
        item.setQuantity(item.getQuantity() + item.getReorderAmount());
        itemRepository.save(item);
    }
}

Spring's TransactionAttributeSource actually ignores @Transactional on non-public methods by design. See AbstractFallbackTransactionAttributeSource.computeTransactionAttribute():

// Spring Framework source (simplified)
protected TransactionAttribute computeTransactionAttribute(Method method, Class<?> targetClass) {
    // Don't allow non-public methods, as configured.
    if (allowPublicMethodsOnly() && !Modifier.isPublic(method.getModifiers())) {
        return null; // ← silently returns null, no transaction advice applied
    }
    // ...
}
6. @Async Methods — Thread Boundary 
@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
        sendConfirmation(order); // ← Runs on async thread pool
        // Transaction commits here on THIS thread
    }

    @Async
    @Transactional // ❌ This is a NEW transaction on a DIFFERENT thread
    public void sendConfirmation(Order order) {
        // This runs OUTSIDE the placeOrder transaction
        // Also: self-invocation problem! @Async won't work either.
        emailService.send(order.getEmail(), "Confirmed");
        order.setConfirmationSent(true);
        orderRepository.save(order); // This is a separate transaction
    }
}

Double problem here: (1) @Async requires external invocation (same proxy issue). (2) Even if called externally, the async method runs on a different thread — the caller's transaction context is NOT propagated.

7. Bean not managed by Spring 
// ❌ Created with 'new' — Spring has no proxy around this
OrderService orderService = new OrderService();
orderService.placeOrder(order); // @Transactional does nothing

// ❌ Also fails: inner classes, prototype beans obtained manually
public class OrderController {
    public void handle() {
        // If OrderProcessor is not a Spring bean...
        OrderProcessor processor = new OrderProcessor();
        processor.process(); // No transaction!
    }
}
8. Transaction Manager Mismatch 
@Configuration
public class DataSourceConfig {
    @Bean
    public PlatformTransactionManager primaryTxManager(DataSource primaryDs) {
        return new DataSourceTransactionManager(primaryDs);
    }

    @Bean
    public PlatformTransactionManager secondaryTxManager(DataSource secondaryDs) {
        return new DataSourceTransactionManager(secondaryDs);
    }
}

@Service
public class ReportService {
    // ❌ Uses default (primary) tx manager, but queries secondary datasource
    @Transactional
    public Report generate() {
        // This hits the secondary database but the transaction
        // is bound to the primary DataSource — no actual transaction protection
        return secondaryJdbcTemplate.query(...);
    }

    // ✅ Fix: specify the correct transaction manager
    @Transactional("secondaryTxManager")
    public Report generateFixed() {
        return secondaryJdbcTemplate.query(...);
    }
}

Rollback Rules — Deep Dive

Default rollback behavior matrix
Exception Type Default Behavior Why?
RuntimeException ✅ Rollback Considered unrecoverable programming errors
Error ✅ Rollback JVM-level failures (OOM, StackOverflow)
Checked Exception ❌ Commit Considered recoverable business conditions (legacy EJB convention)

Best Practice: Always use @Transactional(rollbackFor = Exception.class) for critical operations. The default behavior is a holdover from the EJB era and causes real production bugs.

How Spring decides to rollback — source code walkthrough 
// TransactionAspectSupport.java (simplified)
protected void completeTransactionAfterThrowing(TransactionInfo txInfo, Throwable ex) {
    if (txInfo.transactionAttribute != null) {
        // This is where the rollback decision happens
        if (txInfo.transactionAttribute.rollbackOn(ex)) {
            txInfo.getTransactionManager().rollback(txInfo.getTransactionStatus());
        } else {
            // Checked exception → COMMIT (surprising behavior!)
            txInfo.getTransactionManager().commit(txInfo.getTransactionStatus());
        }
    }
}

// DefaultTransactionAttribute.rollbackOn()
@Override
public boolean rollbackOn(Throwable ex) {
    return (ex instanceof RuntimeException || ex instanceof Error);
}
Custom rollback rules — advanced patterns 
// Rollback on specific checked exceptions
@Transactional(rollbackFor = {PaymentException.class, InventoryException.class})
public void checkout(Cart cart) { ... }

// Rollback on all except specific exceptions
@Transactional(
    rollbackFor = Exception.class,
    noRollbackFor = {DuplicateNotificationException.class}
)
public void processEvent(Event event) { ... }

// Programmatic rollback (when you can't use exceptions)
@Transactional
public OrderResult placeOrder(Order order) {
    orderRepository.save(order);
    
    PaymentResult result = paymentGateway.charge(order);
    if (!result.isSuccessful()) {
        // Force rollback without throwing an exception
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        return OrderResult.failed(result.getReason());
    }
    return OrderResult.success(order.getId());
}

Isolation Levels

Isolation level comparison with real-world implications
Level Dirty Read Non-Repeatable Read Phantom Read Use Case
READ_UNCOMMITTED ⚠️ Yes ⚠️ Yes ⚠️ Yes Analytics on stale data (rare)
READ_COMMITTED ✅ No ⚠️ Yes ⚠️ Yes Default in PostgreSQL, Oracle — most OLTP apps
REPEATABLE_READ ✅ No ✅ No ⚠️ Yes Default in MySQL/InnoDB — financial calculations
SERIALIZABLE ✅ No ✅ No ✅ No Critical sections (rare, high lock contention)
Setting isolation in Spring — and when it silently does nothing 
@Transactional(isolation = Isolation.SERIALIZABLE)
public BigDecimal calculateAccountBalance(Long accountId) {
    // Works: new transaction gets SERIALIZABLE isolation
    return transactionRepository.sumByAccountId(accountId);
}

// ⚠️ TRAP: Isolation is IGNORED when joining an existing transaction!
@Transactional(isolation = Isolation.SERIALIZABLE) // ← IGNORED!
public void innerMethod() {
    // If called within an existing REQUIRED transaction,
    // this joins the OUTER transaction's isolation level.
    // Spring logs a warning but does NOT fail.
}

Gotcha: Isolation level only takes effect when a new transaction is created. With Propagation.REQUIRED (default), if a transaction already exists, the isolation parameter is silently ignored. Use REQUIRES_NEW if you need a specific isolation level guaranteed.

Nested Transactions & Savepoints

REQUIRES_NEW vs NESTED — critical difference 
  REQUIRES_NEW:                              NESTED (Savepoint):
  ─────────────                              ──────────────────

  Outer Tx ──┐                               Outer Tx ──────────────────┐
             │ SUSPEND                                    │              │
             │                                           SAVEPOINT       │
  New Tx  ───┼──── independent ────┐                     │              │
             │                     │         Inner work   │              │
             │      COMMIT/ROLLBACK│                     │              │
             │◀────────────────────┘         ROLLBACK ──▶│ (to savepoint)│
             │ RESUME                                    │              │
  Outer Tx ──┘                               Outer Tx ──┘ (continues)   │
                                                                         │
  • Inner rollback does NOT                  • Inner rollback goes to     │
    affect outer                               savepoint only            │
  • 2 physical transactions                  • 1 physical transaction    │
  • 2 connections from pool!                 • 1 connection              │
When to use REQUIRES_NEW (and the connection pool risk) 
@Service
public class PaymentService {

    @Transactional
    public void processOrder(Order order) {
        orderRepository.save(order);
        
        // This gets its own transaction — commits even if outer fails
        auditService.logPaymentAttempt(order); // REQUIRES_NEW
        
        paymentGateway.charge(order.getTotal()); // might throw
    }
}

@Service
public class AuditService {
    
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logPaymentAttempt(Order order) {
        // This commits independently — audit trail preserved
        // even if the payment fails and outer tx rolls back
        auditRepository.save(new AuditEntry("PAYMENT_ATTEMPT", order.getId()));
    }
}

Connection Pool Risk: REQUIRES_NEW suspends the outer transaction but holds its connection. The inner transaction acquires a second connection. Under load, nested REQUIRES_NEW calls can exhaust HikariCP pools (see Chapter 4). With a pool size of 10 and 10 concurrent requests each doing REQUIRES_NEW, you need 20 connections — instant deadlock.

Real Production Incident

The case of the "phantom order" — orders created but never charged

Severity: P1 — Revenue loss detected after 3 days in production

Symptoms

  • Orders appearing in the database with status CREATED
  • No corresponding payment records
  • No exceptions in logs
  • Happened intermittently — ~2% of orders

Investigation

-- Found 847 orders with no payments over 3 days
SELECT o.id, o.created_at, o.status, p.id as payment_id
FROM orders o
LEFT JOIN payments p ON o.id = p.order_id
WHERE o.status = 'CREATED'
  AND p.id IS NULL
  AND o.created_at > NOW() - INTERVAL '3 days';

Root Cause

@Service
public class CheckoutService {

    @Transactional
    public OrderResult checkout(Cart cart) {
        Order order = orderRepository.save(createOrder(cart)); // ← Saved

        try {
            PaymentResult result = paymentClient.charge(order); // ← HTTP call
            if (result.isDeclined()) {
                throw new PaymentDeclinedException(result.getReason());
                // ✅ RuntimeException → rollback → order removed
            }
        } catch (PaymentGatewayTimeoutException e) {
            // ❌ BUG: This is a CHECKED exception!
            // Transaction COMMITS — order saved without payment
            log.warn("Payment gateway timeout for order {}", order.getId());
            throw e; // Propagates, but damage is done — transaction already committed
        }
        
        order.setStatus("PAID");
        return OrderResult.success(order);
    }
}

The Subtle Bug

PaymentGatewayTimeoutException extended IOException (checked). When the payment gateway was slow (2% of the time under load), the timeout exception was thrown, but Spring committed the transaction because it's a checked exception. The order was persisted without payment.

Resolution

// Fix 1: Add rollbackFor
@Transactional(rollbackFor = Exception.class)
public OrderResult checkout(Cart cart) { ... }

// Fix 2: Team adopted a project-wide rule
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Transactional(rollbackFor = Exception.class)
public @interface SafeTransaction {
    // All new code uses this instead of @Transactional
}

Lessons Learned

  • Added an ArchUnit test: "No method should use bare @Transactional without rollbackFor"
  • Added a reconciliation job to detect orders without payments
  • Payment gateway timeout was 30s — reduced to 5s with circuit breaker
// ArchUnit rule added to CI pipeline
@ArchTest
static final ArchRule transactional_must_specify_rollback =
    methods()
        .that().areAnnotatedWith(Transactional.class)
        .should(new ArchCondition<JavaMethod>("specify rollbackFor") {
            @Override
            public void check(JavaMethod method, ConditionEvents events) {
                Transactional tx = method.getAnnotationOfType(Transactional.class);
                if (tx.rollbackFor().length == 0) {
                    events.add(SimpleConditionEvent.violated(method,
                        method.getFullName() + " uses @Transactional without rollbackFor"));
                }
            }
        });

    Look for: "Creating new transaction", "Participating in existing transaction", "Initiating transaction commit", "Initiating transaction rollback"

  2. Verify proxy is in play:

private OrderService orderService;

@PostConstruct

    log.info("OrderService class: {}", orderService.getClass().getName());
    // Should show: OrderService$$EnhancerBySpringCGLIB$$xxxxx

}

  4. Check for self-invocation:

    Search for this.methodName() or unqualified method calls within the same class where the called method has @Transactional.

  5. Verify transaction manager binding: 
    // Add a TransactionSynchronization to verify transaction is active
@Transactional
public void suspiciousMethod() {
    boolean isActive = TransactionSynchronizationManager.isActualTransactionActive();

log.info("Exception superclass chain:");

    log.info("  → {}", clazz.getName());
    clazz = clazz.getSuperclass();
}
// If you see Exception (not RuntimeException) in the chain — it won't rollback!

Production-Ready Code Examples

Pattern: TransactionTemplate for programmatic control 
@Service
public class OrderService {

    private final TransactionTemplate txTemplate;
    private final TransactionTemplate txReadOnly;

    public OrderService(PlatformTransactionManager txManager) {
        this.txTemplate = new TransactionTemplate(txManager);
        this.txTemplate.setIsolationLevel(TransactionDefinition.ISOLATION_READ_COMMITTED);
        
        this.txReadOnly = new TransactionTemplate(txManager);
        this.txReadOnly.setReadOnly(true);
    }

    // No proxy needed — transaction is explicit
    public OrderResult placeOrder(Order order) {
        return txTemplate.execute(status -> {
            try {
                Order saved = orderRepository.save(order);
                paymentService.charge(saved);
                return OrderResult.success(saved.getId());
            } catch (Exception e) {
                status.setRollbackOnly(); // Explicit rollback
                return OrderResult.failed(e.getMessage());
            }
        });
    }

    // Read-only transaction for queries
    public List<Order> findRecentOrders(Long userId) {
        return txReadOnly.execute(status ->
            orderRepository.findByUserIdAndCreatedAfter(userId, Instant.now().minus(Duration.ofDays(30)))
        );
    }
}

When to use TransactionTemplate: When you need fine-grained control, when dealing with self-invocation scenarios, or in non-Spring-managed classes. It's also useful in tests and batch processing where declarative transactions become unwieldy.

Pattern: Transaction event listeners (post-commit actions) 
@Service
public class OrderService {

    @Autowired private ApplicationEventPublisher eventPublisher;

    @Transactional
    public Order placeOrder(OrderRequest request) {
        Order order = orderRepository.save(new Order(request));
        
        // Publish event — but listener runs AFTER commit
        eventPublisher.publishEvent(new OrderCreatedEvent(order.getId()));
        
        return order;
    }
}

@Component
public class OrderEventListener {

    // ✅ Runs ONLY after the transaction successfully commits
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onOrderCreated(OrderCreatedEvent event) {
        // Safe to send emails, notifications, trigger async workflows
        // If the transaction rolled back, this never executes
        emailService.sendOrderConfirmation(event.getOrderId());
        analyticsService.trackConversion(event.getOrderId());
    }

    // Runs after rollback — for compensating actions
    @TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
    public void onOrderFailed(OrderCreatedEvent event) {
        metricsService.incrementCounter("orders.failed");
    }
}

Pitfall: @TransactionalEventListener(AFTER_COMMIT) runs after the transaction commits but without a transaction. If the listener itself needs a transaction, it must start its own (or use @Transactional(propagation = REQUIRES_NEW)).

Pattern: Read-only transactions — performance implications 
@Transactional(readOnly = true)
public List<OrderSummary> getOrderHistory(Long userId) {
    // What readOnly = true actually does:
    // 1. Hibernate: sets FlushMode to MANUAL (no dirty checking)
    // 2. JDBC: connection.setReadOnly(true) — hint to DB
    // 3. PostgreSQL: routes to read replica (if configured)
    // 4. MySQL: allows InnoDB to skip gap locks
    return orderRepository.findByUserId(userId);
}

// ⚠️ Common mistake: modifying entities in a read-only transaction
@Transactional(readOnly = true)
public void updateLastAccess(Long userId) {
    User user = userRepository.findById(userId).orElseThrow();
    user.setLastAccessTime(Instant.now());
    // ❌ This change is SILENTLY IGNORED — flush is disabled
    // No exception, no error — just lost data
}
Pattern: Testing transactions with @Transactional in tests 
// ⚠️ @Transactional on test methods auto-rolls-back after each test
// This can HIDE transaction boundary bugs!
@SpringBootTest
@Transactional // ← rolls back after each test
class OrderServiceTest {

    @Test
    void placeOrder_shouldPersist() {
        // This test passes even if @Transactional on the service is broken!
        // Because the TEST's transaction wraps everything.
        orderService.placeOrder(testOrder);
        
        // This assertion works inside the test's transaction
        assertThat(orderRepository.findById(testOrder.getId())).isPresent();
    }
}

// ✅ Better: test without test-level @Transactional to catch real issues
@SpringBootTest
class OrderServiceIntegrationTest {

    @Autowired private OrderService orderService;
    @Autowired private OrderRepository orderRepository;

    @Test
    void placeOrder_shouldCommitInRealTransaction() {
        Order order = orderService.placeOrder(testOrder);
        
        // Verify in a new transaction (simulates real usage)
        Order found = orderRepository.findById(order.getId()).orElseThrow();
        assertThat(found.getStatus()).isEqualTo("CREATED");
    }

    @AfterEach
    void cleanup() {
        orderRepository.deleteAll(); // Manual cleanup
    }
}

Common Mistakes

Mistakes that experienced engineers still make
# Mistake Why It's Dangerous Fix
1 Catching exceptions inside @Transactional Swallows the signal — Spring sees success and commits Re-throw or use setRollbackOnly()
2 Long-running HTTP calls inside a transaction Holds DB connection for the duration of the HTTP call Move HTTP calls outside tx boundary or use REQUIRES_NEW
3 @Transactional on interface methods (with CGLIB) CGLIB proxies the class, not the interface — annotation may be missed Always put @Transactional on the implementation
4 Mixing JPA and JDBC in same transaction JPA may flush at unexpected times, JDBC sees stale data Call entityManager.flush() before JDBC operations
5 Using @Transactional on @Configuration classes CGLIB already proxies @Configuration — double proxy issues Use on @Service classes only
6 Lazy loading outside transaction LazyInitializationException in controller/view layer Use @EntityGraph, DTOs, or keep session open

Trade-offs & Alternatives

Declarative vs Programmatic transactions
Approach Pros Cons Best For
@Transactional (declarative) Clean, convention-based, less boilerplate Proxy pitfalls, hidden behavior, hard to debug Standard CRUD services
TransactionTemplate (programmatic) Explicit, no proxy issues, fine control More verbose, clutters business logic Complex workflows, batch processing
AspectJ weaving (compile-time) No proxy — works on private, final, self-calls Build complexity, harder to debug, slow compilation Legacy codebases with severe proxy issues
Transaction scope — narrow vs wide 
  Narrow Transaction (recommended):        Wide Transaction (risky):
  ─────────────────────────────────        ──────────────────────────────

  validate(input)                          ┌─ BEGIN TX ──────────────────┐
  enrichData(input)                        │ validate(input)             │
  ┌─ BEGIN TX ──────┐                      │ enrichData(input)           │
  │ save(entity)    │                      │ save(entity)                │
  │ updateRelated() │                      │ updateRelated()             │
  └─ COMMIT ────────┘                      │ sendEmail()    ← 3s wait!  │
  sendEmail(entity)                        │ callExternalAPI() ← 5s!    │
  callExternalAPI()                        └─ COMMIT ────────────────────┘
                                              (held connection for 8s!)
  Connection held: ~50ms                    Connection held: ~8000ms

Rule of thumb: A transaction should hold a DB connection for the minimum time necessary. Move I/O operations (HTTP calls, file ops, message publishing) outside the transaction boundary wherever possible.

Follow-up Interview Questions

Likely follow-ups and how to answer them
Q: "How would you detect @Transactional issues at compile time?"
Use ArchUnit rules in CI to enforce: no private @Transactional methods, rollbackFor always specified, no self-invocation patterns. Also IntelliJ Spring inspections catch many issues.
Q: "What happens if a @Transactional method calls another @Transactional method in a different bean?"
With default propagation (REQUIRED), the inner method joins the outer transaction. They share the same physical connection. If the inner method throws, the entire transaction is marked for rollback — even if the outer method catches the exception.
Q: "How do distributed transactions work across microservices?"
@Transactional only works for local transactions (single datasource). For distributed transactions: use the Saga pattern (choreography or orchestration), the Outbox pattern with CDC, or in rare cases, XA/2PC with JTA. I strongly prefer Sagas for microservices.
Q: "Can you use @Transactional with Kotlin coroutines or reactive streams?"
No — @Transactional relies on thread-local state. For reactive (WebFlux), use ReactiveTransactionManager with TransactionalOperator. For Kotlin coroutines, use @Transactional with spring-tx's coroutine support (Spring 6.1+) or transactionalOperator.executeAndAwait {}.
Q: "How does @Transactional interact with Spring's retry mechanism?"
@Retryable should wrap @Transactional (retry at a higher level). If @Transactional wraps @Retryable, the retry happens inside the same transaction — which is already marked for rollback. The correct ordering: Caller → @Retryable → @Transactional → business logic. See Chapter 2 for deep dive on retry + idempotency.
Q: "What's the performance impact of @Transactional?"
Minimal per-call overhead (~0.1ms for proxy dispatch + connection acquisition). The real cost is holding connections: a transaction that takes 100ms holds a HikariCP connection for 100ms. With pool size 10 and 100 concurrent requests, that's the bottleneck — not the proxy overhead.

Summary

Interview Takeaways:

  1. @Transactional = AOP proxy. No proxy → no transaction.
  2. Self-invocation is the #1 production trap — fix with self-injection or extract to another bean.
  3. Default rollback is only on RuntimeException — always use rollbackFor = Exception.class for critical paths.
  4. Final/private methods silently skip transactional advice — no compile error, no runtime error.
  5. Transaction context is thread-local — @Async, CompletableFuture, reactive break it.
  6. Isolation level is ignored when joining an existing transaction.
  7. Keep transactions short — never put HTTP calls or message publishing inside a tx boundary.
  8. Use TransactionTemplate when you need explicit control or face proxy limitations.

Chapter 12 — JVM GC Latency

Hard GC JVM Tuning

"Why can JVM garbage collection suddenly increase API latency without high CPU usage?"

Interviewer Intent

What is the interviewer really assessing?

This question targets deep JVM internals knowledge. The interviewer wants to see:

  • JVM memory model understanding — Can you explain generational GC, GC roots, card tables, and remembered sets without hand-waving?
  • Stop-the-world awareness — Do you understand that GC pauses freeze ALL application threads regardless of CPU availability?
  • Collector knowledge — Can you compare G1GC, ZGC, and Shenandoah with specific pause-time characteristics?
  • Production debugging — Have you actually read GC logs at 3 AM and correlated pause events with P99 latency spikes?
  • Tuning experience — Do you know which JVM flags matter and why default settings fail at scale?
  • Allocation-aware coding — Can you write code that minimizes GC pressure without sacrificing readability?
  • Container awareness — Do you understand JVM ergonomics in Kubernetes pods with cgroup memory limits?
  • Trade-off articulation — Can you explain why lower pause times cost throughput, and when that trade-off is acceptable?

Red flag: Candidates who say "just increase heap size" or "switch to ZGC" without explaining why the current collector is causing pauses will not pass the bar at FAANG companies.

Quick Answer

30-second elevator pitch

The core insight: GC pauses are stop-the-world events that freeze all application threads — not because the CPU is busy computing, but because the JVM needs a consistent heap snapshot. During a 200ms Full GC pause, every API request in flight is frozen, causing latency spikes with zero CPU activity.

The structured answer:

  1. STW pauses ≠ CPU usage. During a GC pause, threads are suspended at safepoints. The CPU is mostly idle while the collector traces object references.
  2. Old generation collections are expensive. Minor GC in young gen takes 5-20ms, but mixed/full GC in old gen can take 200ms-2s with G1GC.
  3. Promotion pressure triggers long pauses. Long-lived objects (caches, connection pools, session state) get promoted to old gen, eventually triggering expensive collections.
  4. Humongous allocations bypass young gen. Objects larger than half a G1 region go directly to old gen, causing fragmentation and early mixed GC cycles.
  5. Container memory limits compound the problem. JVM ergonomics may calculate heap size incorrectly in containers, leading to more frequent GC.

Fix strategy: Analyze GC logs → identify promotion rate → tune heap regions → reduce allocation rate → consider low-latency collector (ZGC/Shenandoah) → implement off-heap caching for large objects.

GC Fundamentals

How garbage collection works in the JVM

Generational Hypothesis

The JVM heap is divided into generations based on the empirical observation that most objects die young:

┌─────────────────────────────────────────────────────────────────────┐
│                          JVM Heap                                    │
├─────────────────────────────────┬───────────────────────────────────┤
│         Young Generation        │         Old Generation            │
│  ┌───────┬────────┬────────┐   │                                   │
│  │ Eden  │  S0    │  S1    │   │   Tenured Space                   │
│  │       │(from)  │ (to)   │   │   (long-lived objects)            │
│  │ new   │survivor│survivor│   │                                   │
│  │objects│ space  │ space  │   │                                   │
│  └───────┴────────┴────────┘   │                                   │
├─────────────────────────────────┼───────────────────────────────────┤
│  ~33% of heap (typical)         │  ~67% of heap (typical)           │
│  Minor GC: 5-20ms              │  Major/Full GC: 50ms-2s+          │
└─────────────────────────────────┴───────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                        Metaspace (off-heap)                          │
│   Class metadata, method bytecode, constant pools                   │
│   Grows dynamically (can trigger Full GC if limited)                │
└─────────────────────────────────────────────────────────────────────┘

Object Lifecycle

  1. Allocation: New objects are allocated in Eden space (TLAB — Thread Local Allocation Buffer for lock-free allocation)
  2. Minor GC: When Eden fills, live objects are copied to a survivor space. Dead objects are reclaimed. This is a STW event but typically fast (5-20ms).
  3. Aging: Objects surviving multiple minor GCs (tenuring threshold, default 15) get promoted to old generation.
  4. Major GC: When old gen fills, a much more expensive collection occurs — marking all live objects from GC roots through the entire old gen.

GC Roots — Where Liveness Tracing Begins

// 1. Local variables on thread stacks

        // from a GC root even after this method returns

Stop-the-World (STW) Pauses

Critical concept: During a STW pause, every application thread is suspended at a safepoint. No application code executes. No requests are processed. No responses are sent. The CPU may show 0% user-space utilization because threads are simply parked.

Safepoints are specific locations in code where the JVM can safely stop a thread:

  • Method entry/exit
  • Loop backedges (with counted loop optimization — loops with known bounds may NOT have safepoints)
  • Allocation sites
  • Monitor operations (synchronized)

Time-to-Safepoint (TTSP)

// DANGEROUS: Counted loop without safepoint
// JVM optimizes away safepoint polls in counted loops
public long sumArray(int[] array) {
    long sum = 0;
    // This loop may NOT have a safepoint poll
    // It can delay GC for ALL threads until it completes
    for (int i = 0; i < array.length; i++) {
        sum += array[i];
    }
    return sum;
}

// SAFER: Use long index or add explicit safepoint
public long sumArraySafe(int[] array) {
    long sum = 0;
    for (long i = 0; i < array.length; i++) { // long index = uncounted loop
        sum += array[(int) i];
    }
    return sum;
}

JDK 17+: JEP 376 (ZGC) and JEP 377 improved safepoint behavior. JDK 21+ with virtual threads introduces additional safepoint considerations for carrier threads.

GC Algorithms

G1GC, ZGC, and Shenandoah — comparison and selection criteria

G1GC (Garbage-First Garbage Collector)

Default collector since JDK 9. Divides heap into equal-sized regions (~2048 regions).

┌────────────────────────────────────────────────────────────────────┐
│                    G1GC Region Layout                                │
├────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┤
│ E  │ E  │ S  │ O  │ O  │ H  │ H  │ E  │ O  │ E  │ S  │ O  │Free│
│den │den │urv │ld  │ld  │umon│umon│den │ld  │den │urv │ld  │    │
└────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘
  E = Eden    S = Survivor    O = Old    H = Humongous    Free = Empty

G1GC Phases:
1. Young-only phase    → Evacuates young regions (STW, ~5-20ms)
2. Concurrent marking  → Traces old gen (mostly concurrent, brief STW for remark)
3. Mixed collection    → Evacuates young + selected old regions (STW, ~30-100ms)
4. Full GC (fallback)  → Single-threaded compaction (STW, 500ms-5s+) ← DISASTER

ZGC (Z Garbage Collector)

Ultra-low latency collector. Available since JDK 11 (experimental), production-ready JDK 15+, generational in JDK 21+.

# Enable ZGC (JDK 17+)
-XX:+UseZGC

# Enable Generational ZGC (JDK 21+) — significantly better throughput
-XX:+UseZGC -XX:+ZGenerational

Key characteristics:

  • Pause times < 1ms (sub-millisecond) regardless of heap size
  • Supports heaps from 8MB to 16TB
  • Uses colored pointers (metadata in pointer bits) and load barriers
  • Concurrent relocation — moves objects without stopping application
  • ~3-5% throughput overhead vs G1GC (generational ZGC reduces this to ~1-2%)

Shenandoah

Low-pause collector developed by Red Hat. Available in OpenJDK (not Oracle JDK).

# Enable Shenandoah
-XX:+UseShenandoahGC

# Shenandoah modes
-XX:ShenandoahGCMode=normal    # Default balanced mode
-XX:ShenandoahGCMode=iu        # Incremental-update for lower footprint
-XX:ShenandoahGCMode=passive   # No concurrent work (debugging only)

Key characteristics:

  • Pause times typically < 10ms
  • Uses Brooks forwarding pointers (extra word per object)
  • Concurrent compaction via read/write barriers
  • Available in OpenJDK and Amazon Corretto
  • Slightly higher memory overhead (~5-10%) due to forwarding pointers

When to Use Which

Decision framework:

  • G1GC: Default choice. Good for most Spring Boot services with 4-16GB heaps where 50-100ms pauses are acceptable.
  • ZGC: When P99 latency SLA is < 10ms, heap > 16GB, or you cannot tolerate any pause > 1ms (trading, real-time bidding, gaming).
  • Shenandoah: Similar goals to ZGC but you're on OpenJDK/Corretto and need sub-10ms pauses without Oracle licensing considerations.

Why GC Causes Latency Without High CPU

The mechanics of GC-induced latency spikes

Root Cause: STW Pauses Freeze ALL Application Threads

The key insight that answers the interview question: During a GC pause, application threads are suspended, not computing. The CPU is largely idle — it's waiting for GC work to complete, not processing requests. This is why you see latency spikes without corresponding CPU spikes.

Timeline: GC Pause Impact on Request Processing

Thread-1: ──────────[REQUEST A]────────┤ FROZEN ├──────[RESUME]──→ response (slow)
Thread-2: ──[REQ B]──────┤ FROZEN ├──────────────────[RESUME]──→ response (slow)
Thread-3: ────────────────┤ FROZEN ├─────────────────[RESUME]──→ idle
Thread-4: ─────[REQUEST C]┤ FROZEN ├──────────────────[RESUME]──→ response (slow)
                          │        │
GC Thread: ───────────────│MARKING │SWEEPING│COMPACT│──→ done
                          │<── STW PAUSE ──>│
                          t0    200ms      t1

CPU Usage during pause:
  User:   ~2%  (only GC threads doing tracing work)
  System: ~1%  (minimal kernel activity)
  Idle:   ~97% (all app threads parked!)

External observation:
  - P99 latency spikes by 200ms
  - No CPU alarm fires
  - Thread dump shows all threads at safepoint
  - Connection pool looks full (threads frozen mid-request)

Cause 1: Mixed GC on Old Generation

G1GC mixed collections evacuate both young and old regions. When the old gen has many live objects, evacuation takes longer:

// Scenario: Large in-memory cache causes long mixed GC
@Service
public class ProductCatalogService {
    // 2GB of long-lived objects → all promoted to old gen
    private final Map<String, ProductDetails> catalog = new ConcurrentHashMap<>();

    @PostConstruct
    public void loadCatalog() {
        // Loads 500K products into memory
        // Each product: ~4KB (with descriptions, images metadata)
        // Total: ~2GB in old gen
        productRepository.findAll().forEach(p ->
            catalog.put(p.getSku(), p)
        );
    }

    // Every 30 minutes, refresh the catalog
    @Scheduled(fixedRate = 1800000)
    public void refreshCatalog() {
        Map<String, ProductDetails> newCatalog = productRepository.findAll()
            .stream().collect(Collectors.toMap(Product::getSku, this::toDetails));

        // OLD catalog objects become garbage in old gen
        // NEW catalog objects allocated → promoted to old gen
        // Result: 2GB of garbage in old gen + 2GB new allocation
        // This triggers a MIXED GC or even FULL GC!
        catalog.clear();
        catalog.putAll(newCatalog);
    }
}

Cause 2: Humongous Object Allocation

In G1GC, objects larger than half a region size (~16MB with default 32MB regions) are "humongous" and allocated directly in old gen:

// PROBLEM: Humongous allocations
public class ReportGenerator {
    public byte[] generateLargeReport(String reportId) {
        // With 32MB G1 regions, any allocation > 16MB is humongous
        // Allocated directly in old gen, spanning multiple contiguous regions
        byte[] buffer = new byte[20 * 1024 * 1024]; // 20MB → HUMONGOUS

        // These objects cause:
        // 1. Fragmentation (need contiguous regions)
        // 2. Eager reclamation only during marking cycle
        // 3. Potential Full GC if no contiguous free regions available
        fillReportData(buffer, reportId);
        return buffer;
    }
}

// SOLUTION: Stream the report or use smaller buffers
public class ReportGeneratorFixed {
    public void generateLargeReport(String reportId, OutputStream out) {
        byte[] buffer = new byte[8192]; // 8KB chunks — young gen allocation
        try (var input = reportDataSource.stream(reportId)) {
            int bytesRead;
            while ((bytesRead = input.read(buffer)) != -1) {
                out.write(buffer, 0, bytesRead);
            }
        }
    }
}

Cause 5: Concurrent Mode Failure

G1GC "evacuation failure": When G1 cannot find free regions to copy live objects during a mixed GC, it falls back to a serial Full GC. This single-threaded compaction can take seconds on large heaps.

Sizing Rules of Thumb

The 3-4x rule: Set heap size to 3-4x your live data set (long-lived objects). This gives enough headroom for allocation and avoids frequent old-gen collections.

# Step 1: Determine live data set size
# Run with verbose GC and check heap after Full GC
-Xlog:gc*=info -XX:+UseG1GC

# After Full GC, remaining heap usage = live data set
# Example: Full GC shows 1.2GB remaining → live data = 1.2GB
# Recommended heap: 1.2GB × 3.5 ≈ 4.2GB → set -Xmx4g

# Step 2: Set initial = max to avoid resize pauses
-Xms4g -Xmx4g

# Step 3: For G1GC, consider region size
# Region size = heap / 2048 (rounded to power of 2)
# 4GB heap → 2MB regions
# 8GB heap → 4MB regions
# 32GB heap → 16MB regions (humongous threshold = 8MB!)
-XX:G1HeapRegionSize=4m  # Override if needed

Object Allocation Rate and Churn

How high allocation rates drive frequent GC

Allocation Rate Fundamentals

Allocation rate = bytes allocated per second in young gen. Promotion rate = bytes promoted from young to old gen per second. High allocation rate → frequent minor GC. High promotion rate → old gen fills → mixed/full GC.

Measuring Allocation Rate

# From GC logs — calculate allocation between young GCs
# Before GC: Eden used = allocation since last GC
# Time between GCs = interval
# Allocation rate = Eden used / interval

# Example from GC log:
# [0.523s] GC(0) Pause Young (Normal) 24M->4M(256M) 5.234ms
# [0.891s] GC(1) Pause Young (Normal) 24M->4M(256M) 4.891ms
# Eden = 24MB - 4MB = 20MB allocated between GCs
# Interval = 0.891 - 0.523 = 0.368s
# Allocation rate = 20MB / 0.368s ≈ 54 MB/s (low, healthy)

// Micrometer metrics for allocation rate monitoring
@Configuration
public class GCMetricsConfig {

    @Bean
    public MeterBinder gcAllocationMetrics() {
        return registry -> {
            // Track allocation rate via GarbageCollectorMXBean
            for (GarbageCollectorMXBean gc :
                    ManagementFactory.getGarbageCollectorMXBeans()) {
                if (gc instanceof NotificationEmitter) {
                    ((NotificationEmitter) gc).addNotificationListener(
                        (notification, handback) -> {
                            GarbageCollectionNotificationInfo info =
                                GarbageCollectionNotificationInfo.from(
                                    (CompositeData) notification.getUserData());
                            GcInfo gcInfo = info.getGcInfo();

                            Timer.builder("jvm.gc.pause")
                                .tag("action", info.getGcAction())
                                .tag("cause", info.getGcCause())
                                .register(registry)
                                .record(gcInfo.getDuration(), TimeUnit.MILLISECONDS);
                        }, null, null);
                }
            }
        };
    }

// Usage in a filter/interceptor
@Component
public class LatencyTrackingFilter extends OncePerRequestFilter {
    private final GarbageCollectorMXBean youngGC;

    public LatencyTrackingFilter() {
        this.youngGC = ManagementFactory.getGarbageCollectorMXBeans().stream()
            .filter(gc -> gc.getName().contains("Young"))
            .findFirst().orElseThrow();
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse resp, FilterChain chain) throws Exception {
        long gcCountBefore = youngGC.getCollectionCount();
        long start = System.nanoTime();

        chain.doFilter(req, resp);

        RequestLatencyEvent event = new RequestLatencyEvent();
        event.endpoint = req.getRequestURI();
        event.durationMs = (System.nanoTime() - start) / 1_000_000;
        event.statusCode = resp.getStatus();
        event.gcCountDelta = youngGC.getCollectionCount() - gcCountBefore;
        event.commit();
    }
}

Object Pooling for Expensive Objects

import org.apache.commons.pool2.BasePooledObjectFactory;
import org.apache.commons.pool2.PooledObject;
import org.apache.commons.pool2.impl.DefaultPooledObject;
import org.apache.commons.pool2.impl.GenericObjectPool;
import org.apache.commons.pool2.impl.GenericObjectPoolConfig;

/**
 * Object pool for expensive-to-create objects that would otherwise
 * be allocated and discarded rapidly, causing GC churn.
 *
 * Use case: PDF generators, XML parsers, encryption contexts, large buffers.
 */
public class PdfGeneratorPool {

    private final GenericObjectPool<PdfGenerator> pool;

    public PdfGeneratorPool(int maxPoolSize) {
        GenericObjectPoolConfig<PdfGenerator> config = new GenericObjectPoolConfig<>();
        config.setMaxTotal(maxPoolSize);          // Max objects in pool
        config.setMaxIdle(maxPoolSize / 2);       // Max idle objects
        config.setMinIdle(2);                     // Pre-warm 2 instances
        config.setBlockWhenExhausted(true);       // Wait rather than fail
        config.setMaxWaitDuration(Duration.ofSeconds(5));
        config.setTestOnBorrow(true);             // Validate before use

        this.pool = new GenericObjectPool<>(new PdfGeneratorFactory(), config);
    }

    public byte[] generatePdf(ReportData data) throws Exception {
        PdfGenerator generator = pool.borrowObject();
        try {
            return generator.generate(data);  // Reuse heavy object
        } finally {
            pool.returnObject(generator);     // Return to pool, not GC'd
        }
    }

    private static class PdfGeneratorFactory extends BasePooledObjectFactory<PdfGenerator> {
        @Override
        public PdfGenerator create() {
            // Expensive: loads fonts, initializes rendering engine
            return new PdfGenerator(); // ~50MB of state
        }

        @Override
        public PooledObject<PdfGenerator> wrap(PdfGenerator obj) {
            return new DefaultPooledObject<>(obj);
        }

        @Override
        public void passivateObject(PooledObject<PdfGenerator> p) {
            p.getObject().reset(); // Clear state for reuse
        }

        @Override
        public boolean validateObject(PooledObject<PdfGenerator> p) {
            return p.getObject().isHealthy();
        }
    }
}

Off-Heap Caching with Chronicle Map

import net.openhft.chronicle.map.ChronicleMap;

/**
 * Off-heap cache — stores data outside JVM heap.
 * GC never sees these objects. Zero GC pressure for large caches.
 *
 * Trade-off: Requires serialization/deserialization on each access.
 * Best for: Large caches (> 256MB) with objects that serialize efficiently.
 */
@Configuration
public class OffHeapCacheConfig {

    @Bean(destroyMethod = "close")
    public ChronicleMap<String, byte[]> productCache() throws IOException {
        return ChronicleMap.of(String.class, byte[].class)
            .name("product-cache")
            .entries(500_000)                    // Expected entry count
            .averageKeySize(36)                  // UUID length
            .averageValueSize(4096)              // ~4KB per product
            .maxBloatFactor(2.0)                 // Allow 2x growth
            .createPersistedTo(                  // Memory-mapped file
                new File("/dev/shm/product-cache.dat")  // tmpfs = fast
            );
    }
}

@Service
public class ProductCacheService {

    private final ChronicleMap<String, byte[]> cache;
    private final ObjectMapper objectMapper;

    public ProductCacheService(ChronicleMap<String, byte[]> cache,
                               ObjectMapper objectMapper) {
        this.cache = cache;
        this.objectMapper = objectMapper;
    }

    public Optional<Product> get(String productId) {
        byte[] data = cache.get(productId);  // Off-heap read
        if (data == null) return Optional.empty();
        try {
            return Optional.of(objectMapper.readValue(data, Product.class));
        } catch (IOException e) {
            return Optional.empty();
        }
    }

    public void put(String productId, Product product) {
        try {
            byte[] data = objectMapper.writeValueAsBytes(product);
            cache.put(productId, data);  // Off-heap write — no GC impact
        } catch (JsonProcessingException e) {
            log.warn("Failed to cache product {}", productId, e);
        }
    }
}

    public ProcessingResult processEvent(RawEvent event) {
        // Allocation 1: Parse JSON into new object tree
        Map<String, Object> parsed = objectMapper.readValue(event.getPayload(), Map.class);

        // Allocation 2: Create intermediate DTOs
        EventContext context = new EventContext(
            parsed.get("userId").toString(),      // new String
            parsed.get("action").toString(),      // new String
            Instant.parse(parsed.get("ts").toString()),  // new Instant, new String
            Map.copyOf(parsed)                    // defensive copy = new HashMap + entries
        );

        // Allocation 3: Validation creates error list even when valid
        List<ValidationError> errors = validator.validate(context); // always new ArrayList

        // Allocation 4: Enrichment creates new object
        EnrichedEvent enriched = enricher.enrich(context);  // new object + new fields

        // Allocation 5: Serialization
        byte[] output = objectMapper.writeValueAsBytes(enriched); // new byte[]

        return new ProcessingResult(output, errors.isEmpty());  // new result object
    }
}

// ═══════════════════════════════════════════════════════════════
// AFTER: Allocation-aware (180 MB/s)
// ═══════════════════════════════════════════════════════════════
public class EventProcessorAfter {

    // Reusable thread-local buffers
    private static final ThreadLocal<ByteArrayOutputStream> BUFFER =
        ThreadLocal.withInitial(() -> new ByteArrayOutputStream(8192));

    // Pre-allocated result objects (flyweight pattern)
    private static final ProcessingResult SUCCESS = new ProcessingResult(true);
    private static final ProcessingResult FAILURE = new ProcessingResult(false);

    // Object reuse via Jackson's reusable token buffer
    private final ObjectReader eventReader = objectMapper.readerFor(EventContext.class);

    public ProcessingResult processEvent(RawEvent event, ByteBuffer outputBuffer) {
        // Reuse: Parse directly into pooled object
        EventContext context = contextPool.borrow();
        try {
            // Allocation-free: read into existing object
            eventReader.readValue(event.getPayload(), context);

            // Allocation-free: validate without creating error list
            if (!validator.isValid(context)) {
                return FAILURE;  // No allocation for common path
            }

            // Allocation-free: enrich in-place
            enricher.enrichInPlace(context);

            // Reuse: Write to pre-allocated buffer
            ByteArrayOutputStream buffer = BUFFER.get();
            buffer.reset();  // Reuse without reallocating
            objectMapper.writeValue(buffer, context);

            // Copy to caller's buffer (zero-copy if possible)
            outputBuffer.put(buffer.toByteArray(), 0, buffer.size());

            return SUCCESS;
        } finally {
            context.reset();           // Clear for reuse
            contextPool.release(context);  // Return to pool
        }
    }
}

JFR Event Monitoring for GC Correlation

import jdk.jfr.*;
import jdk.jfr.consumer.*;

/**
 * Real-time GC event monitoring using JFR streaming API (JDK 14+).
 * Correlates GC pauses with application latency in real-time.
 */
@Component
public class GCLatencyMonitor implements SmartLifecycle {

    private static final Logger log = LoggerFactory.getLogger(GCLatencyMonitor.class);
    private final MeterRegistry meterRegistry;
    private RecordingStream stream;

    public GCLatencyMonitor(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
    }

    @Override
    public void start() {
        stream = new RecordingStream();

        // Monitor GC pauses
        stream.enable("jdk.GCPhasePause").withThreshold(Duration.ofMillis(1));
        stream.enable("jdk.GarbageCollection");
        stream.enable("jdk.G1GarbageCollection");
        stream.enable("jdk.OldGarbageCollection");

        // Monitor allocation pressure
        stream.enable("jdk.ObjectAllocationOutsideTLAB");
        stream.enable("jdk.ObjectAllocationInNewTLAB");

        // Monitor safepoint time
        stream.enable("jdk.SafepointBegin");

        // GC pause handler
        stream.onEvent("jdk.GarbageCollection", event -> {
            Duration pause = event.getDuration();
            String cause = event.getString("cause");
            String name = event.getString("name");

            // Record metrics
            Timer.builder("jvm.gc.detailed.pause")
                .tag("cause", cause)
                .tag("collector", name)
                .register(meterRegistry)
                .record(pause);

            // Alert on long pauses
            if (pause.toMillis() > 100) {
                log.warn("Long GC pause: {}ms, cause={}, collector={}",
                    pause.toMillis(), cause, name);
            }

            if (pause.toMillis() > 500) {
                log.error("CRITICAL GC pause: {}ms! cause={}, collector={}. " +
                    "Likely impacting API latency!", pause.toMillis(), cause, name);
                // Trigger PagerDuty/alerting
                meterRegistry.counter("jvm.gc.critical.pause",
                    "cause", cause).increment();
            }
        });

        // Safepoint monitoring (time-to-safepoint)
        stream.onEvent("jdk.SafepointBegin", event -> {
            Duration ttsp = event.getDuration();
            if (ttsp.toMillis() > 50) {
                log.warn("Slow time-to-safepoint: {}ms. " +
                    "Check for counted loops or large array copies.", ttsp.toMillis());
            }
        });

        stream.startAsync();
    }

    @Override
    public void stop() {
        if (stream != null) {
            stream.close();
        }
    }

    @Override
    public boolean isRunning() {
        return stream != null && !stream.isClosed();
    }
}

/**
 * Custom actuator endpoint exposing GC health status.
 * Useful for load balancer health checks that consider GC pressure.
 */
@Component
@Endpoint(id = "gchealth")
public class GCHealthEndpoint {

    private final List<GarbageCollectorMXBean> gcBeans;
    private final MemoryMXBean memoryBean;
    private volatile long lastFullGcTime = 0;
    private volatile long lastFullGcDuration = 0;

    public GCHealthEndpoint() {
        this.gcBeans = ManagementFactory.getGarbageCollectorMXBeans();
        this.memoryBean = ManagementFactory.getMemoryMXBean();
    }

    @ReadOperation
    public Map<String, Object> gcHealth() {
        Map<String, Object> health = new LinkedHashMap<>();

        // Heap utilization
        MemoryUsage heapUsage = memoryBean.getHeapMemoryUsage();
        double heapUtilization = (double) heapUsage.getUsed() / heapUsage.getMax();
        health.put("heapUtilization", String.format("%.1f%%", heapUtilization * 100));
        health.put("heapUsedMB", heapUsage.getUsed() / (1024 * 1024));
        health.put("heapMaxMB", heapUsage.getMax() / (1024 * 1024));

        // GC stats per collector
        List<Map<String, Object>> collectors = new ArrayList<>();
        for (GarbageCollectorMXBean gc : gcBeans) {
            Map<String, Object> collector = new LinkedHashMap<>();
            collector.put("name", gc.getName());
            collector.put("collectionCount", gc.getCollectionCount());
            collector.put("collectionTimeMs", gc.getCollectionTime());
            if (gc.getCollectionCount() > 0) {
                collector.put("avgPauseMs",
                    gc.getCollectionTime() / gc.getCollectionCount());
            }
            collectors.add(collector);
        }
        health.put("collectors", collectors);

        // Health status
        String status = "HEALTHY";
        if (heapUtilization > 0.9) status = "CRITICAL";
        else if (heapUtilization > 0.75) status = "WARNING";
        health.put("status", status);

        return health;
    }
}

Common Mistakes

GC-related anti-patterns and misconceptions
Mistake Why It's Wrong Correct Approach
"Just increase the heap" Larger heap = longer GC pauses when they occur. 32GB heap with G1GC can have 2-5s Full GC pauses. Size heap to 3-4x live data. If you need > 16GB, consider ZGC.
Setting -Xms ≠ -Xmx JVM must GC to grow heap. Growth events trigger Full GC for compaction. Always set -Xms = -Xmx in production to avoid resize pauses.
Calling System.gc() Triggers a Full GC (STW) at unpredictable times. In hot paths, catastrophic. Never call explicitly. Use -XX:+ExplicitGCInvokesConcurrent as safety net.
No GC logging in production Cannot diagnose GC issues post-incident. Flying blind. Always enable GC logging. Overhead is negligible (< 1%). Rotate files.
Tuning without measuring Random flags based on blog posts. Cargo-culting settings from other apps. Measure first: GC logs → identify problem → targeted flag change → measure again.
Ignoring promotion rate Focus on young GC pause time while old gen silently fills up. Monitor promotion rate. If > 50 MB/s, investigate object lifetimes.
Large local caches without GC impact analysis 1GB+ in-memory caches create massive GC pressure on refresh/eviction. Use off-heap (Chronicle Map, MapDB) or external cache (Redis) for > 256MB.
-XX:+DisableExplicitGC Breaks DirectByteBuffer cleanup. NIO apps can OOM on native memory. Use -XX:+ExplicitGCInvokesConcurrent — makes System.gc() use concurrent collector.
Ignoring container memory limits Setting -Xmx to 90% of container memory → OOMKilled by kernel. Leave 30-40% for non-heap (metaspace, threads, native, direct buffers).
Using CMS in JDK 14+ CMS was removed in JDK 14. Still appears in Stack Overflow answers. Use G1GC (default) or ZGC/Shenandoah for low latency.
Finalizers and finalize() Objects with finalizers survive extra GC cycles, clog Finalizer thread. Use Cleaner (JDK 9+) or try-with-resources for cleanup.
Weak/Soft references as "free" caching SoftReferences cleared during GC pressure → thundering herd on cache miss. WeakReferences cleared every GC cycle. Use sized LRU cache (Caffeine) with explicit eviction policy.

Decision framework:

  • If you need guaranteed < 10ms pauses → switch to ZGC (JDK 17+) or Shenandoah

  • If you're on JDK 21+ → Generational ZGC gives best of both worlds

Follow-up Questions

Questions the interviewer might ask next

Q1: "How would you diagnose a memory leak vs high allocation rate?"

Key distinction:

  • Memory leak: Heap-after-GC grows monotonically over time. Objects are retained unintentionally (static maps, listener registrations, ThreadLocal not cleaned).
  • High allocation rate: Heap-after-GC is stable, but GC frequency is high. Objects are created and discarded rapidly.

Diagnosis: Plot "heap used after GC" over hours. If it trends upward → leak. If it's flat but GC is frequent → allocation rate.

Q2: "Your service runs in a 2-CPU, 4GB Kubernetes pod. How do you tune GC?"

# Small container strategy:
-XX:+UseContainerSupport
-XX:ActiveProcessorCount=2          # Ensure JVM sees 2 CPUs
-Xms2560m -Xmx2560m                # 62% of 4GB for heap
-XX:MaxMetaspaceSize=192m
-XX:+UseG1GC
-XX:MaxGCPauseMillis=50             # Aggressive pause target
-XX:ParallelGCThreads=2             # Match CPU count
-XX:ConcGCThreads=1                 # 1 concurrent GC thread
-XX:G1HeapRegionSize=2m             # Smaller regions for smaller heap

# With only 2 CPUs, GC threads compete with application threads!
# Consider ZGC only if GC is still a problem — its concurrent work
# on 2 CPUs may starve the application.

Q3: "How does GC behave differently with virtual threads (JDK 21+)?"

Key points:

  • Virtual threads have small stacks (~few KB vs 1MB for platform threads) — less stack memory pressure
  • Millions of virtual threads mean millions of potential GC roots — root scanning takes longer
  • Virtual threads park/unpark frequently — more safepoint interactions
  • Carrier threads (platform threads pinned during synchronized blocks) affect safepoint behavior
  • Object allocation per virtual thread is typically low, but aggregate allocation across millions can be high

Q4: "How would you handle a service that needs both large cache AND low GC pauses?"

Architecture pattern:

  1. Move large cache off-heap (Chronicle Map for local, Redis for distributed)
  2. Keep small "hot" L1 cache on-heap (Caffeine, < 100MB, short TTL)
  3. Use ZGC for remaining heap activity
  4. Pre-size all collections to avoid resize allocations
  5. Monitor promotion rate — if L1 cache entries are being promoted, reduce L1 TTL

Q5: "What's the difference between 'Allocation Failure' and 'Evacuation Failure' in GC logs?"

Term Meaning Severity
Allocation Failure Eden is full, cannot allocate → triggers minor GC. Normal operation. Normal (expected trigger for young GC)
Evacuation Failure G1 cannot find free regions to copy live objects during evacuation. Falls back to Full GC. Critical (indicates heap pressure or fragmentation)
Concurrent Mode Failure Old gen filled before concurrent marking completed (CMS terminology, similar in G1). Critical (concurrent GC couldn't keep up)
To-space Exhausted No free regions available as copy destination during young GC. High (G1 specific, precedes evacuation failure)

Q6: "How do you prevent GC issues during deployment (rolling restart)?"

Deployment GC considerations:

  • JIT warmup: Fresh JVMs haven't compiled hot paths — interpreted code allocates more temporaries. Use CDS (Class Data Sharing) and AOT compilation.
  • Cache cold-start: Local caches are empty after restart — sudden cache population causes allocation burst. Pre-warm caches before accepting traffic.
  • Readiness probe: Don't mark pod ready until initial GC pressure stabilizes (first 30-60 seconds).
  • Graceful shutdown: Drain connections before stopping — avoid in-flight requests during GC of dying instance.

Summary

Key takeaways for the interview
  1. GC pauses freeze threads, not CPUs. STW events suspend all application threads at safepoints. CPU is idle while threads are parked — this is why latency spikes happen without CPU alarms.
  2. Generational GC is the foundation. Young gen (fast, frequent, cheap) vs old gen (slow, infrequent, expensive). Most GC pain comes from objects being promoted to old gen.
  3. Know your collectors. G1GC: 50-200ms pauses, good default. ZGC: sub-millisecond, JDK 17+. Shenandoah: sub-10ms, OpenJDK only. Choose based on P99 SLA.
  4. Heap sizing is a balance. Too small = frequent GC. Too large = catastrophic pauses when they occur. Target 3-4x live data set.
  5. Allocation rate drives GC frequency. High allocation fills Eden faster → more minor GCs. Reduce allocation in hot paths by reusing objects, avoiding autoboxing, and using parameterized logging.
  6. Large in-memory caches are GC killers. Caches > 256MB should be off-heap or external. Bulk eviction/refresh causes promotion storms and Full GC.
  7. Always enable GC logging in production. Negligible overhead, invaluable during incidents. Use JFR for detailed correlation with application metrics.
  8. Containers need special attention. Leave 30-40% of container memory for non-heap. Set -Xms = -Xmx. Use -XX:+UseContainerSupport. Match ParallelGCThreads to available CPUs.
  9. Measure before tuning. Read GC logs, calculate allocation rate, identify promotion pressure. Then make ONE targeted change and measure again.
  10. Full GC is an emergency. Any Full GC in a latency-sensitive service is a bug. Set up alerting on jdk.OldGarbageCollection events and treat them as P1 incidents.

Medium Redis Caching

Cache Hit Ratio Drops from 95% to 30% — What Would You Check?

Key Takeaway: A sudden cache hit ratio drop is a production emergency requiring systematic diagnosis — check TTL expiry patterns, recent deployments, memory pressure, eviction policies, and serialization compatibility before assuming the cache itself is broken.

Interviewer Intent

What the interviewer is really assessing

This question tests whether a senior engineer can systematically diagnose a production caching issue under pressure. The interviewer evaluates:

  • Systematic thinking: Do you jump to conclusions or follow a structured investigation?
  • Production awareness: Have you actually operated cache infrastructure at scale?
  • Depth of knowledge: Do you understand cache internals (eviction, memory management, replication)?
  • Incident response: Can you triage, mitigate, then root-cause — in that order?
  • Architecture understanding: Do you know how caching fits into the broader system?

💡 Interview Tip: Start with immediate mitigation (can we scale the DB? circuit-break?), then move to diagnosis. This shows you prioritize user impact over root-cause curiosity.

Expected seniority signals
  • Mentions checking recent deployments first (most common cause)
  • Distinguishes between gradual degradation vs. cliff-drop
  • Knows Redis-specific monitoring commands
  • Understands multi-tier caching and where the break might be
  • Discusses mitigation before deep debugging
  • References real incidents or war stories

Quick Answer

30-second structured response

"A cache hit ratio dropping from 95% to 30% is a P1 incident. My immediate response:

  1. Correlate with timeline: Check deployment history, config changes, and traffic patterns in the last hour
  2. Check Redis health: Run INFO stats for keyspace_hits/misses, check memory usage and eviction count
  3. Verify key patterns: Confirm the cache key format hasn't changed (common with serialization updates)
  4. Check TTL distribution: Mass TTL expiry causes thundering herd on the database
  5. Mitigate immediately: Scale read replicas on DB, enable circuit breaker, consider cache warming

The most frequent root cause I've seen: a deployment changed the serialization format or cache key structure, making all existing entries effectively invisible."

Multi-Tier Cache Architecture

L1 / L2 / L3 caching layers 
┌─────────────────────────────────────────────────────────────────┐
│                        Request Flow                               │
└─────────────────────────────────────────────────────────────────┘

  Client Request
       │
       ▼
┌─────────────┐    HIT     ┌──────────────────────────────────┐
│  L1 Cache   │───────────▶│  Return immediately (~1ms)       │
│  (Caffeine) │            │  In-process, per-JVM             │
│  ~10K keys  │            │  No serialization overhead       │
└─────┬───────┘            └──────────────────────────────────┘
      │ MISS
      ▼
┌─────────────┐    HIT     ┌──────────────────────────────────┐
│  L2 Cache   │───────────▶│  Return with network hop (~2ms)  │
│   (Redis)   │            │  Shared across all JVMs          │
│  ~1M keys   │            │  Serialization cost              │
└─────┬───────┘            └──────────────────────────────────┘
      │ MISS
      ▼
┌─────────────┐    HIT     ┌──────────────────────────────────┐
│  L3 Source  │───────────▶│  Return with query (~20-200ms)   │
│ (Database)  │            │  Populate L1 + L2 on return      │
│  Full data  │            │  Most expensive path             │
└─────────────┘            └──────────────────────────────────┘

Why multi-tier? L1 eliminates serialization and network overhead for hot keys. L2 provides shared state across a cluster. The ratio drop could be at any layer — isolate which one first.

Spring Boot multi-tier cache configuration 
@Configuration
@EnableCaching
public class MultiTierCacheConfig {

    @Bean
    public CacheManager cacheManager(RedisConnectionFactory redisConnectionFactory) {
        // L1: Caffeine (in-process, per JVM)
        CaffeineCacheManager l1CacheManager = new CaffeineCacheManager();
        l1CacheManager.setCaffeine(Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofMinutes(5))
            .recordStats());  // Critical for monitoring

        // L2: Redis (distributed, shared)
        RedisCacheConfiguration redisConfig = RedisCacheConfiguration
            .defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(30))
            .serializeKeysWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(new StringRedisSerializer()))
            .serializeValuesWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(new GenericJackson2JsonRedisSerializer()));

        RedisCacheManager l2CacheManager = RedisCacheManager.builder(redisConnectionFactory)
            .cacheDefaults(redisConfig)
            .build();

        // Composite: L1 checked first, then L2
        return new MultiTierCacheManager(l1CacheManager, l2CacheManager);
    }
}
public class MultiTierCacheManager implements CacheManager {

    private final CaffeineCacheManager l1;
    private final RedisCacheManager l2;

    public MultiTierCacheManager(CaffeineCacheManager l1, RedisCacheManager l2) {
        this.l1 = l1;
        this.l2 = l2;
    }

    @Override
    public Cache getCache(String name) {
        Cache l1Cache = l1.getCache(name);
        Cache l2Cache = l2.getCache(name);
        return new MultiTierCache(name, l1Cache, l2Cache);
    }

    @Override
    public Collection<String> getCacheNames() {
        Set<String> names = new LinkedHashSet<>();
        names.addAll(l1.getCacheNames());
        names.addAll(l2.getCacheNames());
        return names;
    }
}
Cache key design principles

Cache key design directly impacts hit ratio. Poor keys cause namespace collisions or unnecessary fragmentation:

// ❌ Bad: version not included — stale data after schema changes
String key = "user:" + userId;

// ❌ Bad: too granular — low reuse
String key = "user:" + userId + ":ts:" + System.currentTimeMillis();

// ✅ Good: versioned, hierarchical, bounded
String key = "v2:user:" + userId;

// ✅ Good: includes relevant context for correct invalidation
String key = "v2:user:" + userId + ":profile";
String key = "v2:user:" + userId + ":preferences";

⚠️ Key format changes are the #1 cause of sudden hit ratio drops. If a deployment changes user:{id} to v2:user:{id}, all existing keys become orphaned misses until they naturally expire.

Why Cache Hit Ratio Drops

Root causes taxonomy

A drop from 95% to 30% is catastrophic — it means ~65% of requests now hit the database that previously didn't. Here's a comprehensive taxonomy:

Category Cause Pattern Severity
Deployment Cache key format changed Cliff drop at deploy time 🔴 Critical
Deployment Serialization format changed Cliff drop, deserialization errors in logs 🔴 Critical
Deployment FLUSHALL in migration script Instant 0% hit ratio 🔴 Critical
TTL Mass TTL expiry (synchronized TTLs) Periodic drops at fixed intervals 🟠 High
Memory maxmemory reached, eviction triggered Gradual decline as memory fills 🟠 High
Memory Hot key eviction under LRU Specific queries slow down 🟡 Medium
Traffic New traffic pattern (bot, scraper) Cache pollution with low-reuse keys 🟡 Medium
Infrastructure Redis cluster rebalancing/resharding Temporary misses during slot migration 🟠 High
Infrastructure Network partition to Redis All requests bypass cache 🔴 Critical
Application Cache stampede / thundering herd Spike in DB load at key expiry 🟠 High
TTL mass expiry

When all keys are set with the same TTL at roughly the same time (e.g., after a cache warm-up or deployment), they all expire simultaneously:

Timeline:
  T=0 (deploy)        T=30min (mass expiry)       T=31min (stampede)
     │                        │                         │
     ▼                        ▼                         ▼
  ┌────────┐            ┌────────┐               ┌────────┐
  │ Warm   │            │ All    │               │ All    │
  │ cache  │            │ keys   │               │ reqs   │
  │ 95%    │            │ expire │               │ hit DB │
  │ hit    │            │ at     │               │ 30%    │
  │ rate   │            │ once   │               │ hit    │
  └────────┘            └────────┘               └────────┘

Fix: TTL jitter

// ❌ Bad: all keys expire at exactly 30 minutes
cache.put(key, value, Duration.ofMinutes(30));

// ✅ Good: add random jitter to spread expiry
private static final ThreadLocalRandom RANDOM = ThreadLocalRandom.current();

public Duration jitteredTtl(Duration baseTtl) {
    // Add ±20% jitter
    long baseSeconds = baseTtl.getSeconds();
    long jitter = (long) (baseSeconds * 0.2 * (RANDOM.nextDouble() - 0.5));
    return Duration.ofSeconds(baseSeconds + jitter);
}

cache.put(key, value, jitteredTtl(Duration.ofMinutes(30)));
Deployment flushed cache

Common anti-patterns that flush cache on deployment:

// ❌ In a @PostConstruct or Flyway migration
@PostConstruct
public void init() {
    // Someone thought "fresh start" was a good idea
    redisTemplate.getConnectionFactory()
        .getConnection().flushAll();
}

// ❌ In application.yml
spring:
  cache:
    redis:
      # This causes FLUSHALL on startup
      flush-on-connect: true

🚨 Never FLUSHALL in production. If you need to invalidate specific keys after a schema change, use targeted key deletion with a pattern scan: SCAN 0 MATCH "user:*" COUNT 100 with batched DEL.

Key pattern change

A subtle but devastating change — the cache key format changes between versions:

// Version 1 (before deploy)
@Cacheable(value = "users", key = "#userId")
public User getUser(Long userId) { ... }
// Generates: "users::42"

// Version 2 (after deploy) — someone "improved" the key
@Cacheable(value = "users", key = "'v2:' + #userId")
public User getUser(Long userId) { ... }
// Generates: "users::v2:42"
// All existing "users::42" keys are now orphaned!

⚠️ Mitigation: Use a versioned cache name prefix in configuration, not in annotations. When you bump the version, implement a migration that warms the new key space before removing the old one.

Memory pressure and eviction

When Redis hits maxmemory, it begins evicting keys based on the configured policy:

# Check memory status
redis-cli INFO memory
# used_memory: 8589934592  (8GB)
# maxmemory: 8589934592    (8GB — full!)
# evicted_keys: 2847561    (keys forcibly removed)

# Check eviction policy
redis-cli CONFIG GET maxmemory-policy
# "allkeys-lru"

When eviction rate exceeds insertion rate, your effective cache size shrinks and hit ratio drops. Common triggers:

  • Large objects being cached (unbounded lists, full entity graphs)
  • Key cardinality explosion (new feature caching per-request data)
  • Memory fragmentation (high fragmentation ratio > 1.5)
Redis cluster rebalancing

During resharding, hash slots migrate between nodes. Keys in migrating slots experience temporary misses:

Before Resharding:
  Node A [slots 0-5460]      Node B [slots 5461-10922]    Node C [slots 10923-16383]
  ████████████████            ████████████████             ████████████████

During Resharding (adding Node D):
  Node A [slots 0-4095]      Node B [slots 5461-10922]    Node C [slots 10923-16383]
  ████████████                ████████████████             ████████████████
       │
       │ migrating slots 4096-5460
       ▼
  Node D [slots 4096-5460]   ← Keys in transit → MISS during migration
  ██████

Redis handles ASK/MOVED redirects, but client libraries may not follow them instantly. Lettuce and Jedis handle this, but connection pool refresh can cause brief miss spikes.

Cache Stampede (Thundering Herd)

How stampedes cause ratio drops

A cache stampede occurs when a popular key expires and hundreds of concurrent requests all miss simultaneously, all query the database, and all try to repopulate the cache:

Normal Operation:                    Stampede:
                                     
  Req1 ──▶ Cache HIT ──▶ Return     Req1 ──▶ Cache MISS ──▶ DB Query ──▶ Write Cache
  Req2 ──▶ Cache HIT ──▶ Return     Req2 ──▶ Cache MISS ──▶ DB Query ──▶ Write Cache
  Req3 ──▶ Cache HIT ──▶ Return     Req3 ──▶ Cache MISS ──▶ DB Query ──▶ Write Cache
  Req4 ──▶ Cache HIT ──▶ Return     Req4 ──▶ Cache MISS ──▶ DB Query ──▶ Write Cache
                                     ...
  1 DB query per TTL cycle           500 DB queries in 100ms!
                                     
  DB Load: ░░░░░ (minimal)           DB Load: █████████████████ (overwhelmed)

🚨 Stampede cascades: DB overload → slower responses → more requests queue up → connection pool exhaustion → timeout errors → even more cache misses (because writes fail) → death spiral.

Prevention strategies

1. Distributed Lock (Mutex)

Only one thread recomputes the value; others wait or get stale data:

@Component
public class StampedeProtectedCache {

    private final StringRedisTemplate redis;
    private final RedissonClient redisson;

    public <T> T getWithLock(String key, Class<T> type,
                              Supplier<T> loader, Duration ttl) {
        // Try cache first
        String cached = redis.opsForValue().get(key);
        if (cached != null) {
            return deserialize(cached, type);
        }

        // Acquire distributed lock
        RLock lock = redisson.getLock("lock:" + key);
        try {
            // Wait up to 5s for lock, hold for max 10s
            if (lock.tryLock(5, 10, TimeUnit.SECONDS)) {
                try {
                    // Double-check after acquiring lock
                    cached = redis.opsForValue().get(key);
                    if (cached != null) {
                        return deserialize(cached, type);
                    }

                    // Only one thread reaches here
                    T value = loader.get();
                    redis.opsForValue().set(key, serialize(value), ttl);
                    return value;
                } finally {
                    lock.unlock();
                }
            } else {
                // Lock timeout — return stale or throw
                throw new CacheLoadTimeoutException(key);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new CacheException("Interrupted while waiting for lock", e);
        }
    }
}

2. Probabilistic Early Expiration (XFetch)

Keys recompute before they actually expire, based on a probability that increases as TTL approaches zero:

public <T> T getWithEarlyExpiry(String key, Class<T> type,
                                  Supplier<T> loader, Duration ttl) {
    CacheEntry<T> entry = getCacheEntry(key, type);

    if (entry != null) {
        double remainingTtl = entry.getExpiresAt() - System.currentTimeMillis();
        double delta = entry.getComputeTime(); // How long the value took to compute
        double beta = 1.0; // Tuning parameter

        // XFetch algorithm: probabilistic early recomputation
        boolean shouldRecompute = remainingTtl <=
            delta * beta * Math.log(Math.random());

        if (!shouldRecompute) {
            return entry.getValue(); // Cache HIT
        }
        // Fall through to recompute (early refresh)
    }

    long start = System.currentTimeMillis();
    T value = loader.get();
    long computeTime = System.currentTimeMillis() - start;

    CacheEntry<T> newEntry = new CacheEntry<>(value, computeTime,
        System.currentTimeMillis() + ttl.toMillis());
    putCacheEntry(key, newEntry, ttl);
    return value;
}

3. Stale-While-Revalidate

Return stale data immediately while refreshing in the background:

@Component
public class StaleWhileRevalidateCache {

    private final StringRedisTemplate redis;
    private final TaskExecutor asyncExecutor;

    public <T> T getStaleWhileRevalidate(String key, Class<T> type,
                                           Supplier<T> loader,
                                           Duration hardTtl,
                                           Duration softTtl) {
        String raw = redis.opsForValue().get(key);
        if (raw == null) {
            // Hard miss — must compute synchronously
            T value = loader.get();
            putWithSoftTtl(key, value, hardTtl, softTtl);
            return value;
        }

        CacheEntry<T> entry = deserialize(raw, type);
        if (entry.isSoftExpired()) {
            // Soft expired — return stale, refresh async
            asyncExecutor.execute(() -> {
                T fresh = loader.get();
                putWithSoftTtl(key, fresh, hardTtl, softTtl);
            });
        }

        return entry.getValue(); // Always returns immediately
    }

    private <T> void putWithSoftTtl(String key, T value,
                                      Duration hardTtl, Duration softTtl) {
        CacheEntry<T> entry = new CacheEntry<>(value,
            Instant.now().plus(softTtl));
        redis.opsForValue().set(key, serialize(entry), hardTtl);
    }
}

Eviction Policies Deep Dive

Redis eviction policies explained

Redis supports 8 eviction policies, configured via maxmemory-policy:

Policy Scope Algorithm Use Case
noeviction — Return errors on write when full Data you cannot afford to lose
allkeys-lru All keys Approximate LRU General-purpose caching (recommended)
allkeys-lfu All keys Approximate LFU Frequency-based workloads
allkeys-random All keys Random eviction Uniform access patterns
volatile-lru Keys with TTL Approximate LRU Mix of persistent + cache keys
volatile-lfu Keys with TTL Approximate LFU Frequency + TTL workloads
volatile-random Keys with TTL Random eviction Uniform access with TTL
volatile-ttl Keys with TTL Shortest TTL first Time-sensitive data

⚠️ Common misconfiguration: Using volatile-lru when most keys don't have TTL set. Redis can't evict keys without TTL under volatile policies → OOM errors → all writes fail → catastrophic miss ratio.

LRU vs LFU: when wrong policy kills hit ratio

Redis uses approximated LRU (samples N keys, evicts the least recently used among them). The sample size is configurable:

# Default samples 5 keys — increase for better accuracy at slight CPU cost
CONFIG SET maxmemory-samples 10
LRU Problem — "Scan pollution":

  Time ──▶  Hot Keys (accessed every second):  A B C D E
            Cold scan (one-time batch job):     X₁ X₂ X₃ ... X₁₀₀₀₀

  With LRU: Scan keys are "recently used" → evict hot keys A-E
  Result:   Hot key misses → hit ratio drops

LFU Solution:

  Key A: frequency counter = 2,847 (high)
  Key X₁: frequency counter = 1 (just accessed once)

  LFU correctly keeps A, evicts X₁
  Result:   Hit ratio preserved despite scan
        
# Switch to LFU for scan-resistant caching
CONFIG SET maxmemory-policy allkeys-lfu

# Tune LFU parameters
# lfu-log-factor: higher = slower counter growth (default 10)
# lfu-decay-time: minutes before counter is halved (default 1)
CONFIG SET lfu-log-factor 10
CONFIG SET lfu-decay-time 1

💡 When to switch to LFU: If you have batch jobs, scrapers, or admin scans that pollute the cache with one-time access keys, LFU preserves your hot working set. Check with OBJECT FREQ key to see access frequency counters.

TTL strategies for optimal hit ratio 
@Configuration
public class TtlStrategyConfig {

    // Different TTLs based on data volatility and cost
    public enum CacheTier {
        // Rarely changes, expensive to compute
        REFERENCE_DATA(Duration.ofHours(24), Duration.ofHours(4)),
        // Changes occasionally, moderate cost
        USER_PROFILE(Duration.ofMinutes(30), Duration.ofMinutes(5)),
        // Changes frequently, cheap to compute
        SESSION_DATA(Duration.ofMinutes(5), Duration.ofSeconds(30)),
        // Real-time data, very short cache
        STOCK_PRICE(Duration.ofSeconds(10), Duration.ofSeconds(2));

        private final Duration hardTtl;  // Max time in cache
        private final Duration softTtl;  // Time before background refresh

        CacheTier(Duration hardTtl, Duration softTtl) {
            this.hardTtl = hardTtl;
            this.softTtl = softTtl;
        }

        public Duration getJitteredHardTtl() {
            long base = hardTtl.toSeconds();
            long jitter = ThreadLocalRandom.current()
                .nextLong(-base / 5, base / 5);
            return Duration.ofSeconds(base + jitter);
        }
    }
}

// Spring Boot listener for cache eviction events
@Component
public class CacheEvictionListener {

    private final MeterRegistry meterRegistry;

    @Bean
    public RedisMessageListenerContainer redisListenerContainer(
            RedisConnectionFactory connectionFactory) {
        RedisMessageListenerContainer container =
            new RedisMessageListenerContainer();
        container.setConnectionFactory(connectionFactory);

        // Listen for eviction events
        container.addMessageListener(
            (message, pattern) -> {
                String key = new String(message.getBody());
                meterRegistry.counter("cache.eviction",
                    "key_prefix", extractPrefix(key)).increment();
                log.warn("Key evicted: {}", key);
            },
            new PatternTopic("__keyevent@*__:evicted")
        );

        return container;
    }

    private String extractPrefix(String key) {
        int idx = key.indexOf(':');
        return idx > 0 ? key.substring(0, idx) : key;
    }
}

Production Incident: Serialization Format Change

The incident timeline

🚨 Real Incident: A deployment changed the Jackson serialization configuration for cached entities. All existing cache entries became unreadable. Hit ratio dropped from 95% to ~5% in 30 seconds. Database connection pool exhausted within 2 minutes.

Timeline:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

14:00  Deploy v2.4.1 starts rolling out (canary → 10% traffic)
       - Changed: ObjectMapper now uses SNAKE_CASE property naming
       - Changed: Added @JsonTypeInfo for polymorphic entities

14:01  Cache hit ratio drops to 82% (canary nodes missing on reads)
       - Old format: {"userId": 42, "firstName": "John"}
       - New format: {"user_id": 42, "first_name": "John", "@type": "..."}
       - Deserialization throws InvalidFormatException → treated as MISS

14:03  Full rollout triggered (automated, hit ratio threshold was 50%)
       - All nodes now read with new format
       - 100% of existing cache entries are unreadable
       - Hit ratio: 5%

14:04  Database connection pool exhausted (200 connections maxed)
       - p99 latency: 12s (up from 45ms)

Root cause analysis

The root cause was a seemingly innocent configuration change in JacksonAutoConfiguration:

// BEFORE (v2.4.0)
@Bean
public ObjectMapper objectMapper() {
    return new ObjectMapper()
        .registerModule(new JavaTimeModule())
        .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
}

// AFTER (v2.4.1) — "improvement" for API consistency
@Bean
public ObjectMapper objectMapper() {
    return new ObjectMapper()
        .registerModule(new JavaTimeModule())
        .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
        .setPropertyNamingStrategy(PropertyNamingStrategies.SNAKE_CASE) // 💣
        .activateDefaultTyping(                                         // 💣
            BasicPolymorphicTypeValidator.builder()
                .allowIfSubType("com.company")
                .build(),
            ObjectMapper.DefaultTyping.NON_FINAL);
}

⚠️ The ObjectMapper was shared between REST API serialization and cache serialization. Changing it for API consistency broke all cached data. Cache serialization should use its own dedicated ObjectMapper.

The fix: isolated cache serializer 
@Configuration
public class CacheSerializationConfig {

    /**
     * Dedicated ObjectMapper for cache serialization.
     * NEVER share with REST API ObjectMapper.
     * Version the format to detect incompatibilities.
     */
    @Bean("cacheObjectMapper")
    public ObjectMapper cacheObjectMapper() {
        return new ObjectMapper()
            .registerModule(new JavaTimeModule())
            .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
            .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
            // Explicit: do NOT use naming strategies
            .setPropertyNamingStrategy(PropertyNamingStrategies.LOWER_CAMEL_CASE);
    }

    @Bean
    public RedisSerializer<Object> cacheValueSerializer(
            @Qualifier("cacheObjectMapper") ObjectMapper mapper) {
        GenericJackson2JsonRedisSerializer serializer =
            new GenericJackson2JsonRedisSerializer(mapper);
        return serializer;
    }

    @Bean
    public RedisCacheConfiguration redisCacheConfiguration(
            RedisSerializer<Object> cacheValueSerializer) {
        return RedisCacheConfiguration.defaultCacheConfig()
            .serializeValuesWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(cacheValueSerializer))
            .prefixCacheNameWith("v1:");  // Version prefix for future migrations
    }
}

// Add temporary diagnostic logging for cache operations
@Aspect
@Component
@ConditionalOnProperty("cache.diagnostics.enabled")
public class CacheDiagnosticAspect {

    private final MeterRegistry meterRegistry;
    private static final Logger log = LoggerFactory.getLogger(
        CacheDiagnosticAspect.class);

    @Around("@annotation(cacheable)")
    public Object diagnoseCache(ProceedingJoinPoint pjp,
                                 Cacheable cacheable) throws Throwable {
        String cacheName = cacheable.value().length > 0
            ? cacheable.value()[0] : "default";
        String key = generateKey(pjp, cacheable);

        long start = System.nanoTime();
        Object result = pjp.proceed();
        long elapsed = System.nanoTime() - start;

        // If the method executed (not from cache), it's a miss
        if (elapsed > 1_000_000) { // > 1ms suggests DB call, not cache hit
            meterRegistry.counter("cache.diagnostic.miss",
                "cache", cacheName,
                "method", pjp.getSignature().toShortString())
                .increment();
            log.debug("Cache MISS: cache={}, key={}, elapsed={}ms",
                cacheName, key, elapsed / 1_000_000);
        } else {
            meterRegistry.counter("cache.diagnostic.hit",
                "cache", cacheName).increment();
        }

        return result;
    }
}

@Component
public class CacheWarmer {

     * Warm cache with top-N most accessed entities.
     * Called on startup or after cache flush incident.

    @Async
    @EventListener(ApplicationReadyEvent.class)
    public void warmOnStartup() {
        log.info("Starting cache warm-up...");
        Instant start = Instant.now();

        // Get hot keys from access logs or pre-computed list
        List<Long> hotUserIds = userRepository
            .findMostAccessedUserIds(PageRequest.of(0, 10000));

        AtomicInteger warmed = new AtomicInteger(0);
        AtomicInteger errors = new AtomicInteger(0);

        // Process in parallel batches
        Lists.partition(hotUserIds, BATCH_SIZE).parallelStream()
            .forEach(batch -> {
                try {
                    List<User> users = userRepository.findAllById(batch);
                    Pipeline pipeline = redis.executePipelined(
                        (RedisCallback<Object>) connection -> {
                            for (User user : users) {
                                String key = "v2:user:" + user.getId();
                                String value = cacheMapper.writeValueAsString(user);
                                Duration ttl = jitteredTtl(Duration.ofMinutes(30));

                                    key.getBytes(),
                                    ttl.getSeconds(),
                                    value.getBytes());

Complete multi-tier cache with Caffeine + Redis 
@Component
public class MultiTierCache implements Cache {

    private final String name;
    private final com.github.benmanes.caffeine.cache.Cache<String, Object> l1;
    private final StringRedisTemplate redis;
    private final ObjectMapper mapper;
    private final MeterRegistry metrics;
    private final Duration redisTtl;

    public MultiTierCache(String name,
                          int l1MaxSize,
                          Duration l1Ttl,
                          Duration redisTtl,
                          StringRedisTemplate redis,
                          ObjectMapper mapper,
                          MeterRegistry metrics) {
        this.name = name;
        this.redisTtl = redisTtl;
        this.redis = redis;
        this.mapper = mapper;
        this.metrics = metrics;
        this.l1 = Caffeine.newBuilder()
            .maximumSize(l1MaxSize)
            .expireAfterWrite(l1Ttl)
            .recordStats()
            .build();
    }

    @Override
    public ValueWrapper get(Object key) {
        String cacheKey = toKey(key);

        // L1: In-process (Caffeine)
        Object l1Value = l1.getIfPresent(cacheKey);
        if (l1Value != null) {
            metrics.counter("cache.hit", "tier", "L1", "cache", name).increment();
            return new SimpleValueWrapper(l1Value);
        }

        // L2: Redis
        try {
            String redisValue = redis.opsForValue().get(redisKey(cacheKey));
            if (redisValue != null) {
                Object deserialized = mapper.readValue(redisValue, Object.class);
                l1.put(cacheKey, deserialized); // Promote to L1
                metrics.counter("cache.hit", "tier", "L2", "cache", name).increment();
                return new SimpleValueWrapper(deserialized);
            }
        } catch (RedisConnectionException e) {
            // Redis down — degrade gracefully, don't fail
            metrics.counter("cache.error", "type", "connection", "cache", name)
                .increment();
            log.warn("Redis unavailable for key {}: {}", cacheKey, e.getMessage());
        } catch (Exception e) {
            // Deserialization error — key is corrupted/incompatible
            metrics.counter("cache.error", "type", "deserialization", "cache", name)
                .increment();
            log.warn("Cache deserialization failed for key {}: {}",
                cacheKey, e.getMessage());
            // Delete corrupted entry
            redis.delete(redisKey(cacheKey));
        }

        metrics.counter("cache.miss", "cache", name).increment();
        return null;
    }

    @Override
    public void put(Object key, Object value) {
        String cacheKey = toKey(key);

        // Write to both tiers
        l1.put(cacheKey, value);

        try {
            String serialized = mapper.writeValueAsString(value);
            redis.opsForValue().set(redisKey(cacheKey), serialized,
                jitteredTtl(redisTtl));
        } catch (Exception e) {
            metrics.counter("cache.error", "type", "write", "cache", name)
                .increment();
            log.error("Failed to write to Redis cache: {}", cacheKey, e);
        }
    }

    @Override
    public void evict(Object key) {
        String cacheKey = toKey(key);
        l1.invalidate(cacheKey);
        redis.delete(redisKey(cacheKey));
    }

    @Override
    public void clear() {
        l1.invalidateAll();
        // Don't FLUSHALL! Only clear keys with our prefix
        Set<String> keys = redis.keys(name + ":*");
        if (keys != null && !keys.isEmpty()) {
            redis.delete(keys);
        }
    }

    private String redisKey(String key) {
        return name + ":" + key;
    }

    private String toKey(Object key) {
        return key == null ? "null" : key.toString();
    }

    private Duration jitteredTtl(Duration base) {
        long jitter = ThreadLocalRandom.current()
            .nextLong(-base.toSeconds() / 5, base.toSeconds() / 5);
        return base.plusSeconds(jitter);
    }
}
Distributed lock for stampede prevention (Redisson) 
@Service
public class StampedeProtectedUserService {

    private final UserRepository userRepository;
    private final StringRedisTemplate redis;
    private final RedissonClient redisson;
    private final ObjectMapper mapper;

    private static final Duration CACHE_TTL = Duration.ofMinutes(30);
    private static final Duration LOCK_WAIT = Duration.ofSeconds(5);
    private static final Duration LOCK_LEASE = Duration.ofSeconds(10);

    @Cacheable(value = "users", unless = "#result == null")
    public User getUser(Long userId) {
        return loadWithStampedeProtection(userId);
    }

    private User loadWithStampedeProtection(Long userId) {
        String key = "user:" + userId;
        String lockKey = "lock:user:" + userId;

        // Try cache
        String cached = redis.opsForValue().get(key);
        if (cached != null) {
            return deserialize(cached);
        }

        // Cache miss — acquire lock to prevent stampede
        RLock lock = redisson.getLock(lockKey);
        try {
            boolean acquired = lock.tryLock(
                LOCK_WAIT.toMillis(), LOCK_LEASE.toMillis(),
                TimeUnit.MILLISECONDS);

            if (acquired) {
                try {
                    // Double-check pattern
                    cached = redis.opsForValue().get(key);
                    if (cached != null) {
                        return deserialize(cached);
                    }

                    // Single thread loads from DB
                    User user = userRepository.findById(userId)
                        .orElseThrow(() -> new UserNotFoundException(userId));

                    redis.opsForValue().set(key, serialize(user),
                        jitteredTtl(CACHE_TTL));
                    return user;
                } finally {
                    if (lock.isHeldByCurrentThread()) {
                        lock.unlock();
                    }
                }
            } else {
                // Lock timeout — another thread is loading
                // Wait briefly and retry cache
                Thread.sleep(100);
                cached = redis.opsForValue().get(key);
                if (cached != null) {
                    return deserialize(cached);
                }
                // Fallback: load from DB (accept duplicate query)
                return userRepository.findById(userId)
                    .orElseThrow(() -> new UserNotFoundException(userId));
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new CacheException("Interrupted during cache load", e);
        }
    }
}
Stale-while-revalidate with Spring Boot 
@Component
public class StaleWhileRevalidateService {

    private final StringRedisTemplate redis;
    private final ObjectMapper mapper;
    private final ThreadPoolTaskExecutor refreshExecutor;

    // Track in-flight refreshes to avoid duplicate background loads
    private final ConcurrentHashMap<String, Boolean> refreshInFlight =
        new ConcurrentHashMap<>();

    public <T> T get(String key, Class<T> type, Supplier<T> loader,
                      Duration softTtl, Duration hardTtl) {
        String raw = redis.opsForValue().get(key);

        if (raw == null) {
            // Hard miss — synchronous load
            T value = loader.get();
            store(key, value, softTtl, hardTtl);
            return value;
        }

        TimestampedValue<T> entry = deserializeWithTimestamp(raw, type);

        if (entry.isSoftExpired(softTtl)) {
            // Soft expired — return stale, refresh in background
            triggerAsyncRefresh(key, type, loader, softTtl, hardTtl);
        }

        return entry.getValue();
    }

    private <T> void triggerAsyncRefresh(String key, Class<T> type,
                                           Supplier<T> loader,
                                           Duration softTtl,
                                           Duration hardTtl) {
        // Deduplicate concurrent refresh attempts
        if (refreshInFlight.putIfAbsent(key, Boolean.TRUE) != null) {
            return; // Already refreshing
        }

        refreshExecutor.execute(() -> {
            try {
                T fresh = loader.get();
                store(key, fresh, softTtl, hardTtl);
            } catch (Exception e) {
                log.warn("Background refresh failed for key {}: {}",
                    key, e.getMessage());
            } finally {
                refreshInFlight.remove(key);
            }
        });
    }

    private <T> void store(String key, T value,
                            Duration softTtl, Duration hardTtl) {
        TimestampedValue<T> entry = new TimestampedValue<>(value, Instant.now());
        String serialized = serialize(entry);
        redis.opsForValue().set(key, serialized, hardTtl);
    }

    @Data
    @AllArgsConstructor
    @NoArgsConstructor
    static class TimestampedValue<T> {
        private T value;
        private Instant storedAt;

        boolean isSoftExpired(Duration softTtl) {
            return Instant.now().isAfter(storedAt.plus(softTtl));
        }
    }
}

Common Mistakes

Mistakes that cause or worsen hit ratio drops
Mistake Why It's Wrong Correct Approach
Shared ObjectMapper for API and cache API serialization changes break cached data Dedicated, version-pinned ObjectMapper for cache
Same TTL for all keys Mass expiry causes thundering herd TTL jitter (±20%) and tiered TTLs by data type
No eviction monitoring Silent memory pressure goes unnoticed Alert on evicted_keys rate and memory usage
FLUSHALL in deployment scripts 100% cache miss rate, DB overload Targeted invalidation with SCAN + DEL
Caching null/empty results without TTL Cache pollution with useless entries Short TTL for negative caching (30s-5min)
No fallback when Redis is down Complete service failure on Redis outage L1 cache + circuit breaker + graceful degradation
Unbounded cache key cardinality Memory explosion, constant eviction Bound key space, use aggregation for high-cardinality data
No cache versioning Schema changes make entries unreadable Version prefix in cache name (v1:users:42)
Ignoring serialization errors Silent misses counted as cache "misses" Log and metric on deserialization failures separately
Using KEYS command in production Blocks Redis (single-threaded), causes timeouts Use SCAN with COUNT for iterative discovery

Cache Consistency vs Performance Matrix

Trade-off analysis
Strategy Consistency Hit Ratio Latency (p50) Latency (p99) Complexity
Write-through Strong 95%+ ~5ms (write penalty) ~15ms Low
Write-behind (async) Eventual 98%+ ~1ms ~5ms High (data loss risk)
Cache-aside (lazy) Eventual 85-95% ~2ms (hit) ~200ms (miss) Low
Read-through Eventual 90-95% ~2ms ~100ms Medium
Refresh-ahead Eventual 98%+ ~1ms ~3ms High

Choosing the right strategy:

  • Write-through: When consistency matters more than write latency (user profiles, permissions)
  • Cache-aside: General purpose, most common in Spring Boot apps
  • Refresh-ahead: For hot keys where you can predict access (product catalog, config)
  • Write-behind: High-write workloads where eventual consistency is acceptable (analytics, counters)

💡 For preventing hit ratio drops: Refresh-ahead (stale-while-revalidate) gives the best hit ratio because keys never actually expire from the reader's perspective. The trade-off is background thread overhead and potential staleness.

Follow-up Questions

Questions the interviewer might ask next
  1. "How would you handle a hot key that receives 100K requests/second?"

    Use local L1 cache (Caffeine) to absorb hot key traffic. For Redis, use read replicas or key replication across multiple slots. Consider client-side caching with Redis 6+ RESP3 protocol and server-assisted invalidation.

  2. "How do you ensure cache consistency across microservices?"

    Event-driven invalidation via Kafka/SNS. Publish cache invalidation events when data changes. Each service subscribes and invalidates its local cache. Use logical timestamps to handle out-of-order events.

  3. "What if your Redis cluster goes down completely?"

    Circuit breaker to bypass cache, fall through to DB with aggressive rate limiting. L1 (Caffeine) serves what it can. Pre-provision DB capacity for cache-down scenario. Consider Redis Sentinel or Cluster mode for HA.

  4. "How would you migrate from one cache key format to another without downtime?"

    Dual-read strategy: try new format first, fall back to old format. Write in new format only. Old keys naturally expire. Monitor both key spaces. Similar to blue-green but for cache data.

  5. "How do you prevent cache penetration (queries for non-existent data)?"

    Bloom filter at the cache layer to reject known-missing keys. Cache null results with short TTL (negative caching). Rate-limit per-key to prevent enumeration attacks.

  6. "How would you size your Redis cluster for this workload?"

    Calculate: (average_value_size × key_count × replication_factor) + overhead. Add 30% headroom for fragmentation. Consider: peak QPS × avg_latency for connection pool sizing. Use Redis benchmarks to validate.

Summary

Key points to remember
  1. Correlate first: Always check deployment history, config changes, and traffic patterns before diving into Redis internals
  2. Mitigate before debugging: Scale DB, enable circuit breakers, rate-limit the miss path — then investigate root cause
  3. Serialization is the #1 killer: Use a dedicated, versioned ObjectMapper for cache — never share with REST API configuration
  4. TTL jitter prevents stampedes: Add ±20% randomness to all TTLs to prevent synchronized mass expiry
  5. Multi-tier caching (L1+L2) provides resilience: Caffeine absorbs hot keys locally even when Redis has issues
  6. Monitor eviction rate, not just hit ratio: Rising evictions are a leading indicator of future hit ratio drops
  7. LFU over LRU for scan-heavy workloads: Prevents cache pollution from batch jobs and scrapers
  8. Stale-while-revalidate eliminates user-visible misses: Return stale data immediately, refresh asynchronously
  9. Test serialization compatibility in CI: Catch format changes before they reach production
  10. Version your cache key format: Enables safe migrations and rollbacks without data loss

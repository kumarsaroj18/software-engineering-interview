Your Application Is Using Asynchronous Methods, but Requests Are Still Blocking. Why?

Medium @Async Virtual Threads

1. Interviewer Intent

What is the interviewer really assessing?

When a senior engineer is asked this question at a FAANG-level interview, the interviewer is probing several dimensions simultaneously:

  • Proxy mechanics understanding: Does the candidate understand how Spring AOP proxies work, and why self-invocation bypasses @Async?
  • Thread pool expertise: Can they reason about thread pool saturation, queue sizing, and rejection policies under load?
  • Reactive vs. imperative awareness: Do they know the difference between non-blocking I/O and merely offloading work to another thread?
  • Production debugging skills: Can they identify and resolve blocking issues in a live system under time pressure?
  • Modern Java fluency: Are they current with Virtual Threads (Project Loom) and understand when reactive is still preferable?
  • Systems thinking: Do they see the full request lifecycle — from Tomcat NIO connector through to downstream I/O?

This question separates engineers who have merely used @Async from those who have debugged production incidents involving async processing at scale.

Expected depth for a 12+ year senior engineer
  • Immediate identification of at least 4-5 root causes without prompting
  • Ability to whiteboard the proxy chain and executor selection process
  • Discussion of thread dump analysis and how to identify blocked async threads
  • Contrast between "async" (offloading to thread pool) and "non-blocking" (event loop)
  • Virtual Threads as a paradigm shift — when they help and when they don't
  • Real production war stories with concrete metrics and resolutions

2. Quick Answer (60-Second Version)

Concise answer for time-pressured interviews

An application using @Async can still block for these primary reasons:

  1. Self-invocation: Calling an @Async method from within the same class bypasses the proxy — the method runs synchronously on the caller's thread.
  2. Missing @EnableAsync: Without this configuration annotation, Spring never registers the AsyncAnnotationBeanPostProcessor, so @Async is silently ignored.
  3. Thread pool exhaustion: When all threads in the async executor are busy and the queue is full, new tasks block or are rejected.
  4. Blocking calls inside async/reactive code: Using JDBC, Thread.sleep(), or synchronized blocks inside a reactive pipeline or on an event-loop thread blocks the entire pipeline.
  5. CompletableFuture.get() on the request thread: Calling .get() without a timeout blocks the HTTP thread waiting for the async result, negating all benefits.
  6. Default executor issues: SimpleAsyncTaskExecutor creates a new thread per invocation with no pooling, leading to unbounded thread creation under load.

Key insight: @Async does not make code non-blocking — it offloads execution to another thread. If that thread pool is saturated or the caller blocks waiting for the result, the request still appears to block from the client's perspective.

3. Async Programming Models in Java/Spring

Thread Pool Based (@Async, ExecutorService)

The most traditional approach in Spring Boot applications. Work is submitted to a thread pool, freeing the caller thread to handle other requests.

// Traditional ExecutorService approach
ExecutorService executor = Executors.newFixedThreadPool(10);
Future<String> future = executor.submit(() -> {
    return callExternalService(); // Runs on pool thread
});
// Caller thread is free... unless you call future.get()

// Spring @Async approach
@Service
public class NotificationService {

    @Async("notificationExecutor")
    public CompletableFuture<NotificationResult> sendNotification(User user) {
        // Executes on the named executor's thread pool
        NotificationResult result = emailGateway.send(user.getEmail(), buildTemplate(user));
        return CompletableFuture.completedFuture(result);
    }
}

Characteristics:

  • Offloads work to a different thread — the original thread is freed
  • Bounded by thread pool size (core pool, max pool, queue capacity)
  • Each pool thread can still perform blocking I/O (JDBC, HTTP calls)
  • Does NOT achieve true non-blocking I/O — just thread offloading
  • Simple mental model, well-understood debugging (thread dumps work normally)
CompletableFuture Composition

Java 8+ CompletableFuture enables composing async operations without blocking the calling thread:

@Service
public class OrderService {

    @Autowired private InventoryClient inventoryClient;
    @Autowired private PricingClient pricingClient;
    @Autowired private UserClient userClient;

    public CompletableFuture<OrderSummary> buildOrderSummary(String orderId) {
        CompletableFuture<Inventory> inventoryFuture =
            CompletableFuture.supplyAsync(() -> inventoryClient.check(orderId), asyncExecutor);

        CompletableFuture<Pricing> pricingFuture =
            CompletableFuture.supplyAsync(() -> pricingClient.calculate(orderId), asyncExecutor);

        CompletableFuture<UserProfile> userFuture =
            CompletableFuture.supplyAsync(() -> userClient.getProfile(orderId), asyncExecutor);

        // Compose all three — no thread blocks waiting
        return CompletableFuture.allOf(inventoryFuture, pricingFuture, userFuture)
            .thenApply(ignored -> new OrderSummary(
                inventoryFuture.join(),
                pricingFuture.join(),
                userFuture.join()
            ));
    }
}

Key pitfall: If you call .get() or .join() on the HTTP request thread, you convert the async pipeline back into a synchronous, blocking call.

WebFlux / Project Reactor (Reactive Streams)

Spring WebFlux uses an event-loop model with non-blocking I/O throughout the entire stack:

@RestController
public class ReactiveOrderController {

    @Autowired private ReactiveInventoryClient inventoryClient;
    @Autowired private ReactivePricingClient pricingClient;

    @GetMapping("/orders/{id}/summary")
    public Mono<OrderSummary> getOrderSummary(@PathVariable String id) {
        Mono<Inventory> inventory = inventoryClient.check(id);   // Non-blocking
        Mono<Pricing> pricing = pricingClient.calculate(id);     // Non-blocking

        return Mono.zip(inventory, pricing)
            .map(tuple -> new OrderSummary(tuple.getT1(), tuple.getT2()));
    }
}

Critical distinction: WebFlux is non-blocking at the I/O level. A single event-loop thread can handle thousands of concurrent requests because it never blocks waiting for network responses. However, introducing a single blocking call (JDBC, Thread.sleep, synchronized) on the event-loop thread will block ALL concurrent requests on that thread.

Aspect @Async (Thread Pool) WebFlux (Reactive)
Concurrency model Thread-per-task Event loop
Blocking I/O allowed? Yes (on pool threads) No — kills throughput
Thread count under load Grows to max pool size Fixed (CPU cores × 2)
Debugging Standard thread dumps Complex (assembly traces)
Backpressure Queue + rejection policy Built-in (Reactive Streams)
Virtual Threads (Java 21+ / Project Loom)

Virtual Threads fundamentally change the async landscape by making blocking cheap:

// Spring Boot 3.2+ with virtual threads enabled
// application.yml:
// spring.threads.virtual.enabled: true

// Every HTTP request gets its own virtual thread
// Blocking I/O is fine — the JVM unmounts the virtual thread from the carrier

@RestController
public class OrderController {

    @GetMapping("/orders/{id}")
    public OrderSummary getOrder(@PathVariable String id) {
        // These look blocking but virtual threads make them cheap
        Inventory inv = inventoryClient.check(id);        // Blocks virtual thread, not carrier
        Pricing price = pricingClient.calculate(id);      // Same — carrier is released
        return new OrderSummary(inv, price);
    }
}

Why this matters: Virtual Threads allow you to write straightforward synchronous-looking code while achieving the throughput of asynchronous systems. The JVM handles the multiplexing — when a virtual thread blocks on I/O, its carrier (platform) thread is released to run other virtual threads.

  • Millions of virtual threads can exist simultaneously
  • Blocking I/O automatically yields the carrier thread
  • No need for reactive APIs or callback chains
  • Standard debugging tools work (stack traces are preserved)
  • Caveat: synchronized blocks and native methods can "pin" the virtual thread to its carrier
Comparison Matrix: When to Use Each Model
Scenario Recommended Model Rationale
Fire-and-forget tasks (email, logging) @Async with bounded pool Simple, well-understood, no result needed
Fan-out to multiple services CompletableFuture or Virtual Threads Parallel execution with result composition
High-concurrency streaming (WebSocket, SSE) WebFlux / Reactor Backpressure needed, event-driven nature
Traditional CRUD with high throughput Virtual Threads (Java 21+) Simple code, blocking JDBC is fine
Legacy migration (Java 8-17) @Async + ThreadPoolTaskExecutor Pragmatic, incremental improvement

4. Why Async Methods Still Block — Root Causes

4.1 @Async Self-Invocation (Proxy Bypass)

The most common and insidious cause. When a method within the same class calls an @Async method, the call bypasses the Spring proxy — exactly the same issue as @Transactional self-invocation.

@Service
public class ReportService {

    // THIS WILL NOT RUN ASYNCHRONOUSLY!
    public void generateFullReport(String reportId) {
        // Self-invocation — bypasses the proxy
        generatePdfAsync(reportId);  // Runs synchronously on caller's thread!
    }

    @Async("reportExecutor")
    public void generatePdfAsync(String reportId) {
        // Intended to run on async thread, but won't if called internally
        pdfEngine.generate(reportId);  // Takes 30 seconds
    }
}

Why this happens:

// What Spring actually creates:
// ReportService$$SpringCGLIB$$Proxy extends ReportService
//
// External call path (WORKS):
//   caller → proxy.generatePdfAsync() → interceptor → executor.submit() → target.generatePdfAsync()
//
// Self-invocation path (BROKEN):
//   caller → proxy.generateFullReport() → target.generateFullReport() → target.generatePdfAsync()
//                                                                         ↑ Direct call, no proxy!

Solutions:

// Solution 1: Inject self reference
@Service
public class ReportService {
    @Lazy @Autowired private ReportService self;

    public void generateFullReport(String reportId) {
        self.generatePdfAsync(reportId);  // Goes through proxy!
    }

    @Async("reportExecutor")
    public void generatePdfAsync(String reportId) {
        pdfEngine.generate(reportId);
    }
}

// Solution 2: Extract to separate service
@Service
public class ReportOrchestrator {
    @Autowired private AsyncReportGenerator generator;

    public void generateFullReport(String reportId) {
        generator.generatePdfAsync(reportId);  // Different bean = goes through proxy
    }
}

@Service
public class AsyncReportGenerator {
    @Async("reportExecutor")
    public void generatePdfAsync(String reportId) {
        pdfEngine.generate(reportId);
    }
}

// Solution 3: Use AopContext (requires exposeProxy=true)
@EnableAspectJAutoProxy(exposeProxy = true)
@Configuration
public class AopConfig {}

@Service
public class ReportService {
    public void generateFullReport(String reportId) {
        ((ReportService) AopContext.currentProxy()).generatePdfAsync(reportId);
    }
}
4.2 Missing @EnableAsync Configuration

Without @EnableAsync, Spring never registers the AsyncAnnotationBeanPostProcessor. The @Async annotation is completely ignored — no warnings, no errors, just synchronous execution.

// BROKEN — @Async annotations are silently ignored
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

// FIXED — @EnableAsync activates async processing
@SpringBootApplication
@EnableAsync
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

Detection: Add a log statement in your @Async method that prints Thread.currentThread().getName(). If it prints the HTTP thread name (e.g., http-nio-8080-exec-1), @Async is not active.

@Async
public void processOrder(Order order) {
    log.info("Running on thread: {}", Thread.currentThread().getName());
    // If output is "http-nio-8080-exec-3" instead of "async-executor-1"
    // then @EnableAsync is missing!
}

Spring Boot auto-configuration note: Spring Boot's TaskExecutionAutoConfiguration creates an executor bean, but it does NOT enable @Async processing. You must explicitly add @EnableAsync.

4.3 Thread Pool Exhaustion

When all threads in the async executor's pool are busy and the work queue is full, new async task submissions will either block or be rejected depending on the rejection policy.

@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean("emailExecutor")
    public ThreadPoolTaskExecutor emailExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(10);
        executor.setQueueCapacity(25);   // Only 25 tasks can wait
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.setThreadNamePrefix("email-async-");
        executor.initialize();
        return executor;
    }
}

Scenario leading to blocking:

  1. 10 email tasks are running (max pool reached)
  2. 25 tasks are queued (queue full)
  3. Task #36 arrives → CallerRunsPolicy executes it on the caller's thread (HTTP thread)
  4. The HTTP thread is now blocked sending an email!
// Monitoring thread pool saturation
@Scheduled(fixedRate = 5000)
public void monitorAsyncPool() {
    ThreadPoolTaskExecutor executor = (ThreadPoolTaskExecutor) asyncExecutor;
    log.info("Async Pool Status - Active: {}, Pool Size: {}, Queue Size: {}, Completed: {}",
        executor.getActiveCount(),
        executor.getPoolSize(),
        executor.getThreadPoolExecutor().getQueue().size(),
        executor.getThreadPoolExecutor().getCompletedTaskCount());

    double utilization = (double) executor.getActiveCount() / executor.getMaxPoolSize();
    if (utilization > 0.8) {
        log.warn("Async thread pool utilization at {}% - risk of saturation!", 
            (int)(utilization * 100));
    }
}

Rejection policies and their blocking behavior:

Policy Behavior When Pool + Queue Full Blocks Caller?
AbortPolicy (default) Throws RejectedExecutionException No (fails fast)
CallerRunsPolicy Executes on caller's thread YES — blocks HTTP thread
DiscardPolicy Silently drops the task No (data loss risk)
DiscardOldestPolicy Drops oldest queued task, retries No (data loss risk)
4.4 Blocking Calls Inside Reactive Chain (JDBC in WebFlux)

The deadliest anti-pattern in reactive programming: performing blocking I/O on an event-loop thread. Since WebFlux uses a small, fixed-size thread pool (typically CPU cores × 2), blocking one thread blocks a significant percentage of your application's capacity.

// DEADLY — Blocking JDBC call on reactor-http-nio thread
@GetMapping("/users/{id}")
public Mono<User> getUser(@PathVariable Long id) {
    return Mono.fromCallable(() -> {
        // This blocks the event-loop thread!
        return jdbcTemplate.queryForObject(
            "SELECT * FROM users WHERE id = ?", userRowMapper, id);
    });
    // Without subscribeOn(Schedulers.boundedElastic()), this runs on the event-loop!
}

// CORRECT — Offload blocking call to bounded elastic scheduler
@GetMapping("/users/{id}")
public Mono<User> getUser(@PathVariable Long id) {
    return Mono.fromCallable(() -> {
        return jdbcTemplate.queryForObject(
            "SELECT * FROM users WHERE id = ?", userRowMapper, id);
    }).subscribeOn(Schedulers.boundedElastic());  // Runs on a separate thread pool
}

// BEST — Use reactive database driver (R2DBC)
@GetMapping("/users/{id}")
public Mono<User> getUser(@PathVariable Long id) {
    return r2dbcTemplate.selectOne(
        query(where("id").is(id)), User.class);  // Truly non-blocking
}

How to detect blocking calls in reactive chains:

// Enable Reactor's BlockHound in tests
// build.gradle: testImplementation 'io.projectreactor.tools:blockhound:1.0.8.RELEASE'
@BeforeAll
static void setupBlockHound() {
    BlockHound.install();
    // Will throw an exception if any blocking call is detected on a non-blocking thread
}

// Reactor debug mode — shows where the blocking subscription originated
Hooks.onOperatorDebug();  // Expensive — use only in development

Common blocking operations that sneak into reactive chains:

  • Thread.sleep()
  • JDBC calls (Connection.prepareStatement, ResultSet.next)
  • synchronized blocks
  • ReentrantLock.lock()
  • InputStream.read() / OutputStream.write()
  • InetAddress.getByName() (DNS lookup)
  • Logging frameworks writing to disk (Log4j2 without async appender)
4.5 CompletableFuture.get() Called on Request Thread

The async work happens on a pool thread, but if the HTTP request thread calls .get() to retrieve the result, it blocks waiting — effectively converting async back to sync.

// BROKEN — .get() blocks the HTTP thread
@GetMapping("/report/{id}")
public ResponseEntity<Report> getReport(@PathVariable String id) {
    CompletableFuture<Report> future = reportService.generateAsync(id);
    try {
        Report report = future.get();  // BLOCKS HTTP THREAD!
        return ResponseEntity.ok(report);
    } catch (InterruptedException | ExecutionException e) {
        return ResponseEntity.status(500).build();
    }
}

// BETTER — Use DeferredResult for async HTTP response
@GetMapping("/report/{id}")
public DeferredResult<ResponseEntity<Report>> getReport(@PathVariable String id) {
    DeferredResult<ResponseEntity<Report>> deferredResult = new DeferredResult<>(30000L);

    reportService.generateAsync(id).thenAccept(report -> {
        deferredResult.setResult(ResponseEntity.ok(report));
    }).exceptionally(ex -> {
        deferredResult.setErrorResult(ResponseEntity.status(500).build());
        return null;
    });

    return deferredResult;  // HTTP thread released immediately
}

// BEST (Spring MVC) — Return CompletableFuture directly
@GetMapping("/report/{id}")
public CompletableFuture<ResponseEntity<Report>> getReport(@PathVariable String id) {
    return reportService.generateAsync(id)
        .thenApply(ResponseEntity::ok)
        .exceptionally(ex -> ResponseEntity.status(500).build());
    // Spring MVC handles the async completion automatically
}

Thread timeline comparison:

# Blocking pattern (.get())
HTTP-thread-1:  |---receive-request---|---BLOCKED waiting for future.get()---|---send-response---|
Async-thread-1: |                     |---doing actual work-------------------|

# Non-blocking pattern (DeferredResult)
HTTP-thread-1:  |---receive-request---|---FREE for other requests---...
Async-thread-1: |                     |---doing actual work---|---setResult()---|
HTTP-thread-1:  |...                                          |---send-response---|
4.6 @Async Returns void but Caller Waits for Result

When @Async returns void, there's no Future to await. But developers sometimes work around this by adding external synchronization, reintroducing blocking:

// Anti-pattern: External synchronization defeats @Async
@Service
public class ProcessingService {

    @Async
    public void processLargeFile(String fileId) {
        // Long-running processing...
        fileProcessor.process(fileId);
        statusStore.markComplete(fileId);
    }
}

@RestController
public class FileController {

    @PostMapping("/process/{fileId}")
    public ResponseEntity<String> processFile(@PathVariable String fileId) {
        processingService.processLargeFile(fileId);

        // ANTI-PATTERN: Polling/waiting for the void async to complete
        while (!statusStore.isComplete(fileId)) {
            Thread.sleep(100);  // BLOCKS HTTP THREAD!
        }
        return ResponseEntity.ok("Done");
    }
}

// CORRECT: Return Future and let the client poll or use WebSocket
@Service
public class ProcessingService {

    @Async("fileProcessorExecutor")
    public CompletableFuture<ProcessingResult> processLargeFile(String fileId) {
        ProcessingResult result = fileProcessor.process(fileId);
        return CompletableFuture.completedFuture(result);
    }
}

@RestController
public class FileController {

    @PostMapping("/process/{fileId}")
    public ResponseEntity<String> submitProcessing(@PathVariable String fileId) {
        processingService.processLargeFile(fileId);  // Fire and forget
        return ResponseEntity.accepted()
            .header("Location", "/process/" + fileId + "/status")
            .build();
    }

    @GetMapping("/process/{fileId}/status")
    public ResponseEntity<ProcessingStatus> getStatus(@PathVariable String fileId) {
        return ResponseEntity.ok(statusStore.getStatus(fileId));
    }
}
4.7 Default SimpleAsyncTaskExecutor — No Pooling

When no custom executor is defined, Spring falls back to SimpleAsyncTaskExecutor, which creates a new thread for every invocation without any pooling or reuse:

// Spring's default behavior when no Executor bean is defined:
public class SimpleAsyncTaskExecutor implements AsyncTaskExecutor {
    @Override
    public void execute(Runnable task) {
        // Creates a NEW thread every single time!
        Thread t = new Thread(task, getThreadNamePrefix() + this.threadCount.incrementAndGet());
        t.start();
    }
    // No pool, no queue, no upper bound (unless concurrencyLimit is set)
}

Under high load, this means:

  • 1000 concurrent async calls = 1000 OS threads created
  • Each thread consumes ~1MB of stack memory by default
  • Thread creation/destruction overhead dominates execution time
  • OS-level thread limits may be hit (unable to create native thread)
  • Context switching overhead degrades performance for ALL threads

Why this appears as "blocking": The system becomes so overloaded with threads that all requests slow to a crawl. The OS scheduler cannot efficiently context-switch thousands of threads, causing every request to appear blocked.

5. Spring @Async Internals

AsyncAnnotationBeanPostProcessor — Registration

When @EnableAsync is present, Spring registers AsyncAnnotationBeanPostProcessor which scans beans for @Async annotations and wraps them with an intercepting proxy:

// Simplified internal flow:
// 1. @EnableAsync imports AsyncConfigurationSelector
// 2. AsyncConfigurationSelector imports ProxyAsyncConfiguration
// 3. ProxyAsyncConfiguration creates AsyncAnnotationBeanPostProcessor bean
// 4. BeanPostProcessor wraps @Async-annotated beans with AOP proxy

// Key class: AsyncAnnotationBeanPostProcessor
public class AsyncAnnotationBeanPostProcessor extends AbstractBeanFactoryAwareAdvisingPostProcessor {

    @Override
    public void setBeanFactory(BeanFactory beanFactory) {
        super.setBeanFactory(beanFactory);
        // Creates an advisor with AsyncAnnotationAdvisor
        this.advisor = new AsyncAnnotationAdvisor(this.executor, this.exceptionHandler);
    }
}

// The advisor contains:
// - Pointcut: matches methods annotated with @Async
// - Advice: AsyncExecutionInterceptor (wraps method call in executor.submit())
Proxy Creation and Method Interception

The async proxy intercepts method calls and submits them to an executor:

// Simplified AsyncExecutionInterceptor logic:
public class AsyncExecutionInterceptor implements MethodInterceptor {

    @Override
    public Object invoke(MethodInvocation invocation) throws Throwable {
        // 1. Determine which executor to use
        AsyncTaskExecutor executor = determineAsyncExecutor(invocation.getMethod());

        // 2. Wrap the method call as a Callable
        Callable<Object> task = () -> {
            try {
                Object result = invocation.proceed();  // Actual method execution
                if (result instanceof Future) {
                    return ((Future<?>) result).get();
                }
            } catch (ExecutionException ex) {
                handleError(ex.getCause(), invocation.getMethod(), invocation.getArguments());
            } catch (Throwable ex) {
                handleError(ex, invocation.getMethod(), invocation.getArguments());
            }
            return null;
        };

        // 3. Submit to executor — returns immediately to caller
        return doSubmit(task, executor, invocation.getMethod().getReturnType());
    }

    // Return type handling:
    // - void: executor.submit(task), return null
    // - Future/CompletableFuture: executor.submit(task), return the Future
    // - ListenableFuture: wrap in ListenableFutureTask
}
Executor Selection Strategy

Spring uses a specific strategy to determine which executor runs the async method:

// Executor resolution order:
// 1. Qualifier specified in @Async("executorBeanName")
// 2. Executor configured via AsyncConfigurer.getAsyncExecutor()
// 3. Bean of type TaskExecutor in the context (if exactly one)
// 4. Bean named "taskExecutor" of type Executor
// 5. Fallback: SimpleAsyncTaskExecutor (no pooling!)

@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {

    @Override
    public Executor getAsyncExecutor() {
        // This becomes the default for all @Async without qualifier
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(50);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("default-async-");
        executor.initialize();
        return executor;
    }

    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (throwable, method, params) -> {
            log.error("Uncaught async exception in {}.{}(): {}",
                method.getDeclaringClass().getSimpleName(),
                method.getName(),
                throwable.getMessage(), throwable);
        };
    }
}

// Named executors for different workloads
@Configuration
public class ExecutorConfig {

        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();

}

Exception Handling in @Async Methods

Error handling differs based on return type:

// Void return type — exceptions are lost without custom handler!
@Async
public void processEvent(Event event) {
    throw new RuntimeException("Processing failed");
    // Without AsyncUncaughtExceptionHandler, this exception is SWALLOWED
}

// Future return type — exception is captured in the Future
@Async
public CompletableFuture<Result> processEvent(Event event) {
    throw new RuntimeException("Processing failed");
    // Caller can catch via future.exceptionally() or future.get() throws ExecutionException
}

// Custom exception handler
@Component
public class GlobalAsyncExceptionHandler implements AsyncUncaughtExceptionHandler {
    @Override
    public void handleUncaughtException(Throwable ex, Method method, Object... params) {
        log.error("Async exception in {}: {}", method.getName(), ex.getMessage());
        metricsService.incrementCounter("async.errors", 
            Tags.of("method", method.getName(), "exception", ex.getClass().getSimpleName()));
        alertService.sendAlert("Async method failed: " + method.getName());
    }
}

6. Proper Thread Pool Configuration

ThreadPoolTaskExecutor — Core Parameters 
@Bean("orderProcessingExecutor")
public ThreadPoolTaskExecutor orderProcessingExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();

    // Core pool: threads kept alive even when idle
    executor.setCorePoolSize(10);

    // Max pool: upper limit under load (only used when queue is FULL)
    executor.setMaxPoolSize(50);

    // Queue: tasks waiting when all core threads are busy
    // WARNING: Max pool threads are only created AFTER queue is full!
    executor.setQueueCapacity(100);

    // Keep-alive: how long excess threads (above core) survive idle
    executor.setKeepAliveSeconds(60);

    // Allow core threads to timeout (scale down to zero under no load)
    executor.setAllowCoreThreadTimeOut(true);

    // Thread naming for debugging
    executor.setThreadNamePrefix("order-proc-");

    // Rejection policy when both pool and queue are saturated
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());

    // Wait for tasks to complete on shutdown
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(30);

    executor.initialize();
    return executor;
}

Critical insight about queue behavior: Java's ThreadPoolExecutor creates new threads (up to maxPoolSize) only when the queue is FULL. This means with an unbounded queue (LinkedBlockingQueue default), maxPoolSize is never reached!

// Common misconception:
// corePoolSize=10, maxPoolSize=50, queueCapacity=Integer.MAX_VALUE
// Under load: core threads busy → tasks go to queue → queue never fills → max threads NEVER created!

// Correct sizing for responsive scaling:
// corePoolSize=10, maxPoolSize=50, queueCapacity=25

Thread pool sizing depends on the nature of the work:

// CPU-bound tasks (computation, serialization, encryption)

// Formula: threads = numCPUs * targetUtilization * (1 + waitTime/computeTime)
// Example: 8 CPUs, 90% target, wait/compute ratio of 10:1
int ioBoundPoolSize = (int)(8 * 0.9 * (1 + 10));  // = 79 threads

public class MonitoredRejectionHandler implements RejectedExecutionHandler {

    private final String executorName;
    private final AtomicInteger rejectionCount = new AtomicInteger(0);

        log.warn("Task rejected by {} (rejection #{}). Pool: {}/{}, Queue: {}/{}",
            executorName, count,

            executor.getQueue().size(), executor.getQueue().remainingCapacity());

        // Strategy: try a fallback executor or fail fast
        if (executor.isShutdown()) {
            throw new RejectedExecutionException("Executor shut down");
        }

        // Option A: Run on caller's thread (backpressure)
        // r.run();

        // Option B: Fail fast with clear error
        throw new RejectedExecutionException(
            String.format("Async executor '%s' saturated. Active: %d, Queue: %d",
                executorName, executor.getActiveCount(), executor.getQueue().size()));
    }
}

7. Virtual Threads (Java 21) — The Paradigm Shift

How Virtual Threads Solve the Blocking Problem

Virtual Threads decouple the application thread from the OS thread. When a virtual thread blocks on I/O, the JVM unmounts it from the carrier (platform) thread, allowing the carrier to run other virtual threads. This makes blocking cheap.

// Traditional: 200 platform threads = 200 concurrent requests max
// Virtual Threads: 200 platform threads can serve 100,000+ concurrent requests

// Spring Boot 3.2+ — enable virtual threads
// application.yml:
// spring:
//   threads:
//     virtual:
//       enabled: true

// What happens under the hood:
// 1. Tomcat uses virtual threads for request handling
// 2. When code blocks (JDBC, HTTP call), the virtual thread is unmounted
// 3. The carrier thread picks up another virtual thread
// 4. When I/O completes, virtual thread is scheduled back on a carrier

// Memory comparison:
// Platform thread: ~1MB stack (1000 threads = 1GB RAM)
// Virtual thread:  ~1KB initially, grows as needed (1M threads = ~1GB RAM)
// Manual virtual thread usage (Java 21+)
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<OrderResult>> futures = orders.stream()
        .map(order -> executor.submit(() -> processOrder(order)))
        .toList();

    // Each .get() blocks a virtual thread, NOT a platform thread
    List<OrderResult> results = futures.stream()
        .map(f -> {
            try { return f.get(); }
            catch (Exception e) { throw new RuntimeException(e); }
        })
        .toList();
}
Pinning — When Virtual Threads Lose Their Advantage

"Pinning" occurs when a virtual thread cannot be unmounted from its carrier thread, typically due to synchronized blocks or native method frames:

// PROBLEM: synchronized pins the virtual thread to its carrier
public class LegacyConnectionPool {
    private final Object lock = new Object();

    public Connection getConnection() {
        synchronized (lock) {  // PINS the virtual thread!
            // If this blocks waiting for a connection,
            // the carrier thread is also blocked
            return pool.borrowConnection();
        }
    }
}

// SOLUTION: Replace synchronized with ReentrantLock
public class ModernConnectionPool {
    private final ReentrantLock lock = new ReentrantLock();

    public Connection getConnection() {
        lock.lock();  // Virtual thread can unmount while waiting
        try {
            return pool.borrowConnection();
        } finally {
            lock.unlock();
        }
    }
}

Structured Concurrency (JEP 453 — Preview)

Structured concurrency ensures child tasks have a clear lifecycle tied to their parent scope, preventing thread leaks and orphaned operations:

// Java 21+ (Preview feature)
// --enable-preview required

import java.util.concurrent.StructuredTaskScope;

public OrderSummary fetchOrderSummary(String orderId) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        // Fork subtasks — each runs on its own virtual thread
        Subtask<Inventory> inventory = scope.fork(() -> inventoryService.check(orderId));
        Subtask<Pricing> pricing = scope.fork(() -> pricingService.calculate(orderId));
        Subtask<UserProfile> user = scope.fork(() -> userService.getProfile(orderId));

        // Wait for all subtasks to complete (or first failure)
        scope.join();              // Blocks the (virtual) thread — cheap!
        scope.throwIfFailed();     // Propagate exception from any failed subtask

        // All succeeded — compose result
        return new OrderSummary(inventory.get(), pricing.get(), user.get());
    }
    // Scope ensures: if any task fails, others are cancelled
    // No orphaned virtual threads possible
}

// ShutdownOnSuccess — return first successful result, cancel others
public String fetchFromFastestMirror(String url) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
        scope.fork(() -> httpClient.get(mirror1 + url));
        scope.fork(() -> httpClient.get(mirror2 + url));
        scope.fork(() -> httpClient.get(mirror3 + url));

        scope.join();
        return scope.result();  // First successful result
    }
}

When NOT to Use Virtual Threads
  • CPU-bound tasks: Virtual threads don't help with computation — you still need N platform threads for N CPUs. Use a fixed platform thread pool for CPU-intensive work.
  • When you need backpressure: Virtual threads are unlimited — there's no queue to provide backpressure. If downstream services can't handle unlimited concurrency, you need semaphores or bulkheads.
  • Libraries with heavy synchronized usage: If core dependencies pin extensively, you lose the virtual thread advantage.
  • ThreadLocal-intensive code: Virtual threads support ThreadLocal but ScopedValues (Preview) are preferred. Millions of virtual threads with large ThreadLocals = large memory footprint.

        return jdbcTemplate.queryForObject("SELECT ...", mapper, id);
    } finally {
        databasePermits.release();
    }
}

CompletableFuture Composition Patterns 
@Service
public class DashboardService {

    @Autowired private UserClient userClient;
    @Autowired private OrderClient orderClient;
    @Autowired private RecommendationClient recClient;
    @Autowired @Qualifier("ioExecutor") private Executor ioExecutor;

    // Pattern 1: Parallel independent calls
    public CompletableFuture<Dashboard> buildDashboard(String userId) {
        CompletableFuture<UserProfile> profileFuture =
            CompletableFuture.supplyAsync(() -> userClient.getProfile(userId), ioExecutor);

        CompletableFuture<List<Order>> ordersFuture =
            CompletableFuture.supplyAsync(() -> orderClient.getRecent(userId, 10), ioExecutor);

        CompletableFuture<List<Product>> recsFuture =
            CompletableFuture.supplyAsync(() -> recClient.getRecommendations(userId), ioExecutor);

        return CompletableFuture.allOf(profileFuture, ordersFuture, recsFuture)
            .thenApply(v -> new Dashboard(
                profileFuture.join(),
                ordersFuture.join(),
                recsFuture.join()
            ));
    }

    // Pattern 2: Sequential dependent calls with error handling
    public CompletableFuture<EnrichedOrder> enrichOrder(String orderId) {
        return CompletableFuture.supplyAsync(() -> orderClient.getOrder(orderId), ioExecutor)
            .thenCompose(order ->
                CompletableFuture.supplyAsync(() -> userClient.getProfile(order.getUserId()), ioExecutor)
                    .thenApply(profile -> new EnrichedOrder(order, profile))
            )
            .thenCompose(enriched ->
                CompletableFuture.supplyAsync(
                    () -> recClient.getSimilar(enriched.getOrder().getProductId()), ioExecutor)
                    .thenApply(enriched::withRecommendations)
            )
            .exceptionally(ex -> {
                log.error("Failed to enrich order {}: {}", orderId, ex.getMessage());
                return EnrichedOrder.partial(orderId, ex.getMessage());
            });
    }

    // Pattern 3: Timeout with fallback
    public CompletableFuture<List<Product>> getRecommendationsWithFallback(String userId) {
        return CompletableFuture.supplyAsync(() -> recClient.getRecommendations(userId), ioExecutor)
            .orTimeout(2, TimeUnit.SECONDS)
            .exceptionally(ex -> {
                if (ex.getCause() instanceof TimeoutException) {
                    log.warn("Recommendations timed out for user {}, returning defaults", userId);
                    return recClient.getDefaultRecommendations();
                }
                throw new CompletionException(ex);
            });
    }

    // Pattern 4: First successful result (racing)
    public CompletableFuture<PriceQuote> getBestPrice(String productId) {
        CompletableFuture<PriceQuote> supplier1 =
            CompletableFuture.supplyAsync(() -> priceClient.getQuote("supplier-a", productId), ioExecutor);
        CompletableFuture<PriceQuote> supplier2 =
            CompletableFuture.supplyAsync(() -> priceClient.getQuote("supplier-b", productId), ioExecutor);
        CompletableFuture<PriceQuote> supplier3 =
            CompletableFuture.supplyAsync(() -> priceClient.getQuote("supplier-c", productId), ioExecutor);

        return CompletableFuture.anyOf(supplier1, supplier2, supplier3)
            .thenApply(result -> (PriceQuote) result);
    }
}

@Service
public class VirtualThreadOrderService {

    @Autowired private OrderRepository orderRepository;
    @Autowired private RestClient userClient;
    @Autowired private RestClient shipmentClient;

    public OrderDetails getOrderDetails(String orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();

        // Parallel execution via structured concurrency
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            var userTask = scope.fork(() -> userClient.get()
                .uri("/users/{id}", order.getUserId())
                .retrieve()
                .body(UserProfile.class));

            var shipmentsTask = scope.fork(() -> shipmentClient.get()
                .uri("/shipments/order/{id}", orderId)
                .retrieve()
                .body(new ParameterizedTypeReference<List<ShipmentStatus>>() {}));

            scope.join();
            scope.throwIfFailed();

            return new OrderDetails(order, userTask.get(), shipmentsTask.get());
        } catch (Exception e) {
            throw new RuntimeException("Failed to build order details", e);
        }
    }
}
MDC Context Propagation with @Async 
// Problem: MDC (Mapped Diagnostic Context) is ThreadLocal-based
// When @Async switches threads, MDC context is lost!

// Solution: Custom TaskDecorator that copies MDC context
public class MdcTaskDecorator implements TaskDecorator {

    @Override
    public Runnable decorate(Runnable runnable) {
        // Capture MDC from the calling thread
        Map<String, String> contextMap = MDC.getCopyOfContextMap();

        return () -> {
            try {
                // Set MDC on the async thread
                if (contextMap != null) {
                    MDC.setContextMap(contextMap);
                }
                runnable.run();
            } finally {
                MDC.clear();  // Clean up after execution
            }
        };
    }
}

13. Follow-Up Questions

Questions the interviewer might ask next
  1. "How would you size a thread pool for a service that makes downstream HTTP calls averaging 200ms?"

    Apply Little's Law: threads = throughput × latency. If target is 1000 req/s with 200ms calls: threads = 1000 × 0.2 = 200 threads. Add 20% headroom → 240 max threads. Consider connection pool limits of downstream services.

  2. "What happens to @Async methods during a graceful shutdown?"

    Without configuration, tasks may be interrupted mid-execution. Set setWaitForTasksToCompleteOnShutdown(true) and setAwaitTerminationSeconds(N). Spring Boot's graceful shutdown period should exceed this value.

  3. "How do you propagate security context to @Async threads?"

    Spring Security's SecurityContext is ThreadLocal. Configure SecurityContextHolder.setStrategyName(MODE_INHERITABLETHREADLOCAL) or use a DelegatingSecurityContextExecutor / custom TaskDecorator.

  4. "If you have a WebFlux application and one endpoint needs JDBC, what do you do?"

    Three options: (1) Use R2DBC for reactive DB access, (2) Wrap JDBC calls in Mono.fromCallable().subscribeOn(Schedulers.boundedElastic()), (3) Consider if that endpoint should be in a separate MVC service.

  5. "How would you implement a rate limiter for @Async tasks without blocking the caller?"

    Use a Semaphore within the async method (acquires on async thread, not caller). Or implement a custom executor wrapper that uses a token bucket. With virtual threads, Semaphore.acquire() is cheap — the virtual thread unmounts while waiting.

  6. "What's the difference between @Async and @Scheduled for background processing?"

    @Async is triggered by method invocation — fire-and-forget from caller. @Scheduled is timer-driven — runs at fixed intervals regardless of invocation. Both use thread pools and have the same proxy/self-invocation issues.

  7. "How do virtual threads interact with connection pools (HikariCP)?"

    Connection pools become the bottleneck. 10,000 virtual threads all wanting a DB connection will queue at HikariCP (typically 10-50 connections). The virtual threads unmount while waiting for a connection, so carriers aren't wasted. But you need to limit effective concurrency via Semaphore or pool sizing.

  8. "Can you use @Transactional with @Async?"

    Yes, but the transaction runs on the async thread, NOT the caller's thread. The caller's transaction context is not propagated. If the @Async method needs its own transaction, annotate it with @Transactional. Ordering: @Async applies first (submits to pool), then @Transactional begins on the pool thread.

  9. "How would you test that @Async is actually running asynchronously?"

    Use a CountDownLatch or awaitility to verify concurrent execution. Assert that the executing thread name matches the expected executor prefix. Use a SlowService stub that takes N seconds and verify the caller returns before N seconds.

  10. "What's the impact of virtual threads on thread-local caches?"

    Thread-local caches (common in serialization, date formatting) become ineffective because millions of virtual threads each get their own copy. Migration path: use ScopedValues (Preview) or instance caches with object pooling.

14. Summary

Key Takeaways
  • @Async ≠ non-blocking. It offloads work to another thread. If that thread pool saturates or the caller blocks for the result, the request still blocks from the client's perspective.
  • Self-invocation is the #1 issue. Same-class calls bypass the proxy — the method runs synchronously. This catches even experienced developers.
  • Always define a bounded executor. The default SimpleAsyncTaskExecutor creates threads without limits. Under load, this leads to OOM.
  • Never call .get() on the HTTP thread. Return CompletableFuture from the controller, or use DeferredResult/WebAsyncTask for true non-blocking HTTP responses.
  • Reactive ≠ always better. WebFlux offers true non-blocking I/O but demands the entire stack be non-blocking. One JDBC call breaks the contract.
  • Virtual Threads change the calculus. With Java 21+, blocking becomes cheap. You can write simple synchronous code and achieve reactive-level throughput. Watch for pinning.
  • Monitor your async pools. Expose thread pool metrics via Micrometer/Prometheus. Alert on utilization > 80% and queue growth.
  • Separate pools for separate workloads. Bulkheading prevents one slow downstream from exhausting threads needed for other operations.
One-Liner for the Interview

"@Async requests still block because the proxy was bypassed (self-invocation), the pool is saturated (CallerRunsPolicy kicks in), the caller blocks on .get(), or you're mixing blocking I/O into a reactive pipeline. The fix is proper pool configuration, correct proxy usage, and — on Java 21+ — virtual threads that make blocking cheap."
